Finding 1: withdrawFees lets feeRecipient bypass the documented 40/40/20 revenue split entirely

Severity: Medium
Confidence: 95
Origin: [both] — independently raised as a FINDING by 9 of 12 Phase-2 agents (math-precision, access-control, economic-security, periphery, invariant, trust-gap, numerical-gap, and corroborated by execution-trace/asymmetry as related) and by the Phase-1 ethskills general/defi-staking passes.
Location: withdrawFees() L186-193, distributeRevenue() L121-149, accruedFees mapping L46

Description: All accrued USDC — regardless of whether it is "fresh" (pending the 40/40/20 split) or "already reserved" (the 20% the NatSpec at L117-120 calls "feeRecipient-withdrawable") — lives in the same accruedFees[address(usdc)] slot. withdrawFees has no notion of this distinction:

function withdrawFees(address token, address to) external {
    require(msg.sender == feeRecipient, "Treasury: not recipient");
    require(to != address(0), "Treasury: zero to");
    uint256 amount = accruedFees[token];     // L189 — entire slot, not just the reserve
    require(amount > 0, "Treasury: nothing to withdraw");
    accruedFees[token] = 0;
    IERC20(token).safeTransfer(to, amount);  // L192
}

feeRecipient can call this at any time — no cooldown, no dependency on distributeRevenue having run, no check against stakingVault/buybackExecutor even being wired — and sweep 100% of accrued USDC instead of the documented 20%. A second, related manifestation of the same root cause: even when distributeRevenue() is allowed to run first, the 20% it retains (accruedFees[address(usdc)] = reserved;, L138) is written back into the identical slot that the next epoch's distributeRevenue() reads as its distribution base (L130), so any un-withdrawn reserve is re-split 40/40/20 on every subsequent call — decaying toward zero rather than staying fixed, contrary to the NatSpec.

Proof of Concept: Assume a week of recordAccessFee/collectAzlAccessFee calls accrues accruedFees[usdc] = 1,000,000,000 (1,000 USDC, 6-decimal). Before anyone calls distributeRevenue(), feeRecipient calls withdrawFees(address(usdc), feeRecipient): amount = 1,000,000,000 (L189), zeroed (L191), transferred in full (L192). stakingVault and buybackExecutor receive 0 instead of their documented 400,000,000 (40%) each. A subsequent distributeRevenue() call reads amount = accruedFees[usdc] = 0 and reverts at L131 ("nothing to distribute"). This can be repeated every epoch indefinitely — feeRecipient faces zero cost or timing constraint to always withdraw first. Decay variant: if distributeRevenue() does run first and leaves reserved = 200,000,000, a second call one epoch later with no new inflow re-splits that 200,000,000 into 80,000,000/80,000,000/40,000,000 — 80% of the "reserve" leaves to stakers/buyback purely from the passage of one more epoch.

Recommendation: Track the reserved/pending-distribution portions in separate storage slots. withdrawFees for USDC should only ever read/zero a dedicated reservedUsdc variable that distributeRevenue populates with the 20% remainder; distributeRevenue's amount should be computed only from fees accrued since the last distribution, not from the full accruedFees[usdc] slot.

uint256 public reservedUsdc;
// in distributeRevenue():
reservedUsdc += reserved;
accruedFees[address(usdc)] = 0; // only fresh accrual lived here
// in withdrawFees(), for the usdc key specifically, read/zero reservedUsdc instead

Finding 2: renounceOwnership (inherited, unoverridden) can permanently brick unset dependencies

Severity: High
Confidence: 90
Origin: [phase1: access-control] — re-examined directly against source in Phase 3 (hybrid re-read), confirmed.
Location: inherited Ownable.renounceOwnership() via Ownable2Step (L12); the five one-shot onlyOwner setters (setAgentDepositVault L81-86, setAzlToken L88-92, setReputationRegistry L94-98, setStakingVault L100-109, setBuybackExecutor L111-115)

Description: TreasuryRouter is Ownable2Step (L12). Ownable2Step overrides only the transfer path (two-step transferOwnership/acceptOwnership); it does not override renounceOwnership(), which remains the vanilla single-step Ownable version — callable by owner at any time, immediately zeroing _owner with no confirmation step. Every one of the five dependency-wiring setters is onlyOwner and one-shot (guarded by an == address(0) check), with no alternate path to set them once ownership is gone. If renounceOwnership() is called before all five have been invoked, whichever remain unset can never be set — permanently disabling distributeRevenue() (needs stakingVault/buybackExecutor), recordNativeSlash() (needs reputationRegistry), the agentDepositVault leg of onlyFeeRecorder, or all AZL fee collection (needs azlToken).

Proof of Concept: Owner deploys TreasuryRouter, calls setAgentDepositVault and setAzlToken only (enough for basic USDC/AZL fee recording to start), then calls the inherited renounceOwnership() before calling setStakingVault/setBuybackExecutor/setReputationRegistry. owner is now address(0). Any subsequent call to those three setters reverts forever with Ownable: caller is not the owner — distributeRevenue() can never be enabled, recordNativeSlash() can never be authorized, permanently, for the life of the contract.

Recommendation: Override renounceOwnership() to revert unconditionally, or gate it on all five dependencies already being set:

function renounceOwnership() public view override onlyOwner {
    revert("Treasury: renounce disabled");
}

Finding 3: feeRecipient is a fully self-administered single point of failure with no owner-level recovery

Severity: High
Confidence: 90
Origin: [both] — Phase-1 access-control domain as a standalone finding; corroborated structurally by nearly every Phase-2 agent's observation that owner has zero authority over feeRecipient (used as a premise in Findings 1's exploit chain).
Location: proposeFeeRecipient() L205-210, acceptFeeRecipient() L212-218, withdrawFees() L186-193, withdrawNativeFees() L195-203

Description: feeRecipient is set once in the constructor (L74) and thereafter rotated exclusively via its own propose/accept two-step (msg.sender == feeRecipient at L206, msg.sender == pendingFeeRecipient at L213) — owner has no path anywhere in the contract that touches feeRecipient or pendingFeeRecipient. This creates two unmitigated failure modes: (a) key loss — if the feeRecipient address (EOA or contract) can no longer call proposeFeeRecipient, every token in accruedFees and all of accruedNative becomes permanently unwithdrawable, with no owner override, timelock, or fallback anywhere in the contract; (b) key compromise — an attacker holding the feeRecipient key can call withdrawFees/withdrawNativeFees immediately, in a single transaction, for the full accrued balance of any token, with no timelock or pause to react.

Proof of Concept: (a) The EOA holding feeRecipient loses its key. accruedFees/accruedNative continue to accumulate from ongoing protocol operation but can never be withdrawn by anyone, forever — there is no function in the contract, callable by owner or anyone else, that can reach these balances except through feeRecipient. (b) An attacker who obtains the feeRecipient private key calls withdrawFees(usdc, attacker) then withdrawFees(azlToken, attacker) then withdrawNativeFees(attacker) in immediate succession — no on-chain mechanism exists to pause or intercept this.

Recommendation: Give owner (or a separate guardian/multisig) an emergency override to force-set feeRecipient, ideally behind a timelock so the override itself can't be abused, and/or add a delay between proposeFeeRecipient and acceptFeeRecipient so a compromise is visible before it takes effect.

Finding 4: recordAccessFee accrues arbitrary amounts with no matching transfer or balance reconciliation

Severity: Medium (permanent-DoS impact if triggered)
Confidence: 85
Origin: [both] — raised independently in Phase 1 by general/erc20/access-control domains (5 separate write-ups converging on the same root cause), and promoted to a fully-proven FINDING by Phase-2 agent-8 (asymmetry) with concrete numeric proof; corroborated as a LEAD by 7 other Phase-2 agents.
Location: recordAccessFee()/_recordAccessFee() L161-178, consumed by withdrawFees() L186-193 and distributeRevenue() L121-149

Description: recordAccessFee is onlyFeeRecorder-gated (taskRegistry or agentDepositVault only) but is pure bookkeeping:

function _recordAccessFee(address token, uint256 amount, AccessFeeKind kind, address payer) internal {
    accruedFees[token] += amount;   // L176 — no corresponding transfer, ever
    emit AccessFeeCollected(kind, payer, token, amount);
}

Unlike collectAzlAccessFee (which pulls tokens via safeTransferFrom at L153 before recording), recordAccessFee credits an arbitrary caller-supplied amount with zero token movement and zero reconciliation against IERC20(token).balanceOf(address(this)) anywhere in the contract. If the trusted recorder ever records more than the contract actually holds — bug, double-fire, or compromise in the out-of-scope taskRegistry/agentDepositVault — accruedFees[token] becomes permanently overstated. Both withdrawFees and distributeRevenue always attempt to move the entire recorded amount, so the safeTransfer reverts on insufficient balance; because the revert unwinds the whole transaction (including the zeroing at L191 or the write at L138), the ledger can never self-correct. This permanently freezes withdrawal/distribution of that token, including the genuinely-backed portion sitting alongside the phantom excess.

Proof of Concept: Contract legitimately holds 100,000,000 raw USDC units and accruedFees[usdc] == 100,000,000. A single erroneous recordAccessFee(address(usdc), 1_000_000_000_000, AccessFeeKind.DISMISS_SEARCH, payer) call from the trusted recorder bumps accruedFees[usdc] to 1,000,100,000,000 while the real balance stays 100,000,000. withdrawFees(usdc, to) now sets accruedFees[usdc]=0 (L191) and calls usdc.safeTransfer(to, 1,000,100,000,000) (L192) → reverts (insufficient balance) → the whole transaction, including the zeroing, rolls back → accruedFees[usdc] is right back at 1,000,100,000,000. distributeRevenue() reads the same poisoned value and hits the identical revert at its own safeTransfer calls (L141/L145). There is no function anywhere in the contract that can decrement accruedFees[token] other than these two, both of which now permanently revert — the real 100,000,000 USDC (and any further legitimate accrual on top) is frozen indefinitely, until a third party voluntarily donates enough raw balance to cover the gap.

Recommendation: Cap withdrawal/distribution amounts at min(accruedFees[token], IERC20(token).balanceOf(address(this))), or require recordAccessFee to be paired with an actual balance-delta check, mirroring collectAzlAccessFee's pull-then-record pattern.

Finding 5: Exit-compensation split (EXIT_PARTY_COMP/EXIT_PROTOCOL_SHARE/ExitCompensationPaid) is dead code

Severity: Medium
Confidence: 90
Origin: [both] — one of the most heavily corroborated findings in this audit: raised in Phase 1 (general domain, all 3 runs) and independently derived as a FINDING or LEAD by 10 of 12 Phase-2 agents.
Location: constants EXIT_PARTY_COMP/EXIT_PROTOCOL_SHARE L27-28, event ExitCompensationPaid L56, constructor invariant L75-78, AccessFeeKind.DISMISS_SEARCH/WORKER_LEAVE L42-43, _recordAccessFee() L170-178

Description: The constructor asserts EXIT_PARTY_COMP + EXIT_PROTOCOL_SHARE == ACCESS_FEE (L76 inside the require spanning L75-78), and the enum members DISMISS_SEARCH/WORKER_LEAVE strongly imply a compensated counterparty on exit — but _recordAccessFee treats every AccessFeeKind identically:

function _recordAccessFee(address token, uint256 amount, AccessFeeKind kind, address payer) internal {
    accruedFees[token] += amount;                          // L176 — full amount, no kind branch
    emit AccessFeeCollected(kind, payer, token, amount);    // L177 — kind is a passthrough event field only
}

ExitCompensationPaid is never emitted anywhere in the file, and EXIT_PARTY_COMP/EXIT_PROTOCOL_SHARE are never read outside the one-time constructor check. There is no function anywhere in TreasuryRouter — for any AccessFeeKind, including the exit-flavored ones — that pays a compensation share to a distinct counterparty; the entire fee lands in the same accruedFees[token] bucket only feeRecipient can withdraw.

Proof of Concept: taskRegistry calls recordAccessFee(usdcAddr, 5_000_000, AccessFeeKind.WORKER_LEAVE, workerAddr). The full 5,000,000 (5 USDC at 6-decimals) accrues to accruedFees[usdcAddr] at L176; workerAddr — the implied beneficiary of EXIT_PARTY_COMP — receives nothing from this contract, ever, under any call sequence. feeRecipient can later sweep the entire amount via withdrawFees.

Recommendation: Either implement the missing split/payout (accept a distinct recipient parameter for exit-kind records, transfer EXIT_PARTY_COMP to them, emit ExitCompensationPaid, and credit only EXIT_PROTOCOL_SHARE to accruedFees), or — if the split is genuinely handled entirely by the out-of-scope AgentDepositVault before it calls recordAccessFee with only the protocol's share — remove the unused constants/event from TreasuryRouter and document that explicitly, so the code doesn't imply an enforcement it doesn't provide.

Finding 6: setAgentDepositVault trusts an unvalidated external return value for usdc

Severity: Medium
Confidence: 80
Origin: [both] — Phase-1 general/access-control domains flagged this (with a severity split between High and Low across runs, reconciled here to Medium); independently promoted to a fully-proven FINDING by 2 Phase-2 agents (execution-trace, first-principles) with concrete numeric traces, and raised as a LEAD by 3 more.
Location: setAgentDepositVault() L81-86, specifically L85; consumed by setStakingVault() L100-109 and distributeRevenue() L121-149

Description:

function setAgentDepositVault(address _vault) external onlyOwner {
    require(agentDepositVault == address(0), "Treasury: vault set");
    require(_vault != address(0), "Treasury: zero");
    agentDepositVault = _vault;
    usdc = IERC20(AgentDepositVault(_vault).usdcToken());   // L85 — no zero-check on the return
}

The one-shot lock is keyed on agentDepositVault == address(0) (L82), not on usdc being valid, and there is no re-point path for either variable once agentDepositVault is set. If AgentDepositVault(_vault).usdcToken() ever returns address(0) — a plausible deploy-ordering mistake (wiring the router before the vault's own USDC token is configured) or a genuinely misbehaving/uninitialized vault — usdc is permanently stuck at address(0). setStakingVault requires address(usdc) != address(0) (L104), so the entire staking-vault wiring — and with it, distributeRevenue()'s require(address(stakingVault) != address(0)) gate (L122) — becomes permanently unreachable.

Proof of Concept: Owner deploys AgentDepositVault and calls setAgentDepositVault(vaultAddr) before the vault's own USDC-token configuration step runs; usdcToken() returns address(0) at that moment. usdc locks to address(0) forever (no re-point path exists). Any subsequent setStakingVault(...) call reverts permanently at L104 ("Treasury: usdc not set"); distributeRevenue() can never be enabled for the life of the contract. (Fees recorded via recordAccessFee against the real USDC token address remain withdrawable through withdrawFees, since that function takes an explicit token parameter independent of the usdc state variable — so this bug disables the staking-distribution subsystem specifically, not all USDC fund access.)

Recommendation: Validate the external return before committing to state:

address _usdc = AgentDepositVault(_vault).usdcToken();
require(_usdc != address(0), "Treasury: vault usdc unset");
agentDepositVault = _vault;
usdc = IERC20(_usdc);

Finding 7: One-shot setters give owner permanent, un-timelocked control over revenue destinations

Severity: Medium
Confidence: 85
Origin: [phase1: access-control] — re-examined against source in Phase 3, confirmed.
Location: setStakingVault() L100-109, setBuybackExecutor() L111-115, setAgentDepositVault() L81-86, setReputationRegistry() L94-98

Description: stakingVault and buybackExecutor are the sole destinations for 80% of every weekly USDC revenue split (distributeRevenue() L133-146), and are set exactly once, instantly, by owner, with no timelock and no re-point mechanism (each guarded only by an == address(0) one-shot check). If owner sets any of these to an incorrect, deprecated, or self-dealt address — by mistake or malice — the protocol has no on-chain way to correct it: every future distributeRevenue() call permanently routes 40%/40% of accrued USDC to that address.

Proof of Concept: owner calls setBuybackExecutor(ownerControlledEOA) and setStakingVault(vaultOwnerAlsoControls). From that point on, the fully permissionless distributeRevenue() routes 80% of all accrued USDC fees to owner-controlled destinations every 7-day epoch, with no governance mechanism, staker vote, or other party able to intervene or redirect.

Recommendation: Add a timelock before these setters take effect (even a short one), and/or a governance-gated re-point path, rather than instant, permanent, single-key control over revenue routing.

Finding 8: distributeRevenue fully couples buyback distribution to UnionStakingVault health

Severity: Medium
Confidence: 80
Origin: [both] — Phase-1 defi-staking domain; corroborated by Phase-2 agent-10 (numerical-gap) identifying the specific coupling of an unrelated invariant to a shared boundary condition.
Location: distributeRevenue() L121-149, precondition L128, external call L142

Description: require(stakingVault.totalStaked() > 0, ...) (L128) gates the entire function — including the buyback transfer (L145), which has no logical dependency on staking activity — and stakingVault.notifyReward(stakerShare) (L142) has no try/catch. Since stakingVault is wired via a one-shot setter with no re-point path (Finding 7), there is no owner recovery if the vault ever has zero stakers (pre-launch, or all stakers exiting) or if notifyReward reverts for any reason (paused, buggy, migrated). In either case the whole transaction reverts, blocking the unrelated buyback leg and the epoch-timer advance right alongside the staking leg. Meanwhile feeRecipient can still sweep 100% of accruedFees[usdc] via withdrawFees regardless (Finding 1), so stakers/buyback can end up permanently at 0% while feeRecipient retains full discretion.

Proof of Concept: UnionStakingVault is deployed and wired via setStakingVault, but no user has staked yet (totalStaked() == 0). Once 7 days elapse and accruedFees[usdc] > 0, any call to distributeRevenue() reverts at L128 every time — the buyback share never reaches buybackExecutor and lastDistributionAt never advances, even though the buyback leg has nothing to do with staking.

Recommendation: Decouple the buyback/reserve legs from the staking-notification leg — e.g. wrap notifyReward in try/catch and re-accrue stakerShare on failure instead of reverting the whole function, or split distribution into independently-callable legs so a staking-side failure cannot block the buyback leg or the epoch-timer advance.

Finding 9: collectAzlAccessFee / setAzlToken — nominal accrual with no fee-on-transfer check, no decimals validation

Severity: Low
Confidence: 75
Origin: [both] — Phase-1 general/erc20/precision-math domains; corroborated as a LEAD by 6 Phase-2 agents.
Location: _collectAzlAccessFee()/collectAzlAccessFee() L151-159, setAzlToken() L88-92, AZL_ACCESS_FEE L26

Description: _collectAzlAccessFee pulls AZL_ACCESS_FEE (1000e18 — hardcodes an 18-decimal assumption) via safeTransferFrom (L153) then unconditionally credits the constant AZL_ACCESS_FEE to accruedFees[azlToken] (L158→176), never measuring balanceOf before/after. setAzlToken is a one-shot owner setter with no decimals() check. If azlToken (once wired, permanently) applies a transfer fee, rebases, or has non-18 decimals, actual custody diverges from recorded accrual with no way to detect or correct it — compounding Finding 4's inability to reconcile.

Proof of Concept: A 2%-fee-on-transfer AZL variant delivers 980e18 of a nominal 1000e18 pull; accruedFees[azlToken] still credits the full 1000e18. Divergence compounds over repeated calls until a withdrawFees(azlToken, ...) call reverts on insufficient balance. Separately, wiring a 6-decimal token via setAzlToken makes every collectAzlAccessFee call attempt to pull 1000e18 raw units (1e15 whole tokens) — an amount no realistic payer holds or approves — permanently breaking AZL fee collection with no re-point path.

Recommendation: Measure balanceOf(this) before/after the safeTransferFrom and record the actual delta; validate IERC20Metadata(token).decimals() == 18 in setAzlToken before locking it in.

Finding 10: Dust-triggered distributeRevenue() resets the 7-day cooldown for near-zero payout

Severity: Low
Confidence: 75
Origin: [both] — Phase-1 general domain; corroborated as a LEAD by Phase-2 agents 7 and 10 (first-principles, numerical-gap).
Location: distributeRevenue() L121-149

Description: The function is permissionless and gated only by amount > 0 (L131). When accruedFees[usdc] is small enough that (amount * 4000) / 10000 truncates to 0 for both stakerShare and buybackShare (e.g. amount ∈ {1, 2} raw units), both transfer blocks are skipped via their if (... > 0) guards (L140, L144), yet lastDistributionAt still unconditionally advances (L137) — consuming the full 7-day epoch for a near-zero distribution.

Proof of Concept: Anyone calls distributeRevenue() the instant accruedFees[usdc] becomes a dust value (e.g. 1-2 raw units, which can occur as leftover reserve dust per Finding 1's decay mechanism). stakerShare/buybackShare truncate to 0, no transfer occurs, but lastDistributionAt = block.timestamp still executes — delaying the next meaningful distribution by a further full epoch.

Recommendation: Consider a minimum-amount threshold before allowing lastDistributionAt to advance.

Finding 11: No sweep/rescue path for tokens or ETH landing outside the tracked accrual channels

Severity: Low
Confidence: 80
Origin: [phase1: general] — re-examined against source in Phase 3, confirmed; also present as a code-smell observation in several Phase-2 agents' notes.
Location: whole contract; withdrawFees() L186-193, withdrawNativeFees() L195-203

Description: Both withdrawal functions move only the internal counters (accruedFees[token], accruedNative), never balanceOf(address(this))/address(this).balance. Direct token transfers, airdrops, or force-fed ETH (selfdestruct, coinbase reward, pre-computed CREATE2 address) are invisible to the counters and permanently unrecoverable — no rescue function exists anywhere in the contract.

Recommendation: Add an owner/feeRecipient-gated sweep of balanceOf(this) - accruedFees[token] (and the ETH equivalent), or explicitly document this as accepted behavior.

Finding 12: withdrawFees/withdrawNativeFees do not guard to against system addresses

Finding 13: collectAzlAccessFee lets the trusted recorder pull from an arbitrary payer with no cap

Severity: Low
Confidence: 75
Origin: [phase1: access-control] — re-examined against source in Phase 3, confirmed.
Location: collectAzlAccessFee() L156-159

Description: collectAzlAccessFee(payer, kind) is callable only by onlyFeeRecorder (taskRegistry/agentDepositVault), but acts on an arbitrary payer rather than msg.sender, with no per-payer/per-kind cap or replay guard in TreasuryRouter itself — the only limit is the payer's standing ERC20 allowance. A bug or compromise in the trusted recorder could call this repeatedly for the same payer, draining their full approved allowance well beyond any single legitimate action.

Recommendation: Consider a per-action identifier/replay-guard, or a rate/amount cap per payer, as defense-in-depth against a compromised recorder.

Severity: Info

Finding 15: PUSH0 opcode compatibility unconfirmed for target chain

Severity: Info
Confidence: 60
Origin: [phase1: general]
Location: pragma solidity ^0.8.24; L2

Description: Solidity ≥0.8.20 emits PUSH0 by default; several L2s/alt-chains have historically lacked support at various points. Deployment-configuration concern only.

Recommendation: Confirm the target chain supports PUSH0, or pin evmVersion in compiler settings.

Leads (plausible, not independently confirmed — confidence < 50)

  • JIT-stake reward sniping around distributeRevenue/notifyReward. Raised independently by 7 of 12 Phase-2 agents and Phase-1's defi-staking domain. distributeRevenue() is permissionless with a fully public, deterministic trigger time and amount, and gates staker eligibility only on a point-in-time totalStaked() > 0 check (L128) with no minimum-duration/snapshot requirement. An actor could stake immediately before, and unstake immediately after, a distributeRevenue() call to capture a disproportionate reward share — but whether this is actually exploitable depends entirely on UnionStakingVault.notifyReward's internal accounting (time-weighted vs. instant pro-rata), which is out of scope for this job. Recommendation: flag explicitly for the UnionStakingVault audit to confirm reward-streaming semantics neutralize this.
  • Token-address collision risk. Nothing in setAzlToken/setAgentDepositVault prevents the owner from wiring azlToken == usdc (or either equal to stakingVault/buybackExecutor/feeRecipient), which would merge USDC- and AZL-denominated accrual into a single accruedFees slot and corrupt distributeRevenue's math. Requires a specific owner misconfiguration; not independently exploitable by a third party.
  • Cross-contract amount/decimal mismatch between ACCESS_FEE/EXIT_PARTY_COMP/EXIT_PROTOCOL_SHARE and whatever the out-of-scope AgentDepositVault actually passes to recordAccessFee. These constants are asserted consistent with each other at construction (L75-78) but never validated against any runtime-supplied amount. Cannot be confirmed without AgentDepositVault's source.
