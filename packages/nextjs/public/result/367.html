🔐 Security Review — VaultfireBatchOnboarder

Target: VaultfireBatchOnboarder at 0x82c6a0dd34F5cF57F8B98Ee118e911B977618890 on Base (chain 8453)
Source: verified via Sourcify (exact match), src/VaultfireBatchOnboarder.sol
Methodology: Two-phase audit — Phase 1 breadth (5 ethskills checklist agents: general, precision-math, access-control, erc4337, dos) → Phase 2 depth (12 pashov attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation.

Scope note

The job brief asked us to focus on "per-entry authorization inside the batch (a batched entry shouldn't be able to escalate privilege), gas-griefing, and partial-failure atomicity" for a "batch onboarding entry point." On inspection, the deployed contract contains no batch, loop, or array logic of any kind — VaultfireBatchOnboarder exposes exactly one external function, onboardAndBond, handling a single agent/bond pair per call. This was independently confirmed by 2 of 17 total agents across both phases. We audited the contract as deployed; the closest analog to "per-entry privilege escalation" turned out to be the entrypoint itself having no caller authorization at all (Finding 1, below), which both phases converged on independently and near-unanimously.

For exploitability context, we also read (but did not exhaustively audit) the two contracts onboardAndBond calls into: ERC8004IdentityRegistry (0xa7BD20bf5De63df949cA5Be2F20835978eCba81A) and AIPartnershipBondsV2 (0x01C479F0c039fEC40c0Cf1c5C921bab457d57441), both verified on Base via Sourcify. Findings below are scoped to VaultfireBatchOnboarder; the two dependency contracts were read only as needed to confirm/refute exploitability.

Findings

[1] Missing caller authorization on onboardAndBond — any third party can permanently squat a delegated EOA's identity and force unwanted bonds

Severity: High
Confidence: 95 — independently reproduced by 15 of 17 total agents across both phases, with a fully concrete, source-verified exploit chain
Location: onboardAndBond() · VaultfireBatchOnboarder.sol:202-245
Origin: [both] — Phase 1 (general, access-control, erc4337, dos) + Phase 2 (access-control, economic-security, execution-trace, invariant, periphery, first-principles, asymmetry, boundary, numerical-gap, trust-gap, flow-gap)

Description: onboardAndBond is external with no access control whatsoever — no msg.sender == address(this) self-call check, no signature or nonce binding the call's parameters to the delegated EOA owner's consent. Under EIP-7702, once an EOA delegates to this contract, address(this) inside the function is always the delegated EOA, but msg.sender is simply whoever sends the top-level transaction — which the contract's own design doc explicitly welcomes being "anyone" (principle 5: "NO RELAYER DEPENDENCY... Anyone can submit a 7702 transaction with a user's authorization. We require nothing else."). Because delegation is persistent (principle 1) and publicly visible on-chain, and because the contract conflates "permissionless gas sponsorship of a pre-signed transaction" with "no validation of call parameters," any third party can call onboardAndBond directly on a previously-delegated EOA at any time, supplying entirely attacker-chosen agentURI, agentType, capabilitiesHash, aiAgent, and partnershipType, funded by only MIN_STAKE_WEI = 1 wei of the attacker's own money.

Both downstream calls attribute their effects to the victim regardless of who calls: IDENTITY_REGISTRY.registerAgent(...) and PARTNERSHIP_BONDS.createBond{value: msg.value}(...) both see msg.sender == address(this) == victim EOA. Critically, ERC8004IdentityRegistry.registerAgent() is a one-time, permanent operation (require(!agents[msg.sender].isRegistered, "Agent already registered"), ERC8004IdentityRegistry.sol:84, with no reset/unregister path and no way to later change agentType/capabilitiesHash). Since registerAgent runs before createBond and any revert unwinds the whole transaction, whoever's call lands first permanently wins the identity slot.

Proof of Concept:

  1. Victim V signs an EIP-7702 authorization delegating their EOA to VaultfireBatchOnboarder (chain 8453), intending to call onboardAndBond with real data — either bundled in the same transaction or as a follow-up, per the contract's own recommended flow. Delegation, once mined, is persistent until V explicitly revokes it — most users won't revoke immediately.
  2. Attacker A observes the delegation on-chain (or, in the bundled-tx case, extracts V's already-broadcast authorization tuple from the mempool and reuses it in their own competing transaction with higher priority fee — EIP-7702 authorization tuples only prove "delegate to this address," never bind to any specific future calldata). A submits: to = V, data = onboardAndBond("ipfs://spam", "spam", 0x00.., A2, "junk") (A2 a second attacker-controlled address to trivially clear the aiAgent != msg.sender guard), value = 1 wei.
  3. Inside execution: address(this) == V, msg.sender == A. All local checks pass. IDENTITY_REGISTRY.registerAgent(...) executes with msg.sender == V, permanently setting agents[V].isRegistered = true with A's garbage metadata. PARTNERSHIP_BONDS.createBond{value:1}(A2, "junk") creates a permanent bond with human == V, aiAgent == A2, funded entirely by A's 1 wei.
  4. V's own subsequent transaction reverts forever at the registerAgent step ("Agent already registered"). V can never successfully call onboardAndBond again. V's on-chain identity metadata (agentType, capabilitiesHash) is permanently attacker-controlled garbage, and V is permanently listed as the human party in an unwanted bond with an attacker-chosen aiAgent.

No direct loss of the victim's pre-existing funds occurs (the attacker stakes only their own wei) — the impact is a permanent, irreversible denial of the contract's core purpose plus permanent corruption of the victim's on-chain identity/bond records. Rated High per standard severity convention ("permanent DoS," not direct fund loss, hence not Critical).

Fix (Option A — self-call restriction, simplest):

 function onboardAndBond(
     string calldata agentURI,
     string calldata agentType,
     bytes32 capabilitiesHash,
     address aiAgent,
     string calldata partnershipType
 ) external payable returns (uint256 bondId) {
+    require(msg.sender == address(this), "only self-initiated calls");
     if (block.chainid != BASE_CHAIN_ID) {
         revert WrongChain(BASE_CHAIN_ID, block.chainid);
     }

Trade-off: preserves the intended self-call flow but sacrifices the contract's advertised "no relayer dependency" design goal — a gas-sponsoring relayer could no longer submit calldata on the EOA's behalf, since a relayer's top-level call always has msg.sender == relayer != address(this).

Fix (Option B — EIP-712 signature, preserves relayer sponsorship):

 function onboardAndBond(
     string calldata agentURI,
     string calldata agentType,
     bytes32 capabilitiesHash,
     address aiAgent,
-    string calldata partnershipType
+    string calldata partnershipType,
+    uint256 deadline,
+    bytes calldata signature
 ) external payable returns (uint256 bondId) {
+    require(block.timestamp <= deadline, "expired");
+    bytes32 digest = keccak256(abi.encode(
+        agentURI, agentType, capabilitiesHash, aiAgent, partnershipType, deadline, block.chainid, address(this)
+    ));
+    require(ECDSA.recover(MessageHashUtils.toEthSignedMessageHash(digest), signature) == address(this), "invalid EOA signature");
     if (block.chainid != BASE_CHAIN_ID) {

This lets any relayer submit the transaction while ensuring only a signature from the EOA's own key can authorize the specific parameters — preserving principle 5 without opening principle 1's "safe in every future invocation context" gap. Note the contract's current "zero storage" design (principle 3) precludes an on-chain nonce; the deadline bound above is the minimal replay mitigation compatible with statelessness, though a determined attacker could still replay the exact same signed payload before deadline if V intended it as one-time-only — if that matters, the "zero storage" principle needs to be revisited to add a nonce/used-flag.

[2] Self-bond guard and OnboardedWithBond event both key off msg.sender instead of address(this)

Severity: Low
Confidence: 90 — confirmed by direct code reading in both phases; downstream impact independently verified as contained
Location: VaultfireBatchOnboarder.sol:225 (SelfBondNotAllowed check), :237-244 (OnboardedWithBond event)
Origin: [both] — Phase 1 (general, access-control, erc4337) + Phase 2 (access-control, execution-trace, numerical-gap, trust-gap, flow-gap, asymmetry)

Description: The contract's own NatSpec claims "Under that delegation, msg.sender IS the delegated EOA" (line 191) — true only when the EOA submits its own transaction, false whenever a relayer or third party calls (a scenario the contract explicitly anticipates per principle 5, and the exact scenario exploited in Finding 1). Two places incorrectly treat msg.sender as if it were the EOA:

  • Line 225: if (aiAgent == msg.sender) revert SelfBondNotAllowed(); — under third-party calls, compares aiAgent against the caller, not the EOA, so it fails to catch a true self-bond (aiAgent == address(this)) and could spuriously reject a legitimate relayed call where aiAgent happens to equal the relayer.
  • Lines 237-244: emit OnboardedWithBond(msg.sender, ...) — the onboardedEoa field, documented as "the EOA being onboarded," is populated with the top-level caller instead of address(this), misattributing the onboarded identity in any relayed call (including the attack in Finding 1) for any off-chain indexer/dashboard consuming this event.

Verified not independently exploitable beyond Finding 1: we confirmed by reading AIPartnershipBondsV2.sol:219-244 that createBond independently re-derives and correctly enforces require(aiAgent != msg.sender) using its own call-frame msg.sender, which correctly resolves to address(this) = the victim EOA regardless of who called onboardAndBond. So the local guard's bug does not itself enable self-bonding — it is a correctness/observability bug, not a second attack path.

Fix:

-        if (aiAgent == msg.sender) revert SelfBondNotAllowed();
+        if (aiAgent == address(this)) revert SelfBondNotAllowed();

         emit OnboardedWithBond(
-            msg.sender,
+            address(this),
             aiAgent,
             bondId,
             msg.value,
             agentType,
             partnershipType
         );

[3] Partial-failure atomicity — confirmed not an issue

Severity: Info
Location: onboardAndBond() · VaultfireBatchOnboarder.sol:228-235
Origin: [phase1: dos]

Directly addressing the client's brief: both external calls (registerAgent, createBond) are plain high-level Solidity calls with no try/catch and no unchecked low-level .call. Any revert in createBond propagates and reverts the entire transaction, rolling back registerAgent's state changes too. There is no scenario where the EOA ends up "half-registered" with no bond. No fix needed.

[4] "BatchOnboarder" naming implies functionality that does not exist

Severity: Info
Location: Contract name; onboardAndBond()
Origin: [phase1: dos]

Confirmed by full read: no loop, array, or batch of entries exists anywhere in this contract — onboardAndBond handles exactly one agent/bond pair per call. This directly affects how the job brief's "per-entry authorization" and "gas-griefing across a batch" questions should be read: there is no batch to escalate within; the real analog is Finding 1 (the single entrypoint itself has no caller authorization). Consider renaming to avoid implying batch semantics, or documenting explicitly that v1 is single-entry only.

Leads investigated and resolved (not promoted to findings)

  • Downstream self-bond enforcement (raised independently in both phases): confirmed via direct read of AIPartnershipBondsV2.sol:219-244 — createBond enforces aiAgent != msg.sender using its own correctly-resolved msg.sender == address(this) == EOA. Closes the gap noted in Finding 2; no independent exploit beyond Finding 1.
  • MIN_STAKE_WEI boundary matching the downstream contract's actual minimum (Phase 2, math-precision agent): confirmed via AIPartnershipBondsV2.sol:220 — _validateNonZero(msg.value, ...) matches MIN_STAKE_WEI = 1's "strictly greater than zero" semantics exactly. No divergence.
  • Trusted address provenance ("Source of truth: theloopbreaker.com/api/contracts" comment; Phase 2 invariant/boundary agents): both hardcoded target addresses independently confirmed via Sourcify to resolve to legitimate, verified ERC8004IdentityRegistry and AIPartnershipBondsV2 contracts on Base mainnet. Documentation smell only, not a code-level bug.
  • Reentrancy surface via IdentityRegistry hooks (Phase 2 invariant agent): ERC8004IdentityRegistry.registerAgent (reviewed in full) is a plain storage-writing function with no external calls or callback hooks. No reentrancy surface exists.
  • No math/precision findings: contract has no division, multiplication, downcasting, or decimal-sensitive logic beyond a single msg.value >= 1 comparison. Confirmed independently by both phases' math-precision agents.
