Findings

[82] 1. INVALID-side dilution lets a losing-side participant convert forfeiture into a risk-free refund, circumventing the protocol's own stated anti-free-option design

Severity: High · OCPVault._deriveOutcome / withdraw · Confidence: 82 · [phase2 only — 2 findings + 1 corroborating lead, independent numeric proofs]

Description
_deriveOutcome() (L169-173) declares YES or NO the winner only if its stake strictly exceeds the sum of the other two sides combined — meaning the INVALID bucket counts against both YES's and NO's majority check simultaneously. A participant already locked to a losing side (one-side lock, L101, prevents switching their own address) can instead stake a second, fresh address into Side.INVALID for just enough to push both YES and NO below strict majority, forcing Outcome.INVALID. Under INVALID, withdraw()'s eligibility check (outcome == Outcome.INVALID, L147) makes every staker eligible for a pro-rata refund of their own principal (denominator = _totalPrincipal, L158-159) — including the manufacturer of the tie and the side that should have forfeited.

This directly circumvents the project's own stated security philosophy. The whitepaper (docs/whitepaper/POC_WHITEPAPER_EN.md §3.2) states: "No withdrawal prevents costless exit; no switching prevents following the visible leader as a free option." The INVALID-dilution mechanic is exactly that free option — escaping a losing position at minimal cost — delivered through a side-channel (a second address staking INVALID) that the one-side lock does not close. This is materially different from, and not covered by, the §3.3 disclosure of "herding, whale influence, and late participation," which addresses who wins a binary side, not a documented cost-free escape hatch from a losing side.

Proof of Concept
YES=1000, NO=900 (staker L holds 500 of the 900). Honest resolution: _deriveOutcome(): 1000 > 1900-1000=900 → true → Outcome.YES; L (NO side) would forfeit their 500 to the YES majority. Attack: a fresh wallet stakes Side.INVALID, 100 before resolutionTime. New totals: YES=1000, NO=900, INVALID=100, total=2000. _deriveOutcome(): 1000 > 2000-1000=1000 → false; 900 > 2000-900=1100 → false → Outcome.INVALID (L172). withdraw() for L: eligible=true (INVALID branch, L147), denominator=_totalPrincipal=2000 (L159), payout = Math.mulDiv(settlementPool, 500, 2000) ≈ 500 (L161) — L recovers the full 500 that honest resolution would have forfeited to YES. The dilution wallet also recovers its 100 in full. Net effect: the legitimate YES majority is stripped of the win the strict-majority rule exists to award them, at zero net cost to whoever manufactured the tie.

Fix

     function _deriveOutcome() private view returns (Outcome) {
         if (_totalStakeBySide[0] > _totalPrincipal - _totalStakeBySide[0]) return Outcome.YES;
         if (_totalStakeBySide[1] > _totalPrincipal - _totalStakeBySide[1]) return Outcome.NO;
         return Outcome.INVALID;
     }

Requires a design decision, not a one-line patch: make the INVALID bucket bear symmetric risk with YES/NO — e.g., stakers who tip an otherwise-decisive majority into INVALID forfeit to the eventual majority the same as a losing side would, rather than receiving a full refund; or require INVALID-side staking to close on an earlier cutoff than YES/NO so a late dilution cannot retroactively erase an already-decided majority.

[65] 2. YES/NO majority capture via last-block staking — disclosed design risk, but deserves stronger in-app disclosure given the severity of impact

Severity: Medium · OCPVault.stake / _deriveOutcome · Confidence: 65 · [both — 5/12 phase-2 agents independently + phase-1 general-1]

Description
stake() (L94-114) has no time buffer before resolutionTime, and _deriveOutcome() (L169-173) is a pure function of instantaneous stake totals. Any address can observe the public running totals and stake into the trailing side in the final block before resolutionTime, deterministically flipping the outcome and capturing the losing side's entire forfeited principal.

This is explicitly disclosed, intended design. The whitepaper's core thesis (§1, §3.1) is "Proof of Commitment" — "the strongest form of credible commitment is the willingness to bear large, verifiable financial risk... capital itself forms consensus" — and §3.3 explicitly states: "Transparency makes the distribution auditable but can create herding, whale influence, and late participation. The protocol accepts these limits instead of hiding them behind extra phases or time-bucket rewards." This is confirmed further by dedicated tests in contracts/test/OCPVault.t.sol asserting this exact behavior.

Why still reported: the disclosure lives in a whitepaper most end-users staking through a UI will never read, and the magnitude — deterministic, total loss of principal for the earlier-committed side — deserves front-and-center, in-app disclosure at the moment of staking, not a whitepaper footnote several sections deep.

Proof of Concept
NO=100 (2 depositors), YES=0. Attacker stakes Side.YES, 101 in the final block before resolutionTime. _deriveOutcome(): 101 > 201-101=100 → true → Outcome.YES. finalize(): settlementPool=201, remainingEligibleClaims = _participantCountBySide[0] = 1 (attacker only). withdraw(): remainingEligibleClaims==1 branch → payout = balanceOf(this) = 201 (L156). Attacker turns 101 into 201 (~99% ROI in one round-trip), and the two honest NO stakers receive eligible=false, payout=0 (L147-149), forfeiting their 100 combined principal entirely.

Fix: No code change required if this is confirmed intended (it clearly is, per the design docs). Require the staking UI/frontend to prominently disclose, at the moment of every stake and again as resolutionTime approaches, that late/large opposing stakes can flip the outcome and forfeit the staker's entire principal. Consider an optional stake-freeze window as a non-breaking parameter for future vaults if the team wants to reduce (not eliminate) last-block sniping.

[70] 3. Stuck final eligible claimant permanently strands their own share plus accumulated dust, with no recovery path

Severity: High · OCPVault.withdraw · Confidence: 70 · [both — 5+ phase-2 agents + phase-1 erc20-1/dos-1]

Description
withdraw()'s remainingEligibleClaims == 1 branch (L154-164) pays the sole remaining eligible claimant the live stakeToken.balanceOf(address(this)) (L156). No function anywhere in either contract sweeps, redirects, or force-releases the vault's residual balance. If that specific address can never successfully call withdraw() — USDC blacklist (a real, disclosed Circle capability), a lost private key, or a contract incapable of initiating the call — the entire remaining balance (their fair share plus all prior mulDiv rounding dust) is permanently locked. Confirmed self-contained: other claimants' independently-computed mulDiv shares (L161) are already paid before the counter reaches 1 and are unaffected by this claimant's status — this is not third-party fund theft, but it is a genuine, irrecoverable fund lock for the affected party.

Proof of Concept
3 eligible winners A, B, C. A and C withdraw successfully via the mulDiv formula (L161), remainingEligibleClaims → 1 (only B remains). USDC blacklists B for unrelated reasons. B calls withdraw(): payout = balanceOf(this) (L156); safeTransfer(B, payout) (L165) reverts because B is blacklisted; the whole transaction — including the _claimed/counter writes — rolls back. B can never successfully call withdraw() again while blacklisted; the residual balance sits in the contract forever.

Fix

+    uint256 private _totalDistributed;
     ...
     function withdraw() external override nonReentrant {
         ...
         if (eligible) {
             require(remainingEligibleClaims > 0, "No eligible claims");
-            if (remainingEligibleClaims == 1) {
-                payout = stakeToken.balanceOf(address(this));
-            } else {
                 uint256 denominator = outcome == Outcome.INVALID
                     ? _totalPrincipal
                     : _totalStakeBySide[outcome == Outcome.YES ? 0 : 1];
                 payout = Math.mulDiv(settlementPool, principal, denominator);
-            }
             remainingEligibleClaims -= 1;
         }

Track cumulative amounts already distributed and compute every claimant's exact mulDiv share — including the last one — accepting that a few wei of rounding dust may remain permanently in the contract (a far smaller, far less severe version of the same underlying issue) rather than making the entire residual hinge on one address's transfer capability. Alternatively, add a claimant-specified alternate-recipient parameter to withdraw().

[60] 4. Vault-address-level USDC blacklist or seizure would freeze 100% of participants' funds with no recovery path

Severity: High · OCPVault.withdraw (whole-contract impact) · Confidence: 60 · [both — phase-2 lead + phase-1 erc20-2]

Description
All staked/donated USDC for a vault sits in a single contract address. If that address itself were ever blacklisted by Circle (false-positive compliance flagging, downstream tainted-funds screening, or sanctions/legal action), every future stakeToken.safeTransfer(msg.sender, payout) call in withdraw() (L165) reverts unconditionally for every participant, permanently — finalize() still succeeds (it only reads balanceOf, L132), so the vault correctly resolves and then strands 100% of principal. Neither contract has a pause, sweep, or migration mechanism.

Fix: There is no way to fully eliminate this risk while using a blacklist-capable centralized stablecoin as sole collateral. Document the risk clearly for users. Consider a long-timelocked, transparency-logged emergency escape hatch usable only after an extended dispute window, so a false-positive freeze is not unconditionally unrecoverable.

[45] 5. stake()/donate() credit the nominal amount parameter rather than a measured balance delta — latent gap, not reachable against the live USDC-pinned deployment

Severity: Low · OCPVault.stake / donate · Confidence: 45 · [phase2 only, calibrated down]

Description
Internal accounting (_totalStakeBySide, _totalPrincipal, info.*, L111-112, L122) is credited with the caller-supplied amount rather than a measured stakeToken.balanceOf delta around safeTransferFrom. For a hypothetical fee-on-transfer/deflationary token this could let a lower-effective-fee staker extract value from a higher-fee staker on the same side via the existing payout formula. Confirmed on-chain (cast call officialStakeToken()) that the live officialStakeToken is genuine Base-native USDC — a standard, non-fee-on-transfer, non-rebasing token — so this vector is not reachable against the audited Factory/Vault today. Retained at Low as defensive-coding advice, since nothing in OCPVault's own code enforces the assumption, and a future Factory-created vault pointed at a non-standard token would be exposed.

Fix: Measure stakeToken.balanceOf(address(this)) before/after safeTransferFrom in both stake() and donate() and credit the actual delta, as defense-in-depth.

Leads

Not independently confirmed to Finding-confidence; recorded for completeness.

  • OCPVault's public constructor doesn't validate msg.sender == factory — OCPVault constructor (L45-55). Anyone can deploy a standalone vault passing the real Factory's address as factory_ and any token as stakeToken_; the vault's .factory() getter would then return the trusted Factory address even though isVault[...] is false for it — a potential integration/phishing vector if a front-end authenticates by vault.factory() instead of factory.isVault(vault). Verified not applicable to the audited instance — on-chain trace confirms Vault 0xCCa7...F8e6 was genuinely created via the Factory's createMarket(). Fix: add require(msg.sender == factory_) to the constructor, or document that isVault() is the only valid authenticity check.
  • Last-claimant live-balance sweep captures stray/direct transfers and rounding dust disproportionately — withdraw() L155-156 (live balance) vs L161 (frozen snapshot for all other claimants). Confirmed intended, tested behavior — the repo's own test suite (test_directTransferAfterFinalizeGoesToLastEligibleClaimant) explicitly asserts this. Recommend only that it be documented in NatSpec/user docs so it isn't later "fixed" in a way that reintroduces permanently-stranded dust.
  • USDC-level pause() causes a temporary, self-recovering DoS on stake/donate/withdraw. No permanent loss; finalize() is unaffected (view-only).
  • Side/Outcome enums use mismatched ordinal numbering (Side.YES=0/NO=1/INVALID=2 vs Outcome.PENDING=0/YES=1/NO=2/INVALID=3) — current code never casts between them, but is a latent footgun for a future refactor that does.
  • OCPVaultFactory.getMarkets() always returns an empty array (dead stub — getVaults() is the real accessor); createMarket()'s initialLiquidity parameter is accepted and silently discarded (no seeding occurs); marketAddr is always address(0). Cosmetic/dead-code only.
  • stakeToken (USDC) is itself an upgradeable proxy — its behavior is entirely outside the protocol's control; disclosed here as an inherent trust assumption of building on a centralized stablecoin, not independently actionable.
