Findings

[95] 1. Zero-amount deposit on a lapsed-but-still-full pool permanently corrupts the Safe owner list and can freeze all pooled ETH

EnsDiamondsEscrow.deposit · Confidence: 95

Description
When a pool sits at totalDeposited == targetAmount with its 1-day EXECUTION_WINDOW lapsed, status() reports Funding again (L116) even though remaining = targetAmount - totalDeposited is exactly 0; deposit() never checks amount > 0 before executing its "new contributor" and "just reached target" state writes, so any invited address can call deposit(poolId){value: 1 wei} — fully refunded — and still get pushed into contributors[] with a permanent zero balance while fundedAt is unconditionally reset.

Impact — three compounding effects from one root cause:

  1. Governance dilution / theft enabler: the free-riding address becomes a full, equal-weight owner of the eventual Gnosis Safe (threshold = owners.length/2+1, L235), diluting genuine contributors' collective control and — combined with Finding 2's mechanics — enabling outright fund theft by a colluding minority.
  2. Indefinite withdraw() denial: since the re-armed fundedAt keeps status() reporting Funded, and withdraw() requires status∈{Funding,Expired} (L205), any single invited address can repeat the 1-wei call roughly once per day to keep every genuine contributor locked out of their own funds indefinitely, at near-zero cost.
  3. Permanent finalize() brick: because the free-riding address's deposits[] balance never leaves 0, isTopUp (L178) stays false forever for that address, so it can be pushed into contributors[] a second time on a later cycle. The real Gnosis Safe v1.4.1 setupOwners() reverts on any duplicate owner address, so createProxyWithNonce — and therefore finalize() — reverts permanently for that pool, with no removal path (_removeContributor only fires from withdraw(), which requires deposits!=0, which a ghost entry never has).

Reachability requires no privileged action — only that a pool's 24-hour finalize window lapses without anyone calling finalize(), which is an explicitly documented, normal operating state of the contract ("If the window lapses unused, the pool reverts to withdrawable Funding status") and a very plausible real-world occurrence given human coordination delays around an ENS purchase decision.

Proof of Concept

  1. Pool created, targetAmount = 1 ether, invitees [Bob] (creator Alice auto-invited).
  2. Alice and Bob together deposit exactly 1 ether → totalDeposited == targetAmount, fundedAt = T0, status = Funded, contributors = [Alice, Bob].
  3. Nobody calls finalize() within EXECUTION_WINDOW (1 day). At T0 + 86401, status(poolId) re-evaluates: totalDeposited == targetAmount is still true (L112), but block.timestamp > fundedAt + EXECUTION_WINDOW (L113), so it falls to return PoolStatus.Funding (L116) — even though the pool is still completely full.
  4. Mallory, merely invited[poolId][Mallory] == true and never having deposited, calls deposit(poolId){value: 1}: invited check passes (L164), status==Funding passes (L165), msg.value != 0 passes (L166). remaining = 1e18 - 1e18 = 0 (L174); amount = (1 > 0) ? 0 : uint96(1) = 0 (L175); refund = 1 (L176). isTopUp = deposits[poolId][Mallory](0) > 0 = false (L178); isExactGap = (0==0) = true (L179), so the BelowMinimum guard at L180 short-circuits to false and does not revert despite amount(0) < MIN_CONTRIBUTION. Since !isTopUp, contributors[poolId].push(Mallory) executes (L182-183) — contributors = [Alice, Bob, Mallory] while deposits[poolId][Mallory] stays 0. p.totalDeposited += 0 unchanged, still == targetAmount (L186), so L188's check re-fires: p.fundedAt = block.timestamp (L189), re-arming the window for another full day, PoolFunded re-emitted. Mallory's 1 wei is refunded in full at L196-198 — her net cost is gas only.
  5. Any subsequent finalize() call now uses owners = [Alice, Bob, Mallory] (L231), threshold = uint8(3/2+1) = 2 (L235) — Mallory holds a full, equal-weight veto seat over the pooled 1 ETH despite contributing $0.
  6. Mallory repeats step 4 on the next lapse cycle. Since deposits[poolId][Mallory] never left 0, isTopUp is false again, so she is pushed a second time: contributors = [Alice, Bob, Mallory, Mallory]. Any future finalize() call now passes a duplicate-owner array to the real Safe factory, which reverts inside setupOwners() — finalize() is permanently broken for this pool. Alice and Bob's only recourse is to catch a brief withdraw-eligible window before Mallory's next griefing transaction lands.

Fix

     function deposit(uint256 poolId) external payable nonReentrant {
         Pool storage p = pools[poolId];
         if (!invited[poolId][msg.sender]) revert NotInvited();
         if (status(poolId) != PoolStatus.Funding) revert WrongStatus();
         if (msg.value == 0) revert ZeroValue();
         if (withdrawBlock[poolId][msg.sender] == block.number) revert SameBlock();

         uint96 remaining = p.targetAmount - p.totalDeposited;
         uint96 amount = msg.value > remaining ? remaining : uint96(msg.value);
         uint256 refund = msg.value - amount;
+        if (amount == 0) revert ZeroValue();

         bool isTopUp = deposits[poolId][msg.sender] > 0;

[88] 2. Safe ownership/control is allocated by contributor headcount, not contribution size — a pool creator can Sybil their way to majority control

EnsDiamondsEscrow.finalize · Confidence: 88

Description
finalize() derives the deployed Safe's owner set and signature threshold purely from contributors[poolId].length (threshold = owners.length/2+1, L235) — never from how much each address actually deposited. invited[poolId][*] is populated entirely and unilaterally by the pool creator at createPool() (L131-160) with no identity or Sybil-resistance check, and up to MAX_OWNERS = 10 total addresses can be invited (L140). Because a first-time deposit only needs to clear MIN_CONTRIBUTION = 0.01 ether (or even less, via the isExactGap bypass at L179-180 for whoever happens to close the exact remaining gap), a malicious creator can invite one real victim alongside several self-controlled addresses, fund the self-controlled addresses with dust, let the victim fund the bulk of targetAmount, and end up controlling a signing majority of the resulting Safe despite contributing a negligible fraction of the pooled capital.

A cheaper single-actor variant exists: a lone address doesn't need to be a "Sybil cluster" at all — simply timing a 1-wei deposit to land as the exact final gap-filler exploits the isExactGap bypass (L179-180) to become a full equal-weight owner without ever meeting MIN_CONTRIBUTION, for the cost of a single deposit.

Proof of Concept

  1. Attacker (creator) calls createPool(label, targetAmount=10 ether, deadline, invitees=[Victim, Sybil2, Sybil3, Sybil4, Sybil5]) — 7 total invited addresses (attacker + 4 sybils + victim), within MAX_OWNERS=10.
  2. Attacker deposits 0.01 ether from themselves and each of Sybil2–Sybil5 (5 addresses, ≈0.05 ether total).
  3. Victim deposits the remaining ≈9.95 ether via the gap-filling logic (L174-176), completing targetAmount exactly.
  4. owners.length == 7 → threshold = uint8(7/2+1) = 4 (L235). Attacker controls 5 of 7 owner keys (self + 4 sybils) — above the 4-signature threshold.
  5. Any contributor calls finalize(); the Safe deploys with the attacker holding a supermajority of signing keys, funded with the full 10 ether (L272).
  6. Attacker executes a Safe transaction using 4 of their own 5 keys, sweeping the entire 10 ether to an address they control. Victim's ≈9.95 ether — over 99% of the pool — is unrecoverable; the victim never held blocking power despite funding nearly the entire purchase.

Fix (Option A — capital-weighted control)
Weight Safe signing authority (or a minimum-diversity requirement) by contribution size rather than raw address count — e.g., cap any single depositor's share of targetAmount, or require the majority-threshold computation to reference deposits[] amounts rather than owners.length alone.

Fix (Option B — close the dust-owner path)

         bool isTopUp = deposits[poolId][msg.sender] > 0;
         bool isExactGap = amount == remaining;
-        if (!isTopUp && !isExactGap && amount < MIN_CONTRIBUTION) revert BelowMinimum();
+        if (!isTopUp && amount < MIN_CONTRIBUTION) revert BelowMinimum();

This closes the cheap single-actor variant but does not by itself prevent the multi-Sybil-at-MIN_CONTRIBUTION variant — Option A is the structural fix; Option B raises the cost floor.

[70] 3. Front-running withdraw() can permanently prevent a pool from ever reaching Funded

EnsDiamondsEscrow.withdraw / EnsDiamondsEscrow.deposit · Confidence: 70

Description
withdraw() is unrestricted while a pool's status is Funding (L205) — any contributor, including one holding only a MIN_CONTRIBUTION-sized dust deposit, can withdraw at will before the pool reaches target. A malicious invitee can front-run the transaction that would close the final funding gap with their own withdraw() call, pulling their stake and enlarging remaining at the exact moment someone else's deposit was about to close it, so the gap-closing deposit lands short of targetAmount and the pool never transitions to Funded. The griefer can redeposit the minimum later and repeat indefinitely, at gas cost only — invited[] is never revocable, so other contributors have no on-chain remedy short of abandoning the pool. Note: withdrawal after Funded is correctly blocked (WithdrawLocked), so this vector is confined to the pre-funding race, not an already-funded window.

Proof of Concept
Pool at targetAmount = 3 ETH; Alice/Bob at 0.99 ETH each, Mallory (malicious) at 0.01 ETH (totalDeposited = 1.99 ETH, gap 1.01 ETH). Alice submits a 1.01 ETH gap-closing deposit; Mallory front-runs with withdraw(), pulling her 0.01 ETH and reopening the gap to 1.02 ETH (L211-212). Alice's deposit lands but is capped short of target (L175). Mallory redeposits 0.01 ETH and repeats whenever the pool nears completion — Funded (and therefore finalize()) is permanently unreachable while Mallory participates.

Fix
No diff provided — structural options: allow the creator or a majority of current contributors to revoke an individual's invited status (with a forced withdrawal) before Funded, or add a cooldown between an address's withdraw() and its ability to re-deposit to raise the cost of repeated cycling.

[55] 4. CREATE2 Safe-adoption branch has no runtime read-back verification, and deploy-time trust of the Safe factory/singleton is unverified beyond code presence

EnsDiamondsEscrow.finalize / _computeSafeAddress / constructor · Confidence: 55

Description
Two related gaps in the same trust chain:

  • Deploy-time (constructor, L95-104): safeProxyFactory/safeSingleton/safeFallbackHandler are validated only via code.length != 0 (L98) — not checked against known canonical Safe v1.4.1 bytecode/extcodehash. If a deployer ever misconfigures these immutables to a non-canonical contract (still passing the weak check), every downstream CREATE2-trust argument collapses.
  • Runtime (finalize(), L256-262): the deploy branch self-verifies (if (safe != predicted) revert SafeDeployFailed(), L259), so any latent divergence between _computeSafeAddress's local re-derivation and the real factory's formula degrades to a safe revert. The adopt branch (else { safe = predicted; }, L260-261) has no equivalent check — it trusts predicted.code.length != 0 alone, with no static-call read-back (e.g. getOwners()/getThreshold()) before p.targetAmount wei is sent to it at L272.

Independently re-confirmed NOT currently exploitable by four separate agents (Phase 1 assembly agent; Phase 2 invariant, periphery, and flow-gap agents), each hand-deriving the real Gnosis Safe v1.4.1 createProxyWithNonce CREATE2 formula and confirming _computeSafeAddress() matches it exactly. Since the CREATE2 salt binds keccak256(initializer) (the exact owners/threshold/fallbackHandler), landing different bytecode at the predicted address without controlling the genuine safeProxyFactory itself would require a keccak256 second-preimage break (~2^256 work) — infeasible. This is a defense-in-depth gap contingent entirely on the deploy-time configuration being honest, not a live third-party attack path.

Fix
No diff provided — pin extcodehash of the expected canonical factory/singleton in the constructor and revert on mismatch; add a cheap static-call owner/threshold comparison before the adoption branch trusts predicted.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be independently confirmed. Not false positives — high-signal leads for manual review. Not scored.

  • uint8 threshold overflow via unbounded contributors[] growth — finalize — Code smells: repeated same-address zero-value pushes (Finding 1's mechanism) could in principle grow contributors[].length past 255, wrapping uint8(owners.length/2+1). Investigated and demoted: the Safe's duplicate-owner revert fires long before any such length is reachable via single-address spam, and distinct-address ghosts are hard-capped by MAX_OWNERS=10 at the invite stage.
  • Same-block re-arm guard bypass via multi-address control — deposit/withdraw — Code smells: an actor controlling 2+ invited addresses could withdraw with one and redeposit with another in the same block, bypassing the SameBlock anti-re-arm marker. No net value extraction — real money must be resupplied — and honest contributors retain finalize() as an escape hatch throughout.
  • status() conflates "actively collecting" and "fully-funded-but-lapsed" under one Funding label — status — Code smells: this ambiguity is the structural enabler of Finding 1. Even after Finding 1's fix, any future code path that branches on status()==Funding should be re-audited for the same implicit "remaining>0" assumption.
  • Funded/Funding cycle timing asymmetry — deposit/withdraw — Code smells: investigated whether a majority bloc could strategically time finalize() across re-arm cycles for a worse minority outcome than Finding 2's single-shot case; the invite list is frozen post-creation (capping the damage), and no worse scenario was constructed.
  • Comment inaccuracy: "no single owner can act alone" does not hold for 1-contributor pools — finalize (L232-235) — Code smells: for owners.length==1, threshold=1/2+1=1, contradicting the inline comment. No security impact — a solo-funded pool's sole owner only ever controls funds they personally contributed.
