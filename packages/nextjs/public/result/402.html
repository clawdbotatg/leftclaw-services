[92] 1. TreasuryRouter.withdrawFees lets the fee recipient bypass the entire 40%/40%/20% revenue split

TreasuryRouter.withdrawFees · Confidence: 92 · [both phases: 10 agents — the single most corroborated finding in this audit]

Description
accruedFees[usdc] accumulates 100% of every collected access fee, and withdrawFees — gated only by msg.sender == feeRecipient, with no epoch gate and no reserve-only cap — can drain that entire balance at any time, before the weekly distributeRevenue() ever runs to carve out the documented 40% staker / 40% buyback / 20% reserve split.

Proof of Concept
Access fees accrue to accruedFees[usdc] = 1,000e6 over a week. feeRecipient calls withdrawFees(usdc, feeRecipient) (TreasuryRouter.sol:186-193) — the full 1,000 USDC is transferred and the accumulator zeroed. A subsequent distributeRevenue() call (TreasuryRouter.sol:121-131) reads amount = accruedFees[usdc] = 0 and reverts on require(amount > 0). Stakers and the buyback executor receive 0% instead of the documented 40%/40%, repeatable every epoch.

Fix

+ uint256 public reserveBalance;
+
  function distributeRevenue() external {
      uint256 amount = accruedFees[address(usdc)];
      require(amount > 0, "Treasury: nothing to distribute");
      uint256 stakerShare = (amount * STAKER_SHARE_BPS) / 10000;
      uint256 buybackShare = (amount * BUYBACK_SHARE_BPS) / 10000;
      uint256 reserved = amount - stakerShare - buybackShare;
      lastDistributionAt = block.timestamp;
-     accruedFees[address(usdc)] = reserved;
+     accruedFees[address(usdc)] = 0;
+     reserveBalance += reserved;
      ...
  }

  function withdrawFees(address token, address to) external {
      require(msg.sender == feeRecipient, "Treasury: not recipient");
      require(to != address(0), "Treasury: zero to");
-     uint256 amount = accruedFees[token];
-     require(amount > 0, "Treasury: nothing to withdraw");
-     accruedFees[token] = 0;
+     uint256 amount = token == address(usdc) ? reserveBalance : accruedFees[token];
+     require(amount > 0, "Treasury: nothing to withdraw");
+     if (token == address(usdc)) { reserveBalance = 0; } else { accruedFees[token] = 0; }
      IERC20(token).safeTransfer(to, amount);
  }

[85] 2. createTask conscripts a non-consenting worker with no exit, then expireTask lets the attacker cheaply stamp a permanent false TASK_FAILED reputation signal

TaskRegistry.createTask / TaskRegistry.expireTask · Confidence: 85 · [phase2: 4 agents]

Description
createTask binds any funded worker address with zero consent, writes the task directly to ACTIVE (skipping the consent-bearing POSTED→CLAIMED flow), and locks MIN_TASK_BALANCE ($8) of the victim's deposit. leaveTask/dismissWorker both require state CLAIMED, which a direct-hire task never occupies — the victim has no self-service exit, only a bonded openDispute. If the attacker also funds and lets the deadline pass, anyone can call expireTask, which refunds 100% of escrow to the attacker and emits a permanent TASK_FAILED (weight 100) reputation signal against the victim — for the cost of a single access fee, repeatable against any target.

Proof of Concept
Attacker (any account with ≥$25 deposited) calls createTask(worker=victim, deadline=<past-or-near>, totalAmount, ...). TaskRegistry.sol:314 sets state: TaskState.ACTIVE; TaskRegistry.sol:333 _bindAgent(worker) binds the victim. Victim's maxWithdrawableDeposit immediately drops by $8 with no exit (leaveTask, TaskRegistry.sol:238-241, reverts "not claimed"). Attacker calls fundTask, waits past deadline, calls expireTask (TaskRegistry.sol:493): wasFundedActive == true triggers reputation.emitSignal(victim, TASK_FAILED, ..., weight 100, ...) (TaskRegistry.sol:514-523) while the full escrow refunds back to the attacker.

Fix

  function createTask(
      address worker,
      ...
  ) external returns (uint256 taskId) {
      require(worker != address(0), "TaskRegistry: zero worker");
      require(worker != msg.sender, "TaskRegistry: self hire");
+     require(workerConsent[worker][keccak256(abi.encode(msg.sender, totalAmount, deadline))], "TaskRegistry: worker has not consented");
      ...
  }

(or, minimally: require an explicit worker-signed acceptance step / a pending-invite→accept flow before a direct-hire task becomes ACTIVE and binding.)

[80] 3. EscrowVault._applyDeposit permanently blocks fundTask top-ups after any milestone release, stranding later-milestone payment on incrementally-funded tasks

EscrowVault._applyDeposit / EscrowVault.depositFor · Confidence: 80 · [phase2: 8 agents]

Description
_applyDeposit only accepts state UNFUNDED or LOCKED, but releasing even one milestone moves state to PARTIAL_RELEASE/RELEASED. A poster who funds a milestone task incrementally (a normal, supported pattern — fundTask is a standalone, repeatedly-callable function) can never add funds for later milestones once the first one is accepted.

Proof of Concept
MILESTONE task [10, 10], total 20. Poster funds 10 via fundTask; worker submitProof(M0); poster acceptMilestone(M0) → releaseMilestone pays 10, totalReleased(10) >= totalDeposited(10) → state RELEASED (EscrowVault.sol:277). Poster calls fundTask(10) for M1 → _applyDeposit (EscrowVault.sol:124-127) requires state ∈ {UNFUNDED, LOCKED}; state is RELEASED → reverts "bad state for deposit", permanently. M1 can never be funded or paid.

Fix

  function _applyDeposit(EscrowRecord storage e, uint256 taskId, uint256 amount) internal {
      require(
-         e.state == EscrowState.UNFUNDED || e.state == EscrowState.LOCKED,
+         e.state == EscrowState.UNFUNDED || e.state == EscrowState.LOCKED || e.state == EscrowState.PARTIAL_RELEASE,
          "EscrowVault: bad state for deposit"
      );
      e.totalDeposited += amount;
      e.state = EscrowState.LOCKED;
      ...
  }

[75] 4. Non-MILESTONE escrow modes give the worker no trustless payment guarantee — STREAMING/HOUR_BLOCKS release is unreachable dead code, and the poster can rug via expireTask

EscrowVault.streamRelease / EscrowVault.claimHourBlock / TaskRegistry.expireTask · Confidence: 75 · [both phases: 13 agent-mentions — the most-corroborated dead-code observation in the audit, 2 agents additionally traced the rug angle]

Description
postTask/createTask accept and store streamRate/hourBlockSize and select EscrowMode.STREAMING/HOUR_BLOCKS, and EscrowVault fully implements incremental release for both (streamRelease, claimHourBlock, both onlyRegistry) — but no TaskRegistry function ever calls them (confirmed by exhaustive grep). submitProof requires MILESTONE mode, so a non-milestone worker can never reach IN_REVIEW or the resolveStaleReview timeout escape hatch. The only payout routes are poster-controlled completeTask (all-or-nothing) or expireTask (all to poster, plus a TASK_FAILED signal against the worker if funded+active) — so a poster can let a worker start real work, never call completeTask, and simply let their own chosen deadline pass to reclaim everything.

Proof of Concept
Poster posts an UPFRONT/STREAMING task, worker claimTasks (consents) and startWorks (ACTIVE). Worker performs real off-chain-verified work. Poster never calls completeTask. After deadline, anyone calls expireTask (TaskRegistry.sol:493-528) — full escrow refunds to poster, TASK_FAILED stamped on the worker who did nothing wrong.

Fix
Wire streamRelease/claimHourBlock callers into TaskRegistry for those modes, or reject non-MILESTONE/non-UPFRONT EscrowMode at task creation. Separately, give workers in any escrow mode a permissionless timeout-based partial-claim path analogous to resolveStaleReview.

[65] 5. Compromised/malicious owner can rotate arbitration to a hostile module and drain FROZEN escrow via caller-supplied split/refund recipients

EscrowVault.split / EscrowVault.refund / the four rotate*ArbitrationModule functions · Confidence: 65 · [both phases: 6 agent-mentions — severity reconciled down from Phase 1's High; see Reconciliation Summary]

Description
EscrowVault.freeze() has no state precondition, and split()/refund() take recipient addresses as caller-supplied parameters rather than reading them from the stored EscrowRecord — so a wired arbitration module can redirect any frozen task's escrow to an arbitrary address, not just the task's actual parties. The four independent rotate*ArbitrationModule functions are the intended safety valve, but their sole real gate (current.disputeOpeningPaused()/activeDisputeCount()==0) is self-attested by the module being replaced, and the rotation is not atomic across the four contracts.

Note: exploiting this requires a compromised or malicious owner willing to rotate in a hostile module — a standard admin-trust risk class present in most owner-controlled contracts. Four independent Phase 2 attacker-mindset agents each identified the mechanism but declined to promote it to a full finding for exactly this reason (no unprivileged amplifier). Reported at Medium to reflect both the real implementation gap (caller-supplied recipients) and the honest precondition.

Proof of Concept
Owner (compromised or malicious) ensures the current arbitration module reports disputeOpeningPaused()==true/activeDisputeCount()==0, deploys EvilModule returning matching cross-refs, calls all four rotate* functions. EvilModule then calls EscrowVault.freeze(id) → EscrowVault.split(id, attacker, attacker, 10000) for every funded task — all locked USDC goes to attacker.

Fix

  function split(uint256 taskId, address worker, address poster, uint256 workerBps)
      external nonReentrant onlyArbitration
  {
      EscrowRecord storage e = escrows[taskId];
      require(e.state == EscrowState.FROZEN, "EscrowVault: not frozen");
+     require(worker == e.worker && poster == e.poster, "EscrowVault: recipient mismatch");
      uint256 remaining = e.totalDeposited - e.totalReleased;
      ...
  }

Plus: put rotate* behind a timelock, and make rotation atomic across the four contracts (single coordinating entrypoint or a shared epoch/nonce with a "rotation in progress" flag).

[70] 6. UnionStakingVault.stake() credits the nominal transfer amount instead of the measured balance delta

UnionStakingVault.stake · Confidence: 70 · [both phases: 5 agents]

Description
stake() credits stakers[].staked/totalStaked by the requested amount, not a measured balance delta — the only inbound token-pull in the codebase without this protection (contrast AgentDepositVault.topUp, which measures balanceOf before/after). If AZL is or becomes fee-on-transfer/deflationary, the ledger overstates real holdings and the last unstaker(s) permanently lose their principal when safeTransfer reverts on insufficient balance.

Proof of Concept
With a 1% fee-on-transfer AZL: Alice stakes 100 → vault receives 99, ledger records 100. Repeated across many stakers, the vault's real balance trails Σstaked; sequential unstaking succeeds for early callers and reverts for the last ones.

Fix

  function stake(uint256 amount) external {
      require(stakingActive, "UnionStaking: not active");
      require(amount > 0, "UnionStaking: zero amount");
      _accrue();
      _settle(msg.sender);
-     azlToken.safeTransferFrom(msg.sender, address(this), amount);
-     stakers[msg.sender].staked += amount;
-     totalStaked += amount;
+     uint256 before = azlToken.balanceOf(address(this));
+     azlToken.safeTransferFrom(msg.sender, address(this), amount);
+     uint256 received = azlToken.balanceOf(address(this)) - before;
+     stakers[msg.sender].staked += received;
+     totalStaked += received;
      _checkpoint(msg.sender);
      emit Staked(msg.sender, amount, totalStaked);
  }

[60] 7. Unbounded milestone arrays can permanently brick the worker's stale-review escape hatch and lock escrow

TaskRegistry.resolveStaleReview / TaskRegistry._finalizePausedTask · Confidence: 60 · [phase1 only: evm-audit-dos]

Description
_validateTaskTerms places no upper bound on milestone count. Both resolveStaleReview (the permissionless unresponsive-poster escape hatch) and _finalizePausedTask's worker-protection branch loop over _pendingReview[taskId] with an external escrow.releaseMilestone call per element. A sufficiently large milestone count creates a task whose release loop exceeds the block gas limit, permanently reverting both recovery paths — cheap to set up on Base's low gas costs.

Proof of Concept
Poster creates a task with several hundred milestones (cheap on Base), funds it. Worker submits proof for every milestone via individually cheap transactions. Poster never accepts; after the 3-day REVIEW_TIMEOUT, worker calls resolveStaleReview — the release loop exceeds the block gas limit and reverts on every attempt, permanently.

Fix
Cap milestone count at task creation to a value whose worst-case release loop safely fits a block; make release paths resumable/paginated (process up to K pending milestones per call, persist progress) rather than looping the full array in one transaction.

[55] 8. Streamed USDC staking rewards are permanently stranded during any zero-stake window, with no recovery path

UnionStakingVault._updateRewardAcc · Confidence: 55 · [both phases: 2 agents]

Description
_updateRewardAcc advances lastRewardUpdateAt on every touch but only accumulates into accUsdcPerToken when totalStaked > 0. Since unstaking is cooldown-free and permissionless, totalStaked can hit zero mid-stream; the elapsed reward slice is skipped from the accumulator but the clock still advances past it, and the already-transferred USDC for that slice is never referenced by any accounting variable again. No owner sweep/rescue function exists.

Fix
Either carry forward un-streamed reward from a zero-stake gap (push rewardPeriodFinish out or fold the skipped amount back into rewardRateScaled on stake resume), or add an owner/treasury-gated rescue path with a strandedRewards accumulator.

Architectural Finding (Info/Low — no direct fund impact by itself, but gates 3 other findings)

[45] 9. The entire balance-health watchdog / pause / platform-block subsystem is provably unreachable dead code

TaskRegistry._enforceBalanceHealth / _firstUnderfunded / _enterPause / _finalizePausedTask; AgentDepositVault.meetsTaskMinimum · Confidence: 45 (below the scoring floor — reported as an architectural Lead, not a scored finding) · [both phases: 6 agents, 5 with independent full traces matching to the line]

Every function that reduces a bound agent's deposits floors the result at or above MIN_TASK_BALANCE ($8): withdraw is bounded by maxWithdrawableDeposit = balance - MIN_TASK_BALANCE; every fee-debit function requires >= MIN_ENTRY_BALANCE + fee and leaves >= MIN_ENTRY_BALANCE; debitDisputeBond requires post-debit >= MIN_TASK_BALANCE. Every binding path requires >= MIN_ENTRY_BALANCE first. So deposits[agent] < MIN_TASK_BALANCE is unreachable for a bound agent. The only other way meetsTaskMinimum fails is isBlocked, whose sole writer (applyPlatformPenalty) is reachable only through this same watchdog — a circular condition that can never bootstrap from a cold start. This was independently, rigorously re-derived by 5 separate Phase 2 agents (economic-security, execution-trace, boundary, numerical-gap-hunter, flow-gap-hunter) with matching line-level traces, corroborating Phase 1's lighter-weight Info-level observation.

This has a direct consequence for reconciliation: three findings raised by other agents across both phases require the watchdog to actually fire, and are therefore currently unreachable, not live bugs:

  • Worker-forfeiture in _finalizePausedTask (the worker-protection release branch only fires when culprit == poster, never culprit == worker — proposed as a FINDING by 2 agents) — demoted to Lead below.
  • EscrowVault freeze-during-pause deadlock (requires the task to reach PAUSED at all) — demoted to Lead below.
  • Disproportionate verifier-bond slash via applyPlatformPenalty→resetSubject (requires applyPlatformPenalty to fire) — demoted to Lead below.

Recommendation: if the pause/solvency watchdog is intended to function, the withdrawal/debit floor must sit strictly below the watchdog's health threshold (or the threshold scaled up by liveTaskBindings, see Finding below). Any such fix must re-examine all three contingent leads together — making the watchdog reachable without also fixing the worker-protection branch reintroduces real fund loss.

Additional Findings (Low)

[50] 10. maxWithdrawableDeposit/meetsTaskMinimum use a flat floor regardless of live-task-binding count

TaskRegistry.maxWithdrawableDeposit (L539-548) / AgentDepositVault.meetsTaskMinimum (L136-138) · Confidence: 50 · [phase2: 6 agents]

The floor is a flat MIN_TASK_BALANCE ($8) instead of MIN_TASK_BALANCE * liveTaskBindings[agent], contradicting the constant's own comment ("$8 per live task binding"). Independent of Finding #9's dead-code status, this has one narrow live effect: an agent withdrawn down to exactly $8 makes debitDisputeBond unconditionally revert (any amount > 0 breaches the floor), which can block arbitration-side dispute-bond debits. Fix: floor = MIN_TASK_BALANCE * liveTaskBindings[agent].

[45] 11. TreasuryRouter.distributeRevenue re-splits the standing reserve every epoch, decaying it toward zero

TreasuryRouter.distributeRevenue L130-138 · Confidence: 45 · [both phases: 2 agents]

amount = accruedFees[usdc] includes any previously-reserved-but-unwithdrawn 20%, which gets re-split 40/40/20 again next epoch — 80% of a standing reserve leaks out every epoch it isn't withdrawn. Fix: track the reserve in a variable excluded from the split base on subsequent calls (same fix as Finding #1 addresses this too).

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed in one analysis pass, or which are structurally contingent on another finding. Not scored.

  • Worker-forfeiture on pause finalization — TaskRegistry._finalizePausedTask — Code smells: the proven-milestone release branch only fires when culprit == t.poster, never culprit == worker; if the worker were ever the flagged party, their proven-but-unaccepted escrow would refund entirely to the poster. Contingent on Finding #9 — currently unreachable since isBlocked can never be set. Flagged so a naive fix to #9 doesn't silently reopen this.
  • Escrow freeze-during-pause deadlock — EscrowVault.freeze / TaskRegistry._finalizePausedTask — Code smells: freeze() has no state precondition; if a task were both FROZEN (by arbitration) and PAUSED (by the watchdog), _finalizePausedTask's refundRemainingToPoster call would revert on every attempt (forbidden while FROZEN), wedging the task permanently. Contingent on Finding #9 — currently unreachable since PAUSED can never be entered.
  • Disproportionate verifier-bond slash — AgentDepositVault.applyPlatformPenalty → ReputationRegistry.resetSubject — Code smells: a platform-block for a $8 in-task shortfall forfeits the culprit's entire unrelated native verifier bond. Contingent on Finding #9 — currently unreachable since applyPlatformPenalty can never fire.
  • Verifier bonds have no lockup and are front-runnable before any slash — ReputationRegistry.stakeVerifierBond/unstakeVerifierBond vs slashVerifierBond/resetSubject — Code smells: unstakeVerifierBond is fully permissionless with no lockup, so a verifier can withdraw ahead of any slash trigger. The slash trigger lives in the out-of-scope arbitration module, so full weaponization is unverified.
  • TaskRegistry.onDisputeResolved assumes the external module always freezes+splits/refunds before resolving — no on-chain cross-check exists; if the module ever called onDisputeResolved without having first frozen and settled escrow, funds would be stranded with no in-scope recovery path. Trigger lives entirely in the out-of-scope module.
  • renounceOwnership left enabled on 5 of 6 contracts — AgentDepositVault deliberately disables it (recognizing owner is load-bearing for arbitration-module recovery); the other five don't, so renouncing on any of them permanently disables that contract's rotate* recovery path.
  • Unbounded delete subjectSignals[subject] can exceed gas, silently voiding a platform penalty's reputation reset — ReputationRegistry.resetSubject's try/catch means the 7-day block still applies even if the (potentially very large) signal-array deletion reverts on gas.
  • distributeRevenue fully reverts if buybackExecutor cannot receive USDC — freezing the entire weekly distribution crank, including the unrelated 40% staker share.
  • EscrowVault.depositFor, _payOrDefer's EOA-as-success ambiguity, and unenforced AZL decimals — three related Low-severity token-handling gaps, none currently reachable given the wired USDC/AZL addresses, bundled for completeness.
  • UnionStakingVault credit-accumulator clock/double-division — _accrue() advances its clock before confirming any credits were minted (dust-level truncation loss), and a double-division in the per-token rate causes a negligible early retirement of the 600k credit cap.

Access-Control Inventory

All 6 contracts use Ownable2Step. Owner unlocks only one-time address(0)-guarded wiring setters and the 4 independent rotate* functions — owner has no direct fund-custody power except indirectly via arbitration-module rotation (Finding #5). AgentDepositVault.renounceOwnership is overridden to always revert; the other 5 contracts use default renounce-to-address(0) (see Leads).

Distinct non-owner privileged roles: feeRecipient (TreasuryRouter, own 2-step rotation, unlocks withdrawFees/withdrawNativeFees — see Finding #1); taskRegistry address (unlocks onlyRegistry functions across EscrowVault/AgentDepositVault/UnionStakingVault, onlyFeeRecorder in Treasury); arbitrationModule address (external, out of scope — unlocks onlyArbitration functions in EscrowVault/AgentDepositVault, checks in ReputationRegistry/TaskRegistry); treasury address (UnionStakingVault's notifyReward gate).

Permissionless entrypoints (arbitrary caller, effects gated by state/time not identity): postTask, claimTask, createTask (see Finding #2), checkTaskBalance, resolveStaleReview (Finding #7), expireTask (Finding #2), EscrowVault.claimPayout, AgentDepositVault.topUp/withdraw/claimPayout, TreasuryRouter.distributeRevenue (Finding #1), UnionStakingVault.stake/unstake/bankCredits/claimRewards, ReputationRegistry.stakeVerifierBond/unstakeVerifierBond.
