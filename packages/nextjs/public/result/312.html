Scope note

It is a thin payment/gatekeeper front-end that delegates all actual NFT minting/extraction logic to two external contracts, signals (0x76a7A7ec5eb0da2534D2F3099145b9C8595A56aB) and fragments (0x0f4B01f1e985205BC3Cbc6fb8Bf479cCE501836f), whose source was not provided for this engagement and is treated throughout as arbitrary/untrusted. Several findings below note where impact is contingent on those contracts' internal behavior — this is a structural characteristic of the target, not a shortcut taken by this audit.

Findings

[F-1] High — Owner can rug in-flight mint/extract transactions via setContracts(), decoupling payment from delivery, and can reset the "sold out" supply cap at will

Origin: [both] — phase1: access-control H-1, erc721 M-1, general M-1 · phase2: agent-11 (trust-gap) FINDING, confidence 80, corroborated as a lead by 8 other agents
Location: setContracts() lines 100-103; exploited via mintParent() (139-170), extractSymbol() (172-180), mintLooseFragment() (182-190)

Description: setContracts() lets owner repoint signals/fragments to any address, instantly, with no validation, no timelock, and no event. All three payable entry points capture ETH into this Minter directly (the interface calls are not payable, so msg.value is never forwarded downstream) and unconditionally trust whatever uint256 the external call returns — no check that a real NFT was minted to the caller. This has two independently provable consequences, both requiring only an owner action (or a compromised owner key) with no cooperation needed from the external contracts' internals:

  1. Payment-without-delivery / front-running a specific victim. An owner can watch the mempool, front-run a user's already-broadcast mintParent/extractSymbol/mintLooseFragment transaction with setContracts(stub, stub), let the victim's transaction execute against a stub that returns a fake id, then swap back and withdraw() the ETH. The victim's transaction succeeds, an event fires, but no NFT is delivered.
  2. Supply-cap reset. mintParent's "sold out" guard (require(signals.totalSupply() < maxSupply, "sold out"), line 142) reads totalSupply() from whichever contract signals currently points to. Swapping to a fresh signals contract with totalSupply()==0 immediately re-arms the mint gate regardless of how many units were sold under the original contract, silently breaking the advertised 1024-unit scarcity cap.

Proof of Concept:

  1. Owner deploys Fake, whose mintWithColors() returns an incrementing counter with no real mint, and whose totalSupply() returns 0.
  2. Alice broadcasts mintParent{value: 0.001 ether}(...). Owner sees it in the mempool and submits setContracts(address(Fake), fragments) with higher gas so it lands first.
  3. Alice's transaction now executes against Fake: totalSupply() < maxSupply passes trivially, her ETH is captured, mintedByWallet[Alice] increments, SignalMinted fires with a bogus id — no real Signal NFT is delivered.
  4. Owner calls setContracts() back to the real signals/fragments addresses (making the incident easy to miss after the fact, since no event is emitted on the change) and withdraw()s the ETH.

Recommendation: Add a timelock/two-step commit on setContracts() (e.g. pendingSignals/pendingFragments + a delayed commitContracts()), emit an event on every change, and validate the new addresses have code. Track mint count with a local monotonic counter (totalMinted, incremented pre-call in mintParent) rather than trusting a live, swappable external totalSupply() for the maxSupply gate. Consider a post-call sanity check on the returned id where feasible.

[F-2] Medium — Mint price, supply cap, and phase flags are mutable at any time with no timelock, undermining marketed scarcity/pricing guarantees

Origin: [phase1 only] — access-control M-2
Location: setMintConfig() (105-110), setFragmentPrices() (112-116), setMintState() (118-124)

Description: maxSupply (marketed as 1024) and mintPrice/maxSignalsPerWallet/fragment prices can be changed instantly by the owner with no bound and no timelock — independent of the setContracts()-based cap reset in F-1, the owner can simply raise maxSupply directly. A buyer has no on-chain guarantee that the terms they see when submitting a transaction will still hold when it mines.

Proof of Concept: Owner calls setMintConfig(mintPrice, 100000, maxSignalsPerWallet) post-launch, silently expanding supply far beyond the advertised 1024.

Recommendation: Make maxSupply immutable after initial configuration (or only lowerable), and/or add a timelock + event-based notice window for price/supply changes.

[F-3] Medium — No ownership transfer or renounce mechanism — single point of permanent failure

Origin: [phase1 only] — access-control M-1, erc721 I-3 (re-examined against source: confirmed — no transferOwnership/renounceOwnership function exists anywhere in the 210-line contract)
Location: owner (line 48), constructor (94-98)

Description: owner is set once in the constructor with no function to ever change it. Every privileged action (setContracts, setMintConfig, setFragmentPrices, setMintState, stopLooseFragmentMinting, setAllowlist, withdraw) depends on this single immutable address. If the key is lost, all admin functions — including withdraw() — become permanently inaccessible and any ETH sent to the contract afterward is stuck forever. If the key is compromised, the attacker has permanent, irrevocable control with no way for the team to migrate to a new key or multisig.

Recommendation: Add a two-step ownership transfer mechanism (e.g. OpenZeppelin Ownable2Step) so keys can be rotated or migrated to a multisig.

[F-4] Medium — extractSymbol/mintLooseFragment charge for fragment extraction with no on-chain ownership check

Origin: [both] — phase1: erc721 (implicit in trust-delegation framing) · phase2: agents 2, 3, 5, 6, 9, 11 (6/12) independently converged; re-examined against source: confirmed
Location: extractSymbol() lines 172-180, mintLooseFragment() lines 182-190

Description: extractSymbol charges a discounted ownerFragmentPrice (0.001 ETH, half of looseFragmentPrice) for any nonzero parentTokenId supplied by the caller. The Minter performs no check that msg.sender actually owns or is authorized for that parent token — it checks only !fragments.lockedWallet(msg.sender) and parentTokenId != 0 — and never calls the canExtract/extractionAllowance views it itself exposes (lines 196-202) before spending the fee. All authorization is delegated entirely to the out-of-scope fragments.extractFor.

Proof of Concept: If fragments.extractFor's authorization is anything weaker than strict msg.sender == owner-of(parentTokenId) (unverifiable — its source is unavailable), any address can pay the cheap "owner" price to extract against a signal it doesn't own, undercutting the price-tier's premise and potentially consuming the real owner's rate-limited extraction allowance (griefing). This cannot be confirmed end-to-end without the fragments source, so it is reported at reduced confidence per the audit's verification standard — flagged for the client to confirm against the actual fragments deployment.

Recommendation: If ownership gating is meant to be enforced at the Minter layer at all, add an explicit check (e.g. signals.ownerOf(input.parentTokenId) == msg.sender, if signals exposes it) before forwarding to fragments.extractFor; otherwise explicitly document/confirm that this invariant is fully enforced inside fragments.

[F-5] Low — mintLooseFragment omits the parentTokenId == 0 invariant enforced by its sibling extractSymbol

Origin: [phase2 only] — agents 4, 6, 8, 9, 12 (5/12) independently converged; re-examined against source: confirmed
Location: extractSymbol() line 175 vs mintLooseFragment() lines 182-190

Description: extractSymbol enforces require(input.parentTokenId != 0, "use loose mint") (line 175), establishing the contract's own sentinel invariant: parentTokenId == 0 ⇔ loose path, non-zero ⇔ real-extraction path. mintLooseFragment has no mirrored require(input.parentTokenId == 0, ...) and forwards the identical ExtractInput struct — including any attacker-chosen parentTokenId, potentially belonging to a signal the caller doesn't own — verbatim to fragments.mintLooseFor(msg.sender, input).

Proof of Concept: A caller invokes mintLooseFragment with input.parentTokenId = <any real signal id> and pays only looseFragmentPrice. Whether fragments.mintLooseFor acts on a populated parentTokenId it wasn't designed to receive (e.g. associating the fragment with, or bypassing that parent's per-token extraction cooldown/allowance normally gated via extractFor) is unverifiable without fragments' source. The code-level asymmetry itself is fully provable from this file alone; downstream impact is contingent on the external contract.

Recommendation:

[F-6] Low — No reentrancy guard on payable functions; maxSupply gate specifically has no local backstop against a reentrant external call

Origin: [both] — phase1: access-control L-2, erc721 L-2, general I-1 · phase2: 9/12 agents converged on the specific mintParent supply-cap variant
Location: mintParent(), extractSymbol(), mintLooseFragment()

Description: Checks-effects-interactions is followed correctly for local state — mintedByWallet/allowlistAllowance are updated before their respective external calls, so no reentrant bypass of wallet-level limits is possible. The one guard with no local backstop is mintParent's "sold out" check (line 142), which re-reads external signals.totalSupply() immediately before the state-changing signals.mintWithColors() call (line 153), with no nonReentrant modifier anywhere in the contract. Phase-2 agents traced a concrete (but unverifiable without signals' source) path: if mintWithColors invokes any callback on the recipient before finalizing its own supply bookkeeping, a reentrant call could re-read a stale totalSupply() and mint past maxSupply. Note this reentrancy-dependent path achieves a strictly weaker version of the cap-reset already proven unconditionally in F-1/F-2 (which need no cooperation from signals' internals) — reported here mainly as defense-in-depth guidance.

Recommendation: Add OpenZeppelin ReentrancyGuard / nonReentrant to all three payable entry points, and combine with a local totalMinted counter (see F-1) so the maxSupply invariant does not depend on external contract behavior at all.

[F-7] Low — Core mint/extract paths unconditionally trust return data and availability of untrusted external signals/fragments contracts

Origin: [phase1 only] — dos DOS-3; related phase2 lead "unenforced-exclusive-minter-trust" (agents 2, 12) — distinct confused-deputy angle, kept separate
Location: mintParent() (142, 153-167), extractSymbol() (178), mintLooseFragment() (188)

Description: Every value-generating function makes a single, un-capped, non-try/catch'd external call into signals/fragments. A misbehaving or compromised target could return an arbitrarily large return blob (memory-expansion gas griefing — state changes revert atomically so no funds are lost, only gas wasted), or the calls could simply revert, unconditionally bricking mintParent for all users with no fallback other than an owner-driven setContracts() repoint (which carries its own risk, see F-1).

Separately (phase2-only lead, not independently re-verifiable): nothing in this file proves signals.mintWithColors/fragments.extractFor/fragments.mintLooseFor restrict their privileged entrypoints to msg.sender == address(thisMinter). If they don't, any address could call them directly, bypassing every gate this Minter enforces (price, pause, allowlist, caps) — a classic confused-deputy risk for a front-end/router contract, worth confirming against the actual signals/fragments deployments.

Recommendation: Wrap external calls in try/catch where feasible, or use low-level staticcall/call with a gas cap and fixed-size return decoding. Confirm with the signals/fragments audit that their privileged entrypoints are restricted to this Minter's address.

[F-8] Low — Unvalidated, caller-supplied palette/metadata fields forwarded with no on-chain cross-check against paletteId

Origin: [phase1 only] — erc721 M-2
Location: mintParent() 153-167 (paletteName, secondaryPaletteName, paletteColors, secondaryPaletteColors); extractSymbol()/mintLooseFragment() 172-190 (analogous Fragments fields)

Description: The Minter forwards attacker-controlled string/array fields (palette name, colors) without validating them against the numeric paletteId/secondaryPaletteId they're supposed to describe. Unless signals/fragments independently re-validate these (unverifiable here), a minter could label their token with misleading/spoofed rare-sounding trait names or colors that don't correspond to the actual paletteId.

Recommendation: Validate palette name/colors against an on-chain registry keyed by paletteId before forwarding, or explicitly confirm this validation is enforced inside signals/fragments.

[F-9] Low — No refund of ETH sent above the required mint/extraction price

Origin: [phase1 only] — erc721 L-1, general L-1 (2/5 phase-1 agents)
Location: mintParent() line 143, extractSymbol() line 176, mintLooseFragment() line 186

Description: All three payable entry points use require(msg.value >= price, ...) and never refund the excess; any overpayment is retained by the contract and only recoverable by the owner via withdraw().

Recommendation: Require exact payment (== price) or refund the difference to the caller.

[F-10] Low — No zero-address / code-existence validation on signals/fragments

Origin: [phase1 only] — access-control L-1, erc721 I-2, general L-2 (3/5 phase-1 agents)
Location: constructor (94-98), setContracts() (100-103)

Description: Neither the constructor nor setContracts() validates that the supplied addresses are non-zero or contain code. A misconfiguration bricks minting (self-inflicted, owner-recoverable DoS) until corrected.

Recommendation: Add require(addr != address(0) && addr.code.length > 0, ...) checks.

[F-11] Low — setAllowlist() unbounded loop over caller-supplied arrays

Origin: [phase1 only] — dos DOS-1
Location: setAllowlist() lines 131-137

Description: No length cap on accounts/allowances. Not third-party exploitable (onlyOwner-gated, arrays supplied fresh each call) — only a self-inflicted out-of-gas risk for the owner's own tooling on an oversized batch.

Recommendation: Optional: cap batch size (e.g. 500) for clearer tooling errors.

Informational

  • setContracts() emits no event — every other owner-only state-changing function does; this is arguably the most consequential admin action in the contract (see F-1) and currently the hardest to monitor off-chain. ([phase1 only], access-control I-1)
  • allowlistMintOpen has no effect once publicMintOpen is true — both flags are currently true on-chain, so the allowlist is presently dead weight. May not match the "V9Phased" naming's implied phase separation; worth confirming intent with the client. ([phase1 only], erc721 I-1)
  • withdraw() external-call pattern is not exploitable — recipient to is owner-chosen per call (default owner), so the owner is never forced into a permanently bricked withdraw path. ([phase1 only], dos DOS-2)
  • looseFragmentMintingStopped is a one-way switch — appears to be an intentional "final phase ended" lever rather than a bug. ([phase1 only], dos DOS-4)
  • mintPrice defaults to 0 with allowlistMintOpen defaulting to true — [both], corroborated by all 5 phase-1 agents' general checklist and effectively every phase-2 agent. If a deployment script called setAllowlist before setMintConfig, allowlisted addresses could mint for free during that window. Moot on the currently live contract, which already has mintPrice = 0.001 ETH configured — flagged as an operational/deployment-ordering note only.
