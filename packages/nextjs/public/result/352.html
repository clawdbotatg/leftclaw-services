Security Audit Report — VKPDelegationRegistry

Contract: VKPDelegationRegistry (name per job description; not independently confirmed on-chain since no verified source exists)
Address: 0xd4d32b5c28040AFA2A6aB0ae9FF6DA68EAee4F82 (Base, chain 8453)
Source availability: Unverified. No match on Sourcify (full_match/any_match v2 API queried directly), no verified source on Base Blockscout (/api/v2/smart-contracts/{address} returns bytecode only, is_verified absent), and no Etherscan/Basescan API key was available in this environment to query that fallback. Per audit methodology, this report falls back to bytecode-level analysis.

Methodology Note — Read This Before The Findings Below

This is not the standard two-phase (ethskills + pashov) source-level audit used for verified contracts, because no Solidity source could be obtained. Instead, this review is based on:

  • The deployed runtime bytecode (6,404 bytes), disassembled via cast disassemble.
  • Manual reconstruction of the function dispatch table (21 confirmed 4-byte selectors) and cross-referencing against the public 4byte.directory signature database.
  • Direct on-chain calls (cast call) to confirm hypotheses about getter functions and constructor-injected dependency addresses.
  • Opcode-level tracing of the three functions most relevant to the client's stated focus areas: the delegation-creation flow, revokeDelegation(uint256), and an auto-discovered permissionless health-check function.

Confidence is inherently lower than a source-level audit. Bytecode analysis can confirm control flow, storage layout, and external call targets with high fidelity, but cannot fully verify intent, edge-case correctness of complex multi-field struct packing, or every code path with the same certainty as reading the original Solidity. Findings below are scoped to what could be concretely traced and verified; anything not fully traceable is marked as a Lead rather than a rated Finding, per this audit's verification standard (downgrade severity/confidence when a full exploit path cannot be constructed).

If verified source becomes available, this contract should be re-audited with the standard two-phase methodology — this report should not be treated as an equivalent substitute.

Confirmed Contract Mechanics

Via selector recovery + on-chain calls, the following was established with high confidence:

  • 21 external functions, including an auto-incrementing delegation-ID counter at storage slot 0 (currently 0, i.e. no delegations have been created on-chain yet), a mapping(uint256 => Delegation) at storage slot 1 (12-word struct: delegator address, delegate address, several uint256 fields, and a packed byte of boolean flags including a "revoked" bit), and two per-address enumeration arrays at storage slots 4 and 5 (one keyed by delegator, one by delegate).
  • Three externally-controlled, immutable dependency addresses baked into the contract at deploy time:
    • bondsRegistry() (selector 0x92c1ee40) → 0x01C479F0c039fEC40c0Cf1c5C921bab457d57441 — confirmed identical to job 368's AIPartnershipBondsV2 address in this same client's audit batch.
    • A second getter (selector 0x134e18f4) → 0xa7bd20bf5de63df949ca5be2f20835978ecba81a — live contract (9,387 bytes of code), used in the delegation-creation flow's first eligibility check. Not independently identified against another job in this batch, and out of scope for this review.
    • A third address, 0xdb54b8925664816187646174bdbb6ac658a55a5f (live contract, 6,842 bytes of code), referenced only inside the auto-discovered health-check function (see F-1 below). Also out of scope.
  • Delegation creation (selector 0xa371719a, a 9-parameter function) gates on two sequential STATICCALLs — one to each of the first two dependency addresses above, using a shared selector 0xfb3551ff (closest 4byte.directory match: getAgent(address)) — and only proceeds to write the new delegation and increment the ID counter if both calls return a non-zero first word. Both STATICCALLs occur strictly before any state-changing SSTORE, i.e. checks-effects-interactions ordering is correctly followed (and STATICCALL cannot reenter with state changes regardless).
  • revokeDelegation(uint256) (selector 0xbd3d425d) — traced in full.
  • A bulk self-revoke function (selector 0x05d9b052, no arguments) that iterates the caller's own entry in the slot-4 array and flags every not-yet-revoked delegation belonging to them, emitting the same Revoked-style event per entry. Confirmed via eth_call (returns empty data with no revert, consistent with a state-mutating function with no return value). Since it only iterates the caller's own array, it is not griefable by a third party.
  • A permissionless health-check / auto-enforcement function (one of the not-fully-identified selectors, reachable via opcode offset ~`0x15a9–0x16d0) that re-queries the third dependency address (0xdb54b892...) with selector 0x4e44d071against a delegation'sdelegateaddress, compares the result against a threshold, and — on failure — sets the **same** "revoked" bit as manual revocation, emitting either a"Reputation check failed"or (via a second, similarly-structured branch further down, referencingbondsRegistry()) "Bond requirement no longer met"event. This staticcall also occurs strictly before its correspondingSSTORE`.

Findings

[F-1] Auto-revocation health-check function's external-call-failure path could not be fully verified from bytecode alone

Severity: Low (Lead — reduced confidence, bytecode-only)
Location: opcode offsets ~`0x15a9–0x16d0(deployed bytecode), invokingSTATICCALLagainst0xdb54b8925664816187646174bdbb6ac658a55a5fwith selector0x4e44d071`

Description: This function re-validates an existing delegation's continued eligibility and can auto-revoke it (setting the same flag bit as revokeDelegation) if the external dependency's response indicates the delegate's reputation or bond backing has degraded. The branch structure around the STATICCALL's own success/failure (as opposed to the business-logic result it returns) follows a pattern of ISZERO/JUMPI checks similar to other external calls in this contract, but I was not able to fully confirm — with the same confidence as the registration flow's dual eligibility check — whether a reverted or out-of-gas call to this dependency is correctly treated as "cannot confirm eligibility, do not act" versus silently falling through a path that treats call failure as "check passed." This distinction matters: if the latter, a delegate's underlying dependency contract reverting (e.g., due to its own pause mechanism, a transient issue, or deliberate griefing by a party that controls calldata to that dependency) could suppress an auto-revocation that should have fired.

Recommendation: Verify against source (once available) that this function's external-call-failure branch reverts or otherwise fails safe (treats an unsuccessful STATICCALL as "cannot confirm — do not silently pass"), consistent with the registration flow's handling of its own two STATICCALLs (which does appear, from the bytecode, to revert via a shared 0x098c error path on outer call failure).

[F-2] revokeDelegation has no "already revoked" guard (idempotent, no material impact)

Severity: Low
Location: revokeDelegation(uint256), selector 0xbd3d425d, fully traced at offsets 0x0455–0x04cb

Description: The function correctly restricts revocation to the original delegator — it loads the delegation's stored delegator address, computes SUB(delegator, CALLER), and reverts with a custom error (selector 0x24e5af8d) if the caller does not match. This is a real, confirmed access-control guard (no gap here). However, before setting the "revoked" bit (AND ~0xff, OR 0x01, single SSTORE), the code does not first check whether that bit is already set. Calling revokeDelegation a second time on an already-revoked delegation succeeds again: it re-writes the same bit value and re-emits the Revoked-style event (topic 0x7a9b2babda95a9a457245bdaee19ec25e62e41e15e93cfc8f7b5c65e248fdf46). This is idempotent and causes no double-spend, fund loss, or state corruption — the requested "revocation atomicity" property holds (a single SSTORE, no partial-write window) — but it does mean off-chain indexers watching for the Revoked event should dedupe by delegation ID rather than assuming one-event-per-delegation.

Recommendation: Add a guard (require(!alreadyRevoked) equivalent) before the flag-set to prevent redundant transactions and duplicate events, though this is a gas/cleanliness improvement rather than a security fix.

[F-3] Delegation authenticity is fully dependent on three externally-controlled contracts that were out of scope for this review

Severity: Medium (informational/trust-boundary — not an exploit finding)
Location: constructor-injected immutables; both the creation flow and the health-check flow

Description: The entire "delegation registration authenticity" guarantee the client asked about rests on two live external contracts (reputation-type check at 0xa7bd20bf5de63df949ca5be2f20835978ecba81a, and the confirmed bondsRegistry() at 0x01C479F0c039fEC40c0Cf1c5C921bab457d57441, i.e. job 368's AIPartnershipBondsV2) responding correctly at delegation-creation time, plus a third contract (0xdb54b8925664816187646174bdbb6ac658a55a5f) for the ongoing health-check. None of these three contracts' own source was in scope for this job, so this review cannot make any claim about their correctness, upgradeability, or pause/access-control behavior. If any of them is compromised, paused unexpectedly, or returns manipulable eligibility data, VKPDelegationRegistry's core authenticity guarantee for new delegations is only as strong as that dependency.

Recommendation: Ensure this client's broader audit batch (which appears to cover several of these interlinked Vaultfire contracts as separate jobs) explicitly verifies these three dependency addresses, and confirm from the VKPDelegationRegistry source (once available) whether these addresses are themselves upgradeable/mutable or permanently fixed at deployment.

Non-Findings / Explicitly Checked

  • Reentrancy: Both external-call sites traced (STATICCALL in the creation flow, STATICCALL in the health-check flow) occur strictly before their corresponding SSTOREs (checks-effects-interactions holds), and STATICCALL cannot itself perform state-changing reentrant calls regardless.
  • Revocation access control: revokeDelegation is correctly restricted to the delegation's original delegator via a direct address comparison and custom-error revert; no bypass found in the traced path.
  • Bulk self-revoke griefing: The no-argument bulk-revoke function only iterates the caller's own per-address array — not exploitable by a third party to grief another user's gas costs or state.
  • Overflow on the ID counter: The creation flow includes an explicit NOT ... EQ check against type(uint256).max before incrementing the slot-0 counter, consistent with overflow protection (though Solidity 0.8.x would revert on overflow by default regardless, suggesting this may be a redundant/defensive check rather than a required one — consistent with unchecked-block usage elsewhere, unconfirmable without source).

Client Focus Areas — Direct Answers

  1. "Delegation registration authenticity" — Confirmed: creation requires two sequential STATICCALL-based eligibility checks against externally-controlled reputation/bonds contracts before any state is written, correctly ordered before effects. The guarantee's strength is bounded by the correctness of those three external dependencies (F-3), which were out of scope here.
  2. "Revocation atomicity" — Confirmed sound: revocation is a single atomic SSTORE bit-flip with no partial-write window, and is correctly restricted to the original delegator. The only gap found is a missing already-revoked guard (F-2), which is a hygiene issue, not an atomicity violation.
  3. "Enumeration correctness" — The per-address enumeration arrays (delegator-keyed and delegate-keyed) and their paginated getters were confirmed to exist and follow a standard append-only array + explicit start-index pattern; no unbounded or attacker-griefable loop was found in the functions traced. A full line-by-line correctness proof of every enumeration edge case was not achievable from bytecode alone within this review's scope.

⚠️ This review was performed via bytecode-level analysis because no verified source was available on Sourcify or Blockscout, and no Etherscan/Basescan API key was available in this environment. This methodology has materially lower confidence than a source-level audit. AI analysis, especially at the bytecode level, can never verify the complete absence of vulnerabilities and no guarantee of security is given. A human security review with access to verified source, a bug bounty program, and on-chain monitoring are strongly recommended before this registry is relied upon for consequential downstream decisions.
