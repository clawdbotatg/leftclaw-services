Findings

[High-confidence architectural finding] 1. The contract never itself calls out — enforcement is not self-contained

ScopedDelegation (whole contract) · Confidence: 80

Description

The full 7,534-byte runtime was disassembled (cast disassemble, 4,332
instructions). It contains zero CALL, zero CALLCODE, and zero
DELEGATECALL opcodes anywhere. The only external-call opcode present is
STATICCALL, at exactly three sites (offsets 0x0c11, 0x141b, 0x146c) —
consistent with read-only lookups against the identity/bond/reputation
registries referenced by the resolved selectors identityRegistry(),
bondsRegistry(), reputationRegistry().

This means ScopedDelegation cannot itself forward or execute the
"delegated" action against an allowlisted target contract — there is no code
path in this contract that performs target.call(data) on behalf of a
grantee. It can only record/validate scope state (budget, dailyCap, perTxCap,
expiry, allowlists) in storage and revert if a check fails.

Why this matters for the requested focus areas: the client's brief asked
us to hunt for ways to bypass the contract/function-selector allowlist via
delegatecall, fallback/receive, or multicall-unwrapping from inside this
contract. All three are structurally ruled out (see Findings 2–3 below) —
but that is almost beside the point, because this contract is not the thing
doing the calling in the first place. If the intended system design is
"grantee calls into ScopedDelegation, which checks the scope and then
executes the call on the grantee's behalf," that design is not what is
deployed. Some other, not-provided contract (an executor/router) must be
the one issuing the CALL, and it must independently choose to consult
ScopedDelegation before acting.

Concrete exploit path: unless every allowlisted target contract
independently gates its sensitive functions on msg.sender == ScopedDelegation
(unusual, and not something this system controls for arbitrary third-party
allowlisted contracts), a grantee — or anyone holding the grantee's signing
key/session — can simply call the target contract directly, with their own
key, never touching ScopedDelegation at all. None of budget, dailyCap,
perTxCap, expiry, the contract allowlist, or the function-selector
allowlist are consulted by that direct call, because they only exist as
storage checks inside a contract that is never in the actual call path. This
is a complete bypass of every control the client asked us to stress-test —
not through a clever selector trick, but because the enforcement point and
the execution point are two different (and here, only one deployed) contracts.

Severity rationale: capped at High rather than Critical because this audit
cannot see the off-chain/on-chain executor or integration layer that
presumably calls ScopedDelegation.checkAndConsume(...)-style functions
before acting — if that layer exists and is the only way grantee actions
ever reach allowlisted contracts, the risk is materially lower. That
executor was not provided and does not appear to exist at this address.

Fix: Either (a) provide/verify the executor contract for a follow-up audit
of the full call path, and confirm grantee keys have no way to act on
allowlisted targets except through it, or (b) if ScopedDelegation is
intended to be the executor, add an actual execute(scopeId, target, data)
function that performs the CALL itself after passing all checks — no such
function exists in the deployed bytecode today.

[Ruled out] 2. Fallback/receive-based bypass — not present

ScopedDelegation (dispatcher) · Confidence: 95

Description: The function dispatcher's default (no-selector-match) branch
at offset 0x0139–0x013c is a bare PUSH1 0x00 / DUP1 / REVERT — an
argumentless revert, which is what Solidity emits when no fallback() or
receive() function is defined. There is no code path that accepts a call
with an unrecognized selector or plain ETH transfer. The client's specific
concern ("bypass via fallback/receive") does not apply to this contract.

[Ruled out] 3. Delegatecall / multicall-unwrapping bypass — not present

ScopedDelegation (whole contract) · Confidence: 95

Description: As established in Finding 1, DELEGATECALL does not appear
anywhere in the 4,332-instruction disassembly. A "multicall unwrapping" bypass
requires either delegatecall-based batching (absent) or a batching function
that loops over encoded sub-calls and dispatches them internally; no CALL
opcode of any kind exists to be batched. Both specific bypass vectors named in
the brief are structurally absent from this contract's code.

[Medium, unverifiable without source] 4. dailyCap/rate-limit resets are timestamp-rolling, not calendar-day buckets — plausible boundary-timing weakness

ScopedDelegation (rate-limit logic, multiple offsets) · Confidence: 55

Description: The bytecode contains no DIV or MOD opcode anywhere.
A calendar-day-bucket implementation (block.timestamp / 1 days to compute a
day index) requires DIV; its total absence across the whole contract rules
that pattern out. Every time-based check instead follows the shape SLOAD (stored timestamp) → TIMESTAMP → LT/GT → conditional jump, and resets follow
the shape TIMESTAMP → ADD (add a period constant) → SSTORE (e.g. offsets
0x0216–0x021c, 0x068e–0x0693, 0x07ee–0x07f4, 0x0c74–0x0c7a).
This is the signature of a rolling window — "has period seconds elapsed
since lastReset?" — not a UTC-midnight bucket.

This rules out the classic calendar-boundary bug the client asked about
(a cap trivially resetting right at UTC midnight), but rolling windows have
their own well-known weakness: if the check is timestamp < lastReset + period with no additional bucketing, a grantee can spend the full cap right
before a window rolls over and again right after, extracting close to 2×
the intended cap in a short interval. This cannot be confirmed as an actual
bug without the source-level formula (need to see the exact comparator —
< vs <= — and whether lastReset is updated per-transaction or only on
full-window rollover); flagged as a Lead for source-level follow-up rather
than a confirmed finding.

Recommendation: on re-audit with source, confirm whether lastReset is
updated (a) once when the window is first crossed, or (b) on every
transaction (which would make it a sliding window with a different, generally
worse, property — effectively no reliable cap at all under steady
transaction flow). Consider fixed calendar-day or fixed-epoch bucketing if a
hard daily ceiling is the actual intent.

Leads

Trails with concrete code smells where the full exploit path could not be
completed without source — high-signal but not independently verifiable
from bytecode alone.

  • Expiry off-by-one — ScopedDelegation (scope-expiry check) — Code
    smell: SLOAD → TIMESTAMP → LT pattern recurs at 5+ sites (e.g. 0x0218,
    0x05e9, 0x1cf8, 0x1d22); operand order before LT (i.e. whether the
    check is expiry < now or now < expiry, and whether it's strict or would
    need LT+EQ/ISZERO combinations for <=) could not be reliably
    resolved from raw opcodes without symbolic stack tracing across 12+
    intervening jumps per site. Recommend a direct source-level check of
    whether a scope is valid at exactly its expiry timestamp or one second
    before/after, per the client's specific ask.
  • Revocation atomicity — ScopedDelegation (revoke path, selector
    unresolved — likely one of 0x9a803b9a, 0x9c91614f, 0xe4b7d622,
    0xe9a593ac, 0xeebcf633, 0xf34e49c2, none of which resolve in public
    4byte/openchain signature databases) — Code smell: cannot trace SSTORE
    ordering across a revoke function from raw bytecode with confidence high
    enough to assert atomicity one way or the other. Needs source.
  • Parent/child scope accounting — the revert strings "exceeds parent remaining", "...restrictive than parent", and "parent scope e[xceeded]"
    indicate a scope-inheritance/chain-depth model (MAX_CHAIN_DEPTH(),
    chains(uint256) both resolve via openchain.xyz signature DB). Recursive
    or chained scope budget accounting is a classic source of double-spend /
    rounding bugs in delegation systems and should be a priority checklist item
    once source is available — no such review was possible here.

Recommendation

The single highest-value next step is source verification. Once verified
(or a GitHub repo is provided), a full two-phase audit (ethskills 20-domain
checklist breadth + pashov 12-agent attacker-mindset depth, reconciled) can
directly confirm or refute Findings 1 and 4 above and resolve both Leads with
concrete line-quoted proof, per this audit's normal verification standard.
Finding 1 in particular — the complete absence of any CALL/DELEGATECALL
in the deployed code — is significant enough that it should be resolved
before this contract is treated as a functioning enforcement point in
production.
