Findings

[M1] cancel() and permissionless emergencyRecover() can preempt an already oracle-signed settle() payload

Severity: Medium
Confidence: 85
Origin: [phase2] — independently raised via two entrypoints (trust-gap agent: cancel(); execution-trace agent: emergencyRecover()), corroborated as a lead by the economic-security agent
Location: cancel() L251-257; emergencyRecover() L335-343; both via _returnPrizeToCreator() L392-398; contrasted with settle() L276-322 (onlyActive L280, oracle signature check L291)

Description: settle()'s payout authorization is cryptographic — an EIP-712 signature from oracle over the exact winners/bpsSplit (L291). cancel()'s authorization is a bare msg.sender ∈ {creator, oracle} check (L138-141) with no signature and no check that a valid settlement already exists or is in flight. Both functions gate on the same status variable (L84) and race for the same prizePool; whichever transaction mines first wins outright and the loser reverts (settle() via onlyActive, L280). This lets creator (or oracle) unilaterally override a legitimate, already-signed settlement, redirecting the entire pool to creator instead of the winners the oracle determined — directly contradicting the contract's own documented trust model: "Settlement requires ONE oracle signature over the winner list and splits... the oracle... derives winners deterministically" (header comment, L9-14). The permissionless emergencyRecover() variant extends the same race to any address at the kickoffTime+60d boundary: a bystander can front-run a merely-late-but-legitimate settle() transaction the instant the window opens; the swept funds still land with creator regardless of who triggers it, so this is primarily a griefing/timing vector that benefits the creator, not the triggering caller.

Proof of Concept: Pool = 100,000 USDC. Oracle computes off-chain and signs Settle(escrow, [Alice], [10000]), then broadcasts a settle() transaction. Before it mines, creator submits cancel() (no signature required, valid while status != Completed/Cancelled, L252-253) with a higher priority fee. cancel() lands first: status → Cancelled (L254), _returnPrizeToCreator() credits pendingWithdrawal[creator] += 100,000e6 (L394-398). The pending settle() transaction then reverts NotActive() (L280). Alice — the oracle's named winner — receives nothing; creator claims the full pool via claimPendingWithdrawal(creator).

Recommendation: Require settle() to have priority once a valid oracle signature for the pot has been produced — e.g., an oracle-signed "commit-to-settle" step that blocks cancel() once issued — or require cancel() itself to carry an oracle co-signature, matching the cryptographic bar already applied to settle(). At minimum, restrict the first period after kickoffTime+60d to oracle/creator before opening emergencyRecover() to arbitrary callers, so a merely-late oracle retains a real window to finalize.

[M2] Sponsor prize contributions have no refund path and are swept entirely to creator on cancellation

Severity: Medium
Confidence: 95
Origin: [both] — phase-1 evm-audit-access-control (access-control-1); phase-2 first-principles agent raised as FINDING, independently corroborated as leads by 5 additional phase-2 agents (access-control, economic-security, invariant, asymmetry, trust-gap, flow-gap — 6 of 12 total)
Location: fundPrize() L184-189 (permissionless, single pooled prizePool counter, no per-funder bookkeeping); cancel() L251-257 and emergencyRecover() L335-343 via _returnPrizeToCreator() L392-398 (unconditionally credits 100% of prizePool to creator)

Description: fundPrize() is explicitly documented as open to any sponsor ("Open to anyone so a sponsor can top up directly," L179-182). cancel() is callable by creator/oracle "at any time" pre-Completed (L251), with no minimum-entries or elapsed-time gate — the contract's own comment notes the "fewer than 2 entries" house policy is explicitly "not enforced on-chain" (L249). Both cancel() and emergencyRecover() route the entire prizePool — sponsor top-ups included — to creator (L396), with no per-funder accounting or refund mechanism anywhere in the contract.

Proof of Concept: 1) Sponsor S calls fundPrize(1_000e6) while the pot is Open. 2) creator (or oracle) immediately calls cancel() — no entries required, no elapsed time required, this is normal documented behavior. 3) _returnPrizeToCreator() credits pendingWithdrawal[creator] += 1_000e6. 4) creator calls claimPendingWithdrawal(creator) and receives S's entire 1,000 USDC deposit; S has zero on-chain recourse.

Recommendation: Track contributions per-funder (mapping(address => uint256) contributions) in fundPrize(), and refund cancellations pro-rata to actual funders instead of unconditionally crediting creator; alternatively, restrict fundPrize() to creator-only if third-party sponsorship funds aren't meant to survive unilateral cancellation.

[M3] settle() never validates that winners are recorded entrants, widening the blast radius of oracle-key compromise

Severity: Medium
Confidence: 90
Origin: [phase1-only] — evm-audit-access-control (access-control-2)
Location: settle() L276-322; entryHashes (L89) / players (L92) never read here

Description: The sole authorization for settle()'s fund distribution is the oracle's EIP-712 signature (L291) — it is never cross-checked against entryHashes[winners[i]] != bytes32(0) or the players roster. A compromised or malicious-but-validly-signing oracle key can direct 100% of prizePool to any arbitrary address, including addresses that never called submitEntry(), with no additional on-chain guardrail. This turns a key compromise from "attacker skews payouts among legitimate winners" into "attacker unconditionally drains the entire pool to itself" — a materially larger and easily-preventable blast radius, and a defense-in-depth gap the contract's own design (per-pot escrow, immutable oracle key with no rotation) makes especially costly since there is no way to recover from a compromised key mid-pot other than the 60-day emergencyRecover() fallback (which itself routes to creator, not back to legitimate entrants).

Proof of Concept: An attacker who obtains the oracle's signing key crafts and signs a Settle payload with winners = [attacker], bpsSplit = [10000], where attacker never called submitEntry(). Since settle() is callable by anyone (auth is purely via signature recovery, L280-291) and never checks entryHashes[attacker], the call succeeds and credits the full prizePool to attacker's pendingWithdrawal, claimable via claimPendingWithdrawal(attacker).

Recommendation: Require entryHashes[winners[i]] != bytes32(0) for every winner in settle(), reverting otherwise — a cheap, defense-in-depth bound on the oracle's spending authority to the actual entrant set.

[H1] Immutable, unrotatable creator address is a single point of failure for every pool-return path if blocklisted by the USDC issuer

Severity: High
Confidence: 80
Origin: [phase1-only] — evm-audit-erc20 (erc20-1)
Location: _returnPrizeToCreator() L392-398, called from cancel() L251-257 and emergencyRecover() L335-343; realized via claimPendingWithdrawal() L354-360

Description: Every path that returns prizePool to creator credits pendingWithdrawal[creator] (L396). creator is immutable — set once at construction (L162), zero-address-checked only (L158) — with no transfer, no admin recovery, no alternate-recipient mechanism, and the contract is not upgradeable. USDC is issuer-blocklistable (Circle can freeze any address for OFAC/compliance reasons, independent of this contract). If creator is ever blocklisted — before or after prizePool has been credited to it — usdc.safeTransfer(creator, amt) in claimPendingWithdrawal() (L358) reverts every time it is attempted, permanently locking the entire returned pool with zero on-chain recovery path, since status is already terminal (Cancelled) and no function can redirect the credited balance.

Proof of Concept: 1) Creator deploys and funds a pot via fundPrize(). 2) Independent of this contract, Circle blocklists the creator address on USDC. 3) cancel() or emergencyRecover() succeeds regardless (pure internal accounting, no external call at this step) and credits pendingWithdrawal[creator]. 4) claimPendingWithdrawal(creator) reverts forever — the funds are permanently stuck with no redirect mechanism.

Recommendation: Add a fallback/rotatable payout address for the creator-return path (e.g., a two-step, oracle-co-signed address-update function), or a documented/permissioned recovery sweep for exactly this scenario.

[L1] Settle struct's address[] field hashed with non-standard packed encoding, deviating from the EIP-712 spec

Severity: Low
Confidence: 90
Origin: [both] — phase-1 evm-audit-signatures (signatures-1); independently raised by 3 phase-2 agents (execution-trace, periphery, asymmetry) — strong cross-phase corroboration on the exact same root cause
Location: _settlementDigest() L400-411, specifically L407 (keccak256(abi.encodePacked(winners)))

Description: SETTLE_TYPEHASH declares address[] winners (L69-70). Per the EIP-712 spec, a dynamic array field's hash is the concatenation of each element's standard 32-byte-padded ABI word (what abi.encode per-element produces, and what every standards-compliant eth_signTypedData_v4 implementation — ethers.js, viem, MetaMask, hardware wallets — computes). This contract instead packs each address as 20 raw bytes (abi.encodePacked), a different encoding than the declared type implies (bpsSplit's packed vs. padded sizes are identical for uint256, so that field is unaffected).

Proof of Concept: A genuine standards-compliant EIP-712 signer produces a signature that will NOT match _settlementDigest()'s output, causing settle() to permanently revert BadOracleSignature() for that payload. The contract only works today because the oracle backend evidently calls the exposed settlementDigest() view directly and raw-signs the returned hash, bypassing standard typed-data tooling — not attacker-exploitable for fund theft, but a real operational footgun if the oracle's signing stack is ever migrated to standard tooling or a third-party co-signer/hardware-wallet workflow.

Recommendation: Hash winners per the EIP-712 spec (loop-concatenate 32-byte-padded elements via abi.encode), or explicitly document this as a non-standard, custom scheme incompatible with generic eth_signTypedData_v4 signers.

[L2] DOMAIN_SEPARATOR cached as immutable at deploy time with no fork-recomputation fallback

Severity: Low
Confidence: 75
Origin: [both] — phase-1 evm-audit-signatures (signatures-3) and evm-audit-chain-specific (chain-specific-1, reached independently via the Base/OP-Stack lens); corroborated by 5 phase-2 agents
Location: L79, constructor L167-173

Description: Correctly includes block.chainid and address(this) at deployment (cross-chain/cross-contract binding IS present), but unlike OpenZeppelin's EIP712._domainSeparatorV4(), there is no runtime fallback recomputation if block.chainid changes post-deployment (a contentious hard fork or L2 chain-ID reassignment). Both _entryDigest/_settlementDigest read the cached value verbatim regardless of the live chain ID.

Proof of Concept: Hypothetical only — requires a chain split/renumbering event during a pot's short (days-to-60-day) lifecycle. Base is a single, centrally-sequenced OP-Stack chain (8453); a contentious fork producing two live chains sharing this contract's pre-fork state is unlikely, and even then both post-fork chains would start from identical state, so a stale-separator-signed payload replayed across both forks authorizes the same intended action on each — not attacker-favorable divergence. No current exploit path on Base.

Recommendation: Mirror OpenZeppelin's dynamic-recompute-on-mismatch pattern if the deployment target is considered fork-risk-sensitive, or accept the risk given Base's low fork likelihood.

[L3] _recoverSigner lacks signature-malleability and v-range validation

Severity: Low
Confidence: 70
Origin: [both] — phase-1 evm-audit-general (general-4) and evm-audit-signatures (signatures-2), merged (same function, same root cause, reported by two domain checklists); corroborated by 9 of 12 phase-2 agents
Location: _recoverSigner() L425-440

Description: Unlike OpenZeppelin's ECDSA.recover, this custom implementation has no check that s is in the lower half of the curve order (no malleability check), and only loosely normalizes v (if (v < 27) v += 27;) without rejecting other out-of-range values. Reused identically by both submitEntry (player auth) and settle (oracle auth) — one root-cause class hitting both signature-verification surfaces in the contract.

Proof of Concept: Not independently exploitable in the current contract — every consumer of _recoverSigner's output keys replay protection off contract state (entryHashes[player] dedup for entries; the one-shot Active→Completed status transition for settlement), not off signature bytes/hash, so a malleable alternate encoding of a captured signature does not enable double-execution today. All 9 phase-2 agents that examined this independently confirmed no live exploit path. Flagged as a hardening gap: any future feature that keys uniqueness off a signature hash (a usedSignatures mapping, a meta-tx nonce derived from sig hash) would inherit a live double-spend/replay primitive from day one.

Recommendation: Replace the custom assembly-based recovery with OpenZeppelin's ECDSA.recover, or add explicit s <= secp256k1n/2 and v ∈ {27,28} checks.

[L4] NatSpec claims 64-or-65-byte signatures are accepted; _recoverSigner only accepts 65, and misreports the error on the entry path

Severity: Low
Confidence: 95
Origin: [both] — phase-1 evm-audit-general (general-3); corroborated by 7 of 12 phase-2 agents
Location: submitEntry() NatSpec L207-208; _recoverSigner() L429

Description: The doc comment states playerSig may be "64 or 65-byte," implying EIP-2098 compact-signature support. _recoverSigner hard-reverts (BadOracleSignature()) on any length other than exactly 65 (L429) — there is no code path that decompresses a 64-byte compact signature into (r,s,v). Additionally, the revert is always BadOracleSignature() even when reached from the submitEntry (player) path, misusing the dedicated BadEntrySignature error for this case.

Proof of Concept: Any client/wallet library producing EIP-2098 compact signatures — as the docs claim is supported — will have every submitEntry/settle call using that format revert, contradicting the documented interface. Fails closed (not a bypass), but a real functional/integration-correctness gap.

Recommendation: Either implement EIP-2098 compact-signature support, or correct the NatSpec to state only standard 65-byte signatures are accepted. Pass/select the correct error per call site.

[L5] settle() has no check that winners[i] (or creator) is not the usdc token contract itself

Severity: Low
Confidence: 70
Origin: [phase1-only] — evm-audit-erc20 (erc20-3)
Location: settle() L305, L316 (winner == address(0) || winner == address(this) — no == address(usdc) check); same gap for creator in the constructor / _returnPrizeToCreator()

Description: Standard USDC does not block transfers to its own contract address; such a transfer would strand funds permanently with no recovery. settle() guards against address(0)/address(this) but not address(usdc).

Proof of Concept: Requires the trusted oracle to sign a payload containing address(usdc) as a winner (backend data bug), or creator == address(usdc) at deploy (misconfiguration) — not a third-party attack vector, but an easily-preventable, irreversible-loss latent bug.

Recommendation: Extend the guard to also reject winner == address(usdc), and check _creator != _usdc at construction.

[L6] fundPrize() credits prizePool from the requested amount, not a measured balance delta

Severity: Low
Confidence: 65
Origin: [both] — phase-1 evm-audit-erc20 (erc20-2); corroborated by the phase-2 economic-security agent
Location: fundPrize() L184-189

Description: prizePool += amount (L187) uses the caller-supplied parameter rather than measuring balanceAfter - balanceBefore. Safe for plain-vanilla USDC (no fee-on-transfer, no max-uint balance semantics) but usdc is only zero-address-checked at construction (L158) with no interface/behavior validation, and is immutable thereafter.

Proof of Concept: Not exploitable against real mainnet/Base USDC. Latent gap only if a future deployment mistakenly wires in a fee-on-transfer or balance-capping token — prizePool would then permanently exceed the real balance, and the last claimant(s) after settlement would find claimPendingWithdrawal reverting for lack of funds.

Recommendation: Measure the actual received amount via balance delta instead of trusting the parameter, or document the hard USDC-only assumption clearly.

[L7] Direct USDC transfers to the contract bypass prizePool accounting and become permanently stuck

Severity: Low
Confidence: 90
Origin: [phase1-only] — evm-audit-general (general-6)
Location: fundPrize() L184-189; contract-wide (no sweep function)

Description: prizePool is credited only by the amount parameter (L187), never by measuring usdc.balanceOf(address(this)). Any USDC sent directly via a raw transfer() bypassing fundPrize() is never reflected in prizePool and is unrecoverable — no function anywhere reads the contract's actual token balance.

Proof of Concept: Any direct transfer to the contract address is permanently stuck.

Recommendation: Document clearly for integrators/sponsors, or add a permissioned sweep for accidental transfers.

[I1] kickoffTime has no upper bound, risking a permanently-bricked emergencyRecover() fallback

Severity: Info
Confidence: 40
Origin: [phase2-only] — numerical-gap agent (lead)
Location: Constructor L160 (only checks _kickoffTime > block.timestamp, no upper bound); emergencyRecover() L338 (kickoffTime + EMERGENCY_WINDOW, checked 0.8.x arithmetic)

Description: If kickoffTime is ever set close enough to type(uint256).max that adding 60 days overflows, every future call to emergencyRecover() reverts unconditionally — the contract's own documented last-resort fallback ("the prize can be recovered even if the TopPot backend is permanently offline," L43-44) becomes permanently unreachable. Requires the trusted creator to supply a pathological, immutable kickoffTime at deploy — an admin self-harm precondition with no external attacker path, and no realistic unit-mistake (e.g., milliseconds vs. seconds) reaches the overflow threshold.

Recommendation: Add a sane upper-bound check on _kickoffTime in the constructor (e.g., reject values beyond block.timestamp + N years) as cheap defense-in-depth.

[I2] Settle signed payloads have no nonce/deadline field

Severity: Info
Confidence: 45
Origin: [phase2-only] — economic-security agent (lead)
Location: SETTLE_TYPEHASH L69-70; settle() L276-322

Description: The signed struct Settle(address escrow, address[] winners, uint256[] bpsSplit) has no nonce or deadline field. Once the oracle signs a settlement payload, it remains valid and executable by anyone forever (until consumed by a successful settle() call). If the oracle backend ever produces more than one signed settlement candidate for the same pot before finalizing (a corrected split after a scoring bug, a staging/preview signature), whichever lands on-chain first executes permanently with no on-chain revocation path. Off-chain oracle single-submission discipline cannot be verified from source alone.

Recommendation: Add a deadline and/or nonce field to SETTLE_TYPEHASH so stale/superseded signed payloads can be invalidated.

[I3] _returnPrizeToCreator() credits without emitting an amount-bearing event

Severity: Info
Confidence: 90
Origin: [phase2-only] — asymmetry agent (lead)
Location: _returnPrizeToCreator() L392-398 (no emit, contrasted with settle()'s PrizePaid at L310/L319)

Description: settle() emits PrizePaid(winner, payout) for every credit it makes. _returnPrizeToCreator() — used by both cancel() and emergencyRecover() — credits pendingWithdrawal[creator] += pool with no amount-bearing event (PotCancelled() carries no amount). Off-chain indexers/accounting reconstructing pending balances purely from events would silently miss creator refunds. Not fund-losing — storage remains correct and claimPendingWithdrawal still works.

Recommendation: Add an event (e.g., PrizeReturned(address indexed creator, uint256 amount)) in _returnPrizeToCreator().

[I4] nonReentrant is not the first modifier on submitEntry() and settle()

Severity: Info
