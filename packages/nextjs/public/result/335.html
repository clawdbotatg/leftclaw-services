Findings

[H-1] Permissionless reportSurveillanceViolation() reuses the owner-gated ban event, letting anyone emit a spoofed "official ban" signal

Severity: High
Origin: [both] — phase 1 (general, access-control, dos) + phase 2 (11 of 12 attack agents; 7 independently reached FINDING-grade proof, conf. 80)
Location: reportSurveillanceViolation() (lines 105-113) vs. banModuleForSurveillance() (lines 116-125); shared event ModuleBannedForSurveillance (lines 73-79)

Description: reportSurveillanceViolation is fully permissionless — its only guard is evidenceHash != bytes32(0), trivially satisfied by any garbage hash. It emits the identical event, ModuleBannedForSurveillance (same name, same three indexed topics), that the onlyOwner-gated banModuleForSurveillance() emits for a genuine enforcement action. The only on-chain differentiator is reasonHash == 0 for reports vs. non-zero for real bans (banModuleForSurveillance requires reasonHash != 0 at line 120) — a convention documented only in a Solidity comment, not encoded in the event schema itself, and the reporter's address (msg.sender) is not included in the event at all. This directly undermines the contract's own stated design goal ("Public reporting is non-binding (prevents griefing/DoS)," lines 12, 100-103): the state-level guarantee holds (bannedForSurveillance[module] is never touched by the report path), but the event-log guarantee does not — the exact griefing surface the contract claims to prevent is achieved one layer up, at the event/interface boundary that off-chain indexers, dashboards, and any downstream integration actually consume.

Proof of Concept:

  1. Attacker (any EOA, no privileges, no prior relationship to module) calls reportSurveillanceViolation(victimModule, BannedDataType.BIOMETRIC_DATA, keccak256("fabricated")).
  2. Only guard require(evidenceHash != bytes32(0), ...) (line 109) passes trivially.
  3. Contract emits ModuleBannedForSurveillance(victimModule, BIOMETRIC_DATA, reasonHash=0x0, evidenceHash=keccak256("fabricated"), block.timestamp) — topic0 = keccak256("ModuleBannedForSurveillance(address,uint8,bytes32,bytes32,uint256)"), byte-for-byte identical to what banModuleForSurveillance would emit for a real ban.
  4. bannedForSurveillance[victimModule] remains false on-chain, but any off-chain indexer/dashboard/bot/partner protocol filtering on the ModuleBannedForSurveillance topic — the natural integration pattern given the event's own name — displays or acts on victimModule as banned, with no owner action and no real evidence involved.
  5. Cost is near-zero (no storage writes, ~30-40k gas), repeatable indefinitely against any address.

Recommendation: Use a distinct event name for the permissionless report path, and include the reporter's address:

+    event SurveillanceViolationReported(
+        address indexed module,
+        BannedDataType violationType,
+        bytes32 indexed evidenceHash,
+        address indexed reporter,
+        uint256 timestamp
+    );

     function reportSurveillanceViolation(address module, BannedDataType violationType, bytes32 evidenceHash)
         external
     {
         require(evidenceHash != bytes32(0), "Evidence hash required");
-        emit ModuleBannedForSurveillance(module, violationType, bytes32(0), evidenceHash, block.timestamp);
+        emit SurveillanceViolationReported(module, violationType, evidenceHash, msg.sender, block.timestamp);
     }

Reserve ModuleBannedForSurveillance exclusively for the onlyOwner path so binding governance bans and non-binding public accusations are never topic-collidable.

[H-2] Owner key loss permanently disables every enforcement function, with no recovery path

Severity: High
Origin: [phase1: governance] — confirmed via hybrid re-read
Location: owner (line 20), onlyOwner modifier (24-27), all gated functions (93-98, 116-125, 128-130, 136-142)

Description: Exactly one address controls every privileged action in the contract, including transferOwnership itself (onlyOwner-gated, line 93). There is no backup admin, no multisig enforced in code (only in a comment — see M-3), and no recovery mechanism of any kind. If the owner's private key is lost or destroyed, banModuleForSurveillance, unbanModule, and verifyModuleSurveillanceFree become permanently uncallable by anyone: a wrongly-banned module can never be unbanned on appeal, and no new module can ever be verified again. State freezes forever at whatever it was at the moment of key loss — a permanent denial-of-service of the entire enforcement mechanism this contract exists to provide.

Proof of Concept: Confirmed by direct read of lines 20-27 and 93-98: owner is a plain address state variable set once in the constructor (owner = msg.sender); every state-changing function checks require(msg.sender == owner, "Only owner") with no fallback branch, no second role, and no time-locked recovery path. If the key controlling owner is lost, every one of these require statements reverts forever for every possible caller.

Recommendation: Use a genuine multisig (e.g., a Gnosis Safe with a sensible threshold such as 3-of-5) as owner rather than a single EOA, so no single lost key disables the contract. Combine with a two-step ownership-transfer pattern (see L-3) to reduce the risk of an irreversible mistake during any future handoff.

[M-1] Ban → unban does not reset verification state; a module can be verifyModuleSurveillanceFree'd exactly once, ever

Severity: Medium
Origin: [both] — phase 1 (general, detailed) + phase 2 (5 of 12 agents independently converged; formally excluded from pashov's strict FINDING list only because the full path requires the owner's own ban→unban sequence with no unprivileged amplifier — the underlying code defect was re-confirmed directly against source, see below)
Location: banModuleForSurveillance() (116-125), unbanModule() (128-130), verifyModuleSurveillanceFree() (136-142), surveillanceFreeModules (line 58)

Description: surveillanceFreeModules[module] is written exactly once, at verification time, and is never reset by any other function. Confirmed by re-reading lines 116-130: banModuleForSurveillance sets bannedForSurveillance[module] = true but never touches surveillanceFreeModules; unbanModule sets bannedForSurveillance[module] = false and likewise never touches it. Consequently, banning a previously-verified module and later unbanning it (e.g., a successful appeal) silently and automatically restores "surveillance-free" status via the surveillanceFreeOnly modifier, using the original, stale verification timestamp — no new review, no new event. Symmetrically, because verifyModuleSurveillanceFree() requires surveillanceFreeModules[module] == 0 (line 138), a module that has ever been verified can never be re-verified — governance has no way to force a fresh attestation after a ban/appeal cycle or a module code change, short of a mechanism this contract does not provide.

Proof of Concept: Owner verifies moduleA at t0 (surveillanceFreeModules[moduleA] = t0). Owner bans moduleA at t1 for a genuine violation (bannedForSurveillance[moduleA] = true; surveillanceFreeModules[moduleA] unchanged). Owner unbans moduleA at t2 on appeal (bannedForSurveillance[moduleA] = false). Immediately, surveillanceFreeOnly(moduleA) passes again using the stale t0 timestamp — with zero fresh review — and any subsequent verifyModuleSurveillanceFree(moduleA) call reverts with "Module already verified".

Recommendation:

     function banModuleForSurveillance(address module, BannedDataType violationType, bytes32 reasonHash, bytes32 evidenceHash)
         external
         onlyOwner
     {
         require(reasonHash != bytes32(0), "Reason hash required");
         require(evidenceHash != bytes32(0), "Evidence hash required");

         bannedForSurveillance[module] = true;
+        surveillanceFreeModules[module] = 0;
         emit ModuleBannedForSurveillance(module, violationType, reasonHash, evidenceHash, block.timestamp);
     }

This forces a fresh verifyModuleSurveillanceFree() call (which will now succeed again post-unban) before a previously-banned module is trusted again.

[M-2] evidenceHash/reasonHash are unenforced raw bytes32 — the permissionless path can publish identifying data despite the "hash-only, no PII" design intent

Severity: Medium
Origin: [phase1: general]
Location: reportSurveillanceViolation() line 109, banModuleForSurveillance() lines 120-121

Description: This is the client's first explicit ask ("any code path that emits identifying data despite the guard"). The contract's stated privacy guarantee rests on using "hashes only to avoid writing evidence/reason text (potential PII) on-chain" (lines 11, 70-71). Solidity cannot enforce that a bytes32 parameter is actually a hash digest rather than raw data — a short name, an encoded identifier, or a truncated string fits comfortably in 32 bytes. Because reportSurveillanceViolation() requires no permission at all, any external caller can permanently and publicly log short identifying data on-chain, indexed and forever discoverable via topic filters — precisely the outcome the "hash-only" design was meant to prevent.

Proof of Concept: reportSurveillanceViolation(module, BannedDataType.SOCIAL_GRAPH_MINING, bytes32("jane.doe@example.com")) passes the only check present (evidenceHash != bytes32(0), line 109) and is emitted as a permanent, public, indexed topic. Nothing in the contract distinguishes this from a legitimate keccak256 digest.

Recommendation: This cannot be fully solved on-chain (a contract can never prove a bytes32 was produced by hashing). Mitigate with: an off-chain preimage-disclosure schema governance can verify before any enforcement action; NatSpec/ABI-level warnings that these fields are trusted-input-only and unvalidated; and a bond or per-caller rate limit on the permissionless path (also mitigates L-1).

[M-3] No timelock on any privileged admin action (ban / unban / verify / ownership transfer)

Severity: Medium
Origin: [phase1: access-control, governance]
Location: banModuleForSurveillance(), unbanModule(), verifyModuleSurveillanceFree(), transferOwnership()

Description: All owner-gated state changes take effect atomically within the calling transaction — no delay, queueing, or grace period. Any integrator gating on surveillanceFreeOnly gets zero notice window before a module they depend on is banned, or before an unaudited module is declared "surveillance-free."

Proof of Concept: Owner calls banModuleForSurveillance(legitModule, ...); any downstream consumer of surveillanceFreeOnly(legitModule) breaks in the same block with no advance warning.

Recommendation: Add a propose/execute pattern with a fixed minimum delay for these four functions (e.g., OpenZeppelin TimelockController, or a custom pendingChange + executeAfter(block.timestamp) guard).

[M-4] Single EOA owner — trust model claimed as "governance/multisig/DAO" in NatSpec but not enforced in code

Severity: Medium
Origin: [phase1: access-control, governance]
Location: owner (line 20), onlyOwner modifier (24-27); NatSpec lines 6, 13, 19, 100-103, 115, 127, 132-135

Description: This is the client's second explicit ask ("access control on toggles"). NatSpec repeatedly says "governance-controlled," "multisig/DAO in production," and labels functions "Governance/admin action" — but the actual implementation is one EOA with a plain require(msg.sender == owner). There is no multisig, DAO, voting, or quorum logic anywhere in the contract. A single compromised or malicious key can falsely verifyModuleSurveillanceFree a violating module, ban a legitimate competitor, or silently unban a genuine violator — all with attacker-chosen reasonHash/evidenceHash that are only checked for non-zero, never validated against real evidence.

Proof of Concept: N/A (design/documentation-mismatch, not a code bypass) — the access control itself is correctly implemented (no bypass found in either audit phase); the finding is that the trust model advertised in the docs does not match what the code enforces.

Recommendation: Enforce the multisig/DAO requirement in code (e.g., require owner be a Safe contract address at deploy time, or migrate to role-based access held by a multisig) rather than only in comments; correct the NatSpec if not implementing this before production use.

[L-1] reportSurveillanceViolation() has no rate limit — cheap, unbounded log spam can bury genuine ban events

Severity: Low
Origin: [both] — phase 1 (dos) + phase 2 (1 agent, lead)
Location: reportSurveillanceViolation() (105-113)

Description: No storage writes occur, so each call costs little beyond base tx gas. No per-caller cooldown, no per-module cap, no fee, no uniqueness constraint on evidenceHash. Compounds H-1: an attacker can flood the ModuleBannedForSurveillance log stream, degrading it as a reliable audit trail.

Recommendation: Add a bond/fee or a per-caller/per-module cooldown; pair with H-1's distinct-event fix so consumers can trivially filter by reporter.

[L-2] unbanModule() emits no event

Severity: Low
Origin: [phase1: general, access-control] — independently flagged pre-gate by 2 of 12 phase-2 agents but formally excluded from the phase-2 report under the pashov methodology's "Do Not Report: missing events" rule
Location: unbanModule() (128-130)

Description: Unlike banModuleForSurveillance and verifyModuleSurveillanceFree, unbanModule performs a state change with no corresponding log. Event-only consumers will show a stale "banned" state indefinitely after a legitimate unban.

Recommendation:

+    event ModuleUnbanned(address indexed module, uint256 timestamp);
+
     function unbanModule(address module) external onlyOwner {
         bannedForSurveillance[module] = false;
+        emit ModuleUnbanned(module, block.timestamp);
     }

[L-3] transferOwnership() is single-step with no accept/claim

Severity: Low
Origin: [phase1: general, access-control]
Location: transferOwnership() (93-98)

Description: Only a zero-address check guards newOwner; there is no pending-owner/acceptOwnership() step. A typo'd or unreachable newOwner permanently and irrecoverably disables every privileged function in the contract (compounds H-2 — no recovery path exists once this happens, since transferOwnership itself requires onlyOwner).

Recommendation: Implement an Ownable2Step-style two-step transfer (pendingOwner + acceptOwnership()).

[L-4] surveillanceFreeOnly modifier is unused within this contract and binds on a caller-supplied module parameter rather than msg.sender

Severity: Low
Origin: [phase2] — 5 of 12 attack agents independently converged; confirmed via hybrid re-read (new finding not surfaced by phase 1)
Location: surveillanceFreeOnly modifier (83-87)

Description: Confirmed by re-read: this modifier is declared but applied to zero functions in this file — it is dead code as shipped, presumably intended for a downstream/out-of-scope contract to reuse. Two compounding issues for any future integrator: (1) as a concrete, non-abstract deployed singleton, this contract's modifier cannot actually be "inherited" by a separately-deployed contract — a downstream integrator would need to re-implement the same checks via external calls to the public mappings, making the NatSpec's claim that restricting verifyModuleSurveillanceFree "preserves the integrity of any downstream gating" (line 134) an overstatement of what the contract actually provides; (2) if the modifier pattern is copied downstream, note it validates whatever module address is passed in as a parameter, not msg.sender — a downstream function like doThing(address module) external surveillanceFreeOnly(module) { ... acts on msg.sender ... } would let an unverified caller "borrow" a verified third party's address to pass the gate. Not exploitable within this contract's own scope (Gate 2: no consuming function exists here), but worth flagging for any integration.

Recommendation: If reused downstream, bind the check to msg.sender explicitly (or require module == msg.sender at the call site) rather than trusting a caller-supplied address; document clearly that this modifier is not automatically inherited by separately-deployed contracts.

[I-1] isDataTypeBanned() ignores its input parameter and always returns true

Severity: Info
Origin: [phase1: general]
Location: lines 153-156

Description: Signature implies a per-type lookup; body discards dataType. Internally consistent with the design (every enum member is permanently banned) but potentially misleading to integrators expecting a real conditional check.

Recommendation: Drop the parameter, or add a NatSpec comment clarifying that all BannedDataType values are permanently banned by design.

[I-2] No zero-address validation on module in ban/verify functions

Severity: Info
Origin: [phase1: general]
Location: banModuleForSurveillance() line 116, verifyModuleSurveillanceFree() line 136

Description: module is never checked against address(0). No meaningful security impact (address(0) can never be a real module), but is a minor hygiene gap for admin-input mistakes.

Recommendation: Optional require(module != address(0), "Invalid module") for defense-in-depth.

[I-3] SurveillanceAttemptBlocked event is declared but never emitted

Severity: Info
Origin: [phase2] — 2 of 12 attack agents; confirmed via re-read (new finding not surfaced by phase 1)
Location: line 81

Description: Confirmed by grep: event SurveillanceAttemptBlocked(address indexed attacker, BannedDataType attemptedType, uint256 timestamp); has no corresponding emit anywhere in the contract. This is dead code, suggesting an enforcement/blocking signal that was planned but never wired up. No state or security impact on its own, but any off-chain system expecting this event as a live signal will never receive it.

Recommendation: Either remove the unused declaration or implement the intended emission path if blocking logic is added in a future version.
