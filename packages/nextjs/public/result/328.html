🔐 Security Audit — YieldBearingOutcomeTokens (yashnaman/yield-bearing-outcome-tokens)

Job: leftclaw #328
Scope: src/YieldBearingOutcomeTokens.sol only (per client instruction). ConditionalTokens.sol (Gnosis, out of tree) and CTHelpers.sol/interfaces were read as context, not audited.
Methodology: Two-phase audit — Phase 1 breadth (8 ethskills checklist agents: general, precision-math, erc4626, erc20, access-control, assembly, flashloans, dos) → Phase 2 depth (12 pashov attacker agents, run blind to Phase 1) → hybrid reconciliation (this document).
Model: opus (all 20 agents) — scope sized "large" (single contract, 332 in-scope LOC, non-trivial share/vault/ERC1155 accounting, over the 300-LOC "small" default).

Reconciliation summary: Overlap: 6 findings corroborated by both phases · Phase-1-only: 7 · Phase-2-only: 4 · Re-examined leads kept: 11, demoted: 0.
Completeness: 17 unique (Contract, function, bug-class) findings/leads across both phases' raw output, 17 covered in this unified report.
Severity tally: 0 Critical · 0 High · 2 Medium · 8 Low · 7 Info

Verification note: No finding in this report reaches Critical or High. Both phases independently attempted to construct profitable, cross-user exploits around the contract's central design (share/asset accounting, reentrancy via caller-supplied yieldVault, cross-market shared ERC-1155 position pool). 11 of 12 Phase-2 attacker agents converged on the same reentrancy/CEI-ordering code smell, but every one of them, after tracing the exploit end-to-end, found the attack interrupted before harm (the outer splitPosition/merge always exactly refills what was transiently borrowed, or the whole transaction reverts). Per this audit's verification standard, findings that could not be walked to a concrete profitable exploit are reported at their demonstrated severity (Low/Info), not inflated.

Findings

[1] Fee-on-transfer collateral can block investing and strand invested funds at redemption

Severity: Medium · Origin: [phase1: evm-audit-erc20]
Location: mergeAndDeposit() L149-163, _withdrawAndSplit() L219-226
Description: collateralToken is arbitrary (read from yieldVault.asset(), never validated). ConditionalTokens.mergePositions/splitPosition and yieldVault.deposit/withdraw all assume the exact nominal amount arrives. A fee-on-transfer collateral desyncs the actual balance from the amount the next call tries to pull, causing a revert.
Proof of Concept: Collateral = 2% FoT token (or USDT-style fee toggled on post-deployment). A redemption needing amount = 500 from the vault calls yieldVault.withdraw(500, ...), which delivers only 490 after the fee. splitPosition(..., 500) then does transferFrom(this, ConditionalTokens, 500), but this contract only holds 490 → reverts. The same desync blocks mergeAndDeposit's vault deposit (mergePositions delivers less than completeSets to the vault-deposit call).
Recommendation: Measure actual received balance via before/after balanceOf and use that instead of the nominal amount, or restrict collateral to a vetted allowlist and document FoT tokens as unsupported.

[2] Raw bool-checked approve reverts for no-return-value tokens (e.g. mainnet USDT), silently disabling yield investing

Severity: Medium · Origin: [phase1: evm-audit-erc20, corroborated by evm-audit-general, evm-audit-assembly]
Location: mergeAndDeposit() L156, _withdrawAndSplit() L224
Description: require(collateralToken.approve(spender, amount), ApproveFailed()) decodes a bool return. USDT's approve returns no data, so the high-level call reverts on ABI-decode even though the call would otherwise have succeeded. Every mergeAndDeposit for USDT-class collateral reverts here; deposit()'s try/catch swallows it, so the market silently never invests — the yield feature is dead for one of the most common collateral tokens, despite ConditionalTokens itself supporting USDT as collateral (the in-code justification is factually incorrect on this point).
Proof of Concept: Deploy a market with yieldVault.asset() == USDT. Deposit matching YES/NO so completeSets > 0. mergePositions succeeds; USDT.approve(vault, completeSets) returns no data → revert → caught by deposit's try/catch → both sides stay dangling forever, market never earns yield.
Recommendation: Replace both raw approve calls with OpenZeppelin SafeERC20.forceApprove, which tolerates missing return data and safely resets non-zero allowances (also fixes finding [3]).

[3] USDT-style non-zero→non-zero approve can permanently disable investing if a vault under-pulls the approved amount

Severity: Low · Origin: [both — phase1: evm-audit-erc20; phase2: boundary, first-principles agents]
Location: mergeAndDeposit() L156
Description: If a non-standard yieldVault.deposit ever consumes less than the full approved completeSets while still succeeding, a residual non-zero allowance persists. The next mergeAndDeposit's approve(spender, nonZero) then reverts against a USDT-style token requiring approve-to-zero first, permanently blocking future investing for that market (redemptions are unaffected — a separate, always-fully-consumed allowance is used for CONDITIONAL_TOKENS).
Proof of Concept: Requires a non-standard vault that partially consumes its allowance, combined with USDT-style collateral. Narrow precondition; no fund loss (dangling path remains redeemable).
Recommendation: Same fix as [2] (SafeERC20.forceApprove).

[4] Missing reentrancy guard: vaultSharesOf[id] is credited/debited after the external vault call (CEI ordering)

Severity: Low · Origin: [both — phase1: evm-audit-general, evm-audit-erc20; phase2: 11/12 attacker agents independently converged (math-precision, access-control, economic-security, execution-trace, invariant, periphery, asymmetry, boundary, numerical-gap, trust-gap, flow-gap)]
Location: mergeAndDeposit() L163 (vaultSharesOf[id] += yieldVault.deposit(...)), _withdrawAndSplit() L219 (vaultSharesOf[id] -= yieldVault.withdraw(...))
Description: vaultSharesOf[id] — which _investedBalance() reads to price every deposit and redeem — is only written after the external, caller-supplied yieldVault call returns. There is no nonReentrant guard anywhere in the contract, and yieldVault is a fully attacker-choosable parameter (not validated or allowlisted). During the external call, _investedBalance is transiently understated (deposit path) or overstated (withdraw path).
Proof of Concept: This is the most heavily investigated pattern in this audit — 11 independent attacker agents in Phase 2 traced concrete reentrancy scenarios against it (same-market share mispricing via a malicious vault, and cross-market drain of the shared ERC-1155 position pool shared by markets on the same (collateralToken, conditionId) but different yieldVault). In every traced scenario, the attack was interrupted before harm: a reentrant "borrow" from the shared position pool is always exactly refilled by the outer splitPosition/mergePositions before the transaction ends, or the entire transaction reverts (undoing the reentrant leg too, since vaultSharesOf[id] -= underflow-reverts on any over-withdrawal). Same-market mispricing is confined to a market the attacker themselves seeded with their own malicious vault — no independent third-party victim was found reachable in any traced scenario, since id = keccak256(yieldVault, collateralToken, conditionId) isolates all storage per vault. We could not construct a profitable, cross-user exploit despite this being the single most-attacked surface in the engagement.
Recommendation: Add a nonReentrant guard to deposit() and redeem() as defense-in-depth, given both call fully attacker-chosen yieldVault addresses. This closes the code smell even though no working exploit was found.

[5] Round-to-zero-shares vault deposit leaks collateral backing to the yield vault's other depositors

Severity: Low · Origin: [both — phase1: evm-audit-precision-math, evm-audit-general, evm-audit-erc4626 (documented in-code as ACCEPTED RISK); phase2: execution-trace, first-principles agents]
Location: mergeAndDeposit() L156-163 (ACCEPTED RISK comment at L158-162)
Description: vaultSharesOf[id] += yieldVault.deposit(completeSets, address(this)). If the vault mints 0 shares for the merged completeSets, the collateral leaves the contract but vaultSharesOf[id] doesn't grow — a permanent leak diluting both sides' shareholders, not just the caller as the in-code comment implies. The code's claimed "~1 wei per attack" bound only holds when the vault's share price is ≈1:1; for an appreciated share price P, up to ceil(P)-1 can leak per merge, and the attack is repeatable (bounded by gas, not a hard cap).
Proof of Concept: Attacker repeatedly supplies matching YES/NO below the vault's per-share threshold; each merge leaks sub-one-share dust to existing vault depositors while consuming the attacker's own backing + gas. Uneconomical at normal decimals/share-price; the containment reasoning in the source comment is imprecise but the practical risk is low.
Recommendation: require(minted > 0) after yieldVault.deposit(...), letting deposit()'s existing try/catch defer the merge instead of silently absorbing a zero-share mint.

[6] redeem() has no graceful degradation if the external yield vault cannot honor withdraw

Severity: Low · Origin: [both — phase1: evm-audit-erc4626; phase2: economic-security, first-principles, boundary agents]
Location: redeem() → _withdrawAndSplit() L210-225
Description: Unlike deposit() (wrapped in try/catch, degrades gracefully), _withdrawAndSplit's yieldVault.withdraw(...) call is unguarded and never checks maxWithdraw. Any redemption whose assets exceed the side's dangling balance reverts entirely if the vault is paused, temporarily illiquid, or charges an unexpected withdrawal fee (which would also silently drain vaultSharesOf[id] faster than accounted, per finding [10]).
Proof of Concept: Not privileged or attacker-triggered — depends on the externally chosen vault's own health/liquidity. Users can work around a temporary block by redeeming only up to the dangling balance; loss is only permanent if the vault permanently bricks.
Recommendation: Document the assumption that the vault must always deliver exactly amount with no fee on withdraw. Optionally check maxWithdraw/support partial-fill semantics.

[7] setAuthorization is non-idempotent — re-asserting the current value reverts

Severity: Low · Origin: [phase1: evm-audit-access-control]
Location: setAuthorization() L230-236
Description: require(newIsAuthorized != isAuthorized[msg.sender][authorized], AlreadySet()) reverts on a no-op write. Not exploitable for authorization bypass — only the authorizer can write their own mapping entry, so nothing can front-run a revocation into a forced revert — but breaks idempotent/batch callers and scripts.
Recommendation: Make the setter a no-op (skip the write/event) instead of reverting when the value is unchanged.

[8] Authorization grant is global (all markets), unlimited, and lets the operator redirect funds to an arbitrary address

Severity: Low · Origin: [phase1: evm-audit-access-control]
Location: redeem() L167-205, setAuthorization() L230-236
Description: setAuthorization(op, true) grants op the ability to redeem() any amount of onBehalf's shares across all markets, sending the resulting outcome tokens to a to of the operator's own choosing — not scoped to a single market, amount, or expiry, and not restricted to to == onBehalf. This is an intentional operator model (like ERC-1155 setApprovalForAll), but broader than a user authorizing "redeem on my behalf for market X" might assume.
Proof of Concept: Requires the victim's own opt-in (setAuthorization); not exploitable without consent. Once granted, attacker can call redeem(anyVault, anyCondition, anySide, victimShares, victim, attacker) for every market where the victim holds shares.
Recommendation: Document the grant's true scope prominently. Consider restricting to == onBehalf when msg.sender != onBehalf, or scoping authorization per-market.

[9] Unwhitelisted, caller-supplied yieldVault fragments markets and is the root trust boundary behind finding [4]

Severity: Low · Origin: [both — phase1: evm-audit-flashloans; phase2: trust-gap, economic-security agents]
Location: _id() L281-283, deposit()/redeem() L80-91, L167-176
Description: A market's identity is keccak256(yieldVault, collateralToken, conditionId); yieldVault is supplied fresh on every call and never pinned/validated against a prior value for a given conditionId, nor allowlisted. Two users intending to trade "the same market" but passing different yieldVault addresses land in isolated markets that never merge into complete sets, even though they share the same underlying ERC-1155 position-id pool. This unrestricted, per-call vault selection is also the single trust boundary that every Phase 2 reentrancy/pricing lead (finding [4]) traces back to.
Proof of Concept: UX/integration hazard, not by itself a solvency bug — confirmed the shared position-pool cannot be drained across fragmented markets (all transfers require real collateral to move; splitPosition/mergePositions are atomic).
Recommendation: Document that (yieldVault, conditionId) jointly define the market; consider pinning the first-seen yieldVault per conditionId and rejecting mismatches, and/or maintaining a vetted vault allowlist to shrink the trust surface for finding [4].

[10] Withdraw-side share-burn rounding is not charged to the redeeming side, socializing wei-scale loss onto the shared invested balance

Severity: Low · Origin: [phase2 only: numerical-gap agent]
Location: _withdrawAndSplit() L217, redeem() L191-197
Description: redeem() credits the counter-side's dangling balance with exactly amount (L195: side[id][!isYes].danglingBalance += amount), but yieldVault.withdraw(amount, ...) (L217) burns vault shares rounded up (standard ERC-4626 previewWithdraw/Rounding.Ceil semantics — verified: vaultSharesOf[id] -= yieldVault.withdraw(...) subtracts the actual shares-burned return value). The realized drop in previewRedeem(vaultSharesOf[id]) can therefore exceed amount by a few wei, and that excess is not charged to the redeeming side — it silently reduces the shared invested balance both sides count as backing.
Proof of Concept: Verified at the code level (standard OZ ERC-4626 rounds withdraw's share-burn up against the caller). Bounded to wei-scale per redemption on a standard vault; not independently profitable for an attacker (the "gain" from any single redemption's rounding accrues to the underlying vault's other depositors, not to the attacker), so this is an accounting-precision note rather than an exploitable drain.
Recommendation: Optional: track the realized asset delta from withdraw's return combined with previewWithdraw pre-call, and charge any shortfall to the redeeming side rather than the shared pool. Low priority given the bound is wei-scale.

[11] Blacklistable/pausable collateral can freeze already-invested funds

Severity: Info · Origin: [phase1: evm-audit-erc20]
Location: whole-contract collateral flow (L149, 163, 219, 226)
Description: If the collateral is a blacklist-capable token (USDC/USDT) and this contract's address is ever blacklisted, or the token is paused, both investing and redeeming the invested portion revert until the block is lifted. Standard, largely inherent risk of accepting arbitrary collateral; not independently triggerable by a third party.

[12] Deposits/redemptions that round to zero still mutate state for no economic effect

Severity: Info · Origin: [phase1: evm-audit-precision-math, evm-audit-general]
Location: deposit() L99-105, redeem() L183-189, 204
Description: shares/assets can floor to 0 for dust-sized inputs on either side (deposit mints 0 shares while still crediting dangling with the deposited assets, donating value to existing shareholders; redeem burns real shares for a 0-token payout). Not reachable at attacker-relevant scale given the virtual-share offset (would require the side's share price to already be ≈1e6 units above par); only self-harms the caller.
Recommendation: Optional require(shares > 0) / require(assets > 0) guards as defense-in-depth.

[13] Pragma ^0.8.34 emits PUSH0 — confirm target chain support

Severity: Info · Origin: [phase1: evm-audit-general]
Location: L2
Description: Solidity ≥0.8.20 emits PUSH0 by default. Deployment will fail on any L2/chain without Shanghai support unless compiled with an explicit older EVM version.

[14] Fee-charging yield vault could socialize entry/exit fees across both sides via the shared invested balance

Severity: Info · Origin: [phase2 only: flow-gap agent]
Location: redeem()/mergeAndDeposit(), _investedBalance() L273
Description: _investedBalance is one shared quantity counted by both YES and NO sides (by design — one unit of invested collateral backs one token of each side). If the underlying vault charges a deposit/withdrawal fee, the fee realized when one side triggers a vault interaction is absorbed by the shared pool and thus partly borne by the side that never itself touched the vault, in tension with the documented "each side runs its own share index" design intent. Unverified whether the magnitude exceeds dust for realistic fee-charging vaults (uncommon among ERC-4626 implementations).

[15] previewRedeem-vs-actual deposit/withdraw drift on non-standard vaults

Severity: Info · Origin: [phase2 only: numerical-gap agent]
Location: _investedBalance() L273-275
Description: Share pricing reads previewRedeem (a view), while state is written from deposit/withdraw return values. On a non-standard vault where previewRedeem(deposit(x)) > x (rounds in the depositor's favor, opposite of OZ's default), a merge-then-immediate-redeem could extract the surplus. Inert on standard OpenZeppelin ERC-4626 vaults, which round against the depositor in both directions; the caller-supplied, unwhitelisted yieldVault (finding [9]) is what admits a non-standard vault at all.

[16] Asymmetric share-rounding (mint rounds down, burn rounds up) could underflow vaultSharesOf[id] on near-full exit

Severity: Info · Origin: [phase2 only: asymmetry, first-principles agents]
Location: mergeAndDeposit() L163 vs _withdrawAndSplit() L217
Description: vaultSharesOf[id] += deposit(...) books shares rounded down (standard ERC-4626); vaultSharesOf[id] -= withdraw(...) subtracts shares rounded up. Cumulative asymmetry over a market's lifetime could in principle make the last redemption(s) underflow-revert. Dust/DoS-scale and self-resolving (the redeemer can request slightly fewer shares); not a fund-loss path.

[17] ERC-4626 inflation attack on the shared invested balance via vault donation — investigated, confirmed mitigated

Severity: Info · Origin: [both — phase1: evm-audit-erc4626 (deepest analysis, concluded no exploitable path); phase2: periphery, economic-security, flow-gap agents (flagged as residual lead, could not exhibit a profitable instance)]
Location: deposit() L99-105, constants L55-58 (VIRTUAL_SHARES = 1e6, VIRTUAL_ASSETS = 1)
Description: Donating collateral directly to the underlying yield vault raises previewRedeem(vaultSharesOf[id]), the classic first-depositor/inflation vector. Both phases independently confirmed this is properly mitigated: danglingBalance is internal-tracked accounting (not balanceOf-derived, so direct outcome-token donations are inert), and the VIRTUAL_SHARES=1e6/VIRTUAL_ASSETS=1 offset raises the cost of nullifying a victim deposit of size V to roughly 2e6×V in donated collateral, which is only recoverable if the attacker dominates the underlying vault's other depositors — otherwise the donation is a net subsidy to them, not a theft.

Domain / agent coverage

  • Phase 1 (8/8 checklists, no agent errors): general, precision-math, erc4626, erc20, access-control, assembly, flashloans, dos.
  • Phase 2 (12/12 agents, no agent errors): math-precision, access-control, economic-security, execution-trace, invariant, periphery, first-principles, asymmetry, boundary, numerical-gap, trust-gap, flow-gap.

Confirmed non-issues (checked explicitly by one or both phases, no exploit found)

  • _partition() inline-assembly block: memory-safe, correct free-memory-pointer handling, correctly ABI-encoded (multiple agents in both phases independently confirmed).
  • onlySelf gate on mergeAndDeposit: unspoofable — no delegatecall, no proxy, no multicall primitive.
  • No unbounded loops / user-growable arrays; force-sent ETH/tokens are inert dust, never read into accounting.
  • Malicious/reverting yieldVault or malicious ERC-1155 receiver to: griefing is confined to the attacker's own self-selected market/output target; all reverts are atomic; the dangling path always remains redeemable, so no funds are ever permanently stuck.
  • Live previewRedeem-based share pricing resists flash-loan sandwich manipulation — donating to the external vault benefits all of its depositors pro-rata, so an attacker's donation cost always exceeds their extractable share of it.
  • Cross-market isolation via id = keccak256(yieldVault, collateralToken, conditionId) holds even under a malicious/reentrant yieldVault — every transfer from the shared ERC-1155 position pool requires atomic, real collateral movement, and the outer split/merge always reconciles the pool by the end of the transaction.
  • Rounding direction is consistently protocol-favoring on the core deposit/redeem formulas (floor on both shares-minted and assets-out); no profitable deposit→redeem round trip found.
