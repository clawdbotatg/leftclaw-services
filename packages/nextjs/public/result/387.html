[95] 1. Oracle-signed reward hash has no chain/contract binding — signature replayable across any deployment sharing the same authorized oracle

RewardDistributor.distributeChainRewards · Confidence: 95 · [both — phase1: signatures, general · phase2: 10 of 12 agents]

Description
rewardHash = keccak256(abi.encodePacked(reward.user, reward.totalAmount, reward.rewardToken, reward.groupId, reward.eventId)) (L112-120), then wrapped only by SignatureLib.toEthSignedMessageHash (L124) — no block.chainid, no address(this), no domain separator. The only replay guard, _distributedRewards[rewardHash] (L122/L129), is per-contract storage. Any two deployments (redeploy after a fix, a second chain, a staging/prod pair) that authorize the same oracle key for the same groupId will accept the byte-identical (reward, signature) pair, each independently marking it undistributed and paying out.

Proof of Concept

  1. Owner deploys RewardDistributor instance A and instance B (e.g., same protocol on two chains, or a redeploy), authorizing the same oracle key K for groupId = G on both, and funds both with rewardToken.
  2. Oracle signs (user, totalAmount, rewardToken, G, eventId) intended for instance A.
  3. Relayer submits it to A — pays out, _distributedRewards set in A's storage only.
  4. The identical calldata (reward, signature) is submitted to instance B — B's _distributedRewards mapping has never seen this hash, the signature still recovers to K, _authorizedOracles[G][K] is true on B too → the same reward pays out a second time from B's balance.

Fix

  bytes32 rewardHash = keccak256(
      abi.encodePacked(
+         block.chainid,
+         address(this),
          reward.user,
          reward.totalAmount,
          reward.rewardToken,
          reward.groupId,
          reward.eventId
      )
  );

(Or adopt EIP-712 with a domain separator bound to chainid and address(this).)

[90] 2. A single deny-listed/blacklisted recipient anywhere in the chain permanently blocks payout to every other chain member

RewardDistributor.distributeChainRewards · Confidence: 90 · [both — phase1: erc20 · phase2: first-principles agent, independently as a Finding]

Description
The transfer loop (L138-142) has no try/catch and no per-recipient failure isolation. If reward.rewardToken implements a deny-list (USDC/USDT-style) and any address among up to 10 chain recipients — including an unrelated upstream ancestor several levels above the current event's subject — is on it, safeTransfer reverts and unwinds the entire transaction, including the _distributedRewards write. Because the chain is deterministically rebuilt from the immutable referralGraph on every retry, this repeats identically forever with no in-contract remedy.

Proof of Concept
Chain = [R0..R9], decaying amounts summing to totalAmount. Suppose R5 is later added to rewardToken's deny-list for reasons unrelated to this event. Any future distributeChainRewards call touching this exact chain reverts at i=5 (L140), unwinding transfers that would have succeeded for R0-R4 in the same call. R0-R4 and R6-R9 (9 unrelated, non-blacklisted addresses) receive nothing, repeatably, with no skip-and-continue, no rescue function, and no owner override anywhere in the file.

Fix

  for (uint256 i = 0; i < recipients.length; i++) {
      if (amounts[i] > 0) {
-         SafeTransferLib.safeTransfer(ERC20(reward.rewardToken), recipients[i], amounts[i]);
+         try this.safeTransferExternal(reward.rewardToken, recipients[i], amounts[i]) {
+         } catch {
+             // credit recipients[i] a claimable balance instead of reverting the batch
+         }
      }
  }

(Or adopt a pull-payment/escrow pattern per recipient so one failure cannot block the batch.)

[65] 3. _getReferralChain has no deduplication or cycle guard — a self-referential or cyclic referral edge lets one actor capture multiple (or all) payout slots in a single event

RewardDistributor._getReferralChain / _calculateChainRewards · Confidence: 65 (contingent — see below) · [both — phase1: general (LEAD) · phase2: 11 of 12 agents, one (trust-gap) promoting to Finding]

Description
This is the finding most directly responsive to the client's request to "check for leaks... in the referral graph."

The chain-building loop (L154-177) appends whatever referralGraph.getReferrer(current, groupId) returns with no check against addresses already in chain — the only exit conditions are hitting address(0)/REFERRAL_ROOT (L164) or filling all 11 slots (L162). _calculateChainRewards (L187-208) then pays every slot in chain independently, with no uniqueness check on recipients. This missing-dedup defect is unconditionally provable from RewardDistributor.sol alone — it holds regardless of what the unprovided IReferralGraph actually does. What is not verifiable from this file is whether IReferralGraph.getReferrer can ever be steered (by self-referral, a colluding pair, or an admin/graph bug) into returning an address already present earlier in the same walk. If it can, a single address (or two colluding addresses) would occupy multiple — potentially all 10 paid — chain slots and capture the geometric-decay split intended for genuinely distinct upstream referrers, up to the full totalAmount for that event, while any real ancestors beyond the loop point never appear in the chain at all.

Proof of Concept (conditional on IReferralGraph behavior, which is unverified)
If referralGraph.getReferrer(A, groupId) == A (self-loop) — or a 2-cycle A → B → A — then _getReferralChain(A, groupId) returns [A, A, A, ...] (or [A, B, A, B, ...]), truncated to 10 paid slots at _calculateChainRewards. rewardCalculator.calculateRewards(totalAmount, 10) is asked for 10 decaying shares regardless of how many distinct addresses are present, so address A (or the A/B pair) receives some or all of those 10 shares — i.e., up to the entire totalAmount — instead of the single slot-0 share a legitimate 1-hop referral would yield.

Why this is reported at Medium-High confidence rather than as a certain High-severity finding: per this audit's verification standard, a finding is downgraded when a concrete exploit cannot be fully constructed. The code-side defect (missing dedup) is fully demonstrated above; whether it is reachable depends entirely on IReferralGraph's referrer-assignment rules (self-service vs. admin-controlled; cycle-permitting or tree-enforced), which were not supplied in this job. This is the single most important open question for the client to resolve — if referrer assignment is user/self-service in any way, this is a live, High-severity leak exactly matching the stated concern.

Fix (recommended regardless of the dependency's actual behavior — free defense-in-depth):

  function _getReferralChain(address user, bytes32 groupId) internal view returns (address[] memory) {
      address[] memory chain = new address[](11);
      uint256 length = 0;

      address current = user;
      chain[length++] = current;

      while (length < 11) {
          current = referralGraph.getReferrer(current, groupId);
          if (current == address(0) || current == REFERRAL_ROOT) {
              break;
          }
+         bool seen;
+         for (uint256 j = 0; j < length; j++) {
+             if (chain[j] == current) { seen = true; break; }
+         }
+         if (seen) break;
          chain[length++] = current;
      }

[55] 4. Oracle signature authorizes an amount and a seed address, but not the resolved recipient chain — signature valid indefinitely, chain re-resolved live at execution time

RewardDistributor.distributeChainRewards · Confidence: 55 (contingent) · [both — phase1: general, signatures (LEADs) · phase2: invariant, trust-gap, flow-gap agents — flow-gap promoting to Finding]

Description
The signed hash (L112-120) commits only to (user, totalAmount, rewardToken, groupId, eventId) — never to the resolved recipient list, a referral-graph snapshot, or an expiry. The actual chain is resolved live, at whatever block a permissionless relayer chooses to submit (L132/L163), from the externally-mutable referralGraph. If referrer edges can change between when an oracle signs a reward and when the (non-expiring) transaction lands — plausible for any live "referral graph" feature — a party able to influence getReferrer(reward.user, groupId) in that window could redirect who is actually paid without invalidating the signature. This is a TOCTOU (time-of-check/time-of-use) gap; like Finding 3, its code-side shape is demonstrable from this file, but real-world reachability depends on IReferralGraph's unverified mutability rules.

Proof of Concept (conditional)
Oracle signs a reward for user = Alice while Alice's live upline is Alice → Bob → Carol. Before the signature is submitted (no expiry field exists to bound this window), an attacker changes Alice's referrer edge to point at themselves. Whoever then submits the still-valid signature causes _getReferralChain to resolve [Alice, Attacker, ...] instead of [Alice, Bob, Carol] — the signature check at L126 never referenced Bob/Carol/Attacker, so it still passes, and Bob's expected share is silently redirected.

Fix
Add an expiry/deadline field to the signed payload, and/or commit a hash of the resolved recipient chain (computed off-chain by the oracle at signing time) into the signed material, verified against the on-chain resolution before paying out.

[80] 5. No on-chain check that the calculator's returned split is bounded by totalAmount or by actual contract balance

RewardDistributor._calculateChainRewards / distributeChainRewards · Confidence: 80 · [both — phase1: precision-math, erc20 · phase2: numerical-gap (lead)]

Description
amounts is copied verbatim from rewardCalculator.calculateRewards() (L199) with no validation that sum(amounts) <= totalAmount, and no check against ERC20(reward.rewardToken).balanceOf(address(this)) anywhere before the transfer loop (L138-142). The contract holds one ambient balance per rewardToken shared across all pending events (no per-event escrow exists in this file), so any shortfall — from a calculator rounding/normalization bug, a fee-on-transfer haircut on the funding leg, a negative-rebasing token, or simply multiple signed rewards drawing on one pool — causes the transfer loop to revert partway through, unwinding the entire distribution atomically (not a partial-payment scenario — Solidity reverts are all-or-nothing). This is a liveness/DoS-until-corrected issue, not a silent fund-loss one.

Proof of Concept
Contract holds 950 units of rewardToken (e.g., after a 10%-fee-on-transfer funding leg reduced an intended 1,000-unit deposit). RewardCalculator, driven off the nominal totalAmount = 1000, returns a 10-way split summing to ~1000. The transfer loop succeeds for early, larger-share recipients, then reverts once cumulative transfers exceed the actual 950-unit balance — unwinding the whole call, including the already-attempted earlier transfers in the same transaction.

Fix

  uint256[] memory chainAmounts = rewardCalculator.calculateRewards(totalAmount, numRecipients);
+ uint256 sum;
+ for (uint256 i = 0; i < chainAmounts.length; i++) sum += chainAmounts[i];
+ require(sum <= totalAmount, "split exceeds totalAmount");
+ require(ERC20(reward.rewardToken).balanceOf(address(this)) >= sum, "insufficient balance");

[75] 6. All-zero-payout distribution still permanently consumes the replay-protection slot

RewardDistributor.distributeChainRewards · Confidence: 75 · [phase1: precision-math]

Description
Only totalAmount == 0 is rejected (L110); there is no check that the resulting amounts array contains any nonzero entry. If the black-box calculator's division-based split rounds every slot to 0 for a small totalAmount spread across a full chain, _distributedRewards[rewardHash] = true (L129) and ChainRewardsDistributed (L144) still fire — the tuple is marked distributed forever with nobody paid, and cannot be resubmitted under the same tuple (a new signed eventId would be needed).

Fix

  (address[] memory recipients, uint256[] memory amounts) = _calculateChainRewards(reward.totalAmount, chain);
+ uint256 sum;
+ for (uint256 i = 0; i < amounts.length; i++) sum += amounts[i];
+ require(sum > 0, "zero payout");

[70] 7. rewardToken address with no deployed code causes safeTransfer to silently no-op — reward falsely marked distributed with zero funds moved

RewardDistributor.distributeChainRewards · Confidence: 70 · [phase1: erc20]

Description
No extcodesize/allowlist check exists on reward.rewardToken (an arbitrary, oracle-signed address, L116). solmate's SafeTransferLib.safeTransfer treats a call to an address with no deployed code as trivially successful (empty returndata = success), so the transfer loop (L138-142) completes without reverting and without moving any value. Since _distributedRewards[rewardHash] = true is set at L129 (before the loop, and the call doesn't revert), the tuple is permanently marked distributed even though nothing was paid, and ChainRewardsDistributed falsely signals success to any off-chain observer.

Fix

  function distributeChainRewards(ChainRewardData calldata reward, bytes calldata signature) external nonReentrant {
      if (reward.totalAmount == 0) revert ZeroRewardAmount();
+     if (reward.rewardToken.code.length == 0) revert InvalidRewardToken();

[70] 8. Owner-key compromise converts directly into unbounded fund drain via self-authorized oracle — no timelock/multisig

RewardDistributor.authorizeOracle / distributeChainRewards · Confidence: 70 (standard centralization/admin-key risk — see note) · [phase1: access-control]

Description
authorizeOracle/unauthorizeOracle are gated only by a single-EOA onlyOwner (solmate Owned), with no timelock, multisig, or delay. Because the real payout gate is "is the ECDSA signer authorized for groupId" rather than a separate governance layer, compromising the owner key lets an attacker authorizeOracle(attacker, groupId) and then sign their own payout, draining the full rewardToken balance in one transaction.

Note on severity convention: most audits treat "if the owner key is compromised, all bets are off" as an accepted baseline risk rather than an escalatable finding, unless the protocol claims a trust-minimized/non-custodial design. This contract makes no such claim in the provided file, so this is reported at Medium rather than Critical/High — it is a legitimate centralization observation with a concretely worse blast radius than a typical "owner can tweak a parameter" pattern (here, owner compromise ⇒ instant full drain, not just governance disruption), which is why it is called out explicitly rather than omitted.

Fix
Gate authorizeOracle/unauthorizeOracle behind a timelock and/or multisig rather than a single EOA.

[70] 9. Single-step ownership transfer (solmate Owned default) — a bad transferOwnership call permanently removes all admin capability

RewardDistributor (inherited Owned) · Confidence: 70 · [phase1: access-control]

Description
No two-step accept pattern, no zero-address guard by default in solmate's Owned. A typo'd or zero-address ownership transfer permanently removes the ability to authorize/revoke oracles — i.e., permanently removes the only incident-response lever available if an oracle key is later suspected compromised.

Fix
Use a two-step ownership pattern (pending-owner + explicit accept).

[55] 10. Chain-length asymmetry — _getReferralChain builds up to 11 addresses, _calculateChainRewards only ever pays 10

RewardDistributor._getReferralChain (L152-177) / _calculateChainRewards (L192-196) · Confidence: 55 · [both — phase1: precision-math, general · phase2: 7 of 12 agents]

Description
_getReferralChain's own docstring (L152) states "up to 11 addresses," and the loop can build exactly that (seed + 10 ancestors). _calculateChainRewards caps numRecipients at 10 (L193-196) before ever calling the reward calculator — when a full 11-address chain is built, the 11th (topmost) ancestor is resolved (spending an external call) but then silently dropped, with no event or signal that truncation occurred. This is a fairness/completeness quirk, not a fund-extraction path — the full split is still computed and paid across the 10 slots that are used.

Fix
Align the two bounds — either cap the chain-walk at 10 total addresses, or extend the payout path to handle all 11.

[45] 11. reward.user (chain seed) is not validated against address(0)/REFERRAL_ROOT before being placed in a payout slot

RewardDistributor._getReferralChain (L158-159) · Confidence: 45 · [both — phase1: general · phase2: 5 of 12 agents, one (numerical-gap) as a Finding]

Description
Every subsequent hop returned by referralGraph.getReferrer is checked against address(0)/REFERRAL_ROOT before being added to the chain (L164), but the initial seed (chain[0] = user, L158-159) is not. Multiple agents note that authorizeOracle (L72) and the constructor (L54) both explicitly guard against address(0) elsewhere in this same file, making the seed's exemption from an equivalent check an inconsistency. If an oracle signs a reward with reward.user == address(0) or == REFERRAL_ROOT, that sentinel receives a real payout slot (typically the largest, under a descending decay curve) with no sweep function anywhere in this file to recover it. Reported at reduced confidence/severity because it requires the trusted oracle to sign malformed input — not attacker-triggerable directly, since reward.user is inside the oracle-signed payload.

Fix

  address current = user;
+ if (current == address(0) || current == REFERRAL_ROOT) revert InvalidRewardUser();
  chain[length++] = current;

[40] 12. Constructor accepts an unvalidated _referralGraph address wired into an immutable, with no re-point or recovery function

RewardDistributor.constructor (L46-58) · Confidence: 40 · [phase1: access-control]

Description

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed because it terminates inside one of the four unprovided dependencies. These are not false positives — they are high-signal leads for whoever holds the missing source to verify.

  • RewardCalculator tail/rounding behavior — RewardDistributor._calculateChainRewards — Code smells: no on-chain check of RewardCalculator.calculateRewards's returned length or sum; multiple independent agents flagged division-before-multiplication, zero-rounding for small totalAmount over a full chain, remainder-to-totalAmount reconciliation, and decimals/overflow behavior for non-18-decimal tokens as plausible but unverifiable patterns for an unseen geometric-decay implementation.
  • SignatureLib.recover correctness — RewardDistributor.distributeChainRewards — Code smells: signature malleability is structurally non-exploitable here (replay protection keys on reward data, not signature bytes), but recover()'s own correctness (revert-vs-zero-address handling, malformed-signature rejection) is unverified without its source.
  • ChainRewardData.eventId concrete type — affects the certainty of the abi.encodePacked-collision analysis (Info item above); unresolved without IRewardDistributor.sol.
  • IReferralGraph.getReferrer mutability and assignment rules — the load-bearing open question behind Findings 3 and 4; whether referrer edges are self-service/Sybil-able, admin-controlled, or immutable-once-set determines whether those two findings are live, High-severity issues or largely theoretical.
