Security Audit Report — FlameBase

Target: 0x7Bac408402421005917D63a1a269C902b4c9485c
Chain: Base (chain id 8453) — verified source pulled from BaseScan.
Scope: Single contract, FlameBase.sol, 133 lines, no external imports/inheritance.
Methodology: Two-phase audit — Phase 1 checklist breadth (4 domain checklists: general, precision-math, access-control, dos) run in parallel, followed by Phase 2 attacker-mindset depth (12 independent agents: 9 specialty + 3 gap-hunter), run blind to Phase 1's findings. A final reconciliation pass cross-checked both phases against each other and against the source.

What this contract does

FlameBase is a small on-chain social app. Users register a free profile, then pay small fixed ETH fees to post, like, comment, or upload an avatar — every one of those fees is forwarded in full, in the same transaction, to a single immutable owner address. A separate tip(postId) function lets anyone send an arbitrary ETH amount to a post, split 90% to the post's author and 10% to owner. The contract never holds a balance between transactions (every payable function pushes its ETH out immediately), and checks-effects-interactions ordering (state written before external calls) is followed consistently everywhere — both audit phases independently confirmed this closes off classic reentrancy fund-drain. The issues that do exist center on two things: (1) owner can never be changed once deployed, and (2) tip()'s payout to an attacker-controllable author address, combined with the missing self-tip check, lets the platform's core reputation signal be fabricated.

Reconciliation summary

Overlap: 5 findings independently discovered by both phases · Phase-1-only: 4 (Low/Info) · Phase-2-only: 1 standout new finding (tip() self-tip/reentrancy) plus 3 new minor leads.

Completeness: 13 unique (contract, function, bug-class) tuples identified across both phases' raw agent output, 13 covered in this unified report.

One severity call required explicit reconciliation judgment: phase 1's dedicated DoS/general checklist agents independently rated the "owner can never be changed" issue High (the blast radius is every user, permanently), while phase 2's stricter attacker-mindset gates classified the same issue as a LEAD only, reasoning that the triggering precondition (owner becomes unable to receive ETH) is admin-caused and therefore "self-harm." On reconciliation, this report sides with phase 1: the precondition may originate from an admin/deployment choice, but the resulting harm — every paid feature permanently and unrecoverably broken for every user, forever — falls on third parties, not the admin alone, and is a materially different situation from an admin knowingly griefing themselves.

Findings

[1] tip() has no self-tip guard and no reentrancy guard — an author can fabricate their own "tips received" reputation stat at ~1/10th real cost

Severity: Medium
Origin: [phase2 only] — independently discovered as a full FINDING by 5 of 12 attacker-mindset agents (execution-trace, invariant, periphery, first-principles, flow-gap-hunter), all converging on matching mathematical proof. Not caught by phase 1's checklist pass.

Location: tip() L95-107.

function tip(uint256 _postId) external payable {
    require(msg.value > 0, "Send some ETH");
    require(_postId < postCount, "Post not found");
    address author = posts[_postId].author;
    posts[_postId].tips += msg.value;
    profiles[author].tips += msg.value;
    uint256 ownerCut = msg.value / 10;
    uint256 authorAmount = msg.value - ownerCut;
    (bool s1, ) = owner.call{value: ownerCut}("");
    (bool s2, ) = author.call{value: authorAmount}("");
    require(s1 && s2, "Transfer failed");
    emit TipSent(_postId, msg.sender, author, msg.value);
}

Description: tip() never checks msg.sender != author, and pays out the author's 90% cut via an unguarded low-level .call — with no nonReentrant modifier anywhere in the contract. posts[_postId].author is fully attacker-controllable: any address (including a contract) can call createProfile() + createPost() and become the author of a post. This means an attacker can tip their own post and get 90% of their payment sent straight back to themselves, while posts[_postId].tips/profiles[author].tips — the platform's on-chain "reputation"/"support received" counters — are incremented by the full amount each time.

Repeating this (sequentially, across separate transactions, or atomically within a single transaction via a receive() hook that immediately re-calls tip() with the just-returned funds) produces a geometric series: with a 90% return rate, Σ 0.9ⁿ = 1/(1-0.9) = 10. The recorded "tips received" total converges to ~10x the attacker's real net spend (the owner's cumulative 10% cut also converges to exactly the attacker's real spend — no ETH is created or stolen from a third party; only the counter is inflated).

Proof of Concept:

  1. Attacker deploys contract Recycler, calls createProfile() then createPost() — Recycler is now posts[P].author.
  2. Attacker calls tip(P){value: 1 ether} (msg.sender can be the attacker's own EOA or Recycler itself). Trace: posts[P].tips += 1e18 → owner.call{0.1e18} succeeds → Recycler.call{0.9e18} triggers Recycler.receive().
  3. Recycler.receive() immediately calls tip(P){value: 0.9 ether} again (reentrant, before the outer call returns). This recurses: 0.9, 0.81, 0.729 ether, etc., each level re-incrementing posts[P].tips/profiles[Recycler].tips on the recycled value before forwarding 90% onward again.
  4. Within normal single-transaction gas/call-stack limits, this reaches ~15-20 levels of recursion, driving posts[P].tips to approach 10 ether recorded from a single 1 ether real deposit — while Recycler's net real cost approaches exactly 1 ether (all of it eventually collected by owner across the recursion).
  5. The same effect is achievable more slowly across separate transactions without any reentrancy at all — simply calling tip() on your own post repeatedly, recycling the returned 90% each time — since msg.sender == author is never checked.

No third-party ETH is stolen (rated Medium rather than High/Critical for this reason), but the platform's core "tips received"/reputation signal — the number any user, leaderboard, or future integration would reasonably treat as evidence of genuine third-party support — becomes fully fabricable by a single address at ~10% of its face-value cost.

Recommendation:

 address author = posts[_postId].author;
+require(msg.sender != author, "Cannot tip own post");
 posts[_postId].tips += msg.value;

This single check closes both the atomic-reentrancy variant (in the reentrant call, msg.sender is still the author's own address) and the simple sequential self-tip variant. A nonReentrant guard is still recommended as defense-in-depth. Note a weaker residual variant remains possible — two attacker-controlled addresses alternately tipping each other's posts across separate transactions — but this is an inherent Sybil-resistance limitation of any on-chain reputation counter without stronger identity binding, not a specific coding defect closable by one function-level check.

[2] owner can never be changed — if it becomes unable to receive ETH, every monetized function is permanently bricked for all users

Severity: High
Origin: [both] — phase1: general + dos checklist agents, independently, both rating High; phase2: raised as a lead by 4 of 12 agents (invariant, first-principles, asymmetry, boundary), but capped at LEAD severity under the stricter pashov "admin self-harm" exclusion. See reconciliation note above for why this report follows phase 1's severity.

Location: owner state var L5, constructor L55-57 (no transferOwnership/setOwner anywhere); forwarding sites: createPost() L70-71, like() L81-82, comment() L90-91, uploadAvatar() L113-114, tip() L103-105.

Description: owner is set exactly once in the constructor and can never be changed afterward — there is no ownership-transfer function of any kind in the contract. Every fee-collecting function unconditionally forwards ETH to owner via a raw .call{value:...}("") immediately followed by require(sent, "Transfer failed"). If owner is ever an address that cannot accept a plain-ETH call — a contract with no receive()/payable fallback(), a contract whose fallback reverts or runs out of gas, or a deployment where the constructor's msg.sender ends up being an unintended factory/multisig contract without a working fallback — then createPost, like, comment, uploadAvatar, and tip all revert permanently, for every user, with no code path to ever recover. tip() compounds this: it requires both legs to succeed (require(s1 && s2, "Transfer failed")), so a broken owner-fee leg blocks the author's otherwise-fine payment too.

Proof of Concept: Arrange for owner to be a contract with no payable fallback (a plausible, real-world deployment mistake — e.g. deploying via a factory contract, or later needing to move treasury custody to a smart-contract wallet with restrictive receive logic). From that point, every call to any of the five monetized functions reverts at the require check. Since owner is immutable, this is unrecoverable by any on-chain action.

Recommendation: Add a guarded (ideally two-step) transferOwnership function, and switch the owner's share to a pull-payment pattern (credit a withdrawable balance instead of pushing inline) so a failure to pay owner can never block a user-facing action. In tip() specifically, decouple s1 from s2 so the author's leg cannot be held hostage by the owner's leg.

[3] No Sybil resistance on like() — self-liking and unlimited duplicate likes let anyone inflate reputation metrics

Severity: Medium
Origin: [both] — phase1: general checklist agent; phase2: promoted to a full FINDING by the first-principles agent, corroborated as a lead by 8 more agents (near-unanimous).

Location: like() L75-84.

Description: like() never checks msg.sender != posts[_postId].author and never de-duplicates repeat likes from the same address (postLikes[_postId].push(msg.sender) is an unconditional append). Any account — including the post's own author — can call like() on the same post any number of times (paying likePrice each time) to arbitrarily inflate posts[postId].likes and the author's flames reputation counter.

Proof of Concept: Author creates a post, then calls like(postId) on it repeatedly from their own address, incrementing likes/flames without bound — no check prevents msg.sender == author or repeat likes from the same address.

Recommendation: Add mapping(uint256 => mapping(address => bool)) hasLiked to enforce one like per address per post, and/or require(msg.sender != posts[_postId].author).

[4] Unbounded postComments/postLikes growth can DoS the aggregate getters

Severity: Medium
Origin: [both] — phase1: general + dos checklist agents; phase2: leads from periphery, boundary, and numerical-gap-hunter agents.

Location: postComments/postLikes mappings L40-41; comment() L89 push; like() L79 push (compounds Finding 3); getPostComments() L127-129; getPostLikes() L131-133.

Description: Both arrays grow without bound and the getters copy the entire array into memory before returning it. Because like() has no per-address dedup (Finding 3) and both likePrice/commentPrice are very small (0.0001/0.0003 ETH), a single account can cheaply grow either array into the tens of thousands of entries, at which point the getters exceed practical eth_call/on-chain gas limits and become permanently unusable for that post. like()/comment() themselves are unaffected (O(1) push) — only the read-side getters degrade.

Recommendation: Add paginated getters (getPostLikes(postId, offset, limit)), or rely on emitted events for off-chain reconstruction instead of full-array getters.

[5] Full msg.value is forwarded rather than the exact price — overpayment is never refunded

Severity: Low
Origin: [both] — phase1: general + access-control checklist agents; phase2: leads from 5 agents (math-precision, first-principles, asymmetry, boundary, trust-gap-hunter).

Location: createPost() L70, like() L81, comment() L90, uploadAvatar() L113.

Description: Each function checks only msg.value >= price but forwards the entire msg.value, not just price. A user who overpays (stale front-end cache, a safety buffer against a possible price bump, or simple error) permanently forfeits the excess with no refund path. This is self-inflicted by the paying caller in every case — no third party can force another user to overpay — so it is rated Low rather than higher.

Recommendation: Forward only the required price and refund msg.value - price to msg.sender, or enforce require(msg.value == price).

[6] tip()'s 10% owner fee rounds down and is fully bypassed for tips under 10 wei

Severity: Low
Origin: [both] — phase1: precision-math checklist agent; phase2: leads from math-precision and numerical-gap-hunter agents.

Location: tip() L101-102: ownerCut = msg.value / 10; authorAmount = msg.value - ownerCut;

Description: ownerCut + authorAmount == msg.value always holds exactly (no dust is stuck), but floor division means the owner's cut always rounds down and the remainder goes to the author — the split favors the fee-paying side, never the fee-collecting side. Since tip() only requires msg.value > 0 (no minimum), any tip of 1-9 wei yields ownerCut = 0 — the owner's fee is completely bypassed for micro-tips. This compounds Finding 1's self-tip issue at the margin (dust-value self-tips recover 100% instead of 90%), but on its own is wei-scale and not separately exploitable for material gain.

Recommendation: Round the owner's cut up (ceiling division) if exact fee capture matters, and/or enforce a sane minimum tip amount — which also helps close Finding 1.

[7] ETH force-fed via selfdestruct (or pre-funding a counterfactual address) is permanently stuck — no withdraw function

Severity: Low
Origin: [phase1 only] — general checklist agent. Re-verified: no receive()/fallback()/withdraw() defined anywhere in the contract.

Description: Direct ETH transfers correctly revert, but ETH can still land in the contract via selfdestruct from another contract or by pre-funding a counterfactual CREATE2 deployment address. Since nothing in the contract ever reads or moves address(this).balance directly, any ETH that arrives this way is permanently unrecoverable by anyone, including owner.

Recommendation: Add an onlyOwner sweep/withdraw function for address(this).balance.

[8] Missing username uniqueness check enables identity squatting

Severity: Low
Origin: [phase2 only] — first-principles agent. Re-verified: createProfile() L59-63 stores _username per-address with no uniqueness or non-empty validation.

Description: Any number of distinct addresses can register the identical username string. Any off-chain surface (frontend, indexer, tipping UI) that treats profiles[x].username as a trustworthy identity handle is fully spoofable — an attacker could register a popular creator's exact username from a different address to impersonate them for phishing purposes. No on-chain fund movement is directly forced by the collision itself (tips/likes are bound to postId/author address, not the username string), so impact depends on how a consuming frontend trusts the field.

Recommendation: Add a mapping(string => bool) usernameTaken (or a hash thereof) and require uniqueness, or explicitly document that username is a non-unique display label only.

[9] tips counters record the full sent amount, not the 90% actually delivered

Severity: Info
Origin: [phase2 only] — numerical-gap-hunter agent. Re-verified: posts[_postId].tips += msg.value (L99) and profiles[author].tips += msg.value (L100) both use the full amount, while only authorAmount (90%) is transferred to the author.

Description: Independent of Finding 1's self-tip exploit, even a single honest, non-repeated tip causes the recorded "tips received" stat to permanently overstate the actual ETH delivered to the author by ~11%. This is a plain accounting/bookkeeping mismatch, not an attack.

Recommendation: If the stat is meant to represent value actually received by the author, increment it by authorAmount instead of msg.value; otherwise document that it represents gross tip volume, not net author proceeds.

[10] Missing event emission on the four price setters

Severity: Info
Origin: [phase2 only] — asymmetry agent. Every other state-changing function in the contract emits an event; setPostPrice/setLikePrice/setCommentPrice/setPhotoPrice (L118-121) do not.

Recommendation: Emit a PriceUpdated(string field, uint256 oldPrice, uint256 newPrice) event for transparency and front-running detection.

[11] Owner can set any price to an extreme value with no bound or timelock

Severity: Low
Origin: [phase1 only] — access-control checklist agent.

Location: setPostPrice()/setLikePrice()/setCommentPrice()/setPhotoPrice() L118-121.

Description: All four setters take an unbounded uint256, applied instantly. Setting a price to type(uint256).max makes that action effectively unusable for everyone (an owner-controlled, reversible per-feature pause); setting it to 0 removes the fee entirely. No third-party funds are at risk.

Recommendation: Add sane bounds per setter and consider a timelock before changes take effect (see also Finding 10).

[12] Inconsistent profile-existence requirement across payable functions

Severity: Info
Origin: [both] — phase1: general checklist agent; phase2: lead from the asymmetry agent.

Location: createPost() L67, uploadAvatar() L111 vs. like()/comment()/tip() (no equivalent check).

Description: createPost/uploadAvatar require an existing profile; like/comment/tip do not, so likes/comments/tips can originate from addresses with no Profile at all. Likely a design inconsistency rather than a vulnerability.

Recommendation: Apply the same require(profiles[msg.sender].exists, ...) to like/comment/tip if profile-gating is meant to be platform-wide, or document the asymmetry as intentional.

[13] No reentrancy guard — confirmed safe today via strict checks-effects-interactions, but structurally fragile

Severity: Info
Origin: [both] — phase1: general checklist agent; phase2: latent-risk leads noted by several agents alongside Finding 1's live exploit.

Description: Every function updates all relevant state before its external .call. This holds for createPost/like/comment/uploadAvatar because their only call target is the trusted, immutable owner — so no reentrancy path exists there today. tip()'s call to the attacker-controllable author address is the one place this actually matters, and it is separately covered (and exploitable) as Finding 1.

Recommendation: Add a standard nonReentrant modifier to all payable functions as defense-in-depth, so any future code change that adds a second attacker-reachable payout target doesn't silently reintroduce a real exploit.

Notes on what was reviewed and cleared (no finding)

  • Access control: the single owner role and its four onlyOwner setters are consistently and correctly guarded; no missing modifiers, no confused-deputy paths (post authorship is immutable once set, not attacker-redirectable), no delegatecall/proxy surface.
  • Reentrancy fund-drain: aside from Finding 1's reputation-stat manipulation, no path was found where reentrancy extracts more ETH than an attacker legitimately contributed — checks-effects-interactions is followed everywhere, and the contract never holds a persistent balance for a classic double-withdraw.
  • Integer arithmetic: the tip() 90/10 split conserves value exactly for every input (ownerCut + authorAmount == msg.value always); no overflow/underflow paths exist (Solidity 0.8.20 checked arithmetic throughout, no downcasts).

This review was performed by AI audit agents (ethskills breadth pass + pashov-methodology depth pass, reconciled). AI analysis cannot verify the complete absence of vulnerabilities and no guarantee of security is given. Findings 1-4 above should be addressed before this contract is relied upon for meaningful reputation/trust signaling or before owner custody is transferred to anything other than a simple, well-tested EOA.
