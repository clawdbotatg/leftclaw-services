Security Audit Report: Vaultfire ProductionBeliefAttestationVerifier

Target: ProductionBeliefAttestationVerifier at 0x2a46B5932e9559176241056A04a608B8fEbCc5A7 (Base, chain 8453)
In-scope contracts: ProductionBeliefAttestationVerifier.sol, IRiscZeroVerifier.sol, IStarkVerifier.sol (source extracted from BaseScan's verified Standard-JSON-Input; not present on Sourcify)
Methodology: Two-phase audit — Phase 1 breadth (5 parallel checklist-driven agents: general, precision-math, access-control, governance/timelock, replay-pattern) → Phase 2 depth (12 parallel attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation (this document).
Reconciliation summary: Overlap: 8 findings independently confirmed by both phases · Phase-1-only: 4 (all involving live on-chain verification) · Phase-2-only: 0 genuinely novel (one phase-2 finding sharpened an existing phase-1 finding into two distinct issues) · Demoted on re-examine: 0.
Completeness: every unique (contract, function, bug-class) raised by either phase's raw agent output is represented below.

Independent on-chain verification performed by the orchestrator: two of this report's Critical findings were verified directly against live Base Mainnet state and the real RISC Zero router's Sourcify-verified ABI, not merely inferred from source review — see [C-1] and [C-2] for the exact cast commands and results.

Summary

This contract is meant to be Vaultfire's production RISC Zero zk-proof verifier for "belief attestations." Both audit phases converged on a striking result: the deployed contract has never worked. Its immutable riscZeroVerifier reference points to an address with zero bytecode (not the real, documented RISC Zero router), and — independently, and even after fixing that — the in-scope interface declares a bool return value that the real router's actual ABI does not have, which would cause every genuinely successful verification to revert uncatchably. attestationCount() reads 0 on the live contract, consistent with it never having recorded a single attestation since deployment. Beyond these deployment-breaking issues, both phases also converged heavily on a moduleId truncation bug in the legacy interface that lets a replayed real proof register an arbitrary, unproven module identifier, and on the complete absence of replay protection for verified proofs. The client's specific question — "can the 48-hour VK-rotation timelock be bypassed, even by the owner?" — was traced in full by the governance-focused phase-1 agent and independently re-confirmed by the orchestrator: the timelock holds; there is no bypass.

Critical Severity

[C-1] Deployed riscZeroVerifier immutable points to an address with zero bytecode — the live contract has never successfully verified a single proof

Origin: [phase1 only] (general agent) — independently re-verified live on-chain by the orchestrator via direct cast calls
Location: constructor (207-217), all verification paths

riscZeroVerifier is set once, immutably, in the constructor. On the live deployment it was set to 0xA054f831B562e729F8D268291EBde1B2EDcFb84F — an address with no deployed bytecode — rather than the documented real Base RiscZeroVerifierRouter at 0x0b144e07a0826182b6b59788c34b32bfa86fb711 (hardcoded in this contract's own header comment).

Proof (independently reproduced by the orchestrator against https://mainnet.base.org):

$ cast call 0x2a46B5932e9559176241056A04a608B8fEbCc5A7 "riscZeroVerifier()(address)" --rpc-url $RPC
0xA054f831B562e729F8D268291EBde1B2EDcFb84F
$ cast code 0xA054f831B562e729F8D268291EBde1B2EDcFb84F --rpc-url $RPC
0x                                    # zero bytecode — not a contract
$ cast code 0x0b144e07a0826182b6b59788c34b32bfa86fb711 --rpc-url $RPC
0x6080604052...                      # 4715+ bytes — the real router
$ cast call 0x2a46B5932e9559176241056A04a608B8fEbCc5A7 "attestationCount()(uint256)" --rpc-url $RPC
0
$ cast call 0x2a46B5932e9559176241056A04a608B8fEbCc5A7 "imageId()(bytes32)" --rpc-url $RPC
0xffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff   # placeholder, not a real guest-program hash

attestationCount()==0 and the placeholder imageId corroborate that this "production" contract has never successfully recorded an attestation since deployment (BaseScan shows only one prior transaction, an ownership transfer). Because riscZeroVerifier is immutable, this cannot be fixed in place — it requires a full redeploy.

Recommendation: Redeploy with the correct constructor argument, and add require(_riscZeroVerifier.code.length > 0) in the constructor to catch this exact class of misconfiguration before it can ship again.

[C-2] IRiscZeroVerifier.verify()'s declared returns (bool) does not match the real router's void ABI — even after fixing C-1, every successful verification would still uncaught-revert

Origin: [both] — Phase 1 (general agent) · Phase 2 (all 12/12 agents raised this in some form; 6 independently fetched/confirmed the real interface from GitHub) — independently re-verified by the orchestrator against the real router's Sourcify-verified ABI
Location: IRiscZeroVerifier.sol:45-49; call sites in _verifyAndRecord (317), verifyAttestation (277)

The in-scope interface declares:

function verify(bytes calldata proof, bytes32 imageId, bytes32 journalDigest) external view returns (bool);

The real, deployed RiscZeroVerifierRouter at 0x0b144e07a0826182b6b59788c34b32bfa86fb711 has — confirmed independently by the orchestrator via its Sourcify-verified ABI, and separately by multiple phase-2 agents against the actual risc0-ethereum GitHub source — "outputs":[]: no return value at all. Both call sites use try riscZeroVerifier.verify(...) returns (bool) { ... }, which attempts to ABI-decode a bool from the 0 bytes of return data the real router actually returns on success.

Proof: A decode failure on the success branch of a try statement's return data is, per Solidity's own semantics, not a catchable exception — it propagates as an uncaught revert of the entire transaction, bypassing both catch Error(string) and the bare catch {}. This means: even after redeploying with the correct router address (fixing C-1), every genuinely valid proof would still cause the whole transaction to revert, because the real router returns 0 bytes on success and the calling code cannot decode a bool from that. Only the failure path (the real router reverting on an invalid proof) is a genuine external-call revert that the try/catch correctly intercepts. This bug is independent of, and compounds with, C-1.

Recommendation: Fix IRiscZeroVerifier.sol's verify signature to match the real ABI (no return value), and update both call sites to try riscZeroVerifier.verify(seal, imageId, journalDigest) { ... } catch ... with no returns (...) clause.

High Severity

[H-1] moduleId truncation mismatch in the legacy verifyProof path lets a replayed real seal register an arbitrary, unproven moduleId

Origin: [both] — Phase 1 (precision-math, general, replay-pattern) · Phase 2 (10/12 agents, all with matching numeric PoCs)
Location: verifyProof (224-241) → _verifyAndRecord (299-335) → _recordAttestation (337-365)

verifyProof validates epoch > MAX_EPOCH (guaranteeing lossless truncation to uint32) but has no equivalent bound check on moduleId. _verifyAndRecord computes the cryptographic journal digest using uint32(moduleId) (truncated), but passes the full, untruncated uint256 moduleId to _recordAttestation, which stores/emits it verbatim. Since uint32(x) == uint32(x + k·2^32) for any integer k, any moduleId congruent to the real proven value mod 2^32 produces an identical journal digest and passes verification against the same seal — while a completely different, attacker-chosen value gets permanently recorded on-chain.

Proof: Given one genuine valid seal for real tuple (H, A, E, trueModuleId=7): anyone (no access control on verifyProof) calls verifyProof(seal, [H, uint160(A), E, 7 + 2**32]). uint32(7+2**32)=7, so the digest matches and verification succeeds; _recordAttestation stores/emits moduleId = 4294967303 — a value never proven by the SNARK, overwriting the prior legitimate record (the storage key excludes moduleId — see M-1).

Confirmed NOT applicable to verifyAttestation: one phase-2 agent independently verified via a live Foundry/anvil test that Solidity's abi.decode into a uint32 slot reverts on non-clean upper bits (unlike an explicit narrowing cast, which silently truncates) — so the preferred verifyAttestation path, which decodes epoch/moduleId directly as uint32, cannot diverge this way. Only the legacy verifyProof path is vulnerable.

Recommendation: Add if (moduleId > type(uint32).max) revert InvalidModuleId(); in verifyProof, mirroring the existing epoch check.

[H-2] No replay/duplicate-submission protection — a valid proof can be resubmitted indefinitely to inflate attestationCount and refresh verifiedAt

Origin: [both] — Phase 1 (replay-pattern, general) · Phase 2 (10/12 agents)
Location: _recordAttestation (337-365), reached unconditionally from both verifyProof and verifyAttestation

IRiscZeroVerifier.verify is a stateless, deterministic view check with no on-chain nullifier — the same exact (seal, publicInputs)/(seal, journalData) tuple, permanently visible in public calldata, can be resubmitted by anyone, any number of times, and will re-verify successfully every time. _recordAttestation never checks attestations[key].exists before overwriting, so every resubmission re-increments attestationCount and bumps verifiedAt to the current block timestamp, despite no new proof having been generated.

Proof: Submit a genuine verifyAttestation(seal, journalData) at t0 → attestationCount=1, verifiedAt=t0. Anyone copies the same calldata from the chain and resubmits at t1 → verification succeeds identically, attestationCount=2, verifiedAt=t1 — for an attestation that was never freshly re-proven. Repeatable indefinitely at gas cost only.

Recommendation: Gate _recordAttestation on !attestations[key].exists (or a usedSeal[keccak256(seal)] nullifier) before incrementing attestationCount/overwriting verifiedAt.

[H-3] Single EOA owner has no independent veto/guardian for a pending malicious imageId proposal

Origin: [phase1 only] (access-control) — re-examined against source and confirmed
Location: proposeImageIdChange/cancelImageIdChange/executeImageIdChange (433-467)

The only guard on a new imageId is non-zero — no on-chain validation ties it to any specific, audited guest program. Critically, cancelImageIdChange is itself onlyOwner, so if the owner key is compromised, the attacker who proposed a malicious imageId is the only party who can cancel it; no guardian role exists to veto a pending change during the 48h review window. This is conditioned on owner-key compromise, not directly triggerable by an outside attacker without that precondition.

Proof (trace): Attacker obtains the owner key → calls proposeImageIdChange(evilImageId) where evilImageId is the hash of an attacker-compiled guest program that trivially satisfies any journalDigest the attacker wants → no other address can cancel this during the 48h window → after 48h, executeImageIdChange() succeeds → attacker can now register arbitrary, forged belief attestations that any downstream Vaultfire consumer trusts.

Recommendation: Make owner a multisig/governance contract; add an independent guardian role that can cancel a pending proposal without the proposer's cooperation; consider requiring published, reproducible-build metadata for any proposed imageId.

Medium Severity

[M-1] Attestation storage key and hasAttestation flag omit moduleId (and effectively epoch) — cross-record overwrite and stale-flag issues

Origin: [both] — Phase 1 (precision-math, replay-pattern) · Phase 2 (6/12 agents, as leads — exploitability depends on downstream consumer semantics not in scope)
Location: _recordAttestation (345-347), hasAttestation mapping (176), isAttested (382-387)

The storage key keccak256(abi.encodePacked(beliefHash, attester, epoch)) excludes moduleId, so two independently valid proofs for the same (beliefHash, attester, epoch) but different moduleId silently overwrite each other's record with no error/event signaling the loss (and attestationCount still increments on the overwrite). Separately, hasAttestation[beliefHash][attester] is keyed by neither epoch nor moduleId, is set once and never cleared, so isAttested() returns true forever after a single, possibly very stale, attestation.

Recommendation: Include moduleId in the storage key (keccak256(abi.encodePacked(beliefHash, attester, epoch, moduleId))); re-key or deprecate hasAttestation/isAttested in favor of getAttestation(...).exists, which is at least epoch-aware.

[M-2] verifyAttestation's VerificationFailed event is unconditionally rolled back by the trailing require — permanently unobservable, unlike the identical event on the legacy path

Origin: [both] — Phase 1 (general, replay-pattern — as one component of a broader inconsistency finding) · Phase 2 (4/12 agents independently)
Location: verifyAttestation (277-293)

Both catch branches emit VerificationFailed(...) then set verified=false; the very next line, require(verified, "Attestation proof verification failed"), reverts the whole call. An EVM revert discards every log emitted since the current call frame began, so the just-emitted event never actually reaches a transaction receipt through this entry point — contradicting the function's own inline comment ("AUDIT FIX: Reverts on proof failure instead of silently returning false") and inconsistent with _verifyAndRecord (the legacy path), which emits the identical event and gracefully returns false without reverting, so that event does persist there.

Recommendation: Either drop the revert and return false (matching the legacy path's observable event), or drop the emit-then-revert dance and propagate the failure reason directly via a custom error.

[M-3] Fail-open legacy verifyProof path re-introduces the exact fail-open pattern the contract's own comment says was already fixed for verifyAttestation

Origin: [both] — Phase 1 (general/replay-pattern, as part of the same broader inconsistency finding) · Phase 2 (trust-gap agent, sharpest framing)
Location: verifyProof/_verifyAndRecord (224-241, 299-335) vs. verifyAttestation (254-293)

verifyAttestation's own inline comment states: "AUDIT FIX: Reverts on proof failure instead of silently returning false." This is the team's own documented record that fail-open verification was previously identified and fixed as a security defect for the "preferred" interface. The legacy verifyProof/_verifyAndRecord path — explicitly documented as a "drop-in replacement wherever the existing Vaultfire contracts reference the verifier" — still contains that exact un-fixed fail-open shape: its catch branches emit VerificationFailed(...) and return false with no revert, meaning an integrator who calls the legacy interface without explicitly checking the boolean return would silently treat a rejected proof as accepted.

Recommendation: Apply the same revert-on-failure fix to verifyProof/_verifyAndRecord, or prominently document that every legacy-interface integrator must check the return value.

[M-4] beliefScore is hardcoded to MIN_BELIEF_THRESHOLD (8000) for every attestation — never derived from or bound by the proof

Origin: [both] — Phase 1 (precision-math, general) · Phase 2 (6/12 agents)
Location: _verifyAndRecord (279), verifyAttestation (323), _recordAttestation (337-365)

The journal schema actually committed to and cryptographically checked is only (beliefHash, attester, epoch, moduleId) — no belief score field exists in the journal at all. Both entry points always pass the literal constant MIN_BELIEF_THRESHOLD, which is then stored and emitted, misleadingly implying a proof-derived graded value when every record will read exactly 8000, forever.

Recommendation: Either extend the journal to genuinely commit a score (requires guest-program changes) or rename/document the field to make clear it is a fixed pass/fail sentinel, not a graded score.

[M-5] Single-step transferOwnership with no two-step acceptance — a typo permanently bricks the entire timelock-gated imageId-update path

Origin: [phase1 only] (access-control, governance) — re-examined against source and confirmed
Location: transferOwnership (470-477)

Only a zero-address check guards the new owner; there is no pendingOwner/acceptOwnership two-step pattern. A single mistyped or inaccessible address transfers owner instantly and permanently — every onlyOwner function (including proposeImageIdChange/executeImageIdChange/cancelImageIdChange) then reverts forever, with no recovery path anywhere in the contract (would require a full redeploy plus repointing every downstream consumer).

Recommendation: Implement an Ownable2Step-style pattern (transferOwnership sets pendingOwner; acceptOwnership() finalizes).

[M-6] verifyAttestation omits the zero-value validation present in verifyProof (unconfirmed lead — depends on out-of-scope guest-circuit constraints)

Origin: [both] — Phase 1 (replay-pattern, as a LEAD) · Phase 2 (3/12 agents)
Location: verifyAttestation (254-293) vs. verifyProof (224-241)

verifyProof explicitly rejects beliefHash==0/attester==0 before recording; verifyAttestation performs no equivalent check before computing the digest and recording — an inconsistent-duplicated-logic pattern between two entry points documented as equivalent. Whether this is practically exploitable depends on constraints enforced by the out-of-scope RISC Zero guest program, which no in-scope file can confirm.

Recommendation: Add the same zero-value checks to verifyAttestation for parity.

[M-7] No expiry on a ready-to-execute imageId proposal

Origin: [phase1 only] (governance) — re-examined against source and confirmed
Location: executeImageIdChange (444-456)

Only a floor (block.timestamp >= pendingImageIdEffectiveAt) is checked; there is no upper bound, so a proposal can sit reviewed-and-ready for months before execution, potentially executing long after the community's original review context is stale. Does not itself weaken the minimum-delay guarantee (see the Governance Verdict below).

Recommendation: Add an expiry window forcing re-proposal (and a fresh 48h wait) if execution doesn't happen within a reasonable time of the timelock clearing.

Low Severity

[L-1] Documentation says journalDigest = keccak256(...); the actual implementation uses sha256(...) throughout

Origin: [both] — Phase 1 (general, precision-math) · Phase 2 (4/12 agents)
Location: IRiscZeroVerifier.sol:40-43 vs. actual code (lines 275, 315)

The doc comment is stale/wrong (sha256 is in fact the correct RISC Zero convention, and the code correctly does this); could mislead an off-chain integrator writing a second verifier or guest program against this doc into using the wrong hash function, causing valid-looking proofs to fail digest matching.

Recommendation: Correct the doc comment to sha256.

[L-2] No maximum bound on moduleId's downstream cast in verifyProof's input validation, and publicInputs[1]→address truncation has no defense-in-depth bound check

Origin: [phase1 only] (precision-math) — re-examined against source and confirmed as a best-practice gap distinct from H-1's confirmed exploit
Location: verifyProof line 232 (address(uint160(publicInputs[1])))

No check that publicInputs[1] <= type(uint160).max before truncating to address. Unlike moduleId (H-1), no exploit path was constructed here since the truncated attester value is used consistently everywhere downstream (no divergence point between what's hashed and what's stored) — this is a defense-in-depth gap, not a confirmed vulnerability.

Recommendation: Add if (publicInputs[1] > type(uint160).max) revert InvalidAttesterAddress(); for defense-in-depth.

[L-3] Vaultfire's own custom MissionEnforcement-style "immutability" framing is absent here — N/A, no analogous claim in this contract (informational cross-reference note)

Origin: [phase1 only] — informational note, no finding
Location: N/A

Unlike other Vaultfire contracts audited in prior/parallel engagements, this contract's NatSpec does not make any "immutable, cannot be changed by any authority" claims about the imageId/verifier trust root that the code fails to honor — its documentation accurately reflects that the owner can rotate imageId (behind a genuine 48h timelock) and that riscZeroVerifier truly is immutable. No governance/documentation-mismatch finding applies to this contract.

Informational

  • isAttested/hasAttestation naming vs. actual semantics: the flag means "has ever, at any point, had one successful attestation recorded" — not "is currently/freshly attested" — worth clarifying in NatSpec given the name's implication of currency.
  • Unbounded pending-proposal window (see M-7) and lack of published on-chain metadata for a proposed imageId (see H-3) compound each other: a proposal could sit pending for months with no way for the community to verify what it actually corresponds to beyond the raw bytes32 hash.

Governance Verdict: Client's Specific Claim

Claim under test: "VK rotation timelock cannot be bypassed (even by owner)."

Verdict: CONFIRMED HOLDS.

  • Grep of the full contract confirms imageId has exactly two write sites: the constructor (one-time) and executeImageIdChange(). There is no assembly, delegatecall, or proxy/implementation-swap surface (confirmed the deployed address is a plain, non-proxy verified contract).
  • executeImageIdChange() is unconditionally gated by pendingImageId != 0 and block.timestamp >= pendingImageIdEffectiveAt, and pendingImageIdEffectiveAt is only ever set to block.timestamp + 48 hours inside proposeImageIdChange() — never to an earlier value by any code path.
  • cancelImageIdChange() + re-proposeImageIdChange() only restarts a fresh 48h clock; it can never shorten or skip the wait for whatever value is ultimately executed.
  • A compromised/new owner (via H-3 or M-5) inherits the exact same propose → wait 48h → execute mechanics for any new imageId of their choosing — ownership compromise is a real, separate governance risk (H-3, M-5), but it does not defeat the minimum-delay guarantee itself.

The only real gaps adjacent to this claim are governance-hygiene issues (H-3's missing veto/guardian role, M-5's single-step ownership transfer, M-7's missing proposal expiry) — none of which allow the 48-hour minimum delay on an image-ID rotation to be skipped or shortened.

Methodology Notes

  • Both phases audited the same three in-scope files independently; Phase 2 was run with no visibility into Phase 1's findings to avoid anchoring.
  • Unlike a typical audit, this engagement required and involved genuine live on-chain verification beyond static source review: the orchestrator independently confirmed C-1 and C-2 against Base Mainnet RPC calls and the real router's Sourcify-verified ABI, and one phase-2 agent independently confirmed H-1's truncation-vs-decode distinction via a local Foundry/anvil test. These are noted explicitly in each finding rather than presented as ordinary static-analysis claims.
  • The unusual near-total overlap between phases (8 of 9 substantive phase-2 conclusions independently matching a phase-1 finding, several with independently-fetched corroborating evidence from the real RISC Zero GitHub repository) reflects that this is a small, self-contained contract where both breadth and depth analysis converge on the same small set of root causes — not a methodology failure.
  • Out of scope: the RISC Zero RiscZeroVerifierRouter/underlying verifier implementations and the off-chain RISC Zero guest program (Rust circuit) were not audited; several Medium findings above are explicitly conditioned on assumptions about that out-of-scope code and are flagged as such.
