🔐 Security Review — NativeTokenLimitModule (Vaultfire job #370)

Scope
Target 0x00000000000001e541f0D090868FBe24b59Fbe06 — deployed byte-identically on Base and Ethereum mainnet (chain 8453 and chain 1)
Implementation Sourcify-verified exact match on both chains, solc 0.8.26, verified name NativeTokenLimitModule
Contract Alchemy Modular Account (ERC-6900 permission module, built on ERC-4337). A global singleton, shared by every smart account that installs it, enforcing a native-token (ETH) spend limit per (entityId, account) — the intended use case is capping what a restricted "session key" can spend.

ModularAccountBase.sol (the account contract this module is installed into) was consulted directly for cross-file verification of every finding below, though it is not itself the deployed target of this job.
Method Two-phase: Phase 1 ethskills breadth (6 checklist agents: general, precision-math, erc4337, access-control, dos, assembly) → Phase 2 pashov depth (12 attacker-mindset agents, blind to Phase 1) → hybrid reconciliation with this orchestrator's own direct source verification against ModularAccountBase.sol for every claim that depended on it.

Both were personally re-verified by this orchestrator by reading the referenced sections of ModularAccountBase.sol directly (not just trusting agent claims). Completeness: 9 unique (Contract, function) issues raised across both phases, all 9 covered below (2 Critical/High + 4 Low + 3 Info/no-action items); re-examined leads kept: 7, none demoted.

⚠️ This contract is live on Ethereum and Base mainnet today

Both findings below describe a currently-exploitable bypass of this module's entire stated purpose in its as-deployed state. This report should be escalated to Alchemy's security team in addition to normal delivery, given the module is an active singleton securing real smart-account funds on two live mainnets.

Findings

[Critical] A performCreate call nested inside executeBatch completely bypasses the native-token spend limit

Confidence: 90 · NativeTokenLimitModule.preExecutionHook · [both — independently reached by 4 of 12 phase-2 agents (invariant, execution-trace, boundary, first-principles) with matching exploit chains, plus this orchestrator's own direct verification]

The bug. preExecutionHook's executeBatch branch computes the native value a batch moves purely by summing each top-level Call.value field:

} else if (selector == IModularAccount.executeBatch.selector) {
    Call[] memory calls = abi.decode(callData, (Call[]));
    for (uint256 i = 0; i < calls.length; ++i) {
        value += calls[i].value;
    }
}

(NativeTokenLimitModule.sol:104-108)

This misses an entire class of native spend: a batch item can target the account itself (Call.target == address(this)) with Call.value == 0 and Call.data encoding a call to performCreate(uint256 value, bytes initCode, bool isCreate2, bytes32 salt). The ETH performCreate sends comes from its own value parameter, spent via the create/create2 opcode against the account's balance — not from the outer Call.value the low-level dispatcher forwards. The hook never decodes into Call.data to see this, so it sums 0 for that item.

Why the nested call doesn't get a second chance to be checked. Two independent, compounding reasons, both verified directly against ModularAccountBase.sol:

  1. The deny-list omits performCreate. _checkExecuteBatchValidationApplicability (ModularAccountBase.sol:895-928) explicitly reverts SelfCallRecursionDepthExceeded() only for nested execute/executeBatch self-calls:

    if (
    nestedSelector == IModularAccount.execute.selector
        || nestedSelector == IModularAccount.executeBatch.selector
) {
    revert SelfCallRecursionDepthExceeded();
}
_checkIfValidationAppliesSelector(nestedSelector, validationFunction, checkingType);

    performCreate is not in this list — the check falls through to _checkIfValidationAppliesSelector, a permission check (is this validation allowed to call performCreate), not a hook-execution guarantee.

  2. The nested self-call skips validation-associated hooks. When executeBatch dispatches the nested call, msg.sender == address(this) for that inner call. _checkPermittedCallerAndAssociatedHooks (ModularAccountBase.sol:650-694) branches on exactly this:

    if (msg.sender != address(_ENTRY_POINT) && msg.sender != address(this) && !...) {
    // loads BOTH selector- and validation-associated exec hooks
    ...
} else {
    // sender is the entry point or the account itself — only selector-associated hooks
    execHooks = MemManagementLib.loadExecHooks(_storage.executionStorage[msg.sig]);
}

    NativeTokenLimitModule is installed as a validation-associated hook (tied to the session key's validation, not to the performCreate selector), so this else branch skips it entirely for the nested call.

Concrete exploit. Session key with a global validation, NativeTokenLimitModule installed with limits[entityId][account] = 1 ether, account balance = 100 ETH:

executeUserOp(
  executeBatch([
    Call({ target: account, value: 0, data: performCreate(100 ether, attackerInitCode, false, salt) })
  ])
)
  • Top-level preExecutionHook runs (required — the account forces executeUserOp whenever the validation carries exec hooks, ModularAccountBase.sol:469-473), sums calls[0].value = 0, decrements the limit by 0.
  • The account self-calls performCreate(100 ether, ...). msg.sender == account, so the validation-associated hook is skipped.
  • create(value: 100 ether, ...) (ModularAccountBase.sol:186-188) deploys attackerInitCode funded with the account's entire balance; the deployed contract forwards it to the attacker.
  • limits[entityId][account] is unchanged at 1 ether — as if nothing happened. A direct (non-batched) performCreate(100 ether, ...) call, by contrast, is correctly caught and reverts (NativeTokenLimitModule.sol:109-116); nesting inside executeBatch is the entire gap.

This requires no more than the standard permission this module is installed to grant in the first place (a session key allowed to call executeBatch and performCreate, up to a value cap) — there is no additional precondition.

Fix: in the executeBatch branch, detect self-targeting calls and decode nested performCreate value into the running total:

 } else if (selector == IModularAccount.executeBatch.selector) {
     Call[] memory calls = abi.decode(callData, (Call[]));
     for (uint256 i = 0; i < calls.length; ++i) {
-        value += calls[i].value;
+        value += calls[i].value;
+        if (calls[i].target == msg.sender && calls[i].data.length >= 4) {
+            bytes4 innerSelector = bytes4(calls[i].data);
+            if (innerSelector == ModularAccountBase.performCreate.selector) {
+                (uint256 createValue,,,) = abi.decode(_slice(calls[i].data, 4), (uint256, bytes, bool, bytes32));
+                value += createValue;
+            }
+        }
     }
 }

A more robust account-side fix is to add performCreate (and any other native-value-spending selector) to the nested-self-call deny-list in _checkExecuteBatchValidationApplicability (ModularAccountBase.sol:895-928), forcing it to always run as a top-level call where the hook already works correctly.

[High] updateLimits/onInstall/updateSpecialPaymaster let the capped session key reset its own cap

Confidence: 80 · NativeTokenLimitModule.updateLimits / onInstall / updateSpecialPaymaster · [both — independently reached by access-control (phase1 + phase2), erc4337 (phase1), trust-gap, asymmetry, flow-gap, boundary, first-principles (phase2) — 7+ agents at FINDING confidence, plus this orchestrator's own direct verification]

The bug. All three configuration setters authorize purely on msg.sender, with no notion of which validation/entity within the account is driving the call:

function updateLimits(uint32 entityId, uint256 newLimit) external {
    limits[entityId][msg.sender] = newLimit;
    emit NativeTokenSpendLimitUpdated(entityId, msg.sender, newLimit);
}

function updateSpecialPaymaster(address paymaster, bool allowed) external {
    specialPaymasters[paymaster][msg.sender] = allowed;
    emit SpecialPaymasterUpdated(msg.sender, paymaster, allowed);
}

(NativeTokenLimitModule.sol:56-67) — and onInstall (NativeTokenLimitModule.sol:123-126) unconditionally re-writes limits[entityId][msg.sender] with no "already initialized" guard, giving an identical reset path.

During any call, msg.sender as seen by the module is always the account itself — which is exactly the same regardless of whether the owner's global validation or the restricted session key's own validation triggered it. The module has no way to tell them apart.

Why this is reachable — the assumed protection does not exist. ModuleBase.sol carries this comment:

"Supporting the IModule interface is a requirement for module installation. This is also used by the modular account to prevent standard execution functions execute and executeBatch from making calls to modules."
(ModuleBase.sol:47-49)

This orchestrator directly read ModularAccountBase.execute and executeBatch (ModularAccountBase.sol:227-264) and confirmed no such check exists:

function execute(address target, uint256 value, bytes calldata data) external payable override wrapNativeFunction
    returns (bytes memory result)
{
    ExecutionLib.callBubbleOnRevertTransient(target, value, data);   // no target-is-module check
    ...

The only place type(IModule).interfaceId is checked anywhere in this codebase is at module installation time (ExecutionInstallDelegate.sol:102 — sanity-checking that what's being installed actually implements IModule), which has nothing to do with restricting execute's runtime target. The comment describes protection that is not implemented.

Concrete exploit. Session key with a global validation, capped at limits[entityId][account] = 1 ether:

executeUserOp(
  execute(NativeTokenLimitModule, 0, abi.encodeCall(updateLimits, (entityId, type(uint256).max)))
)
  • preExecutionHook sees execute with value == 0 (the call carries no ETH — it's a data call into the module), so 0 > limit is false and nothing is decremented.
  • The account calls NativeTokenLimitModule.updateLimits(entityId, type(uint256).max) with msg.sender == account, setting limits[entityId][account] = type(uint256).max.
  • A follow-up UO now transfers unlimited ETH — the cap is gone.

Fix: since the module cannot distinguish the account owner from a session key it's meant to restrict, defense must be structural: e.g. only allow a limit to be lowered through this path (require(newLimit <= limits[entityId][msg.sender]) in updateLimits), remove the reset capability from onInstall after first install, or fix the account-level gap the ModuleBase.sol comment assumes exists — actually block execute/executeBatch targets that implement IModule.

[Low] sub(len, 8) can underflow in ModuleBase._getSelectorAndCalldata's assembly block

Confidence: 55 · ModuleBase._getSelectorAndCalldata · [both — flagged by 5+ agents across both phases]

When unwrapping an executeUserOp-wrapped call, the assembly block strips 8 bytes without checking the inner uo.callData is at least that long:

assembly ("memory-safe") {
    selector := shl(224, mload(add(finalCalldata, 8)))
    let len := mload(finalCalldata)
    finalCalldata := add(finalCalldata, 8)
    mstore(finalCalldata, sub(len, 8))   // underflows if len < 8
}

(ModuleBase.sol:254-265). For len < 8 (a malformed inner calldata shorter than a selector-only call), sub(len, 8) wraps to ~`2^256, and for len == 0themstorewrites 8 bytes past the allocated buffer — a genuine memory-safety violation the("memory-safe")annotation doesn't actually hold for in that case. Multiple agents traced this to a dead end: any selector recovered from garbage/adjacent memory won't matchexecute/executeBatch/performCreate, so valuestays0and the call proceeds harmlessly (or the subsequent decode simply reverts, since matching one of the three tracked selectors requireslen ≥ 8`, which precludes the underflow in the only path that would matter). Self-harm/DoS only — not a spend-limit bypass.

Fix: add a length check before the assembly block:

+require(uo.callData.length >= 8, "invalid inner callData");
 assembly ("memory-safe") { ... }

[Low] onUninstall clears limits but leaves specialPaymasters stale

Confidence: 55 · NativeTokenLimitModule.onUninstall · [both — 3+ agents]

function onUninstall(bytes calldata data) external override {
    uint32 entityId = abi.decode(data, (uint32));
    delete limits[entityId][msg.sender];   // specialPaymasters not touched
}

(NativeTokenLimitModule.sol:129-132). specialPaymasters[paymaster][account] entries set via updateSpecialPaymaster persist across uninstall/reinstall. Effect is one-directional (stricter accounting, more gas gets decremented than the operator may expect post-reinstall) — not a fund-loss path, but a surprising state-persistence bug.

Fix: document that operators must explicitly revoke special paymasters before uninstall, or restructure specialPaymasters to be entity-scoped and enumerable so onUninstall can clear it.

[Low] Native-value spend limit only tracks 3 hardcoded selectors — documented but worth reinforcing given the Critical finding above

Confidence: 50 · NativeTokenLimitModule.preExecutionHook · [both — 6+ agents across both phases]

preExecutionHook only extracts a non-zero value for execute, executeBatch, performCreate; the contract's own header comment acknowledges this ("This module only tracks native transfers for the 3 functions"). Confirmed as reachable-by-design, not a bug in isolation — but the Critical finding above demonstrates that even within these three selectors, nesting can defeat the accounting. This is a related structural weakness of the same "sum what I can see, trust nothing else moves value" design and should be revisited together with the Critical fix rather than treated as merely cosmetic.

Info / no-action items (verified, no fix required)

  • Gas-based limit is charged at the worst-case maxFeePerGas with no post-op refund (_decreaseLimit, NativeTokenLimitModule.sol:167-184). Conservative only — the tracked spend always exceeds real spend, so a session key can be throttled sooner than its true consumption but can never exceed its cap through this path. Multiple agents confirmed the computation exactly mirrors EntryPoint v0.7's own _getRequiredPrefund formula.
  • Special-paymaster gas accounting is denominated in native wei, not the actual (possibly ERC20, possibly marked-up) amount the paymaster pulls — a plausible under-accounting if a special paymaster's effective rate exceeds the raw native-gas-equivalent charged. Flagged as an unverified lead by 2 agents; cannot be confirmed or quantified without the specific paymaster's exchange-rate logic, which is out of scope.
  • postExecutionHook unconditionally reverts (NativeTokenLimitModule.sol:135-137) — correct by design (the module has no post-hook logic), but would brick execution if ever installed with the post-hook flag set. A configuration footgun, not a code defect; consider making it a no-op instead of a revert for defense-in-depth against operator misconfiguration.
  • onInstall doesn't emit an event while updateLimits (writing the identical storage slot) does — an observability gap for off-chain monitors, not a security issue.
  • No cross-account griefing surface: every state read/write in this module is keyed by msg.sender (the calling account), verified exhaustively by multiple agents — no function lets one account's call affect another account's limits/specialPaymasters entries.
  • executeBatch value-summation loop is not a DoS vector: bounded by the same gas budget as the (more expensive) dispatch that follows it, and the array is caller-provided per-call, not attacker-growable across calls.
