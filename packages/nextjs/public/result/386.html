Findings

[70] 1. No balance-delta verification on token transfers — fee-on-transfer and no-op/fake tokens let a settlement finalize as "successful" while under-delivering or delivering nothing

DeliveryVersusPaymentV1.executeSettlementInner · Confidence: 70

Description
safeTransferFrom (L358) is trusted at face value with no before/after balance check on flow.to, so a fee-on-transfer token under-delivers, or a creator-controlled fake token that returns true without moving anything delivers zero — while the reciprocal ETH/token leg completes in full and isSettled=true/SettlementExecuted certify the trade as cleanly executed. Confirmed with full concrete proofs by two independent phase-2 attack agents (first-principles: fee-on-transfer scenario; trust-gap-hunter: creator-controlled fake-token scenario) plus phase-1's erc20 checklist agent.

Fix

       } else {
         // ERC-721 or ERC-20 transfer in the same way (must cast to IERC20 for OZ safeTransfer for ERC-20)
         IERC20 eitherToken = IERC20(flow.token);
         // safeTransfer reverts if unsuccessful for ERC-20 and ERC-721
+        uint256 balBefore = flow.isNFT ? 0 : eitherToken.balanceOf(flow.to);
         eitherToken.safeTransferFrom(flow.from, flow.to, flow.amountOrId);
+        if (!flow.isNFT) {
+          require(eitherToken.balanceOf(flow.to) - balBefore == flow.amountOrId, "delivered amount mismatch");
+        }
       }

[65] 2. ETH-escrow vs. token-allowance asymmetry creates a costless, revocable, front-run-protected option for the token-side party

DeliveryVersusPaymentV1.approveSettlements / revokeApprovals · Confidence: 65

Description
ETH legs are fully escrowed at approval (L213-220) while ERC20/ERC721 legs are only backed by a revocable allowance pulled at execution, and revokeApprovals (L444) has no cutoff gate — so the token-side party holds a free, at-will option to let a favorable trade execute or costlessly walk away from an unfavorable one, while the ETH-side party's capital sits locked with only eventual refund (not completion) guaranteed. Quantified by the economic-security phase-2 agent at roughly 3%+ of notional extractable via standard option-value reasoning on a 7-day-to-cutoff fixed-price trade, and independently corroborated as the same design gap by first-principles and trust-gap-hunter agents.

Fix

This is a protocol-design-level gap rather than a single-line bug; two mitigation directions, present as alternatives:

Option A — symmetric escrow (strongest guarantee, requires holding third-party assets):
  At approveSettlements time, additionally pull each non-ETH flow's asset into the
  contract via safeTransferFrom (mirroring the ETH deposit), refundable on revoke/withdraw
  exactly as ETH is. Removes the token-side party's ability to costlessly back out.

Option B — disclosure only (no code change):
  Document prominently, in the contract's own NatSpec and any front-end, that only the
  ETH leg is escrowed; the token/NFT leg remains fully at the sending party's discretion
  (revocable allowance) until the exact block of execution, and ETH depositors bear this
  asymmetric risk for the full window until cutoff.

[55] 3. Missing flow.to == address(this) validation — ERC20/NFT leg to the contract's own address permanently strands the asset with no rescue function

DeliveryVersusPaymentV1.createSettlement / executeSettlementInner · Confidence: 55

Description
createSettlement's validation loop (L274-275) checks from/to are non-zero but never rejects to == address(this); an ETH leg to the contract's own address bricks that settlement (receive() unconditionally reverts, L505-507 — recoverable via revokeApprovals), but an ERC20/ERC721 leg succeeds, delivering the asset into a contract with no sweep/rescue function anywhere — a permanent, unrecoverable loss. Requires the from party's own approval to reach (self-consented), which is why this is scored below the fund-loss findings above, but it is the only unrecoverable end-state in the entire contract.

Fix

       // Validate addresses
       if (flow.from == address(0)) revert InvalidFromAddress();
       if (flow.to == address(0)) revert InvalidToAddress();
+      if (flow.to == address(this)) revert InvalidToAddress();

[45] 4. NFT tokenId-0 collides with the "not ready" sentinel in the status view; nonexistent/burned tokenId reverts the entire party-status view

DeliveryVersusPaymentV1._getTokenStatuses · Confidence: 45

Description
_getTokenStatuses (L557-566) encodes NFT "approved"/"held" status as the tokenId value itself, which is indistinguishable from the "not ready" default of 0 whenever a settlement legitimately uses tokenId 0 (explicitly permitted at creation); separately, getApproved/ownerOf (L561, L565) revert per EIP-721 on a nonexistent/burned tokenId, so one bad NFT flow makes the entire getSettlementPartyStatus view revert and hides an otherwise-ready party's ETH/approval status. View-only, no fund impact, but breaks the off-chain readiness check the contract's own docs recommend using before approving.

[40] 5. isNFT flag validated at creation but unused at execution — amount/tokenId type confusion for dual-interface tokens

DeliveryVersusPaymentV1.createSettlement / executeSettlementInner · Confidence: 40

Description
Creation-time validation branches on isNFT (ERC165 check vs. decimals() heuristic, L278-282), but execution (L344-358) branches only on token==address(0) and uses one uniform safeTransferFrom regardless of isNFT; a hybrid token that passes both checks lets amountOrId be silently reinterpreted between "amount" and "tokenId" depending on the token's real implementation. Independently identified by two phase-2 agents (numerical-gap-hunter, asymmetry) via different reasoning paths; requires a purpose-built hybrid token and an approving party fooled by the mismatch, so confidence is moderate.

Leads

Vulnerability trails with concrete code smells where the full exploit path requires either a self-consenting victim, a purpose-built adversarial token, or produces no fund impact (griefing/observability only). These are corroborated across many independent agents in both phases — not false positives, but calibrated below the scored-finding threshold.

  • Atomic execution bricked by a single bad flow — executeSettlementInner (L344-360) — Code smells: no dedup check on flows (duplicate NFT ids), no re-check of token allowance/pause state between approval and execution, ETH recipient with a reverting receive() — Independently raised by 8 of 19 total sub-agents across both phases (general, erc20, erc721, dos in phase 1; dos, execution-trace, invariant, boundary, asymmetry, trust-gap-hunter in phase 2). Every agent that traced recovery confirmed ETH is always recoverable via revokeApprovals (no cutoff gate) or post-cutoff withdrawETH — griefing/delay only, not fund loss.

  • Manual-execution catch blocks emit-then-revert; Panic re-throw burns all gas — executeSettlement (L309-324) — Code smells: emit SettlementExecutionFailed* immediately followed by revert/invalid()/assembly-revert in the same frame, so the event never persists; the Panic branch's assembly { invalid() } consumes all remaining gas and discards the specific panic code, unlike its sibling branches. Confirmed by 7 independent agents across both phases (general, assembly in phase 1; assembly, economic-security, execution-trace, asymmetry, trust-gap-hunter in phase 2).

  • withdrawETH double-emits ETHWithdrawn — withdrawETH (L492, L499) — Code smells: per-settlement emit inside the loop plus a redundant aggregate emit after — off-chain indexers summing this event double-count withdrawals. Confirmed by 7 independent agents across both phases (general in phase 1; general, invariant, execution-trace, boundary, asymmetry in phase 2, plus the flow-gap-hunter). No fund impact.

  • _isERC20's decimals()-only heuristic is a weak proof of ERC20-ness — _isERC20 (L599-602) — Code smells: accepts any address returning exactly 32 bytes from a decimals() staticcall, never probing transfer/transferFrom/balanceOf; both over-inclusive (non-token contracts with a coincidental match) and under-inclusive (legitimate ERC20s lacking decimals() are rejected, acknowledged in the contract's own NatSpec at L431-434). Feeds directly into Finding 1's exploit surface.

  • Approval-to-execution window lets a token party revoke allowance or get blocklisted, DoS-ing execution — isSettlementApproved (L154-166) — Code smells: readiness is asserted purely from the approvals boolean, never re-checked against live allowance/balance before execution; a party can approve then quietly revoke allowance, causing every execution attempt to fail until corrected. Same underlying mechanism as the atomic-bricking lead above.

  • Misleading code comment overstates the per-flow ETH-deposit invariant — executeSettlementInner (L348-351) — Code smells: comment claims ethDeposits[flow.from] must == flow.amount, which is false whenever a party is from in more than one ETH flow (the deposit is the sum); the subtraction is nonetheless provably safe (verified independently by 4 phase-2 agents: math-precision, invariant, numerical-gap-hunter, boundary), but the stated safety argument is wrong and could mislead a future refactor.

Confirmed clean (both phases, high corroboration)

  • Access control: zero exploitable findings across both phases (2 independent full passes). The ownerless, permissionless design is internally consistent; the sole privileged mechanism (executeSettlementInner's self-call gate) is airtight.
  • Reentrancy: 9 of 12 phase-2 agents independently traced and confirmed the transient nonReentrant guard set by the four outer entrypoints persists through the this.executeSettlementInner self-call, blocking reentry from malicious flow.to/flow.token callbacks. ERC721 transfers use plain transferFrom (no onERC721Received), removing that reentrancy surface entirely.
  • ETH accounting invariants: a dedicated invariant-hunter agent adversarially tested all 8 documented invariants (flow immutability, id monotonicity, one-way isSettled, ETH deposit-sum consistency, exact msg.value enforcement, ETH/token classification, self-only execution, direct-ETH rejection) — all 8 hold. Corroborated independently by math-precision, numerical-gap-hunter, boundary, and execution-trace agents, including the specific multi-ETH-flow-per-party netting edge case and the approveSettlements loop-local variable scoping (no cross-settlement leakage).
  • Boundary conditions: all timing (cutoff > vs. <=, disjoint and gapless), array (empty-array no-ops), and sentinel (id=0, uint128 max) edges independently confirmed clean.
  • Precision/math: the contract is essentially arithmetic-free (no division, multiplication, or share/fee math); no overflow/underflow/rounding findings in either phase.
