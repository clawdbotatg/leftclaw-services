Security Audit Report — RiderBattleEscrow

Target: RiderBattleEscrowV2.sol — deployed on Base mainnet at 0x55c2847003A9e254b8312bf3C75520e06528aBa6
Source: verified via Sourcify (exact match, chain 8453)
Methodology: Two-phase audit — Phase 1 breadth (6 ethskills checklist agents: general, precision-math, erc20, signatures, access-control, dos) → Phase 2 depth (12 independent pashov attacker agents, run blind to Phase 1) → hybrid reconciliation
Scope: single contract, 217 lines (incl. license/comment header), Solidity ^0.8.24, OpenZeppelin v5.x dependencies (IERC20, SafeERC20, ReentrancyGuard, Ownable, ECDSA, MessageHashUtils)

Summary

RiderBattleEscrow is a non-custodial 1v1 ERC20 wager escrow, redesigned ("V2") to avoid transferFrom/approve for Smart Wallet compatibility: players plain-transfer their wager into the contract, then call createMatch/joinMatch to register it. This redesign introduces a critical, unauthenticated deposit-crediting flaw: the contract determines "who deposited" purely from an aggregate balance check (balanceOf(this) - accounted[token]), never from msg.sender. Any address can consume another user's already-transferred-but-not-yet-registered deposit. Every one of the 18 independent audit agents across both phases that examined this code path (6/6 phase-1 checklists that touched it, 12/12 phase-2 attacker agents) identified this exact bug independently — the strongest possible convergence signal.

Beyond the headline bug, the contract has several centralization/trust-model gaps (owner can retroactively change fee rates and refund windows on already-escrowed matches) and fund-lock risks if the owner ever allowlists a non-standard ERC20 (rebasing, deflationary, or blacklist-capable).

Reconciliation summary: Overlap: 3 findings confirmed independently by both phases · Phase-1-only: 3 findings (2 Low, plus fuller detail on 1 shared High) · Phase-2-only: 0 promoted findings (2 new leads) · Re-examined leads kept: 6, demoted: 0.

Completeness: 8 unique (contract, function, bug-class) groups raised across both phases' raw output; all 8 are represented in the findings/leads below.

Findings

[C-1] Unauthenticated deposit crediting — anyone can steal another user's in-flight wager transfer

Severity: Critical
Origin: [both] — corroborated by 18/18 agents that reached this code path (6 phase-1 checklist agents + all 12 phase-2 attacker agents), unanimous across two independently-run, methodologically distinct passes
Location: createMatch() L103-112, joinMatch() L115-126, _received() L95-97

Description

function _received(address token) internal view returns (uint256) {
    return IERC20(token).balanceOf(address(this)) - accounted[token];
}

_received(token) is a single, per-token global pool with no attribution to any specific depositor. createMatch/joinMatch only check _received(token) >= wager (L107, L119) — they never verify that msg.sender is the address that actually performed the incoming transfer. The contract's own design comment (L9-25) explicitly anticipates a non-atomic, two-transaction deposit flow for "non-batch wallets" ("an abandoned 2-step deposit on a non-batch wallet") — meaning the exploit window is not a contrived edge case, it is the documented fallback path.

Proof of Concept

Token T allowed, accounted[T] = 0, contract balance 0.

  1. Victim Alice sends T.transfer(escrow, 100e18) (tx1), intending to follow with createMatch(1, T, 100e18) (tx2) — the documented 2-step flow.
  2. Before tx2 lands, attacker Mallory calls createMatch(999, T, 100e18). L107: _received(T) = 100e18 - 0 = 100e18 >= 100e18 passes, using Alice's deposit — Mallory transferred nothing. L109: accounted[T] += 100e18. L110: matches[999] = Match(creator: Mallory, ...).
  3. Alice's tx2 now reverts: _received(T) = 100e18 - 100e18 = 0 < 100e18 → "deposit first". Alice's funds are now locked inside Mallory's match.
  4. After acceptWindow (24h default), Mallory calls cancelUnaccepted(999) (L150-160): msg.sender == m.creator ✓, time elapsed ✓ → accounted[T] -= 100e18, safeTransfer(Mallory, 100e18) (L158). Mallory extracts Alice's 100e18 tokens for the cost of two function calls and zero capital.

The identical mechanism applies to joinMatch (L115-126): an attacker calls joinMatch(matchId) on any Open match using a stray unaccounted balance (their own, or a real opponent's just-landed transfer racing their own joinMatch call), becomes m.opponent, and later collects via refundStalled (L162-172) if unsettled. In this variant the true depositor is never recorded anywhere in the Match struct — not creator, not opponent — so no function in the contract can ever pay them back; their funds are unconditionally lost.

Amplifier: for a rebasing/interest-accruing allowlisted token, balanceOf(this) can grow every block with zero transfers in, continuously regenerating a harvestable surplus via the same createMatch → cancelUnaccepted loop — turning a one-off race into a repeatable extraction with no victim required at all.

Recommendation

- function createMatch(uint256 matchId, address token, uint256 wager) external nonReentrant {
-     require(allowedToken[token], "token not allowed");
-     require(wager > 0, "wager=0");
-     require(matches[matchId].status == Status.None, "exists");
-     require(_received(token) >= wager, "deposit first");
-
-     accounted[token] += wager;
+ function createMatch(uint256 matchId, address token, uint256 wager) external nonReentrant {
+     require(allowedToken[token], "token not allowed");
+     require(wager > 0, "wager=0");
+     require(matches[matchId].status == Status.None, "exists");
+     IERC20(token).safeTransferFrom(msg.sender, address(this), wager);
+     accounted[token] += wager;
      matches[matchId] = Match(msg.sender, address(0), token, wager, uint64(block.timestamp), 0, Status.Open);
      emit MatchCreated(matchId, msg.sender, token, wager);
  }

Pull the deposit atomically inside createMatch/joinMatch via safeTransferFrom (this requires an approval — the exact friction V2 was designed to avoid for Smart Wallets, but it can still be sent as one atomic EIP-5792 batch: [approve, createMatch] instead of [transfer, createMatch]). If approve-based pulls are unacceptable, bind the credited amount to the depositor instead — e.g. a deposit() call that snapshots pendingDeposit[msg.sender][token] in the same transaction as the transfer (via a router/multicall entry point) — so createMatch/joinMatch consume only from a ledger keyed by the caller's own address, never a raw unattributed contract-wide balance.

[H-1] refundStalled/settle have no rescue path if a participant or treasury is a blacklisted/reverting recipient

Severity: High
Origin: [phase1: dos]
Location: refundStalled() L162-172, settle() L145-146

Description: Both functions unconditionally safeTransfer to both parties (or winner + treasury) in one transaction, with no try/catch or pull-payment fallback. If a token blacklists (USDC-style) or otherwise reverts transfers to one recipient, the whole call reverts — including the state transition to Refunded/Settled — permanently freezing the match. sweepUnaccounted can never touch accounted funds tied to a match, so there is no owner rescue path once this happens.

Proof of Concept: Match funded with a blacklist-capable token; one participant's address gets blacklisted (independently of this contract, e.g. by the token issuer) before refundStalled/settle is called. safeTransfer to that address reverts every time; the match stays Funded forever with both parties' funds stuck and zero recourse.

Recommendation: Switch to a pull-payment pattern — credit an internal per-address balance mapping and let each party withdraw independently — so one recipient's failure cannot block the other's payout.

[H-2] Rebasing/deflationary tokens can desync the global accounted[token] invariant and strand match funds

Severity: High
Origin: [both] — phase-1 erc20 checklist provided the full trace; phase-2 agents (access-control-lens, boundary, numerical-gap) independently flagged the same underlying balanceOf < accounted desync as a lead but did not complete a full trace, so this is presented at the phase-1 confidence level per the hybrid re-examine (confirmed on source re-read)
Location: _received() L95-97, settle() L141-146, refundStalled() L162-172, sweepUnaccounted() L211-216

Description: accounted[token] is a single global counter shared across every match using that token — nothing enforces balanceOf(this) >= accounted[token]. If the owner ever allowlists a rebasing/negative-yield token, the real contract balance can fall below accounted[token] without any transfer, causing _received() to underflow/revert (DoS on all new matches for that token) and/or causing settle()/refundStalled()'s safeTransfer to attempt moving more than the contract holds (stranding that specific match's funds). Because the pool is shared rather than siloed per match, a shortfall anywhere can propagate to make an unrelated, otherwise-healthy match unsettleable.

Proof of Concept: Match A funded with rebasing token T (accounted[T]=200, balanceOf=200). A 10% negative rebase drops balanceOf to 180 with no transfer event. Any subsequent createMatch/joinMatch on T reverts (underflow at L96). settle(A,...) computes pot=200, attempts to transfer 200 T total, but the contract only holds 180 — the transfer reverts and match A's funds are permanently stuck.

Recommendation: Restrict setTokenAllowed (via owner process, not code) to tokens verified non-rebasing/non-deflationary; defensively cap transfers against actual live balanceOf rather than nominal accounted amounts; consider per-match escrow accounting instead of one global counter per token.

[M-1] Protocol fee is read live at settlement, not locked in when a match is funded

Severity: Medium
Origin: [both] — phase-1 (access-control, signatures, general leads) + phase-2 (trust-gap finding, invariant/first-principles leads); 6 agents total across both phases
Location: settle() L135-142, feeBps() L89-92, setTokenFee()/setDefaultFee() L176-185

Description: feeBps(m.token) is a live view read at settlement time (L142); it is never snapshotted when a match is created/funded, and it is not bound in the settler-signed digest (keccak256(abi.encode(chainid, address(this), matchId, winner)), L136-137). The owner can call setTokenFee/setDefaultFee at any time up to the 10% cap — including immediately before a pending settle() transaction confirms — retroactively changing the winner/treasury split for an already-signed, already-funded match. This is a retroactive rewrite of an already-escrowed value's terms, not merely "admin doing admin things": both players deposited and the settler signed under one fee assumption, and the owner alone can change the outcome economics of that specific, already-locked trade after the fact.

Proof of Concept: Match funded under the 5% defaultFeeBps. Owner calls setTokenFee(token, 1000) (10% cap) in the same block as, or front-running, a pending settle() tx. settle() computes fee at the new 10% rate instead of the 5% rate the players funded the match under, doubling the treasury's cut of that specific pot at the winner's expense.

Recommendation:

  struct Match {
      address creator;
      address opponent;
      address token;
      uint256 wager;
      uint64  createdAt;
      uint64  fundedAt;
      Status  status;
+     uint16  feeBpsSnapshot;
  }

Snapshot feeBps(token) into the Match struct at createMatch time and use the stored value in settle().

[M-2] settleWindow/acceptWindow are global, retroactively-applied, and unbounded above

Severity: Medium (High for settleWindow, since it can permanently strand both players' escrowed stakes with no rescue path; Medium for acceptWindow, since it strands only the creator's own single stake and a legitimate join can still unlock other paths)
Origin: [both] — phase-1 access-control (2 findings, High + Medium) + phase-2 trust-gap (1 finding, confidence 80)
Location: cancelUnaccepted() L150-160, refundStalled() L162-172, setWindows() L203-207

Description: acceptWindow/settleWindow are read live from mutable global state at refund-check time rather than snapshotted per match, and setWindows enforces only a 1-hour lower bound with no upper bound. The owner can call setWindows(1 hours, type(uint256).max) after a match is already Open/Funded, making that match's timeout condition permanently unreachable. For a Funded match this closes the only trustless exit (refundStalled) — the sole remaining path is settle(), which strictly requires the current settler's cooperation; if that party is unavailable, colludes, or ownership has been renounced, both players' wagers are stuck with zero recourse, directly contradicting the "non-custodial" design claim in the contract header.

Proof of Concept: Match becomes Funded at fundedAt=T. Owner calls setWindows(1 hours, type(uint256).max). refundStalled's check block.timestamp >= T + settleWindow (now effectively infinite) can never be satisfied — this and every other currently-Funded match loses its trustless refund path permanently.

Recommendation: Snapshot acceptWindow/settleWindow into the Match struct at creation/funding time, and cap setWindows to a sane maximum (e.g. 30 days) as defense in depth.

[M-3] sweepUnaccounted has no cooldown, letting the owner front-run and drain a player's in-flight deposit

Severity: Medium — requires a malicious or compromised owner to trigger; no unprivileged amplifier exists, so treat as a centralization/trust-model gap rather than a permissionless fund-loss vector
Origin: [both] — phase-1 general (finding) + phase-2 (leads from 4 of 12 agents; one agent promoted to finding, demoted here per gate discipline since no unprivileged actor can trigger this independently of owner action)
Location: sweepUnaccounted() L211-216

Description: sweepUnaccounted has no minimum age/cooldown and no per-depositor allowlist — it cannot distinguish a genuinely abandoned deposit from one that is one block away from being legitimately claimed via createMatch/joinMatch. The doc comment assumes good faith ("recovers tokens... never assigned to a match") but the code enforces nothing. An owner (or compromised owner key) watching the mempool can sweep a player's deposit in the exact window described in [C-1], before the depositor's own registration call lands.

Recommendation: Add a minimum age/cooldown before an unaccounted balance becomes sweepable (e.g. track per-token last-deposit timestamp, require it exceed a grace period comparable to acceptWindow).

[L-1] Single-step ownership transfer

Severity: Low
Origin: [phase1: access-control]
Location: inherited Ownable.transferOwnership()

Description: Contract inherits plain OpenZeppelin Ownable (not Ownable2Step, confirmed by reading the vendored @openzeppelin/contracts/access/Ownable.sol). A mistyped or inaccessible new-owner address permanently disables every onlyOwner function (fee config, token allowlist, settler, treasury, windows, sweep) with no recovery.

Recommendation: Use OpenZeppelin's Ownable2Step.

[L-2] Fee math rounds down (occasionally to zero), favoring the winner over the treasury

Severity: Low
Origin: [phase1: precision-math]
Location: settle() L142

Description: fee = (pot * feeBps(token)) / 10_000 truncates. For wager < 10_000 / (2*feeBps) (e.g. wager <= 4 at the 10% cap), the fee truncates to exactly 0, and in every case the truncated remainder is paid to the winner instead of retained by the treasury — the wrong rounding direction for protocol revenue. Dust-scale value leak only; no realistic large-scale fund-loss vector.

Recommendation: Round the fee up (e.g. Math.mulDiv(pot, feeBps(token), 10_000, Math.Rounding.Ceil)), and/or enforce a sane minimum wager.

Leads

High-signal trails for manual review — not independently exploitable to full confidence, or excluded from Findings for requiring pure admin misbehavior with no unprivileged amplifier.

  • Return-data-bomb / adversarial balanceOf() — _received() / sweepUnaccounted() call balanceOf() directly with no bounded-return handling; only reachable for owner-allowlisted tokens. (phase1: dos)
  • Gas griefing via transfer hooks — a hook-bearing "weird" token allowlisted by the owner could grief settle()'s external transfer calls; standard ERC20 transfer has no callback so this depends entirely on owner's token choice. (phase1: dos)
  • sweepUnaccounted trusts the accounted invariant with no on-chain assertion — every mutation site was traced and found internally consistent for standard ERC20s; [H-2] already demonstrates one concrete way the invariant can break (rebasing tokens). (phase1: access-control; phase2: numerical-gap, boundary — same observation, independently)
  • Fee-on-transfer wager mismatch — caller must know the exact post-fee amount in advance or the call reverts; increases the likelihood of stray unaccounted dust, the exact precondition [C-1] relies on. (phase1: erc20)
  • sweepUnaccounted lacks the nonReentrant guard applied to every other fund-moving function — asymmetric with the rest of the codebase; not independently exploitable today (owner-gated, standard ERC20 has no callback) but becomes a live reentrancy surface if the owner ever allowlists an ERC-777-style hook token. (phase2: numerical-gap)
  • matchId collisions turn ordinary, non-adversarial usage into stray sweepable/stealable balance — two users racing to create a match under the same matchId causes the loser's createMatch to revert with "exists" after their transfer already landed, feeding the same pool [C-1] exploits, with no attacker required. (phase2: flow-gap)
