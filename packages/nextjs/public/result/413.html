Findings

[H-1] Arbitrator reputation and resolved-count accrue only on the fallback-resolver path — exact inverse of the verifier-bond slash condition — guaranteeing honest arbitrators a loss and collapsing all $100+ dispute resolution onto one governance address

Severity: High · Confidence: 95 · Origin: [both] — independently found by 9 of 12 Phase-2 attack agents (5 as full FINDINGs: access-control, invariant, asymmetry, trust-gap, flow-gap; 4 more as corroborating LEADs) and Phase 1's evm-audit-general agent.

Location: ArbitrationModule.sol — resolveDispute() L612-618, _finalise() L707-710 (qualifiedResolution), _prepareVerifierBondSlash() L771-777, proposeArbitrator() tier gates L528-540; sole writer of arbitratorReputation is ReputationRegistry.recordArbitratorResolution (ReputationRegistry.sol:193), reachable only via the gated callback.

Description: resolvedCount[arbitrator] and arbitratorReputation[arbitrator] are incremented ONLY when d.fallbackReplacementUsed == true — i.e. only when the single owner-configured fallbackResolver was seated. _prepareVerifierBondSlash applies the 10%-of-bond slash on the exact logical inverse condition (!d.fallbackReplacementUsed, confirmed by the code's own comment at L767-769: "Every arbitrator-backed ruling carries this penalty... Timeout and fallback paths do not slash"). So mutual-consent arbitrators — the protocol's advertised primary arbitration mechanism — are always slashed and never earn reputation; the fallback resolver is never slashed and is the only address that ever earns reputation. proposeArbitrator's tier-2 gate (rep>=200 && resolvedCount>=5, no bootstrap bypass, unlike tier-1) is therefore permanently unsatisfiable for any mutually-selected arbitrator.

Verified directly against source (lines quoted above match exactly what all 9 converging agents cited).

Proof of Concept: MIN_VERIFIER_BOND = 1 ether; slash = bond/10 >= 0.1 ETH. Arbitrator's only revenue is the forfeited dispute bond, capped at MAX_DISPUTE_BOND = $100. A mutual-consent arbitrator's ruling is therefore always net-negative — max +$100 vs. guaranteed ≥0.1 ETH loss — for every dispute size, every time. Trace: arbitrator A is mutually seated on a $50 (tier-1) dispute → rules → _prepareVerifierBondSlash fires (loses bond/10) → resolvedCount[A]/arbitratorReputation[A] stay 0 (gated on the opposite flag) → repeat any number of times, A's reputation never moves → A can never satisfy tier-1's rep>=50 without an owner bootstrapQualified grant, and can never satisfy tier-2 (no bootstrap escape exists there) → every $100+ dispute is unseatable by any mutual arbitrator and is forced onto the single fallback resolver or a 21-day timeout.

Amplification: ArbitrationModule.escalate() is free, permissionless-to-either-party, and one-directional — either poster or worker can unilaterally force any dispute's tier up to 2 with no counterparty consent, deliberately routing it into the permanently-unseatable bracket and forcing the counterparty into the 7-day fallback delay or 21-day timeout. This turns the incentive bug into an active, zero-cost griefing/delay vector.

Recommendation: Decouple the reward and slash conditions so they are not exact inverses. Grant resolvedCount/arbitratorReputation for every successful byArbitrator ruling regardless of fallbackReplacementUsed (matching the "every arbitrator-backed ruling" framing already in the slash comment), so honest mutual-consent arbitrators can build the reputation the tier system requires of them. Add a regression test asserting escalate() cannot be used to force disputes into a bracket no arbitrator can ever qualify for.

[H-2] ArbitrationRecoveryCoordinator.cancelRecovery() after enterRecoveryLockdown() permanently latches the module's recoveryLockdown flag, freezing dispute-opening, the stale-review escape hatch, and — for tasks whose deadline hadn't already passed — the task-expiry clock forever, locking escrow permanently

Severity: High · Confidence: 90 · Origin: [phase1: dos] — independently re-verified line-by-line against source during Phase 3 reconciliation (see math below).

Location: ArbitrationModule.sol — recoveryLockdown (L80, set true only at L316, never written false anywhere in the contract — grep-confirmed exhaustive), enterRecoveryLockdown() (L309-318, permissionless-to-coordinator, callable the instant pendingArbitration != 0), disputeOpeningPaused() (L367-370, returns true whenever recoveryLockdown), totalDisputeOpeningPausedTime() (L375-398); ArbitrationRecoveryCoordinator.sol — cancelRecovery() (L154-160, clears only the coordinator's own pending state, has no call into the module to clear lockdown); consumers TaskRegistry.openDispute (ArbitrationModule.sol:447), TaskRegistry.resolveStaleReview (TaskRegistry.sol:570), TaskRegistry.expireTask (TaskRegistry.sol:666-673).

Description: recoveryLockdown is a one-way latch. The coordinator's enterRecoveryLockdown() is permissionless once a recovery is proposed; cancelRecovery() — a documented, legitimate governance action to abort a bad proposal — clears the coordinator's pending state but has no path to unset the module's recoveryLockdown. The only code path that would exit lockdown is completing a full module swap via executeRecovery. If a proposal is aborted after lockdown was entered, the currently-wired module is stuck in permanent lockdown.

Proof of Concept / mechanics (verified directly against source):

  1. Owner proposeRecovery(newModule). Anyone calls coordinator.enterRecoveryLockdown() → ArbitrationModule.recoveryLockdown = true permanently (never reset).
  2. Owner reconsiders and calls cancelRecovery() — pending state cleared, but the module is still locked down and still the wired module.
  3. openDispute reverts forever (disputeOpeningPaused() returns true unconditionally once recoveryLockdown). resolveStaleReview reverts forever (same guard).
  4. expireTask's check is block.timestamp > t.deadline + pauseDelta, where pauseDelta = totalDisputeOpeningPausedTime() - _taskPausedTimeAtCreation[taskId]. Once lockdown is permanent, totalDisputeOpeningPausedTime() grows exactly 1:1 with block.timestamp (confirmed algebraically: for T >= lockdownStart L, pausedTime(T) = total + (T - L), so pauseDelta(T) = total + (T-L) - baseline, and the expiry inequality T > deadline + total + (T-L) - baseline simplifies to the time-independent condition L > deadline + total - baseline). For any task whose adjusted deadline had not already passed at the moment lockdown began, this condition is false at L and remains false for all future T — the task can never expire.

Net effect: any task ACTIVE or IN_REVIEW with a silent counterparty at the moment of step 1 can never be disputed, never be stale-review-resolved, and never be expired. Its escrowed USDC is permanently locked, with no remaining code path to release it (the only remaining lever, executeRecovery, itself requires the very dispute-opening/expiry machinery this bug disables to eventually clear any new disputes — though a fresh proposeRecovery→lockdown-avoiding-cancel→executeRecovery sequence, run to completion without cancelling, would still work; the bug is specifically that cancelling after lockdown leaves no recovery path except finishing a swap the owner no longer wants).

Recommendation: Add a coordinator→module exitRecoveryLockdown() call, invoked from cancelRecovery(), that clears recoveryLockdown and finalizes the accrued paused-time interval (mirroring the owner-pause bookkeeping already used for setDisputeOpeningPaused). Alternatively, forbid cancelRecovery() once lockdown has been entered, forcing the flow to always resolve via a completed executeRecovery (a stricter but simpler guarantee that lockdown is always temporary).

[M-1] Recovery execute+grace window (9 days) is shorter than the maximum dispute lifetime (21 days), letting an in-flight dispute force a maximal, repeatable global dispute-freeze

Severity: Medium · Confidence: 90 · Origin: [both] — Phase-2 flow-gap agent (full FINDING, numeric trace) and Phase-1 evm-audit-dos agent (DoS-2); constants independently re-verified in Phase 3.

Location: ArbitrationRecoveryCoordinator.sol — RECOVERY_DELAY = 7 days (L46), RECOVERY_GRACE_PERIOD = 2 days (L47), executeRecovery() requiring activeDisputeCount()==0 within recoveryExecutableAt + RECOVERY_GRACE_PERIOD (L165-169, L175); finalizeExpiredDisputes() (L135-152, all-or-nothing gate on isActiveDisputePastDeadline); ArbitrationModule.sol — ABSOLUTE_RESOLUTION_TIMEOUT = 21 days (L27), absoluteDeadline = block.timestamp + ABSOLUTE_RESOLUTION_TIMEOUT (L474).

Description: 9 days (RECOVERY_DELAY + RECOVERY_GRACE_PERIOD) < 21 days (ABSOLUTE_RESOLUTION_TIMEOUT) — confirmed by direct constant lookup. Any dispute open at lockdown time whose absolute deadline exceeds the 9-day recovery window cannot be force-drained by finalizeExpiredDisputes (which only touches disputes already past their own 21-day deadline) before the recovery attempt's grace window closes, so executeRecovery reverts and governance must re-propose (another 7-day delay). This compounds directly with H-2: during the entire stuck window, dispute-opening and task-expiry are frozen by the same recoveryLockdown mechanics.

Proof of Concept: an adversary (cost: one funded task + a small dispute bond) opens a dispute and never lets it resolve, timed 0-12 days before a recovery proposal — this guarantees the first executeRecovery attempt fails, forcing up to ~21 days of protocol-wide freeze before the lingering dispute finally ages out and a re-proposed recovery can succeed. Bounded (not permanent, since disputes cannot be replenished once openDispute is blocked by lockdown), but a real, cheap, repeatable griefing vector for delaying legitimate governance recovery.

Recommendation: Set RECOVERY_GRACE_PERIOD >= ABSOLUTE_RESOLUTION_TIMEOUT - RECOVERY_DELAY so a single recovery proposal window can always fully drain the active-dispute set, or decouple "active dispute" liveness from recovery execution via a lockdown-time cutoff snapshot that finalizeExpiredDisputes can act on immediately rather than waiting for each dispute's individual 21-day clock.

[M-2] Owner's guardian-approved fallback-resolver override does not clear a stale pending normal rotation, letting anyone permissionlessly reverse the emergency override

Severity: Medium · Confidence: 90 · Origin: [phase1: governance] — independently re-verified against source in Phase 3 (see code excerpt below).

Location: ArbitrationModule.sol — acceptFallbackResolverOverride() (L175-196, confirmed: clears only pendingFallbackResolverOverride/fallbackResolverOverrideReadyAt/fallbackResolverOverrideGuardianApproved, never pendingFallbackResolver/fallbackResolverReadyAt); executeFallbackResolverRotation() (L215-229, permissionless).

Description: If a normal (no-guardian) rotation to R_bad is pending when the owner performs a guardian-approved emergency override to R_safe, the override installs R_safe correctly but leaves pendingFallbackResolver = R_bad armed. Because executeFallbackResolverRotation() requires no permission at all, anyone can call it after the original delay elapses to flip fallbackResolver back to R_bad — defeating the guardian-approved override via a path that never involved the guardian. cancelFallbackResolverRotation() is unavailable while an override is pending, so the owner cannot pre-empt this.

Proof of Concept: pending rotation R_bad armed → owner+guardian override to R_safe (fallbackResolver = R_safe, but pendingFallbackResolver = R_bad survives, verified at L192-195: only override-specific state is deleted) → anyone calls executeFallbackResolverRotation() inside the original grace window → fallbackResolver = R_bad. The fallback resolver rules on frozen escrow splits via resolveDispute, so this is a real seizure of dispute-resolution authority with no guardian consent.

Recommendation: In acceptFallbackResolverOverride(), also delete pendingFallbackResolver; delete fallbackResolverReadyAt; — mirror the correctly-written sibling TreasuryRouter.acceptFeeRecipientOverride() (verified at TreasuryRouter.sol:446-447, which does clear both).

[M-3] Owner's buyback-executor override does not clear a stale pending self-rotation, letting the stale executor permissionlessly reverse the owner's recovery

Severity: Medium · Confidence: 90 · Origin: [phase1: governance] — independently re-verified against source in Phase 3.

Location: TreasuryRouter.sol — acceptBuybackExecutorOverride() (L175-198, confirmed: clears only pendingBuybackExecutorOverride/buybackExecutorOverrideProposedAt, never pendingBuybackExecutor/buybackRotationProposedAt). Same root defect as M-2, in the treasury.

Description: Identical mechanism to M-2. A stale pendingBuybackExecutor = A (from a normal self-proposed rotation) survives an owner override to a safe S. A can then call the self-service acceptBuybackExecutor() within the grace window to flip buybackExecutor back, redirecting the 40% USDC buyback revenue stream to A. cancelBuybackExecutorRotation() is blocked while the override is pending.

Proof of Concept: pendingBuybackExecutor = A armed → owner overrides to safe S (installed, pendingBuybackExecutor = A survives per the verified code) → A calls acceptBuybackExecutor() within grace → buybackExecutor = A → next flushBuybackShare() sends 40% of protocol USDC revenue to A.

Recommendation: In acceptBuybackExecutorOverride(), also delete pendingBuybackExecutor; delete buybackRotationProposedAt; — mirror acceptFeeRecipientOverride.

[M-4] feeRecipient/buybackExecutor owner-override paths have no guardian approval and no dedicated cancel function — the incumbent has zero ability to veto an owner seizure

Severity: Medium · Confidence: 85 · Origin: [phase1: access-control] — independently re-verified: TreasuryRouter.sol has cancelBuybackExecutorRotation() and cancelFeeRecipientRotation() but no cancelBuybackExecutorOverride/cancelFeeRecipientOverride function exists anywhere in the file (grep-confirmed), unlike ArbitrationModule.sol which has both approveFallbackResolverOverride (guardian-gated) and cancelFallbackResolverOverride.

Location: TreasuryRouter.sol — setFeeRecipientOverride()/acceptFeeRecipientOverride() (L421-449); setBuybackExecutorOverride()/acceptBuybackExecutorOverride() (L167-198). Distinct root cause from M-2/M-3 above — same functions, different defect (missing guardrail entirely, vs. a state-clearing bug in an otherwise-present guardrail).

Description: Unlike the fallback-resolver override (guardian co-approval required, cancelable by owner OR guardian), the TreasuryRouter overrides are pure onlyOwner + delay/grace with no guardian sign-off and no cancel path at all. The incumbent feeRecipient (controls 20% USDC reserve + all AZL/native fees) and buybackExecutor (receives the 40% buyback share) have no ability to stop an owner from redirecting all future protocol revenue to an owner-controlled address.

Proof of Concept: owner setFeeRecipientOverride(ownerAddr) → no guardian sign-off required, no cancel function exists for the incumbent to call → after the 2-day delay, acceptFeeRecipientOverride() installs ownerAddr → owner drains usdcReserve/accruedFees/accruedNative via withdrawFees/withdrawNativeFees.

Recommendation: Make the TreasuryRouter overrides symmetric with ArbitrationModule's fallback-resolver override: require separate-guardian co-approval (guardian != owner()) and add explicit cancelFeeRecipientOverride/cancelBuybackExecutorOverride functions callable by owner OR guardian OR the current holder.

[M-5] Just-in-time 1-wei staker can capture an entire orphaned reward-gap emission in one lump, self-triggerable by the last staker who exits mid-stream

Severity: Medium · Confidence: 80 · Origin: [both] — Phase-2 economic-security agent (full FINDING, numeric trace) and Phase-1 evm-audit-defi-staking/evm-audit-precision-math agents.

Location: UnionStakingVault.sol — _updateRewardAcc() (~L315-325, folding undistributedRewardsScaled into accUsdcPerToken in one lump the instant totalStaked > 0 again); contract header's documented stake×time invariant.

Description: Reward emissions that stream while totalStaked == 0 mid-stream (distinct from the zero-stake-at-notifyReward-call-time branch, which IS guarded — see Info section) are not dropped; they accumulate in undistributedRewardsScaled and are credited in full to whoever holds trivial stake at the instant the next accrual runs — contradicting the code's own "earns only for seconds actually staked" documentation.

Proof of Concept: sole staker Alice fully unstakes (no cooldown exists) 1 day into a 7-day, ~10,000 USDC stream → totalStaked = 0 for 3 days while ~4,286 USDC-equivalent of stream accumulates unowned → any account (including Alice herself) stake(1 wei) then claimRewards() → captures the entire orphaned lump for 1 wei staked ~0 seconds. Self-triggerable: Alice can deliberately create the gap she later sweeps, with no cooperation or victim-timing luck needed — this is a real extraction from the pool of honest future stakers' expected pro-rata share, not mere dust.

Recommendation: Either don't carry gap-period slices forward (route to TreasuryRouter reserve instead), or re-stream orphaned slices over a fresh duration on the next notifyReward rather than lump-crediting them to whoever is staked at the instant accrual next runs.

[L-1] Guardian-approval consent gate on the fallback-resolver override is circumventable via the ordinary (no-guardian) rotation path

Severity: Low · Confidence: 80 · Origin: [phase1: governance + access-control] — raised independently by both the Phase-1 governance and access-control agents (same root cause, merged here per the wide-description dedup rule).

[L-6] (reachability unconfirmed) Stale verifier-bond slash amount can be permanently deferred on retry if the arbitrator's bond shrinks before the retry executes

Severity: Low · Confidence: 55 (code defect confirmed; triggering precondition not established by any of 6 independent Phase-2 agents that specifically hunted for it — reported per the audit's confidence floor with an explicit reachability caveat) · Origin: [both] — Phase-1 evm-audit-general/evm-audit-precision-math and 6/12 Phase-2 agents (economic-security, execution-trace, invariant, first-principles, boundary, numerical-gap).

Location: ArbitrationModule.sol — _trySlashVerifierBond() (~L788, clamps slashAmount = currentBond when the bond has shrunk, but does not re-derive the 10% cap); ReputationRegistry.sol — slashVerifierBond() (L246-249, independently re-checks amount <= currentBond*1000/10000).

Description: IF a slash is ever deferred (every agent that traced this concluded the synchronous in-_finalise attempt always succeeds under normal flow — bond is locked through absoluteDeadline and recordNativeSlash cannot revert, so no live trigger for the initial deferral was found) AND the bond then shrinks before a retry (e.g. slashed by a second, concurrent dispute the same arbitrator was seated in), the stored bond/10 amount can be <= currentBond (clamp doesn't fire) yet > currentBond/10 (registry's cap reverts) — the retry re-defers forever, permanently blocking ArbitrationRecoveryCoordinator.executeRecovery (pendingSideEffectCount()==0 requirement).

Recommendation: In _trySlashVerifierBond, recompute as min(storedAmount, currentBond/10) rather than clamping only against currentBond — a one-line defensive fix regardless of current reachability.

  • Guardian provides no real check on a live malicious owner (cancelOwnerRecovery is instant onlyOwner; owner appoints/rotates the guardian; guardian==owner by default at deploy). Disclosed centralization tradeoff, not a bypass of a stated protection. [phase1: governance]
  • finalizeExpiredDisputes batch reverts entirely if it hits a not-yet-expired dispute at swap-pop index 0 mid-batch — gas waste only, no fund/liveness risk beyond M-1's timing. [phase2: periphery]
  • Sub-wei-of-USDC stranded reward-accumulator dust if streaming stops forever, and EscrowVault.split() rounds a sub-unit worker slice to zero in the poster's favor — both immaterial in magnitude. [phase1: precision-math]
  • Systemic USDC/AZL issuer-blocklist or pause risk: pooled USDC is frozen if any protocol vault address is ever blocklisted by Circle (no migration path, one-time-locked wiring); AZL access-fee debt is unrepayable — locking the debtor's USDC principal — if AZL itself is ever paused/blocklisted for all willing repayers. Both inherent to any protocol custodying these tokens long-term; not third-party-triggerable under current token behavior. [phase1: erc20]
