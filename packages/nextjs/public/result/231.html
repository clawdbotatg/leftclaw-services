Detailed Findings

[C-1] No User-Initiated Withdrawal — Complete Exchange Custody

Severity: Critical
Confirmed By: ethskills + pashov
Location: bulkWithdrawItems() (0xeaa2fcda)

Description: Every withdrawal path requires an EXCHANGE_ROLE-signed message. There is no emergency withdrawal callable by the asset owner without exchange server participation. The bulkWithdrawItems() function immediately checks EXCHANGE_ROLE and reverts with "EM: exchange?" if the caller lacks it. Users who deposit assets are entirely dependent on the exchange server — a custodial model with no trustless escape.

If the EXCHANGE_ROLE EOA (0xC89C2E6FE...64020) goes offline, is compromised, or its key is lost, all escrowed assets are permanently locked. No emergencyWithdraw, no time-locked release, no owner-initiated rescue exists anywhere in the 4-byte dispatch table.

Proof of Concept:

  1. User deposits NFT via escrow deposit flow
  2. Exchange server goes offline
  3. User calls bulkWithdrawItems(...) → reverts with "EM: exchange?"
  4. No alternative withdrawal function exists
  5. Assets permanently locked

Recommendation: Add a time-locked user-initiated withdrawal activated after a minimum escrow period:

uint256 constant EMERGENCY_COOLDOWN = 7 days / 12; // ~50,400 blocks
function emergencyWithdraw(uint256 itemId) external nonReentrant {
    require(escrows[itemId].owner == msg.sender, "EM: are you owner?");
    require(block.number >= escrows[itemId].depositBlock + EMERGENCY_COOLDOWN);
    _releaseItem(itemId, msg.sender);
}

[C-2] Uninitialized Implementation — Direct Initialization Succeeds

Severity: Critical
Confirmed By: ethskills + pashov (eth_call confirmed)
Location: __EthscriptionMarket_init() (0x628c868d) on implementation 0x11BA2230F...

Description: The implementation contract's _initialized storage slot is 0. eth_call to __EthscriptionMarket_init() directly on the implementation succeeds with 0x return (no revert). Any EOA can call the initializer, setting itself as Ownable owner and DEFAULT_ADMIN_ROLE holder on the implementation's own storage.

While TransparentUpgradeableProxy uses separate storage (so proxy state is unaffected), initializing the implementation creates a vector for delegatecall-based attacks if future upgrades or misconfigurations route calls to the unprotected implementation. This is a fundamental security hygiene failure.

Proof of Concept:

cast call 0x11BA2230F2275e9DedF3a3147249E9bcB6ACadB4 "0x628c868d"
# Returns: 0x  (SUCCESS — no revert)

Recommendation: Add constructor to implementation:

constructor() {
    _initialized = true;  // Prevent direct initialization
}

[C-3] Single EOA Controls All Upgrades — No Timelock or Governance

Severity: Critical
Confirmed By: ethskills + pashov
Location: ProxyAdmin 0xddac..., owner 0x92545Caf... (EOA)

Description: A single EOA (0x92545Caf...) owns the ProxyAdmin AND is DEFAULT_ADMIN_ROLE AND Ownable owner. This single key can upgrade the ORDEX implementation to any arbitrary contract with zero delay, zero governance, and zero user warning. A compromised key enables full asset drain in 2 transactions:

tx1: ProxyAdmin.upgrade(proxy, maliciousImpl)
tx2: maliciousImpl.drainAll(attacker)
// All escrowed NFTs transferred. ~30 seconds.

Recommendation: Replace EOA with Gnosis Safe multisig (2/3 minimum). Add TimelockController (48h minimum delay) between multisig and ProxyAdmin. Emit upgrade events well before execution to allow user exit.

[C-4] Global Sequential Nonce — Consumed on Revert, Blocks All Users

Severity: Critical
Confirmed By: ethskills + pashov
Location: lastUsedNonce() = 1440; bulkWithdrawItems() nonce logic

Description: A single global nonce shared across ALL users and ALL operations. The nonce is stored BEFORE the item-processing loop. If the loop reverts (OOG, blocked token, bug), the nonce is consumed but no items processed. User must request new signature for N+1. With a global sequential counter, User B cannot withdraw until User A's nonce confirms — any stuck transaction creates indefinite queues for all pending users.

This is an architectural flaw requiring a contract upgrade to fix.

Proof of Concept:

Exchange signs: User A → nonce 1441, User B → nonce 1442
User A's loop reverts (OOG) — nonce 1441 consumed, items unprocessed
User B submits nonce 1442 → REVERTS because nonce validation fails
Both users must request new signatures

Recommendation: Per-user nonces:

mapping(address => uint256) public userNonces;
require(nonce == userNonces[op.from] + 1, "bad nonce");
userNonces[op.from]++;

[C-5] ERC1155 Callback Re-entrancy in checkout() ⚠️

Severity: Critical (lower confidence — source unverified)
Confirmed By: pashov
Location: checkout() — ERC1155 transfer path

Description: ERC1155's safeTransferFrom() invokes onERC1155Received() on the recipient contract. If checkout() calls this BEFORE clearing the escrow record, a malicious buyer contract can re-enter checkout() or bulkWithdrawItems() for the same item while the escrow still shows it as active.

The "ReentrancyGuard: reentrant call" string confirms OZ ReentrancyGuard exists, but its placement on checkout() cannot be confirmed without source code. If nonReentrant is absent from checkout(), this is a live drain vector.

Proof of Concept:

  1. Exchange calls checkout(seller, erc1155Collection, tokenId, price) with MaliciousBuyer (contract) as buyer
  2. ERC1155 safeTransferFrom invokes MaliciousBuyer.onERC1155Received()
  3. Callback calls bulkWithdrawItems with pre-signed exchange sig for same tokenId
  4. If escrow record not yet cleared, withdrawal passes; item issued twice

Recommendation: Apply nonReentrant to checkout(). Follow CEI: clear escrow BEFORE transfer.

[C-6] Double-Spend: Concurrent checkout() + bulkWithdrawItems() ⚠️

Severity: Critical (lower confidence — source unverified)
Confirmed By: pashov
Location: checkout() + bulkWithdrawItems()

Description: No per-item escrow lock prevents the same item from being processed by both checkout() (no nonce) and bulkWithdrawItems() (nonce-based) simultaneously. The EXCHANGE_ROLE holder (0xC89C...) could dispatch both operations, and an MEV bot observing both pending transactions can order them to double-extract the item.

Proof of Concept:

  1. Exchange dispatches checkout(Alice, collection, X, 0) AND signs withdrawal for Alice (nonce 1441) for same item X
  2. MEV bot submits checkout first → item to fake buyer
  3. MEV bot submits bulkWithdrawItems → if tokenBalances[collection][Alice] not yet decremented, item transferred again

Recommendation: Implement per-item status flags. Both checkout() and bulkWithdrawItems must atomically transition item from Active to Pending to prevent concurrent processing.

[H-1] checkout() Unilateral Server-Side Asset Transfer

Severity: High
Confirmed By: ethskills + pashov
Location: checkout(address,address,uint256,uint256) (0x07d28902)

Description: checkout() requires only EXCHANGE_ROLE — no user counter-signature, no item ownership verification. The exchange can call checkout(victim, attacker, anyItemId, 0) to steal any escrowed item. A single EXCHANGE_ROLE key compromise enables draining all user assets.

Recommendation: Require time-bounded seller EIP-712 signature in checkout().

[H-2] Instant Role Grants — No Timelock

Severity: High
Confirmed By: ethskills + pashov
Location: grantRole(bytes32,address) (confirmed via eth_call simulation)

Description: DEFAULT_ADMIN_ROLE can grant EXCHANGE_ROLE to any address instantly. Combined with checkout() having no user consent, admin key compromise allows full drain in 2 transactions.

Recommendation: TimelockController (24h+) on EXCHANGE_ROLE grant operations.

[H-3] INDEXER_ROLE Can Remap Items to Malicious Collections

Severity: High
Confirmed By: ethskills + pashov
Location: itemToCollection(uint256), collectionTypes(address) setters

Description: 2 INDEXER_ROLE EOAs control itemToCollection and collectionTypes mappings. A compromised or malicious indexer can remap a legitimate item to a malicious collection, causing checkout() to invoke arbitrary external code on the malicious contract.

Recommendation: itemToCollection should be immutable after deposit. Apply timelock to any mapping updates.

[H-4] cooldownPeriod = 0 — No Flash-Escrow Protection

Severity: High
Confirmed By: ethskills + pashov
Location: cooldownPeriod() returns 0 (on-chain confirmed)

Description: No minimum time between deposit and withdrawal. Enables: flash-escrow cycling, wash trading at zero cost, potential double-spend in same block.

Recommendation: Set cooldownPeriod to minimum 5 blocks (Ethscriptions protocol standard).

[H-5] EXCHANGE_ROLE is an Upgradeable Proxy — Independent Admin Attack Path

Severity: High
Confirmed By: pashov
Location: 0xC89C2E6FE008592D6a787eFd02DB7fDB8eA64020

Description: EXCHANGE_ROLE holder is itself a TransparentUpgradeableProxy with an independent upgrade admin. Compromising the exchange proxy's admin key enables upgrading it to an arbitrary implementation that calls checkout() and bulkWithdrawItems() to drain all escrowed assets — bypassing the ORDEX ProxyAdmin security entirely.

Recommendation: Verify exchange proxy's admin is governed by the same multisig/timelock as ORDEX. Do not grant EXCHANGE_ROLE to upgradeable contracts unless their governance is equivalent to ORDEX's.

[H-6] tokenBalances Inflatable via Direct NFT Transfer ⚠️

Severity: High (lower confidence — source unverified)
Confirmed By: pashov
Location: tokenBalances(address,address) write path via onERC721Received/onERC1155Received

Description: Direct NFT transfers to the escrow contract via safeTransferFrom may credit tokenBalances[collection][from] without registering the specific tokenId in escrows[itemId]. If withdrawal validation checks aggregate balance but not per-item ownership, an attacker with an inflated balance can withdraw other users' items.

Recommendation: Validate per-item ownership via escrows[itemId].owner == user in ALL withdrawal paths.

[H-7] checkout() Accepts price = 0 — Costless Asset Extraction

Severity: High
Confirmed By: pashov
Location: checkout(address,address,uint256,uint256) — price parameter

Description: No lower-bound on price. EXCHANGE_ROLE can transfer any item at price = 0. Combined with no user signature requirement in checkout(), this enables 100% extraction of escrowed NFT value by the exchange operator at zero cost.

Recommendation: require(price > 0) and add seller signature requirement.

[H-8] Cross-Function Signature Replay (Withdraw/Transfer) ⚠️

Severity: High (lower confidence — source unverified)
Confirmed By: pashov
Location: bulkWithdrawItems() + bulkTransferItems() signature structs

Description: Both functions accept identical signature structs. If the signed digest does not include a function-type discriminator, a withdrawal signature can be replayed as a transfer to a different address, or vice versa.

Recommendation: Include function type ("WITHDRAW"/"TRANSFER") in every signed digest.

[M-1] No Chain ID or Contract Address in Signed Messages

Severity: Medium
Confirmed By: ethskills + pashov
Location: Signature hash construction in bulkWithdrawItems()/bulkTransferItems()

Description: Bytecode analysis shows no EIP-712 domain separator (no block.chainid, no address(this)). Signed messages are replayable on any chain where ORDEX is deployed at the same address, and on Ethereum forks.

Recommendation: Implement full EIP-712 domain separator including chainId and verifyingContract.

[M-2] checkout() Self-Transfer — Fee Bypass and Wash Trading

Severity: Medium
Confirmed By: ethskills + pashov
Location: checkout(address seller, ...)

Description: No check prevents seller == msg.sender. A user can wash-trade their own item at price = 0, bypassing fees and generating fake trade history. Fee calculation also rounds to 0 for small prices (price < 10000/feeBps).

Recommendation: require(msg.sender != seller, "EM: self-trade") and enforce minimum price.

[M-3] Global Nonce Front-Running DoS

Severity: Medium
Confirmed By: ethskills + pashov
Location: lastUsedNonce() / bulkWithdrawItems()

Description: A mempool observer can front-run any pending bulkWithdrawItems by submitting any valid exchange-signed operation with the same nonce, consuming it and invalidating the victim's transaction.

Recommendation: Per-user nonces eliminate this attack entirely.

[M-4] Unbounded Bulk Array — Nonce Consumed on Gas Exhaustion

Severity: Medium
Confirmed By: ethskills + pashov
Location: Bulk functions' array iteration

Description: No upper bound on uint256[] itemIds. If a large array causes OOG, the nonce is consumed but items are unprocessed (nonce stored before loop). User must request new signature.

Recommendation: require(itemIds.length <= 50). Store nonce AFTER loop completion.

[M-5] extcodesize Check Bypassed During Construction

Severity: Medium
Confirmed By: ethskills + pashov
Location: bulkTransferItems() — "EM: not to contract" check

Description: extcodesize(recipient) == 0 returns 0 for contracts during constructor execution. An attacker can use CREATE2 to pre-compute a contract address, obtain an exchange signature for that address (appears as EOA), then deploy malicious contract to receive items.

Recommendation: Use allowlist of registered users rather than extcodesize checks.

[M-6] Upgrade Can Reset lastUsedNonce — Historical Signatures Replayable

Severity: Medium
Confirmed By: pashov
Location: upgradeTo() / lastUsedNonce storage slot

Description: If a new implementation has different storage layout and lastUsedNonce resets to 0, all 1440 previously consumed signed messages become replayable.

Recommendation: Verify lastUsedNonce slot preservation in upgrade process. Emit boundary event before any upgrade.

[M-7] collectionTypes Change Mid-Escrow Permanently Locks Items

Severity: Medium
Confirmed By: pashov
Location: collectionTypes(address) setter

Description: Changing a collection's type while items are escrowed causes all subsequent transfers to revert (wrong interface). Items become unrecoverable.

Recommendation: Prevent type changes when tokenBalances are non-zero for that collection.

[M-8] No Events on checkout() — Silent Stealth Drain

Severity: Medium
Confirmed By: pashov
Location: checkout()

Description: No event literals for item sales found in bytecode. Exchange can transfer all escrowed items via checkout() with no indexed on-chain audit trail visible to users.

Recommendation: Emit indexed ItemSold(seller, buyer, collection, itemId, price, timestamp) in every checkout().

[M-9] Deadline Not Confirmed in Signed Digest ⚠️

Severity: Medium (lower confidence — source unverified)
Confirmed By: pashov
Location: Signature struct (uint256 nonce, uint8 v, bytes32 r, bytes32 s)

Description: Deadline is not visible in the signature struct. If passed as separate calldata not included in digest, an attacker can substitute any deadline value while reusing an old signature.

Recommendation: Include deadline in signed digest.

[M-10] Solidity 0.7.6 Under 0.8.2 Proxy — False Overflow Safety

Severity: Medium
Confirmed By: pashov
Location: Implementation (0.7.6) + Proxy (0.8.2)

Description: Proxy compiled with overflow-safe 0.8.2. Implementation uses 0.7.6 — no built-in overflow protection. The proxy's delegatecall runs 0.7.6 bytecode with zero overflow protection. Creates false sense of security.

Recommendation: Recompile implementation under 0.8.x or ensure SafeMath throughout.

Severity: Info

Risk Assessment

Critical Path

The most dangerous combination is: admin key compromise → grantRole(EXCHANGE_ROLE, attacker) → checkout(victim, attacker, itemId, 0) × N items. This can drain all escrowed assets in a single block. The window for users to react is zero since there is no timelock and no emergency withdrawal mechanism.

Trust Model Assessment

The ORDEX escrow operates as a custodial service where users must trust:

  1. The exchange server (EXCHANGE_ROLE) not to steal items via checkout() or unilateral transfers
  2. The admin (0x92545Caf...) not to upgrade to a malicious implementation
  3. The exchange proxy's own admin (separate entity) not to upgrade the exchange proxy
  4. The INDEXER_ROLE holders not to remap items to malicious collections

This is a 4-party trust requirement with no trustless escape for users. The effective security model is equivalent to a centralized exchange holding user assets.

Comparative Note

The open-source EthscriptionsMarketV3 (from the ethscriptions-protocol GitHub) uses a more trust-minimized design: per-seller signatures in buyWithSignature(), no EXCHANGE_ROLE, no server signing requirement. The deployed ORDEX implementation is architecturally much more centralized.

Recommendations Priority

Immediate (Pre-Launch / Emergency)

  1. Verify source code on Etherscan
  2. Migrate ProxyAdmin to Gnosis Safe + TimelockController
  3. Add emergency user-withdrawal function (7-day cooldown)
  4. Add seller signature requirement to checkout()
  5. Require price > 0 in checkout()

Short-Term (Next Contract Version)

  1. Switch to per-user nonces
  2. Implement full EIP-712 domain separator
  3. Add function-type discriminator to signatures
  4. Set cooldownPeriod to minimum 5 blocks
  5. Add itemId-level escrow status flags to prevent concurrent processing

Medium-Term

  1. Recompile implementation under Solidity 0.8.x
  2. Use OZ ECDSA library instead of raw ecrecover
  3. Restrict collectionTypes and itemToCollection changes while items are escrowed
  4. Add indexed events to all state-changing functions
  5. Verify EXCHANGE_ROLE proxy's governance is equivalent to ORDEX's

Audit Confidence Note

Findings marked ⚠️ carry lower confidence due to unverified source code. Specifically:

  • [C-5]: ERC1155 reentrancy — depends on whether nonReentrant is applied to checkout()
  • [C-6]: Double-spend — depends on exact ordering of state updates vs. external calls
  • [H-6]: tokenBalances inflation — depends on whether receiver hooks validate specific tokenIds
  • [H-8]: Cross-function replay — depends on whether signed digest includes function type
  • [M-9]: Deadline in digest — depends on exact message struct encoding

All other findings are supported by on-chain evidence and bytecode analysis with high confidence.
