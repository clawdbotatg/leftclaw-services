Summary

PoidhV3 ("proof of idea") is a bounty-escrow protocol: an issuer posts ETH as a solo bounty (issuer alone funds and accepts) or an open bounty (multiple contributors pool ETH; once any non-issuer joins, claim acceptance must go through a weighted vote instead of unilateral issuer accept). Claims mint an NFT into this contract's escrow via an external, out-of-scope IPoidhClaimNFT contract; accepting a claim pays the claimant (minus a 2.5% fee to an immutable treasury) and transfers the NFT to the bounty issuer. All ETH exits are pull-based. There is no admin, owner, pause, or upgrade mechanism anywhere in the contract — every configuration value is immutable, constant, or (in one case, votingPeriod) simply has no setter.

The audit found one High-severity finding that breaks the contract's core stated security property: the open-bounty vote — the mechanism that exists specifically to stop an issuer from unilaterally paying out pooled contributor funds — has no quorum and auto-registers the issuer's own stake as a YES vote. A bounty issuer can, in the ordinary case of contributor inattention (no exotic precondition required), route the entire pooled bounty to a second address they control. A related Medium finding shows the same voting mechanism can be used to freeze contributor withdrawals indefinitely at negligible cost to the issuer. All other domains (reentrancy, math/precision, access control below the voting layer, DoS, chain-specific L2 behavior, NFT escrow mechanics) were checked in depth and hold up, with a handful of Low/Informational items noted below.

This report reflects one independent audit run (phase-0 context map → phase-1 breadth → phase-2 depth → reconciliation); findings were not copied from any prior review of this or a related deployment.

Findings

[85] 1. No-quorum weighted vote lets a minority-stake bounty issuer drain pooled contributor funds

PoidhV3.submitClaimForVote / PoidhV3.resolveVote · Confidence: 85

Description
The open-bounty vote — the mechanism that exists specifically to stop an issuer from unilaterally paying out pooled contributor funds (acceptClaim's direct-accept path is force-disabled once everHadExternalContributor is set, L774) — auto-registers the issuer's own contribution as a YES vote (L672: Votes({yes: issuerWeight, no: 0, deadline: deadline})) and then resolves on a majority of cast weight only (L719: bool passed = v.yes > ((v.no + v.yes) / 2);), with no quorum against total pooled weight. Since only the bounty issuer's own address is barred from submitting a claim (L591: if (msg.sender == bountyIssuer) revert IssuerCannotClaim(); — a second address they control is not barred), an issuer can: fund an open bounty with a small stake, let contributors pool a large amount, submit a claim from a second address, start the vote, and — if no contributor casts an active NO vote within the 2-day votingPeriod — the vote passes on the issuer's own minority stake alone (no=0 makes yes > yes/2 true for any nonzero yes), routing the entire pool (minus the 2.5% fee) to the second address.

Concretely verified: issuer funds with MIN_BOUNTY_AMOUNT (e.g. 0.01 ETH, becomes participantAmounts[bountyId][0]); contributors add 100 ETH (bounty.amount = 100.01 ETH); issuer's second address S calls createClaim (passes the IssuerCannotClaim check since S != issuer); issuer calls submitClaimForVote, seeding yes = 0.01e18, no = 0; if contributors do not vote within 2 days, resolveVote computes 0.01e18 > 0.005e18 → true, and _acceptClaim (L797-L818) credits S with 100.01 * 0.975 ≈ 97.51 ETH via pendingWithdrawals[claimIssuer] += payout — withdrawable immediately via withdraw().

Twelve independent phase-2 attacker agents (every specialty and gap-hunter lens run) and two independent phase-1 domain checklists (evm-audit-general, evm-audit-governance) converged on this identical mechanism from different angles, with matching traced numbers. One agent additionally showed a strictly worse sub-case: if the issuer's own weight exceeds the combined weight of all contributors, yes > (yes+no)/2 reduces algebraically to yes > no, so the vote passes even against unanimous contributor NO votes — contributors cannot block it at all in that configuration, regardless of participation.

This is rated High rather than Critical because contributors do have a defense (actively casting NO with combined weight ≥ the issuer's) when the issuer does not hold majority stake — the loss requires the realistic-but-not-universal precondition of contributor inattention or an issuer holding majority weight. Given the severity of impact (complete, irreversible loss of all pooled funds) and the ease of the attack (one extra address, no special capital), this sits at the top of the High band.

Fix

+ // In submitClaimForVote, accumulate total snapshotted weight for the round:
+ uint256 totalWeight;
  for (uint256 i = 0; i < p.length; i++) {
    address a = p[i];
    uint256 w = amounts[i];
    if (a != address(0) && w > 0) {
      voteWeightSnapshot[bountyId][a] = w;
      voteWeightSnapshotRound[bountyId][a] = roundId;
+     totalWeight += w;
    }
  }
+ // store totalWeight in the round's Votes struct (or a parallel mapping)

- bool passed = v.yes > ((v.no + v.yes) / 2);
+ bool passed = v.yes > (totalSnapshotWeight[bountyId] / 2);

Require the passing side to exceed half of the total pooled weight at snapshot time, not half of only the votes actually cast, in both resolveVote (L719) and resetVotingPeriod (L744). Consider also excluding the issuer's own weight from the automatic YES seed so passage requires genuine non-issuer approval.

[75] 2. Costless, unlimited vote re-submission lets an issuer indefinitely freeze contributor withdrawals

PoidhV3.submitClaimForVote / PoidhV3.withdrawFromOpenBounty · Confidence: 75

Description
withdrawFromOpenBounty reverts with VotingOngoing for the entire duration a vote is active (via _requireActiveBounty, L252). Only the issuer can start a vote (submitClaimForVote, issuer-only, L643), and there is no cooldown, no cap on rounds, and no restriction against re-submitting a claim that already lost a vote (L648 only checks claim.accepted, which stays false on a failed round). An issuer can therefore: let a round fail (contributors successfully vote NO), then immediately call submitClaimForVote again on the same claimId in the next transaction, re-freezing withdrawals for another full votingPeriod (2 days), repeating indefinitely at a cost of one transaction per round. A contributor's only escape is winning a sequencer-ordering race in the narrow gap between the failed round's resolution and the issuer's next submission — practically unwinnable against an attentive issuer. This both amplifies Finding 1 (contributors must win every round; the issuer needs only one lapse) and stands alone as a pure fund-freeze griefing vector even when the issuer never wins a vote outright.

Fix

+ mapping(uint256 => uint256) public lastVoteFailedAt;

  function submitClaimForVote(uint256 bountyId, uint256 claimId) external nonReentrant {
    _requireActiveBounty(bountyId);
    _requireOpenBounty(bountyId);
+   require(block.timestamp >= lastVoteFailedAt[bountyId] + VOTE_COOLDOWN, "cooldown");
    ...

Enforce a cooldown after a failed round before the same bounty can re-enter voting, and/or forbid resubmitting a claimId that already lost a vote in a prior round.

[70] 3. _acceptClaim's trailing NFT transfer has no recovery path if it reverts on an open bounty past a passed vote

PoidhV3._acceptClaim · Confidence: 70

Description
All state finalization in _acceptClaim — bounty/claim closure, pull-payment credits to the claimant and treasury (L801-817) — happens before the external NFT transfer, which is the last statement (L822: poidhNft.transferFrom(address(this), bountyIssuer, claimId);). If this call reverts (the out-of-scope NFT contract is paused, blacklists an address, or the escrowed token was moved/burned by a party other than PoidhV3 — plausible if the NFT is not exclusive-minter/operator-locked, an assumption this contract cannot verify on its own), the entire transaction — including the payout credits — rolls back. For a solo bounty this is recoverable (cancelSoloBounty still works). For an open bounty whose vote has already passed, every recovery path is structurally blocked: resolveVote re-reverts on every retry, resetVotingPeriod refuses to discard a winning tally (VoteWouldPass, L745), and cancelOpenBounty/refund functions require the bounty not be mid-vote. If the NFT transfer can never succeed, the escrowed contributor funds are locked permanently with no operator recovery (no admin exists in this contract at all).

Fix

- poidhNft.transferFrom(address(this), bountyIssuer, claimId);
+ try poidhNft.transferFrom(address(this), bountyIssuer, claimId) {} catch {
+   // record claimId as pending NFT delivery; allow a separate retryable claim function
+   // so fund settlement is never coupled to NFT delivery outcome
+ }

Decouple fund settlement from NFT delivery so a delivery failure cannot brick an already-decided, already-paid acceptance.

Low Severity

4. Broken pagination in the four "paginated" view getters — PoidhV3.getBounties / getClaimsByBountyId / getBountiesByUser / getClaimsByUser

All four getters loop for (uint256 i = array.length; i > offset && counter < 10; i--) (e.g. L839) — the walk always starts at the array's tail, regardless of offset; offset only shortens the result from below, it never advances the read window. Verified by trace: with bounties.length == 25, getBounties(0) and getBounties(10) return the identical newest-10 set, since both start at index 24 and the counter < 10 condition ends the loop first. No offset value below length-10 changes the output at all, and entries below the newest 10 are permanently unreachable through these getters (they remain readable via the public bounties(i)/claims(i) array accessors). No fund/security impact — a data-reachability defect affecting any off-chain indexer or frontend that relies on these getters for pagination.

Fix: compute the window start from offset directly (e.g. uint256 start = length > offset ? length - offset : 0, then walk back 10 from start) instead of using offset as a lower bound on a tail-anchored walk.

5. Open bounty with an external contributor has no permissionless liveness fallback if the issuer goes silent

Once any non-issuer contributes, only the issuer can start a vote (submitClaimForVote, L643) or cancel the bounty (cancelOpenBounty, L531). If the issuer goes silent after a claim is created, that claim's escrowed NFT is stranded forever (no reclaim path exists) and the claimant is never paid. Contributors' own principal remains recoverable via withdrawFromOpenBounty while the bounty stays active, so this is a liveness/griefing gap for claimants specifically, not a fund-theft vector for contributors.

Fix: add a permissionless, deadline-gated fallback (e.g., any active participant may submitClaimForVote after a grace period), or explicitly document issuer-controlled finalization as a trust assumption claimants should be aware of.

Informational

  • mintToEscrow return value is unchecked — createClaim (L610). If the external NFT contract silently no-ops or mints to the wrong owner, createClaim still records the claim; the mismatch only surfaces later as a hard revert at _acceptClaim's transferFrom (L822), feeding into Finding 3's lock scenario.
  • Non-accepted claim NFTs are permanently stranded in escrow — only the single winning claim's NFT is ever transferred out; every losing/cancelled/abandoned claim's NFT sits in this contract forever with no burn/reclaim path. UX/lifecycle gap, not a fund-theft vector.
  • No emergency pause or recovery mechanism; immutable dependency on the external NFT contract — a deliberate design tradeoff (no admin = no rug potential), but a broken/hostile poidhNft (immutable, unswappable, L33) can brick accept/claim flows protocol-wide with no operator remedy.
  • votingPeriod (L27) is a mutable-typed storage variable with no setter — functionally fixed at 2 days (no writer exists anywhere in the file), but its non-constant/non-immutable type is misleading and not compiler-enforced.
  • Duplicated vote pass/fail expression at two call sites — the identical predicate v.yes > ((v.no + v.yes) / 2) is written independently at resolveVote L719 and resetVotingPeriod L744; currently consistent (verified), but a future edit to one without the other risks desync. Recommend extracting to a shared internal helper — same fix location as Finding 1's quorum change.
  • _acceptClaim's solvency check is provably dead code — if (bounty.amount > address(this).balance) revert InsufficientBalance(); (L789) compares one bounty's tracked amount against the aggregate contract balance (every bounty's escrow plus all pending withdrawals combined). Since balance == Σbounty.amount + ΣpendingWithdrawals holds under every traced mutation, bounty.amount is always ≤ balance by construction — the check can never fire under honest accounting and cannot be forced to fire adversarially. Harmless; gives a false impression of a meaningful per-bounty solvency guarantee.
  • Fee rounds to zero for sub-40-wei bounties — fee = bountyAmount * 250 / 10000 (L797) truncates to 0 when bountyAmount < 40 wei; only reachable if MIN_BOUNTY_AMOUNT/MIN_CONTRIBUTION (immutable, unconstrained beyond nonzero in the constructor) are deployed below that floor. fee + payout == bountyAmount always exactly, so no dust is lost either way.
  • tx.origin == msg.sender EOA gate bypassable via L1→L2 forced transactions — createSoloBounty/createOpenBounty (L358, L371). An L1 contract can satisfy this check via an OP-Stack deposit (Base) or Arbitrum retryable ticket, becoming a bounty issuer despite the intended EOA-only restriction. Harmless: the bypassing contract only risks becoming its own NFT sink at acceptance (no other user or the protocol is affected), and no code path branches on issuer code-length post-creation.
  • Missing return value on createSoloBounty/createOpenBounty — the new bountyId must be recovered from the emitted event or bountyCounter - 1; an integration ergonomics gap, no fund impact.
  • Misleading Withdrawal event on withdrawTo — withdrawTo emits both Withdrawal(msg.sender, amount) and WithdrawalTo(msg.sender, to, amount); an indexer consuming only the legacy Withdrawal event will misattribute the ETH recipient as msg.sender when it was actually sent to to.
  • joinOpenBounty 150-slot occupation — an attacker can occupy all MAX_PARTICIPANTS = 150 slots with MIN_CONTRIBUTION-sized deposits from distinct addresses, blocking new distinct contributors. Bounded, fully self-funded by the attacker, and reversible (their own capital is withdrawable, freeing slots) — not independently actionable.
  • Fixed-size-10 getter padding with zero-value structs — same getters as Finding 4 return exactly 10 elements, padding with zero-valued structs when fewer real entries exist. Verified no genuine collision is possible with a real all-zero record (real bounties always have nonzero issuer/createdAt); a naive consumer that doesn't filter on this could still misread padding as a real record.

Access-Control Inventory

There is no admin, owner, or role-based access control anywhere in this contract — no Ownable, AccessControl, Pausable, or upgrade authority. treasury and poidhNft are immutable, set once in the constructor and validated non-zero (with poidhNft additionally checked to have code); neither has a setter. MIN_BOUNTY_AMOUNT/MIN_CONTRIBUTION are likewise immutable. votingPeriod (L27, 2 days) is not declared constant/immutable but has zero writers anywhere in the file — effectively fixed post-deploy (see Informational above).

Leads
