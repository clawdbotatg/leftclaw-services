Executive Summary

The VaultID system implements a soulbound credential NFT ecosystem with three contracts: a subscription/profile registry, a core ERC721 credential token, and a marketplace for issuer storefronts. The codebase is well-structured, applies OpenZeppelin standards correctly, and includes several positive security controls: Ownable2Step for ownership transfers, nonReentrant on all value-moving functions, a 48-hour timelock on VaultID registry updates, and a three-actor revocation model with clean separation of revocation flags.

No critical or high severity vulnerabilities were identified. The following findings are presented in priority order.

Medium Findings

[M-1] setBasicMintQuota(0) Permanently DoSes BASIC Subscription Minting

Severity: Medium
Confidence: High (confirmed by both methodologies)
Location: VaultIDRegistry.setBasicMintQuota() (line 302), VaultIDRegistry.consumeBasicMint() (line 160)

Description:
setBasicMintQuota only rejects type(uint32).max, allowing the owner to set the quota to 0. When basicMintQuota == 0, consumeBasicMint evaluates sub.mintsUsedInPeriod >= basicMintQuota as 0 >= 0 = true and always reverts with QuotaExceeded. All BASIC subscription holders are unable to mint despite having a valid, paid, active subscription.

Proof of Concept:

1. owner.call: registry.setBasicMintQuota(0)
2. alice.call: vault.mintWithSubscription(params)  [alice has active BASIC sub]
3. VaultID calls: registry.consumeBasicMint(alice)
   → sub.mintsUsedInPeriod = 0, basicMintQuota = 0
   → 0 >= 0 == true → revert QuotaExceeded()
4. All BASIC subscribers' mintWithSubscription calls revert until quota is restored.

Recommendation:
Enforce a minimum quota of 1:

function setBasicMintQuota(uint32 _basicMintQuota) external onlyOwner {
    if (_basicMintQuota < 1 || _basicMintQuota == type(uint32).max) revert InvalidQuota();
    basicMintQuota = _basicMintQuota;
    emit BasicMintQuotaUpdated(_basicMintQuota);
}

[M-2] VaultIDMarketplace setVault/setRegistry Lack Timelock — Inconsistent With VaultID Core

Severity: Medium
Confidence: High (confirmed by both methodologies)
Location: VaultIDMarketplace.setVault() (line 184), VaultIDMarketplace.setRegistry() (line 178)

Description:
VaultID's registry pointer is protected by a 48-hour timelock (REGISTRY_UPDATE_DELAY) implemented via proposeRegistry/applyRegistryProposal. The VaultIDMarketplace has no equivalent delay for its vault and registry pointers, which can be changed in a single transaction. A compromised owner key can instantly redirect all marketplace purchases to a malicious vault contract, stealing buyer funds and minting fake credentials to buyers.

Proof of Concept:

1. Attacker compromises owner private key.
2. Attacker deploys MaliciousVault that:
   - In marketplaceMint: calls safeTransferFrom(buyer, attacker, …) via front-loaded calldata
   - Returns a fake tokenId
3. Attacker calls: marketplace.setVault(maliciousVault)  — single transaction, immediate
4. Next buyer calls: purchaseProduct(...)
   - _collectPayment sends buyer tokens to platformFeeRecipient and issuer (legitimate)
   - _mintPurchasedVault calls maliciousVault.marketplaceMint — attacker can drain any
     residual approvals or execute arbitrary logic
5. Attacker also calls setRegistry(maliciousRegistry) to manipulate isIssuerActive checks.

Recommendation:
Implement the same timelocked proposal pattern as VaultID:

struct VaultProposal { address proposedVault; uint64 executableAt; }
VaultProposal public vaultProposal;
uint64 public constant VAULT_UPDATE_DELAY = 48 hours;

function proposeVault(address newVault) external onlyOwner {
    if (newVault == address(0)) revert ZeroAddress();
    vaultProposal = VaultProposal({proposedVault: newVault, executableAt: uint64(block.timestamp + VAULT_UPDATE_DELAY)});
    emit VaultUpdateProposed(newVault, vaultProposal.executableAt);
}

function applyVaultProposal() external onlyOwner {
    if (vaultProposal.proposedVault == address(0)) revert ProposalMissing();
    if (block.timestamp < vaultProposal.executableAt) revert DelayNotElapsed();
    vault = IVaultIDForMarketplace(vaultProposal.proposedVault);
    delete vaultProposal;
}

[M-3] USDC/ERC20 Blocklist Causes Permanent Per-Issuer Product DoS in Marketplace

Severity: Medium
Confidence: High (confirmed by both methodologies; USDC blocklist is a well-documented plausible risk)
Location: VaultIDMarketplace._collectPayment() (lines 221–235)

Description:
_collectPayment executes two sequential safeTransferFrom calls: one to platformFeeRecipient and one directly to p.issuer. USDC and USDT maintain operator-controlled address blocklists. If platformFeeRecipient is blocklisted, all products using USDC fail. If an issuer's address is blocklisted, all of that issuer's USDC-denominated products fail permanently — there is no mechanism to change p.issuer after product creation.

Proof of Concept:

State: product.paymentToken = USDC, product.issuer = IssuerAddr
Event: Circle blocklists IssuerAddr
Result: Any buyer's purchaseProduct call:
  safeTransferFrom(buyer, platformFeeRecipient, fee)  → succeeds
  safeTransferFrom(buyer, IssuerAddr, issuerAmount)   → REVERTS (blocklisted)
Consequence: All of IssuerAddr's USDC products are permanently un-purchasable.
             IssuerAddr cannot self-rescue (cannot change p.issuer).
             Owner cannot rescue (no function to update product.issuer).

Recommendation:
Adopt a pull-payment model for issuer proceeds. This eliminates the blocklist DoS attack surface and provides resilience against any token-level transfer restriction:

mapping(address => mapping(address => uint256)) public claimable; // token → issuer → amount

function _collectPayment(Product storage p) internal {
    if (p.price == 0) return;
    uint256 fee = (p.price * p.platformFeeBps) / MAX_BPS;
    uint256 issuerAmount = p.price - fee;
    IERC20 token = IERC20(p.paymentToken);
    if (fee > 0) token.safeTransferFrom(msg.sender, platformFeeRecipient, fee);
    if (issuerAmount > 0) {
        token.safeTransferFrom(msg.sender, address(this), issuerAmount);
        claimable[p.paymentToken][p.issuer] += issuerAmount;
    }
}

function claimProceeds(address token) external {
    uint256 amount = claimable[token][msg.sender];
    if (amount == 0) revert NothingToClaim();
    claimable[token][msg.sender] = 0;
    IERC20(token).safeTransfer(msg.sender, amount);
}

Low Findings

[L-1] _mint Instead of _safeMint — Soulbound Credentials Can Be Permanently Locked in Incompatible Contracts

Severity: Low
Confidence: Medium
Location: VaultID._mintVault() (line 527)

Description:
_mintVault uses _mint(to, tokenId) without calling onERC721Received on the recipient. Because tokens are soulbound (transfers blocked), a credential minted to a smart contract that does not implement IERC721Receiver is permanently unrecoverable unless a recovery wallet was set and that wallet's contract can call recoverVault.

Proof of Concept:
An issuer calls issuerMint(multisigContract, params) where the multisig does not implement IERC721Receiver and params.recoveryWallet == address(0). The credential is permanently locked.

Recommendation:
Use _safeMint for issuer and marketplace mints where the recipient is unknown:

// In _mintVault, for non-self-mints:
if (params.issuer != address(0)) {
    _safeMint(to, tokenId);  // enforces onERC721Received
} else {
    _mint(to, tokenId);       // user self-mints — safe
}

Alternatively, require params.recoveryWallet != address(0) for issuer/marketplace mints to contract addresses.

[L-2] subscriptionPeriod Changes Retroactively Affect All Existing Subscribers

Severity: Low
Confidence: Medium
Location: VaultIDRegistry.setSubscriptionPeriod() (line 296), VaultIDRegistry.consumeBasicMint() (line 155)

Description:
subscriptionPeriod is a global variable used to determine when each subscriber's mint quota resets. A decrease in subscriptionPeriod can cause existing subscribers' periods to appear already-expired relative to the new shorter period, granting them an immediate quota reset on their next mint. An increase delays quota resets for existing subscribers without their knowledge.

Proof of Concept:

Alice: BASIC sub, periodStart = T₀, used 8/10 mints, subscriptionPeriod = 30 days
Admin reduces subscriptionPeriod to 15 days at T₀ + 20 days.
Alice's next consumeBasicMint:
  block.timestamp (T₀+20d) >= periodStart (T₀) + subscriptionPeriod (15d) → true
  → period reset → mintsUsedInPeriod = 0 (unexpected fresh quota for Alice)

Recommendation:
Store periodDuration per-subscription at purchase time and use the subscriber's own recorded duration for quota reset calculations. Only apply new global periods to future subscriptions.

[L-3] No Max-Price Parameter in purchaseProduct — Issuer Front-Run Possible

Severity: Low
Confidence: Medium
Location: VaultIDMarketplace.purchaseProduct() (line 165), VaultIDMarketplace.updateProduct() (line 144)

Description:
An issuer can call updateProduct to raise the price of a product after a buyer has submitted a purchaseProduct transaction. Buyers who approved type(uint256).max (a common wallet pattern) will pay the higher price without consent.

Proof of Concept:

Buyer sees product price: 100 USDC. Approves max USDC to Marketplace.
Issuer frontruns: updateProduct(productId, {price: 10_000e6, ...})
Buyer's purchaseProduct executes at 10,000 USDC.
Issuer profit: 9,900 USDC above the advertised price.

Recommendation:
Add a maxPrice guard to PurchaseParams:

struct PurchaseParams {
    uint256 productId;
    address recipient;
    uint256 maxPrice;  // 0 = no limit
    string encryptedPayloadRef;
    string metadataURI;
    string membershipIdentifier;
    address recoveryWallet;
}

// in purchaseProduct:
if (params.maxPrice > 0 && p.price > params.maxPrice) revert PriceExceeded();

[L-4] extendExpiry Permitted on Revoked Credentials — State Inconsistency

Severity: Low
Confidence: High
Location: VaultID.extendExpiry() (lines 299–316)

Description:
extendExpiry does not check isRevoked. An issuer, token owner, or admin can modify v.expiry on a revoked credential. Although _isValidOwned evaluates revocation flags before the expiry condition (so a revoked credential cannot be made "valid" by extending its expiry), the state inconsistency creates confusion for off-chain systems that may inspect v.expiry directly without also checking revocation status.

Recommendation:
Add a revocation check to extendExpiry:

function extendExpiry(uint256 tokenId, uint64 newExpiry) external {
    address tokOwner = _requireOwned(tokenId);
    if (isRevoked(tokenId)) revert RevokedCredential();
    ...
}

[L-5] Tier Switch in purchaseSubscription Stacks Extension From Previous Tier's paidThrough

Severity: Low
Confidence: Medium
Location: VaultIDRegistry.purchaseSubscription() (lines 127–135)

Description:
When a subscriber switches from ISSUER to BASIC (or vice versa), the extension is calculated from baseTime = sub.paidThrough (their existing paid-through time under the previous tier). This means:

  • An ISSUER subscriber with 12 months remaining who switches to BASIC pays for BASIC periods starting 12 months from now — they do not get immediate BASIC access.
  • The user paid correctly in tokens (the BASIC price was charged), but the effective start of their BASIC subscription is deferred until their ISSUER sub expires.

This is a UX/documentation concern rather than a fund loss, but could lead to confused subscribers who believe they have an active BASIC subscription starting immediately.

Proof of Concept:

Alice: ISSUER sub, paidThrough = now + 365 days
Alice buys 1 BASIC period (30 days):
  baseTime = now + 365 days
  sub.paidThrough = now + 395 days, sub.tier = BASIC
  sub.periodStart = now (reset due to tier change)
Alice cannot use canIssuerMint (now has BASIC tier)
Alice cannot use consumeBasicMint until paidThrough > now (365 days from now)
Alice's BASIC quota kicks in only in 365 days, but she thinks she just bought BASIC

Recommendation:
Document clearly in UX that tier switches take effect at the current paidThrough date. Consider adding an optional flag to forfeit remaining pre-paid time and switch tiers immediately.

[L-6] _calculateExpiry Can Silently Produce Past Timestamps for Extreme Duration Values

Severity: Low
Confidence: Medium
Location: VaultIDMarketplace._calculateExpiry() (line 253), _validateProduct() (line 258)

Description:
_calculateExpiry computes uint64(block.timestamp + duration). _validateProduct does not bound duration. If duration is set to a value such that block.timestamp + duration overflows uint64, the silent truncation produces a timestamp in the past, causing the minted credential to be immediately expired.

Proof of Concept:

block.timestamp ≈ 1,716,000,000 (May 2024)
duration = type(uint64).max - 1,716,000,000 + 1 ≈ 1.844e19 - 1.716e9 + 1

block.timestamp + duration ≈ type(uint64).max + 1 overflows uint64
uint64(type(uint64).max + 1) = 0

Credential expiry = 0 (no-expiry) OR near-zero (past timestamp)
Depending on exact value, credential is either non-expiring or immediately expired.

Recommendation:
Add a maximum duration bound in _validateProduct:

uint64 public constant MAX_PRODUCT_DURATION = 36500 days; // ~100 years

function _validateProduct(ProductParams calldata params) internal view {
    ...
    if (params.duration > MAX_PRODUCT_DURATION) revert InvalidDuration();
    ...
}

Informational Findings

[I-1] isRevoked(tokenId) Returns false for Burned/Non-Existent Tokens

Severity: Info
Location: VaultID.isRevoked() (line 392)

Description: isRevoked returns false when _ownerOf(tokenId) == address(0), which covers both burned and never-issued tokens. External integrators that rely solely on isRevoked() == false as a validity signal will incorrectly treat burned credentials as "not revoked." Use credentialStatus() for complete state information.

Recommendation: Document that isRevoked(id) == false does NOT imply the credential is valid. Add isValid() or direct integrators to credentialStatus() in NatSpec.

[I-2] Inline "Audit Fix" Comment in Production Code

Severity: Info
Location: VaultIDRegistry.registerOrUpdateIssuerProfile() (line 234)

Description: The production code contains // Audit fix: only first registration activates profile. Historical audit-remediation notes should be removed before deployment; they reveal past vulnerability history and suggest incomplete cleanup.

Recommendation: Remove the // Audit fix: prefix from the comment.

[I-3] purchaseProduct Permits Minting to the Marketplace Contract Itself

Severity: Info
Location: VaultIDMarketplace.purchaseProduct() (line 166)

Description: The only recipient validation is != address(0). A buyer can specify params.recipient = address(marketplace). Since VaultID uses _mint (not _safeMint), this succeeds and a soulbound credential is permanently locked in the marketplace contract with no rescue mechanism.

Recommendation: Add if (params.recipient == address(vault) || params.recipient == address(this)) revert ZeroAddress().

Positive Security Observations

The following practices are well-implemented and worth acknowledging:

  • Ownable2Step prevents ownership transfer to a wrong address in all three contracts.
  • 48-hour timelock on registry updates in VaultID provides protection against compromised key rapid attacks.
  • Three-actor revocation (owner/issuer/admin with no cross-clearing) correctly models the trust model described in the NatSpec.
  • SafeERC20 used throughout for all ERC20 transfers.
  • nonReentrant applied to all value-moving functions.
  • Deactivated issuer self-reactivation blocked — the "audit fix" at line 234 correctly prevents a deactivated issuer from re-activating by editing their profile.
  • _userParams correctly forces issuer: address(0) for user self-mints, preventing unauthorized issuer impersonation in the issuer field.
  • Soulbound implementation via _update override is correct; approve and setApprovalForAll are properly disabled.
