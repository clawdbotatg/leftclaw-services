Findings

[85] 1. withdraw() has no alternate-recipient or rescue path — a blocklisted agent's principal is permanently unrecoverable

AgentDepositVault.withdraw · Confidence: 85

Description
withdraw() (98-108) always pays out to msg.sender via safeTransfer(msg.sender, amount) (line 106); if that address is ever blocklisted by the USDC issuer, every future call reverts forever with no redirect parameter and no owner rescue path anywhere in the file — unlike claimPayout(address to) (287), which the same codebase explicitly gives an arbitrary-recipient escape hatch.

Fix

- function withdraw(uint256 amount) external nonReentrant {
+ function withdraw(uint256 amount, address to) external nonReentrant {
+     require(to != address(0), "AgentDeposit: zero recipient");
      require(blockedUntil[msg.sender] <= block.timestamp, "AgentDeposit: blocked");
      require(taskRegistry != address(0), "AgentDeposit: not wired");
      require(amount > 0, "AgentDeposit: zero amount");
      uint256 maxW = ITaskRegistry(taskRegistry).maxWithdrawableDeposit(msg.sender);
      require(amount <= maxW, "AgentDeposit: exceeds withdrawable");
      deposits[msg.sender] -= amount;
      totalDeposits -= amount;
-     IERC20(usdcToken).safeTransfer(msg.sender, amount);
-     emit Withdrawn(msg.sender, amount, deposits[msg.sender]);
+     IERC20(usdcToken).safeTransfer(to, amount);
+     emit Withdrawn(msg.sender, amount, deposits[msg.sender]);
  }

[80] 2. rotateArbitrationModule can be permanently blocked by the current module it is trying to replace

AgentDepositVault.rotateArbitrationModule · Confidence: 80

Description
Every gate in rotateArbitrationModule (163-181) queries the current (outgoing) module for self-reported state — disputeOpeningPaused() (167), activeDisputeCount() (168) — with no owner override, timelock, or locally-tracked reference value. A compromised or adversarial current module can hardcode these getters to never satisfy the requires (or simply revert), permanently entrenching itself while retaining onlyArbitration power to drain every agent's balance to the MIN_TASK_BALANCE floor via debitDisputeBond. Corroborated independently by 5 of 12 phase-2 agents (access-control, first-principles, plus 3 more as leads) and phase-1's general-1/dos-1.

Fix

+ uint256 public forceRotateRequestedAt;
+ address public pendingForceRotateModule;
+ uint256 public constant FORCE_ROTATE_DELAY = 3 days;
+
+ function initiateForceRotation(address _arbitration) external onlyOwner {
+     require(_arbitration != address(0), "AgentDeposit: zero");
+     pendingForceRotateModule = _arbitration;
+     forceRotateRequestedAt = block.timestamp;
+ }
+
+ function executeForceRotation() external onlyOwner {
+     require(pendingForceRotateModule != address(0), "AgentDeposit: none pending");
+     require(block.timestamp >= forceRotateRequestedAt + FORCE_ROTATE_DELAY, "AgentDeposit: delay not elapsed");
+     arbitrationModule = pendingForceRotateModule;
+     pendingForceRotateModule = address(0);
+ }

[80] 3. Agents can evade dispute-bond forfeiture by withdrawing below MIN_TASK_BALANCE before arbitration collects

AgentDepositVault.withdraw / AgentDepositVault.debitDisputeBond · Confidence: 80

Description
withdraw() has no local awareness of MIN_TASK_BALANCE or of any pending dispute — its only ceiling is the external, out-of-scope ITaskRegistry.maxWithdrawableDeposit, whose stated purpose (reserving for live task bindings) is orthogonal to this vault's private bond-floor invariant. An agent who anticipates an unfavorable dispute outcome can call withdraw down to (or below) MIN_TASK_BALANCE before arbitration calls debitDisputeBond; once deposits[agent] < MIN_TASK_BALANCE, line 187's floor check makes the bond debit permanently and unconditionally impossible for any amount > 0, not merely capped.

Fix

  function withdraw(uint256 amount) external nonReentrant {
      require(blockedUntil[msg.sender] <= block.timestamp, "AgentDeposit: blocked");
      require(taskRegistry != address(0), "AgentDeposit: not wired");
      require(amount > 0, "AgentDeposit: zero amount");
      uint256 maxW = ITaskRegistry(taskRegistry).maxWithdrawableDeposit(msg.sender);
      require(amount <= maxW, "AgentDeposit: exceeds withdrawable");
+     require(deposits[msg.sender] - amount >= MIN_TASK_BALANCE || deposits[msg.sender] - amount == 0, "AgentDeposit: breaches task floor");
      deposits[msg.sender] -= amount;
      totalDeposits -= amount;
      IERC20(usdcToken).safeTransfer(msg.sender, amount);
      emit Withdrawn(msg.sender, amount, deposits[msg.sender]);
  }

(The exact policy — full exit permitted only when no live task binding exists — should be reconciled with taskRegistry's own accounting; the point is that this vault currently enforces no floor of its own on withdraw at all.)

[70] 4. rotateArbitrationModule can orphan already-debited dispute bonds even on a fully honest rotation

AgentDepositVault.rotateArbitrationModule / AgentDepositVault.creditDisputeBond · Confidence: 70

Description
Distinct root cause from Finding 2: onlyArbitration/creditDisputeBond (195) binds strictly to whichever address currently sits in arbitrationModule — a single pointer, not a set — and rotation's only check on this is current.activeDisputeCount()==0 (168), a self-reported, point-in-time claim with no in-vault reservation ledger. If a bond was debitDisputeBond-ed to the old module (190) but not yet creditDisputeBond-ed back at the moment of an otherwise-legitimate rotation, the old module permanently loses the ability to refund it (blocked by onlyArbitration), and the new module has no on-chain record that it is owed anything.

Fix

+ mapping(address => uint256) public outstandingBondsHeldBy;
  function debitDisputeBond(address agent, uint256 amount) external onlyArbitration {
      ...
+     outstandingBondsHeldBy[arbitrationModule] += amount;
      IERC20(usdcToken).safeTransfer(arbitrationModule, amount);
  }
  function rotateArbitrationModule(address _arbitration) external onlyOwner {
      ...
+     require(outstandingBondsHeldBy[arbitrationModule] == 0, "AgentDeposit: outstanding bonds");
      arbitrationModule = _arbitration;
  }

[65] 5. _payOrDefer has no zero-address guard — a bad worker/poster from taskRegistry silently burns compensation

AgentDepositVault._payOrDefer · Confidence: 65

Description
_payOrDefer (297-311) never validates recipient, unlike claimPayout (288) which explicitly requires to != address(0) in the same file. A transfer(address(0), amount) reverts inside any standard ERC20, which the tri-condition (302-306) classifies as a soft failure and defers into pendingPayouts[address(0)] — a slot no transaction can ever claim (msg.sender can never be address(0)), permanently burning the compensation instead of reverting the whole fee-debit as a plain safeTransfer would have. Requires taskRegistry (trusted, out-of-scope) to supply a zero role address.

[60] 6. pullEmergencyTopUp has no bound tied to the actual shortfall it exists to cover

AgentDepositVault.pullEmergencyTopUp · Confidence: 60

Description
The contract defines the correct emergency-shortfall bound via the view helper emergencyTopUpRequired (123-126, MIN_TASK_BALANCE - deposits[agent]), but pullEmergencyTopUp (111-121) — whose entire documented purpose is "emergency top-up" — never calls or enforces it; amount is validated only by amount > 0. A buggy or compromised taskRegistry (with a standing large/infinite USDC approval from the agent, a common UX pattern for a contract topped up regularly) can pull far more than any deposit floor requires.

Fix

  function pullEmergencyTopUp(address agent, uint256 amount) external onlyRegistry {
      require(amount > 0, "AgentDeposit: zero amount");
+     require(amount <= emergencyTopUpRequired(agent), "AgentDeposit: exceeds shortfall");
      require(blockedUntil[agent] <= block.timestamp, "AgentDeposit: blocked");
      ...

[55] 7. setArbitrationModule/rotateArbitrationModule change the highest-privilege role with no event and no timelock

AgentDepositVault.setArbitrationModule / AgentDepositVault.rotateArbitrationModule · Confidence: 55

Description
arbitrationModule gates debitDisputeBond/creditDisputeBond, the highest-impact role besides owner. Both setters change it synchronously with no event (unlike wire()'s Wired event) and no timelock, so standard event-indexed monitoring cannot detect a swap before it takes effect.

[50] 8. No poster != worker check in debitDismissFee/debitLeaveFee

AgentDepositVault.debitDismissFee / AgentDepositVault.debitLeaveFee · Confidence: 50

Description
If taskRegistry (trusted, out-of-scope) ever supplies the same address for both roles, that address converts EXIT_PARTY_COMP worth of illiquid deposits into liquid USDC at the cost of only EXIT_PROTOCOL_SHARE, bypassing withdraw()'s external ceiling check. Solvency is preserved (fee = comp + protocolShare is asserted per-call); this is a defense-in-depth gap contingent on unverifiable taskRegistry behavior, not a directly fund-draining bug.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed in one analysis pass. These are not false positives — they are high-signal leads for manual review. Not scored.

  • Reentrancy during rotateArbitrationModule — AgentDepositVault.rotateArbitrationModule — Code smells: external calls to current.disputeOpeningPaused()/activeDisputeCount()/escrow() (167-174) execute before arbitrationModule is reassigned (180), so onlyArbitration still resolves to the outgoing module during these calls — a compromised module could in principle reenter debitDisputeBond. Contingent entirely on whether IArbitrationRecovery's getters are declared view in the out-of-scope interface (would force STATICCALL and block the reentrant state write); unverifiable from this scope.
  • _payOrDefer's abi.decode(data,(bool)) can itself revert — AgentDepositVault._payOrDefer — Code smells: a 32-byte return value that isn't canonical 0/1 panics instead of being classified as failure, defeating the graceful-degradation design. Requires usdcToken to deviate from the construction-time-asserted canonical USDC behavior. Flagged independently by 5 of 12 phase-2 agents.
  • creditDisputeBond's exact-receipt check is asymmetric with topUp/pullEmergencyTopUp — AgentDepositVault.creditDisputeBond — Code smells: received==amount (200) vs. received>0 elsewhere (91, 117); any transfer-amount deviation permanently strands a bond refund.
  • No reentrancy guard on debitAccessFee/debitDismissFee/debitLeaveFee — Code smells: 2-3 external calls to treasury after ledger mutation, no nonReentrant. Three independent phase-2 agents traced this and found CEI ordering closes every constructed path (self-harm only) — not promoted to a finding.
  • wire() has no pairwise address-distinctness check and no rotation path for taskRegistry/treasury/reputationRegistry — if any two are ever wired to the same address, onlyRegistry could be satisfied by a reentrant callback from treasury; and unlike arbitrationModule, there is no recovery path at all if any of the three is later compromised.
  • blockedUntil is not enforced on debitAccessFee/debitDismissFee/debitLeaveFee/debitDisputeBond/creditDisputeBond/claimPayout — a platform-blocked agent's ledger remains fully fee-debitable and bond-debitable, and pending payouts remain claimable. Matches the protocol map's own INV-10 structural note; intentionality unconfirmed.
  • MIN_TASK_BALANCE is a flat floor, not scaled to concurrent task/dispute bindings — the same $8 balance can pass meetsTaskMinimum for arbitrarily many simultaneous bindings; a second concurrent dispute-bond debit against the same agent can be structurally blocked by the first debit already pinning the balance at the floor.
  • debitDismissFee/debitLeaveFee record only protocolShare to treasury.recordAccessFee, not the full fee — may under-count fees in downstream treasury bookkeeping/analytics if TreasuryRouter assumes the recorded amount reflects the full debited fee (unverifiable, out of scope).
