[U-01] syncPartnershipReputation lets anyone forge or self-inflate an agent's ERC-8004 reputation without consent

Severity: High · Origin: [both] (phase1: AccessControl-1, General-3 · phase2: agents 2/3/6/7, AIPartnershipBondsV2 self-dealing)
Location: VaultfireERC8004Adapter.syncPartnershipReputation() (adapter.sol:129-165), reachable via AIPartnershipBondsV2.createBond(), submitPartnershipMetrics() (onlyParticipants), and submitHumanVerification() (fully permissionless, no independence check)

Description: syncPartnershipReputation is callable by anyone and hard-codes verified: true when calling reputationRegistry.submitFeedback(aiAgent, rating, ...). Every step feeding it is permissionless and attacker-controlled:

  • createBond(aiAgent, type) lets any "human" name an arbitrary aiAgent — no consent required, aiAgent != msg.sender is the only constraint, msg.value can be 1 wei.
  • submitPartnershipMetrics is onlyParticipants, and the bond creator is a participant, so the attacker fully controls the score inputs.
  • submitHumanVerification has no check that the verifier is independent of the bond's own participants — anyone, including a participant, can self-submit it.

Two attack directions from the identical root cause:

  • Poison a victim: name a real registered agent V as aiAgent, submit all-zero metrics, sync → V gets a permanent verified-0 feedback it never agreed to.
  • Self-inflate: attacker controls both human and a second aiAgent address, submits all-max metrics, self-submits a full verification, and syncs → mints unlimited verified maximal-rated feedbacks with no third party ever involved. Even a freshly created bond with zero metrics defaults to partnershipQualityScore == 5000, so a "verified 5000" is mintable with no partnership activity at all.

Proof of Concept: A calls partnershipBonds.createBond{value: 1 wei}(V, "coding assistant"); A calls submitPartnershipMetrics(bondId, 0,0,0,0,0,"x") (A is a participant); anyone calls adapter.syncPartnershipReputation(bondId) → submitFeedback(V, 0, "partnership_quality", "", true, bondId). Repeatable at ~1 wei + gas per bond. Symmetric for self-inflation: attacker names a second attacker-controlled address as aiAgent, sets all metrics to 10000, self-submits submitHumanVerification(bondId, true, true, true, ...), and syncs.

Recommendation:

function syncPartnershipReputation(uint256 bondId) external {
    require(!bondReputationSynced[bondId], "Already synced");
    (, address human, address aiAgent, , , , , , bool active) = partnershipBonds.bonds(bondId);
    require(active, "Bond not active");
    require(msg.sender == human || msg.sender == aiAgent, "Not a participant");
    require(autoRegisteredAgents[aiAgent], "Agent has not opted into VaultFire");
    ...
}

Also require the verifier in AIPartnershipBondsV2.submitHumanVerification to be distinct from both bond.human and bond.aiAgent, and stop hard-coding verified = true in the adapter — derive it from genuine independent verification.

[U-02] Underlying ERC8004ReputationRegistry.submitFeedback is fully permissionless with a caller-controlled verified flag

Severity: Medium · Origin: [both] (phase1: AccessControl-2 · phase2: 9 of 12 agents — the most corroborated dependency-adjacent finding)
Location: ERC8004ReputationRegistry.submitFeedback() / submitFeedbackHashed()

Description: Independent of the adapter, any address can call submitFeedback(agentAddress, rating, category, uri, verified, bondId) directly with verified = true and an arbitrary bondId. There is no allow-list restricting writers to the adapter, so every integrity control the adapter tries to add (the one-shot sync flag, deriving rating from real metrics) is moot — an attacker can bypass the adapter entirely and forge "verified" feedback for any active agent.

Proof of Concept: reputationRegistry.submitFeedback(V, 0, "partnership_quality", "", true, 0) called directly and repeatedly; no bond or adapter involvement required. _updateReputation's running average drags averageRating toward 0 (or 10000 for self-inflation) after enough calls.

Recommendation: Restrict feedback writes to an owner-managed allow-list (at minimum the adapter address), and derive verified from a trusted path rather than accepting it from the caller:

mapping(address => bool) public authorizedReporters;
function submitFeedback(...) external {
    require(authorizedReporters[msg.sender], "Not authorized");
    ...
}

[U-03] Quality score can exceed the ERC-8004 [0,10000] ceiling, permanently bricking sync for the best partnerships

Severity: Medium · Origin: [both] (phase1: PrecisionMath-1, General-2 · phase2: agents 1/5/8/9/10/11/12 — 7 of 12, near-unanimous)
Location: VaultfireERC8004Adapter._calculatePartnershipRating() (adapter.sol:172-178) consuming AIPartnershipBondsV2.partnershipQualityScore(); reverts inside ERC8004ReputationRegistry.submitFeedback() (require(rating <= 10000))

Description: The adapter's own comment assumes VaultFire's quality score is "0-10000, which maps directly to ERC-8004 rating" and forwards it unclamped. But partnershipQualityScore = baseQuality * (10000 + verificationBonus) / 10000, where baseQuality maxes at 10000 and verificationBonus is 0/1000/2000 — the true range is [0, 12000]. Any bond with baseQuality > 8333 and full human verification (bonus 2000), or baseQuality > 9090 with partial (2-of-3) verification (bonus 1000), produces a score above 10000, and syncPartnershipReputation reverts every time it's called for that bond — permanently, since bondReputationSynced is never set on a reverted call. The exact partnerships the bridge exists to showcase (high-quality, human-verified) are the ones that can never be synced.

Proof of Concept: Metrics humanGrowth = humanAutonomy = humanDignity = creativityScore = 9000 → baseQuality = 9000; full verification → bonus 2000 → qualityScore = 9000 * 12000 / 10000 = 10800. syncPartnershipReputation(bondId) → submitFeedback(..., 10800, ...) reverts "Rating must be 0-10000" on every call, forever.

Recommendation:

function _calculatePartnershipRating(uint256 bondId) internal view returns (uint256 rating) {
    uint256 qualityScore = partnershipBonds.partnershipQualityScore(bondId);
    return qualityScore > 10000 ? 10000 : qualityScore;
}

[U-04] ZK proof verification is bypassable — submitValidation accepts ZK_PROOF requests without checking any proof

Severity: High · Origin: [both] (phase1: Signatures-1 · phase2: agent 9/boundary)
Location: ERC8004ValidationRegistry.submitValidation() vs submitValidationZK(), reachable via VaultfireERC8004Adapter.requestPartnershipValidation()

Description: The adapter's requestPartnershipValidation can open a ValidationType.ZK_PROOF request. Settlement has two entry points: submitValidationZK actually calls the ZK verifier and reverts on a bad proof; submitValidation also accepts ZK_PROOF requests but only checks zkProof.length > 0 — it never verifies anything and can drive the request straight to APPROVED. Since both entry points are open, the cryptographic guarantee the adapter advertises for ZK_PROOF validations is meaningless.

Proof of Concept: Open a ZK_PROOF request via adapter.requestPartnershipValidation{value: 1 ether}(bondId, "ipfs://claim", ZK_PROOF); any staked validator calls validationRegistry.submitValidation(requestId, true, "", hex"00") (1 non-zero-length byte suffices) → request reaches APPROVED with zero cryptographic verification.

Recommendation:

if (request.validationType == ValidationType.ZK_PROOF) revert("Use submitValidationZK for ZK requests");

[U-05] The one path that does verify ZK proofs is a dev placeholder that reverts on Base and accepts arbitrary bytes elsewhere

Severity: High · Origin: [both] (phase1: Signatures-2 · phase2: agent 9/boundary independently confirmed the chain-id revert)
Location: BeliefAttestationVerifier._verifyStarkProof(), invoked from ERC8004ValidationRegistry.submitValidationZK()

Description: _verifyStarkProof hard-requires block.chainid == 31337 || block.chainid == 1337 ("DEV_VERIFIER: forbidden on non-local chain"). The adapter is deployed on Base (8453), so submitValidationZK — the only sound settlement path — always reverts there. Combined with U-04, every ZK_PROOF request the adapter creates on Base is either unsettleable via the honest path or settleable with zero verification via the unsafe path. Even disregarding the chain guard, the placeholder accepts any proofBytes.length >= 32 as valid, and is explicitly commented "DO NOT DEPLOY TO PRODUCTION" — yet it is the constructor-wired verifier.

Proof of Concept: On Base, submitValidationZK(requestId, true, "", proofBytes, publicInputs) reverts unconditionally at the require(block.chainid ...) check inside _verifyStarkProof.

Recommendation: Deploy a real STARK verifier implementing IStarkVerifier before any Base/mainnet use; add a deploy-time assertion that the wired verifier is not the dev placeholder off local chains.

[U-06] Discovery is broken by construction — the adapter computes the VaultFire capability hash and then discards it

Severity: Medium · Origin: [phase1 only] (General-1, AccessControl-4) — re-examined against source at reconciliation, confirmed
Location: VaultfireERC8004Adapter.registerAgentForPartnership() (adapter.sol:94-122, capability hash computed at line 103, discarded as a no-op statement at line 116) vs discoverVaultfireAgents() (adapter.sol:290-308) vs ERC8004IdentityRegistry.registerAgent()

Description: This is the mapping-consistency invariant break the client specifically asked to have checked. discoverVaultfireAgents(agentType) looks up identityRegistry.agentsByCapability[keccak256("vaultfire-ai-partnership" ++ agentType)]. That array is populated only inside identityRegistry.registerAgent(uri, type, capabilitiesHash), using whatever hash the agent chose when registering their identity — a value the adapter never sees or constrains. registerAgentForPartnership computes the expected hash and then throws it away, only flipping the unrelated autoRegisteredAgents[msg.sender] mapping. There is no invariant tying autoRegisteredAgents to agentsByCapability, so an agent that follows the documented flow ("call identityRegistry.registerAgent() first, then call this") is invisible to discoverVaultfireAgents unless it happened to register with exactly the VaultFire-specific hash — which nothing incentivizes or requires. The adjacent FIX H-01 NatSpec comment in the deployed contract claims this was already fixed by adding the agentType-aware overload; on direct re-read it was not — the real defect (the hash is computed and discarded, never written anywhere) remains.

Proof of Concept: Agent registers identity with an arbitrary someHash; calls registerAgentForPartnership(...) successfully (autoRegisteredAgents[agent] = true); discoverVaultfireAgents("AI Assistant") returns empty/unrelated results for that agent despite it being marked "registered for VaultFire."

Recommendation: Either maintain the discovery index inside the adapter itself (push msg.sender into an adapter-owned mapping(bytes32 => address[]) during registerAgentForPartnership), or require agents to register their identity with the exact expected hash and have the adapter verify it (agents[msg.sender].capabilitiesHash == expected) before setting autoRegisteredAgents.

[U-07] Unbounded, third-party-growable capability array makes discoverVaultfireAgents permanently DoS-able

Severity: Medium · Origin: [phase1 only] (DoS-1) — re-examined against source, confirmed
Location: VaultfireERC8004Adapter.discoverVaultfireAgents() / discoverVaultfireAgents(string) (adapter.sol:290-308) → ERC8004IdentityRegistry.discoverAgentsByCapability()

Description: Both discovery overloads return the entire backing array with no bound or pagination. registerAgent(uri, type, capabilitiesHash) accepts capabilitiesHash as a fully attacker-supplied argument with no access control and unconditionally pushes msg.sender; entries are never removed even on deactivation (confirmed by the phase-2 gap-hunter agents' independent observation that deactivateAgent never prunes the array). Any third party can inflate exactly the "vaultfire-ai-partnership" bucket the adapter reads. Past tens of thousands of entries, the view exceeds eth_call/node gas caps and reverts for every caller — cheap on Base, and unlike sibling contracts in this codebase there is no paginated fallback.

Proof of Concept: Compute h = keccak256(abi.encodePacked("vaultfire-ai-partnership")); from many disposable addresses call identityRegistry.registerAgent("x","x", h) (cheap on Base); once agentsByCapability[h] is large enough, discoverVaultfireAgents() reverts for everyone.

Recommendation: Add a paginated read (discoverAgentsByCapabilityPaginated(hash, offset, limit) + a count getter), mirroring pagination already used elsewhere in this codebase, and expose bounded overloads from the adapter.

[U-08] requestPartnershipValidation forwards ≥1 ETH that is never refunded, and attributes the request to the adapter, not the real caller

Severity: Medium · Origin: [both] (phase1: General-5, AccessControl-5 · phase2: agents 2/3/6/9/11)
Location: VaultfireERC8004Adapter.requestPartnershipValidation() (adapter.sol:186-224) → ERC8004ValidationRegistry.requestValidation()

Description: Two coexisting mechanisms on the same function: (a) the forwarded msg.value (≥MIN_VALIDATOR_STAKE = 1 ether) is stored as request.stakeAmount but never read again anywhere — validator rewards are paid from a separate fixed VALIDATION_REWARD out of general balance, and no function ever returns stakeAmount to the requester, so the deposit is a permanent black hole regardless of outcome; (b) because the adapter itself calls requestValidation, the registry records requester == adapter, not the original caller — all adapter-routed requests are indistinguishable from each other, and any third party can permissionlessly attach an arbitrary claimURI to a real agent's validation history (bounded only by the 1 ETH cost) without that agent's involvement.

Proof of Concept: adapter.requestPartnershipValidation{value: 1 ether}(bondId, "ipfs://malicious-claim", ZK_PROOF) for a bond naming victim agent V — creates a PENDING request attributed to V with an attacker-chosen claim; the 1 ETH is permanently locked regardless of outcome.

Recommendation: Restrict the function to bond participants / opted-in agents (mirror U-01's fix), and either add a refund/settlement path for unused stake in the validation registry or clearly document the deposit as non-refundable by design.

[U-09] One-shot bondReputationSynced flag lets any third party front-run and permanently lock in a stale/neutral rating

Severity: Medium · Origin: [phase1 only] (DoS-2, AccessControl-3, General-4) — re-examined against source, confirmed
Location: VaultfireERC8004Adapter.syncPartnershipReputation() (adapter.sol:130, 164)

Description: syncPartnershipReputation is callable by anyone and gated only by a permanent one-shot flag (bondReputationSynced[bondId]). The rating is a live snapshot of partnershipQualityScore(bondId), which defaults to 5000 before any metrics are submitted. A griefer (not necessarily a bond participant) can call sync immediately after bond creation — before real metrics exist — locking in the neutral 5000 (or any other unfavorable interim value) forever; the legitimate, higher, later-earned score can never be recorded because re-sync always reverts with "Already synced".

Proof of Concept: Bond created, no metrics yet (partnershipQualityScore == 5000); attacker immediately calls adapter.syncPartnershipReputation(bondId) → locks in 5000; later genuine 9000+ score after metrics/verification is unsyncable — any further call reverts "Already synced".

Recommendation: Restrict the caller to a bond participant, and/or require at least one metrics submission and one human verification before the first sync is allowed, and/or replace the hard one-shot with an update-capable mechanism.

[U-10] Adapter's claimHash binds no security-relevant fields and is never checked against the submitted proof

Severity: Medium · Origin: [phase1 only] (Signatures-3) — re-examined against source, confirmed
Location: VaultfireERC8004Adapter.requestPartnershipValidation() (adapter.sol:212, claimHash = keccak256(abi.encodePacked(bondId, qualityScore, block.timestamp)))

Description: claimHash is stored on the ValidationRequest but never read by any verification logic — the ZK path checks proofBytes against caller-supplied publicInputs that are wholly independent of claimHash, so a validator can settle a request with a proof over unrelated inputs. The hash also omits block.chainid/address(this)/requester, and including block.timestamp makes it non-reproducible off-chain while adding no replay protection (nothing dedups on it).

Proof of Concept: Create any ZK request via the adapter; observe settlement never compares the proof's public inputs to request.claimHash anywhere in submitValidationZK or submitValidation.

Recommendation: Bind the fields that matter and enforce the check: keccak256(abi.encode(block.chainid, address(this), aiAgent, bondId, qualityScore)), and require bytes32(publicInputs[0]) == request.claimHash in the ZK settlement path.

[U-11] registerAgentForPartnership treats permissionless self-registration as if it were authentication

Severity: Low · Origin: [phase1 only] (Signatures-4) — re-examined against source, confirmed
Location: VaultfireERC8004Adapter.registerAgentForPartnership() (adapter.sol:96-124); ERC8004IdentityRegistry.registerAgent()

Description: The adapter's NatSpec frames identityRegistry.isAgentActive(msg.sender) as evidence that "identity was authenticated elsewhere." It is not — registerAgent is fully permissionless; any EOA sets its own active = true with an arbitrary URI/type/hash, with no signature or proof of anything. Any address can self-register, pass the adapter's check, and appear as a "VaultFire-compatible agent" in discovery without vetting.

Proof of Concept: Attacker calls identityRegistry.registerAgent("ipfs://fake", "AI Assistant", keccak256(abi.encodePacked("vaultfire-ai-partnership","AI Assistant"))) then adapter.registerAgentForPartnership("ipfs://fake","AI Assistant") — succeeds with no identity ever proven.

Recommendation: Correct the NatSpec (registry membership is not vetted identity); if Sybil resistance matters, require a signature/attestation or stake at registration.

[U-12] Minor / informational cleanup items

Severity: Low / Info · Origin: [phase1 only] (General-6, General-7, General-8, DoS-3)

  • CEI ordering: bondReputationSynced[bondId] = true is set after the external submitFeedback call in syncPartnershipReputation. Not currently exploitable (the reputation registry is a fixed, non-callback contract) but a latent hazard if that contract is ever changed — write the flag before the external call.
  • getAgentCrossPlatformReputation() hardcodes vaultfireRating = 0 with a "placeholder" comment while its NatSpec advertises a real average — integrators may treat the placeholder 0 as a genuine (and indistinguishable from real-zero) rating.
  • discoverVaultfireAgents("") (empty agentType) is byte-identical via abi.encodePacked to the no-arg discoverVaultfireAgents(), aliasing the type-agnostic bucket; use abi.encode for length-safety.
  • requestPartnershipValidation has no per-bond dedup (unlike sync's one-shot flag) — repeatable but self-funded at 1 ETH per call, so impact is cost-bounded.
  • Agent self-deactivation (identityRegistry.deactivateAgent()) causes the agent's own future syncPartnershipReputation/requestPartnershipValidation calls to revert — self-griefing only, no cross-user impact.
  • The adapter itself has no owner/pause — correctly avoids centralization risk; the fix direction for the findings above is consent/authorization, not an admin backdoor.

Appendix — Dependency-contract observations (out of this job's scope)

The client's brief for this engagement is VaultfireERC8004Adapter specifically. Phase 2's 12 attacker-mindset agents were given the adapter's full dependency closure for cross-contract context (as intended, since the client's focus areas — mapping consistency, replay, access control on remapping — are inherently cross-contract concerns), and in doing so surfaced real, well-corroborated bugs that live entirely inside AIPartnershipBondsV2 or ERC8004ValidationRegistry, with no path through any function the adapter exposes. AIPartnershipBondsV2 has its own separate, dedicated audit job in this client's queue (focus: "reentrancy in createBond and distribution paths"). These are reported here for completeness/handoff only — they are not adapter findings and were not counted in the reconciliation above.

  • distributeBond ignores the request-time snapshotAppreciation and recomputes live — found independently by all 12 of 12 phase-2 agents, the single most corroborated defect surfaced in this entire run. requestDistribution snapshots and reserves an appreciation amount (the contract's own documented "HIGH-002" anti-manipulation fix); distributeBond never reads that snapshot and instead recomputes calculateBondValue live, so a participant can inflate metrics/verification during the 7-day timelock and extract far more than was reserved — draining the shared yield pool beyond the documented ("CRITICAL-002") solvency guarantee and starving other bonds' reserved payouts. Given unanimous independent corroboration with concrete, source-quoted exploit traces, this should be treated as a High/Critical finding when AIPartnershipBondsV2 is audited directly.
  • distributeBond's depreciation branch never clears the pending-distribution reservation — found by 8+ of 12 agents. Only the appreciation-positive branch calls _useYieldPool (the sole code that decrements totalPendingDistributions); every depreciating or zero-value bond distribution leaks its reservation permanently, eventually bricking all future requestDistribution calls protocol-wide.
  • ERC8004ValidationRegistry.submitValidation/submitValidationZK have no per-validator dedup — found by 7+ of 12 agents. A single staked validator can submit multiple responses to the same request, unilaterally satisfying multi-validator consensus and collecting a reward per self-submitted response from the shared contract balance.
  • Validator stake permanently locked on DISPUTED (tie) or never-completing requests — found by 6+ of 12 agents. validatorActiveValidations is only decremented inside _distributeRewards, which is skipped on the DISPUTED branch and on requests that never reach validatorsRequired responses.
  • _useYieldPool's minimum-balance floor is checked pre-decrement, not post-decrement — a single distribution can push yieldPool below minimumYieldPoolBalance, inconsistent with withdrawYieldPool's post-decrement check.
  • Minor/unverified leads: ETH sent as msg.value alongside a validation response is never credited to validatorStakes (stranded); a slash-underflow could theoretically block request completion; ERC8004IdentityRegistry.deactivateAgent never prunes agentsByCapability/registeredAgents, reinforcing U-06/U-07 above.
