Findings

[F-01] Single guild agent has unilateral, irreversible control over winner verification, rejection, and crowning

Severity: High
Origin: [both] — Phase 1 access-control (AC-1) + Phase 2 access-control/economic-security/execution-trace/periphery/boundary/trust-gap (6 of 12 agents)
Location: DancepartyEpochManager._onlyDisputeOpener() L174-180; recordEntryVerificationDecision() L873-884; crownWinner() L886-901; closeNoWinner() L903-913; guildReview() L732-768

Description: onlyDisputeOpener passes for any address with guildRegistry.agentIdOf(msg.sender) > 0 — no quorum, no dedicated reviewer sub-role, no multi-sig. On the undisputed path, one agent alone decides which finalists are Rejected (irreversibly — no code path ever un-rejects an entry) vs VerifiedEligible, and then crowns the winner. The 2/3 GuildVoting supermajority only engages if a different agent proactively opens a dispute within the 1-day window. A related mechanism found independently by Phase 2 (execution-trace, trust-gap): during a dispute, a finalist still in Submitted state is auto-promoted to VerifiedEligible and crowned on a single compliant vote (guildReview L753-759) — the verification gate is one agent deep even in the "supervised" path.

Proof of Concept:

  1. Attacker (itself a registered guild agent, or colluding with one) submits an entry via submitEntryForRecipient(url, attacker, ...).
  2. Sockpuppet wallets (each with userEntryCount > 0 from their own low-cost entries) vote() the attacker's entry into the top-5 finalists.
  3. After closeEpochForVerification, during the VerificationPending window (and before anyone else disputes), the attacker agent calls recordEntryVerificationDecision(higherRankedFinalist, false, false) for every finalist ranked above its own — each starts Submitted so the require(state == Submitted) guard passes — marking them permanently Rejected, and marks its own entry VerifiedEligible.
  4. After the DISPUTE_WINDOW (1 day) with no one else disputing, crownWinner(epoch, attackerToken) passes _requireNextCrownableFinalist (all higher-ranked finalists are Rejected) and the VerifiedEligible check.
  5. claimPayout(epoch) pays the entire epochPool (ETH) and epochUsdcPool (USDC) — 25% of every participant's fee plus all boosts for the epoch — to entryPayoutRecipient[attackerToken] = attacker.

Recommendation: Require a quorum/threshold of distinct agents (or an on-chain tally mirroring GuildVoting) for recordEntryVerificationDecision, crownWinner, and closeNoWinner, rather than any single agentIdOf > 0. Restrict to a smaller, more tightly controlled reviewer sub-role. Consider allowing a rejected decision to be appealed/reversed via the same dispute mechanism used for crowned winners.

[F-02] Voter funding-age anti-Sybil requirement is fully implemented in storage but never enforced — unanimous cross-phase, cross-agent finding

Severity: High (escalated from Phase 1's Medium during reconciliation — see rationale below)
Origin: [both] — Phase 1 general (GEN-1) + all 12 of 12 Phase 2 depth agents independently converged on this identical root cause (9 as a direct FINDING, 3 as a LEAD)
Location: vote() L533-551; _isWalletVoteEligibleForEpoch() L219-221; isWalletVoteEligible() L223-225; VOTER_FUNDING_AGE_REQUIREMENT (L22, declared, zero reads); firstQualifiedFundingTimestamp (L59) / setWalletFundingTimestamp() (L862-871, the only writer — zero readers elsewhere)

Description: The contract ships a complete anti-Sybil scaffold — a VOTER_FUNDING_AGE_REQUIREMENT = 10 days constant, a firstQualifiedFundingTimestamp mapping, an owner-only setter setWalletFundingTimestamp, and a WalletFundingTimestampRecorded event — clearly intended to require that a voting wallet was funded/attested at least 10 days before it may vote. None of it is ever consulted: _isWalletVoteEligibleForEpoch checks exclusively userEntryCount[epoch][wallet] > 0. A wallet funded and entered in the same block votes with full weight.

Severity rationale for escalation: Phase 1 rated this Medium (weakened Sybil resistance, general framing). Twelve independently-reasoning Phase 2 attacker agents, working from different specialties (economic-security, execution-trace, invariant, boundary, trust-gap, numerical-gap, etc.), all constructed the identical concrete, low-cost, no-collusion-required exploit chain that directly captures pooled third-party funds. Because the attacker's own submitted content can be genuine (the attack is purely on vote-counting, not on content legitimacy), it does not depend on defeating guild content review — the stated "precondition" is materially just "attacker has ~$190–960 of capital," which is a very low bar for a fund-extraction path. This satisfies the High bar ("loss of funds requiring specific conditions") rather than Medium.

Proof of Concept (as independently constructed by 9+ agents with concrete numbers):

  1. Attacker funds N fresh wallets (no age requirement blocks this — the gate doesn't run).
  2. Each wallet calls submitEntry (0.0013 ETH or $2.99 USDC each) — this is genuine, legitimate content, so it will pass guild verification normally.
  3. N−1 of the wallets vote() for the attacker's chosen entry (self-vote is blocked, cross-sockpuppet voting is not). MAX_ENTRIES_PER_EPOCH = 64 caps this at 63 sockpuppet votes for ≈0.082 ETH / ≈$188 USDC total.
  4. _recordTopFinalists ranks by raw entryVotes, guaranteeing the attacker's entry is epochFinalists[epoch][0] / tentativeWinner.
  5. The entry is genuine content, so it passes normal (even honest, undisputed) guild verification and is crowned.
  6. claimPayout pays the attacker the full winner pool — 25% of every fee and boost contributed by all other participants that epoch, which can substantially exceed the attacker's ~$188–960 outlay whenever the epoch has meaningful organic participation/boosting.

Recommendation:

 function _isWalletVoteEligibleForEpoch(address wallet, uint256 epoch) internal view returns (bool) {
-    return userEntryCount[epoch][wallet] > 0;
+    return userEntryCount[epoch][wallet] > 0
+        && firstQualifiedFundingTimestamp[wallet] != 0
+        && block.timestamp - firstQualifiedFundingTimestamp[wallet] >= VOTER_FUNDING_AGE_REQUIREMENT;
 }

If the funding-age gate was intentionally deprecated in favor of the entry-fee-only model, remove the dead constant/mapping/setter/event to avoid a false sense of protection, and separately harden vote eligibility (e.g. a much higher fee, or a distinct non-Sybil-cheap credential).

[F-03] winnerPayoutRouter contradicts its documented "guild-controlled, 72h-updatable" model — owner can permanently redirect all winner payouts

Severity: Medium
Origin: [both] — Phase 1 general/access-control (GEN-2, AC-4) + Phase 2 access-control/trust-gap
Location: state var comment L54 ("Guild-controlled winner payout target (updatable every 72h)"); setWinnerPayoutRouter() L963-970; claimPayout() L824-835; _creditWinnerUsdc() L993-999; lockPayoutRecipients() L972-991

Description: The only setter is onlyOwner with no guild involvement and no timelock, directly contradicting the inline documentation. _validatePayoutRecipient only blocks this/usdc/nft/natureRouter/self — any owner-chosen EOA is accepted, and once lockPayoutRecipients() is called the value is frozen forever (one-way).

Proof of Concept: Owner calls setWinnerPayoutRouter(ownerEOA) then lockPayoutRecipients(). Every subsequent claimPayout sends the crowned winner's entire ETH+USDC prize to ownerEOA instead of the dancer, permanently and irreversibly.

Recommendation: Implement the documented guild-controlled/72h-throttled mechanism, or correct the misleading comment and add a timelock + event delay; require winnerPayoutRouter == address(0) at lock time, or validate it against a known-good, immutable router so users can verify the guarantee before it's frozen.

[F-04] GuildRegistry has unbounded, admin-controlled agent minting and no revocation/key-rotation path

Severity: Medium
Origin: [both] — Phase 1 access-control/general/governance (AC-2, AC-3, GEN-4, GOV-3) + Phase 2 invariant
Location: GuildRegistry._registerAgent() L98-106; registerEnsuranceAgent()/registerEnsuranceAgentLegacy() L114-142 (onlyMembershipAdminOrOwner); no de-register/rotate function exists anywhere in the contract

Description: Two compounding gaps in the same trust surface: (1) membershipAdmin — a role the owner can delegate — can mint an unlimited number of agents with no cap, and every minted agent immediately gains full onlyDisputeOpener authority (F-01) and a vote in every guild decision; (2) agentIdOf/agentAddress are only ever set, never cleared — a leaked, compromised, or malicious agent key retains permanent power with no on-chain remedy short of abandoning the entire registry (which also requires redeploying GuildVoting, per _validateGuildVotingPair's immutable binding).

Proof of Concept: membershipAdmin (or a compromised holder of that role) pre-registers N colluding addresses via registerEnsuranceAgent before any dispute/proposal snapshot is taken (snapshots correctly block mid-flight registration, but not pre-registration). The N agents collectively clear the 2/3 threshold in GuildVoting.isOverride or NatureSplitRouter.canExecute, or individually exercise F-01's unilateral crown power — with no way for the owner to later evict any of them.

Recommendation: Restrict agent minting to owner only (or a timelocked multisig); cap agent count or require per-agent governance approval. Add an owner/membership-admin deregisterAgent(uint256 agentId) clearing agentIdOf/agentAddress (and ensurance reverse-mappings), plus an address-rotation function, with events.

[F-05] NatureSplitRouter proposals never expire and have no voting deadline — a stale, small-snapshot proposal can be executed much later to hijack the nature recipient

Severity: Medium
Origin: [both] — Phase 1 governance (GOV-1) + Phase 2 numerical-gap (lead)
Location: canExecute()/execute()/vote() L80-134

Description: canExecute has a lower time bound (openedAt + UPDATE_INTERVAL, lastRecipientUpdateAt + UPDATE_INTERVAL) but no upper bound and no round == currentRound() check; vote() has no deadline. A proposal opened when the guild was small (small totalAgentsSnapshot denominator) can sit dormant, accumulate votes indefinitely, and be executed much later against a stale, un-representative snapshot.

Proof of Concept: Guild has 3 agents; attacker propose(X) and gets 3 yes-votes (3*3 > 3*2 passes), but doesn't execute. Guild grows to 100 legitimate agents over the following months. At any later point (once 3 days have passed since the last update), attacker calls execute(oldRound), flipping recipient to X using the stale 3-agent snapshot and redirecting ~70-74% of all participation fees. Gated only by X still being in approvedRecipients.

Recommendation: Require round == currentRound() or an explicit execution deadline in canExecute/execute; add a voting deadline; consider re-reading guildRegistry.totalAgents() for the quorum denominator instead of a frozen snapshot.

[F-06] NatureSplitRouter.propose per-round candidate lock lets a single guild member permanently grief recipient governance

Severity: Medium
Origin: [both] — Phase 1 governance (GOV-2) + Phase 2 periphery/boundary/flow-gap (3 of 12 agents)
Location: propose() L84-97

Description: The first propose() caller in a 3-day round locks that round's candidate (require(p.candidate == candidate, "Round candidate locked")); there is no cancellation, replacement, or admin fallback, and recipient can only change via this vote path.

Proof of Concept: A malicious/obstinate agent calls propose(A) (an approved-but-never-passing candidate) at the start of every 3-day round, permanently blocking propose(B) for the guild's actually-desired candidate B. Cost: one cheap tx per round, indefinitely.

Recommendation: Key proposals by candidate (allow multiple concurrent proposals per round) rather than one-slot-per-round, or provide a bounded, timelocked admin override.

[F-07] Entry-slot exhaustion griefing simultaneously denies submission AND voting for an entire epoch

Severity: Medium (escalated from Phase 1's Low — Phase 2 proved the same attack also strips honest voting rights, not just submission)
Origin: [both] — Phase 1 dos (DOS-2) + Phase 2 economic-security (direct FINDING with costed PoC)
Location: _submitEntry() L473-474 (MAX_ENTRIES_PER_EPOCH=64, MAX_ENTRIES_PER_WALLET_PER_EPOCH=1); _isWalletVoteEligibleForEpoch() (vote eligibility derives solely from userEntryCount)

Description: Only the trivially-Sybil-bypassed per-wallet cap gates entries. Because vote eligibility (F-02's mechanism) is based purely on having an entry, an attacker who fills all 64 global entry slots at epoch start doesn't just block legitimate submissions — they also strip every honest wallet of voting rights for the full 3-day epoch, since no non-attacker wallet can obtain the userEntryCount > 0 required to vote at all.

Proof of Concept: 64 funded wallets each submit a unique-URL entry (≈0.083 ETH / ≈$191 USDC total + Base gas), exhausting epochEntries[epoch].length < MAX_ENTRIES_PER_EPOCH. Honest users get MaxEntriesPerWalletReached/MaxEntriesPerEpochReached on submission and NotEnoughVotes on voting — full governance takeover of that epoch's winner selection, not merely a submission DoS. Honest users can still boost/boostWithUSDC (no slot required), so their contributed funds are only winnable by attacker-controlled entries.

Recommendation: Decouple vote eligibility from entry-slot occupancy (e.g., require the funding-age gate from F-02 instead of/in addition to entry count); consider reserving capacity or adding a per-wallet Sybil cost independent of the shared 64-slot cap.

[F-08] Front-running / URL-squatting of submissions, including canonicalization-based variants

Severity: Low
Origin: [both] — Phase 1 general/dos (GEN-3, DOS-3) + Phase 2 periphery/first-principles/boundary/invariant/numerical-gap (5 of 12 agents)
Location: _submitEntry() dedup L480-486; sourceHash() L442-444; _xCanonical() L390-398; _youtubeCanonical() L360-388

Description: Uniqueness is enforced on a deterministic, public sourceHash(url, platform) with no on-chain proof of content ownership/authorship. An attacker watching the mempool can front-run a victim's submitEntry with the identical (or canonicalization-equivalent) URL, seizing entrySubmitter/entryPayoutRecipient for content they didn't create. Phase 2 additionally identified canonicalization-specific variants: (a) _xCanonical extracts a tweet ID via the first /status/ occurrence regardless of host or username, so a bare/crafted URL can pre-compute and squat a legitimate tweet's canonical hash before the real permalink is submitted; (b) twitter.com/x.com non-/status/ URLs (e.g. profile links) do not normalize to the same hash, allowing the identical content to occupy multiple entry slots under different hosts (under-inclusive dedup, opposite direction); (c) unlisted URL shapes (/embed/, /live/) fall through to near-raw-URL hashing, similarly allowing duplicate representation of the same video.

Proof of Concept: Victim broadcasts submitEntry("https://youtube.com/watch?v=ABC"); attacker front-runs with the identical URL and canonical hash, minting the entry as themselves; victim's tx reverts AlreadySubmitted. Bounded by MAX_ENTRIES_PER_WALLET_PER_EPOCH=1 and expected to be caught by guild content verification as a backstop for outright misattribution, but the canonicalization-variant attacks can also be used purely for slot-duplication/vote-splitting griefing rather than misattribution.

Recommendation: Bind submission to an off-chain ownership attestation the guild can validate, or make attribution disputes explicit in recordEntryVerificationDecision. Harden _xCanonical to require the full expected path structure (not just substring presence) and normalize twitter.com/x.com hosts consistently for all path shapes, not just /status/.

[F-09] Single registered agent can force a ~1-day payout delay on any epoch via repeated disputes

Severity: Low
Origin: [both] — Phase 1 dos (DOS-4) + Phase 2 economic-security/trust-gap
Location: dispute() L707-719 (onlyDisputeOpener)

Description: Any single agent can open a dispute within the window, forcing crownWinner/closeNoWinner to wait out the full DISPUTE_WINDOW (1 day) guild-review period, once per epoch (require(!disputedEpochs[epoch])).

Proof of Concept: Rogue/compromised agent calls dispute(E) on every finalized epoch, delaying settlement ~1 day each time. Always eventually resolvable (bounded delay, not permanent lock).

Recommendation: Require a bond/quorum to open a dispute, or restrict dispute() to a subset of agents.

[F-10] ecosystemRecipient/protocolRecipient are read live per-transaction while natureRecipient is snapshotted per-epoch — inconsistent settlement-recipient freezing

Severity: Low
Origin: [phase2 only] — invariant, trust-gap agents (2 of 12); re-examined against source and confirmed
Location: _recordEthParticipation()/_recordUsdcParticipation() L582-604; _requireCommittedShareRecipients() L575-580; setEcosystem()/setProtocol() L846-860

Description: settlementNatureRecipient[epoch] is frozen at first participation via _recordSettlementNatureRecipient specifically to guarantee epoch-consistent settlement, but ecosystemRecipient/protocolRecipient are read live from state on every credit, with no equivalent per-epoch snapshot. Pre-lockPayoutRecipients, the owner (already broadly trusted per F-03/F-04) can change setEcosystem/setProtocol mid-epoch, causing different participants in the same epoch to have their 4%/1% shares routed to different addresses — an internal inconsistency relative to the nature-recipient design, though bounded to the same owner-trust level already assumed elsewhere.

Recommendation: Snapshot ecosystemRecipient/protocolRecipient per-epoch the same way natureRecipient already is, for design consistency.

[F-11] Nature-router recipient resolving to a forbidden address can brick all participation for an epoch

Severity: Low
Origin: [phase2 only] — execution-trace, flow-gap agents (2 of 12); re-examined against source and confirmed
Location: _liveNatureRecipient() L188-195; _recordSettlementNatureRecipient() L197-204

Description: _liveNatureRecipient()'s call to natureRouter.recipient() is wrapped in try/catch, but the resolved address then flows into _validatePayoutRecipient inside _recordSettlementNatureRecipient with no catch. If NatureSplitRouter's guild-voted recipient() ever resolves to a _validatePayoutRecipient-forbidden value (e.g. the router's own address or winnerPayoutRouter), every submitEntry/vote/boost in that epoch reverts, since the settlement-recipient write can never succeed and the same revert is hit on every subsequent call.

Proof of Concept: Requires multi-party misconfiguration — NatureSplitRouter's recipientAdmin must have approved a colliding candidate in approvedRecipients, and the guild must vote it through via execute(). Once triggered, the affected epoch cannot accept any new participation until governance executes a corrective proposal.

Recommendation: On a forbidden/invalid resolved recipient, fall back to the stored natureRecipient rather than reverting the entire participation call.

[F-12] Tiny/small guild snapshots make the 2/3 supermajority trivial for one or two agents

Severity: Low
Origin: [phase1 only] — governance (GOV-4); re-examined against source and confirmed
Location: GuildVoting.isOverride() L63-74; NatureSplitRouter.canExecute() L115-124

Description: Both use votes*3 > snapshot*2 with no minimum-quorum floor. With snapshot==1, one vote passes. Division-by-zero is correctly guarded (totalAgents==0 short-circuits false) — the only gap is the lack of an absolute quorum floor.

Proof of Concept: Guild has 1 agent; that agent disputes a crowned epoch and votes non-compliant once → override triggers, real pooled funds are rolled to the next epoch, on a single vote.

Recommendation: Enforce a minimum absolute agent count/vote count before an override or recipient change can take effect.

[F-13] Cascading pause/unpause between EpochManager and NFT can brick the intended pause entrypoint

Severity: Low
Origin: [phase1 only] — access-control (AC-5); re-examined against source and confirmed
Location: EpochManager.pause()/unpause() L941-949; DancepartyEntryNFT.pause()/unpause() (onlyOwnerOrManager)

Description: The NFT can be paused/unpaused independently by its own owner or manager. If its pause state diverges from EpochManager's, EpochManager's cascading nft.pause()/nft.unpause() call reverts (OZ's already-in-state guard), reverting the whole tx and leaving EpochManager's own pause entrypoint unusable until manually realigned.

Recommendation: Guard the cascading call (e.g. if (!nft.paused()) nft.pause();) so EpochManager's pause state is never hostage to the NFT's independent state.

[F-14] setManager has no cross-check against the real EpochManager; renounceOwnership can brick critical setters; setGuildRegistry to an empty registry silently removes the owner's fallback authority

Severity: Low
Origin: [both] — Phase 1 access-control (AC-6) + Phase 2 access-control/economic-security (setGuildRegistry sub-issue)
Location: DancepartyEntryNFT.setManager() L48-53; inherited Ownable.renounceOwnership() on all 5 contracts; DancepartyEpochManager._onlyDisputeOpener()/setGuildRegistry() L172-178, 925-932

Description: Three related operator-misconfiguration footguns: (1) setManager accepts any non-zero address with no verification it is the real EpochManager; (2) every contract still exposes single-step renounceOwnership() despite inheriting Ownable2Step — calling it on EpochManager while paused permanently disables unpause(), and on GuildRegistry freezes the agent set forever (compounding F-04); (3) _onlyDisputeOpener's owner-fallback branch only applies when guildRegistry == address(0) — once setGuildRegistry is called (with no check that the registry has any registered agents), the owner permanently loses that fallback, and if the registry is empty or inaccessible, no address can call dispute/recordEntryVerificationDecision/crownWinner/closeNoWinner until the owner separately registers itself as an agent on that registry.

Proof of Concept: All three require operator error rather than external attack. Example: owner calls setGuildRegistry(freshEmptyRegistry) — all onlyDisputeOpener functions revert for everyone, including the owner, until registerAgent(owner) is called on the new registry (recoverable only if the owner controls that registry).

Recommendation: Sanity-check the manager candidate in setManager; override renounceOwnership() to revert where a live owner is required for recovery; have setGuildRegistry verify totalAgents() > 0 (or auto-register the owner) before accepting a new registry.

[F-15] No permissionless timeout/resolution path if guild and owner go inactive during VerificationPending

Severity: Low
Origin: [phase1 only] — general (GEN-5); re-examined against source and confirmed
Location: closeEpochForVerification() (public) vs crownWinner()/closeNoWinner() (onlyDisputeOpener); claimPayout()

Description: Once VerificationPending, only a registered agent (or owner if no registry set) can advance the epoch. If the guild/owner become inactive, that epoch's winner-pool ETH/USDC (and anything later rolled into it) has no time-based fallback and is stuck indefinitely.

Recommendation: Add a permissionless timeout path (e.g., auto-rollover to closeNoWinner after a bounded window, or allow the tentative winner to claim if no guild action occurs within N days).

[F-16] tokenURI accepts non-ASCII/invalid-UTF-8 bytes, risking metadata-parser breakage (JSON structural injection confirmed NOT possible)

Severity: Low
Origin: [phase1 only] — erc721 (NFT-1); re-examined against source and confirmed
Location: DancepartyEntryNFT.tokenURI() L82-102; _hasInvalidUrlCharacter() (EpochManager L349-358, blocks only ", \, and bytes <0x20)

Description: The blocked byte set exactly matches RFC 8259's mandatory-escape set, so structural JSON injection is confirmed impossible. However bytes 0x7F and 0x80-0xFF are still accepted and interpolated raw into base64-encoded JSON metadata, risking rejection/garbling by strict UTF-8-validating parsers.

Recommendation: Restrict _hasInvalidUrlCharacter to a printable-ASCII allowlist (0x20-0x7E), or escape non-ASCII bytes in tokenURI.

[F-17] USDC blacklist/pause can cause temporary (recoverable) reverts on hard safeTransfer push paths

Severity: Low
Origin: [phase1 only] — erc20 (ERC20-1); re-examined against source and confirmed
Location: NatureSplitRouter.flushERC20() L144-150; DancepartyEpochManager._withdrawClaimableUsdcTo() L1076-1086

Description: Both use hard-reverting SafeERC20.safeTransfer with no try/catch. If the target is Circle-blacklisted (or USDC is globally paused), the call reverts.

Recommendation: Acceptable as-is for canonical USDC; document the recipient-rotation (router) / redirect-destination (withdrawClaimableUsdcTo) recovery paths as the operational mitigation.

[F-18] Truncation dust from percentage splits is swept entirely to the protocol share

Severity: Info

Description: All percentage shares multiply-before-divide (no division-before-multiplication bug), and conservation holds exactly (protocol share = residual). At sub-100-unit deposit sizes (only reachable via boost()'s arbitrary msg.value), nature/winner/eco shares floor to zero and protocol absorbs 100% of the dust — not exploitable, no profit motive.

Recommendation: None required; optionally document the intentional dust-absorption behavior.
