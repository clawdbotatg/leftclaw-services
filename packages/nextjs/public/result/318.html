Security Audit Report — Cortex (CX) System

Client-supplied context: the client asked for due diligence on four related Base contracts referenced from "the AI agent chat at cortexprotocol.com." Independent of that framing, the on-chain source (SYN→CX migration at a 5.5:1 ratio, a Synapse-style custom interchain-messaging framework, ERC20Votes governance, a LayerZero OFT bridge) is consistent with a real protocol migration, not a throwaway scam contract — this audit evaluates the code on its own merits regardless of how the client learned about it.

Methodology: Two-phase audit — Phase 1 checklist breadth (9 domain checklists, reflecting the system's real complexity: general, precision-math, erc20, bridges, signatures, governance, access-control, dos, assembly) run in parallel, followed by Phase 2 attacker-mindset depth (12 independent agents: 9 specialty + 3 gap-hunter), run blind to Phase 1's findings. A final reconciliation pass cross-checked both phases against each other, against the source, and — where a finding's severity hinged on live configuration — against the current on-chain state via direct cast calls to the deployed contracts.

Reconciliation summary

Overlap: the headline finding was independently discovered by phase 1's general checklist agent and corroborated by 9 of 12 phase-2 attacker-mindset agents (6 as full findings). Several Medium/Low findings were found independently by both phases. Phase-1-only: the governance/access-control centralization findings and most Info-level items. Phase-2-only: the LockDrop split-unlock rounding trail — initially raised as a full finding by 2 agents, downgraded to a Low/lead after 4 more agents and this orchestrator's own economic modeling showed it's dust-bounded at the deployed parameters.

  • CortexAdapter.hasRole(MINTER_ROLE, ...) → true, CortexMigrator.hasRole(MINTER_ROLE, ...) → true — confirming the preconditions for the headline finding are/were live.
  • CX's transfer-disabled freeze is currently lifted (_transfersEnabled == true, confirmed by simulating a zero-value transfer() between two unrelated, non-allow-listed addresses — it succeeds rather than reverting). This means the headline finding's exploit window has already closed for the current deployment.
  • LockDrop.DROP_RATIO = 5.5e18 (≥ WAD), LOCK_TOKEN = the legacy SYN token, DROP_TOKEN = CX, totalLockedAmount ≈ 29,813 tokens still recorded as locked, and isLockingEnabled() → false (the lock window closed around February 2025) — confirming the split-unlock rounding trail is both dust-bounded at this ratio and currently uncallable on the live instance.
  • CX total supply ≈ 6.2M tokens, far under the ~18.4B cap implied by CortexAdapter's 9 shared decimals.

Completeness: every unique (contract, function, bug-class) tuple raised across both phases' raw agent output is represented below, either as a numbered finding or in the Leads/Cleared sections.

Findings

[1] CortexAdapter bypasses CX's transfer-disabled lock — a second bridge ignores the freeze the native bridge enforces

Severity: Medium (real, provable code-level gap; downgraded from what a naive reading suggests because the freeze window is already closed on the live deployment — see reconciliation note)
Origin: [both] — phase1: general checklist agent; phase2: independently raised as a full FINDING by 6 of 12 agents (access-control, economic-security, execution-trace, periphery, first-principles, asymmetry), corroborated as a LEAD by 3 more (boundary, trust-gap-hunter, flow-gap-hunter) — the strongest convergence of this engagement.

Location: CX._update() (transfer-disabled guard), CX._giveToken()/_takeToken() (native bridge, correctly gated) vs. CortexAdapter._debit()/_credit() (LayerZero bridge, not gated).

Description: CX's _update transfer-disabled guard only reverts when to != address(0) && from != address(0) — mints and burns are always exempt by design, so mint(), burnAllocation, and the LockDrop/Migrator distribution flows keep working pre-launch:

if (!_transfersEnabled && to != address(0) && from != address(0) && !isAllowListed[to] && !isAllowListed[from]) {
    revert CX__TransfersDisabled();
}

CX's own cross-chain bridge adds an explicit extra check on top of this:

function _giveToken(address recipient, uint256 amount) internal virtual override returns (uint256 amountGiven) {
    if (!_transfersEnabled) revert CX__TransfersDisabled();
    return InterchainToken._giveToken(recipient, amount);
}

CortexAdapter is a second, independent bridge (LayerZero OFT) that moves CX via the raw mint()/burnFrom() primitives directly — neither is gated by _transfersEnabled. Since a burn has to==0 and a mint has from==0, both pass _update unconditionally, so a holder of "locked" (pre-launch) CX can burn it via the adapter and mint an unrestricted balance on another chain — the exact action the native bridge was specifically built to prevent.

Proof of Concept: While _transfersEnabled == false: holder approves CortexAdapter, calls send(...) → _debit calls CX.burnFrom(holder, amount) → _update(holder, address(0), amount) → guard skipped (burn exempt) → succeeds. LayerZero delivers to the peer chain → _credit calls CX.mint(recipient, amount) → _update(address(0), recipient, amount) → guard skipped (mint exempt) → succeeds. Confirmed on-chain that the precondition for this to matter was live: CortexAdapter currently holds MINTER_ROLE on CX (hasRole returns true). However, also confirmed on-chain that CX's transfer freeze is currently lifted — a zero-value transfer() between two unrelated addresses succeeds rather than reverting — so this specific bypass window has already closed for the live deployment. The finding stands as a real structural defect (worth fixing for any future re-freeze, a new token launch reusing this architecture, or if a similar dual-bridge pattern is deployed elsewhere) rather than a currently-exploitable drain.

Recommendation:

 function _debit(address _from, uint256 _amountLD, uint256 _minAmountLD, uint32 _dstEid)
     internal virtual override returns (uint256 amountSentLD, uint256 amountReceivedLD)
 {
     (amountSentLD, amountReceivedLD) = _debitView(_amountLD, _minAmountLD, _dstEid);
+    if (!ICX(address(innerToken)).transfersEnabled()) revert TransfersDisabled();
     IMintableToken(address(innerToken)).burnFrom(_from, amountSentLD);
 }

Apply the equivalent check in _credit, or — simpler operationally — only grant CortexAdapter (and CortexMigrator, see Finding 6) MINTER_ROLE after enableTransfers() has been called, so neither bridge is ever live during a frozen window.

[2] DEFAULT_ADMIN_ROLE can self-grant MINTER_ROLE/GOVERNANCE_ROLE for unlimited minting and arbitrary balance destruction

Severity: Medium
Origin: [phase1 only] — governance + access-control checklist agents, independently, both flagging the identical root cause.

Location: ICAppV1 constructor (grants only DEFAULT_ADMIN_ROLE to admin_, no _setRoleAdmin override anywhere), CX.mint(), CX.burnAllocation().

Description: No _setRoleAdmin call exists anywhere in the bundle, so DEFAULT_ADMIN_ROLE is the admin of MINTER_ROLE, GOVERNANCE_ROLE, and IC_GOVERNOR_ROLE (and of itself). The interchain messaging side goes to considerable lengths to become trust-minimized (one-way freezeGovernorAction/freezeLinkedApp), but none of that protects the token-supply/burn powers: whoever holds DEFAULT_ADMIN_ROLE can grantRole(MINTER_ROLE, self) then mint() an unbounded amount (works regardless of transfer-enabled state), or grantRole(GOVERNANCE_ROLE, self) then use burnAllocation/toggleAllowList — all instantly, with no timelock.

Recommendation: Hold DEFAULT_ADMIN_ROLE in a timelock/multisig, not an EOA; consider a supply cap on mint; consider an irreversible "renounce minting" once cross-chain supply is seeded, mirroring the interchain side's freeze story.

[3] burnAllocation() lets GOVERNANCE_ROLE destroy any holder's balance without consent

Severity: Medium
Origin: [phase1 only] — governance checklist agent.

Location: CX.burnAllocation() — gated only by onlyRole(GOVERNANCE_ROLE) whenTransfersDisabled, calls _burn(account, amount) directly with no consent, allowance check, or bound.

Description: Combined with toggleAllowList (grant frictionless transferability to chosen accounts while everyone else is frozen) and the one-way enableTransfers, a single GOVERNANCE_ROLE holder has a structural, unilateral clawback power over third-party pre-launch allocations (and their ERC20Votes checkpoints) with no on-chain acknowledgment from the victim.

Recommendation: If intended as a pre-launch correction tool, document it explicitly, add a dedicated event, constrain it (e.g. non-allow-listed targets only, or a published cap), and hold GOVERNANCE_ROLE in a timelock/multisig.

[4] LockDrop doesn't measure actual received balance — a fee-on-transfer/rebasing LOCK_TOKEN would desync accounting and brick unlock/finalization/recovery

Severity: Medium
Origin: [both] — phase1: erc20 + general checklist agents; phase2: corroborated as leads by 3 agents (math-precision, boundary, flow-gap-hunter).

Location: LockDrop.lock() (credits totalLockedAmount/lockedAmountOf with the nominal parameter, never measures balanceOf(this) before/after safeTransferFrom), unlock(), processFinishedLockdrop(), recover().

Description: If LOCK_TOKEN is fee-on-transfer or rebases down, the contract receives less than the recorded amount, so totalLockedAmount permanently exceeds real balance — unlock() overpays the last unlockers into a revert (principal stuck), processFinishedLockdrop()'s burn reverts if real balance is short, and recover()'s subtraction underflows and reverts, blocking even dust recovery.

On-chain note: the deployed instance's LOCK_TOKEN is the legacy SYN token (confirmed via LOCK_TOKEN() read), a standard non-fee ERC20 — so this is not live-exploitable against the current deployment, but the contract imposes no restriction that would prevent a future LockDrop instance (deployed via the same factory pattern) from using a fee-on-transfer or rebasing token.

Recommendation: Measure the actually-received amount via balanceOf(this) before/after safeTransferFrom and record that delta, or explicitly restrict LOCK_TOKEN to standard tokens and enforce it at the factory.

[5] LockDrop.unlock's per-call rounding lets a locker recover slightly more than they should when splitting an unlock — dust-bounded at the deployed ratio, not practically exploitable

Severity: Low (reduced from an initial higher-severity read — see reconciliation)
Origin: [phase2 only] — initially raised as a full FINDING by 2 of 12 agents (invariant, numerical-gap-hunter) with concrete worked examples; independently re-examined and downgraded by 4 more phase-2 agents (execution-trace, periphery, boundary) plus this orchestrator's own economic modeling.

Location: LockDrop.lock() (mints floor(L·DROP_RATIO/WAD) for the whole locked lump), unlock() (burns floor(lᵢ·DROP_RATIO/WAD) recomputed per call — the same formula applied to each piece, not tracked from what was actually minted).

Description: Because Σ floor(lᵢ·r/W) ≤ floor((Σlᵢ)·r/W) for integer division, fragmenting an unlock into many small pieces burns strictly less drop-token than minting the same aggregate amount would require, letting a locker recover 100% of their principal while keeping a small drop-token surplus. Two phase-2 agents demonstrated this with toy numbers (e.g., DROP_RATIO=5.5e18, lock(2) mints 11, two unlock(1) calls burn 5+5=10, netting 1 wei of surplus drop-token) and, in one case, with a hypothetical DROP_RATIO < WAD where every unit-sized unlock call rounds to a zero burn.

Reconciliation — walking the actual exploit path at the deployed parameters: the live DROP_RATIO is 5.5e18 (≥ WAD = 1e18). At any ratio ≥ WAD, floor(1·r/W) ≥ 1 for every nonzero unit — there is no "zero-burn" call available at all; the leak is bounded to the sub-1-wei fractional remainder per call. Extracting even one whole drop-token of surplus this way requires on the order of 10^18 separate unlock transactions, which is economically and practically infeasible regardless of how cheap gas is. The severe "recover everything for zero burn" variant only becomes meaningfully dangerous if a future LockDrop deployment used a DROP_RATIO many orders of magnitude below WAD — an unusual parameter choice this contract doesn't prevent, but not the case here. Separately confirmed on-chain: the live instance's lock window closed around February 2025 (isLockingEnabled() == false), so lock/unlock are both currently uncallable — this issue cannot be triggered against the live deployment at all right now.

Recommendation: Still worth fixing for defense-in-depth and for any future deployment with a different ratio: track the exact drop-token amount minted per locker (e.g. mintedDropOf[msg.sender] += dropAmount in lock) and burn the proportional recorded amount in unlock rather than recomputing calculateDropAmount(lockTokenAmount) from scratch, so mint and burn stay conserved regardless of how the unlock is batched.

[6] CortexMigrator may offer a parallel transfer-freeze escape via burn-CX/mint-SYN

Severity: Low
Origin: [both] — phase1: general checklist agent (noted as part of the broader "two bridges bypass the lock" pattern); phase2: raised as a lead by 4 agents (access-control, first-principles, boundary, trust-gap-hunter).

Location: CortexMigrator.cxToSYN() — burns CX via burnFrom (passes the freeze-exempt burn path in _update) and mints SYN.

Description: Same root cause as Finding 1 — CX's freeze only lives in _giveToken/_takeToken, not at the mint/burn layer. cxToSYN burns CX (allowed while frozen) and mints liquid SYN; if SYN is transferable during CX's freeze, this converts a locked position into a liquid one via a second channel. Confirmed on-chain: CortexMigrator currently holds MINTER_ROLE on CX. As with Finding 1, this is currently moot in practice since CX's freeze is already lifted on the live deployment, but the code-level gap is real.

Recommendation: Gate cxToSYN's CX-burn leg on _transfersEnabled (mirroring Finding 1's fix), or only grant the migrator its CX minter rights after enableTransfers().

[7] LockDrop owner has unbounded control over lockEndTime

Severity: Low
Origin: [both] — phase1: general + access-control checklist agents; phase2: corroborated as a lead by the economic-security agent.

Location: LockDrop.setLockEndTime() — only enforces a rolling 1-week buffer on both the current and new value, no maximum.

Description: The buffer-boundary logic itself is correct, but with no upper bound the owner can extend the lock indefinitely (delaying finalization forever) or shorten a long advertised lockdrop down to ~7 days' notice, then burn all still-locked tokens via processFinishedLockdrop(). Funds aren't redirected (burned, not stolen), so this is a trust/expectation issue rather than theft. On-chain note: this already happened on the live deployment in the sense that the window did run its full course and has since closed normally (no evidence of anomalous early shortening was checked, as event history is outside this audit's scope) — flagging the structural gap regardless.

Recommendation: Add a maximum extension cap and/or disallow shortening below the originally-advertised duration.

[8] Custom Interchain remoteSend burns CX to a zero recipient with no check (asymmetric with CortexAdapter's guard)

Severity: Low
Origin: [both] — phase1: bridges checklist agent; phase2: corroborated as a lead by 2 agents (execution-trace, periphery).

Location: TokenController._remoteSend()/_remoteSendWithHook() vs. CortexAdapter._send() (which explicitly checks _sendParam.to == 0).

Description: A caller passing a zero recipient burns real CX on the source chain, and the resulting message can never execute on the destination (mint-to-zero reverts), so it's permanently stuck — every retry fails identically.

Recommendation: Add require(recipient != 0) in _remoteSend/_remoteSendWithHook, mirroring CortexAdapter._send.

[9] Unchecked raw mint()/burnFrom() calls on DROP_TOKEN with no code-length check

Severity: Low
Origin: [phase1 only] — erc20 checklist agent.

Description: If a factory misconfigures DROP_TOKEN as an EOA, the raw mint() call silently no-ops — lock() would pull LOCK_TOKEN from users and mint nothing back, with no revert. Moot for the live deployment (DROP_TOKEN is CX itself, confirmed on-chain, a real contract).

Recommendation: Assert DROP_TOKEN.code.length > 0 (and LOCK_TOKEN.code.length > 0) in the constructor, for future deployments via the factory.

[10] lock() credits the locker's redemption right while minting drop tokens to an arbitrary recipient

Severity: Low
Origin: [both] — phase1: erc20 + general checklist agents; phase2: corroborated as a lead by 2 agents (access-control, invariant).

Description: lockedAmountOf[msg.sender] is credited to the caller, but dropAmount is minted to a separate recipient parameter. If recipient != msg.sender, neither party can complete an unlock without the drop tokens being transferred back — a confusing accounting split that can strand redemption, though not a fund-theft vector.

Recommendation: Either key lockedAmountOf consistently with drop-token custody, or clearly document the gift-vs-redemption-right split.

[11] linkRemoteApp silently overwrites an active chain link with no forced freeze; combined with uncapped minting, a compromised governor/minter role mints unlimited CX

Severity: Low
Origin: [phase1 only] — bridges checklist agent.

Description: Freezing a chain link is opt-in and off by default. Combined with addInterchainClient/setLatestInterchainClient and CX's uncapped mint(), a compromised governor/minter key can add a malicious client, relink a chain, forge an incoming message, and mint unbounded CX.

Recommendation: Require an explicit unfreeze/timelock before linkRemoteApp can overwrite a non-zero existing link; add a timelock/multisig on IC_GOVERNOR_ROLE; introduce a per-epoch mint rate limit shared across both mint authorities.

[12] cxToSYN/synToCX round to zero for dust amounts with no zero-output guard

Severity: Low
Origin: [both] — found independently by 3 phase-1 agents (precision-math, general, access-control) and corroborated by the phase-2 math-precision agent.

Description: amountSYN = amountCX * WAD / MIGRATION_RATIO floors to 0 for amountCX ≤ 5 wei; the function still burns the caller's CX and mints 0 SYN. Verified numerically not round-trip-exploitable in either direction (both directions round toward the protocol) — dust-scale self-harm only.

Recommendation: Add if (amountOut == 0) revert in both directions.

[13] CortexAdapter uses single-step Ownable instead of Ownable2Step (inconsistent with LockDrop)

Severity: Low
Origin: [phase1 only] — access-control checklist agent.

Description: A mistyped transferOwnership permanently locks LayerZero peer/endpoint configuration with no recovery.

Recommendation: Switch to Ownable2Step.

[14] No app-level replay protection in appReceive/_receiveMessage; multi-registered-client dedup gap

Severity: Low
Origin: [phase1 only] — bridges checklist agent.

Description: Exactly-once delivery is delegated entirely to the external IInterchainClientV1; _interchainClients intentionally allows multiple simultaneously-registered clients with no in-contract dedup across them.

Recommendation: Add app-level idempotency keyed on (srcChainId, dbNonce) in _receiveMessage, marking each consumed before minting, independent of client-side guarantees.

[15] _isAllowedSender returns true for an unlinked chain when sender == 0

Severity: Low
Origin: [phase1 only] — bridges checklist agent.

Description: For a never-linked chain, _linkedApp[srcChainId] == 0; if a client ever presented sender == bytes32(0), the equality would pass. Defense-in-depth gap, not reachable through a correctly-behaving client.

Recommendation: return _linkedApp[srcChainId] != 0 && _linkedApp[srcChainId] == sender;

Info-level observations (no action required, or informational only)

  • Two independent bridges produce non-fungible, non-interoperable CX representations per remote chain — asset-fragmentation/UX footgun, not a fund-loss bug. [both phases]
  • CortexAdapter.sharedDecimals()=9 truncates dust and caps effective bridgeable supply at ~18.4B CX — current supply (~6.2M, verified on-chain) is far under this. [both phases]
  • processFinishedLockdrop() doesn't clear lockedAmountOf — stale per-user view balances persist forever after finalization (functionally inert). [phase1]
  • CortexAdapter._credit mints to _to with no zero-address fallback — standard LZ OFT substitutes 0xdead; this override drops that safety net. [phase1]
  • setGasLimit is an IC_GOVERNOR_ROLE lever with no freeze coverage — undermines the "freeze everything" governance-lock-in story. [phase1]
  • isAllowListed becomes dead configuration after enableTransfers() — confirmed not weaponizable (no deny-list path exists). [phase1]
  • Hardcoded 1e18-precision ratio math assumes 18-decimal tokens — safe for the current SYN/CX pair (both confirmed 18 decimals); unenforced for future factory deployments with other tokens. [both phases]
  • Cross-chain voting power is fragmented per chain — no double-vote path exists in CX itself; any future Governor must snapshot at a synchronized timepoint. [phase1]
  • MathLib.roundUpToWord silently returns 0 on overflow — unreachable in practice (only realistic byte-array lengths are ever passed). [both phases]
  • Assembly calldataload reads in TokenMessageLib.decodeMessage depend on a later, separate bounds check — currently safe, but an implicit coupling worth making explicit. [phase1]
  • Standard ERC-2612 permit() front-running griefing — universal, unavoidable characteristic; no CX-specific exploitation path. [phase1]

Items explicitly reviewed and cleared (no finding)

  • EIP-712 domain correctly includes block.chainid — permit()/delegateBySig() signatures cannot replay across the multiple EVM chains CX is deployed at the same address on.
  • nonces() diamond-inheritance override correctly resolves to one shared Nonces storage — no desync, no cross-function signature replay.
  • clock()/CLOCK_MODE() timestamp-mode override is fully supported by OZ's Votes/Checkpoints — no double-count risk.
  • CX._update verified to cover every balance-changing path with no diamond-inheritance MRO bypass.
  • LockDrop.recover() correctly excludes locked principal from owner sweeps at every boundary; the factory-constructor trust model is confirmed non-exploitable.
  • CortexMigrator/CortexAdapter misconfigured mint/burn authority fails atomically (clean revert) rather than corrupting state.
  • All DoS surfaces (EnumerableSet growth, hook-call gas, chainGasLimit misconfiguration, ERC20Votes checkpoint growth) are governor-bounded, self-contained, or standard accepted OZ tradeoffs.
  • No reentrancy found anywhere in the 4 contracts (checks-effects-interactions consistently followed).
  • CortexMigrator's 5.5:1 ratio math conserves value exactly in both directions — no round-trip extraction possible.
