Executive summary

A gig-work marketplace with per-task escrow (upfront/milestone/streaming/hourly payout
modes), mutual-consent-or-fallback arbitration, a delayed break-glass mechanism to swap the
arbitration module, and an AZL staking/fee-rebate system. The codebase is well-structured —
consistent two-step ownership, systematic one-time-setter wiring, and a deliberate
defer-on-failure (_payOrDefer) pattern that defends nearly every USDC payout against
blacklisted recipients.

Three High severity bugs were found, each independently rediscovered by a large fraction
of an 18-agent audit fleet working blind to each other — an unusually strong corroboration
signal for this class of finding:

  1. ArbitrationRecoveryCoordinator.enterRecoveryLockdown() has no access control — any
    address can permanently disable dispute-opening and the stale-review auto-release
    mechanism with a single, free, precondition-free transaction.
  2. ArbitrationModule._finalise permanently leaks pendingSideEffectCount whenever an
    ordinary (non-malicious) dispute is resolved by an arbitrator with no native verifier
    bond — bricking the protocol's only arbitration-module recovery path.
  3. TreasuryRouter.flushStakerShare double-decrements accruedFees[usdc] whenever the
    staker share is flushed with zero active stakers, permanently stranding real, physically-
    held treasury USDC behind an underflow revert.

Findings 2 and 3 will very likely trigger in ordinary operation — neither requires an
attacker; they are latent correctness bugs waiting for the first arbitrator without a
verifier bond, or the first zero-stake epoch. Finding 1 requires an attacker but costs them
nothing. All three should be fixed before further mainnet exposure.

A cluster of Medium findings weakens the arbitration economic-security model (verifier-bond
slashing can be reduced to zero by design gaps rather than by exploiting a bug in the slash
math itself), and a long tail of Low/Info findings covers dead code, documentation/behavior
mismatches, and edge-case timing issues.

[H-1] ArbitrationRecoveryCoordinator.enterRecoveryLockdown() has no access control — any address can permanently disable dispute-opening and stale-review release

Severity: High · Confidence: 95 · Origin: [phase2: 2 agents, orchestrator-verified]
Location: ArbitrationRecoveryCoordinator.sol:124-127, ArbitrationModule.sol:274-280,298-301, TaskRegistry.sol:547-548,639-647

// ArbitrationRecoveryCoordinator.sol:122-127
/// @notice Permissionlessly enter the outgoing module's emergency lockdown.
/// The coordinator is the only authorized caller on the module.
function enterRecoveryLockdown() external {
    address outgoing = _consistentOutgoingAuthority();
    IArbitrationRecoveryTarget(outgoing).enterRecoveryLockdown();
}

// ArbitrationModule.sol:274-280
function enterRecoveryLockdown() external {
    require(
        msg.sender == arbitrationRecoveryCoordinator,
        "Arbitration: not recovery"
    );
    recoveryLockdown = true;
}

The coordinator function is external with zero preconditions — not even a requirement
that a recovery has actually been proposed (pendingArbitration != address(0)). It always
succeeds in calling the live module's enterRecoveryLockdown, which only checks that the
caller is the coordinator — trivially true since the coordinator is always the caller.
recoveryLockdown is set true at this single site and is never reset anywhere in the
contract (confirmed by exhaustive grep). It feeds directly into the pause check used by both
openDispute (ArbitrationModule.sol:362) and TaskRegistry.resolveStaleReview
(TaskRegistry.sol:548):

// ArbitrationModule.sol:298-301
function disputeOpeningPaused() public view returns (bool) {
    return recoveryLockdown ||
        (disputeOpeningPauseRequested && block.timestamp <= disputeOpeningPauseUntil);
}

Both revert permanently until a full owner-gated recovery (proposeRecovery → 2-day delay →
executeRecovery, installing an entirely new module) completes.

Fund-freeze escalation: a task in IN_REVIEW when lockdown hits has no escape.
acceptMilestone/completeTask are onlyPoster (TaskRegistry.sol:517-520,587) — the
worker cannot force release even with a fully proven milestone. resolveStaleReview and
openDispute are both blocked. expireTask explicitly excludes IN_REVIEW
(TaskRegistry.sol:639-647, only POSTED/CLAIMED/ACTIVE). A poster who goes silent
after this griefing attack freezes the worker's already-earned funds until governance
completes a full module swap.
Proof of Concept: Any EOA calls ArbitrationRecoveryCoordinator.enterRecoveryLockdown()
— no funds, no role, no proposed recovery required. recoveryLockdown = true on the live
module from that block onward. Every subsequent TaskRegistry.openDispute reverts
("Arbitration: opening paused") and every resolveStaleReview reverts ("TaskRegistry: disputes paused"). A concurrently IN_REVIEW task with a proven-but-unaccepted milestone
stays frozen until the owner runs a full 2-day recovery.
Recommendation: Gate enterRecoveryLockdown() with require(pendingArbitration != address(0), "Recovery: none pending") so lockdown can only follow an owner-initiated
proposeRecovery, or make it onlyOwner outright. Separately, give IN_REVIEW tasks an
escape valve independent of disputeOpeningPaused() (e.g. allow expireTask from
IN_REVIEW once past deadline).

[H-2] ArbitrationModule._finalise permanently leaks pendingSideEffectCount, bricking the sole arbitration-module recovery path

Severity: High · Confidence: 98 · Origin: [both] — 10 independent agents (phase1: evm-audit-general; phase2: 9 of 12 attacker-mindset agents), orchestrator-verified
Location: ArbitrationModule.sol:595-621 (_finalise), specifically lines 596-602 and 726

// ArbitrationModule.sol:596-602
bool qualifiedResolution = byArbitrator &&
    d.snapshotLockedBalance >= MIN_QUALIFIED_DISPUTE;
reputationCallbackPending[disputeId] = qualifiedResolution &&
    reputationRegistry.verifierBond(d.assignedArbitrator) > 0;
registryCallbackPending[disputeId] = true;
pendingSideEffectCount += qualifiedResolution ? 3 : 2;

// ArbitrationModule.sol:726 (_tryRecordReputation)
if (!reputationCallbackPending[disputeId] || address(reputationRegistry) == address(0)) return;

The counter is bumped by a hard-coded qualifiedResolution ? 3 : 2, but the reputation
effect's pending flag carries an extra condition the counter ignores: it's only true when
the arbitrator additionally holds a nonzero native verifier bond. Verifier bonds are entirely
optional — proposeArbitrator gates seating only on a $25 USDC deposit and reputation tier,
never a bond. Bootstrap-qualified arbitrators (owner-granted, no bond requirement) and any
arbitrator who simply never called stakeVerifierBond are the common case, not an edge
case. When such an arbitrator resolves a qualified (≥$1) dispute: pendingSideEffectCount += 3, but reputationCallbackPending = false, so _tryRecordReputation (called via if (qualifiedResolution) _tryRecordReputation(...)) returns at line 726 without ever
decrementing. Net: +1, permanently — retrySideEffects re-hits the identical guarded
early-return forever.

ArbitrationRecoveryCoordinator._validateSafeOutgoing requires
current.pendingSideEffectCount() == 0 before either proposeRecovery or executeRecovery
can proceed. Since the counter can only ever increase from this bug, the protocol's sole
arbitration-module rotation path becomes permanently unusable after the very first ordinary
dispute resolved by an unbonded arbitrator — no malice required, just normal usage.
Proof of Concept: A $50 tier-1 dispute opens; arbitrator A (never staked a verifier bond,
verifierBond(A)==0) is mutually seated and calls resolveDispute. In _finalise:
qualifiedResolution=true → count +=3; reputationCallbackPending=false.
_prepareVerifierBondSlash sees bond=0, adds nothing. _trySettleBond succeeds (−1).
_tryRecordReputation returns without decrementing. _tryRegistryCallback succeeds (−1).
pendingSideEffectCount settles at +1, permanently. From this point,
proposeRecovery/executeRecovery revert forever on the pendingSideEffectCount()==0
check — even in a genuine emergency requiring a compromised-module swap.
Recommendation: pendingSideEffectCount += 2 + (reputationCallbackPending[disputeId] ? 1 : 0); — derive the increment from the flag actually armed, not a hard-coded qualifier.

[H-3] TreasuryRouter.flushStakerShare double-decrements accruedFees[usdc] when totalStaked==0, permanently stranding treasury reserve USDC

Severity: High · Confidence: 98 · Origin: [both] — 12 independent agents (phase1: general/precision-math/defi-staking; phase2: 9 of 12 attacker-mindset agents), orchestrator-verified. The single most corroborated finding of this engagement.
Location: TreasuryRouter.sol:256-276 (flushStakerShare), lines 262-267; manifests in withdrawFees() lines 337-350

// TreasuryRouter.sol:262-267
pendingStakerUsdc = 0;
accruedFees[address(usdc)] -= amount;
if (stakingVault.totalStaked() == 0) {
    usdcReserve += amount;
    return;
}

// TreasuryRouter.sol:341-348 (withdrawFees)
if (token == address(usdc)) {
    amount = usdcReserve;
    usdcReserve = 0;
} else {
    amount = accruedFees[token];
}
require(amount > 0, "Treasury: nothing to withdraw");
accruedFees[token] -= amount;

accruedFees[usdc] is decremented unconditionally before the function knows whether funds
actually leave the contract. When totalStaked()==0, the amount is re-bucketed into
usdcReserve — it never leaves — yet accruedFees was already reduced by the same amount.
withdrawFees later subtracts usdcReserve from accruedFees[usdc] a second time for
the same dollars, underflowing and reverting (Solidity ≥0.8 checked arithmetic), permanently
stranding the reserve. flushBuybackShare can underflow instead depending on call order —
either way, amount of real, physically-held USDC becomes unrecoverable via any code path.
Proof of Concept: accruedFees[usdc]=100e6, staking active, totalStaked()==0.
distributeRevenue(): pendingStakerUsdc=40e6, pendingBuybackUsdc=40e6, usdcReserve=20e6
(invariant accruedFees == Σbuckets holds: 100=0+40+40+20). Permissionless
flushStakerShare(): accruedFees[usdc]→60e6; usdcReserve→60e6; returns, no transfer
(contract still physically holds 100e6). Invariant now broken (buckets sum to 100, ledger
says 60). flushBuybackShare(): accruedFees[usdc]→20e6, sends 40e6 out (contract now holds
60e6, matching usdcReserve). withdrawFees(usdc, to): amount=usdcReserve=60e6;
accruedFees[usdc] -= 60e6 → 20e6−60e6 underflows and reverts. The 60e6 USDC reserve —
correctly, physically present — is permanently unwithdrawable.
Recommendation: Only decrement accruedFees[usdc] on the branch that actually transfers
USDC out — move the decrement below the totalStaked()==0 early-return.

[H-4] allActiveDisputesPastDeadline() scans every dispute ever opened — unbounded gas growth eventually bricks the recovery coordinator

Severity: High (long-horizon — see caveat) · Confidence: 90 · Origin: [phase1: general (Low) + dos (High, authoritative)]
Location: ArbitrationModule.sol:282-293; consumed by ArbitrationRecoveryCoordinator._validateSafeOutgoing (lines 190-195), called from both proposeRecovery and executeRecovery

// ArbitrationModule.sol:282-293
function allActiveDisputesPastDeadline() external view returns (bool) {
    for (uint256 id = 1; id <= disputeCount; id++) {
        Dispute storage d = disputes[id];
        if (
            (d.state == DisputeState.OPEN || d.state == DisputeState.EVIDENCE) &&
            block.timestamp <= d.absoluteDeadline
        ) {
            return false;
        }
    }
    return true;
}

Loops over every dispute ever created — never pruned — despite a correctly-maintained
activeDisputeCount existing and being ignored here. This view is called on-chain inside
the state-changing proposeRecovery/executeRecovery, the sole arbitration-module rotation
path. The return true (recovery-enabling) branch has no early exit and always costs
O(disputeCount) gas. As disputeCount grows over the protocol's life, this eventually
exceeds the block gas limit, permanently disabling recovery — exactly when a compromised or
buggy module most needs to be swapped out.
Caveat on severity/timeline: this requires disputeCount to reach the tens of thousands
before gas cost becomes prohibitive at typical Base gas limits — not an immediate risk, but a
structural one that worsens monotonically and can never self-heal.
Proof of Concept: At ~14k lifetime disputes, the scan alone costs roughly 14,000 × ~2,100
gas ≈ 29M gas, on top of the other validation calls and four cross-contract calls in the same
transaction — eventually exceeding usable per-transaction gas.
Recommendation: Maintain an EnumerableSet of active dispute IDs (added at openDispute,
removed at resolution/timeout) and iterate only that set — bounds cost by concurrently-open
disputes (already small and self-limiting via recoveryLockdown/disputeOpeningPaused), not
lifetime count.

[M-1] Reputation recording and the verifier-bond slash deterrent are both gated on verifierBond > 0 — bondless arbitrators rule with zero economic consequence

Severity: Medium · Confidence: 92 · Origin: [both] — phase1 (general, Low) + phase2 (6+ agents, component of P2-4). Same root cause as H-2, distinct impact — the same fix line resolves both.
Location: ArbitrationModule.sol:599-600 (reputationCallbackPending condition), _prepareVerifierBondSlash (bond/10, no-op when bond==0), proposeArbitrator (no verifier-bond requirement at seating)
Description: Two compounding effects: (1) an arbitrator who resolves qualified disputes correctly but never staked a verifier bond gets resolvedCount incremented but no arbitratorReputation — they can never reach tier-2 (reputation≥200 && resolvedCount≥5) regardless of volume. (2) The stated 10% slash deterrent against a bribed/biased ruling computes verifierBond/10 and no-ops at bond==0. Since no seating path requires a bond, an arbitrator can rule workerBps=0 or 10000 (100% to one side) at zero economic cost simply by never staking.
Proof of Concept: Bootstrap-qualified arbitrator A (no bond) resolves 5 qualified disputes; resolvedCount[A]=5, arbitratorReputation[A]=0, permanently tier-1-locked. Separately, arbitrator B (no bond) colludes with one party and rules 100% in their favor; slash computes to 0; no reputation penalty possible since B had none.
Recommendation: Decouple reputation recording from verifierBond>0 (record for every qualifiedResolution; see H-2's fix). Require a minimum verifier bond at seating time so the slash deterrent is never economically vacuous.

[M-2] Verifier bond is locked only at final arbitrator assignment — a candidate can unstake before being seated, evading a subsequent slash

Severity: Medium · Confidence: 85 · Origin: [both] — phase1 (defi-staking, STAKE-2) + phase2 (2 corroborating leads)
Location: ReputationRegistry.lockVerifierBond()/unstakeVerifierBond(), ArbitrationModule.proposeArbitrator (lock call site on dual-consent only)
Description: lockVerifierBond — whose own comment states it exists to prevent front-running a ruling slash by unstaking — is invoked only at final assignment (second party's consent), not at first proposal. During the single-consent window, unstakeVerifierBond is gated only by the standard 7-day stake cooldown, the normal state for any established arbitrator.
Proof of Concept: Established arbitrator X (cooldown elapsed) is proposed by one party; before the second consent lands, X unstakes the full bond; assignment locks $0; X rules favoring a colluding party with zero slash.
Recommendation: Lock the bond at first consent/proposal, not only at final assignment.

[M-3] Recovery coordinator lets a compromised owner install an arbitrary arbitration authority that can reassign live escrows and drain verifier bonds

Severity: Medium · Confidence: 85 · Origin: [phase1: access-control, AC-1]
Location: ArbitrationRecoveryCoordinator.executeRecovery()/_validateReplacement()
Description: _validateReplacement only checks the replacement's four view getters point back at canonical addresses plus disputeOpeningPaused()==true — trivially satisfiable by any contract the owner deploys. Once installed via the standard propose→2-day-delay→execute flow, the new module holds onlyArbitration authority over EscrowVault.freeze/split/refund and AgentDepositVault bond functions, plus ReputationRegistry.slashVerifierBond/resetSubject — sufficient to freeze then reassign any live task's escrow and drain every verifier's bond.
Proof of Concept: Owner (or a compromised multisig key) deploys Evil satisfying the graph checks; standard recovery flow swaps the module; Evil then calls escrow.freeze/split on any funded task and reputation.resetSubject on every verifier.
Recommendation: Constrain replacement beyond graph-shape checks (implementation allowlist/hash); extend the delay materially; bound per-call slash size in ReputationRegistry itself, independent of caller discretion.

[M-4] _validateSafeOutgoing checks "past deadline" not "resolved" — an abandoned dispute's escrow can be orphaned by a module swap

Severity: Medium · Confidence: 80 · Origin: [phase2: 3 leads]
Location: ArbitrationRecoveryCoordinator._validateSafeOutgoing, ArbitrationModule.allActiveDisputesPastDeadline()
Description: The safety check requires every open dispute to be past its absoluteDeadline, not that it's been finalized — resolveTimedOut is permissionless but nothing forces it to run before recovery executes. If an abandoned past-deadline dispute exists at execute time, its FROZEN escrow is orphaned: the old module's resolveTimedOut reverts post-swap (onlyArbitration no longer matches) and the new module has no record of it.
Proof of Concept: A dispute goes unresolved past its 21-day deadline (nobody happens to crank resolveTimedOut); recovery executes anyway; the escrow is permanently unsettleable by any code path.
Recommendation: Require activeDisputeCount()==0 (not merely "past deadline") in _validateSafeOutgoing, or force-crank lingering disputes as part of the recovery precondition.

[M-5] UnionStakingVault.unstake has no defer/alternate-recipient path for AZL — a blocked staker's principal is unrecoverable

Severity: Medium · Confidence: 88 · Origin: [phase1: general + erc20, GEN-5/ERC20-1]
Location: UnionStakingVault.unstake() (push via azlToken.safeTransfer(msg.sender, amount))
Description: The only value-return path in the entire protocol with no defer-to-pending fallback and no alternate-recipient variant — every other exit path (AgentDepositVault, EscrowVault, and the sibling claimRewardsTo) has one. If AZL is or becomes pausable/blacklist-capable for a given staker, principal is permanently frozen.
Recommendation: Add unstakeTo(recipient, amount) and/or route through a defer pattern mirroring _payOrDefer.
