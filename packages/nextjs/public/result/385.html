[92] 1. StepVesting.transferVesting recomputes the grantor's releaseRate with the wrong formula, letting a claimant over-claim from the shared token pool

SecondSwap_StepVesting.transferVesting() · confrmed independently by 9 of 18 hunting agents across both phases (general-1, precision-math-1, and 7 of 12 pashov agents) · Confidence: 92

Description

At contracts/SecondSwap_StepVesting.sol:230:

grantorVesting.totalAmount -= _amount;
grantorVesting.releaseRate = grantorVesting.totalAmount / numOfSteps;

This recomputes the grantor's per-step release by dividing the entire remaining totalAmount
by the entire numOfSteps — ignoring how many steps/tokens the grantor has already claimed.
The correct remaining-linear formula, used correctly elsewhere in the very same contract's
_createVesting additive branch (contracts/SecondSwap_StepVesting.sol:297-303), is
(totalAmount - amountClaimed) / (numOfSteps - stepsClaimed). Because claimable()'s non-final
branch (contracts/SecondSwap_StepVesting.sol:184, claimableAmount = vesting.releaseRate * claimableSteps) applies no cap against the true remainder totalAmount - amountClaimed (only
the final-step branch at lines 178-181 reconciles), an inflated releaseRate lets the grantor's
amountClaimed climb past totalAmount, paying out real ERC20 tokens that back other
beneficiaries' allocations and the marketplace's escrowed purchases. This is triggered by
completely ordinary usage: any long-term holder who claims some vested steps and later lists part
of their remaining allocation on the marketplace hits this path.

Proof of Concept

numOfSteps = 10, grant totalAmount = 1000 (releaseRate = 100).

  1. At step 5, beneficiary calls claim(): stepsClaimed = 5, amountClaimed = 500. True
    remaining entitlement = 500.
  2. Beneficiary lists 200 on the marketplace → Marketplace.listVesting → VestingManager.listVesting
    → StepVesting.transferVesting(seller, manager, 200). The require at line 224
    (totalAmount - amountClaimed >= amount → 1000-500=500 >= 200) passes. totalAmount becomes
    800. Line 230 sets releaseRate = 800/10 = 80. The correct value would be
    (800-500)/(10-5) = 60.
  3. At steps 6-9, claim() is called each step: non-final branch pays releaseRate * 1 = 80 each
    time (lines 184, no cap). After 4 such claims: amountClaimed = 500 + 4*80 = 820, exceeding
    totalAmount = 800 by 20 tokens — tokens drawn from StepVesting's shared ERC20 balance
    that back the 200 tokens escrowed for the buyer via VestingManager.
  4. At step 10 (the final step), the reconciliation branch computes totalAmount - amountClaimed = 800 - 820, which underflows and reverts — but the 20-token surplus was already extracted in
    step 3, and the beneficiary simply stops claiming before the revert.

The magnitude scales with how much is listed relative to what's already been claimed — larger
listed fractions after partial claims produce proportionally larger drains, up to the point where
the shared pool cannot cover the last legitimate claimant's safeTransfer, causing a permanent DoS
for that party.

Fix

- grantorVesting.releaseRate = grantorVesting.totalAmount / numOfSteps;
+ grantorVesting.releaseRate = (numOfSteps - grantorVesting.stepsClaimed) == 0
+     ? 0
+     : (grantorVesting.totalAmount - grantorVesting.amountClaimed) / (numOfSteps - grantorVesting.stepsClaimed);

As defense-in-depth, also cap the non-final branch of claimable():

- claimableAmount = vesting.releaseRate * claimableSteps;
+ claimableAmount = Math.min(vesting.releaseRate * claimableSteps, vesting.totalAmount - vesting.amountClaimed);

[80] 2. Private-listing whitelist is permissionless self-enrollment — defeats the access gate and enables slot-exhaustion griefing

SecondSwap_Whitelist.whitelistAddress() · corroborated by 3 Phase-1 domains (general-2,
access-control-2, dos-4) and 3 independent Phase-2 agents (access-control, execution-trace,
periphery) · Confidence: 88

Description

contracts/SecondSwap_Whitelist.sol:57-64:

function whitelistAddress() external {
    require(totalWhitelist < maxWhitelist, "SS_Whitelist: Reached whitelist limit");
    require(userSettings[msg.sender] == false, "SS_Whitelist: User is whitelisted");
    userSettings[msg.sender] = true;
    totalWhitelist++;
    emit WhitelistedAddress(totalWhitelist, msg.sender);
}

Enrollment is fully permissionless — any address may self-enroll, bounded only by a headcount cap.
lotOwner (the seller, contracts/SecondSwap_Whitelist.sol:21,47-50) has no function to add or
remove a specific address; setMaxWhitelist (line 83) can only raise the cap, never curate
membership. Since listings[plan][id].whitelist is public and WhitelistCreated is emitted
(contracts/SecondSwap_Marketplace.sol:301-303), the whitelist contract address is discoverable by
anyone. A "private" listing therefore restricts headcount, not identity — two consequences:
(a) any address can self-enroll and buy a listing meant for a curated counterparty; (b) an attacker
can fill every slot with throwaway addresses before the intended buyers act, permanently locking
them out (no un-enroll path exists).

Proof of Concept

Seller creates a private listing with _maxWhitelist = 3, intending to sell only to 3 named
partners off-chain. An unrelated address reads the WhitelistCreated event, calls
whitelistAddress() on the deployed whitelist, and immediately calls spotPurchase — succeeding,
despite never being invited. Separately: an attacker enrolls 3 throwaway addresses first;
totalWhitelist == maxWhitelist; the 3 intended partners' own whitelistAddress() calls now revert
with "Reached whitelist limit," and the seller's only recourse (setMaxWhitelist) merely invites
the attacker to refill the new slots.

Fix

- function whitelistAddress() external {
-     require(totalWhitelist < maxWhitelist, "SS_Whitelist: Reached whitelist limit");
-     require(userSettings[msg.sender] == false, "SS_Whitelist: User is whitelisted");
-     userSettings[msg.sender] = true;
-     totalWhitelist++;
-     emit WhitelistedAddress(totalWhitelist, msg.sender);
- }
+ function addToWhitelist(address[] calldata users) external {
+     require(msg.sender == lotOwner, "SS_Whitelist: not lot owner");
+     for (uint256 i = 0; i < users.length; i++) {
+         require(totalWhitelist < maxWhitelist, "SS_Whitelist: Reached whitelist limit");
+         if (!userSettings[users[i]]) {
+             userSettings[users[i]] = true;
+             totalWhitelist++;
+             emit WhitelistedAddress(totalWhitelist, users[i]);
+         }
+     }
+ }

(Add a symmetric removeFromWhitelist if partial revocation is desired.)

[78] 3. VestingManager.listVesting's maxSellPercent anti-dump cap is bypassable via self-purchase (wash trade)

SecondSwap_VestingManager.listVesting() / SecondSwap_Marketplace.spotPurchase() · found by 1
Phase-2 agent (trust-gap) as a FINDING, corroborated by a second (invariant) as an independently
raised LEAD ("maxsellpercent-bypass-via-buyback") · not surfaced by any Phase-1 domain; verified
against source directly in this reconciliation pass · Confidence: 78

Description

_validatePurchase (contracts/SecondSwap_Marketplace.sol:387-404) never checks that
msg.sender != listing.seller — a seller can buy their own listing. VestingManager.listVesting
(contracts/SecondSwap_VestingManager.sol:121-140) derives the sell ceiling from a mutable
currentAlloc = SecondSwap_Vesting(plan).total(seller) combined with the mutable sold/bought
counters:

uint256 sellLimit = userAllocation.bought;
uint256 currentAlloc = SecondSwap_Vesting(plan).total(seller);
if (currentAlloc + userAllocation.sold > userAllocation.bought) {
    sellLimit += ((currentAlloc + userAllocation.sold - userAllocation.bought) * vestingSettings[plan].maxSellPercent) / BASE;
}

When a seller buys back their own listing via spotPurchase, completePurchase
(contracts/SecondSwap_VestingManager.sol:161-164) increments allocations[buyer].bought and
StepVesting.transferVesting restores the buyer's (=seller's) total() — i.e. currentAlloc is
restored to its pre-listing value while bought permanently increases by the same amount. The
term (currentAlloc + sold - bought) is invariant under a self-purchase cycle (the +currentAlloc
and +bought changes cancel), so each round-trip grows the sell ceiling by another
maxSellPercent slice of the original grant — at the cost of only the buyer/seller fee, paid to
feeCollector. Repeating this cycle lets a seller convert their entire capped, "original
allocation" (default-capped at 20%) into fully resellable liquidity, defeating the documented
anti-dump invariant that sold may never exceed bought + maxSellPercent% of the original grant.

Proof of Concept

Grant = 1000, maxSellPercent = 2000 (20% default), bought = sold = 0.

  1. List 200: currentAlloc(1000)+sold(0) > bought(0) → sellLimit = (1000+0-0)*2000/10000 = 200;
    sold: 0→200 ≤ 200 OK. total(seller) drops to 800 (StepVesting escrow transfer).
  2. Seller calls spotPurchase on their own listing (no guard prevents buyer == seller).
    completePurchase: bought: 0→200; StepVesting.transferVesting(manager, seller, 200) restores
    total(seller) 800→1000 (additive branch in _createVesting).
  3. List another 200: currentAlloc(1000)+sold(200) > bought(200) → sellLimit = 200 + (1000+200-200)*2000/10000 = 200+200 = 400; sold: 200→400 ≤ 400 OK.
  4. Repeat: each cycle raises the ceiling by another 200 (20% of the original 1000), converging
    toward sold = 1000 — the seller has fully liquidated a position the protocol intended to cap
    at 20% at any given time, at the cost of only cumulative marketplace fees.

Fix

+ require(msg.sender != listing.seller, "SS_Marketplace: cannot purchase own listing");

in _validatePurchase (contracts/SecondSwap_Marketplace.sol:387). This closes the bypass because
it is specifically the same address acting as both the escrow-restoring buyer and the
bought-crediting recipient that makes the (currentAlloc + sold - bought) term cancel.
Alternatively, derive the "original grant" slice from an immutable snapshot taken at grant time
rather than the mutable total().

[72] 4. Referral reward is computed and emitted but never paid — fee silently retained by feeCollector

SecondSwap_Marketplace._handleTransfers() · corroborated by 1 Phase-1 domain (general-3) and 1
Phase-2 agent as a FINDING (economic-security) plus a second as a LEAD (execution-trace) ·
Confidence: 72

Description

contracts/SecondSwap_Marketplace.sol:478-491:

referralFeeCost = 0;
if (_referral != address(0) && listing.whitelist == address(0)) {
    referralFeeCost = buyerFeeTotal - (baseAmount * bfee * IMarketplaceSetting(marketplaceSetting).referralFee()) / (BASE * BASE);
}

[68] 5. Global isFreeze pause blocks the seller's unlistVesting exit path, stranding escrowed vesting

SecondSwap_Marketplace.unlistVesting() · Phase 1 only (dos-1); re-examined directly against
source in this reconciliation pass (coverage-gate hole) · Confidence: 68

Description

Once a seller lists (contracts/SecondSwap_Marketplace.sol:339 unlistVesting is the only way
back), their vesting balance has already moved out of their own StepVesting entry into

  2. s2Admin calls setMarketplaceStatus(true).
  3. Seller calls unlistVesting → reverts on isFreeze ("Marketplace is currently frozen").
  4. The seller has no alternative recovery path; the 1,000 tokens remain locked in the manager's
    escrow for as long as the freeze is active, entirely at the admin's discretion.

- function unlistVesting(address _vestingPlan, uint256 _listingId) external isFreeze {
+ function unlistVesting(address _vestingPlan, uint256 _listingId) external {

Remove the pause from the exit/withdraw path (or add a permissionless emergency-unlist that
functions while frozen), so a pause can halt new trading without also locking already-escrowed
user assets.

[65] 6. Arbitrary currency and vesting tokens are trusted as exact-accounting, non-blocking ERC20s — fee-on-transfer, rebasing, and blocklist tokens break accounting or DoS the market

Cluster: SecondSwap_Marketplace.addCoin()/_handleTransfers()/unlistVesting(),
SecondSwap_StepVesting._createVesting()/claim() · corroborated across 4 Phase-1 domains
(general-4/5, erc20-1/2/3/4/7, dos-2/3/6/7) and 2 Phase-2 agents (economic-security, trust-gap) ·
Confidence: 65 (grouped — see sub-points for individual mechanisms)

Description

addCoin's decimals/behavior vetting is fully commented out
(contracts/SecondSwap_Marketplace.sol:208-217), so any token an admin adds as currency is
trusted unconditionally; the vesting token is likewise arbitrary, chosen by the token owner at
VestingDeployer.deployVesting. Neither leg tolerates non-standard ERC20 behavior:

  • Fee-on-transfer / rebasing vesting token (contracts/SecondSwap_StepVesting.sol:307,
    _createVesting books _totalAmount but pulls via safeTransferFrom with no balance-delta
    check) — under-funds the contract relative to booked allocations; later claimants'
    safeTransfer (line 201) reverts for insufficient balance (permanent claim DoS for the
    shortfall).
  • Fee-on-transfer / blocklisting currency (contracts/SecondSwap_Marketplace.sol:476-492) —
    the three sequential transfers (baseAmount+buyerFeeTotal in, baseAmount-sellerFeeTotal to
    seller, buyerFeeTotal+sellerFeeTotal to feeCollector) assume exact receipt; a fee-on-transfer
    currency makes the final leg revert (purchase DoS for that currency); a blocklisting currency
    (USDT-style) DoSes purchase for any listing whose seller — or the single global feeCollector —
    is blocklisted.
  • Zero-fee-transfer revert (contracts/SecondSwap_Marketplace.sol:488-491) — when both
    buyer/seller fees are 0 (allowed, no lower bound), safeTransfer(feeCollector, 0) reverts on
    tokens that revert on zero-value transfers.
  • Penalty-fee path (contracts/SecondSwap_Marketplace.sol:349-360) — the flat usdt penalty
    transfer is independently exposed to the same blocklist/pause risk, blocking early unlist (bounded
    impact: seller can wait out minListingDuration or ask admin).
  • Unguarded decimals() at purchase time (contracts/SecondSwap_Marketplace.sol:465-468) —
    listVesting gates vesting-token existence of decimals() via doesFunctionExist
    (line 264-274, a staticcall-based existence check whose return data is discarded), but
    _handleTransfers calls .decimals() directly with no such guard, so a token that later reverts
    on decimals() bricks purchases of an already-created listing.

Proof of Concept (representative — fee-on-transfer currency)

Admin adds a 1%-fee-on-transfer token via addCoin. Buyer approves and calls spotPurchase;
safeTransferFrom at line 476 delivers 0.99 * (baseAmount+buyerFeeTotal) to the marketplace; the
contract then attempts to pay out baseAmount+buyerFeeTotal split across the seller and
feeCollector legs — the final safeTransfer reverts for insufficient balance, and every purchase
in that currency permanently fails.

Fix

Re-enable and extend the addCoin vetting (decimals bound, and ideally a standard-behavior
allowlist); measure actual received amounts via balance-before/after in both _createVesting
(vesting token) and _handleTransfers (currency token) rather than trusting the requested amount;
guard the feeCollectorTotal transfer with if (feeCollectorTotal > 0); cache vesting-token
decimals at list time instead of re-reading at purchase time.

    MarketplaceSetting.setS2Admin() L232-235 (both checks). A zero/typo'd admin permanently bricks

    both, and consider a two-step transfer pattern given the one-step, no-timelock design across all
    three admin roles.
  • setTokenOwner is one-shot and irrevocable — VestingDeployer.setTokenOwner() L141-144 —
    no way to correct or revoke a wrong owner→token binding once set; a compromised or mistaken
    owner key can never be de-privileged by the admin. Also a NatSpec/code direction mismatch
    (comment says token→owner, code maps owner→token).
  • Shared manager escrow entry desyncs stepsClaimed across sellers → buyers —
    VestingManager.listVesting/completePurchase → StepVesting._createVesting — all sellers of
    one plan escrow into a single _vestings[manager] entry; its stepsClaimed is fixed by the
    first lister and never updated by later listers, so buyers inherit a stepsClaimed unrelated
    to the seller they actually bought from. Multiple Phase-2 agents traced this and confirmed it
    does not break the total-claim cap (timing/fairness distortion only, not fund loss) — hence a
    lead, not a finding.
  • _createVesting fresh-entry branch and StepVesting constructor lack zero-denominator
    guards present elsewhere     — _createVesting() L292 has no guard on numOfSteps - _stepsClaimed == 0 (the additive branch at L297 does); stepDuration = (endTime-startTime) / numOfSteps (constructor L133) can truncate to 0 if numOfSteps > (endTime-startTime) with no
    validation in deployVesting, bricking every claimable() call for that plan. Both are
    configuration-triggered DoS paths, not currently reachable through an unprivileged attack in the
    cases traced; recommend adding the missing guards and a steps <= endTime-startTime check.
  • Discount/rounding edge cases — _getDiscountedPrice() L417-419 divides before multiplying
    in the LINEAR branch (silently zeroing small-buy discounts) and listVesting never bounds
    _discountPct <= BASE (a FIX listing with discountPct > 10000 reverts every purchase,
    self-DoS only); baseAmount/fee division rounds down with no lower-bound enforcement, so very
    small purchases can round trade fees to zero. All self-limiting or dust-scale; recommend
    require(_discountPct <= BASE) and Math.ceilDiv for fee rounding as hardening.
  • No reentrancy guard; currency transfers precede listing.balance/status update in
    spotPurchase     — _handleTransfers() L476-492 vs spotPurchase() L530-531 — every Phase-2
    agent that traced this confirmed Solidity 0.8's checked arithmetic on the balance decrement
    currently blocks a net-profitable reentrant drain via a hook-bearing (ERC777-style) currency; the
    ordering is nonetheless fragile and should not be relied upon. Recommend an explicit
    nonReentrant guard and CEI-ordering the state update before external calls.
  • Unbounded batch loops — StepVesting.createVestings() L260-267,
    VestingDeployer.createVestings() L193-206 (redundant second loop purely for events) — caller
    self-DoS on an oversized array (trusted-caller-only, mitigable by chunking).
  • Informational — WhitelistDeployer.deployWhitelist() is fully permissionless but inert
    unless referenced by a real listing; hardhat/console.sol imported in production contracts;
    unused Ownable imports in VestingManager/Whitelist; referralFeeCollector
    (MarketplaceSetting L69) declared, never assigned or read.
