Findings

[90] 1. Proceeds and platform fee can be pulled to the treasury/fee recipient with no check that purchased tokens remain deliverable — and no refund path exists after finalization

B20FixedSaleV1.finalize / claimProceeds / claimFee / claim / refund · Confidence: 90 · [both] — independently found by phase-1 dos agent (DoS-1, Low) and 5 of 12 phase-2 attack agents (math-precision, first-principles as a full FINDING, numerical-gap, trust-gap, flow-gap); promoted to High here given the corroboration depth, two independent full numeric traces, and the second (receiver-policy) trigger phase-1 didn't have.

Description
On the existing-token sale-creation path (RwagmiRaiseFactory.createFixedSale), the sale only snapshots IB20Minimal(token).multiplier() == WAD once, at construction (B20FixedSaleV1.flat.sol:1544), and never reads the token's transfer-pause or transfer-receiver-policy state at all. finalize() (B20FixedSaleV1.flat.sol:1757-1766) and claimProceeds()/claimFee() (:1771-1790) contain no deliverability check — they release quote to the immutable treasury/feeRecipient unconditionally once the sale is Successful. claim() (:1808-1824) is the only value-moving exit that re-checks _requireUnrebased() (:1810, guard defined at :1873), reverting MultiplierDrift if the token's rebase multiplier has since moved off WAD; the same safeTransfer (:1818 or :1820) is also subject to the token's own pause/receiver-policy logic, which the sale never inspects. refund() (:1793-1803) is gated state() ∈ {Failed, Cancelled} — unreachable once a sale is Finalized, because state()'s priority ordering returns Finalized first (confirmed structurally by 3 independent agents). Net effect: if the issuer supplies an existing B20 Asset whose rebase controller, pause switch, or receiver-policy admin is still live (a documented, supported configuration — the client's own concern doc for B20FixedSaleV1 explicitly discusses the existing-token path), a legitimate post-sale token-state change permanently strands every unclaimed contributor with neither tokens nor a refund, while the treasury and fee recipient have already been paid in full.

Concrete trace (from the phase-2 first-principles agent, independently reproduced by flow-gap): price = 1e6 quote-units/token, tokenDecimals = 18, one contributor pays 1,000 USDC; sale reaches softCap, finalize() runs, claimProceeds() sends ≈950 USDC to treasury. The token's controller then performs a routine rebase to multiplier = 1.01e18. claim(contributor) now reverts MultiplierDrift() permanently; refund(contributor) reverts SaleNotRefundable() because state() is Finalized. The contributor's 1,000 USDC is gone and their tokens are unrecoverable.

Fix

 function finalize() external nonReentrant {
     if (finalized) revert AlreadyFinalized();
     if (state() != SaleState.Successful) revert SaleNotSuccessful();
+    _requireUnrebased();
     finalized = true;
     ...
 }

This closes the rebase-drift trigger by refusing to start the one-way settlement while delivery is already broken. The receiver-policy/pause trigger cannot be fully closed with a single check (a token can be paused after finalize() succeeds); consider additionally exposing a permissionless "claim-failed → refund" path for a Finalized sale where a specific beneficiary's claim() has reverted, drawing from any still-unclaimed proceedsClaimable, so proceeds cannot be fully extracted while a beneficiary's allocation is provably undeliverable.

[85] 2. A sub-token-price residual at the hard cap can permanently strand an all-or-nothing (softCap == hardCap) sale into Failed

B20FixedSaleV1._checkAndClamp / _recordContribution · Confidence: 85 · [phase2, agents: 2 FINDING + 4 corroborating LEADs] — independently found with concrete numeric proofs by the math-precision and numerical-gap-hunter agents; the same fragility (the hard-cap tail is structurally hard to fill) was independently flagged from a different angle (a fresh wallet blocked by minContribution, not by mulDiv flooring) by the invariant, first-principles, boundary, and trust-gap agents.

Description
_checkAndClamp (B20FixedSaleV1.flat.sol:1669-1690) clamps an incoming contribution to capacity = hardCap - totalRaised (:1679-1682), i.e. once anyone's contribution leaves a small enough remaining capacity, every subsequent contributor is force-clamped to exactly that residual — they have no freedom to contribute a different amount. _recordContribution (:1693-1706) then computes owed = Math.mulDiv(accepted, 10**tokenDecimals, price) (:1696) and reverts ZeroTokenEntitlement() (:1699) if that floors to zero. If the residual capacity is smaller than price / 10**tokenDecimals quote-units, owed floors to 0 for every possible contributor (not just new ones — accepted is forced to exactly capacity), and the hard cap can never be reached. For a softCap == hardCap sale (a fully supported configuration — the sale constructor only requires softCap <= hardCap), the sale rides to endTime and settles Failed, refunding everyone.

Proof: token decimals = 6, price = 2e9 (2e9 quote units per whole token) ⇒ owed = accepted / 2000. Let hardCap = softCap = H. A contribution landing totalRaised at H - 1999 leaves capacity = 1999. Every later contributor is clamped to accepted = 1999, giving owed = floor(1999/2000) = 0 ⇒ revert. No amount can add the final 1999 units — a smaller amount only leaves an even smaller, still-unfillable residual. totalRaised is pinned below hardCap forever; at endTime, H - 1999 < softCap(H) ⇒ the sale settles Failed. This is reachable by any ordinary contributor (deliberately, as an attacker, or by simple bad luck in contribution sizing) and requires no privileged action.

Fix

 function state() public view returns (SaleState) {
     if (finalized) return SaleState.Finalized;
     if (cancelled) return SaleState.Cancelled;
     if (!funded || block.timestamp < startTime) return SaleState.Pending;
-    if (totalRaised >= hardCap) return SaleState.Successful;
+    if (totalRaised >= hardCap) return SaleState.Successful;
+    // Treat a residual too small to mint even one token base-unit as cap-reached.
+    if ((hardCap - totalRaised) * (10 ** tokenDecimals) < price) return SaleState.Successful;
     if (block.timestamp < endTime) return SaleState.Live;
     return totalRaised >= softCap ? SaleState.Successful : SaleState.Failed;
 }

(Exact placement/gas cost of the extra multiplication should be reviewed; the intent is that an unfillable residual counts as "cap reached," not "cap unreached forever.")

A related, distinct mechanism at the same two functions: when remaining capacity is below minContribution but still large enough to mint ≥1 token, a fresh wallet (with contributionOf == 0) is rejected by the cumulative-min check at :1687-1689, while an existing contributor topping up can still fill it — an asymmetry between wallet classes. This is bounded to a liveness/UX nuisance (the sale still settles Successful via the soft-cap/end-time door) rather than the harder Failed-forcing bug above, so it is not separately scored but is folded into the fix consideration.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed, or where reachability/impact was judged insufficient for a scored finding. Not false positives — high-signal leads for manual review.

  • LP vault best-effort fee sweep can bypass the bps split on releasePrincipal — RwagmiSaleLpVault._sweepFees / releasePrincipal (RwagmiSaleLpVault.flat.sol:2390-2399, :2428-2450) — Code smells: the try/catch around positionManager.modifyLiquidities swallows a revert and, in at least one agent's trace, the fee-crediting logic itself sits partly outside what the catch actually guards; on any sweep failure, embedded uncollected fees leave the vault attached to the LP NFTs, going to principalRecipient instead of feeRecipients. 5 of 12 phase-2 agents independently converged on this (economic-security, execution-trace, periphery, asymmetry, flow-gap), matching phase-1's DefiAMM-1 (Low) — but every agent that examined it, across both phases, explicitly could not construct a way for an external party to force the sweep to revert (the vault owns the position; only the trusted, bound seeder ever deposits; the PositionManager is a trusted canonical singleton). Reachability under normal operation is unconfirmed — retained as a lead, not scored, despite the unusually strong convergence.
  • LP vault fee accounting has no rebase guard for pool currencies — RwagmiSaleLpVault.collectFees / claimFees (RwagmiSaleLpVault.flat.sol:2378-2418) — Code smells: unlike the sale/distributor, which re-check multiplier()==WAD on every token-moving path, the vault credits a fixed absolute _claimable[recipient][currency] at collection time and pays from live balance later, with zero rebase awareness. [both] — phase-1 erc20 agent (ERC20-1, Medium) and phase-2 invariant agent independently found this; a downward rebase of a pool currency between collection and claim can strand later recipients' shares (their safeTransfer reverts on insufficient balance), an upward rebase permanently strands the surplus. Depends on the LP-seeding wiring (external to this bundle) actually using a rebasing currency, which could not be confirmed either way.
  • Native ETH / arbitrary ERC-20 sent directly to the LP vault is permanently stranded — RwagmiSaleLpVault.receive (:2489-2497) — self-harm only (a voluntary donor loses their own funds; no cross-party extraction); [both], matches phase-1 DefiAMM-2/3.
  • Contribute-on-behalf refund misdirection — B20FixedSaleV1.contribute / refund — a third-party payer funding another address's beneficiary slot has no refund claim if the sale later fails or is cancelled; matches the documented "callable by anyone for any beneficiary" gift model, not exploitable against an unwilling victim (2 phase-2 agents independently noted this).
  • Eligibility is not re-checked at claim/refund time — B20FixedSaleV1.claim / refund — an address whose PolicyRegistry membership is revoked after contributing can still claim tokens or a refund; re-checking would strand a paid contributor's funds, so this is very likely intended, not a defect.
  • Outbound token transfer to the vesting distributor has no balance-delta check — B20FixedSaleV1.claim (:1820-1821) — asymmetric with the inbound fund/contribute delta guards; closed in practice because fund() already established the specific token transfers standardly before any claim can occur.
  • PolicyRegistry behavior on a deleted/retired policy is undefined in-bundle — B20PolicyGate / B20PolicyValidationHook — whether a since-deleted policyId reverts (bricking contributions/bids) or silently returns true (fail-open) depends on the external Base singleton, not verifiable from this repo.
  • Merkle allocation mode has no uncapped escape or minContribution guarantee — B20FixedSaleV1._allocationWalletCap — a whitelisted beneficiary whose off-chain-assigned allocation is below minContribution is structurally unable to ever contribute; an issuer configuration footgun, not a fund-safety issue.
  • Existing-token path relies on the token's transfer-receiver policy matching the sale's own eligibility policy, with no enforcement that they align — B20FixedSaleV1.claim — a contributor who passes the sale's own bid-time gate can still fail the token's independent claim-time receiver policy; this is the second (non-rebase) trigger for Finding 1 above and is folded into that finding's fix discussion rather than scored separately.
  • Cosmetic error-selector mismatch — B20VestingDistributor.bindSale reverts NotSale() where the three sibling bind-once functions (bindFactory, bindAuction, bindSeeder) revert NotBinder() — no security impact.
  • High-frequency permissionless collectFees calls can skew bps-split dust toward the last recipient — RwagmiSaleLpVault._distribute — bounded strictly by real per-call fee accrual; dust-level, not a meaningful drain.
  • B20VestingDistributor's NatSpec claims binder is "zeroed afterwards" but it is immutable — cosmetic doc/code mismatch; the one-shot bind guarantee actually comes from the independent sale != address(0) check and holds regardless.
  • Single-step Ownable on RwagmiRaiseFactory, no timelock on config setters — blast radius is limited by design to future sale creation (fee capped at 5% on every path; existing sales are fully immutable and unaffected by owner state) — a governance-hardening suggestion, not a fund-safety finding.

Scope Note

RwagmiSaleLpVault, B20PolicyValidationHook, and RwagmiB20TokenFactoryAdapter form a second trust island ("subsystem B") that is not wired to RwagmiRaiseFactory anywhere in this codebase (confirmed by exhaustive grep across all 8 files). These three contracts are evidently deployed and bound by an external script outside this repository's scope. Their internal logic was fully audited; their correspondence to any specific presale ("Raise") is a deployment-time assumption this codebase provides no on-chain guarantee for.
