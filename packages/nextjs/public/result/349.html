Security Audit Report: Vaultfire VaultfireNameService (VNS)

Target: VaultfireNameService at 0xA9e6c2c0a731F1f56F6720Dfac2eB1440Ab9453a (Base, chain 8453)
In-scope contract: VaultfireNameService.sol (source verified via Sourcify full match; compiler 0.8.25; single self-contained contract, 244 lines, no external calls, no admin functions)
Methodology: Two-phase audit — Phase 1 breadth (4 parallel checklist-driven agents: general, precision-math, access-control, and a dedicated commit-reveal/front-running specialist) → Phase 2 depth (12 parallel attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation (this document).
Reconciliation summary: Overlap: 5 findings independently confirmed by both phases · Phase-1-only: 5 · Phase-2-only: 3 (all re-examined against source and confirmed; two of the three are High-severity findings phase 1 missed entirely) · Demoted on re-examine: 0.
Completeness: every unique (contract, function, bug-class) raised by either phase's raw agent output is represented below.

Summary

This is a small, ENS-style name registry: users register a .vaultfire name via a commit-reveal scheme (documented as an "AUDIT-H1 fix" for front-running), can transfer their name to another address, or release it back to the pool. It has no admin functions, no external calls, and holds no funds — a genuinely minimal-risk-surface contract on its face.

Despite this, the two-phase methodology surfaced two significant findings that neither phase's dedicated specialists caught on their first pass. Phase 1 assigned a dedicated agent specifically to interrogate the commit-reveal scheme's front-running resistance, and a separate dedicated agent specifically to "ownership transfer authorization" per the client's stated focus — both concluded the relevant mechanisms were sound. Phase 2's independent, blind attacker-mindset agents found that both conclusions were incomplete: (1) transferName has no consent mechanism at all for the recipient, letting any name-holder force-assign a name onto an arbitrary, unconsenting address — found independently by 6 of 12 phase-2 agents, and (2) the commit-reveal scheme correctly defeats a reactive front-runner but has no defense against a patient one who pre-stages matured commitments for desirable names in advance — a realistic, real-world squatting-bot threat model that neither phase-1's specialist nor 11 of 12 phase-2 agents considered, caught by exactly one agent and independently re-verified against source by the orchestrator. Both are now confirmed, High-severity findings.

High Severity

[H-1] transferName has no recipient-consent mechanism — any name-holder can force-assign a name onto an arbitrary, unconsenting address

Origin: [phase2 only] — 6/12 agents independently reached this as an explicit FINDING (trust-gap, periphery, math-precision, invariant, asymmetry, flow-gap), despite phase 1 running a dedicated agent specifically tasked with reviewing "ownership transfer authorization" that did not catch it — re-examined against source and confirmed
Location: transferName (149-166)

function transferName(address newOwner) external {
    require(_hasName[msg.sender], "No name to transfer");
    require(newOwner != address(0), "Cannot transfer to zero address");
    require(newOwner != msg.sender, "Cannot transfer to self");
    require(!_hasName[newOwner], "New owner already has a name");
    ...
    _reverseNames[newOwner] = name;
    _hasName[newOwner] = true;
    ...
}

All four checks reference only the sender's state and the recipient's default (empty) state — none require any action, signature, or acceptance from newOwner. This is a fundamental asymmetry with registerName, which cryptographically requires the recipient themselves to have committed and revealed a matching secret (true self-authorization). transferName lets a completely unrelated third party unilaterally flip the same _hasName flag for an address that never took any action.

Proof of Concept: Attacker registers any cheap throwaway name for themselves via the normal, legitimate commit-reveal flow (gas-only cost), then calls transferName(victim) for any address that has never interacted with the contract — the overwhelming majority of all addresses. Every check passes trivially. After the call: _hasName[victim] = true, _reverseNames[victim] = <attacker's chosen name>, _names[nameHash].owner = victim — none of which the victim authorized. Consequences:

  1. Victim's own future registerName calls now revert on require(!_hasName[msg.sender], "Address already has a name") until they notice and spend an extra transaction on releaseName().
  2. This can be timed to specifically front-run a victim's own pending registerName reveal (visible in plaintext in the mempool), forcing that specific transaction to revert.
  3. resolveAddressToName(victim) — a public, trusted-looking reverse-resolution API — now reports an attacker-chosen string as the victim's registered identity. Since the character set (a-z0-9-) still permits arbitrary words, this is weaponizable for reputational spoofing/defamation against any address, including protocol treasuries or well-known contracts that never opted into having any name at all.

Repeatable indefinitely against unlimited targets at near-zero cost, since registration itself is free ("Free to register — users only pay gas" per the contract's own doc comment).

Recommendation: Require recipient consent via a two-step pattern: transferName records a pending transfer, and a separate acceptTransfer() call from newOwner (itself checking !_hasName[newOwner] at accept time) completes it.

[H-2] Commit-reveal front-running protection defends against a reactive attacker but not a patient one who pre-stages matured commitments for desirable names in advance

Origin: [phase2 only] — found by exactly 1 of 12 agents (flow-gap); this directly qualifies phase 1's explicit "scheme HOLDS" conclusion from its dedicated commit-reveal specialist agent, and was not raised by any of the other 11 phase-2 agents either — independently re-verified against source by the orchestrator and confirmed
Location: registerName (103-142)

registerName verifies only that the caller's own commitment for (name, msg.sender, secret) is matured (past COMMITMENT_MIN_AGE) and unexpired (within COMMITMENT_MAX_AGE), and that the name is currently unclaimed. Nothing ties registration priority to which commitment for a given name existed first — priority is decided purely by the order in which registerName transactions land on-chain (a public, front-runnable event), not by the order of the (private, hash-opaque) commitName calls.

Proof of Concept: An attacker calls commitName(keccak256(name, attacker, secret)) for any number of desirable candidate names (e.g., every short/dictionary-word string) at any time — entirely speculatively, since the commitment hash reveals nothing about which name it targets. This costs only gas and can be done in parallel for arbitrarily many names, refreshed every ~23 hours to stay within COMMITMENT_MAX_AGE. This is exactly how real-world ENS/domain squatting bots operate. Later, victim Bob independently and correctly follows the documented protocol exactly: commits to "eth", waits the required minimum age, and broadcasts registerName("eth", bobSecret) — plaintext "eth" now sits in the public mempool. The attacker, who has held a matured commitment for "eth" since long before Bob ever acted, simply submits registerName("eth", attackerSecret) with competitive gas. Every check on the attacker's transaction passes (their commitment matured long ago, well within its 24h window). The attacker's transaction can land first and claim "eth"; Bob's identical-looking, fully protocol-compliant transaction then reverts on "Name already taken". Bob did everything the documentation instructs and still lost the name to front-running — the exact failure mode the "AUDIT-H1 fix" claims to prevent.

Why the "scheme holds" conclusion from both phase-1's dedicated specialist and 11 of 12 phase-2 agents is correct but incomplete: every one of those analyses considered only a reactive attacker — one who first learns of a target name by observing a victim's specific pending transaction, and must then start fresh (commit, wait 60s, reveal), which is correctly and provably too slow to win. None considered a patient attacker who already held a matured commitment for that exact name from an unrelated, earlier point in time. Since commitments are free, unlimited, and content-opaque, maintaining such a standing inventory for every desirable name is realistic and low-cost — and for any name actually worth contesting (which is precisely the set of names this protection is meant to matter for), this is arguably the primary real-world threat, not an edge case.

Recommendation: Bind registration priority to commit order, not reveal order — e.g., record the first commitment timestamp per name (requires a separate, non-secret-bound name-commitment layer, or a two-layer commit scheme) and reject a reveal if an earlier commitment for the same name exists from a different committer; or require a meaningful, forfeitable stake on commitName so speculative portfolio-squatting carries a real cost.

Medium Severity

[M-1] transferName never refreshes registeredAt, enabling tenure/reputation spoofing

Origin: [phase2 only] — 1/12 agents (invariant), distinct from H-1 — re-examined against source and confirmed
Location: transferName (149-166), registerName (131-135)

registerName sets registeredAt: block.timestamp once, at initial registration; transferName mutates only .owner, never touching .registeredAt. An attacker can register a name, hold it idle for an extended period, then transfer it to a buyer or victim — resolveNameToAddress continues to report the original registration timestamp alongside the new owner, making the name appear to have been held by its current controller far longer than it actually has, exploitable for fake "verified since" social-engineering claims.

Recommendation: Either update registeredAt on transfer to mean "current owner since," or add a separate originalRegisteredAt field so the two concepts (name-existed-since vs. current-owner-since) aren't conflated in one struct field.

Low Severity

[L-1] commitName is not bound to the committer, enabling hash-copy griefing of a victim's commit slot (gas-waste only, no escalation to name theft)

Origin: [both] — Phase 1 (all 4 agents touched on this) · Phase 2 (8/12 agents, near-unanimous, all reaching the identical "gas-waste only" conclusion via independent traces)
Location: commitName (87-91)

commitments[commitment] is keyed purely by the hash value with no binding to who submitted it. Since the raw hash is visible in mempool calldata before confirmation, any observer can front-run a victim's commitName(H) with their own commitName(H) call, forcing the victim's transaction to revert and wasting their gas. Confirmed unanimously across every agent that examined it: the victim's subsequent registerName reveal still succeeds using the attacker-set timestamp, since registerName never checks who wrote the commitment slot, only that a valid one exists. No path to escalate this into name theft or permanent denial was found by any agent.

Recommendation: Bind the commitment slot to its submitter (e.g., a struct storing both timestamp and committer address) so a copied hash from a third party is rejected rather than silently claimed.

[L-2] Expired, never-revealed commitments are never pruned — permanently blocks reuse of the exact same commitment hash

Origin: [both] — Phase 1 (3/4 agents) · Phase 2 (5/12 agents)
Location: commitName (88), registerName (109)

commitments[commitment] is deleted only on successful reveal. An expired (>24h, never revealed) commitment permanently blocks reuse of that exact (name, sender, secret) triple. Confirmed by every agent that examined it to be trivially self-resolved by choosing a new random secret, with no third-party attack vector (an attacker cannot predict a victim's future commitment hash without knowing both their intended name and secret in advance).

Recommendation: Allow re-commit once expired: require(commitments[commitment] == 0 || block.timestamp > commitments[commitment] + COMMITMENT_MAX_AGE, ...).

[L-3] Consecutive hyphens are permitted in names, creating a squatting-adjacent lookalike-name risk

Origin: [phase1 only] (general agent) — re-examined against source and confirmed
Location: character-validation loop, registerName (116-126)

The validation loop only checks character-class membership and that the first/last byte isn't a hyphen — it never checks adjacency to the preceding byte, so "a--b" passes validation and registers as a name fully independent of, and visually confusable with, "a-b"/"ab". Real DNS reserves -- in this position specifically to disambiguate ASCII labels from punycode-encoded IDN labels; this contract has no equivalent restriction, though it does correctly reject all non-ASCII bytes (closing the broader Unicode-homograph class).

Recommendation: Add an adjacency check: require(!(isHyphen && i > 0 && nameBytes[i-1] == 0x2D), "Consecutive hyphens not allowed").

[L-4] Secret reuse across multiple pending commitments creates a post-reveal guessing oracle

Origin: [phase1 only] (commit-reveal specialist) — re-examined against source and confirmed
Description: If a user reuses the same secret across two different pending commitments, the first reveal publishes secret in plaintext on-chain. An attacker can then test guesses for the user's other pending name by checking keccak256(guessed_name2, user, revealed_secret) against the public commitments mapping — degrading secrecy for guessable names, though still not enabling theft since the reveal remains bound to the original user's msg.sender.

Recommendation: Document clearly that a fresh random secret must be used per commitment, never reused across names.

[L-5] transferName has no guard against transferring to the contract's own address; no two-step confirmation

Origin: [phase1 only] (general, access-control agents) — re-examined against source and confirmed
Location: transferName (149-166)

Two related, minor gaps: (a) no check against newOwner == address(this), which would permanently strand a name (self-inflicted, not third-party exploitable); (b) no two-step accept pattern, so a typo'd or uncontrolled recipient address permanently loses the name with no recovery path (partially superseded by H-1's fix, which would also need to address this).

Recommendation: Add require(newOwner != address(this), ...); consider a two-step transfer as part of the H-1 remediation.

Informational

  • Commitment hash lacks block.chainid/address(this) domain separation — not exploitable today given commitments is purely local per-contract storage, but recommended as defense-in-depth hygiene for any future extension (e.g., relayed/meta-transaction commit submission). [phase1 only]
  • keccak256(abi.encodePacked(name, msg.sender, secret)) is collision-safe — confirmed unanimously by all 16 agents across both phases (only one dynamic-length argument, followed by fixed-width address/bytes32, making the encoding provably injective).
  • _hasName/_reverseNames/_names[...].exists triple consistency and the totalNames invariant both hold across every reachable state transition; no desync path found by any agent across either phase.
  • No admin/owner/privileged role exists anywhere — the "fully permissionless" NatSpec claim is verified accurate; permanent name loss on private-key loss is a deliberate, documented design tradeoff, not a bug.
  • No reentrancy surface exists anywhere in the contract (zero external calls).

Methodology Notes

  • Both phases audited the same single in-scope file independently; Phase 2 was run with no visibility into Phase 1's findings to avoid anchoring.
  • This is the clearest demonstration in this audit batch of why the blind two-phase methodology matters. Phase 1 dedicated one full agent specifically to interrogating the commit-reveal scheme's front-running resistance (the client's own stated focus area) and a separate full agent specifically to "ownership transfer authorization" (also client-requested). Both concluded, with detailed and individually correct reasoning for the specific scenarios they tested, that the relevant mechanisms held. Both conclusions were incomplete in ways that only became visible when 12 independent, blind attacker-mindset agents re-approached the same code from different angles — one of which (out of 12) found the pre-staged-commitment squatting bypass, and six of twelve independently found the transferName consent gap. Neither finding was a result of "trying harder" on the same analysis; both required a genuinely different framing of the threat model (patient vs. reactive attacker; third-party-forced state change vs. self-authorized state change) that the first pass's framing didn't surface.
  • Out of scope: no other Vaultfire contracts consume resolveNameToAddress/isAgentRecognized-style name lookups for authorization in this repository; if any downstream Vaultfire contract is ever built to trust this registry's name resolution for access control or identity purposes, both H-1 and H-2 would transitively affect that consumer's security model too.
