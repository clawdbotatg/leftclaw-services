Findings

[Medium-1] lastUpdated is never initialized — the first reward accrual can dump an entire epoch's rewardReserve in one block

Confidence: 85 · CLPool._updateRewardsGrowthGlobal / CLPool.initialize · [both — flagged independently by 8+ phase-1 and phase-2 agents]

lastUpdated (a uint32 state variable, CLPool.sol:100) is never assigned in initialize() (CLPool.sol:148-179) and defaults to 0. It is written nowhere except inside _updateRewardsGrowthGlobal():

function _updateRewardsGrowthGlobal() internal {
    uint32 timestamp = _blockTimestamp();
    uint256 _lastUpdated = lastUpdated;
    uint256 timeDelta = timestamp - _lastUpdated; // skip if second call in same block

    if (timeDelta != 0) {
        if (rewardReserve > 0) {
            uint256 reward = rewardRate * timeDelta;
            if (reward > rewardReserve) reward = rewardReserve;
            rewardReserve -= reward;
            if (stakedLiquidity > 0) {
                rewardGrowthGlobalX128 += FullMath.mulDiv(reward, FixedPoint128.Q128, stakedLiquidity);
            } else {
                rollover += reward;
            }
        }
        lastUpdated = timestamp;
    }
}

(CLPool.sol:934-952)

_updateRewardsGrowthGlobal() is reached only via: stake() — but only when the staked range is currently in-range (CLPool.sol:598-602); swap() — but only on the first crossing of an initialized tick (CLPool.sol:788-791); or the gauge explicitly calling updateRewardsGrowthGlobal(). syncReward() never calls it (see Finding Medium-2).

Concrete trace: pool is cloned + initialize()d → lastUpdated == 0. Gauge sets rewardReserve = R via syncReward() (no staking has happened in-range yet, so _updateRewardsGrowthGlobal has never fired). The first subsequent trigger — a swap crossing an initialized tick, an in-range stake(), or a direct updateRewardsGrowthGlobal() call — computes timeDelta = block.timestamp - 0 ≈ 1.8×10⁹ (current 2026 timestamps). reward = rewardRate * 1.8e9, clamped to rewardReserve = R. The entire epoch's reward budget is consumed in that single call:

  • If stakedLiquidity > 0 at that exact moment, all of R is credited to rewardGrowthGlobalX128 at once — whoever is staked in-range captures a full epoch's emissions instantly instead of over the streamed period, and can unstake immediately after.
  • If stakedLiquidity == 0 at that moment, all of R moves into rollover — where it is then at risk of being silently dropped (see Finding Low-1).

This is not an edge case requiring attacker setup — every pool's first reward-earning event hits lastUpdated == 0 unless the (out-of-scope) gauge happens to call updateRewardsGrowthGlobal() proactively before ever setting rewardReserve > 0, which nothing in this contract enforces or documents.

Fix: initialize lastUpdated = _blockTimestamp() in initialize().

 slot0 = Slot0({...});
+lastUpdated = _blockTimestamp();
 emit Initialize(_sqrtPriceX96, tick);

[Medium-2] syncReward() overwrites reward state without settling the prior period or refreshing lastUpdated

Confidence: 75 · CLPool.syncReward · [both — independently flagged by 6+ phase-2 agents plus phase-1's General checklist]

function syncReward(uint256 _rewardRate, uint256 _rewardReserve, uint256 _periodFinish)
    external override lock onlyGauge
{
    rewardRate = _rewardRate;
    rewardReserve = _rewardReserve;
    periodFinish = _periodFinish;
    delete rollover;
}

(CLPool.sol:954-965)

Unlike stake(), which always calls _updateRewardsGrowthGlobal() before mutating any reward-relevant state (CLPool.sol:600), syncReward() overwrites rewardRate/rewardReserve/periodFinish and deletes rollover with no settlement step and without advancing lastUpdated. If any interval [lastUpdated, now) is unsettled at the old rate when syncReward runs, the next _updateRewardsGrowthGlobal() call charges that entire stale interval against the new rewardRate — either front-loading a large reward burst from a rate that didn't apply to that time window, or (if the old reserve still had unsettled amounts) silently discarding them under the overwrite.

Whether this is exploitable in practice depends on whether the out-of-scope gauge contract always calls updateRewardsGrowthGlobal() immediately before syncReward() in the same transaction — unverifiable from this bundle, and not enforced by the pool.

Fix: settle before mutating, matching the pattern already used in stake():

 function syncReward(uint256 _rewardRate, uint256 _rewardReserve, uint256 _periodFinish)
     external override lock onlyGauge
 {
+    _updateRewardsGrowthGlobal();
     rewardRate = _rewardRate;
     rewardReserve = _rewardReserve;
     periodFinish = _periodFinish;
     delete rollover;
 }

[Medium-3] Fee-on-transfer and rebasing tokens break the pool's virtual-reserve accounting

Confidence: 80 · CLPool.mint / CLPool.swap / CLPool.flash / CLPool._collect · [both — independently corroborated by 6+ agents across both phases]

Payment verification throughout the pool is a pure balance-delta check against live balanceOf, e.g.:

if (amount0 > 0) require(balance0Before.add(amount0) <= balance0(), "M0");   // mint, CLPool.sol:476
require(balance0Before.add(uint256(amount0)) <= balance0(), "IIA");          // swap, CLPool.sol:860
require(balance0Before.add(fee0) <= balance0After, "F0");                    // flash, CLPool.sol:891

Pricing itself is driven entirely by internal liquidity/sqrtPriceX96/tokensOwed state, never by measured balances.

  • Fee-on-transfer tokens (input side): the pool receives less than amount, so the balanceBefore + amount <= balanceAfter check fails and mint/swap-in/flash revert — a hard DoS for any FoT token pair.
  • Fee-on-transfer / rebasing tokens (output side): swap-out, collect, and flash payouts send amount computed from virtual reserves via TransferHelper.safeTransfer; a token that deducts value in flight (FoT fee, or a negative rebase) means real balance drops by more than the virtual debit. Outstanding tokensOwed/liquidity claims can come to exceed balanceOf(pool), so the last LPs to collect/burn find their safeTransfer reverting — a slow insolvency for the tail of LPs, not the first movers.
  • Positive rebases: surplus balance is stranded — there is no skim() function to recover or attribute it to any position.

This is a factory-level trust decision (only whitelisted, well-behaved tokens should be paired), not fixable inside the pool itself without abandoning the virtual-reserve model.

Fix: enforce a token allowlist at the factory (probe-transfer FoT/rebase detection before createPool) rather than attempting an in-pool fix.

[Low-1] rollover rewards can be permanently lost

Confidence: 60 · CLPool._updateRewardsGrowthGlobal / CLPool.syncReward · [phase2: 2 agents]

When rewardReserve > 0 but stakedLiquidity == 0, _updateRewardsGrowthGlobal() moves the accrued reward into rollover (CLPool.sol:944-948) instead of crediting it to rewardGrowthGlobalX128. rollover is read nowhere in this contract except syncReward(), which unconditionally deletes it (CLPool.sol:964) without folding it back into the new rewardReserve. If the out-of-scope gauge does not itself read and re-inject rollover before calling syncReward(), those rewards are permanently stranded — debited from the old reserve, never credited to any staker, then deleted.

Fix: fold prior rollover back into rewardReserve inside syncReward() rather than deleting it, so correctness doesn't depend on gauge-side sequencing:

 function syncReward(uint256 _rewardRate, uint256 _rewardReserve, uint256 _periodFinish)
     external override lock onlyGauge
 {
     _updateRewardsGrowthGlobal();
     rewardRate = _rewardRate;
-    rewardReserve = _rewardReserve;
+    rewardReserve = _rewardReserve + rollover;
     periodFinish = _periodFinish;
     delete rollover;
 }

[Low-2] mint(recipient = gauge) is permissionless and writes directly into the gauge's privileged staked-position storage slot

Confidence: 65 · CLPool.mint / CLPool._updatePosition · [both — independently found by 5 agents across both phases]

mint(recipient, ...) places no restriction on recipient (CLPool.sol:452). _updatePosition derives staked = (owner == gauge) && (owner != address(0)) (CLPool.sol:437) purely from address equality — it has no way to distinguish a legitimate stake()-routed position update from an arbitrary mint() call with recipient = gauge. Verified against Position.update() (Position.sol:44-86): a staked = true position never accrues tokensOwed0/1 (the fee-accrual block is gated if (!staked), Position.sol:63-75).

Concretely: anyone can call mint(gauge, tickLower, tickUpper, amount, data), paying real tokens, and that liquidity lands in positions[keccak256(gauge, tickLower, tickUpper)] — the exact same storage slot stake() uses for its virtual staked-position bookkeeping (CLPool.sol:606) — flagged staked=true so it earns no fees, and with the global stakedLiquidity counter left untouched (only stake() moves that). The caller can never recover this liquidity: the public burn/collect overloads key on owner == msg.sender, and the owner-parameterized overloads are onlyNftManager.

Direct impact within this contract's scope is a self-harm donation (the caller's own funds become unrecoverable). The unverified risk is downstream: if the out-of-scope gauge contract reads positions[gauge].liquidity (or its feeGrowthInside*LastX128) as ground truth for its own staked-liquidity/reward bookkeeping, this griefing-by-donation could desynchronize gauge-side accounting from the pool's actual stakedLiquidity.

Fix: restrict mint's recipient, or gate the staked flag more strictly:

 function mint(address recipient, int24 tickLower, int24 tickUpper, uint128 amount, bytes calldata data)
     external override lock returns (uint256 amount0, uint256 amount1)
 {
     require(amount > 0);
+    require(recipient != gauge && recipient != nft, "RG");
     ...

[Low-3] rewardGrowthOutsideX128 is never initialized when a tick is first touched — deviates from canonical Slipstream, but self-cancels under normal delta-based reward consumption

Confidence: 55 · Tick.update / Tick.getRewardGrowthInside · [both — independently found by 6 agents across both phases; direct source-verified]

Tick.update()'s tick-initialization block seeds feeGrowthOutside0/1X128, secondsPerLiquidityOutsideX128, tickCumulativeOutside, and secondsOutside to current global values when a tick initializes at-or-below the current tick (Tick.sol:173-183) — but never seeds rewardGrowthOutsideX128, and update() isn't even passed rewardGrowthGlobalX128 to do so. getRewardGrowthInside() (Tick.sol:109-136) and cross() (Tick.sol:236-239) both treat rewardGrowthOutsideX128 with the identical "assume prior growth happened below" convention the other five fields rely on being seeded for.

This orchestrator traced the algebra directly: a tick seeded with rewardGrowthOutside = 0 instead of the correct G₀ carries a constant offset of magnitude G₀ that flips sign on every cross() (since cross computes new_outside = G_now - old_outside), and that sign-flip is synchronized with the below/above branch switch in getRewardGrowthInside. For the standard "checkpoint now, read again later, take the delta" pattern any gauge/reward-accounting consumer would use, and where the number of crosses between the two checkpoints is even (including zero), the offset cancels exactly. It does not cancel if a consumer ever reads getRewardGrowthInside as an absolute value at a single point, or checkpoints across an odd number of crosses in a way sensitive to the sign — neither of which can be verified since the gauge contract is out of scope.

Fix (recommended regardless of exploitability, since it's a clear deviation from the canonical pattern used for every other accumulator in the same struct):

 function update(
     mapping(int24 => Tick.Info) storage self,
     int24 tick,
     int24 tickCurrent,
     int128 liquidityDelta,
     uint256 feeGrowthGlobal0X128,
     uint256 feeGrowthGlobal1X128,
     uint160 secondsPerLiquidityCumulativeX128,
     int56 tickCumulative,
     uint32 time,
     bool upper,
-    uint128 maxLiquidity
+    uint128 maxLiquidity,
+    uint256 rewardGrowthGlobalX128
 ) internal returns (bool flipped) {
     ...
     if (tick <= tickCurrent) {
         info.feeGrowthOutside0X128 = feeGrowthGlobal0X128;
         info.feeGrowthOutside1X128 = feeGrowthGlobal1X128;
+        info.rewardGrowthOutsideX128 = rewardGrowthGlobalX128;
         info.secondsPerLiquidityOutsideX128 = secondsPerLiquidityCumulativeX128;
         ...

[Low-4] initialize() has no caller access control — pool safety depends entirely on factory deploy/init atomicity

Confidence: 55 · CLPool.initialize · [both — independently flagged by 5 agents across both phases]

function initialize(address _factory, address _token0, address _token1, int24 _tickSpacing,
                     address _factoryRegistry, uint160 _sqrtPriceX96) external override {
    require(factory == address(0) && _factory != address(0));
    ...

(CLPool.sol:148-156)

The only guard is the one-time latch on factory == address(0) — there is no msg.sender check. Since this is a constructor-less EIP-1167 clone, if the (out-of-scope) CLFactory ever deploys the clone and calls initialize() in a separate transaction from the CREATE2 deployment, anyone can front-run with attacker-chosen _token0/_token1/_tickSpacing/_factoryRegistry/_sqrtPriceX96. _factoryRegistry in particular backstops the onlyGaugeFactory modifier (CLPool.sol:141-144), so an attacker-supplied registry could let the attacker later call setGaugeAndPositionManager and take over the gauge role entirely. Not exploitable if createPool deploys-and-initializes atomically (the standard Slipstream pattern), but the pool contract itself does not enforce or verify this.

Fix: restrict to the deploying factory, e.g. require(msg.sender == expectedFactory) (passed via clone immutable args), or confirm and document that the factory's createPool is always atomic.

[Low-5] Swap fee is read live from the factory on every swap — governance-side fee-sandwich exposure

Confidence: 50 · CLPool.fee / CLPool.unstakedFee · [phase1: defi-amm]

function fee() public view override returns (uint24) { return ICLFactory(factory).getSwapFee(address(this)); }
function unstakedFee() public view override returns (uint24) { return ICLFactory(factory).getUnstakedFee(address(this)); }

(CLPool.sol:181-187), consumed fresh in every swap() (CLPool.sol:716) and flash() (CLPool.sol:878-879). Whoever controls the factory's fee-setter can front-run a large pending swap with a fee hike and revert it after — bounded entirely by the (out-of-scope) factory's own fee cap and access control, which are not in this audit's scope.

Fix: lives in the factory — hard fee cap + timelock on fee changes.

[Low-6] Dust-liquidity ticks can inflate swap gas across a targeted price band

Confidence: 45 · CLPool.swap / Tick.cross / TickBitmap · [phase1: dos]

The swap loop crosses one initialized tick per iteration; each crossing rewrites multiple storage slots. An attacker can mint() minimal-liquidity positions across many adjacent ticks (bounded by maxLiquidityPerTick per tick, not by tick count) to force a legitimate large swap through that band to pay for thousands of tick crossings. Inherent to concentrated-liquidity AMMs generally, amplified by cheap L2 gas (this deploys on Base); does not permanently brick swaps since they can be chunked into multiple transactions.

Fix: none at the pool level without breaking V3 semantics; periphery/routers should support chunked/multi-hop execution.

[Low-7] balanceOf-dependent payment paths revert if a pool token pauses

Confidence: 40 · CLPool.balance0 / balance1 · [phase1: dos, erc20]

mint, swap, and flash all gate on balanceOf succeeding with ≥32 bytes of return data (CLPool.sol:204-219). A pausable/blocklistable token (USDC-style) that reverts or blocks the pool's own address freezes every mint/swap/flash on that pool. Not third-party-triggerable — depends entirely on which tokens the factory allows to be paired.

Info / no-action items (verified, no fix required)

  • calculateFees/splitFees unchecked subtraction (CLPool.sol:978, 1016) assumes stakedLiquidity ≤ liquidity. Six phase-2 agents raised this as a potential unchecked-underflow DoS/fee-corruption lead. Direct re-verification of stake() (CLPool.sol:590-620) refutes this as exploitable under the pool's trust model: the global stakedLiquidity counter is only incremented when the current tick is in-range (CLPool.sol:599-601) — symmetric with how the global liquidity counter itself is only updated in-range in _modifyPosition (CLPool.sol:344-365) — and the per-tick stakedLiquidityNet update is only skipped when a tick is not yet initialized (CLPool.sol:618-619), which cannot happen for any tick that already bounds real minted liquidity (minting always initializes both boundary ticks first). Given stake() is onlyGauge and only stakes already-minted positions, the invariant holds. Recommended as defense-in-depth only, since the pool has zero in-contract enforcement and the entire argument rests on trusting the out-of-scope gauge: require(_stakedLiquidity <= _liquidity) in calculateFees.
  • collectFees() permanently strands 1 wei of each gauge-fee token (CLPool.sol:1025-1034) — a deliberate, standard gas-optimization pattern (avoid clearing a storage slot), not a defect.
  • Silent uint128(...) truncation of gauge/staked fee amounts without SafeCast (CLPool.sol:768, 902, 908) — would require a single fee step to exceed 2^128 base units, unreachable with any realistic token supply.
  • Division-before-multiplication in Oracle.observeSingle's tickCumulative interpolation — verbatim upstream Uniswap V3, immaterial precision loss, not attacker-steerable.
  • TWAP/spot-price manipulability (slot0.sqrtPriceX96 is spot and single-tx-manipulable; the accumulator-based TWAP correctly resists single-tx manipulation but remains manipulable over multiple blocks on thin pools with short windows) — the standard, well-documented AMM oracle caveat for external integrators, not a pool-level bug.
  • Default observation cardinality of 1 — observe() reverts for historical queries until a consumer calls increaseObservationCardinalityNext and the buffer fills; standard inherited Uniswap V3/Slipstream behavior.
  • Inline assembly is confined to FullMath.mulDiv, TickMath.getTickAtSqrtRatio, UnsafeMath.divRoundingUp — all canonical, heavily-audited Uniswap V3 snippets; no memory-safety or calldata/returndata issues found.
  • Flash-loan repayment and reentrancy: flash()'s repayment check (balanceBefore + fee ≤ balanceAfter, rounded up via mulDivRoundingUp) is correct and unbypassable; every state-mutating entrypoint is lock-guarded (or manually guarded in swap), so there is no reentrancy window during any callback.
