[H-1] Cross-function signature domain collision lets an attacker hijack a name's contenthash (or other records) under a signature the owner believed authorized something else

Severity: High
Origin: [phase2: agents 1, 2, 6 — independently discovered by 3 of 12 blind depth agents]
Location: L2Resolver.sol:76-88 (setAddrWithSignature), :98-112 (setTextWithSignature), :121-135 (setContenthashWithSignature), :145-163 (setABIWithSignature)

Description: All four signature-authorized setters build their signed digest the same way:

// setTextWithSignature, L2Resolver.sol:98-100
bytes32 sigHash = keccak256(
    abi.encodePacked(address(this), node, key, value, expiration)
).toEthSignedMessageHash();

// setContenthashWithSignature, L2Resolver.sol:121-123
bytes32 sigHash = keccak256(
    abi.encodePacked(address(this), node, hash, expiration)
).toEthSignedMessageHash();

abi.encodePacked concatenates dynamic bytes/string arguments with no length prefix or delimiter, and neither digest includes a function selector or type tag. Since key||value (two adjacent dynamic strings) packs to exactly the same bytes as a single hash argument of that same length, the digest for a setText call is bit-for-bit identical to the digest for a setContenthash call whenever hash == key||value. A signature the owner produced (or was tricked into producing) for what looked like a text-record update is therefore also a valid signature for setContenthashWithSignature — silently repointing the name's contenthash (the IPFS/Swarm hash most wallets and browsers use to resolve a decentralized website for the name) to attacker-chosen bytes.

A second, narrower instance of the same root cause exists intra-function: setTextWithSignature's key and value are two adjacent dynamic fields with no separator, so (key="a", value="bc") and (key="ab", value="c") produce the identical digest — an attacker who observes one signed authorization can resubmit it with the key/value boundary moved, writing a record the signer never approved.

Proof of Concept:

  1. A dApp/relayer (attacker-controlled or compromised) asks the name owner to sign a "set text record" meta-transaction: key = "note", value = <32 bytes the attacker has chosen so that key||value equals a target IPFS-style content hash>, some expiration.
  2. Owner signs. The relayer never actually submits setTextWithSignature.
  3. Attacker instead calls setContenthashWithSignature(node, hash = bytes("note") ++ value, expiration, signer, signature).
  4. sigHash = keccak256(abi.encodePacked(address(this), node, hash, expiration)) is byte-identical to the setText digest the owner actually signed, so universalSignatureValidator.isValidSig(signer, sigHash, signature) returns true, and isAuthorisedForAddress(signer, node) passes (the signer is still the legitimate owner).
  5. versionable_hashes[recordVersions[node]][node] = hash is written — the name's contenthash now points to attacker-controlled content, without the owner ever knowingly authorizing a contenthash change.

Recommendation: Include a unique, function-specific domain tag in every signed digest, and switch from abi.encodePacked to abi.encode (or hash each dynamic field individually) so no two signed messages — across functions or within one — can ever produce the same digest:

- bytes32 sigHash = keccak256(
-     abi.encodePacked(address(this), node, key, value, expiration)
- ).toEthSignedMessageHash();
+ bytes32 sigHash = keccak256(
+     abi.encode(bytes4(keccak256("setText")), address(this), node, key, value, expiration)
+ ).toEthSignedMessageHash();

Apply the equivalent change (distinct tag, abi.encode) to all four functions.

[M-1] setTextWithSignature's two adjacent dynamic fields collide under abi.encodePacked

Severity: Medium
Origin: [both — phase1: General-2, Signatures-2; phase2: 10 of 12 agents independently flagged this]
Location: L2Resolver.sol:98-100

Description: See H-1 above for the mechanism — this is the intra-function instance (key/value boundary shifting within setText alone, not requiring a second function). It is called out separately because it is exploitable even in isolation (an attacker does not need to target a different function; they only need to resubmit setTextWithSignature itself with a different split of the same signed bytes), and because it was the single most-corroborated finding across all 20 audit agents in this engagement.

Proof of Concept: Owner signs setText(node, key="url", value="https://real.io", expiration). Packed digest input contains the byte run urlhttps://real.io. Attacker calls setTextWithSignature(node, key="urlhttps://real.i", value="o", expiration, signer, signature) — identical packed bytes, identical digest, signature still validates. The record actually written is ["urlhttps://real.i"] = "o"; the owner's intended ["url"] = "https://real.io" is never set.

Recommendation: Same fix as H-1 (Option A: abi.encode; Option B: hash key/value individually with a function tag).

[M-2] Resolver authorization conflates ERC721 transfer-approval with record-write authority, and doesn't honor operator (setApprovalForAll) approvals

Severity: Medium
Origin: [both — phase1: ERC721-4 (partial: missing isApprovedForAll only); phase2: agent 11 independently identified the getApproved-conflation as the more serious half of this issue]
Location: L2Resolver.sol:172-190 (isAuthorisedForAddress)

function isAuthorisedForAddress(address addr, bytes32 node) internal view returns (bool) {
    L2Registry registry = _registry();
    if (registry.registrars(addr)) {
        return true;
    }
    uint256 tokenId = uint256(node);
    address owner = registry.ownerOf(tokenId);
    if ((owner != addr) && (registry.getApproved(tokenId) != addr)) {
        revert Unauthorized(node);
    }
    return true;
}

Description: This function gates every resolver write (setAddr, setText, setContenthash, setABI, and all four *WithSignature variants). It treats getApproved(tokenId) == addr — the ERC721 single-token transfer approval, typically granted to list an NFT on a marketplace — as sufficient authority to rewrite that name's resolver records. This is a broader grant than the owner likely intends: approving a marketplace to sell a name also hands that marketplace (or anyone controlling it) the ability to repoint the name's addr record before the sale settles. Canonical ENS PublicResolver.isAuthorised instead checks isApprovedForAll/isApprovedFor — never the single-token getApproved — for exactly this reason. Symmetrically, this function does not check isApprovedForAll, so a legitimately-delegated operator (standard ERC721 marketplace/delegation pattern) cannot manage records at all — a functionality gap in the opposite direction.

Proof of Concept: Alice owns alice.example.eth and calls approve(marketplace, uint256(node)) to list it for sale. Before any sale executes, marketplace (or an attacker who compromises it) calls setAddr(node, 60, attackerAddress). isAuthorisedForAddress(marketplace, node) returns true because getApproved(tokenId) == marketplace, so Alice's ETH address record is redirected to the attacker despite Alice retaining ownership and never authorizing a record change.

Recommendation: Replace the getApproved check with isApprovedForAll(owner, addr):

- if ((owner != addr) && (registry.getApproved(tokenId) != addr)) {
+ if ((owner != addr) && !registry.isApprovedForAll(owner, addr)) {
      revert Unauthorized(node);
  }

[M-3] Registrars have unconditional write authority over every node, not just names they create

Severity: Medium
Origin: [both — phase1: AccessControl-1, ERC721-1; phase2: agents 2, 4, 9 independently corroborated]
Location: L2Registry.sol:78-83 (onlyOwnerOrRegistrar), L2Resolver.sol:172-181 (isAuthorisedForAddress)

modifier onlyOwnerOrRegistrar(bytes32 node) {
    if (owner(node) != msg.sender && !registrars[msg.sender]) {
        revert Unauthorized(node);
    }
    _;
}

if (registry.registrars(addr)) {
    return true;
}

Description: Both gates check registrars[msg.sender] without regard to node — an approved registrar is authorized for every node in the registry, not just nodes under its own remit. Consequently any approved registrar can (a) call createSubnode under a node it does not own — including subnames already owned by end users — and (b) overwrite addr/text/contenthash/abi records for any existing node, not only ones it registered. A registrar intended only to sell 3LDs under baseNode therefore has, by construction, full write access to every user's name in the registry.

Proof of Concept: Admin adds registrar R (e.g. a marketplace/controller contract) via addRegistrar(R). Alice registers and owns alice.example.eth. R calls setAddr(namehash("alice.example.eth"), 60, attackerAddr) — passes because registrars[R] == true short-circuits before any ownership check, repointing Alice's address record despite her being the sole NFT owner. R can equally call createSubnode(aliceNode, "pay", attacker, []) to mint arbitrary subnames under Alice's name.

Recommendation: Scope the registrar bypass to creation of direct children of baseNode (or the registrar's own designated subtree), and remove it from record-mutation authority over already-owned nodes:

modifier onlyOwnerOrRegistrar(bytes32 node) {
    if (owner(node) != msg.sender && !(registrars[msg.sender] && node == baseNode)) {
        revert Unauthorized(node);
    }
    _;
}

If the broad trust model is intentional (registrars are meant to be fully trusted infrastructure), document this prominently for integrators and name holders.

[M-4] Signature-based setters have no nonce — a captured signature is replayable throughout its (signer-chosen) expiration window

Severity: Medium
Origin: [both — phase1: General-3, Signatures-1; phase2: 10 of 12 agents independently flagged this]
Location: L2Resolver.sol:68-166 (all four *WithSignature functions)

Description: None of the four signed digests include a nonce, and no storage marks a signature as consumed. The only replay guard is unexpiredSignature(expiration), checking block.timestamp <= expiration — and expiration is entirely chosen by whoever constructs the signing request, with no protocol-enforced maximum. A signature can therefore be resubmitted by anyone, any number of times, for as long as it remains unexpired.

Proof of Concept: Owner signs setAddr(node, 60, X) with expiration = now + 365 days; it is relayed and addr(node, 60) becomes X. Five days later the owner updates the address to Y via a fresh call. Any observer who retains the original (still-unexpired) signature can resubmit it, forcing addr(node, 60) back to X — repeatable at will until the year-long expiration elapses, with the owner having no way to invalidate the outstanding signature early.

Recommendation: Add a per-node (or per-signer) nonce, included in the signed digest and incremented/consumed on use:

+ mapping(bytes32 => uint256) public sigNonce;
  ...
  bytes32 sigHash = keccak256(
-     abi.encodePacked(address(this), node, coinType, a, expiration)
+     abi.encodePacked(address(this), node, coinType, a, expiration, sigNonce[node]++)
  ).toEthSignedMessageHash();

[M-5] setAddrWithSignature re-invokes the authorised-gated public setAddr, breaking the gasless-relay pattern the other three setters implement

Severity: Medium
Origin: [both — phase1: General-1; phase2: agents 8, 12 (finding), agent 2 (lead)]
Location: L2Resolver.sol:68-89

Description: setTextWithSignature, setContenthashWithSignature, and setABIWithSignature all write their target storage mapping directly, with a code comment explaining why: "Manually update storage since setText() on the inherited contract cannot be called internally" — because the inherited public setter carries the authorised(node) modifier, which checks msg.sender (the transaction submitter), not the signer. setAddrWithSignature was not converted to this pattern — it ends by calling setAddr(node, coinType, a) (L2Resolver.sol:87), and AddrResolver.setAddr is public virtual authorised(node). That modifier re-evaluates isAuthorisedForAddress(msg.sender, node) against the relayer, not the already-verified signer.

Proof of Concept: Owner O signs a valid setAddr payload and hands it to relayer R, who is not a registrar, owner, or approved address for node (the entire point of the meta-tx pattern is that R needs no such standing). R calls setAddrWithSignature(...). Both signer-side checks pass (isAuthorisedForAddress(O, node) and isValidSig), but execution then reaches setAddr(node, coinType, a) → authorised(node) → isAuthorisedForAddress(R, node) → reverts, because R has no standing. The identical relay pattern succeeds for setTextWithSignature. There is no test in the repository covering setAddrWithSignature, so this regression has no CI signal.

Recommendation: Mirror the other three setters — write storage directly instead of calling the guarded inherited function:

- setAddr(node, coinType, a);
+ versionable_addresses[recordVersions[node]][node][coinType] = a;
+ emit AddressChanged(node, coinType, a);
+ if (coinType == 60) emit AddrChanged(node, address(bytes20(a)));

[M-6] L1Resolver owner can instantly rotate the trusted CCIP-Read signer, with no timelock, controlling all resolution results

Severity: Medium
Origin: [phase1 only: AccessControl-2 — re-examined against source in synthesis, confirmed]
Location: L1Resolver.sol:43 (Ownable), :215-218 (setSigner), :182-196 (resolveWithProof)

Description: resolveWithProof accepts any CCIP-Read gateway response signed by the single address stored in signer. setSigner is a plain onlyOwner function with no timelock, no multi-signer requirement, and no delay between calling it and the new signer taking effect. L1Resolver is a single-address Ownable (see M-7), so control of resolution for every name pointed at this resolver reduces to control of one EOA/contract's owner key.

Proof of Concept: Owner (or an attacker who compromises the owner key) calls setSigner(attackerSigner). Any subsequent resolve() call is now served by a gateway the attacker controls, which can return arbitrary results (e.g. a different addr()) signed by attackerSigner; resolveWithProof accepts it immediately since it only checks _signer == signer.

Recommendation: This trust assumption is partly inherent to CCIP-Read (the gateway itself is already trusted infrastructure), but the governance of who the trusted signer is should not be a single instant admin call. Require a multisig/timelocked owner, and/or add a delay between setSigner being called and the new signer becoming active, with an event emitted in advance.

[L-1] Missing block.chainid in signature digests permits cross-chain replay under a specific deployment coincidence

Severity: Low (re-examined: phase-1 rated this Medium via the Signatures checklist; phase-2's independent, blind read treated it only as an unscored Lead because the precondition is speculative rather than guaranteed — synthesis adopts the more conservative Low)
Origin: [both — phase1: General-4, Signatures-3; phase2: agents 2, 7, 8, 11 (all as Leads)]
Location: L2Resolver.sol:68-166 (all four *WithSignature digests), L2RegistryFactory.sol:51-72

Description: Every signed digest binds address(this) and node but never block.chainid. L2RegistryFactory.deployRegistry deploys registries via Clones.clone (plain CREATE, address = f(factory address, factory nonce)). If the same factory is deployed at the same address on two L2s and reaches the same nonce in the same order on both (realistic only with deliberate deterministic-deployment tooling), the resulting registry clone shares an address across chains, and a signature valid on chain A becomes valid, unmodified, on chain B for the identically-addressed clone.

Recommendation: Include block.chainid in every signed digest — trivial to add alongside the H-1/M-4 fixes since they already touch the same lines:

keccak256(abi.encode(block.chainid, address(this), node, ...))

[L-2] Registry admin authority is bound to a transferable ERC721 token with no two-step safeguard

Severity: Low
Origin: [phase1 only: AccessControl-4 — re-examined against source, confirmed]
Location: L2Registry.sol:190-198 (owner()), :341-346-equivalent (onlyOwner)

Description: owner() returns _ownerOf(baseNode) — the current ERC721 owner of the registry's base-name token. onlyOwner (gating addRegistrar/removeRegistrar/setBaseURI) is therefore just "whoever currently holds this NFT." A single transferFrom/safeTransferFrom (or an operator approved via setApprovalForAll) instantly and irreversibly transfers full admin rights, including the ability to add a malicious registrar (see M-3), with no two-step confirmation and no protection against a mistaken transfer.

Recommendation: Document prominently that transferring or approving the baseNode token transfers/grants admin rights. Consider decoupling admin authority from the tradeable token, or requiring an explicit two-step acknowledgment on baseNode transfers.

[L-3] L1Resolver uses single-step Ownable and does not disable renounceOwnership

Severity: Low
Origin: [phase1 only: AccessControl-3 — re-examined against source, confirmed]
Location: L1Resolver.sol:43,104

Description: L1Resolver inherits OpenZeppelin Ownable, not Ownable2Step. A typo'd transferOwnership call permanently locks out the owner; an inadvertent or malicious renounceOwnership() call permanently disables setURL/setSigner, removing any path to respond to a signer-key compromise.

Recommendation: Use Ownable2Step and override renounceOwnership() to revert.

[L-4] createSubnode mints (triggering an onERC721Received callback) before finalizing names[]/totalSupply — a check-effects-interactions violation confined to self-inflicted corruption

Severity: Low
Origin: [both — phase1: General-5, Proxies-1, ERC721-2; phase2: agents 5, 7, 8, 9, 12 — 5 of 12 blind agents converged on this, but every one independently concluded the reentrant path only lets the newly-minted owner corrupt their own subtree]
Location: L2Registry.sol:138-160, specifically :152 (_safeMint) preceding :155-157 (names[subnode] =, totalSupply++)

Description: _safeMint(_owner, uint256(subnode)) fires onERC721Received on _owner (if a contract) before names[subnode] is written and before totalSupply is incremented. A malicious _owner contract can reenter createSubnode(subnode, childLabel, ...) during that callback — onlyOwnerOrRegistrar(subnode) passes because _owner already holds subnode at that point — while names[subnode] is still empty. _addLabel(childLabel, names[subnode]) then builds a truncated/malformed DNS-encoded name for the grandchild (no parent chain, no terminator), which later reverts InvalidName() in tokenURI/decodeName. Every phase-2 agent that traced this path concluded the corruption is confined to the attacker's own subtree — a self-inflicted griefing outcome, not a third-party exploit — which is why this is rated Low rather than higher despite five independent agents flagging it.

Recommendation: Reorder to checks-effects-interactions: write names[subnode] and increment totalSupply before _safeMint.

+ names[subnode] = dnsEncodedName;
+ totalSupply++;
  _safeMint(_owner, uint256(subnode));
  _multicall(subnode, data);
- names[subnode] = dnsEncodedName;
- totalSupply++;

[L-5] tokenURI's on-chain JSON fallback embeds the decoded name without escaping

Severity: Low
Origin: [phase1 only: ERC721-3 — re-examined against source, confirmed]
Location: L2Registry.sol:269-289

string memory json = string.concat(
    '{"name": "',
    ENSDNSUtils.dnsDecode(names[bytes32(tokenId)]),
    '"}'
);

Description: Labels are validated only for byte length (_addLabel, 1–255 bytes); no character-set restriction exists. A label containing " breaks the generated JSON or injects additional attacker-controlled keys (e.g. a spoofed image field) into metadata that marketplaces and wallets parse and display.

Recommendation: JSON-escape the decoded name before embedding it, or restrict registrable label characters.

[L-6] Unbounded, quadratic string processing of an attacker-controlled name in L1Resolver.resolve()

Severity: Low
Origin: [phase1 only: DoS-1 — re-examined against source, confirmed; phase2 agents did not probe gas/DoS surfaces]
Location: L1Resolver.sol:146-179

Description: resolve() fully decodes and splits an attacker-controlled, arbitrary-depth DNS-encoded name using the arachnid/strings library's per-label split/toString loop, with no cap on label count or total length. Cost scales roughly quadratically with name length. The function is a stateless view (it always ends in a revert carrying the CCIP-Read redirect), so impact is confined to the caller's own eth_call — a sufficiently deep name could exceed a node's gas cap and simply fail to resolve, rather than affecting other users or on-chain state.

Recommendation: Parse only the last two labels directly from the DNS-encoded bytes instead of decoding and splitting the full name, and/or reject names above a sane maximum length/depth early.

[L-7] Hardcoded ERC-6492 UniversalSignatureValidator dependency — permanent DoS of all signature setters if absent on a target chain

Severity: Low
Origin: [phase1 only: Signatures-4, DoS-3 — re-examined against source, confirmed; phase2 agents took the validator's presence as given]
Location: L2Resolver.sol:41-44

IUniversalSignatureValidator private immutable universalSignatureValidator =
    IUniversalSignatureValidator(0x164af34fAF9879394370C7f09064127C043A35E9);

Description: All four *WithSignature functions route through this fixed address with no fallback and no way to reconfigure it post-deployment. Since L2Registry is designed to be cloned across arbitrary L2s via the factory, deploying to a chain where this predeploy is absent permanently disables the entire signature-based record-setting surface (direct setAddr/setText/etc. via owner/approved/registrar still works).

Recommendation: Make the validator address a constructor/initializer parameter, and consider verifying extcodesize > 0 at initialization time with a clear revert if absent.

[L-8] ENSDNSUtils.dnsDecode writes past its allocated buffer without a memory-safe annotation or advancing the free-memory pointer

Severity: Low
Origin: [both — phase1: Assembly-1; phase2: agent 9 (lead, unverified), agent 7 (explicitly concluded not exploitable)]
Location: src/lib/ENSDNSUtils.sol:14-63

Description: The word-at-a-time memcpy can write up to ~30 bytes past both the ens allocation and the free-memory pointer, which is never advanced — the author's own comment acknowledges this ("we clobber 31-=bytes beyond the end … it's ok since we don't call anything"). This is safe under every current caller (no allocation or external call is interleaved between the clobbering writes and the function's return in tokenURI, decodeName, or L1Resolver.resolve), but the assembly blocks are not annotated memory-safe and nothing enforces the invariant the safety argument depends on.

Recommendation: Advance the free-memory pointer to cover the clobbered region after the final length fix, or over-allocate before writing and fix the true length last.

[I-1] L2Registrar.available() and register() disagree on minimum label length

Severity: Info (example contract, explicitly "meant to be modified")
Origin: [both — phase1: General-7; phase2: 6 of 12 agents independently flagged this]
Location: src/examples/L2Registrar.sol:44-64 (register), :70-82 (available)

Description: available() reports labels shorter than 3 characters as unavailable; register() enforces no minimum length at all (L2Registry._addLabel only rejects length 0 or >255), so 1–2 character labels a front-end would report as unregisterable can still be registered directly.

Recommendation: Mirror available()'s policy inside register() if this example is used as a starting point for production registrars.

[I-2] Labels containing . produce a display name whose decoded string doesn't match its ENS namehash

Severity: Info
Origin: [both — phase1: ERC721-6; phase2: agents 5, 7]
Location: L2Registry.sol:251-262 (_addLabel)

Description: A label such as "a.b" is stored and hashed as one atomic label (keccak256("a.b")), but its DNS-decoded display form (a.b.parent.eth) implies a different, hierarchical namehash than the one the token actually corresponds to — enabling confusable/look-alike names.

Recommendation: Reject labels containing 0x2e (.).

[I-3] Non-registrar parent owners cannot atomically gift a subname with initial resolver records to a third party

Severity: Info (fails closed — reverts rather than misbehaving)
Origin: [both — phase1: General-6, AccessControl-6, ERC721-5; phase2: agents 7, 8, 12]
Location: L2Registry.sol:138-160 (createSubnode → _multicall)

Description: _multicall(subnode, data) preserves msg.sender via delegatecall; when a non-registrar parent-node owner mints a subnode to a different _owner and supplies non-empty data, the resolver setter's authorization check fails (the caller is neither the new owner, approved, nor a registrar), reverting the entire createSubnode call.

Recommendation: Either authorize the caller who satisfies onlyOwnerOrRegistrar(node) for the freshly-created child within the same call, or document that non-registrar callers must pass empty data.

[I-4] Permissionless registry deployment enables name squatting with no on-chain consequence

Severity: Info
Origin: [phase1 only: AccessControl-5]
Location: L2RegistryFactory.sol:51-72

Description: Anyone can deploy a registry claiming any parent name (e.g. "vitalik.eth") and become its admin. This confers no real authority — an L1 name's actual owner must separately and explicitly link a registry via the properly-gated L1Resolver.setL2Registry — but could cause off-chain confusion if a squatted registry's name()/metadata is trusted without verifying the on-chain L1 link.

Recommendation: Document that a deployed registry has no authority until linked by the true L1 name owner.

[I-5] setABIWithSignature: contentType == 0 underflows to a Panic instead of a clean revert

Severity: Info
Origin: [both — phase1: PrecisionMath-1; phase2: agent 1]
Location: L2Resolver.sol:157 (equivalent — power-of-two check)

Description: require(((contentType - 1) & contentType) == 0) underflows under checked arithmetic when contentType == 0, producing an opaque Panic(0x11) rather than the intended validation failure. Reached only after signature verification succeeds, so there is no security impact — purely cosmetic, and matches upstream ENS ABIResolver behavior.

Recommendation: require(contentType != 0 && (contentType & (contentType - 1)) == 0);

[I-6] Unnecessary inline assembly for chainid() in the example L2Registrar constructor

Severity: Info
Origin: [phase1 only: Assembly-2]
Location: src/examples/L2Registrar.sol:28-32

Description: assembly { sstore(chainId.slot, chainid()) } is unneeded — block.chainid has been a native Solidity builtin since 0.8.0 — and the accompanying comment claiming assembly is required is incorrect. chainId is also stored as mutable storage where an immutable would suffice.

Recommendation: chainId = block.chainid; using an immutable variable; remove the dead >> 0 in the coinType computation on the following line.

[I-7] _safeMint requires ERC721-receiver support from contract owners; totalSupply is a monotonic mint counter only

Severity: Info
Origin: [phase1 only: ERC721-7]
Location: L2Registry.sol:105-125 (initialize), :138-160 (createSubnode)

Description: Two integrator-facing behavioral notes: a contract _owner/admin without an onERC721Received implementation cannot be assigned a name (registration reverts); and totalSupply only ever increments (no burn path is exposed) with non-sequential, namehash-derived token IDs, so it should not be treated as a live enumeration count.

Recommendation: Document both behaviors for integrators.

Methodology notes

  • This audit ran as two independent passes reconciled after the fact: an 8-checklist breadth pass (ethskills methodology) and a 12-agent blind attacker-mindset depth pass (pashov methodology), each covering the full in-scope source independently before being cross-checked against each other and against the source code directly in this synthesis.
  • Every finding above quotes or cites the specific source lines it is based on; every finding unique to one phase was re-read against source during reconciliation before being included.
  • No Critical-severity finding survived verification: the most severe confirmed issue (H-1) requires the attacker to control what a name owner is asked to sign (a phishing/blind-signing precondition), which is a real and common attack surface for meta-transaction schemes but is not a fully preconditionless direct-loss bug.
  • src/examples/L2Registrar.sol is explicitly documented in-repo as example code "meant to be modified" — its findings (I-1) are lower priority if it is not used as-is in production.
