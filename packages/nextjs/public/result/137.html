Executive Summary

ClawdWorks is a CLAWD-native onchain services marketplace implementing escrow, dispute resolution, and an 80/10/10 fee split (seller / burn / treasury). The core token accounting is sound (BPS sum verified: 8000+1000+1000=10000), and the contract implements meaningful safety mechanisms: two-step ownership transfer, a 7-day treasury timelock, and a 14-day buyer auto-refund safety valve.

The primary security concern is structural: the contract's v1 design places a single entity (the owner) in the roles of seller, arbitrator, and deployer simultaneously. This creates a trust dependency that is intentional but must be understood by buyers. Beyond the design tradeoff, one High finding represents a state machine gap — funds in PAID status have no buyer-accessible exit path if the seller is inactive. Three Medium findings cover slippage, queue griefing, and the arbitration conflict of interest.

Findings

[H-1] PAID-Status Funds Permanently Locked if Seller Never Delivers [BOTH]

Severity: High
Category: State Machine / Access Control
Location: purchase(), disputeJob(), claimDisputeRefund()
Confidence: 90 (both passes confirmed; conditioned on owner inactivity)

Description: When a buyer calls purchase(), the job enters PAID status. There is no exit from this state without seller action (markDelivered). All other recovery paths are blocked:

  • disputeJob() — spec: "only DELIVERED status" — reverts on PAID jobs
  • claimDisputeRefund() — requires disputedAt > 0, which is never set on PAID jobs
  • claimTimeout() — requires deliveredAt > 0, which is 0 for undelivered jobs
  • No buyerCancelJob, emergencyRefund, or equivalent exists in the ABI

If the owner/seller loses their key, goes inactive, or becomes incapacitated, every buyer with an open PAID-status job loses their funds permanently.

Proof of Concept:

  1. Buyer approves CLAWD and calls purchase(listingId, buyerNote)
  2. Job created: {status: PAID, amountPaid: X, deliveredAt: 0, disputedAt: 0}
  3. Owner's key is compromised / lost
  4. All recovery functions check conditions that cannot be satisfied
  5. Buyer's X CLAWD is locked forever

Recommendation: Add a buyerCancelJob function:

function buyerCancelJob(uint256 jobId) external nonReentrant {
    Job storage job = jobs[jobId];
    require(job.buyer == msg.sender, "not buyer");
    require(job.status == JobStatus.PAID, "not PAID");
    require(block.timestamp > job.purchasedAt + DELIVERY_TIMEOUT, "too early");
    _refund(jobId);
    emit JobAutoRefunded(jobId);
}

This requires recording purchasedAt timestamp in the Job struct.

[M-1] No Slippage Protection in purchase() — Price Can Be Raised Between Approval and Execution [BOTH]

Severity: Medium
Category: ERC20 / Access Control
Location: purchase(), setPrice()

Description: The seller (owner) can call setPrice(listingId, newPrice) at any time without timelock or cooldown. purchase() reads listing.priceCLAWD at execution time. A buyer who has granted a large or infinite approval (a common pattern in Scaffold-ETH 2 dApps) can be charged a higher price than the one they saw when deciding to purchase.

Proof of Concept:

  1. Listing L shows priceCLAWD = 100e18
  2. Buyer calls approve(contract, type(uint256).max) (standard Scaffold-ETH pattern)
  3. Seller front-runs buyer's pending purchase(L, ...) with setPrice(L, 900e18)
  4. Buyer's transaction executes: transferFrom(buyer, contract, 900e18) succeeds
  5. Buyer paid 9× the displayed price with no consent

Recommendation: Add a maxPrice parameter to purchase():

function purchase(
    uint256 listingId,
    string calldata buyerNoteIpfsHash,
    uint256 maxPrice          // buyer-supplied ceiling
) external nonReentrant {
    require(listings[listingId].priceCLAWD <= maxPrice, "price exceeded");
    // ...
}

[M-2] Dispute Flooding Can Block Seller Queue for Up to 14 Days [BOTH]

Severity: Medium
Category: DoS / Queue Management
Location: disputeJob(), activeJobCount, DEFAULT_MAX_ACTIVE_JOBS

Description: The queue cap (DEFAULT_MAX_ACTIVE_JOBS = 5, verified on-chain) is enforced via activeJobCount[seller]. Per spec and invariant analysis, activeJobCount does not decrement when a job enters DISPUTED status — only on COMPLETED or REFUNDED. An attacker who purchases all 5 queue slots and disputes every delivery traps the queue in DISPUTED state for up to 14 days (the DISPUTE_AUTO_REFUND window). During this period, no new buyers can purchase.

The attacker recovers their CLAWD via claimDisputeRefund() after 14 days, making this attack nearly costless (only gas on Base ≈ $0.001/tx).

Proof of Concept:

  1. Attacker holds 5 × listing price CLAWD
  2. Purchases all 5 slots → activeJobCount[owner] = 5
  3. Seller delivers all 5 jobs (queue now in DELIVERED)
  4. Attacker calls disputeJob() on all 5 within the 7-day window
  5. All 5 in DISPUTED state; activeJobCount = 5 (no change)
  6. New buyer calls purchase() → reverts: queue full
  7. After 14 days: attacker calls claimDisputeRefund() × 5 → recovers CLAWD
  8. Repeat indefinitely

Recommendation: Decrement activeJobCount when a job transitions from DELIVERED to DISPUTED. The queue cap is logically about concurrent deliveries in-flight, not concurrent disputes. Disputed jobs are in a resolution state and don't reflect active work capacity:

// In disputeJob():
activeJobCount[job.seller]--;  // free slot; dispute is paused work
// Add separate disputedJobCount[seller] if tracking is needed

[M-3] Owner is Simultaneously Seller and Sole Arbitrator in v1 [BOTH]

Severity: Medium
Category: Access Control / Governance / Trust Model
Location: resolveDispute()

Description: In the current deployment (openMarketplace = false, verified on-chain), the contract owner is the exclusive seller. resolveDispute(jobId, refundBuyer, resolutionIpfsHash) is callable only by onlyOwner. This means the same party who delivered the disputed work also decides whether the buyer receives a refund. A malicious or negligent owner can call resolveDispute(jobId, false, ...) immediately upon a buyer's dispute, releasing funds to themselves (as seller) before the buyer's 14-day safety valve activates.

The resolutionIpfsHash parameter carries no enforcement — the contract accepts any non-empty hash without validating content.

Proof of Concept:

  1. Seller delivers empty/fraudulent deliverable
  2. Buyer calls disputeJob(jobId, reasonHash) → job enters DISPUTED
  3. Owner calls resolveDispute(jobId, false, "0x1234") immediately
  4. _release() pays 80% to owner (seller), 10% burned, 10% to treasury
  5. Job status = COMPLETED; buyer's claimDisputeRefund() now reverts (status != DISPUTED)

Recommendation (in order of impact):

  1. Use a Gnosis Safe 2-of-3 multisig as owner, with at least one independent key holder acting as arbitrator
  2. OR: add a mandatory 48-hour dispute response window during which buyers can post evidence before resolveDispute can be called
  3. OR: document this trust model prominently on the frontend and via an on-chain disputePolicyIpfsHash state variable

[L-1] Rounding Dust Accumulates in Contract With No Recovery Path [BOTH]

Severity: Low
Category: Precision Math
Location: _release()

Description: Computing three separate BPS divisions loses up to BPS_DENOMINATOR - 1 = 9999 wei per job:

sellerAmount   = amountPaid * 8000 / 10000  (truncated)
burnAmount     = amountPaid * 1000 / 10000  (truncated)
treasuryAmount = amountPaid * 1000 / 10000  (truncated)

No rescue mechanism exists for the accumulating residual. At realistic CLAWD values and transaction volumes, this is negligible per transaction but compounds over thousands of jobs.

Recommendation: Derive the last split from the remainder:

uint256 sellerAmount   = amountPaid * SELLER_BPS   / BPS_DENOMINATOR;
uint256 burnAmount     = amountPaid * BURN_BPS     / BPS_DENOMINATOR;
uint256 treasuryAmount = amountPaid - sellerAmount - burnAmount; // zero dust

[L-2] expressSellerInterest() Susceptible to Sybil Spam on Base L2

Severity: Low
Category: DoS / Spam
Location: expressSellerInterest()

Description: While hasExpressedInterest[address] prevents duplicate submissions from a single address, Sybil attacks using new wallets are trivially cheap on Base (gas ≈ $0.0001/tx). The sellerInterests array can be flooded with tens of thousands of entries, degrading curation workflows and increasing the gas cost of getSellerInterests() callers. The spec acknowledges this: "If spam becomes a problem, can add a small CLAWD fee in v2" — but on a low-gas L2, v1 spam is practical from day one.

Recommendation: Add a minimum CLAWD fee (e.g., 1–10 CLAWD transferred to treasury) to expressSellerInterest() before deploying to production with real traffic.

[L-4] executeTreasuryChange() Access Control Unverifiable Without Source

Severity: Low
Category: Governance
Location: executeTreasuryChange()

Description: The ABI exposes executeTreasuryChange() as nonpayable with no inputs. Without verified source, it is unknown whether this requires onlyOwner or is publicly callable. If public, any address can execute a pending treasury change after the 7-day timelock without owner confirmation. Additionally, no cancelTreasuryChange() is visible in the ABI — if the owner proposes an incorrect treasury address and cannot cancel, the change WILL execute after 7 days unless the owner can overwrite the proposal.

Recommendation: Verify source (see L-3). Confirm onlyOwner is on executeTreasuryChange(). Add cancelTreasuryChange() callable by onlyOwner.

[I-1] CLAWD Token Assumed Non-Fee-on-Transfer and Non-Rebasing

Severity: Info
Category: ERC20
Location: purchase(), _release(), _refund()

Description: CLAWD (0x9f86dB9fc6f7c9408e8Fda3Ff8ce4e78ac7a6b07, verified: standard 18-decimal ERC20, symbol "CLAWD", no visible owner or pause functions) does not currently exhibit fee-on-transfer or rebasing behavior. However, the contract's accounting model would break if these were added: amountPaid is recorded from the listing price, not from a balance-before/after diff. Incompatibility is latent.

Recommendation: No immediate action. Document the CLAWD token type assumption in the contract's NatSpec.

[I-2] Non-CLAWD Tokens Sent to Contract Are Permanently Locked

Severity: Info
Category: General
Location: Contract storage

Description: No rescueTokens or equivalent function exists in the ABI. Any ERC20 tokens (other than CLAWD tracked in jobs) accidentally sent to the contract, as well as any rounding dust (see L-1), cannot be recovered by the owner or anyone else.

Recommendation: Add rescueTokens(address token, address to, uint256 amount) onlyOwner with a guard preventing rescue of the CLAWD token (which is tracked internally via amountPaid and must not be drained).

[I-3] Base Sequencer Downtime Can Expire Dispute Windows

Severity: Info
Category: Chain-Specific (Base / OP Stack)
Location: disputeJob()

Description: The 7-day dispute window (DELIVERY_TIMEOUT = 604800) is enforced via block.timestamp. If the Base sequencer is offline for a significant period after a seller calls markDelivered(), buyers may be unable to submit disputeJob() transactions until the window has partially or fully elapsed. After sequencer recovery, the window appears to have partially expired from the contract's perspective.

Recommendation: Consider extending the dispute window to 10–14 days. Alternatively, document this operational risk for buyers.
