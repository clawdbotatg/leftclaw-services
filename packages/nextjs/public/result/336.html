It holds no funds, makes no external calls, and (as deployed at this address) has no inheritance chain — every state-mutating function is scoped to msg.sender only. Given its size (95 lines, single contract, no external calls), this is a small-scope engagement per the audit methodology's model-selection rule (sonnet agents throughout).

[1] "Right to be forgotten" is not enforced — grantConsent has no deletion guard

Severity: Medium
Location: grantConsent() (line 68-72), checkDeletionRequest() modifier (line 51-54)
Origin: [both] — Phase 1: general (PG-1). Phase 2: invariant, trust-gap, flow-gap (3 independent FINDINGS, all tracing the identical exploit chain).

Description: The contract's own documentation (getPrivacyPolicy(), guarantee #4) states: "Right to be forgotten - stop future writes + off-chain deletion/redaction." A checkDeletionRequest modifier exists specifically to enforce the "stop future writes" half of that promise:

modifier checkDeletionRequest(address user) {
    require(deletionRequests[user] == 0, "User has requested data deletion");
    _;
}

But it is never applied to grantConsent() — the contract's only "write new data associated with a user" function:

function grantConsent(bytes32 purposeHash) external {
    require(purposeHash != bytes32(0), "Purpose hash required");
    userConsent[msg.sender][purposeHash] = true;
    emit ConsentGranted(msg.sender, purposeHash);
}

Proof of Concept:

  1. User calls requestDataDeletion() — deletionRequests[user] is set to block.timestamp + 30 days, DataDeletionRequested fires.
  2. In the very next call (or any time after, including past the 30-day window), the same user calls grantConsent(purposeHash) — succeeds unconditionally, userConsent[user][purposeHash] flips to true, ConsentGranted fires.
  3. Storage now holds a direct contradiction: deletionRequests[user] != 0 && userConsent[user][purposeHash] == true — a "future write" occurred exactly as the deletion request claims to prevent.

Not exploitable for fund loss (the contract holds no funds), but it is a genuine trust-model/correctness violation: the contract's own marketed privacy guarantee does not hold for the contract as actually deployed.

Recommendation: Apply checkDeletionRequest(msg.sender) to grantConsent(). Decide and document whether revokeConsent() should remain exempt (revocation only removes data rather than adding it, so arguably it should still be allowed post-deletion-request).

[2] Unsalted, deterministic purposeHash enables trivial dictionary attack, defeating the contract's stated privacy guarantee

Severity: Medium
Location: hashPurpose() (line 60-62), userConsent mapping, ConsentGranted/ConsentRevoked events
Origin: [phase1 only] — signatures-privacy agent. No phase-2 specialty specifically targets hash-predictability/privacy-leakage; re-verified directly against source in this synthesis.

Description:

function hashPurpose(string memory purpose) public pure returns (bytes32) {
    return keccak256(abi.encodePacked(purpose));
}

No salt, nonce, or per-user binding. Since purposeHash values are permanently public (mapping storage + indexed event topics) and the hashing scheme is public and trivial to reproduce off-chain, any observer can precompute a rainbow table over the realistic/known vocabulary of purpose strings (typically a small, fixed set exposed by the client's own frontend/docs) and instantly reverse every purposeHash ever emitted for any user — defeating the contract's own stated design intent ("we verify without extracting," "avoids writing user-provided freeform strings on-chain"). Because the hash isn't bound to the consenting address either, two different users consenting to the same purpose produce identical hashes, enabling trivial cross-user correlation even without dictionary reversal.

This is not a commit-reveal scheme (no reveal step exists) — the hash is used permanently as an opaque flag, so its confidentiality rests entirely on hash-inversion difficulty, which is near-zero for low-entropy, guessable purpose strings.

Proof of Concept: Enumerate the dApp's known purpose strings (from its own frontend/docs) → precompute keccak256 for each off-chain, no contract interaction needed → match against on-chain ConsentGranted event topics or userConsent reads → recover exactly which purposes any address consented to, for free.

Recommendation: If purpose confidentiality from on-chain observers is a real design goal, require the caller to supply keccak256(abi.encodePacked(purpose, salt)) with a client-generated high-entropy salt kept off-chain by the user/UI, rather than exposing a trivial one-argument hashPurpose(string) helper over the raw string. At minimum bind the hash to the user's address to remove cross-user linkability. Otherwise, correct the documentation to not claim purpose confidentiality the implementation doesn't provide.

[3] checkDeletionRequest and isDeletionEnforceable implement contradictory deletion semantics

Severity: Low
Location: checkDeletionRequest() modifier (line 51-54) vs. isDeletionEnforceable() (line 106-109)
Origin: [phase2 only] — trust-gap (FINDING), corroborating LEAD from asymmetry. Not surfaced by phase 1. Re-verified directly against source.

Description:

function isDeletionEnforceable(address user) public view returns (bool enforceable, uint256 effectiveAt) {
    effectiveAt = deletionRequests[user];
    enforceable = effectiveAt > 0 && block.timestamp >= effectiveAt;
}

isDeletionEnforceable correctly implements the documented 30-day grace period. But checkDeletionRequest — the modifier meant for the identical purpose, exported for composing modules to gate their own functions — instead reverts the instant deletionRequests[user] != 0, i.e. immediately at request time, 30 days before isDeletionEnforceable would agree the deletion is "in effect." Both read the same deletionRequests mapping but encode different thresholds for the same real-world question. requestDataDeletion()'s own NatSpec states "Data becomes enforceable after DATA_RETENTION_PERIOD" — checkDeletionRequest contradicts that promise by enforcing immediately.

Recommendation: Make checkDeletionRequest call isDeletionEnforceable(user) (or replicate its timestamp check) instead of the raw non-zero check, so both primitives agree with the documented 30-day grace period — or, if immediate lockout is actually the intended behavior, update the NatSpec on requestDataDeletion to say so and remove the "enforceable after" language.

[4] cancelDeletionRequest() allows silently reversing an already-enforced deletion, with no event trail

Severity: Low
Location: cancelDeletionRequest() (line 97-100)
Origin: [phase2 only] — flow-gap agent, full exploit chain traced directly in source. Not surfaced by phase 1. Re-verified directly against source in this synthesis.

Description:

function cancelDeletionRequest() external {
    require(deletionRequests[msg.sender] != 0, "No deletion request pending");
    deletionRequests[msg.sender] = 0;
}

The only guard checks that a request exists — it never checks block.timestamp against effectiveAt. A user can call this at any time, including long after isDeletionEnforceable() has already returned true and (per the contract's own documented off-chain contract) their data has already been purged/redacted off-chain. The reset is silent: deletionRequests[user] returns to 0, indistinguishable from a user who never requested deletion at all, and DataPermanentlyDeleted (declared but never emitted anywhere — see Finding #8) provides no on-chain marker that enforcement ever actually occurred.

Proof of Concept: User calls requestDataDeletion() at t=0. At t=31 days, isDeletionEnforceable() returns true; an off-chain service purges the user's records per the documented policy. At t=40 days, the same user calls cancelDeletionRequest() — succeeds unconditionally, silently resetting state to "no deletion ever happened," with no on-chain trace distinguishing this from a pre-enforcement change of mind.

Recommendation: Once isDeletionEnforceable(user) is true, either block cancelDeletionRequest (require(block.timestamp < deletionRequests[msg.sender])) or emit DataPermanentlyDeleted and transition to a distinct terminal state rather than allowing an indistinguishable silent reset.

[5] cancelDeletionRequest() emits no event (asymmetric vs. every other state-mutating function)

Severity: Low
Location: cancelDeletionRequest() (line 97-100)
Origin: [both] — Phase 1: general (PG-2, Info). Phase 2: asymmetry (FINDING), execution-trace and first-principles (corroborating leads) — 3 phase-2 agents total.

Description: grantConsent, revokeConsent, and requestDataDeletion all pair their storage write with an event. cancelDeletionRequest is the sole exception. Per the contract's own documented off-chain-consumer model, an event-driven redaction pipeline that reacts only to DataDeletionRequested has no signal that a user reversed their request.

Recommendation: Add event DataDeletionCancelled(address indexed user); and emit it in cancelDeletionRequest().

[6] requiresConsent/checkDeletionRequest modifiers decouple user from msg.sender — confused-deputy risk for future inheriting modules

Severity: Info (design risk for composability, not exploitable against this standalone deployment)
Location: requiresConsent() (line 46-49), checkDeletionRequest() (line 51-54)
Origin: [both] — Phase 1: access-control (framed as inert dead code). Phase 2: access-control, execution-trace, periphery, first-principles, flow-gap (5 agents — the single most-corroborated observation of the entire review, escalated to a forward-looking design-risk framing).

Description: Unlike every state-mutating function in this contract (all hard-scoped to msg.sender), both exported modifiers accept an arbitrary address user:

modifier requiresConsent(address user, bytes32 purposeHash) {
    require(userConsent[user][purposeHash], "User consent required");
    _;
}
modifier checkDeletionRequest(address user) {
    require(deletionRequests[user] == 0, "User has requested data deletion");
    _;
}

This is architecturally necessary for the contract's stated role as a "privacy floor for modules that inherit/compose it" (confirmed: ERC8004IdentityRegistry, ERC8004ReputationRegistry, and ERC8004ValidationRegistry elsewhere in the repo do inherit this contract, though those are out of scope here). But nothing enforces user == msg.sender anywhere in this base contract. Any future inheriting module that wires a caller-supplied (rather than msg.sender-derived) user into these modifiers — e.g. function f(address user) external requiresConsent(user, HASH) { ...acts on user's data... } — would let any attacker trigger the gated action against any address that happens to satisfy the consent/deletion condition. Since hasConsent/deletionRequests are public getters, an attacker can always self-grant consent for their own address and pass themselves as user in a mismatched context, or enumerate which real addresses already satisfy the check.

Recommendation: No action required for this deployed instance (the modifiers are inert here — no function in this file uses them). Given confirmed downstream inheritance elsewhere in the wider Vaultfire codebase, this observation should be carried forward into the audit of any contract that actually inherits PrivacyGuarantees — verify every inheriting function that uses requiresConsent/checkDeletionRequest independently confirms msg.sender == user (or has an explicit, deliberate delegation design with its own authorization check).

[7] getPrivacyPolicy() documentation overstates on-chain guarantees actually enforced

Severity: Info
Location: getPrivacyPolicy() (line 111-116)
Origin: [phase1 only] — general (PG-3). Same root cause as Finding #1.

Description: getPrivacyPolicy() is pure and its text is permanently baked into this deployment (the contract's own NatSpec states policy changes require a full redeploy). Since guarantee #4 ("Right to be forgotten - stop future writes") is not actually enforced on-chain (Finding #1), the policy text overstates what the deployed bytecode guarantees, permanently, for the life of this contract instance.

Recommendation: Fold into the fix for Finding #1 — either implement enforcement matching the claims, or soften the claims to accurately reflect current behavior.

[8] DataPermanentlyDeleted event declared but never emitted

Severity: Info
Location: event DataPermanentlyDeleted(address indexed user, uint256 timestamp) (line 41)
Origin: [both] — Phase 1: general (PG-1, noted inline). Phase 2: boundary, first-principles, trust-gap, invariant (4 independent leads).

Description: No function in the contract ever emits this event — not even a hypothetical finalization step once isDeletionEnforceable() becomes true. Off-chain indexers/compliance tooling that expect an on-chain signal for "deletion is now enforceable/permanent" will never see one; the transition can only be discovered by actively polling isDeletionEnforceable(). Directly relevant to Finding #4 — without this event, there is no on-chain trace distinguishing enforcement from a later silent cancellation.

Recommendation: Add a permissionless finalizeDeletion(address user) function that emits DataPermanentlyDeleted once isDeletionEnforceable(user) is true, giving downstream systems and Finding #4's fix a concrete on-chain checkpoint to key off.

What was checked and found sound

No exploitable access-control gap: no owner, no admin role, no parameter-update functions exist (PRIVACY_POLICY_VERSION/DATA_RETENTION_PERIOD are both constant by design), and every state-mutating function in this file is correctly scoped to msg.sender only — confirmed by both phases' dedicated access-control passes. No precision-math surface: the only arithmetic in the entire contract (block.timestamp + DATA_RETENTION_PERIOD) cannot realistically overflow under Solidity 0.8's checked arithmetic (confirmed independently by 2 agents across both phases). No economic/value-extraction surface — the contract holds no funds and makes no external calls, so reentrancy, sandwich, and fund-drain checklist classes are categorically inapplicable. No cross-user griefing or DoS surface — every mapping write is keyed strictly to msg.sender, architecturally ruling out one user affecting another's state. No abi.encodePacked collision risk in hashPurpose (single dynamic argument only, not the multi-argument pattern that class of bug requires).
