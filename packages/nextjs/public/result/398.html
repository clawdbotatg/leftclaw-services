Findings

[70] 1. Scope-write authorization has no continuity/snapshot — a poster change or task-id reuse in the external registry would let a new poster silently inherit control over another party's stored content

TaskScopeRegistry._requirePoster / TaskScopeRegistry._taskExists · Confidence: 70 · Severity: Low · Origin: [both] (phase1: access-control AccessControl-1; phase2: 10/12 agents on poster-continuity, 7/12 agents on id-recycling — same root cause)

Description
_requirePoster (L42-48) re-derives write authority fresh on every call via
ITaskRegistry(taskRegistry).getTask(taskId).poster == msg.sender (L45), and
_taskExists (L38-40) treats the entire valid-id space as the contiguous range
taskId > 0 && taskId <= taskRegistry.taskCount() (L39) with no per-id identity
check. _scopes[taskId] (L15) is written only by unconditional overwrite (L28) —
there is no snapshot of who authored the current value and no delete/clear path.
Two distinct upstream scenarios (both requiring specific, unconfirmed
ITaskRegistry behavior) would let this surface in practice:

  1. Poster reassignment mid-life. If a task's poster can change in taskRegistry
    (e.g. a transfer/reassignment mechanism), the new poster instantly and
    silently gains full overwrite rights over scope text an entirely different,
    prior poster wrote — with no event, flag, or on-chain marker distinguishing
    "current poster editing their own scope" from "new poster overwriting a
    stranger's."
  2. Task-id recycling. If a taskId can be retired and later reused for a
    logically distinct new task, scopeOf (L33-36) would keep returning the
    previous task's stored text to any reader querying the "new" task until its
    new poster happens to call setScope again — since _scopes is never cleared,
    only ever overwritten.

Every one of the 12 phase-2 attack agents that raised this (10 for mechanism 1, 7
for mechanism 2 — overlapping) explicitly could not construct a concrete exploit
from TaskScopeRegistry.sol alone, because both scenarios require assuming
behavior of ITaskRegistry, whose source was not supplied for this job. The
code-level fact — no continuity binding between "who is currently authorized to
write" and "who authored the currently-stored value" — is confirmed by direct
reading; the exploitability is contingent and unverified.

Proof of Concept (contingent, not demonstrable from in-scope code): Poster A
calls setScope(7, "original text") — succeeds. Assume (unconfirmed) taskRegistry
either reassigns task 7's poster to B, or closes task 7 and creates an unrelated new
task also assigned id 7 with poster B. B calls setScope(7, "B's text") —
_requirePoster reads the current poster (B), passes, and B's write silently
replaces A's content with no on-chain trace of the ownership change. Before B's
first call, any reader of scopeOf(7) also sees A's stale text presented as though
it belongs to B's task/tenure.

Fix
If taskRegistry guarantees poster immutability per task and never recycles ids,
state that explicitly as a load-bearing invariant in this contract's NatSpec (the
current comment implies but does not assert it). Otherwise:

+ mapping(uint256 => address) private _scopeAuthor;
+
  function setScope(uint256 taskId, string calldata scope) external override {
      _requirePoster(taskId);
      require(bytes(scope).length > 0, "TaskScope: empty scope");
      require(bytes(scope).length <= MAX_SCOPE_BYTES, "TaskScope: scope too long");

      _scopes[taskId] = scope;
+     _scopeAuthor[taskId] = msg.sender;
      emit TaskScopeSet(taskId, msg.sender, keccak256(bytes(scope)));
  }

This does not block a new legitimate poster from overwriting, but lets
scopeOf-consuming systems/readers detect an authorship change (_scopeAuthor[taskId] != currentPoster) and treat pre-handoff content as stale, without this contract needing to assume anything further about ITaskRegistry's internals.

[55] 2. _taskExists's range check assumes taskRegistry.taskCount() is monotonically non-decreasing; if it ever decreases, previously-valid, already-populated task ids become permanently unreadable/unwritable through this contract with no recovery path

TaskScopeRegistry._taskExists (used by both setScope and scopeOf) · Confidence: 55 · Severity: Info · Origin: [both] (phase1: access-control AccessControl-2; phase2: 5/12 agents)

Description
_taskExists (L38-40) defines existence as taskId > 0 && taskId <= taskRegistry.taskCount(),
recomputed live on every call with no historical high-water mark. If
taskRegistry.taskCount() is not guaranteed monotonically non-decreasing (e.g. task
cancellation, registry reset, or migration reducing the count), a taskId that
previously passed _taskExists — and may already have scope text stored via a prior
setScope — would start failing it. scopeOf (L34) would then revert
("TaskScope: unknown task") for a task whose data is still sitting in _scopes
(L15/28), and the legitimate poster would be blocked from calling setScope again
for that id, with taskRegistry being immutable (L10) and no setter to work
around it. This is an availability effect, not an authorization bypass, and is
entirely contingent on taskRegistry.taskCount()'s monotonicity, which this audit
could not confirm without its source.

Proof of Concept (contingent, not demonstrable from in-scope code): Poster A
calls setScope(50, "text") while taskCount() == 50 — succeeds. taskRegistry
state later changes (unconfirmed mechanism) such that taskCount() drops to 40.
scopeOf(50) now reverts despite _scopes[50] still holding A's text; A calling
setScope(50, ...) again also reverts.

Fix
Confirm with the taskRegistry team whether taskCount() is guaranteed
monotonically non-decreasing. If it is, no code change is needed — just document the
assumption explicitly. If it is not, track existence via a local high-water mark
(e.g. maxSeenTaskId, advanced opportunistically on setScope) rather than a live
range bound, so previously-valid tasks don't lose access to their own already-stored
data purely because the external counter moved backward.

[65] 3. Unconditional dependency on external taskRegistry is a single point of failure for the entire contract

TaskScopeRegistry._taskExists / _requirePoster (reached from both setScope and scopeOf) · Confidence: 65 · Severity: Low · Origin: [phase1 only] (evm-audit-dos)

Description
Every path in this contract makes an unconditional external call into the immutable
taskRegistry (taskCount() at L39, getTask() at L45) with no try/catch and no
fallback. If taskRegistry ever reverts unconditionally for any reason (paused,
bricked, a broken upgrade if it happens to sit behind a proxy on its own side), both
setScope and scopeOf become permanently unusable for every taskId, with no
on-chain recovery since taskRegistry has no setter (L10 is immutable).

Proof of Concept: taskRegistry becomes permanently reverting on
taskCount()/getTask() → every call into _taskExists/_requirePoster reverts →
setScope and scopeOf are dead for all ids, permanently, with no recovery path in
this contract.

Fix
Document as an explicit trust assumption in NatSpec. Rated Low rather than higher
because this mirrors standard "trust the core registry you're built on"
architecture rather than a defect introduced by this file, and any fix (a mutable
registry pointer, or a fallback bypassing the poster check on failure) trades this
risk for a worse one — centralization or an authorization bypass, respectively.
Re-examined for this report (phase-1-only lead, hybrid step): confirmed sound on a
targeted re-read; no phase-2 agent surfaced a stronger variant, so it stands
unchanged.

Roles. No Ownable/AccessControl, no owner/admin, no pause, no upgrade hook —
checked literally by every hunting agent, none present. taskRegistry (L10) is
immutable, set once at construction, never changeable. MAX_SCOPE_BYTES (L13) is a
compile-time constant (8192). The "poster" role is defined entirely by the
external taskRegistry contract; TaskScopeRegistry holds no independent record of
posters and re-derives the answer fresh on every setScope call.

Unguarded entrypoints. None. The sole state-changing entrypoint (setScope) is
gated by _requirePoster. scopeOf is an unrestricted, existence-gated public read
— by design, not a gap.
