Security Audit Report

BuidlGuidl Multisig — MultisigFactory + Multisig + Clones

Job ID: 294
Contract (factory): 0x21f03d2AdaEAaFe75e0C721bD1eBbC4C9aF9602E — Ethereum Mainnet
Scope: MultisigFactory.sol, Multisig.sol, Clones.sol (~510 LOC)
Methodology: Two-phase hybrid audit — Phase 1 ethskills breadth (checklist-driven, 8 specialty agents) + Phase 2 pashov depth (12 attacker-mindset agents, blind); Turn 3 reconciliation.
Date: 2026-07-05

Executive Summary

The BuidlGuidl Multisig is a well-structured M-of-N multisig that supports both EOA (ECDSA/secp256k1) and WebAuthn passkey (secp256r1) signers. It deploys EIP-1167 minimal proxy clones via CREATE2 and implements ERC-1271 for off-chain signature verification.

The core signing and replay-protection logic is sound: getExecHash and getBatchExecHash bind signatures to chainid, contract address, and nonce; the strictly-ascending sig.signer sort prevents duplicates; and the nonReentrant transient guard blocks nested execution. No path was found to forge signatures or bypass threshold verification against an initialized clone.

Two findings require action before production use:

  • The implementation contract's permanently-zero threshold allows anyone to drain any assets sent to it.
  • Passkey (WebAuthn) signatures share an identical challenge format between execTransaction and isValidSignature, enabling cross-domain replay from a malicious ERC-1271 flow into execTransaction.

Additionally, a long-standing design tension in the EOA ERC-1271 path means that standard wallet personal_sign flows silently fail for ERC-1271 consumers.

Findings

[H-1] Implementation threshold == 0 allows anyone to drain assets and forge ERC-1271 signatures [both]

Severity: High
Origin: Phase 1 [G-1] (Low) → elevated by Phase 2 F-P2-1 with full exploit proof
Contracts: Multisig.sol — execTransaction, execBatchTransaction, isValidSignature

Root cause: The implementation contract's constructor calls _disableInitializers() to prevent initialize() from running, but this leaves threshold = 0 and _signers.length = 0 in the implementation's storage. The signature guard if (signatures.length < threshold) revert ThresholdNotMet() evaluates 0 < 0 = false and does not revert. The subsequent loop over zero signatures executes zero iterations. Execution falls through to nonce++ and target.call{value: value}(data).

Impact:

  • Any ETH accidentally sent to the implementation address is drainable by anyone via execTransaction(attacker, balance, "", type(uint256).max, []).
  • isValidSignature(anyHash, abi.encode(new Signature[](0))) returns the ERC-1271 magic value 0x1626ba7e, making the implementation a universal signer that approves any hash — potentially abused by protocols querying the wrong address.
  • The implementation has receive() external payable {} and all three token-received hooks, so it silently accepts ETH and NFTs pushed via safeTransferFrom.

Proof of concept:

1. Attacker sends 1 ETH to implementation (or ETH is forced via pre-fund/selfdestruct).
2. Attacker calls:
   Multisig(implementation).execTransaction(
       attacker, 1 ether, "", type(uint256).max, new Signature[](0)
   )
3. _verifySignatures: signatures.length(0) < threshold(0) → 0 < 0 → false. Pass.
4. Loop: 0 iterations. Returns.
5. nonce++ → nonce=1 in impl storage.
6. implementation.call{value: 1 ether}("") → attacker receives 1 ETH.

Fix:

constructor() {
    _disableInitializers();
    threshold = type(uint256).max; // block execution on uninitialized impl
}

Or add if (threshold == 0) revert ThresholdNotMet(); at the top of execTransaction, execBatchTransaction, and isValidSignature.

[M-1] EOA ERC-1271 path uses raw hash; standard wallet personal_sign silently rejected [both]

Severity: Medium
Origin: Phase 1 [S-1] (Medium), confirmed by Phase 2 Agent 7
Contract: Multisig.sol — isValidSignature

Root cause: execTransaction/execBatchTransaction verify EOA signatures over MessageHashUtils.toEthSignedMessageHash(hash) (the EIP-191 personal_sign-prefixed digest). isValidSignature verifies against the raw hash with no prefix. Any wallet using personal_sign/eth_sign/signMessage produces a signature over the prefixed digest — but isValidSignature recovers against the raw hash, yielding a garbage address and returning 0xffffffff. This is intentional per the M-2 comment (EIP-712 typed-data flows pass a pre-prepared digest), but the practical result is that standard wallet flows are incompatible with this contract's ERC-1271 interface.

Impact: DeFi protocols (Permit2, CoW Swap, OpenSea, limit-order aggregators) that call isValidSignature with a hash the signer approved via personal_sign will silently reject the signature even though the signer intended approval. The signer receives no error; the protocol simply ignores the multisig's authorization.

Proof of concept:

1. Protocol asks Alice to sign hash H via personal_sign.
   Wallet produces σ = sign(privKey, keccak256("\x19Ethereum Signed Message:\n32" ‖ H))
2. Protocol calls isValidSignature(H, abi.encode([{EOA, alice, σ}])).
3. ECDSA.tryRecover(H, σ) recovers addr ≠ alice → returns 0xffffffff.

Fix (backward compatible — try raw, fall back to prefixed):

(address recovered, ECDSA.RecoverError err,) = ECDSA.tryRecover(hash, sig.data);
if (err != ECDSA.RecoverError.NoError || recovered != sig.signer) {
    (recovered, err,) = ECDSA.tryRecover(
        MessageHashUtils.toEthSignedMessageHash(hash), sig.data);
    if (err != ECDSA.RecoverError.NoError || recovered != sig.signer) return 0xffffffff;
}

[M-2] Passkey challenge identical in execTransaction and isValidSignature — cross-domain replay [phase2]

Severity: Medium
Origin: Phase 2 F-P2-2 (new)
Contract: Multisig.sol — _verifySignatures, isValidSignature

Root cause: Both execTransaction and isValidSignature construct the WebAuthn challenge identically:

bytes memory challenge = abi.encodePacked(hash);
WebAuthn.verify(challenge, auth, qx, qy)

A WebAuthnAuth signed over challenge H validates in both functions. By contrast, the EOA path already has accidental domain separation: execTransaction uses toEthSignedMessageHash(hash) while isValidSignature uses raw hash. Passkeys receive no domain separation.

Impact: An attacker can trick threshold-many passkey signers into signing a hash via a malicious dApp's "sign-in" ERC-1271 flow, then replay those signatures to drain the multisig. The attack is directly proportional to difficulty of threshold: threshold=1 requires a single user to visit the phishing page; threshold=2 requires two users.

Proof of concept:

1. Attacker picks (target=attacker, value=balance, data="", deadline=MAX).
2. Computes H = getExecHash(target, value, data, deadline) — deterministic from public nonce.
3. Deploys phishing dApp: "Authenticate with your passkey" → internally calls
   multisig.isValidSignature(H, ...) with the user's WebAuthn sig as part of the flow.
4. Each passkey holder's authenticator signs challenge = abi.encodePacked(H).
5. Attacker collects threshold-many WebAuthnAuth structures.
6. Calls execTransaction(target, value, data, deadline, sigStructs).
7. _verifySignatures: challenge = abi.encodePacked(H) — identical to what authenticator signed.
   WebAuthn.verify returns true. All checks pass. target.call drains balance.

Note: The EOA path is NOT affected (different signed message structures between the two paths).

Fix:

// In _verifySignatures (execution path — add a domain prefix):
bytes memory challenge = abi.encodePacked(bytes32("MULTISIG_EXEC_V1"), hash);

// In isValidSignature (ERC-1271 path — keep current raw bytes):
bytes memory challenge = abi.encodePacked(hash);

This ensures passkey signatures issued under an ERC-1271 authentication flow cannot be replayed to authorize an execTransaction.

[L-1] Duplicate credentialIdHash corrupts reverse lookup; removeSigner deletes survivor's entry [both]

Severity: Low
Origin: Phase 1 [G-3/A-4/V-4], confirmed by all 12 Phase 2 agents
Contract: Multisig.sol — _addSigner, removeSigner

Root cause: _addSigner blindly writes credentialIdToAddress[credId] = signer without checking whether credId already maps to a different active signer. removeSigner then deletes credentialIdToAddress[credentialIdOf[signer]] without checking whether that mapping still belongs to the signer being removed.

Proof of concept:

1. Register P1 with credId=H → credentialIdToAddress[H]=P1, credentialIdOf[P1]=H.
2. Register P2 with credId=H → credentialIdToAddress[H]=P2 (overwritten). credentialIdOf[P1] still=H.
3. removeSigner(P1): reads credentialIdOf[P1]=H → delete credentialIdToAddress[H].
4. P2 is active signer. getPasskeyByCredentialId(H) returns (address(0), 0, 0).

Impact: Off-chain login flow (credential-ID based signer lookup) silently breaks for an active passkey signer. The signer can still sign transactions — only the reverse lookup is affected. Requires a governance action that intentionally or accidentally registers two passkeys with the same credential ID hash.

Fix: Reject re-use of a non-zero credId in _addSigner:

if (credId != bytes32(0)) {
    if (credentialIdToAddress[credId] != address(0)) revert AlreadySigner();
    credentialIdToAddress[credId] = signer;
    credentialIdOf[signer] = credId;
}

Or in removeSigner, guard the delete: if (credentialIdToAddress[credId] == signer) delete credentialIdToAddress[credId];

[L-2] isValidSignature reverts on malformed signature bytes instead of returning 0xffffffff [both]

Severity: Low
Origin: Phase 1 [S-4], confirmed by Phase 2 agents 5, 9
Contract: Multisig.sol — isValidSignature

Root cause: abi.decode(signatures, (Signature[])) on line 329 and abi.decode(sig.data, (bytes32, bytes32, WebAuthn.WebAuthnAuth)) inside the loop revert on malformed input. ERC-1271 consumers that invoke via the high-level Solidity interface (rather than low-level staticcall) will propagate the revert rather than receiving a clean "invalid" response.

Fix: Wrap the outer decode in a try/catch (via external self-call helper) and return 0xffffffff on failure.

[L-3] Threshold reduction retroactively devalues pre-signed future-nonce authorizations [phase2]

Severity: Low
Origin: Phase 2 L-P2-3 (new, Agent 11)
Contract: Multisig.sol — changeThreshold, _verifySignatures

Root cause: getExecHash and getBatchExecHash commit to nonce but not to threshold. _verifySignatures reads threshold at execution time. A changeThreshold reduction between signing and submission allows a subset of already-collected signatures to authorize an action the original signers intended to require more approvals for.

Proof of concept:

1. threshold=3, signers {A,B,C} pre-sign execHash_X for nonce=7.
2. Governance lowers threshold to 1 at nonce=5. nonce advances to 6, then 7.
3. Attacker holds any ONE of the three pre-collected sigs for execHash_X.
4. Submits execTransaction with 1 sig. signatures.length(1) >= threshold(1). Executes.

Impact: Primarily affects governance workflows where signers pre-sign for future nonces. Common in automated multisig orchestration. Requires threshold reduction + pre-existing off-chain signature collection.

Fix: Include threshold in getExecHash/getBatchExecHash:

keccak256(abi.encode(block.chainid, address(this), nonce, threshold, deadline, target, value, keccak256(data)))

[L-4] execTransaction target returndata unbounded — returndata bomb possible [both]

Severity: Low
Origin: Phase 1 [D-1/B-2], confirmed by Phase 2 Agent 7
Contract: Multisig.sol — execTransaction, execBatchTransaction

Root cause: (bool ok, bytes memory ret) = target.call{value: value}(data) copies the full returndata into memory. A malicious target (authorized by threshold sigs) can return megabytes, causing quadratic memory expansion gas cost and reverting OOG. In execBatchTransaction, each call's returndata is also stored in results[i], compounding the effect.

Fix: Cap returndata copy:

assembly ("memory-safe") {
    let sz := returndatasize()
    if gt(sz, 0x1000) { sz := 0x1000 }  // 4 KB cap
    let retPtr := mload(0x40)
    mstore(0x40, add(retPtr, add(sz, 0x20)))
    mstore(retPtr, sz)
    returndatacopy(add(retPtr, 0x20), 0, sz)
    ret := retPtr
}

[L-5] Unbounded signer set makes removeSigner O(N) — DoS risk at scale [phase1]

Severity: Low
Origin: Phase 1 [D-2]
Contract: Multisig.sol — _addSigner, removeSigner

Root cause: No MAX_SIGNERS cap is enforced. removeSigner performs an O(N) linear scan of _signers[]. On L2s where storage is cheap, a colluding quorum can inflate _signers to make removal gas-prohibitive.

Fix: Add if (_signers.length >= MAX_SIGNERS) revert TooManySigners(); (suggested cap: 50–100). Consider a signer → index mapping for O(1) removal.

[L-6] No emergency recovery path if quorum is lost [phase1]

Severity: Low
Origin: Phase 1 [A-1]
Contract: Multisig.sol

Root cause: All admin functions (addEoaSigner, removeSigner, changeThreshold) are gated behind onlySelf reachable only through execTransaction at threshold. If enough signers lose keys, all assets are permanently locked with no recovery path.

Fix: Consider an optional guardian with a long timelock (≥30 days) vetoable by any current signer. At minimum, document this risk prominently in user-facing UX.

[L-7] ERC-1271 signer-set changes retroactively flip attestation validity [phase1]

Severity: Low
Origin: Phase 1 [S-3]
Contract: Multisig.sol — isValidSignature

Root cause: isValidSignature reads live signerInfo and threshold. A 2-of-3 signed limit order valid today becomes invalid if threshold is raised or a signer is removed — or a previously-invalid 1-sig submission becomes valid after threshold reduction.

Fix: Document that ERC-1271 attestations must be verified at settlement. Optionally commit to a signer-set fingerprint in the ERC-1271 digest.

[L-8] No EIP-712 domain separator — signed digests expose no human-readable context [phase1]

Severity: Low
Origin: Phase 1 [S-2]
Contract: Multisig.sol — getExecHash, getBatchExecHash

Root cause: The exec hash includes chainid and address(this) but no protocol name, version, or type-string hash. Hardware wallets and browser extension wallets present an opaque 32-byte blob; signers cannot inspect what they are authorizing.

Fix: Adopt EIP-712. Define TxRequest and BatchTxRequest typed structs and use _hashTypedDataV4(structHash).

[L-9] Signature verification logic duplicated between execution and ERC-1271 paths [phase1]

Severity: Low
Origin: Phase 1 [S-5]
Contract: Multisig.sol — _verifySignatures, isValidSignature

Root cause: Two near-identical loops differ in three ways: revert vs. return, personal_sign vs. raw hash, calldata vs. memory. Future fixes (malleability policy, WebAuthn UV flag changes, new signer types) must be applied to both paths independently. Divergence between parallel verification paths is a common source of multisig vulnerabilities.

Fix: Extract _verifySigsCore(bytes32 digest, Signature[] memory sigs) internal view returns (bool) and delegate from both callers.

[L-10] WebAuthn requireUV=true silently rejects hardware tokens without PIN/biometric [phase1]

Severity: Low
Origin: Phase 1 [S-6]
Contract: Multisig.sol — _verifySignatures, isValidSignature

Root cause: WebAuthn.verify(challenge, auth, qx, qy) defaults to requireUV=true. YubiKeys and other hardware tokens configured without PIN produce flags = 0x01 (UP only, UV=0) — always rejected even though the user physically confirmed the transaction.

Fix: Keep requireUV=true for security, but document the requirement in signer-registration UX. Consider a per-signer requireUV flag in SignerInfo if flexibility is needed.

[L-11] Batch execution can atomically restructure the entire signer set in one signing round [both]

Severity: Low
Origin: Phase 1 [V-1], confirmed by Phase 2 Agent 7
Contract: Multisig.sol — execBatchTransaction

Root cause: A signed batch can contain addEoaSigner(attacker), changeThreshold(1), removeSigner(A), removeSigner(B) in sequence — all validated once against the pre-batch signer set. All admin ops are gated only by onlySelf; the batch loop does not re-verify signatures between calls.

Impact: A social-engineering attack (or compromised co-signer) that obtains threshold approval for a large "routine" batch can take full control in a single signing round.

Fix: Consider a timelock on governance selectors, or forbid governance calls within execBatchTransaction.

[L-12] Threshold=1 with 1 signer is deployable — effectively a single-key wallet [phase1]

Severity: Low
Origin: Phase 1 [V-2]
Contract: Multisig.sol — initialize, changeThreshold

Root cause: No minimum threshold or minimum signer count is enforced beyond threshold >= 1. Combined with L-11, an attacker who gains one threshold signing round can reduce the signer set to 1-of-1.

Fix: Optionally enforce if (_threshold < 2 || total < 2) revert InvalidThreshold();.

Info Severity

[I-1] Clones assembly advances FMP by 0x40 but writes to 0x48 — memory-safe annotation technically violated [both]

Origin: Phase 1 [B-1], confirmed by Phase 2 agents 1, 6, 7
The third mstore(add(ptr, 0x28), ...) writes to ptr+0x28..ptr+0x47. FMP is advanced to ptr+0x40, leaving 8 written bytes above the FMP. Benign (they are zero-padding never read after CREATE2), but violates the compiler contract declared by memory-safe. Fix: Advance FMP to add(ptr, 0x60) or remove the FMP update (bytes are ephemeral).

[I-2] MultisigCreated event omits passkey signers [both]

Origin: Phase 1 [V-6], confirmed by Phase 2 Agent 8
Event emits eoaSigners but not passkeyQxs, passkeyQys, or credentialIdHashes. Off-chain indexers relying only on the event will miss passkey-only multisigs. Fix: Emit passkey data, or at minimum emit a hash of the passkey set.

[I-3] address(this) accepted as EOA signer — permanently dead slot [both]

Origin: Phase 1 [A-2], confirmed by Phase 2 Agents 7, 11
_addSigner rejects only address(0); a signer at the multisig's own address has no private key. Fix: if (signer.code.length > 0 || signer == address(this)) revert InvalidSigner();

[I-4] No on-curve validation for passkey coordinates [phase2]

Origin: Phase 2 L-P2-5 (Agents 1, 4)
initialize and addPasskeySigner reject qx == 0 || qy == 0 but do not verify (qx, qy) is a valid secp256r1 point. Off-curve inputs create permanently unusable signer slots that count toward threshold. Fix: Add a P-256 point-on-curve check at registration.

[I-5] Nonce not consumed on failed execution — signatures remain reusable [phase2]

Origin: Phase 2 L-P2-8 (Agent 7)
When target.call fails, _bubbleRevert reverts the transaction including nonce++. Pre-collected signatures remain valid for the same nonce until deadline expires. Differs from Gnosis Safe which burns nonce on failure. Recommendation: Use short deadlines when the action is time-sensitive.

[I-6] ReentrancyGuardTransient and PUSH0 require Cancun-capable chains [phase1]

Origin: Phase 1 [G-7]
Deploying on pre-Cancun chains (or some L2s without EIP-1153 support) will break reentrancy protection. Fix: Verify chain compatibility before deployment.

[I-7] Factory allows anyone to deploy a clone with arbitrary third-party signers [phase1]

Origin: Phase 1 [A-5]
Anyone can deploy a multisig listing any EOA as a signer. No informed consent from listed signers. Registry pollution / phishing vector. Recommendation: Document in UX.

[I-8] getExecHash reads live nonce — integrators must track nonce off-chain for pre-signing [phase1]

Origin: Phase 1 [S-8]
Pre-computing future execution hashes requires off-chain nonce tracking. Recommendation: Provide a view function that accepts an explicit nonce parameter.

Areas Verified Clean

The following attack surfaces were investigated across both phases and found secure:

  • Signature replay — getExecHash and getBatchExecHash embed block.chainid and address(this); signatures are chain- and contract-specific.
  • Cross-format collision — getExecHash encodes 7 fields (224 bytes encoded); getBatchExecHash encodes 5 fields (160 bytes). Different abi.encode lengths preclude cross-format hash collision.
  • EOA cross-path replay — execTransaction uses personal_sign prefix; isValidSignature uses raw hash. Bridging requires a keccak256 preimage — computationally infeasible.
  • Signer type confusion — signerInfo[addr].qx discriminates EOA (qx=0) from passkey (qx≠0); SignerTypeMismatch revert if types don't match. The passkey qx/qy in the signature payload is verified against the registered values.
  • Front-run clone address capture — Factory's _effectiveSalt = keccak256(msg.sender, salt) namespaces addresses to the deployer. Different callers cannot collide.
  • Initialization front-run — cloneDeterministic + initialize are called atomically in a single transaction; no insertion window.
  • Reentrancy — nonReentrant transient guard on both exec functions shares one slot, blocking cross-function re-entry. nonce++ precedes external call.
  • Threshold ≤ signerCount invariant — Maintained by all writers: initialize, _addSigner, removeSigner, changeThreshold.
  • Underflow in removeSigner — _signers.length - 1 < threshold check guards against underflow; info.exists ensures length >= 1.
  • Clones initcode integrity — Both cloneDeterministic and predictDeterministicAddress assemble identical 55-byte EIP-1167 proxy bytecode; CREATE2 address prediction is consistent.
