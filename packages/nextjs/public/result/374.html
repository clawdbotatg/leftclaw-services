C-1 — Graduation LP add with zero slippage + no pair check → ~90%-of-raise siphon

Severity: Critical · Origin: [both] (phase1 M-1 "Medium/potentially High"; phase2 #1 Critical) · _completeBonding

Source (_completeBonding, lines 215–226):

token.approve(address(uniswapRouter), tokensForLiquidity);
(uint256 amountToken, uint256 amountETH, uint256 liquidity) = uniswapRouter.addLiquidityETH{
    value: ethForLiquidity
}(
    address(token),
    tokensForLiquidity,
    0,               // amountTokenMin
    0,               // amountETHMin
    address(this),
    block.timestamp + 300
);

Both amountTokenMin and amountETHMin are hardcoded 0 and the contract never creates or checks the pair before adding liquidity. The token address is public before graduation (deployed in the curve constructor line 52; also computable via computeTokenAddress lines 298–314), and UniswapV2Factory.createPair is permissionless.

Exploit path (unprivileged, walked end-to-end):

  1. Attacker buys one whole token from the curve early (buyTokens, cheap near curve start — price ≈ totalETHCollected/tokenBalance).
  2. Attacker calls createPair(token, WETH) and seeds it skewed: reserveToken = 1 wei, reserveWETH = 1e18. sqrt(1·1e18) = 1e9 > MINIMUM_LIQUIDITY, so the mint succeeds.
  3. A later organic buy tips totalETHRaised to 7000e18 and runs _completeBonding (line 162→196). With ethForLiquidity = (contractETH·9000)/10000 ≈ 4455 ETH (line 201), Uniswap's _addLiquidity computes amountTokenOptimal = quote(4455e18, reserveWETH=1e18, reserveToken=1) ≈ 4455 wei. The assert(amountTokenOptimal <= amountTokenDesired) passes, amountETHMin=0 never bites, and the router deposits the full 4455 ETH against ~4455 wei of token. msg.value is fully consumed, so no refund fires.
  4. Pool now holds ~4456 wei token / ~4456 ETH. Attacker swaps their whole token in and extracts ≈ 4443 ETH (getAmountOut(1e18, 4456, 4456e18)).

Net theft ≈ 90% of every completed raise, for the cost of a dust token + gas. The contract's LP is sent to address(this) and treated as permanently locked (comment line 235), so the protocol cannot even withdraw to recover.

Fix (verbatim from phase2 — reject a pre-seeded pool and set real mins):

-        token.approve(address(uniswapRouter), tokensForLiquidity);
-
-        (uint256 amountToken, uint256 amountETH, uint256 liquidity) = uniswapRouter.addLiquidityETH{
-            value: ethForLiquidity
-        }(
-            address(token),
-            tokensForLiquidity,
-            0,
-            0,
-            address(this),
-            block.timestamp + 300
-        );
+        address pair = IUniswapV2Factory(uniswapRouter.factory())
+            .getPair(address(token), uniswapRouter.WETH());
+        require(pair == address(0) || IERC20(address(token)).balanceOf(pair) == 0, "Pair pre-seeded");
+
+        token.approve(address(uniswapRouter), tokensForLiquidity);
+
+        (uint256 amountToken, uint256 amountETH, uint256 liquidity) = uniswapRouter.addLiquidityETH{
+            value: ethForLiquidity
+        }(
+            address(token),
+            tokensForLiquidity,
+            (tokensForLiquidity * 99) / 100,
+            (ethForLiquidity   * 99) / 100,
+            address(this),
+            block.timestamp + 300
+        );

Better still: create the pair in the constructor so the curve always sets the initial price (this also closes L-4).

H-1 — Single hardcoded EOA can drain sale ETH, seize the sale token, and pull the "locked-forever" LP

Severity: High (centralization / deceptive lock) · Origin: [both] (phase1 H-1; phase2 #2) · emergencyWithdrawETH / emergencyWithdrawTokens

Source (lines 30–31, 60–76):

address public constant treasury          = 0xe479cf6De426026f984c87177DA2C10A4183a2F9;
address public constant EMERGENCY_WALLET  = 0xe479cf6De426026f984c87177DA2C10A4183a2F9;
...
function emergencyWithdrawETH() external {
    require(msg.sender == EMERGENCY_WALLET, "Only emergency wallet");
    uint256 balance = address(this).balance;
    ...
    (bool sent,) = EMERGENCY_WALLET.call{value: balance}("");
}
function emergencyWithdrawTokens(address tokenAddress) external {
    require(msg.sender == EMERGENCY_WALLET, "Only emergency wallet");
    ...
    require(tokenToWithdraw.transfer(EMERGENCY_WALLET, balance), "Token transfer failed");
}

EMERGENCY_WALLET == treasury is a single constant EOA with no timelock, no multisig, and no state gate. That one key can seize user funds three ways:

  • Mid-sale ETH drain: during an active sale each buy leaves ethAfterTax in the contract (lines 144, 148). emergencyWithdrawETH() empties it; every subsequent sellTokens then reverts on require(ethAmount <= address(this).balance) (line 181) — holders are frozen out with tokens and no exit. Because the withdraw doesn't touch totalETHCollected, the curve keeps quoting prices as if the ETH were present and buyers can keep depositing into an already-drained contract.
  • LP seizure: after _completeBonding, the LP tokens sit at address(this) (line 224). emergencyWithdrawTokens(pairAddress) ships them to the wallet → removeLiquidity drains the pool backing every holder. This directly refutes the "Remaining tokens stay locked in this contract forever" claim (line 235).
  • Inventory seizure: emergencyWithdrawTokens(address(token)) pulls the curve's own unsold sale inventory, bricking buyTokens/_completeBonding.

Walkability: requires the privileged EMERGENCY_WALLET key — this is a centralization/trusted-actor path, not an unprivileged exploit. It is kept at High (not Critical) because it is a concrete, one-transaction fund-seizure against depositors that contradicts a stated security property (the "locked forever" comment), i.e. more than a routine admin-key nicety.

Fix (phase2):

     function emergencyWithdrawTokens(address tokenAddress) external {
         require(msg.sender == EMERGENCY_WALLET, "Only emergency wallet");
+        require(tokenAddress != address(token), "Cannot pull sale token");

     function emergencyWithdrawETH() external {
         require(msg.sender == EMERGENCY_WALLET, "Only emergency wallet");
+        require(bondingComplete, "Sale active");

Send LP to a burn/locker instead of address(this) (line 224), gate these behind a timelock+multisig, and at minimum correct the "locked forever" comment while these functions exist.

M-1 — CREATE2 salt unbound to caller → front-run vanity address, hijack deployer-tax role, grief creators

Severity: Medium (front-running / griefing + tax theft) · Origin: [phase2: agent 3], enabled by phase1 I-2 · createBonding

Source (line 323, and tokenDeployer line 51):

BondingCurveFinal2 bondingContract = new BondingCurveFinal2{salt: salt}(name, symbol);
...
constructor(...) { tokenDeployer = tx.origin; ... }

The deployed address is f(factory, salt, keccak(creationCode ‖ abi.encode(name,symbol))) (getInitCodeHash lines 288–295) — no binding to msg.sender. The deployer-tax recipient is set separately to tx.origin.

Exploit path (re-examined, kept):

  1. A project mines a vanity salt S (the getInitCodeHash/computeTokenAddress helpers exist for exactly this backend salt-miner) and the victim broadcasts createBonding("Foo","FOO",S).
  2. Attacker copies the tuple (name, symbol, S), resubmits with higher gas, lands first, and deploys at the vanity address with tokenDeployer = tx.origin = attacker (line 51).
  3. The victim's tx reverts (CREATE2 to an occupied address), and the attacker collects the 30% DEPLOYER_TAX on every buy/sell of that token thereafter (lines 80, 86).

Even with a random (non-vanity) salt this is a reliable griefing DoS of any createBonding — front-run the tuple, victim reverts. Medium is appropriate: concrete economic gain (tax stream) + reliable DoS, but conditioned on observing the victim's tx and winning the ordering race.

Fix (phase2 — bind the salt to the caller):

-        BondingCurveFinal2 bondingContract = new BondingCurveFinal2{salt: salt}(name, symbol);
+        bytes32 actualSalt = keccak256(abi.encodePacked(msg.sender, salt));
+        BondingCurveFinal2 bondingContract = new BondingCurveFinal2{salt: actualSalt}(name, symbol);

Mirror the change in computeTokenAddress (add a creator param, hash keccak256(creator‖salt)) so the miner mines over a salt only that creator can reproduce.

L-1 — tokenDeployer = tx.origin misdirects the deployer-tax stream

Severity: Low (downgraded from phase1 Medium) · Origin: [both] (phase1 M-2; phase2 lead) · constructor line 51

tokenDeployer = tx.origin; (line 51). Because the curve is always deployed through createBonding (line 323), tx.origin is whichever EOA originated the transaction. Routed through a relayer, 4337 paymaster, multisig, or batching router, the 30% deployer-tax stream (line 86) is permanently bound to the relaying EOA rather than the intended creator, and smart-contract-account creators are mis-set.

Walkability: no unprivileged theft on its own — the tax recipient is fixed at deploy — so this is a correctness/attribution foot-gun, not a fund-drain; hence Low, not Medium. The adversarial escalation (an attacker deliberately becoming tokenDeployer) is captured in M-1. Fix: thread the intended deployer from the factory as a constructor arg (msg.sender), not tx.origin.

L-2 — Overshoot refund paid to msg.sender reverts a factory-seeded over-target buy

Severity: Low · Origin: [both] (phase1 L-2; phase2 #5) · buyTokensFor

Source (lines 156–160; auto-buy line 331–333):

if (ethToRefund > 0) {
    (bool success,) = msg.sender.call{value: ethToRefund}("");
    require(success, "Refund failed");
    emit ExcessEthRefunded(msg.sender, ethToRefund);
}

createBonding calls bondingContract.buyTokensFor{value: msg.value}(0, msg.sender) (line 332), so inside the curve msg.sender is the factory, which has no receive/payable fallback. If that seed buy overshoots BONDING_TARGET + VIRTUAL_ETH (7000 ETH), the refund .call fails and require(success, "Refund failed") reverts the whole createBonding.

Walkability: requires a single createBonding with msg.value > 5000 ETH — economically near-unreachable, and no funds are lost (it reverts). A latent trap for any contract integrator that buys-for-a-recipient across the cap. Low. Fix (phase2): refund recipient, not msg.sender:

-            (bool success,) = msg.sender.call{value: ethToRefund}("");
+            (bool success,) = recipient.call{value: ethToRefund}("");

L-3 — totalETHRaised counts pre-tax + virtual ETH → early graduation with less real backing

Severity: Low (accounting correctness) · Origin: [both] (phase1 L-1; phase2 lead) · buyTokensFor / _completeBonding

Buys increment totalETHRaised by the pre-tax ethToUse (line 149, via newRaised) but totalETHCollected by the post-tax ethAfterTax (line 148); sells decrement both by the same gross curve ethAmount (lines 184–185). The graduation trigger compares totalETHRaised (which also seeds VIRTUAL_ETH at line 57) to BONDING_TARGET + VIRTUAL_ETH (lines 134, 162). Consequences:

  • The curve graduates having collected less real ETH than the nominal 5000-ETH target — organic backing at graduation is ~4950 ETH, and each buy→sell round trip drifts totalETHRaised above totalETHCollected by the tax delta, pushing graduation earlier.
  • The LP is funded from real balance (ethForLiquidity derives from address(this).balance, line 199/201), so the shortfall lands on liquidity depth, not on an underflow. No underflow found (totalETHRaised ≥ totalETHCollected ≥ VIRTUAL_ETH holds); the drift is bounded and self-limiting (moving totalETHRaised costs ~2× in tax). Low. Fix: gate completion on totalETHCollected (or address(this).balance), not the gross totalETHRaised.

L-4 — Graduation atomically coupled to the LP add → stall one buy short if addLiquidityETH reverts

Severity: Low (liveness) · Origin: [phase2: agent 4], demoted from Medium · _completeBonding

bondingComplete = true (line 197) and the addLiquidityETH call (lines 217–226) run in the same transaction as the crossing buyer's buyTokensFor; the cap clamp (lines 134–138) forces every over-target buy onto exactly 7000e18, so every completing buy runs _completeBonding. If the LP add reverts, the buy reverts and the curve can never graduate (funds are not locked — sells still work while !bondingComplete).

Re-examination → demotion: I could not construct a cheap, unprivileged forced revert. With amountTokenMin=amountETHMin=0, a pre-seeded pool does not revert (that is exactly the C-1 siphon path). Forcing INSUFFICIENT_LIQUIDITY_MINTED would require the attacker to sink an unrealistic amount of real WETH so the contract's ~4455-ETH deposit mints 0 LP. Phase 2 itself rated this at the "promotion floor" and noted no concrete revert set was built. The realistic trigger is a misconfigured/wrong hardcoded router (see I-3) or a transient router issue — a deployment-config liveness risk, not an attacker primitive. Hence Low. Fix: decouple completion from the LP add (mark complete, seed liquidity via a separate retryable call) or create the pair in the constructor — both also close C-1.

L-5 — Factory changeCreateState centralization lever + a second, distinct emergency-wallet key

Severity: Low (centralization) · Origin: [phase1: access-control] (L-3), confirmed in source · changeCreateState

Source (lines 245, 257–260):

address public constant EMERGENCY_WALLET = 0xD0Be6F16545EcFC6FF719116D358e02Ee1D70D91;
...
function changeCreateState(bool isEnabled) external {
    require(msg.sender == EMERGENCY_WALLET, "Only emergency wallet");
    createEnabled = isEnabled;
}

The factory's EMERGENCY_WALLET (0xD0Be…) can flip createEnabled to halt all new launches at will, with no timelock. Note it is a different address from the curve's EMERGENCY_WALLET/treasury (0xe479…, lines 30–31) — this doubles the trusted-key surface; confirm the split is intentional. The flag only gates new createBonding (line 321); existing curves are unaffected. Low (centralization, no direct fund path).

Informational

  • I-1 — Floating pragma ^0.8.0 (line 2). Compiles on any 0.8.x; pin an exact audited version. Checked arithmetic + the explicit k overflow guard (line 55) mean this is hygiene, not an active overflow bug. [phase1]
  • I-2 — Deterministic, publicly-computable token/curve addresses (getInitCodeHash/computeTokenAddress, lines 288–314). By design (backend salt miner), but it is the enabler for C-1 (pre-create the pair) and M-1 (front-run the tuple). [phase1]
  • I-3 — Hardcoded, non-canonical Uniswap router (0xf88C…, line 32). Chain-specific; if wrong for the deploy chain, addLiquidityETH always reverts and no curve can graduate (feeds L-4). Confirm it matches the target chain's V2 router. [phase1]
  • I-4 — Dead maxAllowed check (lines 140–141). newRaised is pre-clamped to exactly 7000e18 (lines 134–138), so require(newRaised <= 7350e18) is a tautology — harmless, but signals the author believed the value could exceed the cap. [both]
  • I-5 — Hygiene / minor [both]:
    • sellTokens performs a redundant token.allowance(...) >= tokenAmount pre-check (line 174) before transferFrom (line 187) already enforces it.
    • _completeBonding approves the router for tokensForLiquidity (line 215); if the add consumes less, a non-zero residual approval dangles.
    • receive() (line 239) accepts uncredited ETH donations that inflate contractETH/ethForLiquidity in _completeBonding (line 199), skewing the LP split; donor loses funds, no protocol theft, and the donation is recoverable only via the H-1 emergency path.
    • Curve rounding floors the reserve and favors the user on both buy (calculateTokenAmount, lines 106–113) and sell (calculateSellAmount, lines 115–123); not exploitable today (the ~2% round-trip tax + fixed-k re-pin dominate), but becomes live if the tax is ever reduced. Round against the user for defense-in-depth.
    • EIP-7702 tax liveness: distributeTax (lines 87, 91) and the treasury transfer (lines 231–232) hard-revert if a recipient can't accept ETH. tokenDeployer is classically an EOA, but under EIP-7702 an EOA can carry code whose receive reverts → every buy/sell on that curve bricks (self-grief, single-token blast radius). Prefer pull-payments or try/catch on the tax legs.

Verified sound (skeptical negative results — carried from both phases, re-checked)

  • Curve arithmetic is solvent and non-extractable. totalETHCollected · getTokenBalance() == k holds on both sides; the real-balance invariant balance == totalETHCollected − VIRTUAL_ETH is preserved (buy +ethAfterTax on both counters, sell −ethAmount on both), and calculateSellAmount floors totalETHCollected at VIRTUAL_ETH (lines 120–121), so the virtual 2000 ETH is correctly non-withdrawable. A buy→sell round trip nets ≈ −2% (double tax); no rounding accumulation. No unauthorized/permissionless curve-ETH drain found.
  • No counter underflow. totalTokensSold -= tokenAmount (line 183) is bounded by the seller's checked transferFrom balance; totalETHCollected/totalETHRaised decrements stay ≥ VIRTUAL_ETH.
  • Reentrancy is contained. buyTokensFor/sellTokens are nonReentrant (lines 125, 171) and follow checks-effects-interactions (state written lines 148–150 / 183–185 before external calls). The guard is load-bearing on the buy path: the refund .call to msg.sender (line 157) runs before bondingComplete is set (line 197), so a malicious payer's reentry is blocked. SimpleToken is a plain OZ ERC20 (no transfer hooks), deployed by the curve itself.
  • Completion == trigger cannot be skipped — the cap clamp (lines 134–138) forces the crossing buy onto exactly 7000e18, so the equality (line 162) always fires (barring L-4's LP-add revert).
  • No sell-without-buy / no unprivileged tax theft — circulating supply equals totalTokensSold; tax recipients are fixed at deploy.
