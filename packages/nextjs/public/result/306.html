Two-phase audit: Phase 1 breadth (ethskills, 7 domain checklists) → Phase 2 depth (pashov, 12 blind attack agents) → hybrid reconciliation.

Confidence threshold (1-100) 75

What this contract does: a single-owner Uniswap V4 hook that owns and manages ALL liquidity for one SLEUTH/USDC pool on Base — a concentrated "MAIN" position plus a single-sided USDC "BID" position below current price. All liquidity operations route through owner-only entrypoints into a custom raw-salt unlockCallback dispatch; the standard multi-LP hook API is disabled. Fees auto-compound on every swap via a permissionless, try/catch-wrapped self-call.

Reconciliation: Overlap: 2 major themes independently found by both phases (in one case by 11 of 12 phase-2 agents plus 5 of 7 phase-1 agents — the highest convergence of any theme) · Phase-1-only: several Info-level observations · Phase-2-only: extension of the guard-gap theme to withdrawMain/withdrawBid · Re-examined: the severity split between agents calling the in-swap-compound issue Medium vs. Info was resolved by weighting the agents that fully traced the fund-flow (majority across both phases: no value ever leaves owner control) over those that flagged the asymmetry without completing the trace. No Critical or High findings — this is an unusually defensively-built contract; a key architectural question (does the hook's own internal liquidity calls trip its own LiquidityOnlyViaHook revert, bricking the contract?) was resolved early by verifying Uniswap V4's Hooks.sol noSelfCall modifier, which correctly exempts the hook's own calls.

Findings

[80] 1. seedMain() (and withdrawMain/withdrawBid) have no slippage floor or deadline — sandwichable owner capital moves

OwnerManagedRangeHook.seedMain / _doSeed / withdrawMain / withdrawBid · Confidence: 80 · [both] — raised in phase 1 by general/defi-amm/flashloans (as seedMain-only) and independently in phase 2 by 6 of 12 agents, one of which (first-principles) produced a full concrete PoC; phase 2 additionally identified the same gap in withdrawMain/withdrawBid.

Description

reanchor() (line 168) and compound() (line 233) both take (uint128 minLiquidity, uint256 deadline) and revert on block.timestamp > deadline / L < minLiquidity — explicitly documented in the code's own comments as a "sandwich guard," since both compute liquidity from the live pool spot price. seedMain() (line 143) performs the identical live-price computation in _doSeed ((uint160 sqrtP,) = _slot0(); L = LiquidityAmounts.getLiquidityForAmounts(sqrtP, ..., a0, a1);, lines 380-383) but has neither guard — only if (L == 0) revert ZeroLiquidity();.

Proof of Concept

  1. Owner submits seedMain(amount0Desired, amount1Desired, lower, upper) intending a balanced deposit at the current price.
  2. Attacker front-runs with a swap that pushes sqrtP toward getSqrtPriceAtTick(lower) (or upper).
  3. _doSeed reads the manipulated sqrtP; getLiquidityForAmounts is now bound by only one of a0/a1, so the owner's deposit forms far less liquidity than intended, or an unbalanced/lopsided composition — with no floor to reject the bad outcome.
  4. Attacker back-runs to restore price, realizing the divergence against the owner's freshly-seeded (mispriced) position.
  5. Because there is also no deadline, a seedMain transaction stuck in the mempool can equally be mined later at a completely different, unfavorable price.

withdrawMain/withdrawBid (lines 197, 210) have the mirror-image gap: they return whatever token composition the live price implies with no amount0Min/amount1Min and no deadline, so a withdrawal can also be sandwiched into an unfavorable realized composition. topUpBid is lower-risk: its liquidity math (getLiquidityForAmount1) depends only on fixed band ticks and the USDC amount, not spot price — a manipulated tick can only force a harmless revert (BandNotBelowPrice), never a bad deposit.

Fix

- function seedMain(uint256 amount0Desired, uint256 amount1Desired, int24 lower, int24 upper)
+ function seedMain(
+     uint256 amount0Desired, uint256 amount1Desired, int24 lower, int24 upper,
+     uint128 minLiquidity, uint256 deadline
+ )
      external
      onlyOwner
      whenNotPaused
      nonReentrant
      returns (uint128 added)
  {
+     if (block.timestamp > deadline) revert Expired();
      _validTicks(lower, upper);
      if (mainLiquidity > 0 && (lower != mainTickLower || upper != mainTickUpper)) revert RangeMismatch();
      added = abi.decode(
          poolManager.unlock(
-             abi.encode(Action.SEED, abi.encode(msg.sender, amount0Desired, amount1Desired, lower, upper))
+             abi.encode(Action.SEED, abi.encode(msg.sender, amount0Desired, amount1Desired, lower, upper, minLiquidity))
          ),
          (uint128)
      );
  }

Add if (L < minLiquidity) revert InsufficientLiquidity(); to _doSeed, mirroring _doReanchor/_doCompound. Apply the equivalent amount0Min/amount1Min + deadline pattern to withdrawMain/withdrawBid.

Severity: Medium — impact is confined to the owner's own capital (bounded by their declared deposit/withdrawal amounts, and recoverable via a later reanchor), which is why this rates Medium rather than High under this audit's scale ("owner-only fund loss" is explicitly a Medium criterion, not High). It is a clear, fixable inconsistency: the developer built exactly this protection for the sibling reanchor/compound functions and simply omitted it here.

[75] 2. Permissionless in-swap auto-compound has no slippage guard — contradicts its own stated design intent, but no path extracts value to a third party

OwnerManagedRangeHook._afterSwap / compoundInSwap / _compoundLogic · Confidence: 75 · [both] — this is the single highest-convergence item in the entire audit: 2 of 7 phase-1 agents (access-control, flashloans) called it Medium; 3 of 7 (general, defi-amm, precision-math) traced it fully and called it Info; in phase 2, 11 of 12 independently-run blind agents flagged the identical asymmetry, and every one that completed the value-flow trace agreed it cannot be turned into fund extraction.

Description

compound()'s own NatSpec (lines 226-230) states the manual trigger is onlyOwner specifically "so a non-owner forcing a fee re-add at a price/time of their choosing" is denied, and _doCompound enforces if (addedL < minLiquidity) revert InsufficientLiquidity(); (line 528). The in-swap path — _afterSwap (lines 300-312) calling try this.compoundInSwap() {} catch { emit CompoundFailed(reason); }, which calls _compoundLogic() — is exactly the scenario that guard was written to prevent: any swapper can move price within their own swap, cross the owner-set compoundThreshold0/compoundThreshold1, and force the owner's accrued MAIN fees to be redeployed as liquidity at that swapper-chosen price. This path has no minLiquidity, no deadline, and no TWAP/deviation check whatsoever.

However, across both phases, every agent that traced the full fund flow (the large majority) reached the same conclusion on impact: no value leaves owner control. _compoundLogic only ever redeploys the freshly-collected fees (never the hook's pre-existing claim balance, per its own explicit design — see comment at lines 336-339); getLiquidityForAmounts guarantees used0/used1 ≤ fee0/fee1; any portion that can't form liquidity at the manipulated price is banked as ERC-6909 claims, fully recoverable by the owner via rescue() or a later compound(). An attacker's round-trip swap pays pool trading fees into the very liquidity they're manipulating and receives nothing in return.

One phase-2 agent (numerical-gap) added a sharper detail: since compounding always resets the position's fee-growth checkpoint regardless of how much was actually redeployed, fees stranded at a manipulated range-edge price are not automatically retried on a later, balanced-price swap — a real capital-efficiency degradation, distinct from (and lesser than) fund loss.

Fix

Gate the in-swap redeploy against a manipulation-resistant reference: skip or clamp the compound when the current tick deviates from a short-window TWAP by more than a configurable bound, so a single swapper's in-flight price move can't dictate the compound ratio. Alternatively, keep _afterSwap's permissionless trigger limited to the (harmless) fee collect, and defer the actual liquidity re-add to the owner-only compound().

Severity: Low (downgraded from the Medium two agents initially assigned). The deciding factor, per this audit's own verification standard, is Gate 4 — material harm to an identifiable victim — which requires an actual loss, and the exhaustive multi-agent tracing (11 independent runs) found none. Kept as a finding rather than dropped to a lead because of the very high convergence and the direct contradiction with the contract's own documented design rationale, both of which make it worth the team's explicit attention.

Additional Findings (Low / Info)

[Low] Rounding shortfall could cause repeated compound-revert griefing (LEAD across both phases, not confirmed). _compoundLogic's fee-to-liquidity conversion rounds down while the pool's owed-amount computation for that liquidity rounds up; a 1-wei mismatch could make the claim-burn settlement revert if the hook holds no spare working-capital claims at that instant. Since a revert rolls back the fee-collect itself, the trigger condition never clears, meaning every subsequent swap could re-attempt and re-revert the same compound until owner intervention — wasted gas, not fund loss. Raised across both phases by 4 total agents (dos, periphery, numerical-gap, flow-gap); no agent produced a concrete numeric trace proving it actually fires (in practice, accumulated dust from other operations usually absorbs the 1 wei).

[Low] Auto-compound imposes a per-swap gas tax on all swappers. Once thresholds are configured, _afterSwap's try this.compoundInSwap() call and _mainOwedFees()'s state reads run on every swap regardless of whether the threshold is actually crossed, costing every swapper ~10-15k gas with no benefit to them when below threshold. Raised by 3 agents across both phases (dos, access-control, trust-gap).

[Low] topUpBid's band-below-price check is tick-manipulable — griefing revert only. A front-run that nudges the tick into the target band forces the owner's topUpBid to revert (BandNotBelowPrice); no fund loss, retriable. Raised by 2 agents (flashloans, first-principles).

[Low] reanchor/compound's minLiquidity floor bounds scalar liquidity, not composition/value. A sophisticated sandwich could still degrade the reanchored position's value while keeping L2 >= minLiquidity. Refinement of an existing guard, not a hole in it. (phase 1: flashloans)

[Info] No TWAP/oracle anywhere — the systemic root cause behind every price-manipulation item above. Every price-dependent decision uses raw spot _slot0(). Atomicity correctly kills in-transaction flash-loan injection, but not same-block front-running of owner operations. (phase 1: flashloans, defi-amm)

[Info] setCompoundThresholds changes an auto-execution parameter with no event emitted, unlike its sibling setAutoCompound. Off-chain monitoring gap only. (phase 1: access-control)

[Info] rescue(claims=true) can move claim-backed working capital — documentation nuance, not a vulnerability. The NatSpec says rescue "cannot touch deployed pool liquidity," which is true, but doesn't clarify that claim-held working capital (reanchor dust, pending compound fees) IS rescuable. Owner-only, fail-safe (a wrong claims flag reverts rather than draining the wrong bucket). (phase 1: erc20)

[Info] Semantic overloading of ZeroLiquidity for the over-withdraw case; the contract already has a distinct InsufficientLiquidity error used elsewhere. No security impact. (phase 1: general)

[Info] to receiver unvalidated in withdrawMain/withdrawBid/rescue — owner-only footgun (e.g. passing to == address(poolManager) would silently donate funds). No third-party attack surface. (phase 1: general)

[Info] _mainOwedFees's unchecked fee-growth subtraction is Uniswap's standard wrap-around idiom, verified correct, and used only as a threshold gate, not for actual fund movement. (phase 1: precision-math)

[Info] SLEUTH is assumed to be a standard (non-fee-on-transfer, non-rebasing) ERC-20. A fee-on-transfer token would cause seedMain/topUpBid to revert (CurrencyNotSettled) — a pure DoS on the owner's own operation, not silent mis-accounting, and moot since the pair is immutable and owner-chosen at deploy. (phase 1: erc20, defi-amm)

Verified-safe (checked across both phases, no finding)

  • noSelfCall architecture: Uniswap V4's Hooks.sol skips a hook's own beforeAddLiquidity/beforeRemoveLiquidity when the hook itself calls PoolManager.modifyLiquidity — confirmed directly from source. The contract's internal liquidity management is not bricked by its own inherited LiquidityOnlyViaHook revert, and third-party direct calls to PoolManager.modifyLiquidity are correctly blocked.
  • mainLiquidity/bidLiquidity mirror accounting: provably stays in exact lockstep with on-chain liquidity across every mutating path (seed/reanchor/compound/withdraw) in every agent's trace — no desync, no underflow-DoS.
  • unlockCallback reachability: the raw-salt action dispatch is unreachable by any external caller, since PoolManager.unlock invokes the callback on the unlock-initiator, and only the hook's own owner-gated entrypoints ever initiate an unlock.
  • _beforeInitialize pins the exact pool key + genesis price, blocking initialization front-running/griefing.
  • _doBid's single-sided (SLEUTH-zero) principal check correctly checks (delta - feesAccrued).amount0(), distinguishing principal from pre-accrued fees, and cannot be bypassed by price manipulation.
  • Reentrancy: owner entrypoints are nonReentrant; the in-swap compound path uses only ERC-6909 claim mint/burn (no ERC-20 transfer callback), so it has no reentrancy vector.
  • Ownership: Ownable2Step's two-step transfer has no skip path; renounceOwnership() is correctly disabled to prevent permanently bricking the owner-only recovery paths (withdrawMain/withdrawBid/rescue/unpause).
  • Pause coverage: pause() correctly blocks owner liquidity-shaping operations and the in-swap compound trigger, while never blocking public swaps or the owner's incident-exit paths (withdrawMain/withdrawBid/rescue/unpause).
  • ERC-20 integration: zero raw transfer/transferFrom calls anywhere; every path uses SafeERC20 or Uniswap's CurrencySettler/Currency libraries, both tolerant of missing return values.

⚠️ This review was performed by an AI-orchestrated two-phase audit (breadth checklist pass + blind attacker-mindset pass with 12 independent agents, reconciled against each other and against the verified Uniswap V4 architecture). AI analysis can never verify the complete absence of vulnerabilities and no guarantee of security is given. A human security review is recommended before scaling capital managed by this hook, particularly given the concentration of liquidity operations behind a single owner key.
