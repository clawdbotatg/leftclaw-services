SlopComputer — Final Security Audit Report

Target: SlopComputer.sol
Chain: Base (chain 8453)
Audited commit: main branch, May 2026
Methodology: ethskills (5 domain skills) + pashov (8-agent framework)
Date: 2026-05-10

Executive Summary

SlopComputer is a single-owner on-chain registry for podcast episodes stored as a singly-linked list. There are no third-party funds at risk, no ERC20/ETH handling, no upgradability, and no off-chain signature usage. The contract's security surface is narrow: all writes are onlyOwner, and the only material attack vectors are DoS-against-the-owner and ownership-management best-practice gaps.

Both audit methodologies converged on the same three findings, all Low severity. No High or Critical findings were identified.

Findings

[L-1] O(N) Linked-List Traversal in deleteEpisode Can Permanently Block Tail Deletion

Severity: Low
Confidence: High (confirmed by both methodologies)
Location: deleteEpisode(), lines 116–121

Description:
When the episode to delete is not the head, deleteEpisode must find its predecessor by walking the entire list:

bytes32 cursor = head;
while (_episodes[cursor].nextId != id) {   // line 118
    cursor = _episodes[cursor].nextId;
}

This is O(N) in episode count. Each storage read costs ~2,100 gas (cold) on Base. With Base's 30M block gas limit, the ceiling is approximately 14,000 episodes before a tail deletion permanently reverts with out-of-gas. Once this limit is hit, the oldest episodes can never be removed without first deleting all newer ones in order.

Exploit path (owner-only, self-inflicted):

  1. Owner accumulates > 14,000 episodes over time.
  2. Owner calls deleteEpisode(tailId) — the tail is at position N-1.
  3. The while loop iterates N-1 times, consuming O(N × 2100) gas.
  4. Transaction reverts OOG. The tail episode is permanently undeletable.

Recommendation:
Accept a caller-supplied predecessor ID and verify it with a single storage read, reducing deletion to O(1):

- function deleteEpisode(bytes32 id) external onlyOwner {
+ function deleteEpisode(bytes32 id, bytes32 hintPredecessorId) external onlyOwner {
      if (_episodes[id].id == bytes32(0)) revert EpisodeNotFound(id);
      bytes32 nextId = _episodes[id].nextId;
      if (head == id) {
          head = nextId;
      } else {
-         bytes32 cursor = head;
-         while (_episodes[cursor].nextId != id) {
-             cursor = _episodes[cursor].nextId;
-         }
-         _episodes[cursor].nextId = nextId;
+         if (_episodes[hintPredecessorId].nextId != id)
+             revert InvalidPredecessor(hintPredecessorId);
+         _episodes[hintPredecessorId].nextId = nextId;
      }
      if (live == id) live = bytes32(0);
      delete _episodes[id];
      unchecked { episodeCount -= 1; }
      emit EpisodeDeleted(id);
  }

Alternatively, use a doubly-linked list so each node carries a prevId pointer for O(1) predecessor lookup.

[L-2] Single-Step Ownership Transfer — Missing Ownable2Step

Severity: Low
Confidence: High (confirmed by both methodologies)
Location: import (line 18), contract SlopComputer is Ownable (line 24)

Description:
The contract uses OpenZeppelin's Ownable, which implements single-step transferOwnership. A single erroneous call sc.transferOwnership(wrongAddress) irrevocably hands over control with no confirmation step. The original owner has no recourse unless the recipient cooperates.

On live networks the deploy script hardcodes ownership to a single EOA (ATG_ETH). A phishing attack or fat-finger on transferOwnership permanently transfers management of the entire registry.

Recommendation:
Replace Ownable with Ownable2Step, which requires the new owner to explicitly call acceptOwnership():

- import { Ownable } from "@openzeppelin/contracts/access/Ownable.sol";
+ import { Ownable2Step, Ownable } from "@openzeppelin/contracts/access/Ownable2Step.sol";

- contract SlopComputer is Ownable {
+ contract SlopComputer is Ownable2Step {

No other changes are needed — Ownable2Step is a drop-in upgrade.

[L-3] Inherited renounceOwnership() Permanently Freezes Registry Management

Severity: Low
Confidence: High (confirmed by both methodologies)
Location: Inherited Ownable.renounceOwnership()

Description:
OpenZeppelin's Ownable exposes renounceOwnership() which sets owner to address(0). After this call, all onlyOwner functions — addEpisode, goLive, goOffline, setEpisodeContract, setEpisodeUrl, deleteEpisode — permanently revert. The registry becomes eternally read-only with no on-chain recovery path.

This is particularly dangerous given the single-EOA ownership model: a phishing transaction disguised as something else, or a replay attack in a multi-step signing flow, could call renounceOwnership() inadvertently.

Recommendation:
Override renounceOwnership to revert:

/// @dev Intentionally disabled — ownership of this registry should never be abandoned.
function renounceOwnership() public override onlyOwner {
    revert("SlopComputer: ownership cannot be renounced");
}

If intentional "seal the registry forever" behavior is desired, document it explicitly and gate it behind an additional confirmation parameter.

Informational Findings

[I-1] O(N) View Functions May Timeout for Large Lists

Location: indexOf() (line 161), getEpisodes(index, amount) (line 175)

These view functions traverse the list linearly. indexOf walks the entire list from head; getEpisodes skips index entries before returning. For large lists (thousands of episodes), RPC calls can exceed node-side gas limits and time out. No on-chain state impact. Use getEpisodesFrom (cursor-based) for sequential reads; it is O(1) per call once the cursor is known.

[I-2] Single EOA Centralization

Location: DeploySlopComputer.s.sol line 22; all onlyOwner functions

All registry management depends on a single EOA (0x34aA3F359A9D614239015126635CE7732c18fDF3). For a personal project registry this is expected. If the registry becomes infrastructure consumed by external dApps, migrating ownership to a multisig (e.g., Gnosis Safe) would reduce the risk of a single key compromise affecting downstream consumers.

[I-3] pragma solidity ^0.8.20 Emits PUSH0 — Verify Cross-Chain Use

Location: Line 2

Solidity ≥0.8.20 emits the PUSH0 opcode (Shanghai EVM). Base supports PUSH0 (Canyon upgrade, January 2024), so the stated deployment is unaffected. If redeployed to pre-Canyon chains or custom app-chains, deployment will fail. Not an action item for Base.

[I-4] latest() Returns a Zero-Struct for Empty List — Undocumented Caller Responsibility

Location: latest() (line 151)

latest() returns _episodes[bytes32(0)] when the list is empty — a fully zero-initialized Episode struct. The NatSpec correctly documents this. Off-chain consumers must check ep.id == bytes32(0) to distinguish an empty list from a valid episode. No on-chain risk; purely a consumer-side concern.

Positive Notes

  • Correct use of abi.encode in getId: uses abi.encode (not abi.encodePacked), preventing cross-input hash collisions.
  • Correct CEI pattern: deleteEpisode clears live and performs delete _episodes[id] before emitting the event — no reentrancy surface despite the checks-effects ordering.
  • Invariant preservation: All four key list invariants (episodeCount == reachable count, head validity, live validity, full reachability from head) are correctly maintained across all state-changing functions.
  • Thorough test coverage: The test suite covers head/middle/tail deletion, pagination boundary cases, cursor-based pagination, ownership transfer, and the live→recorded URL swap flow.
  • Deploy-time safety check: DeploySlopComputer.s.sol verifies post-deploy owner == ATG_ETH, preventing accidental misdeploys on live networks.
