Findings

[High] 1. Unbounded, unremovable reward controllers can permanently brick all deposits, withdrawals, and transfers

HATVault._beforeTokenTransfer / addRewardController / withdrawAndClaim,redeemAndClaim · Origin: [phase1: dos], re-examined and confirmed against source

Description

rewardControllers can only grow — addRewardController (lines 442-449) is owner-gated with only an O(n) duplicate check, no removal function, no length cap:

function addRewardController(IRewardController _rewardController) external onlyRegistryOwner noActiveClaim {
    for (uint256 i = 0; i < rewardControllers.length;) { 
        if (_rewardController == rewardControllers[i]) revert DuplicatedRewardController();
        unchecked { ++i; }
    }
    rewardControllers.push(_rewardController);
    emit AddRewardController(_rewardController);
}

Every deposit/withdraw/redeem/transfer runs through _beforeTokenTransfer, which calls rewardControllers[i].commitUserBalance(...) with no try/catch on both the receive side (lines 789-792) and the burn side (lines 803-806). A single controller that reverts, runs out of gas, or is later bricked permanently reverts every mint/burn/transfer path for the whole vault, with no on-chain recovery function.

Verified escape hatch: emergencyWithdraw() sets _isEmergencyWithdraw = true before calling redeem(). This burns shares via _burn, which triggers _beforeTokenTransfer(_from, address(0), _amount) — the receive-side loop is skipped because _to == address(0), and the burn-side loop is explicitly skipped by the if (!_isEmergencyWithdraw) guard at line 802. So principal is not permanently lost via this path, but all normal vault functionality (deposit, withdraw, redeem, transfer, withdrawAndClaim/redeemAndClaim) is bricked forever once any registered controller is stuck.

Proof of Concept: Registry owner (or a later-compromised/buggy already-added controller) causes commitUserBalance to revert for some reason (bug, access-control change, running out of storage, etc.). Any subsequent deposit/withdraw/redeem/transfer reverts inside _beforeTokenTransfer. No removeRewardController exists to recover; the only surviving path is emergencyWithdraw.

Fix

- rewardControllers[i].commitUserBalance(_to, _amount, true);
+ try rewardControllers[i].commitUserBalance{gas: 200_000}(_to, _amount, true) {} catch {}

Wrap all commitUserBalance/claimReward calls in bounded-gas try/catch; add a registry-owner-gated removeRewardController; cap the array length.

[Medium] 2. approveClaim pays bounties via atomic push-only transfers with no pull-payment fallback — several token behaviors can permanently block settlement

HATVault.approveClaim (lines 314-332) · Origin: [both] — phase1 [erc20, dos] (3 mechanisms) corroborated by phase2 agent-4 + agent-9 (2-agent convergence on mechanism (b))

Description

The whole bounty settlement is one atomic transaction with hard-coded recipients and no escrow/pull fallback:

_asset.safeTransfer(_claim.beneficiary, claimBounty.hacker);
_asset.safeTransfer(_claim.committee, claimBounty.committee);
...
_asset.safeApprove(address(_registry), claimBounty.hackerHatVested + claimBounty.governanceHat);
_registry.addTokensToSwap(...);
_asset.safeApprove(address(_registry), 0);

Three distinct token-behavior mechanisms can each permanently prevent a valid, already-approved claim from ever settling:

  • (a) Blacklist tokens (USDC/USDT-style): if beneficiary or committee is blacklisted, the safeTransfer at line 317/318 reverts forever — also lets a project grief a legitimate payout by having the token issuer blacklist the beneficiary.
  • (b) Zero-value-transfer-revert tokens (e.g. LEND): _validateSplit permits bountySplit.hacker == 0 / .committee == 0, and bountyGovernanceHAT/bountyHackerHATVested can independently be 0 (confirmed via getBountyGovernanceHAT/getBountyHackerHATVested, which default from registry values with no non-zero requirement) — any of these zeroes a downstream safeTransfer that isn't >0-guarded (unlike the hackerVested transfer at line 297, which is guarded by if (claimBounty.hackerVested > 0)).
  • (c) Zero-approve-revert tokens (e.g. BNB): the explicit safeApprove(..., 0) reset at line 332 always runs regardless of whether the prior approval was already fully consumed by addTokensToSwap's safeTransferFrom — reapproving 0→0 reverts on tokens that reject redundant zero-approvals.

Proof of Concept: Vault deployed over a USDC-like blacklistable asset. Committee submits a claim naming a beneficiary. Before the challenge period ends, the token issuer blacklists that address. approveClaim then always reverts at the safeTransfer to the blacklisted address — the only path forward is claim expiry/dismissal; the bounty is never paid.

Fix

- _asset.safeTransfer(_claim.beneficiary, claimBounty.hacker);
- _asset.safeTransfer(_claim.committee, claimBounty.committee);
+ if (claimBounty.hacker > 0) pendingWithdrawals[_claim.beneficiary][address(_asset)] += claimBounty.hacker;
+ if (claimBounty.committee > 0) pendingWithdrawals[_claim.committee][address(_asset)] += claimBounty.committee;

Guard every transfer with if (amount > 0); move to a pull-payment/escrow pattern so one uncooperative recipient or edge-case token behavior cannot block the entire claim.

[Medium] 3. swapAndSend's arbitrary routing contract + caller-controlled _amountOutMinimum is a theft vector for a compromised registry owner and an MEV sandwich target

HATVaultsRegistry.swapAndSend / _swapTokenForHAT (lines 301-359, 418-445) · Origin: [phase1: access-control, flashloans, general], re-examined and confirmed against source

Description

function swapAndSend(address _asset, address[] calldata _beneficiaries, uint256 _amountOutMinimum,
    address _routingContract, bytes calldata _routingPayload) external onlyOwner { ... }

function _swapTokenForHAT(...) internal returns (...) {
    IERC20(_asset).safeApprove(_routingContract, _amount);
    ...
    (bool success,) = _routingContract.call(_routingPayload);
    if (!success) revert SwapFailed();
    hatsReceived = _HAT.balanceOf(address(this)) - _balanceBefore;
    amountUnused = _amount - (_assetBalanceBefore - _asset.balanceOf(address(this)));
    if (hatsReceived < _amountOutMinimum) revert AmountSwappedLessThanMinimum();

swapAndSend is onlyOwner, but the owner supplies a completely arbitrary _routingContract, _routingPayload, and _amountOutMinimum. _swapTokenForHAT approves _routingContract for the full earmarked hacker+governance HAT-swap balance and blindly .call()s it, trusting only the HAT balance-delta against the caller-chosen minimum — there is no check on how much of _asset the routing contract actually consumed beyond the informational amountUnused bookkeeping, and no _routingContract.code.length > 0 check.

A malicious/compromised registry owner can point _routingContract at their own contract, set _amountOutMinimum = 0, and sweep the earmarked hacker reward (funds owed to a third party, not the owner) — a direct theft vector for a trusted-but-compromised role. Even with an honest owner, a loosely-set _amountOutMinimum against a thin-liquidity target exposes the (mempool-visible) swap to MEV sandwiching.

Proof of Concept: After a claim is approved, hackersHatReward[asset][hacker] is credited and the asset sits in the registry. Owner (or an attacker who has compromised the owner key) calls swapAndSend(asset, [hacker], 0, evilContract, payload). _swapTokenForHAT approves evilContract for the full amount and calls it; evilContract pulls the funds via the approval and returns 0 HAT; _amountOutMinimum = 0 lets this pass. The hacker's earmarked reward is stolen.

Fix

Restrict _routingContract to an allowlist of vetted swap adapters/routers; enforce a non-zero, sanity-bounded _amountOutMinimum derived from an independent quote; require _routingContract.code.length > 0. Document the remaining trust assumption on the registry owner explicitly.

[Low] 4. emergencyWithdraw skips the reward-controller balance decrement, leaving a phantom reward-earning balance

HATVault.emergencyWithdraw / _beforeTokenTransfer · Origin: [phase2: agent-6, agent-7, agent-8, agent-12 — 4-agent convergence], re-examined against source; reentrancy-escalation sub-claim demoted on re-examination

Description

if (_from != address(0)) {
    if (_amount > maxRedeem(_from)) revert RedeemMoreThanMax();
    withdrawEnableStartTime[_from] = 0;
    if (!_isEmergencyWithdraw) {
        for (uint256 i = 0; i < rewardControllers.length;) { 
            rewardControllers[i].commitUserBalance(_from, _amount, false);
            unchecked { ++i; }
        }
    }
}

The burn-side branch of _beforeTokenTransfer skips the commitUserBalance(_from, _amount, false) notification whenever _isEmergencyWithdraw == true, which emergencyWithdraw() sets for its entire redeem() call. Shares are burned on-chain, but the (out-of-scope) RewardController's internal per-user balance for that user is never decremented — the user retains a phantom reward-earning balance after fully exiting via the emergency path. Full financial impact is unverifiable from in-scope code alone since IRewardController's accounting logic is out of scope, but the code-level asymmetry itself is concrete and reproducible.

Re-examination note: phase 2's escalation — that emergencyWithdraw is "the only asset-moving entrypoint not wrapped in nonReentrant" and that this could compound the desync via ERC777 reentrancy — does not hold up against the source. emergencyWithdraw calls redeem() → _withdraw(), and _withdraw itself carries the nonReentrant modifier (line 752), as does _deposit (line 733) and approveClaim (line 257). OpenZeppelin's ReentrancyGuard status flag is shared across every function carrying the modifier regardless of external/internal visibility, so a reentrant callback during the asset transfer inside _withdraw cannot re-enter deposit/withdraw/redeem/approveClaim — it would revert. The reentrancy-compounding scenario is therefore refuted; only the phantom-balance accounting gap stands.

Fix

  function emergencyWithdraw(address receiver) external returns (uint256 assets) {
+     // notify reward controllers of the forfeited balance instead of unconditionally skipping
      _isEmergencyWithdraw = true;
      address msgSender = _msgSender();
      assets = redeem(balanceOf(msgSender), receiver, msgSender);
      _isEmergencyWithdraw = false;
  }

Reconcile the reward-controller balance (e.g. a best-effort try/catch decrement) rather than unconditionally skipping it.

[Low] 5. Deposits are not blocked during an active claim, exposing fresh deposits to an in-flight bounty with no exit

HATVault.deposit / maxDeposit · Origin: [phase2: agent-5, agent-8, agent-11, agent-12 — 4-agent convergence], re-examined and confirmed against source

Description

function maxWithdraw(address owner) public view ... returns (uint256) {
    if (activeClaim.createdAt != 0 || !_isWithdrawEnabledForUser(owner)) return 0;
    ...
function maxDeposit(address) public view ... returns (uint256) {
    return depositPause ? 0 : MAX_UINT;   // no activeClaim check

maxRedeem/maxWithdraw correctly return 0 while activeClaim.createdAt != 0 (blocking exits), but maxDeposit/maxMint and _deposit (lines 728-742) carry no equivalent noActiveClaim guard. A user (or a front-run victim) can deposit while a bounty claim is pending, immediately have their new shares frozen (maxRedeem == 0) until the claim resolves, and eat a pro-rata share of the payout on approval. All agents that traced the "committee colludes with beneficiary, front-runs their own claim with a deposit to inflate the payout" variant confirmed it nets to a loss for the attacker (the inflated bounty base is funded by the attacker's own capital, distributed pro-rata) — so this is a depositor footgun/UX gap rather than a profitable attack, but the entry/exit asymmetry itself is a real, easily-fixed gap.

Fix

- function maxDeposit(address) public view virtual override(IERC4626Upgradeable, ERC4626Upgradeable) returns (uint256) {
-     return depositPause ? 0 : MAX_UINT;
- }
+ function maxDeposit(address) public view virtual override(IERC4626Upgradeable, ERC4626Upgradeable) returns (uint256) {
+     return (depositPause || activeClaim.createdAt != 0) ? 0 : MAX_UINT;
+ }

[Low] 6. maxDeposit/maxMint report unlimited capacity even when deposits are actually blocked

HATVault.maxDeposit / maxMint (lines 604-612) · Origin: [both] — phase1 [erc4626] + phase2 agent-3 (confidence 90, direct finding)

Description

function maxDeposit(address) public view virtual override(IERC4626Upgradeable, ERC4626Upgradeable) returns (uint256) {
    return depositPause ? 0 : MAX_UINT;
}

Both maxDeposit/maxMint only check depositPause, ignoring that deposit/mint also revert when committeeCheckedIn == false (_deposit, CommitteeNotCheckedInYet, line 734) or when the registry is emergency-paused (_beforeTokenTransfer, line 779). This violates the ERC4626 spec requirement that maxDeposit/maxMint return 0 whenever any deposit would revert, and can break integrators/routers that trust these functions.

Proof of Concept: New vault before committeeCheckIn(): maxDeposit(user) == type(uint256).max, but deposit(1e18, user) reverts CommitteeNotCheckedInYet.

Fix

- return depositPause ? 0 : MAX_UINT;
+ return (depositPause || !committeeCheckedIn || registry.isEmergencyPaused()) ? 0 : MAX_UINT;

(same pattern for maxMint)

[Low] 7. maxRedeem/maxWithdraw overstate the actually-withdrawable amount

HATVault.maxRedeem/maxWithdraw (lines 614-624); floor in _afterTokenTransfer (811-815); fee rounding in previewWithdrawAndFee/previewRedeemAndFee (637-650) · Origin: [phase1: erc4626, general], re-examined and confirmed

Description

Two independent mechanisms make redeem(maxRedeem(owner)) or withdraw(maxWithdraw(owner)) potentially revert:

  • (a) maxRedeem returns the owner's full balance (balanceOf(owner), line 623) with no check against the _afterTokenTransfer floor — redeeming it can push global totalSupply() into the forbidden (0, 1000) band if the owner doesn't hold 100% of supply, reverting AmountOfSharesMustBeMoreThanMinimalAmount.
  • (b) The withdraw-fee round trip: maxWithdraw = previewRedeem(balance) rounds assets down (_convertToAssets(shares, Rounding.Down) then floors the fee), but withdraw() internally recomputes shares via previewWithdrawAndFee, which rounds shares up (_convertToShares(assets + fee, Rounding.Up)) — this round trip can demand one more share than the owner holds.

Proof of Concept (a): Supply 1500 (Alice 1000 / Bob 500). maxRedeem(Alice) = 1000; Alice.redeem(1000) drops supply to 500 → reverts. Alice's true max is 500.
Proof of Concept (b): withdrawalFee = 200 (2%), totalSupply = 1000, totalAssets = 1499, Alice holds all 1000 shares. maxWithdraw = 1470, but withdraw(1470) recomputes shares = ceil(1500·1000/1499) = 1001 > 1000 and reverts.

Fix

Cap maxRedeem to the largest redeemable amount that keeps supply at 0 or ≥1000; derive maxWithdraw from a round-trip-safe calculation. Integrators should prefer redeem(maxRedeem(...)) over withdraw(maxWithdraw(...)).

[Low] 8. Fee-on-transfer / deflationary underlying tokens break share accounting

HATVault._deposit (line 728) → inherited ERC4626Upgradeable._deposit; totalAssets() = raw asset.balanceOf(address(this)) · Origin: [phase1: general, erc20, erc4626], re-examined and confirmed

Description

HATVaultsRegistry.createVault() is permissionless for any ERC20 asset (line 272, no allowlist). _deposit mints shares for the requested assets amount without measuring what was actually received:

function _deposit(address caller, address receiver, uint256 assets, uint256 shares) internal override virtual nonReentrant {
    if (!committeeCheckedIn) revert CommitteeNotCheckedInYet();
    ...
    super._deposit(caller, receiver, assets, shares);   // transfers `assets`, mints `shares` — no balance-delta check
}

A fee-on-transfer/deflationary asset causes the vault to receive less than credited, silently diluting existing shareholders.

Proof of Concept: 1%-fee token; depositor sends 100, vault balance rises by 99, but shares are minted as if 100 arrived — a transfer of value from existing holders to the new depositor.

Fix

Either restrict vault creation to a registry-level allowlist of standard tokens, or measure the actual balance delta around the transfer and mint shares on the delta.

[Low] 9. swapAndSend proportional re-credit of unused swap amount rounds to zero per-beneficiary, stranding dust in the registry

HATVaultsRegistry.swapAndSend (lines 325, 331) · Origin: [phase1: precision-math], re-examined and confirmed

Description

governanceHatReward[_asset] = _swapData.amountUnused.mulDiv(_swapData.governanceHatReward, _swapData.amount);
...
hackersHatReward[_asset][_beneficiaries[i]] = _swapData.amountUnused.mulDiv(_swapData.hackerRewards[i], _swapData.amount);

mulDiv floors by default. When a swap only partially consumes its input, the sum of re-credited amounts can be strictly less than amountUnused, permanently stranding the difference in the registry with no owner. A beneficiary with a small proportional share can have their remaining credit floored entirely to zero.

Proof of Concept: amount = 1000, amountUnused = 500, 999 beneficiaries each with hackerRewards[i] = 1: each re-credit is 500·1/1000 = 0 (floored) — ~500 units become permanently unassigned. Realistic likelihood is low since the owner typically sets swap parameters to fully consume the input.

Fix

Either require full consumption of the swap input (revert on any non-trivial amountUnused), or route the flooring residual deterministically to governanceHatReward instead of splitting it away silently.

[Low] 10. Single-step ownership (no Ownable2Step) plus unguarded renounceOwnership risks permanent bricking

HATVaultsRegistry (imports @openzeppelin/contracts/access/Ownable.sol), HATVault (imports OwnableUpgradeable, _transferOwnership at initialize() line 188) · Origin: [phase1: access-control], re-examined and confirmed — grepped both files for Ownable2Step/renounceOwnership override, found neither

Description

Both contracts use single-step ownership transfer with no acceptance step, and neither overrides renounceOwnership(). A mistyped transferOwnership address or an accidental/malicious renounceOwnership() call permanently and irrecoverably bricks every owner-gated function — including setEmergencyPaused(false) (unpause), meaning a pause-then-renounce sequence freezes the whole registry forever.

Proof of Concept: Registry owner calls setEmergencyPaused(true) then renounceOwnership() — isEmergencyPaused can never be reset, so every vault's deposits/transfers revert permanently.

Fix

Adopt Ownable2Step/Ownable2StepUpgradeable; override renounceOwnership() to revert (or gate it deliberately).

[Low] 11. Committee role becomes unrecoverable once checked in

HATVault.setCommittee (lines 366-378) · Origin: [phase1: access-control], re-examined and confirmed

Description

function setCommittee(address _committee) external {
    if (msg.sender == owner() && committee != msg.sender) {
        if (committeeCheckedIn) revert CommitteeAlreadyCheckedIn();
    } else {
        if (committee != msg.sender) revert OnlyCommittee();
    }

After committeeCheckedIn == true, only the current committee itself can rotate the role — the owner branch reverts. Add an owner/registry-owner recovery path (e.g. timelocked), and validate _committee != address(0).

[Low] 12. swapAndSend iterates an unbounded, owner-supplied beneficiaries array

HATVaultsRegistry.swapAndSend (lines 313-354) · Origin: [phase1: dos], re-examined and confirmed

Description

An oversized _beneficiaries array can exceed the block gas limit, and one bad recipient can revert the whole batch — but the array and the call are both onlyOwner, so this is self-inflicted operational risk, not an externally triggerable griefing vector.

[Low] 13. First-depositor donation attack is raised in cost by MINIMAL_AMOUNT_OF_SHARES but not eliminated — later depositors can still round down to a small share count

HATVault._deposit / _afterTokenTransfer (line 811-815) · Origin: [both, refined] — phase1 [erc4626] concluded "no exploitable window"; phase2 agent-1 (math-precision) produced a concrete numeric counter-example. Re-examined against source: phase 2's refinement is correct and phase 1's conclusion is corrected below.

Description

function _afterTokenTransfer(address, address, uint256) internal virtual override {
    if (totalSupply() > 0 && totalSupply() < MINIMAL_AMOUNT_OF_SHARES) {
      revert AmountOfSharesMustBeMoreThanMinimalAmount();
    }
}

MINIMAL_AMOUNT_OF_SHARES = 1000 is enforced against global totalSupply(), not against any individual deposit's price-per-share. It stops the classic "supply pushed to exactly 1 share" case, but does not stop a funded attacker from inflating price-per-share via a direct donation (a plain ERC20 transfer() to the vault, bypassing deposit() entirely — nothing in totalAssets(), which is raw balanceOf, or _afterTokenTransfer can distinguish a donation from organic yield) after the 1000-share floor is already satisfied, causing a subsequent, unrelated depositor to receive far fewer shares than their deposit is worth. The victim's transaction does not revert (only an exact-zero-share mint reverts via AmountCannotBeZero), so the loss is silent.

Proof of Concept: Attacker deposits 1000 (mints 1000 shares 1:1, satisfies the floor). Attacker then donates 1,500,000 directly to the vault via a raw ERC20 transfer (not through deposit()) — totalAssets() rises to 1,501,000 with no new shares minted. Victim deposits 2000: shares = floor(2000·1000/1,501,000) = 1 share, worth ~1501 versus their 2000 deposited — a ~499 loss that flows entirely to the attacker's existing 1000 shares. Profitability for the attacker is bounded by their locked donation capital (~0.03% return in this example) and generally requires front-running a specific victim's deposit size to be material, so real-world profitability is marginal for well-funded vaults — but the mechanism is real, and the floor does not fully close it as phase 1's initial pass concluded.

Fix

  function initialize(IHATVault.VaultInitParams calldata _params) external initializer {
+     // consider seeding a small protocol-owned first deposit, or migrating to an
+     // ERC4626 implementation with a virtual shares/assets offset

Consider a protocol-seeded first deposit, or migrating to virtual-offset ERC4626 accounting, to remove donation-based price manipulation for the permissionlessly-created low-decimal/thin-liquidity vaults this registry allows.

[Info] 15. Shared HATVault implementation contract has no _disableInitializers()

HATVault — no constructor · Origin: [phase1: proxies, access-control, general], confirmed (no constructor present in the 912-line file)

Description

The singleton implementation (0x028A7C6873dFA8357c9dcF9C9d76EF2abb66256E) can be initialize()-d directly by anyone. [Info] 21. Committee-collusion donation-based bounty inflation analyzed — confirmed not profitable

_calcClaimBounty() (uses raw totalAssets()) · Origin: [phase1: flashloans], methodology re-examined: mandatory withdrawRequest() + 7-day pending period (registry default, confirmed in constructor: withdrawRequestPendingPeriod: 7 days) makes this non-flash-loan-fundable, consistent with phase 1's numeric walkthrough

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed, or where cross-checking demoted/rejected the claim. Not scored.

  • addTokensToSwap has no caller restriction — HATVaultsRegistry.addTokensToSwap — external, no onlyVault check, writes into shared hackersHatReward/governanceHatReward mappings. 9/12 phase-2 agents independently flagged this, and every one concluded it is not exploitable: the credited amount is always fully backed by safeTransferFrom(msg.sender, ...) of the same amount (confirmed at line 297), so a caller can only donate their own tokens (self-harm), never extract value. Recommended as defense-in-depth (restrict to registered vaults) but not a fund-loss finding.
  • swapAndSend duplicate-beneficiary carry-over erasure — HATVaultsRegistry.swapAndSend — _beneficiaries is owner-supplied with no dedup; on a partial swap, a beneficiary listed twice has their re-credited leftover overwritten by the second occurrence's write (confirmed at line 331 — plain assignment, not additive). Requires the onlyOwner caller to pass a duplicate address — an operational/data-entry bug rather than an attack.
  • _swapTokenForHAT unchecked-external-accounting underflow — HATVaultsRegistry._swapTokenForHAT — amountUnused = _amount - (assetBalanceBefore - assetBalanceAfter) (line 440) underflow-reverts if the owner-chosen routing contract consumes more than _amount of the asset. Requires an owner-chosen malicious/buggy router.
  • addRewardController doesn't checkpoint existing holders into the new controller — HATVault.addRewardController — pre-existing depositors are never checkpointed into a controller added mid-life, yet their next withdrawal calls commitUserBalance(_from, amount, false) on it uniformly. Impact entirely depends on out-of-scope RewardController behavior, unverifiable in-scope.
  • approveClaim lacks notEmergencyPaused — HATVault.approveClaim — submitClaim carries notEmergencyPaused (confirmed line 207), approveClaim does not (confirmed line 257) — an emergency pause cannot stop an already-submitted claim from paying out after the challenge period. Plausible as an intentional design choice (pause targets deposits/transfers, not resolving in-flight claims).
  • Registry owner can challengeClaim (not just the arbitrator), freezing withdrawals up to ~5 weeks — HATVault.challengeClaim — confirmed explicit in code: msg.sender != activeClaim.arbitrator && msg.sender != registry.owner() (line 243) — an intentional design giving the registry owner an emergency-check power over committees; a centralization/trust observation rather than a bug, worth documenting as a trust assumption.
  • _afterTokenTransfer min-shares floor can strand the last ~1000 shares among multiple holders — HATVault._afterTokenTransfer — recoverable via coordination (consolidate shares into one holder, then redeem to 0) — griefing/dust-lock, not fund loss.
  • logClaim can strand excess msg.value — HATVaultsRegistry.logClaim — self-harm/user-error scale; no sweep function for stray ETH exists (confirmed lines 167-177).

Notes on paths checked and cleared (no finding)

Both phases independently verified and cleared: the claim state machine's timing gates (submit → challenge → approve/dismiss) under caller/state inversion; _calcClaimBounty's bounty-split conservation (payouts never exceed totalAssets() · bountyPercentage, committee absorbs floor dust); swapAndSend's HAT-distribution conservation (hatsReceived - totalHackerReward cannot underflow); withdrawal/transfer gating funneling correctly through the maxRedeem chokepoint during active claims and safety periods; setMaxBounty/setBountySplit/setHATBountySplit snapshot-and-freeze correctly at claim submission so no admin setter can retroactively alter an in-flight claim; and TokenLockFactory's CREATE-based clone deployment (non-collidable, non-custodial).
