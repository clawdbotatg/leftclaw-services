Summary

VaultfireForumRegistry is a small, non-custodial, permissionless registry mapping human-readable forum "category" strings to opaque XMTP MLS groupId bytes, with a first-write-wins ownership model and no admin/owner/upgradeability. It holds no funds and has no external calls — most of the standard checklist surface (reentrancy, token handling, proxies, oracles, signatures, precision math) is genuinely not applicable, confirmed independently by both audit phases (the precision-math and numerical-gap agents in phases 1 and 2 both returned clean results).

The contract's actual risk is concentrated entirely in its trust model for the category string namespace: no on-chain normalization and no protection against pre-emptive/racing registration, both of which contradict claims made in the contract's own NatSpec. A third issue is a classic unbounded-array spam-DoS on the discovery function.

Reconciliation summary: Overlap: 3 findings in both phases · Phase-1-only: 0 · Phase-2-only: 0 · Re-examined leads kept: 0, demoted: 0 (no phase-unique leads existed — both phases independently converged on the identical 3 issues).

Findings

[90] 1. Unbounded, fee-free _categories growth permanently DoSes listCategories()

VaultfireForumRegistry.listCategories · Confidence: 90 · Severity: High · [both: phase1 evm-audit-dos+evm-audit-general / phase2 agents 3,4,6,8,9,12]

Description
registerGroup() is fully permissionless and feeless with no cap, bond, or rate limit, and pushes to the storage array _categories on every fresh category registration (line 85). listCategories() (lines 119-121) copies the entire array to memory in a single call, and there is no removal path and no admin/upgrade mechanism to ever add one. An attacker can spam-register minimal-size junk categories at roughly 150k gas each; at an estimated ~5,000–6,000 entries the memory-copy cost exceeds typical block-gas / eth_call gas caps, permanently bricking the registry's only bulk-discovery function — for an estimated one-time cost on the order of a few hundred dollars on Base. getGroup()/isRegistered() (O(1) mapping lookups) are unaffected; the damage is specifically to bulk enumeration, which the contract's own NatSpec states is its core purpose ("allow new users to discover... a category's group").

Proof of Concept

  1. Attacker loops registerGroup(uniqueShortString_i, minimalGroupId) for i = 1..N using 1-4 byte throwaway category strings and 1-byte groupId, each call costing ~150k gas.
  2. _categories.length grows unbounded — no code path ever checks or caps it.
  3. At sufficiently large N (~5,000-6,000+), any on-chain caller of listCategories() exceeds the block gas limit and reverts; off-chain eth_call callers hit RPC-provider gas caps or timeouts.
  4. This is permanent: no owner exists to prune, cap, or upgrade the contract.

Fix

- function listCategories() external view returns (string[] memory) {
-     return _categories;
- }
+ function listCategories(uint256 offset, uint256 limit) external view returns (string[] memory page) {
+     uint256 end = offset + limit;
+     if (end > _categories.length) end = _categories.length;
+     page = new string[](end - offset);
+     for (uint256 i = offset; i < end; i++) {
+         page[i - offset] = _categories[i];
+     }
+ }

No-code-change mitigation: off-chain consumers (e.g. the XMTP client) should index via GroupRegistered/GroupRotated events rather than calling listCategories().

[85] 2. Missing category-string normalization enables case/whitespace/homoglyph squatting

VaultfireForumRegistry.registerGroup · Confidence: 85 · Severity: Medium · [both: phase1 evm-audit-general+evm-audit-access-control / phase2 agents 2,4,5,6,7,8,9,11,12]

Description
_entries (line 41) is keyed by exact-byte string equality. registerGroup() validates only byte length (>0, <=64, lines 72-73) — there is no case-folding, whitespace-trimming, or Unicode/homoglyph normalization, despite the NatSpec's documented convention ("Lowercase category slug", line 68) and its "prevents drive-by hijacks" claim (line 18). "general", "General", "general " (trailing space), zero-width-character variants, and Cyrillic-homoglyph lookalikes (e.g. U+0435 in place of Latin 'e') are all distinct, independently-registrable mapping keys.

Proof of Concept

  1. Legitimate publisher registers "general" with the real MLS groupId.
  2. Attacker calls registerGroup("General", attackerGroupId) — a byte-distinct key, so it hits the fresh-registration branch (e.publisher == address(0) for this key) and succeeds unconditionally; no check anywhere rejects it.
  3. Both entries coexist in listCategories()/getGroup(). Any client or user that doesn't strictly canonicalize before display/lookup can be shown or steered into joining the attacker-controlled XMTP MLS group under what appears to be the same category name.
  4. The attacker's entry is permanent and independently rotatable by them forever (e.publisher == msg.sender on their own key).

Fix

+ function _validateCategory(string calldata category) private pure {
+     bytes memory b = bytes(category);
+     for (uint256 i = 0; i < b.length; i++) {
+         bytes1 c = b[i];
+         require(
+             (c >= 0x61 && c <= 0x7A) || (c >= 0x30 && c <= 0x39) || c == 0x2D || c == 0x5F,
+             "invalid character"
+         );
+     }
+ }
  function registerGroup(string calldata category, bytes calldata groupId) external {
      require(bytes(category).length > 0,  "category required");
      require(bytes(category).length <= 64, "category too long");

Confines the key space to lowercase ASCII + digits/hyphen/underscore, eliminating case/whitespace/homoglyph collisions at the contract level.

[85] 3. Front-running / pre-emptive squatting of not-yet-registered category names

VaultfireForumRegistry.registerGroup · Confidence: 85 · Severity: Medium · [both: phase1 evm-audit-access-control+evm-audit-dos / phase2 agents 2,3,4,7,8,9,11]

Description
Ownership of a brand-new category name is decided purely by transaction ordering. A pending legitimate registerGroup(category, ...) transaction is visible in the public Base mempool before confirmation; an attacker can front-run it with the identical category string and a higher priority fee, or simply pre-register predictable/valuable names (e.g. "general", "support") before a legitimate community claims them. This directly contradicts the contract's own NatSpec claim ("First-write-wins: prevents drive-by hijacks", line 18) — that claim only protects an already-confirmed entry from being overwritten, not the initial registration race. Once won, require(e.publisher == msg.sender) (line 89) permanently locks out the rightful party; there is no owner, dispute mechanism, or timeout to reclaim a squatted or abandoned category.

Proof of Concept

  1. Victim (legitimate community organizer) submits registerGroup("general", realGroupId).
  2. Attacker observes it in the mempool (or simply front-runs preemptively without observing anything, given common category names are predictable) and submits registerGroup("general", attackerGroupId) with higher gas/priority fee.
  3. Attacker's transaction mines first, setting e.publisher = attacker permanently.
  4. Victim's transaction then executes against the now-non-zero e.publisher, hits require(e.publisher == msg.sender, "not original publisher"), and reverts.
  5. Attacker permanently owns "general"'s publish/rotation rights and can point it at any groupId, including a malicious or dead MLS group, with no recourse for the community.

Fix

+ mapping(bytes32 => address) private _commitments;
+
+ function commitRegistration(bytes32 commitment) external {
+     _commitments[commitment] = msg.sender;
+ }

+ function registerGroup(string calldata category, bytes calldata groupId, bytes32 salt) external {
+     bytes32 commitment = keccak256(abi.encodePacked(category, salt, msg.sender));
+     require(_commitments[commitment] == msg.sender, "no valid commitment");
      ...

This is partly an accepted design tradeoff the contract's own NatSpec discloses ("zero-trust... anyone can register an unset category"); at minimum, the NatSpec's "prevents drive-by hijacks" wording should be corrected to accurately scope the guarantee to post-registration overwrites only, so integrators don't rely on protection the code doesn't provide for the initial claim.
