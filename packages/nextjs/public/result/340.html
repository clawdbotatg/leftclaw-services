Findings

[F-1] Permissionless finalizeRound has no monotonicity guard — a stale round can silently overwrite a fresher published consensus

Severity: High
Origin: [both] — Phase 1 (General-1, Oracle-1, AccessControl-2) · Phase 2 (9 of 12 agents: access-control, economic-security, execution-trace, periphery, first-principles, asymmetry, boundary, numerical-gap, trust-gap)
Location: startRound() (lines 189-206), finalizeRound() (lines 232-255)

Description: startRound(metricId) never checks whether a previous round for the same metricId is still open or unfinalized. finalizeRound(roundId) is external with no access-control modifier, and once block.timestamp > round.deadline and quorum was met, it unconditionally executes:

latestValue[round.metricId] = median;
latestRoundForMetric[round.metricId] = roundId;

with no comparison against the roundId already recorded in latestRoundForMetric[round.metricId]. Because finalization is permissionless and has no time upper bound (an unfinalized round can be finalized at any point in the future, however much later), any round that reached quorum but was never promptly finalized remains a live "time bomb" that can roll the published feed backward at a time of any caller's choosing.

Proof of Concept (one of many equivalent traces produced independently across both phases):

  1. t=0: owner calls startRound(M) → round 1, deadline t+24h. 3 oracles submit 40, 50, 60. Nobody calls finalizeRound(1) yet — there is no obligation to.
  2. t=5h: owner calls startRound(M) again for the same metric M (nothing in startRound prevents this — a plausible, non-malicious operational occurrence, e.g. an automated daily round-opener, or the owner believing round 1 stalled) → round 2, deadline t+29h. 3 oracles submit 70, 80, 90.
  3. t=29h+1s: anyone calls finalizeRound(2) → median 80 published; latestValue[M]=80, latestRoundForMetric[M]=2.
  4. t=1000h: anyone (any unprivileged address — finalizeRound has zero access restriction) calls finalizeRound(1). It passes every check (startTime != 0, !finalized, deadline long past, quorum was met at 3) and unconditionally overwrites latestValue[M] back to round 1's stale median 50, rolling latestRoundForMetric[M] back down to 1. ConsensusReached fires normally — indistinguishable on its face from a legitimate update.

This requires no oracle collusion and no admin misbehavior — only that overlapping rounds exist for a metric (plausible under ordinary operational cadence) combined with any address calling finalizeRound out of round-ID order, which anyone can trigger at will.

Recommendation:

-    latestValue[round.metricId] = median;
-    latestRoundForMetric[round.metricId] = roundId;
+    if (roundId >= latestRoundForMetric[round.metricId]) {
+        latestValue[round.metricId] = median;
+        latestRoundForMetric[round.metricId] = roundId;
+    }

Additionally (defense in depth), prevent startRound from opening a new round for a metricId while a prior round for that metric is unfinalized, e.g. via a mapping(bytes32 => uint256) activeRoundForMetric that must be finalized before a new round starts.

[F-2] No commit-reveal and no value bounds/deviation enforcement — a last-mover oracle or a 2-of-3 colluding pair can dictate the published median

Severity: High
Origin: [both] — Phase 1 (Precision-2, Oracle-2, Oracle-3) · Phase 2 (agents 1, 3, 5, 10 as FINDINGs; agent 11 as a corroborating lead)
Location: submitMetric() (lines 211-228), _calculateMedian() (lines 313-345)

Description: All submissions are readable in real time via the public getSubmissions(roundId) view and the MetricSubmitted event, with the submission window staying open until block.timestamp > round.deadline. There is no commit-reveal scheme, and submitMetric performs zero validation on value — no bound tied to what a "flourishing score" should plausibly be (e.g. 0-100), despite the docstring implying such scores are meaningfully bounded. MINIMUM_QUORUM is a flat constant of 3, independent of oracleCount (which can scale up to 50). Two independent, mutually reinforcing exploit mechanisms result:

  • Mechanism A — last-mover timing (proven independently by 3 phase-2 agents plus Phase 1's Oracle-3): with two already-visible honest submissions a < b, a third submitter can read them and submit any x with a ≤ x ≤ b; the sorted median becomes exactly x — the last mover's own chosen number, verbatim. Concrete trace: honest submissions 1000 and 1200 are visible on-chain; the last submitter reads them and submits 1199 → sorted [1000, 1199, 1200] → median = 1199.
  • Mechanism B — static 2-of-3 collusion, no timing required (proven structurally by a Phase 2 agent): if 2 of 3 submitters in a round post the same value, that value structurally cannot be dislodged from the middle position of a 3-element sorted array by any third value, in any order. Concrete trace: Alice and Bob both submit 7; Carol (honest) submits 1,000,000 → sorted [7, 7, 1000000] → median = 7, entirely ignoring Carol's honest report regardless of what she submits.

Either mechanism lets as few as 1 (Mechanism A) or 2 (Mechanism B) participants in a given round — out of however many of the up to 50 registered oracles happen to submit — fully determine the "consensus" value stored in latestValue and emitted via ConsensusReached as the authoritative flourishing score, with no revert, no flag, and no bound on the resulting magnitude.

Recommendation: Require a commit-reveal pattern (submit keccak256(value, salt) during the window; reveal value + salt only in a separate post-deadline window) so no submitter can condition its value on others' already-visible submissions. Add explicit bounds validation in submitMetric (e.g. require(value <= MAX_SCORE)). Implement the deviation-band check implied by MAX_DEVIATION_BPS (see F-3) so anomalous submissions are excluded before affecting the median. Consider scaling quorum with oracleCount (e.g. a percentage) rather than a fixed absolute floor of 3.

[F-3] MAX_DEVIATION_BPS is declared and documented but never enforced anywhere in the contract

Severity: Low
Origin: [both] — Phase 1 (Precision-1, General-3, Oracle-6) · Phase 2 (9 of 12 agents flagged this; promoted per multi-agent-convergence rule)
Location: line 97 (declaration), line 18 (NatSpec claim)

Description: The contract-level NatSpec states "Submissions outside the acceptable deviation band are flagged" and defines MAX_DEVIATION_BPS = 2000 (20%). A full-file grep confirms MAX_DEVIATION_BPS is referenced exactly once — its own declaration. It is never read in submitMetric, _calculateMedian, or finalizeRound; there is no comparison, no flagging event, no exclusion path. This is the one control that would have mitigated F-2, and its complete absence directly contradicts the contract's own documented security model — any integrator reading the NatSpec would reasonably, and incorrectly, believe outlier submissions are screened before affecting consensus.

Proof of Concept: Register 3 oracles, start a round, submit 1, 50, 52 (>98% mutual deviation) — all three succeed silently with no flag, event, or rejection.

Recommendation: Either implement the deviation-band check (compare each submission against the round's running median/mean; reject or flag/exclude if it exceeds MAX_DEVIATION_BPS), or remove the constant and correct the NatSpec so integrators do not rely on a non-existent guarantee.

[F-4] Owner can register itself (or Sybil addresses it controls) as an oracle, contradicting the contract's own documented trust model

Severity: Medium
Origin: [both] — Phase 1 (General-2, Oracle-5, AccessControl-1) · Phase 2 (trust-gap agent, filed as a FINDING)
Location: addOracle() (lines 150-160), submitMetric() (line 211), NatSpec (lines 14-19)

Description: The header NatSpec explicitly claims "eliminates single-oracle dependency by requiring multiple independent oracles" and "The owner can register/remove oracles but cannot submit data." Neither is enforced in code: addOracle never checks oracle != owner or any proof of independence, has no timelock, and no cooldown before a newly-added oracle can submit. Since MINIMUM_QUORUM is only 3, the owner can register 3 addresses it controls, start a round, and submit whatever values it wants from all three — the median of 3 owner-controlled submissions is fully owner-determined, with zero external oracle participation required.

Proof of Concept: Owner calls addOracle(ownerAddr), addOracle(sybil1), addOracle(sybil2) — all succeed (no guard exists). Owner calls startRound(metricId) (oracleCount >= 3, passes). Owner submits from all three addresses (e.g. 0, 0, 0). Any address calls finalizeRound; median = 0, published as the authoritative flourishing metric, fully owner-controlled with no independent validation.

Note on methodology: Phase 2's stricter attacker-gate (judging.md) formally rejects admin-action findings unless an unprivileged actor completes the harm chain — since every step here (register, start round, submit) is an owner action, that gate alone would drop this finding. It is retained because Phase 1's breadth methodology explicitly treats trust-model violations as a reportable Medium-severity category, and because a second, independent Phase 2 agent (blind to Phase 1) reached the identical code-level conclusion with a full proof, meeting this report's own two-source verification bar.

Recommendation: Prevent oracle == owner registration in addOracle, and/or add a registration-to-first-submission cooldown, and/or move oracle registration behind a timelock/multisig/governance gate rather than a single EOA owner. At minimum, correct the NatSpec to disclose the owner is a fully trusted party under the current design.

[F-5] getLatestValue exposes no timestamp/age and there is no enforced maximum staleness

Severity: Medium
Origin: [phase1 only] (Oracle-4) — re-examined against source and confirmed
Location: getLatestValue() (lines 263-269), latestValue/latestRoundForMetric mappings (lines 121-124)

Description: getLatestValue(metricId) returns only (value, roundId) — no timestamp. A consumer wanting to know data age must make a second call (getRound(roundId)) and derive an age proxy from round.deadline, a pattern the single-call, obviously-named getLatestValue doesn't invite. There is no enforced maximum age anywhere: if the owner stops calling startRound for a metric, latestValue/latestRoundForMetric remain frozen forever with no expiry or flag. Separately, if a metric has never been finalized, getLatestValue returns (0, 0) — indistinguishable from a legitimately submitted score of 0, since nothing bounds submitted values (F-2).

Proof of Concept: Metric education_score finalized once at round 7 with value 72. Owner never calls startRound again (key loss, abandonment, or simply no further updates scheduled). Any consumer calling getLatestValue("education_score") continuously receives (72, 7) with no on-chain indication the figure is arbitrarily stale.

Recommendation: Add a lastUpdatedAt timestamp directly to getLatestValue's return tuple. Consider a getLatestValueChecked(metricId, maxAge) variant that reverts if stale, and a way to distinguish "never finalized" from a genuine zero-valued consensus (e.g. a bool initialized return).

[F-6] Owner can front-run/censor a pending oracle submission via removeOracle, and can deny quorum mid-round

Severity: Medium
Origin: [phase1 only] (AccessControl-3) — re-examined against source and confirmed
Location: removeOracle() (lines 164-182), submitMetric() (lines 211-228)

Description: removeOracle has no restriction based on round state and takes effect immediately. Since onlyOracle in submitMetric is evaluated at transaction execution time (not signing time), the owner can watch the mempool for a pending submitMetric call carrying a value it dislikes and front-run it with removeOracle(thatOracle), causing the submission to revert (OnlyOracle). This is a direct censorship primitive over which values can join the consensus. Separately, the owner can remove enough oracles mid-round to drop the count of still-eligible submitters below MINIMUM_QUORUM, forcing RoundExpired and denying publication entirely. (Submissions already recorded before removal are not retracted — this only blocks not-yet-submitted values.)

Proof of Concept: Oracle O has a pending submitMetric(roundId, badValue) transaction in the mempool. Owner observes it and submits removeOracle(O) with higher priority so it lands first; O's transaction then reverts.

Recommendation: Snapshot the eligible-oracle set at startRound time rather than checking isOracle live in submitMetric, so removals only apply prospectively to future rounds. At minimum, document this as an accepted owner trust assumption.

[F-7] No emergency pause / round-cancellation mechanism

Severity: Low
Origin: [phase1 only] (AccessControl-5)
Location: contract-wide; submitMetric(), finalizeRound()

Description: There is no pause mechanism and no way to cancel/invalidate an in-flight round. If the owner detects manipulation mid-round (e.g. via F-2/F-4), the only lever is removeOracle, which blocks further submissions from an address but cannot retract already-recorded submissions or stop a permissionless finalizeRound from publishing them once the deadline passes.

Recommendation: Add an owner-gated cancelRound(roundId) (only callable before finalization) that marks a round finalized without computing/publishing a consensus value, mirroring the existing RoundExpired path.

[F-8] Oracle churn during an open round can push a round's submission count past the intended MAXIMUM_ORACLES cap

Severity: Low
Origin: [both] — Phase 1 (DoS-2) · Phase 2 (numerical-gap agent's lead, "quorum-recheck-gap")
Location: submitMetric(), removeOracle(), addOracle(), _submissions mapping (line 115)

Description: hasSubmitted is keyed by address, not by "oracle slot." If the owner calls removeOracle(A) then addOracle(B) while a round is still open, both A and B can each submit once to that round, since removal doesn't clear per-round history and the new address has no submission recorded yet. Repeated churn cycles can push _submissions[roundId].length past 50. This requires sustained, deliberate owner cooperation (each cycle costs ~3 owner/oracle transactions); it does not brick the contract or affect other rounds — worst case is one round's _calculateMedian sort getting gradually more expensive (still negligible in absolute gas terms at any realistically achievable churn count).

Recommendation: Enforce the cap explicitly in submitMetric (revert if _submissions[roundId].length >= MAXIMUM_ORACLES), or snapshot the eligible oracle set at startRound time.

[F-9] Floating pragma

Severity: Info
Origin: [phase1 only] (General-4)
Location: line 2, pragma solidity ^0.8.25;

Description: ^0.8.25 allows compilation with any 0.8.x version ≥ 0.8.25, a minor reproducibility hazard for production deployments.

Recommendation: Lock to the exact deployed compiler version, pragma solidity 0.8.25;.

Leads (not independently rated — informational trails for the team)

  • Check-order asymmetry in submitMetric [phase2 only] — re-examined and confirmed against source: the deadline check (line 214, block.timestamp > round.deadline) is evaluated before the round.finalized check (line 215), but finalizeRound only ever sets finalized = true after its own deadline check (line 236) has already passed — so once a round is finalized, submitMetric's deadline check will always fire first, meaning the RoundAlreadyFinalized revert path is unreachable dead code, masked by RoundNotOpen. Purely cosmetic (wrong revert reason surfaced to integrators); no fund/data impact.
  • Ambiguous zero-value on expired rounds [phase2 only] — re-examined and confirmed against source: an expired round (subs.length < MINIMUM_QUORUM, lines 239-243) is marked finalized = true with consensusValue left at its struct default of 0, indistinguishable from a round that legitimately reached consensus on the value 0. Note latestValue/latestRoundForMetric are not touched in this path, so getLatestValue consumers are unaffected — only direct getRound(roundId).consensusValue callers who don't also check submissionCount could be confused.

Non-Findings (checked, no issue)

  • Even-length median formula (a/2 + b/2 + (a%2+b%2)/2) — verified by two independent agents (exhaustive parity-case analysis and algebraic proof) to be exactly equivalent to truncating (a+b)/2 for all uint256 a,b, with no overflow at any input including a=b=type(uint256).max.
  • removeOracle/oracleList array-mapping consistency — verified sound across all edge cases (single-element list, removing the last element, removing a non-last element); the isOracle[a] == true ⟺ a appears exactly once in oracleList invariant holds for all reachable states.
  • Bounded loops in removeOracle (linear scan) and _calculateMedian (insertion sort) — hard-capped at MAXIMUM_ORACLES = 50; gas cost at n=50 is negligible against the block gas limit, not a DoS vector.
  • No external calls anywhere in the contract — reentrancy, force-feeding, returndata-bombing, and try/catch-related checklist categories are not applicable.
  • Two-step ownership transfer (transferOwnership/acceptOwnership) — correctly implemented with a zero-address check.

Client Focus Areas — Direct Answers

The job description asked specifically about three areas. Direct answers, cross-referenced to the findings above:

  1. "Oracle staleness checks by consumers" — Not implemented. getLatestValue exposes no timestamp and there is no enforced maximum age (F-5); compounded by F-1, which means "latest" isn't even guaranteed to be chronologically latest.
  2. "Score-range validation (should be bounded)" — Not implemented. submitMetric accepts any uint256 with zero bounds, and the one control that suggests bounds were intended (MAX_DEVIATION_BPS) is dead code (F-3), directly enabling F-2.
  3. "Access control on updateScore" — No function named updateScore exists in the deployed contract; the functional equivalent is submitMetric, which is correctly gated by onlyOracle. The more material access-control gaps are in the surrounding oracle-management functions: addOracle doesn't prevent owner self-registration (F-4), and removeOracle can be used to front-run/censor submissions (F-6).
