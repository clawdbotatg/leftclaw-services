[H-1] ERC777 Token Reentrancy in stake() — CEI Violation with Unguarded Attack Surface

Severity: High (Phase 1 Critical · demoted: Phase 2 could not confirm fund theft path)
Source: Phase 1 (erc20, general) + Phase 2 (agents 3, 4, 9, 12 analyzed)
Location: stake() — clawdToken.safeTransferFrom called before all state writes

stake() executes the external safeTransferFrom call (line 39) before pushing to stakes[], incrementing totalStaked, updating totalSupplyStaked, or updating weightedStakeSum (lines 40–44). This is a checks-effects-interactions violation. If clawdToken is an ERC777 token, the sender's tokensToSend hook fires mid-transfer with completely stale state. Two re-entrant stake() calls within the hook produce two stake records, each backed by an independent token transfer. While Phase 2 analysis traced both calls correctly completing their transfers (no single-deposit double-claim), the unguarded re-entrancy path poses serious risk: any future state extension, additional access-control logic, or reward-accrual mechanism layered onto stake() could be exploitable. The attack surface is live today if clawdToken is or becomes ERC777-compatible.

Recommendation: Add nonReentrant modifier to both stake() and unstake(). Additionally, move the safeTransferFrom call to after all state writes (proper CEI):

  function stake(uint256 amount) external nonReentrant {
      require(amount >= MIN_STAKE, "Below minimum stake");
+     uint256 stakeIndex = stakes[msg.sender].length;
+     stakes[msg.sender].push(Stake({ amount: amount, stakedAt: block.timestamp }));
+     totalStaked[msg.sender] += amount;
+     totalSupplyStaked += amount;
+     weightedStakeSum[msg.sender] += amount * block.timestamp;
      clawdToken.safeTransferFrom(msg.sender, address(this), amount);
-     uint256 stakeIndex = stakes[msg.sender].length;
-     stakes[msg.sender].push(Stake({ amount: amount, stakedAt: block.timestamp }));
-     totalStaked[msg.sender] += amount;
-     totalSupplyStaked += amount;
-     weightedStakeSum[msg.sender] += amount * block.timestamp;
      emit Staked(msg.sender, amount, stakeIndex, block.timestamp);
  }

[H-2] Fee-on-Transfer Token Inflates Accounting — Last Stakers Cannot Withdraw

Severity: High
Source: Phase 1 (erc20, general, access-control) + Phase 2 (agents 2, 3, 5, 9, 10, 12 — 6 agents confirmed)
Location: stake() line 39 vs lines 41–44

stake() calls safeTransferFrom(msg.sender, address(this), amount) and then records the caller-supplied amount in Stake.amount, totalStaked[msg.sender], totalSupplyStaked, and weightedStakeSum[msg.sender]. For a fee-on-transfer token, the contract receives amount - fee but records amount. On unstake(), safeTransfer(msg.sender, amount) attempts to return the over-recorded value. The first stakers to unstake draw on later stakers' deposits; the final stakers find the contract balance insufficient and cannot unstake — their tokens are permanently locked.

Proof of concept (1% fee token):

  1. Alice stakes 1000e18; contract receives 990e18, records 1000e18.
  2. Bob stakes 1000e18; contract receives 990e18. Total held: 1980e18, recorded: 2000e18.
  3. Alice unstakes — receives 1000e18 (succeeds, leaving 980e18).
  4. Bob unstakes — contract tries to send 1000e18 from 980e18 → permanent revert.

Fix:

+ uint256 balanceBefore = clawdToken.balanceOf(address(this));
  clawdToken.safeTransferFrom(msg.sender, address(this), amount);
+ uint256 received = clawdToken.balanceOf(address(this)) - balanceBefore;
+ require(received >= MIN_STAKE, "Received amount below minimum");
  uint256 stakeIndex = stakes[msg.sender].length;
- stakes[msg.sender].push(Stake({ amount: amount, stakedAt: block.timestamp }));
- totalStaked[msg.sender] += amount;
- totalSupplyStaked += amount;
- weightedStakeSum[msg.sender] += amount * block.timestamp;
+ stakes[msg.sender].push(Stake({ amount: received, stakedAt: block.timestamp }));
+ totalStaked[msg.sender] += received;
+ totalSupplyStaked += received;
+ weightedStakeSum[msg.sender] += received * block.timestamp;

[H-3] Rebasing Token Stale Accounting — Negative Rebase Causes Insolvency

Severity: High
Source: Phase 1 (erc20, general)
Location: Stake.amount, totalStaked, totalSupplyStaked — all fixed at deposit time

Stake.amount is recorded at deposit time and never updated. If clawdToken is a rebasing token (stETH, aTokens, AMPL), the contract's actual token balance diverges over time. On a negative rebase or slashing event, the contract holds fewer tokens than all recorded stakes. The first unstakers drain remaining tokens; later unstakers' safeTransfer calls revert permanently with no recovery path.

Recommendation: Explicitly document that rebasing tokens are unsupported; if rebasing support is needed, implement share-based accounting where Stake.amount stores shares, not nominal amounts.

[H-4] Token Blacklist or Pause Permanently Locks Staked Funds

Severity: High
Source: Phase 1 (dos, erc20)
Location: unstake() line 60 — clawdToken.safeTransfer(msg.sender, amount)

If clawdToken adds msg.sender to a transfer blocklist (common in USDC, USDT, and many governance tokens), or pauses all transfers, safeTransfer reverts and the entire unstake() transaction reverts. Because this rolls back s.amount = 0, the user is trapped: every unstake attempt reverts indefinitely. There is no admin, no rescue function, and no alternative withdrawal path. The user's staked tokens are irrecoverably locked.

Recommendation: Separate the accounting from the transfer using a pull-payment pattern:

mapping(address => uint256) public pendingWithdrawal;

// In unstake(), replace safeTransfer with:
pendingWithdrawal[msg.sender] += amount;

// Separate function:
function withdraw() external {
    uint256 amount = pendingWithdrawal[msg.sender];
    require(amount > 0, "Nothing to withdraw");
    pendingWithdrawal[msg.sender] = 0;
    clawdToken.safeTransfer(msg.sender, amount);
}

[M-1] Public clawdvictionAccrued Variable Enables Snapshot Gaming

Severity: Medium (New finding from Phase 2 — trust-gap + periphery agents)
Source: Phase 2 (agents 11, 6)
Location: clawdvictionAccrued — public state variable, only updated in unstake()

clawdvictionAccrued[user] is a public state variable updated only when a user calls unstake(). A long-term staker who never unstakes has clawdvictionAccrued == 0 despite potentially years of staking history — all their conviction is only visible through getClawdviction(). Any governance or reward contract that reads clawdvictionAccrued directly (it is a public variable, making direct reads easy and tempting) will systematically undercount long-term holders and overcount active churners.

The attack: An adversary can call unstake() on all positions immediately before a governance snapshot to maximize clawdvictionAccrued, then immediately restake. Long-term holders who never touched their positions show clawdvictionAccrued == 0; the adversary shows full historical conviction. Both had identical economic exposure.

The contract's own NatSpec says "Clawdviction calculated off-chain from events" — yet clawdvictionAccrued is public and will be read by integrators who assume it is the canonical on-chain score.

Recommendation: Make clawdvictionAccrued internal (or private) and force all external reads through getClawdviction(). Document clearly that getClawdviction() is the authoritative score.

- mapping(address => uint256) public clawdvictionAccrued;
+ mapping(address => uint256) internal clawdvictionAccrued;

[M-2] getClawdviction() Intermediate Overflow Causes Permanent View Revert

Severity: Medium
Source: Phase 1 (precision-math) + Phase 2 (agents 1, 10 corroborated)
Location: getClawdviction() line 65 — expression evaluation order

return clawdvictionAccrued[user] + totalStaked[user] * block.timestamp - weightedStakeSum[user];

Solidity evaluates this as (clawdvictionAccrued + (totalStaked * block.timestamp)) - weightedStakeSum. The intermediate sum of clawdvictionAccrued + totalStaked * block.timestamp can overflow uint256 even when the mathematically correct final result fits, because the nearly-equal weightedStakeSum is subtracted only after the addition. Solidity 0.8 checked arithmetic causes a permanent revert for that user's address. Any governance or off-chain scoring system relying on this view function silently stops returning valid data.

Fix (safe: inner subtraction cannot underflow — all stakedAt are in the past):

- return clawdvictionAccrued[user] + totalStaked[user] * block.timestamp - weightedStakeSum[user];
+ return clawdvictionAccrued[user]
+     + (totalStaked[user] * block.timestamp - weightedStakeSum[user]);

[M-3] Unbounded stakes[] Array — getActiveStakes() Gas Exhaustion

Severity: Medium
Source: Phase 1 (dos, general, staking) + Phase 2 (agents 3, 5, 8 confirmed as Finding; 7 additional agents corroborated)
Location: getActiveStakes() — double O(n) loop; unstake() zeroes but never removes entries

stake() appends to stakes[user]; unstake() sets s.amount = 0 but never removes the entry. getActiveStakes() iterates the full array twice — once counting active entries, once filling the output. Dead (zeroed) entries from past unstakes are included in both passes. A user with ~3,500 total stake history entries approaches Base's 30M block gas limit for this view call; above ~5,000–6,000 entries the call permanently reverts. On-chain integrations (aggregators, multi-calls, governance snapshot contracts) will OOG for any such user.

Recommendation: Swap-and-pop in unstake() to reclaim slots. Update Unstaked events to emit the new index of the swapped element for off-chain indexers. Alternatively, enforce MAX_STAKES_PER_USER.

[M-4] Atomic Stake-Unstake Spams Events at Near-Zero Cost

Severity: Medium
Source: Phase 1 (staking) + Phase 2 (agents 3, 4, 5 noted no-lock-period governance risk)
Location: stake(), unstake()

No lock period, no EOA guard, and no minimum hold duration allow a contract to call stake() and unstake(i) in the same transaction. block.timestamp - stakedAt == 0 yields zero clawdviction — the caller retains all tokens and pays only gas. On Base (~$0.004/tx), generating 1,000 spurious event pairs costs approximately $4. Off-chain indexers that process Staked/Unstaked events to build participation metrics or leaderboards can be spammed cheaply, inflating apparent protocol activity and corrupting snapshot-based analyses.

Phase 2 additionally noted: with a 12-second window between blocks, a user staking immediately before a snapshot earns amount × 12 clawdviction — small in absolute terms but worth gaming for large capital if governance decisions are high-value.

Recommendation: Add a short minimum hold:

uint256 public constant MIN_HOLD = 1; // 1 second minimum
// In unstake():
require(block.timestamp >= stakedAt + MIN_HOLD, "Too soon to unstake");

[M-5] Token Admin Mint or Burn Corrupts Accounting

Severity: Medium
Source: Phase 1 (erc20)
Location: totalSupplyStaked, unstake() — no external balance validation

If clawdToken supports admin burns from arbitrary addresses, an admin can burn tokens held by the staking contract, reducing actual balance below totalSupplyStaked. Subsequent safeTransfer calls in unstake() revert for the last stakers. Conversely, if admin minting is unrestricted, an attacker with admin access can mint tokens, stake, accumulate clawdviction, then unstake — potentially draining real user deposits at scale.

Recommendation: Verify in deployment that the CLAWD token contract does not permit admin burns from arbitrary addresses. Document this constraint in the staking contract's NatSpec.

[M-6] Stray Token Transfers Bypass Accounting — Excess Permanently Locked

Severity: Medium
Source: Phase 1 (general, access-control)
Location: Contract-level — no sweep or rescue function

Tokens transferred directly to the contract (not via stake()) increase clawdToken.balanceOf(address(this)) without updating totalSupplyStaked. There is no owner, no rescue function, and no way to distinguish staked from donated tokens. These tokens are permanently locked. Additionally, other ERC20 tokens accidentally sent to this address cannot be recovered.

Recommendation: Add a recovery function restricted to the contract's deployer or a designated role:

function recoverStrayTokens(address token, address to) external onlyOwner {
    if (token == address(clawdToken)) {
        uint256 excess = clawdToken.balanceOf(address(this)) - totalSupplyStaked;
        clawdToken.safeTransfer(to, excess);
    } else {
        IERC20(token).safeTransfer(to, IERC20(token).balanceOf(address(this)));
    }
}

[L-1] ERC777 tokensReceived Hook — Unguarded Chained Unstake Path

Severity: Low (Phase 1 High · demoted: Phase 2 confirmed CEI followed in unstake, no double-spend possible)
Source: Phase 1 (erc20) + Phase 2 (agents 3, 9)
Location: unstake() line 60 — clawdToken.safeTransfer after state zeroing

unstake() correctly follows CEI — s.amount = 0 is set before safeTransfer. A re-entrant call to unstake(sameIndex) is blocked. However, if clawdToken is ERC777, the tokensReceived hook fires after transfer and can call unstake() with a different active index. Phase 2 analysis confirmed this does not enable double-spending (each stake's state is independently zeroed), but it allows a caller to chain multiple unstakes in a single transaction. Future integrations that assume one unstake per transaction (rate-limiting, multi-step flows) may be bypassed.

Recommendation: Add nonReentrant to unstake().

[L-2] weightedStakeSum Invariant Is Fragile Under Future Refactors

Severity: Low
Source: Phase 1 (general) + Phase 2 (agents 1, 5, 10 verified the invariant holds)
Location: stake() line 44, unstake() line 58

The O(1) clawdviction formula depends on weightedStakeSum[user] == Σ(active_stake.amount × active_stake.stakedAt) being maintained exactly. Phase 2 confirmed the invariant holds under current code. However, any future function that modifies s.amount or s.stakedAt without mirroring the change in weightedStakeSum will silently corrupt getClawdviction() for that user with no revert.

Recommendation: Add NatSpec documenting the invariant. Include an invariant assertion in tests.

[L-3] clawdvictionAccrued Never Pruned — Historical Score Persists Indefinitely

Severity: Low
Source: Phase 1 (staking)
Location: clawdvictionAccrued — append-only, no reset or decay

Once accrued, clawdviction never decreases. A user who fully unstaked years ago and holds zero tokens today retains their full historical conviction score. If clawdviction gates governance decisions or airdrops, it measures past exposure rather than current commitment — stakeholders with no active position retain governance influence indefinitely.

Recommendation: If current commitment matters, compute governance weight from totalStaked[user] * snapshotBlock.timestamp - weightedStakeSum[user] (active portion only) rather than getClawdviction().

[L-4] No Zero-Address Validation on _clawdToken Constructor Parameter

[L-5] Block Timestamp Manipulation — Minor Clawdviction Inflation

Severity: Low
Source: Phase 1 (general, chain-specific) + Phase 2 (agents 7, 8, 11, 12 corroborated)
Location: stake(), unstake(), getClawdviction()

All conviction accounting uses block.timestamp exclusively. On Base, the sequencer controls timestamps and can adjust within the allowed drift (~15 seconds). A colluding sequencer or validator can inflate block.timestamp at unstake time relative to stake time, inflating per-position clawdviction. For a user with totalStaked = 10^24 wei, a 15-second manipulation adds 1.5 × 10^25 conviction units in one block. For governance uses, even marginal manipulations matter.

Recommendation: For high-stakes governance decisions, enforce a minimum hold period so per-block manipulation becomes economically negligible.

[L-6] Sequencer Downtime Temporarily Prevents Unstaking

Severity: Low
Source: Phase 1 (chain-specific)
Location: unstake()

During Base sequencer outages, users cannot submit transactions and therefore cannot unstake. Since there are no lock periods or slashing risks, this is a temporary delay only. Clawdviction continues accruing during downtime, marginally benefiting stakers at no cost. No material security risk.

[L-7] getStakeCount() Returns Historical Count Including Dead Slots

Severity: Low (New finding from Phase 2)
Source: Phase 2 (agents 5, 6)
Location: getStakeCount() — returns stakes[user].length

getStakeCount() returns the total length of the stakes[user] array, which includes all historical slots zeroed by unstake(). It can return 1,000 while getActiveStakes() returns 0. Off-chain integrations using this count to iterate or allocate for active positions will encounter ghost entries and must filter by amount > 0.

Recommendation: Rename to getTotalStakeCount() or add a separate getActiveStakeCount() function that iterates and counts only non-zero entries.

Info

[I-1] NatSpec Contradicts On-Chain Implementation
The @notice states "Clawdviction calculated off-chain from events" but the contract implements full on-chain tracking via clawdvictionAccrued, weightedStakeSum, and getClawdviction(). This contradicts the design intent and misleads integrators about which source is authoritative. Update NatSpec to clarify that getClawdviction() is the canonical on-chain score.

[I-2] PUSH0 Opcode — Safe on Base Only
Solidity ^0.8.20 emits PUSH0. Base supports the Shanghai EVM, so this is safe. Risk exists only if the contract is redeployed to pre-Shanghai networks (e.g., older L2s or sidechains without Shanghai support).

[I-3] Theoretical amount * block.timestamp Overflow (Unreachable)
Overflow in weightedStakeSum accumulation (amount * block.timestamp) would require totalStaked approaching ~6.5 × 10^67 — astronomically beyond any realistic ERC-20 supply. Solidity 0.8 would revert rather than silently corrupt state. Informational only. (Phase 2 agents 1, 10 independently verified.)

[I-4] getClawdviction() Subtraction Cannot Underflow
The expression totalStaked[user] * block.timestamp - weightedStakeSum[user] is always non-negative: since all stakedAt timestamps are in the past (stakedAt ≤ block.timestamp), the product totalStaked * now ≥ weightedStakeSum algebraically. The invariant was independently verified by Phase 2 agents 1, 3, 5, 9, 10, 12.
