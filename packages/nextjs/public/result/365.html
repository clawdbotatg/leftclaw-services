Findings

[1] Unbounded external state dependency causes permanent per-agent denial-of-service

Severity: High
Origin: [both] — phase1: evm-audit-dos (DOS-1, DOS-2), evm-audit-general (I-2), evm-audit-erc721 (L-3) · phase2: pashov agents 4,5,6,7,9,10,11,12 (finding + leads), agent 7 promoted with a Foundry-measured gas proof
Location: computeScore() L156-191, and every caller: mintFor() L209-225, refresh() L230-238, tokenURI() L258-294, scoreOf() L194-197, tierOf() L200-203

Description: Two distinct, coexisting mechanisms both cause the same failure mode — computeScore becoming permanently unusable for a given agent, with no recovery path since identityRegistry/partnershipBonds are immutable and there is no owner/admin/pause anywhere in the contract:

  • Mechanism A — unguarded reverts. identityRegistry.getAgent() and the three partnershipBonds calls have no try/catch. If either external contract ever reverts for some/all inputs (paused, upgraded with an access gate, self-destructs), computeScore() reverts unconditionally.
  • Mechanism B — unbounded array copy. partnershipBonds.getBondsByParticipant(agent) (L164) copies an agent's entire bond-ID array into memory even though only ids[0] is ever read (L167-169). Since IPartnershipBondsV2 exposes no pagination/cap and bond count is monotonically non-decreasing, gas cost scales linearly and unboundedly with an agent's historical bond count.

Proof of Concept:

  • Mechanism A: identityRegistry is later paused or upgraded to add an access gate on getAgent. Any call into computeScore(agent) for the affected agent(s) now reverts; tokenURI for every existing token depending on that path breaks in every wallet/marketplace; no further mints/refreshes are possible; nothing in this contract can route around it.
  • Mechanism B: a Foundry harness reproducing computeScore's exact logic against a mock registry measured: bondCount=1 → 22,899 gas; bondCount=1,000 → 938,720 gas; bondCount=5,000 → 4,943,314 gas; bondCount=20,000 → 24,413,664 gas (already exceeds a typical 30M-gas block on its own); bondCount=150,000 → 487,694,462 gas (impossible on any current EVM chain). An agent's own legitimate activity — the exact behavior this reputation system is designed to reward — is the one most likely to trigger its own permanent DoS; a third party can also grief a victim this way if bond creation against an unwilling target is possible on the PartnershipBondsV2 side (unverified, out of scope).

Recommendation:

  function computeScore(address agent) public view returns (...) {
-     (, bool active, , uint256 registeredAt) = identityRegistry.getAgent(agent);
-     registered = (registeredAt > 0 && active);
+     try identityRegistry.getAgent(agent) returns (string memory, bool active, string memory, uint256 registeredAt) {
+         registered = (registeredAt > 0 && active);
+     } catch {
+         registered = false; // degrade instead of reverting
+     }

-     bondCount = partnershipBonds.getBondsByParticipantCount(agent);
-     if (bondCount > 0) {
-         uint256[] memory ids = partnershipBonds.getBondsByParticipant(agent);
-         if (ids.length > 0) {
-             IPartnershipBondsV2.Bond memory b = partnershipBonds.getBond(ids[0]);
+     // Request a bounded/O(1) accessor from IPartnershipBondsV2 instead of
+     // copying the full array to read a single element:
+     // function getBondsByParticipantAt(address participant, uint256 index) external view returns (uint256);
+     bondCount = partnershipBonds.getBondsByParticipantCount(agent);
+     if (bondCount > 0) {
+         uint256 firstId = partnershipBonds.getBondsByParticipantAt(agent, 0);
+         IPartnershipBondsV2.Bond memory b = partnershipBonds.getBond(firstId);

At minimum, document the immutable-dependency trust assumption explicitly for integrators given the deliberate "no admin" design.

[2] refresh() can never report a real tier transition — oldTier always equals newTier

Severity: Medium
Origin: [both] — phase1: evm-audit-erc721 (L-1) · phase2: 6 of 12 agents independently promoted this to a FINDING (agents 5, 8, 9, 12, plus 2 more as leads), confidence 95 — the single most-corroborated issue in the entire run
Location: refresh() L230-238, _liveTier() L345-348

Description: oldTier (via _liveTier(agent) → computeScore(agent), L233) and newTier (a second computeScore(agent) call, L234) both read the same immutable external view-typed state — compiled to STATICCALL, so no state mutation can occur between the two calls within one transaction. oldTier and newTier are therefore mathematically guaranteed identical on every single invocation, contradicting the function's own NatSpec ("Emits StreetCredRefreshed even if the tier didn't change" implies it can also fire when it did). Any indexer/dashboard trusting this event to detect a real tier transition (e.g. alerting on a Platinum→Bronze collapse) will never observe one — the bug silently conceals every real transition automatically, on every call, forever.

Proof of Concept: Mint a badge for agent at Bronze. The agent's bond later becomes Platinum-eligible (or, conversely, their registration lapses and tier collapses to None). Call refresh(tokenId) — the event fires with oldTier == newTier in both directions, every time, regardless of what actually changed since the last refresh.

Recommendation:

+ mapping(uint256 => uint8) private _lastTier;

  function mintFor(address agent) external returns (uint256 tokenId) {
      ...
      (uint16 score, uint8 tier,,,,,) = computeScore(agent);
      if (tier == TIER_NONE) revert NotEligible();
+     _lastTier[tokenId] = tier;
      ...
  }

  function refresh(uint256 tokenId) external returns (uint8 newTier, uint16 newScore) {
      if (!_exists[tokenId]) revert TokenDoesNotExist();
      address agent = address(uint160(tokenId));
-     uint8 oldTier = _liveTier(agent);
+     uint8 oldTier = _lastTier[tokenId];
      (uint16 s, uint8 t,,,,,) = computeScore(agent);
+     _lastTier[tokenId] = t;
      _refreshedAt[tokenId] = block.timestamp;
      emit StreetCredRefreshed(agent, tokenId, oldTier, t, s);
      return (t, s);
  }

[3] bondCount > 1 bonus is decoupled from bond quality — lets a score cross a tier boundary via a worthless second bond

Severity: Medium
Origin: [phase2 only] — pashov agents 3 and 10 independently promoted this to a FINDING (confidence 85), 5 further agents flagged it as a lead. Re-examined against source directly by this auditor and confirmed.
Location: computeScore() L162-189

Description: The "+5 Multiple Bonds" bonus (L189, if (bondCount > 1) s += 5;) is driven purely by getBondsByParticipantCount, entirely independent of hasBond/bondActive/tier-bonus, which are derived only from a single bond, getBond(ids[0]) (L166-172). Verified against the contract's own documented tier bands (L360-366, s<=30→Bronze, s<=55→Silver, s<=75→Gold, else Platinum): an agent at score 75 (registered 30 + hasBond 25 + bondActive 15 + bronze tier-bonus 5, from one 0.02 ETH active bond — sitting at the exact top of the Gold band) crosses into Platinum at score 80 by opening any second bond, regardless of that second bond's stake or active status, since nothing beyond bondCount ever inspects it. This is provable purely from VaultfireStreetCred's own logic — it only requires that a second bond can be opened with lower quality than the first, which nothing in the IPartnershipBondsV2 interface forbids. The same decoupling can also, in the reverse case, grant the +5 bonus while hasBond == false (if ids[0] happens to be the zero-stake/inactive bond).

Proof of Concept: Agent has 1 active bond, stakeAmount = 0.02 ether (bronze band, >= 0.01 ether). score = 30 (registered) + 25 (hasBond) + 15 (bondActive) + 5 (bronze bonus) = 75 → _scoreToTier(75) = TIER_GOLD (L363, s <= 75). Agent opens a second bond with 0 stake, inactive. bondCount = partnershipBonds.getBondsByParticipantCount(agent) now returns 2 → s += 5 (L189) → score = 80 → _scoreToTier(80) = TIER_PLATINUM (L365, else). No increase in real collateral occurred; the Gold→Platinum boundary was crossed purely by bond count.

Recommendation:

- if (bondCount > 1) s += 5;
+ // Only credit the "multiple bonds" bonus for bonds that actually carry
+ // stake and are active — requires either iterating all bond IDs, or a
+ // dedicated aggregate accessor on IPartnershipBondsV2:
+ uint256 qualifyingBonds = _countActiveStakedBonds(agent); // sums stakeAmount>0 && active across all ids
+ if (qualifyingBonds > 1) s += 5;

[4] No revocation path — hasBadge/balanceOf/ownerOf/locked stay permanently true after live eligibility drops to zero

Severity: Medium
Origin: [phase1 only] — evm-audit-access-control (AC-1), evm-audit-general (M-1), corroborated independently by both checklist agents. Re-examined against source directly by this auditor and confirmed. This is the item most directly responsive to the client's stated audit focus ("badge-revocation").
Location: mintFor() L209-225, _exists mapping L113 (set true once, never cleared anywhere in the contract), hasBadge() L241-243, balanceOf() L247-250, ownerOf() L252-255, locked() L298-301 — contrast with the genuinely "live" computeScore()/tokenURI()

Description: _exists[tokenId] is set once in mintFor() and never cleared — there is no burn, revoke, or expiry function anywhere in the contract; refresh() explicitly documents "Does NOT burn or transfer" (L229). tokenURI(), scoreOf(), tierOf() correctly recompute live and will show TIER_NONE/"Unverified" once an agent's identity is deactivated or bond closes — but hasBadge(), balanceOf(), ownerOf(), getApproved() only check _exists and will keep affirming the badge exists forever. Any integrator using the standard ERC-721 idiom (balanceOf(agent) > 0) as a "currently reputable" signal — the natural way to consume a reputation-badge contract — is misled indefinitely once an agent's real standing has lapsed, directly undermining the contract's own "live reputation" framing.

Proof of Concept: Agent A registers and opens a 0.5 ETH bond → computeScore(A) returns Platinum. Anyone calls mintFor(A) → hasBadge(A) == true, balanceOf(A) == 1. A's registration is later deactivated and bond closed → computeScore(A) now returns TIER_NONE/score 0, and tokenURI correctly shows "Unverified" — but hasBadge(A)/balanceOf(A)/ownerOf(tokenId) still report the badge as valid and held, permanently, since nothing clears _exists.

Recommendation:

+ event StreetCredRevoked(address indexed agent, uint256 indexed tokenId);
+ error StillEligible();
+
+ function revoke(uint256 tokenId) external {
+     if (!_exists[tokenId]) revert TokenDoesNotExist();
+     address agent = address(uint160(tokenId));
+     (, uint8 tier,,,,,) = computeScore(agent);
+     if (tier != TIER_NONE) revert StillEligible();
+     delete _exists[tokenId];
+     emit Transfer(agent, address(0), tokenId);
+     emit StreetCredRevoked(agent, tokenId);
+ }

If permanent record-keeping (a provenance record rather than a live-standing check) is the intended design instead, document prominently that hasBadge/balanceOf/ownerOf are NOT eligibility signals and integrators must call tierOf()/computeScore().

[5] Permissionless, non-consensual minting freezes a momentary/manipulable score into an immutable event, with no self-burn/opt-out

Severity: Medium
Origin: [both] — phase1: evm-audit-access-control (AC-2), evm-audit-erc721 (L-2) — no-burn/consent framing · phase2: pashov agent 11 (confidence 75) — immutable-event-divergence framing, a genuinely new mechanism not surfaced in phase 1
Location: mintFor() L209-225 — no burn()/opt-out function exists anywhere

Description: Two related but distinct mechanisms both stem from mintFor being fully permissionless with no cooldown or consent gate:

  • Consent/sovereignty: any third party can permanently mint a soulbound badge onto an eligible agent's address without that agent's consent, and the agent can never remove it (no burn function; transfer/approve always revert).
  • Immutable-event divergence: mintFor requires only that computeScore(agent) is non-zero at the calling block; the resulting tier/score are baked into a permanent StreetCredMinted event. An attacker can call mintFor(victim) the instant a victim becomes minimally eligible (before any bond exists) to permanently record a low Bronze score for a victim who may reach Platinum minutes later — the live tokenURI self-corrects, but off-chain consumers treating the mint event as historical truth (leaderboards, snapshot-based eligibility checks) do not. refresh() offers no remedy since its own before/after diff is dead (Finding 2).

Proof of Concept: Agent A is merely registered in IdentityRegistry (unrelated to wanting a public badge, score 30, Bronze). A third party calls mintFor(A) the instant this becomes true; StreetCredMinted(A, tokenId, tier=Bronze, score=30) is now permanent on-chain history, even though A opens a 0.5 ETH bond five minutes later that would have scored Platinum. A has no recourse — no burn, no transfer.

Recommendation:

+ function burn(uint256 tokenId) external {
+     address agent = address(uint160(tokenId));
+     if (msg.sender != agent) revert Soulbound();
+     if (!_exists[tokenId]) revert TokenDoesNotExist();
+     delete _exists[tokenId];
+     emit Transfer(agent, address(0), tokenId);
+ }

Separately, consider whether StreetCredMinted/StreetCredRefreshed should carry tier/score at all, given they are point-in-time snapshots of a value the contract itself treats as continuously live elsewhere — or require a minimum time-since-registration before mintFor is callable, to reduce the value of adversarial mint-timing.

[6] Unverified assumption that getBondsByParticipant(...)[0] is the agent's most recent bond

Severity: Medium
Origin: [both] — phase1: evm-audit-general (I-1), evm-audit-erc721 (I-3) · phase2: 11 of 12 agents independently flagged this as a lead — the most repeated observation across the entire 12-agent panel — promoted per the multi-agent-convergence rule (2+ agents, consistently demoted not rejected → promote at confidence 75)
Location: computeScore() L162-172

Description: The code comments "Use first (most recent) bond, matching API behaviour" (L168) and unconditionally trusts ids[0] from partnershipBonds.getBondsByParticipant(agent) for hasBond, bondActive, and the entire stake-tier bonus (up to 60 of 95 possible points). IPartnershipBondsV2 is declared only as an interface in this repository — its implementation is not present anywhere on disk (confirmed via filesystem search by multiple agents) — so the ordering guarantee cannot be verified from source. Standard append-only array patterns (the conventional Solidity implementation for a "bonds by participant" list) return index 0 as the oldest entry, not the newest, which would make the code's own comment backwards. If so, an agent's score is permanently pinned to whatever their very first bond looked like — including a since-closed or trivial one — regardless of larger, more active bonds opened later.

Proof of Concept: Not fully provable from this repository alone (the counterpart contract is out of scope), which is why this is presented at Medium/promoted-lead confidence rather than High — but the near-unanimous 11/12 independent agent convergence, combined with the code's own comment asserting an ordering property it does not enforce, makes this a high-priority item for the client to verify against the deployed PartnershipBondsV2 before relying on this score for any consequential decision.

Recommendation: Confirm the ordering guarantee of getBondsByParticipant against the actual PartnershipBondsV2 deployment and document it explicitly here; if unguaranteed (or reverse of what's assumed), select deterministically — e.g. iterate and pick by highest stakeAmount or most recent createdAt — instead of trusting array position.

Informational / Ruled Out

  • onERC721Received not checked on mint [phase1: evm-audit-erc721] — confirmed non-issue: since the token can never subsequently be transferred (Soulbound), the classic "stuck NFT" risk the hook prevents cannot occur here.
  • totalMinted may mislead integrators into assuming enumerable/sequential token IDs [phase1: evm-audit-erc721] — token IDs are uint256(uint160(agent)), sparse and unrelated to totalMinted; contract correctly doesn't advertise IERC721Enumerable. Recommend a NatSpec clarification.
  • Base64 encoder (_b64) heap over-read [phase2: ruled out] — initially flagged as a plausible smell (missing the canonical implementation's scratch buffer); one pashov agent built a Foundry test harness against lengths 1, 2, 4, 5, 29, 31, 32 (including the zero-slack length==32 boundary) and confirmed byte-for-byte correct output in every case against a reference implementation. Documented here as a tested false positive so it isn't re-flagged without re-verification in a future audit.
  • bondCount/ids.length cross-call desync [phase2 lead, both mentioned] — bondCount (getBondsByParticipantCount) and ids.length (getBondsByParticipant) are independent external calls never cross-checked; folded into Finding 3's quality-decoupling analysis above since it's the same underlying root cause (the +5 bonus trusting an unverified count).
  • Stale collateral — stakeAmount possibly not zeroed on bond closure [phase2 lead] — if Bond.stakeAmount is a historical field not zeroed on withdrawal, an agent could retain a permanent high-tier score from a one-time, since-withdrawn stake. Unverifiable without PartnershipBondsV2 source; flagged for the client's follow-up alongside Finding 6.
  • evm-audit-precision-math: no findings — all score/tier boundary math (_bondTierBonusTier, _scoreToTier) was traced exhaustively by two independent passes (one ethskills checklist agent, one pashov math-precision agent) and is gap-free/overlap-free; max achievable score is exactly 95, well within uint16 headroom.

⚠️ This review was performed by AI auditor agents. AI analysis can never verify the complete absence of vulnerabilities and no guarantee of security is given. On-chain monitoring and a follow-up manual review focused on verifying IPartnershipBondsV2's actual bond-ordering and stake-lifecycle semantics (Finding 6 and the related leads above) are strongly recommended before this contract's score is relied upon for high-stakes decisions.
