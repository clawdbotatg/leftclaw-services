Findings

[80] 1. External YRT-supply-freeze precondition is a real, provable, non-timelocked, role-gated toggle — not enforced anywhere in this contract

ProRataDistributor.constructor / swap (cross-contract with the external YakStrategyV2.updateDepositsEnabled / YakStrategyManagerV1.enableDeposits) · Confidence: 80 · Severity: Medium

Description
The contract's entire economic guarantee — that the sum of all payouts across every
swap() call never exceeds totalPayout — depends on yrt.totalSupply() (read
once, at constructor L89, and baked into the immutable rate at L101) never
increasing for the life of the contract. The NatSpec (L21-29) documents this as a
required precondition ("deposits are disabled and must never be re-enabled") that
is "asserted by the deploy script" — i.e., not enforced by any code in this file.

This audit went further than treating that as a documentation-only trust
assumption and independently fetched the real, verified source of the external YRT
contract to test whether the precondition is actually structurally permanent. It
is not:

// YakStrategyV2.sol (external contract, out of this audit's primary scope,
// fetched independently for verification)
function updateDepositsEnabled(bool newValue) public onlyOwner {
    require(DEPOSITS_ENABLED != newValue);
    DEPOSITS_ENABLED = newValue;
    emit DepositsEnabled(newValue);
}

// JoeLendingStrategyV1.sol constructor (external contract)
...
updateDepositsEnabled(true);
transferOwnership(_timelock);   // NOT renounced

// YakStrategyManagerV1.sol (external contract — this is the strategy's owner)
function enableDeposits(address strategy) external {
    require(hasRole(STRATEGY_ENABLER_ROLE, msg.sender), "enableDeposits::auth");
    IStrategy(strategy).updateDepositsEnabled(true);
    emit SetDepositsEnabled(strategy, true);
}

No timelock, delay, or queue mechanism exists anywhere in YakStrategyManagerV1
for this specific call — whoever currently holds STRATEGY_ENABLER_ROLE can
re-enable deposits on this exact YRT strategy in a single transaction, at any time,
with zero on-chain warning beforehand. Once re-enabled, JoeLendingStrategyV1 ._deposit() mints new YRT to any depositor (require(DEPOSITS_ENABLED == true); ... _mint(account, shareTokenAmount);), growing totalSupply() past the value
ProRataDistributor.rate was computed from — with ProRataDistributor itself
having zero mechanism to detect or react to that growth.

Proof of Concept
Live on-chain verification performed for this audit (block ~90,439,508):

  • YRT.owner() = 0x302404cb8F34713A8B8DBF9b4989A41252332068 — a live, 10,085-byte
    contract (verified as YakStrategyManagerV1), not renounced, not address(0).
  • YRT.DEPOSITS_ENABLED() = false — currently disabled, matching the documented
    precondition today.
  • YRT.totalSupply() = 9119526819 — unchanged since ProRataDistributor's
    deployment (no dilution has occurred; this is not a live active exploit).

Exploit chain (not currently triggered, but structurally live and provable):
whoever holds STRATEGY_ENABLER_ROLE on YakStrategyManagerV1 calls
enableDeposits(0x964555644E067c560A4C144360507E80c1104784) → DEPOSITS_ENABLED
flips to true on the strategy → any depositor calls the strategy's deposit() →
new YRT is minted to them → they call ProRataDistributor.swap(newAmount) → paid
out at the stale rate computed for the smaller original supply, diluting or
draining the payout pool that totalPayout was sized for; later legitimate
holders of the original supply hit atomic reverts once the balance is exhausted
(no partial loss, but the documented pro-rata guarantee is silently violated).

Severity rationale: rated Medium rather than Critical/High because triggering
it requires action by a specific, named, currently-legitimate privileged role on a
different contract than the one under audit — not an unprivileged attacker path
against ProRataDistributor itself. It is reported as a confirmed finding (not
merely a caveat) because this audit obtained and read the actual mechanism and
verified on-chain that it is live, un-renounced, and un-timelocked — a concrete,
provable trust dependency rather than a hypothetical.

Fix

+    uint256 public cumulativeSwapped;
+    error ExceedsFrozenSupply();
+
     function swap(uint256 yrtAmount) external {
         if (block.timestamp > deadline) revert SwapWindowOver();
+        if (cumulativeSwapped + yrtAmount > totalSupplyAtDeploy) revert ExceedsFrozenSupply();
         uint256 payoutAmount = quote(yrtAmount);
         if (payoutAmount == 0) revert NothingToSwap();
+        cumulativeSwapped += yrtAmount;
         _safeTransferFrom(yrt, msg.sender, address(this), yrtAmount);
         _safeTransfer(token, msg.sender, payoutAmount);
         emit Swapped(msg.sender, yrtAmount, payoutAmount);
     }

(caps cumulative redemptions at the supply snapshot taken at deployment,
independent of what the external contract's totalSupply() grows to later).
Alternatively/additionally: before funding each round, the deploying team should
independently verify — not merely assume from NatSpec — that the specific YRT
strategy's deposit-enable role has been revoked or is otherwise permanently
disabled for that round.

[78] 2. Constructor never validates the derived rate — a plausible parameter choice silently bricks all swaps, or causes an undetectable permanent shortfall

ProRataDistributor.constructor · Confidence: 78 · Severity: Medium

Description
rate = totalPayout_ * RATE_PRECISION / supply (L101) is computed via floor
division and never checked for degeneracy. The constructor validates
totalPayout_ != 0 (L87) and supply != 0 (L90) independently, but never
validates the quotient itself — a case the checks do not, and structurally
cannot, cover.

Proof of Concept

Case A — total, permanent brick. supply = 1e24 (1,000,000 YRT, 18-decimal),
totalPayout_ = 500000 (an easy decimal-scale mistake) →
rate = 500000*1e18 // 1e24 = 0. Deployment succeeds silently. Every subsequent
swap() computes quote()==0 for any yrtAmount, reverting NothingToSwap()
(L118) unconditionally, forever. After deadline, sweep(token) returns 100% of
the funded totalPayout to the owner having distributed nothing to anyone, with no
on-chain signal that anything went wrong.

Case B — silent large shortfall, worse because nothing ever reverts.
supply = 1e24, totalPayout_ = 1500000 → rate = floor(1.5e24/1e24) = 1. A
holder redeeming the entire supply in one call receives
quote(1e24) = 1e24 * 1 / 1e18 = 1,000,000 — only 1,000,000 of the promised
1,500,000 (a 33% shortfall) is ever claimable in total, even though every
individual swap() succeeds and 100% of YRT is redeemed. This is strictly worse
than Case A operationally since nothing ever reverts or signals the problem — it
is silent value loss from the rate's coarse quantization (1e18/supply resolution
instead of the full 1/supply resolution a direct
yrtAmount*totalPayout/supply computation would give).

Does not affect the live deployment — independently verified:
rate=1186981452639335672, totalPayout=10824709191, supply=9119526819;
quote(supply) = 10824709190, within 1 raw unit of totalPayout (healthy,
expected floor-rounding dust only).

Fix

     uint256 supply = yrt_.totalSupply();
     if (supply == 0) revert ZeroSupply();
     ...
     rate = totalPayout_ * RATE_PRECISION / supply;
+    if (rate == 0) revert ZeroRate();

For Case B, consider computing each payout directly as
yrtAmount * totalPayout / supply inside quote() instead of precomputing rate,
restoring full 1/supply resolution and eliminating the double-floor composition.

[75] 3. No ownership transfer, renounce, or recovery mechanism — permanent owner-key loss would strand any unclaimed payout balance forever

ProRataDistributor.owner / sweep · Confidence: 75 · Severity: Medium

Description
owner (address public immutable, L62) is set once in the constructor (L95),
validated only for non-zero (L86). No transferOwnership, Ownable2Step,
renounce, or rotation path exists anywhere in the contract, and because it is
immutable this is fixed in bytecode forever. sweep() (owner-gated, L128) is the
only function that can ever move the payout-token balance out of the contract
after deadline. Permanent loss of the owner key's signing capability — lost key,
destroyed hardware wallet, decommissioned multisig — leaves any unclaimed payout
balance permanently unreachable by any address, with no on-chain or off-chain
recovery path.

Proof of Concept
(1) Contract is funded with totalPayout. (2) Only a fraction of YRT holders
redeem before deadline — normal, expected behavior, not every holder redeems.
(3) deadline passes; sweep(token) becomes callable. (4) Owner-key access is
lost before that call is made. (5) The remaining balance sits in the contract
forever — no code path can ever reassign owner.

Fix: not retrofittable on this already-deployed, fully immutable instance
(accepted residual risk — the current owner key should have robust custody/backup
procedures, since the contract provides no on-chain backstop). For future
deployments of this template, add a minimal two-step ownership-transfer mechanism
(proposeOwner() / acceptOwnership(), Ownable2Step-style) gated by the current
owner.

[70] 4. swap() trusts the caller-supplied yrtAmount as the amount actually received — no before/after balance check on the YRT leg

ProRataDistributor.swap · Confidence: 70 · Severity: Low

Description
NatSpec disclaims fee-on-transfer/rebasing support for the payout token
(L44-45) but is silent on the identical risk for YRT itself. swap() computes
payoutAmount = quote(yrtAmount) (L115) from the requested amount, then pulls
yrtAmount of YRT via _safeTransferFrom (L119) without ever measuring the
contract's actual YRT balance delta.

Proof of Concept
Not exploitable against the live YRT (a standard, non-fee YakStrategy share
token, confirmed via its fetched source — plain balance-mapping transfers, no
fees, no hooks). Would only matter if this contract were redeployed against a
YRT token that behaved as fee-on-transfer or deflationary.

Fix: Document that YRT must also be non-fee-on-transfer/non-rebasing
(extending the existing payout-token disclaimer), or measure the actual balance
delta before/after the pull if this contract is ever redeployed against a
different share-token implementation.

[65] 5. No emergency pause / circuit breaker on swap()

ProRataDistributor (whole contract) · Confidence: 65 · Severity: Low

Description
The fully immutable design (deliberate) means there is no way for the owner to
halt swap() early if a problem surfaces mid-window — e.g., the payout token
being paused/blacklisting the contract, or the external YRT-supply-freeze
precondition (Finding 1) turning out not to hold.

Fix: Accepted residual risk for the deployed instance (immutable, no retrofit
possible). Future redeployments of this template could add a scoped pause guard
on swap() only, structured so it cannot be used to touch the payout-token
balance before deadline.

[60] 6. sweep()'s arbitrary-token low-level call has no returndata cap or code-existence check

ProRataDistributor.sweep / _safeTransfer · Confidence: 60 · Severity: Low

Description
A maliciously crafted "bait" token sent to the contract and later swept by the
owner could return an oversized bytes payload from transfer(), forcing
expensive memory copying before the abi.decode check at L141 runs. This path is
owner-gated (L128) — no unprivileged actor can trigger it; worst case the owner
burns gas on a failed sweep attempt of a bait token.

Fix: Cap processed returndata (e.g., a fixed 32-byte returndatacopy) and/or
add an explicit extcodesize check before the call.

[55] 7. Centralized/blacklistable payout token (USDT.e) is a single point of total, unrecoverable freeze

ProRataDistributor.swap / sweep · Confidence: 55

Both the swap-payout path (L120) and the post-deadline owner-recovery path (L134)
route through the same token.transfer call. If the token issuer ever blacklists
this contract's address, both revert forever, permanently stranding YRT and any
remaining payout balance with no owner recourse. Requires the token issuer (not an
ordinary attacker) to act — a trust-model dependency inherent to using a
centralized, pausable/blacklistable ERC-20 as the payout asset.

[50] 8. sweep/constructor token-resolution use plain address equality with no defense against token aliasing (future-redeployment risk only)

ProRataDistributor.constructor / sweep · Confidence: 50

Six independent phase-2 attack agents converged on the same code smell: the
constructor never asserts depositToken() != address(yrt_) (L91-97), and
sweep's carve-outs (L129-131) are plain == checks. If a future redeployment of
this reusable template ("Deploy one instance per (YRT, payout) pair") were pointed
at a YakStrategy whose depositToken() returns its own address, token == yrt
would hold, breaking the "escrowed YRT is worthless and unrecoverable" guarantee
and permanently blocking recovery of what should have been the payout token. Not
reachable today — live token (USDT.e) is confirmed structurally distinct from
live yrt. Recommend an explicit constructor check
if (depositToken == address(yrt_)) revert InvalidPayoutToken(); for future
redeployments.

[45] 9. Malformed non-boolean nonzero-length return data causes a raw decode panic instead of TransferFailed()

_safeTransfer / _safeTransferFrom (L138-148) · Confidence: 45

abi.decode(data, (bool)) reverts with a generic panic for non-canonical-boolean
nonzero-length returndata instead of the contract's own error. Transaction still
reverts safely either way — no fund-safety impact, just error-clarity. Fix: guard
with a data.length >= 32 check before decoding.

[40] 10. sweep() may revert on a zero-balance token that disallows zero-amount transfers

ProRataDistributor.sweep (L127-136) · Confidence: 40

A minority of tokens revert on zero-value transfer(). No fund-loss impact —
owner gets a revert instead of a silent no-op. Fix: if (balance == 0) return;
before the transfer.

Leads

Trails with concrete code smells where the full exploit path could not be completed, or that were resolved sound during this audit — recorded for completeness, not scored.

  • Reentrancy surface on swap() — ProRataDistributor.swap — Code smells: YRT
    pulled in (L119) before payout pushed out (L120), no reentrancy guard. Resolved
    sound    : this audit independently fetched the real YRT contract's source and
    confirmed its _transferTokens is a plain balance-mapping update with no
    external calls or hooks; combined with zero mutable per-call state in
    ProRataDistributor, no exploit path exists. No action required.
  • Adversarial swap-splitting to exceed totalPayout — ProRataDistributor.swap
    — Resolved sound: proven algebraically and via brute-force simulation
    (independently by 6+ agents across both phases) that
    Σfloor(aᵢ·rate/1e18) ≤ floor(Σaᵢ·rate/1e18) ≤ totalPayout for any partition.
    No action required.
  • WAVAX fallback constant correctness — constructor L60 — Resolved sound:
    independently verified against external sources to be the correct, real
    Avalanche WAVAX address. Not reachable by the live deployment regardless (its
    depositToken() returned non-zero). No action required.
  • Splitting swaps into many small calls yields ≤ payout of one large swap —
    quote/swap — Self-inflicted rounding loss to the swapper, not a protocol
    risk. Optional documentation only.
