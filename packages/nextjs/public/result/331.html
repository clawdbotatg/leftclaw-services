[90] 1. FeeManager performance-fee formula divides by the wrong price, systematically over-minting fee shares to the fee recipient

FeeManager.calculateFee · Confidence: 90 · [phase2: economic-security agent], verified independently against source by the orchestrator (contradicts phase-1's precision-math pass and two other phase-2 agents that pattern-matched the fee logic as "sound" without doing the per-report magnitude derivation — resolved in favor of this finding after two independent from-scratch numeric derivations against the live source, see below)

Description
priceD18 is "shares per asset" (per IOracle.sol:16: shares = assets * priceD18 / 1e18), so value per share = 1e18/priceD18, and minPriceD18 (the running minimum price ever recorded) is the highest-value-per-share the vault has ever reached. On a new high (priceD18 < minPriceD18_), the correct fee-share count — sized so the fee recipient receives exactly performanceFeeD6 of the value gained, minted at the current value-per-share — is φ · S · (minPriceD18_ − priceD18) / minPriceD18_. The contract instead computes:

shares = Math.mulDiv(minPriceD18_ - priceD18, $.performanceFeeD6 * totalShares, priceD18 * 1e6);

dividing by priceD18 (current) instead of minPriceD18_ (the high-water baseline used to measure the gain). This overcharges by exactly the factor minPriceD18_ / priceD18, which grows without bound as vault appreciation increases, and requires no attacker action — it fires automatically on every performance-fee-triggering report (ShareModule.handleReport → FeeManager.calculateFee, ShareModule.sol:274-306) under completely normal operation.

Proof (concrete numbers): performanceFeeD6 = 20% (0.2e6), totalShares (excl. feeRecipient) = 1000, minPriceD18_ = 1e18, new report priceD18 = 0.5e18 (vault value doubled since the last high). Correct fee (20% of the 1000-share-unit gain, valued at the new price): 0.2 × 1000 × (1e18−0.5e18)/1e18 = 100 shares. Contract's formula: 0.2 × 1000 × (1e18−0.5e18)/0.5e18 = 200 shares — 2× the intended fee. At priceD18 = 0.1e18 (10× appreciation), intended ≈180 shares, contract mints 1800 (10× overcharge); with φ=50% and 10× appreciation the formula mints 4.5×totalShares, handing the fee recipient ~82% of the vault's value — far beyond 50% of the realized profit. Verified directly against src/managers/FeeManager.sol:69-85 and the caller src/modules/ShareModule.sol:274-306 (which passes priceD18 from the report and totalShares from before the fee mint, consistent with the "mint fee shares at current NAV/share" convention that this formula gets backwards).

Fix

- shares = Math.mulDiv(minPriceD18_ - priceD18, $.performanceFeeD6 * totalShares, priceD18 * 1e6);
+ shares = Math.mulDiv(minPriceD18_ - priceD18, $.performanceFeeD6 * totalShares, minPriceD18_ * 1e6);

[85] 2. SignatureDepositQueue / SignatureRedeemQueue bypass both the merkle whitelist and protocol fees that every other queue enforces

SignatureDepositQueue.deposit / SignatureRedeemQueue.redeem · Confidence: 85 · [phase2: trust-gap agent + asymmetry agent — 2 independent agents converged on the identical bug via different lenses]

Description
isDepositorWhitelisted(...) (which enforces both the per-account hasWhitelist flag AND whitelistMerkleRoot) is called only from DepositQueue.deposit and SyncDepositQueue.deposit. SignatureDepositQueue.deposit mints via shareManager().mint(order.recipient, order.requested) directly, never calling it — and the mint-time guard ShareManager.updateChecks (line 1395) checks only the hasWhitelist flag, never the merkle root. For a vault configured with merkle-only KYC (hasWhitelist flag off, whitelistMerkleRoot set), the consensus signer set can mint shares to any address, whitelisted or not. Separately, DepositQueue/SyncDepositQueue/RedeemQueue all route through FeeManager.calculateDepositFee/calculateRedeemFee; SignatureDepositQueue/SignatureRedeemQueue mint/send order.requested verbatim, bypassing the deposit/redeem fee entirely.

Proof: isDepositorWhitelisted call sites confirmed only at DepositQueue.sol (deposit) and SyncDepositQueue.sol (deposit); absent from SignatureDepositQueue.sol deposit path. Fee calls confirmed present in DepositQueue/SyncDepositQueue/RedeemQueue, absent from SignatureDepositQueue/SignatureRedeemQueue.

Fix

  function deposit(Order calldata order, bytes calldata signature) external {
      ...
+     if (!shareManager().isDepositorWhitelisted(order.recipient, merkleProof)) revert NotWhitelisted(order.recipient);
+     uint256 fee = feeManager().calculateDepositFee(order.requested);
+     shareManager().mint(order.recipient, order.requested - fee);
+     if (fee != 0) shareManager().mint(feeManager().feeRecipient(), fee);
-     shareManager().mint(order.recipient, order.requested);
  }

(mirror on SignatureRedeemQueue.redeem for the redeem fee; if the signer set is intended to be the sole trusted deposit/redeem authority superseding whitelist and fees, document that explicitly instead.)

[78] 3. RiskManager.convertToShares reverts on suspicious/zero oracle reports even for balance-decreasing calls, freezing deposit refunds and already-priced redemption settlement

RiskManager.convertToShares (via modifyPendingAssets / modifyVaultBalance) · Confidence: 78 · [phase2: flow-gap agent + first-principles agent — 2 independent agents converged]

Description
DepositQueue.cancelDepositRequest — the only way to reclaim an unfulfilled deposit — calls riskManager.modifyPendingAssets(asset, -assets) → convertToShares → oracle().getReport(asset), which reverts if report.isSuspicious || report.priceD18 == 0. The passed change is negative (it can never breach a limit; the conversion exists only to keep the share-denominated pendingBalance current), yet the call still requires a healthy oracle. The same coupling blocks RedeemQueue.handleBatches (modifyVaultBalance(asset, -demand)) from paying out redemption batches that were already priced at an earlier, healthy report. An asset's price deviating past suspiciousDeviation (but within maxDeviation) is a normal volatility event, not a privileged action, and persists until an operator submits a fresh in-bounds report.

Proof: RiskManager.sol:112-113 — convertToShares unconditionally reverts on isSuspicious/priceD18==0 regardless of the sign of the value argument. cancelDepositRequest has no alternate exit path once a deposit is queued.

Fix

  function convertToShares(address asset, int256 value) public view returns (int256 shares) {
      IOracle.DetailedReport memory report = IShareModule($.vault).oracle().getReport(asset);
-     if (report.isSuspicious || report.priceD18 == 0) {
+     if (value > 0 && (report.isSuspicious || report.priceD18 == 0)) {
          revert InvalidReport();
      }
      ...
  }

(balance-reducing calls should use the last-known-good price or a stored per-request share delta rather than re-pricing against a possibly-unhealthy report.)

[75] 4. Verifier's compact call-verification paths never constrain msg.value, letting a whitelisted-selector operator attach arbitrary subvault ETH

Verifier.getVerificationResult (ONCHAIN_COMPACT / MERKLE_COMPACT) · Confidence: 75 · [both — phase1: general checklist M-1; phase2: invariant agent, independently]

Description
CallModule.call forwards the full value via Address.functionCallWithValue(where, data, value). ONCHAIN_COMPACT checks only isAllowedCall(who, where, data); MERKLE_COMPACT hashes only (who, where, selector) — neither includes value. MERKLE_EXTENDED and every custom protocol verifier (ERC20Verifier/SymbioticVerifier/EigenLayerVerifier, which explicitly reject value != 0) show the team treats value as security-relevant elsewhere; the compact allowlist omits it. Subvaults hold native ETH as a first-class asset (receive() external payable {}), so a CALLER_ROLE operator can attach any ETH amount to any compact-whitelisted call. Neither phase could construct a concrete where that provably leaks value out of the subvault (most realistic payable targets like WETH.deposit() credit the subvault back) — this is a real hardening gap on a control the team clearly intended to be complete, not a demonstrated theft.

Fix

  if (payload.verificationType == VerificationType.ONCHAIN_COMPACT) {
+     if (value != 0) return false;
      return isAllowedCall(who, where, data);
  }

(or extend CompactCall/hashCall(CompactCall) to include value.)

[70] 5. DepositQueue/SyncDepositQueue record the requested deposit amount, not the amount actually received — breaks (and can permanently DoS) processing for stETH and any fee-on-transfer/rebasing asset

DepositQueue.deposit / _handleReport · Confidence: 70 · [both — phase1: general L-2, erc4626 E-1; phase2: boundary agent (elevated to FINDING with concrete stETH proof) + economic-security, periphery, flow-gap agents, all independently]

Description
deposit() records the caller-requested assets (TransferLibrary.receiveAssets pulls assets with no balance measurement); _handleReport later calls TransferLibrary.sendAssets(asset_, vault_, assets) forwarding the full recorded (not received) amount. LidoDepositHook (src/hooks/LidoDepositHook.sol) shows stETH is an explicit, first-class supported asset for this protocol — not a hypothetical edge case. stETH's transfer/transferFrom rounds down through an internal shares conversion, delivering assets − 1..2 wei per transfer; any admin-onboarded fee-on-transfer token has the same effect at larger magnitude. Once the queue's real balance falls short of the recorded sum, sendAssets reverts inside _handleReport, which is invoked from Oracle.submitReports for all deposits of that asset in the batch at once — the entire price report for that asset is blocked, and with it every pending deposit/redeem gated on that report, until an operator manually donates the shortfall to the queue.

Proof: for N stETH deposits summing to nominal S, the queue holds ≤ S − N wei (stETH getPooledEthByShares(getSharesByPooledEth(x)) ≤ x); sendAssets(steth, vault, S) then requires the queue to move more stETH-shares than it holds → ERC20InsufficientBalance revert. Even a single first deposit is already 1-2 wei short.

Fix

- TransferLibrary.receiveAssets(asset_, caller, assets);
- $.requests.modify(index, int256(uint256(assets)));
+ uint256 balBefore = IERC20(asset_).balanceOf(address(this));
+ TransferLibrary.receiveAssets(asset_, caller, assets);
+ uint256 received = IERC20(asset_).balanceOf(address(this)) - balBefore;
+ $.requests.modify(index, int256(received));

(apply the same balance-delta pattern used in LidoDepositHook's output leg to the input leg of every deposit path, or explicitly document/enforce that only zero-fee, non-rebasing assets may be onboarded.)

[65] 6. SyncDepositQueue mints shares synchronously at the last stored (possibly lagging) oracle price, letting a depositor capture value from existing holders during price drift

SyncDepositQueue.deposit / _setSyncDepositParams · Confidence: 65 · [phase1: erc4626 E-2, re-examined against source — confirmed]

Description
Unlike the async DepositQueue (which prices at the next report), SyncDepositQueue.deposit mints immediately at the last stored report, gated only by report.timestamp + maxAge >= block.timestamp and a penaltyD6 haircut. Configuration bounds are penaltyD6 ≤ 50% and maxAge ≤ 365 days — far too loose to be a meaningful backstop on their own; safety depends entirely on the deployer picking a tight maxAge and a penaltyD6 that exceeds the oracle's per-update deviation allowance. Whenever the true asset value rises between oracle updates, a depositor can mint at the stale (cheaper) price minus the penalty, diluting existing holders, then redeem after the next report catches up.

Fix: bound maxAge to a small hard maximum aligned with the oracle's timeout; require penaltyD6 to exceed suspiciousRelativeDeviationD18.

[60] 7. FeeManager owner can set any fee up to 100% instantly, with no per-fee cap or timelock

FeeManager.setFees / setFeeRecipient · Confidence: 60 · [phase1: access-control AC-1, re-examined against source — confirmed, no per-fee cap exists, only sum ≤ 1e6]

Description: setFees only bounds the sum of the four fees at 1e6 (100%); a single fee (e.g. depositFeeD6 = 1e6) is legal and takes effect on the very next report with no delay. Combined with setFeeRecipient (also instant, onlyOwner), a compromised or malicious owner can redirect the entirety of the next batch of deposits/redemptions to an arbitrary address with no warning window for depositors.

Fix: add a conservative per-fee cap (e.g. ≤ 20% each) and route fee/recipient changes through a timelock.

[58] 8. ShareManager global lockup / pause / blacklist flags let a single role holder freeze all or targeted withdrawals indefinitely

ShareManager.setFlags / setAccountInfo / updateChecks · Confidence: 58 · [phase1: access-control AC-2, re-examined against source — confirmed, globalLockupis an unboundeduint32 with no max-duration cap]

Description: SET_FLAGS_ROLE can set globalLockup to type(uint32).max (~year 2106) and/or hasBurnPause/hasTransferPause, freezing all redemptions/transfers protocol-wide; SET_ACCOUNT_INFO_ROLE can blacklist any individual account, permanently blocking their redemptions. Both take effect instantly with no bound or expiry.

Fix: cap globalLockup to a small maximum duration; require pauses to auto-expire; consider a two-role or timelocked path for blacklisting.

[55] 9. Oracle reports have no consumer-side maximum-staleness (heartbeat) check outside SyncDepositQueue

Oracle._handleReport / RiskManager.convertToShares / SignatureQueue.validateOrder · Confidence: 55 · [phase1: oracles O-1, re-examined against source — confirmed; SecurityParams.timeoutis a minimum-spacing guard only, nomaxAge field exists at the Oracle level]

Description: securityParams.timeout only prevents reports arriving too soon; nothing enforces a maximum age on a stored report when consumed. RiskManager.convertToShares checks only isSuspicious/priceD18==0; SignatureQueue.validateOrder's deviation check never inspects report.timestamp. SyncDepositQueue alone implements the missing check, proving the freshness invariant is simply absent elsewhere. If the off-chain submitter stalls, risk-limit accounting and signature-order price validation both silently operate on an arbitrarily stale price.

Fix: add a maxAge field to SecurityParams, enforced at every consumer (or centrally inside Oracle.getReport).

Low Findings

[48] 10. SlotLibrary-derived storage slots are keyed by a mutable constructor version_; an in-place proxy upgrade to an implementation compiled with a different version_ would orphan all proxy storage

SlotLibrary.getSlot / every module constructor · Confidence: 48 (downgraded from the phase-1 agent's initial Medium rating) · [phase1: proxies P-1, re-examined against source and against the team's own deployment scripts]

Description: Every namespaced storage base slot is keccak256(..., contractName, name_, version_) computed from immutable constructor args. Entities deploy behind TransparentUpgradeableProxy, so an in-place upgrade to an implementation compiled with a different version_ would resolve every module's storage struct to a different slot, reading back as all-zero (data loss / brick). Re-examination: the phase-1 finding's proof-of-concept assumed version_ tracks the Factory's implementations-list index (Factory.create(uint256 version, ...)), but that version parameter is unrelated to the constructor's version_ — scripts/common/ProtocolDeploymentLibrary.sol and every network's Constants.sol show the team's tooling passes a single hardcoded DEPLOYMENT_VERSION constant (currently 1) to every contract in a given deployment, and AcceptanceLibrary.sol's compareBytecode helper re-deploys with the same constant specifically to verify bytecode/slot consistency before accepting an upgrade. So this does not fire under the team's normal upgrade workflow — it is a footgun in the design (nothing on-chain enforces the invariant) rather than a live path, hence downgraded to Low.

Fix: decouple the storage namespace from the mutable version_ (derive from a stable contractName only), or add an on-chain assertion that an upgrade target's embedded slot matches the proxy's current slot before allowing the upgrade to take effect.

[45] 11. OracleSubmitter.acceptReports can underflow / mis-index acceptedAt

OracleSubmitter.acceptReports · Confidence: 45 · [both — phase1: general L-1; phase2: periphery, asymmetry, invariant agents — 4 agents total]

Description: acceptedAt[asset][reports(asset) - 1] = timestamp indexes off _reports[asset].length, which is only pushed to by submitReports. Accepting a report for an asset that was only ever submitted directly on Oracle (not through this submitter) underflows and reverts; even when non-empty, the index doesn't necessarily correspond to the report being accepted. All agents agree impact is bounded — the write either reverts cleanly or lands in an unused/mislabeled slot, no fund or state corruption identified.

Fix: track accepted reports independently rather than indexing off the submit-only array length.

[40] 12. DepositQueue aggregate share allocation vs. per-user claim rounding permanently strands dust in allocatedShares, and sub-unit deposits can lose their assets entirely

DepositQueue._handleReport / _claim · Confidence: 40 · [both — phase1: precision-math L-2/L-3, erc4626 E-3; phase2: math-precision, periphery, invariant, numerical-gap agents — 6+ agents, the single most-corroborated item in this audit]

Description: _handleReport allocates floor(Σassets · price) shares for a batch; each depositor later claims floor(their assets · price) individually. Since Σfloor ≤ floor(Σ), unmintable dust permanently accumulates in allocatedShares (counted in totalShares()), marginally inflating the fee/valuation base over the vault's life. Separately, a deposit small enough that its individual claim floors to zero shares is deleted with no mint and no refund, even though its assets were already swept to the vault. All agents across both phases agree: protocol-favorable direction, sub-wei-per-batch magnitude, not attacker-forceable against a third party.

Fix: track/mint the residual on the final claim of a batch, or revert/refund an individual claim that would round to zero shares.
