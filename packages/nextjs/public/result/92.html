Smart Contract Security Audit — PawthereumMamoYieldModule

Contract: 0x12D661f977249778d78985f6ca860f42d7cAC9De on Base
Contract Name: PawthereumMamoYieldModule
Compiler: Solidity 0.8.28, EVM: Cancun
Audit Date: 2026-05-06
Methodologies: ethskills (6 domain agents) + pashov (8 specialized agents, 4-gate evaluation)

Contract Overview

PawthereumMamoYieldModule is a Gnosis Safe module that captures yield from a MetaMorpho/Moonwell USDC strategy and distributes it to configured recipients. The SAFE (multisig at 0x10f76316eB9f132a72E62481018F00cfEe326E15) manages recipients and parameters; executeYieldCapture() is permissionless and callable by anyone.

The strategy holds USDC across three sources: a MetaMorpho ERC4626 vault (0xc1256Ae5FF1cf2719D4937adb3bbCCab2E00A2Ca), a Moonwell mToken (0xEdc817A28E8B93B03976FBd4a3dDBc9f7D176c22), and idle USDC in the MAMO_STRATEGY (0xA5CF54d5EE226F695BC6Ad2931F9520d0f2C1B53). Yield above protectedPrincipal is distributed to recipients according to BPS allocations; unallocated yield compounds into protectedPrincipal.

State at audit: 2 recipients (SAFE @ 4500 BPS, 0xceb30... @ 4500 BPS), protectedPrincipal = 1,500 USDC, executionInterval = 60s, minimumClaimAmount = 1.

Findings

[HIGH-1] USDC Blacklisted Recipient Permanently Freezes All Yield Distribution

Severity: High
Confirmed by: ethskills (ERC20-1/DOS-2) + pashov (Finding 1, confidence 90, [agents: 5])
Location: _payRecipients(), _safeExec()

Description: _payRecipients() iterates over all recipients calling _safeExec(USDC, transfer(to, amt)). Circle USDC v2.2 on Base reverts (does not return false) when transferring to a blacklisted address. Gnosis Safe's execTransactionFromModuleReturnData captures this revert and returns (false, revertData). The _safeExec wrapper then reverts with SafeCallFailed, rolling back the entire executeYieldCapture() transaction including the already-completed strategy withdrawal. Because lastExecutionTimestamp only updates on success, the module enters a permanent DoS state where no yield reaches any recipient.

Proof of Concept:

  1. OFAC or Circle blacklists 0xceb30... (current second recipient).
  2. Any caller calls executeYieldCapture().
  3. Strategy withdrawal succeeds; SAFE receives USDC.
  4. transfer(SAFE, amt0) succeeds; transfer(0xceb30..., amt1) reverts inside USDC.
  5. Safe returns (false, revertData) → SafeCallFailed → full tx revert.
  6. Every subsequent call hits the same path. All yield is permanently frozen.
  7. Recovery requires the SAFE to call setRecipients() to remove the blacklisted address.

Recommendation: Adopt a pull-payment model — compute owed amounts during executeYieldCapture() into a claimable[addr] mapping, then let each recipient call claim() independently. Alternatively, wrap each individual transfer in a try/catch and accumulate undelivered amounts into failedPayments[addr].

[MED-1] Permissionless executeYieldCapture() Enables Front-Running and Forced Distributions

Severity: Medium
Confirmed by: ethskills (GEN-1/AC-1/DOS-1) + pashov (Finding 2, confidence 85, [agents: 4])
Location: executeYieldCapture()

Description: executeYieldCapture() lacks any caller restriction. Any EOA can force yield distribution every 60 seconds, enabling: (a) front-running of setRecipients SAFE transactions so stale recipients receive the current epoch's yield, and (b) MEV extraction by sandwiching the MetaMorpho vault withdrawal.

Proof of Concept:

  1. SAFE broadcasts setRecipients([newRecipients]) to mempool.
  2. Attacker sees it and submits executeYieldCapture() with higher gas priority.
  3. Attacker's tx lands first, distributing yield to old recipients.
  4. SAFE's tx lands second, updating recipients for future epochs only.
  5. Cost to attacker: ~$0.001 Base gas. Loss: one epoch of yield to wrong recipients.

Recommendation: Add a keeper address (set by SAFE, zero address = permissionless) and gate executeYieldCapture() on msg.sender == keeper || keeper == address(0). If truly permissionless execution is required by design, increase executionInterval to at least 900 seconds and document the trust model.

[MED-2] Dual getStrategyValue() Calls Create Inconsistent Oracle State Within One Transaction

Severity: Medium
Confirmed by: ethskills (GEN-4/CHAIN-2) + pashov (Finding 3, confidence 80, [agents: 4])
Location: executeYieldCapture() lines 97 and 112

Description: getStrategyValue() is called twice in executeYieldCapture(). The function calls IMToken.balanceOfUnderlying() on Moonwell (a Compound fork), which is not a view function — it accrues interest by writing to Moonwell storage. The two calls may therefore return different values, causing: (a) the post-execution PrincipalViolation guard to compare against a stale protectedPrincipal value, potentially masking a real violation, or (b) a spurious PrincipalViolation revert on a valid execution if Morpho rounds down on the second read.

Recommendation: Cache getStrategyValue() once at the start. For the post-execution check, derive the expected strategy value deterministically: expectedStrategyValue = strategyValueBefore - totalDistributed. Use this cached computation rather than re-querying live protocol state.

[MED-3] Admin Parameters Lack Timelock — SAFE Compromise Enables Instant Full Drain

Severity: Medium
Confirmed by: ethskills (AC-2/AC-4); pashov demoted to Lead (requires privileged SAFE compromise)
Location: setRecipients(), setProtectedPrincipal()

Description: setRecipients() and setProtectedPrincipal() are callable by SAFE with immediate effect and no time delay. A compromised SAFE quorum can atomically: call setProtectedPrincipal(0) (making entire strategy value distributable as "yield"), call setRecipients([{attacker, 9000}]) (redirecting 90% to attacker), then trigger executeYieldCapture() — extracting ~90% of total strategy value (~1,350 USDC at current principal) within a single block.

Note: pashov strict gate evaluation demotes this to a Lead because it requires SAFE compromise (privileged action). However, the complete absence of any on-chain defense-in-depth (no timelock, no rate-limit, no floor) means there is no opportunity for honest parties to react if a SAFE signer key is stolen.

Recommendation: Implement a 24–48 hour timelock for setRecipients and setProtectedPrincipal changes. At minimum, enforce that protectedPrincipal cannot be reduced by more than a configurable percentage (e.g., 20%) per governance action.

[MED-4] Integer Division Truncation Silently Inflates protectedPrincipal Beyond Strategy Value

Severity: Medium
Confirmed by: ethskills (PRECISION-1/GEN-2) + pashov (Finding 4, confidence 75, [agents: 2])
Location: _computeAmounts(), executeYieldCapture() — protectedPrincipal += compoundedAmount

Description: Each recipient's payout is floored by (totalYield * bps) / BPS. The sum of all truncation remainders accumulates in compoundedAmount and is added to protectedPrincipal, but the truncated dust was never deposited into the strategy. Over many executions (up to 1,440/day at 60-second intervals), protectedPrincipal drifts above actual strategy value, eventually causing all future calls to revert with NoYield. Recovery requires the SAFE to manually call setProtectedPrincipal() to correct the drift.

Recommendation: Assign the last recipient's amount as totalYield - sum(amounts[0..n-2]) to eliminate truncation remainder. Alternatively, set minimumClaimAmount to at least 1e6 (1 USDC) so dust-level executions that amplify the drift are blocked.

[MED-5] PrincipalViolation Safety Guard Is Mathematically Trivial After Normal Execution

Severity: Medium
Found by: pashov (Finding 5, confidence 75, [agents: 3]); not in ethskills
Location: executeYieldCapture() line 112 — if (getStrategyValue() + getSafeUSDC() < protectedPrincipal)

Description: After a normal execution, protectedPrincipal is set to strategyValueBefore - totalDistributed. The second getStrategyValue() call returns approximately the same value (strategy had exactly totalDistributed withdrawn). Adding getSafeUSDC() (always ≥ 0, representing idle USDC in the SAFE unrelated to strategy principal) makes the left side structurally ≥ the right side. The guard can only trigger if Morpho and Moonwell simultaneously suffer losses mid-transaction — a near-impossible scenario. This means the invariant check provides false confidence: a real strategy undercollateralization would not be caught.

Recommendation: Replace with a deterministic check: if (strategyValueBefore - totalDistributed < protectedPrincipal) revert PrincipalViolation(). Do not include getSafeUSDC() in the comparison, as idle SAFE USDC is not part of the strategy principal accounting.

[LOW-1] getStrategyValue() Is Non-View — Accrues Moonwell Interest as Side Effect

Severity: Low
Confirmed by: ethskills (GEN-3) + pashov (Lead)
Location: getStrategyValue() — calls IMToken.balanceOfUnderlying()

Description: IMToken.balanceOfUnderlying() on Moonwell (a Compound fork) calls accrueInterest() internally, which writes to Moonwell's borrowIndex and supplyIndex in storage. This makes getStrategyValue() and previewYieldCapture() state-mutating despite their usage as "view" functions. Off-chain callers using eth_call will experience unexpected storage writes and may get results inconsistent with the live deployment state.

Recommendation: Either use mToken.exchangeRateStored() (which IS view) to compute the underlying balance from shares, or add NatSpec documentation marking both functions as state-mutating.

[LOW-2] 60-Second executionInterval Below Reliable OP Stack Timestamp Threshold

Severity: Low
Confirmed by: ethskills (CHAIN-1); pashov (Lead — sequencer is privileged role)
Location: executionInterval constructor parameter / current on-chain value

Description: The Base (OP Stack) sequencer controls block.timestamp with practical latitude before L1 finality enforces ordering. A 60-second interval is below the ~900-second threshold for reliable timestamp-based access control on OP Stack chains. A malicious or MEV-incentivized sequencer could advance timestamps to allow early re-execution.

Recommendation: Set executionInterval to at least 900 seconds via setExecutionInterval().

[LOW-3] _safeExec Silent Success on Zero-Length Return Data

Severity: Low
Confirmed by: ethskills (GEN-5); pashov (Lead — requires USDC contract change)
Location: _safeExec() — if (ret.length != 0 && !abi.decode(ret, (bool)))

Description: When ret.length == 0, the return-data check is skipped and the call is assumed successful. This is correct for IMamoStrategy.withdraw() (void return) but creates a latent assumption that USDC always returns a 32-byte bool. If Circle upgrades the USDC proxy to a no-return variant (as seen in some ERC20 implementations) and the transfer fails, _safeExec would silently pass.

Recommendation: Use separate wrappers: one for ERC20 calls asserting ret.length == 32, one for void calls asserting ret.length == 0.

[LOW-4] minimumClaimAmount = 1 Allows Economically Wasteful Dust Executions

Severity: Low / Advisory
Confirmed by: ethskills (PRECISION-2); pashov rejected (self-harm only per Gate 4)
Location: executeYieldCapture() — minimum threshold check

Description: minimumClaimAmount = 1 (1 μUSDC = $0.000001) allows the full execution pipeline — two getStrategyValue() calls, a Safe-mediated strategy withdrawal, and N Safe-mediated USDC transfers — for effectively zero value distributed. The gas cost ($0.01–$0.10 on Base) vastly exceeds the distributed amount. Permissionless callers can loop this indefinitely.

Recommendation: Set minimumClaimAmount to at least 1_000_000 (1 USDC in 6-decimal representation) and add a floor validation in setMinimumClaimAmount().

[INFO-1] No On-Chain Safe Module Self-Removal Path

Severity: Info
Confirmed by: ethskills (AC-3)
Location: Contract-wide

Description: The module can only be disabled via a separate Gnosis Safe governance transaction (ISafe.disableModule). If a critical vulnerability is discovered and the SAFE is unavailable, the module remains permanently enabled with full execTransactionFromModuleReturnData rights.

Recommendation: Consider adding emergencyDisableSelf() callable only by SAFE that invokes ISafe(SAFE).disableModule(prevModule, address(this)).

[INFO-2] Compiler Bugs Flagged by BaseScan — Confirmed Not Applicable

Severity: Info
Confirmed by: ethskills (CHAIN-3) + pashov (first-principles agent)

Description: BaseScan flags two Solidity 0.8.28 compiler bugs: TransientStorageClearingHelperCollision (high severity in compiler) and LostStorageArrayWriteOnSlotOverflow (low severity). Neither applies: the contract does not use transient storage (TSTORE/TLOAD), and the storage array (_recipients) is bounded to 16 elements — far below any overflow threshold. No action required.

Key Risk: Pull-Payment Architecture Required

The single highest-priority remediation is replacing the push-payment model in _payRecipients() with a pull-payment model. This one change eliminates HIGH-1 (blacklist DoS) entirely and also mitigates MED-1 (front-running has less impact if recipients pull individually). All other findings are significant but individually less urgent.

This report was produced by dual-methodology AI audit: ethskills (6 domain specialists) and pashov (8 attack-surface agents with 4-gate gate evaluation). AI audits cannot guarantee the absence of vulnerabilities. Manual review, formal verification, and bug bounty programs are recommended for production contracts.
