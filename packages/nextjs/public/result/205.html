Executive Summary

VaultIDV4 is a soulbound ERC721 credential NFT system with associated VaultIDRegistry for managing issuer profiles and subscriptions. Three High severity vulnerabilities were confirmed by both audit methodologies. All three undermine the core trust model of the credential system: (1) token holders can bypass issuer revocations, (2) admin revocations can be nullified using the recovery mechanism, and (3) admin-deactivated issuers can self-reactivate. These findings share a common root cause pattern — state flags are set but not protected against overwrites or bypass paths.

Findings

HIGH

[H-1] Token Holder Bypasses Issuer Revocation via Double-Revoke/Unrevoke

Severity: High
Confirmed by: ethskills (evm-audit-general), pashov (access-control-agent, invariant-agent)
Location: revoke() and unrevoke() in VaultIDV4.sol

Description:
revoke() unconditionally sets _revokedByIssuer[tokenId] = isIssuer. When the token owner calls revoke() on a credential that was already issuer-revoked, isIssuer is false, silently overwriting the true flag left by the issuer. The token owner then calls unrevoke(), which branches on _revokedByIssuer[tokenId] == false (the else path) and permits the token owner to clear the revocation entirely. An issuer's credential revocation is bypassed in exactly two on-chain transactions.

Proof of Concept:

  1. Issuer calls revoke(tokenId) → vaults[tokenId].revoked = true, _revokedByIssuer[tokenId] = true.
  2. Token owner calls revoke(tokenId):
    • isOwner = true, isIssuer = false.
    • Authorization check passes.
    • _revokedByIssuer[tokenId] = false ← issuer flag overwritten.
  3. Token owner calls unrevoke(tokenId):
    • _revokedByIssuer[tokenId] == false → else branch.
    • msg.sender == tokOwner → allowed.
    • vaults[tokenId].revoked = false.
  4. isValid(tokenId) returns true. Credential is valid again.

Recommendation:
Never overwrite _revokedByIssuer to false from a non-issuer caller. Only set it true when the issuer revokes:

  v.revoked = true;
- _revokedByIssuer[tokenId] = isIssuer;
+ if (isIssuer) _revokedByIssuer[tokenId] = true;

[H-2] Admin Revocation Bypassed via Recovery Wallet

Severity: High
Confirmed by: ethskills (evm-audit-general), pashov (access-control-agent, first-principles-agent)
Location: recoverVault() and setRecoveryWallet() in VaultIDV4.sol

Description:
recoverVault() constructs the replacement vault with revoked: issuerRevoked — that is, the _revokedByIssuer[tokenId] flag — rather than v.revoked. When the contract owner (protocol admin) revokes a token, _revokedByIssuer remains false (admin is not an issuer). The recovery produces a fresh credential with revoked = false, silently voiding the admin revocation.

Compounding this: setRecoveryWallet() has no check for whether the token is currently revoked, so the token holder can install a recovery wallet even after admin revocation, then immediately trigger recovery.

Proof of Concept:

  1. Admin calls revoke(tokenId) → vaults[tokenId].revoked = true, _revokedByIssuer[tokenId] = false.
  2. Token holder calls setRecoveryWallet(tokenId, attackerAddress) — no revocation check, succeeds.
  3. attackerAddress calls recoverVault(tokenId):
    • issuerRevoked = _revokedByIssuer[tokenId] = false.
    • New vault: revoked: false.
  4. isValid(newTokenId) returns true.

Recommendation:
Option A — carry the full revocation state through recovery:

  vaults[newTokenId] = Vault({
      recoveryWallet: address(0),
      expiry: v.expiry,
-     revoked: issuerRevoked,
+     revoked: v.revoked,
      ...
  });
+ if (v.revoked) _revokedByIssuer[newTokenId] = issuerRevoked;

Option B — block recovery entirely when the token is revoked:

+ require(!v.revoked, "Cannot recover a revoked credential");

[H-3] Admin-Deactivated Issuer Can Self-Reactivate

Severity: High
Confirmed by: ethskills (evm-audit-access-control), pashov (access-control-agent, first-principles-agent)
Location: registerOrUpdateIssuerProfile() in VaultIDRegistry.sol

Description:
registerOrUpdateIssuerProfile() unconditionally sets profile.active = true on every call, including updates to existing profiles. When the admin calls deactivateIssuer(addr) to revoke an issuer's minting rights (e.g., for regulatory non-compliance), the issuer bypasses the deactivation with a single call to registerOrUpdateIssuerProfile(anyValidName, ...). Critically, the issuer's verified flag is also preserved through the deactivation–reactivation cycle since registerOrUpdateIssuerProfile does not touch profile.verified. A previously-verified deactivated issuer re-emerges as both active and verified.

Proof of Concept:

  1. Admin calls deactivateIssuer(issuer) → issuerProfiles[issuer].active = false.
  2. Issuer calls registerOrUpdateIssuerProfile("LegitName", ...) → profile.active = true.
  3. canIssuerMint(issuer) returns true (given active subscription).
  4. isIssuerVerified(issuer) returns true (verified flag preserved).

Recommendation:
Only set profile.active = true for newly registered profiles, not updates:

  IssuerProfile storage profile = issuerProfiles[msg.sender];
  bool isNew = bytes(profile.name).length == 0;
  profile.name = name;
  profile.logoURI = logoURI;
  profile.bannerURI = bannerURI;
  profile.description = description;
  profile.website = website;
  profile.social = social;
- profile.active = true;
+ if (isNew) profile.active = true;
  if (isNew) emit IssuerProfileRegistered(msg.sender, name);
  else emit IssuerProfileUpdated(msg.sender);

MEDIUM

[M-1] Instant Registry Swap Without Timelock

Severity: Medium
Confirmed by: ethskills (evm-audit-access-control)
Location: setRegistry() in VaultIDV4.sol

Description:
The contract owner can replace registry with an arbitrary address in a single transaction, with no timelock or two-step protection. The registry is the trust anchor for all minting validation (canIssuerMint, isIssuerActive, consumeBasicMint), revocation authorization (isIssuerActive in revoke/unrevoke/extendExpiry), and subscription-based minting. A compromised or malicious owner key could atomically substitute a registry that returns true for all checks, enabling unconstrained minting of credentials attributed to any issuer.

Recommendation:
Implement a two-step registry update with a minimum delay (e.g., 48 hours) so users and issuers have time to react. Emit a proposal event immediately and enforce the delay before applying.

[M-2] Lapsed-Subscription Issuers Retain Administrative Rights

Severity: Medium
Confirmed by: ethskills (evm-audit-access-control), pashov (access-control-agent)
Location: revoke(), unrevoke(), extendExpiry() in VaultIDV4.sol

Description:
The isIssuer authorization check in revoke(), unrevoke(), and extendExpiry() calls registry.isIssuerActive(), which only verifies profile.active && name != "". It does not verify whether the issuer has an active ISSUER-tier subscription. An issuer whose subscription has expired — and who can no longer mint new credentials via issuerMint() — retains indefinite ability to revoke, unrevoke, and extend expiry of every credential they previously issued. This creates an asymmetry where administrative power over existing credentials outlives the paid relationship.

Recommendation:
Decide the intended lifetime of issuer administrative rights. If they should be co-extensive with subscription validity, replace isIssuerActive() with canIssuerMint() in the revoke, unrevoke, and extendExpiry authorization checks. If perpetual administrative rights are intended, document this explicitly.

LOW

[L-1] extendExpiry Unconditionally Reactivates Revoked Membership

Severity: Low
Confirmed by: ethskills (evm-audit-general), pashov (invariant-agent)
Location: extendExpiry() in VaultIDV4.sol

Description:
When extendExpiry() is called on a MEMBERSHIP credential whose vaults[tokenId].revoked == true, the function sets memberships[tokenId].active = true without checking the revoked state. This creates an invariant violation: isValid() returns false for the credential (correctly checking v.revoked), but any external integrator reading memberships[tokenId].active directly sees true. Off-chain systems or future contracts relying on the public memberships mapping for membership validity checks would be misled.

Recommendation:
Conditionally update membership active status:

  if (v.credType == CredentialType.MEMBERSHIP) {
      memberships[tokenId].expiry = newExpiry;
-     memberships[tokenId].active = true;
+     if (!v.revoked) memberships[tokenId].active = true;
  }

[L-2] USDC Blocklist on feeRecipient Permanently Freezes USDC Minting

Severity: Low
Confirmed by: ethskills (evm-audit-erc20)
Location: mintWithUSDC() in VaultIDV4.sol

Description:
USDC implements a blocklist. If feeRecipient is ever added to USDC's blocklist, all calls to mintWithUSDC() will revert because safeTransferFrom(msg.sender, feeRecipient, usdcMintPrice) fails when the recipient is blocklisted. The owner can update feeRecipient, but response latency creates a minting downtime window. The same risk applies to CLAWD if it adds blocklist functionality.

Recommendation:
Monitor feeRecipient for USDC/CLAWD blocklist status and maintain an incident response runbook. Consider using a dedicated fee collection contract that cannot be user-targeted.

[L-3] unchecked Mint Counter Increment: Theoretical Wrap with Extreme Quota

Severity: Low
Confirmed by: ethskills (evm-audit-precision-math)
Location: consumeBasicMint() in VaultIDRegistry.sol

Description:
unchecked { sub.mintsUsedInPeriod += 1; } is safe for any basicMintQuota less than type(uint32).max. However, if the owner ever sets basicMintQuota = type(uint32).max, a user at mintsUsedInPeriod = type(uint32).max - 1 passes the guard (>= max is false for max-1), increments to 0 via wraparound, and the quota barrier is permanently bypassed for subsequent mints in the same period.

Recommendation:
Add a cap in setBasicMintQuota: require(_basicMintQuota < type(uint32).max).

INFO

[I-1] PUSH0 Opcode Is Supported on Base — No Action Required

Both contracts use pragma solidity ^0.8.24 which emits the PUSH0 opcode. Base adopted PUSH0 support in the Canyon upgrade (January 2024). Verified safe for the current target chain; any future deployment to chains without PUSH0 support should recompile with --evm-version paris.

[I-2] vaultContract Unset at Deployment Creates Silent Subscription Failure

VaultIDRegistry.vaultContract is initialized to address(0). Until setVaultContract() is called, all mintWithSubscription() calls revert with NotVaultContract. There is no on-chain check or constructor enforcement. A deployment checklist gap could leave subscription minting silently non-functional.

Recommendation: Set vaultContract in the constructor or emit a deployment checklist requirement.

[I-3] setBackupWallet Is a Redundant Alias

setBackupWallet(uint256, address) is a one-line delegate to setRecoveryWallet(). It adds ABI surface with no new functionality. Remove it or retain for backward compatibility with explicit documentation.

Leads

  • Instant Registry Swap → Unlimited Credential Minting: A compromised owner swaps registry to a contract returning true for all queries. Unauthorized users can issuerMint credentials attributed to any issuer. Severity depends entirely on owner key custody.

  • ERC777 CLAWD Reentrancy Surface: In purchaseSubscription, the token transfer to feeRecipient occurs before sub.paidThrough and sub.active are written. If CLAWD implements ERC777 hooks and feeRecipient is an ERC777-aware contract, the tokensReceived callback fires before subscription state is committed. The nonReentrant modifier protects the outer call but does not cover cross-contract calls into other functions. Full path requires knowledge of CLAWD's implementation.

  • Tier-Switch Quota Reset Enabling Extra Mints Per Window: Switching BASIC→ISSUER→BASIC within a subscription window resets mintsUsedInPeriod = 0 each time due to the sub.tier != tier check in purchaseSubscription. At current prices (1M CLAWD for ISSUER vs 100K for BASIC) this is economically irrational, but the vulnerability exists structurally if pricing changes.
