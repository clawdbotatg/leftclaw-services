Findings

[95] 1. Public, unauthenticated decay-apply function never advances its own timestamp baseline, letting anyone crash any address's reputation to the floor in a handful of free transactions [both]

ReputationDecay.<selector 0xedfcc437>(address) · Confidence: 95

Description

The function dispatched at selector 0xedfcc437(address) applies the time-based decay curve to a user's profiles entry. Its dispatcher entry (raw disassembly offsets 0x231–0x253) checks only CALLVALUE == 0 and calldata size — no CALLER comparison exists anywhere in the path, so it is callable by any address for any target, with no cooldown.

The shared decay subroutine it jumps into (disassembly offset 0x1801, ~170 opcodes ending at 0x190c) does the following, confirmed by hand-tracing the SLOAD/SSTORE targets and the three checked-arithmetic helper subroutines it calls (0x1726=checked-sub, 0x1733=checked-mul, 0x1746=checked-add):

age          = checked_sub(block.timestamp, profiles[addr].field_512)   // field_512 = "last activity" timestamp
if age <= gracePeriod (slot 2):
    profiles[addr].field_768 = block.timestamp                          // touch only, no score change
else:
    daysPastGrace = (age - gracePeriod) / 86400                          // literal constant 0x015180 = 86400
    decayAmt      = checked_mul(daysPastGrace, rate (slot 1))
    if score (field_256) <= decayAmt + minScore (slot 3):
        score = minScore
    else:
        score = checked_sub(score, decayAmt)
    profiles[addr].field_768 = block.timestamp

Every SSTORE in this subroutine targets field_256 (score) or field_768 (a write-only, never-read "last decay touch" stamp). field_512 — the timestamp the whole decay calculation is measured against — is never written here. It is only ever advanced elsewhere, inside the event-recording function's success path (selector 0xe1eec5de, at pseudocode lines 914/933/977/1051/1062/1076/1116/1132/1153), i.e. only when a reporter/owner records a real event for that address.

Consequence: a bare call to 0xedfcc437(victim) recomputes age (and therefore decayAmt) from the same, unmoved baseline every single time. Calling it twice in a row subtracts the same elapsed-time decay amount from an already-decayed score a second time; calling it N times subtracts it N times. The underflow guard on score - decayAmt never triggers, because the preceding floor branch (score <= decayAmt + minScore → score = minScore) always intercepts first — so the attack never reverts, it simply drives the score to the configured floor in a bounded, cheap number of transactions instead of the number of real days the configured rate is supposed to require.

Concrete exploit:

  1. Owner sets conservative decay params, e.g. rate=1/day, gracePeriod=90 days, minScore=0 (setDecayParams, selector 0xa03b08a8).
  2. Victim's profile goes untouched for gracePeriod + 1 day (the minimum for daysPastGrace to be non-zero).
  3. Attacker calls 0xedfcc437(victim) — legitimately applies 1 day of decay (score -= rate).
  4. Attacker calls 0xedfcc437(victim) again immediately (same or next block) — age/decayAmt are identical (baseline unmoved), so the same amount is subtracted again from the now-lower score.
  5. Repeating step 4 a bounded number of times (proportional to score / decayAmt, e.g. ~100 calls at the settings above, or as few as 4 if the victim was already further past grace) drives the score to minScore, in minutes, at attacker's discretion, for free, against any target — completely bypassing the intended gradual per-day decay rate.

This directly defeats the contract's stated purpose (a controlled, rate-limited decay curve) and, since reputation scores from this contract plausibly gate privileges in the broader Vaultfire ecosystem (SLA enforcement, delegation, badge issuance), the blast radius extends beyond this contract alone. Recovery is possible (a reporter/owner event via e1eec5de does reset field_512), so this is not a permanent brick, but it is a real, zero-privilege, zero-cost manipulation primitive against every profile in the system.

Fix

  // inside the decay-apply subroutine, once decayAmt has actually been computed and applied
  if score <= decayAmt + minScore:
      score = minScore
  else:
      score = score - decayAmt
  profiles[addr].field_768 = block.timestamp
+ profiles[addr].field_512 = block.timestamp   // advance the baseline so decay cannot be re-applied for time already accounted for

Equivalently in Solidity terms: whichever function this decompiles from should set lastUpdateTimestamp = block.timestamp in the same branch where decay is actually applied (the else / decay-computed branch), not only the "still in grace period" branch.

[70] 2. Authorized reporter/owner can move any address's score far beyond the intended per-call weight cap by issuing repeated events, since the per-context "dedup" storage does not effectively rate-limit the primary score update [both — mechanism characterized two ways, see Option A/B]

ReputationDecay.<selector 0xe1eec5de>(address user, bytes context, bool positive, uint256 weight) · Confidence: 70

Description

The event-recording function is correctly gated (caller == owner OR stor10[caller] == true, i.e. an owner-set reporter allowlist via setReporter, selector 0xe1bb5133), and per-call weight is correctly bounded to [1,10] for the positive path. However, once inside the function, a reporter (or the owner) can apply an unbounded number of events to the same address with no cooldown/nonce beyond gas cost — there is no aggregate rate limit across separate calls.

Both review passes confirm the practical outcome (a privileged caller can pump/dump any registered agent's score to the 100/minScore caps in a handful of cheap calls by repeating the call with distinct — or, per one trace, even identical — context bytes), but disagree on the precise mechanism, so both are presented:

  • Option A (depth pass): the per-context dedup mapping (storage slot 6, keyed by address ++ keccak256(context)) does prevent replaying the exact same context bytes twice, but since context is fully caller-supplied with no binding to any independently-verifiable identifier, a reporter trivially defeats it by incrementing a nonce string ("evt-1", "evt-2", …) on every call — each treated as a brand-new, un-deduped event.
  • Option B (breadth pass): the score-affecting SSTOREs occur unconditionally, before the per-context dedup check is even evaluated — the dedup bookkeeping in slot 6 only gates whether the context gets pushed into the enumeration array (slot 7) and its own per-context counters, not whether the primary profile score updates. Under this reading, even literally identical context bytes can be replayed to re-apply the same score delta.

Either way, the net effect a client should plan around is the same: a reporter's real-world influence on any address's score is not bounded by the per-event weight cap — only by gas cost and the 100/minScore saturation limits.

Impact: Medium rather than Critical/High because it requires a privileged role (owner or an owner-appointed reporter) — it is not exploitable by an arbitrary unauthenticated address. But reporters are plausibly automated/hot-key bots by design, making this a meaningful risk if any single reporter key is compromised or misbehaves: it can arbitrarily saturate or crater any agent's score, not just nudge it within the documented per-report bounds.

Fix

  // Recommendation: rate-limit real score impact per (address, reporter) pair independently of the
  // caller-supplied context bytes, e.g.:
+ require(block.timestamp >= profiles[user].lastReportTimestamp + MIN_REPORT_INTERVAL, "reporting too frequently");
+ profiles[user].lastReportTimestamp = block.timestamp;
  // and/or bind `context` to something the contract can itself verify (e.g. a hash of calldata from
  // the external reputation-source/agent-registry contracts) rather than trusting caller-supplied bytes.

Verified clean (explicitly checked, no finding)

  • Access control on parameter updates (client focus item 3) — [both]. transferOwnership (owner-only, rejects zero address), setReporter (owner-only, rejects zero address), setDecayParams (owner-only; rate∈[1,10], gracePeriod≥86400s, minScore≤20, recoveryBonus≤20 all enforced) were each traced to their dispatcher entries and confirmed airtight. No non-owner path reaches any of the three, and ownership can never be transferred to the zero address. Note: ownership transfer is single-step (no pendingOwner/acceptOwnership handshake) — standard-practice gap, Low/Informational, not a live vulnerability.
  • Decay-curve underflow (client focus item 2, as literally asked) — [both]. The subtraction score - decayAmt is preceded by a floor comparison (score <= decayAmt + minScore → score = minScore) that always intercepts before the subtraction could underflow, and a checked-sub helper subroutine additionally guards it. No underflow is reachable. (The real decay-arithmetic defect found instead is Finding 1 — a compounding/non-idempotency bug, not an underflow.)
  • block.timestamp manipulation resistance (client focus item 1) — [both]. All decay math operates at whole-day granularity (/86400); the few seconds of sequencer/validator timestamp latitude on Base is immaterial at this granularity. Not a practical risk.
  • Reentrancy — [both]. Every external call (to the immutable agent-registry and reputation-source addresses embedded in the bytecode) is a STATICCALL, which forbids state changes anywhere in the callee's sub-call tree. No reentrant state-mutation path exists.
  • Unchecked external call return values — [both]. Every STATICCALL's success flag is checked; failures revert with the raw returned data. No silent-failure paths.
  • Hidden/backdoor functions — [phase1]. All 24 real dispatcher selectors (verified via PUSH4 → EQ pattern scan, distinguishing genuine dispatch entries from PUSH4 bytes that are just embedded revert-string data) map to accounted-for, named or decompiled logic. No undocumented functions.
  • Dead storage — [phase1]. The struct array at storage slot 8 and the uint256 array at slot 9 have public getters but no writer exists anywhere in the 24 real selectors — unreachable/dead storage, likely template leftovers from the contract's generator. Informational, no risk.
  • Unbounded storage growth — [phase1]. The per-user context-hash list (slot 7) is capped at a very large (~10,000,000-entry) ceiling; enumerating a heavy user's full history is a caller-side gas concern only, not an on-chain DoS to the contract. Informational.
