Executive Summary

0 Critical, 0 High, 0 Medium, 3 Low, 2 Info — all scoped to PMFIPositionFactoryV22.

PMFIPositionFactoryV22 is the registry, collateral-allowlist, and pause-control contract for the PMFI lending system. It creates and initializes each borrower's PMFIPositionVaultV22, mints the position atomically with collateral pull, registers the primary sale with the marketplace, and collects a fixed ETH creation fee. Both prior audit passes independently verified the full permission map of this contract (see table below) and found it complete and consistent — no missing modifier, no unauthorized privileged-path reachability, and no owner action capable of freezing or stealing user funds. All findings below are Low/Info and were independently corroborated by multiple agents in the original 18-agent audit.

Findings

[F291-1] Owner-allowlisted collateral is validated only at listing time, with no re-check at each position's creation window

Severity: Low
Origin: corroborated by 9 of 18 agents in job 290's audit (UNI-1 in that report) — re-verified in scope here
Location: setCollateralAllowed() (line 622 of the shared source), consumed at createPosition() line 677
Description: collateralAllowed[token] is a simple boolean toggle with no expiry, versioning, or re-validation. Once set true, every future createPosition() call for that token is accepted regardless of whether the token's risk profile has changed since it was allowlisted (e.g. an upgradeable proxy token whose implementation changes, or a token that later adds a transfer fee or blocklist). The Factory itself is not directly harmed — the downstream impact (permanently frozen exits) lands on the PMFIPositionVaultV22 instances it deploys — but the allowlist decision that gates the entire blast radius is made exclusively in this contract.
Recommendation: Document that setCollateralAllowed approvals should be periodically re-reviewed, especially for upgradeable or governance-controlled tokens; consider an owner-triggered "delist" that only blocks new positions (existing ones are unaffected either way, since the check is creation-time only by design).

[F291-2] feeRecipient is immutable with no rotation path

Severity: Low
Origin: corroborated by both audit phases in job 290 (AC-1/UNI-6) — re-verified in scope here
Location: feeRecipient (immutable, set in constructor), consumed by withdrawCreationFees() (line 753)
Description: On-chain confirmed: feeRecipient() == owner() == 0x7c8D9Ad4F51299b02755Ec13c018004008b45494 for this deployment. If this key is lost or compromised, accrued ETH creation fees become either permanently stranded or drainable by the compromised key. This risk is strictly bounded to protocol fee revenue — no user collateral, principal, or exit path is affected, since feeRecipient is not referenced anywhere in the vault's user-facing functions.
Recommendation: Accept as a deliberate trust-minimization tradeoff, or add an onlyOwner-gated setFeeRecipient(address) with a zero-address check and event.

[F291-3] CREATION_FEE (0.0001 ETH, confirmed on-chain) is not the actual spam-prevention mechanism on Base

Severity: Info
Origin: job 290's CHAIN-2/UNI-11 — re-verified in scope here
Location: CREATION_FEE constant, enforced in createPosition() line 671
Description: On-chain confirmed CREATION_FEE = 100000000000000 wei = 0.0001 ETH (~$0.30 at typical prices), economically trivial on Base. Actual spam resistance for this contract comes from two independent, stronger mechanisms also enforced here: the collateralAllowed owner allowlist and the requirement to lock the full collateralAmount of real collateral per created vault (_safeTransferCollateralFromExact, line 640). allVaults is append-only and never iterated in any on-chain function (allVaultsLength() only returns its length), so unbounded growth from cheap creation is not a gas-DoS vector.
Recommendation: None required for security. If fee revenue is a design goal, consider making CREATION_FEE owner-settable to track ETH price, since it is currently an immutable constant.

[F291-4] Owner can indefinitely pause new position creation and new purchases — verified scope-limited, no exit-path impact

Severity: Info
Origin: job 290's AC-2/UNI-7 — re-verified in scope here
Location: setCreationPaused() (line 628), setPurchasesPaused() (line 633)
Description: A single onlyOwner call (Ownable2Step-protected, so key transfer itself is safe) can halt all new position creation and all new marketplace purchases indefinitely. As documented in the permission-map verification above, this cannot touch any existing vault's exit, redemption, refund, or settlement path — the worst case is a griefing DoS on new business only, not a fund-freeze on existing users.
Recommendation: None required. Optionally consider a timelock on these owner controls if further operational decentralization is desired.

[F291-5] renounceOwnership() correctly disabled; declared view is cosmetic

Severity: Info
Origin: job 290's AC-3/UNI-8 — re-verified in scope here
Location: renounceOwnership() line 618
Description: Correctly overridden to always revert (OwnershipRenunciationDisabled), preventing the owner from orphaning the collateral allowlist and pause controls — the intended, safe design. Declared public view override onlyOwner; this is legal (more restrictive than the base Ownable function) and harmless since the function reverts unconditionally before any read would occur.
Recommendation: None required; optionally drop the view keyword for clarity, since the intent is a disabled state-mutating function.
