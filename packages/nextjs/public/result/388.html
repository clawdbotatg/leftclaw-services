Findings

[H-1] Signed reward payload does not commit to the resolved referral chain — a registration oracle (or the target user) can redirect a majority of an already-signed distribution

Severity: High | Confidence: 85 | Origin: [both] — phase1: evm-audit-access-control (AC-1); phase2: 5 independent pashov agents (execution-trace, first-principles, numerical-gap, trust-gap, flow-gap)
Location: RewardDistributor.distributeChainRewards(), src/core/RewardDistributor.sol:109-145; _getReferralChain(), src/core/RewardDistributor.sol:154-177; ReferralGraph._register(), src/core/ReferralGraph.sol:114-130.

Description: The distribution oracle's signature covers only (reward.user, reward.totalAmount, reward.rewardToken, reward.groupId, reward.eventId):

bytes32 rewardHash = keccak256(
    abi.encodePacked(reward.user, reward.totalAmount, reward.rewardToken, reward.groupId, reward.eventId)
);

(RewardDistributor.sol:112-120) — it never commits to the referral chain or the recipient/amount split. The actual payout chain is resolved live, at execution time, by walking ReferralGraph state:

function _getReferralChain(address user, bytes32 groupId) internal view returns (address[] memory) {
    address[] memory chain = new address[](11);
    uint256 length = 0;
    address current = user;
    chain[length++] = current;
    while (length < 11) {
        current = referralGraph.getReferrer(current, groupId);
        if (current == address(0) || current == REFERRAL_ROOT) break;
        chain[length++] = current;
    }
    ...
}

(RewardDistributor.sol:154-177). Registration authorization (ReferralGraph._authorizedOracles) is a separate, independently-managed trust set from distribution authorization (RewardDistributor._authorizedOracles) — per the access-control inventory, the registration-oracle role is documented as moving no value. If the distribution oracle signs a reward for a reward.user who is unregistered at signing time (a legal, ordinary state — chain resolves to [user], 100% to user), a registration oracle can insert one or more ancestors above reward.user via ReferralGraph.register() between signing and execution:

function _register(address user, address referrer, bytes32 groupId) internal {
    ...
    if (_referrers[groupId][user] != address(0)) revert UserAlreadyRegistered();
    if (referrer != REFERRAL_ROOT && !_isInReferralTree(referrer, groupId)) revert ReferrerNotInTree();
    _referrers[groupId][user] = referrer;
    _children[groupId][referrer].push(user);
    ...
}

(ReferralGraph.sol:114-130) — this succeeds because the only guard against re-registration is _referrers[groupId][user] != address(0), which is still false for an unregistered reward.user. distributeChainRewards is permissionless (anyone can relay a valid signature, RewardDistributor.sol:109), so the registration and the distribution race independently in the mempool with no atomicity between them. Because _distributedRewards[rewardHash] is set permanently once the distribution executes (RewardDistributor.sol:129), the redirected outcome cannot be corrected.

Proof of Concept (concrete numbers): totalAmount = 1000. Distribution oracle signs ChainRewardData{user: R1, totalAmount: 1000, rewardToken: T, groupId: G, eventId: E} while R1 is unregistered in group G, intending R1 to receive 100% (chain would resolve to length 1, RewardCalculator's cumSums[1] = 10000 gives weights[0]/cumSums[1] = 1.0). Before the signed transaction lands, an address holding ReferralGraph-oracle authorization for G (a role with no value-moving capability per its own access-control entry) pre-builds a 9-hop sybil chain A1 ← A2 ← ... ← A9 ← REFERRAL_ROOT via ordinary register() calls, then calls register(R1, A1, G) — legal since A1 is tree-connected and R1 is still unregistered. When the signed distribution is finally relayed, _getReferralChain(R1, G) now returns [R1, A1, ..., A9] (10 entries, RewardCalculator's hard cap). cumSums[10] = 24845, so R1 receives 1000 * 10000 / 24845 ≈ 403 instead of the full 1000, and A1..A9 collectively capture ≈ 597 — up to ~59.7% (1 − weights[0]/cumSums[10]) of a reward the distribution oracle authorized entirely for R1, using only registration-oracle privilege. A simpler one-hop variant (insert a single referrer) was independently traced by a second agent redirecting 37.5% of a reward in the same way, and a third variant showed the target user themselves front-running their own registration to capture an ancestor's share.

Recommendation: Bind the signature to the resolved recipient set — e.g. sign keccak256(user, totalAmount, rewardToken, groupId, eventId, keccak256(abi.encode(chain))) where chain is enumerated off-chain at signing time, and have distributeChainRewards verify the live-computed chain matches what was signed (revert on mismatch). A cheaper partial mitigation: require referralGraph.isRegistered(reward.user, groupId) at signing time and re-verify at execution that the chain length/composition is unchanged from what the oracle observed.

[H-2] Cross-deployment / cross-chain signature replay — rewardHash has no domain separator

Severity: High | Confidence: 90 | Origin: [both] — phase1: evm-audit-signatures (SIG-1); phase2: 5 independent pashov agents (math-precision, access-control, economic-security, execution-trace, periphery)
Location: distributeChainRewards() hash construction, src/core/RewardDistributor.sol:112-120; SignatureLib.toEthSignedMessageHash(), src/utils/SignatureLib.sol:13-15.

Description: Neither block.chainid nor address(this) (the verifying RewardDistributor instance) is bound into the signed digest. SignatureLib.toEthSignedMessageHash wraps rewardHash in only the generic EIP-191 prefix:

function toEthSignedMessageHash(bytes32 hash) internal pure returns (bytes32) {
    return keccak256(abi.encodePacked("\x19Ethereum Signed Message:\n32", hash));
}

(SignatureLib.sol:13-15), and SignatureLib.recover adds no contract/chain-scoping either (SignatureLib.sol:21-42). _distributedRewards[rewardHash] (RewardDistributor.sol:37) is per-contract storage — the "distributed at most once" guarantee holds only within a single deployment, not across instances. This is realistic in operation: teams commonly reuse the same oracle signing key across a redeployment (bug-fix migration) or across a multi-chain rollout deployed via a deterministic (CREATE2) factory, which places RewardDistributor at the same address on every chain.

Proof of Concept: Deploy RewardDistributor twice — e.g. via CREATE2 on chain A and chain B, or as a redeploy on the same chain — authorizing the same oracle EOA K for groupId = G on both, and fund both with the same rewardToken (true for canonically-deployed tokens at the same address). Oracle K signs one ChainRewardData{user, totalAmount: 1000e18, rewardToken, groupId: G, eventId: E} for a real event that occurred on chain A. This is submitted (and publicly visible as calldata) on chain A, paying out 1000e18. Anyone copies the identical (reward, signature) calldata and submits it to chain B's RewardDistributor: _distributedRewards[rewardHash] is false there (independent storage), SignatureLib.recover returns the same signer (digest has no chain-dependent input), K is authorized for G on chain B too — the full 1000e18 is paid out a second time from chain B's independent token balance, for an event that never occurred there.

Recommendation: Include block.chainid and address(this) in the hashed payload (keccak256(abi.encode(block.chainid, address(this), reward.user, reward.totalAmount, reward.rewardToken, reward.groupId, reward.eventId))), or migrate to full EIP-712 typed-data signing with a standard domain separator — this also resolves the raw-EIP-191-vs-EIP-712 informational gap noted below (I-6).

[H-3] Atomic all-or-nothing payout loop — one blocklisted/reverting recipient anywhere in a chain permanently blocks payment to every other recipient

Severity: High | Confidence: 85 | Origin: [both] — phase1: evm-audit-dos (DOS-1), evm-audit-erc20 (ERC20-2); phase2: 3 independent pashov agents (economic-security, invariant, first-principles)
Location: payout loop, src/core/RewardDistributor.sol:138-142; combined with the immutable-referrer invariant in ReferralGraph._register(), src/core/ReferralGraph.sol:118,126.

Description: The payout loop performs synchronous transfers to every recipient in a single atomic transaction, with no isolation:

for (uint256 i = 0; i < recipients.length; i++) {
    if (amounts[i] > 0) {
        SafeTransferLib.safeTransfer(ERC20(reward.rewardToken), recipients[i], amounts[i]);
    }
}

(RewardDistributor.sol:138-142). If reward.rewardToken is a legitimate deny-list-capable token (USDC/USDT-style) and any one address in the resolved chain is on that token's blocklist — for reasons entirely outside this protocol's control — that single safeTransfer reverts, reverting the entire distributeChainRewards call, including the _distributedRewards write (RewardDistributor.sol:129). Because ReferralGraph._register makes a referrer permanent once set (ReferralGraph.sol:118 reverts on re-registration; no update path exists anywhere in scope), the chain composition for a given reward.user can never change. Every future retry — for this user, or for any descendant sharing the blocked ancestor within the top-10 window — reconstructs the identical chain and reverts identically. This is a permanent denial of payment to the target user and every other un-blocked ancestor, triggered by one unrelated address's real-world blocklisting, with no on-chain recovery path (see M-1, no rescue function exists).

Proof of Concept: A user registers under a 5-level referral chain (ordinary, oracle-driven registration). Independently, an ancestor 3 hops up is later added to USDC's blocklist (e.g. an OFAC listing) — an event wholly unrelated to this protocol. The distribution oracle signs a legitimate reward for the target user's chain. The payout loop reaches the blocklisted ancestor's safeTransfer, which reverts; the whole transaction reverts, so the target user and every other non-blocklisted ancestor also receive nothing. Every future distribution attempt for this user (any eventId, any amount) hits the identical revert, permanently, for as long as the blocklisted address remains in the chain — which, given immutable referrer links, is forever.

Recommendation: Wrap each safeTransfer in a try/catch (via a raw .call() with a success check, since safeTransfer itself is a low-level helper) and credit failed transfers to a per-recipient pull-payment mapping instead of reverting the whole batch — or move to a full pull-payment/claim model where distributeChainRewards only computes and credits balances.

[M-1] No token rescue/recovery function anywhere in scope

Severity: Medium | Confidence: 95 | Origin: [phase1 only] — evm-audit-general (GEN-2); corroborated structurally by the phase-0 external-surface map's funding assumption
Location: RewardDistributor.sol — entire external surface (getReferralGraph, isRewardDistributed, authorizeOracle, unauthorizeOracle, isAuthorizedOracle, getAuthorizedOracles, distributeChainRewards); no deposit/withdraw/rescue/sweep function exists.

Description: RewardDistributor must be funded entirely out-of-band (a direct ERC20 transfer into the contract address — there is no deposit()). There is no mechanism, not even owner-gated, to recover over-funded, orphaned (retired-group), or stuck balances (e.g. the H-3 or L-2 failure modes, or excess dust from a completed distribution round). Any such balance is permanently locked with no code path to move it out.

Recommendation: Add an onlyOwner-gated rescueTokens(address token, address to, uint256 amount) function, or explicitly document this as an accepted risk if intentional.

[M-2] No per-group balance segregation — an oracle authorized for one group can spend funds earmarked for any other group sharing the same token

Severity: Medium | Confidence: 75 | Origin: [phase2 only] — pashov trust-gap agent; re-examined and confirmed by the orchestrator (grep of RewardDistributor.sol for any balance-tracking beyond the replay flag — none found)
Location: distributeChainRewards(), src/core/RewardDistributor.sol:109-145; contract-wide.

Description: Oracle authorization is scoped per groupId via authorizeOracle(oracle, groupId) — separate grants imply, to an operator, per-group trust isolation. But the token balance an authorized oracle can actually spend against is the contract's raw, unscoped balanceOf(address(this)); there is no mapping(groupId => balance) or equivalent anywhere in the contract. Funding is out-of-band and untagged by group (per M-1). An oracle authorized only for a lower-value group B can sign distributeChainRewards({..., groupId: B, totalAmount: <up to the full contract balance>}) and drain tokens that were transferred in expecting to fund group A's participants — nothing on-chain distinguishes "group A's money" from "group B's money," despite the separate authorization mechanics suggesting otherwise.

Proof of Concept: Group A's operator funds RewardDistributor with 100,000 USDC intending it for group A's referral payouts. Group B's independently-keyed, separately-authorized oracle (lower trust, perhaps a newer or lower-scrutiny integration) signs ChainRewardData{user: <address B-oracle controls>, totalAmount: 100000e6, rewardToken: USDC, groupId: B, eventId: E}. distributeChainRewards performs no check that totalAmount is bounded by anything earmarked for group B specifically — it succeeds and drains the entire balance, leaving group A's participants with nothing.

Recommendation: Add a fundGroup(groupId, token, amount) deposit entrypoint that credits a groupBalance[groupId][token] ledger, debited by distributeChainRewards, so a group's oracle can only ever spend what was explicitly earmarked for that group.

[M-3] Unvalidated reward.user == address(0) (or == REFERRAL_ROOT) burns the distribution

Severity: Medium | Confidence: 80 | Origin: [both] — phase1: evm-audit-general (GEN-1, rated High there); phase2: leads from 4 agents plus a traced ROOT-specific variant from the boundary agent
Location: distributeChainRewards() L110 (only totalAmount == 0 is checked), _getReferralChain() L158-159 (chain[0] = user appended unconditionally, before any sentinel check).

Description: distributeChainRewards never validates reward.user. _getReferralChain appends reward.user as chain[0] unconditionally:

address current = user;
chain[length++] = current;

(RewardDistributor.sol:158-159) — note this line runs before the loop's current == REFERRAL_ROOT check, so that check only guards addresses fetched via getReferrer inside the loop, not the initial user value itself. If reward.user == address(0), the chain resolves to [address(0)] and 100% of totalAmount is sent via SafeTransferLib.safeTransfer to the zero address; Solmate-style/minimal ERC20s do not special-case address(0), so the tokens are irrecoverably burned (compounded by M-1 — no rescue path). If reward.user == REFERRAL_ROOT (0x...01), the same happens to that sentinel address; if a registration oracle has separately (and invalidly, per L-3) given REFERRAL_ROOT a fake referrer via register(REFERRAL_ROOT, A, groupId), a further share leaks to that fabricated referrer A as well. Both variants require an oracle-side data error (e.g. an off-chain "unknown referrer" default resolving to 0x0) rather than a purely external attacker — this is why the finding is rated Medium (owner/trusted-party-adjacent fund loss) rather than High, per the audit's severity convention that trust-dependent loss paths are downgraded unless a non-privileged actor can trigger them alone; it remains a real, concrete, irreversible-fund-loss footgun worth a one-line fix.

Recommendation: require(reward.user != address(0) && reward.user != REFERRAL_ROOT); before hash computation in distributeChainRewards.

[M-4] Fee-on-transfer / deflationary reward tokens cause silent recipient underpayment

Severity: Medium | Confidence: 75 | Origin: [both] — phase1: evm-audit-erc20 (ERC20-1); phase2: pashov invariant agent (lead)
Location: payout loop, src/core/RewardDistributor.sol:138-142 — no balance-delta check.

Description: amounts[i] is a nominal value computed by RewardCalculator from reward.totalAmount; it is never reconciled against balanceOf(recipient) before/after the transfer. If reward.rewardToken is a legitimate fee-on-transfer or deflationary token, every recipient receives strictly less than amounts[i], with no revert, no on-chain detection, and no correction possible (the rewardHash is already permanently marked distributed per L-3/M-3's discussion of that flag's permanence). The emitted ChainRewardsDistributed event still reports the full nominal amounts, so off-chain reconciliation built on that event will overstate actual payouts.

Recommendation: Measure balanceOf(recipient) before/after each transfer and either revert on shortfall or emit the actually-delivered amount; alternatively, restrict rewardToken to a vetted, owner-maintained allowlist of standard-compliant tokens.

[L-1] No timelock on authorizeOracle / unauthorizeOracle in either contract

Severity: Low | Confidence: 90 | Origin: [phase1 only] — evm-audit-access-control (AC-2)
Location: ReferralGraph.authorizeOracle()/unauthorizeOracle(), src/core/ReferralGraph.sol:159-186; RewardDistributor.authorizeOracle()/unauthorizeOracle(), src/core/RewardDistributor.sol:71-96.

Description: Both contracts grant/revoke oracle authorization instantly via a single onlyOwner transaction, with no delay or multi-sig enforcement in-scope. For RewardDistributor specifically, authorizeOracle grants unlimited signing power over the group's token balance (compounded by M-2's lack of group segregation) with no warning window for integrators to react to a grant, and no faster-than-owner-reaction path to contain a compromised oracle key.

Recommendation: Consider a timelock (or multisig + delay) on oracle grants, particularly for RewardDistributor.

[L-2] Single-step ownership transfer (Solmate Owned), no two-step confirmation

Severity: Low | Confidence: 85 | Origin: [phase1 only] — evm-audit-access-control (AC-3); confirmed via the compiled out/Owned.sol/Owned.json ABI (only transferOwnership/owner/OwnershipTransferred — no pendingOwner/acceptOwnership)
Location: ReferralGraph (src/core/ReferralGraph.sol:11, inherits Owned), RewardDistributor (src/core/RewardDistributor.sol:18, inherits Owned).

Description: Both contracts use Solmate Owned's single-step transferOwnership. A mistyped address or an accidental transfer to address(0) permanently and irrecoverably locks all owner-gated functions (authorizeOracle/unauthorizeOracle in both contracts) — with no rescue path, meaning a compromised or stale oracle could never be revoked and no new oracle could ever be added again for that contract.

Recommendation: Adopt a two-step ownership pattern (Ownable2Step-style pendingOwner + acceptOwnership).

[L-3] ReferralGraph._register never excludes user == REFERRAL_ROOT as a registrable sentinel

Severity: Low | Confidence: 80 | Origin: [phase2 only] — leads from 5 of 12 pashov agents (math-precision, invariant, first-principles, boundary, flow-gap)
Location: _register(), src/core/ReferralGraph.sol:114-130.

Description: _register checks user == address(0) (ReferralGraph.sol:115) but has no analogous check for user == REFERRAL_ROOT, even though REFERRAL_ROOT is explicitly special-cased for the referrer parameter two lines later (ReferralGraph.sol:122). Four of five agents that raised this traced the consequence and found it inert for the common read path — REFERRAL_ROOT appearing mid-chain via getReferrer is caught by the existing break-before-append check in both _getReferralChain and getAncestors — so this is not independently exploitable on its own. It becomes relevant only combined with M-3's reward.user == REFERRAL_ROOT variant.

Recommendation: if (user == REFERRAL_ROOT) revert InvalidUserAddress(); in _register, mirroring the existing zero-address check.

[L-4] Referral chain collects up to 11 addresses but only ever pays 10 — deepest ancestor silently dropped

Severity: Low | Confidence: 95 | Origin: [both] — phase1: evm-audit-general (GEN-4), evm-audit-precision-math (MATH-1), evm-audit-dos (DOS-5); phase2: economic-security, asymmetry (2 findings + 1 corroborating lead)
Location: _getReferralChain(), src/core/RewardDistributor.sol:152-177 (collects up to 11: user + 10 ancestors); _calculateChainRewards(), src/core/RewardDistributor.sol:192-207, and RewardCalculator.calculateRewards(), src/core/RewardCalculator.sol:22-24 (hard cap at 10).

Description: _getReferralChain's own docstring states it returns "up to 11 addresses," and the collection loop does reach 11 for a fully-populated chain. _calculateChainRewards then clamps numRecipients to 10 before calling RewardCalculator, and only the first 10 chain entries are ever copied into recipients/amounts. When a chain reaches full depth, the 11th (most senior, legitimately-registered) ancestor is read, allocated a memory slot, and then silently dropped — receiving 0, absent from the ChainRewardsDistributed event, with no revert or signal. totalAmount still sums exactly across the paid 10 (the weight table's prefix sums were hand-verified against every cumSums[1..10] entry by multiple independent agents, confirming no fund-accounting bug — this is a fairness/correctness gap, not a fund-loss one).

Recommendation: Cap chain collection at 10 to match payout capacity, or extend RewardCalculator to 11 slots; fix the misleading docstring either way.

[L-5] Codeless / non-existent rewardToken silently "succeeds," permanently burning the distribution slot

Severity: Low | Confidence: 80 | Origin: [both] — phase1: evm-audit-general (GEN-3); phase2: pashov boundary agent
Location: distributeChainRewards() L129 (state write), L140 (safeTransfer).

Description: A low-level call to an address with no deployed code returns (true, ""); Solmate's SafeTransferLib treats empty returndata as success with no extcodesize check. If reward.rewardToken is codeless (typo, wrong-chain address, not-yet-deployed contract), the entire flow "succeeds" with zero tokens actually moved. _distributedRewards[rewardHash] is already permanently set (RewardDistributor.sol:129, written before the transfer loop) — that exact reward tuple can never be retried, and (per M-1) there is no rescue path to recover or reissue it.

Recommendation: require(reward.rewardToken.code.length > 0); before the transfer loop, or restrict rewardToken to an owner-maintained allowlist.

[L-6] RewardDistributor constructor grants the initial oracle without emitting OracleAuthorized

Severity: Low | Confidence: 95 | Origin: [both] — phase1: evm-audit-access-control (AC-5); phase2: leads from 3 independent agents (math-precision, execution-trace, asymmetry)
Location: constructor, src/core/RewardDistributor.sol:46-58 (specifically the initialOracle branch, L54-57), contrasted with ReferralGraph's equivalent constructor branch (which does emit) and RewardDistributor.authorizeOracle itself (which also emits on every subsequent grant).

Description: Off-chain monitoring/indexing keyed on OracleAuthorized events will silently miss the deploy-time grant of the single most consequential role in the protocol (signing power over the contract's entire per-group token balance).

Recommendation: Emit OracleAuthorized(initialGroupId, initialOracle) in the constructor branch, matching ReferralGraph's behavior.

[L-7] No expiration/deadline on distribution signatures

Severity: Low | Confidence: 90 | Origin: [phase1 only] — evm-audit-signatures (SIG-2)
Location: ChainRewardData struct (src/interfaces/IRewardDistributor.sol:12-18); distributeChainRewards().

Description: No deadline/expiry field exists. A signature is valid indefinitely until its exact (user, totalAmount, rewardToken, groupId, eventId) tuple is consumed; there is no way to cancel a specific outstanding signature short of fully de-authorizing the signing oracle (which also invalidates all of that oracle's other legitimate outstanding signatures).

Recommendation: Add a deadline field, included in the hash, checked at call time.

[L-8] batchRegister has no cap on users.length

Severity: Low | Confidence: 90 | Origin: [phase1 only] — evm-audit-dos (DOS-2)
Location: ReferralGraph.batchRegister(), src/core/ReferralGraph.sol:149-156.

Description: An unbounded loop over caller-supplied users[] could exceed the block gas limit for a very large array. Not third-party exploitable — batchRegister is onlyAuthorizedOracle-gated, and the registration oracle is already a fully trusted role — but a self-inflicted operational/availability issue for the trusted operator with no explicit bound.

Recommendation: Add an explicit require(users.length <= MAX_BATCH_SIZE).

[L-9] Pausable reward tokens cause temporary (self-resolving) DoS

Severity: Low | Confidence: 90 | Origin: [phase1 only] — evm-audit-erc20 (ERC20-4)
Location: payout loop, src/core/RewardDistributor.sol:138-142.

Description: Distinct from H-3 — if reward.rewardToken is legitimately paused (USDC/USDT-style pause()), the whole call reverts, but the _distributedRewards write reverts along with it, so the identical signed payload succeeds normally once the token is unpaused. Operational note, not a bug.

Recommendation: None required; document that relaying should be retried after a token-level pause lifts.

[I-1] IReferralGraph NatSpec for register() describes root registration incorrectly

Severity: Info | Confidence: 85 | Origin: [phase2 only] — pashov periphery agent; verified directly by the orchestrator against source
Location: src/interfaces/IReferralGraph.sol:66 (@param referrer ... or address(0) for root registration) vs. actual implementation, src/core/ReferralGraph.sol:116 (if (referrer == address(0)) revert InvalidReferrerAddress();) and :122 (root registration actually requires referrer == REFERRAL_ROOT, the 0x...01 sentinel, never address(0)).

Description: An integrator trusting the interface doc over the implementation would construct a root-registration call with referrer = address(0) and get an unconditional revert. Verified: ReferralGraph.sol:116 reverts InvalidReferrerAddress for referrer == address(0) unconditionally, before the root-sentinel branch is ever reached.

Recommendation: Correct the NatSpec to state REFERRAL_ROOT (not address(0)) as the root-registration sentinel.

[I-2] Two independent oracle-authorization systems provide no on-chain guarantee of separation

Severity: Info | Confidence: 90 | Origin: [phase1 only] — evm-audit-access-control (AC-6)
Location: ReferralGraph._authorizedOracles (src/core/ReferralGraph.sol:22) vs. RewardDistributor._authorizedOracles (src/core/RewardDistributor.sol:31).

Description: Nothing on-chain prevents authorizing the same address as both registration and distribution oracle for the same group, which would collapse the intended blast-radius separation between the two roles to a single key's custody discipline. Operational/documentation note.

Recommendation: Document the requirement for distinct signing keys/custody between the two roles; optionally add an on-chain guard rejecting cross-authorization of the same address in both roles for the same group.

[I-3] unauthorizeOracle's linear scan over the oracle list is owner-controlled growth only, not externally exploitable

Severity: Info | Confidence: 90 | Origin: [phase1 only] — evm-audit-dos (DOS-3)
Location: ReferralGraph.unauthorizeOracle(), src/core/ReferralGraph.sol:169-184; RewardDistributor.unauthorizeOracle(), src/core/RewardDistributor.sol:81-96.

Description: List growth requires onlyOwner plus an idempotency guard preventing duplicate entries — no adversarial path exists to inflate this array. No action required at any realistic owner-driven scale.

[I-4] Unbounded _children array growth — view-only exposure, no on-chain gas-DoS path

Severity: Info | Confidence: 85 | Origin: [phase1 only] — evm-audit-dos (DOS-4)
Location: ReferralGraph._register() (push), src/core/ReferralGraph.sol:127; getChildren(), src/core/ReferralGraph.sol:66-68.

Description: _children can grow without bound, but the only state-changing read of it (_isInReferralTree) checks .length > 0, an O(1) operation regardless of size. The only full enumeration is the view function getChildren — an off-chain indexer/RPC concern at most, not an on-chain gas-DoS vector.

[I-5] Small totalAmount degenerates to "pay recipient 0 only"; no overflow guard on the weight multiplication

Severity: Info | Confidence: 95 | Origin: [phase1 only] — evm-audit-precision-math (MATH-2, MATH-3); hand-verified independently by 4+ phase-2 agents
Location: RewardCalculator.calculateRewards(), src/core/RewardCalculator.sol:35-45 (remainder-to-index-0 rounding); :36 (totalReward * weights[i], unguarded against the ~1.16e73 overflow threshold, unreachable given realistic token supplies).

Description: For totalReward below roughly totalSum/weights[0] ≈ 2.48 per chain slot (n=10), most downstream ancestors receive 0 and index 0 absorbs the full remainder by design — a fairness/documentation note, not a bug (the exact-sum invariant was hand-verified for totalReward = 1, 5, 9 and holds by construction for all inputs). The overflow guard gap is unreachable in practice.

[I-6] No low-s malleability guard / raw EIP-191 instead of EIP-712

Severity: Info | Confidence: 90 | Origin: [both] — phase1: evm-audit-signatures (SIG-3, SIG-4); phase2: pashov boundary agent (lead)
Location: SignatureLib.recover(), src/utils/SignatureLib.sol:21-42.

Description: recover accepts any s value with no low-s canonicalization check. Confirmed non-exploitable under the current design by multiple independent agents: replay dedup keys on rewardHash (content), not signature bytes, so a malleable counterpart simply recovers the same signer/same hash and hits the same already-set replay flag. Raw EIP-191 (vs. EIP-712) is the same root cause behind H-2's missing domain separator; fixing H-2 via EIP-712 migration resolves both.

Recommendation: Add a low-s check as defense-in-depth (matches OpenZeppelin ECDSA convention); migrate to EIP-712 as part of the H-2 fix.
