4. UnionStakingVault Pre-Launch State

stakingActive = false, confirmed as the expected, intentional pre-launch state (not a finding). We independently verified the activation and pre-activation-accounting invariants the job description asked us to check:

  • Activation is exactly one-shot and irreversible. activateStaking() is onlyOwner, guarded by require(!stakingActive), and there is no function anywhere that sets stakingActive back to false. Confirmed by full-text search — no other writer of this variable exists.
  • Activation cannot retroactively grant rewards or Action Credits. activateStaking() resets lastAccrualAt = block.timestamp at the moment of activation, and the credit/reward accrual functions (_accrue, _projectCreditAccrual, _updateRewardAcc) only advance based on elapsed time since lastAccrualAt — there is no code path that back-dates accrual to before activation. stake() itself reverts pre-activation (require(stakingActive)), so totalStaked is provably zero before activation, which makes credit/reward math a no-op regardless.
  • Pre-activation access-fee and reward accounting is safe. Prior to activation, TreasuryRouter.distributeRevenue's staker-share branch correctly detects !stakingVault.stakingActive() and folds that share into the general reserve rather than into an unreachable pendingStakerUsdc bucket. Access-fee discounting via banked Action Credits (TaskRegistry._chargeAccessFee → stakingVault.trySpendCredit) is a no-op pre-activation since no credits can exist yet.

[92] 1. Arbitration-timeout settlement pays hour-block workers for time that has not elapsed, draining the poster's escrow

EscrowVault._settleAtDeadline (HOUR_BLOCKS branch) · Confidence: 92

Description
The HOUR_BLOCKS branch computes accruedBlocks = (deadline - start) / 1 hours using the raw (possibly far-future) task deadline, unlike the STREAMING branch two lines above it which correctly caps at cutoff = min(block.timestamp, deadline) — so when an unresolved dispute times out (ArbitrationModule.resolveTimedOut, permissionless after the 21-day ABSOLUTE_RESOLUTION_TIMEOUT) on an HOUR_BLOCKS task whose own deadline is still far in the future, the worker is credited for hours that have not actually elapsed, up to the full remaining escrow.

Concrete trace: HOUR_BLOCKS task, remaining=1000e6 USDC, hourBlockSize=1e6, deadline=start+100 days. A dispute opens on day 1 and times out on day 22 (21 days later). accruedBlocks=(100 days)/1h=2400; maxPayableBlocks=remaining/hourBlockSize=1000; payableBlocks=min(2400,1000)=1000 → the worker receives the entire remaining $1000 escrow immediately, although only ~22 days (≈528 real hours, ≈$528) of work-time had actually elapsed. The poster loses the ~$472 difference outright.

This is attacker-triggerable by design, not merely a theoretical edge case: any worker on an HOUR_BLOCKS task can open a dispute on themselves (or via the counterparty), decline to consent to any arbitrator, and simply wait 21 days to collect the full escrow regardless of actual elapsed work.

Fix

             } else if (e.mode == EscrowMode.HOUR_BLOCKS) {
                 uint256 start = activatedAt[taskId];
                 if (start != 0 && deadline > start) {
-                    uint256 accruedBlocks = (deadline - start) / 1 hours;
+                    uint256 cutoff = block.timestamp < deadline ? block.timestamp : deadline;
+                    uint256 accruedBlocks = (cutoff - start) / 1 hours;
                     uint256 unpaidBlocks = accruedBlocks > e.hoursClaimed
                         ? accruedBlocks - e.hoursClaimed
                         : 0;

[90] 2. Arbitration-timeout settlement has no milestone/upfront branch — proven-but-unaccepted work is discarded and 100% of escrow refunds to the poster

EscrowVault._settleAtDeadline (missing MILESTONE/UPFRONT branch) · Confidence: 90

Description
_settleAtDeadline's worker-payout logic (lines 311-340) only has branches for EscrowMode.STREAMING and EscrowMode.HOUR_BLOCKS. For MILESTONE and the default/upfront mode, workerAmount is never set and stays 0, so posterAmount = remaining refunds the poster 100% — even when the worker has already submitted on-chain-verified milestone proof (pendingMilestoneLiability set, task in IN_REVIEW) that would otherwise be paid out via the normal resolveStaleReview/acceptMilestone paths.

This is reachable via the dispute-timeout path specifically: a poster who owes a worker for proven milestone work can call openDispute on the IN_REVIEW task (permitted) — which freezes the escrow and disables the worker's 3-day resolveStaleReview self-help — then simply withhold consent to any arbitrator in proposeArbitrator and wait. Once ABSOLUTE_RESOLUTION_TIMEOUT (21 days) elapses with no ruling, anyone can call resolveTimedOut, which routes through this code path: the worker receives $0 for delivered, proven work, and the poster's dispute bond is also refunded (the timeout branch never forfeits it). The only backstop is the permissionless assignFallbackResolver, which seats the single owner-configured neutral resolver during days 7–21 — the worker is only protected if that address is funded and someone invokes it in time.

Independently identified by 3 of 12 phase-2 attack agents as a full finding and corroborated as a lead by 3 more, plus phase-1's access-control and economic-security passes — six-way convergence on the same root cause.

Fix

         uint256 workerAmount;
         if (remaining > 0 && e.worker != address(0)) {
             if (e.mode == EscrowMode.STREAMING) {
                 ...
             } else if (e.mode == EscrowMode.HOUR_BLOCKS) {
                 ...
+            } else if (e.mode == EscrowMode.MILESTONE) {
+                // pay out proven-but-unreleased milestone liability before
+                // refunding the remainder to the poster
+                workerAmount = pendingMilestoneLiabilityFor(taskId); // new: sum of proven, unreleased milestone amounts
             }
             if (workerAmount > remaining) workerAmount = remaining;

(Exact implementation should mirror however pendingMilestoneLiability is already tracked in TaskRegistry/EscrowVault — the fix is architectural: give milestone mode an equivalent "pay what was earned" branch instead of defaulting to zero.)

[85] 3. resolveStaleReview ignores the arbitration-level dispute-opening pause, letting a worker's fraudulent milestone proof pay out while the poster is barred from disputing it

TaskRegistry.resolveStaleReview × ArbitrationModule.disputeOpeningPaused · Confidence: 85

Description
resolveStaleReview (the permissionless, 3-day optimistic-milestone-release safety valve) checks only taskLive/notPaused(taskId) — a task-level pause state that no code path in scope ever sets — and has no check on arbitration.disputeOpeningPaused(). Meanwhile TaskRegistry.openDispute/ArbitrationModule.openDispute does check it and reverts while paused. The owner-controlled pause (used, for example, ahead of an ArbitrationRecoveryCoordinator rotation) lasts up to MAX_PAUSE_DURATION = 7 days and is freely renewable by the owner before it expires.

Because REVIEW_TIMEOUT (3 days) always fits inside any pause window (minimum useful pause ≥ the 2-day RECOVERY_DELAY it's meant to cover, typically the full 7 days), a worker can submit bogus/low-quality proof for every funded milestone on a task while a pause is active; the poster's only defense — opening a dispute — reverts for the pause's duration, while the permissionless stale-review payout keeper remains fully live and pays the worker in full after 3 days regardless.

(Alternatively, extend/freeze reviewSince for the duration of any active pause so the 3-day clock does not run down while the poster is unable to contest.)

[88] 4. TreasuryRouter.feeRecipient has no owner-controlled recovery path — a lost or bricked key permanently locks the entire protocol treasury

TreasuryRouter.feeRecipient / withdrawFees / withdrawNativeFees · Confidence: 88

Description
feeRecipient is the sole address authorized to withdraw the protocol's entire accrued USDC reserve (withdrawFees) and all accrued native-ETH slash revenue (withdrawNativeFees). Its only rotation path is self-initiated: proposeFeeRecipient requires msg.sender == feeRecipient, and acceptFeeRecipient requires msg.sender == pendingFeeRecipient. There is no onlyOwner path anywhere that can set or override feeRecipient — unlike buybackExecutor, whose first assignment and every subsequent rotation both go through the owner (setBuybackExecutor/proposeBuybackExecutor). If the feeRecipient key is ever lost (not even compromised — merely lost or a signer set becoming unavailable), every dollar of accrued and future treasury revenue becomes permanently unwithdrawable, with no governance action able to recover it.

Fix

+    function setFeeRecipientOverride(address newRecipient) external onlyOwner {
+        require(newRecipient != address(0), "Treasury: zero");
+        feeRecipient = newRecipient;
+        pendingFeeRecipient = address(0);
+    }

(Consider gating this behind the same 2-day delay used for buybackExecutor rotation, so it can't be used to silently hijack fees, while still giving governance a genuine recovery path.)

[78] 5. Owner can indefinitely re-arm disputeOpeningPaused, defeating its documented 7-day auto-expiry liveness guarantee

ArbitrationModule.setDisputeOpeningPaused · Confidence: 78

Description
The pause is designed to auto-expire after MAX_PAUSE_DURATION (7 days) specifically to preserve dispute-opening liveness, per the contract's own comments. Nothing prevents the owner from calling setDisputeOpeningPaused(true) again before it expires, refreshing the window indefinitely — and Finding #3 above demonstrates a concrete, non-hypothetical consequence of an extended pause. Owner is the trusted governance multisig, which bounds this to a trust-model gap rather than a third-party exploit, but the "liveness guarantee" the code advertises is not actually enforced on-chain against the owner itself.

Fix
Add a minimum unpaused cooldown between consecutive pauses, or a cap on cumulative paused time per rolling window, so the documented liveness property is actually enforced rather than merely advisory.

[70] 6. feeRecipient rotation carries no timelock, unlike the less-privileged buybackExecutor role

TreasuryRouter.proposeFeeRecipient/acceptFeeRecipient vs. proposeBuybackExecutor/acceptBuybackExecutor · Confidence: 70

Description
buybackExecutor rotation is deliberately delayed 2 days "to give monitoring systems time to detect an incorrect or malicious destination." feeRecipient — which controls strictly more value (the entire treasury reserve, not just the buyback share) — rotates instantly. This does not itself create new attacker capability (a compromised feeRecipient key can already withdraw everything immediately regardless of rotation delay), but it is a process inconsistency that removes the observation window the protocol's own design otherwise considers necessary for revenue-controlling roles.

Fix
Apply the same 2-day staged-delay pattern to feeRecipient rotation as already used for buybackExecutor.

[68] 7. Staged role rotations (buybackExecutor, feeRecipient, fallbackResolver) have no cancel function and no expiry on the pending slot

TreasuryRouter.pendingBuybackExecutor/pendingFeeRecipient, ArbitrationModule.pendingFallbackResolver · Confidence: 68

Description
Unlike ArbitrationRecoveryCoordinator (which provides both cancelRecovery and full re-validation at execute time), none of these three staged rotations can be cancelled once proposed, and none of their accept functions checks an upper bound — only a lower-bound "delay has passed" check. A pending address that is safe today but is lost/compromised at some arbitrary later date can still unilaterally accept the role at that later date, since the pending slot never expires and the current holder must remember to overwrite it.

Fix
Add explicit cancel functions (current holder or owner can reset the pending slot to zero) and an expiry window on each staged accept (e.g., reject if block.timestamp > proposedAt + delay + grace).

[65] 8. Systemic trust concentration — a single multisig controls every privileged lever across all 8 contracts

Cross-cutting; concrete path via ArbitrationRecoveryCoordinator.proposeRecovery/executeRecovery · Confidence: 65

Description
One governance multisig is owner on all 8 Ownable2Step contracts and simultaneously holds every one-shot wiring setter, the dispute-opening pause, bootstrap-arbitrator qualification, activateStaking, and the arbitration-recovery propose/cancel authority. Direct arbitration rotation is hard-disabled, which is the key mitigation, but a compromised multisig could still reach arbitration authority via the (by-design) 2-day-delayed Coordinator path by deploying a graph-consistent replacement module. Impact is bounded: EscrowVault.split/refund can only ever pay the real task's poster/worker, never an arbitrary address, so a malicious module could force unfair rulings and collect dispute-bond fees but could not redirect escrowed principal to an attacker-chosen address.

Fix
No code defect — this is a documented, deliberate centralization tradeoff common to early-stage protocols. Recommend publishing the governance Safe's signer threshold/diversity (see Finding-adjacent Lead below) and considering a split between "pause/propose" authority and "cancel" authority so a single key compromise cannot both quiesce a live module and propose its replacement in the same breath.

[62] 9. bootstrapQualified arbitrator credential is permanent and non-revocable

ArbitrationModule.qualifyBootstrapArbitrator · Confidence: 62

Description
Once granted, bootstrapQualified[arbitrator] = true permanently bypasses the tier-1 reputation gate (rep >= 50) for that address, with no function anywhere to revoke it. If a bootstrapped arbitrator later misbehaves, the owner cannot strip the credential — though both dispute parties must still independently consent to seat that arbitrator (see Finding #10's related analysis), which bounds the practical impact.

Fix

+    function revokeBootstrapArbitrator(address arbitrator) external onlyOwner {
+        bootstrapQualified[arbitrator] = false;
+    }

[55] 10. Native-ETH verifier-bond slashing is entirely unwired — the bond is not actually at risk

ReputationRegistry.slashVerifierBond / resetSubject / stakeVerifierBond · Confidence: 82 (confirmed fact) / impact confidence 55

Description
stakeVerifierBond accepts native ETH into a per-address bond; slashVerifierBond and resetSubject's slash leg have caller-authority wired to arbitrationModule/taskRegistry, but no in-scope function anywhere actually calls them (confirmed by exhaustive grep across all 9 contracts — independently reached by 6 of our review's attack agents). unstakeVerifierBond returns the full bond after only a 7-day cooldown. Anyone relying on "verifier bonds are slashable" as a security assumption for this protocol is trusting a mechanism that does not currently do anything — the ETH is simply a time-locked, risk-free deposit.

Fix
Either wire slashVerifierBond/resetSubject into the dispute-resolution flow they were evidently designed for, or remove the dead mechanism and stop advertising it (events, function names) as an active control if it is intentionally deferred to a future release.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed, or whose impact was assessed as informational — not scored, not counted as findings. Retained for completeness.

  • Dead bond-payout ledger — ArbitrationModule.claimBondPayout/_payBondOrDefer/pendingBondPayouts — Code smells: writer function is never called; real bond settlement routes through AgentDepositVault instead — an integrator calling the same-named function on the wrong contract finds nothing to claim. No fund loss (funds sit correctly in the vault).
  • _enforceBalanceHealth is a no-op — TaskRegistry._enforceBalanceHealth, called ~10× — Code smells: empty pure function with no runtime assertion — the "collateral cannot underflow" guarantee rests entirely on reservation bookkeeping, which we verified holds today by manual reconciliation across every mutator, but there is zero defense-in-depth against a future change breaking it silently.
  • Bond economics invert the intended deterrent — ArbitrationModule dispute bond — Code smells: bond is forfeited to the arbitrator only on an actual ruling and fully refunded on timeout, so opening a dispute purely to freeze a counterparty's escrow and then stalling to the 21-day timeout is free — good-faith arbitration is taxed, freeze-griefing is not.
  • UnionStakingVault.claimableUsdc view under-reports transiently — omits the carried undistributedRewardsScaled term that the state-mutating path includes — view-only inaccuracy in a narrow zero-stake-transition window, no on-chain consumer, no fund impact.
  • pendingStakerUsdc/staking rewards can be temporarily stranded — TreasuryRouter.distributeRevenue/flushStakerShare, UnionStakingVault reward stream — if stakingActive but totalStaked==0 at distribution/emission time, the staker share/reward is unreachable until someone stakes; self-healing, no permanent loss observed, no rescue function exists if staking is permanently abandoned.
  • _payOrDefer outbound legs don't re-verify received amount (EscrowVault, AgentDepositVault) — inert under the pinned non-fee-on-transfer USDC; would silently over-credit under a hypothetical fee-on-transfer token.
  • _payOrDefer's success decode can itself revert on a non-canonical 32-byte bool return — defeats the "never blocks settlement" intent for a token returning a dirty word (e.g. 2); not reachable with pinned USDC (canonical 0/1 returns only).
  • liveTaskBindings/taskBinding counters can drift if a post-dispute registry callback is deferred and never retried — cosmetic telemetry drift; underlying vault fund accounting is unaffected.
  • Reputation "Sybil farming" — investigated and rejected. Six of our independent attack agents flagged that an attacker could self-deal $1+ disputes across three self-controlled addresses to farm arbitratorReputation/resolvedCount. On direct verification against ArbitrationModule.sol (proposeArbitrator's tier gate, _finalise's qualifiedResolution condition, and _tierForAmount's tier boundaries), this path does not exist: any dispute large enough to grant reputation (≥ $1, which is tier ≥ 1) requires the arbitrator to already satisfy the tier-1 gate (rep ≥ 50 OR bootstrapQualified) before being seated — a chicken-and-egg an attacker starting from zero reputation cannot resolve without the owner first calling qualifyBootstrapArbitrator. The two seating paths that bypass the tier gate (assignFallbackResolver, replaceTimedOutArbitrator) always seat the single owner-configured fallback-resolver address, never an attacker's choice. We record this here specifically because it was flagged with unusual consistency across independent review passes, and want the client to know it was investigated to ground truth and disproven, not merely overlooked.
  • Sub-$1 (tier-0) disputes carry no reputation gate at all — confirmed true, but harmless per the analysis above (these disputes never grant reputation either way).
  • AgentDepositVault.topUp is the one inbound transfer that credits net-received rather than requiring an exact match — inert under non-fee-on-transfer USDC; verified it does not desynchronize totalDeposits or reservation accounting even in principle.
