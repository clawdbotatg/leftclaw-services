Methodology Note — source unavailable, bytecode-only audit

No verified source exists for this contract:

  • Sourcify (chain 8453, this address): full_match and partial_match both return null — no match found.
  • BaseScan: contract page confirms not verified ("Verify and Publish your contract" prompt present, no source tab).
  • Etherscan V2 unified API / Blockscout: also return no source / no verification metadata.

Per audit operating procedure, this triggered a bytecode-level fallback audit rather than the standard two-phase (ethskills breadth + pashov depth) Solidity-source pipeline, since that pipeline assumes readable source text. Instead:

  1. Fetched runtime bytecode live via RPC (cast code), disassembled it (cast disassemble), and cross-validated with evmole (automated function-selector/argument/storage-layout inference from bytecode).
  2. Resolved function selectors against the public 4byte.directory signature database plus targeted guessing based on the job's stated scope, then hand-verified the true semantics of every function directly from opcodes (4byte names are frequently coincidental collisions and were not trusted blindly).
  3. Reverse-engineered the full storage layout (8 slots, including a multi-word packed struct for attestations) and manually decoded the constructor, all 5 state-mutating functions, and all 15 view/pure functions from raw opcodes — quoting hex offsets and opcode sequences in place of source line citations.
  4. Ran 4 independent parallel review agents (opus), each assigned a distinct lens (access control / auditor allowlist, storage layout / flag-forgery, consumer-view correctness, issuance flow / general EVM patterns), each working blind from a shared reverse-engineering bundle, then reconciled all four into this single report — cross-checking every claim against the others' opcode-level proofs before inclusion.

Confidence caveat: this is materially harder and slower to fully verify than a source-code review. Every finding below is backed by quoted opcode sequences with hex offsets, cross-checked by at least one other independent agent's reading of the same bytecode. Where agents disagreed or a detail could not be fully pinned down, it is marked as a LEAD rather than a finding, or explicitly marked RESOLVED/REFUTED with the reconciling evidence.

Completeness: 12 unique function/area threads were raised across the 4 agents (isCompliant/checkCompliance divergence, attestations() staleness, compliant-count statistic, ownership/transferOwnership, revokeAuditor, identityRegistry()/issuance external dependency, issueAttestation flag semantics, revokeAttestation access control, addAuditor, pruneExpired, per-address attestation-array getters, auditors() getter) — all 12 are represented in the findings or the "reviewed, no defect found" section below.

IMPORTANT SCOPE NOTE — the on-chain flag semantics do not match the job's description

The client's job description states this registry issues "KYA (Know-Your-Agent), AML, sanctions, and jurisdiction-match flags." Full bytecode decoding of the issuance function (issueAttestation, selector 0x853c79cd) shows the four boolean parameters and their associated revert strings are actually:

"...requires incident reporting"
"...requires post-market monitoring"
"...requires technical documentation"
"...requires human oversight"

— these are EU AI Act high-risk-system obligations, gated by a separate uint256 riskTier parameter (0=minimal, 1=limited, 2=high — requires all 4 bools true, 3=unacceptable — always reverts), not KYA/AML/sanctions/jurisdiction flags. This is an AI-agent risk-tier attestation registry, not a KYC/AML compliance registry, despite the name "ComplianceRegistry."

This does not invalidate the audit (the underlying mechanisms — auditor allowlist, storage integrity, consumer-view correctness — are the same regardless of what the flags represent, and were reviewed as such), but the client should confirm this is in fact the intended target contract before acting on severity/impact framing that assumes KYC/AML semantics.

Finding 1 — isCompliant() returns a stale cache that ignores expiry; diverges from checkCompliance()

Severity: High
Functions: isCompliant(address) (selector 0xa200e5d0, entry 0x044d) vs. checkCompliance(address) (selector 0x2c289dcf, entry 0x1368)
Corroboration: Independently found and proven by 3 of 4 review agents (consumer-view-correctness, storage-layout, issuance-flow), all reaching the same root cause via different code paths.

Root cause

The contract exposes two compliance-gating views that disagree. checkCompliance live-recomputes compliance by iterating the caller's full attestation list (storage slot 5) and, for each id, checking status == 1 (Active) AND block.timestamp < expiry. isCompliant instead returns a cached boolean (slot7[address]) with no timestamp comparison at all. That cache is only refreshed inside a helper subroutine reachable exclusively from the explicit, manually-invoked pruneExpired(uint256 id) (0xd1a9b879) or revokeAttestation (0x1ea1f074) — never automatically. So an attestation whose expiry has passed, but which nobody has bothered to prune, leaves slot7[address] == true and isCompliant() keeps reporting compliant.

Proof

isCompliant (0x044d) — cache read only, no TIMESTAMP opcode anywhere in the function body:

00000470: MSTORE                     ; mem[0]  = address
00000473: PUSH1 0x07; PUSH1 0x20; MSTORE  ; mem[0x20] = 7
00000480: KECCAK256                  ; key = keccak256(address, 7)  -> slot7[address]
00000481: SLOAD                      ; load cached byte
00000482: AND (0xff)
00000487: ISZERO; ISZERO             ; normalize to bool
0000048b: RETURN

checkCompliance (0x1368) — live recompute, does check TIMESTAMP:

00001390: PUSH1 0x05; PUSH1 0x20; MSTORE   ; base = keccak256(address, 5)   (slot5[] array)
00001398: KECCAK256
0000139a: SLOAD                            ; array length
       ... loop over i < length, fetch id = slot5[address][i] ...
000013d5: KECCAK256                        ; base4 = keccak256(id, 4)  (slot4[id] struct)
000013dc: SLOAD; SHR 0xa8; AND 0xff        ; status byte (byte offset 21 of base4+1)
000013e4: PUSH1 0x05; LT; ISZERO; JUMPI 0x0301  ; status>=5 -> Panic(0x21)
000013ec: PUSH1 0x01; EQ                   ; status == 1 (Active)?
00001418: PUSH1 0x03; ADD; SLOAD           ; base4+3 = expiry
0000141f: TIMESTAMP; LT                    ; block.timestamp < expiry  (must be not-yet-expired)

Confirmed by the storage-layout agent's independent trace of the same two functions, and by the issuance-flow agent tracing that slot7 is only ever set true inside issueAttestation and only ever cleared inside the prune/revoke recompute subroutine (0x1b67) — nothing clears it on natural expiry.

Impact

A downstream consumer contract that gates a privileged action (transfer, mint, trade, etc.) on a staticcall to this registry — exactly the client's stated use case, "consumer-facing views used by other contracts to gate calls" — will treat an address as compliant for an unbounded period after its attestation has genuinely expired, as long as nobody calls the permissionless prune function. Critically, the affected address itself has every incentive to never call prune on its own expired attestation, since doing so would correctly flip its own compliance to false. This is a self-serve, no-cooperation-required way for an expired agent to keep passing compliance gates that use isCompliant(). checkCompliance() on the same contract returns the correct answer for the same address at the same time — the two views silently disagree, which is itself a correctness defect independent of which one any given integrator picks.

Recommendation

Make isCompliant() expiry-aware — either have it delegate to the same live-recompute logic as checkCompliance() (accept the higher gas cost), or maintain an additional per-address validUntil timestamp alongside the cached bool and require block.timestamp < validUntil[address] in addition to the cached flag. At minimum, the two views must never return different answers for the same state; consider removing the cheaper cached view entirely if the live-recompute cost is acceptable to callers, since a cheap-but-wrong view is worse than no view.

Finding 2 — attestations(uint256) returns the raw stored status byte without live expiry evaluation

Severity: Medium
Function: attestations(uint256 id) (selector 0x01daf26b, entry 0x169e)

Root cause

This getter unpacks and returns the stored struct fields verbatim, including the status byte ((slot4[id] word1 >> 0xa8) & 0xff), without comparing the also-returned expiry field against block.timestamp. A caller reading .status == 1 (Active) sees "Active" for an attestation whose expiry has already passed but which has not yet been pruned — the same underlying staleness as Finding 1, surfaced through a different getter.

Proof

000016bf: KECCAK256                        ; base = keccak256(id, 4)
000016c7: SLOAD; AND (1<<160)-1            ; field: subject address (base, low 160 bits)
000016ce: PUSH1 0x01; ADD; SLOAD
000016d3: PUSH1 0xa8; SHR; AND (0xff)      ; field: status byte -- RETURNED RAW, no TIMESTAMP check
000016df: PUSH1 0x03; ADD; SLOAD           ; field: expiry (uint256) -- present in return tuple

No TIMESTAMP opcode appears anywhere in the function body (0x169e–0x172f).

Impact

Lower severity than Finding 1 because the raw expiry field IS included in the return tuple, so a careful integrator can compute block.timestamp < expiry themselves. The defect is that the status field alone is not self-consistent with a live check, which is an easy trap for an integrator who reasonably assumes an enum field reflects current truth.

Recommendation

Either compute and return an effective status (return Expired when block.timestamp >= expiry regardless of the stored byte), or add an explicit derived bool isExpired to the return tuple so integrators are not required to independently know to cross-check expiry themselves.

Finding 3 — Compliant-address counter inherits the same staleness as Finding 1

Severity: Medium
Functions: 0xc20404fd (entry 0x0317, returns slot 3 alone) and 0xa2ff542e (entry 0x041e, returns (slot1, slot2, slot3) tuple)

Root cause

Storage slot 3 is a running count of "addresses currently marked compliant" (i.e., #{a : slot7[a] == true}) — it is incremented inside issueAttestation exactly when slot7[subject] transitions false→true, and decremented inside the prune/revoke recompute path exactly when it transitions true→false. The accounting logic itself is internally consistent and correctly guarded against under/overflow (verified — see "Reviewed, no defect found" below), but because it is driven by the same stale slot7 cache as Finding 1, it necessarily overstates the true number of currently-valid, non-expired attestations by however many have expired-but-not-pruned at query time.

Proof

00000432: PUSH1 0x01; SLOAD        ; slot1 (attestation id counter)
00000435: PUSH1 0x02; SLOAD        ; slot2 (auditor count)
00000438: PUSH1 0x03; SLOAD        ; slot3 (compliant-address count)
...RETURN (slot1, slot2, slot3) tuple

Increment site (issue, false→true transition only): 0x0988–0x0996. Decrement site (prune/revoke recompute, true→false transition only, underflow-guarded via helper 0x1b5a): 0x1bc9–0x1bd3.

Impact

An integrator using this counter as "how many agents are currently compliant" will see an inflated number for the same reason isCompliant() is wrong — expired-but-unpruned attestations are still counted. This is a secondary symptom, not an independent bug in the counting logic itself.

Recommendation

Fixed automatically once Finding 1's root cause (the eventual-consistency of slot7) is addressed — no separate counter fix is needed if isCompliant()/slot7 becomes live-accurate (e.g., via a keeper that reliably prunes on schedule, or a redesign that removes the cache).

Finding 4 — Identity registry address is an immutable with no setter (single point of failure)

Severity: Low
Functions: identityRegistry() (selector 0x134e18f4, entry 0x1659); consumed inside issueAttestation (0x853c79cd)

Root cause

The constructor takes one address parameter (an external identity-registry contract), zero-address-checked ("ComplianceRegistry: zero identity address"), and bakes it into the runtime bytecode as a compile-time immutable (PUSH32 at offsets 0x0598/0x166e). No function in the contract writes this value — there is no setter. Every issueAttestation call performs a STATICCALL to this fixed address (selector 0xfb3551ff, subject as argument) and reverts ("agent not registered") if it returns false or malformed data.

Proof

00001659: JUMPDEST                          ; identityRegistry() body
0000166e: PUSH32 0xa7bd20bf5de63df949ca5be2f20835978ecba81a...
                                             ; hardcoded address, masked to 160 bits, RETURN

Full grep of all 42 SSTORE sites in the contract confirms none target this value — it is exclusively a PUSH32 constant, never a storage slot.

Impact

If the external identity-registry contract is ever destroyed, redeployed at a different address, or begins reverting/returning malformed data, all future issueAttestation calls are permanently bricked with no on-chain recovery path (existing attestations and all view functions are unaffected, since only issuance calls out to it). This is an availability risk, not a fund-loss or forgery risk.

Recommendation

Consider an owner-gated setter (with an event) for the identity registry address, or explicitly document and off-chain-verify that the target address (0xa7bd20bf5de63df949ca5be2f20835978ecba81a) is a non-destructible, permanent registry before relying on this contract for production issuance.

Finding 5 — Ownership transfer is single-step with no acceptOwnership handshake

Severity: Low
Function: transferOwnership(address) (selector 0xf2fde38b, entry 0x00f8)

Root cause

transferOwnership is owner-gated and zero-address-checked ("ComplianceRegistry: zero owner"), but directly overwrites storage slot 0 with the supplied address in one step — there is no pendingOwner/acceptOwnership two-phase handshake.

Proof

00000119: CALLER; EQ; JUMP 0x1a67    ; require(msg.sender == owner)
00000135: ISZERO; JUMPI 0x0149       ; require(newOwner != 0)
00000147: SSTORE                     ; slot0 = newOwner  (only owner-slot write in the whole contract)

Impact

A mistyped-but-valid non-zero address permanently and irrecoverably transfers away the ability to manage the auditor allowlist (add/revoke auditors) and to transfer ownership again. Zero-address is already guarded, limiting this to a fat-finger/wrong-address risk rather than a bricking-to-nobody risk.

Recommendation

Adopt the standard 2-step ownership transfer pattern (OpenZeppelin Ownable2Step): store the proposed owner, require them to explicitly acceptOwnership() before the transfer takes effect.

Finding 6 — Revoked auditor's role/metadata string is not cleared (informational)

Severity: Info — no security impact
Function: revokeAuditor(address) (selector 0xb402980b, entry 0x0335)

Root cause

Revocation clears only the low byte (the active flag) of the auditor's packed struct at storage slot 6: slot6[addr] = current & ~0xff. The role/metadata string and other packed fields remain in storage.

Proof

00000394: PUSH1 0xff; NOT           ; mask = ~0xff
00000395: DUP2; SLOAD; AND; SSTORE  ; clear only the active-flag byte

Every access-control check that matters (issueAttestation's and revokeAttestation's auditor gate) reads the same low byte (slot6[caller] & 0xff), so a revoked auditor cannot issue or revoke attestations regardless of the leftover string — this has no security impact.

Recommendation

None required for security. Optionally zero the full struct on revoke for data hygiene if any off-chain indexer reads the role string without also checking the active byte.

Finding 7 — Single owner key is the root of trust for the entire auditor allowlist (centralization, by design)

Severity: Info — by-design trust-model note
Functions: addAuditor, revokeAuditor, transferOwnership, and transitively issueAttestation

Description

addAuditor(address,bytes) and revokeAuditor(address) are both strictly require(msg.sender == owner) (single EOA/contract in storage slot 0). Because auditor status is a prerequisite to issuing any attestation, compromise of the owner key would let an attacker add themselves as an auditor and issue arbitrary attestations. This is a standard centralization/trust-anchor property, not a contract defect — flagged because it is the mechanism underlying the client's stated "auditor allowlist manipulation" concern, and is the only way that concern could ever materialize (see next section for proof that no non-owner bypass exists).

Recommendation

Consider a multisig or timelock as the owner address rather than a single EOA, given the sensitivity of the auditor allowlist.

Reviewed, no defect found

The following areas were specifically hunted for exploitable bugs per the client's stated concerns and the standard bytecode-audit checklist. Each was proven safe from opcodes, with the proof trail summarized:

  • Auditor-allowlist bypass on issuance (client's primary stated concern). issueAttestation (0x853c79cd) unconditionally checks slot6[msg.sender] & 0xff != 0 (revert "caller is not an authorized auditor") before any state write — confirmed at offset 0x556, with no code path that skips this check. revokeAttestation (0x1ea1f074) has the same gate plus an additional (issuer == caller) OR (owner == caller) check. Neither addAuditor nor revokeAuditor can be called by a non-owner (require(msg.sender == owner) at 0x10ab/0x35d). No non-owner path to become or forge an auditor exists.
  • Ownership hijack. Storage slot 0 (owner) is written by exactly one instruction in the entire contract (0x147 SSTORE), inside owner-gated transferOwnership. evmole's initial heuristic flagged revokeAttestation as also writing slot 0; manual decoding showed this is a read (an owner-fallback comparison for the revoke-authorization check), not a write — no hijack path exists.
  • Flag-forgery via storage collision (client's second stated concern). All 42 SSTORE sites were enumerated; every one targets either a hardcoded scalar slot (0–3) or keccak256(key, C) with a hardcoded mapping-base constant (4, 5, 6, or 7). No slot number is derived from user calldata without a keccak256 step, no two mappings share a base constant, and grinding an id/address collision between two distinct mapping regions is a ~2^128 birthday-bound search — infeasible. No arbitrary-storage-write or cross-mapping-collision primitive exists.
  • slot7 (cached compliance bool) forgery via crafted calldata. Every write path derives the target address either from the auditor-gated issueAttestation's own subject parameter (authorized by design) or from the stored struct's subject field inside the prune/revoke recompute subroutine (0x1b67) — never from unvalidated calldata passed to that subroutine. The recompute subroutine also correctly re-scans an address's entire attestation list before flipping the cached bool, so pruning/revoking one expired attestation does not incorrectly clear compliance for an address that still holds another valid one.
  • Packed-array bounds / off-by-one. The per-address attestation-id array (slot5[address], a plain uint256[], confirmed one full storage word per element — the SHL/SHR-by-zero pattern initially flagged as possible sub-slot packing resolved to a genuine no-op) has a correctly-enforced bounds check (Panic(0x32) on out-of-range index) on every read path, and a length cap (Panic(0x41) beyond 2^64) on the write path.
  • Reentrancy / unsafe external calls. The entire contract contains exactly one external call in total — a single STATICCALL to the immutable identity registry inside issueAttestation. STATICCALL cannot mutate state, so no callback-based reentrancy is possible; the return value's success flag, size, and decoded boolean are all explicitly validated before use. No CALL, DELEGATECALL, CALLCODE, CREATE/CREATE2, or SELFDESTRUCT exists anywhere in the bytecode.
  • Integer overflow/underflow. Every counter increment (attestation-id counter, auditor count, compliant-address count, array length) and decrement routes through shared checked-arithmetic helpers that revert with Panic(0x11) on overflow/underflow. Expiry computation (block.timestamp + duration) is explicitly guarded against wraparound, and duration is independently bounded to [30 days, 730 days] by the issuance function, so expiry can never land in the past or overflow.
  • Constructor validation. The single constructor parameter (identity registry address) is zero-address-checked and reverts with a descriptive message if omitted; owner is set to msg.sender with no gap.
