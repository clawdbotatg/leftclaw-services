Findings

[90] 1. Stake-time-only solvency check has no unstake-time mirror — post-stake token behavior change turns withdrawal into a first-come-first-served race that permanently strands losers

CgStaking.unstake · Confidence: 90 · [both phases — 9 of 12 phase-2 agents converged independently; phase-1 erc20 + general domains raised it separately]

Description
stake() verifies solvency only at the instant of its own transfer (token.balanceOf(this) - balanceBefore != amount at L89-91); unstake() (L107-122) never re-derives that guarantee before paying out the static Position.amount at L119, so any token-side balance change that isn't itself a stake/unstake transfer (rebase, admin-toggled fee, elastic-supply contraction) can silently drop the real balance below Σ position.amount — the NatSpec's claim that "accounting can never drift from the actual balance" (L18-20) holds only for that one instant, never for the interval between stake and unstake.

Proof of Concept
Alice stakes 1,000 tokens at t=0; Bob stakes 1,000 at t=1 — both pass the L89-91 check exactly (contract balance 2,000 == Σ amount). At t=15 days the token undergoes a balance-affecting event outside any transfer this contract initiates (e.g. a negative rebase), cutting the real balance to 1,000 while both Position.amount fields remain 1,000 each (static storage, immune to the token's own mechanics). Both positions mature. Alice calls unstake() first: contract has 1,000 ≥ 1,000, safeTransfer (L119) succeeds, balance → 0. Bob calls unstake(): needs 1,000, contract holds 0 — safeTransfer reverts, and because position.amount = 0 (L118) executes before the transfer within the same transaction, the revert rolls back that write too — Bob's position remains a valid-looking, forever-unpayable claim with no partial withdrawal, sweep, or rescue path anywhere in the contract to recover it. Who is stranded depends on transaction order at the moment insolvency occurs, not on stake order.

Rated High rather than Critical because it requires a precondition (the immutable token, chosen once by the deployer, must exhibit balance-affecting behavior outside ordinary transfers) rather than firing unconditionally — but that precondition is a plausible, in-scope class of token behavior for any contract that custodies an arbitrary ERC20, not a contrived edge case, and no attacker privilege is needed to trigger or benefit from it.

Fix

     function unstake(uint256 positionId) external nonReentrant {
         Position[] storage owned = positions[msg.sender];
         if (positionId >= owned.length) revert UnknownPosition(positionId);
         Position storage position = owned[positionId];

         uint256 amount = position.amount;
         if (amount == 0) revert PositionAlreadyUnstaked(positionId);
         if (block.timestamp < position.unlockAt) {
             revert PositionStillLocked(positionId, position.unlockAt);
         }

         position.amount = 0;
-        token.safeTransfer(msg.sender, amount);
+        uint256 available = token.balanceOf(address(this));
+        if (available < amount) revert UnsupportedTokenBehavior();
+        token.safeTransfer(msg.sender, amount);

         emit Unstaked(msg.sender, positionId, amount);
     }

This converts a silent FIFO race into a clean, predictable revert — it does not by itself make an already-insolvent pool whole (there is nothing to pay a stranded staker with once the shortfall exists). The only complete fix is either restricting deployment to tokens verified never to alter this contract's balance outside of stake/unstake transfers, or moving to pro-rata share accounting (payout = position.amount * token.balanceOf(this) / totalRecordedLiability) so a shortfall is borne proportionally rather than by transaction order. Recommend also softening the NatSpec's absolute claim (L18-20) to state the guarantee is stake-time-only.

[85] 2. No sweep/rescue path for tokens sent directly to the contract

CgStaking (contract-wide) · Confidence: 85 · [both phases]

Description
Any token sent directly to the contract (bypassing stake()) becomes permanently unrecoverable — there is no owner, admin, or sweep function anywhere in the 143-line source. This contradicts the literal "hold exactly what was staked" wording (L16-17) since real balance can end up strictly greater than Σ position.amount with no reconciliation path. Not exploitable for profit (no partial withdrawal exists to siphon surplus) — it only harms whoever mis-sends tokens, and is a disclosed consequence of the contract's stated "no admin, ever" design.

Fix

Accept as documented design tradeoff (consistent with the stated minimalism), or correct the docstring from "exactly" to "at least" what was staked. If recovery is desired, scope any sweep function strictly to non-tracked surplus, never touching live Position.amount principal — this would reintroduce admin surface the design deliberately avoids, so weigh carefully against the "no admin" goal.

[80] 3. Unbounded maxLockSeconds at construction — no upper bound, can self-DoS extreme-duration stakes

CgStaking.constructor / CgStaking.stake · Confidence: 80 · [both phases]

Description
The constructor (L59-70) validates only minLockSeconds_ > 0 and minLockSeconds_ <= maxLockSeconds_ — no upper bound on maxLockSeconds_. If set near type(uint64).max, a staker choosing lockSeconds near that ceiling causes the checked uint64 addition at L93 (uint64(block.timestamp) + lockSeconds) to revert with a generic arithmetic panic rather than a custom error. Self-scoped (only that caller's own transaction reverts), no fund loss, entirely a one-time deployer discretion rather than a runtime privilege.

Fix

     constructor(IERC20 token_, uint64 minLockSeconds_, uint64 maxLockSeconds_) {
         if (
             address(token_) == address(0) ||
             minLockSeconds_ == 0 ||
-            minLockSeconds_ > maxLockSeconds_
+            minLockSeconds_ > maxLockSeconds_ ||
+            maxLockSeconds_ > 100 * 365 days
         ) {
             revert InvalidConstruction();
         }

[80] 4. Unbounded per-owner positions array — self-scoped gas griefing on positionsOf()

CgStaking.stake / CgStaking.positionsOf · Confidence: 80 · [phase-1 only]

Description
No cap exists on how many positions a single address may create (L94-101, append-only push). positionsOf(owner) (L125-127) copies the full array to memory in one call, whose cost grows with array length. Confirmed no other function iterates this array — stake/unstake remain O(1) regardless of length, and each address can only ever grow its own array; effect is strictly self-scoped (reaching a gas-prohibitive length requires on the order of 100,000+ transactions from the same address, far beyond any plausible griefing incentive).

Fix

Optional: document the unbounded-growth behavior, or add a paginated getter (positionsOf(owner, offset, limit)) alongside the full-array one for integrators/UIs that may call it on-chain.

[75] 5. Token-issuer-side blacklist/pause can permanently strand matured funds with no recovery path

CgStaking.unstake · Confidence: 75 · [both phases]

Description
If the token issuer (a third party, not the CgStaking deployer) blacklists the contract's own address or globally pauses the token, every stake()/unstake() reverts for all users for as long as the block/pause lasts, with no admin override (by design). If only an individual staker's own address is blacklisted, only that staker's matured position is stranded — unstake() hardcodes msg.sender as the sole payout recipient (L119) with no alternate-recipient path. Requires the deployer's one-time choice of a censorship-capable token and third-party issuer action; no CgStaking-level attacker privilege is involved.

Fix

Document the risk if a censorship-capable token is expected as token; no code fix is compatible with the contract's explicit "no admin, ever" design goal beyond accepting this as a disclosed risk of arbitrary-token custody.

Informational (below reporting threshold for a fix, recorded for completeness)

  • stakedAt sentinel documented but never checked on-chain ([both phases]) — the struct comment (L27) claims 0 marks "a never-created position," but existence is decided purely by array bounds and amount != 0; no branch reads stakedAt. Dead, harmless, but potentially misleading to a maintainer or the offchain indexer.
  • uint64(block.timestamp) narrowing cast is unchecked but structurally unreachable ([both phases], 5 of 12 phase-2 agents independently raised and independently dismissed this) — would only matter ~584 billion years from the Unix epoch. Optional: SafeCast.toUint64.
  • Balance-delta subtraction reverts with a generic Panic instead of the custom error on a negative-delta token ([phase-1 only]) — cosmetic; still reverts safely either way under Solidity 0.8 checked arithmetic.
  • Fee-on-transfer enabled after stake (but before unstake) shorts only that unstaker, not the pool ([phase-1 only]) — distinct from Finding 1: the shortfall here is borne only by the affected unstaker (fee deducted from their own payout), not by other stakers.
  • Offchain "Spark" reward-formula gaming — checked whether onchain events can be fabricated to mislead the offchain indexer; confirmed not exploitable (emitted amount only follows a verified real transfer, timestamps derive from block.timestamp not user input, positions remain genuinely illiquid until real time reaches unlockAt). The reward formula itself is out of scope (offchain, not provided).
  • pragma solidity 0.8.28 emits PUSH0 by default — confirm the target deployment chain supports it, or pin an explicit evmVersion.
  • Access control, reentrancy, and boundary arithmetic — every one of the 18 sub-agents across both phases that touched these independently confirmed no cross-owner access path, no reentrancy bypass (shared nonReentrant lock across both mutators, textbook CEI in unstake), and no off-by-one in any boundary comparison.
