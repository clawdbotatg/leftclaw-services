Findings

[1] vestedLiquidity is never reset across re-lock cycles — a second lockUp() after a full vest permanently strands principal

Severity: High · Confidence: 100 · Origin: [both] — 12/12 phase-2 agents + 3/6 phase-1 agents (general, precision-math, access-control)

ContractName.function: LiquidityVesting._vest (root cause reachable via LiquidityVesting.lockUp/_mintPosition)

Description: lockUp() is gated only by require(!isLocked, "Already locked") (LiquidityVesting.sol:172), and the contract's own state machine is explicitly designed to allow re-use: _vest()'s final branch resets isLocked = false and tokenId = 0 (LiquidityVesting.sol:260-261) specifically so a fresh lockUp() cycle can begin. When a new cycle mints, _mintPosition() refreshes tokenId, initialLiquidity, and lockStart (LiquidityVesting.sol:196-198) — but vestedLiquidity has no reset site anywhere in the contract. It is written exactly once, as an accumulator: vestedLiquidity += toLiquidate; (LiquidityVesting.sol:244).

On a second cycle, _vest() computes:

uint128 totalVestedLiq = uint128(vestedPct * uint256(initialLiquidity) / 1e18);  // L240, capped by the NEW initialLiquidity
uint128 toLiquidate = totalVestedLiq - vestedLiquidity;                          // L241, vestedLiquidity is STALE from the old cycle
  • If the new cycle's initialLiquidity is ≤ the prior cycle's final vestedLiquidity (fully plausible — a second, smaller top-up round): totalVestedLiq can never reach vestedLiquidity, so the subtraction underflows a uint128 under Solidity 0.8's checked arithmetic and reverts on every single call, forever. vest()/claimAndVest() become permanently uncallable for that cycle; burn() (LiquidityVesting.sol:259) is never reached; isLocked never clears again; sweep() explicitly refuses to touch token0/token1 while isLocked (LiquidityVesting.sol:273-276). The entire second-cycle principal is permanently stranded in the Uniswap V3 position.
  • If the new cycle's initialLiquidity exceeds the stale vestedLiquidity: early vest() calls still silently under-decrease the position relative to what should have vested (the stale offset "pre-credits" progress), and when the tracker reaches isFinal (vestedLiquidity >= initialLiquidity, LiquidityVesting.sol:245), burn(tokenId) (LiquidityVesting.sol:259) is called while the position's real on-chain liquidity is still non-zero — Uniswap's NonfungiblePositionManager.burn() requires exactly zero remaining liquidity and reverts, rolling back the whole final _vest() call (including the decreaseLiquidity/collect that already ran). Every retry reproduces the identical revert.

Proof of Concept:

  1. Owner calls lockUp() (cycle 1), position mints with initialLiquidity = 1,000,000.
  2. Owner vests to completion: at full elapsed time, vestedPct = 1e18, totalVestedLiq = 1,000,000, toLiquidate = 1,000,000, vestedLiquidity becomes 1,000,000, isFinal triggers burn(tokenId), isLocked = false, tokenId = 0. vestedLiquidity remains 1,000,000 in storage.
  3. Owner calls lockUp() again (cycle 2, permitted since isLocked == false), minting a new position with initialLiquidity = 500,000 (independent of cycle 1 — depends on new deposit amounts/price/tick range).
  4. Owner calls vest() at any point in cycle 2, even after the entire new vestDuration elapses: totalVestedLiq maxes out at 500,000, so toLiquidate = 500,000 - 1,000,000 underflows and reverts (Panic 0x11) — on every call, for the entire lifetime of cycle 2. The 500,000 liquidity units (real WETH/CLAWD principal) can never be decreased, collected as principal, or burned — only claim()'s fee-only path still functions.

Why this is not "self-harm" / an out-of-scope admin action: the harm follows from using an explicitly supported, documented flow (re-locking after a completed vest) in the ordinary, non-malicious way the code's own guard (!isLocked, not a stronger one-time-use flag) invites. It is a genuine code defect in a supported lifecycle transition, not off-label misuse.

Recommendation:

     function _mintPosition(uint256 amount0Desired, uint256 amount1Desired, int24 _tickLower, int24 _tickUpper, uint256 amount0Min, uint256 amount1Min) internal {
         (uint256 _tokenId, uint128 liquidity, uint256 used0, uint256 used1) = positionManager.mint(
             ...
         );

         tokenId = _tokenId;
         initialLiquidity = liquidity;
+        vestedLiquidity = 0;
         lockStart = block.timestamp;

[2] Permissionless third-party increaseLiquidity() on the shared Uniswap V3 position can permanently block the final burn(), freezing the last vesting tranche

Severity: Critical · Confidence: 90 · Origin: [both] — 1 phase-1 agent (defi-amm) + 2 phase-2 agents (invariant, flow-gap)

ContractName.function: LiquidityVesting._vest

Description: Uniswap V3's NonfungiblePositionManager.increaseLiquidity() has no ownership/authorization check — unlike decreaseLiquidity, collect, and burn (all gated by isAuthorizedForToken in the canonical periphery contract), any external address can add liquidity to any existing tokenId, including the one held by this contract, simply by supplying token0/token1 themselves. _vest()'s vesting math (LiquidityVesting.sol:240-241) is computed purely from this contract's own initialLiquidity/vestedLiquidity counters — it never reconciles against the position's actual live liquidity via positionManager.positions(tokenId). On the final tranche, decreaseLiquidity(toLiquidate) (LiquidityVesting.sol:247-250) only removes the internally-tracked remainder; if a third party has injected any extra liquidity, the position still holds a non-zero balance, and the subsequent unconditional burn(tokenId) (LiquidityVesting.sol:259) reverts (Uniswap's burn() requires exactly zero liquidity and zero owed tokens). This reverts the entire _vest() transaction — no try/catch exists — and every retry recomputes the identical toLiquidate and hits the identical revert, permanently.

Proof of Concept:

  1. Owner locks via lockUp(); position tokenId mints with liquidity L.
  2. At any point before the final vest call, an unrelated attacker calls positionManager.increaseLiquidity({tokenId: <this contract's tokenId>, amount0Desired: dust, amount1Desired: dust, amount0Min: 0, amount1Min: 0, deadline: block.timestamp}) directly on the Uniswap V3 NonfungiblePositionManager — no interaction with LiquidityVesting itself is required, and the attacker's cost is a dust amount of token0/token1.
  3. At full vest, owner calls vest()/claimAndVest(): decreaseLiquidity removes exactly the internally-tracked L, collect() zeroes owed tokens, but burn(tokenId) reverts because the position still holds the attacker-injected dust liquidity.
  4. The transaction reverts; vestedLiquidity's update rolls back; every future call recomputes the same final toLiquidate and hits the same revert. isLocked never clears; sweep() cannot release token0/token1. The final tranche of principal is permanently frozen.

Recommendation: Before calling burn() in the isFinal branch, read live liquidity via positionManager.positions(tokenId) and decrease by the position's actual full remaining liquidity (not just the internally-computed remainder), so burn()'s zero-liquidity precondition is always satisfiable regardless of externally-injected liquidity:

         if (isFinal) {
+            (,,,,,,, uint128 liveLiquidity,,,,) = positionManager.positions(tokenId);
+            if (liveLiquidity > 0) {
+                positionManager.decreaseLiquidity(INonfungiblePositionManager.DecreaseLiquidityParams({
+                    tokenId: tokenId, liquidity: liveLiquidity,
+                    amount0Min: 0, amount1Min: 0, deadline: block.timestamp
+                }));
+                positionManager.collect(INonfungiblePositionManager.CollectParams({
+                    tokenId: tokenId, recipient: owner(),
+                    amount0Max: type(uint128).max, amount1Max: type(uint128).max
+                }));
+            }
             positionManager.burn(tokenId);
             isLocked = false;
             tokenId = 0;
         }

[3] One-step ownership transfer (not Ownable2Step) with renounceOwnership() disabled and no recovery path

Severity: High · Confidence: 90 · Origin: [phase1: access-control]

ContractName.function: LiquidityVesting (inherited transferOwnership), LiquidityVesting.renounceOwnership

Description: Every fund-moving function (lockUp, claim, vest, claimAndVest, sweep) is onlyOwner-gated. The contract inherits plain OpenZeppelin Ownable, not Ownable2Step — transferOwnership(address) is a single atomic call with no acceptance step from the new address. renounceOwnership() is overridden to unconditionally revert (LiquidityVesting.sol:209-211), so the only way to ever change control is this one-shot transfer. A mistyped address, a contract that cannot call these functions, or a lost key permanently locks all custodied funds — potentially a multi-year vesting position plus accrued fees — with no recovery mechanism.

Proof of Concept: Owner locks a large position via lockUp() with a long vestDuration. Owner calls transferOwnership(newOwner) with a typo'd or inaccessible address. owner() is now permanently that address; no one can ever again call claim/vest/claimAndVest/sweep. renounceOwnership() cannot help — total, irreversible loss of custodied funds.

Recommendation: Inherit Ownable2Step and route transfers through transferOwnership() → acceptOwnership().

[4] No handling for fee-on-transfer / non-standard ERC20 behavior in lockUp()/_mintPosition()

Severity: Medium · Confidence: 80 · Origin: [phase1: erc20, general, defi-amm] — 3 agents

ContractName.function: LiquidityVesting.lockUp, LiquidityVesting._mintPosition

Description: lockUp() pulls amount0Desired/amount1Desired via safeTransferFrom (LiquidityVesting.sol:177-178) without measuring actual balance received, then approves and mints using the desired amounts (LiquidityVesting.sol:179-194); the refund logic (LiquidityVesting.sol:203-204) computes amountDesired - used against the nominal desired amount, not real leftover balance. If token0/token1 charges a transfer fee or rebases, the contract can hold strictly less than amountDesired after the pull, which can cause mint()'s internal pull to revert, or the refund transfer to attempt sending more than the contract's real balance (reverting). Worst case is a permanent DoS of lockUp() for such a token pair (immutable, no redeploy path) — not direct fund theft.

Proof of Concept: A 2%-fee token as token1: contract receives desired*0.98; if mint()'s internally-used amount exceeds that reduced balance, minting reverts, or the refund math at L204 attempts to send more than available and reverts — lockUp() becomes permanently unusable for that token pair.

Recommendation: Measure actual balance deltas (balanceOf before/after safeTransferFrom) and use the measured amount for approval, mint()'s amountDesired, and the refund calculation.

[5] Owner-endorsed zero-slippage default (amount0Min/amount1Min = 0) plus no TWAP check enables sandwich attacks on lockUp()/vest()

Severity: Medium · Confidence: 75 · Origin: [phase1: defi-amm], [phase2: economic-security, invariant — lead-level]

ContractName.function: LiquidityVesting.lockUp/_mintPosition, LiquidityVesting._vest

Description: The only price-manipulation protection on mint() (LiquidityVesting.sol:186-194) and decreaseLiquidity() (LiquidityVesting.sol:247-250) is the owner-supplied amount{0,1}Min. No TWAP/calm-period check exists. The contract's own NatSpec explicitly documents 0 as a supported value (amount0Min Minimum token0 accepted (0 to skip), LiquidityVesting.sol:169), sanctioning zero-slippage as normal usage. Since these are public mempool transactions, a searcher can front-run a lockUp()/vest() call with a price-skewing swap, let the mint/decrease execute unprotected, then back-run to extract the difference.

Proof of Concept: Owner submits lockUp(..., amount0Min: 0, amount1Min: 0) per the docstring's suggested usage. Attacker front-runs with a large swap skewing pool price; the mint executes at the skewed ratio with no floor; attacker back-runs to restore price and profits from the mispriced deposit.

Recommendation: Compute amount{0,1}Min off-chain immediately before submission from a TWAP or manipulation-resistant reference; consider rejecting amount0Min==0 && amount1Min==0 outright.

[6] Deny-listed/paused owner address blocks all collect()-routed proceeds (recoverable only via ownership transfer)

Severity: Medium · Confidence: 75 · Origin: [phase1: erc20]

ContractName.function: LiquidityVesting.claim, LiquidityVesting._vest

Description: Both claim() (LiquidityVesting.sol:215-218) and _vest() (LiquidityVesting.sol:253-256) hardcode recipient: owner() in their collect() calls, bypassing this contract's own token-handling entirely. If either token supports a USDC/USDT-style deny-list or pause and the current owner() becomes deny-listed, the transfer inside collect() reverts, making claim()/vest()/claimAndVest() uncallable until ownership changes.

Proof of Concept: Owner address added to a hypothetical token deny-list post-lock; vest() runs decreaseLiquidity successfully (updating vestedLiquidity), then collect()'s internal transfer to the deny-listed owner reverts, reverting the whole call — repeated until ownership moves or the deny-list entry is removed.

Recommendation: Consider allowing claim/vest to accept an explicit (onlyOwner-gated) recipient parameter rather than requiring a full ownership transfer as the only remedy.

[7] previewVest() hardcodes a chain-specific Uniswap V3 factory address

Severity: Low · Confidence: 95 (independently verified on-chain) · Origin: [both] — near-unanimous across both phases

ContractName.function: LiquidityVesting.previewVest

Description: Unlike positionManager/token0/token1/fee (constructor-supplied immutables), the factory address at LiquidityVesting.sol:309 — IUniswapV3Factory(0x33128a8fC17869897dcE68Ed026d694621f6FDfD) — is a hardcoded literal. This audit independently verified via cast against live Base-mainnet state that this address is in fact the genuine, functioning Uniswap V3 factory on Base (24,535 bytes of contract code; getPool(WETH, USDC, 500) returns a valid non-zero pool address) — it is correct for a Base deployment, contradicting one phase-2 agent's claim that it is a code-less EOA (that specific claim is rejected; likely a wrong-chain lookup on the agent's part). The remaining, valid concern is portability: if this contract is ever deployed to a chain other than Base, getPool() will resolve to an unrelated or nonexistent contract, breaking the preview. Confined entirely to the view-only path — never touches the value-moving lockUp/vest/claim flow.

Proof of Concept: Deploy to any non-Base chain; previewVest()/previewClaimAndVest() revert or return incorrect amount0/amount1.

Recommendation: Pass the factory address as an immutable constructor parameter, consistent with the existing pattern for positionManager.

[8] deadline: block.timestamp provides no real expiration protection

Severity: Low · Confidence: 90 · Origin: [phase1: defi-amm], [phase2: several agents — lead-level]

ContractName.function: LiquidityVesting._mintPosition, LiquidityVesting._vest

Description: Both mint() (LiquidityVesting.sol:192) and decreaseLiquidity() (LiquidityVesting.sol:249) set deadline: block.timestamp, which is evaluated at execution time and therefore always "passes" regardless of how long a signed transaction was held before inclusion — providing no protection against delayed inclusion timed for price dislocation (compounds finding [5]).

Recommendation: Accept an explicit deadline parameter from the owner reflecting an actual tolerable time window.

[9] vestDuration has no minimum bound and cannot be corrected once set

Severity: Low · Confidence: 85 · Origin: [phase1: general, access-control]

ContractName.function: LiquidityVesting.lockUp

Description: require(_vestDuration > 0, ...) (LiquidityVesting.sol:173) is the only bound — _vestDuration = 1 is accepted, making the "vesting" guarantee cosmetic (full principal withdrawable a block later). Conversely an accidentally huge value cannot be corrected — no setter exists, and sweep() cannot release token0/token1 while locked.

Recommendation: Enforce a sane minimum vestDuration if a genuine commitment device is intended.

[10] forceApprove(..., 0) reset after mint can revert for tokens that reject zero-value approvals

Severity: Low · Confidence: 70 · Origin: [phase1: erc20]

ContractName.function: LiquidityVesting._mintPosition

Description: LiquidityVesting.sol:200-201 unconditionally resets NFPM allowance to 0 via forceApprove. Some tokens (documented BNB/BEP-20-style behavior) revert on zero-value approvals; forceApprove's fallback would propagate such a revert, breaking lockUp() after tokens were already pulled from the owner in the same transaction.

Recommendation: Wrap the post-mint approval reset in a try/catch, or only reset when non-zero.

[11] sweep()'s token-identity guard uses exact address match, bypassable for tokens with multiple valid addresses

Severity: Low · Confidence: 60 · Origin: [phase1: erc20]

ContractName.function: LiquidityVesting.sweep

Description: The "cannot sweep locked tokens" guard (LiquidityVesting.sol:273-276) compares by exact address. A token with proxy/alias addresses referencing the same balance could let the owner bypass the guard for stray balances sitting directly in the contract (not the position's committed liquidity, which is governed separately).

Recommendation: If aliasing is a concern for the actual token pair, prefer an allowlist of expected strandable tokens over a denylist of token0/token1.

[12] No emergency pause / fund-recovery mechanism beyond restrictively-guarded sweep()

Severity: Low · Confidence: 80 · Origin: [phase1: access-control]

ContractName.function: whole-contract

Description: No pause mechanism and no break-glass recovery path exist. If the contract enters a bad state (findings [1] or [2], or an unexpected NFPM revert), there is no secondary mitigation short of funds being permanently stuck.

Recommendation: Consider an owner-only emergency function that can call decreaseLiquidity/collect/burn directly against the held tokenId, independent of the vestedLiquidity bookkeeping.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed to Finding-level confidence. Not scored.

  • vest() always collects fees via the shared collect() call regardless of includeFees, but only emits Claimed when includeFees=true — LiquidityVesting._vest — Code smells: LiquidityVesting.sol:253-256 always uses amount{0,1}Max = type(uint128).max; the event-emission branch at LiquidityVesting.sol:264-267 is the only place includeFees has any effect — Off-chain consumers summing Claimed events to track fee totals will undercount whenever plain vest() is used instead of claimAndVest(). Not a fund-safety issue (owner still receives full value), but an observability gap worth confirming against any downstream integration.
  • previewVest()'s same-block spot-price read could feed a manipulated value into vest()'s slippage parameters if any off-chain integration derives amountMin from the preview in the same transaction/block — LiquidityVesting.previewVest — Code smells: LiquidityVesting.sol:309-319 reads slot0() with no TWAP. No such integration exists in this repo's scope, so this is unverified rather than a concrete finding.
  • Small initialLiquidity relative to vestDuration could collapse linear vesting into a one-shot cliff — LiquidityVesting._vest / vestedPercent — Code smells: uint128(vestedPct * uint256(initialLiquidity) / 1e18) (LiquidityVesting.sol:240) floors every call; for very small initialLiquidity, every vest() reverts "Nothing to vest" until elapsed >= vestDuration, at which point the entire position unlocks at once. Overlaps with ordinary rounding-dust behavior; only matters for pathologically small mints, not verified against realistic deployment liquidity magnitudes.
