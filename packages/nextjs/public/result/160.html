Smart Contract Security Audit — Final Report

Job ID: 160
Target: MultisigFactory.sol + Multisig.sol — EIP-1167 Multisig Factory & Implementation
Repository: https://github.com/clawdbotatg/slop-computer-wallet/tree/main/packages/foundry/contracts/
Auditor: leftclaw.services automated audit agent
Date: 2026-05-11
Methodologies: EthSkills (6 domain skills) + Pashov (8-agent)

Executive Summary

This audit covers a two-contract system: MultisigFactory deploys Multisig EIP-1167 clones via CREATE2, and Multisig is a self-governed M-of-N wallet supporting EOA (secp256k1) and passkey (secp256r1 / WebAuthn) signers.

Two Medium severity vulnerabilities were found:

  1. A salt front-running attack in the factory that allows a third party to seize the victim's pre-funded multisig address and steal pre-deposited ETH.
  2. An input validation inconsistency in the initialize function that can register a permanently un-signable passkey, bricking the multisig if the threshold cannot otherwise be met.

Three Low severity findings and one Info finding were also identified. No Critical or High vulnerabilities were found.

The core cryptographic logic (nonce-based replay protection, sorted-signer deduplication, WebAuthn verification delegation, ERC-1271 compliance, self-governance via onlySelf) is sound.

Findings

[M-1] Salt Front-Running in createMultisig Enables Pre-Funded ETH Theft

Severity: Medium
Confidence: 90
Contracts: MultisigFactory.sol
Location: createMultisig() line 40; getMultisigAddress() line 47
Confirmed by: EthSkills (evm-audit-general), Pashov (agents 1 + 4)

Description: createMultisig passes the caller-supplied salt directly to Clones.cloneDeterministic. The resulting CREATE2 address is deterministic given only (factory_address, salt, initCodeHash) — all public. Since getMultisigAddress(salt) is provided for pre-computing the clone address before deployment, users are encouraged to pre-fund the predicted address (e.g., to provision a wallet before the creation transaction is mined, or to configure an external system to expect the multisig at that address). This creates a front-running window.

// MultisigFactory.sol line 40 — salt is user-controlled, no msg.sender binding
multisig = Clones.cloneDeterministic(implementation, salt);

Proof of Concept:

  1. Alice calls getMultisigAddress(S) → predicted address P
  2. Alice sends 5 ETH to P
  3. Alice broadcasts createMultisig([Alice, Bob], [], [], [], 2, S)
  4. Bob sees Alice's tx in mempool, front-runs with createMultisig([Bob], [], [], [], 1, S)
  5. Bob's tx mines first; multisig at P has threshold=1, sole signer=Bob
  6. Alice's tx reverts with CloneCreationFailed() (address occupied)
  7. Bob calls execTransaction(Bob_addr, 5 ether, "", deadline, [Bob_sig]) — drains 5 ETH

Alice loses 5 ETH. Attack cost: one createMultisig transaction plus gas.

Recommendation:

function createMultisig(
    address[] calldata eoaSigners,
    bytes32[] calldata passkeyQxs,
    bytes32[] calldata passkeyQys,
    bytes32[] calldata credentialIdHashes,
    uint256 threshold,
    bytes32 salt
) external returns (address multisig) {
    bytes32 effectiveSalt = keccak256(abi.encode(msg.sender, salt));
    multisig = Clones.cloneDeterministic(implementation, effectiveSalt);
    Multisig(payable(multisig)).initialize(eoaSigners, passkeyQxs, passkeyQys, credentialIdHashes, threshold);
    emit MultisigCreated(multisig, salt, eoaSigners, threshold);
}

function getMultisigAddress(address account, bytes32 salt) external view returns (address) {
    return Clones.predictDeterministicAddress(
        implementation,
        keccak256(abi.encode(account, salt)),
        address(this)
    );
}

[M-2] Zero-Coordinate Passkey Accepted in initialize Can Permanently Brick Multisig

Severity: Medium
Confidence: 80
Contract: Multisig.sol
Location: initialize() lines 111–113 vs addPasskeySigner() line 162
Confirmed by: EthSkills (evm-audit-signatures), Pashov (agents 1 + 6)

Description: addPasskeySigner (post-deployment signer add) correctly rejects zero coordinates:

// Multisig.sol line 162
if (qx == bytes32(0) || qy == bytes32(0)) revert InvalidSigner();

initialize (deployment-time signer add) has no equivalent check:

// Multisig.sol lines 111–113
for (uint256 i = 0; i < passkeyQxs.length; i++) {
    address pkAddr = getPasskeyAddress(passkeyQxs[i], passkeyQys[i]);
    _addSigner(pkAddr, passkeyQxs[i], passkeyQys[i], credentialIdHashes[i]);  // no zero check
}

A passkey registered with qx == bytes32(0) is stored as { exists: true, qx: 0, qy: y }. The type-detection helper isPasskey(addr) = signerInfo[addr].qx != bytes32(0) returns false for this signer. Signature verification then fails both code paths in _verifySignatures:

  • EOA path: if (info.qx != bytes32(0)) revert SignerTypeMismatch() — passes (qx=0 matches EOA). ECDSA recovery of WebAuthn-encoded data against the passkey-derived address fails → InvalidSignature.
  • Passkey path: if (info.qx == bytes32(0)) revert SignerTypeMismatch() — reverts immediately.

This signer can never produce a valid signature. If the counted signer cannot be replaced or removed (because threshold requires this signer's participation), the multisig is permanently unable to execute transactions.

Proof of Concept:

  1. Call createMultisig([alice], [bytes32(0)], [real_qy], [credId], 2, salt)
    • Passes initialize validation: total = 1+1 = 2, threshold = 2 → valid
    • Passkey with qx=0 registered — locked out permanently
  2. Alice (EOA) can provide only 1 valid signature; threshold requires 2
  3. Every execTransaction call reverts with ThresholdNotMet
  4. removeSigner requires onlySelf → requires execTransaction → stuck
  5. Multisig holds funds but can never move them

Real-world trigger: UI bug sending qx/qy in wrong byte order, or encoding error in credential registration.

Recommendation:

for (uint256 i = 0; i < passkeyQxs.length; i++) {
    if (passkeyQxs[i] == bytes32(0) || passkeyQys[i] == bytes32(0)) revert InvalidSigner();
    address pkAddr = getPasskeyAddress(passkeyQxs[i], passkeyQys[i]);
    _addSigner(pkAddr, passkeyQxs[i], passkeyQys[i], credentialIdHashes[i]);
}

[L-1] Stale credentialIdToAddress Mapping After Signer Removal

Severity: Low
Confidence: 85
Contract: Multisig.sol
Location: removeSigner() lines 167–181
Confirmed by: EthSkills, Pashov (agent 6 invariant check)

Description: removeSigner deletes the signerInfo entry but does not clear the credentialIdToAddress reverse mapping used for login lookups:

function removeSigner(address signer) external onlySelf {
    ...
    delete signerInfo[signer];                    // ← cleared
    // credentialIdToAddress[credId] is NOT cleared
    ...
}

After removal, getPasskeyByCredentialId(credId) returns the removed signer's address with zeroed qx/qy (because signerInfo was deleted). A wallet or WebAuthn login UI using this lookup will attempt to construct signatures for an address that is no longer a valid signer, producing failed transactions and confusing UX.

Security impact is limited to the view-only getPasskeyByCredentialId function — actual signature verification uses signerInfo[sig.signer].exists, not the reverse mapping.

Recommendation: Store credentialIdHash inside SignerInfo and clear the mapping on removal:

struct SignerInfo {
    bool exists;
    bytes32 qx;
    bytes32 qy;
    bytes32 credentialIdHash;  // add this
}

// In removeSigner:
SignerInfo memory info = signerInfo[signer];
if (!info.exists) revert NotSigner();
if (info.credentialIdHash != bytes32(0)) {
    delete credentialIdToAddress[info.credentialIdHash];
}
delete signerInfo[signer];

[L-2] No Code Existence Validation for _implementation in Constructor

Severity: Low
Confidence: 75
Contract: MultisigFactory.sol
Location: constructor() line 19
Confirmed by: EthSkills (evm-audit-proxies), Pashov (agent 7 — cross-contract echo from Clones.sol Job 159 L-1)

Description: The factory constructor stores _implementation as immutable without verifying it has deployed bytecode:

constructor(address _implementation) {
    implementation = _implementation;  // no extcodesize check
}

Since implementation is immutable, an incorrect deployment (e.g., _implementation = address(0) or an EOA) cannot be corrected — a new factory must be deployed and all integrators must migrate.

All clones created by a misconfigured factory would silently succeed on all calls while doing nothing (EVM behavior for DELEGATECALL to codeless address, as documented in Clones.sol audit finding L-1).

Recommendation:

error InvalidImplementation();

constructor(address _implementation) {
    if (_implementation.code.length == 0) revert InvalidImplementation();
    implementation = _implementation;
}

[L-3] Nonce Incremented Before Batch Loop Enables Out-of-Order Execution via Malicious Target

Severity: Low
Confidence: 65
Contract: Multisig.sol
Location: execBatchTransaction() lines 250–260
Confirmed by: EthSkills (evm-audit-general), Pashov (agents 3 + 8)

Description: execBatchTransaction increments the nonce before executing the batch loop:

_verifySignatures(hash, signatures);
nonce++;                                     // ← N+1 before any calls execute
for (uint256 i = 0; i < calls.length; i++) {
    (bool ok, bytes memory ret) = calls[i].target.call{ value: calls[i].value }(calls[i].data);

A malicious target at position i in the batch can call execTransaction or execBatchTransaction with signatures for nonce = N+1 during its execution. This causes a pre-prepared nonce-N+1 transaction to execute between calls i and i+1 of the original batch, reordering intended execution sequences.

Requirement: This requires threshold signers to have already pre-authorized a transaction for nonce N+1. This limits the attack to scenarios where threshold signers are partially malicious or colluding. Pure external attackers cannot trigger this without valid threshold signatures.

Recommendation: Add nonReentrant to execBatchTransaction if strict intra-batch execution ordering is required. Note this prevents batches that include calls to execTransaction on the same multisig (self-referential batches).

[I-1] Deadline Check Is Inclusive — Transaction Valid at Exactly deadline Timestamp

Severity: Info
Contract: Multisig.sol
Location: execTransaction() line 228; execBatchTransaction() line 248

Description: Both execution functions use strict greater-than for deadline checking:

if (block.timestamp > deadline) revert ExpiredSignature();

This permits execution when block.timestamp == deadline (the deadline block). Signers setting deadline = block.timestamp will be surprised that their transaction can still execute in that block. Convention in most protocols uses >= to make the deadline exclusive.

Recommendation: Change to if (block.timestamp >= deadline) for an exclusive deadline, or document the inclusive behavior in NatSpec so signers can account for it when choosing deadline values.

Not Raised

  • Re-initialization: initializer modifier from OZ Initializable correctly blocks this. ✓
  • Implementation takeover: _disableInitializers() in Multisig constructor correctly prevents direct initialization of the implementation contract. ✓
  • Signature replay across chains: getExecHash and getBatchExecHash both include block.chainid. ✓
  • Duplicate signer submission: Sorted-ascending sig.signer check (if (sig.signer <= prev) revert SignersUnsorted()) enforces uniqueness. ✓
  • Passkey address collision with EOA: _addSigner checks signerInfo[signer].exists → AlreadySigner() for any collision. ✓
  • ERC-1271 replay: isValidSignature accepts arbitrary hash; execTransaction hashes include nonce. No cross-context replay possible without intentional signer cooperation. ✓
  • Atomicity of batch: Revert propagation via _bubbleRevert ensures all-or-nothing batch execution and nonce rollback. ✓
