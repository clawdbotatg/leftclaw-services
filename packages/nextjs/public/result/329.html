Security Audit Report — RiderBattleEscrowV2.sol

Client engagement: leftclaw.services job #329
Target: RiderBattleEscrowV2.sol — Bankr CryptoRider non-custodial 1v1 wager escrow, deployed at 0x55c2847003A9e254b8312bf3C75520e06528aBa6 on Base mainnet (verified via Sourcify)
Methodology: Two-phase audit — Phase 1 breadth (5 ethskills domain checklists, model=sonnet) → Phase 2 depth (12 pashov attacker-mindset agents, blind to phase 1, model=sonnet) → hybrid reconciliation
Scope: single file, ~217 in-scope LOC (small scope)

The contract's own header comment states: "NOT AUDITED. Get a security review before holding meaningful funds." This report identifies a Critical vulnerability that confirms that warning was warranted — the contract's current deposit-crediting mechanism allows outright theft of user funds with no special privileges required.

Reconciliation Summary

Completeness: 20 unique findings across both phases, all 20 covered below.

Overlap: 4 findings independently corroborated by both phases · Phase-1-only: 13 · Phase-2-only: 3 · Re-examined phase-unique leads kept: 16, demoted: 0.

The headline Critical finding (C-1) was independently identified by all 5 of 5 phase-1 checklist agents that touched deposit accounting and all 12 of 12 phase-2 attacker agents — the most unanimous convergence possible for this audit's methodology. Every single analytical lens applied to this contract (breadth checklist and adversarial reasoning alike) arrived at the same conclusion independently: the contract's deposit-crediting design is fundamentally broken.

Findings

[C-1] Deposits are credited from an unauthenticated, shared per-token pool — any address can front-run and steal another user's in-flight deposit

Severity: Critical
Origin: [both] — phase1: general, access-control, erc20 (3 checklists independently flagged this) · phase2: unanimous — all 12 of 12 attacker agents flagged this as the primary finding, several with a dual-sided pot-drain escalation
Location: _received() L95-97, createMatch() L103-112, joinMatch() L115-126

Description: accounted[token] is a single global counter per token, and _received(token) = balanceOf(this) - accounted[token] is a shared, fungible "unaccounted" pool with no notion of which address transferred which tokens. createMatch() and joinMatch() never verify that msg.sender is the address that performed the preceding ERC20 transfer() — they only check that some unaccounted balance of the right token/amount exists anywhere in the contract, then credit whichever address calls first. The contract's own header comments explicitly confirm non-atomic 2-step deposits (a separate transfer() transaction followed by a separate createMatch/joinMatch transaction) are a normal, expected flow for wallets that don't support EIP-5792 atomic batching — meaning the vulnerable window is a designed part of ordinary contract usage, not a contrived edge case. Both accounted(token) and balanceOf are public/derivable, so an attacker needs no mempool access — polling on-chain state after each block is sufficient to find and claim any pending deposit.

Proof of Concept:

  1. Alice, using a non-batching wallet (any standard MetaMask/hardware wallet EOA), sends token.transfer(escrow, 1000e6) (step 1 of the documented 2-step flow), intending to follow with createMatch(1, token, 1000e6).
  2. Before Alice's second transaction lands, an attacker (with zero prior token balance) submits createMatch(999, token, 1000e6). _received(token) >= 1000e6 passes using Alice's already-transferred tokens; accounted[token] += 1000e6; the attacker is recorded as creator of match 999, funded entirely by Alice's money.
  3. Alice's own createMatch(1, token, 1000e6) now reverts ("deposit first") — her funds are already consumed with no recovery path; she is neither creator nor opponent of any match.
  4. The attacker waits out acceptWindow (24h default, owner-configurable down to a 1-hour minimum) and calls cancelUnaccepted(999), which pays the full m.wager to m.creator — the attacker receives Alice's 1000 tokens for the cost of two gas-only transactions.
  5. Escalation (identified independently by multiple phase-2 agents): the identical mechanism applies to joinMatch() on any Open match. An attacker can front-run both the creator's deposit (via createMatch) and the intended opponent's deposit (via joinMatch) for the same match, becoming both parties. The attacker then either recovers both sides via the permissionless refundStalled() (no settler cooperation needed, only a 12-hour settleWindow wait) or gambles on settle() — draining the entire pot regardless of who the settler declares the winner, since the attacker controls both addresses.
  6. Pool-drain variant (no specific victim needed): an attacker can simply poll balanceOf(escrow) - accounted[token] at any time and claim any positive delta — this reflects the sum of every abandoned/in-flight 2-step deposit across all users of the platform, plus any dust, letting an attacker repeatedly call createMatch with fresh IDs to drain the entire unaccounted pool, not just a single victim's deposit.

Recommendation: Bind credited deposits to their depositor instead of relying on a shared pool diffed against accounted. Preferred approach — a deposit() step that snapshots the caller's own contribution atomically:

mapping(address => mapping(address => uint256)) public pendingDeposit;

function deposit(address token) external nonReentrant {
    uint256 amt = _received(token);
    require(amt > 0, "nothing received");
    pendingDeposit[msg.sender][token] += amt;
    accounted[token] += amt;
}

and have createMatch/joinMatch debit pendingDeposit[msg.sender][token] instead of consuming the global _received() directly. This still supports EIP-5792 atomic batching ([transfer(escrow, wager), deposit(token), createMatch(...)] in one bundle) while eliminating the unattributed window entirely. Alternative: revert to a safeTransferFrom-based pull inside createMatch/joinMatch (with a same-batch approve), which closes the gap just as effectively and requires less new state.

[H-1] sweepUnaccounted() lets the owner seize deposits that are legitimately mid-flight, not just abandoned ones

Severity: High
Origin: [both] — phase1: access-control, general (2 checklists) · phase2: 3 agents (access-control, economic-security, boundary) as a lead, same root cause as C-1
Location: sweepUnaccounted() L211-216

Description: sweepUnaccounted transfers balanceOf(token) - accounted[token] to any owner-chosen address, with no minimum age or grace period. Because the contract's normal flow requires a window where deposited-but-not-yet-registered funds sit as "unaccounted" (the same root design flaw as C-1), an owner — or a natural, non-malicious "recover dust" automation job — can sweep a user's in-flight deposit seconds after they send it, before their follow-up createMatch/joinMatch call lands, with no adversarial intent required.

Proof of Concept: Alice transfers 100e6 tokens (step 1 of a 2-step deposit). Before her createMatch transaction is mined, the owner (or an automated sweep job) calls sweepUnaccounted(token, treasury). Alice's subsequent createMatch call reverts with "deposit first", and she has no recovery path.

Recommendation: Require unaccounted balances to age past a grace period before they're sweepable, or — better — adopt the C-1 fix, which eliminates unattributed floating balances (and this function's ambiguity) entirely.

[H-2] Owner can install a self-controlled settler and participate in matches, enabling guaranteed-win self-dealing

Severity: High
Origin: [phase1 only] — access-control checklist. Re-examined: confirmed — setSettler() has no restriction preventing settler == creator/opponent, and no restriction bars the owner from calling createMatch/joinMatch themselves.
Location: setSettler() L195-198, settle() L130-148

Description: settler is a single plain address changeable instantly by the owner, with no timelock and no check preventing it from equaling a match creator/opponent. The owner can set settler to a key they control, participate in matches themselves, and sign settle() messages naming themselves as winner every time, since winner is only constrained to be m.creator or m.opponent — both of which the owner can freely become.

Proof of Concept: Owner calls setSettler(ownerControlledKey). Owner (from a different EOA) creates a match and deposits. A victim joins and deposits, unaware settler is owner-controlled. Owner signs settle(id, ownerAddr, sig) with the settler key it controls, taking the full pot minus fee.

Recommendation: Add a timelock/delay on setSettler changes; restrict settler from ever equaling an outstanding match's creator/opponent; and/or require settler to be a separate governance-controlled multisig distinct from owner.

[H-3] Rebasing / fee-on-transfer tokens desync accounted[token] from real balance, permanently bricking the token and stranding funded matches

Severity: High
Origin: [both] — phase1: erc20, general (2 checklists) · phase2: 6 of 12 agents flagged this as a lead
Location: _received() L95-97, settle() L145-146, cancelUnaccepted() L158, refundStalled() L169-170, sweepUnaccounted() L213

Description: accounted[token] is a nominal ledger never re-synced with balanceOf. If an allowlisted token can reduce the contract's balance without a corresponding transfer call (negative rebase, elastic-supply, reflection/burn-on-holding), or takes a fee from the sender on top of the specified transfer amount, balanceOf(this) can drop below accounted[token]. _received() performs unchecked uint256 subtraction, causing a permanent underflow revert that bricks createMatch/joinMatch/sweepUnaccounted for that token. Worse, settle()/refundStalled()/cancelUnaccepted() don't call _received() but still safeTransfer the originally recorded amounts — if real balance has shrunk below what's owed, the outgoing transfer itself reverts with no partial-payout or pull-based fallback, permanently stranding funded matches. The owner allowlists tokens directly (setTokenAllowed) and is not assumed to be a security expert, making misconfiguration realistic.

Proof of Concept: Owner allowlists a token that rebases negatively for all holders. After a negative rebase, balanceOf(escrow) < accounted[token]. The next createMatch/joinMatch/sweepUnaccounted call for that token reverts with underflow. Any Funded match whose wager*2 now exceeds the real balance can never be settled or refunded — funds frozen indefinitely.

Recommendation: Document/enforce that only standard, non-rebasing, non-fee-on-transfer tokens should be allowlisted. Defensively, guard _received() with saturating subtraction, measure actual balance deltas around outgoing transfers rather than trusting nominal amounts, and add a pull-based/partial-recovery path so a shortfall in one token doesn't permanently strand unrelated funds.

[H-4] Blocklist/deny-list tokens: a single blacklisted recipient permanently freezes escrowed funds with no fallback

Severity: High
Origin: [phase1 only] — erc20 checklist. Re-examined: confirmed at L145-147 (settle) and L169-170 (refundStalled) — both perform unconditional pushes with no try/catch.
Location: settle() L145-147, refundStalled() L169-170

Description: settle() unconditionally safeTransfers to treasury and winner; refundStalled() unconditionally safeTransfers to both m.creator and m.opponent. For deny-list tokens (USDC, USDT-class — plausible for a platform owner to allowlist), if any one recipient is blacklisted, the entire call reverts with no pull-based fallback. A blacklisted treasury bricks settle() for every match in that token; a blacklisted participant bricks both settle() and refundStalled() for that specific match, permanently trapping both parties' stakes.

Proof of Concept: Owner allowlists USDC. Match funded by Alice and Bob. Bob's address is later added to USDC's blacklist (unrelated regulatory action). settle() reverts whenever the payout touches Bob's address; refundStalled() also reverts since it must pay both parties. Alice's stake is now permanently trapped alongside Bob's.

Recommendation: Move to a pull/claim pattern — credit a claimable[user][token] mapping inside settle/refundStalled/cancelUnaccepted, with a separate withdraw() function, so one blocked address never blocks another user's payout.

[M-1] Fee rate is not locked at deposit time — owner can retroactively raise it up to the 10% cap on an already-funded match

Severity: Medium
Origin: [both] — phase1: access-control · phase2: dedicated Finding 2 (confidence 85) with concrete PoC numbers
Location: settle() L142 (feeBps(m.token) read live), setDefaultFee()/setTokenFee() L176-189

Description: The fee percentage used in settle() is read live from current storage rather than snapshotted into the Match struct at creation/funding time. The owner can call setTokenFee/setDefaultFee at any time (bounded only by the 10% cap, no timelock). A player who joined expecting a low or zero fee can have up to 10% silently applied by settlement time, diverting extra value to treasury.

Proof of Concept: Match funded at 0% fee. Owner front-runs the pending settle() call with setTokenFee(token, 1000) (10% cap). settle() now computes fee at 10% instead of 0% — the winner receives 10% less than expected when they deposited, with the difference diverted to treasury.

Recommendation: Snapshot feeBps(token) into the Match struct at joinMatch time (when the match becomes Funded) and use that stored value in settle().

[M-2] setWindows() has no upper bound and applies retroactively to already-open/funded matches

Severity: Medium
Origin: [phase2 only] — 3 of 12 agents (numerical-gap-hunter, trust-gap-hunter, flow-gap-hunter). Re-examined: confirmed — setWindows() (L203-207) enforces only a 1-hour floor with no ceiling, and cancelUnaccepted/refundStalled read the live global acceptWindow/settleWindow against a per-match timestamp rather than a value snapshotted at match creation/funding.
Location: setWindows() L203-207, cancelUnaccepted() L154, refundStalled() L165

Description: Because window values aren't snapshotted per match, an owner can instantly lengthen either window (no maximum enforced) after a match is already Open/Funded, retroactively freezing that match's timeout-based exit path indefinitely — funds already escrowed lose their "eventual refund" guarantee with no grandfathering. Conversely, shortening a window mid-flight lets a losing participant race refundStalled() ahead of a legitimate settle() to escape a loss and reclaim their wager instead of forfeiting it to the winner.

Recommendation: Snapshot the applicable window into the Match struct at creation/funding time, and/or enforce a sane upper bound in setWindows().

[L-1] Settlement fee rounds down, silently reducing to zero for small pots

Severity: Low
Origin: [phase1 only] — precision-math checklist
Location: settle() L141-147

Description: fee = (pot * feeBps(m.token)) / 10_000 truncates toward zero, with the remainder always flowing to the winner. For sufficiently small pot/feeBps combinations, fee computes to exactly 0 regardless of configured rate — dust-level but systematic, and can be forced to zero deliberately by choosing a small wager.

Recommendation: If the fee should never be fully avoidable, round up (Math.mulDiv(..., Rounding.Ceil)); otherwise document the dust-to-zero behavior as intended.

[L-2] Settlement signatures never expire and cannot be individually revoked

Severity: Low
Origin: [phase1 only] — signatures checklist
Location: settle() L130-148

Description: The signed digest has no deadline/nonce beyond matchId. Once settler signs an outcome for a Funded match, that signature remains valid and submittable by anyone indefinitely until the match leaves Funded status. There is no way to void a single erroneous/outdated signature short of rotating the entire settler key.

Recommendation: Add a deadline parameter to the signed digest, and/or an explicit mechanism to invalidate a specific signature without a full key rotation.

[L-3] Signed digest omits wager/token — latent risk if match-immutability assumptions ever change

Severity: Low
Origin: [phase1 only] — signatures checklist
Location: settle() L135-138 vs. createMatch() L103-112

Description: The digest binds only (chainid, address(this), matchId, winner), not m.wager/m.token. Not currently exploitable, since those fields are set once and never mutated, and matchId cannot be reused. However, any future code change permitting match re-parameterization would silently reintroduce a classic "unsigned parameter used in payout" vulnerability.

Recommendation: Include wager/token (or a hash of the full Match struct) in the signed digest for defense-in-depth.

[L-4] setSettler() swap can invalidate an in-flight favorable signature, denying a specific winner's payout

Severity: Low
Origin: [phase2 only] — trust-gap-hunter agent. Re-examined: confirmed — settle() (L138) checks the signature against the current settler storage value with no grace window for a signature already issued by a previous settler.
Location: setSettler() L195-198, settle() L130-148

Description: An owner can front-run a pending, already-issued favorable settler signature with setSettler(newAddr), permanently invalidating that signature. This forces the match toward refundStalled() once settleWindow elapses, which returns each side only their own wager — denying the rightful winner their winnings without directly stealing principal. Distinct from H-2 (self-dealing for profit); this is a targeted denial-of-winnings griefing vector.

Recommendation: Snapshot the applicable settler address into the Match struct at joinMatch time and validate against that stored value in settle(), rather than the live settler storage slot.

[L-5] Single-step Ownable ownership transfer

Severity: Low
Origin: [phase1 only] — access-control checklist
Location: contract declaration L37, inherited transferOwnership

Description: Vanilla OZ Ownable, not Ownable2Step. A mistyped or unreachable address passed to transferOwnership permanently locks out all onlyOwner functions, including sweepUnaccounted (future abandoned deposits become permanently unrecoverable) and setSettler (a compromised settler could never be rotated again). Core user flows are unaffected.

Recommendation: Use Ownable2Step.

[L-6] renounceOwnership() left enabled with no override

Severity: Low
Origin: [phase1 only] — access-control checklist
Location: inherited Ownable.renounceOwnership()

Description: If ever called (accidentally or via a compromised key), owner becomes address(0) permanently, disabling setSettler, setTokenAllowed, and sweepUnaccounted forever. Existing matches can still resolve via settle/cancelUnaccepted/refundStalled.

Recommendation: Override renounceOwnership() to revert.

[L-7] Multiple-address (proxy-aliased) tokens can double-credit the same underlying balance

Severity: Low
Origin: [phase1 only] — erc20 checklist
Location: allowedToken mapping L45, accounted mapping L53

Description: allowedToken/accounted are keyed purely by contract address. If a token exists at multiple addresses aliasing the same underlying balance (proxy/impl migration pattern) and the owner allowlists both, _received() for each alias reads from the same real balanceOf, letting a single real deposit be credited to two different matches.

Recommendation: Document that only the single canonical address of a token should be allowlisted.

[L-8] matchId griefing via unowned namespace

Severity: Low
Origin: [phase2 only] — asymmetry agent. Re-examined: confirmed — createMatch() (L106) only checks matches[matchId].status == Status.None, with no per-creator namespacing.
Location: createMatch() L103-112

Description: matchId is caller-chosen with no contract-enforced namespacing. An attacker holding even 1 wei of unaccounted balance of some allowed token can front-run a victim's intended createMatch(id, ...) call with their own createMatch(id, someToken, 1) to occupy that id, causing the victim's real call to revert ("exists"). Low-cost inconvenience only — the victim's funds remain safely unaccounted and reusable under a different id, so impact is limited to griefing/wasted gas rather than fund loss.

Recommendation: Consider namespacing matchId by creator (e.g. a mapping keyed by (creator, nonce)) to remove the shared global id-space as a griefing surface.

Informational

  • Plain eth_sign-style digest instead of EIP-712 typed data [phase1 only] — replay-safety is unaffected (chainid + contract address are manually included), but a blind-signing risk if settler is ever a human-in-the-loop signer rather than an automated backend.
  • settle() is callable by any address, not just match participants [phase1 only] — intentional per design; payout always goes to the pre-validated winner regardless of caller, so not exploitable for fund diversion; only a benign front-running/gas-griefing race between whoever submits first.
  • No emergency pause mechanism [phase1 only] — assessed as low practical impact: settle() already restricts payout to match participants, and setTokenAllowed(false) already stops new matches for an affected token during an incident; a pause on settle/refund would be counterproductive (traps escrowed funds).
  • Emitted settlement amounts may not reflect actual fee-on-transfer receipts [phase1 only] — MatchSettled logs nominal transfer amounts; off-chain indexers may show inflated payout figures for fee-on-transfer tokens.
  • Verified non-issue: setTokenAllowed(token, false) on a token with active/funded matches does not break refunds or settlement [phase1 only] — only createMatch() checks allowedToken; joinMatch, settle, cancelUnaccepted, refundStalled do not, so de-allowlisting only blocks new matches.

Methodology Note

This report reconciles two independently-run analysis passes against the same source: a 5-agent breadth pass walking domain-specific checklists (general, precision-math, erc20, access-control, signatures), and a 12-agent depth pass using adversarial/attacker-mindset reasoning, run blind to the first pass's output. The Critical finding (C-1) achieved the strongest possible corroboration this methodology can produce — independently rediscovered by every agent across both phases that examined the deposit-crediting logic, from checklist-driven review, Socratic questioning, inversion-based attacker reasoning, invariant analysis, and boundary/asymmetry lenses alike. This is not analytical noise; it is a structural defect in the contract's core accounting model, directly enabled by a usage pattern (non-atomic 2-step deposits) the contract's own comments acknowledge as expected and supported.

Given the Critical severity and live deployment on Base mainnet, we recommend the contract owner pause new deposits (via setTokenAllowed(token, false) for all currently-allowed tokens) immediately upon receipt of this report, until the C-1 fix is deployed. The contract's own header comment ("NOT AUDITED. Get a security review before holding meaningful funds.") suggests the deployer was already aware this contract had not received a security review prior to this audit.
