[97] 1. Unauthenticated shared deposit pool — anyone can steal another user's in-flight deposit

RiderBattleEscrow.createMatch / .joinMatch · Confidence: 97 · [both — phase1: general/access-control/erc20 (3 agents); phase2: 12/12 agents]

Description
Deposits are plain token.transfer() calls made by the user directly to the contract, decoupled from the registration call. Crediting logic checks only a global per-token surplus — _received(token) = balanceOf(this) - accounted[token] — with zero attribution to which address actually transferred the tokens. The contract's own header comments acknowledge the two-step (non-atomic) deposit flow is expected for non-EIP-5792 wallets ("an abandoned 2-step deposit on a non-batch wallet"), making the vulnerable window a documented, common-case occurrence.

function _received(address token) internal view returns (uint256) {
    return IERC20(token).balanceOf(address(this)) - accounted[token];
}
function createMatch(uint256 matchId, address token, uint256 wager) external nonReentrant {
    require(allowedToken[token], "token not allowed");
    require(wager > 0, "wager=0");
    require(matches[matchId].status == Status.None, "exists");
    require(_received(token) >= wager, "deposit first");   // <-- no msg.sender binding
    accounted[token] += wager;
    matches[matchId] = Match(msg.sender, address(0), token, wager, uint64(block.timestamp), 0, Status.Open);

Proof of Concept (verified against source, gate-checked: no guard interrupts the path, reachable via the contract's own documented non-atomic deposit flow, unprivileged actor triggers profitably, material loss to an identifiable victim → CONFIRMED)

  1. Alice sends token.transfer(escrow, 100) (tx1), intending to follow with createMatch(1, token, 100) (tx2).
  2. tx1 confirms → _received(token) = 100.
  3. Before Alice's tx2 lands, Mallory submits createMatch(999, token, 100) with zero tokens of her own. _received(token) >= 100 passes using Alice's deposit; accounted[token] += 100; match 999 opens with Mallory as creator.
  4. Alice's tx2 now reverts (_received == 0) — her funds are inside Mallory's match with no recourse (she is not m.creator of 999).
  5. After acceptWindow (24h default), Mallory calls cancelUnaccepted(999), which refunds m.wager to msg.sender == m.creator — Mallory receives Alice's entire deposit for the cost of two gas transactions. The identical race applies to joinMatch, letting an attacker hijack an intended opponent's deposit.

Fix

+ mapping(address => mapping(address => uint256)) public pendingDeposit; // depositor => token => amount
+
+ function deposit(address token, uint256 amount) external nonReentrant {
+     uint256 before = IERC20(token).balanceOf(address(this));
+     // caller must have transferred `amount` immediately prior in the same batch
+     require(IERC20(token).balanceOf(address(this)) - before + _received(token) >= amount, "deposit not seen");
+     pendingDeposit[msg.sender][token] += amount;
+ }

  function createMatch(uint256 matchId, address token, uint256 wager) external nonReentrant {
      require(allowedToken[token], "token not allowed");
      require(wager > 0, "wager=0");
      require(matches[matchId].status == Status.None, "exists");
-     require(_received(token) >= wager, "deposit first");
+     require(pendingDeposit[msg.sender][token] >= wager, "deposit first");
+     pendingDeposit[msg.sender][token] -= wager;
      accounted[token] += wager;

The core requirement is binding deposit credit to the depositor's own address — via a per-depositor ledger populated by a sender-scoped call, or by reverting to atomic transferFrom/permit — instead of a contract-wide balance-diff pool. Apply the identical fix to joinMatch.

[85] 2. settle() and permissionless refundStalled() are simultaneously callable once settleWindow elapses — losing party can race to force a refund instead of a legitimate settlement

RiderBattleEscrow.settle / .refundStalled · Confidence: 85 · [phase2 only — agent 11; independently re-verified against source in reconciliation]

Description
Neither function checks whether the other is pending or already executed beyond the shared Status.Funded guard. settle() has no upper time bound at all; refundStalled() only requires block.timestamp >= fundedAt + settleWindow (default 12h) and is fully permissionless. Once the window elapses, a party who expects to lose can front-run the settler's incoming settle() transaction with refundStalled(), flipping status to Refunded before settle() lands (which then reverts with "not funded") — the losing party recovers their full wager instead of forfeiting it, and the rightful winner is deprived of pot - fee.

Gate check: no guard interrupts the race (confirmed by re-reading both functions — settle() at lines 130-148 has zero time-window check); reachable through normal usage (settler delay beyond the default 12h window, or an owner-shrunk window per Finding 6, is a plausible operational condition, not a contrived edge case); unprivileged actor (the losing player) triggers profitably; material loss to an identifiable victim (the winner) → CONFIRMED, rated High rather than Critical since it requires the specific condition of settleWindow having elapsed before settle() is mined.

Proof of Concept: Match funded, wager 1000 USDC each side, fundedAt = t0. Off-chain the game resolves with Player A losing; the settler prepares settle(id, B, sig). At t0 + settleWindow + 1s, Player A submits refundStalled(id) with higher gas; it mines first, m.status = Refunded, both players receive their own 1000 USDC back. The settler's pending settle transaction then reverts ("not funded"). Player B (rightful winner) is deprived of pot - fee = 1900 USDC and instead receives only their own 1000 USDC.

Fix

  function settle(uint256 matchId, address winner, bytes calldata sig) external nonReentrant {
      Match storage m = matches[matchId];
      require(m.status == Status.Funded, "not funded");
+     require(block.timestamp < m.fundedAt + settleWindow, "past settle window");
      require(winner == m.creator || winner == m.opponent, "bad winner");

(Alternative: gate refundStalled behind an explicit "abandoned" flag settable only by settler/owner, rather than a bare timestamp check, so a party cannot unilaterally out-race a pending legitimate settlement.)

[80] 3. Blacklist-capable tokens (USDC-style) can permanently lock both parties' funds

RiderBattleEscrow.settle / .refundStalled · Confidence: 80 · [both — phase1: erc20-2; phase2: agent 3]

Description
Both payout functions push tokens unconditionally to both/either fixed participant address in the same transaction as the state transition. If either address is later blacklisted by the token issuer, the safeTransfer reverts, rolling back the entire call (including the status change) — settle() can never succeed for that match, and refundStalled() (which must pay both parties) also reverts once reachable, permanently stranding both players' funds with no pull-payment fallback and no admin override.

Gate check: no guard interrupts (confirmed); reachable through common token behavior (deny-lists are explicitly plausible for contracts accepting arbitrary allowlisted tokens per standard audit convention); harm is not attacker-triggered but results in material, permanent loss of fund access to identifiable victims (both match participants, including the innocent counterparty) → CONFIRMED, High.

Proof of Concept: Match funded with USDC, Alice=creator, Bob=opponent, 100 each. Bob's address is added to USDC's blacklist before settlement (a real, independent on-chain mechanism). Any settle() call that would pay Bob reverts; once settleWindow elapses, refundStalled() also reverts (must pay both creator and opponent). Both Alice's and Bob's combined 200 USDC are permanently stuck.

Fix

- if (fee > 0) IERC20(m.token).safeTransfer(treasury, fee);
- IERC20(m.token).safeTransfer(winner, pot - fee);
+ if (fee > 0) withdrawable[treasury][m.token] += fee;
+ withdrawable[winner][m.token] += (pot - fee);

Switch to a pull-payment pattern — credit an internal withdrawable[user][token] balance in settle/cancelUnaccepted/refundStalled, with a separate withdraw() entrypoint — so one blacklisted/reverting recipient cannot block the other party's legitimate withdrawal.

[78] 4. Rebasing / balance-decreasing tokens break the accounted <= balanceOf invariant → permanent DoS / fund lock

RiderBattleEscrow._received / settle / cancelUnaccepted / refundStalled / sweepUnaccounted · Confidence: 78 · [both — phase1: general-2/erc20-3; phase2: agents 1, 3, 6, 9 leads promoted per multi-agent convergence]

Description
accounted[token] never re-syncs with balanceOf. setTokenAllowed places no restriction on token type. For a token whose balance can decrease independent of an outgoing transfer (negative rebase, slashing, admin burn), balanceOf(this) can drop below accounted[token], causing _received()'s unchecked subtraction to underflow and revert under Solidity 0.8, permanently blocking createMatch/joinMatch/sweepUnaccounted for that token. Separately, settle()/cancelUnaccepted()/refundStalled() attempt safeTransfer of the full nominal accounted amounts, which can exceed the token's now-lower actual balance, reverting and permanently stranding both players' funds.

Gate check: reachable through common token behavior (rebasing tokens are explicitly plausible for contracts accepting arbitrary allowlisted tokens); this is a code-level missing-floor-check defect, not an admin-triggered harm — the DoS fires automatically once a rebase occurs, no privileged trigger required → CONFIRMED, promoted from LEAD via multi-agent convergence (4 phase-2 agents + 2 phase-1 agents), High.

Proof of Concept: Owner allowlists rebasing token R. Two matches funded, accounted[R] = 400, contract holds 400 R. Negative rebase drops actual balance to 380 R. Any createMatch/joinMatch/sweepUnaccounted call for R reverts (underflow); existing funded matches' settle/refundStalled calls revert once the pot to be paid exceeds real balance — funds locked permanently.

Fix

  function _received(address token) internal view returns (uint256) {
-     return IERC20(token).balanceOf(address(this)) - accounted[token];
+     uint256 bal = IERC20(token).balanceOf(address(this));
+     return bal > accounted[token] ? bal - accounted[token] : 0;
  }

Also cap payouts to min(accounted amount, actual balanceOf) in settle/cancelUnaccepted/refundStalled, and/or restrict allowedToken to standard, non-rebasing tokens.

[45] 5. sweepUnaccounted lets the owner race and capture a user's in-flight (non-atomic) deposit

RiderBattleEscrow.sweepUnaccounted · Confidence: 45 (owner-privileged path) · [both — phase1: general-3/access-2/erc20-6; phase2: leads from agents 2, 5, 6, 9, 12]

Description
sweepUnaccounted draws from the exact same unattributed balanceOf - accounted surplus consumed by Finding 1, with no minimum age or grace period. A malicious or compromised owner (or an honest owner acting on stale information) can capture a user's in-flight deposit before their follow-up createMatch/joinMatch call lands, faster than the unprivileged-attacker variant since it requires no acceptWindow wait.

Gate reasoning: this is technically an admin-action path (sweepUnaccounted is onlyOwner), which per the four-gate standard would normally require a named unprivileged amplifier to avoid rejection. It is not treated as "admin privilege by design" here because it is the same missing-guard/access-gap defect as the CONFIRMED unprivileged-exploitable Finding 1 (the access mechanism itself — lack of depositor attribution — is the bug, matching the "access gap" amplifier category), just also reachable via an owner call. Kept as a distinct, lower-confidence finding since it is a different function and the owner-privileged path is a real, if narrower, risk surface (compromised-key or honest-mistake scenarios). Rated Medium, not Critical, since it requires the owner role.

Proof of Concept: Same setup as Finding 1, but instead of an attacker calling createMatch, the owner calls sweepUnaccounted(token, ownerAddr) immediately after Alice's transfer lands and before her createMatch call is mined — capturing her deposit outright, no wait required.

Fix: Fixing Finding 1 (binding deposits to depositors) removes the ambiguity sweepUnaccounted exploits — genuinely-abandoned surplus becomes the only thing ever left unaccounted. As defense-in-depth, also add a minimum age/cooldown (e.g. >= acceptWindow) before unaccounted surplus is sweepable.

[70] 6. settle() cannot validate contract-based (ERC-1271) settlers

RiderBattleEscrow.settle / setSettler · Confidence: 70 · [phase1 only — general-6, sig-01; independently re-verified]

Description
settle() verifies via raw ECDSA.recover, which can only return an EOA-derived address. If settler is ever set to a smart-contract wallet (e.g. a multisig — a reasonable operational hardening choice given the fund-moving authority this role holds), digest.recover(sig) == settler can never be true, and settle() becomes permanently unusable for every match (only refundStalled remains, which returns both wagers rather than resolving a winner).

Gate check: no guard interrupts; reachable via a plausible, non-malicious owner operational choice (hardening settler to a multisig); unprivileged trigger not required — it's a pure code-level compatibility gap; degrades core functionality (trust-model / degraded-behavior category) → CONFIRMED, Medium (matches the severity rubric's "degraded behavior, trust model violation" tier, not fund theft).

Proof of Concept: Owner calls setSettler(multisigAddress). Every subsequent settle() call reverts with "bad sig" since the address ECDSA.recover returns can never equal the multisig's own address.

Fix: Use OpenZeppelin SignatureChecker.isValidSignatureNow(settler, digest, sig) (ECDSA + ERC-1271 fallback) instead of raw ECDSA.recover.

[60] 7. Fee-on-transfer tokens break the exact-match deposit check and can under-deliver payouts vs. emitted events

RiderBattleEscrow.createMatch / .joinMatch / .settle · Confidence: 60 · [phase1 only — erc20-5]

If token charges a fee on transfer, the contract receives wager - fee on deposit, so _received(token) >= wager fails and createMatch/joinMatch revert even for a correctly-intentioned deposit; any user over-send to compensate becomes free unaccounted surplus (compounding Finding 1). On payout, a token fee on the outgoing transfer means the winner receives less than the MatchSettled event's reported toWinner value.

[40] 9. Compromised or self-appointed settler can join and self-settle any match (demoted — see gate reasoning)

RiderBattleEscrow.settle / joinMatch / setSettler · Confidence: 40 · [phase1 only — access-3, access-4; DEMOTED in reconciliation]

Phase-1's access-control agent rated this Critical (a holder of the settler key, or an owner who reassigns settler to itself with no timelock, can joinMatch on any open match and sign its own winning settlement, extracting the counterparty's stake). Reconciliation gate check: settler is explicitly documented as an owner-changeable role ("OWNER CAN CHANGE... settler") and its entire function is to be the trusted arbiter of match outcomes — a dishonest settler could declare either existing party the winner without needing to join as a player at all, so this is fundamentally a restatement of the documented single-settler trust model, not a code-level defect exceeding it. Per the four-gate standard, admin/trusted-role actions are rejected as findings unless a concrete unprivileged amplifier is named; no such amplifier exists here (the "amplifier" — joining the match — is performed by the same privileged/self-interested actor, not a separate unprivileged party). Demoted to Low/Info — retained only as a centralization-risk hardening recommendation: use a threshold/multisig signer for settler rather than a single hot EOA, and consider a timelock on setSettler so a rotation cannot affect matches already Funded at the time of change.
