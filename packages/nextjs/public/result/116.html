Executive Summary

YeetToken is a minimal OZ v5 ERC20 that charges a 1 % transfer tax on Uniswap V2 buy/sell operations. The two independent audit passes found no Critical or High severity vulnerabilities. The most significant issue — liquidity add/remove being silently taxed — was independently confirmed by both methodologies (ethskills M-1, pashov confidence 90/100) and is rated Medium. Four Low and two Informational findings complete the picture.

Contract Overview

address public immutable taxRecipient = 0xB2ac59aE04d0f7310dC3519573BF70387b3b6E3a;
address public immutable deployer;   // set in constructor
address public pair;                 // set once via setPair()

Tax hook — fires on any transfer where from == pair || to == pair:

function _update(address from, address to, uint256 value) internal override {
    address _pair = pair;
    if (_pair != address(0) && (from == _pair || to == _pair)
        && from != address(0) && to != address(0)) {
        uint256 taxAmount = value / 100;
        if (taxAmount > 0) {
            super._update(from, taxRecipient, taxAmount);
            super._update(from, to, value - taxAmount);
            return;
        }
    }
    super._update(from, to, value);
}

Findings

[M-1] Liquidity add/remove silently taxed — LP providers lose 1 % of every deposit and withdrawal

Severity: Medium
Confidence: Confirmed by both methodologies (ethskills M-1 + pashov #1 confidence 90)
Location: YeetToken._update() — tax condition

Description:
The tax guard fires on any transfer where from == pair || to == pair, which includes router-mediated addLiquidity and removeLiquidity calls, not just buy/sell swaps. The NatSpec says the tax applies to "buy" and "sell" but is silent on liquidity operations.

  • addLiquidity: router calls token.transferFrom(LP_provider, pair, amountYEET) → to == pair → 1 % sent to taxRecipient. The pair receives only 99 % of the intended deposit; Alice's LP position records the correct pro-rata share of what was actually received, but she permanently loses 1 % to taxRecipient.
  • removeLiquidity: pair calls token.transfer(LP_provider, amountOut) → from == pair → LP provider receives only 99 % of their share; 1 % goes to taxRecipient.

Proof of Concept:

  1. Deployer calls factory.createPair(WETH, YEET) → pairAddr.
  2. Deployer calls setPair(pairAddr).
  3. Alice calls router.addLiquidity(YEET, WETH, 10_000e18, …).
  4. Router calls YEET.transferFrom(Alice, pairAddr, 10_000e18).
  5. _update(Alice, pairAddr, 10_000e18): tax fires — pairAddr receives 9_900e18; taxRecipient receives 100e18. Alice permanently loses 100 YEET.

Recommendation:
Add a tax-exempt whitelist so the Uniswap V2 router (and any other approved addresses) can perform liquidity operations without tax:

mapping(address => bool) public taxExempt;

function setTaxExempt(address account, bool exempt) external {
    require(msg.sender == deployer, "not deployer");
    taxExempt[account] = exempt;
}

function _update(address from, address to, uint256 value) internal override {
    address _pair = pair;
    bool taxable = _pair != address(0)
        && (from == _pair || to == _pair)
        && from != address(0) && to != address(0)
        && !taxExempt[from] && !taxExempt[to];
    if (taxable) {
        uint256 taxAmount = value / 100;
        if (taxAmount > 0) {
            super._update(from, taxRecipient, taxAmount);
            super._update(from, to, value - taxAmount);
            return;
        }
    }
    super._update(from, to, value);
}

Alternatively, document explicitly that LP operations are taxed and warn users accordingly.

[L-1] Two Transfer events emitted per taxed transfer — non-standard ERC-20 behaviour

Severity: Low
Confidence: Confirmed by both methodologies (ethskills L-1 + pashov #2 confidence 75)
Location: YeetToken._update() — two super._update calls

Description:
ERC-20 specifies one Transfer event per logical token movement. When tax applies, two super._update calls each emit a Transfer event:

Transfer(from, taxRecipient, taxAmount)
Transfer(from, to, value - taxAmount)

Off-chain tools (indexers, explorers, aggregators) that sum Transfer events to compute net flow see value + taxAmount leaving from, which exceeds value (the amount the user sent). This can cause inflated "out" figures in UIs, mismatched totalSupply reconstructions, and failures in protocols that track balances via events.

Recommendation:
Emit a single custom TaxedTransfer(from, to, amount, tax) event and suppress the redundant ERC-20 Transfer. Uniswap V2 itself uses balance diffs so pool operations are unaffected; the risk is purely off-chain tooling.

[L-2] Tax not collected on transfers smaller than 100 wei

Severity: Low
Location: YeetToken._update() — uint256 taxAmount = value / 100

Description:
For value in [1, 99], integer division yields taxAmount = 0, so the if (taxAmount > 0) guard evaluates false and the transfer passes through untaxed. A sophisticated actor could split large pair transfers into 99-wei batches to avoid tax entirely; however, gas cost (≈21,000 gas × many batches) makes this economically infeasible at any realistic price point.

Recommendation:
Document as intentional (avoids zero-amount transfer edge cases). No code change is required unless strict 1 % enforcement on all non-zero amounts is desired.

[L-3] Hardcoded immutable taxRecipient — no recovery if address is lost or compromised

Severity: Low
Confidence: Flagged by ethskills L-3 and pashov Lead
Location: address public immutable taxRecipient = 0xB2ac59aE04d0f7310dC3519573BF70387b3b6E3a

Description:
taxRecipient is compiled into bytecode at deployment. If the key for 0xB2ac59aE… is lost, stolen, or the address becomes inaccessible, all future tax revenue is permanently misdirected with no on-chain remedy. There is no admin function, timelock, or governance mechanism to update it.

Recommendation:
Replace the immutable with a mutable value settable by the deployer (or a multi-sig):

address public taxRecipient;

event TaxRecipientUpdated(address indexed prev, address indexed next);

function setTaxRecipient(address _taxRecipient) external {
    require(msg.sender == deployer, "not deployer");
    require(_taxRecipient != address(0), "zero addr");
    emit TaxRecipientUpdated(taxRecipient, _taxRecipient);
    taxRecipient = _taxRecipient;
}

[L-4] Immutable deployer prevents pair setup if deployer key is lost before setPair

Severity: Low
Confidence: Flagged by ethskills L-4 and pashov Lead
Location: address public immutable deployer; YeetToken.setPair()

Description:
setPair is gated by require(msg.sender == deployer). If the deployer key is lost before setPair is ever called, the pair address can never be set (pair stays address(0) forever) and the tax mechanism is permanently disabled. Conversely, once setPair is called the deployer has no further power, which is a good property.

Recommendation:
Add a two-step deployer transfer to allow key rotation before setPair is called:

address public pendingDeployer;

function initiateDeployerTransfer(address newDeployer) external {
    require(msg.sender == deployer, "not deployer");
    pendingDeployer = newDeployer;
}

function acceptDeployer() external {
    require(msg.sender == pendingDeployer, "not pending");
    deployer = pendingDeployer;
    pendingDeployer = address(0);
}

(This requires removing immutable from deployer.)

[I-1] YEET is a fee-on-transfer token for Uniswap pair interactions — integration warning required

Severity: Info
Location: YeetToken._update()

Description:
Any protocol that calls transferFrom(user, contractAddress, amount) and records amount as the deposited value will over-count by 1 % when the contract address is the V2 pair. The correct integration pattern is balanceAfter - balanceBefore. The contract's NatSpec and documentation should explicitly state that YEET is fee-on-transfer for all transfers touching the V2 pair.

[I-2] pragma ^0.8.20 emits PUSH0 — compatible with Base (Canyon+), not with pre-Canyon chains

Severity: Info
Location: pragma solidity ^0.8.20

Description:
Solidity ≥ 0.8.20 targets the Shanghai EVM by default, which includes the PUSH0 opcode. Base has supported PUSH0 since the Canyon upgrade (January 2024). No issue for the current deployment on Base. If the same bytecode were re-deployed to a pre-Canyon OP Stack chain or app-chain without PUSH0 support, deployment would fail.

Recommendation:
Document that the contract must not be redeployed to pre-Canyon OP Stack instances without recompiling with --evm-version paris.
