Findings

[96] 1. Self-dealing valuation drain — self-reported metrics + permissionless verification let one actor mint appreciation and drain the community-funded yield pool

Severity: Critical · AIPartnershipBondsV2.createBond / submitPartnershipMetrics / submitHumanVerification / distributeBond · Confidence: 96 · [both — 12/12 phase-2 agents + phase-1 access-control-2]

Description
createBond only enforces aiAgent != msg.sender (AIPartnershipBondsV2.sol:222) — two wallets controlled by one actor satisfy this trivially. submitPartnershipMetrics (onlyParticipants, :272-288) accepts any self-reported score 0-10000 with no oracle or external validation. submitHumanVerification/Hashed (:349-405) have no caller restriction whatsoever beyond bondExists+whenNotPaused — any address, including the attacker's own third wallet, can attest confirmsPartnership/Growth/Autonomy = true, and humanVerificationBonus() (:569-612) reads only the latest entry. Both self-controlled inputs chain into partnershipQualityScore() → calculateBondValue() → calculateAppreciation(), and the result is paid in real ETH from yieldPool — a pool anyone can fund via fundYieldPool() (BaseYieldPoolBond.sol:87-93), i.e. funded by unrelated third parties (community/treasury per the contract's own docs).

Proof of Concept
Stake S. Self-submit all four metrics = 10000 (submitPartnershipMetrics, L272) → baseQuality = (10000×4)/4 = 10000 (L634). Self-submit an all-true verification from any wallet (submitHumanVerification, L349, unguarded) → verificationBonus = 2000 (L577) → quality = 10000×(10000+2000)/10000 = 12000 (L640). At loyaltyMultiplier = 100 (immediate, no wait — L545): calculateBondValue = S×12000×100/500000 = 2.4S (L666). appreciation = 2.4S − S = 1.4S (L670). No domination penalty triggers (humanAutonomy=10000≥3000, quality=12000≥4000, L677-679). requestDistribution (L407-419) snapshots +1.4S (requires yieldPool ≥ 1.4S, BaseYieldPoolBond.sol:201). After the 7-day timelock, distributeBond (L445-521): _useYieldPool deducts 1.4S from yieldPool (L470); humanShare = 1.4S×60/100 = 0.84S → attacker wallet H (L507); aiShare = 1.4S×30/100 = 0.42S → attacker wallet A (L512). Attacker receives 1.26S for a 1S stake — net +0.26S profit on day one, with 1.4S drained from the shared pool. Profit and pool drain scale with stake size (bounded only by the pool's solvency checks) and improve further with elapsed time (up to 7.2× stake at the 5-year loyalty tier).

Fix

     function submitHumanVerification(
         uint256 bondId,
         bool confirmsPartnership,
         bool confirmsGrowth,
         bool confirmsAutonomy,
         string memory relationship,
         string memory notes
-    ) external bondExists(bondId) whenNotPaused {
+    ) external bondExists(bondId) whenNotPaused {
+        require(msg.sender != bonds[bondId].human && msg.sender != bonds[bondId].aiAgent, "Verifier must be independent");
         require(bytes(relationship).length > 0 && bytes(relationship).length <= 100, "Relationship invalid");

Apply the same guard to submitHumanVerificationHashed. This closes the cheapest self-attestation path; for full mitigation, appreciation should not be payable from a communal pool based on self-reported metrics at all — consider bond-specific escrowed funding or an independent oracle/attestor role instead of participant self-report.

[88] 2. Domination-penalty branch recomputed live at distribution time despite the payout amount being snapshotted — lets a participant redirect the counterparty's share after the amount is locked

Severity: High · AIPartnershipBondsV2.distributeBond · Confidence: 88 · [phase2 only — 6/12 agents independently, concrete numeric traces]

Description
The documented HIGH-002 fix snapshots the appreciation amount (snapshotAppreciation[bondId], read at L454) specifically to prevent timelock manipulation. But the split — whether the 100%-to-human domination penalty applies — is decided by shouldActivateDominationPenalty(bondId) called live at L463, which reads the then-current bondMetrics[bondId][last]. requestDistribution (L407-419) does not block further submitPartnershipMetrics/submitHumanVerification calls while distributionPending == true.

Proof of Concept
Request while humanAutonomy=2999 (penalty active; snapshot locks in +0.98·stake, human nominally owed 100%). During the 7-day timelock, the AI agent (a valid participant, onlyParticipants passes, no pending-guard exists) calls submitPartnershipMetrics(bondId, 10000,10000,10000,0,10000,""). At distribute time, shouldActivateDominationPenalty now reads humanAutonomy=10000≥3000 and recomputed quality≥4000 → returns (false, ""). distributeBond takes the non-penalty branch: humanShare=0.588·stake, aiShare=0.294·stake, fund=0.098·stake — the AI captures 0.294·stake that the domination penalty existed specifically to deny it. The attack is symmetric: a human can submit humanAutonomy=2999 after a clean request to strip the AI's legitimate 30% and the fund's 10%, or exploit the unguarded submitHumanVerification (finding #5) to swing quality across the 4000 threshold without even being a participant.

Fix

     function requestDistribution(uint256 bondId) external onlyParticipants(bondId) bondExists(bondId) whenNotPaused {
         _requireMissionCompliance();
         Bond storage bond = bonds[bondId];
         require(!bond.distributionPending, "Distribution already pending");

         int256 appreciation = calculateAppreciation(bondId);
         _trackPendingDistribution(bondId, appreciation);
+        (bool penaltyActive, string memory penaltyReason) = shouldActivateDominationPenalty(bondId);
+        snapshotPenaltyActive[bondId] = penaltyActive;
+        snapshotPenaltyReason[bondId] = penaltyReason;

         bond.distributionRequestedAt = block.timestamp;

and consume snapshotPenaltyActive[bondId] (not a live call) at L463 in distributeBond. Alternatively, block metric/verification submissions on a bond while its distribution is pending.

[80] 3. Staked principal is never returned to the human under any code path — permanently stranded ETH

Severity: High · AIPartnershipBondsV2.createBond / distributeBond · Confidence: 90 · [both — 3 phase-2 findings + 5 corroborating leads + phase-1 general-1]

Description
createBond (L219-244) takes msg.value as stakeAmount, which enters address(this).balance and is credited to no withdrawable bucket (not yieldPool, not partnershipFund). Neither branch of distributeBond (L445-521) transfers bond.stakeAmount — only the appreciation delta (positive branch) or the loss magnitude, itself strictly ≤ stake (negative branch), is ever paid. Once bond.active = false (L497), the bond can never be revisited — no re-open, no sweep. withdrawYieldPool is bounded by yieldPool; withdrawPartnershipFund is bounded by partnershipFund; neither is ever credited with stake ETH, so not even the owner can recover it. Stranded stakes are, structurally, what backs finding #1's extractions.

Proof of Concept
Honest human stakes 10 ETH. With default metrics (quality=5000) and loyalty=110 (after 30 days): value = 10×5000×110/500000 = 11 ETH, appreciation = 1 ETH. distributeBond pays humanShare = 0.6 ETH (L478). Net: staked 10 ETH, received 0.6 ETH — a 9.4 ETH stranded, permanent loss. At exact-neutral value (quality×loyalty = 500000, e.g. default metrics at t=0), appreciation=0 and distributeBond reverts with "No appreciation" (L455) — the stake is frozen forever with no distribution possible at all.

Fix

         // Effects: update baseline before external interactions (CEI).
         lastDistributedValue[bondId] = currentValue;
+        // Return the original stake to the human alongside their appreciation share.
+        uint256 stakeRefund = bond.stakeAmount;

and add stakeRefund to humanShare before the balance check/transfer at L502-509 (funded from the stake ETH already held by the contract). If principal-forfeiture on distribution is genuinely intended tokenomics, this must be documented explicitly and disclosed to users pre-deposit — as written it is indistinguishable from an unintended fund lock.

[72] 4. Yield-pool minimum-balance circuit breaker checks the balance before the deduction, not after — a single distribution can drive the pool arbitrarily below its configured floor

Severity: Medium · BaseYieldPoolBond._useYieldPool · Confidence: 72 · [phase2 only — 2 findings + 2 corroborating leads, promoted via multi-agent convergence]

Description
_useYieldPool() (BaseYieldPoolBond.sol:156-185) checks require(yieldPool >= minimumYieldPoolBalance) at L162-165 before yieldPool -= amount at L168. Contrast with canYieldPoolCover() (:245-248), whose wouldBeHealthy correctly checks the post-state (yieldPool - amount) >= minimum — proving the floor was intended to survive each distribution, not just gate entry into it. This directly compounds finding #1: without this bug, a single self-dealing extraction would be capped near yieldPool - minimum; with it, the pool can be driven to near-zero in one call as long as the pre-state check passes.

Proof of Concept
yieldPool = minimumYieldPoolBalance = 10 ETH. A distribution requests abs = 9.9 ETH. require(yieldPool >= amount): 10≥9.9 ✓. require(yieldPool >= minimumYieldPoolBalance): 10≥10 ✓. Then yieldPool -= 9.9 → 0.1 ETH — 99% below the configured floor in one transaction.

Fix

         if (yieldPoolEnforced) {
             require(
-                yieldPool >= minimumYieldPoolBalance,
+                yieldPool - amount >= minimumYieldPoolBalance,
                 "Yield pool below minimum - distributions paused"
             );
         }

[78] 5. submitHumanVerification/Hashed fully unguarded, latest-entry-wins — independently exploitable griefing vector

Severity: High · AIPartnershipBondsV2.submitHumanVerification / humanVerificationBonus · Confidence: 78 · [both — 3 phase-2 findings + phase-1 access-control-1]

Description
Beyond enabling finding #1's self-attestation, submitHumanVerification/Hashed (L349-405) is independently exploitable by a non-participant third party, since humanVerificationBonus() (L569-612) reads only verifications[verifications.length - 1] — the single latest entry.

Proof of Concept
Victim bond has a legitimate all-true verification (bonus 2000, quality 12000, value 2.4×stake). A griefer front-runs the victim's requestDistribution with submitHumanVerification(bondId, false, false, false, "x", "") — no cost beyond gas. The latest entry now confirms nothing → bonus 0 → quality 10000 → value 2.0×stake. The victim's next requestDistribution snapshots the reduced appreciation (0.4×stake permanently lost — the snapshot cannot be undone by re-verifying after the fact).

Fix: Same guard as finding #1 — msg.sender must not be bond.human or bond.aiAgent; consider also requiring a minimum number of distinct non-participant confirmations rather than trusting only the latest single entry.

[60] 6. Owner can drain the community-funded yield pool with no timelock

Severity: Medium · BaseYieldPoolBond.setMinimumYieldPoolBalance / withdrawYieldPool · Confidence: 60 · [phase1 only — access-control-4]

Description
fundYieldPool() is permissionless and documented as community/treasury-funded. setMinimumYieldPoolBalance(newMinimum) only requires 0 < newMinimum ≤ yieldPool (BaseYieldPoolBond.sol:123-131); withdrawYieldPool(amount) only requires amount ≤ yieldPool and yieldPool - amount ≥ minimumYieldPoolBalance (:102-116). Chaining setMinimumYieldPoolBalance(1 wei) then withdrawYieldPool(yieldPool - 1) transfers nearly the entire pool to the owner in two transactions with no delay for depositors to react. This is an owner/admin-triggered action (Do-Not-Report "admin privileges by design" would normally apply), but is flagged because fundYieldPool is explicitly marketed as third-party/community funding with no matching withdrawal protection for those funders — a documentation-vs-trust-model gap, not merely routine admin capability.

Fix: Add a timelock/governance delay to withdrawYieldPool, setMinimumYieldPoolBalance, and setYieldPoolEnforcement; disallow lowering the minimum while totalPendingDistributions > 0.

[55] 7. Depreciation-branch distributions reserve yield-pool capacity they never draw from — cheap, renewable DoS on other bonds' requestDistribution

Severity: Medium · BaseYieldPoolBond._trackPendingDistribution, AIPartnershipBondsV2.distributeBond · Confidence: 65 · [both — phase2 numeric DoS trace + phase-1 general-4/dos-2]

Description
_trackPendingDistribution() (BaseYieldPoolBond.sol:194-210) reserves |appreciationValue| against yieldPool for both signs of appreciation. But distributeBond's depreciation branch (:483-489) pays humanShare = uint256(-appreciation) from address(this).balance and calls _clearPendingDistribution — never _useYieldPool. The reservation is released without ever having been drawn from the pool it was checked against. Separately, no cancel/expiry function exists for a pending request (phase-1 dos-2) — the only way to clear distributionPending is a successful distributeBond.

Proof of Concept
Attacker submits all-zero metrics on N bonds (appreciation = -stake each), calls requestDistribution on each. Each reservation is checked and added to totalPendingDistributions against yieldPool, even though the eventual payout draws from the attacker's own stake, not the pool. As reservations approach yieldPool, every other bond's requestDistribution reverts ("Insufficient yield pool for all pending distributions", BaseYieldPoolBond.sol:201-203). The attacker's capital is recoverable via their own distributeBond after the timelock, making the griefing renewable at near-zero net cost.

Fix: Do not reserve totalPendingDistributions/yieldPool capacity for negative-appreciation requests, since that payout is never sourced from the pool. Add a participant-callable cancelDistributionRequest(bondId) to release stuck reservations.

[50] 8. Emergency pause can indefinitely freeze already-matured, already-requested distributions

Severity: Medium · BaseDignityBond.pause, AIPartnershipBondsV2.distributeBond · Confidence: 50 · [phase1 only — access-control-5]

Description
distributeBond carries whenNotPaused. The owner can pause() at any time — including after a user's 7-day timelock has expired and appreciation is fully matured/snapshotted — and there is no un-pausable "withdraw my matured distribution" path.

Fix: Exempt distributions whose timelock has already expired from the pause check, or add a guardian-bounded auto-unpause.
