What this contract does: a permissionless "dust sweeper" — a user batches up to 50 small ERC20 balances, pulls them into the router either via a Permit2 signature (with a custom EIP-712 witness) or a plain ERC20 allowance, executes each swap leg as a best-effort call to an owner-allowlisted DEX target/spender, refunds anything unconsumed, takes a protocol fee in bps on the settled output, and delivers the net output (ERC20 or unwrapped native ETH) to a recipient.

Findings

[85] 1. Protocol fee is permissionlessly bypassable — no floor on caller-supplied feeBpsOverride

DustSwapSweepRouter._resolveFeeBps · Confidence: 85 · [both] — corroborated by phase-1 general checklist + 8 of 12 independent phase-2 attacker agents (math-precision, access-control, economic-security, first-principles, asymmetry, periphery, numerical-gap, flow-gap)

Description
_resolveFeeBps only rejects overrides above MAX_FEE_BPS; any caller — the same party who pays the fee — can pass feeBpsOverride = 0 (directly in Allowance mode, or by self-signing a zero-fee Permit2 witness, since Permit2 validates the signature against msg.sender) and pay the protocol nothing, on every single sweep, with no precondition.

function _resolveFeeBps(uint16 feeBpsOverride) internal view returns (uint16 effectiveFeeBps) {
    effectiveFeeBps = feeBpsOverride == FEE_OVERRIDE_SENTINEL ? feeBps : feeBpsOverride;
    if (effectiveFeeBps > MAX_FEE_BPS) revert FeeTooHigh();
}

With default feeBps = 100 (1%) and a sweep realizing 1,000 units of gross output, the honest path pays 10 units to feeCollector; setting feeBpsOverride = 0 pays 0. The owner-configured feeBps only ever applies to callers who voluntarily pass FEE_OVERRIDE_SENTINEL — the fee mechanism is entirely opt-in.

Fix

 function _resolveFeeBps(uint16 feeBpsOverride) internal view returns (uint16 effectiveFeeBps) {
     effectiveFeeBps = feeBpsOverride == FEE_OVERRIDE_SENTINEL ? feeBps : feeBpsOverride;
     if (effectiveFeeBps > MAX_FEE_BPS) revert FeeTooHigh();
+    if (effectiveFeeBps < feeBps) revert FeeTooLow();
 }

[80] 2. Protocol fee bypassable via a second, independent mechanism — routing swap output directly to the recipient, bypassing router custody

DustSwapSweepRouter._settleOutput / executeRoute · Confidence: 80 · [phase2-only] — found by the boundary-lens agent; re-examined against source and confirmed reachable

Description
grossAmountOut is measured purely as the router's own ERC20 balance delta (balanceOf(this) - initialOutputBalance). Each swap leg's route.data is opaque, off-chain-constructed calldata that the router never inspects — it is only hash-bound in the Permit2 witness, never interpreted. Most general-purpose DEX routers/aggregators (Uniswap Universal Router, 0x, 1inch) accept a caller-specified output recipient in their calldata. A user can encode every leg to deliver output straight to params.recipient instead of address(this). The router then observes grossAmountOut = 0; with minAmountOut = 0 (a value the same user also freely controls — see finding 8), _settleOutput does not revert, feeAmount = 0, and the user has already received their full swap proceeds directly from the DEX.

grossAmountOut = IERC20(st.actualOutput).balanceOf(address(this)) - st.initialOutputBalance;
if (grossAmountOut < params.minAmountOut) revert InsufficientOutput();   // 0 < 0 is false
feeAmount = (grossAmountOut * st.effectiveFeeBps) / BPS_DENOMINATOR;     // 0

This is architecturally independent of finding 1 — fixing the feeBpsOverride floor does not close this path, since it never touches feeBpsOverride at all.

Fix
There is no clean single-line fix given the current design (the router intentionally does not interpret route.data). Options: (a) restrict allowedTargets to integrations verified to always deliver output to msg.sender (the router) with no caller-overridable recipient parameter; (b) reject minAmountOut == 0 on-chain (see finding 8) to at least remove the simplest triggering condition; (c) treat grossAmountOut == 0 on a non-empty, non-fully-skipped route set as an error rather than a silent zero-fee success.

[75] 3. minAmountOut slippage floor is enforced on gross (pre-fee) output, so the recipient can receive less than their signed minimum

DustSwapSweepRouter._settleOutput · Confidence: 75 · [both] — corroborated by phase-1 defi-amm checklist + 9 of 12 independent phase-2 agents (near-unanimous convergence)

Description
The slippage check happens before the fee is subtracted, but the recipient is paid the post-fee net amount:

grossAmountOut = IERC20(st.actualOutput).balanceOf(address(this)) - st.initialOutputBalance;
if (grossAmountOut < params.minAmountOut) revert InsufficientOutput();   // checked on GROSS
feeAmount   = (grossAmountOut * st.effectiveFeeBps) / BPS_DENOMINATOR;
netAmountOut = grossAmountOut - feeAmount;                                // recipient gets NET

With minAmountOut = 100 and the maximum effectiveFeeBps = 300 (3%), a swap realizing exactly gross = 100 passes the check (100 < 100 is false) but delivers only net = 97 — 3% below the floor the user signed. The witness does bind feeBps, so a diligent frontend can pre-discount minAmountOut, but the contract itself provides no guarantee that the delivered amount meets the user's stated minimum.

Fix

     grossAmountOut = IERC20(st.actualOutput).balanceOf(address(this)) - st.initialOutputBalance;
-    if (grossAmountOut < params.minAmountOut) revert InsufficientOutput();
-
     feeAmount = (grossAmountOut * st.effectiveFeeBps) / BPS_DENOMINATOR;
     netAmountOut = grossAmountOut - feeAmount;
+    if (netAmountOut < params.minAmountOut) revert InsufficientOutput();

[70] 4. Fee-on-transfer input combined with a pre-existing stranded balance lets a sweep over-sell and extract funds that were never pulled from the caller

DustSwapSweepRouter.executeRoute · Confidence: 70 · [both] — phase-1 general checklist flagged the accounting pattern; phase-2 flow-gap agent produced a full concrete trace (corroborated as leads by the periphery and first-principles agents)

Description
The fee-on-transfer guard checks the router's total balance of tokenIn, not the amount this specific pull actually delivered:

if (tokenIn.balanceOf(address(this)) < route.amountIn) revert InsufficientHeldBalance();
tokenIn.forceApprove(route.spender, route.amountIn);

If the router already holds a stranded balance S of tokenIn (plausible in normal operation — e.g. left behind by an earlier sweep's RefundFailed, which this same audit shows is a real and reachable state for weird/non-standard tokens — see finding 12), a caller can submit a fee-on-transfer route whose delivered amount is < amountIn. The aggregate check still passes because freshlyDelivered + S >= amountIn, so the router approves and sells the full amountIn, drawing the shortfall out of the stranded balance S. The refund logic (current - initial) never claws this back — it simply observes current < initial and refunds nothing, silently converting someone else's stranded funds into the current caller's swap output.

Concrete trace: router holds 1,000 stranded units of a 2%-fee-on-transfer token. Attacker submits amountIn = 100; pull delivers 98 (balance → 1,098). Guard 1098 < 100? No → passes. Router approves and sells the full 100 → balance → 998 (below the 1,000 snapshot) → no refund triggered. The attacker delivered 98 but the DEX sold 100 on their behalf — 2 units of stranded (protocol/prior-user) funds were converted into the attacker's output.

Fix

- if (tokenIn.balanceOf(address(this)) < route.amountIn) revert InsufficientHeldBalance();
- tokenIn.forceApprove(route.spender, 0);
- tokenIn.forceApprove(route.spender, route.amountIn);
+ // caller must pass the amount actually received by THIS pull (measured immediately
+ // before/after the transfer in _pullInputsWith*), not the requested amountIn
+ if (receivedThisPull < route.amountIn) revert InsufficientHeldBalance();
+ tokenIn.forceApprove(route.spender, 0);
+ tokenIn.forceApprove(route.spender, receivedThisPull);

[65] 5. Blacklist or pause on the output token can permanently DoS every sweep into that token via the mandatory fee transfer

DustSwapSweepRouter._settleOutput · Confidence: 65 · [both] — corroborated by phase-1 erc20 checklist + phase-2 economic-security agent

Description
The protocol fee transfer to feeCollector happens unconditionally (not best-effort) before the recipient payout:

IERC20(st.actualOutput).safeTransfer(collector, feeAmount);   // reverts the WHOLE sweep on failure

If the output token has a blocklist (USDC/USDT-style) and feeCollector becomes blacklisted, or the token issuer pauses transfers, every sweep with feeAmount > 0 into that output token reverts for all users, protocol-wide, until the owner rotates feeCollector via setFeeCollector.

Fix
Make the fee transfer resilient — either accrue fees per-token in contract storage and let the collector pull them separately, or wrap the fee transfer so a failing collector degrades to a best-effort skip (mirroring the pattern already used for user refunds) rather than blocking the user's payout.

[65] 6. No timelock on setAllowedTarget/setAllowedSpender — the allowlist is the sole guardrail on an otherwise arbitrary-call + arbitrary-approval primitive

DustSwapSweepRouter.setAllowedTarget / setAllowedSpender / executeRoute · Confidence: 65 · [both] — corroborated by phase-1 access-control checklist + 3 independent phase-2 agents (access-control, economic-security, invariant — all of which explicitly could not construct a working exploit given the current approval design, so this is presented as a centralization/defense-in-depth gap rather than a live exploit)

Description
executeRoute performs route.target.call(route.data) with fully caller-supplied calldata after granting route.spender an ERC20 approval of exactly route.amountIn. The only thing preventing this from being an arbitrary-call/arbitrary-approval primitive is allowedTargets/allowedSpenders, both mutable instantly and without delay by the owner. Every reviewing agent confirmed that, given the current exact-amount/reset-on-revert approval design and the absence of any pooled third-party funds, a malicious addition cannot be turned into fund theft beyond the current caller's own approved amount for that leg — but this rests entirely on the owner never allowlisting a misbehaving pair, with no on-chain delay for users to react.

Fix
Add a timelock (24–48h) to additions in allowedTargets/allowedSpenders, and/or govern the allowlist via a multisig.

[60] 7. Failed best-effort refunds are recoverable only by the owner via rescueERC20, with no user-callable reclaim path

DustSwapSweepRouter._refundLeftoverInputs / rescueERC20 · Confidence: 60 · [both] — corroborated across phase-1 access-control/erc20/dos checklists and the phase-2 trust-gap agent

Description
If a leftover input's transfer back to the user fails or returns non-compliant data, _refundLeftoverInputs emits RefundFailed and leaves the tokens in the router by design (to preserve best-effort semantics). The only recovery mechanism is rescueERC20, onlyOwner, sendable to an arbitrary address — a malicious or compromised owner can redirect a user's stranded balance to themselves, and even an honest owner is a mandatory trust dependency for a user to ever recover their own funds.

Fix
Track failed-refund amounts per original payer and expose a permissionless claimRefund(token), or explicitly document rescueERC20/rescueNative as a custodial backstop requiring user trust in the owner.

[45] 8. minAmountOut == 0 is accepted, disabling all on-chain slippage protection

DustSwapSweepRouter._validateParams · Confidence: 45 · [phase1-only], re-examined and confirmed

No on-chain floor forces a non-zero minAmountOut; combined with finding 3 and finding 2, a zero floor removes essentially all delivered-amount guarantees for a self-directed caller. For frontend-driven flows this is a UX/config risk rather than an exploit.

[45] 9. No per-leg slippage validation; only an aggregate output-token floor exists, and proceeds landing in an unexpected (non-input, non-output) token are permanently stranded

DustSwapSweepRouter.executeRoute / _settleOutput · Confidence: 45 · [phase1-only], re-examined and confirmed

Each leg's own slippage/deadline parameters live in opaque route.data never validated on-chain; the only protection is the aggregate minAmountOut on the final output token. A sandwicher can extract up to the user's full aggregate slippage tolerance from a single leg. Separately, any token produced by a mis-encoded or unexpected leg that is neither an input token nor the settled output token is invisible to both the refund and settlement logic and is permanently stranded pending owner rescueERC20.

[40] 10. Single-step ownership (Ownable, not Ownable2Step) can permanently freeze unpause/allowlist/rescue if the owner key is lost or renounced

Ownable (inherited) · Confidence: 40 · [phase1-only], re-examined and confirmed

If ownership is lost or renounceOwnership() is called, unpause, allowlist updates, fee configuration, and both rescue functions become permanently uncallable — including bricking recovery of any stranded balances from finding 7.

[35] 11. Owner-controlled fee changes griefs in-flight sentinel-mode signatures, asymmetrically between the two pull modes

_resolveFeeBps / _pullInputsWithPermit2 · Confidence: 35 · [both]

Permit2-mode sentinel signatures fail safely (revert) on an owner feeBps change between signing and execution. Allowance-mode sweeps using the sentinel have no signature at all, so the identical owner change is applied silently, up to the 3% cap, with no on-chain commitment to the rate the user expected.

[30] 12. _refundLeftoverInputs reverts the entire batch on a non-boolean 32-byte transfer return (abi.decode panic)

_refundLeftoverInputs · Confidence: 30 · [both]

abi.decode(ret, (bool)) panics (Panic(0x21)) on any 32-byte return value other than 0/1. This sits outside the only try/catch boundary in the flow, so it reverts the caller's entire sweep. All value in the reverted transaction belongs to the same msg.sender and is fully restored by the atomic revert — this is a self-inflicted availability bug (a batch containing a specific non-compliant token can never complete) rather than a fund-loss path, which is why it scores below the confidence threshold despite two independent phases finding it.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed. Not scored.

  • feeCollector not bound by the Permit2 witness — _settleOutput/setFeeCollector — Code smells: fee amount is witness-bound and capped, but fee destination is owner-mutable mid-flight — An owner can redirect where an already-signed sweep's fee is paid; no impact on the user's net output, purely a centralization observation.
  • Blind signing of route bodies — hashRoutes/PERMIT2_WITNESS_TYPE_STRING — Code smells: SweepRoute fields are cryptographically bound into the witness but never included in the human-readable EIP-712 type string — A compromised frontend could induce a signature over malicious (but allowlisted-target) routes with no visible wallet warning; compensating control is the owner allowlist.
  • Fee-on-transfer input tokens can never actually be swept — executeRoute — Code smells: the held-balance guard requires balanceOf(this) >= amountIn immediately after a pull, which a FoT token can never satisfy — Every FoT input route is silently skipped and (partially) refunded, contradicting the contract's stated purpose of handling "weird/unknown" dust; not a fund-loss bug.
  • Fee-on-transfer output token weakens minAmountOut — _settleOutput — Code smells: minAmountOut is checked against the router's balance delta, not what the recipient receives after a further on-transfer fee — Compounds finding 3 for FoT output tokens.
  • Native-output sweeps pay the protocol fee in WETH while the recipient receives unwrapped ETH; events log the ETH sentinel for both — _settleOutput — Code smells: asset-type mismatch between what feeCollector and recipient each receive, with identical event logging — Benign unless feeCollector integration assumes ETH.
  • Uncapped returndata copied from target.call and from the low-level refund transfer — executeRoute/_executeRoutesBestEffort/_refundLeftoverInputs — Code smells: no bound on copied returndata size before re-emitting/re-reverting it — A misbehaving allowlisted target or weird token could grief gas costs; bounded by the allowlist trust boundary on one side and self-inflicted on the other.
  • Custom inline-assembly blocks lack memory-safe annotations — executeRoute/_snapshotInputs — Code smells: both blocks are genuinely memory-safe (verified) but unannotated, unlike the inherited OZ blocks — cosmetic/optimizer-only.
  • route.target.call() never checks the target has code — executeRoute — Code smells: a codeless allowlisted target would report success with no swap — benign failure mode (input refunded or InsufficientOutput reverts), confined to an owner allowlist mistake.
  • Deadline check is inclusive (> not >=) — _validateParams — one-second-wider validity window than "expired at deadline" phrasing implies; no fund impact.
