[1] Zero-threshold signature check lets execution/ERC-1271 approval bypass with zero real signatures

Severity: Critical
Origin: [phase2-only] — independently found by 2 of 12 attack agents (execution-trace, periphery), then confirmed by the orchestrator directly against the live deployed contract
Location: _verifySignatures() (contracts/Multisig.sol:296), isValidSignature() (contracts/Multisig.sol:330)

Description: Both signature-checking entry points guard on signatures.length < threshold:

function _verifySignatures(bytes32 hash, Signature[] calldata signatures) internal view {
    if (signatures.length < threshold) revert ThresholdNotMet();   // line 296
    ...
}

function isValidSignature(bytes32 hash, bytes memory signatures) external view returns (bytes4 magicValue) {
    Signature[] memory sigs = abi.decode(signatures, (Signature[]));
    if (sigs.length < threshold) return 0xffffffff;                 // line 330
    ...
}

threshold is a uint256 that defaults to 0 and is only ever written inside initialize() (one-shot) or changeThreshold() (both reject 0). Nothing gates execTransaction/execBatchTransaction/isValidSignature on "has initialize() actually succeeded." When threshold == 0, an attacker supplying a literal empty Signature[] makes 0 < 0 evaluate false — the guard never fires, the subsequent per-signature loop runs zero iterations (no ECDSA/WebAuthn check, no signer-existence check, nothing), and the function falls through to success.

Proof of Concept — verified live against the deployed contract in scope (not a hypothetical; run directly via cast during this audit):

$ ADDR=0x346Db4e22dDF585c8f97496820c2106aE277df1e
$ cast call $ADDR "threshold()(uint256)"    --rpc-url $RPC   →  0
$ cast call $ADDR "signerCount()(uint256)"  --rpc-url $RPC   →  0
$ cast call $ADDR "nonce()(uint256)"        --rpc-url $RPC   →  0
$ cast balance $ADDR --rpc-url $RPC                          →  0

$ cast call $ADDR "initialize(address[],bytes32[],bytes32[],bytes32[],uint256)" \
    "[0x1111111111111111111111111111111111111111]" "[]" "[]" "[]" "1" --rpc-url $RPC
  → Error: execution reverted, data: "0xf92ee8a9"
  # 0xf92ee8a9 == keccak256("InvalidInitialization()")[:4] — confirmed via `cast sig "InvalidInitialization()"`.
  # This is the deployed *implementation* contract itself: its constructor called
  # _disableInitializers() (line 90), which OZ's Initializable permanently sets
  # _initialized = type(uint64).max on. initialize() can NEVER succeed on this
  # address — threshold is stuck at 0 forever.

$ cast call $ADDR "execTransaction(address,uint256,bytes,uint256,(uint8,address,bytes)[])" \
    0x1111111111111111111111111111111111111111 0 0x 99999999999 "[]" --rpc-url $RPC
  → SUCCEEDS (returns empty bytes, no revert)
  # A literal empty Signature[] array is accepted. Zero signatures, zero signers,
  # full execution authority.

This proves, against the actual on-chain bytecode and storage at the audited address, that execTransaction (and by identical logic, isValidSignature) currently accepts an empty signature array as fully authorized. The contract's balance is 0 ETH today, so no funds are at risk right now, but:

  • Any ETH ever sent to this exact address (e.g. by mistake, since it is publicly verified under the project's name on Etherscan) is immediately and trivially stealable by any caller via execTransaction(attacker, address(this).balance, "", <future deadline>, []).
  • A self-call variant is equally live: execTransaction(address(this), 0, abi.encodeCall(this.addEoaSigner,(attacker)), deadline, []) succeeds because the nested call's msg.sender == address(this) satisfies onlySelf — an attacker can permanently graft themselves into _signers/signerInfo with zero signatures (moot for legitimacy on this specific address only because initialize() is now permanently blocked, so no "real" signer set can ever be established here either).
  • The identical unguarded check in isValidSignature (line 330) means any observer can also mint a 0x1626ba7e ("valid ERC-1271 approval") for literally any hash, with zero signatures, against any instance where threshold == 0 — which includes every freshly cloned-but-not-yet-initialized instance of this contract, not just the disabled implementation.

Recommendation:

 function _verifySignatures(bytes32 hash, Signature[] calldata signatures) internal view {
-    if (signatures.length < threshold) revert ThresholdNotMet();
+    if (threshold == 0 || signatures.length < threshold) revert ThresholdNotMet();

 function isValidSignature(bytes32 hash, bytes memory signatures) external view returns (bytes4 magicValue) {
     Signature[] memory sigs = abi.decode(signatures, (Signature[]));
-    if (sigs.length < threshold) return 0xffffffff;
+    if (threshold == 0 || sigs.length < threshold) return 0xffffffff;

Given threshold can never legitimately be 0 after a successful initialize()/changeThreshold(), an explicit threshold == 0 check closes this for both the permanently-disabled implementation and any transiently-uninitialized clone.

[2] Unprotected/front-runnable initialize() on any non-atomically-deployed clone

Severity: High
Origin: [both] — Phase 1 (proxies + access-control checklists) and Phase 2 (5 of 12 attack agents: 2 direct findings, 3 leads promoted via multi-agent convergence)
Location: initialize() (contracts/Multisig.sol:101-126), constructor() (contracts/Multisig.sol:88-91)

Description: _disableInitializers() in the constructor only protects the logic/implementation contract itself (confirmed: this is exactly the mechanism blocking initialize() on the audited address, see Finding 1). initialize() is external, guarded only by OZ's initializer modifier (callable-once), with no caller/factory/deployer restriction. If a factory deploys a clone and calls initialize() in a separate transaction (or a counterfactual/CREATE2 clone address is known ahead of time), anyone can front-run and become the sole signer before the legitimate owner.

Proof of Concept: Factory deploys a clone at address C (tx A). Before the factory's follow-up initialize(...) call (tx B) lands, an attacker calls Multisig(C).initialize([attacker], [], [], [], 1), becoming sole signer with threshold 1. The legitimate init call now reverts (InvalidInitialization). Any funds later sent to C are drainable via execTransaction with the attacker's own signature.

Not demonstrable against the specific address in scope (its initialize() is already permanently disabled — see Finding 1), so this finding concerns the general contract pattern as it would apply to any clone/proxy instance deployed pointing at this implementation by an external factory (out of scope — no factory contract exists in the audited repo).

Recommendation:

+ address public immutable FACTORY;
+ constructor(address factory) {
+     FACTORY = factory;
+     _disableInitializers();
+ }

  function initialize(...) external initializer {
+     if (msg.sender != FACTORY) revert NotSelf();
      ...
  }

or guarantee atomic clone+init in the deployment factory (single transaction, no external-call window).

[3] No domain separation between execution-authorization signatures and ERC-1271 message-validation signatures

Severity: High (escalated from Phase 1's initial Medium assessment)
Origin: [both] — Phase 1 signatures checklist flagged the design gap; Phase 2 (4 of 12 attack agents: asymmetry, numerical-gap, trust-gap, flow-gap) independently completed the full exploit trace with concrete quoted code, converging on the identical mechanism from different angles
Location: getExecHash()/getBatchExecHash() (contracts/Multisig.sol:221-232), _verifySignatures() (contracts/Multisig.sol:295-322), isValidSignature() (contracts/Multisig.sol:328-358)

Description: The same signer set/threshold authorizes both on-chain execution and generic ERC-1271 attestations, with no domain/purpose tag distinguishing the two. For passkey signers, the WebAuthn challenge construction is byte-identical between the two paths:

// _verifySignatures (execution path), line 318:
bytes memory challenge = abi.encodePacked(hash);
if (!WebAuthn.verify(challenge, auth, qx, qy)) revert InvalidSignature();

// isValidSignature (message-validation path), line 352:
bytes memory challenge = abi.encodePacked(hash);
if (!WebAuthn.verify(challenge, auth, qx, qy)) return 0xffffffff;

A passkey signature set gathered to approve a routine execTransaction/execBatchTransaction call is therefore directly — with zero transformation — a valid isValidSignature(execHash, sigs) proof for that same hash, and isValidSignature has no nonce/expiry mechanism, so this replayable approval never becomes stale even after the real transaction executes and nonce advances. getExecHash/getBatchExecHash are public view, so the exact digest any signer will be asked to approve is fully precomputable off-chain by anyone. For EOA signers, the only separation is the fixed personal_sign prefix (MessageHashUtils.toEthSignedMessageHash) — a publicly-computable transform, not a designed domain separator — and one Phase-2 agent separately noted this also enables blind-signing phishing, since the raw digest has no EIP-712 structure for a wallet UI to render meaningfully to the human signer.

Proof of Concept: Threshold-many passkey signers approve a routine, innocuous-looking execTransaction(target, value, data, deadline, sigs) (e.g., a normal payment). The transaction's calldata (and hence sigs) is public once submitted (or observable pre-submission in the mempool). Anyone can compute execHash = getExecHash(target, value, data, deadline) and then call Multisig.isValidSignature(execHash, sigsBytes) — or present (execHash, sigsBytes) to any third-party contract that itself calls Multisig.isValidSignature on a hash it derives independently — receiving the ERC-1271 magic value 0x1626ba7e as a "valid multisig attestation" for that hash, with no expiry, for a purpose the signers never separately agreed to.

Impact caveat: This does not directly drain the audited contract on its own — isValidSignature never triggers a .call. Material harm requires an external protocol that accepts a caller/attacker-influenced hash and treats a valid isValidSignature result as a meaningful, freestanding attestation (e.g. a generic attestation registry, session/delegate-key registry, or any "verify a signature over a caller-supplied hash" integration) — a plausible but external-system-dependent precondition. The severity is escalated above Phase 1's initial Medium rating given the strength and unanimity of independent confirmation (4 separate attack agents, converging from distinct methodologies, all producing the identical concrete mechanism) and the complete absence of any mitigating factor for the passkey path specifically.

Recommendation:

+ bytes32 private constant EXEC_DOMAIN = keccak256("BG_MULTISIG_EXEC_V1");

  function getExecHash(address target, uint256 value, bytes calldata data, uint256 deadline)
      public view returns (bytes32)
  {
-     return keccak256(abi.encode(block.chainid, address(this), nonce, deadline, target, value, keccak256(data)));
+     return keccak256(abi.encode(EXEC_DOMAIN, block.chainid, address(this), nonce, deadline, target, value, keccak256(data)));
  }

Apply an equivalent distinct tag to getBatchExecHash so exec-approval digests can never collide with (or be trivially derived into) a digest an external ERC-1271 consumer would independently construct. Consider EIP-712 structured typed data more broadly, so compliant EOA wallets can render the actual approved action to signers instead of an opaque 32-byte blob.

[4] Unbounded _signers growth can permanently disable removeSigner

Severity: Medium
Origin: [phase1: access-control, dos] — re-examined against source for this reconciliation; no Phase-2 agent independently surfaced this
Location: _addSigner() (contracts/Multisig.sol:206-216), removeSigner() (contracts/Multisig.sol:189-196)

Description: No cap exists on signer count. removeSigner linearly scans _signers to find/swap-pop the target. A large enough signer set makes this scan exceed the block gas limit, permanently blocking any future signer removal. Triggering this requires an already-threshold-holding quorum to repeatedly add signers — this does not grant an outside attacker new capability beyond what threshold control already provides, but it is a genuine self-entrenchment / recovery-blocking footgun (a compromised or careless majority can make a bad signer set permanent).

Proof of Concept: A threshold-holding quorum calls addEoaSigner/addPasskeySigner many times (thousands of entries, via repeated execTransaction/execBatchTransaction). Once _signers.length is large enough, removeSigner's loop cannot complete within a block; no signer — honest or not — can ever be removed again.

Recommendation: Add a MAX_SIGNERS cap in _addSigner, and/or replace the linear scan in removeSigner with an index mapping (address => index) for O(1) removal regardless of signer count.

[5] Unbounded returndata copy on external .call() enables gas-griefing ("return bomb")

Severity: Medium
Origin: [phase1: dos, general, assembly] — corroborated by 3 of the 7 Phase-1 checklist agents; no Phase-2 agent independently surfaced this
Location: execTransaction() (contracts/Multisig.sol:253), execBatchTransaction() (contracts/Multisig.sol:278), _bubbleRevert() (contracts/Multisig.sol:286-291)

Description: target.call{value: value}(data) implicitly copies all returndata into ret with no cap; a callee can return/revert an arbitrarily large payload via inline assembly regardless of its ABI signature. Memory-expansion cost is quadratic in size. _bubbleRevert re-throws the same buffer on failure, so the cost applies on both success and failure paths. In a batch, one such call can make the whole signed batch un-executable within practical gas limits.

Proof of Concept: A signed-but-not-yet-executed target (whose code/behavior can change before execution — e.g. upgradeable, or simply a payee-supplied contract) implements receive()/fallback with assembly { return(0, 2000000) }. Executing the pre-approved call now costs tens of millions of gas in memory expansion alone, potentially exceeding available gas and permanently blocking that specific signed action.

Recommendation: Cap copied returndata via assembly (bounded returndatacopy) for both the success and revert-bubbling paths, e.g.:

(bool ok, ) = target.call{value: value}(data);
uint256 len;
assembly { len := returndatasize() }
bytes memory ret = new bytes(len > MAX_RET ? MAX_RET : len);
assembly { returndatacopy(add(ret, 0x20), 0, mload(ret)) }
if (!ok) _bubbleRevert(ret);

[6] Atomic batch execution: one reverting call blocks the entire signed batch

Severity: Low
Origin: [phase1: dos]
Location: execBatchTransaction() loop (contracts/Multisig.sol:277-282)

Description: The batch loop reverts the whole transaction on the first failing call. If a batch bundles independent actions and one target becomes unable to accept the call between signing and execution (blocklisted recipient, paused contract, reverting fallback), none of the batch's other, otherwise-valid calls execute, requiring a full re-signing ceremony.

Recommendation: Document as intended all-or-nothing semantics, or add an optional per-call allowFailure flag (Multicall3-style).

[7] credentialIdHash reuse across signers corrupts reverse-lookup for a still-active signer

Severity: Low
Origin: [both] — flagged by both Phase 1 checklist agents (general, access-control) and essentially all 12 Phase-2 attack agents (as either a direct finding or a lead) — the single most-corroborated observation across the entire two-phase audit
Location: _addSigner() (contracts/Multisig.sol:206-216), removeSigner() (contracts/Multisig.sol:182-187)

Description: _addSigner never checks whether a supplied credId is already assigned to a different active signer. If reused, credentialIdToAddress[credId] is silently overwritten to the newer signer while the older signer's credentialIdOf still holds the same hash. Removing the older signer then deletes credentialIdToAddress[credId], wiping the still-active newer signer's reverse-lookup entry. This is off-chain login/lookup impact only — _verifySignatures/isValidSignature never read these mappings, so on-chain fund safety and signature verification are unaffected.

Proof of Concept: Register passkey A with credId=X, later register passkey B (different qx/qy) also with credId=X (no uniqueness check exists at any call site). removeSigner(A) deletes credentialIdToAddress[X], breaking B's (still-valid signer) credential lookup even though B was never touched.

Recommendation:

  function _addSigner(address signer, bytes32 qx, bytes32 qy, bytes32 credId) internal {
      if (signer == address(0)) revert InvalidSigner();
      if (signerInfo[signer].exists) revert AlreadySigner();
+     if (credId != bytes32(0) && credentialIdToAddress[credId] != address(0)) revert InvalidSigner();
      ...
  }

  function removeSigner(address signer) external onlySelf {
      ...
      bytes32 credId = credentialIdOf[signer];
      if (credId != bytes32(0)) {
-         delete credentialIdToAddress[credId];
+         if (credentialIdToAddress[credId] == signer) delete credentialIdToAddress[credId];
          delete credentialIdOf[signer];
      }

[8] Deadline-bound execution griefable via block-stuffing before expiry

Severity: Low
Origin: [phase1: dos]
Location: execTransaction() (contracts/Multisig.sol:248), execBatchTransaction() (contracts/Multisig.sol:271)

Description: An attacker able to delay inclusion (block-stuffing, cheap on some L2s) until block.timestamp > deadline forces ExpiredSignature, requiring signers to re-run the signing ceremony. No funds-at-risk impact, operational/availability cost only.

Recommendation: Choose deadlines with adequate buffer; consider a same-nonce resubmission-with-new-deadline convenience path.

[9] isValidSignature results should not be assumed permanently valid if implementation is upgradeable

Severity: Info
Origin: [phase1: signatures]

If this logic contract sits behind an upgradeable proxy (implied by the Initializable pattern), a future upgrade could change validation semantics without changing the contract address. Integrators should not cache isValidSignature results as permanently authoritative.

[10] Signature-verification logic duplicated between _verifySignatures() and isValidSignature()

Severity: Info
Origin: [phase1: general]

The signer-matching/ordering/WebAuthn-dispatch loop is implemented twice, differing only in EOA hash preparation. Recommend factoring into one shared internal helper parameterized by the EOA digest-prep step, so both entry points stay in sync automatically.

[11] PUSH0 opcode default emission may break deployment on some chains

Severity: Info
Origin: [phase1: general]

Solidity ≥0.8.20 emits PUSH0 by default; not all EVM-compatible L2s/alt-chains support it. Confirm target-chain support or pin evmVersion if deploying broadly.

[12] .call to a codeless address silently "succeeds" and drops data

Severity: Info
Origin: [phase1: assembly]

A signed execTransaction targeting a not-yet-deployed (e.g. counterfactual CREATE2) or self-destructed address reports success and burns the nonce/emits Executed without the intended call logic ever running. Expected EVM behavior for a general-purpose multisig; document as expected.

[13] isValidSignature unbounded signature-array decode cost

Severity: Info
Origin: [phase2: economic-security] (lead)

No cap on Signature[] length before ABI-decoding full WebAuthnAuth structs per entry; a caller who controls the signatures blob could pad it to burn gas. No concrete profitable exploit constructed — a plausible but unverified griefing shape against a caller (e.g. bundler/relayer) that forwards attacker-supplied signature bytes.
