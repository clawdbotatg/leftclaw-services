Security Audit Report — Obol Validator Manager (OVM)

Target: ObolValidatorManager + ObolValidatorManagerFactory
Deployed instance audited: 0x2c26B5A373294CaccBd3DE817D9B7C6aea7De584 (Ethereum mainnet), verified source pulled from Sourcify
Context supplied by client: "OVM Factory" — https://docs.obol.org/learn/readme/obol-splits
Methodology: Two-phase audit — Phase 1 breadth (7 domain-checklist agents: general, precision-math, access-control, erc20, dos, defi-staking, assembly) → Phase 2 depth (12 independent attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation (this document).
Scope note: The verified source is a single flattened file containing well-known, heavily-audited Solmate (ERC20, ReentrancyGuard) and Solady (Ownable, OwnableRoles, SafeTransferLib) library code, plus two custom contracts that are the actual audit target: ObolValidatorManager (~511 lines) and ObolValidatorManagerFactory (~101 lines). All findings below concern the custom contracts and their use of the audited libraries / external system contracts (ETH2 deposit contract, EIP-7251 consolidation predeploy, EIP-7002 withdrawal predeploy). Library internals were reviewed for correct usage but not re-audited as novel code.

Reconciliation Summary

  • Unique (Contract, function) tuples raised across both phases: 16, all 16 covered in the unified findings below (0 dropped).
  • Overlap: 9 of 16 items were found independently by both Phase 1 and Phase 2 (marked [both] below) — strong corroboration, including one item independently rediscovered by 9 of the 19 total agents (7 Phase-1 + 12 Phase-2).
  • Phase-1-only: 4 items (mostly Info-level documentation/scoping notes).
  • Phase-2-only: 3 items, most notably the sharpest new finding of the audit (transfer() incomplete ownership handover).
  • Re-examined leads kept: all phase-unique items were re-confirmed against source during reconciliation; none were demoted.
  • No Critical or High severity findings. Every path that looked promising for unprivileged fund extraction was traced to a concrete dead end (checks-effects-interactions ordering, bounded/checked arithmetic, or an already-required role) by at least one and usually several independent agents across both phases. The confirmed findings are privilege-boundary and role-scoping issues (Medium) plus a cluster of low-severity/latent robustness gaps.

Findings

[1] setAmountOfPrincipalStake is gated by SET_BENEFICIARY_ROLE, letting that role redirect reward funds to itself

Severity: Medium
Origin: [both] — Phase 1: AccessControl-1, Staking-2. Phase 2: found independently by 6 of 12 agents (access-control, first-principles, asymmetry, boundary, trust-gap, flow-gap), some as direct FINDINGs.
Location: ObolValidatorManager.setAmountOfPrincipalStake() (line 1857), setBeneficiary() (line 1848), _distributeFunds() (lines 2160-2222)
Description: setAmountOfPrincipalStake overwrites amountOfPrincipalStake — the single variable _distributeFunds uses to decide how much of the contract's balance is paid to principalRecipient (as "principal") versus rewardRecipient (as "reward"). This function is gated by SET_BENEFICIARY_ROLE (bit 0x04) rather than a dedicated role. That role's name and its other function (setBeneficiary, which only changes the principal recipient address) imply a narrower scope than "control the entire principal/reward split." A holder of SET_BENEFICIARY_ROLE who was only meant to be trusted with address rotation can instead redirect funds that should go to rewardRecipient — a party protected by a separate, distinct role (SET_REWARD_ROLE).
Proof of Concept: Owner grants Alice SET_BENEFICIARY_ROLE (intending only "she can update the beneficiary address"). Alice calls setBeneficiary(alice) → principalRecipient = alice. Alice calls setAmountOfPrincipalStake(type(uint128).max). Anyone then calls distributeFunds(). In _distributeFunds, since _fundsToBeDistributed <= amountOfPrincipalStake is now always true, the entire distributable balance — including what should have been reward — is classified as principal and paid to Alice. rewardRecipient receives nothing.
Recommendation: Gate setAmountOfPrincipalStake behind onlyOwner, or introduce a dedicated role (e.g. a new bit distinct from both SET_BENEFICIARY_ROLE and SET_REWARD_ROLE) so address management and economic-split control are not conflated.

[2] sweep() lets the owner redirect the principal recipient's already-credited pull balance to an arbitrary address

Severity: Medium
Origin: [both] — Phase 1: General-3, AccessControl-2, Staking-5. Phase 2: found by 4 of 12 agents (execution-trace, periphery, trust-gap — as a direct FINDING, flow-gap).
Location: ObolValidatorManager.sweep() (lines 1876-1896)
Description: The pull-payment pattern (distributeFundsPull() → pullBalances[recipient]) exists to give a recipient a safe, self-custodied claim they alone can withdraw via withdrawPullBalance. However, sweep(beneficiary, amount) lets the owner redirect those already-credited funds: it always debits pullBalances[principalRecipient], but when beneficiary != address(0) (owner-only branch), it sends the ETH to that arbitrary address instead of to principalRecipient. This defeats the pull mechanism's safety guarantee for principal funds that have already been "distributed" into the recipient's ledger.
Proof of Concept: distributeFundsPull() credits pullBalances[principalRecipient] = 10 ETH. Before the recipient calls withdrawPullBalance, the owner calls sweep(attackerAddr, 0). _checkOwner() passes; sweepAmount = pullBalances[principalRecipient] = 10 ETH; balance zeroed; 10 ETH sent to attackerAddr instead of the rightful principal recipient.
Recommendation: Debit the pull balance of the actual destination being paid (require the caller to be that account, or restrict sweep's destination to principalRecipient only), rather than always debiting principalRecipient's balance while allowing redirection elsewhere.

[3] transfer() performs an incomplete ownership handover — roles and rewardRecipient survive

Severity: Medium
Origin: [phase 2 only] — execution-trace agent, reported as a direct FINDING with a concrete attack chain. Corroborates and sharpens Phase 1's General-2 (Low), which flagged the same code but without the pre-planted-role attack scenario.
Location: ObolValidatorManager.transfer() (lines 2009-2017), transferOwnership() (line 2080)
Description: transfer(newBeneficiary, newOwner) — presented as the mechanism to hand over an OVM instance to a new owner — only updates principalRecipient and the owner slot. It never revokes previously-granted operator roles (WITHDRAWAL_ROLE, CONSOLIDATION_ROLE, SET_BENEFICIARY_ROLE, RECOVER_FUNDS_ROLE, SET_REWARD_ROLE, DEPOSIT_ROLE) and never resets rewardRecipient. A new owner receiving an OVM (e.g. via a secondary transfer of a validator-manager position) inherits any previously-granted operators they never authorized and have no on-chain visibility into.
Proof of Concept: Owner A grants SET_REWARD_ROLE to an EOA they control, then calls transfer(newBeneficiary, B) to hand the contract to buyer B. Post-handover, the EOA still holds SET_REWARD_ROLE and calls setRewardRecipient(attackerAddr), redirecting all future reward distributions to the former owner's collaborator — with B, the new owner, unaware anything is wrong.
Recommendation: Have transfer() clear the role bitmap for all known role bits (or expose a bulk-revoke the new owner is required to invoke as part of accepting a handover), and/or document prominently that role grants and rewardRecipient are NOT reset by transfer()/transferOwnership().

[4] Instant, timelock-free redirection of all principal by the owner or SET_BENEFICIARY_ROLE

Severity: Medium
Origin: [phase 1 only] — AccessControl-3. Re-examined during reconciliation: confirmed against source; no phase-2 agent flagged this as a distinct issue (several touched adjacent territory in findings [1]/[2] but not this specific timelock angle), so it is kept as a Phase-1-only, re-confirmed item rather than dropped.
Location: setBeneficiary() (line 1848), transfer() (line 2009)
Description: principalRecipient can be changed instantly, with no timelock or delay window, by the owner or any SET_BENEFICIARY_ROLE holder. Combined with finding [1], a compromised or malicious owner/role-holder can front-run a distribution, redirect principalRecipient to themselves, and capture funds with no advance warning to the legitimate recipient.
Proof of Concept: Owner (or SET_BENEFICIARY_ROLE holder) calls setBeneficiary(attacker), then distributeFunds() — all principal ETH is sent to attacker in the same block.
Recommendation: Consider a timelock or 2-step confirmation on beneficiary changes, and/or require a multisig owner. This reflects inherent trust-model centralization rather than an unauthorized-third-party exploit; at minimum, document the trust assumption prominently for integrators/depositors.

[5] deposit() never verifies withdrawal_credentials point back to this contract

Severity: Medium
Origin: [both] — Phase 1: Staking-1 (defi-staking agent). Phase 2: boundary agent, LEAD, corroborating.
Location: ObolValidatorManager.deposit() (lines 1829-1845)
Description: deposit() forwards a caller-supplied withdrawal_credentials to the ETH2 deposit contract and unconditionally executes amountOfPrincipalStake += msg.value, without checking that the credentials actually designate this OVM (0x01/0x02 prefix + address(this)) as the withdrawal destination. DEPOSIT_ROLE is a role distinct from SET_BENEFICIARY_ROLE/owner, so a narrowly-scoped operator trusted only to fund validators could (via misconfiguration or malice) point a deposit's credentials elsewhere. The ETH then never returns to this contract, but principal accounting is inflated regardless — causing later legitimate rewards from other validators sharing this OVM to be misclassified as principal and routed away from rewardRecipient. This also exposes the classic DVT/DKG withdrawal-credential front-running risk (an operator who knows the pubkey in advance can pre-deposit with their own credentials).
Proof of Concept: DEPOSIT_ROLE holder calls deposit{value: 32 ETH}(pubkeyX, attackerCredentials, sig, root). amountOfPrincipalStake increases by 32 ETH regardless of where the funds actually end up. Later, 32 ETH of legitimate rewards from other validators sharing the OVM arrive; distributeFunds() classifies them as principal (since amountOfPrincipalStake is inflated) and pays principalRecipient, starving rewardRecipient.
Recommendation: Require withdrawal_credentials.length == 32 and that it encodes this contract's own address (withdrawal_credentials[0] == 0x01 or 0x02, and the trailing 20 bytes equal address(this)).

[6] _validateAndReturnFee() silently returns fee=0 and system-contract calls no-op against a code-less address

Severity: Low
Origin: [both] — Phase 1: General-1, Assembly-1 (with empirical forge verification). Phase 2: corroborated by 5 of 12 agents (economic-security, periphery, boundary, numerical-gap, flow-gap).
Location: _validateAndReturnFee() (lines 2132-2139), consumed by consolidate() (line 1941) and withdraw() (line 1973)
Description: _validateAndReturnFee performs feeContract.staticcall("") and only reverts if the call itself fails (!readOK). A low-level staticcall/call to an address with no deployed code returns (true, "") — no extcodesize/code.length check is performed on any of the three immutable system-contract addresses. If withdrawalSystemContract/consolidationSystemContract were misconfigured or point to a chain/pre-fork state where the Pectra predeploys don't exist, fee decodes to 0 (empirically verified: uint256(bytes32("")) == 0), which passes the fee > maxAllowedFee guard, and the subsequent request .call{value: fee}(...) also succeeds silently against the same no-code address. The transaction reports success (emits ConsolidationRequested/WithdrawalRequested, refunds msg.value) while no request was ever actually queued on the beacon chain.
Proof of Concept: Deploy with withdrawalSystemContract pointing at a no-code address. withdraw([pubkey], [amount], 0, recipient) with msg.value = 0 succeeds, emits the event, but nothing is queued.
Recommendation: Require code.length > 0 on all three system-contract immutables at construction; require feeData.length == 32 in _validateAndReturnFee before decoding.

[7] fundsPendingWithdrawal downcast guard checks the wrong value (latent, economically unreachable)

Severity: Low
Origin: [both] — Phase 1: Precision-1, corroborated by Assembly agent. Phase 2: corroborated by 6 of 12 agents (math-precision, access-control, invariant, asymmetry, numerical-gap, flow-gap) — near-unanimous independent agreement.
Location: _distributeFunds() line 2212/2214, guard at line 2192/2194
Description: fundsPendingWithdrawal = uint128(_memoryFundsPendingWithdrawal + _principalPayout + _rewardPayout). The only overflow guard (if (_fundsToBeDistributed > type(uint128).max) revert) bounds the new distribution amount, not the cumulative sum being downcast (pre-existing pending balance + new payouts). If that sum exceeded type(uint128).max (~3.4e38 wei ≈ 3.4e20 ETH), the cast would silently truncate, breaking the fundsPendingWithdrawal == sum(pullBalances) invariant.
Proof of Concept: Every one of the 6+ agents that traced this concluded it requires combined balances roughly 12 orders of magnitude beyond total ETH supply (~1.2e8 ETH) — not reachable in practice for a native-ETH contract.
Recommendation: For correctness/defense-in-depth, guard the actual downcast value: require(_memoryFundsPendingWithdrawal + _principalPayout + _rewardPayout <= type(uint128).max), or use SafeCast.

[8] Threshold-based aggregate-balance classification can reclassify accrued reward as principal (design tradeoff — needs protocol confirmation)

Severity: Low
Origin: [both] — Phase 1: General-LEAD, Staking-3. Phase 2: corroborated by 6 of 12 agents (math-precision, invariant, first-principles, asymmetry, numerical-gap, flow-gap), several supplying concrete numeric traces independently.
Location: _distributeFunds() (lines 2160-2222, branch at line 2176/2178)
Description: Classification of incoming ETH as "principal" vs. "reward" is based on the aggregate undistributed balance at the moment distributeFunds/distributeFundsPull (both permissionless) is called, not on the origin of each wei. Since receive() accepts ETH from anyone, a party can nudge the aggregate over principalThresholdWei with a small deposit, causing accrued reward ETH to be classified and paid as principal — this also wrongly decrements amountOfPrincipalStake by reward money.
Proof of Concept (numerical-gap agent's trace): principalThreshold = 16 ETH, amountOfPrincipalStake = 2048 ETH (active large-balance validator that never fully exits), 10 ETH of rewards have genuinely accrued (correctly sub-threshold, would be reward if distributed now). principalRecipient sends 6 ETH of dust via receive(), pushing the distributable balance to 16 ETH ≥ threshold. Anyone calls distributeFunds(): the entire 16 ETH (including the 10 ETH of real reward) is classified as principal and paid to principalRecipient; rewardRecipient receives 0 of the reward it was owed at that moment.
Assessment: This mirrors the documented 0xSplits/Obol Optimistic-Withdrawal-Recipient threshold design (mitigated operationally by calling distributeFunds frequently, before rewards accumulate past the threshold), and for validators that fully exit it can self-correct over the position's lifetime. Whether the residual risk (permanent misallocation for validators that never fully exit, e.g. post-Pectra max-effective-balance validators, or misallocation compounded by slashing — see the related Phase-1 Staking-3 slashing scenario) is acceptable depends on Obol's intended reward/principal semantics. Flagged for the team to confirm rather than asserted as a clean bug, given the volume of independent agents that converged on it with concrete numeric proofs.
Recommendation: Document the "distribute frequently" operational requirement prominently for integrators; consider whether classification could be driven by confirmed per-withdrawal amounts rather than aggregate live balance.

[9] Unbounded, atomic batch loops in consolidate()/withdraw() — self-inflicted gas DoS and all-or-nothing batch failure

Severity: Low
Origin: [phase 1 only] — DoS-1. Re-examined: confirmed against source (no explicit cap on pubKeys.length in withdraw, nor on requests.length in consolidate); no phase-2 agent raised this specific angle independently, kept as Phase-1-only re-confirmed item.
Location: consolidate() (lines 1914-1950), withdraw() (lines 1953-1983)
Description: Both functions iterate caller-supplied arrays with no upper bound, and any single failed system-contract call reverts the entire batch. However, both are gated by CONSOLIDATION_ROLE/WITHDRAWAL_ROLE, and the arrays are supplied by that same authorized caller — not third-party-injectable — making this self-inflicted rather than an attacker-triggerable DoS against another party.
Recommendation: Add an explicit upper bound on batch sizes for documented safe sizing; optionally support partial-failure processing.

[10] Single-step ownership transfer in transfer() and exposed renounceOwnership can permanently strand admin control

Severity: Low
Origin: [phase 1 only] — AccessControl-4. Re-examined: confirmed against source; distinct from finding [3] (this is about losing control entirely via typo/renounce, not about a former owner retaining latent control).
Location: transfer() (lines 2009-2017, uses single-step transferOwnership), renounceOwnership() override (line 2085)
Description: Although Solady's Ownable exposes a safe 2-step handover, transfer() uses the single-step transferOwnership, so a typo in newOwner (only the zero-address is guarded) permanently transfers ownership to an unrecoverable address. Separately, renounceOwnership() is exposed and, once called, permanently disables all onlyOwner capability — including future role grants/revocations — while existing role holders continue to function indefinitely.
Recommendation: Route transfer()'s ownership change through the existing 2-step handover, and/or consider overriding renounceOwnership to revert given the contract's reliance on an owner for role management.

[11] Push-mode distributeFunds() can be blocked by a reverting recipient — fully mitigated by the pull-mode fallback

Severity: Info
Origin: [both] — Phase 1: DoS-2, Staking-4. Phase 2: corroborated by economic-security agent (LEAD).
Location: _distributeFunds(PUSH)/_payout() (lines 2216-2235)
Description: In PUSH mode, a single reverting principalRecipient or rewardRecipient blocks the entire distribution (both payouts happen in one call using Solady's reverting, non-force safeTransferETH). This is not a permanent fund lock: distributeFundsPull() is always permissionless and callable, credits pullBalances with no external call, and recipients (or the owner, via sweep) can always recover through the pull path.
Recommendation: No change strictly required; document distributeFundsPull as the guaranteed-liveness path when recipients may be untrusted contracts.

[12] recoverFunds/withdrawPullBalance lack the nonReentrant guard used by other value-moving functions

Severity: Info
Origin: [both] — Phase 1: ERC20-1. Phase 2: corroborated by 5 of 12 agents (access-control, economic-security, invariant, asymmetry, trust-gap) — every agent that traced a concrete reentry attempt confirmed checks-effects-interactions ordering prevents any double-spend.
Location: recoverFunds() (line 1986), withdrawPullBalance() (line 1994)
Description: Unlike sweep, distributeFunds, distributeFundsPull, consolidate, and withdraw (all nonReentrant), these two functions are not. No agent across either phase could construct an exploit — both zero the relevant balance/state before making the external call — but the inconsistency is a defense-in-depth gap that would become load-bearing if either function's logic changes in the future.
Recommendation: Add nonReentrant to both functions for consistency and future-proofing.

[13] ObolValidatorManager constructor omits threshold-bounds validation that the factory enforces

Severity: Info
Origin: [both] — Phase 1: General-5. Phase 2: numerical-gap agent, corroborating.
Location: constructor (lines 1790-1814) vs. ObolValidatorManagerFactory.createObolValidatorManager() (lines 2330-2331)
Description: The factory rejects principalThreshold == 0 and > 2048 * 1e9 (gwei), but the OVM constructor itself accepts any uint64 value. A directly-deployed (non-factory) instance could have principalThreshold == 0 (classifying everything as principal) or an extreme value (breaking the intended threshold-vs-reward split entirely).
Recommendation: Move the bounds checks into the OVM constructor so every deployment path is validated, not just the factory path.

[14] principalThreshold upper-bound check allows exactly 2048 ETH despite "below 2048 ether" documentation

Severity: Info
Origin: [phase 1 only] — Precision-2. Re-examined: confirmed as written (> 2048 * 1e9 permits equality); no phase-2 agent raised this specific documentation mismatch.
Location: createObolValidatorManager() (line 2331)
Description: NatSpec/error naming says "must be below 2048 ether," but the check (> 2048 * 1e9) permits the boundary value itself. Harmless — no overflow, purely a policy-ceiling off-by-one against documentation.
Recommendation: Change to >= or update the documentation to "at most 2048 ether."

[15] _refundExcessFee can silently strand ETH on a failed refund; no zero-address check on excessFeeRecipient

Severity: Info
Origin: [phase 2 only] — economic-security, execution-trace (new: missing zero-address check), periphery, boundary agents, all as LEAD.
Location: _refundExcessFee() (lines 2151-2157), called from consolidate()/withdraw()
Description: If the excess-fee refund .call fails, the code only emits UnsentExcessFee — the ETH remains in the contract and gets folded into the next distribution as reward/principal rather than returned to the fee payer. Additionally, no check prevents excessFeeRecipient == address(0); a call to the zero address with value succeeds, silently "burning" the excess into general contract balance instead of triggering the UnsentExcessFee fallback path a caller might expect.
Recommendation: Consider requiring excessFeeRecipient != address(0), and/or crediting stranded excess to a pull balance rather than leaving it as undifferentiated contract balance.

[16] Batch fee-staleness assumption in consolidate/withdraw

Severity: Info
Origin: [phase 2 only] — invariant agent, LEAD, assessed as likely non-issue.
Location: consolidate()/withdraw(), fee read once via _validateAndReturnFee then reused per-operation in the loop.
Description: Reading the EIP-7251/7002 predeploy fee once and charging that same fee for every operation in the batch assumes the fee is constant within a transaction. The agent confirmed this matches the documented predeploy semantics (fee updates only at block boundaries), so this is noted as an external-dependency assumption rather than a defect.
Recommendation: None required; noted for completeness/documentation.

Confirmed Non-Issues (explicitly investigated, no finding)

  • Weird-ERC20 behaviors (fee-on-transfer, rebasing, ERC777 hooks, approve races, blocklists, decimals) — not applicable; the OVM is a pure-ETH contract and recoverFunds is the only, narrowly-scoped, non-accounting-critical ERC20 touchpoint.
  • Returndata bombing — not exploitable; all .call/.staticcall targets are immutable canonical system-contract addresses, never attacker-controllable.
  • Reentrancy on all guarded functions, and on the two unguarded ones (recoverFunds, withdrawPullBalance) — checks-effects-interactions ordering prevents any double-spend; confirmed independently by at least 7 different agents across both phases.
  • Fee/refund accounting in consolidate/withdraw — net-zero against contract balance; never dips into pull-earmarked funds; the msg.value >= totalFee check and refund logic hold under adversarial tracing.
  • fundsPendingWithdrawal == sum(pullBalances) and balance >= fundsPendingWithdrawal invariants — hold across every mutation path (deposit, distribute PUSH/PULL, sweep, withdrawPullBalance) except the latent, economically-unreachable case in finding [7].
  • Factory (ObolValidatorManagerFactory) — permissionless deployment is by design (no shared state to corrupt); parameter validation on owner/recipients/threshold is complete; uses CREATE (not CREATE2), so no metamorphic/address-prediction concerns; ENS registration calls use high-level interface calls that revert cleanly on a code-less registrar.
  • Assembly usage — no inline assembly written by the custom contracts; Solady/Solmate library assembly (used for Ownable, OwnableRoles, SafeTransferLib) is well-audited and correctly invoked.
  • Compiler/version footguns — pragma solidity =0.8.19, no PUSH0 emission, no L2/multichain push0 concern for this deployment.

Overall assessment: No unprivileged, no-precondition path to fund loss was found by either phase's agents, despite deep adversarial tracing across 19 independent agent runs. The confirmed issues cluster around role-scoping and privilege-boundary design — several distinct mechanisms (setAmountOfPrincipalStake, sweep's redirect branch, transfer's incomplete handover, instant beneficiary changes) all reduce to the same underlying theme: roles and ownership in this contract grant broader economic control than their names imply, and handovers/grants are not defensively scoped. We recommend the team prioritize findings [1]–[5] (all Medium) before further deployment, as they affect the integrity of the principal/reward split that is the contract's core economic promise.
