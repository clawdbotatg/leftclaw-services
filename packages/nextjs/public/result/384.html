[92] 1. Cross-tenant ShareOFT hijack via caller-controlled shareOftSaltOverride — attacker's wrapper becomes a permanent, unauthorized minter on a victim's ShareOFT

DeploymentBatcherPhase1Module.finalizePhase1Split · Confidence: 92 · Severity: High

Description
The ShareOFT's CREATE2 salt (deriveShareOftSalt(owner, shareSymbolLower, version), DeploymentBatcher.sol:473-479) and its constructor args (abi.encode(shareName, shareSymbolUpper, oftBootstrapRegistry, batcher), line 837) both omit creatorToken — and shareOftSaltOverride is a caller-supplied bytes32 accepted by both deployPhase1CoreWithSalt and finalizePhase1WithSalt. Because Phase 1a and Phase 1b are separate transactions, an attacker can read a victim's shareOftSalt (public via the phase1SplitStates mapping or the Phase1CoreDeployed event) and shareName/shareSymbol (visible in the victim's own Phase-1a calldata) after the victim's Phase 1a but before their Phase 1b, then race their own self-service deployment — using shareOftSaltOverride set to the victim's salt and copying the victim's exact shareName/shareSymbol — to deploy the ShareOFT first, with the attacker's own wrapper wired as an authorized minter (setMinter(attackerWrapper, true), line 854). When the victim's own finalizePhase1Split later runs, create2Deployer.deploy reverts on the address collision, and the catch branch (lines 843-849) adopts the attacker's already-deployed contract — its "verification" (verifyHash != shareOftInitCodeHash) is tautological (both sides are computed from the same inputs in the same call) so it cannot detect the substitution. The victim's finalize then adds the victim's wrapper as an additional minter (setMinter is additive, matching the codebase's set*(address,bool) grant/revoke convention used everywhere else) without removing the attacker's. The attacker's wrapper remains a permanently authorized minter on what is now the victim's official, registry-registered ShareOFT, letting the attacker mint/dilute it at will by depositing attacker-controlled (potentially worthless) attackerToken into their own wrapper.

Severity is High rather than Critical because the attack requires winning a front-running race in the public window between a victim's Phase 1a and Phase 1b transactions — a real, standard-MEV-tooling-winnable condition, but a precondition nonetheless.

Fix

 function deriveShareOftSalt(address owner, string calldata shareSymbolLower, string calldata version)
     external
     pure
     returns (bytes32)
 {
-    bytes32 base = keccak256(abi.encodePacked(owner, shareSymbolLower));
+    bytes32 base = keccak256(abi.encodePacked(creatorToken, owner, shareSymbolLower));
     return keccak256(abi.encodePacked(base, "CreatorShareOFT:", version));
 }

Add creatorToken to the salt preimage (and to shareOftArgs at line 837) so the ShareOFT's CREATE2 identity is properly namespaced per-deployment. As defense-in-depth, also replace the tautological verifyHash check (line 846-847, see Finding #6) with a genuine greenfield check on the adopted contract (e.g. assert its vault/minter set is unconfigured) before wiring it. Consider removing caller control over shareOftSaltOverride entirely, since it is what makes the collision trivial to force rather than requiring an actual preimage collision.

[95] 2. whitelistPayoutRouterOnWrapper / setPayoutRouterShareOftNoFees have no caller authorization — any address can inject itself into an in-flight deployment's fee-exemption/whitelist during the batcher-ownership window

DeploymentBatcher.whitelistPayoutRouterOnWrapper / DeploymentBatcher.setPayoutRouterShareOftNoFees · Confidence: 95 · Severity: High

Description
Both functions (DeploymentBatcher.sol:2028-2033, 2037-2042) are external with no msg.sender check — their only guard is that the batcher currently owns the target (IOwnableView(wrapper/shareOFT).owner() == address(this)). Every other state-changing function on this contract is gated by _requireOwner(params.owner) or onlyProtocolTreasury; these two are not. The wrapper and ShareOFT are deployed with tempOwner = address(this) in Phase 1 and are only transferred to owner/protocolTreasury at the end of finalizePhase2Execution (lines 1140-1146) — a separate, later transaction. This is not an edge case: the multi-transaction window exists on every single deployment, by design. Any third party can call these functions during that window to permanently whitelist an arbitrary address on the wrapper, or mark an arbitrary address fee-exempt (OperationType.NoFees = 2) on the ShareOFT — a flag/entry that persists after ownership transfers to treasury, with no revocation path anywhere in the contract. This finding was independently re-derived, blind, by 10 of the 20 total hunting agents across both phases (Phase 1: general, access-control; Phase 2: access-control, execution-trace, invariant, periphery-adjacent boundary/asymmetry agents, first-principles, flow-gap-hunter, trust-gap-hunter).

Fix

-function whitelistPayoutRouterOnWrapper(address wrapper, address payoutRouter) external {
+function whitelistPayoutRouterOnWrapper(address wrapper, address payoutRouter) external onlyProtocolTreasury {
     if (wrapper == address(0) || payoutRouter == address(0)) revert ZeroAddress();
     address wrapperOwner = IOwnableView(wrapper).owner();
     if (wrapperOwner != address(this)) revert WrapperOwnerMismatch(wrapper, wrapperOwner);
     ICreatorOVaultWrapper(wrapper).setWhitelist(payoutRouter, true);
 }

-function setPayoutRouterShareOftNoFees(address shareOFT, address payoutRouter) external {
+function setPayoutRouterShareOftNoFees(address shareOFT, address payoutRouter) external onlyProtocolTreasury {
     if (shareOFT == address(0) || payoutRouter == address(0)) revert ZeroAddress();
     address shareOwner = IOwnableView(shareOFT).owner();
     if (shareOwner != address(this)) revert ShareOftOwnerMismatch(shareOFT, shareOwner);
     ICreatorShareOFT(shareOFT).setAddressType(payoutRouter, 2);
 }

(Alternatively gate via _requireOwner bound to the specific deployment's owner, if the payout-router configuration is meant to be creator-controlled rather than treasury-controlled.)

[75] 3. CREATOR/USDC Uniswap v3 pool initialization price is unvalidated and front-runnable

DeploymentBatcherPhase3Helper.deployPhase3Strategies · Confidence: 75 · Severity: Medium

Description
params.initialSqrtPriceX96 (DeploymentBatcher.sol:175-181) is accepted with no sanity check against the protocol's own creator-token oracle (resolved moments later for Charm/Ajna wiring, but never used to bound the pool price). Because createPool/initialize on the canonical Uniswap v3 factory are permissionless, a third party can create and initialize the CREATOR/USDC pool ahead of the batcher's Phase 3 transaction with a skewed price; getPool(...) then returns the attacker's pool and the batcher's own initialize branch is silently skipped entirely. This pool becomes the price anchor for the Charm vault/strategy deployed immediately after, letting an arbitrageur extract value once the strategy provides liquidity at the wrong ratio.

Fix

+uint160 refSqrtPriceX96 = _oracleSqrtPriceX96(params.creatorToken, usdc); // resolve before the pool block
 address v3Pool = IUniswapV3Factory(uniswapV3Factory).getPool(params.creatorToken, usdc, V3_FEE_TIER);
 if (v3Pool == address(0)) {
     if (params.initialSqrtPriceX96 == 0) revert MissingInitialSqrtPriceX96();
+    _requireWithinBand(params.initialSqrtPriceX96, refSqrtPriceX96);
     v3Pool = IUniswapV3Factory(uniswapV3Factory).createPool(params.creatorToken, usdc, V3_FEE_TIER);
     if (v3Pool == address(0)) revert V3PoolMissing();
     IUniswapV3Pool(v3Pool).initialize(params.initialSqrtPriceX96);
+} else {
+    (uint160 spot,,,,,,) = IUniswapV3Pool(v3Pool).slot0();
+    _requireWithinBand(spot, refSqrtPriceX96); // reject a front-run/mispriced existing pool
 }

[72] 4. ShareMesh Uniswap v4 hook whitelist is populated from unvalidated caller input and never reconciled with the pool's actual hook

DeploymentBatcherShareMeshHelper.deployShareMeshLpManager · Confidence: 72 · Severity: Medium

Description
params.hooksToApprove[] and params.poolHook (DeploymentBatcher.sol:405-411) are approved on a freshly deployed hook registry independently of poolKey.hooks, which is read separately from the caller-supplied params.ccaLaunchArm.getPoolKey() (line 418). [55] 5. ShareOFT/creatorToken transfer-fee not reconciled across the CCA/auction/Solana/vesting split legs

DeploymentBatcherPhase2Module.finalizePhase2Execution / launchDeferredAuctionExecution · Confidence: 55 · Severity: Medium (contingent — see caveat)

Description
The batcher's own code proves the ShareOFT has a per-address transfer-fee mechanism (setAddressType(_, 2 /*NoFees*/), line 2041, explicitly commented "mark fee-exempt"). The vesting leg is fee-safe — LinearVesting4626.seed() records token.balanceOf(this), the actually-received amount. The LP-reserve transfer to the CCA (line 1116) and the retained auction allocation (later validated by balanceOf(this) < amount in launchDeferredAuctionExecution, line 1253) both use the nominal pre-transfer split amount with no balance-delta reconciliation. If the batcher is not itself marked fee-exempt on the ShareOFT, every deployment's CCA/auction legs are silently under-funded, and in the worst case the retained balance falls below the recorded auctionAmount, permanently bricking launchDeferredAuction for that deployment (compounding Finding #9/#10 below, since hasActivePendingAuction then has no clear path). This concern was independently raised by 9 of 20 total hunting agents across both phases, each from a different specialty lens (precision-math, erc20, erc4626, economic-security, invariant, asymmetry, boundary, numerical-gap-hunter, flow-gap-hunter).

Confidence caveat: the ShareOFT's actual fee model, and whether the batcher/vesting/CCA addresses are auto-exempt as protocol-internal addresses, could not be verified — the ShareOFT implementation is out of scope (deployed via an external bytecode store, not present in this snapshot). The volume of independent, blind, cross-lens corroboration is what keeps this at Medium/55 rather than as a bare Lead.

Fix

+uint256 balBefore = IERC20(params.shareOFT).balanceOf(params.ccaLaunchArm);
 IERC20(params.shareOFT).safeTransfer(params.ccaLaunchArm, result.lpReserveAmount);
+uint256 received = IERC20(params.shareOFT).balanceOf(params.ccaLaunchArm) - balBefore;
+// use `received`, not the nominal `lpReserveAmount`, in any downstream accounting

Or, more simply, mark the batcher (and any intermediate holding contracts) NoFees on the ShareOFT before distribution.

[70] 6. Hardcoded 200k executor gas and zero native value on the Solana-bound OFT lzReceive option

DeploymentBatcherPhase2Module._bridgeShareAllocationToSolana · Confidence: 70 · Severity: Medium

Description
extraOptions (DeploymentBatcher.sol:1219-1221) are built from a compile-time DEFAULT_SHARE_BRIDGE_GAS_LIMIT = 200_000 gas and 0 native value. A Solana-side OFT credit commonly needs lamports to create/rent the recipient's associated token account; supplying 0 provides none, and neither figure is tunable per-destination without redeploying the Phase 2 module. Because the Base-side debit happens before Solana-side execution, under-provisioning risks the cross-chain message failing on delivery after the source tokens are already gone, with no in-contract recovery path.

-    OptionsBuilder.newOptions(), DEFAULT_SHARE_BRIDGE_GAS_LIMIT, 0
-),
+extraOptions: OptionsBuilder.addExecutorLzReceiveOption(
+    OptionsBuilder.newOptions(), shareBridgeGasLimit, shareBridgeNativeValue
+), // both admin-configurable via a treasury setter, not compile-time constants

[80] 7. Solana-lane misconfiguration or failure reverts the entire finalizePhase2 — every deployment is permanently coupled to bridge liveness

DeploymentBatcherPhase2Module.finalizePhase2Execution / _bridgeShareAllocationToSolana · Confidence: 80 · Severity: Medium

Description
The Solana leg (30% of every deposit) always runs; any misconfiguration (runtime.enabled == false, unset solanaDestination/peer, msg.value below the quoted fee) reverts the entire finalizePhase2 call, including the creatorToken pull — there is no path to finalize a deployment without successfully bridging. Once IOFT.send itself succeeds, the Base-side debit is final with no in-contract recovery if delivery later fails on the Solana side.

Fix
Decouple the bridge from the rest of finalize: on a bridge-config failure, escrow the 30% allocation for later manual/permissioned dispatch instead of reverting the whole deployment, and expose an explicit retry/rescue entry point for a send that succeeded on Base but failed to land on Solana.

[60] 23. LinearVesting4626's declared NotSeeded error is never enforced

  • Vault/wrapper CREATE2 deploys lack a collision-tolerant recovery path (root cause of Finding #9) — DeploymentBatcherPhase1Module.deployPhase1Core — Code smells: unlike the OFTBootstrapRegistry (existence-checked) and ShareOFT (try/catch adopt) deploy sites in the same function, the vault/wrapper deploys have neither. — If the external create2Deployer is permissionlessly callable by anyone (unverified, out of scope), a front-run occupation of the deterministic address would brick that (creatorToken, owner, version) tuple with no recovery; contingent on external deployer access control.
