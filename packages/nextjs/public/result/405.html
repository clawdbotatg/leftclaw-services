A. Executive summary

Overall risk rating: Medium. No Critical or High finding survived independent verification.
The accounting core (escrow conservation, dispute-bond ledger, milestone/stream/hour-block
vesting, staking dual-accumulators, treasury fee-bucket conservation) was attacked by 18
independent agents across two blind phases and held up in every case traced to real code —
this is a well-engineered, heavily defensive codebase for the core money-movement paths. The
Medium findings are concentrated in governance/liveness edges (a single EOA owner, an
instant unbounded dispute-pause switch, an arbitration-dispute state that can trap a worker's
funds if a mutually-selected arbitrator later goes silent or self-disqualifies) and one
confirmed deployment/wiring defect (TaskScopeRegistry bound to the wrong TaskRegistry).

Is this safe for production use? Conditionally — yes for the escrow/payment core, no
until: (1) ownership is moved off a single EOA to a multisig/timelock before meaningful value is
at risk, (2) the dispute-EVIDENCE trap (F-02) and the "direct hire requires consent" bypass
(F-04) are fixed, and (3) TaskScopeRegistry is redeployed correctly.

Immediate recommendations:

  • Transfer ownership of all 8 Ownable2Step contracts to a multisig/timelock before allowing
    meaningful escrow value into the system. (F-03)
  • Redeploy TaskScopeRegistry pointed at the live TaskRegistry — the current instance is
    permanently wired to a superseded registry and cannot be repaired (immutable). (F-01)
  • Add a fallback/escape path for disputes stuck in EVIDENCE state before real funds flow
    through the marketplace at scale. (F-02)
  • Fix the direct-hire consent bypass (F-04) before advertising direct-hire as consent-gated.
  • No on-chain funds are at risk today — both the live and stale TaskRegistry report
    taskCount() == 0 (block 48680219), i.e. the protocol has not yet processed a single real task.
    This audit was performed on a pre-launch (or freshly-launched, zero-activity) deployment.

F-01 — TaskScopeRegistry permanently wired to a stale/superseded TaskRegistry

Severity: Medium | Confidence: 97 | Origin: [both] — independently confirmed
on-chain (cast call) in this audit's own Phase-0 pass, and corroborated by 8 of 12 Phase-2
agents and Phase-1 AC-1.
Location: TaskScopeRegistry.sol:10 (address public immutable taskRegistry), set at
constructor :17-20; read at :30 (acceptanceCriteriaHashes), :45 (taskCount), :51
(getTask(...).poster).

Live on-chain read (block 48680219): TaskScopeRegistry.taskRegistry() == 0xa6050C3dE02b4A5038B5F1fA5BeFbceC1aa4e189,
which is not the canonical manifest's TaskRegistry (0xCe3eBC0B256831BD270AD2D1b039293d24Dbe319).
The address it does point to is itself a live, real TaskRegistry-shaped contract (responds to
owner(), arbitration(), escrow(), taskCount()) but wired to a different EscrowVault
(0x73207410a64D50eb761c79CeaB22F93A22CDdF94) and arbitration module
(0xaE4D9151cC2126AfFEDD9f821AB75eD10a7f0283) that appear nowhere in the canonical manifest —
consistent with an earlier/superseded deployment of the whole stack.

taskRegistry is immutable, so this cannot be fixed by calling a setter — it is a permanent
defect in the deployed TaskScopeRegistry at 0xf7bD3Fec…a9d0. TaskRegistry holds no
back-reference to TaskScopeRegistry (grep-confirmed one-directional dependency), so no core
protocol fund path is affected — but the effect on TaskScopeRegistry itself is total: setScope
authorizes the caller as poster against the wrong registry's getTask(taskId), and validates the
scope hash against the wrong registry's acceptanceCriteriaHashes(taskId).

Impact today: both the live and the stale TaskRegistry report taskCount() == 0 (pre-launch),
so no live task's scope has yet been mis-authorized. Impact once tasks exist: an honest poster
of live task N cannot publish its scope (_requirePoster reads the wrong registry's poster for
id N, which will not equal the caller, so setScope reverts "TaskScope: not poster"); if the
stale registry is independently used and produces overlapping task IDs, a party on that stale
system could publish an unrelated scope string under the same numeric ID that off-chain UIs would
attribute to the live task.

Recommendation: Redeploy TaskScopeRegistry with its constructor argument pointed at the live
TaskRegistry 0xCe3eBC0B256831BD270AD2D1b039293d24Dbe319. The current instance cannot be repaired
and should be treated as abandoned; update any off-chain integration pointing at it.

F-02 — A dispute stuck in EVIDENCE state has no fallback if the seated arbitrator goes silent or self-disqualifies; timeout then awards 100% to the poster

Severity: High | Confidence: 85 | Origin: [phase2: flow-gap agent], re-examined
and confirmed against real source in this reconciliation pass (bundle line numbers from the raw
agent output did not match the real files and were re-derived below).
Location: ArbitrationModule.sol — proposeArbitrator() seats into EVIDENCE at :306-309;
resolveDispute() requires msg.sender == d.assignedArbitrator (:348) and
agentDepositVault.meetsEntryMinimum(msg.sender) (:353-356); assignFallbackResolver() requires
d.state == DisputeState.OPEN (:367) — not reachable once state is EVIDENCE; escalate()
likewise requires OPEN (:315); resolveTimedOut() accepts OPEN || EVIDENCE (:334) after
absoluteDeadline (21 days) and always finalises with workerBps = 0 (:343, comment at
:340-342 confirms this is an intentional "no ruling ⇒ return to poster" default).

Verified mechanism: once both dispute parties mutually consent to the same arbitrator (each
independently calls proposeArbitrator with the same address), the dispute moves OPEN → EVIDENCE
(:306-309) and the only two ways out are (a) that specific arbitrator calling resolveDispute,
or (b) anyone calling resolveTimedOut after the 21-day absoluteDeadline. There is no path back
to OPEN, no re-proposal, and no fallback-resolver seating once in EVIDENCE. If the seated
arbitrator simply never calls resolveDispute — or deliberately withdraws their own
AgentDepositVault balance below MIN_ENTRY_BALANCE so meetsEntryMinimum fails even if they
change their mind (:353-356) — the dispute is provably stuck until the 21-day timeout, which then
awards 100% of the frozen escrow to the poster (workerBps=0) regardless of whether the worker
actually delivered.

Proof of concept / attack sequence:

  1. Worker delivers real value on a STREAMING task; poster refuses to pay and opens a dispute
    (TaskRegistry.openDispute → ArbitrationModule.openDispute), freezing escrow.
  2. Poster proposes a specific arbitrator (could be a low-cost address that meets registration
    requirements — self-registration only needs a $25 deposit + 1-day cooldown per
    registerArbitrator/registerArbitratorGlobal). Worker, believing this is a fair path forward
    (or under social/time pressure — the worker also wants a ruling rather than defaulting to
    resolveTimedOut's poster-favorable outcome), calls proposeArbitrator with the same address →
    dispute enters EVIDENCE.
  3. The (colluding, bribed, or simply unresponsive) arbitrator never calls resolveDispute, or
    withdraws their AgentDepositVault deposit below $25 so any later attempt to rule reverts
    "Arbitration: arbitrator ineligible".
  4. assignFallbackResolver and escalate both revert (state != OPEN). The worker has no
    permissionless recourse.
  5. After 21 days, anyone calls resolveTimedOut → _finalise(d, id, 0, false) →
    escrow.split(taskId, worker, poster, 0) sends 100% of the frozen escrow to the poster.
  6. The worker's genuinely-earned value (streamed/hour-block accrual that was frozen at dispute
    open) is lost with no recourse once EVIDENCE is reached.

Why High and not Critical: this requires the worker's own initial consent to a specific
arbitrator (not a zero-precondition attack — a diligent worker who refuses to consent and instead
waits for the permissionless assignFallbackResolver after day 7, staying in OPEN, retains the
fallback-resolver protection). It also requires a full 21-day wait. It is rated High rather than
Medium because the loss is total (100% of frozen value) and the triggering conditions (arbitrator
apathy or deliberate self-disqualification) are entirely plausible in an adversarial or even
merely unreliable-arbitrator setting, with no code-level mitigation whatsoever once EVIDENCE
is reached.
Recommendation: Allow assignFallbackResolver (or an equivalent re-proposal path) to fire once
resolutionDeadline has passed even from EVIDENCE state if the seated arbitrator has not ruled
within some grace window, rather than only from OPEN; and/or have resolveTimedOut default to a
neutral (e.g., 50/50, or fallback-resolver-ruled) split rather than workerBps=0 when a dispute
had already progressed past mutual arbitrator selection.

F-03 — Single EOA controls all 8 Ownable2Step contracts and is the sole arbitration-recovery proposer

Severity: Medium | Confidence: 85 | Origin: [phase1: access-control], corroborated
structurally by this audit's own on-chain read (owner 0x418D156C7e6f17685926539a03b3F579b171804B,
confirmed EOA — codesize 0 — via cast codesize).

Every privileged action across the protocol (one-shot wiring, setFallbackResolver,
qualifyBootstrapArbitrator, setDisputeOpeningPaused, setBuybackExecutor,
activateStaking, and — critically — ArbitrationRecoveryCoordinator.proposeRecovery, the only
entrypoint into the delayed-recovery path since direct rotation is hard-disabled everywhere) is
gated on this one key. renounceOwnership() is disabled on all 8 contracts (always reverts), and
several rotations carry a 2-day delay — real protections — but there is no backup proposer and no
multisig. Two concrete consequences: (1) if the key is lost, the arbitration module can never be
replaced again (no alternate proposer exists); (2) if the key is compromised, an attacker can
deploy a validly-wired malicious arbitration module, wait out the 2-day recovery delay, and then —
as the new onlyArbitration authority — direct dispute-bond settlement and escrow splits.

Recommendation: Move ownership of all 8 contracts to a multisig (ideally with a timelock)
before allowing meaningful value into the system; add a documented backup/guardian proposer for
ArbitrationRecoveryCoordinator.proposeRecovery so recovery liveness does not depend on one key.

F-04 — A direct-hire task silently reopens to public claiming after the invited worker leaves or is dismissed pre-acceptance, defeating "direct hire requires worker consent"

Severity: Medium | Confidence: 80 | Origin: [phase2: invariant/asymmetry agents],
re-derived and corrected against real source in this reconciliation (the raw agent claim
conflated claimTask's missing directHire guard with an incorrect claim about startWork; the
verified mechanism below is the actual bug).

Verified mechanism: createTask (direct hire) sets directHire[taskId]=true, t.state = CLAIMED, t.worker = <invited address>. Before the invited worker calls acceptDirectHire, either
the poster can call dismissWorker (TaskRegistry.sol:286-302, requires only state==CLAIMED) or
the invited worker can call leaveTask (:304-318, same state requirement) — both reset
t.worker = address(0), t.state = POSTED, but neither clears directHire[taskId]. Now the
task is POSTED with directHire[taskId] still true. claimTask (:256-273) has no
directHire check at all — it only requires state==POSTED, worker==0, and
msg.sender != poster — so any address can now call claimTask and become t.worker, state → CLAIMED. That new, uninvited claimer then satisfies acceptDirectHire's onlyWorker guard
(msg.sender == t.worker, now the new claimer) and directHire[taskId]==true (still set), so they
can call acceptDirectHire (:426-438) and activate the task exactly as if the poster had
originally selected them.
Impact: the poster's explicit choice of counterparty (the entire point of "direct hire") is
silently discarded the moment the originally-invited worker declines via leaveTask/dismissWorker
rather than declineDirectHire — the task becomes public-claim, and the poster has no way to
re-establish exclusive selection (re-dismissing the new claimer just reopens it to the next public
claimer, indefinitely).
Recommendation: Clear directHire[taskId] (and require the task go through startWork rather
than acceptDirectHire) whenever dismissWorker/leaveTask resets a task to POSTED, or block
claimTask on tasks where directHire[taskId]==true.

F-05 — Dispute bond is forfeited to the arbitrator on any ruling regardless of who prevails, contradicting the module's own top-level NatSpec

Severity: Medium | Confidence: 75 | Origin: [phase2: trust-gap agent], verified
against real source.
Location: Contradiction between ArbitrationModule.sol:32-33 ("Refunded if the initiator
prevails (or on timeout); forfeited to the arbitrator otherwise") and the actual implementation at
:484-513 (_settleDisputeBond, whose own inline comment at :484-485 correctly describes what
the code does: "a fixed service fee paid for any ruling, independent of initiator, winner, or
BPS. With no ruling it is fully refunded").

The code forfeits the initiator's bond to the arbitrator on every ruled dispute
(byArbitrator == true, line :496), even when the initiator wins outright (workerBps fully in
their favor). Only a timeout (byArbitrator == false) refunds. This means: a worker who is forced
to dispute a withholding poster (see F-06, UPFRONT mode has no other recourse) loses their bond
(5% of locked value, clamped $1–$100) to the arbitrator even after being fully vindicated —
converting what the top-level spec comment promises as a loser-pays mechanism into a
pay-to-litigate tax on the party correctly using the dispute system.
Recommendation: Either fix the top-level NatSpec to describe the actual "flat service fee"
model (if intended), or change _settleDisputeBond to refund the prevailing party's bond and
charge the losing party's, matching the documented spec.

F-06 — resolveTimedOut sends 100% of frozen escrow to the poster with no accrual credit for STREAMING/HOUR_BLOCKS workers; combined with F-02/F-05 this makes UPFRONT/streaming disputes structurally poster-favorable

Severity: Low | Confidence: 60 | Origin: [both] — Phase-1 GEN-2 and 7 of 12 Phase-2
agents independently converged on this.
Location: ArbitrationModule.resolveTimedOut() :331-344 vs. EscrowVault.settleExpired()
:278-322 (which does pay time-accrued entitlement before refunding remainder on ordinary
expiry — the asymmetry is specifically in the dispute-timeout path, not the ordinary-expiry path).

Standalone this is Low severity: the worker's defense is the permissionless
assignFallbackResolver, available days 7–21 while the dispute is still OPEN — a diligent worker
who declines to consent to a specific arbitrator and instead waits for the neutral fallback is
protected. It rises to the High severity of F-02 only once EVIDENCE is reached and the seated
arbitrator stalls. Reported separately here because the underlying default (workerBps=0 with no
accrual credit) is itself inconsistent with the ordinary-expiry path's behavior and worth fixing on
its own terms even after F-02 is addressed.
Recommendation: See F-02's recommendation; additionally, when timing out a STREAMING/
HOUR_BLOCKS dispute, compute the worker's deadline-bounded accrued entitlement (as
settleExpired does) rather than defaulting to zero.

F-07 — Balance-health watchdog (_enforceBalanceHealth/pause/auto-delete/platform-penalty) is unreachable dead code

Severity: Low | Confidence: 90 | Origin: [both] — Phase-1 GEN-1 and 11 of 12
Phase-2 agents independently derived and proved this identical fact, the single strongest
cross-agent convergence in the entire audit.
Location: AgentDepositVault.meetsTaskReservation() :177-181, consumed by
TaskRegistry._firstUnderfunded() :860-862 and _enforceBalanceHealth() :824-851.

meetsTaskReservation returns taskReservations[taskId][agent] >= MIN_TASK_BALANCE && deposits[agent] >= totalReserved[agent]. The first clause is always true while bound
(taskReservations is set to exactly MIN_TASK_BALANCE at bind, AgentDepositVault.sol:213, and
only ever deleted whole). The second clause is a global invariant preserved by every
deposit-reducing path: reserveTask (the only writer that increases totalReserved) requires
availableBalance >= required first (:212); _withdrawTo caps at availableBalance
(:133-135); debitAccessFee/debitDismissFee/debitLeaveFee each require
availableBalance >= MIN_ENTRY_BALANCE + fee before debiting; consumeDisputeBondReservation
decrements deposits and totalReserved by the identical amount (:291-294). Hence
deposits[agent] >= totalReserved[agent] cannot be violated by any reachable sequence, so
_firstUnderfunded always returns address(0), and the entire pause → emergencyTopUp →
_finalizePausedTask (auto-delete) → applyPlatformPenalty (7-day block + reputation reset) chain
never fires. No fund loss results (the reservation model already over-collateralizes), but a
documented safety mechanism does not work as designed — likely because the intended check was live
availableBalance(agent) >= MIN_TASK_BALANCE, not the static reservation constant.
Recommendation: If the watchdog is meant to be functional, key it off live availableBalance
rather than the immutable per-task reservation; otherwise remove the dead machinery
(emergencyTopUp/pullEmergencyTopUp/pause state/penalty path) to avoid a false sense of
protection. Also note: ReputationRegistry.slashVerifierBond and recordReplacementPenalty have
no live caller anywhere in the system (confirmed by grep across all 9 contracts) — verifier bonds
can never actually be slashed, and the worker-replacement penalty signal can never fire (the
replacement flow itself is hard-disabled, TaskRegistry.sol requestReplacement/
assignReplacementWorker unconditionally revert).

F-08 — setDisputeOpeningPaused is an instant, unbounded owner censorship lever over new disputes

Severity: Low | Confidence: 70 | Origin: [phase1: access-control].
Location: ArbitrationModule.setDisputeOpeningPaused() :149-157; enforced only in
openDispute() :206.

Owner can freeze all new dispute openings instantly and indefinitely (no delay, no expiry). This
audit specifically walked whether pausing could also block legitimate arbitration-module recovery
(the brief's stated concern) — it does not: recovery requires the outgoing module to already
be paused as a precondition (ArbitrationRecoveryCoordinator._validateSafeOutgoing), so pausing
enables rather than blocks recovery. The residual risk is one-directional: an UPFRONT-mode worker
with no self-service claim path and a non-cooperative poster has no recourse if disputes are
paused — expireTask at deadline refunds 100% to the poster with no arbitration ever available.
Recommendation: Add a maximum pause duration, or move the switch behind the multisig
recommended in F-03.

F-09 — Unbounded poster-chosen streamRatePerSecond can overflow the vesting multiplication and permanently lock a task's own escrow

Severity: Low | Confidence: 55 | Origin: [both] — Phase-1 MATH-1 and 3 of 12
Phase-2 agents (math-precision, invariant, numerical-gap) independently derived this.
Location: EscrowVault._checkpointStream() (streaming vesting) and settleExpired()
(STREAMING branch); validateTaskTerms only requires streamRate > 0, no upper bound.

newlyVested = Δt * streamRatePerSecond is computed before the unvested cap is applied. A
poster who commits an extreme rate (baked into their own settlement digest, so self-inflicted) can
cause this multiplication to overflow and revert once any time has elapsed, bricking
claimStream, streamRelease, and the expireTask → settleExpired exit path for that task —
locking the escrowed USDC with no admin rescue. No third party benefits or is harmed; the poster
harms only their own escrow (and the worker's claim on it).
Recommendation: Bound streamRate in validateTaskTerms (e.g. streamRate <= totalAmount) so
the multiplication cannot overflow for any plausible task duration.

F-10 — Treasury-leg hard safeTransfers have no rotation path if the recipient is USDC-blocklisted

Severity: Low | Confidence: 70 | Origin: [phase1: dos + erc20].
Location: AgentDepositVault.debitAccessFee/debitDismissFee/debitLeaveFee (treasury leg);
TreasuryRouter.flushBuybackShare (recoverable — buyback executor is rotatable).

By design, user-facing payouts use a deferred pull-ledger (_payOrDefer) so a blocklisted
worker/poster/arbitrator cannot brick a state transition — verified to hold in every reachable
payout path. The protocol's own treasury leg uses a hard, non-deferred safeTransfer, and
AgentDepositVault.treasury has no rotation mechanism (set once via wire()). If Circle ever
blocklists TreasuryRouter, every postTask/claimTask/createTask/dismissWorker/leaveTask
call reverts permanently, with no on-chain remediation. This requires an external trusted-issuer
action, not an attacker precondition.
Recommendation: Route the treasury USDC leg through the same deferred-ledger pattern, or add a
delayed treasury-rotation path mirroring the existing buyback-executor rotation.

F-11 — Two USDC/AZL pull sites skip the fee-on-transfer balance-delta guard used everywhere else (latent — token is fixed)

Severity: Low | Confidence: 85 | Origin: [both] — Phase-1 ERC20-1/2/GEN-3, and
independently found again by a Phase-2 boundary agent.
Location: EscrowVault.depositFor() and TreasuryRouter._collectAzlAccessFee().

Every other pull site (AgentDepositVault.topUp, UnionStakingVault.stake, the treasury flushes)
measures the received balance delta and reverts on short delivery. These two sites credit the
nominal amount directly. Not currently exploitable — postTask/createTask hard-constrain the
escrow token to agentVault.usdcToken() (fixed, non-fee-on-transfer Base USDC), and AZL is
similarly fixed and non-taxing — but inconsistent defense-in-depth.
Recommendation: Apply the same balance-delta measurement used at every other pull site.

F-12 — Missing reentrancy guard in UnionStakingVault.stake/unstake (conditional on AZL ever gaining transfer hooks)

Severity: Low | Confidence: 60 | Origin: [phase1: defi-staking].
Location: UnionStakingVault.stake()/unstake() — AZL transfer occurs before _checkpoint()
re-anchors the caller's accumulator debt; the vault has no ReentrancyGuard.

Not reachable with the current AZL token (standard OZ ERC20, no hooks); would become exploitable
(double-counted credit/reward accrual) if AZL is ever upgraded to a hook-bearing token.
Recommendation: Add ReentrancyGuard to UnionStakingVault and mark stake/unstake
nonReentrant, or checkpoint before transferring.

Leads (confidence < 50 or unconfirmed preconditions — not rated findings)

  • Consent-reset griefing in proposeArbitrator: either dispute party can reset the
    counterparty's recorded consent by proposing a different (but still eligible) arbitrator,
    potentially stalling selection indefinitely — bounded by the permissionless
    assignFallbackResolver after day 7 while still OPEN. [phase2: access-control agent]
  • distributeRevenue epoch front-running: a griefer can call the permissionless
    distributeRevenue the instant any dust fee accrues, consuming the 7-day epoch stamp and
    delaying the week's real fee distribution by up to a further epoch. No funds lost, only timing
    degraded. [phase2: economic-security agent]
  • Self-dealt arbitrator reputation farming: an entity controlling poster+worker+arbitrator
    addresses can cheaply mint resolvedCount/reputation via self-disputes on minimum-qualifying
    ($1+) tasks, potentially building a legitimate-looking track record before soliciting real
    parties' consent (relevant precondition for F-02's social-engineering angle). Real parties must
    still independently consent, so this is a precondition-builder, not a closed exploit.
    [phase2: trust-gap agent]
  • _accrue advances lastAccrualAt even when periodCredits truncates to zero, forfeiting
    sub-threshold credit accrual under very low totalStaked — negligible at any realistic stake
    size (100M+ AZL). [phase1: defi-staking STAKE-7, phase2: trust-gap/numerical-gap]
  • Settlement "digest" (SETTLEMENT_DOMAIN_V2) performs no actual security function — there is
    no ecrecover/EIP-712/signer anywhere in the system; the caller supplies every field directly
    as arguments and the digest, so the check can only fail if the caller deliberately mismatches
    their own inputs. Removing it would change no on-chain security property. Flagged only because
    the naming may give false confidence of replay/tamper protection that does not exist.
    [phase1: signatures SIG-1, phase2 corroboration]

Verified sound (attacked, did not break)

  • Escrow conservation (totalReleased ≤ totalDeposited) across UPFRONT/MILESTONE/STREAMING/
    HOUR_BLOCKS, including boundary timestamps at deadline.
  • Dispute-bond reserve-vs-consume monotonicity (reserved on totalAmount, consumed on
    lockedBalance ≤ totalAmount) — never underflows, never double-reserves across concurrent
    tasks (per-task-per-agent keyed reservations, AgentDepositVault.taskReservations[taskId][agent]).
    Explicitly revalidates the brief's "collateral/bond reservations cannot be reused across
    concurrent tasks."
  • escrow.split/refund recipients are the dispute's immutable snapshotWorker/snapshotPoster
    (captured at openDispute), not caller-supplied — verified at
    ArbitrationModule.sol:393 (escrow.split(d.taskId, d.snapshotWorker, d.snapshotPoster, workerBps)). Explicitly revalidates that brief item.
  • submitProof reverts if block.timestamp > t.deadline (TaskRegistry.sol:513) — no optimistic
    post-deadline milestone payout path exists. Explicitly revalidates that brief item.
  • Zero-stake reward carry, late-whale Action-Credit capture, and just-in-time staking around
    reward notifications were each independently attacked with concrete numeric traces by multiple
    agents (Phase-1 defi-staking + 2 Phase-2 agents) — all three of the brief's named staking
    protections hold as designed.
  • Blocklisted recipients cannot brick required state transitions for user-controlled addresses
    (deferred pull-ledger design verified at every forced payout site) — the residual exposure is
    confined to protocol-controlled addresses themselves being blocklisted (F-10), an external-issuer
    scenario, not a user-triggerable one.
  • Failed reputation side-effects cannot block required settlement — try/catch isolation around
    bond settlement, reputation recording, and the registry callback in ArbitrationModule._finalise,
    each independently retryable via retrySideEffects.
  • Ownership renunciation is disabled (reverts) on all 8 Ownable2Step contracts — cannot brick
    critical contracts via renounce.
  • Settlement digests do bind chain ID, contract address (registry), worker, all payment terms,
    and the acceptance-criteria hash (verified field-by-field in _computeSettlementDigest) — though
    see the Leads section for why this digest carries no actual authentication weight.
  • Timeout paths do not award arbitrator reputation or resolvedCount without a ruling
    (resolveTimedOut's byArbitrator=false skips _tryRecordReputation entirely) and refund
    rather than forfeit the bond on timeout specifically (contrast F-05, which is about the
    ruled-but-lost case, not the timeout case).
  • No source/bytecode mismatch on any of the 9 contracts (all BaseScan "Exact Match").
    TaskRegistry is EIP-170 compliant with a 465-byte margin.
  • Wiring-order dependency on setArbitrationRecoveryCoordinator's cross-checks: cannot pass
    vacuously on address(0)==address(0) because the ARC constructor itself requires all four
    peer addresses to be non-zero contracts before it can be deployed.
  • One-shot ("set-once") setters carry no front-running race — all are onlyOwner; the only
    permissionless "accept" steps are the second leg of explicit owner-proposed rotations.
