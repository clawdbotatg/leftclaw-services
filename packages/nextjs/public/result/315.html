🔐 Security Review — HoprStake

Chain: Gnosis Chain (100) · Address: 0x912f4d6607160256787a2ad40da098ac2afe57ac · Methodology: Two-phase audit — Phase 1 breadth (6 checklist agents: general, precision-math, ERC20, staking, ERC721, access-control) → Phase 2 depth (12 independent attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation with live on-chain verification.

Client question

"Find a way for someone to withdraw the HOPR token (an ERC677 token at 0xd057604a..., i.e. LOCK_TOKEN/xHOPR) which are held by this contract."

Direct answer: No path was found for an unprivileged actor to redirect LOCK_TOKEN to their own address — unlock()'s transfer always pays the account parameter (never msg.sender), the ERC677 deposit hook's sender cannot be spoofed, and the owner-only reclaim functions cannot be invoked by an outside party. The actual, verified, high-impact bug runs in the opposite direction: Finding 1 shows that any unprivileged third party can permanently freeze a staker's LOCK_TOKEN inside the contract — and on-chain verification (below) indicates this is not theoretical: a large share of the contract's holdings appear to already be stuck today.

Findings

[100] 1. Permissionless claimRewards() permanently bricks unlock(), freezing staked LOCK_TOKEN and escrowed Boost NFTs forever

HoprStake.unlock (via _claim/_sync) · Confidence: 100 · [both phases — 12/12 Phase 2 agents, 5/6 Phase 1 agents]

Description
unlock() (line 1219-1235) unconditionally calls _claim(account) (line 1227) before returning the staker's principal and any escrowed Boost NFTs:

function unlock(address account) external {
    require(block.timestamp > PROGRAM_END, "HoprStake: Program is ongoing, cannot unlock stake.");
    uint256 actualStake = accounts[account].actualLockedTokenAmount;
    uint256 virtualStake = accounts[account].virtualLockedTokenAmount;
    _sync(account);
    accounts[account].actualLockedTokenAmount = 0;
    accounts[account].virtualLockedTokenAmount = 0;
    totalLocked -= actualStake;
    _claim(account);                                        // <-- unconditional, can revert
    IERC20(LOCK_TOKEN).safeTransfer(account, actualStake);   // <-- never reached if _claim reverts
    for (uint256 index = 0; index < redeemedNftIndex[account]; index++) {
        nftContract.transferFrom(address(this), account, redeemedNft[account][index]);
    }
    emit Released(account, actualStake, virtualStake);
}

_claim() (line 1315-1326) hard-reverts whenever there is nothing new to pay out:

uint256 amount = account.cumulatedRewards - account.claimedRewards;
require(amount > 0, "HoprStake: Nothing to claim");

PROGRAM_END (1642424400, Jan 17 2022) is a fixed timestamp already permanently in the past. _getCumulatedRewardsIncrement() (line 1273-1298) short-circuits to 0 forever once account.lastSyncTimestamp >= PROGRAM_END (line 1275). So the first _sync performed for any account at/after PROGRAM_END permanently freezes its cumulatedRewards; every later _claim call for that account computes amount == 0.

claimRewards(address account) (line 1210) is public with no access control on account — any third party can call claimRewards(victim) for any staker, at any time. This is not theft on its own (the reward is paid to victim), but it pins claimedRewards == cumulatedRewards. From that moment, every future unlock(victim) call — by anyone, forever — reverts inside _claim with "Nothing to claim", unwinding the entire transaction, including the state zeroing, the LOCK_TOKEN transfer, and the Boost-NFT return loop. There is no other function that returns a staker's principal or NFTs, and the owner's reclaimErc20Tokens(LOCK_TOKEN) cannot rescue it either, since totalLocked still (correctly, since the revert undoes the decrement) accounts for the frozen stake.

This requires no capital and no privilege, and is equally reachable through entirely ordinary usage — any staker who calls "Claim Rewards" before "Unlock/Withdraw" (a common two-button staking UI pattern) self-triggers the identical permanent freeze. Because PROGRAM_END passed over four years ago, this has had ample time to manifest against real, live-staked value.

A second, independent trigger reaches the exact same failure mode: _claim's other guard, require(availableReward >= amount, "HoprStake: Insufficient reward pool."), fires identically if the reward pool is ever insufficient to cover an account's owed amount at the moment unlock() runs — this blocks every remaining staker contract-wide, not just accounts that already claimed.

Proof of Concept

  1. Alice stakes X LOCK_TOKEN before PROGRAM_END (accounts[alice].actualLockedTokenAmount = X), possibly with redeemed Boost NFTs.
  2. Any time after PROGRAM_END (i.e., any time in the last 4+ years, including today), anyone calls claimRewards(alice). _sync finalizes cumulatedRewards; _claim pays Alice her earned wxHOPR and sets claimedRewards = cumulatedRewards.
  3. Alice (or anyone) calls unlock(alice). _sync now computes increment 0 (already clamped past PROGRAM_END). _claim(alice) computes amount = 0 and reverts "HoprStake: Nothing to claim".
  4. The entire unlock(alice) transaction reverts. Every future call behaves identically — alice's X LOCK_TOKEN and any escrowed Boost NFTs are permanently unrecoverable.

On-chain verification (performed live against the deployed contract, Gnosis Chain block 47088635, 2026-07-08):

totalLocked()                          = 4,337,527.43 xHOPR
LOCK_TOKEN.balanceOf(HoprStake)         = 4,109,123.36 xHOPR
availableReward()                       = 0.4899 wxHOPR
REWARD_TOKEN.balanceOf(HoprStake)       = 0.4899 wxHOPR   (exactly equals availableReward)

The reward pool (availableReward) is almost completely depleted (0.49 wxHOPR left) while totalLocked still records over 4.3 million xHOPR of principal not yet returned to stakers. This pattern — nearly all rewards already paid out, but the overwhelming majority of principal still locked, more than four years after the program ended — is consistent with a large number of stakers having already called claimRewards() (or having had it called for them) and subsequently being unable to complete unlock(). It also means the "insufficient availableReward" trigger described above is now live: with only 0.49 wxHOPR remaining in the pool, essentially any staker with a nonzero pending reward who has not yet triggered the first failure mode will likely fail unlock() via the second one instead. This finding appears to already be actively impacting real funds, not merely a theoretical risk.

Fix

 function _claim(address _account) private {
     Account memory account = accounts[_account];
     uint256 amount = account.cumulatedRewards - account.claimedRewards;
-    require(amount > 0, "HoprStake: Nothing to claim");
+    if (amount == 0) {
+        return;
+    }
     accounts[_account].claimedRewards = accounts[_account].cumulatedRewards;
     require(availableReward >= amount, "HoprStake: Insufficient reward pool.");
     availableReward -= amount;
     IERC20(REWARD_TOKEN).safeTransfer(_account, amount);
     emit Claimed(_account, amount);
 }

Keep a require(amount > 0) in the standalone claimRewards() entry point only, if a revert-on-nothing-to-claim UX is desired there — never let unlock()'s principal-withdrawal path depend on there being a nonzero (and fully-covered) reward claim. Given real user funds appear to already be affected on the live deployment, the client should treat this as urgent: a migration/rescue mechanism may be needed to recover principal for accounts already stuck, since this logic bug cannot be patched in an already-deployed, non-upgradeable contract.

[70] 2. reclaimErc20Tokens can drain the entire wxHOPR reward pool owed to stakers

HoprStake.reclaimErc20Tokens · Confidence: 70 · [Phase 1: general, defi-staking, access-control — 3/6 agents; Phase 2: 10/12 agents raised this, demoted to lead under the strict unprivileged-trigger gate since it requires owner action with no unprivileged amplifier]

Description
The LOCK_TOKEN branch correctly excludes committed principal before sweeping:

if (tokenAddress == LOCK_TOKEN) {
    difference = IERC20(LOCK_TOKEN).balanceOf(address(this)) - totalLocked;
} else {
    difference = IERC20(tokenAddress).balanceOf(address(this));
}
IERC20(tokenAddress).safeTransfer(owner(), difference);

For every other token — including REWARD_TOKEN (wxHOPR) — the entire balance is swept, with no subtraction of availableReward, the counter tracking rewards already earmarked for stakers. This is an owner-gated action (not triggerable by an unprivileged third party), which is why Phase 2's strict attacker-mindset gates demoted it to a lead — but it is a genuine, verifiable code-level asymmetry with the analogous LOCK_TOKEN protection in the very same function, and a mismanaging or compromised owner could break reward payouts for every remaining staker. Currently the live reward pool is only 0.49 wxHOPR (see Finding 1's on-chain check), so the present blast radius is small, but the code gap would matter again if the pool is ever refueled.

Fix

 if (tokenAddress == LOCK_TOKEN) {
     difference = IERC20(LOCK_TOKEN).balanceOf(address(this)) - totalLocked;
+} else if (tokenAddress == REWARD_TOKEN) {
+    difference = IERC20(REWARD_TOKEN).balanceOf(address(this)) - availableReward;
 } else {
     difference = IERC20(tokenAddress).balanceOf(address(this));
 }

[70] 3. reclaimErc721Tokens has no protection against seizing a staker's already-redeemed Boost NFT

HoprStake.reclaimErc721Tokens · Confidence: 70 · [Phase 1: defi-staking, erc721, access-control — 3/6 agents; Phase 2: 8/12 agents raised this, demoted to lead under the same admin-action gate as Finding 2]

Description

function reclaimErc721Tokens(address tokenAddress, uint256 tokenId) external onlyOwner nonReentrant {
    IHoprBoost(tokenAddress).transferFrom(address(this), owner(), tokenId);
}

No exclusion exists for tokenAddress == address(nftContract) or for tokenIds recorded in any redeemedNft[account][...]. The owner can seize a Boost NFT a staker legitimately redeemed and is still owed back at unlock(). This compounds directly with Finding 1: if a staker's NFT is seized this way, their unlock() NFT-return loop reverts on the missing token even if Finding 1 is fixed, permanently blocking recovery of their principal and every other NFT in the same call. Owner-gated (no unprivileged amplifier), so demoted to lead under Phase 2's strict gates, but a real and easily-fixed asymmetry with the analogous LOCK_TOKEN protection.

Fix

 function reclaimErc721Tokens(address tokenAddress, uint256 tokenId) external onlyOwner nonReentrant {
+    require(tokenAddress != address(nftContract), "HoprStake: Cannot reclaim escrowed Boost NFTs");
     IHoprBoost(tokenAddress).transferFrom(address(this), owner(), tokenId);
 }

Leads

High-signal trails for manual review — origin-tagged, not independently scored.

  • onTokenTransfer trusts the ERC677 callback's _value instead of a measured balance delta — HoprStake.onTokenTransfer — [both phases] — Code smells: accounts[_from].actualLockedTokenAmount += _value; totalLocked += _value; assumes LOCK_TOKEN never applies a transfer fee or rebases. Not exploitable against the current, presumed-standard xHOPR token; would only matter if LOCK_TOKEN's transfer semantics changed.
  • No nonReentrant guard on unlock()/claimRewards()/tokensReceived() — [both phases] — REWARD_TOKEN (wxHOPR) is ERC777-compatible via ERC1820 registration, so _claim's safeTransfer could trigger a recipient hook. Every agent that traced a concrete reentry path found checks-effects-interactions (state zeroed/updated before the external call) blocks a double-spend. Defense-in-depth only.
  • Unbounded Boost-NFT bookkeeping loops (redeemedFactorIndex in _getCumulatedRewardsIncrement; redeemedNftIndex in unlock's NFT-return loop) — [both phases] — No cap on either index; a large count could gas-DoS an account's own future sync/unlock calls. Demoted from an initial High rating on re-examination: new Boost-NFT redemption requires block.timestamp <= PROGRAM_END, which has permanently passed, so this can now only matter for an account that already accumulated an unusually large redeemed-NFT count before Jan 2022 — not confirmed on any specific account within this audit's on-chain verification scope (would require a full historical event-log scan). Client should check redeemedNftIndex(account) for any large historical staker before assuming this is moot.
  • reclaimErc20Tokens(LOCK_TOKEN) currently reverts due to a live balance/accounting deficit — HoprStake.reclaimErc20Tokens — [discovered via direct on-chain verification during reconciliation, not by either blind phase] — On-chain, totalLocked (4,337,527.43 xHOPR) exceeds the contract's actual LOCK_TOKEN balance (4,109,123.36 xHOPR) by ~228,404 xHOPR (~5.3%). difference = balanceOf(this) - totalLocked therefore underflows and reverts under Solidity 0.8 checked arithmetic — the owner cannot currently call this function for LOCK_TOKEN at all. Under this contract's own internal logic, balance and totalLocked should move in exact lockstep (every deposit and every successful unlock() adjusts both by the same amount), so a deficit implies an external event reduced the contract's LOCK_TOKEN balance outside of this contract's own code paths (e.g., a token-level migration or burn on xHOPR itself) — recommend the client confirm with the HOPR team. Practical implication: even after Finding 1 is fixed, the contract is presently under-collateralized, so the last stakers to attempt unlock() would still fail on an insufficient-balance revert.
  • onERC721Received ignores the ERC721 operator parameter — HoprStake.onERC721Received — [Phase 1 only, erc721] — Any address holding transfer approval over another user's Boost NFT could force it into the staking program without the owner's direct action. Historical-only: the redemption window (block.timestamp <= PROGRAM_END) has permanently closed, so this can no longer be triggered against any account going forward.
  • Boost factor read live from nftContract.boostOf, not snapshotted at redemption — HoprStake._getCumulatedRewardsIncrement — [Phase 2 only, trust-gap] — If the out-of-scope IHoprBoost contract's boostOf is admin-mutable, a HoprBoost-side admin could retroactively alter reward rates for already-redeemed tokens. IHoprBoost's implementation is out of scope for this engagement and was not reviewed.
  • Single-step Ownable with no timelock on admin functions — [Phase 1 only, access-control] — A mistaken transferOwnership()/renounceOwnership() permanently disables lock() and both reclaim* functions. Does not affect core user-facing unlock/sync/claimRewards paths.
  • Stale redeemedNftIndex/redeemedFactorIndex never reset after unlock() — [Phase 1 only] — Not currently exploitable (blocked by Finding 1's _claim revert and the closed redemption window), but would need addressing alongside a Finding 1 fix to avoid a fresh double-return bug.
  • Reward accrual floors to zero for dust-level stakes or sub-second sync intervals — [Phase 1 only, precision-math] — One-directional value loss (never gain) from integer division by FACTOR_DENOMINATOR; not exploitable for fund extraction.
