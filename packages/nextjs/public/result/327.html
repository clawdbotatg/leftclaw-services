Findings

[C-1] creatorFallbackSettle() lets the creator unilaterally redirect the entire prize pool to arbitrary addresses

Severity: High
Origin: [both] — phase1: access-control, general · phase2: math-precision agent (FINDING), trust-gap-hunter agent (FINDING), first-principles + flow-gap-hunter (leads)
Location: creatorFallbackSettle() L352-361, _settle() L419-452

Description: Once 30 days pass after seasonDeadline, creatorFallbackSettle() requires only onlyCreator — no oracle involvement, no verification the oracle actually failed to respond, and _settle() never checks that winners[i] are members of players[]. The 30-day gate is purely time-based and every deployed league is guaranteed to eventually satisfy it. A creator can simply withhold cooperation on settle(), wait 30 days, and name themselves (or anyone) as 100%-bps "winner," draining every player's deposit — with no oracle involvement and no requirement that the payout bear any relation to actual season results. This directly contradicts the contract's own documented invariant: "Neither party can redirect funds without the other's agreement." The missing winner-membership check is a genuine access gap in the fallback mechanism's design, not merely expected admin-trust behavior — the documented intent is "creator settles real results alone if oracle is unreachable," not "creator pays themselves the entire pool regardless of results."

Proof of Concept:

  1. Paid pot, 100 players deposit $25 USDC each → prizePool = 2,500,000,000 ($2,500).
  2. Season ends. Oracle signs the correct standings and makes the signature available (per the documented flow), but the creator simply never submits settle().
  3. At seasonDeadline + 30 days + 1, creator (satisfying onlyCreator/onlyActive) calls creatorFallbackSettle(winners=[creator], bpsSplit=[10000]).
  4. In _settle(): total == 10000 passes the split check; the single winner (also the last winner) receives remaining == pool — the entire $2,500 goes to the creator, with zero oracle input and zero recourse for the 100 depositors.

Recommendation: Require winners[i] ∈ players[] (or, for free pots, restrict to the intended recipient set), and/or require the fallback payout to match a previously oracle-attested standings snapshot rather than an arbitrary creator-supplied list.

[C-2] Unconditional payout loops in _refundAll() and _settle() let one blocked recipient DoS every other recipient

Severity: High
Origin: [both] — phase1: erc20, dos (2 checklists) · phase2: economic-security, execution-trace, invariant, boundary, first-principles (5 FINDING agents) + math-precision, boundary (leads)
Location: _refundAll() L454-474 (called by cancelLeague()), _settle() L439-451 (called by settle()/creatorFallbackSettle())

Description: Both functions loop over recipients calling usdc.safeTransfer with no per-iteration isolation (no try/catch, no pull-payment fallback). USDC has an issuer-enforced blacklist (a real, precedented Circle/FiatToken capability for sanctioned or flagged addresses); a transfer to a blacklisted address reverts. A single blacklisted player or winner reverts the entire cancelLeague()/settle()/creatorFallbackSettle() transaction, blocking payout to every other, unrelated participant. This is most severe for _refundAll(): its recipient set (players[]) is deterministic and cannot be altered on retry, so cancelLeague() becomes permanently unusable once any depositor is blacklisted — the only recourse for the other honest players is waiting the full 180-day emergencyWithdraw() window (correctly pull-based and per-player-isolated, unaffected by this bug). The _settle() variant is marginally more recoverable since oracle+creator (or creator alone, via fallback) can in principle re-sign a corrected payload excluding the blacklisted winner — but that still requires off-chain coordination and blocks the original settlement attempt entirely.

Proof of Concept:

  1. Player deposits into a paid pot, is later added to USDC's blacklist (unrelated compliance/sanctions event).
  2. Creator calls cancelLeague(). _refundAll()'s loop reaches the blacklisted player's safeTransfer, which reverts; the entire transaction — including the status = Cancelled write — rolls back.
  3. Every subsequent call to cancelLeague() reverts identically, since players[] cannot be modified once Active. All non-blacklisted players' refunds are frozen for up to 180 days.
  4. The identical mechanism applies to _settle(): a blacklisted address anywhere in a signed winners[] list blocks payout to every other listed winner in that same call.

Recommendation: Convert both payout paths to a pull-based pattern (mirroring emergencyWithdraw()'s isolation), e.g. credit a pendingRefund/pendingClaim mapping on transfer failure instead of reverting the batch:

mapping(address => uint256) public pendingRefund;

function _refundAll() internal {
    uint256 fee = entryFee;
    for (uint256 i = 0; i < players.length; i++) {
        address player = players[i];
        if (hasDeposited[player]) {
            hasDeposited[player] = false;
            pendingRefund[player] += fee;
            emit RefundIssued(player, fee);
        }
    }
    uint256 seed = creatorSeed;
    if (seed > 0) {
        creatorSeed = 0;
        pendingRefund[creator] += seed;
        emit SeedRefunded(creator, seed);
    }
    prizePool = 0;
}

function claimRefund() external nonReentrant {
    uint256 amt = pendingRefund[msg.sender];
    if (amt == 0) revert NothingToWithdraw();
    pendingRefund[msg.sender] = 0;
    usdc.safeTransfer(msg.sender, amt);
}

Apply the equivalent pattern to _settle()'s winner payout loop.

[C-3] Contract's own address being blacklisted permanently bricks all fund movement, with no rescue path

Severity: High
Origin: [phase1 only] — erc20 checklist. Re-examined in Turn 3 against source: confirmed — no owner role, no admin/rescue/sweep function exists anywhere in the contract.
Location: whole contract — every fund-moving function (deposit, withdraw, fundSeed, _settle, _refundAll, emergencyWithdraw) transfers to/from address(this)

Description: If the escrow contract's own address is ever added to USDC's issuer blacklist (precedented for contracts that receive tainted/sanctioned funds), every deposit and every payout path reverts — including emergencyWithdraw(), the contract's designed last resort. The contract has no owner, no admin role, and no rescue/sweep function of any kind. All funds held by the escrow at that point become permanently unrecoverable by any party.

Proof of Concept: League is funded normally with real USDC. Circle blacklists the escrow contract's address for any compliance reason. From that point, deposit(), withdraw(), settle(), creatorFallbackSettle(), cancelLeague(), and emergencyWithdraw() all revert permanently — there is no function in the contract that does not route a USDC transfer through address(this).

Recommendation: This is a structural/architectural gap rather than a simple bug; document the risk explicitly. If desired, a heavily time-locked, multi-sig-gated emergency sweep function — usable only long after all normal and emergency windows have passed — would provide a last-resort recovery path without weakening the contract's day-to-day trust model.

[C-4] Free-pot creatorSeed has no recovery path if the creator's key is lost — emergencyWithdraw() does not cover it

Severity: High
Origin: [both] — phase1: general, access-control (2 checklists) · phase2: access-control, execution-trace, invariant, asymmetry, numerical-gap-hunter (5 FINDING agents) + periphery, trust-gap-hunter (leads). The single most heavily corroborated finding in this audit (9 of 19 total agents across both phases).
Location: emergencyWithdraw() L370-383, deposit() L194-206, fundSeed() L254-264

Description: For a free pot (entryFee == 0), deposit() always reverts, so hasDeposited[player] is never true for any address — the entire prize pool for a free pot is creatorSeed, funded solely via fundSeed(). emergencyWithdraw() is gated exclusively on hasDeposited[msg.sender] and never references creatorSeed. The only functions that can ever move creatorSeed (cancelLeague(), settle(), creatorFallbackSettle()) all require the creator's continued key access. If the creator's key is lost, destroyed, or abandoned — precisely the "both parties disappeared" scenario the contract's own NatSpec says emergencyWithdraw() protects against — the seeded prize is permanently stranded, even past the 180-day emergency window. This is third-party harm, not creator self-harm: the seed is a committed prize for the league's participants, not the creator's retained capital.

Proof of Concept:

  1. Creator deploys a free pot, calls fundSeed(10,000_000000) ($10,000 USDC), then startLeague().
  2. Creator's key is lost/abandoned before settlement; the oracle backend is also offline.
  3. 180+ days after seasonDeadline, any address calls emergencyWithdraw() — it reverts NothingToWithdraw() for every caller, since no free-pot participant ever has hasDeposited == true.
  4. The $10,000 has no remaining code path that can ever move it out of the contract.

Recommendation: Add a creator-seed-specific recovery path reachable after the emergency window without requiring the creator's signature:

function emergencyRefundSeed() external nonReentrant {
    if (status == Status.Completed || status == Status.Cancelled) revert AlreadySettled();
    if (block.timestamp < seasonDeadline + EMERGENCY_WINDOW) revert EmergencyWindowNotReached();
    uint256 seed = creatorSeed;
    if (seed == 0) revert NothingToWithdraw();
    creatorSeed = 0;
    prizePool -= seed;
    usdc.safeTransfer(creator, seed);
    emit SeedRefunded(creator, seed);
}

[M-1] Unbounded seasonDeadline can overflow the fallback/emergency window checks, permanently disabling both safety valves

Severity: Medium
Origin: [both] — phase1: precision-math (finding with concrete overflow proof) · phase2: math-precision, economic-security (leads)
Location: creatorFallbackSettle() L356, emergencyWithdraw() L373; root cause: constructor L161-186 (no validation of _seasonDeadline)

Description: _seasonDeadline is an unvalidated uint256. seasonDeadline + CREATOR_FALLBACK_WINDOW / + EMERGENCY_WINDOW use Solidity 0.8 checked arithmetic. If _seasonDeadline > type(uint256).max - 180 days, both additions revert unconditionally on every call, permanently disabling both fallback settlement and emergency withdrawal. Separately, a _seasonDeadline of 0 or a past timestamp collapses both windows to be immediately satisfiable, defeating the intended 30-day/180-day waiting periods entirely.

Proof of Concept: Deploy with _seasonDeadline = type(uint256).max - 100. Players deposit; league goes Active. If settle() never completes and the creator withholds cancelLeague(), both creatorFallbackSettle() and emergencyWithdraw() revert unconditionally on the overflowing addition — all funds permanently locked.

Recommendation: Validate _seasonDeadline against a sane bound in the constructor, e.g. require(_seasonDeadline > block.timestamp && _seasonDeadline <= block.timestamp + 3650 days).

[M-2] oracleSigner == creator is not prevented, collapsing 2-of-2 settlement into unilateral 1-of-1 control

Severity: Medium
Origin: [both] — phase1: general, access-control (2 checklists) · phase2: trust-gap-hunter, economic-security (leads)
Location: constructor L161-186 (zero-address checks only)

Description: The constructor checks non-zero addresses but never _oracleSigner != _creator. If misconfigured to the same address/key (deployment-tooling bug or malicious deployment), one private key can produce both the raw EIP-712 oracle signature and the personal_sign-prefixed creator signature over the identical payload, satisfying settle() immediately with no 30-day wait and no independent oracle cooperation — silently defeating the documented 2-of-2 model.

Recommendation: Add if (_oracleSigner == _creator) revert ZeroAddress(); in the constructor.

[M-3] cancelLeague() has no timing restriction — creator can unilaterally override a known outcome; zero-cost prize rugpull for free pots

Severity: Medium
Origin: [both] — phase1: access-control · phase2: access-control (paid-pot override), trust-gap-hunter (free-pot rugpull variant) — 2 independent FINDING agents covering two distinct exploitation modes of the same root cause
Location: cancelLeague() L290-297, _refundAll() L454-474

Description: cancelLeague() is callable at any time in Open/Active, with no gate tying it to "before results are known." Two distinct harms follow from the same missing guard:

  • Paid pots: a creator who is also a depositor and would receive an unfavorable split under the agreed bpsSplit can withhold their settle() signature and call cancelLeague() instead — recovering their full stake while the actual winner(s) receive only a refund of their own entry fee, losing the profit they earned.
  • Free pots: players[] is always empty (free-pot participants never call deposit()), so _refundAll()'s player loop is a no-op and cancellation is economically identical to "creator reclaims the entire seeded prize on demand, forever, at zero cost" — no oracle or player agreement required at any point.

Proof of Concept (paid pot): 4-person pot, $25 each, creator is a depositor. Season ends; oracle signs standings giving another player 100%. Creator refuses to co-sign settle() and calls cancelLeague() instead — every player, including the creator, gets back only their own $25; the actual winner never receives the $75 they earned.

Proof of Concept (free pot): Creator seeds $1,000 via fundSeed(), startLeague()s. Season ends, oracle attests a real winner off-chain. Creator, not wanting to pay out, calls cancelLeague() at any moment before Completed — the full $1,000 seed returns to the creator; the actual winner receives nothing.

Recommendation: Disallow cancelLeague() once block.timestamp >= seasonDeadline (forcing settle()/creatorFallbackSettle() once the season has concluded), or require oracle cooperation/attestation for any post-deadline cancellation.

[M-4] Unbounded maxEntries allows players[] to grow large enough to gas-DoS _refundAll()/cancelLeague()

Severity: Medium
Origin: [both] — phase1: dos · phase2: flow-gap-hunter (lead)
Location: constructor L161-186 (maxEntries unvalidated), _refundAll() L454-474

Description: maxEntries has no upper-bound validation. _refundAll() iterates the entire players array with an external call + SSTOREs per element. A sufficiently large players array (via misconfiguration or Sybil deposits on a low-fee/L2 deployment) makes cancelLeague() exceed the block gas limit and revert unconditionally, with no recovery except the 180-day emergencyWithdraw().

Recommendation: Cap maxEntries in the constructor to a value that keeps _refundAll()'s worst-case gas well under the block gas limit; combine with the pull-based refund pattern from C-2 for full mitigation.

[M-5] Creator's EIP-712 "approval" signature is blind-signed over an opaque digest

Severity: Medium
Origin: [both] — phase1: signatures · phase2: boundary (lead)
Location: settle() L329-336, _settlementDigest() L406-417

Description: The contract's docs state the creator signature lets them "review and approve the final standings." In practice settle() computes the digest on-chain and has the creator personal_sign the raw 32-byte hash — blind signing. The creator's wallet cannot display which winners/splits are being approved; all assurance depends on the frontend rendering correctly. A compromised or malicious frontend can request a signature over attacker-chosen winners while displaying correct-looking standings, defeating the documented independent-review property. (Requires attacker control of the signing pipeline — not third-party-triggerable on its own.)

Recommendation: Have the creator sign true EIP-712 typed data (eth_signTypedData_v4) directly against DOMAIN_SEPARATOR/SETTLE_TYPEHASH so wallets can render the struct fields for human review, instead of collapsing to an opaque personal_sign digest.

[M-6] Permissionless startLeague() allows griefing via premature or truncated lock

Severity: Medium (elevated from an initial Low assessment — see note)
Origin: [both] — phase1: general, access-control (2 checklists, initially assessed Low) · phase2: 6 of 12 attacker agents independently reported this as a direct FINDING (access-control, economic-security, execution-trace, periphery, first-principles, asymmetry) plus 3 more as leads — the most heavily corroborated Medium-tier issue in the audit.
Location: startLeague() L277-284

Description: Any address can call startLeague() the moment a league is deployed and Open, with no minimum-participation or minimum-funding check, permanently closing further deposit()/fundSeed() calls. Two exploitation variants surfaced across phase 2's independent passes:

  1. Paid pots: an attacker calls startLeague() before any player deposits (or after only a handful), permanently bricking the league at far below its intended size — the only recovery is cancelLeague() + full redeployment.
  2. Free pots: an attacker watches for the creator's first fundSeed() call (the contract explicitly documents that fundSeed() "may be called multiple times to top up the seed before lock") and immediately calls startLeague() before further top-ups land, permanently capping the prize below the creator's intended amount.

Given this was independently rediscovered by half the phase-2 attacker fleet from distinct reasoning angles (access-control, economic incentive, execution trace, boundary conditions), this is reclassified from the initial phase-1 Low rating to Medium — it is a cheap (gas-only), reliably repeatable griefing vector against every league the platform deploys, not merely a theoretical edge case.

Proof of Concept: Creator deploys a paid pot (entryFee = 25 USDC, maxEntries = 100), intending to collect entries over several days. An unrelated address calls startLeague() in the very next block, before any deposit() lands. players.length == 0, prizePool == 0, status == Active — permanently; deposit() now reverts NotOpen() for everyone, forcing the creator to cancelLeague() (a no-op refund) and redeploy an entirely new escrow.

Recommendation: Restrict startLeague() to onlyCreator (or an authorized backend address), or require players.length > 0 (for paid pots) / a creator-configured minimum before allowing the Open → Active transition.

[L-1] No validation of winners[i] against address(0)/address(this) in _settle()

Severity: Low
Origin: [phase1 only] — general checklist. Re-examined: confirmed, no such check exists at L448.
Location: _settle() L448

Description: If an off-chain bug produces a zero address or the escrow's own address in winners, that share is either burned or trapped with no recovery function (the contract is already Completed by that point).

Recommendation: if (winners[i] == address(0) || winners[i] == address(this)) revert ZeroAddress();

[L-2] Internal accounting trusts nominal transfer amounts instead of measured balance deltas

Severity: Low
Origin: [phase1 only] — erc20 checklist. Re-examined: confirmed at deposit() L199-203 and fundSeed() L258-261 — no balance-delta measurement.
Location: deposit() L199-203, fundSeed() L258-261

Description: prizePool/creatorSeed are incremented by the requested amount, not a measured balanceOf delta. Not exploitable with genuine, fixed-at-deploy USDC (no transfer fee), but if usdc were ever misconfigured to a fee-on-transfer/deflationary token, accounting would overstate the real balance, eventually stranding some depositor's withdrawal/payout.

Recommendation: Low priority given usdc is immutable and expected to be canonical USDC; mitigated by hardening the constructor per L-6 below rather than changing the accounting pattern.

[L-3] Settle struct has no nonce/deadline — signatures remain valid indefinitely while the league is Active

Severity: Low
Origin: [phase1 only] — signatures checklist. Re-examined: confirmed no deadline/nonce field in SETTLE_TYPEHASH.
Location: SETTLE_TYPEHASH L71-72, _settlementDigest() L406-417

Description: Once signed, a winners/split payload stays valid forever (until the league leaves Active). Payouts are computed from the current prizePool, not a value fixed at signing time — a stale-but-valid signature pair submitted after intervening emergencyWithdraw() calls would distribute a shrunken pool by the original split, producing outcomes neither signer intended at signing time.

Recommendation: Add a deadline/nonce field to the Settle struct and typehash; enforce it in settle().

[L-4] DOMAIN_SEPARATOR cached as immutable at deployment — no fork-safe recomputation

Severity: Low
Origin: [both] — phase1: signatures · phase2: access-control (lead)
Location: constructor L179-185

Description: Unlike OpenZeppelin's EIP712._domainSeparatorV4(), there is no fallback recomputation if block.chainid diverges from the cached value post-deployment (e.g. after a contentious hard fork). Not exploitable under current conditions; only relevant in a chain-split scenario.

Recommendation: Recompute the domain separator against live block.chainid, falling back to the cached value only when it matches.

[L-5] winners array hashed with abi.encodePacked instead of spec-conformant EIP-712 array encoding

Severity: Low
Origin: [both] — phase1: signatures · phase2: periphery (lead)
Location: _settlementDigest() L413

Description: keccak256(abi.encodePacked(winners)) packs each address as 20 raw bytes rather than the EIP-712-spec 32-byte-padded element encoding. Internally self-consistent (both signing paths replicate the same non-standard hash), but non-conformant with the declared SETTLE_TYPEHASH/DOMAIN_SEPARATOR — any tooling assuming standard EIP-712 semantics (native eth_signTypedData_v4 UI, third-party verifiers) would compute a mismatched digest.

Recommendation: Encode winners per spec (each element individually padded to 32 bytes) if migrating to native typed-data signing.

[L-6] No ERC-1271 support — a smart-contract-wallet creator can never complete the primary settle() path

Severity: Low
Origin: [phase1 only] — signatures checklist. Re-examined: confirmed, _recoverSigner only implements raw ecrecover.
Location: _recoverSigner() L476-491, settle() L335

Description: If creator is a smart-contract wallet (Gnosis Safe, ERC-4337 account), it can never produce an ecrecover-verifiable signature, so settle() always reverts BadCreatorSignature — permanently forcing such leagues onto the 30-day-delayed creatorFallbackSettle() path (which inherits C-1's risk).

Recommendation: Add ERC-1271 isValidSignature support when creator.code.length > 0.

[L-7] No upper bound on winners.length relative to players.length in _settle()

Severity: Low
Origin: [both] — phase1: dos · phase2: flow-gap-hunter (lead)
Location: _settle() L419-452

Description: Nothing prevents an arbitrarily long signed winners array (bounded only by what oracle+creator agree to sign) from making the payout loop expensive enough to revert on gas. Requires collusion/compromise of both signers, so not third-party exploitable on its own, but no on-chain sanity check exists.

Recommendation: if (winners.length > players.length) revert InvalidWinners();

Informational

  • No validation that _usdc is the canonical Base USDC address [phase1 only] — deployment-tooling risk; no independent exploit path.
  • USDC issuer-controlled global pause halts every function, including emergencyWithdraw() [phase1 only] — inherent to depending on a centralized, pausable stablecoin; not fixable on-chain.
  • nonReentrant not the leftmost modifier on cancelLeague()/settle()/creatorFallbackSettle() [phase1 only] — harmless today (preceding modifiers only perform storage reads), latent footgun for future changes.
  • startLeague() NatSpec contradicts the deposit-flow lifecycle [phase1 only] — the comment claims the backend calls it "right after deploying," which would break the paid-pot deposit window if taken literally; likely a documentation error.
  • _recoverSigner() always reverts BadOracleSignature(), even when validating a malformed creator signature [both] — corroborated across 3 phase-1 checklists (assembly, signatures, access-control) and multiple phase-2 leads; misleading revert reason, no fund-safety impact.
  • ecrecover return not explicitly checked against address(0) in _recoverSigner() [phase1 only] — not exploitable; oracleSigner/creator are enforced non-zero and immutable at construction.
  • Signature malleability — s not restricted to the lower half of the curve order [both] — not exploitable; no signature-derived uniqueness/replay key is used anywhere in the contract.
  • emergencyWithdraw() never removes the caller from players[] [phase2 only] — getPlayers()/playerCount() over-report participants after an emergency exit; a view-consistency issue with no fund-safety impact, since _refundAll()/_settle() both gate on hasDeposited, not array membership.
  • prizePool accounting is correctly decoupled from live usdc.balanceOf() — checked specifically for force-transfer/self-destruct griefing; no issue found, noted for completeness.

Methodology Note

This report reconciles two independently-run analysis passes against the same source: a 7-agent breadth pass walking domain-specific checklists (general, precision-math, erc20, signatures, access-control, assembly, dos), and a 12-agent depth pass using adversarial/attacker-mindset reasoning, run blind to the first pass's output. The unusually high cross-pass and cross-agent corroboration on the top findings (C-1, C-2, C-4, M-6 were each independently rediscovered by 4 or more of the 19 total agents) is a strong signal these represent genuine, structurally-reachable issues rather than analytical artifacts — none were speculative "the deployer probably wouldn't do X" scenarios; each has a concrete, traced exploit path quoted against the actual source lines.
