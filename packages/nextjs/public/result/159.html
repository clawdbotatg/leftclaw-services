Executive Summary

Clones is a Solidity library implementing EIP-1167 minimal proxy deployment via CREATE2 and deterministic address prediction. The core cryptographic logic — the EIP-1167 bytecode construction, CREATE2 address formula, and memory layout — is correct and matches the canonical OpenZeppelin implementation. No Critical or High severity vulnerabilities were found.

Three Low-severity findings and one Informational finding were identified, all relating to defensive coding practices, missing input validation, and version portability. The library functions correctly as written.

Findings

[L-1] No Validation That implementation Has Deployed Code

Severity: Low
Confidence: 90
Category: Defensive validation / proxy pattern
Location: cloneDeterministic() — line 22
Confirmed by: EthSkills (evm-audit-assembly), Pashov (periphery-agent)

Description: cloneDeterministic does not verify that implementation has deployed bytecode before creating a proxy pointing to it. If called with address(0), an EOA, or a not-yet-deployed address, the CREATE2 deployment succeeds — producing a clone whose every call returns (true, "") silently. This is because DELEGATECALL to a codeless address returns success with empty data by EVM specification.

// Clones.sol line 22 — no guard before assembly
function cloneDeterministic(address implementation, bytes32 salt) internal returns (address instance) {
    assembly {
        // implementation is never validated
        ...
        instance := create2(0, ptr, 0x37, salt)
    }

Proof of Concept:

  1. Call cloneDeterministic(address(0), salt) — succeeds, returns clone address
  2. Call any function on the returned clone — returns (true, "") silently
  3. Caller interprets success as correct execution; actual operation did nothing

Recommendation:

if (implementation.code.length == 0) revert CloneCreationFailed();

If pre-commitment deployments (CREATE2 address pre-funding before implementation exists) are a valid use case, document this explicitly in NatSpec.

[L-2] Missing memory-safe Assembly Annotation; Free Memory Pointer Not Advanced

Severity: Low
Confidence: 85
Category: Assembly correctness / best practices
Location: cloneDeterministic() lines 25–34; predictDeterministicAddress() lines 54–59
Confirmed by: EthSkills (evm-audit-assembly), Pashov (execution-trace-agent)

Description: Both assembly blocks read the Solidity free memory pointer (mload(0x40)) to obtain a scratch buffer but never advance it after writing. Neither block uses the memory-safe assembly annotation (assembly ("memory-safe") { }). Without this annotation, the Solidity optimizer cannot make correct alias analysis assumptions around the assembly, potentially degrading optimization quality in the importing contract.

In predictDeterministicAddress, the subsequent abi.encodePacked(...) call allocates from the same base address as the assembly scratch, overwriting the assembly data. Functional correctness is preserved because initCodeHash is already captured as a stack variable before abi.encodePacked runs — but this is a non-obvious reliance on evaluation order.

The canonical OpenZeppelin Clones.sol marks both blocks as memory-safe and explicitly advances the free memory pointer.

// Current
assembly {
    let ptr := mload(0x40)
    mstore(ptr, ...)
    // FMP never updated
    instance := create2(0, ptr, 0x37, salt)
}

// Recommended
assembly ("memory-safe") {
    let ptr := mload(0x40)
    mstore(ptr, ...)
    mstore(0x40, add(ptr, 0x60))  // advance FMP past the 55-byte allocation (rounded up to 96)
    instance := create2(0, ptr, 0x37, salt)
}

Recommendation: Add assembly ("memory-safe") { } to both blocks and advance the free memory pointer by 0x60 (96 bytes, the next 32-byte-aligned boundary after the 55-byte allocation).

[L-3] Broad Solidity Version Pragma Allows PUSH0-Emitting Compilers

Severity: Low
Confidence: 80
Category: Cross-chain portability
Location: Line 3: pragma solidity >=0.8.0 <0.9.0
Confirmed by: EthSkills (evm-audit-general)

Description: The >=0.8.0 <0.9.0 pragma permits compilation with Solidity ≥ 0.8.20, which defaults to the paris EVM target and emits the PUSH0 opcode (EIP-3855). PUSH0 is not recognized on chains that have not adopted the Shanghai hardfork. Deployment on such chains would produce bytecode that reverts at the first PUSH0 instruction.

This library is intended to be part of a wallet factory (slop-computer-wallet), which may be deployed on multiple EVM-compatible chains.

Proof of Concept:

  1. solc 0.8.20 Clones.sol (default EVM target = paris) → emits PUSH0 in boilerplate
  2. Deploy compiled bytecode to a pre-Shanghai EVM chain → execution fails

Recommendation: Pin to a specific version (e.g., pragma solidity 0.8.19;) or explicitly specify --evm-version london in the build pipeline to prevent PUSH0 emission.

[I-1] Clones with selfdestruct-Capable Implementations Can Be Destroyed and Redeployed

Severity: Info
Confidence: 70
Category: Architectural / proxy design note
Location: cloneDeterministic() — general design behavior
Confirmed by: EthSkills (evm-audit-proxies), Pashov (first-principles-agent)

Description: EIP-1167 clones use unconditional DELEGATECALL, executing implementation code in the clone's context. If the implementation exposes a selfdestruct path (directly or through a library), invoking it through the clone destroys the clone (not the implementation), because selfdestruct acts on the current execution context.

After destruction, the same (deployer, salt, implementation) triple produces an identical CREATE2 address, allowing re-deployment of a fresh clone. Systems relying on a clone address as a persistent, immutable identity (e.g., multi-sig wallets that pre-authorize the address) may be disrupted.

Note: as of EIP-6780 (Dencun / Cancun hardfork), selfdestruct only destroys the contract if called in the same transaction as the contract's creation. On Dencun+ chains, post-creation selfdestruct only sends ETH; the code remains. However, pre-Dencun chains and some L2s may still fully destroy contracts.

Recommendation: Document in NatSpec that implementations with callable selfdestruct paths are incompatible with address-as-persistent-identity assumptions. On Dencun+ chains this risk is substantially reduced.

Findings Not Raised (Gate-Rejected)

  • Salt front-running: User-controlled salt only affects the deployer's own CREATE2 namespace. Other deployers use a different address prefix. Self-harm only — rejected.
  • abi.encodePacked hash collision: All four arguments to abi.encodePacked in predictDeterministicAddress are fixed-size types (bytes1, address, bytes32, bytes32) — no dynamic type collision possible — rejected.
