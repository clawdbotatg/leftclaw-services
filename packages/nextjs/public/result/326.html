Medium findings

M-01 — Owner-swappable VRF coordinator defeats anti-steering; migration orphans in-flight requests

Centralization (requires malicious/compromised owner). [both: P1 checklist "VRF/randomness" · P2 access-control/invariant]
FWA.sol:1587 (rawFulfillRandomWords), FWA.sol:2668 (setAddr(VRF_COORDINATOR)), FWA.sol:1527 (unconditional acquisitions[requestId] write), FWA.sol:1679 (word % totalWeight).

The randomness callback authenticates purely on the coordinator address, itself an unrestricted, un-timelocked onlyOwner setter:

// FWA.sol:1587
function rawFulfillRandomWords(uint256 requestId, uint256[] calldata randomWords) external {
    if (msg.sender != address(s_vrfCoordinator)) revert OnlyCoordinator();

// FWA.sol:2668
} else if (key == FWAConfigKeys.VRF_COORDINATOR) {
    s_vrfCoordinator = IVRFCoordinatorV2Plus(value);

Exploit path. Selection is target = randomWords[0] % totalWeight. A malicious/compromised owner sets s_vrfCoordinator to an address they control, then calls rawFulfillRandomWords(requestId, [chosenWord]) — solving word % totalWeight for any desired slot — allocating any listing to any purchaser. The owner can steer an under-priced NFT to themselves and keepNFT it, or steer a target depositor's listing into allocation and combine with M-02 to seize its backing. The entire "no player can steer selection" guarantee rests on the coordinator being honest, and the owner can replace it atomically with no delay. Fabricated requestIds are still blocked by the status == Pending guard, so this is steering, not minting.

Two secondary defects on the same setter: (a) a legitimate migration orphans in-flight requests made to the old coordinator (they revert OnlyCoordinator and stick Pending until cancelAcquisition); (b) acquisitions[requestId] is written unconditionally at FWA.sol:1527, so a new coordinator's requestId can collide with a live Pending id and clobber its escrow record → stuck ETH.

Severity. Medium (centralization). Not High: it requires the trusted owner to act maliciously; no unprivileged path exists.
Fix. Make the coordinator immutable, or gate VRF_COORDINATOR / VRF_SUB_ID / VRF_KEY_HASH behind a timelock with a challenge window; drain/settle in-flight requests before migration; namespace acquisitions by (coordinator, requestId) or block migration while pendingAcquisitionCount != 0.

M-02 — Owner fee levers can seize 100% of settling backing and the whole depositor acquisition-fee pool, retroactively

Centralization (requires malicious/compromised owner). [both: P1 access-control · P2 access-control/first-principles]
FWA.sol:2610-2612 (setUint(OWNER_SETTLEMENT_FEE_BPS)), FWA.sol:2604-2607 (SETTLEMENT_DISCOUNT_BPS ≤ BPS), FWA.sol:1948-1949 (_payoutBackingToDepositor), FWA.sol:2609 (OWNER_ACQUISITION_FEE_BPS = _bpsCapped), FWA.sol:1717 (acquisition-cut split).

// FWA.sol:2610
} else if (key == FWAConfigKeys.OWNER_SETTLEMENT_FEE_BPS) {
    if (value > settlementDiscountBps) revert InvalidConfig();   // only ceiling is the (owner-set) discount
    ownerSettlementFeeBps = value;

// FWA.sol:1948
uint256 ownerCut = value * ownerSettlementFeeBps / BPS;

Exploit path. settlementDiscountBps is capped only at ≤ BPS (FWA.sol:2604). The owner sets SETTLEMENT_DISCOUNT_BPS = 10000 then OWNER_SETTLEMENT_FEE_BPS = 10000, after which every NFT-outcome resolution (keepNFT, depositorReclaimBacking, permissionless finalizeUnsettled, relistNFT) returns toDepositor = 0 — the depositor's entire escrowed backing accrues to accruedOwnerFees. M-03 — Sustained cheap acquisitions freeze all depositor withdrawals (exit-gate lock griefing)

Liveness DoS (unprivileged). [both: P1 reentrancy/DoS · P2 first-principles]
FWA.sol:1169-1173 (_requireExitUnlocked), refreshed at FWA.sol:1416/1456.

// FWA.sol:1169
function _requireExitUnlocked() internal view {
    if (pendingAcquisitionCount != 0 && block.number <= lastSelectionBlock + maxCallbackDelayBlocks) {
        revert WithdrawLocked();
    }
}

Exploit path. The gate keys on a single global lastSelectionBlock that any acquire refreshes to block.number, and each request keeps pendingAcquisitionCount != 0 for the several blocks until its callback lands. An attacker firing one acquire at least once every maxCallbackDelayBlocks (default 8) blocks keeps both conditions permanently true, so every withdrawListing and backing-decrease for every depositor reverts WithdrawLocked indefinitely (e.g. to trap a whale's NFT in the acquisitionable pool). No capital is stolen.

Severity. Medium. Each acquire costs a real, non-refundable vrfServiceFee (~a few ETH/day sustained); the attacker's own acquisitions must either allocate (returning backing to depositors — self-limiting) or be driven to backlog-refund via M-04; and withdrawOnly self-heals the gate within 8 blocks (acquisitions halt → lastSelectionBlock stops refreshing). Staged deposits always retain the instant cancelStagedListing exit.
Fix. Cap the gate's absolute lock duration independent of lastSelectionBlock refresh, or scope the lock to each individual pending request's still-honorable block range so a griefer's fresh acquisitions can't extend the freeze on unrelated depositors; document withdrawOnly as the intended response.

M-04 — Staging-queue stuffing forces backlog refunds — griefing open by default

DoS (unprivileged). [both: P1 M-04 (Medium) · P2 L-1 (Low)] — severity reconciled to Medium (default-open on a fresh deploy).
FWA.sol:440 (maxStagedListings default 0 = unlimited), FWA.sol:1637 (backlog-refund fork), FWA.sol:1763 (VRF fee non-refundable).

// FWA.sol:1637
if (!_drainStaging(maxActivationsPerCallback)) {
    uint256 refundBacklog = _refundAcquisition(acquisition);
    emit AcquisitionRefundedBacklog(requestId, acquisition.purchaser, refundBacklog);
    return;
}

Exploit path. maxStagedListings defaults to 0 = unlimited, so the StagingQueueFull valve is inactive out of the box. The callback drains at most maxActivationsPerCallback (default 3) matured staged listings; if a block-matured entry still remains, it refunds instead of selecting. While pendingAcquisitionCount != 0, an attacker stuffs ≥4 deposits (each an NFT + ≥ minBacking) that mature at the same FIFO-head block; every honored callback then drains 3, sees a 4th, and refunds — the game cannot produce a winner while the backlog sits at the head. Victims lose their non-refundable vrfServiceFee and their draw.

Severity. Medium. Bounded by attacker capital (recoverable via cancelStagedListing) and by the permissionless activateListings (defenders clear the queue → it's a race, not a permanent brick) — but it is reachable on a default deployment, which is why this reconciles to phase 1's Medium over phase 2's Low. The code's own note (FWA.sol:438) says setting maxStagedListings ≤ maxActivationsPerCallback closes it entirely.
Fix (both phases agree). Ship a non-zero default maxStagedListings (e.g. = maxActivationsPerCallback), or enforce maxStagedListings ≤ maxActivationsPerCallback when non-zero, or drain the matured prefix under the gas budget rather than refunding at the count cap.

M-05 — buyback() swaps with no minOut and no price limit — sandwichable

MEV / value leak (unprivileged, once externals open). [both: P1 uniswap-v4 · P2 economic/uniswap/first-principles/accounting-seam — 4 lenses]
FWAToken.sol:313 (buyback, nonReentrant), FWAToken.sol:360-364 (unlockCallback).

// FWAToken.sol:360
BalanceDelta d = poolManager.swap(
    key,
    SwapParams({zeroForOne: true, amountSpecified: -int256(amountIn), sqrtPriceLimitX96: TickMath.MIN_SQRT_PRICE + 1}),
    ""
);
// ... amountOut accepted unconditionally; no minOut check anywhere

Exploit path. buyback() is permissionless, spends up to BUYBACK_INCREMENT (1 ether) of protocol ETH per call, rate-limited only by BUYBACK_DELAY_BLOCKS = 1, and the FWA protocol-fee sink continually refills it. The pool is deliberately thin and single-sided (launched 100% token, buy-only), so a 1-ETH buy moves price hard. With externalBuysEnabled == true (the intended end state) a searcher bundles: front-run buy (push price up) → buyback() (protocol buys at the inflated price for few tokens, searcher collects the CALLER_REWARD_BPS bounty) → back-run sell into the pop. Repeatable every block; protocol buyback ETH bleeds to MEV. FWA's own buy path correctly guards (FWA.sol:2194 if (amountOut < minOut) revert SlippageBuy()); the token buyback is the one buy path that omits it. Not exploitable during the gated bootstrap phase.
Fix. Thread a caller-supplied minOut (or a short-TWAP / max-tick-move floor) into the buyback swap and revert if amountOut falls short.

M-06 — rescueTokens lets the owner claw back all unclaimed FWAToken

Centralization (requires malicious/compromised owner). [both: P1 M-06 (Medium) · P2 L-8 (Low)] — severity reconciled to Medium (unbounded claw-back of user rewards).
FWA.sol:2317 (rescueTokens).

// FWA.sol:2317
function rescueTokens(address to) external onlyOwner returns (uint256 amount) {
    if (token == address(0)) revert TokenNotConfigured();
    if (to == address(0) || !withdrawOnly) revert InvalidConfig();
    depositorRatePerSec = 0;
    purchaserDailyPot = 0;
    amount = SafeTransferLib.balanceOf(token, address(this));
    if (amount != 0) SafeTransferLib.safeTransfer(token, to, amount);

Exploit path. The owner flips setBool(WITHDRAW_ONLY, true) then rescueTokens(owner) and takes the contract's entire FWAToken balance — which backs unclaimed tokenCredit, claimAccruedTokens, claimDepositorTokens, claimEpochTokens, and every purchaserEpochPot. Those user claims then revert until/unless the owner re-funds. This is an intentional migration hatch (it also ends the emission schedule to stay solvent on resume), but it is an unbounded owner claw-back of user reward tokens with no on-chain notice period — hence Medium over phase 2's Low. The ETH side is genuinely safe (no owner ETH-sweep exists), so this is FWAToken-only.
Fix. Enforce an on-chain announced delay between entering withdrawOnly and rescueTokens, or rescue only the un-emitted bucket (balance minus outstanding credits/pots).

M-07 — Transfer-lock bypass via leaked transient allowance after a distributor buy

Invariant break (unprivileged, bootstrap phase). [both: P1 L-04 (Low) · P2 M-3 (Medium)] — severity reconciled to Medium (phase 2 walked a concrete same-tx bypass).
FWATokenHook.sol:236-245 (_afterSwap buy branch), FWAToken.sol:405-422 (_afterTokenTransfer, distributor short-circuit at :408), FWA.sol:2195 (distributor-exempt take).

On a buy the hook bumps the token's transient transfer-allowance (slot 0) by the net output it expects the pool to send the buyer:

// FWATokenHook.sol:238
allowanceForRouter = uint256(uint128(swapAmount)) - uint256(uint128(feeDelta));
// :245
if (allowanceForRouter > 0) IFWAToken(tok).increaseTransferAllowance(allowanceForRouter);

But the only bootstrap-phase buyer is FWA, a registered distributor, and _afterTokenTransfer checks the distributor branch before the PoolManager branch:

// FWAToken.sol:408
if (isDistributor[from] || isDistributor[to]) return;   // FWA's take exits here — allowance NOT consumed
// :414
if (from == pm || to == pm) { require(allowance >= amount, InvalidTransfer()); /* consume */ }  // never reached for FWA

Exploit path (same tx). After every FWA purchaser-buy (claimAccruedTokens / acceptBidAsTokens), ≈amountOut of allowance dangles in transient slot 0 for the rest of the transaction (transient storage clears only at tx end). An attacker who holds FWAToken (legitimately obtained via a distributor→attacker claim) calls FWA.claimAccruedTokens (leaving the surplus), then within the same tx calls poolManager.unlock themselves; in their own callback they settle FWAToken from address A (attacker→PM, pm-branch consumes allowance) and take to address B (PM→B, pm-branch consumes allowance) — moving locked FWAToken A→B, which a direct transfer would revert InvalidTransfer(). This defeats the bootstrap-phase non-transferability invariant (no secondary/OTC movement until externalBuysEnabled).

Severity. Medium. Impact is bounded by v4 delta-netting — no pool/LP theft, no value stolen — which is why phase 1 (finding no theft) rated it Low; but phase 2 constructed a concrete, self-contained same-tx bypass of a core invariant, so it reconciles to Medium. The sell branch (FWATokenHook.sol:242) has the same shape and is latently affected.
Fix. Reorder _afterTokenTransfer so the PoolManager branch is checked before the distributor branch (safe for existing flows — token self-take and hook fee-take are non-distributor, self-bump), or have FWA.unlockCallback reset the token's transient allowance to 0 after its take.

M-08 — vrfServiceFee priced on caller tx.gasprice → subscription under-collection / DoS

Liveness / subsidy leak (unprivileged). [phase2: invariant/economic/boundary/first-principles/accounting-seam — 5 lenses]
FWA.sol:1359-1361 (vrfServiceFee).

// FWA.sol:1359
function vrfServiceFee() public view returns (uint256) {
    return vrfServiceGasEstimate * tx.gasprice * (BPS + vrfServiceMarginBps) / BPS + vrfServiceFlatWei;
}

Exploit path. The purchaser pays a VRF fee computed from their own acquire tx's tx.gasprice (escrowed to vrfReserve), but the Chainlink coordinator later bills the owner's subscription for the actual fulfillment gas at fulfillment-block price, plus premium and a flat native fee. vrfServiceFlatWei defaults to 0. A purchaser submitting with priority fee 0 / via a private relay / during a low-base-fee window pays ≈0 into the reserve while the subscription is charged full cost. Sustained, vrfReserve accrues less than the sub is billed → the subscription bleeds → once it can't cover a request, requestRandomWords fails-closed (FWA.sol:1516) and acquire/acquireBatch revert until the owner tops up out of pocket. This is a subsidy/liveness leak, not user-escrow insolvency (the sub is owner-funded); the 30% margin absorbs normal variance, hence Medium.

Re-examined this pass: vrfServiceFee (FWA.sol:1359) confirmed to read tx.gasprice with vrfServiceFlatWei defaulting to 0; kept at Medium.
Fix. Price the gas component on block.basefee (or max(basefee, tx.gasprice)) and set a mandatory non-zero vrfServiceFlatWei floor covering the coordinator flat fee + a buffer.

M-09 — Window-config seam: requestConfirmations not snapshotted → owner mid-flight change reopens steering

Anti-steering seam (owner mis-config + word foreknowledge). [phase2: VRF-steering gap-hunter]
FWA.sol:1520 (C handed to coordinator, not stored), FWA.sol:1527 (Acquisition written without C), FWA.sol:2576-2585 (setters), FWA.sol:2688 (_checkWindowInvariants).

Exploit path. The anti-steering proof R < C + D is validated by _checkWindowInvariants against the live C, but the C that actually governed an in-flight request is the one passed to the coordinator at request time (requestConfirmations: requestConfirmations, FWA.sol:1520) — it is not snapshotted into the Acquisition struct (FWA.sol:1527-1533 writes no confirmations field) and appears in no runtime gate. With defaults C=3,D=10,R=8: block 100 acquire (word knowable ~103, honored ≤108). Block 101 owner setUint(REQUEST_CONFIRMATIONS,8) — checker 8<8+10, 8≥8, 30>8 ✓. Block 102 owner setUint(MAX_CALLBACK_DELAY_BLOCKS,17) — checker 17<18 ✓; the honored window for the block-100 request is now ≤117. Block 103 an attacker who can observe the word early (the semi-trusted-oracle/reorg threat model this subsystem defends) listNFTs a crafted listing X, staged, matures at 113. Block 114 callback lands: 114 ≤ 117 (not late-refunded), _drainStaging activates X, and word % totalWeight now includes attacker-chosen, word-informed X. Anti-steering defeated. These two changes are exactly what a well-intentioned owner does when hardening; requires owner mid-flight reconfiguration and word foreknowledge, hence Medium.

Re-examined this pass: confirmed requestConfirmations is passed at FWA.sol:1520 and absent from the Acquisition write at FWA.sol:1527; _checkWindowInvariants (FWA.sol:2688) checks live C only; kept at Medium.
Fix. Freeze the C/D/R setters while pendingAcquisitionCount != 0, or snapshot confirmations into Acquisition and cap each request's honored window at requestBlock + storedC + D - 1.

M-10 — Best-effort NFT delivery strands an unrecoverable NFT on a passive purchaser

Asymmetric settlement (unprivileged, depositor-side). [phase2: settlement-seam gap-hunter]
FWA.sol:1868/1893 (_settleNFTToPurchaser(..., false)), FWA.sol:1926-1930 (strict vs best-effort split), FWA.sol:1952 (backing paid first), FWA.sol:1988-1993 (_deliverNFT records stuckNFTRecipient).

// FWA.sol:1926 — _settleNFTToPurchaser
if (strict) {
    ERC721(listing.collection).safeTransferFrom(address(this), purchaser, listing.tokenId);
} else {
    _deliverNFT(listingId, listing.collection, purchaser, listing.tokenId);   // best-effort
}
// FWA.sol:1988 — _deliverNFT
try ERC721(collection).transferFrom(address(this), to, tokenId) {} catch {
    stuckNFTRecipient[listingId] = to;   // just a record; ETH already paid
}

Exploit path. The purchaser-initiated path (keepNFT) is strict (reverts on undeliverable NFT, purchaser can fall back to acceptDepositorBid). But the depositor-initiated (depositorReclaimBacking) and permissionless (finalizeUnsettled) paths are best-effort: _payoutBackingToDepositor pays the depositor value − ownerCut (99%) first (FWA.sol:1952), then _deliverNFT merely records stuckNFTRecipient on a revert. A depositor listing a collection whose transferFrom reverts selectively for the purchaser's address (a collection they control, or any pausable/blocklist NFT) waits out settlementWindow, calls depositorReclaimBacking, keeps 99% of backing and effectively retains the NFT (it never leaves custody; recoverStuckNFT reverts forever while the collection keeps failing). The passive purchaser is left with a dead recovery record, having paid the acquisition fee.

Severity. Medium. Mitigated because the purchaser could have force-taken the settlementDiscountBps (85%) ETH via acceptDepositorBid during the window — a purchaser who acts has an 85% floor. The defect is the asymmetry (strict for the purchaser side, best-effort for the depositor/finalize side).

Re-examined this pass: strict/best-effort split confirmed at FWA.sol:1926; backing-first at FWA.sol:1952; _deliverNFT catch-records at FWA.sol:1988; kept at Medium.
Fix. Make depositorReclaimBacking's delivery to the purchaser strict (forcing the depositor to depositorReclaimNFT if undeliverable), or on delivery failure do not release the full 99% — hold the backing / route the purchaser's ETH floor to the counterparty who ends up NFT-less.

M-11 — Dust-crushed harmonic-mean EV enables cheap wash-farming of the purchaser emission pot

Economic (unprivileged). [phase2: economic/first-principles]

    if (totalWeight == 0) return 0;

}
// FWA.sol:1708 — every successful acquisition credits the purchaser's epoch tally unconditionally
uint64 e = _currentEpoch();
acquisitionsInEpoch[e] += 1;
userAcquisitionsInEpoch[e][acquisition.purchaser] += 1;

Exploit path. acquisitionFee() is the harmonic mean of pool backings (a lone 0.01-ETH listing collapses pool-wide fee to ≈0.011 ETH). Every successful acquisition credits the purchaser's epoch tally unconditionally, and claimEpochTokens splits the fixed purchaserDailyPot pro-rata by raw acquisition count. A self-dealing attacker (own dust listing, acquire→keepNFT recycling most of the fee back to themselves as the sole depositor) pays only ~2% owner cuts + VRF fee per wash-acquisition, cheaply dominating the day's acquisition count to capture the bulk of purchaserDailyPot. The harmonic-mean coupling that defeats fee extraction actively helps the wash-farmer by making acquisitions cheap; it does not defend the emission buckets. Couples with L-16 (minBacking = 0).

Re-examined this pass: harmonic-mean EV at FWA.sol:1369; unconditional raw epoch tally at FWA.sol:1708-1710; kept at Medium.
Fix. Weight the purchaser pot (and epoch credit) by fee paid / realized value rather than raw acquisition count; consider a minimum economic distance between a depositor and the purchaser of their own listing; keep a non-zero minBacking.

Low findings

  • L-01 — setToken is repointable (not one-shot) → token-accounting takeover. [both] FWA.sol:2715. Unlike the token's launch, the hook's setToken, and FWA's setEmission (all one-shot), FWA's setToken has no guard. Repointing token to a malicious contract lets it call onTokenReceived (FWA.sol:2205, gated only by msg.sender == token) with arbitrary amounts, inflating accTokenPerSqrt, or repoint the pool used by acceptBidAsTokens/claimAccruedTokens. Requires a malicious owner. Fix: one-shot or timelock.
  • L-02 — Emission solvency depends on unenforced off-chain funding. [both] FWA.sol:2160, FWA.sol:2726. The accumulators credit token claims regardless of whether the FWAToken bucket was funded; if emissions start unfunded, early claims succeed and late ones revert on safeTransfer (first-come-first-served insolvency). Fix: gate emission-start on balanceOf(this) >= depositorTotal + purchaserTotal.
  • L-03 — Illiquid pool strands tokenBuyAllowance. [both] FWA.sol:1501-1508, FWA.sol:2152. Once token != 0 every acquisition diverts a surcharge slice into tokenBuyAllowance, but claimAccruedTokens's _buyTokens reverts until the pool is liquid, leaving that ETH locked with no alternate exit. Fix: gate the slice carve on pool readiness (launched/liquidity), not merely token != 0; provide an ETH fallback.
  • L-04 — fulfillRandomWords is not nonReentrant. [both] FWA.sol:1587-1601, 1620-1671. The four refund forks forceSafeTransferETH (~100k-gas stipend) to the purchaser inside an unguarded callback; safe today only because refunds are the last mutation and the success path makes no external call. Any future edit adding an interaction after _refundAcquisition silently becomes reentrant. Fix: a coordinator-permitting reentrancy flag, or pin the invariant.
  • L-05 — feeAddress ETH send runs mid-swap with a reentry window. [phase1] FWATokenHook.sol:268, 281. The 1% fee is forceSafeTransferETH'd to feeAddress inside _afterSwap while the pool lock is open; the stipend lets a contract feeAddress execute. Safe today (force-send can't DoS; reentrant buys fail isPool[sender]); feeAddress is owner-set/trusted, so residual is a compromised-fee-wallet window. Fix (optional): accrue fees to the hook and let feeAddress pull them in a separate tx.
  • L-06 — Swap before setFeeAddress burns the 1% fee to address(0). [phase2] FWATokenHook.sol:120, 268, 281. feeAddress defaults to zero and nothing gates swapping on it being set; forceSafeTransferETH(address(0), x) succeeds, silently burning the fee. Fix: require(feeAddress != address(0)) at swap entry, or set it in the constructor.
  • L-07 — launch() leaves a permanent max Permit2 + ERC20 approval. [phase1] FWAToken.sol:262. _approve(this, permit2, max) and permit2.approve(this, positionManager, max, max) are never revoked. Post-launch the token holds only dust and PM can only pull as designated payer, so exploitability is low, but the dangling unlimited approval is unnecessary standing risk. Fix: zero the approvals after positionManager.multicall.
  • L-08 — Single-step ownership + renounceOwnership can brick admin. [phase1] Solady Ownable. A mistyped transfer bricks all admin; renounce sets owner to 0. User pull-paths stay permissionless so funds are not locked, but the game can no longer be started/paused and sweepEmptyEpoch becomes impossible (zero-acquisition pots strand). Fix: two-step handoff; consider disabling renounceOwnership.
  • L-09 — Uncapped surchargeBps / vrfServiceMarginBps; no purchaser-side VRF-fee slippage guard. [phase1] FWA.sol:2596, 2571. surchargeBps is guarded per-call by maxAcquisitionFee, but the VRF fee is not covered by any acquire/acquireBatch slippage parameter, so an owner can front-run a purchaser, inflate vrfServiceMarginBps, and skim their msg.value buffer into owner-recoverable vrfReserve (see also M-08). Fix: add a maxVrfFee param; cap vrfServiceMarginBps.
  • L-10 — Thin-pool concurrent acquisitions strand non-refundable VRF fees. [phase2] FWA.sol:1649/1667. On a 1–2 listing pool the first callback empties/shifts it and later in-flight words refund (NoListing/Slippage), each losing its VRF fee. Inherent to concurrency; surface pool depth in quoteAcquisitionPrice.
  • L-11 — InvalidTreeResult / OOG revert strands a request Pending. [phase2] FWA.sol:1684/1688. A revert after the pendingAcquisitionCount -= 1 undoes the whole callback; the coordinator won't retry, so the acquisition silently fails (recoverable via cancelAcquisition). Fix: fall through to a refund on internal inconsistency instead of reverting.
  • L-12 — vrfSubId freely owner-settable; topUpSubscription forwards vrfReserve to any subscription. [phase2] FWA.sol:2565, 1569. Bounded (VRF fees are protocol revenue) but an unvalidated redirect of {value: vrfReserve}. Fix: validate the sub lists this contract as consumer, or 2-step it.
  • L-13 — maxCallbackDelayBlocks = 8 vs real VRF tail latency. [phase2] FWA.sol:266, 1620. The header itself cites p95=46/max=102 for the wrapper; a legitimate congested callback at r+9 is refunded (AcquisitionRefundedLate), degrading liveness/UX. Fix: tune R/D against observed live latency; surface the refund cause.
  • L-14 — acquisitionFee division-before-multiplication truncates the surcharge. [phase2] FWA.sol:1369-1370. ev = weightedBackingTotal/totalWeight then ev*(BPS+surcharge)/BPS; on a sub-wei-EV pool the surcharge rounds away entirely. Bounded to dust on realistic (≥0.01 ETH) pools. Fix: weightedBackingTotal * (BPS+surchargeBps) / (totalWeight * BPS).
  • L-15 — _openAcquisition re-derives EV from the already-floored fee. [phase2] FWA.sol:1506-1507. The token-buy slice's edge = fee − ev can misroute ~1 wei on micro pools; no insolvency (distributable = fee − slice ≥ 0). Fix: carry the true ev from acquisitionFee().
  • L-16 — minBacking = 0 admits dust that distorts pricing/selection. [phase2] FWA.sol:2619. 1-wei listings (weight 1e36) dominate selection and collapse EV; the flat fee share bounds sybil fee-farming but not the distortion (see M-11). Fix: enforce a non-zero protocol floor.

Assurances — checked by both phases and found sound

Recorded so the client need not re-derive them; each was traced end-to-end.

  • VRF anti-steering holds under an honest coordinator. The staging FIFO (D ≥ 1), the exit gate over [r, lastSelectionBlock + R], the strict window invariant R < C + D (FWA.sol:2688, load-bearing), the late/backlog/no-listing/slippage refund forks, the single up-front pendingAcquisitionCount decrement, and the pre-selection _drainStaging compose correctly. No way found for a word-informed player to steer an honored callback (owner-config seam M-09 and coordinator swap M-01 are the only ways to break it, both privileged/mis-config).
  • Modulo bias is negligible. randomWords[0] % totalWeight with totalWeight ≤ ~2^152 gives bias ~2^-104.
  • pendingAcquisitionCount cannot desync. +1 per request, −1 per terminal outcome; the status == Pending mutual exclusion between fulfill and cancel keeps the exit gate from opening early or sticking closed; the P==0 fast path never fires with a live word.
  • Accounting is solvent. Both dividend accumulators honor Σ credited ≤ Σ collected via consistent ceil-on-join / floor-on-claim / floor-on-distribute rounding. No "join-then-claim" free-fee, no double-count of the allocated listing, updateBacking re-price telescopes exactly; liability buckets (vrfReserve, tokenBuyAllowanceTotal, accruedOwnerFees) are disjoint from escrowed backing; topListingPot settles once per tenure; the purchaser FWAToken-buy never draws from listing backing.
  • State machine is one-way. Acquisition (Pending→Fulfilled/Cancelled/Refunded) and Listing (Active/Staged→Allocated/Withdrawn/Settled) transitions are guarded and terminal-once; the Settled flip is the first write, pre-external-call, under nonReentrant; all resolver pairs are mutually exclusive.
  • Tree / totals consistency. tree[1] == totalWeight, feeShareTotal == activeListingCount, sqrtBackingTotal == Σ listingSqrtBacking, weightedBackingTotal == Σ weight·value maintained on every transition; slots freed only after their leaf weight is zeroed (no stale-weight reuse); capacity 2^32 off-by-one-clean; InvalidTreeResult unreachable absent OOG.
  • Uniswap-v4 delta accounting is correct, including the nested buy-fee swap (net-zero hook delta), ExactOutputNotAllowed, direction inference, _swapTokenToEth self-skip, and the launch latch (currency0==ETH, currency1==token one-shot, launching() transient, deploymentBlock one-shot) which cannot be front-run/re-run/squatted; seed LP burned to DEAD_ADDRESS. The buy-gate (isPool[sender] && isBuying()) holds against the reentrancy/ride paths tried.
  • No unprivileged fund-loss reentrancy, no ERC721 double-delivery/double-list, no stuck-ETH-without-path. All money-moving externals are nonReentrant with effects-before-interaction; forceSafeTransferETH cannot be bricked; _deliverNFT uses plain transferFrom (no onERC721Received pivot); FWA holds no receive/fallback and never reads its own balance for accounting.
  • The economic auction self-neutralizes classic attacks. JIT fee-farming, sybil fee-splitting, self-dealing round-trips, top-listing-pot theft/grief net ≈0 or a loss (verified numerically). Note the exception M-11: the emission buckets (raw acquisition count) are not defended by the same coupling.
  • Permissionless surface is well-designed: every anyone-can-call money-mover routes funds only to a hard-coded rightful recipient (listing depositor, acquisition purchaser, payoutAddress, or the VRF subscription) — never a caller-chosen address. The config-key dispatcher has no collisions and rejects unknown keys with guarded narrowing casts.
