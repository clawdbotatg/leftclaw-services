Findings

[90] 1. proposeArbitrator never excludes the dispute's own poster/worker — self-arbitration steals escrowed funds

ArbitrationModule.proposeArbitrator / registerArbitratorGlobal / resolveDispute · Confidence: 90

Description
registerArbitrator explicitly excludes task parties (require(msg.sender != t.poster && msg.sender != t.worker), line 116) — proving the intended invariant "arbitrator ≠ litigant." registerArbitratorGlobal (137-154) has no equivalent check, and critically, proposeArbitrator (198-246) never re-applies it before seating: its eligibility check (207-209) only verifies registeredArbitrator[...] || globalArbitrator[...], never arbitrator != d.snapshotPoster/d.snapshotWorker. A task party who joins the global pool can be nominated by both sides (trivially, via a colluding or sybil counterparty) and seated as arbitrator of their own dispute. Tier-0 disputes (locked value < $1) require zero reputation (219-224 has no branch for tier 0), so this needs nothing beyond a single deposit. Once seated, the attacker calls resolveDispute with an arbitrary workerBps, claims 100% of the escrow via escrow.split, and — since resolvedCount/reputation are credited unconditionally (286, 301-312) — can chain cheap tier-0 self-dealt disputes to farm the resolvedCount>=5/rep>=200 credentials needed to self-arbitrate arbitrarily large (tier-2) disputes too. Independently found and proved by 9 of the audit's specialized agents.

Proof of Concept

  1. Attacker registers wallet A globally: registerArbitratorGlobal() (137) — passes with only the deposit minimum, no party check exists on this path.
  2. Attacker (controlling both P=poster and W=worker on a self-created minimal-value task, or colluding with a real counterparty) triggers a dispute via taskRegistry; snapshot sets d.snapshotPoster=P, d.snapshotWorker=W.
  3. Both P and W call proposeArbitrator(id, A) (198) — passes globalArbitrator[A]==true (207), meetsEntryMinimum(A) (211-214), and tier-0 skips the reputation branch entirely (219-224). Both consents set → d.assignedArbitrator=A, state→EVIDENCE (241-245).
  4. A calls resolveDispute(id, 10000) (280) — passes trivially since msg.sender==A==d.assignedArbitrator (282). _finalise → escrow.split sends 100% of escrow to the worker side (298); resolvedCount[A]+=1 (286) and full RESOLVE_REP_POINTS credited (301-312).

Fix

  function proposeArbitrator(uint256 disputeId, address arbitrator) external {
      Dispute storage d = disputes[disputeId];
      require(d.state == DisputeState.OPEN, "Arbitration: not open");
      require(
          msg.sender == d.snapshotPoster || msg.sender == d.snapshotWorker,
          "Arbitration: not party"
      );
      require(arbitrator != address(0), "Arbitration: zero arbitrator");
+     require(
+         arbitrator != d.snapshotPoster && arbitrator != d.snapshotWorker,
+         "Arbitration: arbitrator cannot be a party"
+     );
      require(
          registeredArbitrator[d.taskId][arbitrator] || globalArbitrator[arbitrator],
          "Arbitration: not registered"

[85] 2. Tie-break logic in _settleDisputeBond lets any seated arbitrator guarantee bond forfeiture by ruling an exact 5000bps tie

ArbitrationModule._settleDisputeBond · Confidence: 85

Description
initiatorWon = initiatorIsWorker ? workerBps > 5000 : workerBps < 5000 (335) — at exactly workerBps==5000, this is false for either role, so an arbitrator ruling a tie via resolveDispute (byArbitrator=true) always trips byArbitrator && !initiatorWon (337) and forfeits the initiator's bond. The identical 5000 split reached via the permissionless resolveTimedOut (277, byArbitrator=false) always refunds (340-344) — the same economic outcome (a 50/50 escrow split) produces opposite bond consequences purely based on which function produced it. A profit-maximizing arbitrator can therefore rule exactly 5000 on every dispute they're seated on, extracting the full bond (up to MAX_DISPUTE_BOND=$100) with zero merit-based justification, zero economic risk, and no way for either party to detect the difference from an honest tie. Independently found and proved by 8 of the 12 depth agents, with several producing exhaustive worked traces.

Proof of Concept

  1. Task escrow locked = $100 (100,000,000 units). Poster P opens dispute as initiator; bond = 5% = $5, debited via debitDisputeBond (188).
  2. Both parties legitimately consent to arbitrator A — no collusion required.
  3. A calls resolveDispute(id, 5000) regardless of the actual merits.
  4. _settleDisputeBond: initiatorIsWorker=false, initiatorWon=(5000<5000)=false. byArbitrator(true) && !initiatorWon(true) → forfeit branch fires (337-339): A receives P's full $5 bond, resolvedCount[A]+=1.

Fix

- bool initiatorWon = initiatorIsWorker ? workerBps > 5000 : workerBps < 5000;
+ bool isTie = workerBps == 5000;
+ bool initiatorWon = isTie
+     ? true  // treat an exact tie as bond-neutral, matching resolveTimedOut's treatment
+     : (initiatorIsWorker ? workerBps > 5000 : workerBps < 5000);

[78] 3. Either party can stonewall arbitrator consent to force a merit-blind 50/50 outcome with a guaranteed floor and no bond risk

ArbitrationModule.resolveTimedOut / proposeArbitrator · Confidence: 78

Description
Reaching EVIDENCE requires both posterConsented and workerConsented on the identical address (241), with no tie-break, forced default, or penalty for non-participation. A party who knows a fair ruling would give them less than 50% has a strictly dominant strategy: never consent to any arbitrator (optionally combined with escalate to keep resetting the clock — see Finding 7). After the deadline, anyone calls the fully permissionless resolveTimedOut (268), which always splits 50/50 and — since byArbitrator=false unconditionally skips the forfeiture branch (337) — always refunds the initiator's bond regardless of who was actually at fault. This defeats the purpose of merit-based arbitration for any party willing to stall.

Proof of Concept

  1. Worker delivers nothing on a $1000 task; poster opens a dispute as initiator (fair ruling: workerBps=0).
  2. Worker never calls proposeArbitrator with a matching candidate (no cost, no penalty).
  3. After the (possibly escalate-extended) deadline, anyone calls resolveTimedOut(id) → _finalise(d, id, 5000, false) → worker keeps 50% of escrow they were never entitled to, at zero cost.

Fix
Introduce consequences for unilateral non-consent — e.g., a default/fallback arbitrator selectable by the non-stalling party after a grace period, or make the timeout outcome depend on which party obstructed consent, rather than an unconditional 50/50 available to whichever side benefits from stalling.

[75] 4. Bond-refund branch has no failure isolation — a single revert permanently locks the dispute and its escrowed funds

ArbitrationModule._settleDisputeBond · Confidence: 75

Description
The forfeit branch defers to pendingBondPayouts on any transfer failure (_payBondOrDefer, 356-368). The refund branch — which covers every timeout (the fallback explicitly designed to guarantee eventual resolution) plus every "initiator wins" ruling — has no equivalent protection: forceApprove + creditDisputeBond (341-342) are called unwrapped. Any revert (vault pause, blacklist, internal cap — IAgentDepositVault is out of scope) propagates through _finalise, unwinding escrow.split (298) and state=RESOLVED too. No owner override exists anywhere to force resolution. Corroborated by 4 agents across both phases.

Proof of Concept

  1. Dispute opens, bond debited from initiator I.
  2. I later becomes ineligible for a vault credit (pause/blacklist/cap — plausible operational vault behavior).
  3. Deadline passes; anyone calls resolveTimedOut → refund branch → creditDisputeBond(I, bond) reverts → entire tx reverts. resolveDispute hits the identical wall. Dispute permanently stuck OPEN/EVIDENCE; escrowed task funds never release.

[68] 5. _payBondOrDefer's raw .call has no contract-existence check — a no-code token address silently destroys the bond

ArbitrationModule._payBondOrDefer · Confidence: 68

Description
A .call to an address with no deployed code returns (ok=true, data.length=0) — satisfying none of the tri-condition's failure branches (360-364), misclassified as a successful transfer. Since usdcToken() is fetched fresh from the vault on every settlement (332) rather than cached/validated, if it ever resolves to a non-contract address (misconfiguration window, unset default), the forfeiture "succeeds" (DisputeBondForfeited emitted, disputeBond already zeroed at 330) but no tokens moved and no pendingBondPayouts credit is created — an unrecoverable silent loss. The same file's own forceApprove/safeTransfer calls (341, 352) go through OpenZeppelin's code-existence-safe SafeERC20, proving the protection exists in this codebase and simply wasn't applied here.

[65] 6. _finalise's reputation accounting doesn't distinguish a real ruling from a permissionless timeout default

ArbitrationModule._finalise · Confidence: 65

Description
Two related mechanisms, same root defect (the reputation block at 300-312 doesn't gate on byArbitrator): (a) resolveTimedOut hardcodes workerBps=5000 (277), and workerWon = workerBps >= 5000 (302) unconditionally credits the worker as dispute "winner" on every single timeout, regardless of actual merits — a worker can force every dispute they're party to into timeout (per Finding 3) and collect a guaranteed "won" reputation entry for free. (b) The arbitrator reputation credit (305, if (d.assignedArbitrator != address(0))) fires whenever an arbitrator was ever seated, not only when they actually ruled — an arbitrator who is seated and then simply never calls resolveDispute still earns the full RESOLVE_REP_POINTS (50 == MIN_REP_TIER1 exactly) via the timeout path, letting a do-nothing arbitrator clear the tier-1 eligibility bar for free.

Fix

-     bool workerWon = workerBps >= 5000;
-     reputationRegistry.recordDisputeOutcome(d.snapshotWorker, d.taskId, workerWon);
-     reputationRegistry.recordDisputeOutcome(d.snapshotPoster, d.taskId, !workerWon);
-     if (d.assignedArbitrator != address(0)) {

[60] 7. escalate() lets a single party unilaterally and repeatedly reset the resolution deadline and disrupt in-flight consent

ArbitrationModule.escalate · Confidence: 60

Description
No counterparty consent, cost, or cooldown required — any party can call this while OPEN, wiping any pending arbitrator proposal/consent (259-261) and resetting the full 7-day deadline (262), up to 3 times (MAX_TIERS). A party anticipating an unfavorable outcome can front-run the counterparty's consent completion, stall up to 21 additional days, and/or push the dispute into a tier whose resolvedCount>=5 requirement is unreachable early in the protocol's life, forcing the dispute toward the always-favorable-to-stallers timeout outcome (Finding 3).

Fix
Require mutual consent for escalation past tier 0, decouple deadline extension from tier bump, or cap cumulative extension from the original open timestamp.

[50] 9. No dedup check on openDispute for the same taskId — a second dispute can become permanently unresolvable

ArbitrationModule.openDispute / _finalise · Confidence: 50

Description
openDispute writes a fresh disputes[disputeId] on every call with no check for an already-open dispute on the same taskId. If two disputes are opened on the same task before the first resolves, and the first resolves first (running escrow.split, which by its own purpose mutates lockedBalance), the second dispute's snapshotLockedBalance becomes permanently stale — every future call to _finalise for it (via either resolveDispute or the permissionless resolveTimedOut) reverts unconditionally at the escrow-equality check (294-297), with no recovery path anywhere in the contract.

Fix
Track and enforce "at most one active dispute per taskId" in openDispute (e.g. a mapping(uint256 => bool) hasActiveDispute guard, cleared in _finalise).

[45] 10. Bond charge is frozen at dispute-open time, decoupled from arbitration eligibility's live vault check

ArbitrationModule.openDispute / proposeArbitrator · Confidence: 45

Description
openDispute skips the bond-debit block entirely if agentDepositVault isn't yet set (186), and never re-derives the bond later. proposeArbitrator, by contrast, live-reads agentDepositVault at seating time. A dispute opened before the owner's one-time setAgentDepositVault call is permanently bond-free (disputeBond[id] stays 0), yet can still receive a full-power real arbitrator ruling once the vault is configured — defeating the bond's stated anti-spam purpose for that dispute.

Fix
Either require agentDepositVault to be set as a precondition of openDispute (mirroring registerArbitrator's hard requirement), or re-derive the bond at proposal/seating time rather than freezing it at open.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed in one analysis pass. These are not false positives — they are high-signal leads for manual review. Not scored.

  • Token-identity drift — _settleDisputeBond/claimBondPayout — Code smells: agentDepositVault.usdcToken() is re-fetched fresh at settle (332) and claim (352) time rather than cached/pinned; pendingBondPayouts stores a bare amount with no token reference. Every agent that raised this independently chose to file it as a lead rather than a finding, since it requires unverifiable IAgentDepositVault token-mutability.
  • Escrow-balance equality is a hard revert with no recovery path — _finalise, lines 294-297 — depends entirely on unverified IEscrowVault.freeze semantics; if lockedBalance can legitimately drift post-freeze for any reason, the dispute (and its bond) is stuck forever with no admin override.
  • No ReentrancyGuard anywhere in the contract — every one of the 12 depth agents traced the external-call sites in _finalise/_settleDisputeBond/claimBondPayout and found CEI ordering closes every constructed same-dispute path; cross-dispute reentrancy fan-out during escrow.split's black-box payout mechanism could not be ruled out and remains a hardening gap worth adding a lock for regardless.
  • _payBondOrDefer's raw .call copies unbounded return data before validation — defense-in-depth gap (return-data-bomb exposure) contingent on usdcToken() ever resolving to a hostile contract.
  • _bondForAmount's clamp contradicts its own documented "proportional to value" claim at both extremes — a $1 dispute pays a bond 1,000,000× its value; a $1,000,000+ dispute pays a flat $100 (0.01%). Intentional clamp behavior, not a rounding accident — worth a threshold-design revisit.
