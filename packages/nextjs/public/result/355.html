[1] submitAttestation has no attester-side access control — any address can arbitrarily inflate or destroy any agent's trust score for free

Severity: Critical
Corroboration: [both] — found independently by all 12 phase-2 attacker agents (unanimous) and by the access-control, oracles, general, and DoS phase-1 checklists (precision-math did not target this area but independently found the related truncation bug below).
Location: submitAttestation() lines 142-202, _updatePerformance() lines 208-242

Description: submitAttestation gates only the target of the attestation (identityRegistry.isAgentActive(agent)) — the attester (msg.sender) needs no registration, stake, fee, or prior relationship to the agent. The contract does compute isVerified = identityRegistry.isAgentActive(msg.sender), but this flag is purely cosmetic — it only increments a separate verifiedAttestations counter and never gates or weights whether the score counts toward averageQuality:

if (perf.totalAttestations < MAX_FOR_TRUE_AVG) {
    uint256 totalScore = perf.averageQuality * perf.totalAttestations;
    totalScore += newScore;
    perf.totalAttestations += 1;
    perf.averageQuality = totalScore / perf.totalAttestations;   // unconditional — verified or not
} else {
    perf.averageQuality = (perf.averageQuality * 9 + newScore) / 10;  // unconditional
    perf.totalAttestations += 1;
}
if (verified) { perf.verifiedAttestations += 1; }   // only affects this separate counter

Compounding this, the only anti-spam mechanism — _hasAttested[msg.sender][agent][taskId] — is skipped entirely when taskId == 0, which the contract's own documentation defines as the valid, expected value for "standalone" attestations (taskId doc comment: "Reference to task (0 if standalone)"). Even when taskId > 0, the guard only blocks exact reuse of the same (attester, agent, taskId) triple; since taskId is a bare, attacker-chosen integer never validated against any real task or escrow system, incrementing it (1, 2, 3, ...) defeats the guard just as completely as using 0.

The self-attestation guard (agent != msg.sender, line 154) provides no real protection either — it blocks only the literal same address, not a second wallet the agent operator also controls.

Impact: Any address, with no registration or economic stake, can move performance[agent].averageQuality to any value between 0 and 10000 for any active agent, at the cost of L2 gas alone. This directly and completely defeats the contract's stated purpose — the NatSpec's own example, "this agent completed 47 tasks with a 96% satisfaction rate," is fully fabricable by a single unfunded EOA in dozens of cheap transactions, or by two colluding "verified" agents producing an indistinguishable-from-genuine record. Severity is Critical rather than High because there is no precondition beyond ordinary gas, no cap on direction or magnitude, and this contract exists specifically to be a trust primitive other Vaultfire contracts are expected to consume for real decisions (bonding, staking, access control) — several of which are in this same audit queue.

Proof of Concept:

  1. Attacker picks any active, registered victimAgent (or a colludingAgent they also control).
  2. From a single fresh, unregistered EOA, loop: submitAttestation(victimAgent, 0, 0, keccak256("x"), keccak256("y")) (taskId=0 skips all dedup) — repeat N times to crash the score, or use qualityScore=10000 against a colluding agent to pump it.
  3. Numeric trace (verified independently by two agents and the orchestrator): a legitimately-earned averageQuality=9500 over 50 real attestations collapses to (9500*50 + 0*500)/550 ≈ 863 (a 91% drop) after 500 cheap spam calls from one address. A brand-new agent reaches averageQuality=10000 after its very first self-serving call.

Recommendation: Require the attester to satisfy a real Sybil-resistance precondition before their score counts — e.g. require identityRegistry.isAgentActive(msg.sender) (gate, not just record), and/or require attestations to reference a task validated against an external task/escrow registry that can confirm msg.sender was the genuine counterparty. Apply anti-spam dedup/rate-limiting regardless of taskId. See phase2-report.md for a concrete diff.

[2] Fixed-weight EMA past 1,000 attestations makes long-established agents cheaper to manipulate, not harder

Severity: High
Corroboration: [both] — phase1's oracles, general, and precision-math checklists independently flagged this; 4 of 12 phase-2 agents (math-precision, periphery, first-principles, trust-gap) independently derived and quantified it.
Location: _updatePerformance() lines 217-225

Description: Below MAX_FOR_TRUE_AVG (1000) attestations, each new score has diminishing weight ~1/n on the true running average — the intended "more history = harder to move" property. At totalAttestations >= 1000, the code switches instantly to a flat-10%-weight EMA ((avg*9+newScore)/10) forever after, with no scaling by accumulated history. This is a discontinuous ~100x jump in per-call influence at the exact threshold meant to represent a agent becoming "established."

Proof of Concept: An agent with averageQuality=9500 after 5,000 or even 50,000,000 legitimate attestations can be dragged to ~500 by roughly 29 cheap qualityScore=0 spam calls (9500 * 0.9^29 ≈ 460), or pumped from a low baseline to ~9900 in ~16 calls (0.9^16 ≈ 0.185) — independent of how much real history exists. This inverts the intended trust property: the agents whose scores matter most (long track record) become the cheapest per call to manipulate once they cross the threshold.

Recommendation: Use a decay factor that scales with accumulated sample size (e.g. weight ∝ 1/min(N, cap) for a much larger cap) rather than a fixed 10%, or restrict full EMA weight to verified attestations only.

[3] Compounding truncation in the running-average reconstruction causes systematic score drift

Severity: Medium
Corroboration: [both] — phase1's precision-math checklist flagged this; 2 of 12 phase-2 agents (math-precision, numerical-gap) independently derived it with concrete numeric traces; the orchestrator independently re-verified the exact arithmetic before including it in this report.
Location: _updatePerformance() lines 217-221

Description: totalScore = perf.averageQuality * perf.totalAttestations reconstructs the cumulative sum from the already floor-divided averageQuality rather than persisting an exact running sum. Every step's rounding loss compounds into the next and never self-corrects, since the "sum" fed into each division is itself already-truncated.

Verified Proof of Concept (re-derived independently):

avg, n = 0, 0
for score in [3, 0, 0]:
    totalScore = avg*n + score
    n += 1
    avg = totalScore // n
# call1 score=3: avg = 3/1 = 3
# call2 score=0: avg = 3/2 = 1   (true running sum is 3, true mean so far is 1.5)
# call3 score=0: avg = 2/3 = 0   (true mean of [3,0,0] is exactly 1)

Three legitimate, distinctly-keyed attestations with an exact-integer true mean of 1 produce a stored averageQuality of 0 — not a rounding-ambiguity case, a demonstrably wrong result. Ascending scores 1..10 pin the average at 1 against a true average of 5 (verified by the orchestrator); the error grows to ~500x understatement by 1000 attestations under adversarial ordering, and to a consistent ~2.5-5% downward bias under ordinary random traffic. The error is one-directional (always downward, since Solidity / floors) and affects every agent, not just attacked ones.

Recommendation: Persist an explicit totalScoreSum accumulator (bounded, <= 10000*1000, no overflow risk) and derive averageQuality = totalScoreSum / totalAttestations from that exact value each call instead of reconstructing it from the rounded average. See phase2-report.md for a concrete diff.

[4] Unbounded per-agent/per-attester ID arrays create a permanent getter-DoS risk

Severity: High
Corroboration: [both] — phase1's DoS checklist; 5+ of 12 phase-2 agents flagged this as a lead (impact caveated on an unconfirmed downstream on-chain consumer).
Location: _agentAttestations/_attesterAttestations (lines 75, 78), getAgentAttestations()/getAttesterAttestations() (lines 277-283)

Description: Every submitAttestation call (unlimited, per Finding 1) pushes onto both arrays with no cap; the getters return the full array in one call. An attacker can grow a target's array until any on-chain consumer calling the getter reverts out-of-gas permanently (arrays never shrink), or until off-chain eth_call integrators exceed RPC gas caps. Rated High rather than Medium given Finding 1 makes the enabling spam completely free and unbounded — this is not a separate cost/effort barrier, it inherits Finding 1's zero-cost trigger.

Recommendation: Paginate the getters (offset, limit); consider reconstructing history from AttestationSubmitted events off-chain instead of maintaining on-chain enumeration arrays.

[5] taskId and evidenceHash are never validated against a real task

Severity: Medium
Origin: [phase1: oracles] — re-examined against source, confirmed; several phase-2 agents noted this as the root enabler of Finding 1 rather than filing it separately.
Location: submitAttestation() lines 142-160

Description: Only categoryHash is required non-zero; evidenceHash can be bytes32(0), and taskId is never checked against any task/escrow contract. This undermines the "verifiable... off-chain evidence" premise in the contract's own NatSpec, independent of the spam volume in Finding 1 — even a single, well-intentioned attester can reference a task that never existed.

Recommendation: Require evidenceHash != 0; validate taskId against a real task/escrow contract confirming the referenced task existed and that msg.sender was the legitimate counterparty.

[6] No staleness enforcement

Severity: Low
Origin: [phase1: oracles + general] — directly addresses the client's "staleness handling" focus area.
Location: AgentPerformance.lastUpdated (line 50), getPerformance() (lines 256-275)

Description: lastUpdated is correctly tracked and exposed (positive control), but there is no heartbeat concept, no documented expected update frequency, and no helper that reverts/flags on staleness. An agent that goes dormant keeps a frozen, seemingly-current score indefinitely unless every integrator remembers to independently check lastUpdated — the same integration-mistake class flagged repeatedly for Chainlink updatedAt staleness checks.

Recommendation: Add a convenience isStale(agent, maxAge) / getPerformanceIfFresh(agent, maxAge) helper; document a recommended maxAge in NatSpec.

[7] No minimum-sample-size signal

Severity: Low
Origin: [phase1: oracles]
Location: _updatePerformance() lines 217-221

Description: The first attestation sets averageQuality outright (division by 1); totalAttestations is available to defend against this but nothing forces a consumer to check it.

Recommendation: Expose a confidence-aware getter that reverts/flags below a minimum sample count.

[8] averageQuality == 0 is ambiguous

Severity: Low
Origin: [phase1: general]

Description: Both a brand-new agent and one successfully driven to 0 via Finding 1 read identically unless totalAttestations is also checked.

Recommendation: Document that averageQuality must always be interpreted together with totalAttestations, or expose a hasHistory bool.

[9] Minor code-hygiene notes

Severity: Info
Origin: [phase1: precision-math + general]

  • unchecked { attestationId = ++_attestationCounter; } (line 173) lacks the checklist-required justification comment (not practically exploitable — would need ~1.15e77 calls to overflow).
  • The contract's NatSpec states intent to deploy on Base, Avalanche, Arbitrum, and Polygon; Solidity ≥0.8.20 emits PUSH0 by default, which rolled out at different times across those chains. Pin an explicit --evm-version before reusing this build on a target that may lack PUSH0 support.

[10] Hard dependency on external isAgentActive() with no fallback

Severity: Info
Origin: [phase1: dos]
Location: submitAttestation() lines 157-160, 171

Description: If identityRegistry ever reverts or pauses, submitAttestation becomes fully unusable with no circuit breaker. Normal architectural coupling, not a bug in this contract, but worth documenting as an accepted dependency.

Explicitly Ruled Out (checked, no finding)

  • Reentrancy: nonReentrant guard present; the only external call (identityRegistry.isAgentActive) compiles to STATICCALL (interface marked view), which cannot itself perform state-changing reentrancy. Confirmed independently by both phases.
  • qualityScore <= 10000 range check: correctly enforced with no off-by-one.
  • Centralization/admin risk: no owner, no pausability, no upgradeability — cuts both ways (no rug risk, but also no remediation path once Finding 1 is exploited; noted as a contributing severity factor, not a separate finding).
