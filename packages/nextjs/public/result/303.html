Overall assessment

This contract has a Critical, unauthenticated fund-theft vulnerability in its core deposit-crediting logic that is trivially exploitable by any on-chain observer with no privileged access and no capital at risk. It was independently discovered by all 18 agents across both audit phases — the strongest possible corroboration this methodology can produce. If this contract is live and accepting deposits, it should be paused/deprecated immediately; the vulnerability allows systematic, permissionless theft of every user's deposited wager. Three further High-severity issues compound the risk: the owner can seize the same in-flight deposits even faster via sweepUnaccounted, a single blocklisted/paused token address can permanently freeze both players' escrowed funds, and the owner can rotate the settler key to install themselves as the outcome authority for matches whose funds are already locked — including matches the owner is personally playing in.

Critical

[1] Unauthenticated shared deposit pool lets any address hijack and steal another user's pending deposit

Severity: Critical
Origin: [both] — unanimous: 5 of 6 phase-1 agents (general, precision-math, erc20, access-control, dos — the signatures agent's checklist scope did not cover this) and all 12 of 12 phase-2 agents independently found this
Location: _received() (lines 4437-4439), createMatch() (lines 4441-4454), joinMatch() (lines 4456-4468)
Description: Deposits are plain ERC20 transfers made in a separate transaction before createMatch/joinMatch — the contract's own comment documents this as the intended flow ("the deposit is a plain transfer done just before"). Crediting is authorized purely by:

function _received(address token) internal view returns (uint256) {
    return IERC20(token).balanceOf(address(this)) - accounted[token];
}

an ambient, token-wide pool with no binding to depositor identity. Whoever calls createMatch/joinMatch first after a deposit lands claims that balance, regardless of who sent it.
Proof of Concept: Victim sends 1,000 USDC to the contract intending to call createMatch(myId, USDC, 1000e6) next. An attacker watching for Transfer events (or simply the mempool) submits createMatch(attackerId, USDC, 1000e6) first — it passes _received(USDC) >= 1000e6 using the victim's deposit. accounted[USDC] += 1000e6; matches[attackerId] = Match(creator: attacker, ...). The victim's own createMatch call then reverts ("deposit first"); their 1,000 USDC is now the wager of the attacker's match. After acceptWindow (24h default), the attacker calls cancelUnaccepted(attackerId) and receives the victim's 1,000 USDC directly — theft complete, zero capital risked beyond gas. An identical variant against joinMatch lets an attacker become m.opponent using a victim's deposit, then recover it via refundStalled()'s equal-split refund after settleWindow (12h) — a guaranteed, no-coinflip-required extraction, since no legitimate settler will ever sign an outcome for a match the attacker didn't actually play.
Recommendation: Pull funds atomically inside createMatch/joinMatch via safeTransferFrom(msg.sender, address(this), wager) (requiring prior approve), eliminating the two-step race entirely:

     function createMatch(uint256 matchId, address token, uint256 wager) external nonReentrant {
         require(allowedToken[token], "token not allowed");
         require(wager > 0, "wager=0");
         require(matches[matchId].status == Status.None, "exists");
-        require(_received(token) >= wager, "deposit first");
+        IERC20(token).safeTransferFrom(msg.sender, address(this), wager);

         accounted[token] += wager;
         matches[matchId] = Match(msg.sender, address(0), token, wager, uint64(block.timestamp), 0, Status.Open);
         emit MatchCreated(matchId, msg.sender, token, wager);
     }

Apply the same pattern to joinMatch. If a push-then-register UX must be kept, bind deposits to depositor identity via a per-user pendingDeposit[msg.sender][token] mapping populated by an explicit deposit() call — never a shared pool.

High

[2] sweepUnaccounted() lets the owner steal any user's deposit that is mid-flight to a match — faster and with no waiting period

Severity: High
Origin: [both] — phase-1 (general, erc20, access-control, dos — 4 of 6 agents); phase-2 (leads, agents 2 and 11, both explicitly noting this is an even faster owner-side variant of Finding [1], requiring no waiting period at all)
Location: sweepUnaccounted() (lines 4551-4558)
Description: This function uses the identical balanceOf(this) - accounted[token] heuristic exploited in Finding [1] — it cannot distinguish a genuinely abandoned deposit from a deposit a legitimate user sent seconds ago and is about to consume via createMatch/joinMatch. The docstring's claim that it "can never touch tokens escrowed in matches" is only true for balances already folded into accounted[]; it is false for in-flight deposits. Unlike Finding [1]'s public exploitability, this requires the owner role — but the owner can act instantly, with no acceptWindow/settleWindow delay.
Proof of Concept: User sends 500 DAI intending to call createMatch next. Before that transaction lands, the owner calls sweepUnaccounted(DAI, ownerWallet); extra = 500 is transferred to the owner. The user's createMatch call then reverts and their 500 DAI is gone, with no recourse.
Recommendation: Same root fix as [1] (atomic pull via safeTransferFrom eliminates any legitimately-ambiguous "unaccounted" balance). As a secondary mitigation, require unaccounted balance to have aged beyond a grace period before it becomes sweepable.

[3] No pull-payment fallback — a blacklisted or paused token recipient permanently freezes both players' escrowed funds

Severity: High
Origin: [both] — phase-1 (erc20, dos, general, precision-math — 4 of 6 agents, covering both the blocklist-token and rebasing/deflationary-token angles); phase-2 (FINDING, agent 3; corroborating leads from agents 1, 4, 5, 7, 9, 10, 12 on the non-standard-token variant)
Location: settle() (transfers at lines 4487-4488), cancelUnaccepted() (line 4500), refundStalled() (transfers at lines 4511-4512)
Description: All payouts are push-only safeTransfer calls with no try/catch and no alternate recipient/pull path. If the token is blocklistable (USDC/USDT-style — relevant since this is deployed on Base, USDC's native chain) and either winner, m.creator, or m.opponent becomes blocked, or the token is a negative-rebasing/deflationary type whose real balance can drop below the recorded nominal wager/pot, every payout function for that match reverts unconditionally and permanently — there is no owner override, no split-payout, and sweepUnaccounted explicitly cannot touch escrowed balances.
Proof of Concept: Alice and Bob fund a 1,000 USDC match. Circle blacklists Bob's address (unrelated compliance action). Any settle() naming Bob as winner reverts forever; refundStalled() (which must pay both parties in one transaction) also reverts forever at Bob's leg. Both Alice's and Bob's combined 2,000 USDC are frozen permanently — Alice, an uninvolved party, loses access to her funds too.
Recommendation: Add a pull-payment fallback: on transfer failure, credit owed[token][recipient] += amount instead of reverting the whole settlement, and expose a separate withdraw(). Additionally restrict setTokenAllowed to vetted standard-conforming tokens, and make _received() saturate at zero instead of reverting on underflow.

[4] Owner can rotate settler mid-match to install themselves as the outcome authority for an already-committed match

Severity: High
Origin: [both] — phase-1 (access-control H-2); phase-2 (FINDING, agent 11, with a concrete self-dealing PoC sharper than phase-1's — owner plays as m.creator, waits for the victim to fund and genuinely win, then rotates settler to themselves and signs their own victory)
Location: settle() (lines 4472-4490), setSettler() (lines 4537-4540)
Description: settle() validates the signature against the current settler storage value, not the settler in effect when the match was funded. setSettler() takes effect instantly with no timelock and no restriction on matches already Funded. Because winner is only constrained to {m.creator, m.opponent} (not to the real off-chain outcome), a new settler key chosen by the owner can sign an outcome contradicting reality for any currently-Funded match — including one the owner is personally a party to.
Proof of Concept: Owner creates a match as m.creator (depositing their own funds). Victim V deposits and joins as m.opponent, and genuinely wins the off-chain contest. Before the honest settler signs, the owner calls setSettler(owner), signs a message naming themselves (owner) as winner using their own key, and calls settle(matchId, owner, sig) — every check passes (winner == m.creator ✓, digest.recover(sig) == settler ✓ since settler is now the owner). The pot, funded partly by V's legitimately-won stake, pays out entirely to the owner; V receives nothing.
Recommendation: Snapshot the authoritative settler into the Match struct at funding time and check against that stored value in settle(), not the live settler variable:

     struct Match {
         address creator;
         address opponent;
         address token;
         uint256 wager;
         uint64  createdAt;
         uint64  fundedAt;
         Status  status;
+        address settlerAtFund;
     }
...
-        require(digest.recover(sig) == settler, "bad sig");
+        require(digest.recover(sig) == m.settlerAtFund, "bad sig");

[5] setWindows() is unbounded and applies retroactively — owner can permanently freeze the refund/cancel safety net

Severity: High
Origin: [phase1-only] — dos, access-control. Re-examined: confirmed on re-read — setWindows() (lines 4545-4549) only enforces accept_ >= 1 hours && settle_ >= 1 hours, no upper bound; cancelUnaccepted() (line 4496) and refundStalled() (line 4507) read acceptWindow/settleWindow live rather than snapshotted per-match. Kept at High.
Location: setWindows() (lines 4545-4549); consumed live by cancelUnaccepted() (line 4496) and refundStalled() (line 4507)
Proof of Concept: Match funded with the default 12h settleWindow. Owner calls setWindows(1 hours, type(uint256).max). refundStalled()'s m.fundedAt + settleWindow computation now overflows and reverts on every call, permanently disabling the refund path for that match and all other currently-funded matches, unless the owner later lowers the window again — leaving settle() (dependent on the same owner-controlled settler, see [4]) as the only remaining exit.
Recommendation: Add a sane upper bound to setWindows (e.g. <= 30 days), and/or snapshot the effective deadlines into the Match struct at creation/funding time so later global changes only affect future matches.

Medium

[6] Fee rate is read live at settlement, not locked in when the match is funded

Severity: Medium
Origin: [both] — phase-1 (precision-math, general, signatures, access-control, erc20 — 5 of 6 agents); phase-2 (FINDING, agent 11; LEAD, agent 10)
Location: settle() line 4484 (feeBps(m.token)), setDefaultFee() (lines 4518-4522), setTokenFee() (lines 4523-4527)
Description: Match stores no fee snapshot; settle() calls feeBps(m.token) live. The owner can change the rate (bounded only by MAX_FEE_BPS = 1000, 10%) at any point between funding and settlement — including immediately before a pending settle() transaction — silently redirecting a larger share of the pot to treasury than players agreed to when they funded the match. The signed settlement digest also does not bind the fee, so a valid signature's economic effect can be altered without re-signing anything.
Proof of Concept: Match funded when defaultFeeBps = 500 (5%); winner expects 95% of pot. Owner calls setDefaultFee(1000) (10%, the hard cap) before settle() executes; the winner receives 5 fewer percentage points than expected, captured instead by treasury.
Recommendation: Snapshot feeBps(token) into the Match struct at joinMatch() time and use the stored value in settle().

[7] Race between settle() and refundStalled() — a losing party can front-run a valid signed outcome once settleWindow elapses

Severity: Medium
Origin: [phase1-only] — signatures SIG-1. Re-examined: confirmed on re-read — the signed digest (lines 4477-4479) has no expiry, settle() imposes no deadline of its own, and refundStalled() (line 4504) becomes callable by anyone once block.timestamp >= m.fundedAt + settleWindow regardless of a pending signature. Kept at Medium.
Location: settle() (lines 4472-4490), refundStalled() (lines 4504-4514)
Proof of Concept: Off-chain contest concludes; Bob loses. The settler's settle(matchId, Alice, sig) transaction is delayed (backend latency) until at or after settleWindow. Bob sees it pending and front-runs with refundStalled(matchId), which succeeds first (status flips to Refunded) and returns his full wager instead of forfeiting it; Alice's rightful winnings are never paid, and the pending settle() call reverts.
Recommendation: Make the windows mutually exclusive — bound settle() to only be callable strictly before m.fundedAt + settleWindow, or embed a settler-chosen deadline in the signed digest.

Low

[8] settle() only supports EOA-style ECDSA signers — no ERC-1271 fallback for a contract-based settler

Severity: Low
Origin: [phase1-only] — signatures SIG-3. Re-examined: confirmed — ECDSA.recover (line 4480) cannot validate a smart-contract signer, and setSettler() (lines 4537-4540) has no code.length check preventing a contract address. Kept at Low.
Location: settle() line 4480, setSettler() (lines 4537-4540)
Recommendation: Either reject contract addresses in setSettler, or use OZ's SignatureChecker.isValidSignatureNow to support both EOA and ERC-1271 signers.

[9] Fee always rounds down — treasury collects zero fee on small wagers

Severity: Low
Origin: [phase1-only] — precision-math L-1. Re-examined: confirmed the mechanism (fee = (pot * feeBps) / 10_000 floors at lines 4483-4484), but one phase-2 agent (numerical-gap) independently considered this exact pattern and concluded it is "ordinary rounding dust with no accounting drift" since accounted[] is decremented by the untruncated pot — i.e., no phantom balance accumulates, this is a fee-collection shortfall only, not an accounting-integrity bug. Kept at Low given both perspectives.
Location: settle() lines 4483-4484
Proof of Concept: With the default 5% fee, any match with wager <= 9 (pot <= 18) settles with fee = 0.
Recommendation: Round the fee up (Math.mulDiv(..., Rounding.Ceil)) if fee collection is intended to be guaranteed on any nonzero rate.

[10] Caller-chosen matchId enables cheap griefing via ID-squatting

Severity: Low
Origin: [phase1-only] — erc20, dos. Re-examined: confirmed — createMatch() line 4448 only checks matches[matchId].status == Status.None, with matchId fully caller-chosen. Kept at Low.
Location: createMatch() line 4448
Recommendation: Derive matchId internally (auto-increment or keccak256(msg.sender, nonce)) rather than trusting caller input.

[11] sweepUnaccounted() is the only value-moving function missing nonReentrant

Severity: Low
Origin: [both] — phase-1 (general, erc20); phase-2 (LEAD, agent 2)
Location: sweepUnaccounted() (lines 4551-4558)
Description: Every other state-mutating, fund-moving function carries nonReentrant; this one does not. Low real-world risk since it's onlyOwner-gated with an owner-chosen recipient, but inconsistent with the contract's defensive posture.
Recommendation: Add nonReentrant for consistency.

[12] Single-step Ownable with no timelock/multisig; renounceOwnership not disabled

Severity: Low
Origin: [phase1-only] — access-control L-1. Re-examined: confirmed — the contract inherits plain OZ v5 Ownable (single-step transferOwnership, renounceOwnership not overridden). Kept at Low.
Location: contract declaration (line 4379); inherited OZ v5 Ownable
Description: Every privileged function (setSettler, setTreasury, setTokenAllowed, fee/window setters, sweepUnaccounted) depends on a live, correct owner. A mistyped transferOwnership target or accidental renounceOwnership() permanently locks out all administration, including the ability to ever rotate settler again if its key is lost.
Recommendation: Use Ownable2Step or a multisig/timelock-controlled owner; override renounceOwnership() to revert given the contract's ongoing operational dependence on the role.
