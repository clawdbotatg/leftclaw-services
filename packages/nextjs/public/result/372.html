1. [High] VRF acquisition selection steerable / DoS-able via unlocked dust deposits

Category: [both] — independently found by 4 agents (general-checklist, oracles-checklist in Phase 1; numerical-gap and trust-gap in Phase 2, blind)
Location: FWA.listNFT() (no lock, src/FWA.sol:719-817), FWA.fulfillRandomWords() selection (:1196-1296, index computed at :1221-1223), withdrawListing/updateBacking locks (:832-834, :892-894), fulfillment slippage guard (:1204-1214)

Description

The winning listing is computed at VRF-callback time against live, mutable state:

uint256 target = randomWords[0] % totalWeight;   // :1221
uint256 slot = _selectSlot(target);              // walks the live segment tree

withdrawListing/updateBacking-decrease respect a withdrawLockBlocks window (default 5 blocks) after the most recent acquisition — but listNFT (deposits) is never gated by that window, by explicit design (src/FWA.sol:726: "Deposits are otherwise always allowed, even with acquisitions in flight."). Because selection weight is weight = 1e36 / value (inverse of backing), a 1-wei deposit gets weight ≈ 1e36 — roughly 10^18× a normal 1-ETH listing's weight — while minBacking defaults to 0, placing no floor on how small a deposit can be.

Two independent, coexisting attack variants share this one root cause:

  • Targeted steering. The Chainlink VRF v2.5 fulfillment transaction (carrying the random word) is visible in the mempool before it mines. An attacker computes _selectSlot(randomWords[0] % totalWeight) against current state and, if it doesn't land on their target, front-runs the fulfillment with a deposit sized to shift the modulus onto the target listing — while keeping the deposit's backing near the pool's harmonic mean so the EV-based fulfillment slippage guard (which only bounds the fee, not which slot is chosen) doesn't trip.
  • Cheap denial-of-service. A single default-minBacking (0) deposit of 1 wei captures near-100% of selection weight and simultaneously collapses acquisitionFee() (a harmonic mean) toward ~1 wei. Every in-flight acquisition's fulfillment then either force-refunds via the slippage guard (burning the purchaser's non-refundable VRF fee) or is won by the worthless dust listing — making the pool effectively unusable for as long as the dust listing sits resident.

Proof of Concept (concrete numbers, phase-2 numerical-gap agent)

Pool of ten 1-ETH listings: each weight = 1e36/1e18 = 1e18, totalWeight = 1e19, EV = weightedBackingTotal/totalWeight = 1e18 (1 ETH), fee ≈ 1.1 ETH. A griefer deposits one 1-wei listing: weight = 1e36/1 = 1e36. New totalWeight ≈ 1e36 + 1e19 ≈ 1e36. P(select dust) = 1e36/(1e36+1e19) ≈ 1 − 1e-17. New EV ≈ (1e37 + 1e36)/1e36 ≈ 10 wei → acquisitionFee ≈ 11 wei. Any purchaser's maxAcquisitionFee ceiling (set to protect against overpaying) does not prevent this — 11 wei clears any reasonable ceiling — so purchasers keep paying to draw the dust listing (or trigger a slippage refund, at cost of their VRF fee) while the real listings sit at ~0% selection probability.

Recommendation

Selection must be a pure function of state committed no later than the VRF request. Snapshot the selection basis (totalWeight plus enough structure to reconstruct ordering — e.g. a checkpointed tree) into the Acquisition record at request time, and resolve fulfillRandomWords against that snapshot, not the live tree. As a secondary, defense-in-depth measure: gate listNFT behind the same withdrawLockBlocks window used for withdrawals (deposits distort selection exactly like withdrawals do), and enforce a non-trivial minBacking floor so no single deposit can dominate totalWeight. Do not rely on selectionSlippageBps to protect the discrete index draw — it only bounds the fee amount, never which slot is chosen.

2. [Medium] withdrawListing's strict safeTransferFrom can lock NFT + ETH together

Category: [phase1: evm-audit-erc721, evm-audit-dos] — re-verified via direct source read
Location: withdrawListing() — src/FWA.sol:855-856 (confirmed exact lines during reconciliation)

Description

Every other NFT-exit path in the contract deliberately decouples the ETH leg from NFT deliverability (_deliverNFT wraps transferFrom in try/catch with a stuckNFTRecipient fallback). withdrawListing is the sole exception:

SafeTransferLib.forceSafeTransferETH(msg.sender, value);           // :855
ERC721(collection).safeTransferFrom(address(this), msg.sender, tokenId);  // :856 — strict, reverts whole tx

safeTransferFrom invokes onERC721Received on the recipient. Two failure vectors converge here: (a) a contract-wallet depositor without that hook can never withdraw — the entire transaction, including the ETH refund, reverts every time; (b) if the collection later pauses transfers or blacklists the FWA contract, the same strict revert locks the backing ETH together with the NFT. This is the only self-service exit for a never-allocated (active) listing — unlike keepNFT, there is no fallback path.

Proof of Concept

A smart-contract-wallet depositor (no onERC721Received) lists an NFT with backing ETH and is never selected for acquisition. They call withdrawListing — it reverts every time at line 856, permanently locking both the NFT and the ETH through this path; their only recourse is hoping a third party's acquisition happens to allocate the listing so depositorReclaimNFT's plain transferFrom applies instead.

Recommendation

- ERC721(collection).safeTransferFrom(address(this), msg.sender, tokenId);
+ ERC721(collection).transferFrom(address(this), msg.sender, tokenId);

The recipient is msg.sender, who explicitly requested the token, so no receiver-safety benefit is lost by using the plain form (consistent with every other exit path in the contract).

3. [Medium] Token-buy partial-fill silently strands unspent ETH

Category: [both] — erc20, defi-amm checklists (phase 1); execution-trace FINDING (78 confidence) + invariant/boundary/periphery/flow-gap leads (phase 2, 5 agents total)
Location: FWA.claimAccruedTokens() / FWA.acceptBidAsTokens() → _buyTokens() → unlockCallback()

Description

claimAccruedTokens zeroes the caller's full tokenBuyAllowance (and acceptBidAsTokens commits the full payout) before the swap. unlockCallback runs a Uniswap v4 exact-input swap (sqrtPriceLimitX96 = TickMath.MIN_SQRT_PRICE + 1, no explicit floor) and settles only what the pool actually consumed (uint256(int256(-d.amount0()))). If the pool's in-range liquidity is exhausted before the full input is spent — plausible especially early post-launch, before deep liquidity accumulates — the swap partially fills, and the difference between the committed amount and the actually-spent amount is silently orphaned in the contract's general balance. Critically, minOut only bounds token output (which is naturally larger, not smaller, on an underspend), so it provides no protection against this failure mode.

Proof of Concept

Purchaser has tokenBuyAllowance = 5 ETH; pool liquidity is thin; the swap fills only 2 ETH worth before running out of in-range FWAToken. settle moves 2 ETH; the remaining 3 ETH sits in FWA's general balance, un-attributed to anyone. The purchaser's allowance was zeroed for the full 5 ETH — the 3 ETH is permanently lost to them, with no recovery path.

This is the single most independently-corroborated item in the entire audit (5 of 12 phase-2 attacker agents converged on it from different angles, plus phase 1's ERC20 and AMM checklist passes), which is why it is rated Medium here despite each individual agent capping confidence below the auto-promote threshold (it requires a specific — if realistic — liquidity condition rather than being unconditionally triggerable).

Recommendation

  BalanceDelta d = tokenPoolManager.swap(key, params, "");
+ uint256 consumed = uint256(int256(-d.amount0()));
  key.currency0.settle(tokenPoolManager, address(this), uint256(int256(-d.amount0())), false);

- tokenBuyAllowance[msg.sender] = 0;
- tokenBuyAllowanceTotal -= amount;
+ tokenBuyAllowance[msg.sender] = amount - consumed;   // re-credit unspent remainder
+ tokenBuyAllowanceTotal -= consumed;

Apply the equivalent re-credit (refund payout - consumed ETH to the purchaser) in acceptBidAsTokens.

4. [Medium] FWAToken.buyback() has no slippage protection

Category: [both] — defi-amm checklist (phase 1); economic-security (phase 2)
Location: FWAToken.buyback() / FWAToken.unlockCallback()

Description

buyback() is permissionless and spends up to BUYBACK_INCREMENT (1 ETH) per call against the v4 pool with sqrtPriceLimitX96 = TickMath.MIN_SQRT_PRICE + 1 (the "no limit" sentinel) and no amountOut >= minOut check anywhere — unlike FWA's own token-buy paths (claimAccruedTokens/acceptBidAsTokens), which correctly enforce SlippageBuy() against a caller-supplied minOut. The ETH spent is real protocol value (routed from protocolFeeToTokenBps of accrued fees, or any directly-sent ETH), and the FWAToken received is distributed to depositors/purchasers or burned — under-buying directly shortchanges those beneficiaries. A related, unresolved architectural question (see Informational, item [i]) is whether the out-of-scope hook even authorizes this swap consistently with FWA's own isBuying-gated buys.

Proof of Concept

Once the pool's sell side is open, an attacker can sandwich any buyback() call: front-run to move price up, let the unprotected buyback execute at the inflated price, back-run to sell back for a profit funded by the buyback reserve. Since buyback() is permissionless, the attacker can also trigger it themselves inside the sandwich. Per-call loss is capped at the 1-ETH slice but is repeatable every time the delay window (BUYBACK_DELAY_BLOCKS) elapses.

Recommendation

Add a slippage floor — gate buyback() behind an owner/keeper-supplied minAmountOut, or derive one from a short on-chain TWAP checkpoint (a raw current-spot minOut is itself manipulable).

5. [Medium] setRequestConfirmations/setCallbackGasLimit unbounded, break timing invariants

Category: [both] — oracles, access-control checklists (phase 1); periphery, boundary (phase 2)
Location: setRequestConfirmations(), setSelectionTimeoutBlocks(), setCallbackGasLimit()

Description

setSelectionTimeoutBlocks enforces newSelectionTimeoutBlocks >= requestConfirmations, but setRequestConfirmations performs no validation and never re-checks that invariant from its own side. If the owner raises requestConfirmations above the current selectionTimeoutBlocks (default 30) or withdrawLockBlocks (default 5), an acquisition becomes cancellable — permissionlessly, via cancelAcquisition — before the wrapper can legitimately deliver the callback, griefing purchasers out of their non-refundable VRF fee when the late callback then reverts (UnknownRequest). Separately, setCallbackGasLimit has no floor; the contract's own NatSpec documents a measured ~578k-gas cold cost and warns that a lower limit makes every fulfillRandomWords revert out-of-gas, silently bricking acquisitions until fixed (recoverable via cancelAcquisition — no permanent fund lock, but a real, uncapped DoS lever).

Proof of Concept

Owner calls setRequestConfirmations(50) while selectionTimeoutBlocks == 30. A purchaser's acquire() sits pending; at block requestBlock+30 anyone calls cancelAcquisition (succeeds, refunds pool fee); at block requestBlock+50 the genuine callback lands and reverts UnknownRequest — the purchaser has lost their VRF fee for nothing.

Recommendation

Bound setRequestConfirmations to [wrapper-min, selectionTimeoutBlocks] (and ideally <= withdrawLockBlocks), and add a floor to setCallbackGasLimit comfortably above the documented cold-cost (e.g. 600k). Re-assert selectionTimeoutBlocks >= requestConfirmations whenever either setter runs.

6. [Medium] Settlement-economics parameters mutable in-flight on allocated listings

Category: [both] — access-control checklist (phase 1, focused on ownerSettlementFeeBps); invariant + trust-gap (phase 2, broadened to settlementDiscountBps and retainedToProtocol)
Location: setOwnerSettlementFeeBps(), setSettlementDiscountBps(), setRetainedToProtocol(), applied live in _settleNFTToPurchaser() / _settleBackingToPurchaser()

Description

ownerSettlementFeeBps's only bound is <= settlementDiscountBps, which itself can reach BPS (100%) — so the owner's cut of a depositor's returned backing can legally reach up to 85% under default config, or 100% if settlementDiscountBps is first raised. All of these parameters — ownerSettlementFeeBps, settlementDiscountBps, and the retainedToProtocol routing flag — are read live at settlement time, not snapshotted when the listing was allocated. A listing can sit Allocated for up to finalizeWindow (default 7 days) with the depositor unable to withdraw. The owner can therefore change any of these parameters after a listing is allocated but before it resolves, retroactively re-pricing a specific, already-committed depositor or purchaser with no advance warning or opt-out.

Proof of Concept

Depositor lists an NFT with ownerSettlementFeeBps = 100 (1%) live; a purchaser's VRF draw allocates it (depositor can no longer withdraw); owner calls setOwnerSettlementFeeBps(8500) (valid — <= settlementDiscountBps); on keepNFT/finalizeUnsettled, _settleNFTToPurchaser computes ownerCut = value * 8500/BPS, and the depositor receives only 15% of their backing while losing the NFT.

Recommendation

Cap ownerSettlementFeeBps at a small absolute constant (e.g. a few hundred bps) independent of settlementDiscountBps. Snapshot settlementDiscountBps, ownerSettlementFeeBps, and retainedToProtocol into the Listing (or Acquisition) record at allocation time, and settle against the snapshot so a mid-flight owner change cannot apply retroactively.

7. [Medium] setToken re-callable with no one-shot guard; malicious tokenPoolManager can drain escrow

Category: [both] — access-control checklist (phase 1); access-control (phase 2)
Location: setToken(), sink in unlockCallback()

Description

setToken can be called at any time (no "once" guard), rewiring token, tokenPoolManager, and tokenHook. tokenPoolManager is then fully trusted inside _buyTokens/unlockCallback: the callback settles native ETH for whatever BalanceDelta the pool manager's swap() returns. If the owner (maliciously, or under key compromise) points tokenPoolManager at an attacker-controlled contract, that contract can return a crafted delta equal to the entire contract's ETH balance, and settle forwards it out — draining every depositor's escrowed backing in one transaction triggered by any token-buy path. Separately (phase-2 corroboration), re-wiring after outstanding liabilities (tokenBuyAllowance, tokenCredit, purchaserEpochPot) have accrued against the old token leaves them denominated against a token no longer wired up.

Proof of Concept

Users have listed NFTs with escrowed backing. Owner calls setToken(anyToken, maliciousPoolManager, anyHook), then triggers any _buyTokens path. The malicious manager's unlock→swap returns a delta sized to the contract's full ETH balance; settle transfers it all out.

Recommendation

Make the token/pool wiring one-shot (settable once, then locked), or immutable via constructor; at minimum forbid re-wiring after emissionStart != 0 / after the token has been "launched."

8. [Low] cancelAcquisition can front-run a legitimate VRF fulfillment at the timeout boundary

Category: [phase2: execution-trace] — re-verified via direct source read
Location: cancelAcquisition() — src/FWA.sol:1311 confirmed: if (block.number < acquisition.requestBlock + selectionTimeoutBlocks) revert SelectionNotStale();

Description

cancelAcquisition is permissionless and becomes callable at exactly block.number == requestBlock + selectionTimeoutBlocks. If the genuine Chainlink fulfillment is delayed close to that boundary (network congestion, or the window simply being tight under load), any third party can snipe-cancel the pending acquisition one block before the real callback lands. The subsequent legitimate fulfillment then reverts (status != Pending), converting what would have been a valid allocation into a forced refund and burning the purchaser's non-refundable VRF fee. This is distinct from finding #5 (which covers owner misconfiguration) — this is a narrow but real race under correct default configuration.

Recommendation

Widen the safety margin between requestConfirmations and selectionTimeoutBlocks (require the timeout to exceed confirmations by a fixed buffer, not just >=), and/or give the requesting purchaser (not just anyone) priority to cancel their own request during a short window before it opens up permissionlessly.

9. [Low] FWAToken is transfer-locked; rewards can be permanently non-transferable

Category: [phase1: evm-audit-erc20] — re-verified via direct source read
Location: FWAToken._afterTokenTransfer() — confirmed lines 405-425: every branch other than mint/burn, isDistributor, owner, or PoolManager-with-allowance reverts with InvalidTransfer()

Description

Ordinary holders cannot transfer FWAToken to each other at all. Every FWAToken FWA hands to depositors/purchasers (emissions, settlement top-ups) lands on a recipient who cannot move or sell it until the (out-of-scope) hook opens selling via the transient allowance mechanism. This is very likely an intentional pre-launch lock, but it is a real, undocumented-to-holders liquidity assumption — if selling is never opened, rewards are permanently soft-locked.

Recommendation

Document explicitly (to users/integrators) that reward tokens are non-transferable until selling is enabled, and ensure there is a guaranteed path/timeline to opening it.

10. [Low] setSettlementWindow can be set to 0, removing the purchaser's exclusive decision window

Category: [phase2: trust-gap] — re-verified via direct source read
Location: setSettlementWindow() — src/FWA.sol:2203-2207 confirmed: only bound is newSettlementWindow > finalizeWindow reverts; 0 is legal

Description

settlementWindow is meant to give the purchaser exclusive time to choose NFT-or-ETH before the depositor may resolve the listing themselves. With settlementWindow = 0, a depositor can call depositorReclaimNFT essentially immediately after allocation — clawing the NFT back for the discounted settlementDiscountBps payout before the purchaser has any practical chance to keepNFT.

Recommendation

Add a sane non-zero floor to setSettlementWindow (e.g. a minimum of several minutes/blocks) so the purchaser always has a meaningful decision window.

11. [Low] Perpetual withdrawal-lock griefing via renewed acquisitions

Category: [both] — dos checklist (phase 1); economic-security, execution-trace (phase 2)
Location: acquire()/acquireBatch(), lock check in withdrawListing/updateBacking

Description

The withdrawLockBlocks window applies globally (to all depositors) after any acquisition, keyed off a single lastSelectionBlock. An attacker firing acquire() at least once every withdrawLockBlocks (default 5) blocks can keep the pool-wide withdrawal lock open indefinitely. Self-throttling — each renewal costs the non-refundable vrfFee() — and fully mitigated by the owner via withdrawOnly emergency mode, which bypasses the lock.

Recommendation

Consider gating the lock per-pending-acquisition rather than globally, or cap total contiguous lock duration; otherwise document withdrawOnly as the intended operator response.

12. [Low] Single-step Ownable, no 2-step transfer, on both contracts

Category: [phase1: evm-audit-access-control]
Location: Both FWA and FWAToken (Solady Ownable)

Description

Both contracts use plain (single-step) Ownable. A mistyped transferOwnership target permanently loses control of every onlyOwner function (including the emergency withdrawOnly escape hatch), and renounceOwnership is live and would freeze all owner-gated configuration. Given the scope of owner power (findings #5-7 above), the blast radius of key loss or compromise is the entire protocol's escrowed ETH/NFTs.

Recommendation

Use Ownable2Step (pending-owner accept flow) for both contracts, and place ownership behind a multisig/timelock.

13. [Low] keepNFT's strict delivery forces contract purchasers into the discounted ETH bid

Category: [phase1: evm-audit-erc721] — re-verified: keepNFT at src/FWA.sol:1333 calls _settleNFTToPurchaser(listingId, listing, true) with strict=true, which uses safeTransferFrom
Location: _settleNFTToPurchaser() strict branch

Description

A contract purchaser without onERC721Received can never call keepNFT and is forced to fall back to acceptDepositorBid (85% of backing, forfeiting the NFT) — even though every other delivery path in the contract (_deliverNFT, used by depositorReclaimBacking/finalizeUnsettled) proves the NFT is in fact deliverable via plain transferFrom.

Recommendation

Route keepNFT through _deliverNFT's best-effort + stuckNFTRecipient fallback instead of a strict safeTransferFrom.

14. [Low] Owner-controlled distributor whitelist bypasses the transfer lock

Category: [phase1: evm-audit-access-control]
Location: setDistributor() (FWAToken.sol)

Description

The owner can flag any address as a distributor, exempting it from finding #9's transfer lock with no restriction. Combined with the owner's own transfer exemption, this lets the owner (or a designated accomplice) move/sell FWAToken freely while ordinary holders remain locked — an insider-exit trust assumption.

Recommendation

Document explicitly; consider restricting setDistributor to contract addresses and/or adding a timelock so additions are visible before taking effect.

15. [Low] Lingering unlimited approvals to PositionManager/Permit2 after launch()

Category: [phase1: evm-audit-defi-amm]
Location: FWAToken.launch()

Description

launch() grants type(uint256).max/type(uint160).max approvals to Permit2/PositionManager that are never revoked after the one-time launch call. Counterparties are canonical Uniswap contracts, so real-world risk is low, but the standing max grant is unnecessary after a single-use operation.

Recommendation

Revoke (approve(..., 0)) after launch() completes, or scope the approval to the exact amount seeded.

16. [Low] JIT deposit around permissionless buyback() captures disproportionate depositor emission

Category: [phase2: flow-gap]
Location: FWA.onTokenReceived() (invoked from FWAToken.buyback())

Description

The depositor slice of a buyback is distributed by current √value share (accTokenPerSqrt += depositorAmt·SCALE/sqrtBackingTotal). Because buyback() is permissionless and its trigger timing is publicly known, an attacker can deposit a large-backing listing (which, per finding #1's inverse-weighting, carries near-zero selection/allocation risk) immediately before triggering buyback(), capture a disproportionate share of that round's depositor emission, then withdraw the backing after the withdrawLockBlocks window — diluting genuine standing depositors.

Recommendation

Consider a minimum listing age before it counts toward the √value emission denominator, or checkpoint the buyback's depositor slice against a time-weighted average of sqrtBackingTotal rather than the instantaneous value.

17. [Low] claimEpochTokens/setEmission floor-rounding strands token dust / silently zero-emits

Category: [phase1: evm-audit-precision-math]
Location: claimEpochTokens()/_purchaserEpochAmount(), setEmission()

Description

Per-purchaser epoch-pot shares are floored; the sum of floored claims is strictly less than the pot, and the remainder is unrecoverable for any epoch with acquisitionsInEpoch > 0 (the only sweep path, sweepEmptyEpoch, requires zero acquisitions). Separately, setEmission floors depositorTotal/EMISSION_DURATION and purchaserTotal/EMISSION_DAYS with no revert-on-zero, so a small enough bucket silently emits at rate 0 for the whole window with no error signal.

Recommendation

Let closed non-empty epochs' post-claim remainder be swept, or track claimed totals and let a final claimant sweep the rest. Revert setEmission if a nonzero total produces a zero rate/pot.

18. [Low] Additional unbounded owner setters (surcharge, owner-acquisition-fee, batch size)

Category: [phase1: evm-audit-access-control, evm-audit-dos]
Location: setSurchargeBps(), setOwnerAcquisitionFeeBps(), setMaxAcquisitionsPerTx()

Description

setSurchargeBps has no upper bound (can be set high enough to overflow acquisitionFee()'s multiplication, reversibly DoS'ing acquire); setOwnerAcquisitionFeeBps is capped only at 100% (owner could route the entire distributable acquisition fee to the protocol, zeroing depositor yield); setMaxAcquisitionsPerTx has a non-zero floor but no ceiling. All are owner-only, reversible, and cause no direct fund loss to third parties.

Recommendation

Add sane upper bounds to each (e.g. a few thousand bps cap on surcharge, a materially-below-100% cap on the owner acquisition fee, and a small integer ceiling on batch size).

19. [Low] Sybil self-dealing can farm FWAToken emissions

Category: [phase1: evm-audit-general]
Location: Epoch tally in fulfillRandomWords(), depositor emission accrual, acquisitionTokenSlice

Description

Nothing prevents one actor from being both the majority depositor and the acquiring purchaser, recapturing most of their own distributed acquisition fee plus ongoing emissions, at a marginal cost of just the VRF fee and owner cuts. Bounded by real per-loop costs; a tuning/monitoring concern rather than a direct exploit.

Recommendation

Ensure vrfFee + owner cuts + retained penalty exceeds expected per-acquisition emission value at launch parameters; consider excluding self-acquisitions from purchaser-pot tallies.

20. [Low] Division-before-multiplication in acquisitionFee()

Category: [phase1: evm-audit-precision-math]
Location: acquisitionFee()

Description

ev = weightedBackingTotal / totalWeight floors before the surcharge multiply, understating the fee by at most ~1 wei versus the precision-preserving weightedBackingTotal * (BPS+surchargeBps) / (totalWeight*BPS) ordering. Not exploitable at ether-scale magnitudes; a best-practice deviation.

Recommendation

Reorder to multiply before dividing.

Informational (no action required, or documentation-only)
