Findings

[90] 1. Unbounded stakes[user] array degrades getActiveStakes()/getStakeCount() for that address only

TurboFaithStaking.getActiveStakes · Confidence: 90 · Severity: Low

Description
stakes[user] (L43) only ever grows via push() (L81); unstake() zeroes a slot's amount (L104) but never removes it. getActiveStakes() (L135–158) does two full passes over the array. Growth is strictly self-inflicted — stake() always writes to stakes[msg.sender] (L80–81), so no attacker can bloat another user's array — but it's cheap: since unstake() returns the full principal (L108), an attacker can recycle a single MIN_STAKE (1000 tokens) through repeated stake()→unstake() cycles at pure gas cost (no capital lockup), growing their own array by one slot per cycle. On Base's low gas, reaching ~7,000–15,000 entries (enough to exceed a ~30M gas read ceiling) is estimated at tens-to-low-hundreds of dollars. stake() and unstake() themselves remain O(1) regardless of array length — no funds are ever at risk, only the convenience view degrades, and only for its own owner (or a third-party integrator that batch-enumerates users on-chain without per-call isolation — no such integrator exists in scope, see Leads).

Fix

-    function getActiveStakes(address user)
+    function getActiveStakes(address user, uint256 offset, uint256 limit)
         external
         view
         returns (uint256[] memory amounts, uint256[] memory stakedAts, uint256[] memory indices)
     {
-        Stake[] storage userStakes = stakes[user];
-        uint256 len = userStakes.length;
+        Stake[] storage userStakes = stakes[user];
+        uint256 len = Math.min(userStakes.length, offset + limit);
         // iterate from `offset` to `len` instead of `0` to `userStakes.length`
     }

[90] 2. stake() violates checks-effects-interactions — mitigated by shared nonReentrant lock and a hook-free token

TurboFaithStaking.stake · Confidence: 90 · Severity: Info

Description
stake() pulls tokens via safeTransferFrom (L78) before writing stakes/totalStaked/totalSupplyStaked/weightedStakeSum (L80–86), unlike unstake() which correctly writes state before its external call (L101–105 vs L108). Not exploitable today: OpenZeppelin's ReentrancyGuard uses one shared _status slot across every nonReentrant function in the contract, so a reentrant call into either stake() or unstake() during the transfer reverts regardless of entry point (independently confirmed by 6 of 12 phase-2 agents); and the actual deployed stakingToken (verified ClankerToken source) has a hook-free _update() — a bare passthrough — so no callback can fire during the transfer in the first place.

Fix

     function stake(uint256 amount) external nonReentrant {
         require(amount >= MIN_STAKE, "Below minimum stake");
-        stakingToken.safeTransferFrom(msg.sender, address(this), amount);
-
         uint256 stakeIndex = stakes[msg.sender].length;
         stakes[msg.sender].push(Stake({ amount: amount, stakedAt: block.timestamp }));
         totalStaked[msg.sender] += amount;
         totalSupplyStaked += amount;
         weightedStakeSum[msg.sender] += amount * block.timestamp;
+        stakingToken.safeTransferFrom(msg.sender, address(this), amount);

         emit Staked(msg.sender, amount, stakeIndex, block.timestamp);
     }

[90] 3. No balance-delta accounting — structural gap, not exploitable against the deployed token

TurboFaithStaking.stake · Confidence: 90 · Severity: Info

Description
Accounting credits the caller-supplied amount parameter (L82–84) rather than measuring balanceOf(this) before/after the transfer. Would matter against a fee-on-transfer or rebasing token (later unstakers could find the pool short of what's recorded). stakingToken is immutable (fixed at deploy, cannot be swapped) and the actual deployed token is a plain, non-fee, non-rebasing ERC20 — confirmed via its _update() override being an unmodified passthrough, and via an on-chain snapshot at audit time showing stakingToken.balanceOf(stakingContract) == totalSupplyStaked exactly (4,635,026.129...e18 both sides). Not exploitable against this specific, already-deployed instance.

Fix: For any future redeployment of this bytecode against a different token, measure the balance delta around the transfer instead of trusting the parameter.

[85] 4. MIN_STAKE hardcodes an 18-decimal assumption

TurboFaithStaking.MIN_STAKE (L35) · Confidence: 85 · Severity: Info

Description
MIN_STAKE = 1_000e18 assumes an 18-decimal token; the constructor never validates decimals(). Confirmed correct for the live, immutable deployment (stakingToken.decimals() == 18, verified on-chain via cast call). Would misbehave only if this exact bytecode were redeployed against a non-18-decimal token — a template-reuse fragility, not a live bug.

Fix: For future redeployments, derive MIN_STAKE from stakingToken.decimals() instead of hardcoding.

[85] 5. No rescue/sweep for stray tokens sent directly to the contract

TurboFaithStaking (contract-wide) · Confidence: 85 · Severity: Info

Description
Tokens sent via a bare transfer() (bypassing stake()) become permanently unclaimable — no admin/sweep function exists. This is intentional given the no-admin design goal (adding a sweep function would reintroduce a privileged role); documented here as an accepted tradeoff, not a defect.

Fix: None required — consistent with the contract's documented no-admin design. Consider noting this behavior for users/integrators.

[75] 6. Constructor doesn't validate _stakingToken has code

TurboFaithStaking.constructor (L69–72) · Confidence: 75 · Severity: Info

Description
The constructor checks only _stakingToken != address(0) (L70), not _stakingToken.code.length > 0. Traced both OpenZeppelin SafeERC20 major-version implementations (4.x, 5.x) and confirmed each independently guards against no-code targets and reverts cleanly rather than silently no-op-succeeding — so this is not exploitable even in the worst case, and moot regardless since the actual deployed stakingToken is a real, verified contract.

Fix: None required for this instance; optionally add an explicit code.length > 0 check for defense-in-depth in future deployments.

Findings below confidence threshold

The following are documented for completeness but scored below the report's confidence-for-fix threshold (still ≥50, so listed as findings rather than Leads per the reporting floor) — description only, no fix block.

[65] 7. totalSupplyStaked is a write-only variable — never read by any function in this contract

TurboFaithStaking.totalSupplyStaked (L49) · Confidence: 65

Incremented in stake() (L83) and decremented in unstake() (L105) but consumed by no calculation anywhere in the contract — purely an informational public tally (e.g., for an off-chain dashboard). Confirmed to feed no on-chain logic, so it cannot itself be a vector for cross-user harm within this contract; flagged only because a hypothetical companion contract elsewhere that reads this getter as a trust signal is not something a single-contract audit can rule out.

[65] 8. Same-block stake/unstake momentarily inflates public TVL counters (rejected as a Finding — no identifiable victim in scope)

TurboFaithStaking.stake / unstake · Confidence: 65

An attacker can stake(X) then unstake(sameIndex) within one transaction; totalSupplyStaked/totalStaked[attacker] are genuinely inflated by X for the duration between the two calls (these are simple running counters with no time-lock). This was raised as a FINDING by one phase-2 agent but rejected at Gate 4 (Impact): no identifiable victim exists — TurboFaithStaking.sol itself never reads totalSupplyStaked in any calculation, and no other in-scope contract reads these getters. Documented here as a design note: these two counters are unsafe for any future external integrator to trust as an instantaneous, same-block signal.

[60] 9. getFaith()'s multiplication uses absolute block.timestamp rather than a bounded duration

TurboFaithStaking.getFaith (L115) · Confidence: 60

unstake() multiplies amount by a bounded elapsed duration (block.timestamp - stakedAt, L98), while getFaith() multiplies totalStaked[user] by the unbounded, ever-growing absolute block.timestamp (L115). Constructed the theoretical overflow threshold explicitly: requires block.timestamp > ~1.15e48 seconds since epoch (~3.6e40 years) at the token's actual max supply (1e29) to matter — not reachable within any real blockchain's lifetime. Purely structural/architectural note.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed. These are not false positives — they are high-signal leads for manual review. Not scored.

  • Third-party batch-enumeration DoS via self-griefed array — getActiveStakes — Code smells: if any external integrator batch-enumerates getActiveStakes() across many users on-chain without per-user try/catch isolation, one self-griefed user (Finding #1) could revert that integrator's entire batch call. No integrator contract exists in this audit's scope to confirm or refute this — raised at confidence 40 by the originating agent (below the reporting floor).
  • crosschainBurn reachability against the staking contract's own token balance — external, ClankerToken.crosschainBurn / SuperchainTokenBridge — Code smells: IERC7802's crosschainBurn is gated to the official SuperchainTokenBridge predeploy; reasoning (not independently verified against the predeploy's bytecode) indicates standard burn-from-caller-only semantics, and the staking contract never initiates a bridge call or grants any allowance, so this is assessed as unreachable — but flagged since it rests on standard-but-not-bytecode-verified bridge semantics rather than a direct read of this audit's in-scope source.

Explicitly Ruled Out (verified during phase 0/1/2, not repeated as findings)

  • Cross-user fund theft, double-unstake, read-only/cross-contract reentrancy — blocked by msg.sender-scoped storage keys + shared nonReentrant lock + hook-free token. Confirmed independently by 4+ phase-2 specialty agents (access-control, first-principles, invariant, trust-gap) with concrete call-sequence traces.
  • Precision/arithmetic bugs — the contract contains zero division operations; every subtraction was proven non-underflowing via the I2/I3 accounting invariants; every multiplication was proven ~35+ orders of magnitude below uint256 overflow given the real token's fixed 1e29-base-unit supply (full numeric proof by the phase-1 precision-math agent, independently re-verified by phase-2 math-precision and numerical-gap agents).
  • Faith-formula gaming via stake-chunking, interleaving, or unstake-ordering — proven algebraically chunk-invariant and order-invariant by 3 independent agents with concrete worked numeric examples; realized Faith can never exceed Σ(amount_i × duration_i) for a user's true history.
  • Blocklist/pause/rebase/fee-on-transfer/hook token classes — all confirmed N/A against the actual deployed token via its verified source (ClankerToken: plain OZ ERC20/Votes/Permit/Burnable, no such extensions, _update() bare passthrough).
  • First-depositor / share-price inflation attack (ERC4626-style) — structurally impossible; there is no share/asset conversion ratio anywhere in the contract, confirmed by the trust-gap agent.
