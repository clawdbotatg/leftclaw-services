It inherits MissionEnforcement (owner governance + advertised "immutable" mission principles) and PrivacyGuarantees (consent + data-deletion registry, previously reviewed standalone). [1] Identity model is fundamentally non-conformant with ERC-8004 — breaks interop

Severity: High
Location: mapping(address => AgentIdentity) public agents, registerAgent()
Origin: [phase1 only] — governance-and-standards-compliance agent, verified against the live ERC-8004 (Trustless Agents) spec at eips.ethereum.org/EIPS/eip-8004.

Description: The real ERC-8004 Identity Registry is an ERC-721(URIStorage) contract: every agent is a sequentially-assigned agentId tokenId, transferable/delegatable by the token owner, with a separate rotatable agentWallet field (set via setAgentWallet + EIP-712 proof, auto-cleared on transfer) that decouples the controlling key from the identity itself. This is the entire point of the design: an agent can rotate its key or change operator hands without losing its identity or accumulated reputation.

This contract implements none of it. Identity is keyed directly on msg.sender — no ERC-721 token, no agentId, no transfer/succession/wallet-rotation mechanism exists. If an agent's key is lost, rotated, or compromised, the identity (and any reputation built on genuine ERC-8004 reputation/validation registries) is permanently unrecoverable and non-portable, directly contradicting the contract's own marketed claim: "Portable reputation: Works across all ERC-8004 platforms."

Proof of Concept: Agent registers from 0xAAA. Operator needs to rotate to 0xBBB after a key exposure (standard security practice) — no function exists to do this. Re-registering from 0xBBB creates an entirely disconnected new identity; all history tied to 0xAAA is orphaned. A genuine ERC-8004 reputation/validation registry querying by agentId tokenId finds no match against this contract at all — interop is impossible by construction, not by omission.

Recommendation: Re-architect as an actual ERC-721(URIStorage) registry with sequential agentId, transferable ownership, and a separate rotatable agentWallet per the spec. If full conformance is out of scope, remove the "implements ERC-8004 / portable across all platforms" claims from documentation to avoid misleading integrators.

[2] Deactivating an agent permanently and irreversibly bricks its registration

Severity: High
Location: deactivateAgent(), registerAgent(), updateAgentURI()
Origin: [both] — surfaced independently by every one of the 18 total agent-passes across both phases (6 phase-1 domain checklists + all 12 phase-2 attacker agents, either as a direct FINDING or a corroborating LEAD). This is the single most-corroborated observation of the entire engagement.

Description: A prior fix (per an in-code comment: "MEDIUM FIX — Prevent duplicate registration on re-register, 2026-04") introduced a permanent isRegistered flag guarding registerAgent():

require(!agents[msg.sender].isRegistered, "Agent already registered");

But deactivateAgent() only clears the separate, mutable active flag — it never touches isRegistered. No function anywhere sets active back to true. Once an agent calls deactivateAgent():

  • registerAgent() reverts — isRegistered is already true.
  • updateAgentURI() reverts — it checks active, which is now false.
  • deactivateAgent() itself reverts — same check.

The identity is permanently frozen, directly contradicting the function's own NatSpec: "Agent can reactivate by registering again." The fix that closed one bug (duplicate registration) silently introduced a new, more severe one (irrecoverable identity loss).

Proof of Concept:

  1. Agent registers: isRegistered=true, active=true.
  2. Agent calls deactivateAgent() (e.g., for planned maintenance, per the documented "reactivate later" workflow): active=false.
  3. Agent attempts recovery via any of the three self-service functions — all revert. The only "recovery" is abandoning the wallet and registering an entirely new, disconnected identity — which itself compounds Finding #1's portability problem.

Recommendation: Add a reactivateAgent() function gated on isRegistered && !active that sets active = true without re-pushing into registeredAgents[]/agentsByCapability[] (preserving the anti-duplicate protection the original fix intended), and correct the deactivateAgent() NatSpec to describe the real mechanism once implemented.

[3] Function signatures, events, and management surface don't match the ERC-8004 interface at all

Severity: Medium
Location: registerAgent(), updateAgentURI(), event definitions
Origin: [phase1 only] — governance-and-standards-compliance agent, verified against the live spec.

Description: Beyond the identity-model break (Finding #1), essentially every interface element diverges from ERC-8004: the spec requires register(...) returns (uint256 agentId), setAgentURI(agentId, uri), setAgentWallet/getMetadata/setMetadata, and events Registered(uint256 indexed agentId, ...)/URIUpdated(...)/MetadataSet(...). This contract instead exposes registerAgent(string,string,bytes32) (no return value), updateAgentURI(string) keyed on msg.sender, and emits differently-named events keyed on address, not agentId. A conformant ERC-8004 client/indexer would find no matching selectors or event topics — onboarding against this contract fails entirely, independent of the deeper identity-model issue.

Recommendation: Adopt the spec's exact function selectors, return values, and event names/topics, built on the ERC-721 base recommended in Finding #1. If out of scope, drop the compliance claims.

[4] registerAgent/updateAgentURI ignore inherited deletion-request guard — "Right to be Forgotten" not enforced

Severity: Medium
Location: registerAgent(), updateAgentURI(); inherited checkDeletionRequest modifier
Origin: [both] — Phase 1: general, signatures-privacy (2 agents, independently identical). Phase 2: invariant, boundary, flow-gap (3 FINDINGS) plus 5 corroborating leads (execution-trace, periphery, first-principles, asymmetry, trust-gap) — 8 of 12 phase-2 agents total.

Description: This is the concrete realization of a risk flagged in the standalone PrivacyGuarantees audit (a separate engagement): that contract's checkDeletionRequest modifier was found unused-but-dormant in isolation, with an explicit note that any future inheriting contract needed review. This is that inheriting contract, and it does not wire the guard up. Neither registerAgent() nor updateAgentURI() — the only two functions that write new data permanently associated with msg.sender — apply checkDeletionRequest(msg.sender). A user who calls the inherited requestDataDeletion() can still freely register or update an agent identity, directly contradicting this contract's own "Privacy over surveillance" claim and MissionEnforcement's enumerated RIGHT_TO_BE_FORGOTTEN principle.

Proof of Concept: User calls requestDataDeletion() (inherited from PrivacyGuarantees) — deletionRequests[user] becomes non-zero. User immediately calls registerAgent(...) or updateAgentURI(...) — succeeds unconditionally; fresh permanent data is written and an event fires.

Recommendation: Apply checkDeletionRequest(msg.sender) to both registerAgent() and updateAgentURI().

[5] Agent cards store plaintext freeform strings, contradicting inherited privacy design

Severity: Medium
Location: AgentIdentity.agentURI, agentType fields; AgentRegistered/AgentUpdated events
Origin: [phase1 only] — signatures-privacy agent.

Description: PrivacyGuarantees states as an explicit design invariant: "It intentionally avoids writing user-provided freeform strings on-chain. All consent purposes are represented as hashes." ERC8004IdentityRegistry inherits this "privacy floor" and does the opposite for its primary data — agentURI and agentType are stored permanently in plaintext and emitted in indexed events, permanently and publicly linking a wallet address to arbitrary user-supplied content. This is in direct tension with the contract's own "ZK-compatible agent cards" and "Privacy over surveillance" claims, and — combined with Finding #4 — this data can never be gated by a deletion request either.

Recommendation: Store only a commitment/hash of the agent card on-chain (mirroring the purposeHash pattern already used elsewhere in the inherited base) and keep freeform content off-chain, or explicitly document that agent cards are intentionally public and drop the privacy-first marketing claims.

[6] Owner can unilaterally adjudicate any module's mission compliance — centralization

Severity: Medium
Location: adjudicateMissionViolation(), certifyModuleMissionCompliant()
Origin: [phase1 only] — governance-and-standards-compliance agent.

Description: The only binding mission-compliance state transitions are onlyOwner-gated with no timelock, multisig, or quorum. reportMissionViolation() is explicitly documented as non-binding — the community can only file a claim, never decide one. This directly contradicts the contract's advertised non-negotiable principle #4: "Community can CHALLENGE any claim." Impact is currently contained because this compliance state gates no actual operation (see Finding #7), but the trust-model claim itself is false as written.

Recommendation: Route binding adjudication through a timelock + multisig, or give community reports genuine on-chain effect (e.g., time-boxed challenge windows).

[7] Mission-enforcement machinery is entirely dead code

Severity: Low
Location: enforceMission modifier, verifyAIProfitCap(), verifyHumanFinalSay(), verifyNoKYC()
Origin: [both] — Phase 1: precision-math, governance (2 agents). Phase 2: boundary (FINDING), asymmetry, trust-gap, periphery (3 corroborating leads).

Description: The docstrings emphatically claim these principles are "cryptographically enforced," "cannot be changed by governance, upgrades, or any authority." In reality, enforceMission and all three verify* pure helpers have exactly one reference in the entire codebase — their own definitions. No function anywhere calls or gates on them.

Recommendation: Either wire this machinery into real operations with require statements, or remove the "cryptographically enforced" language so documentation matches actual behavior.

[8] discoverAgentsByCapability() unbounded array — DoS risk and Sybil discovery-poisoning

Severity: Low
Location: discoverAgentsByCapability(), agentsByCapability mapping
Origin: [both] — Phase 1: dos agent (unbounded-return DoS framing). Phase 2: periphery agent (content-poisoning framing) — two independent, complementary angles on the same root cause.

Description: capabilitiesHash is fully attacker-chosen with no validation, and agentsByCapability[hash] is permissionlessly append-only, never pruned. As it grows: (a) the function eventually becomes uncallable within gas/response limits for a popular hash (DoS on the contract's core "trustless discovery" purpose), and (b) an attacker can Sybil-register many addresses under a legitimate/popular capability hash with phishing agentURI values, polluting what external consumers treat as a trusted discovery list — with no active-filtering to exclude even deactivated agents.

Recommendation: Add a paginated getter and length accessor rather than returning the full array; consider registration friction (fee/allowlist) to raise Sybil cost.

[9] Unbounded missionReports growth enables storage-bloat griefing

Severity: Low
Origin: [both] — Phase 1: dos, governance (2 agents). Phase 2: boundary, periphery, trust-gap (3 leads).

Description: reportMissionViolation() is permissionless with no rate limit, dedup, or cap, and pushes up to 1000 bytes of evidence into missionReports[module] for any address. Impact is bounded — nothing reads the array on-chain (only single-index getters exist), so this is storage bloat and off-chain-indexing burden, not a gas-DoS.

Recommendation: Rely on the MissionViolationReported event alone (cheap, permissionless, doesn't bloat contract storage) rather than persisting an unbounded on-chain array; or add a per-reporter rate limit / small bond.

[10] cancelDeletionRequest() emits no event

Severity: Low
Origin: [phase2 only] — asymmetry agent. Same defect independently found in the standalone PrivacyGuarantees audit (separate engagement, different deployment).

Description: requestDataDeletion() emits DataDeletionRequested; its inverse, cancelDeletionRequest(), emits nothing (no DataDeletionCancelled event even exists). An off-chain deletion-tracking pipeline watching only the request event has no signal a user rescinded.

Recommendation: Add and emit event DataDeletionCancelled(address indexed user);.

[11] Misleading "Agent not registered" revert message on registered-but-inactive agents

Severity: Low
Origin: [phase1 only] — general agent, corroborated in phase 2 by execution-trace's lead.

Description: updateAgentURI() and deactivateAgent() both gate on active but revert with the string "Agent not registered" — misleading for a deactivated (but still isRegistered) agent, and directly related to Finding #2's root confusion between the two flags.

Recommendation: Fix alongside Finding #2; use accurate, distinct revert reasons for "never registered" vs. "registered but inactive."

[12] updateAgentURI cannot correct capabilitiesHash/agentType post-registration; stale discovery entries never pruned

Severity: Info
Origin: [both] — flow-gap lead (phase 2), related to phase-1 general G-4.

Description: Since re-registration is permanently blocked (Finding #2's root cause), an agent whose capabilities change has no path to update its discovery-index entry, and deactivated agents are never removed from agentsByCapability/registeredAgents. discoverAgentsByCapability results drift permanently stale.

Recommendation: Document that discovery results include historical/inactive entries and must be filtered by consumers via isAgentActive().

[13] Verified sound — no issue

2-step ownership transfer (transferOwnership/acceptOwnership) is implemented correctly: zero-address and self-transfer rejected, no front-running risk (bound to exact pendingOwner), no renounceOwnership brick path. Independently confirmed by phase-1 and phase-2 access-control agents. The "self-sovereign identity" claim — that no owner/admin can act on another agent's identity — is also verified accurate: every registry write is strictly msg.sender-scoped with no target-address parameter and no admin override.

[14] adjudicateMissionViolation doesn't clear the stale missionCompliantModules certify timestamp

Severity: Info
Origin: [phase2 only] — asymmetry lead.

Description: When a module is adjudicated non-compliant, its earlier missionCompliantModules[module] certify timestamp is never cleared, so it simultaneously reads as both "certified" and "in violation." No practical effect today since nothing reads either mapping operationally (ties directly into Finding #7).

What was checked and found sound

No exploitable access-control gap beyond the deactivation state machine (Finding #2) — every state-mutating function is correctly scoped, onlyOwner functions are properly restricted, and 2-step ownership transfer is sound (Finding #13). No economic-security surface — the contract holds no funds and the dedicated economic-security agent explicitly confirmed no findings apply to its specialty. No precision-math exploit — the sole formula (verifyAIProfitCap) is dead code (Finding #7) and would round conservatively even if called. No reentrancy/external-call surface — zero external calls anywhere in scope. No cross-user attack path — every write is strictly msg.sender-scoped.

⚠️ This review was performed by an AI-orchestrated two-phase audit process (breadth checklist pass + blind attacker-mindset pass + hybrid reconciliation), including a live web-verified comparison against the ERC-8004 standard specification. AI analysis can never verify the complete absence of vulnerabilities and no guarantee of security is given. This contract holds no funds, so all findings concern correctness, availability (Finding #2), and standards-compliance/interop (Findings #1, #3) rather than direct financial risk — but Finding #1 in particular should be treated as blocking for any integration that depends on genuine ERC-8004 interoperability. A human security review is recommended, especially before this registry is relied upon by external ERC-8004 consumers.
