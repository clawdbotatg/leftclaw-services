[F-1] HIGH — Mutual abandonment of an Assigned/WorkSubmitted task permanently locks escrowed USDC; no timeout, no permissionless escape, governance unreachable without a live disputing party

Origin: [both] — Phase 1: 5/5 agents (General, Access-control, DoS specialist with concrete PoC, dedicated escrow-lifecycle specialist with concrete PoC). Phase 2: 6/12 agents (access-control agent elevated to FINDING; economic-security, execution-trace, invariant, periphery, trust-gap corroborate).

Location: acceptBid (336-354), submitWork (369-375), approveWork (386-410), disputeTask (419-439), resolveDispute (449-472), cancelTask (481-502).

Root cause: deadline never drives a state transition — it is only a require guard in bidOnTask, acceptBid, submitWork. The sole path out of Assigned/WorkSubmitted besides the honest flow is disputeTask, self-authorized only by msg.sender == task.poster || task.assignee (426-429). resolveDispute requires status == Disputed (458) and is governance-only — governance has no unilateral entry point and no timeout on resolveDispute itself.

Proof of concept (converged on independently by two Phase-1 agents and re-confirmed here against source):

  1. createTask → USDC pulled in (271). bidOnTask → acceptBid → status = Assigned (351).
  2. Assignee never calls submitWork; poster never calls disputeTask.
  3. Every state-changing entrypoint reverts: cancelTask (491, blocked once Assigned), approveWork (394, requires WorkSubmitted), resolveDispute (458, requires Disputed — never reached because nobody called disputeTask). submitWork becomes permanently unreachable for the assignee once block.timestamp > deadline (371).
  4. Zero authorized actor — including governance — can ever move task.reward.

A parallel trace from WorkSubmitted: if the poster ghosts after legitimate submitWork, the assignee can self-rescue via disputeTask, but this only shifts liveness dependency onto governance, which has no deadline on resolveDispute — a dead/slow/key-lost governance freezes the funds indefinitely with no fallback.

Resolved internal disagreement: Three Phase-2 agents (boundary, flow-gap, first-principles) asserted "no permanent lock — governance is a universal backstop," reasoning that disputeTask is always available from Assigned/WorkSubmitted. Re-checking against source: that reasoning implicitly assumes at least one of the two counterparties remains willing to call disputeTask. It does not address the case where both are silent — which is exactly the scenario the DoS specialist, deadline specialist, and Phase-2 access-control agent each independently walked to an unrecoverable state. The three agents' "backstop" claim is true only conditional on an assumption their own analysis didn't state; it does not refute the finding. F-1 stands at High.

Mitigating nuance: Requires mutual silence (or governance failure in the WorkSubmitted branch) — not a unilateral attacker action. On an autonomous-agent marketplace, unilateral abandonment by a defunct/deregistered counterparty is a realistic steady-state event, not a contrived edge case.

Recommendation: Add deadline+grace self-service exits: poster can reclaim from Assigned once block.timestamp > deadline + GRACE with no submission; assignee can self-claim from WorkSubmitted once block.timestamp > deadline + APPROVAL_GRACE with no poster action; add a timeout fallback on Disputed (auto-split or return-to-claimable) so a dead governance cannot freeze funds forever.

[F-2] MEDIUM — Dispute channel is a unilateral, zero-cost fee-bypass: any assignee can force settlement to net +1% (or more) instead of going through approveWork

Origin: [both], dominated by Phase 2 — Phase 1: Access-control agent (Low framing, "collusion incentive"). Phase 2: 9/12 agents, with trust-gap and invariant agents each independently elevating to FINDING.

Location: disputeTask (419-439) vs. approveWork (386-410) vs. resolveDispute (449-472).

Root cause: approveWork deducts the 1% FEE_BPS fee (398-407); resolveDispute pays task.reward in full with no fee (466-468, explicit "no fee deducted" per NatSpec). disputeTask requires no deliverable, no bond, and is self-authorized by the assignee alone.

Sharpened exploit (Phase 2 trust-gap agent, the framing that elevates this beyond Phase 1's collusion-only read): An assignee who has delivered legitimate work has no reason to wait for approveWork — they can call disputeTask directly. Once Disputed, approveWork becomes permanently unreachable for that task (396 requires WorkSubmitted), leaving resolveDispute as governance's only non-lock option. Given genuinely delivered work, governance would rationally rule for the assignee, paying 100% instead of 99%. This requires zero cooperation from the poster and no malice — just ordinary self-interest by the worker acting alone — and is repeatable on every single task, structurally driving protocol fee revenue toward zero. The Phase-2 invariant agent independently confirms the second-order effect: since dispute is unbonded and free, either party can also freeze any live task's escrow at will (feeding into F-1), converting "automatic settlement" into an on-demand manual-governance process.

Reconciliation note on severity: No counterparty loses money they were owed — the poster still pays the same escrowed reward regardless of settlement path. The loss is entirely borne by the protocol's own fee revenue, and the "attack" looks identical to legitimate dispute usage. That caps this at Medium rather than High, but its reliability (deterministic outcome given real delivered work) and total absence of any code-level cost or gate make it a real, systemic economic defect rather than a documentation nit.

Recommendation: Deduct the same FEE_BPS fee inside resolveDispute before paying payTo, routing it to feeRecipient, so settlement economics are branch-independent. Separately, consider a refundable dispute bond forfeited on a losing ruling to remove the zero-cost griefing property called out by the invariant agent.

[F-3] MEDIUM — feeRecipient USDC-blacklist bricks approveWork protocol-wide; immutable address, no fallback

Origin: [both] — Phase 1: DoS specialist (Low framing, per-task/protocol-wide distinction noted but capped low given dispute recoverability). Phase 2: 6/12 agents, economic-security agent elevating to FINDING with a quantified illustration.

Location: approveWork (386-410), specifically the two sequential hard-require'd transfers (402-407); feeRecipient declared immutable (line 101).

Root cause: Worker payout and fee payout are atomically coupled in one transaction. USDC (Circle, native on Base) reverts (does not return false) on transfer to a blacklisted address. A single blacklist event on the immutable feeRecipient reverts the fee leg, which unwinds the worker payout too — bricking approveWork for every task, protocol-wide, permanently (no redeploy-free remediation), forcing all settlement through the dispute path — which, per F-2, also pays zero fee. So a blacklisted feeRecipient converts every subsequent settlement into a fee-free payout on top of the availability failure.

Quantified illustration (economic-security agent): 1,000 tasks × 1,000 USDC reward → 10 USDC/task fee (10,000 USDC total) permanently unrealizable if feeRecipient is ever blacklisted, and every worker must additionally wait on manual governance action just to be paid at all.

Why Medium, not High: Funds are not lost — the dispute→resolveDispute path remains available and pays out in full — so this is an availability/DoS-class defect, not fund loss. It is elevated above Phase 1's initial Low framing because Phase 2's 6-agent corroboration establishes the blast radius is protocol-wide (every task, not an isolated one) and permanent (immutable address, no setter).

Recommendation: Decouple the fee transfer from the worker transfer — accrue-and-pull pattern (pendingFees[feeRecipient] += fee, withdrawn separately) so a blocked fee recipient can never block worker payment. Consider making feeRecipient governance-updatable.

[F-4] LOW — Deregistered/deactivated agents retain full control over in-flight tasks (identity kill-switch defeated)

Origin: [both] — Phase 1: Access-control agent. Phase 2: invariant, flow-gap agents.

Location: onlyRegisteredAgent modifier applied only to createTask and bidOnTask — never re-checked in acceptBid, submitWork, approveWork, or disputeTask.

Description: If identityRegistry deactivates an agent after they've been assigned a task, they keep full assignee rights indefinitely — the identity check is a point-in-time gate at entry, not continuous authorization. Both phases explicitly note this may be intentional (a revocation shouldn't strand an in-progress worker's payment), so it is reported as a design-clarity gap rather than a clear defect.

Recommendation: Document as intended, or re-check isAgentActive at acceptBid/submitWork if continuous authorization is the intended model.

[F-5] LOW — Accept-side deadline-squeeze griefing: poster can accept a bid with zero submission window

Origin: [phase2 only] — 5/12 agents (access-control, periphery, asymmetry, boundary, trust-gap). Re-examined against source directly: confirmed real.

Location: acceptBid (346, require(block.timestamp < task.deadline)) vs. submitWork (371, require(block.timestamp <= task.deadline)).

Description: No minimum gap is enforced between bid acceptance and the deadline. A poster can call acceptBid one second before task.deadline; the assignee then has no realistic window to call submitWork. The task is stranded in Assigned — cancelTask is blocked once Assigned (492), approveWork requires WorkSubmitted — leaving disputeTask → governance (subject to F-1's liveness risk) as the only exit. This only ever wastes the poster's own escrowed funds and the assignee's uncompensated effort; the poster gains nothing financially, so this is a griefing/liveness issue, not a theft vector. New relative to Phase 1, which surfaced dispute-timing/evidence gaps (F-6 below) but not this specific accept-side squeeze.

Recommendation: Enforce a minimum interval between acceptBid and task.deadline (e.g., require(task.deadline - block.timestamp >= MIN_SUBMISSION_WINDOW)), or grant a fixed grace period after acceptance regardless of the original deadline.

[F-6] LOW — disputeTask has no deadline gate and no proof-of-work requirement

Origin: [phase1 only] — Escrow-lifecycle specialist. Re-examined: confirmed directly against source during that agent's own line-by-line trace; no Phase-2 agent contradicted it (several touched the same lines for F-2/F-5 without flagging this specific angle).

Location: disputeTask (419-439), submitWork (371).

Description, two sub-issues: (a) An assignee who misses the submitWork deadline (371 correctly reverts — boundary confirmed, no off-by-one) can still call disputeTask (no deadline check at 419-439) and potentially be awarded the full reward by governance despite deliverableURI still being empty. (b) A poster can call disputeTask the instant a bid is accepted (Assigned, line 431 permits it), before the assignee has any real window to submitWork, forcing premature governance adjudication with zero on-chain evidence from either side. Both are fairness/griefing-adjacent gaps, not incremental fund-loss beyond what governance's pre-existing full discretion already implies.

Recommendation: Consider requiring the poster wait until past-deadline to dispute an Assigned task, and surface deliverableURI == "" explicitly to governance tooling so it isn't asked to pay for a phantom deliverable.

[F-7] LOW — Unbounded _bids[taskId] array degrades off-chain consumers; no on-chain gas-DoS

Origin: [both] — Phase 1: DoS specialist. Phase 2: execution-trace, asymmetry, boundary.

Location: bidOnTask (298-328, unconditional push), getTaskBids (527-534, returns full array).

Description: No cap on bids per task; a Sybil ring of registered agents can push _bids[taskId] to thousands of entries. Confirmed by both phases that this never affects on-chain settlement (acceptBid's bid-index lookup stays O(1)), but getTaskBids as an eth_call can return a payload large enough to break RPC/indexer/UI consumers — an off-chain availability issue, not a fund risk.

Recommendation: Cap bids per task, and/or add a paginated getTaskBids(taskId, offset, limit).

[F-8] LOW / INFO — createTask records the requested reward, not the measured balance delta (latent fee-on-transfer/rebasing risk, not exploitable under actual USDC)

Origin: [both] — Phase 1: Access-control agent (assumption flag), DoS specialist (cross-checked, confirmed no shortfall under standard USDC). Phase 2: economic-security, invariant, boundary agents.

Location: createTask (271, transferFrom; 278-282, stores reward).

Description: No balanceOf delta measurement; all tasks share one pooled contract balance trusting that transferFrom delivers exactly reward. If usdc were ever fee-on-transfer or rebasing (not true of the actual immutable, canonical Circle USDC deployment), recorded escrow would exceed real holdings and the last task to settle would revert on an insolvent transfer. Both phases independently confirm this is not exploitable under the real deployment — flagged purely as a missing defensive check.

Recommendation: Record the measured balanceOf delta as a defensive measure, though not required given the immutable token choice.

[F-9] INFO — Fee rounds to zero for rewards under 100 raw USDC units; immaterial value impact but a genuine spec-conformance gap

Origin: [both] — Phase 1: Precision-math agent (zero-dust confirmation), DoS specialist (zero-value-transfer-is-safe note). Phase 2: math-precision agent (LEAD, confirmed non-exploitable), numerical-gap agent (elevated to FINDING on NatSpec-invariant grounds).

Location: approveWork (398-401).

Description: fee = (reward * 100) / 10000 truncates to 0 whenever reward < 100 raw units (< $0.0001 USDC). The numerical-gap agent's elevation is worth preserving as context even though value impact is immaterial: the contract's own NatSpec documents "1% protocol fee on every settlement," and this boundary makes that claim silently false — chaining many micro-tasks was checked by the math-precision agent and confirmed to net at most ~$0.0099, economically meaningless.

Recommendation: Cosmetic/spec-conformance only — no fix required given the value scale, but consider a documented floor (if (fee == 0 && reward > 0) fee = 1;) if strict "fee on every settlement" conformance matters.

[F-10] INFO — Misleading comment on reward decimal handling

Origin: [phase1 only] — General agent. No Phase 2 agent touched this line; it is purely documentation.

Line 62 comment ("total USDC locked (18-dec equivalent; USDC is 6-dec — stored as-is)") implies scaling logic that does not exist anywhere in the code — reward is used as-is throughout with no conversion. No functional impact.

[F-11] INFO — Inconsistent deadline comparison operators, confirmed harmless

Origin: [phase1 only] — General agent noted it; Escrow-lifecycle specialist explicitly verified the boundary is correct (no off-by-one). Distinct from F-5, which is about the absence of a minimum gap, not the operator choice itself.

bidOnTask/acceptBid use strict < (311, 346); submitWork uses <= (371). A 1-second asymmetry with no exploitable consequence in isolation.

Confirmed non-issues (unanimous or near-unanimous across both phases)

  • Reentrancy / CEI ordering: nonReentrant (124-129) applied first on every mutating function; terminal status always set before external transfers. Confirmed sound by essentially every agent across both phases.
  • Fee-split arithmetic: workerAmount + fee == task.reward always holds exactly (398-399) — no dust accumulation, no rounding leak beyond F-9.
  • No hostile-recipient reentrancy/blocking vector: Standard ERC-20 transfer/transferFrom invoke no recipient code — closed attack class, confirmed by DoS specialist (Phase 1) and multiple Phase 2 agents.
  • No unbounded on-chain loops: _bids is the only user-growable structure and is never iterated on-chain (only .length and single-index access).
  • No fund-theft, double-spend, or privilege-escalation path: Every Phase 2 agent that reached a verdict on the core state machine independently confirmed per-task fund conservation (reward in = reward out, exactly once, via mutually exclusive terminal states) and correct role-gating (payouts hardcoded to stored poster/assignee, never msg.sender-redirectable; governance's resolveDispute cannot pay itself).
  • Sybil self-dealing on acceptBid: A poster accepting their own second identity's bid only risks their own escrowed funds with no victim and no external state corruption — explicitly concluded not a finding (Phase 1 escrow-lifecycle specialist).
