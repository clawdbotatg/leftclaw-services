Findings

[88] 1. unstakeVerifierBond has no lock, letting a verifier evade a pending slash or reset-forfeiture

ReputationRegistry.unstakeVerifierBond (L201-208) · Confidence: 88 · [phase2-only] — found
independently by 4 of 12 pashov agents (economic-security, invariant, math-precision, trust-gap),
each with a full numeric trace; not surfaced by phase-1's checklist pass.

Description: unstakeVerifierBond checks only amount>0 (L202) and the caller's own balance
(verifierBond[msg.sender] >= amount, L203) — no reference to arbitration/dispute state, no
cooldown, no "frozen pending slash" flag. A verifier who anticipates or observes (mempool-visible)
an incoming slashVerifierBond/resetSubject targeting them can call
unstakeVerifierBond(fullBond) first: verifierBond[subject] drops to 0 (L204), so the
subsequent slashVerifierBond reverts at its balance check (require(verifierBond[subject] >= amount), L216) and resetSubject's forfeiture branch (if (bond>0 && treasury!=0), L116)
silently no-ops — the punitive mechanism the bond exists to back is fully and freely defeated,
via a purely unprivileged action requiring no admin cooperation. rotateArbitrationModule
elsewhere in this same file already checks activeDisputeCount()==0 (L83), proving the codebase
has the concept of "is there a live dispute" available but never applies it to withdrawal.

Proof: Verifier V stakes 5 ETH → verifierBond[V] = 5e18. arbitrationModule submits
slashVerifierBond(V, 5e18, reason). V front-runs with unstakeVerifierBond(5e18) at higher gas:
verifierBond[V] -= 5e18 → 0 (L204), raw call succeeds (L205-206), V recovers the ETH. The
pending slash tx now evaluates require(0 >= 5e18) → reverts. Identically, if resetSubject(V)
is used instead, bond = 0 (L115) makes the if at L116 false — forfeiture is skipped with no
revert, while subjectSignals/arbitratorReputation are still wiped, giving the appearance of a
completed punishment.

Fix:

+ mapping(address => uint256) public lockedBond;
+
+ function lockBond(address subject, uint256 amount) external {
+     require(msg.sender == arbitrationModule || msg.sender == taskRegistry, "ReputationRegistry: not slash authority");
+     lockedBond[subject] += amount;
+ }

  function unstakeVerifierBond(uint256 amount) external {
      require(amount > 0, "ReputationRegistry: zero unstake");
-     require(verifierBond[msg.sender] >= amount, "ReputationRegistry: insufficient bond");
+     require(verifierBond[msg.sender] - lockedBond[msg.sender] >= amount, "ReputationRegistry: insufficient unlocked bond");
      verifierBond[msg.sender] -= amount;

(Illustrative — the exact locking trigger/lifecycle should be designed with the arbitration
module's dispute-open/close flow in mind.)

[85] 2. Unbounded subjectSignals growth makes resetSubject permanently un-executable for high-activity subjects (DoS)

ReputationRegistry.resetSubject (L122), subjectSignals (L36), push at L156 · Confidence: 70 ·
[both] — phase-1 dos-domain finding D1, corroborated independently by the phase-2 periphery
agent.

Description: subjectSignals[subject] only grows — six entrypoints push to it
(emitSignal, recordDisputeOutcome, recordArbitratorRegistration, recordArbitratorResolution,
recordCompletion, recordReplacementPenalty) with no bound — and is only ever cleared by a
whole-array delete in resetSubject (L122). Deleting a large dynamic storage array costs gas
linear in its length (every element slot is zeroed). A subject who has accumulated on the order of
several thousand signals — entirely reachable through normal, legitimate high-throughput usage by
trusted Set A callers, no attacker cooperation required — can push resetSubject's gas
requirement past the block gas limit, permanently blocking reset (and bond forfeiture) for that
subject. There is no chunked/paginated alternative.

Fix: Replace the whole-array delete with a lazy-invalidation scheme (e.g. a per-subject epoch
counter that getSubjectSignalCount/consumers check against, incremented on reset instead of
iterating the array), or provide a bounded, repeatable, paginated reset function.

[82] 3. emitSignal lets non-arbitration Set A callers forge arbitration-only signal types

ReputationRegistry.emitSignal (L127-136) · Confidence: 90 · [both] — phase-1
access-control finding AC1, corroborated independently by 10 of 12 phase-2 attack agents (the
strongest-attested result across both phases).

Description: recordDisputeOutcome (L160-170), recordArbitratorRegistration (L172-176),
and recordArbitratorResolution (L178-182) hard-restrict DISPUTE_WON/DISPUTE_LOST/
ARBITRATOR_STANDBY/ARBITRATOR_RESOLVED signals to msg.sender == arbitrationModule (L161,
173, 179) with fixed/derived weights. emitSignal (L127-136) is gated only by the broader
onlyAuthorized (taskRegistry ‖ arbitrationModule ‖ agentDepositVault, L56-64) and forwards a
fully caller-controlled signalType/weight straight into _recordSignal (L138) — nothing ties
the signal type to the caller's identity. taskRegistry or agentDepositVault — both explicitly
excluded from the narrower gate — can call emitSignal(victim, SignalType.DISPUTE_WON, taskId, 0x0, type(uint256).max, 0x0) directly, producing a signal byte-for-byte indistinguishable from a
legitimate arbitration-issued one, with an unbounded weight the dedicated function would never
allow (hardcoded to 100). For the ARBITRATOR_* types, the forged signal additionally desyncs
from arbitratorReputation (untouched by emitSignal, only updated at L174/L180), corrupting the
very "evidence layer for off-chain aggregation" the contract's own header comment (L9) states is
its purpose.

Fix:

  function emitSignal(
      address subject,
      SignalType signalType,
      uint256 taskId,
      bytes32 taskTypeHash,
      uint256 weight,
      bytes32 payloadHash
  ) external onlyAuthorized returns (uint256 signalId) {
+     require(
+         signalType != SignalType.DISPUTE_WON &&
+         signalType != SignalType.DISPUTE_LOST &&
+         signalType != SignalType.ARBITRATOR_STANDBY &&
+         signalType != SignalType.ARBITRATOR_RESOLVED,
+         "ReputationRegistry: reserved signal type"
+     );
      return _recordSignal(subject, signalType, taskId, taskTypeHash, weight, payloadHash);
  }

[80] 4. resetSubject grants agentDepositVault bond-forfeiture power slashVerifierBond deliberately withholds from it

ReputationRegistry.resetSubject (L114-125) vs. slashVerifierBond (L210-222) · Confidence: 82 ·
[both] — phase-1 access-control finding AC2, corroborated at FINDING level by 2 of 12 phase-2
agents (boundary, trust-gap) with concrete traces, plus 2 more phase-2 agents flagging the same
area as leads.

Description: slashVerifierBond deliberately excludes agentDepositVault from its caller
set (arbitrationModule ‖ taskRegistry only, L211-214). resetSubject performs a strictly
larger action on the same verifierBond state — unconditional full-bond forfeiture, no
caller-chosen amount (L115-119) — yet is reachable by the broader onlyAuthorized (Set A), which
includes agentDepositVault. A verifier stakes 10 ETH; agentDepositVault — excluded from
slashVerifierBond — calls resetSubject(verifier) and achieves the identical
TreasuryRouter.recordNativeSlash seizure of the full 10 ETH that slashVerifierBond would have
reverted for the same caller. The narrower Set C gate provides no real protection since the same
effect is reachable through the broader resetSubject door.

Fix: Scope resetSubject's bond-forfeiture branch to Set C (arbitrationModule ‖ taskRegistry) only, or split the bond-forfeiture piece from the signal/reputation-wipe piece.

[68] 5. resetSubject silently skips bond forfeiture (but still reports success) while treasury is unset

ReputationRegistry.resetSubject (L116) · Confidence: 68 · [phase2-only] — 1 of 12 phase-2
agents (first-principles) raised this at FINDING level with a full trace; 5 more independently
flagged the identical mechanism as a lead, meeting the multi-agent-convergence promotion rule.

Description: The forfeiture branch is gated if (bond>0 && treasury!=address(0)) (L116).
treasury is an independent, optional, one-time setter (setTreasury, L107) with no ordering
dependency on setAuthorized — nothing requires it to ever be called before resetSubject
becomes reachable. If a Set A caller invokes resetSubject while treasury==address(0), the
forfeiture branch is skipped with no revert, while subjectSignals/arbitratorReputation are
still wiped (L122-123) and ReputationReset still emits (L124), giving the appearance of a
completed punishment. The subject keeps their full bond, later withdrawable via
unstakeVerifierBond. slashVerifierBond's sibling check (require(treasury != address(0), ...),
L217) reverts instead of silently proceeding — confirming this is an inconsistency, not intended
behavior, and directly contradicting resetSubject's own NatSpec ("forfeit remaining verifier
bond", L112).

Fix:

  function resetSubject(address subject) external onlyAuthorized {
      uint256 bond = verifierBond[subject];
-     if (bond > 0 && treasury != address(0)) {
+     if (bond > 0) {
+         require(treasury != address(0), "ReputationRegistry: no treasury");
          verifierBond[subject] = 0;
          TreasuryRouter(treasury).recordNativeSlash{value: bond}();
          emit VerifierBondSlashed(subject, bond, bytes32("PLATFORM_PENALTY"));
      }

[75] 6. rotateArbitrationModule can be permanently blocked by the current or replacement module, with no owner override

ReputationRegistry.rotateArbitrationModule (L78-99) · Confidence: 75 · [both] — phase-1
dos-domain and access-control-domain findings (D3/AC4, merged within phase 1), corroborated
independently by the phase-2 periphery agent.

Description: Two of the eight gate checks (L82-83) require the current — potentially
compromised or malfunctioning — module to self-report disputeOpeningPaused()==true and
activeDisputeCount()==0 before a replacement can be installed. No owner override exists. A
compromised/buggy current module can revert, run out of gas, or simply always report "not
paused"/"disputes active" to permanently block its own replacement, defeating the apparent
recovery purpose of IArbitrationRecovery. arbitrationModule gates Set B entirely and half of
Set C, so this is a single point of permanent failure for a large share of the contract's trusted
surface.

Fix: Add an owner-gated emergency override that bypasses the current.* checks (e.g. a
timelocked force-rotate), or wrap each external view call in try/catch with a gas stipend.

[60] 7. Silent, irrecoverable fund loss if treasury is a codeless address

ReputationRegistry.setTreasury (L107-110); resetSubject (L118); slashVerifierBond (L220) ·
Confidence: 60 · [both] — phase-1 general-domain finding G1 (originally rated High from
first principles), corroborated independently by the phase-2 boundary agent; confidence reduced
from phase-1's initial rating on hybrid re-examination because it requires an honest deployment
mistake (no malice) whose likelihood cannot be assessed without deployment-process context.

Description: setTreasury validates only non-zero (L109), no code-existence check, and is a
one-time permanent setter. TreasuryRouter(treasury).recordNativeSlash{value:X}() (L118, L220) is
a typed call to a function with no return value — Solidity omits the automatic codesize guard for
no-return-value calls, so a call to a codeless address (an EOA, an undeployed CREATE2 address, a
typo) returns success=true with the attached value effectively stranded, while verifierBond is
still decremented as if the slash succeeded. No malicious owner action is required — this can
happen from a single honest misconfiguration, and is permanent since setTreasury cannot be
re-run once set.

Fix:

  function setTreasury(address _treasury) external onlyOwner {
      require(treasury == address(0), "ReputationRegistry: treasury set");
      require(_treasury != address(0), "ReputationRegistry: zero");
+     require(_treasury.code.length > 0, "ReputationRegistry: not a contract");
      treasury = _treasury;
  }

[55] 8. resetSubject/slashVerifierBond fully dependent on TreasuryRouter never reverting

ReputationRegistry.resetSubject (L118), slashVerifierBond (L220) · Confidence: 55 · [both]
— phase-1 dos-domain finding D2, corroborated independently by the phase-2 economic-security
agent. Confidence capped below 60 because it is entirely contingent on the out-of-scope
TreasuryRouter's actual revert behavior, which neither phase could inspect.

Description: Both calls are plain typed calls with no try/catch/isolation; a callee revert
bubbles and unwinds the whole caller tx. If TreasuryRouter.recordNativeSlash() can ever revert
for a given subject/amount (rate limit, blocklist, pause, downstream failure), both the bond
forfeiture and the unrelated subjectSignals/arbitratorReputation wipe in resetSubject
become permanently blocked for that subject, since there's no independent path for the
non-monetary cleanup.

Fix: Decouple local state effects from the external call's success (pull-based accounting, or
proceed with cleanup regardless of the treasury call's outcome and emit a distinguishing event on
failure).

[65] 9. Premature renounceOwnership permanently bricks unset roles / forecloses future arbitration-module rotation

Inherited Ownable/Ownable2Step; interacts with setAuthorized/setAgentDepositVault/
setTreasury/rotateArbitrationModule (all onlyOwner) · Confidence: 65 · Severity: Low ·
[phase1-only] — access-control finding AC5.

Description: If the owner renounces before all one-time setters have run, those slots stay
address(0) forever (no non-owner path sets them) — core onlyAuthorized/Set B/C functions
become permanently unreachable. Even after full wiring, renouncing forecloses any future
rotateArbitrationModule call, removing the only mitigation for Finding 6.

Fix: Guard renounceOwnership (require wiring complete first), or accept as documented
operational risk under process control (e.g. multisig-gated deployment sequencing).
