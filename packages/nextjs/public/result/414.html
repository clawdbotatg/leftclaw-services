Findings

[1] UnionStakingVault.stake() orphan-reward restart permanently strands the un-emitted remainder of a live USDC reward stream

Severity: High · Confidence: 97 · Origin: [both] — independently found by 9 of the 18 hunting agents across both phases (phase1: general, precision-math; phase2: math-precision, economic-security, execution-trace, invariant, periphery, asymmetry, numerical-gap)

Location: UnionStakingVault.sol:151-155 (orphan-restart block), UnionStakingVault.sol:328-333 (_startRewardStream), contrast the correct fold at UnionStakingVault.sol:249-253 (notifyReward).

// UnionStakingVault.sol:249-254 (notifyReward — CORRECT: folds the live remainder)
uint256 scaled = (amount * USDC_ACC_SCALE) + rewardRemainderScaled;
if (block.timestamp < rewardPeriodFinish) {
    scaled += (rewardPeriodFinish - block.timestamp) * rewardRateScaled;
}
rewardRemainderScaled = 0;
_startRewardStream(scaled);

// UnionStakingVault.sol:151-155 (stake — BUGGY: does NOT fold the live remainder)
if (undistributedRewardsScaled > 0) {
    uint256 orphaned = undistributedRewardsScaled;
    undistributedRewardsScaled = 0;
    _startRewardStream(orphaned);
}

// UnionStakingVault.sol:328-333
function _startRewardStream(uint256 scaled) internal {
    rewardRateScaled = scaled / REWARD_DURATION;
    rewardRemainderScaled = scaled % REWARD_DURATION;
    rewardPeriodFinish = block.timestamp + REWARD_DURATION;
    lastRewardUpdateAt = block.timestamp;
}

Description: notifyReward correctly rolls a running 7-day USDC reward stream over by folding in the still-scheduled remainder (rewardPeriodFinish - now) * rewardRateScaled before restarting. The orphan-restart branch inside stake() — which fires when a new stake arrives after the pool went fully empty mid-stream — calls _startRewardStream(undistributedRewardsScaled) using only the amount that was emitted while the pool sat empty. _startRewardStream then unconditionally overwrites rewardRateScaled, rewardPeriodFinish, and rewardRemainderScaled. If the new stake arrives before the original rewardPeriodFinish, the still-scheduled future portion of that original stream — real USDC that was already transferred into the vault via notifyReward/flushStakerShare — is discarded from every accounting variable and can never be claimed by any staker. No sweep or rescue function exists anywhere in the contract.

Proof of Concept: Sole staker holds 1e20 AZL. Treasury calls notifyReward(700e6) (700 USDC) at t0: rewardRateScaled ≈ 1.157e39 (scaled), rewardPeriodFinish = t0 + 604800 (7 days). At t0+86400 (day 1) the staker fully unstakes: _updateRewardAcc correctly credits ~100 USDC for the elapsed day, totalStaked → 0, lastRewardUpdateAt = t0+86400. At t0+172800 (day 2) a new staker calls stake(): _updateRewardAcc runs with totalStaked==0 and parks only the elapsed-while-empty slice [t0+86400, t0+172800] (~100 USDC) into undistributedRewardsScaled. The orphan block then calls _startRewardStream(100e6 scaled), overwriting rewardRateScaled/rewardPeriodFinish to a fresh 7-day stream of just that 100 USDC. The originally-scheduled [t0+172800, t0+604800] slice — 500 of the original 700 USDC (5/7 of the batch) — is now referenced by no state variable whatsoever. It sits in the vault's physical USDC balance forever, unclaimable by anyone. The loss magnitude scales with how early the pool empties relative to the stream length and how long the empty gap lasts; near-total loss of a distribution is achievable with a longer gap.

Regression test recommendation: Add a Foundry test that (1) funds a reward stream, (2) fully unstakes mid-stream, (3) re-stakes before rewardPeriodFinish, and (4) asserts sum(all stakers' eventual claimableUsdc) + vault's remaining unclaimed-but-still-scheduled amount == total notified. The current code fails this invariant; the fix below should pass it.

Fix:

  if (undistributedRewardsScaled > 0) {
      uint256 orphaned = undistributedRewardsScaled;
      undistributedRewardsScaled = 0;
+     if (block.timestamp < rewardPeriodFinish) {
+         orphaned += (rewardPeriodFinish - block.timestamp) * rewardRateScaled;
+     }
+     orphaned += rewardRemainderScaled;
+     rewardRemainderScaled = 0;
      _startRewardStream(orphaned);
  }

[2] Verifier-bond slash on every seated-arbitrator ruling exceeds the maximum possible reward, making decentralized arbitration economically irrational and collapsing UPFRONT-mode payment protection onto a single owner-controlled fallback resolver

Severity: High · Confidence: 82 · Origin: [phase2: trust-gap], corroborated by 3 independent leads (economic-security, asymmetry, execution-trace) converging on the same root cause from different angles; also noted informationally (not escalated) by [phase1: general].

Location: ArbitrationModule.sol:773-793 (_prepareVerifierBondSlash), ReputationRegistry.sol:53 (MIN_VERIFIER_BOND = 1 ether), AgentDepositVault.sol:28 / ArbitrationModule.sol:38 (MAX_DISPUTE_BOND = 100_000_000 = $100 USDC), EscrowVault.sol:346-348 (_settleAtDeadline UPFRONT branch), EscrowVault.sol:294-303 (settleArbitrationTimeout routes through the same function).

// ArbitrationModule.sol:778-793
// Every arbitrator-backed ruling carries this penalty, regardless of
// which party wins or the worker split. Timeout and fallback paths do
// not slash. The bond is locked through the absolute deadline when
// both parties consent to seat the arbitrator.
if (
    !byArbitrator ||
    d.fallbackReplacementUsed ||
    address(reputationRegistry) == address(0)

uint256 bond = reputationRegistry.verifierBond(d.assignedArbitrator);
uint256 amount = bond / 10;

// EscrowVault.sol:346-348
} else if (e.mode == EscrowMode.UPFRONT) {
    // Pure timeout has no ruling; favor the poster.
    workerAmount = 0;

Description: _prepareVerifierBondSlash confiscates 10% of a seated arbitrator's entire staked ETH bond — at minimum 0.1 ETH given the 1 ETH MIN_VERIFIER_BOND — on every ruling that arbitrator issues, unconditionally, win or lose or any split (the code's own comment states this explicitly). The arbitrator's only possible compensation is the dispute-initiator's bond, hard-capped at $100 USDC. At any ETH price above roughly $1,000, the guaranteed 10%-of-bond slash meets or exceeds the maximum possible reward; at typical prices the ruling is a clear net loss for any profit-seeking arbitrator. Consequently no rational arbitrator will ever call resolveDispute through the normal mutual-selection path — the fallback-resolver path is the sole ruling mechanism explicitly exempt from this slash (d.fallbackReplacementUsed short-circuits it), making it the only economically-functioning path to a real ruling, and it is a single owner-controlled address. This has a direct payment-denial consequence for UPFRONT-mode tasks specifically: UPFRONT has no worker-callable release function (claimStream/claimHourBlock/submitProof all revert outside their own modes) — the only way an UPFRONT worker is paid is the poster voluntarily calling completeTask, or a favorable arbitration ruling. Since mutual arbitration is economically dead, a poster can deliver-then-withhold completeTask and simply let any dispute run to its 21-day absolute timeout; resolveTimedOut → _finaliseTimeout → EscrowVault.settleArbitrationTimeout → _settleAtDeadline's UPFRONT branch pays the worker zero regardless of whether the timeout came from a pure expiry or from an opened-then-abandoned dispute. The worker's only real protection is the single owner-controlled fallback resolver choosing, at its own discretion, to rule in their favor.

Proof of Concept: Poster posts a $1,000 UPFRONT task; worker claims, delivers work off-chain (per the task's off-chain deliverable convention). Poster never calls completeTask. Worker opens a dispute at/near the deadline. No profit-seeking registered/global arbitrator accepts seating-and-ruling (0.1+ ETH cost vs. $50 max bond reward for a $1,000 dispute — bondForAmount = 5% capped at $100, here min(1000e6*500/10000, 100e6) = 50e6). The dispute sits in EVIDENCE/OPEN until the 21-day absoluteDeadline; resolveTimedOut fires; _finaliseTimeout calls EscrowVault.settleArbitrationTimeout, which hits the UPFRONT branch (workerAmount = 0); the full $1,000 is refunded to the poster. The worker recovers nothing for delivered work, unless the owner's fallback resolver had separately intervened before the 21-day mark.

Fix: Scale the verifier-bond slash to a small, disputed-value-proportional fraction rather than a flat 10% of the ETH bond (so ruling cost and ruling reward are commensurable and honest arbitration is profitable), and/or restrict the slash to demonstrably incorrect/overturned rulings; separately, give UPFRONT-mode tasks a worker-side proof-of-delivery/attestation release path so payment does not depend entirely on poster cooperation or a single centralized fallback resolver.

[4] Owner-pause / recovery-lockdown interval overlap is mis-accounted, inflating totalDisputeOpeningPausedTime_ via two distinct mechanisms

Severity: Medium · Confidence: 90 · Origin: [phase2: boundary, asymmetry, first-principles] (Mechanism A) + [phase2: flow-gap] (Mechanism B). Resolves Phase 0's Open Question #1/#2 and Fragility Cluster #1.

Location: ArbitrationModule.sol:281-298 (setDisputeOpeningPaused, unpause branch — Mechanism A), ArbitrationModule.sol:330-335 (exitRecoveryLockdown — Mechanism B).

// ArbitrationModule.sol:281-298 — Mechanism A
if (!paused && disputeOpeningPauseRequested && pauseStartedAt != 0) {
    uint256 cutoff = block.timestamp < previousPauseUntil ? block.timestamp : previousPauseUntil;
    if (
        recoveryLockdownStartedAt != 0 &&
        recoveryLockdownStartedAt > pauseStartedAt &&   // <-- only handles lockdown-after-pause
        recoveryLockdownStartedAt < cutoff
    ) {
        cutoff = recoveryLockdownStartedAt;
    }
    totalDisputeOpeningPausedTime_ += cutoff - pauseStartedAt;
    pauseStartedAt = 0;
}

// ArbitrationModule.sol:330-335 — Mechanism B
uint256 start = recoveryLockdownStartedAt;
if (pauseStartedAt != 0 && pauseStartedAt < start) {
    start = pauseStartedAt;   // <-- reaches back with no check that the pause was still active
}
totalDisputeOpeningPausedTime_ += nowTs - start;

Description — Mechanism A: The unpause-time clamp only fires when the lockdown started after the current pause (recoveryLockdownStartedAt > pauseStartedAt). If a recovery lockdown is already active when the owner pauses, and the owner un-pauses while lockdown is still active, the clamp is skipped and the full pause duration is added at unpause time — then exitRecoveryLockdown later re-adds the same interval (since pauseStartedAt was already zeroed, it counts from recoveryLockdownStartedAt, which spans back over the already-counted nested pause).

Description — Mechanism B: exitRecoveryLockdown reaches back to pauseStartedAt whenever it is nonzero and predates the lockdown, without checking whether that pause had already auto-expired (past disputeOpeningPauseUntil) before the lockdown began. Since pauseStartedAt is only zeroed by a subsequent setDisputeOpeningPaused call or by exitRecoveryLockdown's own else-branch, an owner pause that is simply left to auto-expire (never explicitly un-paused) leaves pauseStartedAt stuck indefinitely — so an unrelated, much-later lockdown will count the entire dead gap in between as if it were paused time.

Proof of Concept (A): lockdown enters at T=1000; owner pauses at T=1086400 (nested); owner un-pauses at T=1172800 → clamp condition 1000 > 1086400 is false, so the full 86400s is added and pauseStartedAt zeroed; lockdown exits at T=1259200 → start = 1000 (pauseStartedAt is 0), adds 258200s. Stored total = 86400 + 258200 = 344600s (~4 days). True union (pause fully inside lockdown) = 258200s (~3 days). Over-count = 1 day, permanent.

Proof of Concept (B): owner pauses at t=0 (disputeOpeningPauseUntil = 604800), never explicitly un-pauses. Lockdown enters at t=691200 (8 days — 1 day after the pause already lapsed). Lockdown exits at t=777600 (9 days). start = min(691200, pauseStartedAt=0) = 0; adds 777600 - 0 = 777600s (9 days). True union [0,604800] ∪ [691200,777600] = 604800 + 86400 = 691200s (8 days). Over-count = 1 day (equal to the dead gap, which is unbounded).

Impact: TaskRegistry.totalDisputeOpeningPausedTime() reads this accumulator directly; every task's pauseDelta (used by expireTask, openDispute, resolveStaleReview) inherits the inflation — posters can be blocked from timely expireTask refunds, and dispute-opening/stale-review windows stay open longer than entitled, for every task whose lifecycle spans the affected window.

Fix (A): also handle recoveryLockdownStartedAt != 0 && recoveryLockdownStartedAt <= pauseStartedAt in the unpause branch by adding zero (the interval is fully subsumed by the lockdown).
Fix (B): in exitRecoveryLockdown, only reach back to pauseStartedAt when disputeOpeningPauseUntil >= recoveryLockdownStartedAt (the pause was still active when the lockdown began); otherwise start counting from recoveryLockdownStartedAt.

Fix: Move the worker's _bindAgent/reserveTask call out of createTask and into acceptDirectHire, so collateral is reserved only after the invited worker consents. Keep requireMinimum(worker) (a stateless solvency pre-check) at creation time.

[6] Colluding poster+worker can seat and freeze any global arbitrator's ETH bond via tier-0 (sub-$1) disputes, with no arbitrator consent required

Severity: Medium · Confidence: 78 · Origin: [phase2: asymmetry], corroborated by leads from flow-gap and math-precision (the latter identifying the enabling tier-0 gate gap).

Location: ArbitrationModule.sol:512-551 (proposeArbitrator), ArbitrationModule.sol:918 (_tierForAmount), ArbitrationModule.sol:31 (MIN_QUALIFIED_DISPUTE = 1_000_000 = $1 USDC).

// ArbitrationModule.sol:540-551 — tier 0 has NO reputation gate
uint256 rep = address(reputationRegistry) != address(0)
    ? reputationRegistry.arbitratorReputation(arbitrator)
    : 0;
if (d.tier == 1) {
    require(rep >= MIN_REP_TIER1 || bootstrapQualified[arbitrator], "Arbitration: rep tier1");
} else if (d.tier >= 2) {
    require(rep >= MIN_REP_TIER2, "Arbitration: rep tier2");
    require(resolvedCount[arbitrator] >= MIN_RESOLUTIONS_TIER2, "Arbitration: insufficient resolutions");
}
// tier 0 (lockedAmount < $1): no rep/resolvedCount requirement at all

Description: A dispute's arbitrator-eligibility tier is derived from the disputed amount; disputes under $1 (tier 0) impose no reputation requirement in proposeArbitrator — only that the named arbitrator is registered/global, meets the $25 entry minimum, and holds ≥1 ETH verifier bond. An attacker controlling both a poster and a worker account can create a minimally-funded (<$1) direct-hire task, open a dispute, and have both attacker-controlled "parties" name any bonded global arbitrator — including a specific target — satisfying the code's mutual-consent check without that arbitrator's actual agreement. Seating locks the arbitrator's ETH bond via lockVerifierBond until the dispute's 21-day absoluteDeadline. Because the lock is extend-only and globalArbitrator has no deregistration path, a persistent attacker can re-seed the lock before each expiry, keeping the target's bond frozen at a recurring cost of roughly $5 USDC + 1,000 AZL + ~$1 escrow per 21-day cycle.

Proof of Concept: Attacker-controlled poster P and worker W: createTask(worker=W, totalAmount=500000 /* $0.50 */, mode=UPFRONT, ...); W acceptDirectHire; openDispute — _tierForAmount(500000) = 0 (tier 0). Both P and W call proposeArbitrator(disputeId, victim) where victim is a real, bonded global arbitrator. Seating succeeds with zero reputation check; lockVerifierBond(victim, absoluteDeadline) fires. Victim's ETH bond is now locked for 21 days without their consent or any action on their part. Attacker repeats before expiry to sustain the freeze.

Fix: Require the seated arbitrator's own explicit per-dispute acceptance before lockVerifierBond fires (not just the two parties' mutual consent); and/or add an arbitrator-controlled globalArbitrator de-registration path (blocked only while actively seated); and/or bound the lock to the dispute's evidenceDeadline rather than the full 21-day absoluteDeadline.

[7] Arbitration-authority codehash pin is enforced only in the coordinator; target contracts trust the coordinator's word with no independent verification

Severity: Medium · Confidence: 65 · Origin: [phase1: access-control] (carried forward; not independently re-examined by Phase 2's blind agents in this exact framing, though the related compromised-coordinator-owner scenario is corroborated as a Lead below).

Location: EscrowVault.sol:99-105, AgentDepositVault.sol:248-254, ReputationRegistry.sol:122-128, TaskRegistry.sol:136-145 (all four emergencySetArbitration* functions).

// EscrowVault.sol:99-105 (identical pattern in the other three targets)
function emergencySetArbitrationModule(address _arbitration) external {
    require(msg.sender == arbitrationRecoveryCoordinator, "EscrowVault: not coordinator");
    require(_arbitration != address(0), "EscrowVault: zero arbitration");
    address oldModule = arbitrationModule;
    arbitrationModule = _arbitration;
    emit ArbitrationModuleChanged(oldModule, _arbitration, true);
}

Description: The protocol's advertised safety property — that arbitration authority can only be replaced by a byte-identical, codehash-pinned module — lives entirely inside ArbitrationRecoveryCoordinator._validateReplacement (which does correctly pin approvedArbitrationCodeHash at construction and check it on every proposeRecovery). But each of the four target contracts' emergencySetArbitration* functions performs no independent validation of what the coordinator passes in — they check only msg.sender == arbitrationRecoveryCoordinator. The one-shot setArbitrationRecoveryCoordinator setters attempt to validate the coordinator itself by calling its own view getters (candidate.taskRegistry(), candidate.escrow(), etc.) — but those are plain view functions on an address the owner is choosing to trust, and an attacker-supplied contract can return whatever values are needed to pass those checks. The entire codehash guarantee therefore reduces to trusting the owner to wire the genuine coordinator during the one-shot window; a malicious or compromised owner wiring a fake coordinator (only possible before the real one is set) bypasses the codehash/graph safety property entirely, once, permanently (since wiring is one-shot).

Proof of Concept: Attacker deploys EvilCoordinator whose taskRegistry()/escrow()/agentDepositVault()/reputationRegistry() view functions return the addresses the real four contracts expect (spoofed). While a target contract's arbitrationRecoveryCoordinator is still unset, its owner (malicious or compromised) calls setArbitrationRecoveryCoordinator(evilCoordinator) — passing the target's own validation since it only reads the attacker contract's self-reported views. EvilCoordinator then calls target.emergencySetArbitrationModule(attackerModule) — no codehash check exists on the target side to stop it.

Fix: Have each target contract independently store and verify the approved arbitration codehash at the point of authority change (inside emergencySetArbitration*), rather than delegating the entire guarantee to the coordinator's internal check.
