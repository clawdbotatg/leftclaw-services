Methodology: Two-phase audit — Phase 1 breadth (8 ethskills domain checklists) → Phase 2 depth (12 pashov attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation with targeted source re-verification of every phase-unique finding.

FWA is a randomized NFT acquisition pool: depositors list an ERC721 backed by ETH; purchasers pay an EV-priced fee for a Chainlink VRF draw that allocates a listing weighted inversely to its backing. FWAToken is a transfer-locked, fixed-supply ERC20 that funds a permissionless on-pool buyback, both contracts driving a single Uniswap v4 ETH/FWAToken pool directly via IUnlockCallback.

Reconciliation summary: Phase 1 (8 domain agents) and Phase 2 (12 attacker-mindset agents, blind) were run independently. Overlap: 4 distinct root-cause findings corroborated by both phases (in several cases by 4–6 independent agents each, with independently-derived numeric proofs). Phase-1-only: 4 findings (all owner-trust/access-control items, confirmed via targeted source re-read in this synthesis). Phase-2-only: 1 novel finding (JIT buyback-reward capture) not surfaced by any Phase 1 checklist — confirmed via targeted source re-read. All phase-unique findings were re-examined against source directly before inclusion below; none were dropped.

[1] Deposit during VRF flight window force-refunds pending acquisitions (griefing DoS)

Severity: High
Location: listNFT() (FWA.sol:717-754), fulfillRandomWords() slippage branch (FWA.sol:1175-1214), acquisitionFee() (FWA.sol:1015)
Origin: [both] — Phase 1: precision-math (P-1, Low), oracles-vrf (O-1, High). Phase 2: economic-security, execution-trace, invariant, asymmetry (4 independent FINDINGS, with independently-derived numeric proofs).

Description: listNFT deposits are deliberately exempt from the withdrawLockBlocks gate that protects withdrawals — the code comment states "Deposits are otherwise always allowed, even with acquisitions in flight: pool growth never invalidates an acquisition." This is incorrect. acquisitionFee() is the harmonic mean of all active listings' backing (weightedBackingTotal / totalWeight), and fulfillRandomWords re-checks this live value against the fee escrowed at request time, with only a ±5% (selectionSlippageBps) tolerance:

// FWA.sol:1203-1210
uint256 liveFee = acquisitionFee();
uint256 escrowed = acquisition.priceEscrowed;
uint256 tolerance = escrowed * selectionSlippageBps / BPS;
if (liveFee > escrowed + tolerance || liveFee + tolerance < escrowed) {
    acquisition.status = AcquisitionStatus.Refunded;
    if (escrowed != 0) SafeTransferLib.forceSafeTransferETH(acquisition.purchaser, escrowed);
    emit AcquisitionRefundedSlippage(requestId, acquisition.purchaser, escrowed, escrowed, liveFee);
    return;
}

Because minBacking defaults to 0 (FWA.sol:256) and deposits are unlocked, any address can deposit a below-pool-average listing at any moment — including inside the ~3-block Chainlink VRF confirmation window between a victim's acquire() and its callback — and collapse or spike the live fee past the 5% band.

Proof of Concept (from the asymmetry agent, independently re-derived by 3 other agents):

  1. Pool holds one listing backed 10 ETH → acquisitionFee() ≈ 11 ETH (10 ETH EV × 1.1 surcharge).
  2. Victim calls acquire(), escrowing ~11 ETH and paying the non-refundable Chainlink native VRF fee. A VRF request opens.
  3. Within the confirmation window, attacker calls listNFT{value: 0.001 ether}(whitelistedCollection, tokenId). New weightedBackingTotal ≈ 2e36, totalWeight ≈ 1e21 → live EV collapses to ≈ 0.002 ETH — a >99% drift, ~20x past the 5% tolerance.
  4. VRF callback lands, sees liveFee + tolerance < escrowed, and refunds the victim's escrowed fee via AcquisitionRefundedSlippage. No listing is allocated. The victim's non-refundable VRF fee is gone with nothing received.
  5. Attacker withdraws the dust listing (and backing) after the short lock elapses. Cost: gas + one whitelisted NFT + trivial recoverable backing. Repeatable against every subsequent acquisition in any pool where a single deposit can move the harmonic mean >5% — true for any pool of roughly ≤19 listings of similar size, and easily achievable in larger pools with a correspondingly larger (but still fully recoverable) deposit.

The guard is two-sided, so an oversized deposit can equally spike the live fee upward past tolerance — the attack works in either direction depending on what's cheapest for the attacker to achieve.

Recommendation: Gate listNFT and updateBacking increases with the same withdrawLockBlocks window applied to withdrawals whenever any acquisition is in flight (or globally), so the pool a pending purchaser priced against cannot be altered before their VRF callback lands. Alternatively, make the fulfillment guard one-sided — only refund when the live fee has risen (protecting the purchaser from overpaying), never when it has fallen, since a falling price cannot itself harm the purchaser.

[2] JIT/flash-deposit capture of buyback's depositor token injection

Severity: High
Location: onTokenReceived() (FWA.sol:1721-1735), claimDepositorTokens() (FWA.sol:1745-1767)
Origin: [phase2 only] — trust-gap, economic-security, flow-gap (3 independent FINDINGS, converging on the identical mechanism from three different attack lenses). Not surfaced by any Phase 1 checklist. Re-verified directly against source in this synthesis.

Description: FWAToken's permissionless buyback() routes a slice of newly-bought FWAToken to FWA via onTokenReceived, which credits depositors through:

// FWA.sol:1723-1730
if (depositorAmt != 0) {
    if (sqrtBackingTotal == 0) {
        ITokenBurnable(token).burn(depositorAmt);
    } else {
        _advanceToken();
        accTokenPerSqrt += depositorAmt * SCALE / sqrtBackingTotal; // inject into Mechanism 2
        emit ProtocolTokensRedistributed(depositorAmt);
    }
}

This is an instantaneous lump-sum injection weighted by whoever holds √backing at that exact block — architecturally inconsistent with the contract's own continuous emission stream (_advanceToken), which correctly time-integrates via depositorRatePerSec * dt. Critically, claimDepositorTokens (FWA.sol:1745) has no withdraw-lock — it only requires listing.status == Active and listing.depositor == msg.sender — because it doesn't touch weight or value:

// FWA.sol:1747-1750
function claimDepositorTokens(uint256[] calldata listingIds) external nonReentrant returns (uint256 total) {
    if (token == address(0)) revert TokenNotConfigured();
    _advanceToken();
    for (uint256 i = 0; i < listingIds.length; i++) {
        ...
        if (listing.status != ListingStatus.Active) revert ListingNotActive();
        if (listing.depositor != msg.sender) revert NotDepositor();
        uint256 pending = _pendingToken(listingId);

Proof of Concept:

  1. Honest pool holds one 1 ETH listing (√value ≈ 1e9, contributing to sqrtBackingTotal).
  2. Attacker calls listNFT{value: 100 ether}(...) — √value ≈ 1e10, now dominating sqrtBackingTotal ≈ 1.1e10.
  3. Attacker (or anyone) calls FWAToken.buyback() (permissionless, 1-block rate limit) — onTokenReceived injects depositorAmt into accTokenPerSqrt in the same block the attacker's large deposit is present.
  4. Attacker's instantaneous share of the injection ≈ 1e10 / 1.1e10 ≈ 91%, for roughly zero holding time. Attacker immediately calls claimDepositorTokens([id]) — no lock blocks this.
  5. Attacker calls withdrawListing(id) once the short withdrawLockBlocks window elapses (or immediately, if no recent acquire() has refreshed the lock — a common condition), recovering the 100 ETH principal.

Because none of steps 2-5 require holding capital across a meaningful time window, this is plausibly executable via a single flash-loaned transaction whenever the withdraw lock is not currently active (i.e., whenever no acquisition has recently been requested) — making the attack effectively capital-free beyond gas and flash-loan fees. Every honest long-term depositor is diluted to near-zero on any buyback the attacker chooses to trigger.

Recommendation: Route the buyback-sourced depositor slice through the same time-integrated accumulator used for continuous emission (accrue it into a pending bucket released gradually via depositorRatePerSec-style streaming) rather than crediting it instantaneously against the current sqrtBackingTotal. Alternatively, require a minimum deposit age before claimDepositorTokens can realize tokens accrued from a discrete buyback injection.

[3] FWAToken.buyback() has no slippage protection — permissionless, sandwichable

Severity: High
Location: FWAToken.buyback() / unlockCallback() (FWAToken.sol:313-350, ~2609-2672 in combined source)
Origin: [both] — Phase 1: defi-amm (H-1, High), erc20 (T-1, Medium). Phase 2: economic-security (FINDING), access-control and boundary (corroborating leads).

Description: The buyback swap executes with no output floor and an extreme price limit:

// unlockCallback, buyback path
BalanceDelta d = poolManager.swap(key,
    SwapParams({zeroForOne: true, amountSpecified: -int256(amountIn), sqrtPriceLimitX96: TickMath.MIN_SQRT_PRICE + 1}), "");

No minOut parameter exists on this path, unlike FWA's own user-facing buys (claimAccruedTokens, acceptBidAsTokens) which correctly enforce a caller-supplied minOut and revert with SlippageBuy if unmet. buyback() is permissionless, callable by anyone with a 0.5% caller bounty, and the pool runs at POOL_LP_FEE = 0 — a sandwicher pays zero fee to bracket each buyback.

Proof of Concept: Once external sells are open (post-launch, hook-gated), an attacker can: (1) buy FWAToken from the pool, pushing price up; (2) call (or wait for someone to call) buyback(), which executes its ≤1 ETH slice at the now-inflated price with no floor; (3) sell the FWAToken from step 1 back into the pool at the now-higher price, capturing the price impact the buyback paid — extracted directly from the protocol's buyback reserve, meaning fewer tokens reach depositors/purchasers/burn than the ETH should have bought. BUYBACK_DELAY_BLOCKS = 1 provides negligible protection — the reserve can be drained one slice per block across consecutive blocks.

Recommendation: Add a manipulation-resistant minOut to the buyback swap — derive it from an on-chain TWAP over the pool (or a stored/decaying reference price) and revert if amountOut falls short. Increasing BUYBACK_DELAY_BLOCKS alone does not fix this without a price floor.

[4] Owner can seize up to 100% of an allocated listing's escrowed backing

Severity: Medium
Location: setOwnerSettlementFeeBps() (FWA.sol:2135-2137), setSettlementDiscountBps() (FWA.sol:2116-2120), _settleNFTToPurchaser() (FWA.sol:1443-1464), reachable permissionlessly via finalizeUnsettled() (FWA.sol:1410-1418)
Origin: [phase1 only] — general (G-1) and access-control (AC-1), 2 independent agents. Not flagged by Phase 2's dedicated access-control agent (which scoped owner-authorized-but-excessive powers as outside its unauthorized-access remit). Re-verified directly against source in this synthesis — confirmed accurate.

Description:

// FWA.sol:2135-2137
function setOwnerSettlementFeeBps(uint256 newOwnerSettlementFeeBps) external onlyOwner {
    if (newOwnerSettlementFeeBps > settlementDiscountBps) revert InvalidConfig();
    ownerSettlementFeeBps = newOwnerSettlementFeeBps;
}

The only bound is <= settlementDiscountBps, which itself can be raised as high as BPS (10,000 = 100%) via setSettlementDiscountBps (bounded only to [MIN_SETTLEMENT_DISCOUNT_BPS=5000, BPS]). In _settleNFTToPurchaser:

// FWA.sol:1454-1456
uint256 ownerCut = value * ownerSettlementFeeBps / BPS;
toDepositor = value - ownerCut;

This path is reached by finalizeUnsettled, which is permissionless and callable by anyone once finalizeWindow has elapsed on an Allocated listing (FWA.sol:1410-1418, confirmed no access modifier beyond the state/timing checks).

Proof of Concept: Owner calls setSettlementDiscountBps(10000) then setOwnerSettlementFeeBps(10000). A depositor's listing is allocated to a purchaser and left unsettled past finalizeWindow. Anyone calls finalizeUnsettled(listingId) → ownerCut = value, toDepositor = 0 — the depositor's entire escrowed backing accrues to accruedOwnerFees while the NFT still ships to the purchaser.

Recommendation: Bound ownerSettlementFeeBps to a small absolute cap independent of settlementDiscountBps (e.g. a few hundred bps, matching the documented ~1% intent), or snapshot fee parameters at allocation time so an already-locked-in listing's economics cannot be changed retroactively.

[5] Owner/distributors bypass FWAToken's transfer lock

Severity: Medium
Location: setDistributor() (FWAToken.sol:183-186), _afterTokenTransfer() (FWAToken.sol:405-421)
Origin: [phase1 only] — access-control (AC-2), 1 agent. Re-verified directly against source — confirmed accurate.

Description:

// FWAToken.sol:405-410
function _afterTokenTransfer(address from, address to, uint256 amount) internal override {
    if (from == address(0) || to == address(0)) return; // mint / burn
    if (isDistributor[from] || isDistributor[to]) return;
    address o = owner();
    if (from == o || to == o) return;
    ...

The token is designed to be buy-only (transfer-locked) until the hook opens selling. But the owner is unconditionally exempt from the lock, and setDistributor (owner-only, unbounded) can grant the same exemption to any address. This lets the owner (or any owner-blessed address) sell FWAToken into the pool while ordinary holders remain locked out.

Recommendation: Document this as an explicit trust assumption if intentional (it mirrors a referenced prior design). Otherwise, scope the distributor exemption strictly to protocol-internal routing addresses and remove the blanket owner exemption post-launch.

[6] Owner can redirect buyback proceeds via unconstrained setPool

Severity: Medium
Location: setPool() (FWAToken.sol:191-195), consumed in buyback() (FWAToken.sol:339-343)
Origin: [phase1 only] — access-control (AC-3), 1 agent. Re-verified directly against source — confirmed accurate.

Description:

// FWAToken.sol:191-195
function setPool(address g) external onlyOwner {
    if (g == address(0)) revert InvalidAddress();
    pool = g;
    emit PoolSet(g);
}

No validation that g is the legitimate FWA contract. In buyback(), the depositor+purchaser slice (80% by default via routeDepositorBps/routePurchaserBps) is transferred to pool and IBuybackRouter(pool).onTokenReceived(...) is called. Combined with setDistributor (finding #5), the owner can point pool at a self-controlled sink (also granted distributor status so the transfer passes the lock) and divert the routed buyback proceeds away from depositors/purchasers entirely — and since buyback() is permissionless, the owner doesn't even need to trigger it themselves.

Recommendation: Make pool settable only once, or immutable after first configuration, or place it behind a timelock so a malicious redirect is publicly visible before it can be exploited.

[7] withdrawListing strict NFT transfer can strand a depositor's ETH + NFT

Severity: Medium
Location: withdrawListing() (FWA.sol:825-858)
Origin: [both] — Phase 1: erc721 (E-1, Medium), dos (D-1, Low). Phase 2: boundary (lead), periphery (adjacent).

Description: Every resolution path (_deliverNFT, FWA.sol:1503-1510) delivers the NFT best-effort via try/catch, recording stuckNFTRecipient on failure so the ETH legs always settle independently. withdrawListing does not follow this pattern — it sends the ETH backing, then attempts a strict safeTransferFrom:

SafeTransferLib.forceSafeTransferETH(msg.sender, value);
...
ERC721(listing.collection).safeTransferFrom(address(this), msg.sender, tokenId); // strict, no fallback

If the NFT leg reverts (depositor is a contract without onERC721Received, or the collection is paused/blacklisted/reverting), the entire call reverts, including the ETH refund — violating the contract's own stated invariant that "any un-allocated listing is fully withdrawable by its depositor."

Mitigating factor (noted by the dos-agent): updateBacking(id, minBacking) does not touch the NFT and can still recover ETH backing down to minBacking, so the loss is generally partial (the residual minBacking slice + the NFT) rather than a full lock, except when minBacking is at or near the deposited amount.

Recommendation: Route withdrawListing's NFT return through _deliverNFT (best-effort + stuckNFTRecipient fallback), matching every other exit path.

[8] buyback() pays caller bounty even on a zero-output swap

Severity: Low
Location: buyback() (FWAToken.sol:313-350)
Origin: [both] — general (G-2) and erc20 (T-2), 2 phase-1 agents. Re-verified: incentive is computed from slice and paid unconditionally at the end regardless of amountOut.

Description: Once the seeded single-sided LP position is fully bought out, further buyback() calls swap for amountOut == 0 but still pay the 0.5% caller bounty from the pre-swap slice, and still advance lastBuybackBlock. An MEV bot can drain the ETH reserve at 0.5%/block with zero buyback benefit once this state is reached.

Recommendation: Only pay the bounty (and advance lastBuybackBlock) when amountOut > 0.

[9] Inverse-weight formula has no minBacking floor by default

Severity: Low (informational restatement — root cause of Finding #1)
Location: minBacking (FWA.sol:256, defaults to 0), listNFT() weight computation
Origin: [both] — this is the same underlying design gap that enables Finding #1; listed separately here because Phase 1's precision-math agent flagged it purely as a pricing-distortion curiosity (Low) before Phase 2 demonstrated it is actively weaponizable as griefing DoS.

Recommendation: Ship a non-zero default minBacking and/or cap per-listing weight so a single lightly-backed listing cannot dominate totalWeight or collapse the harmonic-mean price. This single change substantially mitigates Finding #1.

[10] Partial-fill swaps can strand purchaser ETH

Severity: Low
Location: claimAccruedTokens() / _buyTokens() / unlockCallback() (FWA.sol ~1670-1716), acceptBidAsTokens()
Origin: [phase2 only] — boundary, periphery, trust-gap, first-principles, flow-gap (5 independent leads converging on the identical mechanism; none could confirm reachability against live pool liquidity).

Description: claimAccruedTokens zeroes the caller's tokenBuyAllowance for the full requested amount before the swap executes. The swap is exact-input with sqrtPriceLimitX96 = MIN_SQRT_PRICE + 1; unlockCallback settles only the ETH actually consumed (-d.amount0()). If the pool's FWAToken liquidity is exhausted before the full input is absorbed, the swap partial-fills for less than amount, and the unspent difference remains in the contract with the allowance already zeroed — silently stranded rather than returned to the caller.

Reachability: Unconfirmed. This requires the single-sided seeded launch position to be exhausted within one swap, which depends on on-chain pool depth at the time of the call — not verifiable from source alone. Five independent agents flagged the identical mechanism without being able to construct a concrete trigger, which is a strong-enough signal to report but not to rate above Low pending on-chain liquidity verification.

Recommendation: Check d.amount0() against amount post-swap and refund any shortfall to the caller rather than treating a partial fill as a full spend.

Low / Info — Single-source items (not independently corroborated, included for completeness)

[11] Low — Single-step Ownable, no forced 2-step handover. Both contracts use Solady's single-step Ownable; transferOwnership/renounceOwnership are immediately effective with no recovery. (Phase 1, access-control.)

[12] Low — setSurchargeBps uncapped; setOwnerAcquisitionFeeBps capped only at 100%. Owner can price acquisitions arbitrarily high (griefing, not fund loss — purchasers are protected by their own maxAcquisitionFee slippage guard) or route the entire acquisition fee to themselves instead of depositors. (Phase 1, access-control.)

[13] Low — No timelock on any owner parameter. All economic parameters (fees, windows, splits) apply instantly and retroactively to in-flight positions. General centralization observation; concrete instances are Findings #4 and #12. (Phase 1, general/access-control.)

Info items (no fund-risk, included for completeness): block-count windows (withdrawLockBlocks, MAX_WINDOW_BLOCKS, requestConfirmations) assume ~12s L1 blocks and are miscalibrated if deployed to a fast L2; stale side-mappings not cleared on listing removal (harmless dead storage); non-standard ERC721 collections (e.g. CryptoPunks) cannot be deposited (compatibility only); _deliverNFT/recoverStuckNFT trust non-reverting transferFrom semantics, so a deliberately non-standard whitelisted collection could strand an NFT with no recovery path; an uncontested vacant topListingId can be seized by a minimal-backing listing (2 phase-2 agents, unverified profitability given dust listings displace quickly); flat per-listing fee-sharing rewards listing count over backing size, enabling mild Sybil farming (self-limiting, since dust listings also collapse acquisitionFee() per Finding #9); an unbounded accTokenPerSqrt accumulator could theoretically overflow and brick listing removal at extreme accumulated values — not reachable under realistic token-supply/emission parameters per the agents' own bounds (2 phase-2 leads); tokenBuyAllowanceTotal is written but never read anywhere (dead state, no functional impact); setWithdrawLockBlocks has no lower bound unlike its sibling setSelectionTimeoutBlocks (owner-misconfiguration risk only).

What was checked and found sound

Across both phases (10+ independent agent-passes over the core accounting): ETH/token conservation from acquisition escrow through distribution/settlement (traced independently by 6+ agents — always balances exactly); the sparse segment-tree selection invariant (tree[1] == totalWeight, bounded to fixed TREE_DEPTH, no unbounded loops); VRF request/response correlation, native-fee pass-through, and callback authentication (base contract enforces msg.sender == wrapper); reentrancy surface (all state-changing externals nonReentrant, both unlockCallbacks and onTokenReceived correctly msg.sender-gated, no untrusted external calls inside the VRF callback so a hostile purchaser cannot brick fulfillment); top-listing pot single-settle discipline (_vacateTop/_setTop always zero the pot atomically, no double-pay path); epoch-tally divisor safety (fulfillment-epoch tallying prevents reviving swept/closed epochs); the fee/token dividend accumulators' ceil-on-debt/floor-on-credit discipline (Σcredited ≤ Σcollected always holds); no unauthorized-access / missing-modifier path found by either phase's dedicated access-control review (all admin setters onlyOwner, all depositor/purchaser actions correctly keyed to msg.sender).

The FWATokenHook contract that enforces the buy-only transfer lock's pool-initialization gating and sell-side allowance bumps is not present in this repository and could not be audited; several findings' full risk picture (in particular the transfer-lock's front-running resistance during launch()) depends on that out-of-scope contract being correct.
