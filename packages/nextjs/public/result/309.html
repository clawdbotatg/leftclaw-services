Findings

[70] 1. Shared-vault token blacklist/pause freezes ALL claims for every voter, not just the affected party

FundablePoll._calculatePayout → safeBalanceOf/safeTransfer in cancelVote, claimNonWinningFunds, claimWinningOptionsFunds · Confidence: 70 · [both — phase1: dos-1, erc20-4; phase2: agents 3, 9]

Description
All voters' stakes for a poll live in one contract holding one immutable votingToken. If the token issuer blocklists the poll contract address (USDC/USDT-style) or globally pauses transfers, every payout function reverts for every participant simultaneously. Per-voter blacklisting is NOT a problem — claims are fully independent per address — only a contract-level block/pause is systemic. votingToken is chosen freely by whoever calls the permissionless deployPoll, with only a code.length != 0 sanity check.

Gate check: reachable through common token behavior (blacklisting/pausing is explicitly plausible for contracts holding arbitrary allowlisted tokens); no guard interrupts; material harm to identifiable victims (all voters in the affected poll) → CONFIRMED, Medium (not High, since it requires an external token-issuer action, not a code-exploitable path with no preconditions).

Fix: Inherent to accepting an arbitrary pooled ERC20. Document the risk prominently in poll creation UX, and/or add a factory-level allowlist restricting votingToken to tokens without a freeze authority over arbitrary holders.

[65] 2. pollCreator's winning-fund claim has no fallback if the creator's key is lost

FundablePoll.claimWinningOptionsFunds, pollCreator immutable · Confidence: 65 · [phase1 only — access-1; independently re-verified against source]

Description
Winning-option funds have exactly one exit path: claimWinningOptionsFunds(), gated msg.sender == pollCreator, one-shot via winningFundsClaimed. pollCreator is immutable with no transfer mechanism. Winning-option voters cannot reclaim their own stake either — claimNonWinningFunds explicitly reverts VoteIsWinningOption for them. If the creator's key is lost (or the address can never receive the token, e.g. a permanently blacklisted creator address), the entire winning pool is frozen forever with no recovery path.

Gate check: no guard interrupts; reachable (key loss is a normal real-world occurrence, not a contrived edge case); material harm — permanent loss of fund access — to an identifiable set of victims (winning-option voters whose stake is now unrecoverable by anyone) → CONFIRMED, Medium (owner-only-adjacent fund loss per the severity rubric, since the creator's own claim is what's stuck, but winning voters are also permanently denied any recourse).

Fix: Add a grace-period fallback — e.g. after a long timeout past endTime with no claimWinningOptionsFunds call, allow winning-option voters to reclaim their stake pro-rata, or allow the creator-recipient address to be updated pre-finalization by a designated backup.

[55] 3. winningOptionsCount == totalOptions lets a poll be configured so 100% of every voter's stake goes to the creator regardless of vote choice

FundablePoll constructor (winningOptionsCount_ > totalOptions_ is a strict >, not >=) · Confidence: 55 · [both — phase1: general-1, access-2; phase2: agents 7, 12]

Description
Equality is permitted, so a creator can deploy a poll where every option is marked "winning" at finalization, making claimNonWinningFunds revert for every voter and routing the entire pool to the creator via claimWinningOptionsFunds, irrespective of which option anyone backed. Fully observable pre-vote (immutable public state + the PollDeployed event), so not a hidden rug, but a footgun for inattentive voters — and a concrete configuration a bad-faith creator could exploit for informational asymmetry against unsophisticated users.

Gate check: no guard interrupts (the constructor's own boundary allows it); reachable through normal, permissionless factory usage; unprivileged voters bear the harm, but only after voluntarily opting into an observably-configured poll → CONFIRMED, Low (transparency mitigates severity).

Fix: If "at least one losing option must exist" is intended, tighten the constructor check to require(winningOptionsCount_ < totalOptions_). Otherwise, surface the ratio prominently in any front-end / voting UI.

[50] 4. Zero-amount payouts revert on tokens that reject zero-value transfers

FundablePoll._calculatePayout (can return 0) → unguarded safeTransfer in all three payout functions · Confidence: 50 · [both — phase1: dos-4, erc20-3; phase2: agents 9, 10]

Description
_calculatePayout returns 0 when the caller's liability is 0, _totalOutstandingFunds is 0, or (under downward balance drift) proportional rounding floors to 0. No caller guards against a 0 result before calling safeTransfer, which reverts on tokens like LEND/BNB that reject zero-value transfers — blocking the claim from ever succeeding (though nothing of value is actually at stake in this exact case).

Fix

+ if (payoutAmount == 0) { emit ...; return; }
  IERC20Minimal(votingToken).safeTransfer(msg.sender, payoutAmount);

Skip the transfer when payoutAmount == 0 after applying state effects, so bookkeeping still clears without attempting a zero-value transfer.

Findings below confidence threshold (description only)

[45] 5. _calculatePayout multiplication can overflow and permanently brick withdrawals for extreme-supply tokens

FundablePoll._calculatePayout · Confidence: 45 · [phase2 only — agents 1, 3, 6, 10]

(liabilityAmount * currentBalance) / totalOutstandingFunds computes the product before dividing. Once _totalOutstandingFunds exceeds ~2^128 (≈3.4e20 raw token units), the intermediate product for any non-last claimant overflows uint256 and reverts, permanently — no claimant can ever shrink outstanding to reach the safe branch. Requires an atypical token/tokensPerVote combination, not a realistic mainstream deployment, but is a genuine unguarded code-level gap. Recommend Math.mulDiv (OpenZeppelin) for the full 512-bit intermediate.

[40] 6. Voters on a winning option can escape forfeiture by cancelling right before endTime

FundablePoll.cancelVote · Confidence: 40 · [phase2 only — agent 4]

cancelVote() is fully unrestricted (full pro-rata refund) until block.timestamp <= endTime. Since backing a "winning" option means losing your stake to the creator while backing a "losing" option gets you refunded, the dominant rational strategy for any attentive voter is to cancel just before the deadline if their option is leading — undermining the product's funding mechanism (the creator may only ever collect from inattentive voters). This is a game-theory/mechanism-design property with no third-party victim (no one's funds are stolen; a voter simply reclaims their own stake as the contract explicitly permits), so it is reported as a design observation rather than a security finding, but is worth the client's attention given it may materially undermine the product's intended economics.

[30] 7. Return-data bombing via unbounded low-level call in SafeTokenTransfer

SafeTokenTransfer.safeTransfer/safeTransferFrom/safeBalanceOf · Confidence: 30 · [phase1 only — dos-2]

The hand-rolled helpers use .call/.staticcall capturing bytes memory data with no returndatasize() cap. A malicious votingToken could return a multi-megabyte blob, forcing quadratic memory-expansion gas and an out-of-gas revert — bricking that poll (only reachable via a creator-selected malicious token, no cross-poll impact). Recommend inline-assembly returndatacopy capped to 32 bytes.

[25] 8. Fee-added-on-top tokens can revert the final sweep claim

FundablePoll._calculatePayout sweep branch · Confidence: 25 · [phase1 only — erc20-8]

For the rare token class that charges its transfer fee ON TOP of the transferred amount, the final claimant's exact-remainder sweep can require more than the contract's actual balance, reverting. Niche token class; document as unsupported or add balance headroom.

Leads

Vulnerability trails investigated with concrete code smells; not scored, or explicitly refuted during reconciliation.

  • Investigated and REFUTED: creator sybil-voting to flip which option wins, hoping to seize additional voter funds at "zero risk" (own stake always recoverable via claimNonWinningFunds if the boost fails). Phase-2 agent 5 raised this; agent 11 disproved it by direct trace and it was independently re-derived algebraically during reconciliation: winners are always the top-winningOptionsCount options by total funds, which is already the maximum-value set the creator captures passively. Any sybil boost needed to flip a marginal option into the winning set costs the creator exactly the funding gap it had to cover, netting a pure loss, never a profit. Not a vulnerability.
  • Predictable tiebreak seed — FundablePoll._finalizeIfNeeded — tieBreakSeed derives only from deploy-time immutables, fully computable before the poll opens. Flagged by every one of the 17 agent-runs across both phases that touched finalization logic, and all independently concluded it is not profitably exploitable: ties only matter between options with exactly equal funds, and "winning" a tie is economically bad for that option's backers (their stake flows to the creator), so there is no incentive to game a knowable outcome. Informational only — the standout example of extremely broad, correctly-calibrated non-findings in this audit.
  • Stray/donated token balance is swept by the last or a favorably-timed claimant — FundablePoll._calculatePayout — tokens sent to the poll outside vote() are redistributed pro-rata to current claimants rather than returned to the donor. No protocol-user's principal is at risk. [phase2, agents 3, 4, 6, 7, 9]
  • _optionFunds not decremented in claimNonWinningFunds (unlike cancelVote) — confirmed cosmetic, causes only stale currentVotingResults() view data post-claim, no accounting impact. [phase1 general-3 context; phase2 agents 5, 7, 8, 12]
  • Non-standard token return-data (1–31 bytes) causes a raw abi.decode revert in SafeTokenTransfer instead of a clean handled failure — no mainstream token exhibits this. [phase2, agent 3]
  • No factory-level token allowlist — isolated per-poll risk only; cross-poll drain is not possible (each FundablePoll only ever touches its own immutable votingToken and balance). [phase1 erc20-5; phase2 agent 9]
  • Winning-voter mappings never cleared after the creator's lump claim — inert leftover state, no read path converts it to value. [phase2, agent 12]
  • finalizePoll lacks the nonReentrant modifier applied to every other state-changing function — harmless (no external calls, idempotent via the finalized flag), a consistency note only. [phase2, agent 2]
