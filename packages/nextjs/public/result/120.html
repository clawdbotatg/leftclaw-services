Executive Summary

VaultID is a soulbound ERC-721 identity vault for the LeftClaw ecosystem. Tokens are non-transferable (ERC-5192), minted by paying CLAWD or CV ERC-20 fees, and carry an encrypted IPFS bundle CID plus a backup wallet address as on-chain metadata. The contract is architecturally sound — it uses Ownable2Step, ReentrancyGuard, SafeERC20, and enforces soulbound semantics through an _update override.

Two Medium findings require attention before the contract is widely integrated: the most significant is that any caller can mint a soulbound vault to any address without the recipient's consent, permanently associating attacker-controlled identity metadata with the victim. The second Medium is a JSON-escaping gap that can corrupt marketplace metadata for entire token categories.

No Critical or High severity findings were identified.

Findings

[M-1] Unsolicited Third-Party Minting Enables Soulbound Identity Poisoning

Severity: Medium
Confidence: High — confirmed independently by ethskills (ERC721 domain) and pashov (economic-security + access-control agents)
Location: _mintVault() L301–347, mintWithCLAWD() L273–281, mintWithCV() L289–299

Description: mintWithCLAWD and mintWithCV allow any msg.sender to mint a soulbound vault to an arbitrary recipient (to), paying the fee from their own token balance. No consent, authorization, or signature from to is required. The minter has full control over every vault attribute: encryptedContentURI, contentHash, backupWallet, and category.

Because the token is soulbound (_update reverts on transfer) and only a soft-burn is exposed (burn() sets active = false but does not call _burn, leaving the struct permanently in storage), the recipient cannot fully remove the vault or its contents. getVault(tokenId) will return the attacker-supplied IPFS CID and backupWallet forever, even after soft-burn.

Attack Vectors:

  1. Identity poisoning: Attacker calls mintWithCLAWD(victim, 0, attackerAddr, "ipfs://malicious-cid", attackerHash). Any ecosystem service that resolves identity by querying getVault() for vaults where holder == victim now sees attacker-supplied content and an attacker-controlled backupWallet. If any downstream contract grants recovery/access rights based on backupWallet, the attacker has injected a privileged address into the victim's identity record.

  2. Permanent balanceOf inflation (related): No per-recipient mint cap exists and burn() does not call ERC-721 _burn, so balanceOf(victim) grows monotonically regardless of how many soft-burns the victim performs. Downstream systems using balanceOf(VaultID, user) >= N for access control or Sybil-resistance can be permanently spoofed.

  3. Zero-fee amplification: clawdMintFee can be set to 0 by the owner (valid since 0 ≤ MAX_MINT_FEE). At zero fee, the attack costs only gas (~150k per mint on Base ≈ fractions of a cent), making large-scale spam economically trivial.

Proof of Concept (concrete exploit, fee = 0):

// Attacker
for (uint i = 0; i < 10000; i++) {
    vault.mintWithCLAWD(
        victim,          // to
        0,               // category
        attackerAddr,    // backupWallet
        "ipfs://Qmfake", // encryptedContentURI
        keccak256("fake") // contentHash
    );
}
// victim.balanceOf(vault) == 10000, can never be reduced
// getVault(any of those tokenIds).backupWallet == attackerAddr

Recommendation:

  1. Require msg.sender == to inside _mintVault (vaults must be self-requested), or require an EIP-712 authorization signature from to.
  2. Implement a hard-burn: override burn() to call ERC-721 _burn(tokenId) (removing _owners[tokenId] and decrementing balanceOf) and delete _vaults[tokenId] so the vault data is fully purged.
// Option 1 — self-mint only (simplest)
function _mintVault(address to, ...) internal {
    if (to != msg.sender) revert Unauthorized();
    // ...
}

// Option 2 — hard burn
function burn(uint256 tokenId) external {
    Vault storage v = _vaults[tokenId];
    if (v.holder == address(0)) revert TokenNotFound(tokenId);
    if (ownerOf(tokenId) != msg.sender) revert NotTokenOwner();
    if (!v.active) revert TokenAlreadyBurned(tokenId);
    delete _vaults[tokenId];
    _burn(tokenId);  // requires _update to allow auth == owner
    emit VaultBurned(tokenId, msg.sender);
}

[M-2] _jsonEscape Omits ASCII Control Characters — Owner Can Corrupt All Marketplace Metadata for a Category

Severity: Medium
Confidence: High — flagged by both ethskills (dos + general domains) and 3 pashov agents
Location: _jsonEscape() L558–574, setCategoryLabel() L241–246

Description: _jsonEscape only escapes " (0x22) and \ (0x5C). RFC 8259 §7 mandates that all code points U+0000–U+001F be escaped in JSON strings. setCategoryLabel validates only byte length (≤ 32). A category label containing a raw newline (0x0A), tab (0x09), carriage return (0x0D), or NUL (0x00) will be embedded unescaped into the tokenURI JSON. Strictly-conforming JSON parsers (as used by most NFT marketplaces and indexers) will reject the resulting data URI.

Similarly, _svgBody embeds _safeCategoryLabel(v.category) directly into the SVG <text> element without XML escaping (<, >, &). A label like </text><rect .../> would corrupt the SVG structure. The same trusted owner controls both surfaces.

Impact: A single setCategoryLabel(categoryId, "Label\n") call breaks metadata display for every vault in that category across all marketplace integrations, silently and persistently until the owner corrects the label. If cached metadata has already propagated, restoration may require active cache-busting.

Proof of Concept:

// Owner (accidentally or maliciously):
vault.setCategoryLabel(0, "Personal\nDev");
// All token IDs with category 0 now return malformed tokenURI JSON.
// JSON.parse() throws: SyntaxError: Bad control character in string literal

Recommendation:

function _jsonEscape(string memory s) internal pure returns (string memory) {
    bytes memory b = bytes(s);
    bytes memory out = new bytes(b.length * 6); // worst case: \uXXXX per byte
    uint256 j = 0;
    for (uint256 i = 0; i < b.length; i++) {
        bytes1 c = b[i];
        if (c == 0x22 || c == 0x5c) {
            out[j++] = 0x5c; out[j++] = c;
        } else if (c == 0x0a) {
            out[j++] = 0x5c; out[j++] = 0x6e; // \n
        } else if (c == 0x0d) {
            out[j++] = 0x5c; out[j++] = 0x72; // \r
        } else if (c == 0x09) {
            out[j++] = 0x5c; out[j++] = 0x74; // \t
        } else if (c < 0x20) {
            // \u00XX
            out[j++] = 0x5c; out[j++] = 0x75; out[j++] = 0x30; out[j++] = 0x30;
            out[j++] = _hexNibble(uint8(c) >> 4); out[j++] = _hexNibble(uint8(c) & 0xf);
        } else {
            out[j++] = c;
        }
    }
    bytes memory trimmed = new bytes(j);
    for (uint256 k = 0; k < j; k++) trimmed[k] = out[k];
    return string(trimmed);
}

Alternatively, add a content guard in setCategoryLabel:

for (uint256 i = 0; i < bytes(label).length; i++) {
    require(bytes(label)[i] >= 0x20, "Label contains control character");
}

[L-1] extendExpiry Allows Finite-to-Permanent Conversion — Documented Invariant Violated

Severity: Low
Confidence: High — confirmed by 3 independent agents (invariant, execution-trace, access-control)
Location: extendExpiry() L373–382

Description: The NatSpec explicitly states "Setting newExpiresAt to 0 is NOT allowed once a finite expiry was set." The guard conditions are:

if (v.expiresAt == 0 && newExpiresAt != 0) revert InvalidExpiryExtension();   // (1)
if (newExpiresAt != 0 && newExpiresAt <= v.expiresAt) revert InvalidExpiryExtension();  // (2)

When v.expiresAt = T > 0 and newExpiresAt = 0: guard (1) fails (v.expiresAt != 0) and guard (2) fails (newExpiresAt == 0). v.expiresAt is overwritten with 0, making the vault permanent.

Proof of Concept: Vault minted with 365-day expiry → extendExpiry(tokenId, 0) → vault is now permanent. isExpired(tokenId) always returns false thereafter.

Recommendation:

if (v.expiresAt != 0 && newExpiresAt == 0) revert InvalidExpiryExtension();

Add this as the first check in extendExpiry.

[L-2] extendExpiry Does Not Enforce MAX_VALIDITY_PERIOD

Severity: Low
Location: extendExpiry() L381

Description: setDefaultValidityPeriod enforces newPeriod <= MAX_VALIDITY_PERIOD (100 years), but extendExpiry places no upper bound on newExpiresAt. Owner can set newExpiresAt = type(uint64).max (~year 584 billion), effectively making any finite-expiry vault permanent without using the explicitly-permanent path.

Recommendation: 

if (newExpiresAt != 0 && newExpiresAt > uint64(block.timestamp) + MAX_VALIDITY_PERIOD) 
    revert ValidityPeriodTooLarge();

[L-3] setCvToken Accepts address(0) — One-Shot Guarantee Inconsistently Enforced

Severity: Low
Confidence: High — 3 independent agents
Location: setCvToken() L211–215

Description: The one-shot gate checks address(cvToken) != address(0). Calling setCvToken(address(0)) while cvToken is unset is a logical no-op (0 → 0), but it emits a CvTokenUpdated(address(0)) event and the function can be called again with any address, including address(0) again. Off-chain event consumers believing the CV token is now configured are misled.

Recommendation: Add if (newCvToken == address(0)) revert ZeroAddress(); at the top of setCvToken.

[L-4] Instant Fee Changes Enable Front-Running Against Users with Unlimited Allowances

Severity: Low
Location: setClawdMintFee() L217, setCvMintFee() L222, _mintVault() L333–341

Description: Fee setters take effect immediately with no timelock or delay. A user who has approved type(uint256).max CLAWD can be front-run: owner calls setClawdMintFee(MAX_MINT_FEE), then the user's pending mint transaction executes at the inflated fee, draining up to MAX_MINT_FEE (1 billion CLAWD) from the user's wallet.

Recommendation: Add a slippage parameter to mint functions:

function mintWithCLAWD(
    address to, uint8 category, address backupWallet,
    string calldata encryptedContentURI, bytes32 contentHash,
    uint256 maxFee  // NEW
) external nonReentrant returns (uint256 tokenId) {
    if (clawdMintFee > maxFee) revert FeeTooLarge();
    tokenId = _mintVault(to, category, backupWallet, encryptedContentURI, contentHash, false);
}

[L-5] Unbounded encryptedContentURI — On-Chain Integrators Can Be DoS'd by Large Vaults

Severity: Low
Location: _mintVault() L312, L320

Description: No upper-length bound on encryptedContentURI. A caller can store a multi-kilobyte string (paying gas themselves). getVault() returns the full struct; on-chain integrators calling getVault() with a gas limit may revert OOG when the URI is excessively large.

Recommendation: Cap at a reasonable bound: if (bytes(encryptedContentURI).length > 256) revert UriTooLong();

[L-6] feeRecipient Can Be Set to address(this) — Fee Tokens Permanently Locked

Severity: Low
Location: setFeeRecipient() L229–233

Description: Only address(0) is rejected. If feeRecipient = address(this), all subsequent CLAWD/CV fees are sent to the contract, which has no sweep or rescue function.

Recommendation: Add if (newRecipient == address(this)) revert ZeroAddress();, or add an owner-restricted rescueERC20(address token, address to) function.

[L-7] Soft-Burn Leaves ERC-721 Ownership Intact — balanceOf Permanently Inflated

Severity: Low
Location: burn() L357–364

Description: burn() only sets v.active = false without calling _burn(tokenId). ownerOf and balanceOf are unchanged. No Transfer(holder, address(0), tokenId) event is emitted. Standard ERC-721 tooling (wallets, indexers) continues to display the token as held. This is the intentional soft-burn design, but it diverges from ERC-721 conventions and enables the balanceOf inflation described in [M-1].

Recommendation: Either implement a hard-burn path (see [M-1] recommendation) or emit a synthetic Transfer(holder, address(0), tokenId) in burn() so indexers update, and document prominently that balanceOf includes soft-burned tokens.

[I-1] isExpired Reverts for Non-Existent Tokens While isActive Returns false

Severity: Info
Location: isExpired() L397, isActive() L403

Description: Callers checking both functions on the same non-existent tokenId get inconsistent results — isActive returns false gracefully; isExpired reverts TokenNotFound. Standardize to one convention.

[I-2] renounceOwnership Incorrectly Marked view

Severity: Info
Location: renounceOwnership() L253

Description: The override is declared public view override onlyOwner. Dropping view matches the parent signature exactly and avoids reader confusion. Functionally equivalent since the function always reverts.

[I-3] Receiver-Hook Self-Burn Inverts Event Ordering (VaultBurned Before VaultMinted)

Severity: Info
Location: _mintVault() L344–347, burn() L357

Description: A contract recipient can call burn(tokenId) from within onERC721Received (since burn lacks nonReentrant and ownership is set by _update before the callback fires), emitting VaultBurned before Locked/VaultMinted. This is self-harm only, but produces reversed event ordering for indexers.

Recommendation: Add nonReentrant to burn(), or emit Locked/VaultMinted before the _safeMint call.

[I-4] Vault State Briefly Inconsistent with ERC-721 Ownership During Fee Transfer

Severity: Info
Location: _mintVault() L319–344

Description: _vaults[tokenId] is written before safeTransferFrom and _safeMint. During a fee-transfer hook (e.g., ERC-777-style CV token), getVault(tokenId) succeeds while ownerOf(tokenId) reverts. nonReentrant blocks re-entering mint; burn() is also blocked (ownerOf fails). No concrete exploit path identified with standard ERC-20 tokens; relevant only if cvToken is set to a hook-bearing token.

Recommendation: Document that clawdToken and cvToken must be standard ERC-20s (already noted for FOT tokens in NatSpec). No code change required.

Non-Findings (Explicitly Verified Safe)

  • Soulbound enforcement: _update override correctly reverts on all post-mint movement. approve/setApprovalForAll revert at entry points. No bypass path found.
  • Reentrancy on mint: nonReentrant on both mintWithCLAWD/mintWithCV prevents re-entry. Fee-pull-before-_safeMint follows CEI for the reentrancy-sensitive path.
  • Downcast overflow (uint64(block.timestamp) + defaultValidityPeriod): Both operands uint64, sum ~5e9 seconds, uint64 max ~1.84e19. No overflow risk for centuries. Solidity 0.8 checked arithmetic would revert before silent wrap.
  • Token counter overflow: _nextTokenId is uint256; would require ~2^256 mints.
  • _shortAddr bounds: 42-char hex input correctly indexed; 13-byte output correctly filled.
  • burn() authorization: Checks v.holder != 0 first, then ownerOf == msg.sender. Correct ordering — ownerOf would revert for un-minted tokens.
  • extendExpiry on burned vaults: Guarded by !v.active.
  • Math/precision: No division operations, no oracle math, no share/asset accounting — flat fee transfers only. No precision issues.
  • Chain-specific (Base/OP Stack): block.timestamp suitable for long-term expiry. PUSH0 supported on Base mainnet. No sequencer-dependent logic. No block.number for timing. No ETH transfers.
