Scope note on the client's brief. The job requested focus on "reentrancy in deposit/withdraw, share-price manipulation via first-depositor inflation attack, and access control on parameter updates" for a "Bond-Insurance-Pool vault holding assets." All three phases confirm this specific contract cannot exhibit any of those three bug classes — it is a stateless, zero-state-changing-entrypoint read-only facade (see §Protocol Summary): every deposit/mint/withdraw/redeem call reverts unconditionally, it holds no funds, and it has no owner/admin/parameter of any kind. The real economic activity (contributions, claims, payouts) lives in a separate, already-deployed contract (VaultfireBondInsurancePool) that this vault only reads from — that pool was out of scope for this engagement. The findings below are what all three phases actually surfaced for the in-scope contract: not reentrancy or inflation-attack bugs, but an accounting-basis mismatch that misrepresents pool state to anything trusting the vault's ERC-4626/ERC-20 interface.

Protocol Summary

VaultfireBIPVault is an immutable, stateless ERC-4626-shaped read-only adapter over VaultfireBondInsurancePool. It holds zero mutable storage post-construction (only constants and one immutable pool reference), has zero functioning write paths (every deposit/mint/withdraw/redeem/transfer/transferFrom/approve call and every plain ETH transfer reverts with a typed error), and every accounting figure it reports (totalAssets, totalSupply, balanceOf, isInsured, contributorProfile, vaultStats) is a live, unvalidated passthrough of 8 view calls into the immutable pool. No owner, admin, role, or upgrade path exists anywhere in the contract.

Findings

[82] 1. balanceOf (gross, monotonic) vs. totalSupply/totalAssets (net of claim payouts) breaks the ERC-20/4626 accounting identity

VaultfireBIPVault.balanceOf / totalSupply / totalAssets / convertToAssets · Confidence: 82 · [both] — corroborated independently by the ethskills breadth pass and 7 of 12 blind pashov attack agents (math-precision, economic-security, invariant, periphery, first-principles, boundary, flow-gap), each with its own numeric proof.

Description

balanceOf(account) (VaultfireBIPVault.sol:202-205) reads pool.getContributorProfile(account).totalContributed — a gross figure the pool only ever increments (VaultfireBondInsurancePool.sol:196, profile.totalContributed += msg.value), never decrements. totalAssets()/totalSupply() (VaultfireBIPVault.sol:183-193) both read pool.totalPoolBalance(), which the pool decrements on every approved insurance-claim payout (VaultfireBondInsurancePool.sol:301, totalPoolBalance -= payoutAmount) with no corresponding change to any contributor's totalContributed. So sum(balanceOf(all contributors)) == totalSupply() + pool.totalPaidOut() at every block once any claim has paid out — permanently, and the gap only widens. convertToAssets(shares) (VaultfireBIPVault.sol:211-213) is a hardcoded 1:1 identity, so convertToAssets(balanceOf(user)) reports the same overstated figure directly.

Proof (worked numeric trace, corroborated independently by 3 separate agents)

  1. Alice calls pool.contribute{value: 1 ether}(). State: totalContributed[Alice] = 1e18, totalPoolBalance = 1e18. Vault reads: totalSupply()==totalAssets()==balanceOf(Alice)==1e18 — consistent.
  2. Alice is now insured (totalContributed >= MIN_FOR_INSURED = 0.01 ETH) and submits a claim for 0.1 ether — within the pool's 10%-of-current-balance cap (VaultfireBondInsurancePool.sol:243, maxPayout = totalPoolBalance * MAX_CLAIM_PERCENT / BPS_DENOM).
  3. The pool owner calls resolveClaim(id, true, 0.1 ether) — an ordinary, designed pool operation (VaultfireBondInsurancePool.sol:278-313). Effect: totalPoolBalance -= 0.1e18 → 0.9e18; totalContributed[Alice] is untouched.
  4. Now: vault.totalAssets() == vault.totalSupply() == 0.9e18, but vault.balanceOf(Alice) == 1e18 and vault.convertToAssets(1e18) == 1e18. A single holder's reported balance now exceeds the vault's entire reported total supply/assets (111%).
  5. The flow-gap agent additionally traced that the pool's per-claim 10% cap is checked against the balance at submission time, not re-checked at resolution time — so several claims submitted while the balance is still high can be resolved sequentially, driving totalPoolBalance toward exactly zero while balanceOf figures stay frozen at their historical highs. At totalSupply()==0, the standard 4626 ratio formula balanceOf(user)*totalAssets()/totalSupply() divides by zero for any downstream integrator using it.

Gate trace: Gate 1 (attack execution) clears — no guard interrupts this path; it is the pool's designed, ordinary claim-resolution flow. Gate 2 (reachability) clears — achievable through entirely normal usage. Gate 3 (trigger) clears — the divergence is a passive side effect of intended pool operation, not an admin acting maliciously against documented intent. Gate 4 (impact) is capped: no funds are ever at risk in the vault itself (it holds none), and impact requires a downstream integrator to trust the ERC-4626 interface literally — exactly the audience the vault's own NatSpec targets ("readable to DeFi aggregators... indexers, aggregators, and 4626-aware tooling"), but no live integration relying on this was confirmed from source alone.

Recommendation

Already partially disclosed in NatSpec (VaultfireBIPVault.sol:195-201). If integrator-facing misrepresentation risk is judged material, choose one direction:

  • Option A — stop presenting this as ERC-4626/ERC-20 conformant. Rename balanceOf/totalSupply off the standard interface (e.g. cumulativeContribution/grossContributed) so generic tooling can't mechanically assume sum(balanceOf)==totalSupply.
  • Option B — make the accounting bases consistent. Have the pool expose (and the vault consume) a genuinely net-of-payout per-contributor figure, or surface pool.totalPaidOut() inline wherever balanceOf/convertToAssets are documented (currently only visible via the separate vaultStats() call), so a caller can self-correct.

[76] 2. previewRedeem/previewWithdraw (hardcoded 0) contradict convertToAssets/convertToShares (identity) for the same question

VaultfireBIPVault.previewRedeem / previewWithdraw / convertToAssets / convertToShares · Confidence: 76 · [both] — raised as a finding or corroborating lead by essentially every agent across both phases (multi-agent convergence).

Description

convertToAssets(shares) (VaultfireBIPVault.sol:211-213) returns shares unchanged. previewRedeem(shares) (VaultfireBIPVault.sol:264-266) returns 0 for the same input, unconditionally, at every block. Per EIP-4626, previewRedeem should track convertToAssets absent fee/slippage — here they are maximally contradictory (100% vs. 0%), and neither function's declaration site documents why.

Proof: convertToAssets(1e18) → 1e18. previewRedeem(1e18) → 0. Reproducible with no state precondition, same block.

Gate trace: Gate 1/2 clear trivially. Gate 4 caps severity: redeem() itself always reverts regardless of what either preview reports (VaultfireBIPVault.sol:268-270), so no on-chain value ever moves on the strength of the wrong number — impact is confined to off-chain tooling that cross-checks the two views or displays one without the other.

Recommendation: Document the divergence explicitly at both declaration sites, or make previewWithdraw/previewRedeem mirror the identity convention previewDeposit/previewMint already use (EIP-4626 explicitly instructs preview functions to ignore operational limits).

[75] 3. asset() returns WETH (an ERC-20 the vault never transfers/holds) while totalAssets() is denominated in the pool's native-ETH accounting

VaultfireBIPVault.asset / totalAssets · Confidence: 75 · [both] — raised across nearly all agents in both phases.

Description

asset() (VaultfireBIPVault.sol:177-179) returns WETH_BASE (0x4200000000000000000000000000000000000006) as tooling metadata; confirmed by every agent that no IERC20(WETH_BASE) call exists anywhere in the file. IERC20(WETH_BASE).balanceOf(vault) is always 0, while totalAssets() (native-ETH pool accounting) is nonzero whenever the pool holds funds — a live, checkable contradiction for any integrator performing the standard defensive check "does asset()'s token balance reconcile with totalAssets()."

Gate trace: Gate 4 caps severity at Low — already disclosed in NatSpec (VaultfireBIPVault.sol:174-176), numerically 1:1 in value (WETH:ETH), and no transfer of either token ever occurs, so no fund-loss path exists — only automated-tooling misclassification risk.

Recommendation: Consider a sentinel/zero-address return, or explicit non-4626-standard denomination metadata, if broad automated-tooling compatibility matters.

Leads

High-signal trails where all agents agreed impact is confined to off-chain/deployer-side risk, or where the exploit path could not be fully completed. Not scored.

  • Constructor validates only non-zero-ness of pool_, no interface/code-existence check — VaultfireBIPVault.constructor (VaultfireBIPVault.sol:165-168) — Code smells: pool_ != address(0) is the only guard before permanently committing the immutable pool; no extcodesize/interface probe. Raised independently by 8+ agents across both phases; every one concluded this is not exploitable against the already-deployed instance (whose pool is fixed and confirmed to be the genuine VaultfireBondInsurancePool) — a deploy-time/re-deployment-template risk only.
  • No atomic way to read balanceOf(user) together with totalSupply() — VaultfireBIPVault.balanceOf / totalSupply — vaultStats() bundles pool-wide aggregates atomically but has no per-account sibling; an integrator computing an ownership ratio must make ≥2 separate eth_calls, opening a narrow cross-call staleness window if a claim resolves in between calls.
  • isInsured badge never reflects current pool solvency — VaultfireBIPVault.isInsured / vaultStats — the pool's insured flag is permanent once earned and never re-evaluated against current pool balance; an agent that qualified early still shows isInsured==true after the pool has been drained toward zero by unrelated claims. Root mechanism lives in the out-of-scope pool; the vault only passes it through faithfully.
  • Forced ETH via selfdestruct bypasses receive/fallback, no sweep function — VaultfireBIPVault.receive / fallback (VaultfireBIPVault.sol:347-353) — both revert on ordinary sends, but a forced send leaves address(this).balance > 0 with no function anywhere reading or recovering it. Self-harm only (a griefer burns their own ETH); no accounting impact since nothing in the contract reads address(this).balance.
  • No Transfer/Deposit/Withdraw events ever emitted — VaultfireBIPVault (contract-wide) — implements IERC4626/IERC20Metadata (which declare these events) but never emits any event. Impact depends on whether any consumer indexes via event logs rather than polling views (unverified).
  • previewDeposit ignores maxDeposit==0 — VaultfireBIPVault.previewDeposit / maxDeposit — previewDeposit returns a nonzero identity value despite maxDeposit correctly reporting 0. Zero economic consequence since deposit() reverts regardless; EIP-4626 explicitly permits previews to ignore max-limits.
  • Downstream divide-by-zero if totalSupply() reaches exactly 0 — VaultfireBIPVault.totalSupply / balanceOf — an integrator computing balanceOf(user) * X / totalSupply() hits a hard revert if the pool is ever fully drained by approved claims (structurally possible per the traced pool claim-resolution mechanics in Finding 1). The division itself never happens inside this contract, so this is an off-chain integrator risk, not a vault-side exploit.
