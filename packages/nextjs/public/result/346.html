Security Audit Report: Vaultfire DilithiumAttestor

Target: DilithiumAttestor at 0xef703bBe9b21960ede3e96abBB0Bbd0c525Fe050 (Base, chain 8453)
In-scope contracts: DilithiumAttestor.sol, IStarkVerifier.sol (source verified via Sourcify full match; compiler 0.8.25; OpenZeppelin v5.1.0 dependencies)
Methodology: Two-phase audit — Phase 1 breadth (4 parallel checklist-driven agents: general, signatures, access-control, precision-math) → Phase 2 depth (12 parallel attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation (this document).
Reconciliation summary: Overlap: 6 findings independently confirmed by both phases · Phase-1-only: 3 · Phase-2-only: 1 (documentation-narrative observation, folded into the primary finding below) · Demoted on re-examine: 0.
Completeness: every unique (contract, function, bug-class) raised by either phase's raw agent output is represented below.

Independent on-chain verification performed by the orchestrator and multiple agents: origin() = 0xA054f831B562e729F8D268291EBde1B2EDcFb84F (a plain EOA, not the multisig the contract's own NatSpec recommends), zkEnabled() = false, verifierAddress() = address(0) — confirming the live deployment operates in pure signature-only mode, with the entire ZK/STARK code path permanently dead.

Summary

The client's job description for this audit calls the target a "post-quantum Dilithium signature attestor/verifier" and asks for a review of "correctness of the verification path relative to the Dilithium reference." Both audit phases immediately surfaced a foundational problem with that premise: the contract's own NatSpec explicitly discloses it implements plain ECDSA (secp256k1), not Dilithium, and provides zero post-quantum protection. There is no Dilithium code anywhere in scope. Beyond that headline issue, both phases converged — with unusually strong, unanimous cross-agent corroboration in Phase 2 (12 of 12 independent agents reached the identical conclusion via different reasoning paths) — on a second, more conventional but equally serious defect: the origin signature that authorizes each attestation is never bound to the submitting address, letting anyone who observes a valid signature (trivially available once used, since all transaction calldata is public) front-run or replay it to steal "prover" credit for someone else's attestation. Both phases also independently confirmed the live origin signer is a plain EOA — not the multisig the contract's own documentation recommends — with no rotation or recovery mechanism should that key ever be compromised.

High Severity

[H-1] Contract name and NatSpec claim post-quantum "Dilithium" security; the deployed contract provides zero post-quantum protection

Origin: [phase1 only] (general agent, headline finding) — the misrepresentation itself is a documentation/narrative-level issue that phase-2's code-exploit-focused agents did not independently surface as a distinct finding, but it was verified directly against the contract's own source and the client's own job description
Location: contract-level NatSpec, lines 9-25

The contract's own NatSpec states, verbatim: "IMPORTANT: Despite the name, this contract uses standard ECDSA (secp256k1) signature verification, NOT post-quantum Dilithium signatures... AUDIT-C4: Dilithium verification is NOT implemented." Yet the surrounding docstring for the overall system still headlines "Post-quantum secure (future-proof)" as a design property, and — notably — the client's own request that generated this audit describes the target as a "Post-quantum Dilithium signature attestor / verifier," repeating the same misrepresentation. On the live deployment, the STARK layer anyone might associate with "post-quantum" is confirmed permanently disabled (zkEnabled=false). Every bit of trust in attestedBeliefs reduces to a single secp256k1 keypair (origin) — precisely the cryptographic primitive quantum computers are expected to break. There is no fund-loss vector in this contract, but any user or integrator who selects this specific deployment because of its name or documented "post-quantum"/"Dilithium" claims is relying on a guarantee that flatly does not exist.

Recommendation: Rename the contract to reflect actual behavior (e.g., ECDSABeliefAttestor), strip "post-quantum"/"Dilithium" language from all NatSpec and client-facing material describing this address, and expose a machine-readable securityModel() view so integrators querying the contract programmatically — not just reading buried NatSpec — get the correct signal.

[H-2] Origin signature is not bound to msg.sender — any observer of a valid signature can steal or front-run "prover" attribution

Origin: [both] — Phase 1 (signatures agent, general agent — 2/4 agents, both with full exploit traces) · Phase 2 (12/12 agents, unanimous — the single strongest cross-agent corroboration observed across all audits run today)
Location: attestBelief (94-123)

bytes32 messageHash = keccak256(abi.encodePacked(beliefHash, block.chainid, address(this)));
bytes32 ethSigned = messageHash.toEthSignedMessageHash();
require(ECDSA.recover(ethSigned, originSignature) == origin, "Origin sig mismatch");
...
emit BeliefAttested(beliefHash, msg.sender, zkVerified);

The signed payload never includes msg.sender or any nonce. require(ECDSA.recover(...) == origin) is therefore a pure function of (beliefHash, chainid, address(this), signature) — completely independent of who calls the function. msg.sender is used only as the prover value recorded in the emitted event.

Proof: A legitimate submitter is handed a valid (beliefHash, originSignature) bundle and broadcasts attestBelief. The instant that transaction is pending (or, more simply, once it's mined — calldata is permanently public thereafter), anyone can copy the exact bundle and call attestBelief themselves. The signature check passes identically for the copier, since it never referenced the original submitter's address. The copier's call succeeds and emits BeliefAttested(beliefHash, copier, false) — recording the copier, not the legitimate submitter, as the "prover." This is unconditional in the contract's own documented default launch configuration (zkEnabled=false, confirmed live). Given this is explicitly a reputation/loyalty-attestation system (per the contract's own NatSpec — "loyalty proof," "Vaultfire-approved paths," reputation language throughout), attribution is the entire value of the event, making this a directly exploitable credit-theft vector, not a cosmetic one.

Note on the ZK path: the STARK verification branch (dead on this deployment) does bind proverAddress = msg.sender into its public inputs, which would incidentally block this specific attack if zkEnabled=true and the external verifier genuinely constrains that input (unconfirmed — see M-1). The signature-only path — the contract's actual, documented, live production configuration — has no equivalent protection at all.

Recommendation: Bind msg.sender into the signed hash (e.g. keccak256(abi.encodePacked(beliefHash, msg.sender, block.chainid, address(this)))), forcing origin to co-sign the intended submitter.

[H-3] origin signing key has no rotation, pause, or revocation path — and the live signer is a plain EOA, not the multisig the contract's own documentation recommends

Origin: [both] — Phase 1 (access-control agent, general agent — with independent on-chain verification) · Phase 2 (invariant agent, corroborating)
Location: contract-wide; origin immutable (35), constructor (56-73)

origin is immutable, set once at construction. There is no setOrigin, no pause(), no owner, no timelock, no emergency stop anywhere in the contract (confirmed by exhaustive grep — only 4 functions exist total). If the origin private key is ever compromised, an attacker can forge arbitrary valid attestBelief calls permanently, with no possible remedy on this contract instance.

Independently confirmed on-chain that the live origin (0xA054f831B562e729F8D268291EBde1B2EDcFb84F) is a plain, actively-used EOA (239 transactions, holds unrelated ERC-20s/NFTs, funded from Coinbase) — not the multisig the contract's own NatSpec explicitly recommends ("governance multi-sig recommended"). For comparison, the sibling Vaultfire contract ProductionBeliefAttestationVerifier protects an arguably less-critical parameter with an owner + 48-hour timelock, proving the team is capable of building recovery paths when it chooses to — this contract's sole root of trust received none.

Recommendation: Add a timelocked origin-rotation mechanism controlled by a genuine multisig, or a one-way emergency disable() circuit breaker a designated guardian can trip. At minimum, ensure _origin is actually deployed as a multisig/threshold signer, consistent with the contract's own documented recommendation.

Medium Severity

[M-1] Unverified assumption that the ZK path's proverAddress binding is actually enforced by the external verifier (out of scope, unconfirmed)

Origin: [phase2 only] — 8/12 agents raised this as a lead
Location: verifyZKProof (149-167)

verifyZKProof passes proverAddress = msg.sender as a public input to the external, out-of-scope IStarkVerifier. Whether the underlying STARK circuit cryptographically constrains that public input, or merely carries it as inert, unconstrained metadata, cannot be determined from the interface alone. If the real deployed verifier does not hard-constrain it, the exact same front-running/credit-theft attack from H-2 would also apply were zkEnabled ever set to true. Not independently exploitable against the live deployment, since zkEnabled=false there.

Recommendation: Confirm with the guest-circuit/verifier team that proverAddress is a hard constraint, not an advisory public input, before ever enabling zkEnabled=true in production.

[M-2] No guard against re-attesting an already-attested beliefHash — a signature can be replayed indefinitely, independent of the sender-binding issue

Origin: [both] — Phase 1 (general, signatures agents) · Phase 2 (invariant agent as a distinct second finding; implicit in all 12 agents' exploit chains)
Location: attestBelief (121-122)

attestedBeliefs[beliefHash] = true and the subsequent event emission execute unconditionally — there is no require(!attestedBeliefs[beliefHash]) check anywhere. This is a distinct exploitation window from H-2: even ignoring front-running, the same valid signature can be resubmitted by the same or different callers an unlimited number of times, at any point in the future, each producing a fresh BeliefAttested event.

Recommendation: Add require(!attestedBeliefs[beliefHash], "Already attested"); before the state write. This closes the "replay after success" window; fixing H-2 separately closes the "front-run/steal before success" window — both fixes are needed, neither alone fully closes the exploit surface.

Low Severity

[L-1] Dead ZK/STARK code path has several latent design gaps, relevant only to a hypothetical future zkEnabled=true deployment

Origin: [both] — Phase 1 (general, precision-math, access-control agents, 3/4 as leads) · Phase 2 (4 agents: CEI-ordering, unchecked public-input count, missing domain separation)
Location: verifyZKProof (149-167), constructor (56-73)

Not exploitable on the live contract (zkEnabled=false, verifierAddress=0x0), but flagged for completeness since the source is presumably reused across deployments:

  • The origin signature never binds proofData, so the two authorization layers (signature and ZK proof) are cryptographically independent rather than linked.
  • The external verifier call happens before the state write (attestedBeliefs[beliefHash] = true), a checks-effects-interactions ordering violation — no concrete exploit was constructed, since the state affected is a simple, already-replay-exposed boolean (see M-2), but it's worth fixing as defense-in-depth.
  • The constructor's extcodesize(_verifierAddress) > 0 check is shallow — it would accept any contract with any bytecode (including one that always returns true), rather than validating it actually implements IStarkVerifier correctly via the interface's own getProofSystemId()/getPublicInputsCount() sanity functions, which exist but are unused.
  • The ZK public inputs ([beliefHash, proverAddress, 0, 0]) lack the same chain-ID/contract-address domain separation the signature path deliberately added — epoch/moduleID are hardcoded to 0 rather than genuine per-deployment values.

Recommendation: If a full-ZK deployment is ever made: bind proofData into the signed message; move the state write before the external call (or add a reentrancy guard); add real sanity-check calls to the verifier at construction time; bind block.chainid/address(this) into the ZK public inputs.

[L-2] The "AUDIT-C4 FIX" code comment implies complete replay protection but only covers the chain/contract axis, not the caller axis

Origin: [phase2 only] — 1 agent (asymmetry), narrative/documentation observation
Location: attestBelief, comment at lines 104-106

The inline comment reads as a full replay-protection guarantee ("A signature valid on one chain is NOT valid on another chain or against a different contract deployment") but says nothing about the caller-binding gap that is H-2's root cause — plausibly why this specific gap survived a prior audit pass that clearly did examine replay protection in general.

Recommendation: Update the comment to accurately scope what it protects against, so future reviewers don't assume replay protection is comprehensive.

[L-3] Constructor's verifier validation is a shallow bytecode-presence check, not a correctness check (subsumed detail of L-1, listed separately per phase-1 access-control agent's framing)

Origin: [phase1 only] (access-control agent)
Location: constructor (59-68)

Already covered in L-1's third bullet; listed separately here because the phase-1 access-control agent treated it as its own numbered finding with a distinct recommendation (adding getProofSystemId()/getPublicInputsCount() sanity calls at construction time rather than only at first use).

Informational

  • Cross-chain / cross-deployment replay protection: confirmed effective. block.chainid and address(this) are both included in the signed hash preimage, correctly blocking replay across chains and across multiple same-chain deployments sharing the same origin. No action needed. [both phases]
  • Signature malleability and abi.encodePacked hash construction: confirmed safe. OpenZeppelin v5.1.0's ECDSA.recover correctly rejects malleable signatures via revert; the packed encoding of fixed-width types (bytes32, uint256, address) has no collision ambiguity. No action needed. [both phases]
  • attestBelief being fully permissionless is correct, intentional design — authorization comes entirely from the origin signature, not from msg.sender identity, which is the standard meta-transaction/relayer-friendly pattern. Not a missing-modifier bug. [both phases]

Methodology Notes

  • Both phases audited the same two in-scope files independently; Phase 2 was run with no visibility into Phase 1's findings to avoid anchoring.
  • This is the smallest and most tightly-scoped of the three Vaultfire contracts audited in this batch (176 lines total, with the live deployment's active code path reducible to roughly 30 lines of real logic given zkEnabled=false), which explains the unusually high (12/12) unanimous phase-2 agent convergence on the primary finding — there was simply one dominant, unambiguous defect for every reasoning lens to independently discover.
  • Out of scope: IStarkVerifier's concrete implementation (the external STARK verifier contract) was not available for review; M-1 and parts of L-1 are explicitly conditioned on assumptions about that out-of-scope code.
  • The headline finding (H-1) is not a traditional code-level vulnerability but a direct, source-verified contradiction between the contract's documented/marketed security model and its actual implementation — reported because it directly answers the client's own framing of this audit request ("post-quantum Dilithium signature attestor").
