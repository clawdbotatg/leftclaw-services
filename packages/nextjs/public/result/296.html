What this system does

LiquidityVestingFactory.deploy(owner) (permissionless) creates a LiquidityVesting instance for owner. The owner calls lockUp() to deposit WETH + CLAWD into a Uniswap V3 concentrated-liquidity position (minted via the real INonfungiblePositionManager), which the contract holds as an NFT. Liquidity then vests linearly to owner over vestDuration: vest()/claimAndVest() decrease the position by the currently-vested slice and forward the proceeds (plus accrued trading fees) to owner; claim() collects only fees. On full vesting, the position is burned and the contract becomes re-lockable.

Findings

[1] Permissionless increaseLiquidity() on the position NFT permanently bricks the final vest, freezing the owner's locked principal

Severity: High
Origin: [phase2: agent 12 — flow-gap], independently re-verified by source re-read in synthesis
Location: _vest() — LiquidityVesting.sol:258-262

Description: Uniswap V3's NonfungiblePositionManager.increaseLiquidity(tokenId, ...) carries no ownership/authorization check — unlike decreaseLiquidity, collect, and burn, which all require isAuthorizedForToken. Anyone can therefore add liquidity directly to this contract's position NFT at any time, for the cost of a small amount of WETH/CLAWD plus gas. _vest()'s completion branch calls positionManager.burn(tokenId) unconditionally once its own internal bookkeeping (vestedLiquidity >= initialLiquidity) believes the position is empty:

// LiquidityVesting.sol:247-262
positionManager.decreaseLiquidity(INonfungiblePositionManager.DecreaseLiquidityParams({
    tokenId: tokenId, liquidity: toLiquidate,
    amount0Min: amount0Min, amount1Min: amount1Min, deadline: block.timestamp
}));

(amount0, amount1) = positionManager.collect(INonfungiblePositionManager.CollectParams({
    tokenId: tokenId, recipient: owner(),
    amount0Max: type(uint128).max, amount1Max: type(uint128).max
}));

if (isFinal) {
    positionManager.burn(tokenId);   // <-- no check that on-chain liquidity is actually 0
    isLocked = false;
    tokenId = 0;
}

Uniswap's burn() reverts with "Not cleared" unless position.liquidity == 0 && tokensOwed0 == 0 && tokensOwed1 == 0. decreaseLiquidity above only removes the contract's own internally-tracked toLiquidate amount — any liquidity an attacker externally added via increaseLiquidity is untouched and remains on the position. The unconditional burn() call then reverts every single time the final vest tranche is attempted, for the rest of time — there is no other code path to remove liquidity, transfer the NFT, or otherwise recover.

Proof of Concept:

  1. Owner lockUp()s, minting a position with initialLiquidity = L.
  2. At any point before the final vest, an attacker calls positionManager.increaseLiquidity({tokenId, amount0Desired: <small>, amount1Desired: <small>, amount0Min: 0, amount1Min: 0, deadline: block.timestamp}) directly on the Uniswap NonfungiblePositionManager — this succeeds because increaseLiquidity has no authorization gate. The position's on-chain liquidity is now L + Δ (Δ ≥ 1), while the contract's own initialLiquidity variable stays L.
  3. Once elapsed >= vestDuration, the owner calls vest()/claimAndVest(). totalVestedLiq = initialLiquidity = L, toLiquidate = L - vestedLiquidity, and this final call sets isFinal = true.
  4. decreaseLiquidity(toLiquidate) removes exactly L (the amount the contract believes is the whole position), leaving Δ liquidity on the position. collect(max) zeroes tokensOwed.
  5. positionManager.burn(tokenId) executes with position.liquidity == Δ ≠ 0 → reverts with "Not cleared" → the entire _vest() transaction reverts.
  6. elapsed only grows from here, so every future attempt recomputes the identical final tranche and hits the identical revert. The position (and up to 100% of the owner's remaining locked principal, depending on when the attack lands) is permanently frozen inside Uniswap with no path to recovery.

Cost to the attacker is bounded by gas plus a token amount small enough to register as ≥1 unit of liquidity in the position's tick range — a few cents at most. This is a genuine third-party griefing vector, not owner self-harm: the attacker gains nothing but permanently damages the victim (the vesting contract's owner).

Recommendation:

  if (isFinal) {
-     positionManager.burn(tokenId);
-     isLocked = false;
-     tokenId = 0;
+     (,,,,,,, uint128 remainingLiquidity,,, uint128 owed0, uint128 owed1) = positionManager.positions(tokenId);
+     if (remainingLiquidity == 0 && owed0 == 0 && owed1 == 0) {
+         positionManager.burn(tokenId);
+         isLocked = false;
+         tokenId = 0;
+     }
+     // else: leave the position open; expose an owner-only function to decreaseLiquidity
+     // any externally-added dust and retry burn, instead of being permanently stuck.
  }

[2] vestedLiquidity is never reset across lock cycles — a second lockUp() after a full vest permanently locks the new deposit

Severity: Medium
Origin: [both] — Phase 1 (General-1) and Phase 2 (6 of 12 blind agents: access-control, first-principles, invariant, periphery, execution-trace, trust-gap — independently converged with matching numeric traces)
Location: lockUp() / _mintPosition() (LiquidityVesting.sol:171-207) vs _vest() (LiquidityVesting.sol:237-268); state variable vestedLiquidity (line 148)

Description: _vest()'s completion branch sets isLocked = false and tokenId = 0, which — combined with lockUp()'s guard of only require(!isLocked) — makes the contract explicitly re-lockable. On a second lockUp(), initialLiquidity, lockStart, and vestDuration are all refreshed, but vestedLiquidity is never reset to 0.

Proof of Concept:

  1. Owner locks with liquidity L_old, fully vests. End state: vestedLiquidity == L_old, isLocked == false.
  2. Owner re-locks, minting a new position with liquidity L_new. initialLiquidity == L_new, but vestedLiquidity is still L_old.
  3. In _vest(): totalVestedLiq = pct * L_new / 1e18, toLiquidate = totalVestedLiq - vestedLiquidity(=L_old).
    • If L_new <= L_old: totalVestedLiq never exceeds L_new <= L_old, so toLiquidate underflows on every call (checked uint128 arithmetic reverts) — vest()/claimAndVest() are permanently DoS'd for the entire new cycle.
    • If L_new > L_old: vesting only ever accounts for L_new - L_old; when isFinal triggers, only that difference has been decreased, leaving L_old worth of liquidity still on the position, so the final burn(tokenId) reverts (non-empty position) — the excess L_old liquidity is permanently stranded.

Recommendation:

  function lockUp(uint256 amount0Desired, uint256 amount1Desired, uint256 _vestDuration, int24 _tickLower, int24 _tickUpper, uint256 amount0Min, uint256 amount1Min) external onlyOwner {
      require(!isLocked, "Already locked");
      require(_vestDuration > 0, "Duration must be > 0");
+     vestedLiquidity = 0;
      isLocked = true;
      vestDuration = _vestDuration;
      ...

[3] Fee-on-transfer CLAWD would permanently DoS lockUp()

Severity: Medium
Origin: [both] — Phase 1 (ERC20-1), Phase 2 lead (agents 3, 8, 12)
Location: lockUp() / _mintPosition() — LiquidityVesting.sol:177-204

Description: lockUp() pulls amount1Desired of CLAWD via safeTransferFrom, then approves and passes the same amountDesired value into positionManager.mint(...). Uniswap V3 requires the pool to receive exactly the amount it's told to expect; if CLAWD ever deducts a transfer fee, the contract holds less than it approved, and the pool's mint callback reverts. Uniswap V3 positions are fundamentally incompatible with fee-on-transfer tokens. CLAWD's source is unverified on Sourcify/explorers, so this cannot be ruled out from on-chain data.

Proof of Concept: Not a fund-loss path — lockUp() reverts atomically, no tokens are stranded. Flagged as a total, permanent DoS of the contract's sole purpose if CLAWD has (or later gains, e.g. via upgradeable/admin-controlled logic) a transfer fee.

Recommendation: Confirm CLAWD cannot become fee-on-transfer. If robustness is desired regardless, measure balanceOf(address(this)) before/after safeTransferFrom and feed the actually-received amount into mint.

[4] Pausable/blocklistable CLAWD (or WETH) can freeze vest()/claim(), stranding vested liquidity

Severity: Medium
Origin: [both] — Phase 1 (ERC20-2), Phase 2 lead (agent 3: "dependency-permanent-lock")
Location: _vest() / claim() — LiquidityVesting.sol:213-268

Description: claim(), vest(), and claimAndVest() all terminate in positionManager.collect(...recipient: owner()...). If CLAWD implements transfer pausing, or blocklists owner(), collect reverts and no liquidity or fees can be withdrawn. The recipient is hardcoded to owner() with no alternate address, so a blocklisted owner has no way to redirect funds elsewhere.

Proof of Concept: Token admin pauses CLAWD transfers or blocklists owner(). Every subsequent vest()/claim()/claimAndVest() reverts. Liquidity is not lost outright (it remains in the Uniswap position) but is frozen until the token-side condition is lifted — indefinitely, if never lifted.

Recommendation: Document as an accepted trust assumption on CLAWD's admin, or change collect's recipient to address(this) and let the owner withdraw to an arbitrary address afterward, so a blocklisted owner() still has a route to funds.

[5] Single-step transferOwnership risks permanently misdirecting all future proceeds

Severity: Low
Origin: [phase1 only: Access-1] — re-examined in synthesis: confirmed real, no phase-2 contradiction (phase-2's access-control agent independently verified the onlyOwner gating is tight but did not evaluate the ownership-transfer mechanism itself)
Location: LiquidityVesting (inherits OZ Ownable)

Description: claim(), _vest(), and sweep() all route proceeds to owner(), and only owner may call any fund-moving function. OZ's single-step transferOwnership means a mistyped or unreachable target address permanently redirects all future vesting/fees/sweeps with no recovery. renounceOwnership() is disabled but does not protect against a bad transfer.

Recommendation: Use Ownable2Step instead of Ownable so a transfer requires the new address to acceptOwnership().

[6] Permissionless deploy(owner) enables fake-instance / indexer-poisoning and unbounded registry growth

Severity: Low
Origin: [both] — Phase 1 (Access-2, Access-5), Phase 2 lead (agents 2, 4, 9, 12)
Location: LiquidityVestingFactory.deploy() (lines 18-24), getDeployments() (26-28)

Description: deploy(address owner) has no access control; owner is caller-supplied. Anyone can create instances attributed to an arbitrary victim address, which get recorded in deploymentsByOwner[victim]/allDeployments and emitted via ContractDeployed. A UI/indexer trusting getDeploymentsByOwner(victim) could display attacker-created decoy contracts as "victim's vaults" — a phishing/confusion vector (the attacker cannot operate the fake instance since owner is fixed at construction and all fund-moving functions are onlyOwner, so this is not direct theft). Separately, since deploy() is unbounded and permissionless, allDeployments can be inflated arbitrarily, and getDeployments() returning the full array could eventually exceed practical eth_call limits for off-chain consumers.

Recommendation: Set owner = msg.sender (deployers create only their own instances) or add an allowlist; also index by deployer so consumers can distinguish self- vs third-party-deployed instances. Consider a paginated getter and rely on the ContractDeployed event for enumeration instead of the full-array view.

[7] No minimum bound on _vestDuration — a "locked liquidity" position can be trivially unlockable

Severity: Low
Origin: [phase2 only: agents 1, 9] — re-examined: confirmed real by direct read of lockUp(), line 173: require(_vestDuration > 0, "Duration must be > 0") is the only bound
Location: lockUp() — LiquidityVesting.sol:173

Description: The owner may set _vestDuration = 1 (one second), making a position that is publicly presented as "locked liquidity vesting to owner" fully withdrawable almost immediately. vestDuration is public and on-chain, so this is transparent rather than hidden, but nothing in the contract enforces any minimum lock horizon — any community relying on this contract as a liquidity-lock guarantee must manually inspect the parameter per-instance.

Recommendation: Consider an owner-configurable but factory-enforced minimum vestDuration if the product's intent is to offer a credible locked-liquidity guarantee.

[8] Ineffective deadline: block.timestamp on mint()/decreaseLiquidity()

Severity: Low
Origin: [both] — Phase 1 (General-2/AMM-2), Phase 2 lead (agents 3, 5, 7, 8)
Location: _mintPosition() (line 192), _vest() (line 249)

Description: Both position-manager calls pass deadline: block.timestamp, which can never expire — a transaction sitting in the mempool executes whenever finally mined, however late. Slippage is still bounded by caller-supplied amount0Min/amount1Min, so this is not an independent fund-loss vector, but becomes material if a caller ever passes zero minimums (see Finding 9).

Recommendation: Accept a caller-supplied deadline parameter on lockUp, vest, claimAndVest and forward it instead of hardcoding block.timestamp.

[9] Owner-controlled zero slippage minimums expose lockUp/vest to sandwiching — self-harm only

Severity: Low
Origin: [both] — implicit in Phase 1's AMM review, explicit Phase 2 lead (agents 3, 8)
Location: lockUp(), vest(), claimAndVest()

Description: amount0Min/amount1Min are documented as "0 to skip." If the owner passes 0, mint/decreaseLiquidity are fully exposed to ordinary sandwiching (compounded by Finding 8's ineffective deadline). All recipients are the owner themselves, so this is self-exposure, not third-party theft — kept at Low/informational rather than elevated.

[10] _tickLower/_tickUpper unvalidated in lockUp()

Severity: Low
Origin: [phase1 only: AMM-3] — re-examined: confirmed, no phase-2 contradiction; low materiality since lockUp is onlyOwner and an invalid range simply reverts inside the pool's mint
Location: lockUp() / _mintPosition() — LiquidityVesting.sol:171-194

Description: No check that _tickLower < _tickUpper, that both fall within MIN_TICK/MAX_TICK, or that they align to the fee tier's tick spacing (200, for the 1% tier). Purely a UX/robustness gap — invalid input reverts safely with no fund risk.

Recommendation: Optionally validate ordering/bounds/spacing for a clearer revert reason.

[11] previewVest() uses manipulable spot price with no TWAP; diverges from what vest() actually returns

Severity: Low
Origin: [both] — Phase 1 (Oracle-1/AMM-1), Phase 2 lead (agents 1, 6, 7, 10 — agent 10 additionally found previewClaim reads stale, un-poked tokensOwed)
Location: previewVest() — LiquidityVesting.sol:309-318; previewClaim() — lines 289-294

Description: previewVest() reads the instantaneous spot price via slot0() (no TWAP, no staleness check, no Base-sequencer-uptime check) and excludes fees; the real vest() never touches spot price at all (amounts come from decreaseLiquidity/collect returns) and always includes fees. previewClaim() similarly reads tokensOwed fields that are only realized on a position "poke," so it can understate real claimable fees versus what claim() actually collects. Confirmed by full call-graph trace: no state-changing function consumes previewVest's or previewClaim's output — both are view-only, so there is no on-chain fund-loss path. The hardcoded Uniswap V3 factory address (0x33128a8fC17869897dcE68Ed026d694621f6FDfD) was independently confirmed correct for Base mainnet by three separate agents.

Recommendation: Document that these preview functions are estimates only and must never be used to derive amount0Min/amount1Min for the real vest()/claim() calls. If a trustworthy preview matters, price via TWAP (pool.observe()) and include the same fee-collection logic _vest() uses.

[12] vest() always collects trading fees regardless of the includeFees flag — event/NatSpec mismatch

Severity: Info
Origin: [both] — Phase 1 (General-3/AMM-5), Phase 2 lead (8 of 12 agents — the single strongest convergence in the whole audit)
Location: _vest() — LiquidityVesting.sol:252-266

Description: collect inside _vest() always uses type(uint128).max for both maxes, so plain vest() (includeFees = false) also sweeps all accrued fees to the owner. includeFees only toggles whether the Claimed event fires — it does not change any token movement, so vest() and claimAndVest() are behaviorally identical on-chain. No fund-loss impact (funds still go to the rightful owner either way), but off-chain accounting or indexers keyed on Vested vs Claimed will misattribute fee income as vested principal or vice versa.

Recommendation: Clarify NatSpec, or emit Claimed unconditionally so events reflect actual token flow.

[13] Trading fees are not subject to the vesting schedule — only principal liquidity is locked

Severity: Info
Origin: [phase2 only: agent 9] — design observation, not a bug
Location: claim() — LiquidityVesting.sol:213-220

Description: claim() lets the owner pull 100% of accrued trading fees at any time during the lock, entirely unrestricted by vestDuration. If the product's intended guarantee to a token community is "liquidity AND its earnings are locked," this deviates from that; if the intent is only to lock principal (fees are a separate reward stream), this is expected behavior. Flagged for completeness — design intent could not be confirmed from source alone.

[14] Constructor performs no token0 < token1 ordering validation

Severity: Info
Origin: [both] — Phase 1 (General-4), Phase 2 lead (agent 8)
Location: LiquidityVesting constructor — line 157; LiquidityVestingFactory.sol:19

Description: The factory always supplies token0 = WETH (0x4200...0006) < token1 = CLAWD (0x9f86...6b07), the correct Uniswap ordering, so all 7 live-deployed instances are unaffected. LiquidityVesting's own constructor performs no ordering check, so a hypothetical direct (non-factory) deployment with reversed tokens would construct successfully and only fail later, at lockUp()'s mint.

Recommendation: Optionally add require(_token0 < _token1) for direct-deployment safety.

[15] Owner is a single point of control over all fund-moving functions — inherent, not a defect

Severity: Info
Origin: [both] — Phase 1 (Access-4), Phase 2 general agreement (boundary, access-control agents)
Location: sweep(), lockUp(), claim(), vest()

Description: The owner is also the sole beneficiary/depositor — there is no third-party user whose funds this contract custodies on their behalf. sweep() correctly cannot pull token0/token1 while locked or touch the position manager address; renounceOwnership is disabled so the contract cannot be bricked into an unowned state. Compromised-owner risk (a stolen owner key could sweep non-locked balances and redirect future vests) is the standard single-key exposure inherent to this design — mitigable via a multisig owner, no code change required.

[16] ERC777/callback-hook reentrancy surface exists but is not exploitable

Severity: Info
Origin: [both] — Phase 1 (ERC20-4), Phase 2 (near-universal CEI confirmation across agents)
Location: _vest() — LiquidityVesting.sol:237-268

Description: If CLAWD has transfer hooks, the final collect() to owner() mid-_vest() execution is a reentrancy surface. Not exploitable: all mutating functions are onlyOwner (any reentrancy only affects the beneficiary's own funds), and checks-effects-interactions holds (vestedLiquidity += toLiquidate is committed before the external calls), so a reentrant vest() recomputes toLiquidate == 0 and reverts with "Nothing to vest".

[17] Inlined FullMath.mulDiv/TickMath libraries are faithful, correct copies of canonical Uniswap V3

Severity: Info
Origin: [phase1 only: Asm-1/Asm-2] — dedicated assembly-focused review; no phase-2 contradiction (phase-2's math-precision agent independently verified the surrounding vesting arithmetic is sound but did not do a line-by-line canonical diff of these libraries)
Location: FullMath.mulDiv() (lines 82-108), TickMath.getSqrtRatioAtTick() (lines 48-77)

Description: The overflow guard (require(denominator > prod1)) is present and correct, all 20 TickMath magic constants match canonical Uniswap V3 exactly, and both libraries are memory-safe. They are reachable only from the view function previewVest(), so even a hypothetical defect here could not affect locked funds.

[18] Division-before-multiplication in vesting percentage computation — self-correcting, not exploitable

Severity: Low
Origin: [both] — Phase 1 (Math-1), Phase 2 independent numeric verification (agent 1: math-precision) confirming no drift/underflow risk
Location: _vest() (lines 239-240), vestedPercent() (285), previewVest() (305)

Description: vestedPct = elapsed * 1e18 / vestDuration then totalVestedLiq = uint128(vestedPct * initialLiquidity / 1e18) truncates the ratio before rescaling, rather than computing elapsed * initialLiquidity / vestDuration directly. The 1e18 scaling bounds relative error to ~1e-18; the terminal branch (elapsed >= vestDuration ⇒ vestedPct = 1e18) recomputes totalVestedLiq = initialLiquidity exactly, so any rounding fully reconciles at completion — independently confirmed via numeric trace by both phases, no drift or underflow occurs.

Recommendation:

uint128 totalVestedLiq = elapsed >= vestDuration
    ? initialLiquidity
    : uint128(uint256(initialLiquidity) * elapsed / vestDuration);

The standout result of running both phases is Finding 1 — a real, low-cost, third-party griefing attack (permissionless increaseLiquidity() bricking the unconditional final burn()) that the checklist-driven Phase 1 pass did not surface, but which a single blind Phase 2 attacker agent (flow-gap specialty) found and which this synthesis independently re-verified against the deployed source.
