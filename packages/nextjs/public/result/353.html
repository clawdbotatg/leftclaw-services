Security Audit Report — VKPFactory

Target: 0x174E29E6FAdD3096387030429Eb4677eA569e625 (Base, chain 8453)
Client focus areas: initialization access control on freshly created VKPs, CREATE2 salt collisions if used, and reentrancy on deploy hooks

⚠️ Methodology note — source code unavailable

As with the related VKPSessionKeyManager audited in this same queue (job 351), this contract's source is not verified on Sourcify or BaseScan, and no Etherscan/BaseScan API key was available in this environment to check further. This audit was performed via bytecode-level reverse engineering: selector recovery via public 4byte/OpenChain signature databases, evmole static analysis for argument types/state-mutability/storage layout, and manual disassembly of every function — including the child contract's full creation bytecode, which is embedded directly inside this factory's own runtime code and was extracted and separately disassembled. No live on-chain calls were needed for this job since the factory is small enough (7 functions) to trace exhaustively.

Reconstructed model: A minimal factory with 7 functions. createVault(uint256,uint256,uint256,uint256) (selector 0xcb0354f0) is the only state-changing function; it deploys a new "VKP" child contract via plain CREATE (using an embedded ~4.2KB init-code template with the caller-supplied parameters and the caller's own address appended as constructor arguments), records the new address in a per-deployer array (storage slot 1) and a global array (tracked via counter at slot 0, with allVaults(uint256) reading elements from a separate hardcoded/non-standard base storage slot rather than the array's own Solidity-derived slot), and emits a creation event. The remaining 6 functions are all view/pure getters (totalVaults()/vaultCount() — apparent aliases sharing one code path, allVaults(uint256), two variants of a per-deployer vault lookup, and identityRegistry(), which returns the same hardcoded identity-registry address 0xa7BD20bf5De63df949cA5Be2F20835978eCba81A seen in the related VKPSessionKeyManager contract).

Findings Summary

None of the three client-hinted risk areas produced an exploitable finding. This is a genuine "clean" result, not an inability to analyze — the reasoning for each is below, along with two minor informational observations.

# Severity Title
1 Info Initialization is atomic and safe — no front-running window
2 Info CREATE2 is not used — no salt-collision surface exists
3 Info No external call occurs during deployment except a read-only STATICCALL — no reentrancy vector on deploy
4 Info Global vault-index array uses a non-standard, hardcoded base storage slot rather than Solidity's normal dynamic-array slot derivation
5 Info Redundant length tracking (separate counter alongside an array whose own .length already provides the count)

[1] Initialization access control — atomic, safe

Severity: Info (positive finding)

createVault builds the new VKP's full constructor argument list — msg.sender (the caller, hardcoded via the CALLER opcode, not taken from calldata), the shared identityRegistry address (a hardcoded constant), and the caller's 4 supplied uint256 parameters — and passes all of this atomically as part of the single CREATE call. The owner is fixed to the actual deployer within the same transaction that creates the contract; there is no separate initialize() step and therefore no window in which a third party could call an initializer first and seize ownership/control of a freshly deployed VKP. This directly and positively addresses the client's stated concern.

Additionally, the extracted child init-code was disassembled independently and confirmed to make its own STATICCALL to the identity registry very early in its constructor (before any state-changing logic), consistent with the VKP performing its own owner/identity validation at construction time as a second layer of defense.

[2] CREATE2 is not used

Severity: Info (not applicable)

The factory's only deployment opcode is plain CREATE, not CREATE2 — confirmed directly in the disassembly (no CREATE2 opcode appears anywhere in the contract). Deployed VKP addresses are therefore determined by the factory contract's account nonce, not by any caller-supplied salt, so the "salt collision" risk the client asked about does not apply to this implementation. (A minor design trade-off, not a security issue: this also means a deployer cannot predict their new VKP's address in advance of the transaction confirming.)

[3] No reentrancy vector on deploy — no state-changing external call occurs

Severity: Info (positive finding)

createVault performs its CREATE call, then only does storage bookkeeping (appending the new address to two arrays and incrementing a counter) and emits an event — it makes no CALL/DELEGATECALL/STATICCALL to the newly created contract afterward ("no deploy hook" exists in this function to reenter through). The one external interaction that happens during deployment is the child's own constructor issuing a STATICCALL to the identity registry — and STATICCALL is read-only by EVM design (it disallows SSTORE and any further state-changing sub-calls for the remainder of that call's execution context), so even a fully malicious identity-registry implementation could not use this call to reenter and corrupt either the factory's or the new VKP's state. No exploitable reentrancy path was found on the deployment path.

[4] Non-standard storage layout for the global vault-index array

Severity: Info
Location: allVaults(uint256) (selector 0x9094a91e)

Description: The global vault list's length is tracked at ordinary sequential storage slot 2, but its elements are read from a hardcoded, keccak-looking constant base slot (0x405787fa12a823e0f2b7631cc41b3ba8828b3321ca811111fa75cd3aa3bb5ace) plus the index — not from Solidity's standard keccak256(slot) dynamic-array element derivation. This is consistent with the array being manipulated via inline assembly rather than a plain Solidity address[] public allVaults; declaration. This is not a bug on its own (the reads and writes observed are internally consistent), but it is unusual enough, and separated enough from the length counter, that it increases the risk of a future code change accidentally writing to the wrong base and desynchronizing the length from the actual stored elements. Recommend a source-level review confirm this is deliberate (e.g., a custom-packed layout for gas savings) and add a test asserting allVaults(i) for every i < totalVaults() returns a non-zero, correct address after multiple deployments from different callers.

[5] Redundant counter alongside array length

Severity: Info

totalVaults()/vaultCount() reads a dedicated counter at slot 0, which is incremented separately from the global array's own length (tracked at slot 2). Since the array's length already serves this purpose, this is redundant state that costs extra gas per deployment and creates a (currently consistent, but unnecessary) second value that could theoretically desync from the array length if a future code change updates one without the other. No functional impact observed at the current bytecode; noted for completeness.

Caveats

  • This audit is bytecode-derived (no verified source). A source-level review is recommended to confirm the above with certainty, particularly Finding 4's storage layout.
  • The full VKP child contract (extracted from the embedded init-code template) was disassembled only far enough to confirm its constructor's external-call behavior; a full audit of the child VKP contract's own runtime logic is a separate scope (not requested for this job) and should be requested separately if desired.
