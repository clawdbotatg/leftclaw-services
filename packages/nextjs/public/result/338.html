Security Audit Report — Vaultfire BeliefAttestationVerifier (dev/placeholder version)

Target: BeliefAttestationVerifier.sol (contract BeliefAttestationVerifier) + IStarkVerifier.sol (interface)
Address: 0x32211773C8266774A704aeD471f8eF073f34bA79 on Base (chain 8453)
Source verification: Sourcify match (creation + runtime), compiled with solc 0.8.25+commit.b61c2a91, viaIR: true, evmVersion: cancun, verified 2026-06-27
Lines of code: 189 (main contract) + 26 (interface)
Client brief: "Earlier belief attestation verifier. Focus on: any missing timelock on parameter updates that the production version added, replay of proofs, and access control on admin functions."

Methodology

Two independent audit passes, run blind to each other, then reconciled:

  • Phase 1 — breadth (ethskills checklists): 5 domain checklists applied by parallel sonnet sub-agents — evm-audit-general, evm-audit-precision-math, evm-audit-access-control, evm-audit-governance, evm-audit-signatures (chosen for relevance: proof/replay concerns route to signatures; timelock concerns route to governance; the client explicitly asked about access control and timelocks).
  • Phase 2 — depth (pashov attacker-mindset methodology): 12 parallel sonnet attack agents (9 single-specialty + 3 cross-lens gap-hunters), each reading only the raw source with no visibility into phase 1's findings.
  • Phase 3 — reconciliation: cross-phase dedup, hybrid re-read of phase-unique items against source.

Reconciliation summary: 11 unique (function, bug-class) items raised across both phases, 11 covered in this unified report. 6 items corroborated by both phases ([both]) — including the top finding, independently surfaced by all 5 phase-1 agents in some form and by 12 of 12 phase-2 attack agents, the strongest possible convergence signal available from this methodology. 3 items phase-1-only (informational "not applicable" observations answering the client's explicit questions). 2 items phase-2-only (new, both speculative/out-of-scope-contingent, confirmed via hybrid re-read as reasonable but unverifiable without sibling contracts not included in this job's scope).

Key context (established identically by every one of the 17 total sub-agents across both phases)

This contract is a self-documented, non-functional placeholder. Its own NatSpec header states in a bordered warning box: "DEVELOPMENT-MODE VERIFIER — DO NOT DEPLOY TO PRODUCTION." It has:

  • Zero mutable state. PROOF_SYSTEM_ID, PUBLIC_INPUTS_COUNT, MIN_BELIEF_THRESHOLD, MAX_EPOCH are all Solidity constants baked into bytecode — there is no constructor, no setter, and no owner/admin of any kind.
  • A core verification function that unconditionally reverts. _verifyStarkProof() (lines 153-170) discards all five of its parameters and executes revert("ZK verification not implemented - use ProductionBeliefAttestationVerifier") on every call, regardless of input. verifyProof() can therefore never return true or false — every call either reverts on an early require or reverts here.

Because of this, the client's two specific questions — "missing timelock on parameter updates" and "access control on admin functions" — do not apply to this contract: there are no parameters to update and no admin functions to protect (see I-1, I-2 below). The client's third question — "replay of proofs" — is also currently moot, since nothing can ever be successfully verified once, so nothing can be replayed (see I-3). This is a materially different risk profile than the separate, out-of-scope ProductionBeliefAttestationVerifier, which is presumably where these three questions become load-bearing.

The substantive risk in this contract is not what it does today (nothing) but what its own documentation claims about itself, which does not match the code — see H-1.

Findings

[H-1] NatSpec header claims a chain-ID deployment guard and "accept-any-proof" placeholder behavior that do not exist anywhere in the code

Severity: High
Origin: [both] — phase 1 (general, access-control, governance — 3 of 5 agents) + phase 2 (12 of 12 attack agents, unanimous)
Location: Header NatSpec (lines 9-19) vs. _verifyStarkProof() (lines 153-170)

Description: The header box explicitly claims: "This contract contains a PLACEHOLDER proof verifier that accepts ANY non-empty proof ≥ 32 bytes. It is restricted to Hardhat/local chains (ID 31337 / 1337) via multiple guards." Neither claim is implemented. A full-text search of the contract for block.chainid, 31337, or 1337 (outside the comment itself) returns zero matches — and _verifyStarkProof is declared pure, which is structural proof no such check can exist without a signature change (a pure function cannot read block.chainid). There is also no "accept any proof ≥32 bytes" logic anywhere — the function never inspects proofBytes.length at all before its unconditional revert. The documented safety model is entirely fictional; the contract is currently safe only by the accident of failing closed, not because of any implemented guard.

Proof of Concept: Confirmed independently by all 17 sub-agents across both audit phases via direct source inspection. Failure mode: a future maintainer reads the header, reasonably believes chain-ID guards already protect this contract, and "fixes" _verifyStarkProof to match its own documented behavior (accept any proof ≥32 bytes) — believing it's already gated to devnets. Deploying that change to the current mainnet address would let any caller submit a fabricated belief attestation for any beliefHash/proverAddress with zero real proof checking and no chain restriction to stop it.

Recommendation: Either implement the guard the comment claims:

-    function _verifyStarkProof(
+    function _verifyStarkProof(
         bytes calldata proofBytes,
         bytes32 beliefHash,
         address proverAddress,
         uint256 epoch,
         uint256 moduleID
-    ) internal pure returns (bool) {
+    ) internal view returns (bool) {
+        require(
+            block.chainid == 31337 || block.chainid == 1337,
+            "BeliefAttestationVerifier: dev-only, wrong chain"
+        );
         ...

or — since this contract is explicitly a throwaway placeholder — strip the misleading claims from the NatSpec entirely and state plainly that the only current protection is the unconditional revert.

[M-1] DevVerifierUsed event — the one detective/monitoring control the docs describe — is declared but never emitted

Severity: Medium
Origin: [both] — phase 1 (general, governance) + phase 2 (4+ of 12 agents)
Location: Event declaration (lines 74-82); no emit site anywhere in the contract

Description: NatSpec states this event should fire "every time the dev verifier is invoked" and that "monitoring tools SHOULD alert" on its presence on any non-devnet chain as "a critical misconfiguration." Confirmed by full-text search across both audit phases: the event name appears only in its declaration and NatSpec, never in an emit statement. Combined with H-1 (no chain-ID guard), the one described safety net for detecting "wrong verifier deployed to production" does not function at all — it exists only in comments.

Recommendation: Either wire up the event (emit at function entry, before any revert-prone logic, since reverts roll back logs) or remove the misleading NatSpec claim.

[M-2] Deployed verifier unconditionally reverts on every call — full, permanent failure of the belief-attestation flow at this live mainnet address

Severity: Medium
Origin: [both] — phase 1 (general) explicit finding; phase 2 implicitly corroborated by all 12 agents' independent confirmation that every execution path terminates in this revert
Location: _verifyStarkProof() (153-170), reached via verifyProof() (102-139)

Description: _verifyStarkProof discards all five parameters and unconditionally revert()s. verifyProof() can therefore never return true (nor false — see L-3), and the ProofVerified event (67-72) is unreachable dead code. Flagged at Medium rather than High because this is self-documented, known, and intentional given the "DO NOT DEPLOY TO PRODUCTION" labeling and the client's own framing of this as the "earlier" verifier — but still worth recording precisely, since any live integration currently pointed at this address on Base mainnet gets a hard revert on every attempt.

Recommendation: Confirm no production-facing caller (e.g. the NatSpec-referenced DilithiumAttestor) is currently configured to point at this address; if any are, redirect them to ProductionBeliefAttestationVerifier.

[L-1] Downstream caller could turn a revert-only failure mode into a silent authorization bypass

Severity: Low
Origin: [phase2] — 2 of 12 attack agents (trust-gap, flow-gap specialties) independently converged; new finding not surfaced by phase 1
Location: verifyProof() — interaction with its (out-of-scope) caller

Description: The NatSpec (line 87) names DilithiumAttestor as "the main verification function called by DilithiumAttestor" — but that contract's source is not included in this job's scope, so this is necessarily speculative. If that caller wraps verifyProof() in a low-level .call() or a try/catch and treats a failed/reverted call as "unverified, fall through to a permissive default path" rather than a hard stop, a permanently-reverting verifier at this address would produce a silent authorization bypass rather than a pure availability/DoS problem — the opposite of the fail-closed behavior this contract otherwise exhibits in isolation.

Proof of Concept: Not verifiable from this contract's source alone — the risk is entirely in how the caller handles a revert. Flagged for a future engagement that includes DilithiumAttestor in scope.

Recommendation: When auditing DilithiumAttestor (or any caller of this interface), specifically verify it treats every verifyProof() outcome other than a clean true return as a hard failure, with no low-level-call/try-catch path that silently defaults to a permissive branch.

[L-2] _verifyStarkProof comment references a testMode variable that does not exist anywhere in the contract

Severity: Low
Origin: [both] — phase 1 (general, access-control) + phase 2 (several agents' doc-mismatch leads specifically cite this)
Location: line 168

Description: Comment reads "To enable for testing, deploy with testMode = true" — no such state variable, constructor parameter, or immutable exists anywhere in the file, and the function is pure (cannot read state regardless, same structural point as H-1). Dangling reference to unimplemented functionality; a future maintainer might add an unguarded testMode toggle to satisfy this comment, which — if not access-controlled and chain-gated — would itself become a Critical bypass.

Recommendation: Remove the stale comment, or implement a genuine immutable testMode set only in the constructor, combined with the chain-ID guard from H-1.

[L-3] verifyProof() can never return false — only revert — diverging from the IStarkVerifier interface's documented boolean contract

Severity: Low
Origin: [both] — phase 1 (signatures) + phase 2 (3+ of 12 agents)
Location: verifyProof() (132-138), _verifyStarkProof() (153-170)

Description: IStarkVerifier's NatSpec implies validity is reported via boolean return (@return True if proof is valid...), suggesting callers might branch on a false return for "invalid proof" handling. That path is unreachable here — _verifyStarkProof's only exit is an unconditional revert, so verifyProof always either reverts on an early require or reverts inside _verifyStarkProof; it never returns a value at all. Compounds L-1: an integrator expecting "invalid proof → false" rather than "invalid proof → revert" would be surprised by the actual behavior, and any error-handling logic built around the boolean contract needs re-examination.

Recommendation: Advisory for the production replacement — ensure genuine true/false branches exist for "proof rejected" vs. reverting only on malformed/out-of-gas conditions.

[L-4] Unchecked uint256 → uint160 downcast when deriving proverAddress from public inputs

Severity: Low
Origin: [both] — phase 1 (general, precision-math) + phase 2 (5+ of 12 agents, one with a fully worked truncation proof)
Location: verifyProof() line 111 — address proverAddress = address(uint160(publicInputs[1]));

Description: publicInputs[1] is a caller-supplied uint256; casting to address via uint160(...) truncates silently for values ≥ 2^160 (explicit downcasts don't revert in Solidity). No preceding range check exists — the only downstream guard, require(proverAddress != address(0)) (line 117), only rejects the exact case where the truncated result is zero; it does not detect the general truncation case. Concretely: publicInputs[1] = k·2^160 + realAddress truncates to realAddress and passes validation with no indication the raw public input didn't match what a real STARK proof would have committed to. Currently unreachable/inert since _verifyStarkProof always reverts before this value is used for anything security-relevant (M-2) — but a latent bug if the same extraction pattern is copied into ProductionBeliefAttestationVerifier without a range check, where two distinct oversized field elements differing only in bits above 160 would silently alias to the same on-chain address.

Recommendation:

+        require(publicInputs[1] <= type(uint160).max, "proverAddress overflow");
         address proverAddress = address(uint160(publicInputs[1]));

or use SafeCast.toUint160. Carry the fix into the production verifier.

[I-1] No missing-timelock finding — contract has zero mutable parameters

Severity: Info
Origin: [phase1: general, governance]
Location: whole contract

Description: Directly answering the client's first question: this contract has no parameters that can be updated at all. PROOF_SYSTEM_ID, PUBLIC_INPUTS_COUNT, MIN_BELIEF_THRESHOLD, and MAX_EPOCH are all compile-time constants with no setter, no constructor argument, and no owner/admin role capable of changing anything post-deployment. "Missing timelock on parameter updates" does not apply here because there is nothing to timelock.

Recommendation: Re-check this question when auditing ProductionBeliefAttestationVerifier if it introduces mutable parameters (a configurable threshold, a verifying key, etc.) — that contract, not this one, is where a timelock analysis is load-bearing.

[I-2] No access-control finding — no admin or privileged functions exist to protect

Severity: Info
Origin: [phase1: general, access-control]
Location: whole contract

Description: Directly answering the client's second question: this contract has no admin functions. verifyProof() and the three view getters are intentionally unrestricted — correct design for a public proof-verification entry point, since anyone should be able to submit a proof for verification. There is no owner, no Ownable/AccessControl inheritance, and no function that mutates any state (there is no mutable state to mutate).

Recommendation: No action needed for this contract. If the production version introduces admin-gated functions (e.g. to rotate a verifying key), access control on those functions should be reviewed in that engagement.

[I-3] No on-chain replay protection for proof submissions — currently moot, worth tracking for the production version

Severity: Info
Origin: [phase1: general, signatures]
Location: verifyProof() (102-139)

Description: Directly answering the client's third question: no nonce or used-proof/used-beliefHash registry exists. This is currently moot since nothing can ever verify successfully (M-2), and the conceptual "circuit logic" described in NatSpec comments says nothing about proof uniqueness either. Flag for the production verifier to add explicit replay protection (e.g. mapping(bytes32 => bool) usedBeliefHash) independent of the ZK circuit's own soundness guarantees, since replay protection is not part of even the conceptual design as documented here.

Recommendation: When auditing ProductionBeliefAttestationVerifier, confirm replay protection exists either in that verifier or, if by design, in the calling DilithiumAttestor — this dev placeholder provides none, which should not be mistaken for an oversight specific to production.

[I-4] Cross-domain width mismatch between the on-chain uint32 epoch bound and an unspecified off-chain circuit field width

Severity: Info
Origin: [phase2] — 1 of 12 attack agents (flow-gap); highly speculative
Location: verifyProof(), MAX_EPOCH = type(uint32).max

Description: NatSpec asserts that the on-chain epoch <= MAX_EPOCH check (bounding epoch to 32 bits) constitutes the "epoch validity" check the off-chain RISC0 guest program relies on (referenced only as /risc0-guest/src/main.rs, not present in this repository or job scope). Whether the guest program's own field-width assumptions for epoch actually match this 32-bit bound cannot be verified without that source. Included for completeness only — this is unverifiable from the files in scope and should not be treated as a confirmed defect.

Recommendation: When the off-chain guest program and ProductionBeliefAttestationVerifier are both in scope for a future engagement, confirm the on-chain epoch bound matches whatever width the circuit actually constrains.
