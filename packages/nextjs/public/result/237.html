Multisig.sol — Security Audit Report

Audit Date: 2026-06-01
Methodology: EthSkills (8 domains) + Pashov (8 agents)
Contract: packages/foundry/contracts/Multisig.sol
Repository: https://github.com/clawdbotatg/slop-computer-wallet

Executive Summary

Multisig.sol is an M-of-N upgradeable (proxy-deployed) multisig wallet that accepts EOA, passkey (WebAuthn/secp256r1), and ERC-1271 contract signers, and itself implements ERC-1271 so it can act as a signer on other contracts. Execution is gated by a sorted-signature threshold check with chainid/address/nonce/deadline-bound digests, and admin actions are self-governed via threshold-approved self-calls. The contract is well-hardened — prior audit fixes (M-1, M-2, L-1, L-3, I-3) are visible — and no Critical or High severity issues with concrete third-party exploit paths were confirmed. The principal risks are liveness/bricking from required contract signers losing code, an off-chain replay surface on the passkey ERC-1271 path, a state-corruption bug in credentialId reverse-lookups, and an unprotected-initialization front-running risk dependent on deployment hygiene.

Finding counts: Critical 0, High 0, Medium 3, Low 6, Info 3.

Findings

[F-1] Required ERC-1271 contract signer that loses code permanently bricks the multisig

Severity: Medium
Category: evm-audit-governance / first-principles [confirmed by both passes]
Location: _addContractSigner(), _isValidContractSig(), removeSigner()
Description: _addContractSigner enforces signer.code.length != 0 only at registration time — a point-in-time snapshot, not a maintained invariant. A registered contract signer can later lose its code (selfdestruct in the same-tx creation pattern still permitted post-EIP-6780, or a CREATE2 address that is destroyed and not redeployed). Once codeless, _isValidContractSig always hits the catch and returns false, so that signer can never contribute toward threshold again. If the configuration makes that signer necessary to reach threshold (e.g. threshold == signerCount, or enough contract signers go codeless that usable signers fall below threshold), the wallet is permanently bricked: removeSigner and changeThreshold are themselves onlySelf and can only be reached through an execTransaction that now cannot meet threshold — a circular dependency. Funds are frozen with no recovery path.
Proof of Concept:

  1. 2-of-2 multisig: signer A (EOA), signer B (contract, had code at registration).
  2. B selfdestructs / becomes codeless.
  3. _isValidContractSig(B,...) now returns false; only A can ever produce a valid signature → max 1 valid signature < threshold 2.
  4. removeSigner(B) and changeThreshold(1) both require reaching threshold 2 via execTransaction → impossible. Wallet permanently bricked.
    Recommendation: Ensure EOA/passkey signers alone can always meet threshold so the wallet never depends on a contract signer's liveness; document this operational requirement. Alternatively, pin extcodehash at registration and re-check it in _isValidContractSig (rejecting changed/absent code explicitly), and/or add a recovery path that lets remaining live signers re-threshold when a contract signer has demonstrably lost its code.

[F-2] Passkey signatures are replayable verbatim between the ERC-1271 isValidSignature path and execTransaction

Severity: Medium
Category: evm-audit-signatures / economic-security [confirmed by both passes]
Location: Passkey branch of _verifySignatures() and isValidSignature()
Description: For EOA signers the contract deliberately separates the two entry points — _verifySignatures (exec path) recovers over MessageHashUtils.toEthSignedMessageHash(hash) (personal_sign prefix) while isValidSignature recovers over the raw hash (M-2). For passkeys this asymmetry does not exist: both paths build challenge = abi.encodePacked(hash) and call WebAuthn.verify(challenge, auth, qx, qy) with no path/domain discriminator. A WebAuthn auth blob that validates for a given hash on the off-chain ERC-1271 path is byte-for-byte valid on execTransaction whenever getExecHash(...) == hash. The only thing preventing weaponization is that getExecHash binds chainid, address(this), and nonce, so an attacker submitting an arbitrary hash to isValidSignature cannot freely make it equal a pending exec digest. The residual risk: a malicious dapp that registers this multisig as an ERC-1271 signer can prompt a passkey member to "sign" a 32-byte value crafted to equal a future getExecHash, then replay that assertion as an execution authorization.
Proof of Concept:

  1. Attacker dapp uses the multisig as an ERC-1271 signer and asks a passkey member to approve hash = H, where the attacker has chosen H == keccak256(abi.encode(chainid, multisig, currentNonce, deadline, target, value, keccak256(data))).
  2. The member's wallet produces a WebAuthn assertion over H.
  3. The attacker submits execTransaction(target, value, data, deadline, sigs) with that assertion; getExecHash recomputes H, the passkey branch verifies the identical challenge, and the call executes.
    Requires the attacker to control/predict target/value/data/nonce/deadline and to obtain a member signature over the exact resulting hash — contrived but not blocked by any domain separation.
    Recommendation: Domain-separate the passkey challenge per path (e.g. prefix the execution-path challenge with a constant tag such as keccak256("EXEC"), or include a path discriminator inside the signed hash), mirroring the EOA prefix asymmetry, so an off-chain passkey approval can never coincide with an execution digest.

[F-3] Reused credentialId hash corrupts passkey reverse-lookup, bricking login for a still-active signer

Severity: Medium
Category: evm-audit-invariant / vector-scan [confirmed by both passes]
Location: _addSigner(), removeSigner(), addPasskeySigner()
Description: _addSigner writes the credentialId mappings without checking whether the hash is already claimed:

if (credId != bytes32(0)) {
    credentialIdToAddress[credId] = signer;
    credentialIdOf[signer] = credId;
}

If two passkey signers are registered with the same credId, the second registration silently overwrites credentialIdToAddress[credId] to point at the new signer while the first signer's credentialIdOf still equals credId. When the second signer is later removed, removeSigner deletes credentialIdToAddress[credId] (based on the second signer's credentialIdOf), leaving the first — still active — signer unreachable via login lookup. The invariant credentialIdToAddress[credentialIdOf[S]] == S for every active passkey signer is broken. No fund loss, but the off-chain passkey login flow for an active signer is permanently broken until re-registered.
Proof of Concept:

  1. addPasskeySigner(qx1, qy1, X) → A active; credentialIdToAddress[X]=A, credentialIdOf[A]=X.
  2. addPasskeySigner(qx2, qy2, X) → B active; credentialIdToAddress[X]=B (overwritten), credentialIdOf[B]=X, credentialIdOf[A] still X.
  3. removeSigner(B) → reads credentialIdOf[B]=X, deletes credentialIdToAddress[X] and credentialIdOf[B].
  4. A is still an active signer, but getPasskeyByCredentialId(X) returns (0,0,0). A's login lookup is bricked.
    Recommendation: Reject duplicate credentialId hashes in _addSigner:
if (credId != bytes32(0)) {
    if (credentialIdToAddress[credId] != address(0)) revert InvalidSigner();
    credentialIdToAddress[credId] = signer;
    credentialIdOf[signer] = credId;
}

[F-4] Unprotected initialize is front-runnable if deployment is not atomic

Severity: Low
Category: evm-audit-proxies / access-control [confirmed by both passes]
Location: initialize()
Description: initialize is external initializer with no authorization over who calls it first. The implementation is safe (_disableInitializers() in the constructor), but each fresh proxy/clone is claimable by whoever calls initialize first. If a deployment flow creates the proxy in one transaction and initializes in a separate, later transaction, an attacker can front-run with initialize([attacker], [], [], [], [], 1) and become the sole signer (threshold 1), taking full control of the wallet and any funds sent to it.
Proof of Concept:

  1. Deployer broadcasts proxy-creation tx without initialization.
  2. Attacker observes the new proxy and calls initialize([attacker], [], [], [], [], 1) — passes all checks (1 <= threshold <= total).
  3. Attacker is the only signer with threshold 1 and drains any assets.
    No exploit if deploy + initialize occur atomically (factory, ERC-1967 constructor _data, or multicall).
    Recommendation: Deploy and initialize atomically via a factory (the repo's MultisigFactory was reviewed and binds the CREATE2 salt to msg.sender, which mitigates this when used). Document that direct proxy deployments must initialize in the same transaction.

[F-5] No EIP-712 typed data — execution signers blind-sign an opaque hash

Severity: Low
Category: evm-audit-signatures
Location: getExecHash(), getBatchExecHash(), EOA branch of _verifySignatures()
Description: The exec digest correctly binds block.chainid, address(this), nonce, and deadline (computed live, no caching), so there is no replay or fork-staleness vector. However, EOA signers sign personal_sign(getExecHash(...)) — an opaque 32-byte blob. Hardware/software wallets render this as an unreadable hash rather than human-readable typed data, so signers cannot see the target, value, or data they authorize, increasing blind-signing risk if a frontend is malicious. This is a UX/security best-practice gap, not an on-chain replay bug.
Proof of Concept: Not an on-chain exploit. A signer using a hardware wallet sees only a hash; a malicious frontend could present a different intended action than the hash encodes. A correct frontend is safe and the on-chain binding is sound.
Recommendation: Adopt EIP-712 typed structured data for Call/Call[] so wallets render the authorized target/value/data, retaining the existing chainid/address/nonce/deadline fields inside the typed struct + domain separator.

[F-6] ERC-1271 contract signer can be an upgradeable/CREATE2-substitutable contract that changes validation behavior post-registration

Severity: Low
Category: evm-audit-signatures / governance
Location: _addContractSigner(), _isValidContractSig()
Description: Registration only checks non-self and code.length != 0. A registered contract signer that is an upgradeable proxy (or a CREATE2 address destroyed and redeployed with different bytecode) can later change its isValidSignature to return the magic value for any hash, making that slot auto-approve unconditionally — or to revert, making it fail closed (see F-1). Validation is always re-run live (no caching, which is good), and the trust placed in a contract signer is equivalent to trust in an EOA key. This is a known trust assumption rather than a direct vulnerability: a single such slot still only counts as one signer toward threshold.
Proof of Concept: Register upgradeable proxy P as a contract signer. P is later upgraded so isValidSignature always returns 0x1626ba7e. P now satisfies its slot toward threshold for any execution that includes P in the sorted signatures. Equivalent to a compromised key; does not alone reach threshold unless P alone meets it.
Recommendation: Document that contract signers are trusted equivalently to EOAs and that upgradeable/metamorphic contract signers can change validation behavior. For higher assurance, restrict contract signers to non-upgradeable contracts or record and re-check extcodehash at verification time.

[F-7] Low-level call to a codeless target returns success, silently faking execution

Severity: Low
Category: evm-audit-assembly
Location: execTransaction(), execBatchTransaction()
Description: (bool ok, bytes memory ret) = target.call{ value: value }(data) returns ok = true with empty returndata when target has no code. If signers approve a data-bearing call to an address they believe is a contract (typo, not-yet-deployed CREATE2 target, or a self-destructed contract), the call "succeeds," nonce increments, and Executed is emitted, but the intended state change never occurred. Threshold-gated, so this is a silent-failure footgun rather than a third-party exploit; pure value transfers to EOAs are intentional.
Proof of Concept: Signers sign an exec for target = 0xDEAD... with data = transfer(...); the address has no code; the call returns ok=true, ret=""; _bubbleRevert is not invoked; nonce++; Executed emitted. Observers believe the transfer happened.
Recommendation: When data.length > 0, require code at the target:

if (data.length > 0 && target.code.length == 0) revert ExecutionFailed();

[F-8] Unbounded returndata copy enables return-bomb gas griefing

Severity: Low
Category: evm-audit-assembly / dos
Location: execTransaction(), execBatchTransaction(), _bubbleRevert()
Description: Both exec functions copy full returndata into bytes memory ret (and execBatchTransaction retains every call's returndata in results[i]), and _bubbleRevert copies arbitrary-length revert data. A malicious target can return megabytes to inflate memory-expansion gas, potentially OOG-ing a relayer's transaction. Because target/data are threshold-signed, this primarily grief a relayer for a call the signers already authorized; it is not a third-party theft vector.
Proof of Concept: Signers approve a batch including a target returning new bytes(1_000_000); a relayer submits the batch and pays quadratic memory gas or reverts OOG.
Recommendation: If full returndata is not needed by integrators, bound the copied size with assembly (returndatacopy of a capped length) and cap the data copied in _bubbleRevert.

[F-9] Mutual/cyclic ERC-1271 contract-signer graphs can exhaust gas during verification

Severity: Low
Category: evm-audit-assembly / vector-scan
Location: _addContractSigner(), _isValidContractSig()
Description: _addContractSigner blocks only direct self-reference (signer == address(this)), not cycles through other contracts. Multisig A can register B as a contract signer and B can register A; verifying a signature that relies on the contract slot triggers A.isValidSignature → B.isValidSignature → A.isValidSignature … until gas/depth is exhausted. The try/catch fails closed (the signature is treated invalid), so there is no false-accept or fund loss — the impact is wasted gas / inability to validate, in a configuration the signers chose.
Proof of Concept: A adds B as a contract signer; B adds A. Verifying A's contract-signer slot recurses into B, which recurses into A, until OOG; the catch returns false.
Recommendation: Document that contract-signer graphs must be acyclic and shallow. Optionally forward a bounded gas amount to isValidSignature and/or add a transient-storage recursion-depth guard.

[F-10] No minimum threshold floor allows a 1-of-N configuration

Severity: Low
Category: evm-audit-governance
Location: initialize(), changeThreshold()
Description: Both initialize and changeThreshold accept a threshold of 1. A 1-of-N "multisig" means any single signer or leaked key/passkey can move all funds and rewrite the entire signer set — a single point of failure. There is no on-chain enforcement of a sane minimum. This is a configuration-policy concern rather than a code bug.
Proof of Concept: Deploy with eoaSigners=[a,b,c], _threshold=1; any one of the three alone can execute arbitrary calls including draining assets. Same via changeThreshold(1) post-deploy.
Recommendation: Consider enforcing a documented floor (e.g. _threshold >= 2) or surface a warning in deployment tooling. If 1-of-N must be supported, document it as an explicit, intentional mode.

[F-11] ERC-1271 isValidSignature is a stateless, non-expiring approval oracle

Severity: Info
Category: evm-audit-signatures / governance [confirmed by both passes]
Location: isValidSignature(bytes32 hash, bytes memory signatures)
Description: isValidSignature validates an arbitrary 32-byte hash against the current signer set with no nonce, expiry, or domain separator of its own — standard ERC-1271 behavior where the consuming protocol owns the digest. The consequence integrators must understand: a collected Signature[] blob over a given hash is valid forever and reusable in any context that presents the same hash, and is invalidated only by rotating signers/threshold. There is no on-chain revocation of a previously approved message hash.
Proof of Concept: Not exploitable within Multisig itself; depends on the consuming protocol embedding its own replay protection.
Recommendation: Document that ERC-1271 consumers MUST supply properly domain-separated (EIP-712) digests including chainId and a unique nonce. Optionally add an onlySelf-settable "revoked hash" set so signers can invalidate a previously approved hash on-chain.

[F-12] Passkey-derived addresses share the 160-bit namespace with EOA/contract signers

Severity: Info
Category: evm-audit-access-control / math-precision [confirmed by both passes]
Location: getPasskeyAddress(), _addSigner()
Description: getPasskeyAddress = address(uint160(keccak256(abi.encodePacked(qx, qy)))) truncates to 160 bits, sharing the address space with EOA and contract signers. _addSigner rejects duplicates (AlreadySigner) and _verifySignatures enforces sig.sigType == info.kind and re-checks stored (qx, qy), so a collision cannot let one signer type impersonate another — it can only block registration of a second signer at a colliding address. Forcing a collision against a specific target address is ~2^80 (birthday) work and not practical; impersonation would additionally require passing WebAuthn against the stored coordinates.
Proof of Concept: Not exploitable for impersonation; worst case a ~2^80-effort collision denies registration of one intended signer slot (self-inflicted DoS of configuration).
Recommendation: No change required for security. Optionally namespace passkey addresses (e.g. set a high bit) so they cannot collide with real EOA/contract addresses, and document the shared keyspace.

[F-13] No storage gap / documented layout for an upgradeable contract

Severity: Info
Category: evm-audit-proxies
Location: Multisig storage layout (no __gap)
Description: The contract is proxy-deployed but declares no reserved __gap and no @custom:storage-location documentation for its own state (signerInfo, _signers, threshold, nonce, credentialIdToAddress, credentialIdOf). Initializable and ReentrancyGuardTransient use ERC-7201 namespaced / transient slots so they do not collide today, but a future upgrade that inserts a base contract with regular storage, or reorders/retypes the contract's own variables (including the packed SignerInfo struct), would corrupt live proxy state with no in-source guardrail.
Proof of Concept: Not exploitable as deployed. Failure mode: a V2 that inserts a base contract with a non-namespaced variable before Multisig's state shifts all slots, so signerInfo[signer].exists reads garbage and the wallet is bricked/hijackable.
Recommendation: Add a trailing uint256[50] private __gap; (or adopt ERC-7201 namespaced storage for the contract's own state), document the immutable layout, only append new variables at the end, never reorder the SignerInfo struct, and run @openzeppelin/upgrades storage-layout checks in CI on every upgrade.

Composite Attack Chains

  • F-10 (1-of-N) + F-4 (front-runnable init): A non-atomic deployment front-run with initialize([attacker], …, 1) yields immediate, single-key full control. Mitigated entirely by atomic deploy+init via the reviewed factory.
  • F-1 (contract-signer brick) + F-6 (upgradeable contract signer): An upgradeable/metamorphic contract signer can be flipped to always-revert after registration; if that slot is required to reach threshold, the wallet is permanently bricked with no recovery path. The mitigation is the same as F-1: ensure EOA/passkey signers alone meet threshold.
  • No chain produces direct third-party fund loss without operator misconfiguration or an already-leaked/solicited signer signature.

Scope and Methodology

Two independent audit passes were merged. The EthSkills pass ran eight domain reviewers (general, precision-math, signatures, governance, access-control, dos, proxies, assembly). The Pashov pass ran eight specialized agents (vector-scan over a 266-item catalogue, math-precision, access-control, economic-security, execution-trace, invariant, periphery, first-principles). Findings were deduplicated by root cause (contract + function + bug class), cross-confirmed findings were given higher confidence, and every candidate Critical/High was walked step-by-step against the source — none survived as Critical/High because each requires either operator misconfiguration, an already-leaked/solicited signature, or self-inflicted griefing. In scope: packages/foundry/contracts/Multisig.sol (inline source) and, by reference from the periphery pass, MultisigFactory.sol and OpenZeppelin Clones.sol (EIP-1167 bytecode parity and CREATE2 salt binding confirmed sound; OZ WebAuthn, ECDSA, MessageHashUtils reviewed as unmodified v5.6). No on-chain deployment, test suite, or off-chain signing tooling was in scope.
