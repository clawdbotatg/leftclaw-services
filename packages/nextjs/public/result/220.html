Executive Summary

BasenameRegistrar is a well-structured abstract contract with a clear purpose: let any smart contract inherit the ability to register and manage a Basename (name.base.eth) on Base. The ETH handling logic is sound — it correctly uses msg.value (not address(this).balance) to isolate per-call ETH from any treasury the inheriting contract holds, and the arithmetic is safe under Solidity 0.8.x checked math.

No critical or high severity findings were identified.

Both audit methodologies converged on the same three low-severity issues and identified the same informational leads. The findings are consistent across both passes with no contradictions.

Findings

[LOW-1] Excess ETH silently stranded if refund to msg.sender fails

Confirmed by: Both methodologies (EthSkills E-1, Pashov P-1) | Confidence: 85

Location: _registerBasename(), refund block

Description:
After controller.register completes successfully, _registerBasename attempts to return overpaid ETH:

(bool ok, ) = msg.sender.call{value: excess}("");
ok; // non-reverting — registration already succeeded

The return value ok is deliberately discarded. If msg.sender is a smart contract whose receive() reverts — for example, a multisig in a restricted state, a proxy with a non-payable fallback, or any contract that conditionally reverts on ETH receipt — the excess ETH is not returned to the caller. Because _registerBasename is internal and the abstract base defines no sweep or rescue function, this ETH may be permanently stranded in the inheriting contract unless the inheritor explicitly provides an ETH recovery path.

Proof of Concept:

  1. Authorized caller (e.g., onlyOwner) invokes registerBasename("myapp", 365 days) sending 0.01 ETH.
  2. Registration price is 0.001 ETH; excess = 0.009 ETH.
  3. controller.register succeeds; name is registered.
  4. msg.sender.call{value: 0.009 ether}("") is issued to the caller.
  5. If the caller is a contract with a reverting receive(), the call returns ok = false.
  6. ok is discarded; registration event is emitted.
  7. 0.009 ETH is stuck in the inheriting contract with no recovery mechanism from the abstract base.

Recommendation:
Emit an event on failed refund so it can be tracked and recovered off-chain, and document that inheritors must provide an ETH rescue function:

event RefundFailed(address indexed recipient, uint256 amount);

if (excess > 0) {
    (bool ok, ) = msg.sender.call{value: excess}("");
    if (!ok) emit RefundFailed(msg.sender, excess);
}

Also add to NatSpec: "Inheriting contracts SHOULD expose an owner-callable ETH withdrawal function to recover any stranded refunds."

[LOW-2] _setForwardResolution silently updates the wrong ENS node when passed a full name

Confirmed by: Both methodologies (EthSkills E-2, Pashov P-2) | Confidence: 82

Location: _setForwardResolution(), BasenameUtils.basenameNode() call

Description:
_setForwardResolution passes its name argument directly to BasenameUtils.basenameNode(), which treats the input as a bare label and computes:

basenameNode(name) = keccak256(BASE_ETH_NODE || keccak256(name))

When name = "myapp" this correctly produces the namehash of myapp.base.eth. When name = "myapp.base.eth" it produces the namehash of the nonexistent myapp.base.eth.base.eth — the wrong ENS node — with no error or revert.

In contrast, _setPrimaryBasename accepts both labels and full names via _endsWithBaseEth(). A developer who correctly uses _setPrimaryBasename("myapp.base.eth") and applies the same pattern to _setForwardResolution("myapp.base.eth") would set the forward resolver record for the wrong node, breaking forward resolution silently.

Proof of Concept:

  1. Developer registers myapp.base.eth successfully.
  2. Calls _setForwardResolution("myapp.base.eth") following the _setPrimaryBasename convention.
  3. basenameNode("myapp.base.eth") = keccak256(BASE_ETH_NODE, keccak256("myapp.base.eth")) = namehash of myapp.base.eth.base.eth.
  4. L2Resolver.setAddr(wrongNode, address(this)) is called — sets the addr record for the wrong name (or silently no-ops if unowned).
  5. ForwardResolutionSet("myapp.base.eth", address(this)) event is emitted, misleading monitors.
  6. myapp.base.eth → address(this) forward resolution never gets set; bidirectional resolution is broken.

Recommendation:
Mirror the input normalization from _setPrimaryBasename:

function _setForwardResolution(string memory name) internal {
    if (bytes(name).length == 0) revert EmptyName();
    // Accept both "myapp" and "myapp.base.eth" — normalize to bare label
    string memory label = _endsWithBaseEth(name)
        ? _stripBaseEthSuffix(name)  // new helper: removes last 9 bytes
        : name;
    bytes32 node = BasenameUtils.basenameNode(label);
    IL2Resolver(_getL2Resolver()).setAddr(node, address(this));
    emit ForwardResolutionSet(label, address(this));
}

Or add a prominent NatSpec @dev warning that name MUST be the bare label only.

[LOW-3] Constructor silently falls back to mainnet addresses when only some arguments are zero

Confirmed by: Both methodologies (EthSkills E-3, Pashov P-3) | Confidence: 78

Location: constructor()

Description:
The constructor uses an all-or-nothing check:

if (registrarController_ != address(0) &&
    reverseRegistrar_ != address(0) &&
    l2Resolver_ != address(0))
{
    _useCustomAddresses = true;
    ...
}

If a developer passes non-zero addresses for two parameters but address(0) for the third (e.g., accidentally forgets the testnet resolver), the entire condition evaluates to false. All three parameters are silently ignored and the mainnet constants are used. There is no revert, no event, and no way to detect this at runtime.

On testnet, this causes the contract to interact with Base mainnet contracts instead of testnet contracts, leading to confusing failures that may be misdiagnosed as network issues.

Proof of Concept:

constructor() BasenameRegistrar(
    0x49ae3cc2e3aa768b1e5654f5d3c6002144a59581,  // testnet RegistrarController
    0x876eF94ce0773052a2f81921E70FF25a5e76841f,  // testnet ReverseRegistrar
    address(0)  // accidentally omitted testnet L2Resolver
) {}
// Result: _useCustomAddresses = false, all calls go to Base mainnet

Recommendation:
Revert on partial configuration:

constructor(address registrarController_, address reverseRegistrar_, address l2Resolver_) {
    bool anySet = registrarController_ != address(0)
               || reverseRegistrar_   != address(0)
               || l2Resolver_         != address(0);
    bool allSet = registrarController_ != address(0)
               && reverseRegistrar_   != address(0)
               && l2Resolver_         != address(0);
    if (anySet && !allSet) revert("Pass all three addresses or none");
    if (allSet) {
        _useCustomAddresses = true;
        _customRegistrarController = registrarController_;
        _customReverseRegistrar    = reverseRegistrar_;
        _customL2Resolver          = l2Resolver_;
    }
}

[INFO-1] Reentrancy window in refund path — inheritor wrappers not warned

Confirmed by: Both methodologies (EthSkills E-4, Pashov P-4) | Confidence: 72

Location: _registerBasename() — msg.sender.call{value: excess}("")

Description:
After controller.register completes, a second external call is made to msg.sender for the refund. This creates a reentrancy window before _registerBasename returns. While the abstract contract itself has no exploitable state (the registration is already committed on-chain), inheriting contracts that update state after calling _registerBasename — without a nonReentrant guard — are exposed to reentrancy. The NatSpec example code does not include a reentrancy guard.

The CEI (Checks-Effects-Interactions) pattern is also violated: the BasenameRegistered event is emitted after the external call to msg.sender, meaning off-chain monitors may see events mid-reentry.

Recommendation:
Add to _registerBasename NatSpec:

/// @dev ⚠️ REENTRANCY: This function calls msg.sender (ETH refund) before returning.
///      Any public wrapper that updates state MUST use a nonReentrant modifier.

Move the event emit before the refund to restore CEI order:

+ emit BasenameRegistered(name, address(this), duration);
  uint256 excess = msg.value - totalPrice;
  if (excess > 0) {
      (bool ok, ) = msg.sender.call{value: excess}("");
      if (!ok) emit RefundFailed(msg.sender, excess);
  }
- emit BasenameRegistered(name, address(this), duration);

[INFO-2] Hardcoded Basename ecosystem addresses — no on-chain upgrade path

Confirmed by: Both methodologies (EthSkills E-5, Pashov P-7) | Confidence: 65

Location: REGISTRAR_CONTROLLER, REVERSE_REGISTRAR, L2_RESOLVER constants

Description:
All three Basename ecosystem addresses are immutable public constant values. If the Base team upgrades these contracts (e.g., a new RegistrarController proxy is deployed), all deployed inheriting contracts using the default mode become non-functional with no on-chain remedy — the only fix is redeployment.

Recommendation:
Document the deployment block/date for the hardcoded addresses and add a comment directing users to check the Base documentation for the latest contract addresses before deploying. Consider whether an immutable-but-not-constant pattern (set in constructor via address(0) override path) would allow future flexibility.

[INFO-3] Registration price can increase between gas estimation and execution during premium decay

Confirmed by: Both methodologies (EthSkills E-6, Pashov Lead) | Confidence: 60

Location: _registerBasename() — controller.rentPrice → controller.register sequence

Description:
Newly re-available names carry a time-decaying premium that changes block by block. The price quoted by rentPrice at gas estimation time may be lower than the price charged when the transaction is mined. If the caller sends exactly the quoted price (e.g., using getBasenamePrice), the register call may revert with an insufficient ETH error. This is correct behavior but not documented.

Recommendation:
Add to _registerBasename NatSpec:

/// @dev During premium decay periods, callers should send a 2-5% buffer above
///      getBasenamePrice() to absorb per-block price changes. Excess is refunded.

Appendix: Non-Issues Examined

The following were investigated and found to be non-issues:

  • Arithmetic overflow in price.base + price.premium: Solidity 0.8.x checked math; overflow reverts. A MAX_UINT price from the controller would revert the registration, not allow a free one. ✓
  • msg.value - totalPrice underflow: Protected by the InsufficientETH revert check immediately above. ✓
  • Treasury isolation: The code correctly uses msg.value (not address(this).balance) throughout, ensuring treasury ETH is never used to fund registrations. ✓
  • PUSH0 opcode: Solidity ^0.8.23 emits PUSH0 (Shanghai EVM). Base mainnet supports Shanghai. ✓
  • transfer() / send() usage: Not used — the code correctly uses .call{value: x}("") for ETH transfers. ✓
  • abi.encodePacked hash collisions: All abi.encodePacked calls in BasenameUtils combine bytes32 + bytes32 (fixed-size types); no collision risk. ✓
  • basenameNode vs ENS namehash consistency: basenameNode("myapp") correctly produces the same node as namehash("myapp.base.eth") — verified by the on-chain test asserting incrementer.base.eth matches a known value. ✓
  • _endsWithBaseEth correctness: The suffix check is byte-accurate with no off-by-one errors. ✓
