🔐 Security Review — RwagmiB20Launcher

Two-phase audit: Phase 1 (ethskills, breadth — 6 checklist agents) → Phase 2 (pashov, depth — 12 attacker agents, run blind to Phase 1) → hybrid reconciliation.

Phase 2 agents 9 single-specialty + 3 gap-hunter (12, opus)

Summary: RwagmiB20Launcher is a one-transaction launcher that creates a Base "B20" token, initializes a Uniswap v4 pool through an owner-allowlisted hook, seeds single-sided launch liquidity into an owner-allowlisted LP locker, and runs owner-allowlisted post-launch extensions. launchB20 is permissionless; every hook/locker/extension/pairedToken/mevModule address must be on the owner's allowlist, but every other parameter is fully caller-controlled.

Reconciliation summary: 16 unique findings after cross-phase dedup (from ~35 phase-1 raw findings and ~40 phase-2 raw findings/leads). Overlap: 7 findings independently confirmed by both phases · Phase-1-only: 5 · Phase-2-only: 4. All phase-unique findings were re-examined directly against source in this reconciliation pass; all 9 were confirmed and kept at their stated (or adjusted) severity — none were demoted or dropped.

Findings

Medium

1. CREATE2 token address is namespaced only by (variant, salt), not by caller — any launch is front-runnable and hijackable [both — phase1: general/erc20, phase2: 8 of 12 agents]

RwagmiB20Launcher._validatePredictedTokenPair / _createB20 · Confidence: 95

Description
getB20Address(uint8(b20.variant), address(this), b20.salt) (line 343) and createB20(uint8(b20.variant), b20.salt, ...) (line 410) both pass address(this) — the launcher itself — as the CREATE2 sender, never msg.sender, so the deployed token address depends only on the caller-chosen, mempool-visible salt. An attacker who observes a victim's pending launchB20(config, salt=S) can front-run with their own launchB20 reusing salt S: their token deploys first at getB20Address(variant, launcher, S), and the victim's createB20 reverts on the CREATE2 collision — bricking the victim's launch, or, if that address was pre-computed/advertised by a frontend, letting the attacker's look-alike token occupy it and capture the victim's intended fee stream and buyers.

Fix

- b20Factory.getB20Address(uint8(b20.variant), address(this), b20.salt);
+ bytes32 effectiveSalt = keccak256(abi.encode(msg.sender, b20.salt));
+ b20Factory.getB20Address(uint8(b20.variant), address(this), effectiveSalt);

(mirror the same effectiveSalt derivation at the createB20 call site, line 410)

2. Documented "10% RWAGMI" protocol fee is never enforced — any direct caller can route 100% of LP fees to themselves [phase2 only — 2 of 12 agents, re-verified directly against source in reconciliation]

RwagmiB20Launcher._validateRewards · Confidence: 92

Description
The contract's NatSpec (line 30) documents a "default 90% creator / 10% RWAGMI" fee split, but _validateRewards (lines 289-305) only enforces that rewardRecipients/rewardBps/rewardAdmins are parallel, non-empty (≤7), non-zero-address, and that rewardBps sums to exactly 10,000 — there is no RWAGMI address constant/immutable anywhere in the file (confirmed: grepped every constant/immutable declaration) and no minimum-bps floor for any specific recipient. A caller supplying rewardRecipients=[attacker], rewardBps=[10000] satisfies every check and captures 100% of that token's perpetual LP fees.

3. Admin-mode initCalls filter is a narrow two-selector blocklist, and _createB20's supply check validates only the launcher's own balance — together allow a hidden pre-mint [both — phase1: access-control/erc20/general (3 of 6), phase2: 6 of 12 agents]

RwagmiB20Launcher._validateB20AmmInitCalls / _createB20 · Confidence: 90

Description
For AdminMode.Admin, caller-supplied initCalls execute with role gates bypassed (forwarded verbatim, line 410); the only filters block the updateMultiplier selector and grantRole(OPERATOR_ROLE, ...) specifically (lines 514-533) — every other selector, including grantRole(DEFAULT_ADMIN_ROLE/MINT_ROLE, ...) and direct mint(...), passes through unchecked. _createB20's post-creation invariant (lines 416-418) only checks that the launcher's own balance equals expectedSupply — it never checks totalSupply(). A caller can include mint(launcher, expectedSupply) (satisfies the balance check) plus mint(attacker, HUGE) (a hidden pre-mint invisible to the launcher's checks and understated in the B20TokenCreated event), then dump the hidden supply into the freshly-seeded pool against unsuspecting buyers.

+ // Positive allowlist instead of two-selector blocklist in _validateB20AmmInitCalls
+ if (!_isAllowedAdminSelector(selector)) revert DisallowedInitCall(selector);

- if (balance != expectedSupply) revert UnexpectedLaunchSupply();
+ if (balance != expectedSupply) revert UnexpectedLaunchSupply();

5. Hook-returned startingTick is never reconciled with the launcher's locally-computed expectedStartingTick [both — phase1: general/precision-math/defi-amm (3 of 6), phase2: 7 of 12 agents]

RwagmiB20Launcher.launchB20 · Confidence: 75

Description
expectedStartingTick is computed locally (lines 193-194) and used to validate that all launch positions are one-sided (line 195) before initializePool is called; the hook's actual returned startingTick (line 200) is used only in the emitted event and never compared. If the allowlisted hook's tick derivation ever rounds/snaps differently (Phase 2's numerical-gap agent traced a concrete one-tick boundary case where an edge-touching position becomes two-sided), the one-sided-liquidity invariant the launcher validated no longer matches the pool's real state. Not independently exploitable from in-scope source alone — the hook implementation is out of scope and trusted — but no code-level guarantee prevents the divergence.

6. Admin-mode AMM-safety checks are a launch-instant snapshot; retained admin can invalidate every one of them post-launch [both — phase1: erc20/defi-amm (2 of 6), phase2: 7 of 12 agents]

RwagmiB20Launcher._assertB20AmmSafety · Confidence: 70 (admin-action gated — no unprivileged amplifier; kept Low, not Medium, per judging Gate 3)

Description
_assertB20AmmSafety enforces non-rebasing/unpaused/open-transfer/permissive-mint state only at launch time. AdminMode.Admin tokens retain DEFAULT_ADMIN_ROLE on initialAdmin (nothing in this contract revokes it), so the same admin can call updateMultiplier (rebase), pause, re-grant OPERATOR_ROLE, or tighten transfer/mint policies the very next block — after liquidity is already locked into the pool. This is consistent with the disclosed "Admin" (mutable) trust model, but the launch-time filtering could give LPs/buyers a misleading impression of durable safety.

7. Immutable-mode "no live admin" check only enumerates three hardcoded addresses [both — phase1: erc20/access-control (2 of 6), phase2: 1 of 12 (independently converged)]

RwagmiB20Launcher._assertB20AmmSafety · Confidence: 65

Description
The immutable-mode assertion checks hasRole(DEFAULT_ADMIN_ROLE, ...) against exactly {initialAdmin=0, address(this), b20Factory} (lines 504-511). A DEFAULT_ADMIN_ROLE grant to any fourth address (e.g. a factory-configured treasury or bootstrap co-admin) is invisible to this check, so a token that isn't actually immutable could still pass validation and be advertised as AdminMode.Immutable. Not exploitable via any caller-controlled path in this contract; depends on out-of-scope factory bootstrap behavior.

8. forceApprove to the locker is never reset; no post-launch balance-drained assertion [both — phase1: erc20, phase2: 1 of 12 (independently converged)]

RwagmiB20Launcher.launchB20 · Confidence: 65

Description
The launcher approves the locker for exactly poolSupply and calls placeLiquidity (lines 213-226), but never resets the allowance afterward and never asserts the launcher's own balance reaches zero. If the locker pulls less than the full approved amount (e.g. rounding across positions), a residual allowance and stranded dust persist indefinitely with no sweep/rescue function.

9. Unchecked negation of tickIfToken0IsB20 reverts unconditionally at type(int24).min; no explicit tick-range validation [both — phase1: general/precision-math, phase2: 1 of 12 + 1 corroborating]

RwagmiB20Launcher.launchB20 / _validatePool · Confidence: 60

Description
int24 is asymmetric (min = -8388608); -pool.tickIfToken0IsB20 overflows and reverts with an opaque panic when tickIfToken0IsB20 == type(int24).min. _validatePool never bounds the tick to Uniswap's valid range (±887272) before the sign flip. Self-DoS only (caller's own malformed config) — not a third-party exploit.

10. MAX_STATIC_LP_FEE permits fees up to 100% of swap value, enabling honeypot-style pools [phase1 only — defi-amm; re-verified directly against source]

RwagmiB20Launcher._validatePool · Confidence: 70

Description
Confirmed directly: MAX_STATIC_LP_FEE = 1_000_000 (line 44), the only bound on pool.lpFee besides Uniswap v4's own ceiling (line 329). Since the LP position is owned by the locker and fees are distributed to caller-chosen rewardRecipients (finding 2 above shows this can be 100% attacker-controlled), a caller can launch with e.g. a 99% static fee, siphoning nearly all of a buyer's input as "fee." Publicly visible on-chain in the PoolKey, which partially mitigates.

11. grantRole role-check is skipped for calldata shorter than 68 bytes [phase1 only — assembly; re-verified directly against source]

RwagmiB20Launcher._validateB20AmmInitCalls · Confidence: 55

Description
Confirmed directly: if (selector != GRANT_ROLE_SELECTOR || callData.length < 68) continue; (line 523) skips the OPERATOR_ROLE check entirely for any grantRole-selectored call shorter than 68 bytes. Against a standard Solidity ABI decoder this is safe (a too-short static-argument call reverts on the token side too), but it is a defense-in-depth gap dependent on the B20 token's exact calldata handling, which is out of scope.

12. Asymmetric allowlist validation — setHook checks the interface, other setters accept any address [phase1 only — general/access-control; re-verified directly against source]

RwagmiB20Launcher.setHook vs. setLocker/setExtension/setMevModule/setPairedToken · Confidence: 55

Description
Confirmed directly: setHook validates via _supportsHookV2 (ERC-165 + code-length check, lines 101-105) before enabling; the other four setters (lines 107-127) perform no validation at all. An owner mistake (e.g. setExtension(eoaAddress, true)) can silently enable a non-conforming address; a subsequent launch could forward ETH to an EOA via receiveTokens{value:...} with no revert to signal the misconfiguration.

13. _validateB20Metadata trusts its own guessed factory ABI layout when decoding caller-supplied params [phase2 only — 1 of 12, re-verified directly against source]

RwagmiB20Launcher._validateB20Metadata · Confidence: 55

Description
The event-truth guarantee ("direct callers cannot emit a launch event describing a different token," lines 307-311) holds only if the launcher's local AssetCreateParams decode of the opaque params bytes (lines 80-86, 312-322) is byte-identical to the external B20Factory's own decode of the same bytes. Confirmed the launcher never reads metadata back from the created token to cross-check. If the two layouts diverge, validation could pass while the factory mints a token with different name/symbol/decimals than the emitted event describes. Unverifiable further without the factory source (out of scope).

14. Caller-controlled mevModuleData/poolData can neuter a launch's own MEV protection [phase1 only — defi-amm]

RwagmiB20Launcher.launchB20 · Confidence: 50

Description
While mevModule/hook addresses are owner-allowlisted, their opaque data payloads (lines 209, 246) are fully caller-controlled and unvalidated by the launcher. A caller can configure their own launch's anti-snipe parameters to be trivially weak — self-harm only, contingent on the allowlisted modules validating their own inputs.

15. No timelock/multisig on Ownable; renounceOwnership reachable [phase1 only — access-control; re-verified directly against source]

RwagmiB20Launcher (contract-level) · Confidence: 50

Description
Confirmed directly: plain OZ Ownable (line 10, 36), single-step transferOwnership, renounceOwnership() not overridden. A typo or accidental renouncement permanently freezes all allowlist administration and the deprecated kill-switch — an availability risk, not direct fund loss. Overlaps with finding 4 (recommend Ownable2Step + override renounceOwnership() to revert).

Reconciliation notes

  • Salt-collision (finding 1) was the single most-corroborated issue: independently flagged by both phase-1 checklist agents and 8 of 12 phase-2 attacker agents, several with a full proof-of-concept including an address-hijack variant beyond simple griefing.
  • RWAGMI fee bypass (finding 2) was missed entirely by Phase 1's checklist-driven pass (no checklist item covers "is the protocol's own documented revenue split enforced on-chain") and only surfaced through Phase 2's first-principles/flow-gap attacker agents — a good illustration of why the two-phase approach catches different bug classes.
  • All Phase-1-only and Phase-2-only findings were re-examined against the live source in this reconciliation pass (not just re-stated); all were confirmed as accurate descriptions of the code and kept, several with confidence adjusted to reflect single-phase corroboration versus the double-corroborated findings.
  • No Critical or High findings survived judging gates. The contract's nonReentrant guard, exact-balance minting check (partially bypassable per finding 3), and owner-allowlisted external-call surface close off most third-party fund-loss paths under an honest-owner assumption; the two Medium-severity unprivileged findings (salt collision, RWAGMI fee bypass) are the most actionable items for a pre-mainnet fix.

⚠️ This review was performed by AI agents (ethskills checklist pass + pashov attacker-mindset pass, cross-reconciled). AI analysis can never verify the complete absence of vulnerabilities and no guarantee of security is given. A human security review, bug bounty program, and on-chain monitoring are strongly recommended before this contract is deployed as the sole gate for permissionless token launches.
