Finding 1: Reentrancy in stake()/unstake() enables double-settlement of credits and USDC, drainable via claimRewards()

Severity: High
Confidence: 80
Origin: [both] — independently proven by 5 of 12 Phase-2 agents (execution-trace, first-principles, boundary, numerical-gap, plus Phase 1's general-checklist domain), each with an independent, fully-traced numeric exploit. Two Phase-2 agents (invariant, asymmetry) examined the same code and treated it as non-exploitable under the current token assumption — noted below.
Location: stake() L120-132, unstake() L134-146, _settle() L281-294, _checkpoint() L296-300 (contrast claimRewards() L214-225, which gets the ordering right)

Description: Both stake() and unstake() call _settle(msg.sender) — which banks the pending credit/USDC delta between the global accumulators and the staker's debt checkpoint — before their external AZL transfer, but call _checkpoint(msg.sender) — which advances the debt checkpoint to stop double-accrual — only after that transfer:

function stake(uint256 amount) external {
    require(stakingActive, "UnionStaking: not active");
    require(amount > 0, "UnionStaking: zero amount");
    _accrue();
    _settle(msg.sender);                                        // L124 — banks pending delta

    azlToken.safeTransferFrom(msg.sender, address(this), amount); // L126 — external call, BEFORE checkpoint
    stakers[msg.sender].staked += amount;
    totalStaked += amount;

    _checkpoint(msg.sender);                                    // L130 — debt advanced only now
    emit Staked(msg.sender, amount, totalStaked);
}

unstake() follows the identical pattern (_settle L138, transfer L142, _checkpoint L144). There is no nonReentrant guard anywhere in the contract. If azlToken ever invokes a callback during transfer (ERC777-style tokensToSend/tokensReceived, or any other transfer-hook-bearing token), a reentrant call into any settle-triggering entrypoint (bankCredits(), stake(), unstake()) during that callback finds s.creditDebt/s.usdcDebt still at their pre-call (stale) values — _settle() recomputes and re-banks the same accrual delta a second time before the outer call's _checkpoint() ever executes.

Proof of Concept: Let accCreditPerToken advance from 500 to 700 during the _accrue() at the top of stake(), with the staker's staked=1e18 and creditDebt=500. The outer _settle() computes credits = 1e18*(700-500)/1e18 = 200 and banks it. The AZL transfer at L126 fires a hook that re-enters bankCredits(): _accrue() no-ops (elapsed==0, same block), but _settle() re-runs with the unchanged creditDebt=500 and re-computes the identical credits=200, banking it a second time — bankedCredits ends at 400 instead of the correct 200. The reentrant call's own _checkpoint() finally syncs the debt, making the outer call's later _checkpoint() a no-op. The identical mechanism doubles pendingUsdc via the same _settle() call; a subsequent claimRewards() (which is itself correctly CEI-ordered — L222 zeroes pendingUsdc before L223's transfer) pays out the inflated amount in real USDC, funded from the shared reward pool other stakers are entitled to — this is direct fund theft, not merely an internal accounting artifact. One Phase-2 agent (boundary) further showed the over-credit scales with reentrancy nesting depth, bounded only by gas.

Precondition: azlToken must invoke a callback during safeTransferFrom/safeTransfer. azlToken is immutable, chosen once at construction by the deployer; this audit cannot confirm or rule out non-standard transfer semantics for the actual deployed token, since only this contract's source was provided. Two Phase-2 agents concluded this makes the finding non-exploitable "as scoped" (standard IERC20 assumed); this report treats the missing CEI ordering and missing reentrancy guard as a real code-level defect regardless, since AZL is the protocol's own token (not a well-known audited stablecoin) and the assumption is unverified rather than confirmed safe.

Recommendation: Move _checkpoint(msg.sender) to immediately after _settle(msg.sender), strictly before any external call, in both stake() and unstake() — matching the safe ordering already used in claimRewards(). Add ReentrancyGuard/nonReentrant to all four staker-facing entrypoints as defense-in-depth regardless of the token's current implementation.

function stake(uint256 amount) external {
    require(stakingActive, "UnionStaking: not active");
    require(amount > 0, "UnionStaking: zero amount");
    _accrue();
    _settle(msg.sender);
    stakers[msg.sender].staked += amount;
    totalStaked += amount;
    _checkpoint(msg.sender);                                    // moved before the external call

    azlToken.safeTransferFrom(msg.sender, address(this), amount);
    emit Staked(msg.sender, amount, totalStaked);
}

Finding 2: Credit-cap clamp distributes the fixed final remainder by instantaneous stake — near-total capture by a short-lived whale

Severity: High
Confidence: 85
Origin: [phase2 only, corrects phase1] — independently proven by 4 of 12 Phase-2 agents (economic-security, periphery, asymmetry, trust-gap), each with a full numeric trace. Phase 1's defi-staking domain explicitly examined this scenario and concluded it was not exploitable, missing the specific mechanism described below; this reconciliation adopts the Phase-2 finding as authoritative.
Location: _accrue() L243-263, specifically the clamp at L256-259 and the accumulator write at L262

Description: In the uncapped branch of _accrue, totalStaked cancels algebraically out of each staker's share:

uint256 periodCredits =
    (elapsed * CREDIT_UNIT * totalStaked) / (CREDIT_BASE_STAKE * CREDIT_PERIOD);   // L252-253
...
accCreditPerToken += (periodCredits * ACC_SCALE) / totalStaked;                     // L262

A staker's eventual claim is staked_i * periodCredits / totalStaked = staked_i * elapsed * CREDIT_UNIT / (CREDIT_BASE_STAKE * CREDIT_PERIOD) — independent of totalStaked, so ordinary just-in-time staking earns exactly proportional to stake × time held, matching the NatSpec's "no race to claim first" claim (L18-19). The moment the 600,000-credit cap is crossed, however:

if (totalCreditsIssued + periodCredits >= CREDIT_CAP) {
    periodCredits = CREDIT_CAP - totalCreditsIssued;    // L257 — now a FIXED remainder
    emit CreditCapReached(CREDIT_CAP);
}
totalCreditsIssued += periodCredits;
accCreditPerToken += (periodCredits * ACC_SCALE) / totalStaked;   // L262 — totalStaked no longer cancels

periodCredits becomes a fixed number R = CREDIT_CAP - totalCreditsIssued, decoupled from elapsed time — whoever holds the largest staked_i at the instant this one clamping tick fires captures the largest share of R, regardless of how briefly they've held it.

Proof of Concept (from the trust-gap agent's trace): existing stakers collectively hold H = 500,000,000e18 AZL, accumulated over the program's entire history; R = 5e18 (5 credits) remain before CREDIT_CAP. Attacker calls stake(4,500,000,000e18) (9× H) — this call's own _accrue() runs against the old totalStaked (elapsed==0 idempotency prevents self-triggering the crossing), so the attacker gains nothing yet, but totalStaked is now 5,000,000,000e18. Approximately one day later, the attacker (or anyone) calls bankCredits(): periodCredits computed against the new, inflated totalStaked exceeds R, so it clamps to R=5e18; accCreditPerToken += 5e18*1e18/5,000,000,000e18. The attacker's _settle() credits them 4,500,000,000e18 * 5e18 / 5,000,000,000e18 = 4.5e18 — 90% of the last 5 credits ever to exist — for roughly one day of exposure, versus the long-term stakers' entire program history. The attacker then calls unstake() for the full principal; banked credits survive unstaking by design (NatSpec L21). Since totalCreditsIssued now equals CREDIT_CAP, issuance halts permanently (L250) — there is no future period in which the diluted long-term stakers can recover their share.

Note: unlike Finding 1, this requires no external token assumptions — it is a pure on-chain capital-and-timing attack, executable by any address with sufficient capital, fully within an attacker's own control.

Recommendation: Snapshot totalStaked at the start of the pending-elapsed interval (i.e., as of lastAccrualAt) rather than reading it at the trigger-call moment, so mid-interval stake changes cannot affect that interval's clamped remainder; or impose a minimum stake-duration/bonding period before newly-staked AZL counts toward the denominator of a cap-crossing distribution.

Finding 3: treasury is a permanent, non-rotatable role and notifyReward never verifies USDC funding

Severity: High
Confidence: 85
Origin: [both] — Phase-1 access-control domain (full FINDING with drain-race exploit chain), corroborated as a LEAD by 4 Phase-2 agents and as a FINDING by Phase-1's general-checklist domain.
Location: notifyReward() L188-202, setTreasury() L103-107

Description: treasury is set exactly once by the owner (L103-107) with no rotate/revoke path anywhere in the contract. notifyReward is gated only by msg.sender == treasury (L189) and never checks usdcToken.balanceOf(address(this)) — it purely trusts the NatSpec-documented assumption ("a USDC reward already transferred to this vault," L185) and folds the caller-supplied amount directly into rewardRateScaled/rewardPeriodFinish (L194-199). If treasury is ever compromised or misconfigured, it can call notifyReward(amount) with an arbitrary, unfunded amount, inflating accUsdcPerToken accrual for all stakers based on a rate that was never backed by a matching transfer — and because treasury can never be rotated, there is no remediation once this begins.

Proof of Concept: treasury = T is compromised (or a bug causes it to misreport). The vault genuinely holds 10,000 USDC from prior, correctly-funded cycles. Attacker (controlling T) calls notifyReward(1,000,000e6) with no matching transfer; rewardRateScaled (L198) is computed purely from this unbacked figure. The attacker's own staked position accrues a large pendingUsdc share quickly and calls claimRewards() first, draining the real 10,000 USDC before other legitimate stakers can claim. Remaining stakers' claimRewards() calls revert on insufficient balance despite their pendingUsdc bookkeeping showing a nonzero, "earned" amount — and treasury can never be replaced to stop the pattern.

Recommendation: Have notifyReward pull funds atomically via usdcToken.safeTransferFrom(treasury, address(this), amount) instead of trusting a prior out-of-band transfer, and add an owner-gated rotation path for treasury (dropping the permanent one-shot guard).

Finding 4: taskRegistry is a permanent, non-rotatable role that can grief-drain any staker's banked Action Credits

Severity: High
Confidence: 85
Origin: [phase1: access-control] — re-examined against source in Phase 3, confirmed; corroborated as a "confused-deputy" LEAD by 3 Phase-2 agents (access-control, trust-gap, and one gap-hunter).
Location: trySpendCredit() L158-170, onlyRegistry modifier L85-88, setTaskRegistry() L97-101

Description: taskRegistry is set exactly once by the owner (L97-101) with no rotate/revoke path. trySpendCredit(address agent) is onlyRegistry-gated but takes an arbitrary agent parameter chosen entirely by whichever address holds the taskRegistry role — the vault performs no check that agent consented to or benefited from the call. Each call, if agent has ≥1 banked credit, unconditionally deducts one CREDIT_UNIT (L166) with no cooldown, per-call cap, or way for agent to object. If taskRegistry is ever compromised or misconfigured, it can call trySpendCredit(victim) repeatedly to burn down any staker's entire banked-credit balance with zero benefit delivered — and the role can never be revoked or rotated.

Proof of Concept: taskRegistry = R is compromised. Victim has banked 5 credits via prior bankCredits()/settlement calls. Attacker (controlling R) calls trySpendCredit(victim) 5 times in a row (or across 5 separate transactions — no rate limit exists), destroying the victim's entire banked-credit balance with no fee ever bypassed on their behalf. No owner intervention is possible since taskRegistry cannot be replaced.

Recommendation: Add an owner-gated (ideally timelocked or multisig-gated) rotation/revocation path for taskRegistry, dropping the permanent one-shot guard; consider a pausable circuit breaker on trySpendCredit so the owner can freeze credit-spending if the registry is known to be compromised.

Finding 5: renounceOwnership (inherited, unoverridden) can permanently brick the one-shot setup path

Severity: High
Confidence: 85
Origin: [both] — Phase-1 general/access-control domains (full FINDING); Phase-2's access-control agent examined the same path and classified it as a LEAD under the "admin can misconfigure their own contract" exclusion rule rather than a third-party-exploitable finding. This reconciliation keeps it as a Finding since the phase-2 exclusion rule is about third-party exploitability, and the audit's severity definitions explicitly include owner-only fund/functionality loss under Medium-and-above categories; the mechanical consequence here (permanent, irrecoverable bricking) matches the "permanent DoS" criterion for High regardless of who triggers it.
Location: inherited Ownable.renounceOwnership() (not overridden anywhere in this file); setTaskRegistry() L97-101, setTreasury() L103-107, activateStaking() L111-116

Description: UnionStakingVault is Ownable2Step (L28). Ownable2Step hardens only the transfer path into a two-step propose/accept flow — it does not override renounceOwnership(), which remains the single-step, immediate Ownable version. setTaskRegistry, setTreasury, and activateStaking are each onlyOwner and one-shot (guarded by an == address(0)/!stakingActive check) with no alternative path once ownership is gone. If the owner renounces before completing any subset of the three, that subset can never be set by anyone, ever.

Proof of Concept: Contract is deployed; owner has called none of the three setup functions yet. Owner calls the inherited renounceOwnership(). owner() is now address(0); setTaskRegistry/setTreasury/activateStaking are all permanently unreachable — stake() reverts forever (stakingActive can never become true), and trySpendCredit/notifyReward are permanently unreachable since their gating addresses default to address(0), unsatisfiable by any msg.sender.

Recommendation: Override renounceOwnership() to revert, or gate it on all three setup steps being complete:

function renounceOwnership() public view override onlyOwner {
    revert("UnionStaking: renounce disabled");
}

Finding 6: One-shot setTaskRegistry/setTreasury have no timelock or correction path for a configuration mistake

Severity: High
Confidence: 85
Origin: [phase1: access-control] — re-examined against source in Phase 3, confirmed.
Location: setTaskRegistry() L97-101, setTreasury() L103-107

Description: Both setters accept any non-zero address and, once set, can never be called again. There is no timelock, no propose-then-confirm flow, and no way to correct even a simple operator error (e.g., a stale or mistyped address). This is distinct from Findings 3/4 (a compromised role holder) and Finding 5 (never set at all): here, a single, irreversible transaction with no review window permanently locks in whatever address the owner supplies, with no remediation if it is wrong.

Proof of Concept: Owner intends to wire the real TaskRegistry contract but supplies the wrong (yet valid, non-zero) address — a copy-paste error or stale deployment address. setTaskRegistry(wrongAddress) succeeds and can never be corrected; the credit-spend feature (the core advertised utility, per NatSpec L18) is permanently dead for the life of the deployment. The identical failure mode applies to setTreasury.

Recommendation: Replace the irreversible one-shot pattern with a timelocked or two-step propose/confirm setter that still restricts each role to being set only once in production but gives the owner a window to catch and correct mistakes before they become permanent.

Finding 7: No handling for a blocklist/pausable stake or reward token — vault-level blocklisting permanently freezes funds

Severity: High
Confidence: 75
Origin: [phase1: erc20]
Location: claimRewards() L223, unstake() L142

Description: usdcToken is typed exactly as a realistic USDC deployment, which implements Circle-style blocklist/pause functionality where a flagged address can neither send nor receive tokens. If the vault's own address is ever blocklisted (compliance action, false positive, or a protocol-wide pause), usdcToken.safeTransfer(msg.sender, amount) in claimRewards() (L223) reverts for every staker, permanently — there is no owner-controlled emergency sweep or migration function anywhere in the contract. The identical risk applies symmetrically to azlToken/unstake() if that token ever implements an equivalent mechanism, in which case all staked principal (not just rewards) becomes unrecoverable.

Proof of Concept: The vault holds $500,000 in accrued pendingUsdc across all stakers. The vault's address is blocklisted by USDC's administrator for any reason. Every subsequent claimRewards() call reverts permanently — no mechanism in the contract can un-blocklist the address, reroute payment, or rescue the funds to a fresh deployment.

Recommendation: Add an owner-gated (ideally timelocked) emergency-sweep/migration function for this scenario, and/or support a per-claim "pay to arbitrary address" parameter so a blocklisted user's own address doesn't compound the problem.

Finding 8: Internal AZL accounting credited from the requested amount, not a measured balance delta — insolvency risk

Severity: High
Confidence: 80
Origin: [both] — Phase-1 erc20/general/precision-math domains (full FINDING with numeric trace); corroborated as a LEAD by 4 Phase-2 agents, all noting the precondition is unverified for the actual deployed azlToken.
Location: stake() L126-128

Description: stake() pulls azlToken via safeTransferFrom (L126) and then credits stakers[msg.sender].staked/totalStaked with the full requested amount (L127-128) — never a measured balanceOf delta. If azlToken ever applies a transfer fee or rebases downward, the vault's actual token balance permanently falls short of what totalStaked claims, with no reconciliation anywhere in the contract.

Proof of Concept: Assume azlToken charges a 2% transfer fee. Alice calls stake(10,000e18): the vault records staked += 10,000e18 but only receives 9,800e18. Repeated across many stakers, the gap between recorded totalStaked and the real azlToken.balanceOf(vault) widens monotonically and never self-corrects. Eventually, unstake()'s safeTransfer (L142) for whichever staker(s) unstake last will attempt to pay out more than the vault actually holds and revert — their recorded principal becomes permanently unredeemable.

Recommendation: Measure the actual balance delta around safeTransferFrom and credit that instead of the parameter:

uint256 balBefore = azlToken.balanceOf(address(this));
azlToken.safeTransferFrom(msg.sender, address(this), amount);
uint256 received = azlToken.balanceOf(address(this)) - balBefore;
stakers[msg.sender].staked += received;
totalStaked += received;

Finding 9: No recovery path for USDC permanently stranded when totalStaked is zero mid-stream

Severity: Low
Confidence: 80
Origin: [phase1: defi-staking] — re-examined in Phase 3; the underlying "stranded slice" mechanism was independently confirmed (not disputed) by multiple Phase-2 agents while examining related JIT-staking questions.
Location: notifyReward() L188-202, _updateRewardAcc() L232-239

Description: notifyReward never checks totalStaked > 0 before starting/refreshing a 7-day stream. If totalStaked is 0 for any portion of an active stream (before the first staker, or after a mass-unstake), _updateRewardAcc still advances lastRewardUpdateAt unconditionally (L238) while skipping the accUsdcPerToken increment (L235-237, guarded by totalStaked > 0) — that USDC (already sitting in the vault, per the notifyReward contract) is permanently unattributable, with no owner sweep function anywhere.

Proof of Concept: Treasury calls notifyReward(10,000e6) immediately after activateStaking(), before anyone stakes. No one stakes for 7 days. Every _updateRewardAcc call during this window hits the zero-stake branch; accUsdcPerToken never increases. After rewardPeriodFinish, the first staker finally arrives — the entire 10,000 USDC is now permanently stuck with no recovery path.

Recommendation: Require totalStaked > 0 in notifyReward, and/or add an owner-only rescue function for USDC held in excess of all outstanding obligations.

Finding 10: Hardcoded 18/6-decimal assumptions never validated against deployed tokens

Severity: Low
Confidence: 80
Origin: [both] — Phase-1 erc20/precision-math domains (full FINDING with numeric trace); corroborated as a LEAD by 2 Phase-2 agents.
Location: constructor L90-95, CREDIT_BASE_STAKE L33, USDC_ACC_SCALE L38

Description: CREDIT_BASE_STAKE = 100,000,000 * 1e18 assumes 18-decimal AZL; USDC_ACC_SCALE = 1e36 is explicitly tuned (per the code comment) for 6-decimal USDC. Neither the constructor nor any other function ever calls decimals() on either token to validate these assumptions.

Proof of Concept: If azlToken were deployed with 6 decimals instead of 18, a "100,000,000 AZL" stake would numerically be 100,000,000 * 1e6, but CREDIT_BASE_STAKE still divides by 100,000,000 * 1e18 — the credit-issuance rate silently drops by a factor of 1e12, meaning periodCredits floors to 0 for essentially any realistic elapsed time/stake size, permanently disabling credit mining with no revert to signal the misconfiguration.

Recommendation: Validate decimals at construction:

require(IERC20Metadata(_azlToken).decimals() == 18, "UnionStaking: AZL must be 18 decimals");
require(IERC20Metadata(_usdcToken).decimals() == 6, "UnionStaking: reward token must be 6 decimals");

Finding 11: creditsRemaining() omits pending accrual, unlike its sibling creditsOf()

Severity: Low
Confidence: 75
Origin: [phase2 only]
Location: creditsRemaining() L179-181, creditsOf() L151-154, _pendingCredits() L265-278

Description: creditsRemaining() returns CREDIT_CAP - totalCreditsIssued (L180) with no projection of pending, not-yet-checkpointed accrual — while creditsOf() explicitly includes _pendingCredits(s) (L153) for the equivalent per-agent view. The global view is therefore stale by exactly the pending-accrual amount whenever _accrue() hasn't been triggered recently.

Proof of Concept: With totalStaked = CREDIT_BASE_STAKE and totalCreditsIssued exactly one credit short of CREDIT_CAP, if 30 days elapse with no on-chain interaction, the pending (unrealized) accrual is exactly 1 whole credit — meaning the cap has effectively already been reached in real time. creditsRemaining() still reports "1 credit available" throughout that entire 30-day window, right up until the next state-changing call finally triggers _accrue() and consumes it.

Recommendation: Have creditsRemaining() project pending global accrual the same way _pendingCredits does, or document it explicitly as "as of the last on-chain accrual, may be stale."

Finding 12: _accrue advances lastAccrualAt before confirming credits were computed — dust forfeiture at extreme low stake

Severity: Low
Confidence: 70
Origin: [both] — Phase-1 precision-math domain; corroborated by 3 Phase-2 agents, all concluding negligible real-world exploitability outside a narrow pre-adoption window.
Location: _accrue() L246-254

Description: lastAccrualAt = block.timestamp (L248) is written before the totalStaked==0/cap-reached check (L250) and the periodCredits==0 check (L254). When periodCredits floors to zero (reachable whenever elapsed * totalStaked is below roughly 2.6e14 wei-seconds), that window is discarded rather than carried forward.

Proof of Concept: With totalStaked = 1e14 wei and elapsed=1: periodCredits = floor(1e14 * 1e18 / 2.592e32) = 0, early return at L254, but lastAccrualAt already advanced. If calls keep resetting the window faster than the threshold is crossed, credit issuance stalls indefinitely at that stake level — reachable only in a brief post-launch window before real capital arrives, since a single whole AZL token already defeats the threshold.

Recommendation: Only advance lastAccrualAt when credits are actually issued, or track a carry-forward remainder for sub-threshold windows.

Finding 13: Floor-division dust loss in the credit accumulator

Severity: Info
Confidence: 80
Origin: [phase1: precision-math]
Location: _accrue() L262, _settle() L284

Description: totalCreditsIssued counts the full unrounded periodCredits against the cap, but accCreditPerToken += periodCredits*ACC_SCALE/totalStaked floors, so the amount actually redeemable by stakers is always ≤ periodCredits. Standard MasterChef/Synthetix rounding tradeoff; economically negligible.

Recommendation: No code change strictly necessary; document that totalCreditsIssued is a cap-tracking counter, not a guarantee of exactly-600,000 claimable credits.

Finding 14: PUSH0 opcode compatibility unconfirmed for target chain

Severity: Info
Confidence: 60
Origin: [phase1: general]
Location: pragma solidity ^0.8.24; L2

Description: Solidity ≥0.8.20 emits PUSH0 by default; several L2s/alt-chains have historically lacked support. Deployment-configuration concern only.

Recommendation: Confirm the target chain supports PUSH0, or pin evmVersion in compiler settings.
