Findings

[97] 1. No self-review, no signature/stake, no Sybil resistance on feedback submission — reputation is freely forgeable in both directions

ERC8004ReputationRegistry.submitFeedback / submitFeedbackHashed · Confidence: 97 · Severity: High · Origin: [both] — flagged independently by all 12 phase-2 agents and 3 phase-1 checklists (signatures, access-control, general)

Description
Lines 153-199 and 226-273 gate feedback submission on nothing but identityRegistry.isAgentActive(agentAddress), rating <= 10000, and a non-empty category. There is no check that msg.sender != agentAddress (self-review), no signature or EIP-712 authentication of the reviewer (despite the contract's own docstring at line 27 claiming feedback "Prevents fake reviews through economic stakes"), no stake, no per-reviewer rate limit or dedup, and the caller-supplied bondId (lines 161/234) is stored and emitted but never validated against the AIPartnershipBonds contract or checked to involve either party. Any address — including the agent itself — can call these functions an unlimited number of times for the cost of gas alone.

Proof of Concept

  1. Attacker registers agent A via ERC8004IdentityRegistry.registerAgent(...) → isAgentActive(A) == true.
  2. A calls submitFeedback(A, 10000, "partnership_quality", "", false, 0) repeatedly. Nothing rejects reviewer == agentAddress. Each call feeds _updateReputation(A, 10000, false), driving A's averageRating toward 10000 with zero real partnerships.
  3. Symmetrically, an attacker griefs a rival R by calling submitFeedback(R, 0, "x", "", false, 0) repeatedly — no cost beyond gas, no limit, no proof of ever interacting with R.
  4. A fabricated bondId (e.g. a real bond ID the caller was never party to) can be attached to lend false partnership credibility to an otherwise-unverified review.

Fix

     function submitFeedback(
         address agentAddress,
         uint256 rating,
         string calldata category,
         string calldata feedbackURI,
         bool verified,
         uint256 bondId
     ) external {
         require(identityRegistry.isAgentActive(agentAddress), "Agent not registered");
+        require(msg.sender != agentAddress, "Cannot review self");
         require(rating <= 10000, "Rating must be 0-10000");
         require(bytes(category).length > 0, "Category required");

(apply the identical require(msg.sender != agentAddress, ...) to submitFeedbackHashed)

This is the minimum viable fix. For the full trust model the contract's own docs promise, additionally bind submission to a validated bondId (verify against AIPartnershipBonds that the bond exists, is settled, and that msg.sender is a counterparty) and/or require an EIP-712-signed attestation from the counterparty with a nonce, rather than trusting bare msg.sender.

[95] 2. EMA weighting in _updateReputation lets ~20–60 free transactions wipe or fabricate an agent's entire reputation history

ERC8004ReputationRegistry._updateReputation · Confidence: 95 · Severity: High · Origin: [both] — phase-1 precision-math (P-2) + 7 of 12 phase-2 agents independently derived the same exploit math

Description
Once totalFeedbacks >= 1000 (MAX_FEEDBACKS_FOR_TRUE_AVG), line 304 switches from a true running average to a fixed-alpha EMA: averageRating = (averageRating * 9 + newRating) / 10. Every subsequent feedback — regardless of how much honest history precedes it — moves the score by a flat 10% of the gap to the new rating. Combined with finding [1]'s total lack of Sybil resistance, this converts a large amount of genuine history into something a handful of free transactions can override.

Proof of Concept
Agent has averageRating = 9000 from 1000+ genuine reviews (past the EMA threshold). Attacker submits rating = 0 repeatedly:

  • After 1 call: 8100
  • After 10 calls: ≈3138
  • After 22 calls: ≈882 (a ~90% wipe)
  • After 40 calls: ≈148

Symmetrically, ~20 calls of rating = 10000 restore or fabricate a near-perfect score for any active agent, regardless of true history. Contrast the pre-1000 true-average branch, where the same 22 zero-ratings against an agent with 1000 honest reviews move the score only ~2%. The EMA branch is ~100x more exploitable than the branch it replaced.

Fix

-    function _updateReputation(
-        address agentAddress,
-        uint256 newRating,
-        bool verified
-    ) internal {
-        AgentReputation storage rep = reputations[agentAddress];
-
-        if (rep.totalFeedbacks < MAX_FEEDBACKS_FOR_TRUE_AVG) {
-            uint256 totalRating = rep.averageRating * rep.totalFeedbacks;
-            totalRating += newRating;
-            rep.totalFeedbacks += 1;
-            rep.averageRating = totalRating / rep.totalFeedbacks;
-        } else {
-            rep.averageRating = (rep.averageRating * 9 + newRating) / 10;
-            rep.totalFeedbacks += 1;
-        }
+    // Store the exact cumulative sum instead of switching to a fixed-alpha EMA.
+    // ratingSum cannot overflow uint256 for any realistic feedback count
+    // (10000 * 2^60 feedbacks would still fit comfortably).
+    function _updateReputation(
+        address agentAddress,
+        uint256 newRating,
+        bool verified
+    ) internal {
+        AgentReputation storage rep = reputations[agentAddress];
+        rep.ratingSum += newRating;
+        rep.totalFeedbacks += 1;
+        rep.averageRating = rep.ratingSum / rep.totalFeedbacks;

(add uint256 ratingSum; to the AgentReputation struct.) This also resolves finding [7]'s truncation drift, since the average is derived from an exact sum rather than reconstructed from a previously-rounded value.

[90] 3. Deactivated agents are permanently bricked — contradicts documented reactivation behavior

ERC8004IdentityRegistry.deactivateAgent / registerAgent / updateAgentURI · Confidence: 90 · Severity: Medium · Origin: [both] — flagged by phase-1 access-control/general and 10 of 12 phase-2 agents (as LEAD, promoted — deterministic exploit chain fully present in source)

Description
deactivateAgent() (lines 125-131) sets active = false but leaves the permanent isRegistered flag set. Its own NatSpec (line 123) claims "Agent can reactivate by registering again" — but registerAgent() (line 84, the MEDIUM-severity anti-duplicate-registration fix) now reverts whenever isRegistered == true, and updateAgentURI() (line 113) requires active == true. No reactivateAgent() function exists anywhere. Once an agent deactivates itself, it can never re-register, never update its URI, and — because ERC8004ReputationRegistry.submitFeedback/submitFeedbackHashed gate on isAgentActive, — can never receive feedback again.

Proof of Concept

  1. Agent registers: isRegistered = true, active = true.
  2. Agent calls deactivateAgent(): active = false, isRegistered unchanged.
  3. Agent calls registerAgent(...) → reverts "Agent already registered".
  4. Agent calls updateAgentURI(...) → reverts "Agent not registered".
  5. Identity is permanently stranded; no code path restores active.

This is currently self-triggered only (no third party can deactivate another agent), so it is scoped as Medium rather than High.

Fix

+    function reactivateAgent() external {
+        require(agents[msg.sender].isRegistered, "Not registered");
+        require(!agents[msg.sender].active, "Already active");
+        agents[msg.sender].active = true;
+        emit AgentRegistered(
+            msg.sender,
+            agents[msg.sender].agentURI,
+            agents[msg.sender].agentType,
+            agents[msg.sender].capabilitiesHash,
+            block.timestamp
+        );
+    }

Also correct the stale NatSpec on deactivateAgent().

[85] 4. ERC8004ReputationRegistry.owner has no transfer mechanism — permanent single point of failure

ERC8004ReputationRegistry — owner / constructor / verifyFeedback · Confidence: 85 · Severity: Medium · Origin: [both] — phase-1 access-control (AC-3) + governance (M-1); phase-2 agent 2

Description
ERC8004ReputationRegistry declares its own owner (line 33), set once in the constructor (line 137). Unlike MissionEnforcement in the same codebase, there is no transferOwnership, acceptOwnership, or renounceOwnership — no code path anywhere writes owner after deployment. owner is the sole gate on verifyFeedback(). If the deployer key is lost, verification is permanently unusable; if it is compromised, the attacker controls it forever with no recovery.

Proof of Concept
Grep the file for any assignment to owner after line 137 — none exists. This is a design gap, not an active exploit: the failure mode triggers on key loss/compromise.

Fix

+    address public pendingOwner;
+    event OwnershipTransferStarted(address indexed previousOwner, address indexed newOwner);
+
+    function transferOwnership(address newOwner) external onlyOwner {
+        require(newOwner != address(0) && newOwner != owner, "Invalid new owner");
+        pendingOwner = newOwner;
+        emit OwnershipTransferStarted(owner, newOwner);
+    }
+
+    function acceptOwnership() external {
+        require(msg.sender == pendingOwner, "Only pending owner");
+        owner = pendingOwner;
+        pendingOwner = address(0);
+    }

[85] 5. Hashed feedback can never be verified — verifyFeedback only reaches the legacy string-feedback mapping

ERC8004ReputationRegistry.verifyFeedback / getVerifiedFeedbackPercentage · Confidence: 85 · Severity: Low · Origin: [both] — flagged as LEAD by 9 of 12 phase-2 agents plus phase-1 access-control/economic checklists; promoted (deterministic, ≥2 agents)

Description
verifyFeedback() (lines 210-222) bounds-checks against nextFeedbackId and mutates only the legacy feedbacks mapping. There is no equivalent for feedbacksHashed / nextFeedbackIdHashed. Since the contract's own docs (line 46) recommend submitFeedbackHashed() as the privacy-preferred path, any agent reviewed exclusively through that path can never have any of its feedback marked verified — yet totalFeedbacks (the denominator in getVerifiedFeedbackPercentage, line 405) is incremented by both paths. The verified-percentage metric is therefore structurally biased against the recommended, privacy-preserving submission path.

Client focus-area note: storage of feedbackURI/feedbackHash itself was checked directly against source (lines 173-182, 246-255) and is correct — no field swap or truncation. This finding is about the verification path, not the storage assignment.

Fix

+    function verifyFeedbackHashed(address agentAddress, uint256 feedbackId) external onlyOwner {
+        require(feedbackId > 0 && feedbackId < nextFeedbackIdHashed, "Invalid feedback ID");
+        FeedbackHashed storage fb = feedbacksHashed[feedbackId];
+        require(fb.agentAddress == agentAddress, "Feedback does not belong to agent");
+        require(!fb.verified, "Already verified");
+        fb.verified = true;
+        reputations[agentAddress].verifiedFeedbacks += 1;
+        emit FeedbackVerified(agentAddress, feedbackId);
+    }

[80] 6. bondId is accepted and stored but never validated against any bond registry

ERC8004ReputationRegistry.submitFeedback / submitFeedbackHashed — bondId parameter · Confidence: 80 · Severity: Low · Origin: [both] — phase-1 signatures (S-2); phase-2 agents 3, 9, 11

Description
bondId (lines 159/181/232/254) is documented as linking feedback to "a verified VaultFire partnership" and to AIPartnershipBonds (lines 23-24), but it is stored verbatim with no existence check, no ownership check, and no cross-contract call to confirm the bond exists or that msg.sender/agentAddress are its participants. A caller can attach an arbitrary or unrelated real bondId to fabricate partnership-backed provenance for off-chain consumers.

Fix
Validate bondId against the AIPartnershipBonds contract before accepting it (bond exists, is settled, and msg.sender/agentAddress are its counterparties), or reject any nonzero bondId that fails validation.

[75] 7. Running-average reconstruction from an already-rounded value causes monotonic, adversarially-steerable downward drift

ERC8004ReputationRegistry._updateReputation (pre-1000-feedback branch) · Confidence: 75 · Severity: Low · Origin: [both] — phase-1 precision-math (P-1); phase-2 agents 1, 7, and 10 (agent 10 supplied the strongest concrete proof)

Description
Lines 296-299 reconstruct totalRating = rep.averageRating * rep.totalFeedbacks from the already floor-divided averageRating, rather than storing an exact running sum. Because the stored average is floor(sum/n), averageRating * totalFeedbacks <= true sum, and the discarded remainder compounds on every subsequent call. The drift is monotonically non-decreasing (e_n = e_{n-1} + (T_n mod n) >= e_{n-1}), not bounded rounding dust — and an adversarial reviewer can choose ratings to maximize (T_n mod n) each step, deliberately deflating a competitor's stored average while each individual submitted rating looks unremarkable.

Proof of Concept
Ratings submitted in order [1, 2, 3, 4, 5]: stored averageRating reads 1, 1, 1, 1, 1 at every step, while the true mean is 1, 1.5, 2.0, 2.5, 3.0 — a drift of 2.0 after only 5 feedbacks that keeps growing with count.

Fix
Same fix as [2]: store an exact ratingSum and derive averageRating = ratingSum / totalFeedbacks, flooring exactly once rather than reconstructing and re-flooring on every call. The overflow this branch was originally written to avoid was never real — 10000 * (realistic feedback count) << 2^256.

[70] 8. Unbounded feedback/discovery arrays returned wholesale by view getters — permanently uncallable once inflated

ERC8004ReputationRegistry.getAgentFeedbacks / getReviewerFeedbacks; ERC8004IdentityRegistry.discoverAgentsByCapability · Confidence: 70 · Severity: Low · Origin: [phase1-only] — evm-audit-dos checklist (DOS-1/DOS-2), cross-checked against source directly by the orchestrator

Description
agentFeedbacks[agent] / agentFeedbacksHashed[agent] grow by one element on every free, unauthenticated submitFeedback/submitFeedbackHashed call (finding [1] makes this cheap and unlimited). getAgentFeedbacks() (lines 352-358) and getReviewerFeedbacks() (413-419) return the full array by copy; once large enough this exceeds eth_call gas limits and permanently breaks any on-chain contract that consumes it, with no prune path. discoverAgentsByCapability() (ERC8004IdentityRegistry.sol:165-171) has the analogous issue via Sybil-registered addresses sharing one capabilitiesHash. No state-changing function iterates these arrays, so this is not a classic block-gas-limit DoS — the impact is confined to view-getter/on-chain-consumer availability, but it is irreversible.

Fix
Add paginated variants, e.g.:

function getAgentFeedbacks(address agent, uint256 offset, uint256 limit)
    external view returns (uint256[] memory page)
{
    uint256[] storage all = agentFeedbacks[agent];
    uint256 end = offset + limit;
    if (end > all.length) end = all.length;
    page = new uint256[](end - offset);
    for (uint256 i = offset; i < end; i++) page[i - offset] = all[i];
}

[65] 9. MissionEnforcement owner can unilaterally flip "immutable" mission-compliance state with no timelock

MissionEnforcement.adjudicateMissionViolation / certifyModuleMissionCompliant · Confidence: 65 · Severity: Low · Origin: [both] — phase-1 access-control (AC-4) + governance (M-2); phase-2 agent 5 (as "unenforced-invariant", same underlying gap)

Description
The contract's NatSpec repeatedly claims principles are "IMMUTABLE — cannot be changed by governance or upgrades" (lines 12-24, 46, 299). In reality, a single onlyOwner key freely flips missionCompliance[module][principle] in either direction via certifyModuleMissionCompliant/adjudicateMissionViolation (lines 226-259), with no timelock, multisig, or community ratification. Impact is currently latent because no in-scope function actually consumes enforceMission/missionCompliance (see [15]), but any future VaultFire module gated by it inherits full single-key control, directly contradicting the marketed "cryptographic enforcement."

Fix
Either place these functions behind a timelock/multisig, or drop the "immutable"/"cannot be changed by governance" language to accurately describe the real (owner-mutable) trust model.

[70] 10. Privacy guarantees (consent, right-to-be-forgotten) are defined but never enforced on any write path

PrivacyGuarantees.requiresConsent / checkDeletionRequest; consumers ERC8004ReputationRegistry, ERC8004IdentityRegistry · Confidence: 70 · Severity: Low · Origin: [both] — phase-1 general (G-7); phase-2 agents 2, 4, 6, 7, 8, 12 (6 of 12, unusually high consensus for a LEAD)

Description
PrivacyGuarantees defines requiresConsent and checkDeletionRequest modifiers plus a requestDataDeletion() "right to be forgotten" mechanism (lines 44-52, 86-93), but grep across all four files confirms neither modifier is ever applied to any state-changing function. A user who calls requestDataDeletion() can still have new Feedback records written that reference their address via submitFeedback/submitFeedbackHashed. The advertised privacy floor is inert.

Fix
Apply checkDeletionRequest(agentAddress) (and/or the reviewer) to submitFeedback/submitFeedbackHashed, or explicitly document that enforcement is off-chain-only and the on-chain modifiers are advisory scaffolding.

[55] 11. reportMissionViolation is an unauthenticated, unbounded spam/griefing vector against arbitrary modules

MissionEnforcement.reportMissionViolation · Confidence: 55 · Severity: Low · Origin: [both] — phase-1 governance (L-1) + dos (DOS-3); phase-2 agent 9

Description
reportMissionViolation() (lines 203-220) is external with no access control, stake, or rate limit. Anyone can push arbitrary MissionReport structs (up to 1000-byte evidence) against any module, including honest ones, to smear it in off-chain dashboards. Because reports are explicitly non-binding (only adjudicateMissionViolation changes real state) and the array is never iterated on-chain, this is not a gas-limit DoS — just storage bloat and reputational noise.

Fix
Require a small refundable/slashable bond per report, restrict reporting to registered agents, and/or dedupe (reporter, module, principle).

[50] 12. Two-step ownership transfer has no cancellation path and no acceptance deadline

MissionEnforcement.transferOwnership / acceptOwnership · Confidence: 50 · Severity: Low · Origin: [phase1-only] — governance checklist (L-2)

Description
Once transferOwnership(newOwner) sets pendingOwner (line 271), the current owner has no way to cancel it — transferOwnership requires newOwner != owner (line 270), so the owner cannot re-target the slot to themselves, and there is no dedicated cancel function. acceptOwnership() (lines 278-284) has no deadline, so a stale pending transfer can be accepted arbitrarily far in the future.

Fix
Add cancelOwnershipTransfer() (owner-only, sets pendingOwner = address(0)), and optionally a pendingOwnerExpiry enforced in acceptOwnership.

[50] 13. missionViolations is a single scalar per module — stale/overwritten violation state

MissionEnforcement.missionViolations, adjudicateMissionViolation, certifyModuleMissionCompliant · Confidence: 50 · Severity: Low · Origin: [phase1-only] — governance checklist (L-3)

Description
missionViolations is mapping(address => CorePrinciple) — one value per module. adjudicateMissionViolation (line 235) overwrites it, so a module violating two principles only ever reflects the most recent. certifyModuleMissionCompliant never clears it, so a re-certified module can read as compliant via missionCompliance while missionViolations still reports a stale violation.

Fix
Track violations as mapping(address => mapping(CorePrinciple => bool)) (or timestamped), and clear the relevant entry inside certifyModuleMissionCompliant.

[40] 14. MissionEnforcement's enforcement primitives are unused — "cryptographic enforcement" claims are aspirational

MissionEnforcement.enforceMission, verifyAIProfitCap, verifyHumanFinalSay, verifyNoKYC · Confidence: 40 · Severity: Info · Origin: [both] — phase-1 general (G-8) + governance (I-1); phase-2 agents 5, 6

Description
enforceMission is never applied to any in-scope function; the three verify* helpers are pure and have no callers; MissionBypassAttemptBlocked is declared but never emitted. No fund/security impact today, but integrators relying on the "cannot be changed / enforced at contract level" claims should know the enforcement machinery is currently disconnected.

[30] 15. verifyAIProfitCap rounds the AI cap to zero for small totals (safe direction, not exploitable)

MissionEnforcement.verifyAIProfitCap · Confidence: 30 · Severity: Info · Origin: [phase1-only] — precision-math checklist (P-3, P-4)

Description
maxAIShare = (totalAmount * capPercentage) / 100 (line 155) correctly multiplies before dividing and rounds down, which is the protocol-safe direction for a cap check. For very small totalAmount (e.g. totalAmount=3, capPercentage=30 → maxAIShare=0), the AI's allowed share collapses to exactly zero — over-restrictive, never over-permissive. The unguarded multiplication could theoretically overflow only for totalAmount > ~1.15e75, unreachable with any realistic value, and reverts safely under 0.8.x checked arithmetic rather than wrapping.

Fix
None required for safety; document the small-amount edge case if exact proportional behavior matters.

[40] 16. capabilitiesHash can never be updated after registration

ERC8004IdentityRegistry.updateAgentURI · Confidence: 40 · Severity: Info · Origin: [phase1-only] — general checklist (G-9)

Description
updateAgentURI() (lines 112-119) updates only agentURI. There is no function to change capabilitiesHash or re-index the agent in agentsByCapability. Combined with the permanent isRegistered re-registration block (finding [3]'s root cause), an agent's discovery capabilities are frozen for life at first registration.

Fix
Add updateCapabilities(bytes32 newHash) that removes the agent from its old capability bucket and pushes to the new one.

[20] 17. Floating pragma ^0.8.25 across all four files

All in-scope files, line 2 · Confidence: 20 · Severity: Info · Origin: [phase1-only] — general checklist (G-11)

Description
Allows compilation with any 0.8.x ≥ 0.8.25, so deployed bytecode could differ from what was audited if recompiled with a different point release. No overflow/downcast/unchecked-block issues exist in this code otherwise (all uint256, no unchecked blocks, no narrowing casts). Pin an exact version: pragma solidity 0.8.25;.
