Executive Summary

The codebase implements an M-of-N multisig wallet supporting both EOA (ECDSA/secp256k1) and passkey (WebAuthn/secp256r1) signers. Clones are deployed via an EIP-1167 minimal proxy factory using CREATE2. The core signing and threshold logic is sound — no threshold bypass or signature forgery vulnerability was found. Two Medium findings were confirmed by both methodologies, both affecting correctness and compatibility rather than direct fund theft by external attackers.

Finding counts: 2 Medium · 3 Low · 4 Info

Findings

[M-1] initialize() Does Not Validate Passkey Coordinates — Permanent Signer DoS

Severity: Medium
Confirmed by: EthSkills (evm-audit-access-control) + Pashov (access-control-agent, invariant-agent)
Confidence: 80

Location: Multisig.sol:initialize() (lines 95–118) vs Multisig.sol:addPasskeySigner() (lines 161–165)

Description: addPasskeySigner guards against zero public-key coordinates:

if (qx == bytes32(0) || qy == bytes32(0)) revert InvalidSigner();

The initialize function has no equivalent check. Passing passkeyQxs[i] = bytes32(0), passkeyQys[i] = bytes32(0) calls _addSigner with a signer at getPasskeyAddress(0, 0) — a deterministic address controlled by no one — and stores SignerInfo.qx = 0. In _verifySignatures, a signer with qx == 0 requires SignerType.EOA, but no private key exists for that address. The signer slot is permanently frozen: it counts toward total in threshold validation but can never produce a valid signature.

Impact: If threshold == eoaSigners.length + passkeyQxs.length (all signers required) and any passkey has zero coordinates, the multisig is permanently inoperable. Funds locked in it cannot be recovered. Even with threshold < total, the broken signer misleads users about effective quorum.

Exploit Path:

factory.createMultisig(
    [],           // no EOA signers
    [bytes32(0)], // passkey qx = 0 (invalid)
    [bytes32(0)], // passkey qy = 0 (invalid)
    [bytes32(0)],
    1,            // threshold = 1
    salt
) → deploys multisig with one registered signer that can never sign → wallet permanently bricked

Recommendation: Add coordinate validation inside initialize:

for (uint256 i = 0; i < passkeyQxs.length; i++) {
    if (passkeyQxs[i] == bytes32(0) || passkeyQys[i] == bytes32(0)) revert InvalidSigner();
    address pkAddr = getPasskeyAddress(passkeyQxs[i], passkeyQys[i]);
    _addSigner(pkAddr, passkeyQxs[i], passkeyQys[i], credentialIdHashes[i]);
}

[M-2] isValidSignature Applies toEthSignedMessageHash — Breaks EIP-712 Protocol Integrations

Severity: Medium
Confirmed by: EthSkills (evm-audit-signatures) + Pashov (economic-security-agent, periphery-agent)
Confidence: 85

Location: Multisig.sol:isValidSignature() line 319:

bytes32 ethHash = MessageHashUtils.toEthSignedMessageHash(hash);
(address recovered, ECDSA.RecoverError err,) = ECDSA.tryRecover(ethHash, sig.data);

Description: isValidSignature(bytes32 hash, bytes memory signatures) wraps the incoming hash with toEthSignedMessageHash before ECDSA recovery. This requires EOA signers to have signed keccak256("\x19Ethereum Signed Message:\n32" || hash) rather than hash itself.

The ERC-1271 standard is intended for smart contract wallets acting as signers in DeFi protocols. When Seaport, Permit2, CoW Protocol, or similar protocols call isValidSignature(protocolHash, sig), they expect the multisig's signers to have used signTypedData_v4 (EIP-712) to sign the protocol's hash — producing a signature over keccak256("\x19\x01" || domainSep || structHash). This is entirely different from toEthSignedMessageHash(protocolHash).

The NatSpec comment explicitly says "Supports ERC-1271 signature validation so the multisig itself can sign off-chain messages" — but this implementation silently rejects all EIP-712-based protocol signatures, making that stated capability non-functional for the most common DeFi use case.

Exploit Path (protocol integration failure):

  1. Users want the multisig to hold an NFT and make a Seaport listing.
  2. Signers sign the Seaport orderHash using MetaMask signTypedData_v4.
  3. Seaport calls isValidSignature(orderHash, sigs).
  4. Multisig computes toEthSignedMessageHash(orderHash) and fails to recover the expected addresses.
  5. Returns 0xffffffff → Seaport rejects the order → multisig cannot trade.

Note: execTransaction/execBatchTransaction are unaffected — signers correctly use eth_sign for those execution hashes. Only isValidSignature is broken for external protocol use.

Recommendation: Remove toEthSignedMessageHash from isValidSignature. Verify signatures against the raw hash parameter:

// Replace lines 318–321:
(address recovered, ECDSA.RecoverError err,) = ECDSA.tryRecover(hash, sig.data);
if (err != ECDSA.RecoverError.NoError || recovered != sig.signer) return 0xffffffff;

The _verifySignatures function used for execTransaction can retain the toEthSignedMessageHash wrapping unchanged.

[L-1] removeSigner Does Not Clear credentialIdToAddress — Stale Reverse Lookup

Severity: Low
Confirmed by: EthSkills (evm-audit-general) + Pashov (invariant-agent)

Location: Multisig.sol:removeSigner() lines 167–182

Description: removeSigner deletes signerInfo[signer] but does not clear the credentialIdToAddress reverse mapping. After removal, getPasskeyByCredentialId(credId) returns the removed signer's address with qx = qy = 0 (from the deleted signerInfo). Off-chain login UIs relying on this lookup will present incorrect data. If a new passkey with the same credential ID hash is later registered, _addSigner overwrites the mapping correctly, but the stale window persists.

Authentication is not affected: _verifySignatures uses signerInfo (not credentialIdToAddress) for all security checks.

Recommendation: Store credentialIdHash inside SignerInfo and clear it on removal:

struct SignerInfo {
    bool exists;
    bytes32 qx;
    bytes32 qy;
    bytes32 credentialIdHash; // added field
}

// In removeSigner, before deleting signerInfo:
if (info.credentialIdHash != bytes32(0)) {
    delete credentialIdToAddress[info.credentialIdHash];
}
delete signerInfo[signer];

[L-2] CREATE2 Salt Front-Running in MultisigFactory.createMultisig

Severity: Low
Confirmed by: EthSkills (evm-audit-proxies) + Pashov (access-control-agent)

Location: MultisigFactory.sol:createMultisig() lines 32–43

Description: createMultisig uses a caller-supplied bytes32 salt for CREATE2 deployment without binding the salt to msg.sender. A mempool watcher can front-run a pending createMultisig transaction with the same salt, deploying a clone at the victim's predicted address with attacker-controlled signers. The victim's transaction then reverts with CloneCreationFailed (CREATE2 address already occupied).

Amplified impact: If the victim pre-funded the predicted CREATE2 address before deployment (a pattern sometimes used for counterfactual wallets), those funds are now in an attacker-controlled multisig.

Recommendation: Incorporate msg.sender into the effective salt:

bytes32 effectiveSalt = keccak256(abi.encodePacked(msg.sender, salt));
multisig = Clones.cloneDeterministic(implementation, effectiveSalt);

Also update getMultisigAddress to accept msg.sender or a deployer parameter.

[L-3] Clones.sol Assembly Does Not Update Free Memory Pointer

Severity: Low
Confirmed by: EthSkills (evm-audit-assembly) + Pashov (periphery-agent)

Location: Clones.sol:cloneDeterministic() lines 26–36; Clones.sol:predictDeterministicAddress() lines 55–60

Description: Both assembly blocks read the free memory pointer (mload(0x40)), write 55 bytes to that address, and use them for create2 / keccak256, but never advance the pointer. This violates Solidity's memory management contract. While no exploitable corruption occurs in the current code (data is consumed before any subsequent Solidity allocations overwrite it), any future change adding Solidity memory operations between the assembly block and the use of initCodeHash in predictDeterministicAddress could silently corrupt the hash computation.

Recommendation:

assembly {
    let ptr := mload(0x40)
    mstore(ptr, ...)
    mstore(add(ptr, 0x14), shl(0x60, implementation))
    mstore(add(ptr, 0x28), ...)
    mstore(0x40, add(ptr, 0x37))  // advance FMP
    instance := create2(0, ptr, 0x37, salt)
}

[I-1] Custom Hash Scheme Instead of EIP-712

Severity: Info
Location: Multisig.sol:getExecHash() line 209; Multisig.sol:getBatchExecHash() line 214

Description: Execution hashes use keccak256(abi.encode(...)) rather than EIP-712 typed data. Hardware wallets and custody solutions that only support signTypedData_v4 cannot sign execution transactions. Adopting EIP-712 would improve hardware wallet compatibility and provide clearer human-readable signing prompts.

[I-2] Duplicated Signature Verification Logic

Severity: Info
Location: Multisig.sol:_verifySignatures() lines 271–298; Multisig.sol:isValidSignature() lines 304–333

Description: The signer-sort check, signerInfo lookup, and EOA/passkey dispatch logic are duplicated across two functions with different error handling (revert vs return 0xffffffff). Divergence during future maintenance is a latent bug risk. Consider extracting a shared _validateSigners helper that returns a boolean rather than reverting.

[I-3] Empty calls Array Burns Nonce in execBatchTransaction

Severity: Info
Location: Multisig.sol:execBatchTransaction() line 243

Description: execBatchTransaction with an empty calls array succeeds, consuming a nonce and emitting BatchExecuted(0). While not harmful (signers must authorize it), this behavior is undocumented and could confuse users or analytics.

[I-4] removeSigner Is O(n); No Maximum Signer Count

Severity: Info
Location: Multisig.sol:removeSigner() line 174

Description: The linear scan of _signers in removeSigner and the unrestricted _addSigner calls mean gas cost grows with signer count. In practice, multisig signer sets are small (< 20), making this a negligible concern, but a documented signer limit (e.g., require(_signers.length < 256)) would make gas bounds explicit.

Security Properties Verified Sound

The following core security properties were verified to hold through both audit methodologies:

  1. No threshold bypass: The ascending-sort + unique signer check in _verifySignatures prevents the same signer from appearing twice; all submitted signatures must correspond to registered signers.
  2. No signature replay: Execution hashes include block.chainid, address(this), nonce, and deadline. Nonce is incremented before the external call (correct CEI).
  3. No cross-chain replay: block.chainid is dynamically read, not cached.
  4. Implementation protected: _disableInitializers() in Multisig constructor prevents the implementation from being initialized directly.
  5. Atomic factory initialization: MultisigFactory.createMultisig deploys and initializes in a single transaction; no front-run of the initialization step is possible.
  6. Signer type integrity: EOA and passkey slots are mutually exclusive via SignerTypeMismatch checks; an EOA signature cannot satisfy a passkey slot.
  7. OZ ECDSA handles address(0): Using ECDSA.recover (which reverts on invalid signatures) in _verifySignatures; ECDSA.tryRecover in isValidSignature (which returns an error code).
