[1] Removed/de-authorized issuer permanently retains the ability to revoke every credential it ever issued

Severity: High
Origin: [both] — corroborated. Phase 1: evm-audit-general, evm-audit-access-control. Phase 2: 8 of 12 independent attacker agents (access-control, execution-trace, invariant, periphery-adjacent, first-principles, asymmetry, boundary, trust-gap, flow-gap) converged on this exact bug unprompted.
Location: revokeCredential() lines 288-309; removeIssuer() lines 165-168
Description: revokeCredential's authorization is require(msg.sender == cred.issuedBy || msg.sender == owner) (lines 300-304) — it checks the immutable, point-in-time issuedBy field but never re-validates current approvedIssuers status. This is inconsistent with issueCredential/addTaskProof, which both use the onlyIssuer modifier (live approvedIssuers[msg.sender] check) on every call. removeIssuer() only flips the mapping — it has no way to reach into already-stored Credential.issuedBy values. The result: an issuer who is explicitly de-authorized (e.g. for being compromised or malicious) retains permanent, standing power to deactivate every credential it ever issued, indefinitely, with no expiry and no recourse (there is no reactivation function).
Proof of Concept:

  1. owner calls approveIssuer(I).
  2. I calls issueCredential(agentX, capHash, 0) → credential #7 created, issuedBy = I, active = true, permanent (no expiry).
  3. owner discovers I is compromised/malicious and calls removeIssuer(I) — approvedIssuers[I] = false. I is now correctly blocked from issueCredential/addTaskProof (both use onlyIssuer).
  4. I calls revokeCredential(7). The check msg.sender == cred.issuedBy (I == I) passes — approvedIssuers[I] is never read. Credential #7 is deactivated: agentProfiles[agentX].activeCredentials -= 1, agentCapability[agentX][capHash] = 0.
  5. I can repeat step 4 for every credential it ever issued, at any time in the future, fully griefing agents the owner believed were protected by the removal.

Walked end-to-end: no guard interrupts steps 1-4; all actions are normal admin/issuer lifecycle operations (approve → issue → remove → revoke), not an unusual precondition. Harm (permanent, unrecoverable loss of a specific agent's verified credential) is concrete and irreversible — no reactivateCredential exists anywhere in the contract.
Recommendation:

         require(
-            msg.sender == cred.issuedBy || msg.sender == owner,
+            msg.sender == owner ||
+            (msg.sender == cred.issuedBy && approvedIssuers[msg.sender]),
             "VaultfireCapabilityCredentials: only issuer or owner can revoke"
         );

[2] Approved issuer can self-issue a credential to itself as the agent

Severity: Medium (downgraded from an initial High call in phase 1 — see verification note)
Origin: [phase1-only] — evm-audit-general, evm-audit-access-control. Re-examined against source in this synthesis pass: confirmed, no phase-2 agent independently raised this angle.
Location: issueCredential() lines 181-247
Description: issueCredential is gated only by onlyIssuer; nothing requires agent != msg.sender. The owner is auto-approved as issuer in the constructor, and approveIssuer lets owner add any address with no restriction. Any approved issuer that is also a registered active agent in identityRegistry can call issueCredential(self, capabilityHash, expiresAt) and mint itself a fully "active" credential with zero independent verification — directly undermining the contract's stated purpose ("proof that an agent can actually do what it claims").
Proof of Concept: An approved issuer address that is simultaneously isAgentActive == true in the identity registry calls issueCredential(selfAddress, keccak256("data-analysis"), 0). All checks pass (onlyIssuer, isAgentActive, no existing active credential) → succeeds. Can then call addTaskProof repeatedly to fabricate an inflated proof history (compounds with Finding 5).
Verification note: The exploit requires a specific precondition — the acting issuer must also be independently registered as an active agent in a separate, out-of-scope identity-registry contract — and requires a trusted role (an approved issuer) to misuse its granted permission for self-dealing, rather than an arbitrary unprivileged third party. Per this audit's verification standard, this combination of a non-default precondition plus a privileged actor as the "attacker" supports Medium rather than High.
Recommendation: require(agent != msg.sender, "issuer cannot self-issue"); in issueCredential. If self-issuance is intended for owner-bootstrapping, scope that exception narrowly and flag such credentials (e.g. a selfIssued bool) so consumers can discount them.

[3] Unbounded, never-pruned credential/holder arrays; revocation resets the "one active credential" guard, enabling cheap re-issue growth

Severity: Medium (phase 1's dos checklist agent initially rated High assuming a malicious/compromised issuer; reconciled down — see note)
Origin: [both]. Phase 1: evm-audit-dos, evm-audit-general. Phase 2: independently raised by 8+ of 12 agents (as findings by execution-trace, invariant, periphery; as leads by math-precision, economic-security, asymmetry, boundary, numerical-gap, flow-gap).
Location: issueCredential() pushes at lines 232-233; revokeCredential() lines 288-309; getAgentCredentials() lines 323-325; getCapabilityHolders() lines 327-329
Description: _agentCredentials[agent] and _capabilityHolders[capabilityHash] are append-only; nothing removes an element, including on revoke. Critically, revokeCredential() resets agentCapability[cred.agent][cred.capabilityHash] to 0 (line 305), so the very next issueCredential() call for that same pair takes the existingId == 0 fast path and skips the "already exists" check entirely — no need to wait for expiry. A single approved issuer can grow both arrays without bound by alternating issueCredential/revokeCredential on one (agent, capabilityHash) pair. Both arrays are returned in full by view getters, so any on-chain consumer iterating them is exposed to gas-limit DoS once large enough; _capabilityHolders additionally accumulates duplicate entries for the same agent across repeat issuances.
Proof of Concept: Approved issuer loops issueCredential(agent, capHash, ...) → revokeCredential(id) N times (cheap on Base/Arbitrum/Polygon, the chains this contract's NatSpec targets). After N iterations, getAgentCredentials/getCapabilityHolders return arrays large enough that any on-chain consumer calling them in a state-changing transaction runs out of gas and reverts.
Verification note: Triggering the aggressive growth pattern requires a currently-or-formerly-trusted issuer role to act (not an arbitrary unprivileged party), and no on-chain consumer contract is in scope to confirm real gas-limit impact today — reconciled to Medium rather than phase 1's initial High.
Recommendation: Swap-and-pop on revoke; track holder membership via mapping(bytes32 => mapping(address => bool)) to avoid duplicate pushes; replace full-array getters with paginated variants (offset, limit) plus a length getter.

[4] Credential validity fields (Credential.active, agentProfiles.activeCredentials) go stale on passive expiry — direct hit on the client's "expiry enforcement by consumers" focus area

Severity: Medium
Origin: [both]. Phase 1: evm-audit-general (both the getCredential().active angle and the agentProfiles.activeCredentials counter angle). Phase 2: independently raised as full findings by 4 of 12 agents (invariant, periphery, first-principles, flow-gap) and as leads by 2 more (boundary, numerical-gap).
Location: Credential.active; getCredential() line 315; agentProfiles.activeCredentials; contrast with the correctly-computed hasActiveCredential() line 331-336
Description: active is only flipped false by explicit revokeCredential() or by the lazy-replacement branch inside issueCredential() when re-issuing for the same capability — never by the mere passage of expiresAt. Only the purpose-built hasActiveCredential() correctly ANDs active with the expiry check. Any consumer reading getCredential() and checking .active alone (a natural mistake given the field name) treats an expired credential as currently valid. The same staleness applies to agentProfiles.activeCredentials, which over-counts real-time-valid credentials after natural expiry with no follow-up transaction.
Proof of Concept: Issue with expiresAt = block.timestamp + 1. One block later the credential is logically expired (hasActiveCredential correctly returns false), but getCredential(id).active still reads true and getAgentProfile(agent).activeCredentials still counts it — until someone happens to call revokeCredential or reissue for that exact (agent, capabilityHash) pair.
Recommendation: Compute real-time validity in getCredential()'s returned struct (active && (expiresAt==0 || expiresAt>block.timestamp)) without touching storage, and/or document prominently that only hasActiveCredential() reflects real-time validity — raw active/activeCredentials are lifecycle-only fields, not consumer-safe validity signals.

[5] addTaskProof is not restricted to the credential's original issuer

Severity: Medium
Origin: [both]. Phase 1: evm-audit-access-control (full finding, concrete PoC). Phase 2: raised as leads by periphery and trust-gap agents (demoted to lead under phase 2's stricter "trusted-role-trigger" gating, since it requires a second approved issuer to act).
Location: addTaskProof() lines 254-281
Description: Only onlyIssuer is checked — not msg.sender == cred.issuedBy. Any currently-approved issuer, not just the one accountable for a given credential, can inflate taskProofCount/totalTaskProofs on any active, non-expired credential it never issued.
Proof of Concept: Issuer A issues credential #1 to Agent X. Unrelated Issuer B calls addTaskProof(1) repeatedly — succeeds every time, taskProofCount climbs with no relation to work B verified. Compounds with Finding 2 (self-issued credentials can then be padded by the same or a colluding issuer).
Recommendation: require(msg.sender == cred.issuedBy || msg.sender == owner).

[6] identityRegistry.isAgentActive() status is checked only once, at issuance — never re-validated afterward

Severity: Medium
Origin: [phase2-only] — independently raised by 6 of 12 agents (economic-security, access-control, execution-trace, invariant, periphery, flow-gap; the last formalized it as a full finding). Re-examined against source in this synthesis pass: confirmed — identityRegistry is referenced exactly once in the whole contract, at line 195 inside issueCredential; no other function queries it.
Location: issueCredential() line 195; contrast with hasActiveCredential() (never re-checks the registry) and addTaskProof() (never re-checks the registry)
Description: The only real-world trust check this contract performs — "is this agent actually legitimate" — happens once at issuance and is never revalidated. If the identity registry later deactivates/bans an agent (for misconduct unrelated to this contract), that agent's existing credentials (especially permanent ones, expiresAt == 0) continue reporting as valid via hasActiveCredential() forever, and issuers can keep calling addTaskProof to further pad its record. This directly contradicts the contract's own stated design goal: "agents with verified credentials get priority... when routing tasks."
Proof of Concept: Agent X receives a permanent credential while isAgentActive(X) == true. X is later banned/deactivated in the identity registry (an event this contract has no visibility into). hasActiveCredential(X, capHash) still returns true indefinitely; any downstream task router trusting this contract's signal keeps prioritizing a banned agent.
Recommendation: Re-check identityRegistry.isAgentActive(agent) inside hasActiveCredential() (and/or gate addTaskProof on it), or provide a mechanism for issuers/owner to mass-revoke a deactivated agent's credentials.

[7] identityRegistry.isAgentActive() external call has no try/catch, gas cap, or fallback

Severity: Medium
Origin: [phase1-only] — evm-audit-dos. Re-examined against source: confirmed — no try/catch anywhere in the contract, no {gas: ...} stipend on the call at line 195, identityRegistry is immutable with no way to swap it out.
Location: issueCredential() lines 193-196
Description: The contract's only credential-minting entry point makes a mandatory, unmitigated external call to the immutable identityRegistry. If the registry ever reverts (paused, buggy upgrade, compromised admin), issuance is permanently bricked with no recourse — the registry address cannot be changed. Default ABI decoding also forwards effectively all remaining gas and copies the full return buffer, so a misbehaving registry could inflate return data to grief the caller's gas budget.
Proof of Concept: If the (out-of-scope) registry's admin pauses it or a bug makes isAgentActive revert unconditionally, every issueCredential call reverts permanently with no owner-side workaround in this contract.
Recommendation: Wrap in try/catch with a distinct "registry unavailable" revert reason; bound forwarded gas or use a fixed-size staticcall return read; consider making the registry address governance-updatable (with timelock).

[8] No way for on-chain consumers to filter to only-active credentials without O(n) extra calls

Severity: Low
Origin: [phase1-only] — evm-audit-dos. Re-examined against source: confirmed — getAgentCredentials() returns the raw, unfiltered ID array; a caller must independently call getCredential(id) per entry to determine current validity.
Location: getAgentCredentials() lines 323-325 combined with getCredential() lines 315-321
Description: Corollary of Findings 3 and 4 — because historical IDs are never pruned and validity fields go stale, any consumer wanting only currently-active credentials must perform one extra call per historical entry. This compounds gas cost for any on-chain consumer even under purely honest, non-malicious usage (normal revoke/re-issue churn over time).
Recommendation: Maintain a separate, actively-pruned index of currently-active credential IDs per agent, since agentCapability[agent][capabilityHash] already gives O(1) lookup of the current active ID for a known capability.

[9] Owner is a single, immutable point of failure with unrestricted, instant, uncapped control over the issuer set

Severity: Low
Origin: [phase1-only] — evm-audit-general, evm-audit-access-control. Re-examined against source: confirmed — owner is immutable (line 58), set once in the constructor, no transfer/renounce/recovery function exists; approveIssuer/removeIssuer have no timelock and no cap on issuer count.
Location: owner (line 58); approveIssuer()/removeIssuer() (lines 159-168); constructor (lines 130-136)
Description: This is a design/centralization observation rather than an independently-exploitable bug (no unprivileged attacker path exists) — noted because it materially amplifies the blast radius of Findings 1, 2, and 5: if the owner key is compromised, an attacker gets instant, undelayed ability to approve sybil issuers and mint/inflate fraudulent credentials system-wide; if lost, the issuer set is frozen forever (no new issuers, no removal of a bad one).
Recommendation: Use a multisig/timelock as owner; add a timelock delay on approveIssuer; consider a cap or governance step for growing the issuer set. Treat as an operational/deployment recommendation rather than a code defect.

[10] unchecked counter increment lacks inline safety justification

Severity: Info
Origin: [both] — phase 1's evm-audit-precision-math agent and phase 2's math-precision attacker agent both traced this independently and both concluded it is not exploitable (would require ~2^256 issuances to wrap).
Location: issueCredential() line 218 — unchecked { credentialId = ++_credentialCounter; }
Recommendation: Add a comment justifying the unchecked block's safety, or drop it — the gas savings are negligible relative to the rest of the function's SSTOREs.
