[95] 1. wire()'s re-wire gate checks raw token balance, not the ledger — permanently, permissionlessly griefable with a 1-wei donation

AgentDepositVault.wire() · Confidence: 95 · Severity: High · [both — phase1: general/erc20/dos; phase2: 11/12 agents independently]

Description
Re-wiring taskRegistry/treasury/reputationRegistry (once already set) requires IERC20(usdcToken).balanceOf(address(this)) == 0 (L69-72). Any address can call usdcToken.transfer(vault, 1) directly — bypassing topUp/pullEmergencyTopUp/creditDisputeBond, so deposits is untouched — to permanently keep the raw balance non-zero. No sweep/rescue function exists anywhere in the contract.

// L68-72
if (taskRegistry != address(0)) {
    require(
        IERC20(usdcToken).balanceOf(address(this)) == 0,
        "AgentDeposit: live funds - cannot re-wire"
    );
}

Proof of Concept
(1) Vault wired once. (2) All legitimate agents withdraw to zero — deposits sums to 0, balanceOf(vault) == 0. (3) Any address calls usdcToken.transfer(vaultAddress, 1) — ~$0.000001, no approval or vault interaction needed. (4) Owner later calls wire(...) to rotate a compromised/buggy taskRegistry — reverts forever at L69-72, since nothing in the contract can ever move that untracked 1 wei back out. Verification note: raised independently by 11 of 12 blind Phase-2 attack agents plus 3 of 5 Phase-1 domain agents, all with matching PoCs — the single most corroborated finding in this engagement. Severity set to High (permanent DoS of the owner's only recovery/migration mechanism), recalibrated up from an initial Medium-leaning read given the strength and unanimity of independent corroboration and the zero cost / zero precondition of the attack.

Fix

+ uint256 public totalDeposits;
  function wire(address _taskRegistry, address _treasury, address _reputationRegistry) external onlyOwner {
      require(_taskRegistry != address(0) && _treasury != address(0) && _reputationRegistry != address(0), "AgentDeposit: zero addr");
      if (taskRegistry != address(0)) {
-         require(IERC20(usdcToken).balanceOf(address(this)) == 0, "AgentDeposit: live funds - cannot re-wire");
+         require(totalDeposits == 0, "AgentDeposit: live funds - cannot re-wire");
      }
      ...
  }

(with totalDeposits incremented/decremented alongside every deposits[...] write throughout the contract)

[80] 2. withdraw()'s external call to taskRegistry precedes the ledger write — no reentrancy guard in the contract

AgentDepositVault.withdraw · Confidence: 65 · Severity: High (confidence-capped for an unverifiable out-of-scope precondition) · [phase2 only: agent 4 full trace, agent 2 corroborating lead]

Description
withdraw() is the only function where an external call to an owner-configurable (non-hardcoded) contract happens before the corresponding ledger write, and no function in the file uses nonReentrant (no ReentrancyGuard imported anywhere).

// L93-96
uint256 maxW = ITaskRegistry(taskRegistry).maxWithdrawableDeposit(msg.sender);
require(amount <= maxW, "AgentDeposit: exceeds withdrawable");
deposits[msg.sender] -= amount;
IERC20(usdcToken).safeTransfer(msg.sender, amount);

Proof of Concept
Agent (smart-contract wallet) A has deposits[A] = 100e6. A calls withdraw(60e6). If ITaskRegistry.maxWithdrawableDeposit is not enforced as a true view function (unknown — the interface is out of scope) and its execution can hand control back to A, then during the external call at L93, A reenters withdraw(40e6): the nested call re-queries maxWithdrawableDeposit (still sees deposits[A] == 100e6), passes, decrements to 60e6, transfers 40e6. Control returns to the outer frame, which decrements the remaining 60e6 and transfers it too. Total extracted: 100e6 (A's full balance) in one transaction. Solidity 0.8's checked arithmetic caps total extraction at the agent's own recorded balance — this is not a cross-agent drain — but it lets an agent bypass whatever per-call throttle or partial-withdrawal policy taskRegistry.maxWithdrawableDeposit was designed to enforce.
Verification note: the chain is fully traced and internally consistent given the stated precondition; it cannot be confirmed or ruled out without ITaskRegistry's source. Confidence capped at 65 to reflect that dependency, but the underlying code-level gap (no reentrancy guard on the one call-before-write function in the contract) is unconditionally real regardless of ITaskRegistry's actual behavior.

- contract AgentDepositVault is Ownable2Step {
+ contract AgentDepositVault is Ownable2Step, ReentrancyGuard {
  ...
-  function withdraw(uint256 amount) external {
+  function withdraw(uint256 amount) external nonReentrant {

[85] 3. Blocklisted worker/poster counterparty permanently reverts debitDismissFee/debitLeaveFee

AgentDepositVault.debitDismissFee / debitLeaveFee · Confidence: 85 · Severity: High · [phase1 only: erc20 + dos domains, corroborated independently by both]

Description
Both functions push comp directly to the counterparty's wallet in the same atomic transaction as the debited party's ledger decrement and the treasury cut, with no try/catch or fallback. Real USDC enforces an issuer-controlled blocklist — if the counterparty is ever blocklisted, safeTransfer reverts and the entire function reverts, permanently blocking the other party from resolving that task binding via this path.

// L189-192 (debitDismissFee)
deposits[poster] -= fee;
IERC20(usdcToken).safeTransfer(worker, comp);
IERC20(usdcToken).safeTransfer(treasury, protocolShare);

Proof of Concept
Worker's address is added to USDC's blocklist while bound to a task. Poster calls (via taskRegistry) debitDismissFee(poster, worker) → safeTransfer(worker, comp) at L191 reverts because worker is blocklisted → the whole call reverts → poster can never dismiss this worker through this path. Symmetric for debitLeaveFee/blocklisted poster.

Fix

- IERC20(usdcToken).safeTransfer(worker, comp);
+ // credit an internal claimable balance instead of a direct push, so a blocklisted
+ // counterparty cannot block the debited party's state transition
+ pendingPayouts[worker] += comp;
  IERC20(usdcToken).safeTransfer(treasury, protocolShare);

(with a separate claimPayout() function for counterparties to pull their pendingPayouts balance)

[75] 4. debitDisputeBond is the only debit path exempt from the MIN_ENTRY_BALANCE/MIN_TASK_BALANCE floor

AgentDepositVault.debitDisputeBond · Confidence: 90 · Severity: Medium · [both — phase1: general/access-control; phase2: agents 5, 11, 12 independently]

Description
debitAccessFee (L172), debitDismissFee (L188), debitLeaveFee (L215) all require deposits[x] >= MIN_ENTRY_BALANCE + fee. debitDisputeBond only checks deposits[agent] >= amount (L152) — a legitimate call from arbitrationModule can drive an agent's ledger to exactly 0, breaking the floor invariant meetsEntryMinimum/meetsTaskMinimum assume holds for an active agent, with no notification back to taskRegistry.

// L150-156
function debitDisputeBond(address agent, uint256 amount) external onlyArbitration {
    require(amount > 0, "AgentDeposit: zero bond");
    require(deposits[agent] >= amount, "AgentDeposit: insufficient for bond");
    deposits[agent] -= amount;
    IERC20(usdcToken).safeTransfer(arbitrationModule, amount);
    emit DisputeBondDebited(agent, amount);
}

Proof of Concept
Agent has deposits[agent] == MIN_ENTRY_BALANCE (25_000_000). arbitrationModule calls debitDisputeBond(agent, 25_000_000) — succeeds, deposits[agent] becomes 0. meetsEntryMinimum/meetsTaskMinimum now both return false with no fee-debit path having enforced this transition, and if taskRegistry still considers the agent bound to a live task per its own (out-of-scope) state, the two systems' views of the agent's eligibility diverge.

Fix

  function debitDisputeBond(address agent, uint256 amount) external onlyArbitration {
      require(amount > 0, "AgentDeposit: zero bond");
      require(deposits[agent] >= amount, "AgentDeposit: insufficient for bond");
+     require(deposits[agent] - amount >= MIN_TASK_BALANCE || deposits[agent] - amount == 0, "AgentDeposit: below min task balance");
      deposits[agent] -= amount;

(or, if bonds are intentionally floor-exempt, document this explicitly in NatSpec and confirm ITaskRegistry handles the resulting sub-floor state)

[70] 5. Owner (wire/setArbitrationModule) and arbitrationModule have no timelock; a compromised trusted role can drain deposits down to the floor (or to zero via Finding 4)

AgentDepositVault.wire / setArbitrationModule / debitAccessFee / debitDismissFee / debitLeaveFee · Confidence: 85 · Severity: Medium · [phase1 only: access-control domain]

Description
taskRegistry/treasury/reputationRegistry/arbitrationModule are owner-settable with no timelock — the only friction is Finding 1's (weak) zero-balance gate on wire(); setArbitrationModule has no gate at all beyond "not already set." A compromised or malicious owner key can point these at attacker-controlled contracts, which then have full authority to call every registry/arbitration-gated debit function.

Proof of Concept
Owner (compromised) calls wire(evilRegistry, evilTreasury, reputationRegistry) at a zero-balance moment, and/or setArbitrationModule(evilArbitration). Agents deposit normally. Attacker's evilTreasury.ACCESS_FEE() is crafted to drain each agent to the floor via debitAccessFee; attacker (as evilArbitration) calls debitDisputeBond(agent, remainingBalance) (Finding 4) to take the rest.
Severity note: per the standard severity taxonomy ("Medium: ... or owner-only fund loss"), this requires a trusted-role compromise as precondition, which excludes it from the Critical/High bands reserved for permissionless, no-precondition fund loss — recalibrated down from an initial Critical-leaning read for exactly this reason.

Fix: Add a timelock (48-72h) for all four setters with a pending-value event, so agents/monitors can react; consider a multisig/governance-controlled owner. Independently close Finding 4.

[75] 6. applyPlatformPenalty() lets a reverting reputationRegistry.resetSubject veto the platform block itself

AgentDepositVault.applyPlatformPenalty · Confidence: 85 · Severity: Medium · [both — phase1: dos domain; phase2: agent 12]

Description
The blockedUntil write and the conditional resetSubject call happen atomically with no try/catch — if resetSubject reverts, the whole call (including the block) reverts.

// L234-240
function applyPlatformPenalty(address agent) external onlyRegistry {
    blockedUntil[agent] = block.timestamp + PLATFORM_BLOCK_DURATION;
    emit PlatformBlocked(agent, blockedUntil[agent]);
    if (reputationRegistry != address(0)) {
        ReputationRegistry(reputationRegistry).resetSubject(agent);
    }
}

Proof of Concept
reputationRegistry.resetSubject reverts for a given agent (paused registry, edge-case revert, bug). taskRegistry calls applyPlatformPenalty(agent) → reverts entirely at L238 → blockedUntil[agent] never set → agent continues operating unblocked despite taskRegistry having identified misbehavior.

Fix

  function applyPlatformPenalty(address agent) external onlyRegistry {
      blockedUntil[agent] = block.timestamp + PLATFORM_BLOCK_DURATION;
      emit PlatformBlocked(agent, blockedUntil[agent]);
      if (reputationRegistry != address(0)) {
-         ReputationRegistry(reputationRegistry).resetSubject(agent);
+         try ReputationRegistry(reputationRegistry).resetSubject(agent) {} catch {
+             emit ReputationResetFailed(agent);
+         }
      }
  }

[70] 7. Fee-debit functions are a single point of failure on treasury, including a self-lockout via collectAzlAccessFee

AgentDepositVault.debitAccessFee / debitDismissFee / debitLeaveFee · Confidence: 80 · Severity: Medium · [phase1 only: dos domain, corroborated by phase2 agent 6's "unbounded external trust" lead]

Description
Each function makes 3-4 sequential external calls into treasury, all of which must succeed. collectAzlAccessFee pulls a second (AZL/AZZLE) token from the debited party's wallet — an agent fully funded in USDC but lacking AZZLE approval/balance is completely blocked from posting/claiming/dismissing/leaving, with no partial-success path.

Proof of Concept
Agent has deposits[agent] >= MIN_ENTRY_BALANCE + fee but no AZZLE approval to treasury. taskRegistry calls debitAccessFee(agent, kind) → collectAzlAccessFee at L176 reverts on insufficient allowance → the whole call reverts → agent locked out of an otherwise-fully-funded action.

Fix: Decouple the AZL collection from the critical USDC-debit path (best-effort/try-catch, or surface the AZZLE-approval requirement clearly upstream) rather than making it a hard blocker.

[55] 9. Registry/arbitration-driven debit and credit functions do not check blockedUntil

AgentDepositVault.debitDisputeBond / creditDisputeBond / debitAccessFee / debitDismissFee / debitLeaveFee · Confidence: 85 · Severity: Low · [both — phase1: general/access-control; phase2: agents 8, 12]

Description

Fix: Decide and document the intended policy (blocked agents debitable but not creditable, or fully frozen) and apply it consistently across all five functions.

[55] 11. arbitrationModule has no rotation/reset path once set

AgentDepositVault.setArbitrationModule · Confidence: 70 · Severity: Low · [phase2 only: agents 6, 8]

Description
Unlike taskRegistry/treasury/reputationRegistry (jointly re-settable via wire()), arbitrationModule can be set exactly once with no reset function. If later found buggy, compromised, or wrongly set, debitDisputeBond/creditDisputeBond are permanently pinned to it.

Fix: Consider allowing rotation under a similar (or stronger, timelocked) gate as wire(), rather than a true one-time set with no recovery path.

[50] 12. Ledger credited by requested amount, not measured balance delta, on all inbound-transfer paths

AgentDepositVault.topUp / pullEmergencyTopUp / creditDisputeBond · Confidence: 60 · Severity: Low · [both — phase1: general/erc20; phase2: agents 5, 9, 12, all concluding not concretely exploitable against a standard token]

Description
All three credit paths call safeTransferFrom(..., amount) then unconditionally deposits[x] += amount, with no pre/post balanceOf delta check. If usdcToken (immutable, chosen once at construction) were ever fee-on-transfer or deflationary, deposits would permanently over-state actual holdings.

Proof of Concept
Not concretely exploitable against a standard, non-fee-on-transfer USDC deployment (today's real USDC is not fee-on-transfer) — flagged as a latent assumption tied to the one-time, unrecoverable token choice at deploy, not a live exploit.

Fix: Measure the actual balance delta and credit that instead of the caller-supplied amount, as defense-in-depth given usdcToken's immutability.
