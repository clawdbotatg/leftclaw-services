Security Audit Report — PublicMintRescueV5

Target: 0x4738086538893cBbadC431EC8FEF8f426496d52C
Chain: Base (chain id 8453) — verified source pulled from BaseScan. Identical bytecode observed at the same address on Ethereum mainnet (unverified there).
Scope: Single contract, PublicMintRescueV5.sol, 502 lines, no external imports/inheritance.
Methodology: Two-phase audit — Phase 1 checklist breadth (8 domain checklists: general, precision-math, signatures, assembly, access-control, erc721/erc1155, erc20, dos) run in parallel, followed by Phase 2 attacker-mindset depth (12 independent agents: 9 specialty + 3 gap-hunter), run blind to Phase 1's findings. A final reconciliation pass cross-checked both phases against each other and against the source.

What this contract does

PublicMintRescueV5 is designed to be the target of an EIP-7702 delegation from a compromised EOA. Once delegated, address(this) in the contract's code is the compromised wallet. A relayer ("sponsor") submits executeBatch() carrying an EIP-712 signature from the EOA's own key, authorizing: a short batch of arbitrary calls (typically claiming/minting an asset), and a sweep of the EOA's ERC20/ERC721/ERC1155/native balances to a signer-chosen safeRecipient. A "capture-and-sweep" mechanism uses the token receiver hooks (onERC721Received etc.) to record exactly which asset IDs arrive during the batch, so they can be swept atomically without needing to predict mint-generated token IDs off-chain (the race condition this replaces from V4).

The overall signature/replay/reentrancy scaffolding is well-built: EIP-712 domain binds block.chainid + address(this) (the EOA itself), nonce is strictly sequential, the sponsor is bound as the live msg.sender inside the digest (blocking front-running/relay-substitution), signature malleability is correctly guarded, and nonReentrant closes off reentrancy. Both audit phases independently confirmed all of this is sound. The real issues live in the newer "capture-and-sweep" mechanism and its interaction with strictMode.

Findings

[1] Capture-buffer overflow silently strands assets, defeating strictMode's all-or-nothing guarantee

Severity: High
Origin: [both] — phase1: general/erc721/access-control checklists; phase2: independently raised as a full FINDING by 8 of 12 attacker-mindset agents (execution-trace, invariant, periphery, asymmetry, boundary, both numerical- and flow-gap-hunters, trust-gap-hunter), the strongest convergence of the entire audit.

Location: _record() L358-366, onERC721Received/onERC1155Received/onERC1155BatchReceived L189-215, executeBatch() L157-182, _sweepCaptured() L329-343.

Description: During executeBatch, capturing is set to 1 for the duration of the batch-call loop (L162, L177). Every inbound ERC721/1155 transfer during that window fires a receiver hook, which calls _record. Once capturedCount reaches MAX_CAPTURED = 50 (L82), _record takes this branch:

if (c >= MAX_CAPTURED) {
    emit CaptureBufferOverflow(token, tokenId);
    return;                                    // <-- no revert, ever
}

This function has no visibility into request.strictMode at all — it is called from the receiver hooks, which never receive or check the flag. Contrast this with every other failure path in the contract, which honors strictMode explicitly:

// _sweep, L304/309/314, and _sweepCaptured, L340 — all do this:
if (!ok && request.strictMode) revert StrictSweepFailed();

The result: a batch call that mints/delivers more than 50 tokens (a single bulk-mint call, or an onERC1155BatchReceived with >50 ids in one shot, L201-215) silently drops everything past the 50th into the void — never recorded, never attempted, never even failing in a way strictMode can catch. _sweepCaptured only ever iterates store.capturedCount (≤50, L332), so it has nothing to fail on. executeBatch completes normally and emits MintRescueExecuted (L181) as if the rescue fully succeeded, even under strictMode=true.

Proof of Concept:

  1. Victim's EOA delegates to this contract via EIP-7702; victim signs a strictMode=true batch whose one signed call claims/mints 60 NFTs from a bulk-mint contract in a single call (well within MAX_CALL_GAS_LIMIT=1_000_000/MAX_TOTAL_CALL_GAS_LIMIT=5_000_000).
  2. Sponsor submits executeBatch. Each of the 60 _safeMints fires onERC721Received → _record. Slots 0-49 fill normally; for tokens 51-60, c >= MAX_CAPTURED is true, so each just emits CaptureBufferOverflow and returns.
  3. capturing resets to 0; _sweepCaptured sweeps only the 50 recorded tokens to safeRecipient. executeBatch finishes and emits MintRescueExecuted — no revert, despite strictMode=true.
  4. The remaining 10 NFTs sit in the still-key-compromised EOA. The attacker who originally compromised the key (the entire reason this rescue is happening) can take them at any time afterward — the exact race condition this contract's "atomic capture-and-sweep" design was built to eliminate is silently reopened for anything past the 50th asset.

Gate walk: no guard interrupts this (Gate 1 clears — explicitly no strictMode check exists in the overflow branch); reachable through completely normal usage of a single bulk-mint call, no privileged action required (Gate 2/3 clear); results in material, identifiable loss — assets the rescue was specifically trying to save remain exposed to the known-compromised key (Gate 4 clears). Rated High rather than Critical because it requires a specific batch shape (>50 items delivered in one rescue), not an unconditional drain.

Recommendation:

 struct MintRescueStorage {
     uint256 rescueNonce;
     uint256 reentrancyLock;
     uint256 capturing;
     uint256 capturedCount;
+    uint256 overflowed;
     CapturedItem[MAX_CAPTURED] captured;
 }
@@
 function _record(MintRescueStorage storage store, address token, uint256 tokenId, bool isERC1155) internal {
     uint256 c = store.capturedCount;
     if (c >= MAX_CAPTURED) {
         emit CaptureBufferOverflow(token, tokenId);
+        store.overflowed = 1;
         return;
     }
     store.captured[c] = CapturedItem({token: token, isERC1155: isERC1155, tokenId: tokenId});
     store.capturedCount = c + 1;
 }
@@
 function _sweepCaptured(address safeRecipient, bool strictMode) internal {
     MintRescueStorage storage store = _mintRescueStorage();
+    if (strictMode && store.overflowed == 1) revert StrictSweepFailed();
     uint256 n = store.capturedCount;
     ...
     store.capturedCount = 0;
+    store.overflowed = 0;
 }

This makes an incomplete strict-mode capture fail loudly instead of silently succeeding. Also consider raising/removing the fixed 50-slot cap, since the loop is already gas-bounded by the batch's own limits.

[2] Untrusted batch-call target can deliberately force a strictMode rescue to revert (unauthenticated capture-hook injection)

Severity: Medium
Origin: [both] — phase1: access-control checklist agent (flagged this exact mechanism independently); phase2: full FINDING from the periphery agent, corroborated as a lead by 3 more agents (invariant, first-principles, trust-gap-hunter).

Location: onERC721Received() L189-193, onERC1155Received() L195-199, _sweepCaptured() L329-343, _sweepERC721() L391-413.

Description: The receiver hooks record (msg.sender, tokenId) unconditionally whenever store.capturing == 1, with no verification that a real transfer actually happened:

function onERC721Received(address, address, uint256 tokenId, bytes calldata) external returns (bytes4) {
    MintRescueStorage storage store = _mintRescueStorage();
    if (store.capturing == 1) _record(store, msg.sender, tokenId, false);
    return ERC721_RECEIVED;
}

Because capturing stays 1 for the whole batch-call loop, any contract invoked as one of the signed batch calls can call this hook directly, mid-execution, with any tokenId it likes. If it supplies an id it doesn't actually own, _sweepCaptured's later _erc721OwnerOf check (L397-401) fails ("not owner"), and under strictMode this reverts the entire batch via StrictSweepFailed (L340) — not just the poisoned entry, but every other asset the batch would otherwise have successfully rescued (other ERC20/native sweeps included, since a revert unwinds the whole transaction).

This is directly relevant to this contract's threat model: its entire purpose (PublicMintRescue) is interacting with third-party "public mint" contracts, which are inherently less trusted than the rest of the signed batch — exactly the kind of target that could behave adversarially (whether maliciously or just buggy).

Proof of Concept: Victim signs a strictMode=true batch that (a) sweeps an existing ERC20 balance and native ETH, and (b) calls a "mint" contract M. M, when invoked, first calls address(this).onERC721Received(0, 0, 999, "") directly (an id M does not own as address(this)), then does whatever else it does (or nothing). _sweepCaptured later calls _sweepERC721(M, 999, safeRecipient), finds ownerOf(999) != address(this), returns false, and strictMode reverts the entire transaction — including the ERC20 and native sweeps that had nothing to do with M.

Recommendation: Verify real ownership/balance before recording, not just that a call arrived:

 function onERC721Received(address, address, uint256 tokenId, bytes calldata) external returns (bytes4) {
     MintRescueStorage storage store = _mintRescueStorage();
-    if (store.capturing == 1) _record(store, msg.sender, tokenId, false);
+    if (store.capturing == 1) {
+        (bool ok, address owner) = _erc721OwnerOf(msg.sender, tokenId);
+        if (ok && owner == address(this)) _record(store, msg.sender, tokenId, false);
+    }
     return ERC721_RECEIVED;
 }

Apply the analogous balance check to the ERC1155 hooks.

[3] Redundant capture + explicit listing of the same asset reverts an otherwise-successful strictMode rescue

Severity: Medium
Origin: [both] — phase1: general + erc721 checklist agents; phase2: full FINDING from 3 of 12 agents (first-principles, numerical-gap-hunter, flow-gap-hunter), corroborated as a lead by 6 more (near-unanimous across the panel).

Location: executeBatch() L179-180 (_sweepCaptured runs before _sweep), _sweep() L301-315, _sweepERC721() L391-413, _sweepCapturedERC1155() L348-356.

Description: _sweepCaptured always runs before _sweep (L179-180). If a signer lists an asset in erc721Items/erc1155Items that also happens to arrive via capture during the same batch (e.g., a cautious signer redundantly listing the tokenId they expect to mint, or simply not realizing capture already covers it), the capture pass moves it first. The subsequent explicit sweep for the same asset then fails its precondition check:

// _sweepERC721, L397-401
(bool ownerOk, address owner) = _erc721OwnerOf(token, tokenId);
if (!ownerOk || owner != address(this)) {          // now owned by safeRecipient, not this
    emit SweepERC721Failed(token, tokenId, "not owner");
    return false;
}

// _sweep, L308-309
bool ok = _sweepERC721(item.token, item.tokenId, request.safeRecipient);
if (!ok && request.strictMode) revert StrictSweepFailed();

Under strictMode, this reverts the entire transaction — including the already-successful capture sweep, since a Solidity revert unwinds every state change made earlier in the same call. The net effect: a rescue that actually succeeded end-to-end reports total failure and must be retried, costing time during an active key-compromise race. (The ERC1155 captured path already handles the analogous re-visit gracefully — _sweepCapturedERC1155 at L354 treats a zero remaining balance as success — but no equivalent idiom exists on the ERC721 path or the reverse direction: captured-then-explicit.)

Proof of Concept: Sign a strictMode=true batch that mints ERC721 (C, 7) and also lists erc721Items = [{C, 7}] as a defensive redundancy. Trace: capture records (C,7) → _sweepCaptured transfers it to safeRecipient successfully → _sweep's explicit pass calls _sweepERC721(C, 7, safeRecipient) → ownerOf(7) == safeRecipient != address(this) → returns false → revert StrictSweepFailed(). Nothing is rescued (the tx fully reverts), rescueNonce is not consumed, and the signer must diagnose and re-sign without the duplicate.

Recommendation: Treat "asset already at safeRecipient" as success rather than failure:

 function _sweepERC721(address token, uint256 tokenId, address safeRecipient) internal returns (bool) {
     if (token == address(0) || token.code.length == 0) {
         emit SweepERC721Failed(token, tokenId, "not contract");
         return false;
     }

     (bool ownerOk, address owner) = _erc721OwnerOf(token, tokenId);
+    if (ownerOk && owner == safeRecipient) return true;   // already delivered (e.g. by capture pass)
     if (!ownerOk || owner != address(this)) {
         emit SweepERC721Failed(token, tokenId, "not owner");
         return false;
     }
     ...

Apply the same idiom to _sweepERC1155, mirroring the existing bal==0 → return true pattern already used in _sweepCapturedERC1155.

[4] EIP-712 struct hides calls/asset lists behind opaque bytes32 hashes — blind-signing / non-conformance

Severity: Low
Origin: [both] — phase1: general + signatures checklist agents; phase2: access-control agent flagged the same non-standard encoding as Info.

Location: MINT_RESCUE_TYPEHASH L67-69, _digest() L251-269, _hashCalls() L271-288.

Description: The signed MintRescueAuth type declares callsHash/erc20Hash/erc721Hash/erc1155Hash as flat bytes32 rather than true nested EIP-712 array/struct members. callsHash at least uses a proper per-item CALL_ITEM_TYPEHASH struct hash; the three asset-list hashes use plain keccak256(abi.encode(array)) (L258-260) with no item typehash at all. A standards-compliant wallet's typed-data UI can therefore render only opaque 32-byte values for the calls and every asset being swept — not the actual call targets/calldata or token/amount lists — which is a meaningful transparency gap for a tool whose safety model depends on the signer (often under stress, having just discovered their key is compromised) reviewing exactly what they're authorizing.

Recommendation: Declare the true nested struct types (CallItem[], ERC721Item[], ERC1155Item[]) in the EIP-712 type string and encode arrays per spec (keccak of concatenated per-item struct hashes) so compliant wallets can decode and display the content being authorized.

[5] Non-canonical bool/address ABI-decode can turn a graceful sweep failure into a whole-batch revert

Severity: Low
Origin: [phase1 only] — erc20 checklist agent. Re-verified against source during reconciliation (no phase-2 agent independently raised this).

Location: _erc20Transfer() L455-461, _erc721OwnerOf() L463-467.

function _erc20Transfer(address token, address to, uint256 amount) internal returns (bool) {
    (bool success, bytes memory data) = token.call(abi.encodeWithSelector(ERC20_TRANSFER_SELECTOR, to, amount));
    if (!success) return false;
    if (data.length == 0) return true;
    if (data.length == 32) return abi.decode(data, (bool));   // reverts on non-canonical word
    return false;
}

Description: The sweep helpers are designed to tolerate weird tokens gracefully (the beforeBal/afterBal delta is the real source of truth downstream). But abi.decode(data, (bool)) reverts if the 32-byte word isn't canonically 0/1; abi.decode(data, (address)) similarly reverts on a dirty upper-12-bytes word. Neither call is wrapped in try/catch, so a token/collection returning a non-canonical value reverts the whole executeBatch — defeating the documented non-strict-mode "keep going on a bad asset" behavior, since the balance-delta check downstream would otherwise have handled a merely-lying-but-canonical token correctly.

Recommendation: Decode defensively without reverting — e.g. treat any non-zero 32-byte word as true, or mask the address word instead of abi.decode — so a malformed return degrades to a per-token failure rather than aborting the batch.

[6] SweptERC20 amount/success can misrepresent what the recipient actually received

Severity: Low
Origin: [phase1 only] — erc20 checklist agent. Re-verified: _sweepERC20's success/amount derive from the sender-side delta, not a recipient-side read.

Location: _sweepERC20() — success/amount derived from beforeBal - afterBal.

Description: For a fee-on-transfer token, beforeBal - afterBal == beforeBal (sender drained to 0) but the recipient receives less; the SweptERC20 event overstates the delivered amount by the fee. No fund misdirection occurs (destination is always the signed safeRecipient) and residual dust is re-sweepable in a later signed batch — this is an event-accuracy issue, not a theft path.

Recommendation: Document that SweptERC20.amount is a sender-side delta, not a guaranteed-delivered amount, or measure the recipient-side balance delta instead.

[7] Sweep arrays (erc20Tokens/erc721Items/erc1155Items) have no length cap — OOG can revert the whole rescue

Severity: Low
Origin: [phase1 only] — dos checklist agent. Re-verified: _validateBatch() (L225-236) only bounds request.calls.length; the three sweep arrays are unbounded.

Description: A sufficiently long signed array exhausts the outer transaction's gas mid-sweep, hard-reverting the whole executeBatch (including the already-executed batch calls and captured sweep) rather than gracefully degrading. Since the arrays are part of the signed digest, only the signer can construct this — self-inflicted risk or a way to grief a voluntary sponsor's gas on a guaranteed-revert transaction (the nonce is not consumed on revert, so retry is possible).

Recommendation: Add explicit length caps on the three sweep arrays in _validateBatch, reverting with a named error before attempting the sweep.

[8] Batch-call return data is copied unbounded — gas amplification outside item.gasLimit

Severity: Low
Origin: [both] — phase1: dos checklist agent; phase2: economic-security agent independently raised the identical mechanism as a lead.

Location: executeBatch() L169: (bool ok, bytes memory ret) = item.target.call{value, gas: item.gasLimit}(item.callData);

Description: Solidity auto-copies all returndata into memory; the callee's execution gas is capped by item.gasLimit (≤1M), but the caller-side RETURNDATACOPY + memory-expansion cost is paid from the outer transaction's gas, uncounted against item.gasLimit/MAX_TOTAL_CALL_GAS_LIMIT. Across up to 10 calls this can add meaningfully to outer-tx gas cost. Since call targets are part of the signed digest, this is signer-authorized (self-inflicted or sponsor-griefing), not third-party exploitable.

Recommendation: Use an assembly call wrapper that discards or caps captured returndata (e.g., to 256 bytes) for the failure-event hash/length.

[9] Missing assembly ("memory-safe") annotations

Severity: Info
Origin: [phase1 only] — assembly checklist agent, which independently recomputed the ERC-7201 storage slot and confirmed both assembly blocks are memory-safe in practice but unannotated.

Location: _hashCalls() L283, _mintRescueStorage() L296. Gas/best-practice only — no correctness issue.

[10] Dead/unused error codes suggest dropped validation

Severity: Info
Origin: [both, two distinct instances]

  • BadChain (phase1: general checklist agent) — MintRescueAuth.chainId (L48) is signed but _digest always substitutes live block.chainid (L262) rather than validating the signed field against it; error BadChain() (L147) is never thrown. Not a vulnerability (replay-across-chains is already fully closed via block.chainid in both the struct and the domain separator) — just dead/misleading code.
  • CallValueTooHigh (phase2: asymmetry agent) — declared but never thrown; per-call value is bounded only in aggregate (valueTotal > msg.value, L167), unlike per-call gas which has both a per-call and aggregate cap. Informational only — the aggregate cap already fully bounds total spend.

Recommendation: Remove both unused errors, or wire up the validation they imply, to avoid misleading future readers into thinking explicit checks exist.

[11] EIP-712 domain not bound to the specific 7702 delegate implementation

Severity: Info
Origin: [phase1 only] — signatures checklist agent.

Location: _domainSeparator() L290-292 — uses only NAME_HASH, VERSION_HASH, block.chainid, address(this); nothing binds it to the specific implementation code currently delegated-to. Requires an unlikely re-delegation scenario to matter; not practically exploitable today. Recommendation: ensure any future rescue implementation bumps VERSION_HASH.

[12] Checked-add revert on a lying ERC1155 balanceOf (benign, signer-only path)

Severity: Info
Origin: [both] — phase1: precision-math agent; phase2: math-precision agent, independently, with identical reasoning.

Location: _sweepERC1155() L441: afterBal + amount <= beforeBal. A hostile token could return an afterBal near type(uint256).max, causing the checked addition to overflow and revert rather than fail gracefully. Only reachable via a token the signer themselves chose to list; no third-party impact. Optional hardening: compare via beforeBal - afterBal >= amount instead.

Leads (not promoted to findings — no identifiable third-party victim, or impact bounded to self)

  • Full-balance ERC1155 capture over-sweep — _sweepCapturedERC1155 sweeps the account's entire balance of a captured id (by design, per the code comment), not just the amount delivered during the batch — so a pre-existing (unsigned) holding of the same id gets swept too. Reviewed and not escalated: the destination is always the signer's own safeRecipient, so this is over-inclusive rescue, not third-party theft. [phase2: 6 of 12 agents]
  • ERC721 captured-duplicate asymmetry — the ERC1155 captured path treats a re-visited (already-zero) balance as success, but no equivalent idiom exists on the ERC721 path, so a duplicate ERC721 capture record can independently trigger the same class of strict-revert as Finding 3. [phase2: numerical-gap-hunter]
  • Capture attribution breaks for routed/proxied mints — capture attributes the token to the hook's msg.sender; a mint routed through an intermediary/wrapper contract makes that intermediary — not the real NFT contract — the recorded "token," silently leaving the real asset unswept. Unverified against real-world mint-router patterns. [phase2: boundary agent]
  • Sponsor's unspent attached ETH is swept to safeRecipient, not refunded — considered and explicitly rejected as a finding: msg.value becomes part of the compromised EOA's own balance the moment the sponsor calls, so any unspent portion legitimately belongs to the account being rescued and correctly routes to the signer's own safeRecipient. This is standard payable-function behavior, not a redirection bug. [phase2: trust-gap-hunter, reviewed and demoted during reconciliation]

Notes on what was reviewed and cleared (no finding)

  • Signature scheme: domain separator correctly binds block.chainid + address(this) (the EOA itself), closing cross-chain and cross-account replay on two independent axes; sponsor is bound as live msg.sender inside the digest, correctly preventing relay/front-running substitution; nonce is strictly sequential and consumed before any external call; signature malleability guard (s ≤ secp256k1n/2, verified digit-for-digit against OpenZeppelin's constant) and v normalization are correct; _recover safely returns address(0) on any malformed input.
  • ERC-7201 namespaced storage: the storage slot constant was independently recomputed by three separate agents across both phases and matches exactly; no non-namespaced storage variables exist; no collision risk.
  • Reentrancy: nonReentrant guards the sole state-mutating entrypoint; any revert rolls back the lock along with everything else, so it cannot get stuck.
  • Weird-token handling: fee-on-transfer, no-return-value (USDT-style), and rebasing ERC20s are handled via before/after balance-diff accounting (aside from Finding 5/6's edge cases above).
  • The "attacker also holds the compromised key" race: this is an inherent, accepted property of the rescue-race design (the entire threat model is racing an already-compromised key), not a contract defect, and was correctly not flagged as a bug by any of the 20 agents across both phases.

This review was performed by AI audit agents (ethskills breadth pass + pashov-methodology depth pass, reconciled). AI analysis cannot verify the complete absence of vulnerabilities and no guarantee of security is given. A human security review, and ideally a bug bounty, is recommended before this contract is used to protect meaningful value — the strictMode findings above (1–3) in particular should be fixed before broad production use.
