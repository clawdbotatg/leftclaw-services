Findings

[C-01] Same-transaction spot-price slippage guard enables atomic, unprivileged sandwich extraction on every DCA cycle

Severity: Critical
Origin: [both] — corroborated by defi-amm, chain-specific, general, flashloans (phase 1) and math-precision, access-control, economic-security, execution-trace, invariant, periphery, first-principles, asymmetry, boundary, trust-gap, flow-gap (phase 2) — 15/19 total agents, independently, with concrete numeric proofs-of-concept.
Location: executeDCA():

uint256 quotedOut = ROUTER.getAmountsOut(swapAmount, path)[1];
uint256 minOut = (quotedOut * (BPS - p.maxSlippageBps)) / BPS;
...
IERC20(WETH).safeTransfer(BUYBACK_ENGINE, fee);
IERC20(WETH).forceApprove(address(ROUTER), swapAmount);
uint256[] memory out =
    ROUTER.swapExactTokensForTokens(swapAmount, minOut, path, p.owner, block.timestamp);

Description: quotedOut/minOut are derived from the AMM pool's live reserves in the same transaction as the swap that then trades against those same reserves. executeDCA is fully permissionless and every input needed to construct an attack (target, amountPerCycle, maxSlippageBps, due-time via public isExecutable()) is public on-chain state. An attacker therefore needs no visibility into anyone else's pending transaction — they originate the entire manipulate → executeDCA() → unwind sequence themselves, atomically, financeable via flash loan (zero capital requirement). The contract's own NatSpec cites Abstract's private sequencer mempool ("no public pending pool to snipe") as mitigation; every one of the 15 agents that flagged this independently identified that reasoning as inapplicable, since it only defends against front-running a third party's pending transaction, not a self-authored atomic bundle. Several agents further noted the guard fails even at maxSlippageBps = 0, since the "tolerance" is applied to an already-manipulated reference price, not a fair one.

Proof of Concept (one representative trace, from independent phase-2 agents; multiple agents produced consistent variants at 30–97% loss depending on manipulation size vs. pool depth):
Pool WETH/TARGET reserves 100 : 100,000 (spot ≈ 1,000 TARGET/WETH). Victim position: amountPerCycle = 10 WETH, maxSlippageBps = 300 (3%, a normal-looking setting). Fee 0.30% → swapAmount = 9.97 WETH.

  1. Fair-value quote for this swap (no manipulation): ≈ 9,043 TARGET.
  2. Attacker flash-borrows 50 WETH and swaps WETH→TARGET into the same pool first. Reserves become ≈150 : 66,667.
  3. Attacker (or anyone) calls executeDCA(id). ROUTER.getAmountsOut now reads the manipulated reserves: quotedOut ≈ 4,145 TARGET — a 54% shortfall from fair value. minOut = quotedOut * 0.97 ≈ 4,020, trivially satisfied by the swap executing against the same manipulated reserves. The position owner receives ~4,145 TARGET instead of the fair ~9,043.
  4. Attacker sells the TARGET back into the pool, restoring price and realizing a profit of several WETH (net of ~0.6% round-trip AMM fees and flash-loan fee), extracted entirely from the value that should have accrued to the DCA position owner.
  5. Repeatable every time the position becomes due, for every open position, for the life of each position.

Gate evaluation (per judging.md): Gate 1 (attack execution) clears — nonReentrant does not interrupt the attack since manipulation/unwind legs call the router/pair directly, never re-entering DollarCostAverager. Gate 2 (reachability) clears — proven achievable through ordinary permissionless use by 11 independent numeric traces. Gate 3 (trigger) clears — any unprivileged address, zero capital required (flash-loanable). Gate 4 (impact) — CONFIRMED, material loss to an identifiable victim (the position owner), demonstrated at 30–97% of cycle value depending on pool depth and manipulation size.

Recommendation: Do not derive minOut from a same-transaction spot quote. Use a manipulation-resistant reference price — a Uniswap V2 TWAP (via price0CumulativeLast/price1CumulativeLast over a meaningful window) or an owner/keeper-supplied off-chain price floor validated against such a reference — instead of ROUTER.getAmountsOut() called immediately before the swap it's supposed to protect.

- uint256 quotedOut = ROUTER.getAmountsOut(swapAmount, path)[1];
- uint256 minOut = (quotedOut * (BPS - p.maxSlippageBps)) / BPS;
+ // Derive minOut from a TWAP (e.g. UniswapV2 cumulative price accumulators sampled
+ // over >= N minutes) or a stored/owner-supplied reference price, never from a
+ // spot quote taken in the same transaction as the swap it bounds.

[H-01] Target-token or pool state fully controlled by a third party can permanently DoS a position's execution

Severity: High
Origin: [both] — corroborated across both phases with multiple distinct mechanisms sharing one root cause (external token/pool behavior the contract cannot control, acting on the hardcoded to: p.owner swap recipient or on the swap's own liquidity precondition):

  • Mechanism A — deny-list/blacklist on the owner [phase1: erc20 (High), dos (Medium)] [phase2 lead: economic-security]
  • Mechanism B — pausable target token [phase1: erc20 (Medium)]
  • Mechanism C — liquidity fully removed / thin pool causes zero-quote revert [phase2: execution-trace, invariant, first-principles, numerical-gap, trust-gap — 5 agents, promoted per multi-agent lead-convergence rule]
  • Mechanism D — isExecutable() cannot detect any of the above [phase1: dos] [phase2: numerical-gap]

Location: executeDCA() (swap to: p.owner, and the ROUTER.getAmountsOut/swapExactTokensForTokens calls); isExecutable().

Description: The swap's output recipient is hardcoded to p.owner. If target is a deny-list token (USDC/USDT-style) and p.owner is later blocklisted, or if target is globally paused, every future executeDCA(id) for that position reverts permanently (Mechanisms A/B). Separately, createPosition only validates FACTORY.getPair(WETH, target) != address(0) — pair existence, never liquidity depth — so a pool drained after position creation, or one too thin relative to amountPerCycle, causes getAmountsOut/the swap itself to revert every cycle (Mechanism C). In all cases isExecutable() only checks funding/timing gates and will keep returning true, misleading keeper bots into repeatedly submitting doomed transactions (Mechanism D). In every case, principal remains recoverable via cancelPosition() (which touches only WETH, never target), so this is automation-availability DoS, not fund loss — but it can be targeted deliberately (e.g., an attacker seeds a token with a blacklist admin function, waits for a victim to create a position, then blacklists them).

Proof of Concept: Victim creates a position on EvilToken (has a working WETH pair at creation, admin blacklist() function). After 1–2 cycles execute normally, attacker blacklists the victim. Every subsequent executeDCA(id) reverts permanently; victim must cancelPosition() to recover remaining WETH, losing the schedule going forward. Equivalent PoC for the liquidity-drain variant: attacker removes all liquidity from the pair after the victim funds a position; getAmountsOut reverts on every subsequent call.

Recommendation: Consider a pull-based output pattern (swap to the contract, credit an internal per-owner balance of target, let the owner withdraw separately) so a blocklist/pause on target doesn't brick executeDCA for that position. Add a liquidity/quote sanity check at createPosition time (e.g., require(ROUTER.getAmountsOut(amountPerCycle, path)[1] > 0)), and extend isExecutable() (or add a preview helper) to surface these failure modes distinctly so keepers don't waste gas on doomed transactions.

[M-01] Fee-on-transfer / deflationary target tokens silently defeat the slippage check and misreport the Executed event

Severity: Medium
Origin: [both] — [phase1: erc20, general] [phase2: economic-security, asymmetry, boundary, flow-gap — 4 agents, promoted per multi-agent lead-convergence rule]
Location: executeDCA() — swap + Executed event.

Description: createPosition only checks that target has a Uniswap V2 WETH pair — nothing restricts fee-on-transfer or deflationary tokens. The router's own amountOutMin check (and this contract's minOut) validates the pre-fee computed swap amount, not what p.owner actually receives after the token's internal transfer deduction. A fee-on-transfer target can therefore deliver strictly less than minOut implied while the transaction still succeeds, silently defeating the owner's configured slippage tolerance. The Executed event's received field (out[out.length-1]) also overstates the real amount delivered, corrupting off-chain accounting.

Recommendation: Use swapExactTokensForTokensSupportingFeeOnTransferTokens and verify p.owner's balance delta directly against minOut, or explicitly document/restrict target to standard, non-fee-on-transfer ERC-20s.

[L-01] Fee collection rounds fully to zero for sub-334-wei amountPerCycle

Severity: Low
Origin: [both] — [phase1: precision-math] [phase2: math-precision, economic-security, numerical-gap — 3 agents, promoted per multi-agent lead-convergence rule]
Location: executeDCA(), uint256 fee = (amount * FEE_BPS) / BPS;

Description: Standard floor division; for amountPerCycle < 334 wei, fee truncates to 0 and 100% of the cycle bypasses the buyback fee. createPosition places no floor on amountPerCycle (only != 0). All agents that raised this independently concluded it is not economically exploitable at scale — the maximum obtainable budget via this route is on the order of 1e12 wei, and per-cycle gas cost (a full executeDCA transaction, interval-gated) dwarfs the fee saved.

Recommendation: Round fee up in the protocol's favor if strict correctness is desired: (amount * FEE_BPS + BPS - 1) / BPS, and/or enforce a minimum amountPerCycle.

[L-02] deadline = block.timestamp gives the swap no real expiration protection

Severity: Low (demoted from phase-1's High/Medium calls after Turn-3 re-examination — see reasoning)
Origin: [phase1 only: defi-amm (Low), chain-specific (Medium)] — re-examined against source in Turn 3, not independently found by any phase-2 agent.
Location: executeDCA(), ROUTER.swapExactTokensForTokens(swapAmount, minOut, path, p.owner, block.timestamp).

Description: block.timestamp always satisfies its own deadline check at inclusion time, so this parameter is a no-op — a theoretical concern if a centralized sequencer could hold a submitted transaction and release it once conditions are favorable. Re-examination finding: this does not provide an attacker any capability beyond what C-01 already grants — C-01's attack is atomic and self-contained (no held-transaction window needed), so a real deadline would not close C-01, and exploiting the deadline gap on its own would require trusting that a malicious/compromised sequencer withholds a specific transaction, a more extreme and separately-scoped threat model than an unprivileged on-chain attacker. Demoted to Low as a best-practice gap rather than an independently exploitable High/Medium.

Recommendation: Accept a real deadline parameter (owner/keeper-supplied, or block.timestamp + smallFixedWindow at call time) so the router's deadline check is meaningful, as defense-in-depth alongside the C-01 fix.

[L-03] No protocol-enforced ceiling on maxSlippageBps

Severity: Low
Origin: [phase1 only: defi-amm] — re-examined: confirmed in source (if (maxSlippageBps >= BPS) revert BadParams(); permits up to 9999 bps). Not independently raised by phase 2, but several phase-2 agents building C-01's PoC explicitly noted the guard fails regardless of this ceiling (even at 0 bps) — this finding is an amplifying/independent hardening measure, not a standalone attack vector.
Location: createPosition().

Description: Any value up to 99.99% is accepted and immutable for the position's lifetime. Combined with C-01, this means slippage protection can be configured to near-zero with no recourse besides cancel-and-recreate — though C-01 remains exploitable even at the tightest setting.

Recommendation: Enforce a sane protocol maximum (e.g. ≤ 1,000 bps).

[I-01] interval unbounded — checked uint64 arithmetic can permanently self-DoS a position after cycle 1

Severity: Info (self-inflicted, principal recoverable)
Origin: [both] — [phase1: precision-math] [phase2 lead: numerical-gap / boundary]
Location: executeDCA(), uint64 nextEligible = p.lastExecuted + p.interval;

Description: interval has no upper bound at creation. Once lastExecuted is nonzero, if lastExecuted + interval overflows uint64, every subsequent call reverts permanently (Solidity 0.8+ checked arithmetic applies to all widths). Principal recoverable via cancelPosition.

Recommendation: Bound interval to a sane maximum in createPosition, or compute the check in uint256.

[I-02] ROUTER/FACTORY are independent immutables with no cross-validation

Severity: Info
Origin: [phase1 only: defi-amm] — re-examined: confirmed, constructor never checks ROUTER.factory() == FACTORY. Deployment/configuration risk only, not attacker-triggerable.
Location: constructor().

Recommendation: Assert IUniswapV2Router02(router).factory() == factory in the constructor if the router exposes that getter.

[I-03] No rescue path for tokens sent directly to the contract

Severity: Info
Origin: [phase1 only: general] — re-examined: confirmed, no sweep/rescue function exists, and no admin/owner could add one post-deployment (no upgrade path by design).
Location: contract-wide.

Recommendation: Document prominently that only createPosition should be used to fund the contract, or add a permissionless "sweep excess" function limited to balanceOf(this) - sum(remaining).

[I-04] BUYBACK_ENGINE is a single, unguarded, immutable dependency

Severity: Info
Origin: [phase2 only: boundary] — re-examined against source: confirmed, safeTransfer(BUYBACK_ENGINE, fee) has no try/catch and sits ahead of the swap in every executeDCA call. Unverified beyond this contract since BUYBACK_ENGINE's own code is out of scope.
Location: executeDCA().

Description: If the out-of-scope buyback engine ever reverts on receiving WETH (paused, blacklists this contract, etc.), every open position across the entire protocol becomes permanently unexecutable until the dependency is fixed.

Recommendation: Wrap the fee transfer in try/catch (skip the fee rather than revert the whole cycle on failure), or otherwise decouple executeDCA's success from BUYBACK_ENGINE's liveness.

[I-05] minOut rounds down by ≤ 1 wei; immutable addresses only checked for non-zero

Severity: Info
Origin: [phase1 only: precision-math, general] — re-examined: both confirmed as described, negligible in magnitude and deployment-time trust assumptions respectively, not independently exploitable.

Recommendation: No action required beyond documentation; optionally require(router.code.length > 0) etc. as defense-in-depth.
