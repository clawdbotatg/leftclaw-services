Methodology: EthSkills (7 domain checklists) + Pashov (12-perspective methodology)

Contract: TrustSwap StakingPool — permissionless ERC20 staking pool factory with time-bounded reward distribution.

Executive Summary

The StakingPool contract allows any address to create staking pools where users lock ERC20 tokens to earn rewards proportionally over a fixed time period. The audit uncovered 2 High, 5 Medium, 6 Low, and 3 Informational findings.

The most critical issues are:

  1. A contract-owner backdoor (saveMe()) that can drain all user deposits and rewards.
  2. No functional emergency exit for users before pool.endTime, exposing users to permanent fund lockup if the pool owner's key is lost.
  3. A last-minute large-deposit attack that can steal the final reward distribution from honest stakers.

The contract is upgradeable (TransparentUpgradeableProxy), which mitigates some risks but requires the proxy admin to act responsibly.

Findings confirmed by both methodologies receive a confidence boost.

Findings

[C-1] Critical → [H-1] saveMe() enables contract owner to drain all user funds

Severity: High [confirmed by both methodologies — elevated confidence]
Category: Access Control
Location: saveMe() (line ~2609)

Description:
saveMe(address tokenAddress, uint256 amount) is an onlyOwner function that transfers any token out of the contract with no guard against active pool balances. Because the contract holds all user staking deposits and all unclaimed reward tokens across every pool, a compromised or malicious contract owner can steal every user's principal and rewards in a single transaction.

function saveMe(address tokenAddress, uint256 amount) external onlyOwner nonReentrant {
    IERC20Upgradeable token = IERC20Upgradeable(tokenAddress);
    token.safeTransfer(address(msg.sender), amount);  // ← no guard against pool funds
}

Exploit Path:

  1. Pool 0 has 1,000,000 USDC staked by users (pool.totalStaked = 1,000,000e6).
  2. Owner calls saveMe(USDC, 1,000,000e6).
  3. All user deposits transferred to owner.
  4. Users call withdraw() after pool ends → safeTransfer reverts (insufficient balance).

Recommendation:
Prevent saveMe() from withdrawing tokens belonging to active pools:

function saveMe(address tokenAddress, uint256 amount) external onlyOwner nonReentrant {
    uint256 locked = 0;
    for (uint256 i = 0; i < poolInfo.length; i++) {
        PoolInfo storage p = poolInfo[i];
        if (block.timestamp < p.endTime) {
            if (address(p.stakingToken) == tokenAddress) locked += p.totalStaked;
            if (address(p.rewardToken) == tokenAddress) locked += p.totalReward;
        }
    }
    require(
        IERC20Upgradeable(tokenAddress).balanceOf(address(this)) - amount >= locked,
        "Cannot withdraw locked pool funds"
    );
    IERC20Upgradeable(tokenAddress).safeTransfer(msg.sender, amount);
}

Alternatively, restrict saveMe() to tokens that are not the staking or reward token of any active pool.

[H-2] No functional emergency exit — users can be locked for up to 5 years

Severity: High [confirmed by both methodologies — elevated confidence]
Category: DeFi Staking / Access Control
Location: emergencyWithdraw(), withdraw(), claimReward()

Description:
All three user exit functions enforce if (block.timestamp < pool.endTime) revert CannotClaimBeforePoolEnds(). The emergencyWithdraw() function is misnamed — it provides no earlier exit than the regular withdraw(). If the pool owner's key is lost, stopReward() cannot be called to advance endTime, leaving users trapped for the remaining pool duration (up to 5 years per addPool()'s validation).

The contract has no contract-owner override to force-end a pool.

Exploit Path (lost-key scenario):

  1. Pool owner creates a pool with endTime = now + 4 years.
  2. Pool owner's key becomes inaccessible.
  3. Users deposit expecting to be able to exit early in emergencies.
  4. No one can call stopReward().
  5. All user staking tokens are inaccessible for 4 years.

Note: The contract is upgradeable (proxy admin could deploy a fix), which partially mitigates this. However, the current implementation provides no in-code protection.

Recommendation:
Option A — Make emergencyWithdraw() available before endTime (forfeiting rewards is an acceptable tradeoff):

function emergencyWithdraw(uint256 poolId) external nonReentrant {
    if (poolId >= poolInfo.length) revert PoolDoesNotExist(poolId);
    PoolInfo storage pool = poolInfo[poolId];
    // REMOVED: require(block.timestamp >= pool.endTime)
    // ... rest unchanged
}

Option B — Add a contract-owner override:

function forceEndPool(uint256 poolId) external onlyOwner {
    updatePool(poolId);
    poolInfo[poolId].endTime = block.timestamp;
    emit PoolStopped(poolId);
}

[M-1] Last-minute large deposit dilutes existing stakers' final reward period

Severity: Medium [unique to Pashov economic-security perspective]
Category: Economic Security
Location: deposit()

Description:
deposit() has no check that the pool is still active (block.timestamp < pool.endTime). An attacker can deposit a large amount of staking tokens in the final reward window, capture most of the last updatePool() distribution, then immediately withdraw after endTime passes.

Concrete exploit (1-second final period example):

Pool: 1,000 reward tokens, 1000-second duration, 1,000 staking units deposited by users.
T=999: attacker deposits 999,000,000 staking units.
  → updatePool() distributes T=last_update to T=999 to existing 1,000 units (correct).
  → pool.totalStaked = 999,001,000.
T=1000: any updatePool() call distributes final ~1 token to 999,001,000 units.
  → Attacker captures: 999M / 999.001M × 1 ≈ 0.999 tokens.
  → Existing stakers capture: 1K / 999.001M × 1 ≈ 0.000001 tokens (vs expected 1 token).
T=1000: attacker calls withdraw(), recovers 999,000,000 staking units + 0.999 reward tokens.

Profitable when reward_token_value × final_period_proportion > gas_cost. On Base with
sub-cent gas costs, this is viable whenever final-period rewards exceed a few cents.

Recommendation:
Add a pool-active check to deposit():

function deposit(uint256 _amount, uint256 poolId) external nonReentrant {
    ...
    if (block.timestamp >= pool.endTime) revert PoolEnded();  // ← add this
    ...
}

Pool owners should also set poolStakeLimit to cap exposure.

[M-2] Reward tokens stranded for no-staker periods cannot be recovered by pool owner

Severity: Medium [confirmed by both methodologies — elevated confidence]
Category: DeFi Staking / Math
Location: stopReward()

Description:
stopReward() refunds the pool owner using:

((oldEnd - max(block.timestamp, start)) * pool.totalReward) / (oldEnd - start)

This formula returns the "future" portion of rewards but does NOT account for past periods
where totalStaked == 0. During those periods, updatePool() advances lastRewardTimestamp
without distributing anything, leaving reward tokens physically in the contract but
unattributed. When stopReward() is called, those "unearned past" tokens are not returned
to the pool owner — only the contract owner can recover them via saveMe().

Numerical proof:

Pool: start=1000, end=2000, totalReward=1000 tokens.
T=1000→1500: no stakers (500 tokens unearned, accTokenPerShare=0).
T=1500: stopReward() called.
  → Returns: (2000-1500) × 1000 / (2000-1000) = 500 tokens.
  → Stranded: 500 tokens (the no-staker period) — permanently stuck unless saveMe() used.

Recommendation:
Return all non-user-earned tokens:

// Calculate user-earned balance (can't be withdrawn by owner):
uint256 earnedByUsers = (pool.accTokenPerShare * pool.totalStaked) / pool.precision;
// Return everything else:
uint256 toReturn = pool.rewardToken.balanceOf(address(this_pool_portion)) - earnedByUsers;
pool.rewardToken.safeTransfer(owner, toReturn);

(Requires tracking per-pool balances separately, e.g., via a balance-tracking variable incremented in addPool() and decremented on claims.)

[M-3] initializePoolV2() lacks access control — can be front-run to block operator initialization

Severity: Medium [confirmed by both methodologies — elevated confidence]
Category: Proxies / Access Control

[M-4] Precision loss at minimum precision setting causes total reward loss at scale

Severity: Medium [confirmed by both methodologies — elevated confidence]
Category: Precision/Math
Location: updatePool()

Description:
The reward accumulation step pool.accTokenPerShare += (rewards * pool.precision) / lpSupply
rounds to zero when rewards * pool.precision < lpSupply. Because lastRewardTimestamp
still advances, those rewards are permanently lost — not deferred.

Numerical proof:

precision_param = 6 → pool.precision = 1e6 (minimum allowed)
lpSupply = 1e27 (1 billion 18-decimal staking tokens)
totalReward = 1000e18, duration = 31,536,000 seconds

Per-2-second-block: rewards = ~6.34e13 wei
  rewards × precision = 6.34e13 × 1e6 = 6.34e19
  6.34e19 / 1e27 = 0 ← every update distributes nothing

After 1 year: accTokenPerShare = 0, all 1000 reward tokens stranded.

Recommendation:
Increase minimum precision to 18:

if (precision < 18 || precision > 36) revert InvalidPrecision();

Document that precision should equal 18 + stakingToken.decimals() for 18-decimal reward tokens.

[M-5] Rebasing staking tokens cause withdrawal shortfall for last users

Severity: Medium [confirmed by both methodologies — elevated confidence]
Category: ERC20 / DeFi Staking
Location: withdraw(), emergencyWithdraw()

Description:
user.amount records the balance delta at deposit time and is never updated. If the
staking token rebases downward (slashing event for stETH, negative rebase for AMPL),
the contract's actual token balance falls below sum(user.amount). The last users to
withdraw receive less than their recorded balance, or face reverts entirely.

Exploit path (rebase-down):

10 users each deposit 10 stETH → pool.totalStaked = 100 stETH.
Validator slashing: contract holds 95 stETH.
First 9 users withdraw 10 stETH each → contract has 95 - 90 = 5 stETH.
User 10 tries to withdraw 10 stETH → REVERTS (only 5 available).
User 10 is permanently locked without contract owner intervention.

Recommendation:
Explicitly disallow rebasing tokens with a prominent NatSpec warning:

/// @dev WARNING: Do not use rebasing tokens (stETH, wstETH, AMPL, aTokens) as stakingToken.
///      Use non-rebasing wrappers (wstETH) instead. Rebasing-down events will cause
///      the last stakers to be unable to withdraw.

[L-1] Implementation lacks _disableInitializers() constructor

Severity: Low [confirmed by both methodologies]
Category: Proxies
Location: Implementation constructor (missing)

Description:
No constructor calls _disableInitializers() on the implementation contract
0x11073E14.... Anyone can call initialize() directly on the implementation and
claim ownership of that instance. For a Transparent Proxy, the implementation's storage
is separate from the proxy's, so no direct fund theft on the proxy is possible. However,
the attack surface allows social-engineering attacks and confusing dual-owner states.

Recommendation:

/// @custom:oz-upgrades-unsafe-allow constructor
constructor() {
    _disableInitializers();
}

[L-2] Single-step ownership transfer risks permanent ownership loss

Severity: Low [confirmed by both methodologies]
Category: Access Control
Location: transferOwnership() (inherited from OwnableUpgradeable)

Description:
A single typo in the destination address permanently locks out saveMe() and any future
owner-gated functions added in upgrades.

Recommendation:
Upgrade to Ownable2StepUpgradeable from OpenZeppelin.

[L-3] emergencyWithdraw() forfeits all rewards with no timing advantage over withdraw()

Severity: Low [confirmed by both methodologies]
Category: DeFi Staking
Location: emergencyWithdraw()

Description:
emergencyWithdraw() has the same endTime requirement as withdraw() but silently forfeits
all accumulated rewards. Users who call it in a panic lose their full reward entitlement
unnecessarily. The function is strictly worse than withdraw() in all scenarios after
pool ends.

Recommendation:
Either remove the function (fully superseded by withdraw()) or make it available before
endTime (the only scenario where forfeiting rewards has a meaningful trade-off).

[L-4] Fee-on-transfer reward tokens cause last-claimant shortfall

Severity: Low [confirmed by both methodologies]
Category: ERC20
Location: claimReward(), withdraw()

Description:
The contract records totalReward as the net-received amount (via transferFunds balance diff).
But when paying out, safeTransfer(user, pendingReward_) deducts the full pendingReward_
from the contract's balance while the user receives only pendingReward_ × (1 - fee). Over
many claims, the pool's token balance depletes faster than accounting tracks, causing the
final claimants to face reverts.

Recommendation:
Document that fee-on-transfer tokens are not supported as rewardToken, or implement a
balance-waterfall approach that caps payouts at available balance.

[L-5] No storage gap in StakingPool itself — upgrade can shift all pool accounting

Severity: Low [unique to Pashov methodology]
Category: Proxies
Location: Contract storage layout

Description:
OwnableUpgradeable has __gap[49] and ContextUpgradeable has __gap[50]. However,
StakingPool itself has no __gap. If a future upgraded parent in the inheritance chain
adds a state variable, all of StakingPool's own variables (poolInfo, userInfo, _status, etc.)
shift down by one slot, catastrophically corrupting all pool accounting.

Recommendation:

// Add at end of StakingPool state variable declarations:
uint256[50] private __gap;

[L-6] Deposits into ended pools waste gas and confuse users

Severity: Low
Category: General
Location: deposit()

Description:
No check prevents users from depositing into a pool that has already ended. The deposit succeeds
(costing gas), the user earns zero rewards (pool ended), and they can immediately withdraw.
This also interacts with the M-1 finding.

Recommendation:

if (block.timestamp >= pool.endTime) revert PoolEnded();

Adding this single check simultaneously fixes M-1 (last-minute deposit attack) and L-6.

[I-1] Hardhat console.log library in production bytecode

Severity: Info
Category: General

The 1530-line Hardhat debugging library is compiled into the deployed bytecode, adding
~70KB to the contract size and increasing deployment costs significantly.

Recommendation: Remove import "hardhat/console.sol" from the production source and rebuild.

[I-2] hasBeenStaked mapping never written or read

Severity: Info
Category: General

Dead state variable. Remove to save a storage slot and reduce confusion.

[I-3] poolVersion mapping written but never validated or used

Severity: Info
Category: General

Values are written in addPool() but no function reads them. Dead code.

Appendix: Contract Architecture

TransparentUpgradeableProxy (0x2a70a42...)
  └── implementation: StakingPool (0x11073E14...)
        ├── OwnableUpgradeable (owner controls saveMe, updateVersion)
        ├── Initializable (initialize / initializePoolV2)
        └── Storage:
              poolInfo[]           — all staking pools
              userInfo[][]         — per-user staking data
              _status              — reentrancy guard
              rewardCredit[][]     — pending reward accumulator
              poolStakeLimit[]     — optional deposit caps (per pool owner)

Roles:

  • Contract Owner (TrustSwap): saveMe(), updateVersion(), proxy upgrades
  • Pool Owner (any address): addPool(), stopReward(), setPoolStakeLimit()
  • User (any address): deposit(), withdraw(), claimReward(), emergencyWithdraw()
