[1] Unbounded loop in removeSigner() — permanent signer-removal DoS

Severity: High
Corroboration: [both] — found independently by all 5 phase-1 checklist agents (general, precision-math notwithstanding no-finding, access-control, governance, DoS all flagged it except precision-math) and all 12 phase-2 attacker agents (unanimous — the strongest possible signal this methodology can produce).
Location: removeSigner(), lines 275-284

// ✅ HIGH FIX: Clear the removed signer's confirmations on all pending transactions
// so their stale votes do not contribute to the threshold after removal.
for (uint256 i = 0; i < transactionCount;) {
    if (!transactions[i].executed && confirmations[i][signer]) {
        confirmations[i][signer] = false;
        transactions[i].confirmations--;
    }
    unchecked { ++i; }
}

Description: This loop — itself a documented prior "HIGH FIX" for a ghost-confirmation bug — scans every transaction ever proposed, not just pending ones. transactionCount is incremented once per proposeTransaction() call (line 172, txId = transactionCount++), a function gated only by onlySigner — any single signer can call it unlimited times, with no fee beyond gas, no cooldown, and no pruning of dead/expired entries. Each iteration costs at minimum two cold SLOADs (transactions[i].executed and the nested-mapping confirmations[i][signer], ≈2,100 gas each under EIP-2929, ≈4,200-4,500 gas/iteration). At a ~30,000,000 gas block limit, roughly 6,900-7,000 stored transactions are enough to make this loop alone exceed the entire block gas limit — after that point, removeSigner() reverts with out-of-gas for every signer, permanently. One phase-2 agent (boundary) noted an even cheaper variant: if the attacker also confirms their own spam proposals, each matching iteration triggers two additional SSTOREs, roughly tripling per-iteration cost and cutting the required proposal count to ~2,000-2,500.

This directly undermines the contract's stated purpose ("reduce centralization risk," "signers can be added/removed via the multisig itself") — the one mechanism meant to eject a compromised or malicious signer can be permanently disabled by that very signer, using only the unprivileged proposeTransaction() function they already have access to. It can also occur organically on a long-lived, actively-used governance multisig with no attacker at all, since expired-but-unexecuted proposals are never pruned from the loop's range.

Proof of Concept:

  1. Signer M (any current signer, e.g. 0xA054f831... or 0x909f0197... on the live deployment) anticipates being removed, or simply wants to entrench the current signer set.
  2. M calls proposeTransaction(cheapTarget, 0, "") repeatedly (cheap, unilateral, auto-confirms only their own vote, no cooperation needed from anyone) until transactionCount exceeds ~6,900-7,000 (or ~2,000-2,500 if M also confirms each spam proposal).
  3. The remaining signers propose, confirm, and attempt executeTransaction → removeSigner(M).
  4. The internal cleanup loop must iterate the full, now-inflated transactionCount range; its gas cost alone exceeds the block gas limit; the call reverts with ExecutionFailed, unconditionally, in every future block.
  5. removeSigner is now permanently unusable — not just for M, but for removing any signer, since the loop bound is global and only ever grows.

Recommendation — two viable, distinct fixes:

Option A — bounded per-signer tracking:

- for (uint256 i = 0; i < transactionCount;) {
-     if (!transactions[i].executed && confirmations[i][signer]) {
-         confirmations[i][signer] = false;
-         transactions[i].confirmations--;
-     }
-     unchecked { ++i; }
- }
+ // Track a bounded set/list of each signer's currently-confirmed,
+ // unexecuted txIds (populated in _confirm, removed on revoke/execute/
+ // expiry) and iterate only that signer's own set here, instead of
+ // the full [0, transactionCount) range.

Option B — lazy invalidation (eliminate the eager sweep entirely):

- // removeSigner: drop the O(transactionCount) cleanup loop entirely.
+ // executeTransaction / isTransactionReady: instead of maintaining an
+ // eagerly-cleared running counter, re-validate that counted
+ // confirmations still come from addresses currently in isSigner[]
+ // at read/execute time.

[2] Live deployment is 2-of-2 — no on-chain recovery path if either signer is lost or uncooperative

Severity: High
Origin: [phase1: governance] — flagged and independently verified live on-chain during this audit.
Reconciliation note: One phase-2 gap-hunter agent (flow-gap) explicitly considered this exact scenario ("N-of-N unanimous-threshold key-loss deadlock") and classified it as "a real liveness gap but... an inherent, well-known property of any M-of-N multisig (identical in Gnosis Safe) rather than a defect in this implementation" — i.e., not a code bug, a design tradeoff, and excluded it under the judging framework's "standard tradeoff, do not report" rule. That framing is correct for the code in the abstract. But this audit is of a specific live deployment, and we independently confirmed via direct RPC calls that the deployed configuration is genuinely, currently, 2-of-2 — the worst-case N=threshold configuration, with zero redundancy. We are keeping this as a High finding scoped to the deployment, not the code, since the client asked us to focus on "threshold enforcement" and "admin-key privileges that undermine the multisig," and an M==N configuration with no fallback is a direct, present-tense answer to that question for this specific contract instance.
Location: addSigner()/removeSigner()/changeThreshold(), all onlySelf (lines 245-299)

Description: Every repair function is gated by onlySelf, reachable only by the multisig executing a transaction against itself — i.e., by reaching the current threshold. There is no lower-threshold recovery path and no fallback admin. With the live threshold=2, signerCount=2, both signers must agree on literally everything, including any attempt to fix the signer set itself.

Proof of Concept: Signer A (either of the two live signers) becomes unresponsive (lost key, incapacitated, or simply uncooperative). Signer B proposes removeSigner(A) — auto-confirms 1-of-2. A never confirms. B tries changeThreshold(1) as a workaround — same problem, needs 2-of-2. addSigner(replacement) — same problem again. There is no on-chain path forward; the contract (and anything it governs) is frozen permanently.

Recommendation: Redeploy/migrate to N > threshold with real redundancy (e.g. 2-of-3), or document this risk explicitly to the client/end-users so they can plan a manual/social-recovery contingency (e.g. a pre-signed emergency migration path) outside the contract.

[3] Threshold checked live, not snapshotted — stale minority-confirmed proposals can be retroactively activated

Severity: Medium (elevated from phase-1's initial Medium call given phase-2's concrete, gate-confirmed drain trace — see below)
Origin: [both] — phase1 flagged this from both the governance checklist (concrete PoC, rated Medium) and access-control checklist (rated Info); phase2's trust-gap agent independently produced a full attack trace and it survived all four pashov validation gates (attack execution, reachability, trigger — via the "retroactive sweep" unprivileged-amplifier exception, and impact) at confidence 80.
Location: changeThreshold() (lines 292-299) interacting with executeTransaction() (line 231)

Description: Transaction.confirmations has no association with the threshold in effect when each confirmation was cast; executeTransaction only checks the counter against the current, live threshold. If a transaction gathers only minority support under a stricter threshold and sits dormant (renewable indefinitely by re-proposing before the 7-day expiry), and the threshold is later legitimately lowered for unrelated reasons, that dormant proposal can instantly become executable with confirmations gathered under a bar that no longer reflects what any signer intended to allow — without any signer re-confirming intent under the new rules.

Proof of Concept: Threshold 3-of-5. Signer M proposes a self-serving transaction (auto-confirms, 1/3, or 2/3 with one colluding co-signer). No one else confirms; it sits dormant, unexpired. Days later, for unrelated legitimate reasons (e.g. two signers lost keys), the group executes changeThreshold(2). The instant that executes, M's dormant 2-confirmation proposal from earlier now satisfies 2 >= 2 and anyone can execute it — a minority coalition achieves execution of a payload the original 3-of-5 policy was specifically designed to block, using an honest signer's unrelated, good-faith threshold-reduction vote as the unwitting enabler.

Recommendation:

  struct Transaction {
      address target;
      uint256 value;
      bytes data;
      bool executed;
      uint256 confirmations;
      uint256 proposedAt;
      uint256 expiresAt;
+     uint256 requiredThreshold;
  }
  ...
  transactions[txId] = Transaction({
      ...,
+     requiredThreshold: threshold,
      ...
  });
  ...
  function executeTransaction(uint256 txId) ... {
      Transaction storage txn = transactions[txId];
-     if (txn.confirmations < threshold) revert ThresholdNotMet();
+     if (txn.confirmations < txn.requiredThreshold) revert ThresholdNotMet();

Alternatively, invalidate/expire all pending transactions whenever the threshold changes.

[4] addSigner() has no mechanism keeping threshold proportionate to signer count

Severity: Medium
Origin: [phase1: access-control] — re-examined against source, confirmed.
Location: addSigner(), lines 245-253

Description: addSigner only adds a signer; it never touches threshold. Repeated calls can grow N arbitrarily while threshold stays fixed, silently diluting quorum (e.g. 2-of-3 = 66% can become 2-of-10 = 20% with no on-chain check, event warning, or invariant), unlike Gnosis Safe's addOwnerWithThreshold pattern which forces threshold to be restated on every membership change.

Proof of Concept: Deploy 3 signers, threshold 2. Governance legitimately adds 7 more signers over time via separate addSigner calls without ever calling changeThreshold. The multisig is now 2-of-10 (20% quorum) with no on-chain signal that security materially weakened.

Recommendation: Require the caller to specify the resulting threshold atomically with each signer addition (mirror addOwnerWithThreshold), or add an invariant/event warning when signers.length grows disproportionately to threshold.

[5] addSigner() does not reject address(this) as a signer

Severity: Low
Origin: [phase1: access-control] — re-examined, confirmed as a real (if low-severity) gap.
Location: addSigner(), line 245

Description: Neither the constructor nor addSigner() blocks signer == address(this). If the multisig ever added itself as a signer via normal threshold consensus, executeTransaction calls out with msg.sender == address(this) from the callee's perspective — so one threshold-reaching execution could reenter and satisfy onlySigner for a different pending txId (e.g. confirmTransaction), manufacturing a vote not backed by an independent keyholder.

Recommendation: if (signer == address(this)) revert ZeroAddress(); (or a dedicated error) in addSigner().

[6] Governance calls to a codeless target (or non-reverting-failure token) silently no-op

Severity: Low
Origin: [both] — phase1 general checklist flagged the codeless-target case directly; phase2's boundary and flow-gap agents independently flagged the same root theme (call-success ≠ intended-effect-happened) but both kept it as a Lead rather than a Finding, citing insufficient forcing-function specificity to this contract.
Location: executeTransaction(), line 235

Description: txn.target.call{value: txn.value}(txn.data) has no target.code.length check. A low-level call to a codeless address returns (true, "") regardless of calldata; similarly, a non-standard token that returns false instead of reverting would also register as success. If a governance-approved action's target has no code at execution time (typo, not-yet-deployed CREATE2 target, later-destroyed contract) or targets such a token, the call "succeeds," executed = true is set permanently, and the intended action silently never happens while the governance budget for that txId is spent.

Recommendation: If txn.data.length > 0, require txn.target.code.length > 0 before calling, reverting otherwise. For attached ETH value with empty data, no check is needed (plain transfers to any address are fine).

[7] No re-validation of target code between proposal and execution

Severity: Low
Origin: [phase1: governance]
Location: proposeTransaction() / executeTransaction()

Description: A proposal's target/data are fixed at proposal time and can sit gathering confirmations for up to 7 days. If target is redeployed at the same address (CREATE2 after SELFDESTRUCT) or is itself upgradeable, its behavior can change between review and execution without re-confirmation.

Recommendation: Optionally record and re-check target.codehash at execution time for security-sensitive proposals.

[8] Signer-set changes are not atomic/batchable

Severity: Low
Origin: [phase1: governance]
Location: executeTransaction() (single target/data per call)

Description: "Swap signer X for Y" requires two independent propose/confirm/execute rounds since each executed transaction is a single call. Between rounds the live N/threshold ratio is transiently something no signer intended, and each round is independently exposed to Findings 1/2 above.

Recommendation: Consider allowing self-targeted multicall data so related signer-set changes execute atomically.

[9] NatSpec claims transaction expiry is "configurable"; it is a hardcoded constant

Severity: Low
Origin: [phase1: general]
Location: Contract doc (line 18), TRANSACTION_EXPIRY (line 85)

Description: The header comment states expiry is "a configurable window (default 7 days)," but TRANSACTION_EXPIRY is constant with no setter anywhere. A reviewer or signer relying on the doc could wrongly believe the window can be shortened via governance in response to an incident.

Recommendation: Fix the doc to state the window is fixed at deployment, or add an onlySelf-gated setter if configurability was actually intended.

[10] Unbounded signers array growth

Severity: Info
Origin: [phase2: invariant + boundary agent leads] — phase2 only; not independently proven to reach a gas-breaking size since growth requires full multisig consensus (onlySelf), unlike Finding 1's unilateral trigger.
Location: addSigner(), getSigners(), removeSigner()'s swap-and-pop scan

Description: No upper bound exists on signer count; getSigners() returns the full array and removeSigner's scan is O(signers.length). Consensus-gated, so far harder to weaponize than Finding 1, but worth noting if the signer set is expected to grow very large over time.

Recommendation: Document a soft operational cap on signer count; not urgent given the consensus gate.

[11] Uncapped return-data on executeTransaction's low-level call

Severity: Info
Origin: [phase1: dos]
Location: executeTransaction(), line 235

Description: The call forwards all gas and copies unbounded return data. A malicious target (chosen by a signer, requiring insider collusion to reach threshold) could inflate the executing signer's own gas cost. Limited blast radius — only wastes the executor's own gas.

Recommendation: Low priority; consider a returndatasize()-capped copy if defense-in-depth is desired.

Explicitly Ruled Out (checked, no finding)

  • Replay of governance actions: none — execution is on-chain-state-based (no signatures), txIds are never reused, executed is set before the external call (correct checks-effects-interactions ordering), so double-execution of the same transaction is structurally impossible. Confirmed independently by both phases.
  • Precision/math: no division/multiplication, no share/asset conversion. The one arithmetic surface (confirmations++/--) is protected by a tightly-paired boolean-flag invariant at every mutation site — overflow/underflow unreachable under Solidity 0.8 checked math. Confirmed independently by both phases.
  • Missing access-control modifiers / onlySelf bypass: every state-changing function is correctly gated; no delegatecall exists anywhere in the contract, so there is no path to spoof msg.sender == address(this) other than the intended self-call route.
  • Reentrancy on executeTransaction: executed = true is set before the external call; same-txId re-execution is structurally blocked. Cross-function reentrancy during the callback does not bypass any threshold or accounting invariant.
  • Zero-address / duplicate-signer checks: present and correct in constructor and addSigner.
  • Cannot-remove-last-signer / threshold-exceeds-signers guards: correct ordering in removeSigner, no underflow.
