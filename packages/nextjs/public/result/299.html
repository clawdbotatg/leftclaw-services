[100] 1. Unauthenticated publishCommittee lets anyone hijack the committee encryption key for non-aggregation E3s [both: phase2 agents 2&9 · orchestrator-verified against source]

CiphernodeRegistryOwnable.publishCommittee · Confidence: 100

Description
publishCommittee (external, no access modifier) sets c.publicKey = pkCommitment unconditionally, and only runs the cryptographic DKG-proof verification (_verifyAndStoreDkgAnchors) when e3.proofAggregationEnabled == true — a value the requester chooses per-E3 (request(), never forced true). When aggregation is disabled, any address can post an arbitrary pkCommitment; "first caller wins" via the c.publicKey == bytes32(0) guard, so an attacker who front-runs the honest aggregator permanently substitutes their own key. The requester's confidential inputs then encrypt to a key the attacker controls, or the E3 is permanently bricked (honest publish reverts CommitteeAlreadyPublished).

Independently confirmed by the orchestrator reading CiphernodeRegistryOwnable.sol:289-336: line 307 (c.publicKey = pkCommitment) executes before the if (e3.proofAggregationEnabled) gate at line 311, and no caller check exists anywhere in the function.

Fix

  function publishCommittee(
      uint256 e3Id,
      bytes calldata publicKey,
      bytes32 pkCommitment,
      bytes calldata proof,
      bytes calldata dkgAttestationBundle
  ) external {
      Committee storage c = committees[e3Id];
      require(c.stage == ICiphernodeRegistry.CommitteeStage.Finalized, CommitteeNotFinalized());
      require(c.publicKey == bytes32(0), CommitteeAlreadyPublished());
      require(pkCommitment != bytes32(0), PkCommitmentRequired());
      ...
      E3 memory e3 = interfold.getE3(e3Id);
      if (e3.proofAggregationEnabled) {
          _verifyAndStoreDkgAnchors(...);
+     } else {
+         // Non-aggregation mode still needs SOME authenticated poster —
+         // e.g. a signature from the committee/aggregator over (e3Id, pkCommitment),
+         // or restrict msg.sender to an active committee member / trusted relayer role.
+         require(_isAuthorizedPublisher(e3Id, msg.sender, pkCommitment), UnauthorizedPublisher());
      }
      ...
  }

[90] 2. CommitteeHashLib.hash double-shifts each address, corrupting the committee-hash domain binding used by every BFV/DKG proof verifier [phase1: assembly · orchestrator-verified via first-principles bit arithmetic]

lib/CommitteeHashLib.hash · Confidence: 90

Description
bytes20 a = bytes20(nodes[i]) is already left-aligned in the 256-bit EVM word (Solidity represents bytesN as value << (256-8N), so a already equals addr << 96). The code then applies shl(96, a) — a second left-shift — discarding the top 96 bits and leaving only the address's low 64 bits (its last 8 bytes) in the high 8 bytes of the stored word, with the remaining 24 bytes zero. keccak256(packed) therefore never matches the canonical keccak256(concat(raw 20-byte addresses)) the on-chain NOTE explicitly says it must match (to agree with the off-chain/circuit e3_utils::committee_hash::hash_committee_addresses), and — independent of the off-chain mismatch — the resulting hash retains only 8 bytes of address entropy per node, so distinct committees whose members share trailing address bytes collide.

The orchestrator independently re-derived this via bit arithmetic: for a 256-bit word a with data in bits [255:96] (address left-aligned), shl(96, a) produces a word with data only in bits [192:255] — i.e., addr's bits [0:63] (last 8 bytes) — confirming the bug exactly as described, with a concrete forge-run example in the source pass (0xa284dd... expected vs. 0x3db399... actual for a 2-address committee).

Since BfvPkVerifier/BfvDecryptionVerifier gate DomainBindingMismatch on this hash matching the value the off-chain circuit computed over the true raw addresses, this bug either bricks 100% of proof-aggregation E3s in the currently-deployed state, or — if somehow tolerated — collapses the domain-separation the hash exists to enforce.

Fix

  assembly ("memory-safe") {
-     mstore(add(add(packed, 0x20), offset), shl(96, a))
+     mstore(add(add(packed, 0x20), offset), a)   // bytes20 `a` is already left-aligned; no shift needed
  }

[85] 3. Slashed collateral is routed and paid out in the per-E3 feeToken, which is never enforced to equal the ticket-collateral underlying — cross-E3 insolvency and fund drain [both: phase1 erc20 · phase2 agents math-precision, economic-security, execution-trace, invariant, boundary, first-principles (6 of 12)]

E3RefundManager.escrowSlashedFunds / _applySlashedFunds / distributeSlashedFundsOnSuccess · Confidence: 85

Description
Slashed collateral physically arrives at E3RefundManager as the ticket token's fixed underlying stablecoin (BondingRegistry.redirectSlashedTicketFunds → InterfoldTicketToken.payout → safeTransfer(underlying(), ...)), but is credited and paid out in the per-E3 feeToken — an independently rotatable, allow-listed value (Interfold.setFeeToken/setFeeTokenAllowed, snapshotted per-E3 in _e3FeeTokens). Nothing anywhere asserts feeToken == ticketToken.underlying().

Concrete numeric proof (from the "invariant" agent): E3 fee payment = 100 DAI, failed at Requested so requesterAmount = 95, protocolAmount = 5. A 50 USDC slash lands. _applySlashedFunds computes requesterGap = 100 - 95 = 5, credits dist.requesterAmount = 100 (still DAI-denominated). The refund manager physically holds only 100 DAI (from this E3) + 50 USDC (from the slash). The requester's claim of 100 DAI draws 5 DAI that never entered this E3's pool — silently stolen from other E3s' DAI balances held in the same contract — while the 50 USDC is never creditable to anyone in the DAI-denominated distribution and is permanently stranded.

This requires an intended, documented governance action (fee-token rotation, "survives global token rotation" per code comments) as a precondition, but once that supported configuration exists, the drain is fully automatic and harms uninvolved third parties (other E3s' requesters/honest nodes) — not self-harm.

Fix

- // amount received is always the ticket-token underlying, but credited as feeToken units
- dist.requesterAmount += amount;
+ // Track slashed-fund credits in the ticket-collateral underlying, separately
+ // from the fee-token ledger, and pay those claims in that token.
+ address slashedToken = address(ticketToken.underlying());
+ _pendingSlashedInUnderlying[e3Id][recipient] += amount;

or, more simply, enforce at the config boundary:

  function setFeeTokenAllowed(IERC20 token, bool allowed) external onlyOwner {
+     if (allowed) {
+         require(address(token) == address(ticketToken.underlying()), FeeTokenMustMatchCollateral());
+     }
      _feeTokenAllowed[token] = allowed;
  }

[80] 4. Proof-based (Lane A) deferred slash proposals do not block operator deregistration during the appeal window, letting the accused drain collateral before execution [phase2: agents execution-trace & asymmetry (2 of 12) · orchestrator-verified against source]

SlashingManager._proposeSlash / executeSlash · BondingRegistry.deregisterOperator · Confidence: 80

Description
BondingRegistry.deregisterOperator (lines 350-364) explicitly blocks deregistration while hasOpenLaneBProposal is true, and the developer's own comment states the intent precisely: "block deregistration while an unresolved Lane B slash proposal exists. An operator could otherwise drain ticket / license collateral during the appeal window and leave the slasher with nothing to slash." However hasOpenLaneBProposal reads _openLaneBCount, which is incremented only inside proposeSlashEvidence (Lane B, SlashingManager.sol:487). _proposeSlash (Lane A, lines 370-438) never touches this counter — confirmed by direct read — even though setSlashPolicy permits proof-based (Lane A) policies with appealWindow up to MAX_APPEAL_WINDOW (30 days), and fileAppeal's own code explicitly supports appeals on Lane A proposals with a non-zero window.

Proof-of-concept trace: An operator is accused via a Lane A proof-based policy with appealWindow = 30 days. The proposal defers (not atomic, since appealWindow != 0). The operator immediately calls deregisterOperator() — not blocked, since _openLaneBCount is 0 for a Lane A accusation. After exitDelay (≥1 day) elapses, they call claimExits() and withdraw their entire ticket + license collateral. When executeSlash finally becomes callable (up to 30 days later), slashTicketBalance/slashLicenseBond compute min(requested, available) = min(requested, 0) = 0 — the slash nets nothing. The exact protection the developers built for Lane B has a coverage gap for Lane A.

Fix

  function _proposeSlash(...) internal returns (uint256 proposalId) {
      ...
      uint256 executableAt = block.timestamp + policy.appealWindow;
      ...
+     if (policy.appealWindow > 0) {
+         _openLaneBCount[operator] += 1;   // reuse the same exit-block counter for any deferred lane
+     }
      if (policy.appealWindow == 0) {
          _executeSlash(proposalId, Lane.LaneA);
      }
  }
  function executeSlash(uint256 proposalId) external {
      ...
+     if (p.appealWindow > 0) {
+         _openLaneBCount[p.operator] -= 1;
+     }
  }

(and decrement symmetrically wherever a deferred Lane A proposal resolves without executing, e.g. a Lane A equivalent of resolveAppeal.)

[75] 5. ExitQueueLib permanently locks an operator's ticket balance and license bond after 64 lifetime single-asset exit-queue operations [phase2: agent periphery (1 of 12) · orchestrator-verified against source]

lib/ExitQueueLib.queueAssetsForExit / _takeAssetsFromQueue · Confidence: 75

Description
The live-tranche cap is require(len - min(headT, headL) < MAX_ACTIVE_TRANCHES) (64), but _takeAssetsFromQueue only advances the head for whichever asset type is actually processed — gated in claimAssets by if (maxTicketAmount > 0) / if (maxLicenseAmount > 0). An operator who bonds a license once at registration and thereafter only adjusts their ticket balance (a completely ordinary usage pattern) never triggers the License branch, so headL stays 0 forever while headT advances with every ticket exit.

Orchestrator-verified from source (ExitQueueLib.sol:140-206, 449-524 and BondingRegistry.sol:350-467): after 64 ticket-only exit cycles, len - min(headT, 0) = len = 64, and any further queueAssetsForExit call reverts TooManyTranches — including deregisterOperator (line 391, combined ticket+license call) and unbondLicense (line 467, the only two calls that could ever push a license tranche and thus advance headL). This is a circular deadlock: the operator's remaining ticket balance and their entire license bond become permanently unwithdrawable, with no recovery path, purely through ordinary long-term operation.

Fix

- uint256 headT = state.queueHeadIndexTicket[operator];
- uint256 headL = state.queueHeadIndexLicense[operator];
- uint256 earliestHead = headT < headL ? headT : headL;
- require(len - earliestHead < MAX_ACTIVE_TRANCHES, TooManyTranches());
+ // Cap on tranches that still hold a nonzero amount of EITHER asset, not on
+ // raw index distance from whichever head has advanced more slowly.
+ uint256 liveCount = _countLiveTranches(state, operator); // count tranches with ticketAmount>0 || licenseAmount>0
+ require(liveCount < MAX_ACTIVE_TRANCHES, TooManyTranches());

[70] 6. E3RefundManager.escrowSlashedFunds reads a frozen honest-committee snapshot never filtered against later expulsions — a slashed operator can reclaim up to 100% of their own penalty [phase2: agent flow-gap (1 of 12)]

E3RefundManager.escrowSlashedFunds · Confidence: 70

Description
_honestNodes[e3Id] is snapshotted once at processE3Failure (_getHonestNodes → getActiveCommitteeNodes). CiphernodeRegistryOwnable.expelCommitteeMember only flips memberStatus, never touching this stored array. If node A is later slashed and expelled for the same E3, the latecomer branch of escrowSlashedFunds (_claimCount>0 && honestNodeCount>0) still treats A as one of the "honest nodes" splitting the slashed pot. With a 1-member committee where A is the sole snapshotted honest node, A recovers 100% of their own seized stake via claimSlashedFundsOnSuccess. _applySlashedFunds (the _claimCount==0 branch) shares the identical defect.

Fix

- address[] storage nodes = _honestNodes[e3Id];
+ address[] memory nodes = ciphernodeRegistry.getActiveCommitteeNodes(e3Id); // re-fetch current active set, excluding expelled members
  for (uint256 i = 0; i < nodes.length; i++) {
      _pendingSlashedSuccess[e3Id][nodes[i]] += perNode;
  }

[65] 7. Late-arriving slashed funds skip the requester-first priority, permanently diverting requester compensation to honest nodes [phase2: agent asymmetry (1 of 12)]

E3RefundManager.escrowSlashedFunds · Confidence: 65

Description
The pre-first-claim branch (_applySlashedFunds) fills the requester's originalPayment gap before crediting honest nodes. The latecomer branch (triggered once any claim has been made, _claimCount>0) instead routes 100% of a subsequently-arriving slash to honest nodes with no check of whether the requester was ever made whole — the code's implicit assumption that _applySlashedFunds already ran is false whenever the first slash post-dates the first claim. Concrete numbers: requester capped at 550/1000 after failure; an honest node claims first; a 300 slash then arrives and is split entirely among honest nodes (150/150) instead of first topping the requester up to 850.

Fix

  // latecomer branch in escrowSlashedFunds
+ uint256 requesterGap = originalPayment - dist.requesterAmount;
+ uint256 toRequester = amount < requesterGap ? amount : requesterGap;
+ dist.requesterAmount += toRequester;
+ amount -= toRequester;
  uint256 perNode = amount / honestNodeCount;

[60] 8. Interfold.registerE3Program has no access control — anyone can allow-list an arbitrary E3 program contract [both: phase1 general & access-control · phase2 agents access-control, execution-trace, economic-security, boundary, first-principles (5 of 12) — 7 total independent flags across both phases]

Interfold.registerE3Program · Confidence: 60

Description
Every sibling setter (setDecryptionVerifier, setPkVerifier, setParamSet, disableEncryptionScheme) is onlyOwner; registerE3Program is not. Anyone can permanently enable an arbitrary contract as an E3 program, whose validate()/verify() run as external calls mid-request() (before e3s[e3Id] is committed, before the fee transfer, before requestCommittee) and at publishCiphertextOutput. No single agent constructed a concrete cross-party fund-theft chain — the malicious program only executes within the flow of the requester who selects it and pays their own fee, and the reentrancy window each agent traced self-funds or reverts on incomplete state — but this is the single most cross-corroborated item in the entire audit (7 of 21 total agent-passes across both phases flagged it independently), which per the audit methodology's multi-agent-convergence rule promotes it from a widely-demoted lead to a scored finding.

Fix

- function registerE3Program(IE3Program e3Program) external {
+ function registerE3Program(IE3Program e3Program) external onlyOwner {
      require(!e3Programs[e3Program], ModuleAlreadyEnabled(address(e3Program)));
      e3Programs[e3Program] = true;
      emit E3ProgramRegistered(e3Program);
  }
+ function disableE3Program(IE3Program e3Program) external onlyOwner {
+     e3Programs[e3Program] = false;
+ }

[55] 9. Owner can instantly halt all committee formation via unbounded, non-timelocked ticketPrice/minTicketBalance [both: phase1 governance · phase2 lead (economic-security)]

BondingRegistry.setTicketPrice / setMinTicketBalance · Confidence: 55

Description
Sortition weight for every operator is availableTickets = ticketBalance / ticketPrice, gated by require(availableTickets > 0). setTicketPrice only enforces != 0 — no upper bound, no timelock (unlike MIN/MAX_EXIT_DELAY). setMinTicketBalance has no bounds at all. A malicious or compromised owner sets ticketPrice above every operator's balance in a single transaction; every submitTicket then reverts NodeNotEligible, no committee can ever form, and every pending/future E3 fails. Owner-only, no fund loss, but a full, instant, single-transaction DoS of the core sortition subsystem with no timelock to allow reaction.

Fix: Add MIN_TICKET_PRICE/MAX_TICKET_PRICE and MAX_MIN_TICKET_BALANCE bounds analogous to existing exit-delay guards, and route these changes through the same delayed/timelocked flow already used for the ticket-token registry pointer and the DKG verifier.

[50] 10. Non-aggregation E3s finalize with zero output verification, paying the committee for unverified plaintext [phase2: agents trust-gap & boundary (2 of 12)]

Interfold.publishPlaintextOutput · Confidence: 50

Description
Sharing the same proofAggregationEnabled toggle as Finding #1, publishPlaintextOutput sets success = true with no decryptionVerifier.verify() call when aggregation is off, then distributes the full fee to the committee. Likely intended as an accepted trust-mode tradeoff since the requester opts into non-aggregation, but shares the identical unverified-boundary root cause as Finding #1.

Fix: Require aggregation-mode verification unconditionally, or explicitly document/gate non-aggregation E3s as a "trusted mode" with a clear interface-level warning.

[50] 11. Critical fund-routing pointers (e3RefundManager, slashingManager, bondingRegistry, ciphernodeRegistry) are swappable instantly with no timelock, unlike other critical pointers in the same codebase [phase1: access-control]

Interfold.setE3RefundManager (and peer setters) · Confidence: 50

Description
The team already recognized this exact "compromised owner swaps a critical address" risk for dkgFoldAttestationVerifier and protected it with a 2-day propose/commit timelock. The equally-powerful fund-routing pointer e3RefundManager has none: setE3RefundManager → processE3Failure (permissionless) sends the E3's escrowed payment to whatever address currently sits there, so a compromised owner can redirect all failed-E3 refunds/rewards to an attacker-controlled sink in one transaction.

Fix: Put critical wiring pointers behind the same propose/commit timelock already used for the DKG fold verifier, or route through governance.
