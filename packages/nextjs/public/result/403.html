[92] 1. createTask binds a non-consenting worker, enabling reputation forgery and a permanent partial deposit lock

TestTaskRegistry.createTask · Confidence: 92 · Severity: High

Description
createTask(worker, ...) (TaskRegistry.sol:280-340) binds any address holding ≥$25 in AgentDepositVault as the task's worker and activates the task immediately (state = ACTIVE, L314; _bindAgent(worker), L333) — the only checks are worker != msg.sender (L293) and a balance/blocked check (requireMinimum(worker), L299); there is no signature, approval, or acknowledgment from the named worker. The victim cannot self-exit: leaveTask requires state == CLAIMED (L240), but a direct hire is born ACTIVE and never passes through CLAIMED. Because deadline is also unvalidated (no deadline > block.timestamp check anywhere in createTask or postTask), an attacker can set it to any value. Two independent harms follow, both reachable in the same attack:

  • Reputation forgery. If the attacker funds the task (fundTask, even 1 wei) so EscrowVault.lockedBalance(taskId) > 0, and lets the deadline pass, anyone can call expireTask (permissionless). Because wasFundedActive = (state==ACTIVE && locked>0) is true (TaskRegistry.sol:503) and t.worker != address(0), expireTask emits a full-weight (100) TASK_FAILED signal against the victim (L514-523) — a permanent on-chain reputation mark for a task the victim never agreed to and had no ability to complete or decline. The attacker's funded escrow is refunded to them at the same call (L505-507). Net attacker cost: one access fee (~$5 USDC + 1,000 AZL); the 1-wei funding is fully refunded.
  • Deposit lock. With liveTaskBindings[victim] > 0, maxWithdrawableDeposit (TaskRegistry.sol:539-548) reserves the MIN_TASK_BALANCE ($8) floor of the victim's deposit for as long as the task stays open. With a far-future deadline, this is an indefinite lock; the victim's only self-service escape is openDispute (TaskRegistry.sol:474), which pulls them into arbitration and can cost them a dispute bond.

Verification: Read directly against TaskRegistry.sol in this reconciliation pass (lines above quoted from the actual file, not agent paraphrase). Independently reconstructed with a concrete numeric PoC by 9 of 12 blind Phase-2 attack agents (access-control, periphery, execution-trace, economic-security, first-principles, boundary, invariant, trust-gap, flow-gap) and by the Phase-1 access-control checklist agent — the highest-convergence finding of the engagement.

[88] 2. EscrowVault.streamRelease/claimHourBlock have no reachable release path — STREAMING/HOUR_BLOCKS workers have no enforceable payout

EscrowVault.streamRelease / EscrowVault.claimHourBlock · Confidence: 88 · Severity: High

Description
TestTaskRegistry.postTask/createTask accept EscrowMode.STREAMING and EscrowMode.HOUR_BLOCKS with no restriction (_validateTaskTerms, TaskRegistry.sol:597-614, only constrains MILESTONE mode — L603 returns immediately for any other mode), and fundTask funds them normally via depositFor. But EscrowVault.streamRelease (EscrowVault.sol:158) and claimHourBlock (EscrowVault.sol:182) are onlyRegistry, and no function anywhere in TaskRegistry.sol calls either one (grep-confirmed across the full file). submitProof — the only path into the worker-protective IN_REVIEW state and its resolveStaleReview optimistic-acceptance backstop — reverts for any non-MILESTONE task (TaskRegistry.sol:355-358, "TaskRegistry: not milestone").

Consequently, a worker who claims and performs work on a STREAMING/HOUR_BLOCKS task has exactly two ways the funded escrow can move: poster-discretionary completeTask (all remaining escrow → worker, TaskRegistry.sol:444-460), or permissionless post-deadline expireTask (all remaining escrow → poster, TaskRegistry.sol:493-527). There is no unilateral worker claim, and no partial-payment protection of any kind — a poster can let a streaming worker deliver work for the task's full duration and then simply never call completeTask, reclaiming 100% of the funded escrow via expireTask once the deadline passes.

Verification: grep -n "streamRelease\|claimHourBlock" src/*.sol confirms the only occurrences are the two function definitions themselves — zero call sites. Independently found as a Finding by 2 of 12 blind Phase-2 agents (first-principles, asymmetry) and as a Lead by 4 more (periphery, boundary, flow-gap, numerical-gap); flagged at Low severity in Phase 1 (general-3) before the payment-loss implication was traced through by Phase 2.

[80] 3. TreasuryRouter's 20% protocol reserve is not segregated from the distributable pool — permissionlessly recycled every epoch, and fully drainable by feeRecipient before distribution

TreasuryRouter.distributeRevenue / TreasuryRouter.withdrawFees · Confidence: 80 · Severity: Medium

Description
distributeRevenue (TreasuryRouter.sol:121-149) splits accruedFees[usdc] 40% staker / 40% buyback / 20% reserved, then writes the reserve back into the same storage slot it just read as its distribution base:

uint256 amount = accruedFees[address(usdc)];              // L130
...
uint256 reserved = amount - stakerShare - buybackShare;   // L135
lastDistributionAt = block.timestamp;
accruedFees[address(usdc)] = reserved;                     // L138 — same slot

Two consequences, both verified directly against the source:

  • Permissionless recycling (no privilege required): distributeRevenue is callable by anyone once the 7-day epoch elapses. With no new fees accruing, the "reserve" decays geometrically: $1,000 → epoch 1 leaves $200 reserved → epoch 2 leaves $40 → epoch 3 leaves $8 → → 0, with the difference each round paid out 40/40 to stakers/buyback instead of retained. The documented "20% remains accrued as protocol reserve" (L119 comment) does not hold across more than one distribution.
  • feeRecipient full-pool capture: withdrawFees(token, to) (TreasuryRouter.sol:186-193) reads and zeroes the entire accruedFees[token] with no cap and no ordering guarantee relative to distributeRevenue. Because the reserve and the not-yet-distributed 80% staker/buyback share live in the same variable, feeRecipient calling withdrawFees(usdc, ...) before distributeRevenue runs takes 100% of accrued USDC — not just the intended 20% — leaving stakers and the buyback executor with nothing that epoch (and distributeRevenue then reverts with "nothing to distribute").

This degrades the documented 40/40/20 revenue-sharing invariant and undermines the UnionStakingVault USDC-reward value proposition (stakers' expected yield is not actually guaranteed by the code). It does not let an external, unprivileged attacker steal funds for themselves — the misdirected value stays within the protocol's own destinations (reserve vs. stakers vs. buyback) or requires the trusted feeRecipient role — which is why this is Medium rather than High/Critical per the given severity rubric (trust-model violation / incorrect accounting, not external fund theft).

Verification: Read directly against TreasuryRouter.sol in this reconciliation pass. Independently found as a Finding by 3 of 12 blind Phase-2 agents (math-precision with a full numeric trace, periphery, trust-gap) and as a Lead by 3 more (economic-security, numerical-gap, invariant); corroborates Phase 1's staking-1 (also Medium).

[78] 4. MIN_TASK_BALANCE is a flat per-agent floor, not per-binding — under-collateralizes multi-task agents and makes the balance-health watchdog structurally unreachable

AgentDepositVault (meetsTaskMinimum, all debit functions) / TestTaskRegistry (maxWithdrawableDeposit, _enforceBalanceHealth) · Confidence: 85 · Severity: Medium

Description
MIN_TASK_BALANCE = 8_000_000 is documented "$8 per live task binding" (AgentDepositVault.sol:20), and liveTaskBindings[agent] (TaskRegistry.sol:36) exactly tracks how many live tasks an agent is bound to. But every place the floor is actually enforced treats it as a flat value, independent of that count:

  • maxWithdrawableDeposit (TaskRegistry.sol:539-548): if (liveTaskBindings[agent] > 0) { floor = agentVault.MIN_TASK_BALANCE(); ... return bal - floor; } — a single MIN_TASK_BALANCE, not MIN_TASK_BALANCE * liveTaskBindings[agent].
  • meetsTaskMinimum (AgentDepositVault.sol:136-138): deposits[agent] >= MIN_TASK_BALANCE && !isBlocked(agent) — same flat comparison, used by every solvency check in the system.

An agent bound to N concurrent tasks is therefore "healthy" and can freely withdraw down to a single shared $8, not $8×N — the documented per-task collateral guarantee does not exist in the code.

This is verified (this reconciliation pass, by direct enumeration of every deposits[x] -= site) to have a second, more structural consequence. Every function that decreases deposits[agent] enforces a floor ≥ this same flat value:

  • withdraw (AgentDepositVault.sol:98-108): capped by maxWithdrawableDeposit, floors at $8 while bound.
  • debitDisputeBond (AgentDepositVault.sol:184-192): require(deposits[agent] - amount >= MIN_TASK_BALANCE) — floors at $8.
  • debitAccessFee/debitDismissFee/debitLeaveFee (AgentDepositVault.sol:207-275): each requires deposits >= MIN_ENTRY_BALANCE + fee before debiting the fee, leaving the post-debit balance ≥ MIN_ENTRY_BALANCE ($25).
  • Every binding entrypoint (postTask, claimTask, createTask) requires ≥ MIN_ENTRY_BALANCE ($25) via requireMinimum/requireBalanceForFee before the corresponding _bindAgent call.

So a bound agent's deposits[agent] can never fall below $8 through any code path. The only other way meetsTaskMinimum can return false is isBlocked(agent), and blockedUntil (the sole storage backing isBlocked) is written in exactly one place: applyPlatformPenalty (AgentDepositVault.sol:277-279), whose only caller in the entire codebase is _finalizePausedTask (TaskRegistry.sol:711), which itself only runs when a task that is already PAUSED reaches pauseEndsAt (TaskRegistry.sol:628-631) — and a task only becomes PAUSED when _firstUnderfunded (TaskRegistry.sol:656-660) returns a non-zero address, i.e. when meetsTaskMinimum is already false for some party. This is fully circular with no bootstrap: nothing outside this exact subsystem can ever produce the state ("underfunded or blocked") that the subsystem exists to detect and act on.

Net effect: the permissionless "balance-health watchdog" — checkTaskBalance → pause → resume-or-finalize → 7-day platform block + best-effort reputation reset — can never trigger for any agent, for any task, under any reachable sequence of calls. It is fully dead code, despite being described in an inline @notice comment (TaskRegistry.sol:253) as an active protection ("Permissionless balance watchdog — pause, resume, or finalize delete"). This also means emergencyTopUp (which requires state == PAUSED) is unreachable, and the _finalizePausedTask milestone-forfeiture asymmetry (Finding 5, below) is currently dormant.

Verification: Read directly against AgentDepositVault.sol and TaskRegistry.sol in this reconciliation pass; every deposits[x] -= site and the sole blockedUntil writer were individually traced and confirmed to hold the floor invariant described above, with no bypass found. Independently converged on from different angles by 5 of 12 blind Phase-2 agents (boundary and invariant as standalone Findings; asymmetry, trust-gap, and flow-gap as Leads reaching the identical circular-precondition conclusion); the flat-floor half was separately flagged (without the dead-watchdog implication) by Phase 1's general-1 (Low).

     // TaskRegistry.sol
     function maxWithdrawableDeposit(address agent) external view returns (uint256) {

-        if (liveTaskBindings[agent] > 0) {
-            uint256 floor = agentVault.MIN_TASK_BALANCE();

[55] 5. _finalizePausedTask forfeits a worker's already-proven milestones to the poster when the worker (not the poster) is the pause culprit

TestTaskRegistry._finalizePausedTask · Confidence: 55 (Low — currently unreachable, see Finding 4) · Severity: Low

Description
When a paused task finalizes, _finalizePausedTask (TaskRegistry.sol:679-715) only releases proven-but-unaccepted milestones to the worker when culprit == t.poster && p.resumeState == IN_REVIEW (L684-697). In the mirror case — culprit == t.worker while IN_REVIEW with proven milestones sitting in _pendingReview — that branch is skipped and refundRemainingToPoster (L698) returns the entire remaining escrow, including the worker's already-delivered, proof-accepted-pending value, to the poster; the worker is additionally 7-day platform-blocked (applyPlatformPenalty). A worker who did the work and submitted proof loses it entirely if they happen to be attributed as the culprit.

This asymmetry is real in the code but is currently contingent on Finding 4: since _firstUnderfunded can never return a non-zero address today, no task can ever reach _finalizePausedTask with any culprit at all, poster or worker. It becomes live the moment Finding 4 is fixed (correctly, since fixing 4 is what makes underfunding — and hence a worker-culprit finalize — reachable), so both should be fixed together.

[40] 8. Self-dealt post→claim→complete cycle mints a full-weight, non-discounted TASK_COMPLETED reputation signal cheaply
A single actor controlling two funded ($25+) addresses can postTask→claimTask→completeTask between themselves for ~2 access fees, producing a recordCompletion signal with taskTypeHash = 0 (the non-direct-hire/"arms-length" signal, TaskRegistry.sol:578-582) indistinguishable on-chain from a genuine completion. [38] 9. expireTask stamps TASK_FAILED on workers who already delivered accepted milestones
wasFundedActive (TaskRegistry.sol:503) can't distinguish a wholly-failed worker from one who completed and was paid for earlier milestones before hitting the deadline on remaining scope — both get the same full-weight (100) TASK_FAILED signal (L514-523). Fix: skip/discount the signal when _completionRecorded[taskId] is already true.

[35] 10. A milestone task cannot be topped up once its first milestone is released
EscrowVault._applyDeposit (L123-127) requires state == UNFUNDED || LOCKED; after the first releaseMilestone the state becomes PARTIAL_RELEASE, so a subsequent fundTask/depositFor reverts. A poster who under-funds a milestone task and accepts the first milestone can never fund the remaining milestones — submitProof then reverts "unfunded" for the rest — a workflow dead-end, not a fund-loss. Fix: allow deposits while PARTIAL_RELEASE, or require full funding before the first milestone release.
