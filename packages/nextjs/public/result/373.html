[95] 1. Zero threshold on the un-initializable implementation contract lets anyone drain it with zero signatures

Multisig._verifySignatures / execTransaction / execBatchTransaction / isValidSignature · Confidence: 95 · [both: phase1 proxies-domain agent + phase2 agents 5 (invariant) & 7 (first-principles), independently]

Description
The constructor's _disableInitializers() permanently blocks initialize() on the raw implementation contract (the address every clone delegates to, publicly readable via MultisigFactory.implementation()), but nothing else ever sets threshold there, so it stays 0 forever; _verifySignatures's gate signatures.length < threshold is 0 < 0 == false for an empty array, so an empty Signature[] "passes" a 0-of-0 quorum, and execTransaction/execBatchTransaction/isValidSignature all proceed as if fully authorized.

Proof of Concept

  1. implementation (Multisig.sol) is a real, permanently deployed contract with an unconditional receive() (L403) and unconditionally-accepting ERC-721/1155 hooks (L405-419) — any ETH or NFT sent to it (by mistake, an automated sweep, or a probe) is accepted.
  2. Attacker calls Multisig(payable(implementation)).execTransaction(attacker, implementation.balance, "", block.timestamp + 1, new Signature ).
  3. Inside _verifySignatures (L318-337): threshold == 0 (never set — initialize, the only writer, is permanently blocked at L98-100/L116), signatures.length == 0, so if (signatures.length < threshold) (L319) evaluates 0 < 0 == false → no revert; the for loop (L322) runs zero iterations.
  4. Back in execTransaction: nonce++ (L274), then target.call{value: implementation.balance}("") (L276) sends the balance to the attacker. The identical bypass makes isValidSignature (L377-399) return the ERC-1271 magic value for any hash via the same 0 < 0 gate at L379.

No live clone can reach this state — initialize's own bound check (_threshold == 0 || _threshold > total, L121) and changeThreshold's (L217) prevent threshold from ever being 0 post-init — this is specific to, but always present on, the one implementation contract every deployment of this system requires.

Fix

     function _verifySignatures(bytes32 hash, Signature[] calldata signatures) internal view {
-        if (signatures.length < threshold) revert ThresholdNotMet();
+        if (threshold == 0 || signatures.length < threshold) revert ThresholdNotMet();

     function isValidSignature(bytes32 hash, bytes memory signatures) external view returns (bytes4 magicValue) {
         Signature[] memory sigs = abi.decode(signatures, (Signature[]));
-        if (sigs.length < threshold) return 0xffffffff;
+        if (threshold == 0 || sigs.length < threshold) return 0xffffffff;

[85] 2. No domain separation between the exec digest and generic ERC-1271 message signing enables blind-signing phishing

Multisig.getExecHash / getBatchExecHash / isValidSignature / _recoversTo · Confidence: 85 · [both: phase1 general + signatures domains + phase2 agent 4 (execution-trace, full concrete numeric proof) & agent 12 (flow-gap)]

Description
getExecHash/getBatchExecHash (L244-255) are bare abi.encode digests with no EIP-712 domain separator or type-hash. isValidSignature (L377-399) — which the contract's own NatSpec advertises as letting "the multisig itself sign off-chain messages" (L19-20) — validates any externally-supplied bytes32 hash through the identical signer-verification path (_isValidAccountSig/_isValidPasskeySig) used to authorize fund transfers, and _recoversTo (L365-371) accepts both a raw digest and a personal_sign-prefixed one. A signer therefore cannot tell, from an opaque hash they're asked to personal_sign for what looks like a message-signing or nested-cosigning request, whether it is in fact a live spend-authorization digest for the wallet's current nonce.

Proof of Concept

  1. Attacker reads public state: nonce, address(this), block.chainid, and picks target = attacker, value = <victim balance>, data = "", a near-future deadline.
  2. Attacker computes H = getExecHash(attacker, value, "", deadline) off-chain (a pure view function) using the wallet's live nonce.
  3. Attacker presents H to threshold signers independently disguised as an unrelated "sign in" / message-approval / nested-Safe-cosigning request (a raw hex blob — nothing in a personal_sign prompt distinguishes it from an exec digest).
  4. Once threshold signers have each personal_signed H, attacker assembles the sorted Signature[] and calls execTransaction(attacker, value, "", deadline, signatures) before deadline — _verifySignatures (L318-337) recomputes and matches H exactly, passes, and the wallet is drained.

Fix

-    function getExecHash(address target, uint256 value, bytes calldata data, uint256 deadline)
-        public
-        view
-        returns (bytes32)
-    {
-        return keccak256(abi.encode(block.chainid, address(this), nonce, deadline, target, value, keccak256(data)));
-    }
+    bytes32 private constant EXEC_TYPEHASH =
+        keccak256("ExecTransaction(uint256 chainId,address wallet,uint256 nonce,uint256 deadline,address target,uint256 value,bytes32 dataHash)");
+
+    function getExecHash(address target, uint256 value, bytes calldata data, uint256 deadline)
+        public
+        view
+        returns (bytes32)
+    {
+        return _hashTypedDataV4(keccak256(abi.encode(
+            EXEC_TYPEHASH, block.chainid, address(this), nonce, deadline, target, value, keccak256(data)
+        )));
+    }

Adopt OZ EIP712 (domain separator over name/version/chainid/verifyingContract) with a distinct type-hash for getBatchExecHash too, and give isValidSignature's generic message-signing path its own, differently-tagged type-hash (mirroring Safe's SafeTx vs SafeMessage split) so a signature valid in one context can never validate in the other.

[70] 3. No enforced maximum validity window lets signed transactions become stale "time bombs"

Multisig.execTransaction / execBatchTransaction · Confidence: 70 · [phase1: governance domain]

Description
deadline (L268, L288 params) is caller/signer-chosen with no protocol-enforced upper bound; the only check is block.timestamp > deadline (L271, L294). A signature set collected for prompt execution (e.g. a swap with a minOut computed off current prices) remains a live, executable authorization for as long as the wallet's nonce doesn't move — which can be indefinite if the wallet is otherwise idle — so state-dependent parameters can go stale, or the signers' intent can simply no longer match reality, before anyone (signer or not, since these functions have no caller restriction) finally submits it.

Proof of Concept
Signers sign execTransaction(dex, value, swapCalldata(minOut=X), deadline=block.timestamp+365 days) intending same-day execution. Submission is delayed (slow relayer, or a signer intentionally withholds it). Months later, market conditions have moved so minOut=X is now stale/unfavorable; any address holding the still-valid signature set executes it at the old parameters — the nonce binding stops replay but does nothing to stop late-but-first execution.

Fix

+    uint256 public constant MAX_DEADLINE_WINDOW = 7 days;
+
     function execTransaction(...) external nonReentrant returns (bytes memory result) {
         if (block.timestamp > deadline) revert ExpiredSignature();
+        if (deadline > block.timestamp + MAX_DEADLINE_WINDOW) revert ExpiredSignature();

(mirror in execBatchTransaction)

[97] 4. credentialIdHash collision lets removeSigner wipe an unrelated, still-active signer's reverse lookup

Multisig._addSigner / removeSigner · Confidence: 97 · [both: phase1 access-control domain + 10 of 12 phase2 agents independently: math-precision, access-control, economic-security, execution-trace, invariant, periphery, first-principles, asymmetry, boundary, numerical-gap, trust-gap]

Description
_addSigner (L229-239) writes credentialIdToAddress[credId] = signer and credentialIdOf[signer] = credId with no check that credentialIdToAddress[credId] is already claimed by a different signer. If two passkey signers are ever registered with the same non-zero credentialIdHash (duplicate entries in one initialize() call, or a later addPasskeySigner), the second registration silently overwrites the first signer's reverse-lookup entry while the first signer's own credentialIdOf stays stale, pointing at the same shared hash. A later, entirely legitimate removeSigner on the first signer then deletes the second, still-active signer's live reverse-lookup entry as collateral damage — breaking the documented invariant credentialIdOf[a]==c!=0 => credentialIdToAddress[c]==a. This does not affect signature verification or fund custody — _verifySignatures/isValidSignature key off signerInfo[address].qx/qy directly, never through this mapping — the impact is confined to getPasskeyByCredentialId's off-chain login/lookup convenience function.

Proof of Concept

  1. Passkey signer A registered (via initialize or addPasskeySigner) with credId = X: credentialIdToAddress[X] = A, credentialIdOf[A] = X.
  2. Passkey signer B later registered, different (qx,qy) but the same credId = X (typo, copy-paste, or two entries in one initialize array): _addSigner (L234-236) overwrites credentialIdToAddress[X] = B; credentialIdOf[A] is untouched and still reads X.
  3. Quorum calls removeSigner(A) for an unrelated reason (e.g. device rotation): removeSigner (L199-203) reads credId = credentialIdOf[A] == X, and executes delete credentialIdToAddress[X] — but that slot currently belongs to B, a fully active signer never touched by this call. getPasskeyByCredentialId(X) now returns address(0) even though B remains a valid, threshold-eligible signer.

Fix

     function _addSigner(address signer, SignerType kind, bytes32 qx, bytes32 qy, bytes32 credId) internal {
         if (signer == address(0)) revert InvalidSigner();
         if (signerInfo[signer].exists) revert AlreadySigner();
         signerInfo[signer] = SignerInfo({ exists: true, kind: kind, qx: qx, qy: qy });
         _signers.push(signer);
         if (credId != bytes32(0)) {
+            if (credentialIdToAddress[credId] != address(0)) revert AlreadySigner();
             credentialIdToAddress[credId] = signer;
             credentialIdOf[signer] = credId;
         }

and in removeSigner, only clear the reverse entry if it still points back at the signer being removed:

         bytes32 credId = credentialIdOf[signer];
         if (credId != bytes32(0)) {
-            delete credentialIdToAddress[credId];
+            if (credentialIdToAddress[credId] == signer) delete credentialIdToAddress[credId];
             delete credentialIdOf[signer];
         }

[65] 5. Unbounded ERC-1271 recursion via nested/cyclic Multisig signers (gas-griefing DoS)

Multisig.isValidSignature / _isValidAccountSig · Confidence: 65 · [both: phase1 signatures domain + phase2 agents 5, 4, 3]

Description
Only direct self-registration is blocked (_addAccountSigner rejects signer == address(this), L225); an indirect cycle is not — Multisig A can register Multisig B as a signer while B independently registers A. _isValidAccountSig's staticcall to a signer's isValidSignature (L347) has no depth counter, so a crafted nested signature walking such a cycle recurses until gas exhaustion or the 1024-call-depth limit, reverting that specific execution/validation attempt.

Fix: track and cap recursion depth through the ERC-1271 delegation path (e.g. pass a depth counter via a wrapper, reverting past a small max), or require nested-signer registrations to pass an explicit acyclic-hierarchy check (e.g. via getSigners() introspection when the candidate is itself a Multisig).

[60] 6. Signer/threshold governance has no timelock

Multisig.onlySelf cluster (removeSigner, changeThreshold) via execBatchTransaction · Confidence: 60 · [phase1: access-control domain]

Description
A coalition reaching exactly threshold can bundle changeThreshold(1) + removeSigner(...) for every other signer + an arbitrary fund transfer into one atomic execBatchTransaction (L287-307), with no delay or notice for the excluded signers. This is inherent to any purely self-governed M-of-N scheme (identical to Gnosis Safe's own model) — flagged for completeness and deployment guidance rather than as a distinct code defect.

Fix: optionally add a timelock/delay specific to signer-set and threshold changes (distinct from ordinary fund-moving execTransaction), or explicitly document that reaching threshold is equivalent to permanent full control, not just approval of a single transaction.

[55] 7. Self-governed quorum has no recovery path if enough signers become unavailable

Multisig.removeSigner / changeThreshold / execTransaction · Confidence: 55 · [phase1: governance domain]

Description
All signer/threshold changes are onlySelf, reachable only via a threshold-signed self-call. If threshold == signerCount (N-of-N) and even one signer's key is permanently lost, no remaining coalition can ever reach threshold again — the wallet, including its own recovery functions, locks forever. Inherent to pure self-governance (same property Gnosis Safe has), not a coding defect.

Fix: document the risk for integrators/deploy tooling (warn against threshold == signerCount); optionally offer an opt-in, long-time-locked fallback recovery path for deployments that want resilience against key loss.

[55] 8. A single key can satisfy two "independent" signer slots via a nested Multisig sharing that key

Multisig._verifySignatures / isValidSignature / _isValidAccountSig · Confidence: 55 · [phase2 only: trust-gap agent, full concrete trace]

Description
_addAccountSigner only blocks literal signer == address(this) (L225); it cannot detect that a separately-registered Account signer (e.g. a nested Multisig clone) resolves its own quorum using the same private key already registered directly on the parent. One signing action by that shared key can then satisfy both the direct ECDSA check and the nested wallet's isValidSignature (which itself re-derives from the same key), silently collapsing the wallet's effective threshold. This requires the quorum to voluntarily register the overlapping configuration — no general on-chain check can detect key correlation across independently-registered contract wallets.

Fix: document that registering both a direct signer and a nested wallet under common key control degrades the effective threshold; where the nested signer is introspectable (another instance of this same Multisig contract), optionally reject registration if getSigners() of the candidate overlaps with the parent's own _signers.

[90] 9. Free-memory-pointer bump under-counts bytes written by the clone-bytecode assembly (currently benign)

Clones.cloneDeterministic / predictDeterministicAddress · Confidence: 90 · [both: phase1 assembly domain + phase2 agents 1, 6 — all three independently confirmed via byte-level trace]

Description
The third mstore (Clones.sol:29 / :58) writes a full 32-byte word starting at ptr+0x28 (40), touching memory through ptr+0x48 (72). The subsequent mstore(0x40, add(ptr, 0x40)) (Clones.sol:33 / :61) only reserves through ptr+0x40 (64) — 8 bytes [ptr+64, ptr+72) are written but fall outside the newly-reserved region. Verified directly against the source: those 8 bytes are the trailing zero-padding of the suffix literal (0x5af43d82803e903d91602b57fd5bf3 followed by 17 zero bytes, of which the last 8 land past the reservation), and Solidity assumes unallocated memory is zero — so the gap is harmless today only because those specific bytes happen to be zero, not because the arithmetic accounts for the true write extent. A future edit to the suffix constant with non-zero low bytes would silently corrupt the next allocation.

Fix

-        mstore(0x40, add(ptr, 0x40))
+        mstore(0x40, add(ptr, 0x48))

(apply to both cloneDeterministic and predictDeterministicAddress)

[80] 10. Reliance on Cancun-only opcodes (transient storage) with no pinned EVM version risks unusable or silently-non-functional deployments on some chains

Multisig.sol (import of ReentrancyGuardTransient, L9) · Confidence: 80 · [phase1: general domain; corroborated by repo's own deploy-target list]

Description
ReentrancyGuardTransient uses TLOAD/TSTORE (EIP-1153, Cancun); combined with the >=0.8.24 pragma (which by default also emits PUSH0, Shanghai), deployment requires both Shanghai and Cancun support. foundry.toml defines RPC endpoints for several chains that may lag full Cancun support, and its own comments already flag zkSync/Abstract as CREATE2-incompatible for a different reason — deploying to a chain without transient-storage support would either fail to deploy or, worse, silently no-op the reentrancy guard the code comments explicitly rely on ("audit C L-3").

Fix: pin evm_version in foundry.toml to the intended target chain(s) per-deployment, or fall back to a standard storage-slot ReentrancyGuard if broad multichain/L2 deployment is in scope.

[80] 11. Signature-verification logic duplicated between _verifySignatures and isValidSignature

Multisig._verifySignatures (L318-337) vs isValidSignature (L377-399) · Confidence: 80 · [both: phase1 general domain + phase2 agent 6 (periphery)]

Description
The same threshold/ordering/kind-matching/per-signer-validation loop is implemented twice — once reverting on failure, once returning a magic-value/failure-selector. Diffed field-by-field by three independent agents across both phases: currently semantically identical, but nothing enforces they stay that way under future edits.

Fix: factor the shared loop into one internal _checkSignatures(hash, signatures) returns (bool) helper used by both call sites.

[75] 12. isValidSignature can revert instead of returning the ERC-1271 failure selector on malformed input

Multisig.isValidSignature (L377-378) / _isValidPasskeySig (L355-357) · Confidence: 75 · [both: phase1 signatures domain + phase2 agent 7 (first-principles)]

Description
abi.decode on caller-supplied signatures/data blobs reverts on malformed input rather than returning 0xffffffff per ERC-1271 convention. Not independently exploitable — this contract's own internal caller (_isValidAccountSig) already wraps external ERC-1271 calls in try/catch, and standard SignatureChecker-style callers use a static call that tolerates reverts — listed for strict standards compliance.

Fix: optionally guard the decode with a length/format pre-check that returns the failure selector instead of reverting on malformed input, for callers that don't tolerate reverts.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed, or where reconciliation determined the trail largely matches documented design intent. Not scored above the confidence floor.

  • EIP-7702 signer authority widening — Multisig._isValidAccountSig — Code smells: signer.code.length is re-read live on every verification (L346), not pinned at registration time, so an EOA signer registered when codeless can later acquire code via an EIP-7702 delegation the multisig has no visibility into, silently shifting that slot's authentication from "this key signs" to "whatever the delegated code approves." Demoted from a top-level finding during reconciliation: the contract's own NatSpec (L14-17) explicitly lists "EIP-7702-delegated EOA" as a supported Account-signer flavor and documents the ECDSA-then-ERC-1271 fallback as intentional — the residual risk is scoped to an individual signer's own wallet/authorization hygiene, the same accepted trust boundary as any Safe/nested-Multisig signer, rather than a distinct code defect.
  • Unvalidated secp256r1 curve point for passkey registration — Multisig.addPasskeySigner / _addSigner (via initialize) — Code smells: only qx != 0 && qy != 0 is checked (L128, L186); no on-chain validation that (qx, qy) is actually a point on the curve. A garbage pair permanently burns a signer slot that can never produce a valid signature but still counts toward the threshold denominator. Registration is cooperative/self-selected, so this is self-harm-adjacent — flagged for defense-in-depth.
  • Passkey registration path missing the self-reference guard that the Account path has — Multisig._addSigner (via addPasskeySigner/initialize) — Code smells: _addAccountSigner rejects signer == address(this) (L225); the passkey path has no equivalent check against getPasskeyAddress(qx,qy) == address(this). Exploiting this requires a ~2^160 preimage search — infeasible with current hash functions; flagged as a consistency/defense-in-depth gap only.
  • CREATE2 address squatting if createMultisig is ever invoked through a shared relayer/forwarder — MultisigFactory.createMultisig / _effectiveSalt — Code smells: effectiveSalt = keccak256(msg.sender, salt) isolates addresses per literal msg.sender; safe for direct EOA calls (the only pattern demonstrated in the in-scope code), but would allow front-running/address-squatting if a shared relayer or meta-tx forwarder were ever the caller on behalf of multiple end users. Not reachable in the code as scoped — noted as a deployment-pattern caveat for any future integration, not a finding against the current contracts.
