What this contract is: a single-owner, hook-owned-liquidity Uniswap v4 hook for one specific SLEUTH/USDC pool on Base. The owner manages a concentrated "MAIN" range position and a single-sided USDC "BID" band below the market price, routed through a custom raw-salt unlock/unlockCallback dispatcher. Public liquidity provision is disabled (addLiquidity/removeLiquidity always revert) — the hook is the pool's sole LP. On every swap, _afterSwap may permissionlessly trigger an auto-compound of accrued MAIN fees back into the position, threshold-gated and wrapped in try/catch so it can never revert the swap.

Findings

[70] 1. Permissionless in-swap auto-compound has no slippage floor — accrued fees redeploy at attacker-influenceable spot price

OwnerManagedRangeHook._afterSwap() / compoundInSwap() / _compoundLogic() · Confidence: 70 · [both] — phase1: evm-audit-general (GEN-1), evm-audit-defi-amm (AMM-2) · phase2: FINDING (execution-trace, agent 4) + LEADs (math-precision, access-control, economic-security, periphery, first-principles, asymmetry, boundary, trust-gap, flow-gap — 9 of 12 agents)

Description
The owner-triggered compound() path enforces a minLiquidity slippage floor (_doCompound, line 553: if (addedL < minLiquidity) revert InsufficientLiquidity()), and the code's own comment (lines 246-249) states this restriction exists specifically so "a non-owner [cannot force] a fee re-add at a price/time of their choosing." The permissionless in-swap path — any swap triggers _afterSwap → this.compoundInSwap() → _compoundLogic() once accrued fees cross an owner-set threshold — calls _compoundLogic() directly with no slippage floor and no deadline. _compoundLogic() reads the post-swap spot price via _slot0() (line 361) and re-adds the hook's collected fees as MAIN liquidity at that price. A swapper can skew price toward a MAIN range boundary within their own swap so that LiquidityAmounts.getLiquidityForAmounts collapses to a single-sided (or near-zero) add, stranding the other side as idle ERC-6909 claims and degrading the position the owner would otherwise have grown.

Proof of Concept

  1. Owner has autoCompound = true and a nonzero compoundThreshold0/compoundThreshold1; MAIN has accrued fees ≥ threshold.
  2. Attacker (any address, no privilege) submits a swap that pushes sqrtP toward mainTickLower or mainTickUpper.
  3. _afterSwap fires; compoundInSwap() sees owed ≥ threshold; _compoundLogic() collects fees, computes addedL = getLiquidityForAmounts(sqrtP_skewed, ...), and re-adds at that skewed ratio with zero floor.
  4. Outcome: the hook's already-earned fees are converted to liquidity at an off-market ratio; the unused side sits as owner-rescuable-but-idle ERC-6909 claims until a future compound or manual rescue().

Every agent that attempted to trace attacker profit from this path (economic-security, first-principles, invariant, boundary, asymmetry) independently concluded that under the pool's current 1% fee tier (EXP_FEE = 10000), the round-trip cost of manipulating price materially exceeds the extractable value from the bounded, threshold-gated fee amount — so this is not a clean third-party-theft primitive today. However, per this audit's severity rubric ("Medium: degraded behavior... or owner-only fund loss"), the finding stands as Medium: it is a real, unprivileged, repeatable degradation of the owner's capital efficiency with no guard at all (versus a real guard on the sibling owner path), and severity would scale directly with the pool's fee tier or threshold configuration.

Fix

 function _compoundLogic() internal returns (uint128 addedL, uint256 used0, uint256 used1) {
     int24 lower = mainTickLower;
     int24 upper = mainTickUpper;

     (BalanceDelta cd,) =
         poolManager.modifyLiquidity(poolKey(), ModifyLiquidityParams(lower, upper, 0, MAIN_SALT), "");
     uint256 fee0 = cd.amount0() > 0 ? uint256(uint128(cd.amount0())) : 0;
     uint256 fee1 = cd.amount1() > 0 ? uint256(uint128(cd.amount1())) : 0;
     if (fee0 > 0) EXP_C0.take(poolManager, address(this), fee0, true);
     if (fee1 > 0) EXP_C1.take(poolManager, address(this), fee1, true);

     (uint160 sqrtP,) = _slot0();
     addedL = LiquidityAmounts.getLiquidityForAmounts(
         sqrtP, TickMath.getSqrtPriceAtTick(lower), TickMath.getSqrtPriceAtTick(upper), fee0, fee1
     );
+    // reject compounding at a manipulated spot price / degenerate ratio
+    if (addedL < minCompoundLiquidityBps_of(fee0, fee1)) return (0, 0, 0);
     if (addedL == 0) return (0, 0, 0);
     ...

Practical options: (a) require the post-swap tick to sit strictly inside [mainTickLower, mainTickUpper] before compounding (skip otherwise — fees simply remain as claims for the next attempt), or (b) compare _slot0() against a short TWAP / last-good sqrtP checkpoint and skip the re-add if deviation exceeds an owner-set bound. Either check must sit inside the try-wrapped call so a skip never reverts the swap.

[65] 2. reanchor/seedMain/compound deploy liquidity at live spot price with no TWAP or calm-period check — sandwichable despite minLiquidity

OwnerManagedRangeHook.reanchor() / seedMain() / compound() via _doReanchor() / _doSeed() / _compoundLogic() · Confidence: 65 · [phase1 only: evm-audit-defi-amm] — re-examined and confirmed by the orchestrator against source.

Description
Every owner rebalance op reads the current pool price (_slot0()) at execution time and deploys liquidity at that price, bounded only by a minLiquidity floor — a bound on resulting L, not on price fairness. An attacker who observes an owner's reanchor/seedMain/compound transaction in the mempool can front-run it with a large swap to move price, let the owner's tx deploy liquidity into a range straddling the manipulated price (a manipulated price can still yield L2 ≥ minLiquidity), then back-run to restore price and extract value from the freshly-placed, mis-priced liquidity. Because the hook is the pool's sole LP, any such loss falls entirely on the hook/owner. This clears the audit's admin-action gate because the harm requires an unprivileged front-runner/sandwicher acting against the owner's normal-course transaction (the "race" amplifier pattern), not the owner acting maliciously.

Proof of Concept

  1. Owner submits reanchor(newLower, newUpper, minLiquidity, deadline).
  2. Attacker front-runs with a large SLEUTH buy, moving sqrtP up.
  3. _doReanchor removes MAIN (composition skewed by the manipulated price) and re-adds L2 computed at the manipulated sqrtP into [newLower, newUpper]; L2 ≥ minLiquidity still passes.
  4. Attacker back-runs, trading back through the freshly-placed liquidity at the favorable manipulated price, capturing the spread. The atomic remove+add in one unlock() removes the classic two-tx MEV window but does not remove single-tx sandwich risk around the owner's tx itself.

Recommendation
Add a calm-period / deviation check before deploying liquidity in _doReanchor, _doSeed, and _compoundLogic (owner path): compare _slot0() spot to a short TWAP (or a recent-tick checkpoint) and revert if divergence exceeds an owner-configured bound, e.g.:

function _requireCalm() internal view {
    (uint160 spot,) = _slot0();
    uint160 twap = _twapSqrtPrice(twapInterval);
    uint256 devBps = spot > twap
        ? uint256(spot - twap) * 10_000 / twap
        : uint256(twap - spot) * 10_000 / twap;
    if (devBps > maxDeviationBps) revert PriceOutOfRange();
}

Enforce sane bounds on maxDeviationBps/twapInterval themselves so they cannot be configured to be a no-op.

[60] 3. Fee-on-transfer SLEUTH permanently DoSes seedMain; rebasing SLEUTH silently leaks value

OwnerManagedRangeHook.seedMain() / _doSeed() (via CurrencySettler.settle) · Confidence: 60 · [phase1 only: evm-audit-erc20] — re-examined and confirmed by the orchestrator against CurrencySettler.sol in the dependency tree.

Description
SLEUTH (currency0) is an arbitrary, owner-chosen ERC20 at deploy time — nothing in the hook validates its transfer behavior. When seeding MAIN, _doSeed settles the owed SLEUTH principal via EXP_C0.settle(poolManager, payer, amount, false), which performs safeTransferFrom(payer, poolManager, amount) then poolManager.settle(). Uniswap v4's settle() credits the delta by the PoolManager's measured balance increase, not the amount argument. If SLEUTH is fee-on-transfer, the PoolManager receives less than amount, the currency0 debt is only partially cleared, and the transaction reverts with CurrencyNotSettled at unlock finalization — this is a hard, permanent revert (fail-safe, not silent corruption) that makes seedMain entirely unusable for such a token. Separately, if SLEUTH is a rebasing token, neither the PoolManager's L-based position accounting nor the mainLiquidity/bidLiquidity mirrors resync to balanceOf — a positive rebase becomes externally arbitrageable, a negative rebase silently under-collateralizes the hook's banked ERC-6909 claims, and the hook has no mechanism to reconcile either (rescue() only reaches stray balances/claims, not deployed positions).

Proof of Concept
Deploy with a fee-on-transfer SLEUTH as c0. Owner calls seedMain(a0, a1, lower, upper, minL, deadline) with lower < currentTick < upper. modifyLiquidity produces d.amount0() < 0; EXP_C0.settle(..., amount, false) pulls amount from the owner but the PoolManager only nets amount - fee; unlock finalization reverts CurrencyNotSettled. MAIN can never be seeded with this token. (reanchor/compound settle from ERC-6909 claims with burn = true, which skips the ERC20 transfer, so only owner-funded settles on currency0 are exposed.)

Recommendation
Document that SLEUTH MUST NOT be fee-on-transfer or rebasing, and validate at/before deployment — there is no in-contract fix that preserves exact 1:1 liquidity math for such tokens:

// off-chain / pre-deploy check, or a one-time guarded probe in the constructor
require(_isStandardErc20(Currency.unwrap(c0)), "unsupported token behavior");

OwnerManagedRangeHook.rescue() · [phase1 only: evm-audit-access-control] (AC-1). 9. _compoundLogic can revert on a 1-wei rounding shortfall when the hook holds zero spare working capital

OwnerManagedRangeHook._compoundLogic() · [phase2 only] — boundary-agent and invariant-agent independently (2 of 12). addedL is computed via down-rounded getLiquidityForAmounts, but the pool's actual add-cost can round up by up to 1 wei per side; if the hook holds no pre-existing claim balance on that side, settle(...,true) (claim burn) could underflow-revert. Self-limiting: caught by try/catch in the in-swap path (emits CompoundFailed, swap unaffected) and retryable in the owner path as fees continue to accrue. No fix required; documented for completeness.

10. Auto-compound externalizes its gas cost onto whichever swapper happens to cross the fee threshold

OwnerManagedRangeHook._afterSwap() · [both] — phase1: evm-audit-dos (DOS-1) · phase2: invariant-agent LEAD. An owner-set low compoundThreshold0/1 makes the compound fire on effectively every swap, taxing an arbitrary unrelated swapper with the gas of two modifyLiquidity calls plus settle/take. Recommend enforcing a sane minimum in setCompoundThresholds so the owner cannot configure it to fire every swap.

11. One-sided fee accrual can leave collected fees as claims outside the mainLiquidity/bidLiquidity mirror, recoverable only via rescue

OwnerManagedRangeHook._compoundLogic() · [phase2 only: numerical-gap-agent]. When addedL == 0 (e.g. price parked at one edge of MAIN so one leg's implied liquidity is zero), the just-collected fees are banked as ERC-6909 claims but tracked by no state variable and not swept by reanchor (which re-adds only the removed principal, per its own inline comment). Funds are not lost — recoverable by the owner via rescue() — but the "auto-compound converts fees back into position" invariant silently no-ops. Consider tracking un-recompounded claim balances explicitly, or documenting that rescue() is the intended recovery path for this case.

12. compoundInSwap's per-token OR threshold can fire the compound path for a no-op re-add

OwnerManagedRangeHook.compoundInSwap() · [phase2 only: numerical-gap-agent]. The threshold check (owed0 >= compoundThreshold0 || owed1 >= compoundThreshold1) evaluates two independently-scaled tokens (SLEUTH 18-dec, USDC 6-dec) with OR logic; a swap that crosses only the SLEUTH-side threshold can still yield addedL == 0 if the binding leg is USDC, resulting in a collect-and-rebank with no actual liquidity added. Cosmetic/gas-inefficiency only — no funds at risk. No action required beyond awareness.

13. _doReanchor's re-add settlement has no positive-delta branch (currently unreachable, fragile if invariants change)

OwnerManagedRangeHook._doReanchor() · [phase2 only: asymmetry-agent]. Unlike _doSeed (which handles both delta signs on both currencies), the reanchor re-add only settles the negative-delta case. This holds today because MAIN has exactly one position that was just fully removed before the re-add, so a positive delta cannot currently occur — but the omission would cause a DoS (CurrencyNotSettled) rather than fund loss if a future change ever produced one. Recommend adding the symmetric take branch defensively:

     if (ad.amount0() < 0) EXP_C0.settle(poolManager, address(this), uint256(uint128(-ad.amount0())), true);
+    else if (ad.amount0() > 0) EXP_C0.take(poolManager, address(this), uint256(uint128(ad.amount0())), true);
     if (ad.amount1() < 0) EXP_C1.settle(poolManager, address(this), uint256(uint128(-ad.amount1())), true);
+    else if (ad.amount1() > 0) EXP_C1.take(poolManager, address(this), uint256(uint128(ad.amount1())), true);

14. USDC blacklist of the hook itself can strand raw (non-claim) USDC sent directly to the contract

OwnerManagedRangeHook.rescue() · [phase1 only: evm-audit-erc20] (ERC20-4). Pool funds are never lockable this way — deployed liquidity and withdrawals move exclusively through the PoolManager (take), which is blacklist-agnostic with respect to the hook. Only stray raw USDC accidentally sent directly to the hook address would be stranded if the hook itself is blacklisted, since rescue's claims=false branch requires the hook to be a valid safeTransfer sender. Low-likelihood, low-impact; no action required beyond awareness.

15. Pause does not protect against a compromised/malicious owner key; mainLiquidity/bidLiquidity mirror invariants hold under adversarial re-analysis

[both, informational] — phase1: evm-audit-access-control (AC-2), evm-audit-dos (DOS-4) · phase2: independently re-verified safe by at least 6 of 12 agents (access-control, invariant, asymmetry, boundary, numerical-gap, flow-gap), one of which (access-control) still logged it as a LEAD for completeness. unpause()/withdrawMain/withdrawBid/rescue are all onlyOwner, so pause provides no mitigation against a compromised owner key by design (it is an operational kill-switch, not a compromise safeguard) — accepted single-owner trust model, not a bug.
