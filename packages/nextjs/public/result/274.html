Protocol Architecture

A zero-coupon bond lending protocol on Base:

Lifecycle:

  1. Borrower calls createVault(collateral, collateralAmt, loanAmt, repayAmt, fundingDeadline, repayDeadline, name, sym) + 1e14 wei CREATION_FEE
  2. Factory deploys Vault via CREATE (deterministic address from factory nonce)
  3. Factory does fee-on-transfer check: balanceOf(vault) before/after transferFrom(borrower, vault, collateralAmt)
  4. Factory calls vault.initializePosition() → vault reads balanceOf(vault), mints initialCollateralAmount P tokens and N tokens to borrower
  5. Borrower sells P tokens on Marketplace for USDC (lenders buy at discount)
  6. Borrower calls closeFunding(loanAmt) to take USDC; closeFunding(0) = cancel and return collateral
  7. Borrower calls repayInFull() before repaymentDeadline
  8. On success: P holders call redeemP(pTokens) → receive pTokens × repayAmt / P.totalSupply() USDC
  9. On default: permissionless settle() → P holders claim collateral proportionally

Token math:

  • P supply = N supply = initialCollateralAmount (in collateral token wei, e.g., 18-decimal WETH units)
  • P tokens: transfersEnabled = true (tradeable)
  • N tokens: transfersEnabled = false (borrower only, non-tradeable)

[H-1] P/N Token Supply Inflation via CREATE Address Pre-funding

Severity: High
Category: Vault Inflation Attack (analogous to ERC4626 share inflation)
Location: vault.initializePosition() — balance-based accounting
Confirmed by both ethskills and pashov passes | Both flag as highest severity

Description:
The VaultFactory deploys vault contracts using the CREATE opcode, making each vault's address deterministic from keccak256(rlp([factory, nonce])). Anyone who knows the factory's current nonce can predict the next vault's address before it is deployed.

The initializePosition() function sets initialCollateralAmount = token.balanceOf(vault) at initialization time — reading the TOTAL balance of the vault, not just the amount transferred by the factory's transferFrom. The factory correctly validates the fee-on-transfer receipt (using before/after delta), but initializePosition() independently re-reads the balance and stores it, including any tokens present before the vault was even created.

Call trace (vault 2 creation):

CALL factory → vault: initializePosition()
  STATICCALL vault → WETH: balanceOf(vault)   ← reads TOTAL balance (not delta!)
  CALL vault → PToken: mint(borrower, totalBalance)   ← inflated
  CALL vault → NToken: mint(borrower, totalBalance)   ← inflated

On-chain proof:

  • Vault 2 creation specified collateralAmount = 3,000,000,000,000,000 WETH wei (3e15)
  • vault.initialCollateralAmount() = 3,001,500,000,000,000 (+1,500,000,000,000 extra = 1.5e12 wei)
  • P2.totalSupply() = 3,001,500,000,000,000 (inflated; should be 3e15)
  • The 1.5e12 WETH pre-donation occurred before vault creation (confirmed by balance trace)

Exploit scenario:

  1. Attacker observes factory nonce n → computes victim_vault = keccak256(rlp([factory, n]))
  2. Attacker sends D collateral tokens to victim_vault (no code yet — this is valid on EVM)
  3. Victim borrower calls createVault() → factory does transferFrom(borrower, vault, S) (S = specified amount)
  4. Factory's FoT check passes: balanceOf(vault_after) - balanceOf(vault_before) = D + S - D = S ✓
  5. initializePosition() reads balanceOf(vault) = D + S → mints D + S P tokens and N tokens
  6. Borrower (colluding with attacker) holds D extra P tokens to sell on marketplace
  7. Honest P holders now hold diluted claims: receive repayAmt × pHeld / (S + D) instead of repayAmt × pHeld / S

Economic impact:

  • Attacker donates D tokens (small cost), receives D extra P tokens
  • P token holders collectively lose: repayAmt × D / (S + D) USDC
  • For vault 2 (D=1.5e12, S=3e15, repayAmt=4,857,220): loss ≈ 0.0024 USDC (negligible at current scale)
  • For a vault with S=1e22 (10,000 ETH) and D=1e20 (1% inflation): loss = ~1% of repayAmt

Recommendation:
Pass the factory-verified received amount to initializePosition rather than re-reading balance:

// In VaultFactory.createVault():
uint256 balBefore = collateral.balanceOf(address(vault));
collateral.transferFrom(msg.sender, address(vault), collateralAmount);
uint256 received = collateral.balanceOf(address(vault)) - balBefore;
if (received != collateralAmount) revert FeeOnTransferUnsupported();
vault.initializePosition(received);   // ← pass verified amount

// In Vault.initializePosition(uint256 receivedAmount):
// Store receivedAmount, NOT balanceOf(address(this))
initialCollateralAmount = receivedAmount;
PToken(p).mint(msg.sender, receivedAmount);
NToken(n).mint(msg.sender, receivedAmount);

[M-1] 12-Decimal Mismatch Creates Systematic Dust Loss in Redemption

Severity: Medium
Category: Precision math — decimal scale mismatch
Location: vault.redeemP() — per-token USDC calculation
Confirmed by both ethskills (M-2) and pashov (math-precision) passes

Description:
P token supply is set equal to initialCollateralAmount in collateral token wei units (18 decimal scale for WETH). repaymentAmount is denominated in USDC (6 decimal scale). The 12-decimal gap creates severe per-unit precision loss.

Arithmetic:

P.totalSupply  = 3,001,500,000,000,000   (3.0015e15 — WETH scale, 18 dec)
repaymentAmount = 4,857,220               (USDC scale, 6 dec)

Per-unit P token USDC value:
  floor(1 × 4,857,220 / 3,001,500,000,000,000) = 0   ← truncated to ZERO

Minimum P tokens to receive 1 USDC wei:
  ceil(P.totalSupply / repaymentAmount) ≈ 617,985 P units

Scenario — 100 lenders hold equal shares:
  each holds = 3.0015e15 / 100 = 3.0015e13 P units
  each redeems = floor(3.0015e13 × 4,857,220 / 3.0015e15) = 48,572 USDC wei
  total paid   = 48,572 × 100 = 4,857,200 USDC wei
  dust locked  = 4,857,220 - 4,857,200 = 20 USDC wei (permanent)

Severity increases for large-collateral vaults: with S=1e22 (10,000 ETH), the minimum meaningful holding grows to ~2e15 P units, and dust accumulation per settlement round scales with lender count.

Recommendation:
Store a normalized precision factor and use it for per-token rate computation:

uint256 constant RATE_PRECISION = 1e18;
// At closeFunding or settle time:
uint256 redemptionRatePerToken = repaymentAmount * RATE_PRECISION / P.totalSupply();
// At redeemP:
uint256 usdcOut = pTokenAmount * redemptionRatePerToken / RATE_PRECISION;

Alternatively, mint P tokens normalized to USDC decimal scale (collateralAmount / 1e12) to align the two denominations.

[M-2] N Token Permanently Non-Transferable — Borrower Locked In

Severity: Medium
Category: ERC20 token design, access control
Location: NToken.transfersEnabled = false
Confirmed by both passes

Description:
N tokens representing the borrower's residual collateral claim have transfersEnabled = false with no observable on-chain mechanism to enable transfers. Selector 0xc1566cb1 (likely setTransfersEnabled) reverts. The borrower cannot:

  • Sell N tokens to hedge collateral exposure
  • Transfer N tokens to another wallet
  • Use N tokens as collateral in other protocols

Only three exits exist for borrowers:

  1. repayInFull() before deadline → retrieve collateral
  2. redeemPair(pTokens) → burn both P+N tokens for collateral (requires re-acquiring P tokens from market)
  3. Default → lose collateral to P holders

Recommendation:
If intentional, document this clearly in user-facing documentation and ensure redeemPair() is accessible and well-audited as the primary borrower exit. If unintentional, implement setTransfersEnabled(bool) callable on N token after fundingClosed = true, allowing borrowers to freely trade their collateral position.

[L-1] No Timelock on Admin Pause and Collateral Whitelist Functions

Severity: Low
Category: Access control — centralization risk
Location: factory.setCollateralAllowed(), factory.setPurchasesPaused(), factory.setCreationPaused(), factory.withdrawCreationFees()

Description:
Factory admin functions execute immediately with no delay:

  • setCollateralAllowed(address, bool) — can de-whitelist collateral instantly
  • setPurchasesPaused(bool) / setCreationPaused(bool) — pause with no notice
  • withdrawCreationFees() — drain accumulated ETH immediately

Positive finding: 2-step ownership (pendingOwner() / acceptOwnership() from OZ Ownable2Step) is confirmed from on-chain selectors — mitigates unauthorized transfer.

Front-running risk: Owner (or attacker with owner key) can observe a pending createVault(collateralX, ...) tx in the mempool and front-run with setCollateralAllowed(collateralX, false), causing the borrower's creation to revert after they've already approved the collateral transfer.

Recommendation: Apply a minimum 24-hour timelock to collateral de-whitelisting and pause operations (OZ TimelockController). Emit CollateralDelistScheduled(address, uint256 effectiveAt) events to give users time to react. For fee withdrawal, add a rate limit or delay.

[L-2] Vault Creation Atomically Coupled to Marketplace Notification

Severity: Low
Category: External call dependency — single point of failure
Location: factory.createVault() → marketplace.notifyVaultCreated() (selector 0x9e0406c6)

Description:
At the end of vault creation, the factory makes an external call to the marketplace which performs 7+ internal callbacks into the vault and factory:

CALL factory → marketplace: 0x9e0406c6
  STATICCALL marketplace → factory: isVault()
  STATICCALL marketplace → vault: borrower()
  STATICCALL marketplace → vault: initialCollateralAmount()
  STATICCALL marketplace → vault: [repaymentAmount]
  STATICCALL marketplace → vault: fundingDeadline()
  STATICCALL marketplace → vault: P()
  STATICCALL marketplace → PToken: balanceOf()

If the marketplace reverts for any reason (bug, pause, upgrade, gas exhaustion), the entire vault creation is rolled back — despite the vault being fully deployed and collateral transferred. This gives the marketplace complete veto power over vault creation.

Recommendation:

try marketplace.notifyVaultCreated(vaultAddr, ...) {
} catch {
    emit MarketplaceNotificationFailed(vaultAddr);
}

Vaults should remain valid even without marketplace registration, with a separate function to register existing vaults.

[L-3] Repayment Deadline Gap Validation Unconfirmed (Source-Pending)

Severity: Low (conditional)
Category: Parameter validation
Location: factory.createVault() — deadline validation logic

Description: The factory validates fundingDeadline within [now + MIN_FUNDING_PERIOD, now + MAX_FUNDING_PERIOD]. It is unclear from bytecode analysis whether a minimum gap between fundingDeadline and repaymentDeadline is enforced. If not, a borrower could set repaymentDeadline = fundingDeadline + 1 second, giving lenders zero effective trading window after funding closes.

Recommendation: Require repaymentDeadline >= fundingDeadline + MIN_REPAYMENT_GAP (e.g., at least 1 day). Verify this check exists in source.

[I-1] CREATION_FEE Excess Handling Ambiguous

Severity: Info
Category: ETH value handling
Location: factory.createVault() — msg.value check

Description: Bytecode shows CALLVALUE - CREATION_FEE → JUMPI suggesting branching when msg.value ≠ 1e14 wei. Both observed transactions sent exactly 1e14 wei, suggesting exact-only enforcement, but the behavior for msg.value > CREATION_FEE is unconfirmed without source.

Recommendation: Verify with source. If excess ETH is retained, add explicit require: require(msg.value == CREATION_FEE, "Wrong fee").
