Executive Summary

The contract at 0xcC3E1C18b58eE8Ec6550C60b75d820E4b45e2D2F is a curated P2P token marketplace on Base. Sellers list custom ERC20-compatible "tokenA" contracts for sale; buyers pay USDC. All sale parameters (price, amount, deadline) are defined by the tokenA contract itself at listing time. The marketplace acts as a coordinator, enforcing access controls via an external registry contract.

The audit was conducted entirely through bytecode disassembly, on-chain state queries, and event log analysis — no verified source code was available on Sourcify or Etherscan.

The most critical finding is a permanent fund-lock vulnerability: all close paths (cancel, expire, and final-fill) depend on a mandatory external callback (onSaleClosed) to the tokenA contract. If this callback reverts for any reason — including bugs in tokenA, intentional freezing by the tokenA developer, or self-destructed tokenA contracts — the seller cannot recover their tokens. This is a systemic architectural risk.

Overall risk rating: HIGH — the fund-lock vulnerability must be addressed before production use at scale.

Detailed Findings

HIGH-1

Permanent fund lock if onSaleClosed callback reverts

Contract: 0xcC3E1C18b58eE8Ec6550C60b75d820E4b45e2D2F
Location: Close helper at bytecode offset 0x12d5; external CALL at 0x132b; revert-if-failed at 0x132c–0x132e

Description:

The close helper at 0x12d5 is the single code path called by all three close operations:

  • cancel() — seller cancels active sale
  • closeExpired() — anyone closes an expired sale
  • buy() — final-fill completion of fully-purchased sale

In each case, the close helper makes an external CALL to tokenA.onSaleClosed(...) (selector 0x1568e7e9). After the call, it checks RETURNDATASIZE / ISZERO and reverts with error 0x3cfa1313 if the call failed or returned empty data.

If the tokenA onSaleClosed function reverts (for any reason — bug, intentional freeze, tokenA self-destructed), the entire transaction reverts. The marketplace offers no alternative close path.

Consequences:

  • Seller cannot call cancel(). Their deposited tokenA tokens remain locked in the marketplace contract.
  • closeExpired() also reverts. The sale cannot be expired externally.
  • The last buyer attempting to fully exhaust the lot cannot complete their purchase. Partial fills succeed; the final fill always fails.
  • No on-chain recovery mechanism exists.

Attack scenario (malicious tokenA developer):

  1. Deploy tokenA with a time-delayed onSaleClosed revert (e.g., reverts after block X).
  2. Get tokenA approved by the registry.
  3. Create a sale. The marketplace locks seller tokens.
  4. After block X, trigger the revert condition in tokenA.
  5. All close attempts for this sale now permanently fail. Seller tokens locked.

Severity: HIGH
Likelihood: Medium (requires registry to approve a buggy or malicious tokenA)
Impact: Critical (permanent, irrecoverable loss of seller funds)

Fix:

Use a try/catch or low-level call pattern for the callback. Do not revert the close operation if the callback fails. Instead, emit an event so the tokenA team can investigate:

// In close helper:
bool callbackSuccess;
(callbackSuccess,) = address(tokenA).call(
    abi.encodeWithSelector(0x1568e7e9, saleId)
);
emit SaleClosed(saleId, tokenA, callbackSuccess);
// Do NOT revert if callbackSuccess == false

Alternatively, add a protocol admin emergency-close that skips the callback.

MEDIUM-1

Registry centralization — admin can halt marketplace

Location: sell() at offset 0x0276; registry call to 0x652b9b41(address) on 0xb2458426...

Description:

All new sale listings are gated through the registry contract at 0xb2458426.... The registry admin can:

  • Remove any tokenA from the approved set, blocking new listings for that token.
  • Pause or brick the registry entirely, blocking all new sales.

Existing sales are unaffected (registry is not re-checked during buy() or cancel()), but the marketplace's ability to accept new listings depends entirely on the registry admin key remaining honest and uncompromised.

Severity: Medium
Fix: Document registry admin key management. Use a timelock (≥48h) for de-listing decisions. Consider a DAO or multisig governance structure.

MEDIUM-2

closeExpired() permissionless — anyone can trigger close of expired sales

Location: closeExpired() at offset 0x0378

Description:

closeExpired() verifies only that block.timestamp >= sale.deadline and !sale.isClosed. No msg.sender check is present. Any EOA or contract can close any expired sale.

Consequences:

  • Sellers lose control of when closure happens. A seller who expires a sale intentionally and wants to quickly re-list cannot prevent bot-triggered closure at an adversarial time.
  • The onSaleClosed callback fires from the marketplace, triggered by an arbitrary external actor. tokenA callbacks that behave differently based on closure timing (e.g., redistributing accrued value at closure) can be exploited.

Severity: Medium
Fix: Restrict closeExpired() to the seller, or add a documented keeper incentive system with explicit permissionless intent.

MEDIUM-3

Registry address immutable with no migration path

Location: factory() / registry() view at offset 0x017c; returns immutable 0xb2458426...

Description:

The registry address is stored as a bytecode immutable. No setter function appears in the dispatcher. If the registry is compromised, exploited, or needs upgrading, the marketplace has no mechanism to switch to a new registry. The entire marketplace must be redeployed, stranding all active sales on the old contract.

This is a double-edged property: the admin cannot maliciously change the registry, but there is also no legitimate upgrade path.

Severity: Medium
Fix: Add a setRegistry(address) function with a 2-step confirmation and timelock, or document that the immutability is intentional and explain how registry upgrades are handled operationally.

MEDIUM-4

closeExpired() timing enables economic manipulation via callback

Location: closeExpired() at 0x0378; onSaleClosed callback CALL at 0x132b

Description:

A combination of MEDIUM-2 (permissionless closeExpired) and the fact that the onSaleClosed callback can perform arbitrary economic logic creates a timing manipulation surface.

If a tokenA's onSaleClosed callback performs price-sensitive actions (e.g., redistribute USDC proceeds to tokenA holders, trigger a liquidity event, update an on-chain price oracle), an MEV bot can:

  1. Monitor for sale expiration.
  2. Call closeExpired() in a block where the callback's economic outcome is most profitable (e.g., when token price is high, when target pool is in a specific state).

The marketplace cannot prevent tokenA callbacks from performing complex logic. The registry is the only defence, but cannot detect timing-sensitive callback behavior at registration time.

Severity: Medium (conditional on tokenA callback design)
Fix: Document standards for onSaleClosed callback implementations. Restrict closeExpired() to seller or a permissioned keeper. Discourage time-sensitive or price-oracle-interacting logic in callbacks.

MEDIUM-5

Seller asymmetrically depends on tokenA callback for fund recovery

Description:

From a first-principles perspective, a seller who deposits tokenA tokens into the marketplace should have unilateral ability to retrieve them via cancel(). However, the cancel() path mandates the onSaleClosed callback, creating an asymmetric dependency: the seller's access to their own funds requires a third party's cooperation (the tokenA contract).

This violates the principle of least surprise. Sellers may not realize that a tokenA contract bug (outside their control) can permanently trap their deposit.

Severity: Medium (architectural design risk)
Fix: Two-phase close: unconditionally update sale state and release tokens to seller in phase 1; fire the callback in phase 2 (non-reverts, emit event on failure). The seller's access to their tokens should not depend on the callback's success.

LOW-1

Protocol fee rounds to zero for dust purchases

Location: Fee calculation in buy() at approximately offset 0x0d25–0x0d35

Description:

Fee = amountUSDC * 10 / 10000 (integer division). For amountUSDC < 1000 (< $0.001 in USDC 6-decimal representation), fee = 0. Buyers can split large purchases into sub-$0.001 transactions to pay zero fees.

Severity: Low
Fix: Use ceiling division: fee = (amountUSDC * 10 + 9999) / 10000. Or enforce minPurchaseAmount >= 10000 USDC units.

LOW-2

tokenA controls all sale parameters; malicious or buggy tokenA exploits possible

Location: sell() at offset 0x0276; staticcalls to 0x7df1f1b9, 0xc276f44d, 0xc9aabdaf, 0x796b23bb on tokenA

Description:

The marketplace reads all sale parameters (price, amount, deadline, min-fill) from the tokenA contract at listing time. A tokenA that passes registry validation but returns:

  • deadline = 0 → sale immediately expired, closeable by anyone
  • pricePerUnit = 0 → tokens sold for free (see also LOW-4)
  • minAmountPerBuy = amountA → only a single all-or-nothing purchase possible

could trap the seller's tokens or allow exploitation. Registry is the only guard, but cannot detect adversarially-chosen parameter values at registration time.

Severity: Low
Fix: Add on-chain validation in sell(): require(pricePerUnit > 0), require(deadline > block.timestamp), require(amountA > 0), require(minAmountPerBuy <= amountA).

LOW-3

No visible fee withdrawal function; USDC fees may be unrecoverable

Location: USDC balance management in buy()

Description:

In buy(), the buyer pays amountUSDC + fee. The seller receives amountUSDC. The contract retains fee as USDC. No function with a recognizable fee-withdrawal selector appears in the contract's dispatcher. If no withdrawal mechanism exists, protocol fees accumulate in the contract permanently with no way to extract them.

Severity: Low (protocol revenue loss, not user fund loss)
Fix: Verify a fee withdrawal function exists. If not, add withdrawFees(address recipient) with appropriate access control.

LOW-4

Zero pricePerUnit allows free token extraction

Location: sell() parameter reading from tokenA getters; buy() USDC calculation

Description:

If a tokenA approved by the registry returns pricePerUnit = 0 from its getter, any buyer can purchase the entire sale lot for 0 USDC. The seller receives nothing. No on-chain check prevents pricePerUnit = 0 in sell().

Severity: Low (requires registry to approve malicious tokenA)
Fix: require(pricePerUnit > 0) in sell().

LEAD-1

Fee-on-transfer tokenA creates accounting mismatch

Description:

During sell(), the marketplace calls transferFrom(seller, marketplace, amountA) and records amountA in the struct. If tokenA has a transfer fee, the marketplace receives amountA * (1 - fee) but records amountA. Subsequent buyers could face a shortfall on the last fill.

This is unverified without source code. The 0x2116da5b call in buy() performs before/after balance checks for the buyer's receipt of tokenA. It's unclear whether a similar check exists in sell().

Recommendation: Perform a before/after balance check in sell() and store the actually-received amount, not the getter-stated amount, in amountA.

Global mutex at storage slot 0. Set to 2 (locked) on entry to all state-modifying functions; reset to 1 (unlocked) on exit. Pattern correctly implemented. No reentrancy vulnerability found.

INFO-3

_safeTransfer at offset 0x1683 handles ERC20 tokens that return no value from transfer(). Correctly handles non-standard tokens. No issue.

INFO-4

CEI pattern correctly followed in buy()

State updates (amountARemaining, isClosed) precede all external calls. Combined with the reentrancy guard, defence-in-depth against reentrancy is present. No reentrancy vulnerability found.

Architecture Notes

Registry-gated curation model: Only tokenA contracts approved by 0xb2458426... can be listed. This is the primary safety mechanism for the entire marketplace. Its integrity is critical.

Callback-dependent architecture: The mandatory onSaleClosed callback is the most significant architectural risk. The pattern of requiring external contract cooperation for internal state transitions is unusual and fragile.

Hardcoded USDC payment token: The payment token is immutable. No mechanism for additional payment tokens or token swaps exists. This limits flexibility but reduces attack surface.

No upgradeability: No proxy pattern observed. The contract is not upgradeable. Bug fixes require redeployment.

Conclusion

The marketplace demonstrates solid foundational security: the reentrancy guard is correctly implemented, CEI pattern is followed, Safe ERC20 is used, and arithmetic is checked throughout. The access control on cancel() correctly restricts to the seller.

However, the architectural decision to make all close paths depend on a mandatory external callback (onSaleClosed) creates a systemic fund-lock risk that is not mitigated at the protocol level. The registry is the only guard, and it cannot prevent post-registration tokenA behaviour changes.

The highest-priority recommendation — making the callback non-reverting — would eliminate the HIGH finding and materially reduce the MEDIUM-2, MEDIUM-4, and MEDIUM-5 risks simultaneously.
