Findings

[H-01] Unauthenticated LP-position deposit lets any attacker permanently brick RwagmiSaleLpVault's pool custody

Severity: High · Confidence: 95 · Origin: [both] — found independently by 4/7 Phase-1 domain agents (general, defi-amm, erc721, dos) and unanimously by all 12/12 Phase-2 attack agents, run blind.

Location: RwagmiSaleLpVault.onERC721Received() — flattened/RwagmiSaleLpVault.flat.sol:2286-2308 (doc comment at 2279-2285; gate at 2290; position cap at 2291; pool-pinning logic at 2295-2303)

Description

2279: /// @dev The pool key is derived from the received position itself via the
2280: ///      PositionManager (not a caller-supplied setter), so a junk NFT from
2281: ///      an unrelated pool cannot corrupt the vault: the first accepted
2282: ///      position pins the pool, and any later NFT from a different pool is
2283: ///      rejected. The stored-position count is bounded so a flood cannot
2284: ///      brick the batch fee collection.
2286: function onERC721Received(address operator, address, uint256 tokenId, bytes calldata)
2287:     external
2288:     returns (bytes4)
2289: {
2290:     if (msg.sender != address(positionManager)) revert NotFromPositionManager(operator);
2291:     if (positionIds.length >= MAX_POSITIONS) revert TooManyPositions();
2295:     (PoolKey memory key,) = positionManager.getPoolAndPositionInfo(tokenId);
2296:     bytes32 keyHash = keccak256(abi.encode(key));
2297:     if (!poolKeySet) {
2298:         poolKey = key;
2299:         poolKeySet = true;
2301:     } else if (keccak256(abi.encode(poolKey)) != keyHash) {
2302:         revert PoolMismatch(keccak256(abi.encode(poolKey)), keyHash);
2303:     }
2305:     positionIds.push(tokenId);

The only access check on deposits (line 2290) verifies that the caller is the Uniswap v4 PositionManager singleton — it does not verify who initiated the transfer (operator/from are received but never checked). Because the PositionManager faithfully relays safeTransferFrom for any position owner, any address holding any Uniswap v4 position NFT — from any pool, with any currencies — can deposit into this vault.

The vault then uses first-writer-wins pinning: whichever NFT is accepted first permanently sets poolKey/poolKeySet (lines 2297-2299). There is no owner, no admin, and no function anywhere in the contract that resets poolKeySet (verified by grep — it is written only at line 2299). Once pinned, every subsequent NFT from a different pool reverts PoolMismatch (lines 2301-2302) forever.

The doc comment directly above the function (lines 2279-2285) asserts this design is safe — "a junk NFT from an unrelated pool cannot corrupt the vault... the first accepted position pins the pool" — but that claim assumes the first NFT is always the legitimate one, which is exactly what is unenforced. This is the vulnerability, stated in the code's own reasoning.

A secondary, self-contained variant of the same root cause: once the correct pool is pinned, an attacker can flood positionIds up to MAX_POSITIONS = 20 (line 2291) with cheap same-pool dust positions, blocking any further legitimate staged deposit with TooManyPositions. (In this variant the attacker's own NFTs are eventually swept to the immutable principalRecipient on release, making it self-costing — the primary wrong-pool-pin vector above requires only one attacker-owned junk position and is not self-costing in the same way.)

Proof of Concept

  1. RwagmiSaleLpVault is deployed for a raise and set as the eventual recipient of the raise's seeded Uniswap v4 LP position. Per the protocol map, this wiring is done off-chain by deploy scripts / the LBP strategy — deployment and LP seeding are not guaranteed to be atomic, so a window exists where poolKeySet == false.
  2. Attacker mints a trivial Uniswap v4 position with minimal liquidity in any pool they control (cost: a few cents of gas plus dust liquidity).
  3. Attacker calls positionManager.safeTransferFrom(attacker, vaultAddress, junkTokenId). The PositionManager invokes vault.onERC721Received(attacker, vaultAddress, junkTokenId, "") with msg.sender == positionManager — the only gate passes. poolKeySet is false, so poolKey is permanently set to the attacker's junk pool, and junkTokenId is pushed to positionIds.
  4. The legitimate LP-seeding transaction later calls positionManager.safeTransferFrom(strategy, vaultAddress, realTokenId) for the real pool. onERC721Received computes keyHash(realPool) != keyHash(junkPool) and reverts PoolMismatch. This transaction — and every future attempt to seed the real position — reverts permanently.
  5. collectFees() and releasePrincipal() now only ever operate on the attacker's worthless junk position. The vault's entire purpose (custody of the raise's real LP, fee streaming, principal release) is permanently defeated with no on-chain recovery; the only remedy is redeploying a fresh vault instance and re-running the off-chain wiring.

Recommendation

Authenticate the depositor, not just the transport. Options (any one is sufficient):

  • Add an immutable seeder/expectedDepositor address at construction and require operator == seeder (or from == seeder) inside onERC721Received, mirroring the bind-once pattern already used elsewhere in this codebase (B20FixedSaleDeployer.bindFactory, B20PolicyValidationHook.bindAuction, B20VestingDistributor.bindSale).
  • Pin the expected PoolKey (or its hash) as an immutable constructor argument and validate every received NFT — including the first — against it, instead of trusting whichever NFT arrives first.

[M-01] releasePrincipal() does not sweep accrued LP fees before transferring positions out, letting principalRecipient capture value earmarked for feeRecipients

Severity: Medium · Confidence: 80 · Origin: [phase2: agent 11 trust-gap (FINDING)], corroborated [phase2: agent 7 first-principles (LEAD)] — promoted per multi-agent convergence, not raised in Phase 1.

Location: RwagmiSaleLpVault.releasePrincipal() — flattened/RwagmiSaleLpVault.flat.sol:2356-2372

Description

2356: function releasePrincipal() external nonReentrant {
2357:     if (unlockTime == 0) revert PermanentlyLocked();
2358:     if (block.timestamp < unlockTime) revert StillLocked();
2359:     if (positionIds.length == 0) revert NoPositions();
2364:     while (positionIds.length > 0) {
2365:         uint256 id = positionIds[positionIds.length - 1];
2366:         positionIds.pop();
2367:         IERC721Minimal(address(positionManager)).safeTransferFrom(
2368:             address(this), principalRecipient, id
2369:         );
2370:         emit PrincipalReleased(id, principalRecipient);
2371:     }
2372: }

releasePrincipal transfers every held LP-position NFT to the immutable principalRecipient without first calling collectFees() (line 2313, which is a separate, independent function). Uniswap v4 positions accrue trading fees continuously between collectFees() calls. Any fee accrual since the last collectFees() call remains embedded in the position and transfers out with the NFT — it is never realized into the vault's balance and never reaches _distribute()'s fixed bps split. Whoever now owns the position (principalRecipient) can independently collect that trailing fee amount in full via the Uniswap v4 PositionManager directly, bypassing the vault's feeRecipients split entirely. After release, collectFees() reverts NoPositions (line 2315), so the diverted amount is permanently unrecoverable by feeRecipients.

releasePrincipal is permissionless (any caller can invoke it once unlockTime has passed), and principalRecipient is a distinct immutable address from feeRecipients — so this is not self-harm: it is a real transfer of value away from the fee-split beneficiaries to a different, fixed party, reachable through completely normal operation (fees accrue by default; no attacker action beyond calling a permissionless function at the right time is required).

Proof of Concept

  1. Pool accrues trading fees continuously on the vault's held LP position(s) after the last collectFees() call.
  2. At (or after) unlockTime, any caller — most plausibly principalRecipient itself, who benefits directly — calls releasePrincipal() without a preceding collectFees().
  3. The position NFT(s), still holding the uncollected fee accrual, transfer to principalRecipient.
  4. principalRecipient can now call Uniswap v4's PositionManager directly to collect that fee accrual in full, while feeRecipients' configured bps share of it is never distributed and can never be, since the vault no longer holds any position (NoPositions on the next collectFees() attempt).

Impact is bounded by the fee accrual since the last collectFees() call (not the full custodied value), which limits it to Medium rather than High — but it is a real, unconditional accounting/trust-model gap in the fee-split's intended guarantee.

Recommendation

Call collectFees()'s sweep-and-distribute logic (or an equivalent internal helper) at the start of releasePrincipal(), before any NFT transfer, so all fees accrued through the release moment are credited to feeRecipients first.

[M-02] Sale/vesting token rebase-immunity is enforced only at construction time, not across the sale lifecycle

Severity: Medium · Confidence: 65 · Origin: [phase1: erc20], corroborated as leads [phase2: agent 3 economic-security, agent 12 flow-gap] — both phases independently concluded this is real but narrowly scoped.

Location: B20FixedSaleV1 constructor — flattened/B20FixedSaleV1.flat.sol:1534-1538; token-side accounting at flattened/B20FixedSaleV1.flat.sol:1797-1812 (claim), 1818-1848 (cleanupUnsold); B20VestingDistributor.release() — flattened/B20VestingDistributor.flat.sol:630-637

Description

1534: try IB20Minimal(cfg.token).multiplier() returns (uint256 multiplier_) {
1535:     if (multiplier_ != WAD) revert InvalidConfig("multiplier != WAD");
1536: } catch {
1537:     revert InvalidConfig("not an Asset B20");
1538: }

The constructor rejects a rebasing sale token by checking multiplier() == WAD once, at deployment. But on the B20 Asset token standard, multiplier() is a live, mutable value (its own interface docs describe it as "Asset variant rebase multiplier"). This check is a point-in-time snapshot taken before the sale holds any tokens; nothing re-checks it after fund(), and all token-side accounting (tokensSold, tokensOwedTo[], claimedTokens) is stored as fixed absolute amounts that never re-sync to balanceOf.

If the sale token rebases down between fund() and settlement, the contract's actual token balance can fall below the sum of tokensOwedTo. claim() (line ~1806/1808) transfers the fixed owed amount; once the balance is insufficient, remaining claimants' transactions revert permanently (their quote contribution has already been routed to the treasury via finalize/claimProceeds, so this is an uncompensated loss for the last claimants). B20VestingDistributor.release() inherits the identical exposure, since it holds the same token and pays out fixed schedule amounts with no balance check.

Scoping: this is not reachable on the createFixedSaleWithNewB20 path, because the factory mints the community B20 with initialAdmin = address(0) (no live rebase controller exists post-mint). It is reachable only on the createFixedSale (existing-token) path, and only if the issuer supplies an Asset B20 whose rebase controller remains active post-deployment and that controller later triggers a downward rebase — which harms that same issuer's own contributors. This self-inflicted precondition is why both phases rate it Medium rather than High.

Proof of Concept

  1. Issuer creates a sale via createFixedSale using an existing B20 Asset token whose multiplier() reads WAD at construction time but whose rebase controller (e.g. a role the issuer or a third party still holds) remains live.
  2. Sale funds and collects contributions normally; finalize() runs.
  3. The token's controller triggers a downward rebase.
  4. Early claim() callers succeed and drain the (now insufficient) balance; later callers' claim() reverts with insufficient balance, permanently — their quote-side payment was already irreversibly routed to the treasury.

Recommendation

Either (a) re-read multiplier() and require it still equals WAD at the start of fund() and at each settlement/claim path, reverting if it has drifted, or (b) apply the same balance-delta discipline already used in fund()/_contributeErc20 to the payout side — cap each claim/cleanupUnsold/release transfer to min(owed, balanceOf(this) - reserved) and account any shortfall explicitly. At minimum, document that the existing-token path must only be used with a permanently non-rebasing (or admin-renounced) Asset B20.

Leads

Vulnerability trails with concrete code smells where the full exploit path could not be completed, or where impact was confirmed to be self-harm / non-profitable. Not scored; included for completeness per the client's request to flag anything "still exploitable" beyond prior review coverage.

  • LP-vault donated/stray ETH is unattributable and permanently stranded — RwagmiSaleLpVault.receive() (flattened/RwagmiSaleLpVault.flat.sol:2406) accepts native ETH unconditionally; collectFees()'s fee accounting is a balance-delta measured strictly around modifyLiquidities (lines 2320-2334), so any pre-existing balance (including donations) is excluded from every future distribution. Confirmed independently by 9+ agents across both phases: no profitable misattribution path exists (donations before the call are excluded by construction; donations timed to land during modifyLiquidities would be split among the fixed feeRecipients, which is donor self-harm, not attacker profit). No sweep/rescue function exists. Recommendation: reject unexpected ETH in receive() when no pinned pool currency is native, or add a guarded sweep of un-attributed balance.
  • fund() is callable by any address, but cleanupUnsold's ReturnToIssuer mode always pays the immutable issuer, never the actual funder — flattened/B20FixedSaleV1.flat.sol:1579 (fund) / 1845 (cleanupUnsold ReturnToIssuer). In the intended flow the issuer funds their own sale, so this only matters if a third party (e.g. a keeper acting on the issuer's behalf) funds the sale and it later fails/cancels — their tokens return to issuer, not to them. Not attacker-triggerable against an unwilling victim; a documentation/off-path-usage footgun, not a confirmed finding.
  • B20PolicyValidationHook.validate() trusts auction-supplied owner/sender parameters — flattened/B20PolicyValidationHook.flat.sol:213-222. The hook enforces sender == owner when requireSenderIsOwner is set, but both values are supplied by the bound CCA auction, not independently derived on-chain. This is a documented, out-of-scope trust boundary (the auction is trusted once bound); real EOA/relayer enforcement lives in the auction contract, which is outside this audit's scope.
  • RwagmiSaleLpVault.onERC721Received lacks nonReentrant — flattened/RwagmiSaleLpVault.flat.sol:2286. A position returned to the vault during a principalRecipient callback (e.g. via releasePrincipal's safeTransferFrom) can re-enter and re-push to positionIds. Confirmed this is the documented, intentional design (the pop-before-transfer comment at lines 2360-2363 explicitly anticipates append-during-callback), and principalRecipient is immutable/trusted, so no third-party exploit exists — only the trusted recipient's own accounting is affected.
  • Existing-token createFixedSale path omits the predict()-vs-actual cross-check that createFixedSaleWithNewB20 performs at flattened/RwagmiRaiseFactory.flat.sol:2512 (predict) / :2517 (revert PredictionMismatch if the deployed sale address differs). Confirmed benign by both phases: the sale's CREATE2 address is relative to B20FixedSaleDeployer's own address and deploy() is strictly factory-gated, so no third party can occupy the deterministic target address; the salt is additionally namespaced by msg.sender and a monotonic raise counter. No exploitable consequence.
  • LP-vault bps fee split biases sub-unit dust to the last-listed recipient (RwagmiBpsSplit.splitShare, flattened/RwagmiSaleLpVault.flat.sol:915) — bounded to <n currency base-units per collectFees() call, sum-exact (no stranding), and gas-dominated to farm. Standard rounding-dust tradeoff per the judging rubric's safe-patterns list; not reported as a finding.
