1. Executive Summary

GitlawbStaking is a tier-weighted, MasterChef-style revenue-share staking contract for the $GITLAWB ERC20 token on Base L2. Users stake $GITLAWB and earn a pro-rata share of revenue deposited by the treasury, multiplied by a tier factor (1x / 2x / 4x / 8x) based on stake size. Unstaking requires a 7-day cooldown, which the contract documents as "to prevent reward sniping."

The contract is short, readable, and follows a well-known accounting pattern. However, the audit surfaced one High-severity bug that causes direct loss of earned rewards for every user that unstakes, a High-severity design flaw that completely defeats the stated goal of the 7-day cooldown, and several Medium- and Low-severity issues ranging from griefing vectors to weak admin hygiene.

Ship-blockers (must fix before mainnet)

  • [H-01] unstake() discards all rewards accrued during the 7-day cooldown — every unstaker silently loses up to 7 days of yield.
  • [H-02] The 7-day cooldown does not prevent reward sniping. claimRewards() is not gated by cooldown, so an attacker can front-run a depositRevenue tx, capture their share, claim immediately, then walk through the cooldown with principal. The contract's primary economic defense is a no-op.

Recommended, but not ship-blockers

  • Gate depositRevenue (or enforce a minimum per-call amount) to prevent lossy 1-wei donations that lock funds.
  • Pull state updates and transfers into a canonical CEI order + add ReentrancyGuard (defense-in-depth against future ERC777-style reward tokens).
  • Adopt OZ SafeERC20 + Ownable2Step.
  • Fix partial-unstake + tier-threshold edge case (stake dust below OBSERVER_THRESHOLD earns 0 but is held hostage to another requestUnstake/unstake round-trip).

2. Contract Overview

2.1 Architecture

One contract, no inheritance, no proxies, no external oracles.

GitlawbStaking
├── immutable IERC20 token          — the $GITLAWB token
├── address owner                   — admin (unused except for transfer)
├── mapping(address => StakeInfo)   — per-user positions
├── uint256 totalWeightedStake      — Σ(amount_i * tierMultiplier_i)
├── uint256 accRewardPerShare       — MasterChef accumulator
├── uint256 totalStaked             — Σ(amount_i) raw
└── uint256 totalRewardsDistributed — lifetime revenue deposits

StakeInfo tracks amount, rewardDebt, pendingRewards, unstakeRequestAt, unstakeAmount.

2.2 External entry points

Function Access Effect
stake(uint256) public Pull tokens, update weights, snapshot rewardDebt
requestUnstake(uint256) public Start 7-day cooldown (does NOT burn weight)
unstake() public After cooldown, reduce weight and return principal
claimRewards() public Harvest and transfer accrued rewards
depositRevenue(uint256) public (uncontrolled) Push rewards into accRewardPerShare
transferOwnership(address) onlyOwner Single-step transfer

2.3 Tier thresholds and multipliers

Tier Minimum stake Reward multiplier
None 0 0x (earns nothing)
Observer 1,000 × 1e18 1x
Curator 10,000 × 1e18 2x
Steward 100,000 × 1e18 4x
Validator 1,000,000 × 1e18 8x

2.4 Reward accounting model

Standard SushiSwap/MasterChef-style accRewardPerShare accumulator, but weighted: the "share" unit is amount * tierMultiplier rather than raw amount. For each user:

pending = (weight * accRewardPerShare) / 1e18 - rewardDebt

rewardDebt is re-snapshotted whenever the user's weight changes. On depositRevenue(amount):

accRewardPerShare += (amount * 1e18) / totalWeightedStake

2.5 Trust assumptions

  • $GITLAWB token is assumed to be a standard, non-rebasing, non-fee-on-transfer, non-ERC777, non-pausable, non-blacklisting ERC20. The audit report notes that if any of these assumptions fail, the accounting breaks (see [M-02]).
  • owner is trusted but has no critical powers in this version of the contract. Because there is no pause, no emergency withdraw, and no upgrade, the protocol is effectively immutable — both a benefit (no rug-pull surface) and a liability (no incident response).

3. Findings

3.1 High

[H-01] unstake() forfeits all rewards accrued during the 7-day cooldown

Severity: High
Category: evm-audit-defi-staking, evm-audit-precision-math, evm-audit-general
Location: unstake() at lines 132–161

Description.
During the 7-day cooldown, the user's info.amount is unchanged and therefore their weight in totalWeightedStake is unchanged. This is intentional — the design is that the cooldown period still accrues rewards. Any depositRevenue call during the cooldown increases accRewardPerShare, and the user's share of those rewards is earned.

However, unstake() never calls _harvest() before mutating state:

function unstake() external {
    StakeInfo storage info = stakes[msg.sender];
    if (info.unstakeAmount == 0) revert NoPendingUnstake();
    if (block.timestamp < info.unstakeRequestAt + COOLDOWN_PERIOD) revert CooldownNotElapsed();

    uint256 amount = info.unstakeAmount;

    // Remove old weighted stake
    uint256 oldWeight = _weightedAmount(info.amount);
    totalWeightedStake -= oldWeight;

    info.amount -= amount;
    totalStaked -= amount;

    // Add new weighted stake (may be 0)
    uint256 newWeight = _weightedAmount(info.amount);
    totalWeightedStake += newWeight;

    // Reset reward debt                                  <-- discards cooldown rewards
    info.rewardDebt = (newWeight * accRewardPerShare) / ACC_PRECISION;
    ...
}

The final line overwrites rewardDebt with the current accRewardPerShare, calculated against newWeight (the post-unstake weight). Any rewards earned between requestUnstake and unstake — i.e., between the last harvest at requestUnstake time and now — are never folded into info.pendingRewards. After unstake(), pendingRewards() will compute:

weight_new * accRewardPerShare_now / 1e18  -  rewardDebt  =  0

(because rewardDebt was just set to exactly that value), so the cooldown-era rewards are permanently lost — they stay behind in the pool, silently redistributed to other stakers as if the user had never earned them.

Proof of Concept.

  1. Alice stakes 1,000,000 $GITLAWB (Validator tier, weight = 8,000,000 × 1e18). She is the only staker.
  2. Alice calls requestUnstake(1,000,000 × 1e18). _harvest runs, pending = 0 (no revenue yet), rewardDebt = 8,000,000e18 * accRewardPerShare / 1e18.
  3. Over the next 7 days, the treasury calls depositRevenue(10,000 × 1e18). accRewardPerShare += 10,000e18 * 1e18 / 8,000,000e18 = 1250 (in ACC_PRECISION units).
  4. 7 days later, Alice calls unstake().
    • oldWeight = 8,000,000e18, removed from total.
    • info.amount -= 1,000,000e18 → info.amount = 0.
    • newWeight = _weightedAmount(0) = 0.
    • info.rewardDebt = 0 * accRewardPerShare / 1e18 = 0.
  5. Alice calls claimRewards(). _harvest sees info.amount == 0 and returns immediately. pendingRewards == 0. Revert with NoRewards.

Alice earned 10,000 $GITLAWB of rewards fairly, held her position through the cooldown as designed, and received 0.

Recommendation.
Add a _harvest(msg.sender) at the top of unstake(), identical to what requestUnstake and stake do:

function unstake() external {
    StakeInfo storage info = stakes[msg.sender];
    if (info.unstakeAmount == 0) revert NoPendingUnstake();
    if (block.timestamp < info.unstakeRequestAt + COOLDOWN_PERIOD) revert CooldownNotElapsed();

    // Harvest cooldown-period rewards before mutating weight
    _harvest(msg.sender);

    uint256 amount = info.unstakeAmount;
    ...
}

After this fix, info.pendingRewards accumulates the cooldown-era rewards, which Alice can subsequently claim. Add a unit test that stakes, requests unstake, deposits revenue during cooldown, unstakes, and asserts non-zero claimable rewards.

[H-02] 7-day cooldown does not prevent reward sniping — claimRewards() is not cooldown-gated

Severity: High
Category: evm-audit-defi-staking (sniping), evm-audit-general (design-code mismatch)
Location: claimRewards() at lines 164–177; natspec at line 17

Description.
The contract header comment states:

7-day cooldown on unstaking to prevent reward sniping.

The cooldown applies only to principal withdrawal (unstake()). It does not apply to reward claims (claimRewards()). Pending rewards can be claimed at any time, including in the same block as the stake that earned them.

This means a classic snipe works end-to-end:

  1. Attacker watches mempool for a large pending depositRevenue(X) transaction from the treasury.
  2. Attacker front-runs with stake(huge_amount) — preferably pushing into Validator tier for the 8× multiplier.
  3. depositRevenue(X) executes; accRewardPerShare increases; attacker's share is credited in the next accrual.
  4. In the same block (or any subsequent block), attacker calls claimRewards() and walks away with their share of X.
  5. Attacker calls requestUnstake(huge_amount). Starts 7-day clock.
  6. 7 days later, attacker calls unstake() and retrieves principal.

The attacker's only cost is:

  • 7 days of opportunity cost on the principal (the capital is locked but principal is never at risk).
  • Two transactions of gas on Base (negligible on L2).

The profit is a share of the revenue deposit proportional to attackerWeight / totalWeightedStake. For a Validator-tier attacker who size-matches or exceeds the existing totalWeightedStake, this captures ≥50% of every revenue deposit they front-run.

Moreover, because the attacker is still staked at Validator tier during the 7-day cooldown, they continue to earn from every subsequent depositRevenue call. The cooldown period is more profitable than the snipe block itself, not less.

Proof of Concept (conceptual).

Assume totalWeightedStake from honest stakers = 1,000,000e18 (e.g., 125,000 Validator-weight tokens).

  • Treasury broadcasts depositRevenue(100,000 × 1e18). Attacker sees this in mempool.
  • Attacker front-runs with stake(1,000,000 × 1e18) → weight = 8,000,000e18. New totalWeightedStake = 9,000,000e18.
  • depositRevenue lands next. accRewardPerShare += 100,000e18 * 1e18 / 9,000,000e18 ≈ 11,111.
  • Attacker's accrued = 8,000,000e18 * 11,111 / 1e18 = 88,888 × 1e18 → ≈88.9% of the deposit.
  • Attacker claimRewards() in same block or next → receives 88.9 × 10³ $GITLAWB.
  • Attacker requestUnstake(1,000,000e18) → 7-day clock.
  • During 7 days: every depositRevenue call still credits attacker 88.9% share. If the treasury makes multiple deposits in that window, the attacker captures all of them.
  • 7 days later: unstake() returns 1,000,000 $GITLAWB principal.

The cooldown makes the attack more attractive, not less.

Recommendation.

Pick one of:

  1. Gate reward claims by cooldown: require a user to have been staked for ≥7 days before their rewards can be claimed. Track stakeStartedAt per user, reset on every stake() call.
  2. Apply a "cooldown for rewards" model: after stake(), rewards accrue but are locked for 7 days. After 7 days, they unlock linearly (or step-unlock). This is cleaner economically but requires more state.
  3. Use a time-weighted reward model (Geyser / Synthetix Unipool): rewards per user are integrated over time against their weighted stake duration, not a point-in-time snapshot. This is the "correct" fix for sniping but is a larger refactor.
  4. Restrict depositRevenue to a committed-reveal / Merkle schedule: commit the intent to deposit N blocks ahead (so attackers cannot front-run the deposit itself).

At minimum, fix the documentation. The current comment is materially misleading — users might stake believing they are protected from sniping when they are not.

3.2 Medium

[M-01] depositRevenue can be called by anyone with tiny amounts, permanently locking dust in the contract

Severity: Medium
Category: evm-audit-access-control, evm-audit-precision-math, evm-audit-dos
Location: depositRevenue(uint256) at lines 181–192

Description.
depositRevenue has no access control and no minimum-amount check beyond amount != 0. Given 18-decimal tokens and the minimum Observer threshold of 1,000 × 1e18, totalWeightedStake is always ≥ 1e21 once anyone stakes — and realistically much higher once multiple Validators stake.

The update line is:

accRewardPerShare += (amount * ACC_PRECISION) / totalWeightedStake;

If amount * 1e18 < totalWeightedStake, integer division rounds to 0 and accRewardPerShare does not change. But the tokens are pulled in via transferFrom and totalRewardsDistributed += amount is still executed. The tokens now sit in the contract balance with no reward attribution to any staker, and no mechanism can ever release them — there is no rescueTokens, no owner withdraw, nothing.

Example. If totalWeightedStake = 8,000,000 × 1e18 (one Validator staking 1M tokens), any depositRevenue(amount) with amount < 8,000,000 (i.e., less than 8e-12 $GITLAWB) silently locks the tokens.

Proof of Concept.

totalWeightedStake = 8_000_000 * 1e18
attacker calls depositRevenue(1)
  accRewardPerShare += (1 * 1e18) / (8_000_000 * 1e18) = 0
  totalRewardsDistributed += 1
  token balance of contract += 1

Repeat cheaply on Base L2. Each 1-wei call permanently locks 1 wei. Aggregate effect is small in absolute terms but the locked tokens are unclaimable by anyone.

A stronger variant: if an attacker is the first to call depositRevenue right after a stake, and chooses an amount just below totalWeightedStake / 1e18, they can grief by locking up to totalWeightedStake / 1e18 - 1 wei with no effect on accRewardPerShare.

Recommendation.

  1. Require a minimum deposit that guarantees non-zero per-share increase:
    if (amount * ACC_PRECISION < totalWeightedStake) revert InvalidAmount();
  2. Optionally, restrict depositRevenue to an allowlist of treasury addresses:
    mapping(address => bool) public isRevenueDepositor;
...
if (!isRevenueDepositor[msg.sender]) revert NotAuthorized();
  3. Optionally, add a "donation sweep" mechanism: if a non-zero residual exists in token.balanceOf(this) - totalStaked - (unaccrued rewards), allow the owner to redistribute it via a new depositRevenue call that uses the full residual, recovering the locked dust.

[M-02] No protection against fee-on-transfer or rebasing $GITLAWB token variants

Severity: Medium
Category: evm-audit-erc20, evm-audit-general
Location: stake() line 93; depositRevenue() line 185

Description.
Both stake and depositRevenue call token.transferFrom(sender, this, amount) and then record amount verbatim into storage (info.amount += amount, totalStaked += amount, accRewardPerShare += amount * 1e18 / totalWeightedStake). If $GITLAWB is ever deployed with a fee-on-transfer mechanic, or upgraded to a rebasing model, or has any behavior where received != sent, internal accounting drifts from the true contract balance.

Consequences:

  • Fee-on-transfer: users' info.amount is inflated. Eventually a user attempts to unstake() their recorded amount but token.transfer(msg.sender, amount) reverts because the contract's real balance is lower. The last user in gets stuck; earlier users effectively drained principal of later users.
  • Rebasing: contract accounting never updates with rebases. Positive rebases (yield) leak to whoever calls unstake() last (they get more than they deposited). Negative rebases (slashing) bankrupt later unstakers.
  • Pausable / blacklisting token: all functions that transfer revert. Stakers' funds stuck indefinitely.

The $GITLAWB source was not in scope for this audit and cannot be confirmed against these assumptions. If $GITLAWB is a vanilla, fixed-supply, non-fee, non-rebasing ERC20, this is Info. Given the uncertainty, rated Medium.

Recommendation.

  1. Check actual transferred amount via balance diff:

    uint256 balBefore = token.balanceOf(address(this));
bool ok = token.transferFrom(msg.sender, address(this), amount);
if (!ok) revert TransferFailed();
uint256 received = token.balanceOf(address(this)) - balBefore;
if (received != amount) revert UnexpectedTransferAmount();

    And use received rather than amount in the accrual math.

  2. Alternatively, document explicitly in NatSpec and deployment README that the staking contract is only safe for standard ERC20 tokens and will not function with FoT / rebasing / pausable variants. Add an invariant test asserting token.balanceOf(this) >= totalStaked.

  3. If $GITLAWB is controlled by the same team, ensure the token contract has no transfer hooks, no fees, no rebases, and no pause mechanism that would brick the staking contract.

[M-03] No ReentrancyGuard — vulnerable if $GITLAWB is ever ERC777-compatible or has transfer hooks

Severity: Medium
Category: evm-audit-general, evm-audit-erc20
Location: All external mutating functions — stake, unstake, requestUnstake, claimRewards, depositRevenue

Description.
None of the state-changing functions carry a reentrancy guard. stake() has a particularly concerning order: _harvest runs, state in info.pendingRewards is updated, then token.transferFrom is called before the rest of the state (info.amount, totalWeightedStake, rewardDebt) is finalized.

If $GITLAWB is ever an ERC777 token (backward-compatible with ERC20), or if a future upgrade adds tokensToSend / tokensReceived hooks, the transferFrom call in stake() triggers a tokensToSend callback on msg.sender before the stake's state updates are written. The attacker can reenter into claimRewards, requestUnstake, etc. while info.amount still reflects the pre-stake value.

Worked example with a malicious ERC777 token:

  1. Attacker has info.amount = 1,000e18 (Observer, weight = 1,000e18), rewardDebt matches.
  2. Attacker calls stake(999,000e18) with intent to reach Validator (1M tokens, weight = 8M × 1e18).
  3. _harvest runs; rewardDebt snapshotted at old weight.
  4. token.transferFrom(...) is called → tokensToSend callback on attacker.
  5. Attacker reenters requestUnstake(1,000e18). This runs _harvest again (pending = 0, rewardDebt already fresh), sets info.unstakeRequestAt and info.unstakeAmount. Returns.
  6. Original stake() resumes. Now totalWeightedStake -= oldWeight (1,000e18), info.amount += 999,000e18 → 1,000,000e18. totalWeightedStake += newWeight (8,000,000e18). rewardDebt = 8,000,000e18 * accRewardPerShare / 1e18.
  7. Attacker now has a pending unstake request for 1,000e18 with a fresh 7-day clock but is stake-weighted at Validator tier. 7 days later they pull 1,000 tokens out and keep 999,000 at Validator weight.

The above scenario isn't directly catastrophic, but it violates invariants (user has a pending unstake for an amount that represents an older, smaller position — mental model breakage). Other reentry paths may be more severe; the general rule is: any time a contract calls an external token before finalizing state, add reentrancy protection.

With a standard non-777 ERC20, there is no exploit. Rated Medium because (a) we cannot verify $GITLAWB's current interface is and will remain ERC20-only, and (b) the cost of adding a guard is near-zero.

Recommendation.

  1. Import and apply OpenZeppelin's ReentrancyGuard:
    import {ReentrancyGuard} from "@openzeppelin/contracts/utils/ReentrancyGuard.sol";
contract GitlawbStaking is ReentrancyGuard { ... }

function stake(uint256 amount) external nonReentrant { ... }
function requestUnstake(uint256 amount) external nonReentrant { ... }
function unstake() external nonReentrant { ... }
function claimRewards() external nonReentrant { ... }
function depositRevenue(uint256 amount) external nonReentrant { ... }
  2. Reorder stake() so that all state updates happen before transferFrom (proper CEI). This requires carefully snapshotting the old weight value locally, updating info.amount/totalWeightedStake/rewardDebt first, then doing transferFrom last. This gives defense-in-depth even if the reentrancy guard fails.

[M-04] Partial unstake can leave user with dust below OBSERVER_THRESHOLD, trapping tokens in a zero-weight state

Severity: Medium
Category: evm-audit-defi-staking, evm-audit-general
Location: requestUnstake(uint256) lines 117–129; unstake() lines 132–161

Description.
requestUnstake validates only amount > 0 and amount <= info.amount. It does not check that the remaining info.amount - amount either stays above OBSERVER_THRESHOLD or drops to exactly zero.

Consequence: a user with 10,000 tokens (Curator) can requestUnstake(9,999.5 × 1e18). After the 7-day cooldown and unstake(), their remaining info.amount = 0.5 × 1e18 (dust below Observer threshold). The remaining dust has _weightedAmount() = 0, earns no rewards, and cannot be increased via stake() because stake enforces the minimum on the post-stake amount.

Actually, the user CAN re-stake — the stake() check is if (info.amount < OBSERVER_THRESHOLD) revert BelowMinimumStake(); which is applied to the new info.amount after addition. So they could stake another 999.5 tokens to become Observer again. But the dust itself is stuck in a non-productive state until fully unstaked. More importantly, the asymmetry is weird:

  • stake() enforces min threshold.
  • requestUnstake() doesn't enforce "leaving above threshold or fully exiting."

A user who doesn't realize this will unstake "everything but a little" and end up with dust earning 0%, then need a second full-lifecycle requestUnstake + 7 day wait + unstake to retrieve the rest. UX footgun, not a direct fund-loss, but violates user expectations and creates weird accounting states.

Recommendation.
Enforce the symmetry at requestUnstake:

function requestUnstake(uint256 amount) external {
    StakeInfo storage info = stakes[msg.sender];
    if (amount == 0) revert InvalidAmount();
    if (amount > info.amount) revert InsufficientStake();

    uint256 remaining = info.amount - amount;
    if (remaining != 0 && remaining < OBSERVER_THRESHOLD) revert BelowMinimumStake();

    _harvest(msg.sender);
    info.unstakeRequestAt = block.timestamp;
    info.unstakeAmount = amount;
    emit UnstakeRequested(msg.sender, amount, block.timestamp + COOLDOWN_PERIOD);
}

This forces either a full exit or remaining ≥ Observer threshold. No dust states.

3.3 Low

[L-01] transferOwnership is single-step — no Ownable2Step

Severity: Low
Category: evm-audit-access-control
Location: transferOwnership(address) lines 276–280

Description. Single-step transfer with no acceptOwnership flow. Mistyping newOwner (wrong checksum, wrong address) permanently locks the contract out of its (currently unused) owner role. The only validation is newOwner != address(0).

Recommendation. Use OpenZeppelin Ownable2Step or implement a pending-owner pattern:

address public pendingOwner;
function transferOwnership(address newOwner) external onlyOwner {
    if (newOwner == address(0)) revert ZeroAddress();
    pendingOwner = newOwner;
}
function acceptOwnership() external {
    if (msg.sender != pendingOwner) revert NotPendingOwner();
    owner = pendingOwner;
    pendingOwner = address(0);
}

Note: since the contract's owner has no functional powers (no pause, no upgrade, no admin setters), the practical impact of this bug is zero in the current version. But if any admin function is added in a v2, the pattern must be upgraded simultaneously.

[L-02] Constructor missing zero-address check on token

Severity: Low
Category: evm-audit-general
Location: constructor at lines 77–80

Description.

constructor(address _token) {
    token = IERC20(_token);
    owner = msg.sender;
}

No validation that _token != address(0). A fat-finger deployment bricks the contract from block zero (all token.* calls will revert). Since token is immutable, no recovery.

Recommendation.

constructor(address _token) {
    if (_token == address(0)) revert ZeroAddress();
    token = IERC20(_token);
    owner = msg.sender;
}

[L-03] Raw IERC20.transfer / transferFrom — should use SafeERC20

Severity: Low
Category: evm-audit-erc20
Location: stake() line 93, unstake() line 157, claimRewards() line 173, depositRevenue() line 185

Description. The contract uses bool ok = token.transfer(...) and checks ok. This works for well-behaved ERC20s that return bool. But it fails for:

  • Tokens that don't return a bool (classic USDT on Ethereum mainnet).
  • Tokens that return false without reverting even on success (Tether Gold and similar edge-case tokens).

Since $GITLAWB is presumably a standard ERC20, this is Info in practice. Still, using OZ's SafeERC20 is best practice and protects against a future scenario where the protocol wants to support additional reward tokens.

Recommendation.

using SafeERC20 for IERC20;

token.safeTransferFrom(msg.sender, address(this), amount);
token.safeTransfer(msg.sender, amount);

Remove the TransferFailed custom error, since safeTransfer reverts with a decoded message on failure.

[L-04] requestUnstake silently overwrites a prior pending request, resetting the cooldown

Severity: Low
Category: evm-audit-general, evm-audit-defi-staking
Location: requestUnstake(uint256) lines 117–129

Description. If a user already has info.unstakeAmount > 0 with a cooldown in progress, calling requestUnstake again overwrites both unstakeAmount and unstakeRequestAt with new values. This resets the 7-day timer without warning.

Proof of Concept. Alice calls requestUnstake(100 × 1e18) on day 0. On day 6.9, Alice (panicking or confused) calls requestUnstake(200 × 1e18). Her cooldown clock is now reset; she has to wait 7 more days. No event indicates that a previous request was clobbered.

Recommendation. Revert if a pending request already exists, forcing the user to either unstake (if cooldown elapsed) or call a new cancelUnstake function:

function requestUnstake(uint256 amount) external {
    StakeInfo storage info = stakes[msg.sender];
    if (info.unstakeAmount != 0) revert UnstakePending();
    ...
}

function cancelUnstake() external {
    StakeInfo storage info = stakes[msg.sender];
    if (info.unstakeAmount == 0) revert NoPendingUnstake();
    info.unstakeAmount = 0;
    info.unstakeRequestAt = 0;
}

Alternatively, if overwriting is the desired UX, at least emit a distinct event (UnstakeRequestReplaced) so offchain indexers can track it.

[L-05] transferOwnership without emitting an event

Severity: Low
Category: evm-audit-access-control
Location: transferOwnership(address) lines 276–280

Description. No event is emitted on ownership change. Offchain monitors, block explorers' Contract tab, and governance dashboards all rely on an OwnershipTransferred event to update their views.

Recommendation.

event OwnershipTransferred(address indexed previousOwner, address indexed newOwner);

function transferOwnership(address newOwner) external {
    if (msg.sender != owner) revert NotOwner();
    if (newOwner == address(0)) revert ZeroAddress();
    emit OwnershipTransferred(owner, newOwner);
    owner = newOwner;
}

[L-06] No emergency pause or escape hatch — contract is fully immutable

Severity: Low
Category: evm-audit-access-control, evm-audit-general
Location: Contract-wide

Description. There is no pause() function, no emergency withdraw, no way to migrate users to a new staking contract, and no way to recover mis-sent tokens (ERC20 other than $GITLAWB sent to the contract are stuck forever — relevant if anyone mistakenly airdrops to the address). This is partly a feature (no rug surface, fully trustless) and partly a liability (no ability to respond to a bug in $GITLAWB itself, e.g., if the token gets paused or frozen, all stakers' principal is locked).

Recommendation. Consider at minimum adding:

  • A pause() guarded by the owner that blocks stake and depositRevenue (but leaves unstake and claimRewards open, to avoid stranding users).
  • A rescueToken(IERC20 alien, address to, uint256 amount) callable by owner, restricted so that alien != token (cannot rug the staking token).

These trade off some centralization for incident response. If the project's north star is full immutability, skip and document explicitly.

[L-07] Solidity ^0.8.24 — floating pragma

Severity: Low
Category: evm-audit-general
Location: pragma solidity ^0.8.24; line 2

Description. The caret pragma allows any compiler version >=0.8.24 <0.9.0. For production contracts, pin to the exact version tested and audited to avoid compiling with a future version that may have different codegen, different optimizer behavior, or a new compiler bug.

Also note: ^0.8.24 emits the push0 opcode. Base L2 supports push0 (post-Shanghai hardfork), so this is fine on Base specifically, but any multichain redeployment must confirm target chain's support.

Recommendation. Pin to pragma solidity 0.8.24; (no caret). Document the exact tested compiler version in the repo README.

3.4 Info

[I-01] _harvest returns silently for users with info.amount == 0

Severity: Info
Location: _harvest(address) lines 252–264

Description.

function _harvest(address staker) internal {
    StakeInfo storage info = stakes[staker];
    if (info.amount == 0) return;
    ...
}

If a user has info.amount == 0 but info.pendingRewards > 0 (e.g., they've already unstaked but not yet claimed), _harvest returns early. Then claimRewards() proceeds to transfer info.pendingRewards. This works correctly because claimRewards reads info.pendingRewards after the early-return and transfers it. No bug. Just noting the control flow so maintainers don't accidentally break the invariant in the future.

Recommendation. Add a comment documenting that early-return from _harvest is safe because pendingRewards is already snapshotted.

[I-02] Stakers with weight = 0 do not accrue but occupy storage

Severity: Info
Location: _weightedAmount(uint256) lines 266–272

Description. If a user partially unstakes below OBSERVER_THRESHOLD (see M-04 above), their info.amount > 0 but _weightedAmount(info.amount) = 0. They occupy a storage slot but accrue nothing and distort "unique staker count" metrics. Not exploitable. Cleaning this up is part of the M-04 fix.

[I-03] Staked event fires getTier(msg.sender) after state update — correct, but worth noting

Severity: Info
Location: stake() line 113

Description. getTier(msg.sender) reads the new tier after info.amount += amount. This is the intended behavior (event reports the user's post-stake tier). Verified correct.

[I-04] Tier thresholds and multipliers are constant and immutable

Severity: Info
Location: lines 33–38

Description. All tier thresholds and the cooldown period are constant. If tokenomics change (e.g., protocol wants to add a new tier, adjust thresholds for market price, or shorten the cooldown for a liquidity event), redeployment is required and users must migrate. This is an intended design tradeoff; flagging for the record.

[I-05] import {IERC20} from "lib/forge-std/src/interfaces/IERC20.sol"; — unusual import path

Severity: Info
Location: line 4

Description. Importing IERC20 from forge-std works but is unconventional. The canonical import is from OpenZeppelin or a project-local interfaces directory. Using forge-std IERC20 means the production deployment depends on forge-std's interface definition, which is a testing framework rather than a production dependency. Not a bug, but worth switching to @openzeppelin/contracts/token/ERC20/IERC20.sol or similar for clarity.
