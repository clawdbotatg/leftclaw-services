Protocol Summary

A fixed-term collateralized lending protocol:

  1. Borrowers create vaults via the Factory (paying 0.0001 ETH creation fee), depositing ERC20 collateral.
  2. Each vault has immutable parameters: borrower, P-holder (lender address, stored as uint256), N-holder (stored as uint256), collateral, initialCollateralAmount, fundingDeadline, repaymentDeadline.
  3. Lenders buy P-positions on the Marketplace by paying USDC (0.1% protocol fee).
  4. If no lenders fund by fundingDeadline, the borrower calls closeFunding() and recovers their collateral.
  5. If funded, the borrower repays via repayInFull() by repaymentDeadline — or lenders call settle() to seize collateral.
  6. USDC is the lending currency (0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913).

Live state at audit time (2026-06-20, timestamp 1781974725):

  • 3 vaults, 3 marketplace sales
  • Vault 2 is active: borrower = 0x61068AbfB8349f90bd0bAb12347ec10e0C55C20f, WETH collateral (0.003 WETH), funding deadline ~30 days out
  • Protocol owner/feeRecipient: 0x7C8d9ad4F51299b02755Ec13C018004008b45494

Findings

Critical

[F-1] settle() Access Control Unconfirmed — Vault 1 Is Overdue Right Now

Severity: Critical (LEAD — confirm via source/decompile)
Confidence: Both audit passes flagged; on-chain evidence of overdue vault
Location: Vault · settle()

Description: Vault 1's repaymentDeadline = 1781925447, and the current block timestamp is 1781974725 — 13+ hours past deadline. The vault is settled = false. If settle() is permissionless (no require(msg.sender == address(uint160(P)))), any actor can call it right now and trigger collateral disbursement to an address they specify rather than the legitimate P-holder. Even if Vault 1 has zero balance (its collateral was returned via closeFunding), this same pattern applies to all future vaults where the borrower misses the repayment deadline.

Proof of Concept (Vault 2 scenario):

  1. Vault 2: fundingClosed = true, accountedCollateral = 3001500000000000 WETH, repaymentDeadline = ~60 days from now.
  2. Borrower misses deadline.
  3. Attacker calls vault.settle() at deadline+1 block.
  4. If settle() is permissionless: 0.003 WETH disbursed to attacker-controlled address instead of legitimate P-holder.

Recommendation: Restrict settle() to msg.sender == address(uint160(P)) or implement a claim-based pattern where P-holder calls after deadline. This is the highest-priority finding: decompile bytecode immediately.

[F-2] initializePosition() Re-initialization Guard Unconfirmed

Severity: Critical (LEAD)
Location: Vault · initializePosition()

Description: initialized() returns bool (confirmed via cast call), suggesting a guard variable exists. However, it cannot be confirmed that initializePosition() checks this flag. If re-initialization is possible, any caller can overwrite P-holder, deadlines, or collateral amounts after a lender has purchased a position — directly stealing lender funds.

Proof of Concept:

  1. Lender buys P-position (1000 USDC enters vault).
  2. Attacker calls initializePosition() with attacker-controlled P address (if unchecked).
  3. Attacker becomes P-holder; calls redeemP() to drain 1000 USDC.

Recommendation: Confirm initializePosition() contains require(!initialized(), "Already initialized") and initialized is set in the same transaction. Second-highest priority decompilation target.

High

[F-3] Borrower Can Self-Assign P-Position — Self-Funded Circular Loan

Severity: High
Confidence: High — no on-chain enforcement preventing it
Location: VaultFactory · createVault() / Marketplace · buy()

Description: P and N addresses are borrower-supplied at vault creation with no validation. A borrower who sets P = borrower pays USDC to themselves (net: only 0.1% fee), posts collateral, then recovers it via settle() if they miss the deadline. This allows attracting third-party N-position lenders while the borrower faces no real economic consequence.

Recommendation: require(address(uint160(P)) != borrower && address(uint160(N)) != borrower && P != N) in createVault.

[F-4] No Oracle and No Liquidation — Rational Strategic Default Always Available

Severity: High
Confidence: High — confirmed by on-chain state (no oracle calls observed)
Location: Protocol design

Description: The protocol accepts any whitelisted ERC20 as collateral at face token-amount with no price oracle. Borrowers hold a perpetual American put: if collateral value drops below the outstanding USDC at any point, defaulting is rational. There is no mechanism to liquidate before repaymentDeadline. Confirmed live: GITLAWB (vaults 0–1) has no verifiable market price and a supply of 1×10²⁹, meaning any USDC lent against it was effectively unsecured.

Recommendation: Require a Chainlink or TWAP oracle for every whitelisted collateral. Implement a liquidation threshold (e.g., health factor < 1.0). At minimum, enforce minimum overcollateralization (150% LTV) at vault creation and document the strategic default risk prominently.

[F-5] Stale Marketplace Listings Remain Active After Vault Repayment

Severity: High
Confidence: High — Marketplace has no vault state callback
Location: Marketplace · buy()

Description: When a vault transitions to settled or repaid, any outstanding P/N listings on the Marketplace remain buyable. A buyer who purchases a P-token listing after repayInFull() has already been called by the borrower gets a token with no USDC claim — the previous holder already redeemed, or the original P-holder is about to redeem and the listing buyer gets nothing.

Proof of Concept:

  1. Borrower calls repayInFull() — 1000 USDC in vault, redeemable by P-holder.
  2. P-holder lists tokens on Marketplace at any price before redeeming.
  3. Buyer pays 900 USDC for the listing.
  4. Buyer calls redeemP() — either reverts (tokens burned) or returns 0 (P-holder already claimed).
  5. Buyer loses 900 USDC.

Recommendation: In buy(), check vault.settled() and vault.fundingClosed(). Revert if vault is no longer in a fundable state. Emit events when vault state changes to allow off-chain indexing of invalid listings.

[F-6] Direct Token Transfer to Vault Inflates Balance Without Updating Accounting

Severity: High
Confidence: High — accounting mismatch observable via accountedCollateral vs balanceOf
Location: Vault · all collateral disbursement functions

Description: Any actor can send collateral tokens directly to the vault address. accountedCollateral is only set at initialization. If disbursement uses live balanceOf: donated tokens inflate all redeemers' share (invariant broken, last-redeemer benefit). If disbursement uses accountedCollateral: donated tokens are permanently locked with no sweep path. Both paths violate the protocol invariant. Confirmed: Vault 2 currently shows balanceOf == accountedCollateral, showing the invariant is intended to hold.

Recommendation: All collateral disbursement must use accountedCollateral, never live balanceOf. Add an owner-callable sweep(address token) to recover any tokens exceeding accountedCollateral.

[F-7] Instant Collateral Whitelist Removal Retroactively Affects Active Vaults

Severity: High
Location: VaultFactory · setCollateralAllowed(address,bool)

Description: setCollateralAllowed(token, false) takes effect immediately with no timelock. If any vault function (particularly repayInFull()) checks factory.collateralAllowed(vault.collateral), an admin calling this function on an active vault's collateral can block borrower repayment while settle() remains available — forcing the borrower into default with no recourse.

Recommendation: Track active vaults per collateral token. Disallow removal if any unfunded or funded-but-unsettled vault uses that token. Add a 7-day timelock for whitelist removals.

[F-8] Single EOA Controls All Admin Functions — No Timelock, No Multisig

Severity: High
Location: VaultFactory + Marketplace · all admin functions

Description: Owner = feeRecipient = 0x7C8d9ad4F51299b02755Ec13C018004008b45494. This EOA can: pause/unpause (trapping or releasing funds), add/remove collateral tokens, withdraw all protocol fees, transfer ownership — all in a single block. A compromised key = full protocol control.

Recommendation: Migrate to a 3/5 multisig. Add 48-hour timelock for all parameter changes. Separate feeRecipient from the admin key. At minimum, emit events for all parameter changes to allow monitoring.

[F-9] Reentrancy Risk in settle()/redeemP() for Custom ERC20 Collateral

Severity: High (LEAD — vault reentrancy guard unconfirmed)
Location: Vault · settle(), redeemP(), redeemPair()

Description: Marketplace slot 0 = 1 confirms a reentrancy guard (NOT_ENTERED) on the Marketplace. Vault contracts' storage layout at known slots does not show an equivalent guard. GITLAWB is a custom token with unknown transfer semantics. If GITLAWB implements ERC777-style hooks, a malicious P/N holder could reenter redeemP() before settled is set to true, draining the vault multiple times.

Recommendation: Apply nonReentrant to all vault state-changing functions. Follow strict checks-effects-interactions: write settled = true before any token transfer. Audit GITLAWB independently.

[F-10] repayInFull() Amount Basis Unconfirmed — Partial Repayment May Trap USDC

Severity: High (LEAD)
Location: Vault · repayInFull()

Description: If the repayment amount is computed from a creation-time parameter (e.g., maximum principal) rather than actual USDC raised at closeFunding time, a partially-funded vault would require incorrect repayment. Underpayment leaves P-holders undercovered; overpayment may cause permanent revert — making the vault non-settleable and trapping lender USDC.

Recommendation: Store totalUSDCRaised at closeFunding time. Compute repayment dynamically as exactly totalUSDCRaised. Validate via post-transferFrom balanceOf check.

[F-11] redeemPair() Callable Post-Repayment Burns P-Token USDC Claims

Severity: High (LEAD)
Location: Vault · redeemPair(uint256)

Description: redeemPair() burns both P and N tokens (for the collateral-seizure default path). If callable after repayInFull(), a holder of both token types calling redeemPair() instead of redeemP() burns their P-tokens without receiving the USDC those tokens entitled them to, permanently trapping the repaid USDC.

Recommendation: Gate redeemPair() strictly on settled = true (default path only). After repayInFull, disable redeemPair and only allow redeemP.

[F-12] closeFunding() Access Control Unconfirmed — Potential Premature Closure or Double-Extraction

Severity: High (LEAD)
Location: Vault · closeFunding(uint256)

Description: If closeFunding is callable by anyone (not just the borrower), a griefer can close a vault immediately after creation before any lenders fund it. More critically, if callable by the borrower before the funding deadline and after some USDC has been raised, the borrower could trigger collateral return while also keeping the raised USDC — a double-extraction attack.

Recommendation: Restrict to msg.sender == borrower. Only callable after fundingDeadline if USDC was raised; callable any time if USDC raised == 0. Validate minUSDC parameter prevents premature close when lenders are involved.

Medium

[F-13] Fee Calculation Rounds to Zero for Purchases Below 1000 USDC Units

Severity: Medium
Confidence: High — confirmed by fee formula analysis; accruedProtocolFees = 2000 on 3 sales
Location: Marketplace · buy()

Description: fee = amount * 10 / 10000. For amount < 1000 (< $0.001 in USDC), fee = 0. Sellers can split large transactions into sub-1000-unit chunks on Base (near-zero gas) and pay zero protocol fees.

Recommendation: fee = max(1, (amount * SALE_FEE_BPS) / BPS_DENOMINATOR). Or enforce minimum purchase size.

[F-14] Decimal Mismatch in quoteUsdc — USDC (6 dec) vs. Collateral (18 dec)

Severity: Medium (LEAD — cannot confirm scaling without source)
Location: Marketplace · quoteUsdc(uint256,uint256)

Description: USDC has 6 decimals; WETH and GITLAWB have 18. Any price formula bridging these must apply a 10¹² scaling factor. If quoteUsdc does not, it produces quotes 10¹² × too large or too small, making any minimum-price check in buy() trivially bypassed.

Recommendation: Confirm formula is (collateralAmount * pricePerWholeToken) / (10 ** collateralDecimals) with pricePerWholeToken in USDC base units. Fetch decimals() dynamically.

[F-15] USDC Denylist Permanently Blocks redeemP() for Denylisted P-Holders

Severity: Medium
Confidence: High — USDC denylist is well-documented on-chain
Location: Vault · redeemP()

Description: USDC (Circle) maintains a denylist. If a P-position holder is added to the denylist after purchasing, redeemP() reverts on the USDC transfer, permanently locking the USDC in the vault with no alternative claim path.

Recommendation: Pull-based USDC redemption: record the pending amount in storage, allow P-holder or a designated recovery address to withdraw via a separate function. Never push tokens to potentially denylisted addresses atomically.

[F-16] purchasesPaused Flag May Freeze Lender Redemptions

Severity: Medium (LEAD)
Location: VaultFactory · setPurchasesPaused(bool) → Vault · redeemP()

Description: If vault redemption functions check factory.purchasesPaused(), the admin can freeze all lender redemptions after borrowers have already repaid in full — trapping already-returned USDC.

Recommendation: Decouple purchasesPaused from redemption flows. Only buy() should be gated by this flag; redeemP, redeemPair, and settle() must remain perpetually callable.

[F-17] MEV Front-Running repayInFull() — Risk-Free Arb at Seller's Expense

Severity: Medium
Confidence: High — public mempool, Base L2
Location: Marketplace · buy() ↔ Vault · repayInFull()

Description: When a borrower broadcasts repayInFull(), MEV bots observe the pending tx and front-run by buying discounted P-token listings (listed at a default-risk discount). Post-repayment, these tokens are immediately redeemable at face value — risk-free arb at the original seller's expense.

Recommendation: Mitigation options: private mempool for repayInFull, or atomically cancel all Marketplace listings when repayInFull executes. At minimum, document the MEV risk.

[F-18] repayInFull()/settle() Mutual Exclusion Unconfirmed — Double-Disbursement Race

Severity: Medium (LEAD)
Location: Vault · repayInFull() · settle()

Description: If both functions can execute on the same vault in the same block (borrower submits repayInFull, lender submits settle()), the first to execute wins. If the settled flag is not set atomically in both, the second call may double-disburse or cause accounting corruption.

Recommendation: Confirm settled = true is the first state change in both functions, before any external token calls (strict CEI).

[F-19] Factory ETH Overpayments Permanently Locked

Severity: Medium
Location: VaultFactory · createVault() (payable)

Description: Standard fee guards use >= CREATION_FEE. If the Factory does not refund msg.value - CREATION_FEE, user overpayments are locked. No confirmed ETH withdrawal function exists for the Factory.

Recommendation: Use require(msg.value == CREATION_FEE) or refund surplus. Add owner ETH withdrawal.

[F-20] renounceOwnership() Permanently Bricks Admin Functions

Severity: Medium
Location: VaultFactory · renounceOwnership()

Description: Calling renounceOwnership() permanently disables all owner-only functions (collateral whitelist management, pause, fee withdrawal). Accrued fees become irrecoverable.

Recommendation: Override renounceOwnership() to revert. If progressive decentralization is intended, migrate to governance before renouncing.

[F-21] P() and N() Return uint256 for Addresses — Type Confusion Risk

Severity: Medium
Confidence: High — confirmed by on-chain value analysis
Location: Vault · P() · N()

Description: Addresses are stored and returned as uint256 (confirmed: P for Vault 0 = 0x349761bbf00a4e48939f9063919ae780c94eab11 as uint256). Any code doing address(uint256(P)) truncates to 160 bits; if upper bits are ever non-zero (malformed vault), authorization checks produce wrong results.

Recommendation: Store P and N as address. If uint256 is intentional, validate P <= type(uint160).max at creation.

Low

[F-22] No Lender Withdrawal Path Before fundingDeadline

Severity: Low
Location: Vault · (missing function)

Description: Once USDC enters a vault, lenders cannot exit before fundingDeadline except by selling on the Marketplace. If Marketplace is paused or illiquid, lenders are locked for up to 30 days.

Recommendation: Implement withdrawFunding(uint256 amount) callable before fundingClosed = true, burning P-tokens and returning USDC at face value.

[F-23] No Grace Period Before settle() — MEV Collateral Seizure at Exact Deadline

Severity: Low
Location: Vault · settle()

Description: At repaymentDeadline, MEV bots can call settle() before the borrower can call repayInFull(). On Base (2-second blocks), the timing window is narrow but exploitable. A borrower intending to repay but delayed by congestion loses their collateral.

Recommendation: Add a 1-hour grace period after repaymentDeadline during which only the borrower can call repayInFull(). After grace period, allow any address to call settle().

[F-24] 365-Day Maximum Repayment Period Locks Lender Capital

Severity: Low
Location: VaultFactory · 0x70c1340f constant (31,536,000 seconds)

Description: Combined with the 30-day funding period, lenders can have USDC locked for up to 13 months with no oracle, no liquidation, and no early exit. Collateral can depreciate to near zero over that horizon.

Recommendation: Reduce maximum repayment period or implement secondary market position transfers. Display maximum lock duration prominently in UI.
