Executive Summary

0 Critical, 0 High, 0 Medium, 11 Low, 9 Info.

This is a peer-to-pool, zero-coupon-bond-style lending primitive: a borrower locks arbitrary owner-allowlisted collateral, mints matched "P" (payout claim, sold to lenders for USDC) and "N" (reclaim right, non-transferable, borrower-only) tokens, and settlement is strictly binary — full repayment pays P holders in USDC and returns all collateral to the borrower, or a missed deadline lets P holders split the collateral pro-rata. There is intentionally no oracle and no liquidation mechanism.

Both audit passes — 6 breadth checklist agents and 12 independent blind attacker-mindset agents (18 agents total) — converged on the same conclusion: the core accounting is unusually tight. The invariant pairedN + exercisedN + N.totalSupply() == initialCollateralAmount and the pre-settlement identity accountedCollateral == P.totalSupply() == N.totalSupply() are asserted and preserved across every reachable state transition. All 12 blind attack agents attempted concrete fund-extraction, DoS, and invariant-breaking exploits and reported zero raw FINDINGs — only bounded LEADs, most of which cross-corroborate the same handful of root causes identified independently by the breadth pass. No exploit chain rated above Low survived source-level verification.

The residual risk in this codebase is concentrated in one structural theme, corroborated by 6 of the 12 blind agents plus 3 of the 6 breadth agents (9 of 18 total) — the highest-corroboration finding in this audit:

Arbitrary owner-allowlisted collateral is validated only at position-creation time, but positions live up to ~13 months. A collateral token that is well-behaved at listing but later becomes fee-on-transfer, rebasing, or blocklist-capable will permanently DoS every exit path, because every collateral outflow enforces a strict exact-balance-delta check with no fallback or sweep. See [UNI-1] below.

Findings

[UNI-1] Owner-allowlisted collateral that later changes transfer behavior can permanently freeze all exits

Severity: Low
Origin: [both] — phase1: [GEN-2], [ERC20-3], [LEND-1]; phase2: [PASHOV-2] [agents: 6] — the single most-corroborated issue in this audit (9 of 18 total agents)
Location: PMFIPositionVaultV22.redeemP(), redeemPair(), claimCollateralRefund(), repayInFull(); gate is PMFIPositionFactoryV22.setCollateralAllowed()

// PMFIPositionFactoryV22.createPosition() — allowlist checked ONLY here, at creation:
if (!collateralAllowed[collateralAddress]) {
    revert CollateralNotAllowed();
}
...
// PMFIPositionVaultV22._redeemP() — every later exit enforces an EXACT delta:
uint256 userCollateralAfter = collateral.balanceOf(user);
if (
    userCollateralAfter < userCollateralBefore
        || userCollateralAfter - userCollateralBefore != collateralOut
) {
    revert FeeOnTransferUnsupported();
}

Description: collateralAllowed[token] (factory line 677) is validated exactly once, at createPosition(). A position can remain open for MAX_FUNDING_PERIOD (30 days) plus MAX_REPAYMENT_PERIOD (365 days) — up to ~13 months. accountedCollateral is a cached accounting snapshot (vault line 131), not derived from live balanceOf. If the allowlisted collateral is an upgradeable-proxy token, a USDT-style token with a dormant fee switch, a rebasing token (stETH-style), or later gains a per-address blocklist, its balance behavior can diverge from the cached snapshot mid-life. Every subsequent outbound collateral transfer — redeemP, redeemPair, claimCollateralRefund, and the collateral leg of repayInFull — enforces a strict exact-delta check (FeeOnTransferUnsupported revert on any deviation) with no fallback, no partial-payout path, and no sweep/rescue function. This directly contradicts the factory's own design intent stated in its NatSpec: "Pause controls only block new positions and new purchases. User exits are never paused." Token-level behavior changes bypass that guarantee entirely.
Proof of Concept: Owner allowlists token X (fee-free, non-rebasing at listing time — passes the exact-delta check at deposit in _safeTransferCollateralFromExact). A position is created, funds, and later defaults (deadline passes unpaid). Before all P holders redeem, token X's issuer enables a transfer fee, or the vault becomes blocklisted, or X rebases down. accountedCollateral still reflects the pre-change amount. Every subsequent redeemP() call by a remaining P holder now fails the exact-delta check and reverts — that holder's entire pro-rata collateral share is permanently locked, with no code path to recover it. This was independently constructed and confirmed via source-tracing by 9 of the 18 total audit agents across both phases.
Recommendation: Operationally restrict setCollateralAllowed to audited, fixed-supply, non-upgradeable, fee-free, non-rebasing tokens — the contract's own FeeOnTransferUnsupported naming shows this was already a conscious design tradeoff; document it explicitly for the owner. As a code-level mitigation, consider degrading gracefully instead of a hard revert:

uint256 available = collateral.balanceOf(address(this));
uint256 payout = Math.min(collateralOut, available);
// pay `payout`, and either write off the shortfall or track it for later top-up

[UNI-2] Outbound collateral transfers validate only the recipient's balance delta, not the vault's own

Severity: Low
Origin: [both] — phase1: [ERC20-1]; phase2: [PASHOV-1] [agents: 1]
Location: redeemPair() L314-323, _redeemP() L490-501, claimCollateralRefund() L290-297, repayInFull() L401-412

// _safeTransferCollateralFromExact (factory, inbound) — checks BOTH legs:
uint256 payerBalanceBefore = token.balanceOf(payer);
uint256 recipientBalanceBefore = token.balanceOf(recipient);
IERC20(address(token)).safeTransferFrom(payer, recipient, amount);
...
if (payerBalanceAfter > payerBalanceBefore || payerBalanceBefore - payerBalanceAfter != amount
    || recipientBalanceAfter < recipientBalanceBefore || recipientBalanceAfter - recipientBalanceBefore != amount)
{ revert FeeOnTransferUnsupported(); }

// redeemPair (outbound) — checks ONLY the recipient's leg:
uint256 recipientBalanceBefore = collateral.balanceOf(msg.sender);
IERC20(address(collateral)).safeTransfer(msg.sender, amount);
uint256 recipientBalanceAfter = collateral.balanceOf(msg.sender);
if (recipientBalanceAfter < recipientBalanceBefore || recipientBalanceAfter - recipientBalanceBefore != amount)
{ revert FeeOnTransferUnsupported(); }
// vault's own balanceOf(address(this)) delta is never checked here

Description: Every inbound transfer and every USDC transfer in this codebase symmetrically validates both sender and recipient balance deltas. The four outbound-collateral paths validate only the recipient's delta. A collateral token whose transfer fee is charged to the sender depending on the sender's role/address (e.g. waived for EOA depositors, charged when the sender is a contract) would pass the symmetric inbound check at deposit time (payer = EOA borrower) but silently over-drain the vault on every withdrawal (payer = vault contract) without being detected, since only the recipient's exact-amount receipt is checked.
Proof of Concept: Requires a crafted, owner-allowlisted token implementing asymmetric per-sender-role fees — a narrow but concrete gap distinct from UNI-1 (that one is about behavior changing over time; this one is a code-level check asymmetry present from day one for a specific token shape).
Recommendation: Make the four outbound helpers symmetric with the existing USDC/inbound helpers — assert the vault's own balance delta in addition to the recipient's.

[UNI-4] Rounding produces bounded, self-limiting dust — never exploitable for extraction

Severity: Info
Origin: [both] — phase1: [MATH-1], [MATH-2], [LEND-3]; phase2: [PASHOV-5] [agents: 6]
Location: quoteFee() L907-911, previewRedeemP()/_redeemP() L464-519
Description: quoteFee's cumulative round-down design (mulDiv(s.usdcRaisedToSeller + sellerPrice, SALE_FEE_BPS, BPS_DENOMINATOR) minus already-accrued fee) makes total under-collection bounded to <1 USDC base unit for a sale's entire lifetime regardless of fill fragmentation — confirmed by both the math-precision agent's telescoping proof and independent verification by the numerical-gap and invariant agents. _redeemP can burn P for a zero payout on sub-threshold amount when collateral decimals are high (up to 30) relative to a small USDC pool (mulDiv(usdcPoolRemaining, amount, currentSupply) floors to 0) — this is self-harm only: it reduces the caller's own claim and marginally increases the pro-rata share of remaining holders. No path allows a third party to extract this dust.
Proof of Concept (MATH-2, worst case): 30-decimal collateral, pSupplyAtSettle = currentSupply = 1e36, early settle with usdcPoolRemaining = 1e12 (1,000,000 USDC). Redeeming amount = 1e23 P yields usdcOut = floor(1e12·1e23/1e36) = 0 — the P is burned for nothing. Break-even threshold: amount ≥ 1e24.
Recommendation: Optional: if (collateralOut == 0 && usdcOut == 0) revert ZeroAmount(); in previewRedeemP to prevent accidental zero-payout burns. If exact-to-the-wei fee capture matters, round quoteFee's cumulative fee up via Math.Rounding.Ceil.

[UNI-5] USDC/collateral blocklist can permanently DoS a sale or post-settlement exits

Severity: Low
Origin: [both] — phase1: [ERC20-2]; phase2: [PASHOV-4] [agents: 5]
Location: buy() seller payout L970 (_safeTransferUsdcExact(s.seller, sellerPrice)), _redeemP()/repayInFull() post-settlement transfers L492/509/399/403
Description: The factory's "user exits are never paused" guarantee covers only the protocol's own pause flags, not token-issuer-level controls. Official USDC (Circle) on Base carries blocklist/pause capability. If the borrower (the sale's fixed seller) becomes blocklisted mid-funding, every buy() on that sale reverts — only cancel/closeExpired remain, and the borrower simply cannot raise further (largely self-harm). If the vault itself becomes blocklisted post-settlement, every redeemP() call reverts, stranding every P holder's funds with no alternative withdrawal path.
Recommendation: Largely inherent to using official USDC and cannot be fully removed. Consider a pull-payment/escrow model in buy() so a single blocklisted seller can't brick purchases for the whole sale. Document the residual risk for the vault-blocklist case, which has no code-level mitigation.

[UNI-6] feeRecipient is immutable in both factory and marketplace with no rotation path

Severity: Low
Origin: [both] — phase1: [AC-1]; phase2: [PASHOV-7] [agents: 1]
Location: PMFIPositionFactoryV22.feeRecipient L544, PMFIPrimaryMarketplaceV22.feeRecipient L774
Description: Set once at construction and never rotatable. Only feeRecipient may call withdrawCreationFees() (L753) and withdrawProtocolFees() (L1038). If the key is lost or compromised, protocol fee revenue — never user principal or collateral — is permanently stranded or drainable by the compromised key. Blast radius is strictly limited to protocol fees; no user-facing exit path depends on feeRecipient.
Recommendation: Accept as a deliberate trust-minimization tradeoff, or add an onlyOwner-gated setFeeRecipient(address) with a zero-address check and event.

[UNI-7] Owner-controlled purchase/creation pauses never touch user exits — verified, plus a mid-raise angle

Severity: Info
Origin: [both] — phase1: [AC-2]; phase2: [PASHOV-8] [agents: 1]
Location: setCreationPaused() L628, setPurchasesPaused() L633, consumed only in createPosition() L670 and buy() L948
Description: Both phases independently traced every exit/refund/redemption path (redeemPair, repayInFull, settle, settleAndRedeemP, redeemP, claimCollateralRefund, cancel, closeExpired) and confirmed neither pause flag is read there — the NatSpec claim holds for the protocol's own controls. Phase 2 added a specific angle: pausing purchases mid-funding (not just pre-funding) can starve a specific in-progress raise, pushing it toward forced expiry. No lender loses already-purchased P, and the borrower's obligation shrinks proportionally to unsold P — a liveness/governance lever, not a fund-loss path.
Recommendation: None required for security; document as an intentional (if centralization-flavored) owner lever.

[UNI-9] P claim tokens sent to non-redeeming contracts permanently strand their share of the settlement pool

Severity: Low
Origin: [phase1 only: GEN-1] — re-examined against source in reconciliation, confirmed, not demoted
Location: previewRedeemP()/_redeemP() L464-519

collateralOut = Math.mulDiv(accountedCollateral, amount, currentSupply);
usdcOut = Math.mulDiv(usdcPoolRemaining, amount, currentSupply);

Description: Post-settlement redemption divides a fixed pool by live P.totalSupply(). P is a freely transferable ERC20 (transfersEnabled = true in PMFILegTokenV22). There is no redemption logic reachable from the vault or marketplace themselves — if P is sent to either contract (or any other non-redeeming address) after settlement, it is never burned. currentSupply in the denominator still includes that stranded P indefinitely, so every remaining real holder's calculated share is understated relative to their true entitlement, and the corresponding slice of the pool becomes permanently unclaimable (no sweep function exists).
Proof of Concept: Position settles in default with accountedCollateral = funded, P.totalSupply() = funded. A holder transfers X P to the vault or marketplace address. Real holders' subsequent redeemP calls still divide by a currentSupply that includes X. The final real redemption leaves mulDiv(pool, X, funded) worth of collateral backing the now-unredeemable X, permanently locked. The party who sent the P forfeits their own claim (unprofitable self-sacrifice) — but the resulting stranded pool value is a real, permanent loss borne collectively by the remaining legitimate holders, not the sender.
Recommendation: Either track an explicit "redeemable P" counter decremented only by genuine _redeemP burns (denominator becomes this counter, not live totalSupply()), or block P transfers to the vault/marketplace addresses in PMFILegTokenV22._update().

[UNI-10] Sequencer downtime spanning repaymentDeadline can force a solvent borrower into default

Severity: Low
Origin: [phase1 only: CHAIN-1] — chain-specific domain not covered by the blind pashov pass; re-examined against source in reconciliation, confirmed, not demoted
Location: repayInFull() L373, _settle() L442

// repayInFull — borrower can only repay strictly before/at the deadline:
if (block.timestamp > repaymentDeadline) { revert RepaymentClosed(); }
...
// _settle — anyone can crystallize default the instant the deadline passes:
bool deadlinePassed = block.timestamp > repaymentDeadline;
if (!early && !deadlinePassed) revert TooEarly();

Description: Base runs a single centralized OP-stack sequencer. If it is down or censoring transactions in the window immediately before repaymentDeadline, a solvent, willing borrower's repayInFull() transaction cannot be sequenced. The instant the sequencer resumes past the deadline, any P holder can call settle() and irreversibly transfer the borrower's entire accountedCollateral to P holders — a real transfer of value driven purely by L2 liveness, not borrower behavior. No in-contract grace period exists; the only recourse is the slow L1 forced-inclusion path via the OptimismPortal delayed inbox, which is unlikely to land within a typical deadline window and is not surfaced to users by this contract.
Recommendation: Add a fixed grace period after repaymentDeadline before default-settlement is permitted, e.g.:

uint256 public constant SETTLE_GRACE = 6 hours;
// _settle(): bool deadlinePassed = block.timestamp > repaymentDeadline + SETTLE_GRACE;
// repayInFull(): allow repayment through repaymentDeadline + SETTLE_GRACE as well

Rated Low rather than higher because the borrower chooses repaymentDeadline (up to 365 days) and can self-impose buffer by setting an earlier personal deadline than the contractual one.
