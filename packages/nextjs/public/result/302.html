Security Audit Report — TheDAO (DAO.sol)

Target: 0xBB9bc244D798123fDe783fCc1C72d3Bb8C189413 (Ethereum mainnet)
Contract: The historic 2016 "TheDAO" contract (Token, TokenCreation, ManagedAccount, DAO, DAO_Creator) — 1235 LOC, Solidity ~0.3.1
Client request: "See if it is secure or if funds can get stolen. Focus on reentrancy."
Methodology: Two-phase audit — Phase 1 breadth (6 ethskills checklist agents: general, precision-math, erc20, governance, access-control, dos) → Phase 2 depth (12 pashov attacker-mindset agents, run blind to Phase 1) → this hybrid reconciliation.

Context note

This address is the original, historically famous "TheDAO" contract. It was exploited via a recursive-call reentrancy bug in June 2016, draining ~3.6M ETH and precipitating the Ethereum/Ethereum-Classic hard-fork split. The client's framing ("I launched a DAO contract... focus on reentrancy") suggests this audit is either a deliberate historical/educational exercise or a check against a redeployment/fork of the original code. This report is a fresh, independent audit of the deployed bytecode's source — every finding below was independently re-derived by this run's 18 agents (6 breadth + 12 depth) from the source itself, not copied from public historical write-ups. The findings corroborate the well-known history but go beyond it (see Finding 3, a distinct accounting bug not part of the famous 2016 narrative).

Reconciliation summary

  • Overlap: 12 findings identified independently by both phases (near-unanimous on the core reentrancy family — up to 12/12 phase-2 agents on the headline bug).
  • Phase-1-only: 12 findings (re-examined against source below; 1 demoted from Medium to Low on re-read).
  • Phase-2-only: 1 major finding (reward-accounting inflation, independently verified by the orchestrator against source with a concrete numeric trace) + several minor leads.
  • Re-examined leads kept: 12 (all phase-1-only findings confirmed on re-read). Demoted: 1 (transfer/transferFrom silent-false finding downgraded — the deployed DAO contract's own override always throws, so the base Token semantics are dead code in this deployment, not a live risk).
  • Completeness: 25 unique (Contract, function, bug-class) tuples identified across both phases combined; all 25 are represented in the findings below.

Critical

[1] Reentrancy in splitDAO() drains the DAO — the historic June 2016 exploit

Severity: Critical
Origin: [both] — found independently by all 6 phase-1 agents and all 12 phase-2 agents (unanimous corroboration)
Location: splitDAO() DAO.sol:1007-1013
Description: splitDAO() calls withdrawRewardFor(msg.sender) (line 1009), which reaches ManagedAccount.payOut → _recipient.call.value(_amount)() (line 197) before balances[msg.sender], totalSupply, and paidOut[msg.sender] are zeroed (lines 1010-1012):

1007	        // Burn DAO Tokens
1008	        Transfer(msg.sender, 0, balances[msg.sender]);
1009	        withdrawRewardFor(msg.sender); // be nice, and get his rewards
1010	        totalSupply -= balances[msg.sender];
1011	        balances[msg.sender] = 0;
1012	        paidOut[msg.sender] = 0;

Proof of Concept: Attacker votes yes on a split proposal naming itself _newCurator, then calls splitDAO. The first pass creates the child DAO and sends fundsToBeMoved (computed from balances[msg.sender], lines 982-985) via createTokenProxy.value(...) (line 985). Execution then reaches line 1009, triggering attacker.call.value(reward)(); the attacker's fallback re-enters splitDAO with the same proposal ID. All guards (blocked[msg.sender]==proposalID, votedYes, balances[msg.sender] != 0) still pass because state isn't zeroed until line 1011, so fundsToBeMoved is recomputed at full value and another tranche of ether is sent to the attacker's child DAO. Recursion continues until gas/call-depth exhaustion. This is the exact mechanism that drained ~3.6M ETH in June 2016.
Recommendation: Apply checks-effects-interactions — zero balances[msg.sender], totalSupply, paidOut[msg.sender] before any external call:

-        Transfer(msg.sender, 0, balances[msg.sender]);
-        withdrawRewardFor(msg.sender); // be nice, and get his rewards
-        totalSupply -= balances[msg.sender];
-        balances[msg.sender] = 0;
-        paidOut[msg.sender] = 0;
+        uint senderBalance = balances[msg.sender];
+        Transfer(msg.sender, 0, senderBalance);
+        totalSupply -= senderBalance;
+        balances[msg.sender] = 0;
+        paidOut[msg.sender] = 0;
+        withdrawRewardFor(msg.sender); // now safe

Add a reentrancy guard shared across splitDAO, executeProposal, getMyReward, retrieveDAOReward.

[3] withdrawRewardFor() reward formula inflates after any splitDAO() burn — over-claim + permanent DoS for later claimants

Severity: Critical
Origin: [phase2-only] — agent 10 (full numeric proof), agent 11 (independent lead corroboration) — independently re-verified by the orchestrator against source (this is a distinct bug from the reentrancy findings; no reentrancy is required to trigger it)
Location: withdrawRewardFor() DAO.sol:1059-1063; splitDAO() DAO.sol:1009-1010; ManagedAccount DAO.sol:190-203
Description: reward = balanceOf(_account) * rewardAccount.accumulatedInput() / totalSupply - paidOut[_account]. accumulatedInput only ever increases (via ManagedAccount's fallback, accumulatedInput += msg.value, line 191) and is never decremented when payOut sends ether out — confirmed: payOut (lines 194-203) has no accumulatedInput write. Meanwhile totalSupply is permanently reduced every time any holder calls splitDAO() (line 1010). Because the numerator stays fixed while the denominator shrinks, every remaining/future claimant's computed entitlement inflates after each split — with no corresponding increase in rewardAccount's actual ether balance.
Proof of Concept (verified against source, no reentrancy required — pure sequential/benign usage): accumulatedInput = 300, totalSupply = 300, holders C/A/B = 100 tokens each, paidOut = 0 for all, rewardAccount.balance = 300.

  1. C calls getMyReward(): reward = 100·300/300 − 0 = 100. Paid. rewardAccount.balance = 200, paidOut[C] = 100.
  2. A splits via splitDAO: A's own withdrawRewardFor runs with the pre-decrement totalSupply = 300 (fair for A): reward = 100·300/300 − 0 = 100. rewardAccount.balance = 100. Then totalSupply -= 100 → 200.
  3. C calls getMyReward() again: reward = 100·300/200 − 100(paidOut) = 150 − 100 = +50. Paid — C has now extracted 150 total against an original fair share of 100. rewardAccount.balance = 50.
  4. B (never withdrew) calls getMyReward(): reward = 100·300/200 − 0 = 150, but rewardAccount.balance is only 50 — the payOut call's _recipient.call.value(150)() fails (insufficient balance), so withdrawRewardFor throws. B is permanently unable to withdraw any of their 100-wei entitlement while the pool remains short.

This is loss of funds for legitimate token holders (B in the trace above) triggered by entirely benign, non-malicious sequential usage (one holder splitting, others later claiming) — not merely a griefing/DoS edge case.
Recommendation: Compute reward against the reward pot's actual remaining/distributable balance rather than the monotonic accumulatedInput, or rescale all holders' paidOut proportionally whenever totalSupply changes in splitDAO so that reward-per-token is conserved across burns. At minimum, track a separate "distributed so far" counter decremented in step with payOut so total entitlements can never exceed rewardAccount's actual balance.

[7] Division-by-zero in splitDAO() blocks all splits while rewardToken[address(this)] == 0

Severity: High
Origin: [both] — phase-1 (precision-math P-1, governance M-2, dos D-1 — 3 agents); phase-2 (leads from agents 7,8,10; disputed by agent 1)
Location: splitDAO() DAO.sol:994-995
Description: paidOutToBeMoved = DAOpaidOut[address(this)] * rewardTokenToBeMoved / rewardToken[address(this)] divides by rewardToken[address(this)], which starts at 0 and is only incremented by executeProposal() (lines 922-923) after a successful external spend. Until then, every splitDAO() call reverts on division by zero.
Note on compiler semantics: one phase-2 agent disputed whether Solidity reverts on division by zero in this era, suggesting the raw EVM DIV opcode's zero-return behavior might apply. We resolve this in favor of "reverts": Solidity has, since its earliest releases, compiled a runtime check that throws on division/modulo by zero — this is a language-level guarantee distinct from the raw EVM opcode, corroborated independently by 4 of 6 phase-1 agents and by the well-documented behavior of this exact contract generation. Splitting is the DAO's only minority-exit mechanism, so this disables that safety valve for the entire period before any proposal has executed a spend.
Proof of Concept: Fresh DAO, no proposal has yet spent externally → rewardToken[address(this)] == 0. A minority passes a split proposal and calls splitDAO; execution reaches line 994, 0/0, reverts. Every subsequent attempt reverts identically until an unrelated proposal executes a spend.
Recommendation: paidOutToBeMoved = rewardToken[address(this)] == 0 ? 0 : DAOpaidOut[address(this)] * rewardTokenToBeMoved / rewardToken[address(this)];

[8] Curator centralization: unilateral censorship of spending + unilateral quorum reduction

Severity: Medium
Origin: [both] — phase-1 (access-control AC-1/AC-2, governance M-1, dos D-4); phase-2 (lead, agent 11: curator front-run)
Location: changeAllowedRecipients() DAO.sol:1143-1149; whitelist gate in executeProposal() DAO.sol:875-879; halveMinQuorum() DAO.sol:1175-1186
Description: Only curator may whitelist spending recipients, and newProposal rejects any non-split proposal whose recipient isn't whitelisted. A curator can de-whitelist a recipient after a proposal has passed but before execution, forcing executeProposal to abort-and-refund — vetoing an already-passed vote. halveMinQuorum() also lets the curator halve the required quorum every 2 weeks, independent of the 25-week community fallback path.
Proof of Concept: (a) Curator never whitelists any recipient → no spending proposal can be created. (b) Curator lets a proposal reach quorum, then calls changeAllowedRecipients(recipient, false) before execution → the passed vote never executes and the ether is never sent. (c) Curator repeatedly calls halveMinQuorum() to drive quorum toward 0.
Recommendation: Gate whitelist edits and halveMinQuorum behind token-holder votes/timelock; forbid de-whitelisting the recipient of an already-passed, not-yet-executed proposal; require a multisig/timelock for the curator role.

[9] Quorum threshold recomputed from mutable live state at execution time, not snapshotted at proposal creation

Severity: Medium
Origin: [phase1-only] — governance M-3. Re-examined: confirmed on re-read — minQuorum() (DAO.sol:1168-1172) is invoked at execution time (lines 892/897/908) using live totalSupply/actualBalance()/rewardToken[address(this)], while p.yea/p.nay are frozen at vote time. Kept at Medium.
Location: minQuorum() DAO.sol:1168-1172; consumed in executeProposal() DAO.sol:892/897/908
Description: Any split (which reduces totalSupply, line 1010) between voting and execution shifts the passing bar the frozen vote tally is compared against.
Proof of Concept: A large split reduces totalSupply after votes are cast but before a proposal executes. minQuorum(p.amount) at execution now uses the smaller totalSupply, potentially pushing through a proposal that lacked genuine quorum during the debate period (or blocking one that had it).
Recommendation: Snapshot the quorum denominator into the Proposal struct at creation time and use the frozen values at execution.

Overall Assessment

The client's instinct to "focus on reentrancy" is well-founded: this contract's dominant risk is a family of four independent, unguarded checks-effects-interactions violations (splitDAO, withdrawRewardFor/getMyReward, executeProposal, retrieveDAOReward, plus refund), all sharing the same root cause — ManagedAccount.payOut()'s raw _recipient.call.value(_amount)() (DAO.sol:197) hands control to attacker-influenced code before the caller's books are updated. Finding [1] is the exact mechanism that drained ~3.6M ETH from this contract in June 2016 and remains live in the currently deployed bytecode. Beyond reentrancy, this audit also surfaces a previously under-documented, independently exploitable accounting flaw (Finding [3]) where the reward-per-token formula silently inflates after any minority split, causing legitimate late-claiming token holders to be permanently unable to withdraw their fair entitlement — a genuine fund-safety defect distinct from the historical narrative. None of these issues have been patched in the deployed contract; if this address is live and holds funds, it should be treated as immediately exploitable by the same class of attack that occurred in 2016.
