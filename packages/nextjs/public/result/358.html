Findings

[F-1] No timeout or quorum — a single non-voting arbitrator permanently freezes the entire disputed stake

Severity: High
Origin: [both] — Phase 1 (General-1, DoS-1, Governance-3) · Phase 2 (all 12 agents, unanimous)
Location: castVote() (lines 311-367), assignPanel() (lines 261-304), cancelDispute() (lines 414-433)

Description: _resolveDispute only triggers when totalVotes == panel.length — literal unanimous participation — even though the contract's own odd-panel-size rule guarantees a majority becomes mathematically unbeatable before every member votes (e.g., 2-of-3 already settles the outcome). There is no timeout, no owner override, no forceResolve, and no reassignPanel anywhere in the contract. cancelDispute explicitly requires status == Filed, which is permanently unreachable once a panel is assigned. If even one of the 3-7 assigned arbitrators never votes — offline, bribed to abstain, or simply disinterested — the dispute is stuck forever, at zero cost to the withholding arbitrator (they only forfeit an unguaranteed fee) and total, permanent loss of access to the claimant's stake.

Proof of Concept: Claimant files a dispute with 1 ETH stake. Owner assigns a 3-person panel. Two arbitrators vote (already a mathematically decisive 2-0 split). The third is bribed by the losing side to simply never vote — free for the briber, since inaction requires no on-chain transaction and is undetectable in advance. totalVotes remains stuck at 2 forever; _resolveDispute never executes; the 1 ETH is unrecoverable by any party for the life of the contract.

Recommendation:

  uint256 totalVotes = d.votesForClaimant + d.votesForRespondent;
- if (totalVotes == panel.length) {
+ if (d.votesForClaimant > panel.length / 2 || d.votesForRespondent > panel.length / 2) {
      _resolveDispute(disputeId);
  }

Additionally add a voting deadline with a force-resolve/refund fallback for the case where no majority is ever reached.

[F-2] Atomic multi-party payout with no pull-pattern — a single non-payable winner or arbitrator permanently bricks dispute resolution

Severity: High
Origin: [both] — Phase 1 (General-2, DoS-2) · Phase 2 (all 12 agents, unanimous, with several sharpening the attack to a fully claimant-controlled variant)
Location: _resolveDispute() (lines 373-408), invoked synchronously from castVote() (line 365)

Description: _resolveDispute pays the winner and every arbitrator via separate .call{value} transfers in one atomic transaction, each gated by require(ok). If any single one of these panel.length + 1 recipients cannot accept a plain ETH transfer, the entire transaction reverts — including the triggering arbitrator's own vote, which is silently rolled back rather than persisted. This failure is deterministic and permanently repeatable on every subsequent retry. Critically, respondent in fileDispute is never validated to be a registered agent or capable of receiving ETH at all — only the claimant is checked. This means the claimant themselves can unilaterally name a non-payable contract as the respondent when filing, guaranteeing that if the panel ever rules in the respondent's favor, resolution is permanently bricked — no hostile arbitrator or owner cooperation is required.

Proof of Concept: A claimant calls fileDispute(evilContract, "reason", hash) where evilContract has no payable receive()/fallback(). The owner assigns a panel; two of three arbitrators vote ForRespondent in good faith (already a locked-in majority). The third arbitrator's vote completes turnout, triggering _resolveDispute, which attempts evilContract.call{value: payout}("") — this reverts, require(ok) fails, and the entire transaction (including the deciding vote) is undone. Because the majority is already fixed at 2-of-3, every future retry reproduces the identical revert. The stake and all arbitrators' fees are locked in the contract forever.

Recommendation:

+ mapping(address => uint256) public pendingWithdrawals;
  function _resolveDispute(uint256 disputeId) internal {
      ...
-     (bool ok, ) = winner.call{value: payout}("");
-     require(ok, "...winner payout failed");
+     pendingWithdrawals[winner] += payout;
      for (uint256 i = 0; i < panel.length; i++) {
          arbitrators[panel[i]].totalFeesEarned += feePerArbitrator;
-         (bool ok2, ) = panel[i].call{value: feePerArbitrator}("");
-         require(ok2, "...arbitrator fee failed");
+         pendingWithdrawals[panel[i]] += feePerArbitrator;
      }
      ...
  }
+ function withdraw() external nonReentrant {
+     uint256 amount = pendingWithdrawals[msg.sender];
+     pendingWithdrawals[msg.sender] = 0;
+     (bool ok, ) = msg.sender.call{value: amount}("");
+     require(ok, "withdraw failed");
+ }

[F-3] Owner can pack the arbitration panel with itself or colluding addresses to guarantee any outcome and collect the arbitrator fee

Severity: High
Origin: [phase1 only] (AccessControl-1, Governance-1 — 2x corroboration within phase 1) — re-examined against source and confirmed
Location: assignPanel() (lines 261-304)

Description: assignPanel excludes only the two disputing parties — there is no exclusion of owner itself, no anti-collusion or Sybil-resistance check, and no stake-weighting or reputation enforcement despite the docstring's claim that arbitrators are "selected based on Street Cred score." Since panel size is always odd (3-7) and outcome is simple majority, an owner who controls (or colludes with) just 2 of 3 registered-agent addresses on a panel it assigns fully determines the outcome — and collects roughly two-thirds of the 5% arbitrator fee in the process.

Proof of Concept: Owner controls registered agent addresses A and B. Owner assigns panel [A, B, C] where C is an honest, irrelevant third vote. A and B both vote for whichever side the owner favors; _resolveDispute pays that side 95% of the stake and splits the 5% fee among A, B, C — meaning the owner pockets roughly two-thirds of the fee on every dispute it chooses to rig, with the actual merits or evidence hash never factoring into the outcome.

Recommendation: Exclude owner from eligible panel members at minimum (require(panel[i] != owner)). More robustly, replace unilateral owner-selection with verifiable-random selection (e.g., VRF) from the registered-agent pool, and/or require arbitrator staking with slashing for provable collusion.

[F-4] No commit-reveal voting — the deciding "swing" arbitrator is publicly identifiable in advance, enabling targeted bribery

Severity: Medium
Origin: [phase1 only] (Governance-2)
Location: castVote() (lines 311-367), getVote() (line 451), VoteCast event (line 156)

Description: Votes are written to storage and emitted immediately, with no commit/hide phase. Because resolution auto-triggers the instant turnout completes, whichever arbitrator votes last on a panel that has split its earlier votes is publicly identifiable in advance as the guaranteed decision-maker. This turns "bribe a majority of the panel in advance" into the much cheaper "wait for the tally to split, then bribe or coerce just the one remaining voter with certainty of effect."

Recommendation: Use a commit-reveal scheme (arbitrators submit keccak256(vote, salt) during a fixed window, then reveal after the window closes), or at minimum decouple "last vote received" from "instant resolution" by resolving only after a fixed deadline.

[F-5] castVote never re-verifies an arbitrator's registered-agent status at vote/payout time

Severity: Medium
Origin: [both] — Phase 1 (AccessControl-2) · Phase 2 (access-control, execution-trace, asymmetry agents, as corroborating leads)
Location: castVote() (lines 311-367), _resolveDispute() (lines 399-403)

Description: Agent eligibility is checked only once, at assignPanel time. castVote never re-checks it. If an arbitrator is deactivated after panel assignment — e.g., precisely because F-3's collusion is discovered mid-dispute and the registry operator revokes the offending agent's status as a remedial action — that agent can still cast a binding vote and still collects the arbitrator fee at resolution.

Recommendation: Re-check identityRegistry.isAgentActive(msg.sender) inside castVote before accepting the vote, and/or withhold fee payment at resolution time for members whose status is no longer active.

[F-6] Immutable owner is a single point of failure for panel assignment (partially, not fully, mitigated by claimant self-cancel)

Severity: Low
Origin: [phase1 only] (AccessControl-3)
Location: owner (line 99), constructor (line 183), assignPanel() (line 264)

Description: owner is immutable with no rotation mechanism. If the owner key is lost, assignPanel becomes permanently uncallable, and any dispute still in Filed status can never get a panel assigned. This is partially mitigated because cancelDispute is not owner-gated — the claimant can unilaterally reclaim their stake at any time while status remains Filed. However, the respondent has no equivalent self-service escape, and disputes already past Filed are unaffected by owner-key loss (they depend only on the panel already assigned).

Recommendation: Introduce a two-step ownership transfer or governance/multisig-controlled owner, and/or a timeout-based fallback allowing permissionless panel assignment or cancellation if the owner doesn't act within a defined window.

[F-7] Fee-splitting division leaves rounding dust permanently stuck in the contract

Severity: Low
Origin: [both] — Phase 1 (Precision-1, General-3) · Phase 2 (math-precision, numerical-gap agents, as corroborating leads)
Location: _resolveDispute(), line 391

Description: totalFee / panel.length is integer division; since panel size is always odd (3, 5, or 7), the result generally doesn't divide evenly. The remainder (up to panel.length - 1 wei) is never paid to anyone and the contract has no sweep/rescue function — it accumulates permanently in the contract's balance.

Proof of Concept: stakeAmount = 1 ether, panel.length = 3: totalFee = 0.05 ether, feePerArbitrator = 16666666666666666 wei (floor), 3 × feePerArbitrator = 49999999999999998, leaving 2 wei stuck forever.

Recommendation: Have the winner absorb the rounding remainder, or add an owner-only sweep function restricted to provably-unaccounted balance.

Non-Findings (checked, no issue)

  • Ties are structurally impossible: verified by direct code trace in both phases — odd panel size plus mandatory non-abstain voting means votesForClaimant == votesForRespondent can never occur when resolution triggers.
  • No overflow/underflow risk: the fee calculation and payout subtraction cannot realistically overflow or underflow given ETH supply bounds and the fixed 5% fee rate.
  • assignPanel's access control: correctly restricted to onlyOwner with no bypass found; non-panel-member voting and double-voting are both correctly blocked in castVote.
  • Bounded loops: assignPanel's duplicate check and castVote's panel-membership scan are both hard-capped at MAX_PANEL_SIZE = 7 — trivial gas cost, not exploitable as DoS.
