This contract is a job-marketplace escrow: clients post jobs paying in CLAWD (direct), USDC (swapped to CLAWD via Uniswap V3), ETH (wrapped + swapped), or off-chain "CV" credit; an owner-managed worker allowlist accepts and completes jobs; on acceptance, escrowed CLAWD is forwarded once to a treasury address.

Reconciliation summary: Overlap (found independently by both ethskills and pashov phases): 5 · Phase-1-only: 1 escalated finding + long LEAD tail · Phase-2-only: 1 novel finding + 2 leads · Re-examined leads kept: 2, demoted: 0 · Coverage holes closed this pass: 0 (both phases already covered all 23 state-changing entrypoints and all 8 threat-catalog rows).

Findings

[95] 1. Consultation jobs paid on-chain permanently strand their escrow — no code path ever releases it

_createJob / completeConsultation / acceptJob · Confidence: 95 · [both] — found independently by ethskills (general-1, Critical; precision-2, High) and 8 of 12 pashov agents.

Description
_isConsultation(serviceTypeId) (L540-542) hardcodes IDs 1 and 2. _createJob (L544-578) routes these jobs straight to JobStatus.IN_PROGRESS (L565-567), skipping OPEN entirely. acceptJob (L286-304) is the only function in the contract that ever transfers paymentClawd to treasury (L297-301), gated by require(job.status == JobStatus.OPEN || job.status == JobStatus.REASSIGNED) (L289) — a status a consultation job can never legitimately hold. completeConsultation (L351-364), the client's own completion path, only writes status/resultCID/completedAt — zero token calls, zero paymentClaimed/totalLockedClawd writes. Nothing in _validateService (L518-524) or any of postJob/postJobFor/postJobWithUsdc/postJobWithETH restricts consultation service-type IDs to CV-only (off-chain) payment.

Proof of Concept

  1. Owner adds service type 1 as a "consultation" (_isConsultation matches IDs 1/2), priceUsd > 0, status "active".
  2. Client calls postJob(1, 100e18, "please review") — clawdToken.safeTransferFrom pulls 100e18 CLAWD (L205), totalLockedClawd += 100e18 (L554), job created directly IN_PROGRESS (isConsult true at L556).
  3. Client calls completeConsultation(jobId, "ipfs://result") (L351-364) — passes job.client == msg.sender (L354), status == IN_PROGRESS (L355), _isConsultation (L356) — job → COMPLETED. No clawdToken call anywhere in this function.
  4. Every fund-moving function is now unreachable for this job: acceptJob requires OPEN/REASSIGNED (fails, job is COMPLETED); declineJob/cancelJob/adminCancelJob all require OPEN (fail). The 100e18 CLAWD is permanently stuck — totalLockedClawd still counts it (so withdrawStuckTokens can never sweep it as surplus either), but no client- or worker-facing function ever forwards it anywhere. The only escape is an undocumented owner workaround: adminResetJob (valid on COMPLETED, L402-413) forces the job to REASSIGNED, then an unrelated worker calls acceptJob to trigger the transfer — to treasury, never back to the client, and it corrupts a job the client already marked delivered.

Fix

 function completeConsultation(uint256 jobId, string calldata resultCID) external nonReentrant {
     Job storage job = jobs[jobId];
     require(job.id != 0, "!job");
     require(job.client == msg.sender, "!client");
     require(job.status == JobStatus.IN_PROGRESS, "!active");
     require(_isConsultation(job.serviceTypeId), "!consult");
     require(bytes(resultCID).length > 0, "!result");

     job.status = JobStatus.COMPLETED;
     job.resultCID = resultCID;
     job.completedAt = block.timestamp;

+    if (job.paymentClawd > 0 && !job.paymentClaimed) {
+        totalLockedClawd -= job.paymentClawd;
+        job.paymentClaimed = true;
+        clawdToken.safeTransfer(treasury, job.paymentClawd);
+    }

     emit JobCompleted(jobId, msg.sender, resultCID);
 }

Alternative: reject non-CV PaymentMethod for consultation service-type IDs at posting time instead.

[90] 2. adminCancelJob decrements escrow accounting without refunding the client — chainable into withdrawStuckTokens fund extraction

adminCancelJob / withdrawStuckTokens · Confidence: 90 · [both] — found independently by all 12 of 12 pashov agents and by ethskills general-2/precision-1/access-1.

Description
cancelJob (L321-335) and declineJob (L306-319) both pair their totalLockedClawd decrement with clawdToken.safeTransfer(...) back to the client. adminCancelJob (L416-427) is the sole exception: it decrements totalLockedClawd -= job.paymentClawd (L422) with no transfer call anywhere in the function. This fires under the function's own documented intended use ("for cleanup of stuck jobs," L415) — no owner malice required, just two ordinary admin calls performed in sequence.

Proof of Concept

  1. Client posts a job via postJob, escrowing 1,000e18 CLAWD (totalLockedClawd = 1000e18, contract CLAWD balance = 1000e18), job OPEN.
  2. Owner calls adminCancelJob(jobId): require(status == OPEN) passes (L419) → totalLockedClawd -= 1000e18 → 0; status = CANCELLED (L425). No safeTransfer. Contract balance still holds the 1000e18. Client cannot recover it — cancelJob/declineJob both require OPEN (now CANCELLED, revert).
  3. Owner calls withdrawStuckTokens(address(clawdToken), to) (L446-457): require(balance > totalLockedClawd) → 1000e18 > 0 → passes; transfers balance - totalLockedClawd = 1000e18 to to (L452-453) — the client's full un-refunded escrow, indistinguishable on-chain from genuine surplus dust.

Fix

 function adminCancelJob(uint256 jobId) external onlyOwner nonReentrant {
     Job storage job = jobs[jobId];
     require(job.id != 0, "!job");
     require(job.status == JobStatus.OPEN, "!open");

     if (job.paymentClawd > 0) {
         totalLockedClawd -= job.paymentClawd;
+        clawdToken.safeTransfer(job.client, job.paymentClawd);
     }

     job.status = JobStatus.CANCELLED;
     emit JobCancelled(jobId, address(0));
 }

[80] 3. Malicious/compromised owner can drain real CLAWD by pointing swapPath/ethSwapPath at a self-controlled pool

setSwapPath / postJobFor / postJobWithUsdc / _swapETHToClawd / acceptJob · Confidence: 80 · [phase1-only, re-examined and confirmed]

Description
setSwapPath (L435-439) and setEthSwapPath (L441-444) validate only a minimum byte length (>= 43 / >= 23) — never that the path's leading token matches usdcToken/weth, nor that the trailing token is clawdToken. All three swap-bearing posters trust the router's returned amountOut directly as clawdReceived (L222-231, L242-251, L530-537), with no clawdToken.balanceOf check before/after. job.paymentClawd = clawdReceived (L562) feeds totalLockedClawd (L554) and, on acceptJob, is paid out of the contract's real clawdToken balance (L300) — a balance made up of other clients' legitimately escrowed CLAWD, entirely independent of whatever token the manipulated path actually delivered.

Proof of Concept

  1. Owner deploys a throwaway ERC20 and seeds a shallow Uniswap V3 pool (owner controls both sides) such that a small USDC input yields a huge reported output of that token.
  2. Owner calls setSwapPath(usdcToken ++ fee ++ fakeToken) — passes the >= 43 length check; no endpoint-token check exists.
  3. Owner (or an accomplice) calls postJobWithUsdc(serviceTypeId, "x", 0) (minClawdOut=0 permitted, see Finding 4) paying only the cheapest service's priceUsd. The swap executes against the owner's own pool and returns a huge amountOut, accepted unconditionally as clawdReceived.
  4. job.paymentClawd and totalLockedClawd are inflated by this bogus figure. Owner (if not already a worker) calls addWorker(self) then acceptJob(jobId) — clawdToken.safeTransfer(treasury, job.paymentClawd) (L300) executes against the contract's real CLAWD balance, draining CLAWD escrowed by other, unrelated jobs to treasury (itself owner-controlled via setTreasury, L429).
  5. Bounded only by the contract's actual CLAWD balance at the time — i.e., the entire pool of currently-escrowed client funds, not merely protocol-owned surplus.

Fix: validate that newPath's leading 20 bytes match the expected input token and its trailing 20 bytes match address(clawdToken) in both setters; additionally measure clawdToken.balanceOf(address(this)) before/after each swap and use the observed delta (not the router's return value) as clawdReceived.

[70] 4. postJobFor/postJobWithUsdc allow minClawdOut = 0, enabling swap-sandwich value extraction

postJobFor / postJobWithUsdc · Confidence: 85 · [both] — found by 8 of 12 pashov agents and by ethskills general-5/precision-3/amm-2.

Description
postJobWithETH requires minClawdOut > 0 (L260); postJobFor (L214-232) and postJobWithUsdc (L235-252) accept minClawdOut = 0, passed straight to exactInput's amountOutMinimum (L227, L247). A sandwiched swap can drive clawdReceived toward zero while the client still pays the full priceUsd in USDC. declineJob/cancelJob always refund in CLAWD, not the original USDC, so value lost to a sandwich is permanently unrecoverable to the client.

Proof of Concept: Caller invokes postJobWithUsdc(serviceTypeId, "desc", 0). An MEV searcher sandwiches the exactInput call against the USDC→WETH→CLAWD pool (0.05%/1% tiers per constructor L145-148), minimizing clawdReceived; the swap still succeeds since 0 always satisfies the floor. The resulting job shows the full priceUsd but escrows near-zero CLAWD.

Fix

 function postJobWithUsdc(uint256 serviceTypeId, string calldata description, uint256 minClawdOut) external nonReentrant {
     (uint256 priceUsd, ) = _validateService(serviceTypeId);
     require(bytes(description).length > 0, "!desc");
+    require(minClawdOut > 0, "!minOut");

Same change in postJobFor.

[75] 5. completeJob/logWork don't verify the caller is the job's assigned worker

completeJob / logWork · Confidence: 88 · [both] — found independently by ethskills general-3 and 7 of 12 pashov agents.

Description
acceptJob (L292) is the only place job.worker is bound to a specific address. completeJob (L337-348) and logWork (L366-377) are gated only by generic onlyWorker allowlist membership (L111-118) plus status == IN_PROGRESS — neither checks job.worker == msg.sender.

Proof of Concept

  1. Worker A calls acceptJob(jobId) — job.worker = A, escrow already released to treasury.
  2. Worker B (any other allowlisted, unrelated address) calls completeJob(jobId, "ipfs://garbage") — require(job.id != 0) and require(status == IN_PROGRESS) both pass; no check against job.worker. Job forced to COMPLETED with B's arbitrary resultCID; A's subsequent legitimate completeJob call reverts (!active).
  3. Identical gap in logWork lets B inject fabricated progress notes into A's active job. Given the contract's own "no disputes" design, this is unrecoverable except via owner's adminResetJob.

Fix

 function completeJob(uint256 jobId, string calldata resultCID) external nonReentrant onlyWorker {
     Job storage job = jobs[jobId];
     require(job.id != 0, "!job");
+    require(job.worker == msg.sender, "!assigned");
     require(job.status == JobStatus.IN_PROGRESS, "!active");

Same addition in logWork.

[65] 6. postJobFor lets any caller assign an arbitrary client, with concrete fund-recoverability loss for consultation jobs

postJobFor · Confidence: 70 · [both] — ethskills escalated to Medium (access-2/general-6); pashov agents raised it as a corroborated LEAD across nearly all 12 without finding a third-party fund-extraction path.

Description
postJobFor(address client, ...) (L214-232) only checks client != address(0) (L215) — any caller can name an arbitrary client while paying the USDC themselves. That address becomes job.client, gaining exclusive cancelJob/completeConsultation rights. The NatSpec (L209-213) states this is meant to be called only by a trusted x402 relayer server, but nothing on-chain enforces it. Combined with Finding 1: if the caller targets a consultation service-type ID, the named "client" is now the only address that can ever call completeConsultation — and doing so still permanently strands the escrow per Finding 1, with the payer (not the named client) having no recourse at all.

Proof of Concept: Any EOA calls postJobFor(victim, serviceTypeId, "desc", 0), paying USDC from its own wallet. jobs[jobId].client == victim is created without victim's involvement or consent — usable for job-history spam/griefing (visible via getJobsByClient(victim)), and for consultation-type IDs, strands the caller's own payment with the victim as the only address that could ever (uselessly, per Finding 1) call completeConsultation.

Fix: gate postJobFor to an explicit onlyRelayer/allowlisted-caller check rather than relying on an undocumented off-chain trust assumption, or require client == msg.sender absent such a role.

[55] 7. postJob/postJobCustom never validate clawdAmount against the service's priceUsd

postJob / postJobCustom · Confidence: 60 · [phase2-only, re-examined and confirmed]

Description
postJob (L200-207) only enforces clawdAmount >= 1e18 (L203), with no check against _validateService's returned priceUsd. postJobCustom (L276-282) doesn't call _validateService at all and accepts a fully caller-chosen customPriceUsd independent of clawdAmount. Contrast with postJobFor/postJobWithUsdc, which pull exactly priceUsd in USDC. Not a theft vector — declineJob/cancelJob refund exactly what was paid — but a business-logic gap: a direct-contract caller (bypassing the frontend, which the NatSpec at L199 says computes clawdAmount off-chain "from USD price at market rate") can post a job for an expensive service while escrowing only the 1-token floor, relying entirely on a worker manually noticing and declining.

Proof of Concept: postJob(expensiveServiceId, 1e18, "desc") succeeds regardless of serviceTypes[expensiveServiceId].priceUsd, creating a job whose displayed priceUsd is unrelated to its actual paymentClawd.

Fix: enforce an on-chain price relationship in postJob (e.g., a stored CLAWD/USD rate with a tolerance band), or compute clawdAmount on-chain from priceUsd the way the USDC/ETH paths do.

[60] 8. Escrow is released irrevocably on acceptJob (a worker action), with no client-recovery path once a job is IN_PROGRESS

acceptJob / cancelJob / adminCancelJob / adminResetJob · Confidence: 65 · [phase1-only, re-examined and confirmed]

Description
Any allowlisted worker can call acceptJob, which unconditionally forwards the full escrowed CLAWD to treasury (L300) the moment the job transitions to IN_PROGRESS — before any work is delivered or verified. Once IN_PROGRESS, no path refunds the client: cancelJob/adminCancelJob both require OPEN (L325, L419); adminResetJob (the only owner tool for IN_PROGRESS jobs, L402-413) reassigns the job but never touches funds. A worker who accepts and simply never calls completeJob grieves the client indefinitely with only owner-mediated adminResetJob as (partial, non-refunding) recourse.

Proof of Concept: Client posts a job, escrow held. A worker calls acceptJob — full escrow instantly forwarded to treasury. Worker never calls completeJob. Client has no cancelJob (status no longer OPEN). Only remedy is owner's adminResetJob, which reassigns for free rework rather than refunding the client.

Fix: consider releasing escrow on completeJob rather than acceptJob, or add a client/timeout-triggered reclaim path for jobs stuck IN_PROGRESS beyond a reasonable window.

Leads

Corroborated code smells with partial paths; plausible but not independently confirmed as standalone exploitable findings. Confidence < 50 or contingent on unverified external facts.

  • setEthSwapPath validates only >= 23 bytes vs. the true minimum valid single-hop path of 43 bytes (swapPath's check correctly uses >=43) — [both]. An owner-set malformed ethSwapPath between 23-42 bytes would brick postJobWithETH/_swapETHToClawd (self-inflicted DoS on the ETH payment path). Fix: align to >= 43.
  • No deadline parameter on any exactInput call — [phase1-only] (amm-3). ISwapRouter02.ExactInputParams as declared here has no deadline field; combined with two-of-three paths permitting minClawdOut=0 (Finding 4), a delayed/held transaction has no on-chain expiry protection.
  • Fee-on-transfer/rebasing CLAWD assumption — [both]. Nominal transfer amounts (clawdAmount, priceUsd) are trusted without balance-delta checks throughout; contingent on CLAWD's actual token implementation, which is out of this file's scope. The contract's own header comment claims "no fees," reducing likelihood.
  • Blacklist-token DoS on refund paths — [both]. declineJob/cancelJob's unconditional safeTransfer to job.client/msg.sender would revert and strand that one job if CLAWD ever supported blocklisting a specific address. Not verifiable against CLAWD's actual implementation.
  • Price front-run against infinite-approval clients — [phase2-only]. Owner could front-run a pending postJobFor/postJobWithUsdc tx with updateServiceType to spike priceUsd, pulling more USDC than a client (who granted a large/unlimited allowance) expected. Standard admin-key trust risk; not independently verified against actual frontend approval patterns.
  • Unbounded jobs growth via free postJobWithCV — [both]. postJobWithCV requires no on-chain payment; combined with unbounded linear scans in getJobsByClient/getJobsByStatus/getOpenJobs (no pagination), cheap spam could eventually make these views revert for all callers.
  • cvDivisor validated/stored but never used in on-chain computation; postJobWithCV's cvAmount is unrelated caller input — [both]. No on-chain funds move for CV jobs, so this is informational.
  • Zero job-id sentinel collision — [phase2-only]. nextJobId = _startJobId (L143) has no require(_startJobId > 0); every existence check uses id != 0 as the "doesn't exist" sentinel. Mitigated in the current deployment — DeployLeftClawServicesV2.s.sol hardcodes a non-zero currentNextJobId. Deploy-time footgun, not attacker-triggerable.
  • totalLockedClawd never reconciled against actual balanceOf — [phase1-only]. A static counter with no periodic re-sync; would drift permanently if CLAWD were ever rebasing.
  • IWETH9.approve return value unchecked in _swapETHToClawd — [both]. Deviates from the SafeERC20/forceApprove discipline used everywhere else; low risk in practice since canonical WETH9 always returns true.
  • Unbounded O(n) scans over workers[] — [both]. onlyWorker, addWorker's dup-check, removeWorker, isWorker are all linear; owner-only mutation bounds the practical risk.
  • Single-step Ownable (not Ownable2Step) — [phase1-only]. A mistaken transferOwnership call permanently locks out all admin functions, including worker onboarding and fund rescue.
  • No timelock on treasury/setSwapPath/setEthSwapPath — [phase1-only]. All take effect immediately with no user reaction window.
  • postJobCustom bypasses all service-type pause gating — [phase1-only]. It skips _validateService entirely (hardcodes serviceTypeId = 0), so it remains callable even if every registered service type is paused — no contract-wide circuit breaker exists.
  • renounceOwnership not overridden/disabled — [phase1-only]. Standard OZ Ownable footgun; would permanently disable all admin functions if ever called.
  • withdrawETH's raw .call has no return-data-bomb protection — [phase1-only]. Owner-only trigger; self-inflicted at worst.
  • nonReentrant not the first modifier on 4 owner-only functions — [phase1-only]. Non-exploitable — onlyOwner has no external-call surface.
