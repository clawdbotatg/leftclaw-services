[95] 1. claimHourBlock has no state guard — bypasses freeze() and erases the FROZEN flag

EscrowVault.claimHourBlock · Confidence: 95 · [both] — unanimous 12/12 Phase-2 agents (blind), corroborated by 2/5 Phase-1 agents (general, access-control)

Description
Every other release path (releaseMilestone L143-146, streamRelease L161-165, releaseRemainingToWorker L235-238) requires e.state == LOCKED || PARTIAL_RELEASE; claimHourBlock (L184-186) checks only e.mode and a balance bound, so it remains callable — and pays the worker — after arbitrationModule.freeze() has set state = FROZEN. Worse, _releaseToWorker (L272-283) unconditionally overwrites .state to PARTIAL_RELEASE/RELEASED based purely on running totals, so a single post-freeze hour-block claim doesn't just leak funds during a dispute — it silently clobbers the FROZEN flag itself, which then makes refund/split (both require(state==FROZEN), L202/L220) revert until arbitration re-freezes. Concrete trace: task 7, HOUR_BLOCKS, hourBlockSize=100e6, totalDeposited=1000e6. claimHourBlock(7) ×2 → totalReleased=200e6, state PARTIAL_RELEASE. arbitrationModule.freeze(7) → state FROZEN. taskRegistry.claimHourBlock(7) again: 200e6+100e6<=1000e6 passes (no state check exists to fail), pays worker another 100e6 and resets state to PARTIAL_RELEASE. Arbitration's refund/split now revert until re-frozen — funds already left, and the freeze's entire purpose is defeated for this mode.

Fix

 function claimHourBlock(uint256 taskId) external nonReentrant onlyRegistry {
     EscrowRecord storage e = escrows[taskId];
     require(e.mode == EscrowMode.HOUR_BLOCKS, "EscrowVault: not hour blocks");
+    require(e.state == EscrowState.LOCKED || e.state == EscrowState.PARTIAL_RELEASE, "EscrowVault: not locked");
     uint256 amount = e.hourBlockSize;
     require(e.totalReleased + amount <= e.totalDeposited, "EscrowVault: insufficient");
     e.hoursClaimed += 1;
     _releaseToWorker(e, amount);
 }

[90] 2. Deposit accounting credits the nominal amount, not a measured balance delta — shared per-token pool lets one task's shortfall permanently strand another task's real deposit

EscrowVault._applyDeposit / depositFor / _payOrDefer · Confidence: 90 · [both] — 8/12 Phase-2 agents (math-precision, economic-security, execution-trace, boundary, flow-gap, invariant, first-principles, asymmetry) as full findings, corroborated by 2/5 Phase-1 agents (general, erc20)

Description
_applyDeposit (L128, e.totalDeposited += amount) credits the caller-supplied amount parameter rather than measuring the vault's actual balanceOf before/after safeTransferFrom (L119). token is chosen per-task via configureTask (L102) with no allowlist, and all tasks sharing the same token draw against one contract-wide balance — there is no per-task segregation and no balanceOf reconciliation anywhere in the contract. For a fee-on-transfer or deflationary token, nominal totalDeposited overstates real holdings; whichever task releases first against the shared pool drains real tokens actually owed to a different task using the same token. Concrete trace: token X charges a 2% transfer fee. depositFor(1, 1000) → vault receives 980, totalDeposited[1]=1000. depositFor(2, 1000) (same token) → vault receives another 980, totalDeposited[2]=1000. Real balance = 1960; nominal sum = 2000. releaseRemainingToWorker(1) succeeds, draining 1000 (real balance now 960). releaseRemainingToWorker(2) sets totalReleased[2]=1000 internally (passes the amount<=remaining guard, which is purely accounting-based) but the actual _payOrDefer transfer of 1000 fails (only 960 held) and defers into pendingPayouts[X][worker2] — a credit claimPayout's reverting safeTransfer (L290) can never honor, since the pool never recovers the shortfall.

Fix

[85] 3. configureTask re-callable while UNFUNDED leaves stale, independently claimable milestoneAmounts on array shrink

EscrowVault.configureTask / releaseMilestone · Confidence: 80 · [both] — 5/12 Phase-2 agents (economic-security, boundary, numerical-gap, first-principles, invariant) as full findings with matching numeric proofs, corroborated by 1/5 Phase-1 agent (general, rated Low as a Lead)

Description
configureTask is guarded only by state==UNFUNDED (L101) and never writes state itself, so it is re-callable any number of times before the first deposit. The MILESTONE-mode loop (L108-112) only overwrites indices 0..newLen-1 of the new array; it never clears higher indices left by a prior, longer configuration. Once funded, releaseMilestone never bounds milestoneIndex against a "current" count (none is stored) — only against milestoneReleased/amount>0/the generic remaining-balance check. Five independent Phase-2 agents, each blind to the others, reproduced the identical exploit trace: configureTask(1, ..., MILESTONE, [50e6,100e6,100e6], ...) → configureTask(1, ..., MILESTONE, [50e6], ...) (still UNFUNDED, only index 0 overwritten) → depositFor(1, 250e6) → releaseMilestone(1,0) pays 50e6, releaseMilestone(1,1) pays the stale 100e6, releaseMilestone(1,2) pays the stale 100e6 — 250e6 released against a plan whose only current milestone was 50e6. This consistency across five independently-run agents, several framing the reconfiguration as an ordinary "poster edits the milestone plan before funding" flow rather than a contrived edge case, raises confidence enough to promote this from Phase-1's Low/Lead rating to a Medium finding.

Fix

 function configureTask(

 ) external onlyRegistry {

     e.streamRatePerSecond = streamRate; e.hourBlockSize = hourBlockSize;
     if (mode == EscrowMode.MILESTONE) {
+        uint256 prevLen = milestoneCount[taskId];

         }
+        for (uint256 i = milestones.length; i < prevLen; i++) {

[80] 4. rotateArbitrationModule requires cooperation from the very module it exists to replace — a compromised or uncooperative module can never be removed

EscrowVault.rotateArbitrationModule · Confidence: 80 · [phase1: dos, general, access-control] — 3 independent Phase-1 agents converged on this; not raised by Phase-2 (which focused elsewhere), no contradiction found on re-examination

Description
The only path to change arbitrationModule after the initial one-shot setArbitrationModule requires two external view calls into the current (outgoing) module: current.disputeOpeningPaused() (L69) and current.activeDisputeCount()==0 (L70). There is no owner override bypassing this. A malicious or simply broken current module can make either call return false or revert forever, permanently blocking rotation — while retaining unconditional freeze() power (no state guard) and arbitrary-recipient refund/split power (Finding 6) over every task. Trace: arbitrationModule = M becomes compromised. M.freeze(taskId) on every active task. M never calls refund/split. Owner calls rotateArbitrationModule(newModule) — reverts at L69 forever since M.disputeOpeningPaused() is attacker-controlled. No other function can change arbitrationModule. Every frozen task's remaining escrow is permanently stuck.

Fix

+uint256 public rotationRequestedAt;
+address public pendingArbitrationModule;
+uint256 public constant ROTATION_DELAY = 14 days;
+
+function requestArbitrationRotation(address _new) external onlyOwner {
+    require(_new != address(0), "zero");
+    pendingArbitrationModule = _new;
+    rotationRequestedAt = block.timestamp;
+}
+function finalizeArbitrationRotation() external onlyOwner {
+    require(pendingArbitrationModule != address(0), "none pending");
+    require(block.timestamp >= rotationRequestedAt + ROTATION_DELAY, "too soon");
+    arbitrationModule = pendingArbitrationModule;
+    pendingArbitrationModule = address(0);
+}

[75] 5. _payOrDefer can double-credit a recipient when a token returns false despite actually completing the transfer

EscrowVault._payOrDefer · Confidence: 75 · [phase1: erc20] — single-agent finding on re-examination; the underlying decode-logic gap is unconditionally verifiable by inspection

Description
The decode tree (L299-303) treats a false boolean return as proof no tokens moved, crediting pendingPayouts on that basis. This fails for tokens (documented in the weird-ERC20 corpus, e.g. Tether Gold-style behavior) that perform the transfer correctly but unconditionally return false. For such a token, the raw .call genuinely moves amount tokens to recipient, but because the returned bool is false, the function also records a pendingPayouts credit for the same amount — which the recipient can then claim a second time via claimPayout, funded out of other tasks' pooled balance of that token. On re-examination this mechanism is fully concrete and requires no assumption about taskRegistry — only that the token exhibiting this behavior be selected for a task, which configureTask's lack of an allowlist permits.

Fix

         abi.encodeCall(IERC20.transfer, (recipient, amount))
     );
+    bool balOk = IERC20(token).balanceOf(address(this)) == balBefore - amount;
     if (
         !ok ||
         (data.length != 0 && data.length != 32) ||
-        (data.length == 32 && !abi.decode(data, (bool)))
+        (data.length == 32 && !abi.decode(data, (bool))) ||
+        !balOk

[65] 7. streamRelease accrual anchor is not reset on top-up deposits — later deposits can vest instantly

EscrowVault.streamRelease / _applyDeposit · Confidence: 65 · [both] — 1/12 Phase-2 agent (asymmetry) full finding + 1 corroborating lead (trust-gap), matches 1/5 Phase-1 agent (precision-math)

Description
e.streamStart is set once, on the first deposit only (L130-132), and never updated by later top-ups. owed = elapsed * streamRatePerSecond (L167-168) is computed from that fixed anchor and capped at the current totalDeposited. A deposit added after significant time has already elapsed can become instantly, fully releasable, defeating the time-based vesting the mode exists to enforce (and the dispute/freeze window it's meant to give the poster). [55] 9. _payOrDefer's unbounded returndata copy is a gas-griefing vector on every payout path
