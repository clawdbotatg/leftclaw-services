Findings

[95] 1. Signature replay across contract instances — missing domain separator in mint-authorization digest

ForgerToken.createNewTokensFromOwnerSignature · Confidence: 95 · CONFIRMED — live-exploitable on this exact target

Description
The owner-authorized mint function verifies a signature over digest = keccak256(abi.encode(to, amount, salt, deadline)), which contains no address(this), no block.chainid, and no EIP-712 domain separator — any valid owner-signed mint authorization is therefore valid on every deployment of this bytecode that shares the same owner key (the constructor hardcodes owner = 0xC9caF9E17BBB4E4d27810D97D2c2A467A701e0D5 as a literal rather than deriving it from msg.sender, so every clone of this contract shares the same owner automatically), since the per-contract signatureUsed mapping starts empty on every fresh deployment and never sees the replayed hash.

This was not left as a theoretical concern: a previously-broadcast, successfully-executed authorization was found reused identically across three independent "ForgerToken" clones on Sepolia, and the exact same calldata was replayed via a read-only eth_call against this specific audit target (which has totalSupply() == 0 and has never redeemed this signature) — the call returned cleanly with no revert, confirming that broadcasting this known, already-public transaction today would mint 100 FT to 0x1D96F2f6BeF1202E4Ce1Ff6Dad0c2CB002861d3e with zero further action from the real key holder.

signature = 0xf73465952465d0595f1042ccf549a9726db4479af99c27fcf826cd59c3ea7809402f4f4be134566025f4db9d4889f73ecb535672730bb98833dafb48cc0825fb1c
to        = 0x1D96F2f6BeF1202E4Ce1Ff6Dad0c2CB002861d3e
amount    = 100000000000000000000  (100e18)
salt      = 0x044852b2a670ade5407e78fb2863c51de9fcb96542a07186fe3aeda6bb8a116d

Confirmed successfully redeemed (status: "ok") on clones 0xC3826373725fC9155c3b5Ab719dabDADd0e4981E, 0x401C1Bc43f0d2357017843e283Ae851795144947, 0x67ea6E6e014bB5597408Be85DAbfcBE2Ea98212F, and confirmed still valid (clean eth_call, no revert) against 0xFe5B2D39A7DDd8f93b2a6B7BE7588E0B12507A4d itself.

Fix

- bytes32 digest = keccak256(abi.encode(to, amount, salt, deadline));
+ bytes32 digest = keccak256(abi.encode(address(this), block.chainid, to, amount, salt, deadline));

(Ideally replace with a full EIP-712 domain separator + typed struct hash, which simultaneously fixes Finding 3 below.)

[62] 2. Replay protection keyed by signature bytes instead of message digest

ForgerToken.createNewTokensFromOwnerSignature / invalidateSignature · Confidence: 62

Description
signatureUsed is keyed by keccak256(signature) (the raw ECDSA bytes) rather than by the signed digest. ECDSA signing is only unique-per-message if the signer uses deterministic (RFC 6979) nonces; if the owner's off-chain signing process ever produces two distinct valid signatures for the same logical (to, amount, salt, deadline) authorization (non-deterministic-k signer, retried signing request), both are independently redeemable, and invalidateSignature can only revoke a signature the owner physically possesses, not the underlying intent. No on-chain evidence of this occurring was found — all observed signatures for a given tuple were byte-identical across clones, consistent with deterministic signing — so this is reported as a design weakness (demoted per gate: requires an off-chain signer behavior outside normal, attacker-uncontrolled operation) rather than a proven live exploit.

Fix

- if (signatureUsed[sigHash]) revert SignatureUsed();
- bytes32 digest = keccak256(abi.encode(to, amount, salt, deadline));
+ bytes32 digest = keccak256(abi.encode(address(this), block.chainid, to, amount, salt, deadline));
+ if (signatureUsed[digest]) revert SignatureUsed();
  ...
- signatureUsed[sigHash] = true;
+ signatureUsed[digest] = true;

Disclosed Design / Centralization Risks (not scored as exploits — admin-privileges-by-design, no unprivileged amplifier)

  • Unbounded, uncapped owner-signature minting — createNewTokensFromOwnerSignature has no supply cap, no per-period limit, no timelock, and no multisig; a single EOA signature can mint arbitrary amounts. This is the evident intended function of the contract (an owner-gated mint mechanism), not a code defect, but should be disclosed to anyone treating this token as having a fixed or predictable supply.
  • Owner is a hardcoded literal, not the deployer, with no rotation mechanism — owner = 0xC9caF9E17BBB4E4d27810D97D2c2A467A701e0D5 is set once in the constructor and can never be changed (no transferOwnership/renounceOwnership exists anywhere). A deployer of this bytecode gains no control over "their" token; the fixed key permanently and irrecoverably controls all minting, and loss of that key permanently freezes the mint pathway.
  • Raw-digest signing, no EIP-191/EIP-712 structuring — ecrecover is called directly on a bare abi.encode digest with no personal-sign prefix and no typed-data structure, meaning the owner must sign opaque hex with non-standard tooling rather than a wallet's normal display-and-confirm flow. Fixed jointly with Finding 1 by adopting EIP-712.
  • invalidateSignature requires the exact signature bytes — the owner can only pre-emptively revoke a leaked authorization if they possess the literal signed blob, not just its parameters (salt/to/amount/deadline). Limits incident-response usefulness. Fixed jointly with Finding 2 by keying on the digest.
