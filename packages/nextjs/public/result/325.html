Detailed Findings

[1] Blacklist/deny-list tokens can permanently freeze funds

Severity: High
Location: every safeTransfer call site — vote() L123, cancelVote() L148, claimNonWinningFunds() L166, claimWinningOptionsFunds() L180
Origin: [phase1: erc20]

FundablePollFactory.deployPoll() accepts any votingToken with nonzero code — no allowlist. USDC/USDT-style tokens let their issuer blocklist individual addresses; any blocked address can never again be the recipient of a transfer from this contract.

Proof of Concept: Three voters back a losing option with 100 tokens each (_totalOutstandingFunds = 300, contract balance = 300). Two claim normally. The third is later blocklisted by the token issuer (unrelated to this protocol). Their claimNonWinningFunds() call reaches safeTransfer(thirdVoter, 100), which reverts every time because USDC's transfer reverts for blocklisted recipients. Their 100 tokens are permanently stuck — no retry, no reroute. Worse: if the pollCreator itself is blocklisted, claimWinningOptionsFunds() never succeeds and the entire winning pot (totalWinningFunds) is frozen forever, since winningFundsClaimed never becomes claimable by anyone else.

Recommendation: Maintain a factory-level allowlist of vetted, non-blocklisting tokens, and/or let an affected party register an alternate payout address they control before claiming.

[2] Sole/first staker can sweep pre-existing balance surplus (donations, dust) via the exact-match payout branch

Severity: Medium
Location: _calculatePayout() L278-286, exploited via cancelVote() L136-151
Origin: [phase1: flashloans, FL-2] — not independently found by any of the 12 phase-2 agents, but the underlying mechanism (_calculatePayout's exact-match branch sweeping the full live balance) was flagged as a code smell by 4 of them (access-control, first-principles, numerical-gap, trust-gap), each of whom modeled only the "attacker donates to themselves" variant and concluded (correctly, for that variant) it's unprofitable. None modeled the third-party-donor variant. Re-examined directly against source for this report; confirmed exploitable.

function _calculatePayout(uint256 liabilityAmount) internal view returns (uint256) {
    uint256 totalOutstandingFunds = _totalOutstandingFunds;
    if (liabilityAmount == 0 || totalOutstandingFunds == 0) return 0;
    uint256 currentBalance = IERC20Minimal(votingToken).safeBalanceOf(address(this));
    if (liabilityAmount == totalOutstandingFunds) return currentBalance;   // <-- sweeps the FULL live balance
    return (liabilityAmount * currentBalance) / totalOutstandingFunds;
}

Proof of Concept:

  1. A fresh poll is deployed. Balance = 0, _totalOutstandingFunds = 0.
  2. Any third party (a sponsor pre-funding the poll to attract voters — plausible given the platform is literally named "Fundable Polls" — or simply a mistaken/well-meaning transfer) sends D tokens directly to the poll contract via a plain transfer, bypassing vote(). Now balance = D, _totalOutstandingFunds still 0 (unaccounted).
  3. An attacker calls vote(x) with exactly tokensPerVote = p (their own capital, or borrowed via flash loan since it's returned before the transaction ends). balanceBefore = D, transferFrom pulls p, balanceAfter = D + p, receivedAmount = p. State: _voterStakeByWallet[attacker] = p, _totalOutstandingFunds = p.
  4. In the same transaction (or any later block while the poll is still active), the attacker calls cancelVote(). stakeAmount = p. _calculatePayout(p): since _totalOutstandingFunds == p (attacker is the only outstanding claim), the exact-match branch fires and returns the entire current balance, D + p.
  5. Attacker receives D + p, repays any borrowed p, and nets D — the third party's entire donation — using zero permanent capital.

This is not a rounding/dust artifact bounded to <1 wei — it captures the full surplus. If other real voters have already staked before the attacker acts, the attacker only captures their pro-rata slice of the surplus (bounded by their fraction of _totalOutstandingFunds, extractable up to ~100% by splitting the flash-loaned capital across many wallets, per the phase-1 N-wallet analysis), so the maximum loss is capped at whatever surplus (currentBalance - _totalOutstandingFunds) exists at attack time — never touches other voters' own principal in a token with no fee/rebase behavior. Severity is capped at Medium because impact is bounded to the surplus amount, not the full pool, and requires a surplus to exist in the first place (a poll with no donations and a well-behaved token never diverges from balance == outstanding).

Recommendation: Refund cancelVote() (and non-winning claims) at the flat recorded stake (_voterStakeByWallet[msg.sender]) rather than pro-rata against live balance, decoupling refunds from incidental balance changes:

- uint256 payoutAmount = _calculatePayout(stakeAmount);
+ uint256 payoutAmount = stakeAmount; // or min(stakeAmount, currentBalance) for insolvency safety

If pro-rata against live balance is intentional (to gracefully share fee-on-transfer/rebase losses), instead cap the exact-match branch so it can never exceed the sum of legitimately-outstanding liabilities, and route any true surplus to a separate, explicitly-claimable sweep (e.g. by the poll creator) rather than to whoever happens to claim in a favorable order.

[3] Transfer-pausable tokens cause full DoS of votes/cancels/claims

Severity: Medium
Location: all safeTransfer/safeTransferFrom/safeBalanceOf call sites
Origin: [phase1: erc20 E-2, dos D-2] [phase2: economic-security "dependency-freeze"]

USDC/USDT-class issuers can pause all transfers. While paused, every vote/cancel/claim path reverts for every participant simultaneously (not selective — this affects the whole poll, unlike finding #1's targeted blacklist). If the pause is permanent (deprecated token), funds are locked indefinitely with no on-chain escape hatch.

Recommendation: Same as #1 — allowlist vetted tokens; document pause risk to poll creators and voters.

[4] Arbitrary/creator-controlled mintable-burnable token can dilute or drain the pool

Severity: Medium
Location: constructor votingToken_.code.length == 0 check (L103); _calculatePayout()'s live-balance read (L282)
Origin: [phase1: erc20 E-3, general G-3] [phase2: access-control "malicious-voting-token", boundary "trusted-external-balanceof", trust-gap "live-balance-payout-sensitivity"]

The only token vetting is "has code." A poll creator can deploy a poll backed by a token they fully control. Because every payout reads the token's live balanceOf, the creator can burn the poll's balance after voters have staked (or before real claims), causing every subsequent pro-rata payout to round toward zero — a self-serve rug on their own voters, since the creator's off-chain gain (e.g. accepting deposits, promoting the token) is independent of the poll's on-chain payout math.

Proof of Concept: Creator deploys EvilToken (self-mintable/burnable), opens a poll, voters stake. After endTime, before any claims, creator calls EvilToken.burn(pollAddress, almost_all_balance). currentBalance ≈ 0; every claimNonWinningFunds()/claimWinningOptionsFunds() now pays ≈0 regardless of recorded stake.

Recommendation: Curate a token allowlist at the factory level; prominently disclose the creator-chosen token to voters before they stake.

[5] Immutable pollCreator has no recovery path

Severity: Low
Location: pollCreator (L57), claimWinningOptionsFunds() (L171-183)
Origin: [phase1: access-control AC-3]

pollCreator is immutable and the only address permitted to call claimWinningOptionsFunds(). If that key is lost or compromised after the poll ends, totalWinningFunds becomes permanently unclaimable by anyone — not stealable by a third party, just stranded.

Recommendation: Accept as a documented trade-off of the fully-immutable, no-admin design, or let the creator nominate a beneficiary/successor address at deploy time.

[6] _optionFunds goes stale after non-winning claims

Severity: Low
Location: claimNonWinningFunds() (L153-169) vs cancelVote() (L136-151)
Origin: [phase1: general G-1] [phase2: execution-trace, invariant, periphery, asymmetry (x2 angles), boundary, flow-gap — 7 of 12 agents independently converged]

cancelVote() decrements _optionFunds[optionNumber-1]; claimNonWinningFunds() does not, even though it clears the same voter's stake. Verified across both phases: _optionFunds is read only once, inside _finalizeIfNeeded() (guarded by the finalized flag, so it never runs again after claims begin), and by the currentVotingResults() view. There is no payout-path consumption of the stale value — confirmed no fund-accounting impact — but currentVotingResults() reports misleading (higher-than-actual) per-option totals once claims start.

Recommendation:

  _voterOptionByWallet[msg.sender] = 0;
  _voterStakeByWallet[msg.sender] = 0;
+ _optionFunds[optionNumber - 1] -= stakeAmount;
  _totalOutstandingFunds -= stakeAmount;

Or document that currentVotingResults() is only meaningful pre-finalization.

[7] ERC777/hook tokens let a wallet exceed the intended tokensPerVote weight

Severity: Low
Location: vote() L122-131
Origin: [phase1: erc20 E-4] [phase2: periphery "callback-token-overstake"]

Reentrancy itself is fully blocked (nonReentrant + checks-effects-interactions), so this is not a fund-theft vector. But an ERC777-style tokensToSend hook fired during transferFrom could push additional tokens into the poll (from the voter's own balance) before balanceAfter is read, inflating receivedAmount beyond tokensPerVote and giving one wallet outsized voting weight — self-funded, not theft, but breaks the "one wallet, fixed weight" assumption.

Recommendation: Credit min(receivedAmount, tokensPerVote), or document hook-style tokens as unsupported.

[8] Zero-payout claims can revert permanently on zero-transfer-reverting tokens

Severity: Low
Location: _calculatePayout() (can return 0) → safeTransfer(msg.sender, 0) in cancelVote/claimNonWinningFunds/claimWinningOptionsFunds
Origin: [phase1: erc20 E-5, dos D-3] [phase2: first-principles, flow-gap]

Some tokens (e.g. LEND, BNB) revert on transfer(_, 0). If a claim's payout floors to zero (only reachable with a non-standard/deflationary token where balance < outstanding), the transfer reverts and the voter's on-chain vote state is never cleared, permanently bricking that wallet's exit from a token that already gave them nothing.

Recommendation: if (payoutAmount != 0) IERC20Minimal(votingToken).safeTransfer(...), and still clear state unconditionally.

[9] First finalizer bears the entire finalization gas cost

Severity: Low
Location: _finalizeIfNeeded() L219-265
Origin: [phase1: dos D-1] [phase2: invariant "gas-griefing", first-principles "first-caller-gas-burden"]

The partial selection-sort is O(totalOptions × winningOptionsCount), bounded by MAX_OPTIONS = 100 to ~8-12M gas worst case — comfortably under Base's block gas limit, so this is not a DoS. It is purely a fairness issue: whoever calls finalizePoll()/first claims after endTime pays the whole one-time cost.

Recommendation: Optional — no action required for security; consider incentivizing/compensating the first finalizer.

[10] Tie-break seed is fully predictable before voting starts

Severity: Info
Location: _finalizeIfNeeded() L222-231
Origin: [phase1: general G-4] [phase2: access-control, economic-security, execution-trace, periphery, boundary, trust-gap — 6 of 12 agents converged]

tieBreakSeed = keccak256(address(this), factory, pollCreator, startTime, endTime, totalOptions, winningOptionsCount) depends only on immutable, deploy-time-known values, so the entire tie-break ordering is computable by anyone before a single vote is cast. This is explicitly documented as intended ("Ties are broken by the contract's deterministic per-option hash, not random selection"). Every one of the 6 phase-2 agents who flagged this concluded they could not construct an attacker-profitable exploit — it only matters when two options land on an exact funding tie, and no agent found a way to force that condition onto a victim's option.

Recommendation: None required if determinism is intended (it appears to be, per the platform description). If unpredictability is desired, incorporate a value only fixed at/after endTime.

[11] Theoretical multiplication overflow in _calculatePayout

Severity: Info
Location: _calculatePayout() L286: (liabilityAmount * currentBalance) / totalOutstandingFunds
Origin: [phase2 only — math-precision, execution-trace, invariant, periphery, boundary, numerical-gap, first-principles, flow-gap: 8 of 12 agents converged independently; not raised by phase 1]

No mulDiv/512-bit intermediate is used. If both liabilityAmount and currentBalance approach ~2^128 (≈3.4×10^38 wei, i.e. ~3.4×10^20 whole 18-decimal tokens), the product overflows uint256 and reverts under Solidity 0.8 checked math, bricking the non-exact-match payout branch for that poll. Every agent that flagged this independently concluded it requires token magnitudes far beyond any realistic ERC20 supply (typical supplies stay well under 10^30 wei) — re-confirmed here: this is not reachable with any real-world token, but the fix is trivial and worth applying defensively given how many independent lenses converged on it.

Recommendation: Math.mulDiv(liabilityAmount, currentBalance, totalOutstandingFunds) (OpenZeppelin) for defense-in-depth.

[12] SafeTokenTransfer return-data is unbounded

Severity: Info
Location: SafeTokenTransfer.safeTransfer/safeTransferFrom/safeBalanceOf L14-31
Origin: [phase1: dos D-4]

Low-level .call/.staticcall copies the full return buffer into memory; a malicious token could return an oversized buffer to inflate gas costs. Self-scoped — only makes the creator's own hostile-token poll more expensive to interact with, not a cross-user griefing vector.

Recommendation: Optional — cap copied return data via assembly if hardening against arbitrary tokens is desired.

[13] Refuted: creator self-voting to flip the winning option

Severity: Info (no action needed)
Origin: [phase2 only: economic-security "incentive-griefing"] — raised as a lead, mathematically refuted during reconciliation.

The lead proposed a creator could vote on their own losing-but-favored option with just enough capital to overtake the natural winner, then reclaim everything (including their own stake) via claimWinningOptionsFunds(). Re-derivation: net creator profit from such a flip = (boosted_option_legit_funds) - (natural_winner_legit_funds), and by construction this is always strictly negative — the option needed boosting from the creator's own capital because its organic funding was already behind the natural winner's. The creator's own added capital is returned to them regardless of whether they manipulate the outcome, so it cancels out of the profit calculation; only the legitimate funds captured differ, and that difference always favors the unmanipulated (natural) outcome. No profitable path exists in the two-option case; more complex multi-winner scenarios were not found to change this conclusion. No action required.

Notes on scope and design intent

  • The permissionless factory, permissionless finalizePoll(), and full immutability (no owner, no pause, no upgrade) are all explicitly intended per the platform description and were independently validated as not introducing privilege-escalation paths by every phase-2 access-control-focused agent.
  • The core pro-rata payout engine (_calculatePayout plus the vote/cancelVote/claim state machine) proved unusually robust under adversarial review from 18 independent agent passes (6 phase-1 checklists + 12 phase-2 attackers): fee-on-transfer tokens are correctly measured via balance deltas, reentrancy is fully blocked via a shared lock with checks-effects-interactions ordering, and the balance/outstanding-funds ratio is provably preserved across every claim ordering for well-behaved tokens.
  • The recurring theme across nearly every Medium/High finding is the same root cause: the factory imposes no allowlist or vetting on votingToken beyond "has code." A curated token allowlist (or, short of that, prominent voter-facing disclosure of the creator-chosen token) would eliminate or substantially reduce findings #1, #3, #4, and #7.

This review was performed by an AI-driven two-phase audit (ethskills breadth + pashov depth, run blind and reconciled). AI analysis can never verify the complete absence of vulnerabilities. A human security review and/or bug bounty program is recommended before mainnet deployment with real value.
