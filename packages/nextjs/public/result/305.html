Findings

[85] 1. dao.wei role model has no re-verification after a parent-name transfer — role hijack and permanent veto-bypass, both confirmed against the live NameNFT contract

WeiDAO._roleHolder / WeiDAO._holder / WeiDAO.execute / WeiDAO.constructor · Confidence: 85 · [both] — independently raised by 4 phase-1 agents (general, governance, access-control, erc721/nft) and confirmed as an executable FINDING by 1 phase-2 agent (flow-gap); root cause verified directly against NameNFT.sol source in reconciliation.

Description

vetoer()/executor() resolve live, gated only on the DAO currently owning the parent name dao.wei (_roleHolder → _holder(PROPOSAL_PARENT) == address(this)) and on the target role subdomain's parentEpoch matching the parent's current epoch. I pulled the verified NameNFT source (0x0000000000696760E15f265e828DB644A0c242EB) to check the load-bearing assumption every agent had to infer from WeiDAO's own documentation, and confirmed it directly:

  • A plain transferFrom/safeTransferFrom of dao.wei never bumps epoch — only _register() does (NameNFT.sol:680-711), which runs on fresh registration or subdomain overwrite, never on a transfer. _beforeTokenTransfer (NameNFT.sol:142-150) only blocks transfers of inactive (expired) tokens; it does not touch epoch.
  • registerSubdomainFor(label, parentId, to) requires only ownerOf(parentId) == msg.sender (NameNFT.sol:302-309) — whoever currently owns dao.wei can (re)assign exec.dao.wei/veto.dao.wei to any address at any time, with no staleness or existence check for subdomains (_register's AlreadyRegistered guard applies only to top-level names, NameNFT.sol:684-687; a subdomain "overwrite" always succeeds for the current parent owner).
  • Top-level names (dao.wei itself) become re-registerable by anyone, permissionlessly, via commit()/reveal(), once block.timestamp > expiresAt + GRACE_PERIOD (NameNFT.sol:687, GRACE_PERIOD = 90 days, REGISTRATION_PERIOD = 365 days — NameNFT.sol:80-81). Re-registration does bump epoch (NameNFT.sol:696).

WeiDAO.sol has no function anywhere that renews dao.wei. Combining these three facts yields a directly confirmed attack:

Path A — passive neglect (works even if the DAO launched perfectly cleanly):

  1. Nobody renews dao.wei for 365 + 90 = 455 days after its last renewal (no automation exists in WeiDAO.sol; renewal would require a deliberate execute/rescue call to NameNFT.renew).
  2. Anyone permissionlessly re-registers dao.wei via commit()/reveal() (NameNFT.sol:238-267) — this bumps its epoch and makes the caller the new owner.
  3. The attacker calls registerSubdomainFor("exec", dao.wei, attacker) (they're now the parent owner — always succeeds, no staleness guard on subdomains).
  4. The attacker transfers dao.wei back to the DAO (a plain transfer — confirmed above this does not bump epoch again).
  5. _holder(PROPOSAL_PARENT) now returns the DAO (owns an active, non-expired dao.wei) → _roleHolder's gate passes. _holder(EXEC_ROLE): parentEpoch (set at attacker's re-registration) still equals the parent's current epoch (unchanged by the plain transfer in step 4) → resolves to the attacker. executor() == attacker → rescue(anyTarget, treasuryBalance, anyData) drains the entire treasury.
  6. Even without step 4 (attacker never gives dao.wei back), any proposal the attacker had already parked past threshold+executionDelay becomes permanently unvetoable and undrainable-by-nobody-but-executable-by-everybody: veto() requires vetoer()/executor() to be non-zero, which they cannot be while an outsider holds dao.wei — but execute() (WeiDAO.sol:445-463) has no equivalent check and keeps working regardless of who owns dao.wei. This half of the chain was independently found and gate-verified as a standalone FINDING by the phase-2 flow-gap agent.

Path B — deferred/careless handover (documented-but-risky deployment path): the constructor's atomic pull-and-mint (WeiDAO.sol:262-273) does unconditionally overwrite veto.dao.wei/exec.dao.wei to the intended roleHolder on every successful pull (confirmed: registerSubdomainFor always succeeds on subdomains, so this path is actually self-correcting even against pre-seeding — several phase-1 leads assumed it would revert on a pre-existing subdomain; verification shows it does not). The real gap is the contract's own documented fallback: "no approval / no active name ⇒ deployment still succeeds and the name is handed over later" (WeiDAO.sol:256-261). That later, manual transferFrom into the DAO has no equivalent post-transfer role verification/re-mint anywhere in the code — whatever exec.dao.wei/veto.dao.wei already exist under dao.wei at that moment (pre-minted by whoever controlled it before handover) are inherited as-is.

Fix

 function execute(uint256 id) external returns (bytes memory result) {
     if (id == 0 || id > proposalCount) revert NoProposal();
     Proposal storage p = proposals[id];
     if (p.vetoed) revert Vetoed();
     if (p.executed) revert AlreadyExecuted();
     if (block.timestamp < p.created + executionDelay) revert TooSoon();
+    if (_holder(PROPOSAL_PARENT) != address(this)) revert Unauthorized(); // fail closed with veto, not open
 
     _sync(p);
     if (p.conviction < threshold) revert Rejected();

Additionally: bind role validity to DAO-controlled provenance rather than current parent ownership — e.g. record the epoch at which the DAO itself acquired dao.wei and require any trusted role subdomain's parentEpoch to equal that recorded value, not merely the parent's live epoch; and/or make dao.wei renewal a hard, permissionless-but-DAO-funded invariant (e.g. a public keep() function anyone can call that renews dao.wei from the treasury before it lapses). For the deferred-handover path, require _holder(VETO_ROLE) == address(0) && _holder(EXEC_ROLE) == address(0) before trusting a manually-transferred dao.wei.

Severity note: rated High, not Critical — Path A requires either 455 days of renewal neglect (a specific-but-realistic precondition, not privileged) or a deployer choosing the documented-but-risky deferred-handover path (Path B) and accepting dao.wei from an unverified party. Both are "specific conditions" per the audit's own High-severity definition ("loss of funds requiring specific conditions"), not zero-precondition Critical.

[75] 2. Conviction weight is snapshotted at support() time and never re-validated against continued ownership

WeiDAO.support / WeiDAO.unsupport / WeiDAO.execute · Confidence: 75 · [phase2: economic-security] — phase-1 raised adjacent stale-support leads (NFT-1, Governance-5, Governance-6) but not this specific ownership-decoupling framing; re-examined against source and confirmed as described.

Description

support() checks nft.ownerOf(tokenId) == msg.sender only at the moment of the call (WeiDAO.sol:395); nothing thereafter re-checks live ownership or live weight. A supporter can back a proposal and immediately sell/transfer the backing name — the position keeps driving conviction until the new, uninvolved owner chooses to unsupport (WeiDAO.sol:423, owner-gated for a non-stale position) or until the frozen snapshot term naturally elapses and becomes permissionlessly prunable (up to a year later, per weightOf's own 365-day runway model). This collapses the intended cost from "sink W of ETH for the whole conviction ramp" (the contract's own stated sybil-resistance rationale: "weight = sunk ETH already provides sybil resistance") to "control W for one block."

Fix

The most direct fix is to let a position also be pruned by anyone once the backing name has changed hands (not only once it's stale/re-registered), since a transfer is exactly the signal that the original supporter's stake is gone:

  function unsupport(uint256 id, uint256 tokenId) external {
      Support memory s = _support[id][tokenId];
      uint256 w = s.weight;
      if (w == 0) revert NotSupporting();
      (,,, uint64 epoch,) = nft.records(tokenId);
-     bool stale = block.timestamp >= s.expiresAt || epoch != s.epoch;
+     address currentOwner = nft.ownerOf(tokenId);
+     bool stale = block.timestamp >= s.expiresAt || epoch != s.epoch || currentOwner != s.originalSupporter;
      if (!stale && nft.ownerOf(tokenId) != msg.sender) revert NotHolder();

(illustrative — requires storing the original supporter's address in the Support struct.)

Note: mitigated during launch by veto + executionDelay (an attentive vetoer can catch and cancel a suspiciously-cheap threshold crossing); this compounds severely with Finding 1 — once dao.wei lapses, the veto backstop this finding relies on is also gone, and the two chain into an unstoppable, cheaply-manufactured treasury drain.

Chain: [Finding 1] + [Finding 2] — conf = min(85, 75) = 75. A dao.wei lapse (Finding 1) removes the only backstop against a proposal whose conviction was manufactured via ownership-decoupled support (Finding 2), producing an attack strictly worse than either alone.

Additional Findings (Low / Info — below confidence threshold, or admin-gated by design)

These did not clear the 75-confidence bar for a full write-up (mostly because they are bounded, admin-gated, or require an already-privileged actor) but are real, source-verified observations worth the team's attention. Severity uses the standard scale (Critical/High/Medium/Low/Info).

[Medium] Veto is unbounded, permanent, single-role censorship. veto() (WeiDAO.sol:434-441) lets a single veto.dao.wei/exec.dao.wei holder cancel any not-yet-executed proposal forever, with no un-veto and no scope limit — total governance DoS by one compromised role NFT. [phase1: access-control]

[Medium] executionDelay is a live global, not a per-proposal snapshot. A passed proposal (or exec) calling setExecutionDelay(0) (WeiDAO.sol:514-519) instantly collapses the veto-reaction window for every other in-flight proposal, not just future ones. Two independent phase-2 agents (boundary, trust-gap) sketched the same two-proposal race. [both: governance, boundary, trust-gap]

[Low] Proposals never expire. execute() has no upper time bound — a proposal that ever crosses threshold stays executable indefinitely if any support lingers, even against a completely changed treasury/target years later. [phase1: governance]

[Low] Stale/expired support inflates conviction until permissionlessly pruned, and can strip a renewed-but-not-re-supported name's live backing. unsupport's staleness check (WeiDAO.sol:422) is keyed to the frozen support-time snapshot expiry, not the name's live (possibly renewed) expiry — corroborated by 7 of 12 phase-2 agents plus 3 phase-1 agents (highest cross-agent convergence of any secondary item). Documented as an intended "keeper duty," but real griefing/UX surface. [both, 10 agents]

[Low] setAlpha retroactively reprices every un-synced proposal's entire backlog. Changing alpha applies the new decay rate over each proposal's whole un-synced gap rather than only going forward, letting a trusted setter nudge a near-threshold proposal by adjusting a global. Gated to gov/exec — governance-hygiene issue, not an external exploit. [both, 5 agents]

[Low] Uncapped returndata in execute()/rescue(). Both copy and (for execute) re-emit the callee's full returndata with no cap — a target returning a very large blob could brick that one proposal's execution via gas inflation. Bounded because the target is always governance/exec-chosen. [phase1: general, dos, assembly]

[Low] execute()/rescue() don't verify the target has code. A passed proposal with a codeless/typo'd target and value > 0 silently burns treasury ETH with no effect while marking the proposal executed. [phase1: general]

[Low] Extreme-parameter overflow of _accrue/convictionMax/_passWeight. No upper bound on threshold beyond != 0; combined with alpha near SCALE, the conviction math can in principle overflow-revert. Computed thresholds for this are 30+ orders of magnitude above any sane configuration (verified: default getFee is 0.001 ETH/year, making realistic threshold values land around 1e26-1e27 vs. an overflow point near 1e58-1e59) — unreachable in practice. [both, 8 agents across both phases — highest raw convergence, all converging on "not reachable"]

[Info] _holder ignoring a role subdomain's own expiresAt — REFUTED. Six separate agent runs (3 in phase 1, 3 in phase 2) independently flagged this as an unverifiable lead. Direct verification against NameNFT.sol:706 shows subdomain records are always created with expiresAt: parentId == 0 ? ... : 0 — subdomains never have an independent expiry; the field is always 0. _holder's subdomain branch correctly has nothing to check here. No fix needed; this lead is dropped from the report per the reconciliation's hybrid re-examine step.

[Info] setHtml-served wallet-bridge JS is a phishing surface for the fully-trusted exec/governance path. A malicious (pre-relinquishment) exec or a passed proposal can rewrite the on-chain dapp's JS to prompt harmful signatures under the DAO's trusted origin. Admin-gated. [phase2: access-control]

[Info] Future-proposal-id name-squatting griefs on-chain rendering only. A passed proposal can pre-register <future-id>.dao.wei, causing that later proposal's own naming to silently fail (swallowed by propose's try/catch) — cosmetic UI-only impact. [phase2: asymmetry]

[Info] Alt-chain deployment caveat. pragma ^0.8.30 emits PUSH0 by default; irrelevant for the current mainnet deployment. [phase1: general]
