Security Audit Report: Vaultfire VaultfireTeleporterBridge

Target: VaultfireTeleporterBridge at 0x62edf0cBc8Fa3d98B6A07197DFE9cb1c128a7eC7 (Base, chain 8453)
In-scope contracts: VaultfireTeleporterBridge.sol, ITeleporterMessenger.sol, ITeleporterReceiver.sol (source verified via Sourcify full match; compiler 0.8.25)
Methodology: Two-phase audit — Phase 1 breadth (5 parallel checklist-driven agents: general, bridges, access-control, dos, precision-math) → Phase 2 depth (12 parallel attacker-mindset agents, run blind to Phase 1) → hybrid reconciliation (this document).
Reconciliation summary: Overlap: 7 findings independently confirmed by both phases · Phase-1-only: 7 · Phase-2-only: 2 (both re-examined against source and confirmed) · Demoted on re-examine: 0.
Completeness: every unique (contract, function, bug-class) raised by either phase's raw agent output is represented below.

Independent on-chain verification performed by the orchestrator: teleporterMessenger() = 0x0, remoteBridgeAddress() = 0x0, remoteChainId() = 0, owner() = 0xfA15Ee28939B222B0448261A22156070f0A7813C, getRelayerCount() = 1. The bridge is deployed but not yet configured to any remote chain — a pre-launch state. The code-level design below is the actual audit target, since this configuration is expected to be completed before the bridge goes live.

Summary

This contract syncs AI-agent trust metadata (registrations, partnership/accountability bonds, reputation, validation status — no token/value transfer) between Base and Avalanche C-Chain, and per the client's description, eventually Arbitrum and Polygon too. It has two inbound paths with starkly different security properties: receiveTeleporterMessage, gated by Avalanche's own cryptographically-verified Teleporter/ICM infrastructure, and relayMessage, gated only by an owner-managed relayer whitelist with zero cryptographic proof that a submitted message reflects anything that actually happened on the claimed source chain. Because Base, Arbitrum, and Polygon all lack native Avalanche ICM, relayMessage is not a fallback for any of those deployments — it is the entire bridge. Both audit phases converged overwhelmingly (in Phase 2, essentially every one of the 12 independent agents reached the same conclusions from different angles) on this being the dominant risk, compounded by a second, independently serious defect: none of the five state-sync handlers enforce message ordering or freshness, so out-of-order delivery — which can happen with zero adversary, purely from ordinary asynchronous relay/ICM behavior — silently rolls back an agent's trust state to a stale, more favorable snapshot.

Critical Severity

[C-1] relayMessage — the sole functioning inbound path on any non-Avalanche deployment — has zero cryptographic source-chain authenticity, enabling arbitrary trust-state injection

Origin: [both] — Phase 1 (bridges agent rates Critical; general and access-control agents rate High for the same root cause) · Phase 2 (12/12 agents raised this in some form; 2 as explicit Critical/High-framed findings, the rest as leads with identical substance)
Location: relayMessage (489-493) → _processInboundMessage (592-629)

relayMessage is gated only by onlyAuthorizedRelayer — an owner-managed whitelist. The relayer supplies an arbitrary ABI-encoded BridgeMessage containing a self-declared sourceChainId field, and the only "source verification" is require(bridgeMsg.sourceChainId == remoteChainId) — a comparison against a value the relayer typed inside their own submitted blob. There is no signature, no Merkle/state proof, no light client — nothing cryptographically binding the payload to anything that actually happened on the real source chain. Contrast this with receiveTeleporterMessage, which enforces both sourceBlockchainID == remoteBlockchainID and originSenderAddress == remoteBridgeAddress, delegating real authentication to Avalanche's Teleporter/Warp messaging infrastructure. Because Base, Arbitrum, and Polygon all lack native Avalanche ICM — confirmed live on this Base deployment, where teleporterMessenger=0x0 makes onlyTeleporter unconditionally unsatisfiable — relayMessage is not a fallback for any of those chains; it is the entire bridge.

Proof of Concept: Any authorized relayer key (or the owner, auto-whitelisted at construction) calls:

relayMessage(abi.encode(BridgeMessage{
  messageType: SYNC_ACCOUNTABILITY_BOND, sourceChainId: remoteChainId, nonce: N, timestamp: now,
  sender: anything,
  payload: abi.encode(AccountabilityBondPayload{
     bondId: X, aiCompany: attacker, companyName: "FakeCo",
     quarterlyRevenue: 1e18, stakeAmount: 1e18, createdAt: now, active: true })
}))

This passes every check and writes fabricated collateral/reputation/registration state directly into syncedAccountabilityBonds, syncedReputations, syncedAgents, etc. — with no possibility for any on-chain observer to distinguish it from a genuine cross-chain sync. Any downstream Vaultfire contract that treats isAgentRecognized/getSyncedReputation/getSyncedAccountabilityBond as cross-chain-verified ground truth is fully spoofable by a single relayer key.

Recommendation: Do not treat the relayer path as cryptographically authentic. Require the relayer to submit a source-chain proof (light-client header + Merkle/storage proof of the emitting event), an EIP-712 signature from a source-side authorized signer bound to both chain IDs and the destination bridge address, or route through a real message-verification protocol (CCIP/LayerZero/Wormhole/Hyperlane) for non-Avalanche legs. At minimum, require N-of-M relayer quorum rather than a single key, and prominently document that the relayer path is a fully trusted model with no cryptographic minimization.

High Severity

[H-1] No freshness/ordering check on any synced-state handler — out-of-order (but fully authentic) message delivery silently rolls back trust state

Origin: [both] — Phase 1 (general and bridges agents, with concrete before/after traces) · Phase 2 (12/12 agents — the single most unanimously-confirmed finding of this engagement; 7 as explicit FINDINGs)
Location: all 5 _handleXxx functions (635-691); lastProcessedNonce (169, 601-603)

Every handler unconditionally overwrites stored state (syncedReputations[p.agentAddress] = p; etc.) with no comparison against the already-stored registeredAt/createdAt/lastUpdated/timestamp. lastProcessedNonce is written but never read to gate or reject anything — a passive high-water-mark with no enforcement power. Critically, this requires no adversary whatsoever: Avalanche ICM/Teleporter guarantees single execution of a message but not cross-message ordering, so this can occur on the fully honest delivery path via ordinary asynchronous relay behavior, retries, or re-processing of an old event batch.

Proof of Concept: Source emits reputation update nonce=5 (rating=90) then nonce=6 (rating=20, after the agent misbehaved). Both are distinct, genuine messages with distinct hashes, so both independently pass replay-dedup. If nonce=6 is delivered first (syncedReputations[agent].averageRating=20), then nonce=5 arrives later — 5 > 6 is false so lastProcessedNonce is untouched, but nothing prevents the subsequent write — _handleReputation still unconditionally overwrites back to the stale rating=90. The identical mechanism can silently reactivate a revoked partnership/accountability bond (a stale active:true overwriting a legitimately-later active:false) or revert a validation from rejected back to approved.

Recommendation: Store and compare a per-entity highest-nonce-or-timestamp before writing; reject or no-op any incoming record that is not strictly newer than what's currently stored. A single global lastProcessedNonce cannot do this since independent entities' update streams interleave.

[H-2] BridgeMessage has no destination binding — genuine messages can replay across sibling bridge instances sharing the same remoteChainId

Origin: [phase1 only] (bridges agent, with general agent corroboration) — re-examined against source and confirmed; the specific cross-instance framing was not independently re-derived by phase 2 (though [2-2]'s root cause — a self-declared, unauthenticated sourceChainId — is the same underlying gap)
Location: BridgeMessage struct (74-81); _processInboundMessage (592-606)

The message envelope binds only to its claimed origin (sourceChainId) — never to an intended destination chain or destination bridge address. processedMessages is a per-contract-instance mapping, so the identical encoded message shows as "unprocessed" on every other deployed instance. Under the client's own described topology — a hub-and-spoke where Avalanche is the trust anchor and Base/Arbitrum/Polygon are spokes, all naturally configured with remoteChainId = 43114 — a single genuine Avalanche-origin message legitimately relayed to one spoke passes the identical source check on every sibling spoke, and none of their independent processedMessages maps have seen it. No owner error is required — this is the natural consequence of the shared-remote-anchor configuration the architecture itself implies. Any relayer authorized on more than one spoke can fan a single message out to, or replay it against, all siblings.

Recommendation: Add destinationChainId and destinationBridgeAddress fields to BridgeMessage, set at send time, and enforce destinationChainId == block.chainid / destinationBridgeAddress == address(this) on receipt; fold both into the dedup hash.

Medium Severity

[M-1] bondId == 0 / requestId == 0 sentinel collision — duplicate pushes into tracking arrays on every re-sync of a legitimately-zero-valued ID

Origin: [both] — Phase 1 (4/5 agents, near-unanimous) · Phase 2 (12/12 agents in some form, with the invariant agent splitting it into three separate per-handler findings)
Location: _handlePartnershipBond (651), _handleAccountabilityBond (662), _handleValidation (685)

"Is this a new ID" is decided by reading the stored struct's own key field (syncedPartnershipBonds[p.bondId].bondId == 0), which is indistinguishable from "not yet seen" when the ID is genuinely 0. The address-keyed handlers (_handleAgentRegistration, _handleReputation) avoid this by additionally requiring agentAddress != address(0) — the ID-keyed handlers have no equivalent guard. If the source-chain ID counters ever start at 0 (plausible and unverified from these files alone), every single re-sync of that entity — an active flag toggling, an approval count incrementing — re-pushes 0 into the tracking array indefinitely, corrupting getSyncedXxxCount() and any consumer that assumes count equals distinct entries. This occurs even with a fully honest relayer syncing fully honest data.

Recommendation: Track membership with an explicit mapping(uint256 => bool) presence flag rather than overloading the ID field as a sentinel.

[M-2] transferOwnership does not revoke the outgoing owner's relayer privilege

Origin: [both] — Phase 1 (access-control agent, general agent) · Phase 2 (access-control agent, independent full PoC)
Location: transferOwnership (275-279) vs. constructor relayer grant (267-268)

The constructor auto-authorizes the deployer as a relayer permanently. transferOwnership mutates only the owner variable — it neither revokes the old owner's relayer status nor grants the new owner one. After a key rotation (including one done because the old key is suspected compromised), the old address retains full C-1-style state-injection power indefinitely, until someone remembers to removeRelayer(oldOwner).

Recommendation: In transferOwnership, explicitly reconcile the relayer set, or clearly document that relayer membership is managed independently of ownership and must be handled separately on every rotation.

[M-3] Single-step transferOwnership with no two-step accept

Origin: [phase1 only] (access-control) — re-examined against source and confirmed
Location: transferOwnership (275-279)

Only a zero-address check guards the new owner. A typo or paste of an uncontrolled address permanently forfeits every privileged function — relayer management, pause, remote-bridge configuration — with no secondary admin/guardian role anywhere to recover from it.

Recommendation: Adopt an Ownable2Step-style pattern.

[M-4] Instant, non-timelocked relayer additions and remote-bridge reconfiguration

Origin: [phase1 only] (access-control) — re-examined against source and confirmed
Location: addRelayer (310-316), setRemoteBridge (288-298), setTeleporterMessenger (304-306)

All take effect in the same transaction with no delay or observation window, unlike more defensive patterns seen in sibling Vaultfire contracts (48h timelocks on less-sensitive parameters). A compromised owner key escalates instantly to full C-1-style state-injection power via addRelayer.

Recommendation: Add a timelock or queue-then-apply pattern for addRelayer and remote-configuration changes; route admin through a multisig.

Low Severity

[L-1] ABI trailing-byte / non-canonical encoding malleability defeats the sole replay guard

Origin: [both] — Phase 1 (precision-math agent, empirically confirmed via Foundry harness against solc 0.8.25) · Phase 2 (5/12 agents, all as leads with matching substance)
Location: _processInboundMessage (596-598)

abi.decode does not require the input length to exactly match the encoded payload — trailing bytes past the consumed region are silently ignored, so many distinct byte strings decode to the identical BridgeMessage but hash differently. Since processedMessages[keccak256(encoded)] is the only replay guard (nonce is never enforced, only tracked as a max), an authorized relayer can take any already-processed blob, append arbitrary trailing bytes, and resubmit it indefinitely — each pass re-runs the handler and re-emits events, and combined with M-1, replaying an ID-0 message compounds the duplicate-push growth. Empirically confirmed, not merely theoretical: a Foundry test showed enc and enc || 0x00... decode to the identical struct but hash differently, both passing the dedup check.

Recommendation: Derive the dedup key from canonical decoded content (e.g. hash (sourceChainId, nonce, messageType, payload) post-decode) rather than the raw input bytes.

[L-2] setTeleporterMessenger has no code-presence check and emits no event

Origin: [phase1 only] (access-control) — re-examined against source and confirmed
Location: setTeleporterMessenger (304-306)

No zero-address or extcodesize check (unlike the defensive pattern used in sibling Vaultfire verifier contracts), and no event emitted. If ever misconfigured to an attacker-controlled address, that address could call receiveTeleporterMessage with arbitrary sourceBlockchainID/originSenderAddress claims.

Recommendation: Add a code-presence check and emit a configuration-change event.

[L-3] Unbounded append-only synced-state arrays — a single relayer-key compromise can cheaply bloat the entire dataset

Origin: [phase1 only] (dos, bridges) — re-examined against source and confirmed
Description: No on-chain function iterates these arrays (so no on-chain out-of-gas DoS), but a compromised relayer can cheaply fabricate thousands of unique entries to degrade off-chain consumers, and there's no owner-level pruning/reset capability to recover.

Recommendation: Add owner-only pruning functions, or avoid on-chain enumerable arrays entirely in favor of off-chain event-log reconstruction.

[L-4] requiredGasLimit has no min/max bound

Origin: [phase1 only] (dos) — re-examined against source and confirmed
Location: setRequiredGasLimit (300-302)

No validation on the owner-settable gas limit forwarded to Teleporter. Too low silently makes outbound messages permanently unexecutable on the destination chain; too high may make delivery economically unattractive to ICM relayers. Moot on the current Base deployment since teleporterMessenger=0x0 skips this path entirely.

Recommendation: Add sane bounds (e.g. 100k–5M gas).

[L-5] _sendViaTeleporter discards the returned messageID and hardcodes a zero relayer fee

Origin: [both] — Phase 1 (bridges agent) · Phase 2 (economic-security agent, corroborating the fee-liveness angle)
Location: _sendViaTeleporter (579-590)

The returned bytes32 messageID is never captured, precluding later retry/fee-top-up correlation. feeInfo is hardcoded to {feeTokenAddress: address(0), amount: 0} — on Avalanche, ICM relayers are reward-driven, so a zero-fee message may never be picked up, silently stalling outbound sync (a liveness issue, not a security bug).

Recommendation: Capture and store/emit messageID; make the fee configurable.

[L-6] Source-chain check is trivially satisfiable while remoteChainId == 0 (current unconfigured state)

Origin: [phase1 only] (general) — re-examined against source and confirmed
Location: _processInboundMessage (606); setRemoteBridge (288-298)

No remoteChainId != 0 guard exists anywhere. While unconfigured (the current live state), any authorized relayer can pass the source check trivially with sourceChainId=0. This adds no defense beyond what C-1 already concedes.

Recommendation: Require remoteChainId != 0 both in setRemoteBridge and defensively in _processInboundMessage.

[L-7] Cross-channel dedup poisoning — a relayer can pre-empt native Teleporter delivery of the same message, causing it to permanently revert

Origin: [phase2 only] — re-examined against source and confirmed as a plausible mechanism
Location: relayMessage / receiveTeleporterMessage shared processedMessages mapping

Both inbound paths share a single dedup mapping. An authorized relayer can call relayMessage with the exact bytes Teleporter will later deliver for the same logical message; once processed via the relay path, the subsequent native Teleporter delivery of the identical bytes reverts on "already processed." No state corruption results (the state ends up identical either way), but it could strand Teleporter-side delivery/retry/fee accounting for that message.

Recommendation: Consider separate dedup namespaces per inbound channel, or accept this as low-severity given no state divergence results.

Informational

  • Outbound send* functions have no binding to any real source-chain event either — the relayer specifies fully arbitrary payload fields on the outbound side too, mirroring C-1's trust gap in the opposite direction. [phase2 only]
  • isAgentRecognized's NatSpec claims "either native or synced" but the body only checks synced state — there is no native registry in this contract. [both phases]
  • Dead-code else { revert("unknown message type") } fallback is genuinely unreachable — abi.decode of the MessageType enum reverts first on any out-of-range value (confirmed empirically on solc 0.8.25 by multiple agents). No action needed.
  • onlyTeleporter modifier is sound; msg.sender cannot be spoofed short of controlling the real address, and correctly disables the native path entirely when teleporterMessenger=0x0 (as on this live deployment). [phase1]
  • Pause coverage is complete on every inbound and outbound state-mutating entry point; no bypass path found. [phase1]

Methodology Notes

  • Both phases audited the same three in-scope files independently; Phase 2 was run with no visibility into Phase 1's findings to avoid anchoring.
  • This engagement showed the highest degree of cross-agent convergence of any of the Vaultfire contracts audited in this batch: on H-1 (stale-overwrite), all 12 of 12 independent Phase 2 agents — using entirely different reasoning lenses — reached the identical root cause and constructed matching concrete exploit traces, and Phase 1's precision-math agent independently confirmed L-1 via live Foundry testing rather than static inference.
  • Out of scope: the concrete source-chain registries that assign bondId/requestId values (relevant to M-1's precondition) were not available for review; the real Avalanche TeleporterMessenger/ICM infrastructure's exact retry/fee semantics (relevant to L-5, L-7) were reasoned about from the provided interfaces and general knowledge of Avalanche ICM, not independently verified against live Avalanche state.
