[U-1] removeLastOwner() can zero the owner set, permanently bricking the wallet

Severity: Medium
Origin: [phase1: access-control, erc4337]
Location: MultiOwnable.removeLastOwner() — MultiOwnable.sol:137-144; allow-listed in CoinbaseSmartWallet.canSkipChainIdValidation() — CoinbaseSmartWallet.sol:281-292

Root cause: removeOwnerAtIndex refuses to remove the last owner (ownerCount()==1 → revert LastOwner(), MultiOwnable.sol:122-124). removeLastOwner is its mirror-image: it requires exactly one owner remain and removes it (MultiOwnable.sol:137-144), driving ownerCount() to 0. _removeOwnerAtIndex never decrements nextOwnerIndex, only increments removedOwnersCount (MultiOwnable.sol:263) — ownerCount() = nextOwnerIndex - removedOwnersCount (MultiOwnable.sol:193-195). initialize()'s only guard is nextOwnerIndex() != 0 (CoinbaseSmartWallet.sol:128-130), which stays permanently true once any owner has ever been added — re-initialization is impossible. Every mutating function is onlyOwner, so once ownerCount()==0 nothing can ever add a new owner again.

Concrete exploit walk: Sole owner O calls removeLastOwner(index, ownerBytes) — passes onlyOwner, ownersRemaining()==1. _removeOwnerAtIndex deletes the slot and increments removedOwnersCount to equal nextOwnerIndex. ownerCount() → 0. initialize() still reverts Initialized() forever. No function in either contract can add an owner without first passing onlyOwner, which now has zero valid callers. All held assets (currently ≈0.00637 ETH plus historical USDC/AERO flows through this address) are permanently frozen. removeLastOwner.selector is also in canSkipChainIdValidation's allow-list (CoinbaseSmartWallet.sol:286), so one owner-signed replayable UserOp bricks every chain-deployment of this wallet address in one shot.

Verification note: this exact function is present unmodified in Coinbase's canonical, publicly-audited CoinbaseSmartWallet/MultiOwnable — it is not specific to this deployment. It appears to be an intentional "formally decommission this wallet" primitive rather than a coding defect, but its name and NatSpec ("Removes owner at the given index, which should be the only current owner") give no warning that this is irreversible and no recovery path exists. Severity kept at Medium (not High) because it requires the wallet's own authorized owner to invoke it — no external attacker path exists — but the impact (total, permanent, unrecoverable loss of the wallet and its funds from a single call) is severe enough that Low would understate it.

Recommendation: If this decommissioning behavior is intentional, gate it behind an explicit two-step confirmation or a distinctly-named function that makes the irreversibility unambiguous, and strip removeLastOwner.selector from canSkipChainIdValidation so a single signature cannot brick every chain deployment at once.

[U-2] Injected validateUserOp upgrade-check loop: redundant, ERC-4337-validation-phase risk, and can stall the replayable-nonce channel

Severity: Low
Origin: [both — highest corroboration in this audit: phase1 P1-6/P1-7 + 11 of 12 phase2 agents]
Location: CoinbaseSmartWallet.validateUserOp() — CoinbaseSmartWallet.sol:169-183 (the only deviation from Coinbase's canonical upstream source in this deployment)

// Check for upgrade calls in the batch and validate implementation has code
bytes[] memory calls = abi.decode(userOp.callData[4:], (bytes[]));
for (uint256 i; i < calls.length; i++) {
    bytes memory callData = calls[i];
    bytes4 selector = bytes4(callData);

    if (selector == UUPSUpgradeable.upgradeToAndCall.selector) {
        address newImplementation;
        assembly {
            // Skip reading the first 32 bytes (length prefix) + 4 bytes (function selector)
            newImplementation := mload(add(callData, 36))
        }
        if (newImplementation.code.length == 0) revert InvalidImplementation(newImplementation);
    }
}

Root cause: this block only runs on the executeWithoutChainIdValidation (cross-chain replayable) path and scans batched calls for upgradeToAndCall, reverting if the target implementation has no code on the current chain. It is fully redundant: Solady's UUPSUpgradeable.upgradeToAndCall (lib/solady/src/utils/UUPSUpgradeable.sol:83-93) already staticcalls proxiableUUID() on the new implementation and reverts UpgradeFailed() when it returns anything other than the ERC-1967 slot — a codeless address returns empty data, so that call already fails at execution time, on every chain, with or without this loop. All 12 phase-2 agents and 2 of 6 phase-1 domain agents independently confirmed no signature-bypass, fund-theft, or privilege-escalation path through this code — every constructed attack path (short/malformed batch elements, code-existence spoofing, cross-chain address squatting) terminates in a revert, not a bypass.

Three concrete effects were verified:

  1. Bundler-rejection risk ([phase1: P1-6], corroborated by 9 phase-2 agents): newImplementation.code.length compiles to EXTCODESIZE on a calldata-derived address, executed during the ERC-4337 validation phase. ERC-7562 canonical-mempool rules restrict EXTCODE* opcodes on addresses outside the permitted entity set during validation; a strict public bundler may drop the UserOp in simulation. Unverified in general — depends on the specific bundler's ERC-7562 enforcement — but the risk is real and easy to avoid by not touching foreign code in validation at all.

  2. Out-of-bounds read on malformed input ([phase1: P1-7], corroborated by 8 phase-2 agents): matching bytes4(callData) == upgradeToAndCall.selector only guarantees callData.length >= 4; the unconditional mload(add(callData, 36)) requires >= 36. A batch element with the right selector but fewer bytes reads adjacent memory as newImplementation. Owner-signed input only (self-harm); the near-certain outcome is the same InvalidImplementation revert on a garbage address, and even were it skipped, the real upgradeToAndCall call would separately fail to ABI-decode the truncated calldata at execution.

  3. Validation-phase revert can stall the sequential replayable-nonce channel (phase-2-only — independently surfaced by 3 agents, most concretely proven by the flow-gap agent): every other failure path in this system that can result from a malformed/inapplicable op resolves at execution time, which ERC-4337 v0.6's EntryPoint catches — the sequential REPLAYABLE_NONCE_KEY nonce is still consumed, and the channel self-heals for the next queued op. This injected check is the only condition in the entire contract that reverts during validation instead. Concretely: if an owner signs a replayable batch where sequence N is upgradeToAndCall(newImpl, ...) and newImpl has no code yet on chain B, validateUserOp reverts at validation on chain B — a compliant bundler's simulateValidation never includes it on-chain, so the nonce is never consumed there, and every later-sequenced replayable op (N+1, N+2, …) is blocked behind it until newImpl is deployed on chain B. This is owner-recoverable: because EntryPoint's per-key sequence enforcement only requires a valid op at that exact (key, sequence) slot, the owner can sign and submit an alternate innocuous replayable op (e.g. a no-op addOwnerAddress targeting an existing owner scenario, or simply waiting for newImpl's deployment) to advance past the stuck slot — it is not a permanent brick, and no third party can trigger or worsen it.

Recommendation: delete the entire injected block (lines 169-183, i.e. revert to canonical upstream validateUserOp). This resolves all three effects at once: Solady's own proxiableUUID() check already blocks codeless-implementation upgrades at execution time (self-healing, nonce-consuming), the EXTCODESIZE-in-validation risk disappears, and the OOB-read surface disappears with the assembly block that caused it.

[U-3] Cross-chain replayable upgradeToAndCall guard (if kept) checks code existence, not code identity

Severity: Low
Origin: [both] — [phase1: P1-5], [phase2: agents 4, 7, 10]
Location: validateUserOp() — CoinbaseSmartWallet.sol:175-181

Root cause: the U-2 check (newImplementation.code.length == 0) only proves some code exists at the target address on the current chain — not that it is the intended CoinbaseSmartWallet implementation. Contract addresses only carry identical bytecode across chains when deployed via CREATE2 with identical initcode; a CREATE-deployed (nonce-dependent) address, or one an attacker pre-populates with unrelated code on another chain, would satisfy this check while pointing the proxy at foreign logic.

Concrete exploit walk: owner signs a replayable upgradeToAndCall(0xIMPL, initData) where 0xIMPL is legitimate on chain A (say, CREATE-deployed by a factory whose nonce differs per chain). On chain B, 0xIMPL happens to already hold unrelated code with nonzero length (attacker-controlled, or simply a different contract that landed at that address through unrelated activity). Replaying the signed op on chain B passes this check and upgrades that deployment to foreign logic. Not exploitable if the team's actual deployment process always uses CREATE2 with identical initcode across chains (same address ⟹ same bytecode by construction) — which is standard practice for this class of wallet and was not falsifiable from on-chain data alone.

Relationship to U-2: this finding is superseded if U-2's recommended fix (delete the check entirely) is applied — there would then be no validation-time upgrade guard to strengthen. Reported separately because it has a distinct implication: if the team wants to keep a validation-time cross-chain upgrade guard for other reasons, code-identity (EXTCODEHASH == expectedHash) rather than code-existence is the correct primitive.

Recommendation: if the U-2 loop is kept for any reason, verify implementation identity, not mere existence. Otherwise, moot — remove per U-2.

[U-4] Permissionless initialize(); empty/zero-address owner arrays are not rejected

Severity: Low
Origin: [both] — [phase1: P1-3], [phase2: agents 9 ("reinitialization"), 10 ("empty-owners-boundary")]
Location: CoinbaseSmartWallet.initialize() — CoinbaseSmartWallet.sol:127-133; MultiOwnable._initializeOwners() — MultiOwnable.sol:213-228

Root cause: initialize has no caller restriction, gated only by nextOwnerIndex() != 0 (verified at CoinbaseSmartWallet.sol:128). initialize([]) is accepted (the owner-add loop simply runs zero times) and leaves nextOwnerIndex==0 — the wallet is left un-owned yet permanently re-initializable, since the guard never trips.

Concrete exploit walk: (a) if a proxy is ever deployed without initialize bundled atomically in the same transaction as deployment, any address can front-run initialize(attackerOwners) and seize the wallet before the legitimate owner's call lands — standard uninitialized-proxy risk, mitigated entirely by the deploying factory's atomicity (this proxy was deployed via LibClone.deployERC1967, which itself provides no atomicity guarantee — that responsibility sits in the calling factory, out of scope here and not independently verified). (b) a buggy/malicious factory calling initialize([]) leaves a silently un-owned, still-reinitializable wallet with no on-chain signal beyond an absent owner-added event.

Recommendation: reject empty owner arrays (and address(0)/zero-pubkey entries, see U-12) in initialize/_initializeOwners. Verify the actual deploying factory's transaction bundles deployment and initialization atomically.

[U-5] Flat single-owner authority — no threshold, no timelock (design note, re-examined and downgraded)

Severity: Low (demoted from phase 1's Medium — see reasoning)
Origin: [phase1: access-control]
Location: MultiOwnable._checkOwner() — MultiOwnable.sol:271-277; _authorizeUpgrade — CoinbaseSmartWallet.sol:352

Root cause: every privileged function (addOwner*, removeOwnerAtIndex, execute, executeBatch, upgradeToAndCall) accepts any single registered owner — no m-of-n threshold, no timelock, no veto for co-owners. A single compromised owner key can unilaterally evict every other owner and take full control.

Re-examination / demotion reasoning: this is not a coding defect but the documented, intentional trust model of Coinbase Smart Wallet — "multi-owner" here means multiple equally-privileged keys (e.g. one per device), not an m-of-n multisig. A threshold requirement would be a product-design change, not a bug fix, and the exploit precondition ("attacker already controls one of your registered owner keys") is equivalent to full compromise for any single-signer credential scheme, not something specific to this contract. Downgraded from the phase-1 domain agent's Medium to Low: documentation/UX note, not a vulnerability.

Recommendation: document the equal-trust model explicitly for integrators and end users so they understand that adding a co-owner is equivalent to giving that key full control.

[U-6] Unconstrained, instantly-effective upgradeability

Severity: Low
Origin: [phase1: access-control, erc4337, proxies]
Location: _authorizeUpgrade() — CoinbaseSmartWallet.sol:352; canSkipChainIdValidation() — CoinbaseSmartWallet.sol:281-292

Root cause: _authorizeUpgrade is a bare onlyOwner with no timelock or implementation allow-list. upgradeToAndCall.selector is in canSkipChainIdValidation's allow-list, so a single owner signature upgrades the account on every chain sharing that signature, immediately.

Recommendation: consider a timelock or implementation allow-list for upgrades if stronger guarantees are desired; otherwise document the total-upgradeability trust assumption.

[U-7] Replayable ops carry no validUntil/validAfter — valid on every chain, forever, resubmittable by anyone (re-examined, downgraded)

Severity: Low (demoted from phase 1's Medium — see reasoning)
Origin: [phase1: erc4337]
Location: validateUserOp() — CoinbaseSmartWallet.sol:151-153, 161-188; getUserOpHashWithoutChainId() — CoinbaseSmartWallet.sol:263-265

Root cause: per the NatSpec at CoinbaseSmartWallet.sol:151-153 and verified in the code, validationData always encodes validUntil=0, validAfter=0 (indefinite). getUserOpHashWithoutChainId drops block.chainid from the signed digest. A replayable-path UserOp is valid on every chain sharing the wallet's address, forever, and — because a submitted signed UserOp becomes publicly visible — resubmittable by any third party (sender is still bound via UserOperationLib.hash, confining this to the same wallet address, but not to a chain or time window).

Re-examination / demotion reasoning: this is explicit, NatSpec-documented canonical behavior, not an implementation defect — the comment at line 151-153 states the indefinite validity outright. The content of any such op was owner-authorized to begin with; a third party can only relay it faster/wider than the owner intended, not forge new authority. Downgraded to Low: a documentation/expectation-setting matter, not a vulnerability, consistent with the treatment of U-5.

Recommendation: make this an explicitly documented, load-bearing invariant in user-facing materials ("a replayable signature authorizes its content on every chain, forever, until executed"). Consider validUntil support or an owner-controlled replay-epoch nonce if bounding is later desired.

[U-8] WebAuthn passkey verification accepts user-presence only (requireUV: false)

Severity: Low
Origin: [phase1: signatures, erc4337]
Location: _isValidSignature() — CoinbaseSmartWallet.sol:342

Root cause: WebAuthn.verify({..., requireUV: false, ...}) enforces only the User-Present (UP) bit, not User-Verified (UV — biometric/PIN). Challenge binding (abi.encode(hash)) is correctly verified.

Recommendation: if passkeys are intended as a strong factor, set requireUV: true and provision credentials accordingly, or document that current passkey security reduces to device-possession.

[U-9] secp256k1 signature malleability not rejected (accepted design)

Severity: Info
Origin: [phase1: signatures]
Location: _isValidSignature() — CoinbaseSmartWallet.sol:334, via Solady SignatureCheckerLib.isValidSignatureNow

Root cause: Solady's SignatureCheckerLib does not enforce canonical low-s; both (r,s,v) and (r, n-s, v^1) validate for the same signer. Not exploitable for replay/double-spend within these contracts — ERC-4337 nonce uniqueness is EntryPoint-managed, not signature-keyed.

Recommendation: document for any external infrastructure that might deduplicate by raw signature bytes instead of (sender, nonce).

[U-10] Index-based owner removal is fragile to cross-chain owner-set divergence (confirmed self-healing on re-examination)

Severity: Low
Origin: [both] — [phase1: signatures], [phase2: agent 11 — "cross-chain-owner-desync"]
Location: removeOwnerAtIndex/removeLastOwner — MultiOwnable.sol:121-144, 253-263; replay path CoinbaseSmartWallet.sol:163-167

Root cause: owner removal is keyed by index, matched against keccak256(owner_) != keccak256(owner) (MultiOwnable.sol:256). If owner sets diverge across chains (different add/remove ordering or timing), a replayed removal targeting a stale index either removes the wrong entry — blocked by the hash-match revert (independently confirmed by phase-2 agent 11) — or reverts outright, consuming the sequential replayable nonce on that chain and stalling subsequent replayable ops there (the same self-healing/owner-recoverable class of issue as U-2's stall mechanic).

Recommendation: consider keying replayable owner-removal by owner-bytes rather than index, or document the cross-chain ordering-discipline requirement.

[U-11] validateUserOp reverts rather than returning the 1 sentinel on malformed signature-format input

Severity: Low
Origin: [both] — [phase1: erc4337], [phase2: agent 12 — "sim-affordance"]
Location: _isValidSignature() — CoinbaseSmartWallet.sol:319, 326, 340, 345

Root cause: ERC-4337 convention is that signature-format failures return 1 (SIG_VALIDATION_FAILED) for clean bundler simulation; only structural/protocol violations should revert. Here, malformed SignatureWrapper encoding, out-of-range ownerIndex, mismatched owner-bytes length, or invalid WebAuthn auth encoding all revert the entire call instead.

Recommendation: wrap decode/owner-lookup paths so recoverable signature-format issues return 1; reserve reverts for nonce-key/selector routing violations.

[U-12] addOwnerAddress/addOwnerPublicKey accept zero-value owners with no sanity check

Severity: Low
Origin: [phase1: access-control, signatures]
Location: MultiOwnable.sol:101-111, 236-244

Root cause: neither addOwnerAddress(address(0)) nor addOwnerPublicKey(0,0) is rejected. Confirmed not exploitable for signature forgery — Solady's SignatureCheckerLib.isValidSignatureNow short-circuits on a zero signer (the for { signer := ... } signer {} guard, independently re-confirmed by phase-2 agents 2 and 8 by direct inspection of SignatureCheckerLib.sol:40). Residual risk is an accounting/UX footgun: a dead address(0) owner consumes an index and inflates ownerCount(), interacting with U-1/U-4.

Recommendation: require owner != address(0) in addOwnerAddress/_initializeOwners; require !(x==0 && y==0) in addOwnerPublicKey.

Refuted / considered and dismissed

  • Zero-address owner → ecrecover-to-zero signature bypass: refuted independently by phase-1 (SIG-4) and phase-2 (agents 2, 8) — SignatureCheckerLib's zero-signer guard blocks this structurally.
  • MultiOwnable counter overflow (nextOwnerIndex++/removedOwnersCount++, phase-2 agent 1): refuted — uint256 overflow requires ~2^256 owner operations, not reachable.
  • Memory-vs-calldata ABI decode divergence between validateUserOp's in-memory re-decode and executeWithoutChainIdValidation's calldata decode (phase-2 agent 9): refuted — both are strict Solidity 0.8 ABI decoders that revert identically on malformed input; no divergent-interpretation encoding was constructed.
  • Implementation contract direct initialization/upgrade/self-destruct: refuted — constructor seeds owner[0]=address(0) (CoinbaseSmartWallet.sol:113-118), permanently failing initialize()'s guard on the implementation itself; Solady's onlyProxy modifier additionally blocks direct upgradeToAndCall calls on the implementation.
  • Storage collision across MultiOwnable (ERC-7201), the ERC-1967 implementation slot, and stateless ERC1271: refuted — all namespaced/hashed slots, no sequential storage overlap.
  • Self-call (address(this)) privilege escalation: refuted — execute/executeBatch are onlyEntryPointOrOwner; no path lets an externally-called target re-enter them as a non-owner, non-EntryPoint caller.
  • ERC-1271 replay-safe hash / EIP-712 domain separator caching bugs: refuted — chainId + address(this) are bound fresh on every call, no caching.
